# 代码说明

## 一、项目到底做什么

这个项目把 PDF 里的文字变成“可以搜索的知识”。用户提问时，程序先从知识库找出相关片段，再把这些片段交给本地大模型生成答案。

这就是 RAG（Retrieval-Augmented Generation，检索增强生成）：

1. **Retrieval：检索**——从知识库找依据。
2. **Augmented：增强**——把找到的片段放进提示词。
3. **Generation：生成**——模型根据片段组织自然语言答案。

程序的核心原则是：模型只能依据检索片段回答，找不到依据就拒答，避免凭空编造。

## 二、目录含义

| 路径 | 含义 |
|---|---|
| `backend/server/` | FastAPI 服务入口（包）：`__init__.py` 装配应用，`routes_*` 按业务分组，`answer.py` 负责生成与引用 |
| `backend/pipeline/` | 离线构建管线（包）：pdf_parse / text_clean / chunking / vectors / build |
| `backend/retrieval/` | 在线混合检索（包）：query / bm25 / recall / fusion / rerank / context |
| `static/index.html` | 不依赖前端框架的网页界面 |
| `data/pdfs/` | 上传的原始 PDF |
| `Milvus/rag_docs_v6` | 知识库向量集合 |
| `data/documents.json` | 文档登记信息，例如页数、chunk 数、构建时间 |
| `eval/` | 检索评测脚本和评测数据 |
| `tests/` | 自动化测试 |

## 三、`pipeline/`（构建管线）：文档如何进入知识库

### 1. `milvus_client()`

创建并复用 Milvus 客户端，连接 `MILVUS_URI`，并确保 `rag_docs_v6` 集合、1024 维 COSINE 索引和加载状态就绪。Milvus 是独立服务，需要先启动 Docker Compose 中的 standalone、etcd 和 minio。

### 2. `parse_pdf()`

选择 PDF 解析器：

- 默认先尝试 MinerU，适合表格、版面和公式较复杂的 PDF。
- MinerU 没安装、运行失败，或者设置 `RAG_PARSER=pypdf` 时，使用 pypdf。

解析结果统一成：

```python
[{"page": 1, "text": "第 1 页文字"}, ...]
```

统一格式后，后面的清洗和分块代码就不需要关心 PDF 来自哪个解析器。

### 3. `normalize_text()` 和 `clean_text()`

这两个函数负责清洗原始文本：

- 把不同的破折号统一。
- 把 `SF 6` 统一为 `SF6`。
- 把 `GB / T 44653 - 2024` 统一为 `GB/T 44653-2024`。
- 删除页眉、页脚、目录点线、纯数字等噪声。
- 合并不必要的空格。

清洗的目的不是让文字好看，而是让同一个术语以同一种形式进入检索系统。

### 4. `keep_body_pages()`

许多标准 PDF 前面有封面、目录和说明。这个函数从“1 范围”开始保留正文；如果找不到这个标题，就保留原文，避免误删内容。

### 5. `chunk_pages()`

把长文档切成较小的片段：

- 优先识别类似 `1 范围`、`3.2 设备要求` 的章节标题。
- 每块大约 400 个字符。
- 超长文本硬切时保留 40 个字符重叠，避免一句话正好被切断。
- 给每块分配 `chunk-000`、`chunk-001` 这样的编号。

分块太大，问题会被无关内容淹没；分块太小，上下文会断裂。这里的 400 和 40 是简单、容易调整的工程参数。

### 6. `embed()`

调用 Ollama 的 `/api/embed` 接口，让 `bge-m3` 把每个 chunk 转成数字数组：

```text
"设备应具备净化功能" → [0.012, -0.084, ...]
```

文本不能直接进行向量相似度计算，所以必须先向量化。

### 7. `store_chunks()`

把向量和原始信息一起写进 Milvus。每条记录包括：

- `vector`：用于语义检索。
- `source`：来源文件名。
- `page`：页码。
- `section`：章节。
- `text`：chunk 原文。
- `chunk_id`：分块编号。

查询命中后，程序就能同时返回“内容”和“出处”。

### 8. `build_pipeline()`

这是离线构建总入口，顺序固定为：

```text
parse_pdf
  → clean_text / keep_body_pages
  → chunk_pages
  → embed
  → delete_document_vectors / store_chunks
```

同名 PDF 入库前会先删除旧向量，因此重复上传是“替换”，不会无限堆积重复数据。`progress` 回调把每一步状态交给 `server/`（构建状态定义在 `state.py`），网页才能显示进度。

## 四、`retrieval/`（检索链路）：问题如何找到答案依据

### 1. `tokenize()`

使用 jieba 分词，把中文句子拆成关键词，同时删除常见虚词、标点和纯数字。BM25 需要这些词来进行字面匹配。

### 2. `BM25`

BM25 是关键词检索算法。它会考虑：

- 查询词是否出现在文档中。
- 一个词在当前文档出现多少次。
- 一个词在整个语料中是否稀有。
- 文档长度对分数的影响。

它特别适合标准编号、专业术语和条款名称。比如用户明确输入 `GB/T 44653-2024` 时，BM25 能补足纯向量检索可能漏掉的结果。

### 3. `normalize_query()` 和 `rewrite_query()`

查询改写把口语问题变成更适合检索的术语。例如：

```text
SF6 净化装置有哪些功能？
→ SF6 净化处理装置 过滤 干燥 吸附 低温冷却 精馏 功能 六氟化硫
```

这是规则改写，不调用大模型，速度快、结果可解释。

### 4. `dense_hits()`

把问题向量化，然后到 Milvus 查询最相似的 20 个 chunk。它理解语义相近但字面不同的表达，例如“回充设备”和“气体重新充入装置”。

### 5. `keyword_hits()`

用 BM25 对整个语料打分，取前 20 个结果。它更重视字面相同的词。

### 6. `rrf_merge()` 和 `fuse_hits()`

向量分数和 BM25 分数不是同一套尺度，不能直接相加，所以使用 RRF（Reciprocal Rank Fusion）：

```text
RRF 分数 = 1 / (60 + 排名)
```

关键词路乘以 2.5，因为标准文档中的精确术语很重要。两路都命中的片段通常会排得更靠前，只命中一路的有价值片段也不会被完全丢掉。

### 7. `rerank()`

把融合后的候选片段交给 `qwen2:7b`，要求模型只输出 `编号:分数`，例如：

```text
1:5
2:3
3:1
```

程序解析分数后重新排序。如果 Ollama 不可用或模型输出格式错误，就回退到 RRF 顺序，不让一次精排失败拖垮整个检索流程。

### 8. `organize_context()`

生成答案前做三件事：

- 去除重复片段。
- 丢弃明显低分的候选。
- 控制总字符数，防止提示词过长。

它还为每个片段增加 `snippet`，供问答模型使用。

### 9. `retrieve_with_trace()`

这是检索总入口，按顺序调用：

```text
查询改写
→ 语义召回
→ 关键词召回
→ RRF 融合
→ 候选精排
→ 上下文组织
```

每一步都会记录 `step`、`status`、`detail` 和耗时 `ms`。这些 trace 数据既能用于调试，也能显示在网页的“检索链路”页面。

## 五、`server/`（服务与接口）：接口和业务流程

### 上传 `/api/upload`

1. 校验文件名和扩展名。
2. 把 PDF 保存到 `data/pdfs/`。
3. 启动后台线程执行 `build_pipeline()`。
4. 立即返回，避免浏览器一直等待。
5. 前端轮询 `/api/build/status` 获取进度。

### 检索 `/api/search`

只调用 `retrieve_with_trace()`，把候选片段、最终结果和 trace 返回给前端，方便观察“为什么命中这些内容”。

### 问答 `/api/ask`

1. 先检索。
2. 把片段拼成上下文。
3. 调用 Ollama 的 `/api/chat`。
4. 返回答案和引用。

### 流式问答 `/api/ask/stream`

使用 SSE 格式返回多条事件：

```text
start → trace → retrieval_done → answer → done
```

当前版本按事件返回；它的重点是让前端能展示处理阶段，而不是把模型输出拆成单字。

### 知识库接口

- `kb_overview()`：扫描 Milvus，统计真实 chunk 数。
- `kb_chunks()`：按 `source` 过滤，返回某文档的 chunk 明细。
- `delete_document()`：同时删除 Milvus 记录、登记信息和原始 PDF，避免留下脏数据。

### 角色扮演接口

`server/` 还恢复了 `/api/roleplay/*` 路由（见 `routes_roleplay.py`）：

- `GET /api/roleplay/roles`：列出内置角色和自定义角色。
- `POST /api/roleplay/roles`：保存自定义角色。
- `POST /api/roleplay/sessions`：新建会话。
- `GET /api/roleplay/sessions`：查看某个用户的会话列表。
- `GET /api/roleplay/sessions/{session_id}/messages`：查看会话历史。
- `POST /api/roleplay/chat`：执行一次角色聊天。

## 六、`roleplay/`（角色扮演）：角色扮演如何工作

角色扮演不是单独的大系统，而是在 RAG 主链路上加了“角色”和“记忆”。

### 1. 角色

角色保存在 SQLite 的 `roles` 表中。每个角色包含：

- `persona`：角色是谁。
- `style`：怎么说话。
- `safety_notice`：安全边界。
- `knowledge_sources`：可选，限制只引用某些文档。

默认保留了虚拟朋友、智能客服、医生、学习教师和奇幻 NPC。

### 2. 会话和短期记忆

`users`、`sessions`、`messages` 三张表保存用户、会话和消息。最近若干轮对话会放进提示词，形成短期记忆。

### 3. 长期记忆

用户消息会向量化后写入 Milvus 的 `roleplay_memories` 集合。下一次聊天时，程序用当前问题检索同一用户、同一角色下的历史记忆。

这部分只用 Milvus 存储长期记忆，SQLite 存储角色、会话和短期消息。

### 4. `chat()` 主流程

一次角色聊天的步骤是：

```text
校验消息和角色
→ 找到或创建会话
→ 保存用户消息
→ 调用 retrieve_with_trace 检索知识库
→ 读取短期历史和长期记忆
→ 拼角色提示词
→ 调 Ollama 生成回答
→ 清理输出并补引用
→ 保存助手消息
→ 保存长期记忆
```

如果本地模型不可用，会返回一个 fallback 答案，不会编造内容。

## 七、`static/index.html`

这是原生 HTML、CSS 和 JavaScript 页面，没有 React、Vue 或 CDN：

- “文档构建”调用上传和状态接口。
- “知识库”调用统计、chunk 和删除接口。
- “检索”展示查询改写、两路召回、RRF 和最终结果。
- “问答”读取 SSE 事件，展示答案和引用。

`fetchJson()` 统一处理 HTTP 请求和错误；`escapeHtml()` 防止把文档内容直接插入 HTML 时产生脚本注入。

## 八、一次提问的完整例子

用户输入：

```text
SF6 气体净化装置有哪些功能？
```

程序执行：

1. 规范化 `SF6` 写法。
2. 扩展“过滤、干燥、吸附、低温冷却、精馏”等术语。
3. 向量路找语义相近片段。
4. BM25 路找精确出现这些术语的片段。
5. RRF 合并排名。
6. qwen2:7b 给候选打相关性分数。
7. 选出不超过 3600 字符的上下文。
8. qwen2:7b 根据上下文回答。
9. 返回文件名和页码引用。

## 九、为什么这个版本更容易学习

原项目包含 Redis、MySQL、多个可选 PDF 解析器和 BGE 精排等生产扩展。当前版本保留 Milvus 作为统一向量后端，其他组件仍按需启用。

当前版本保留两条清晰主线：

```text
PDF 入库 → 混合检索 → 引用问答
角色提示词 → SQLite 会话 → Milvus 长期记忆 → 角色回答
```

也就是说，角色扮演恢复了，但只保留本地 SQLite + Milvus 的简单实现。
