# Query 理解优化：多轮对话（工单 05）

**工单编号：人工智能NLP-RAG-Query理解优化**
（工单 PDF 原文：`人工智能NLP-RAG-Query 理解优化任务`）

在工单 03 的招股说明书问答系统之上，本工单加的是**多轮对话能力**：

> 用户不再一次把问题问完整，而是用「**他**」「**这个公司**」「**那 XX 公司呢**」连续追问。
> 系统必须结合对话历史，先把这些短问题**补全成完整独立问题**，再走原有的检索与生成。

| 轮次 | 用户问题 | 标准答案 | 考察能力 |
| --- | --- | --- | --- |
| Q1 | 报告期内，武汉兴图新科电子股份有限公司来自军用领域的收入分别是多少？ | 4 个年度数字 | 表格检索 |
| Q2 | **他**参与的哪个工程荣获了国家科技进步一等奖？ | 某情报、指挥、控制与通信网络一体化工程 | **指代消解** |
| Q3 | **这个公司**的法定代表人是谁？ | 程家明 | **指代消解** |
| Q4 | **那武汉力源信息技术股份有限公司呢？** | 赵马克 | **话题切换 + 省略补全** |
| Q5 | 武汉力源信息技术股份有限公司组织结构图中，**哪个销售部的销售处最多？有哪些销售处？** | 大客户销售部 + 6 个销售处 | **图结构解析** |

### 实测结果（本机 RTX 4060 Laptop）

**① 5 轮验收序列**（`python run_acceptance.py`）——**5/5 逐轮全对**，最大耗时 **1998ms**，全部 ≤3 秒：

| 轮次 | 改写方式 | 独立问题 | 耗时 |
| --- | --- | --- | --- |
| Q1 | `passthrough` | （完整问题，直通不改写） | 1818ms |
| Q2 | `coref_llm` | 武汉兴图新科电子股份有限公司参与的哪个工程荣获了国家科技进步一等奖？ | 1998ms |
| Q3 | `coref_llm` | 武汉兴图新科电子股份有限公司的法定代表人是谁？ | 1096ms |
| Q4 | `ellipsis_llm` | 武汉力源信息技术股份有限公司的法定代表人是谁？ | 1240ms |
| Q5 | `passthrough` | （完整问题，直通不改写） | 1360ms |

> 上表是 `data/eval/acceptance_result.json` 里**最近一次运行**的实测值（逐轮明细与全文本见
> `docs/06-验收序列逐轮报告.md`）；耗时逐次运行有几十到一两百毫秒的正常波动。

**② 20 轮三方对比**（`python evaluate_multiturn.py`，10 个会话 / 11 类指代）：

| 指标 | **工单5 多轮** | 工单3 单轮（优化前） | 纯 LLM |
| --- | --- | --- | --- |
| **事实命中率** | **0.9062** | 0.8125 | 0.0 |
| 改写准确率（严格） | 0.9474 | n/a | n/a |
| 指代实体准确率 | **1.0** | n/a | n/a |
| 无候选反问率 | 1.0 | n/a | n/a |
| p50 / p90 耗时 | 1301.5 / 2407.1 ms | 1013.9 / 1398.5 ms | 207.4 / 444.6 ms |
| ≤3s 占比 | **1.0** | 1.0 | 1.0 |

**按指代类型看增益**（这是本工单价值最直观的证据）：

| coref_type | 工单5 多轮 | 工单3 单轮 |
| --- | --- | --- |
| 指示代词·英文（this company） | 0.0 ᵃ | **0.0** |
| 指示代词·「该公司」 | **1.0** | **0.0** |
| 省略·话题切换（那 XX 呢） | **1.0** | **0.0** |
| 省略·英文（What about X?） | 0.0 ᵃ | **0.0** |
| 人称代词（他 / he） | 1.0 | 1.0 |
| 零指代 / 话题回指 | 1.0 | 1.0 |

> ᵃ 这两轮的**指代实体准确率仍是 1.0**（`this company`→武汉力源、`What about …?`→武汉兴图新科，
> 一个没错），失分来自英文作答时 3B 把中文人名**音译**（赵马克→"Zhao Mark"），
> 事实匹配按中文原名判。详见 `docs/03` §四 第 5 条与 `docs/技术文档.md` §10 第 10 条。

> 单轮系统为什么有些指代题也不输？因为工单3 把「该公司/其/公司」**硬编码替换成第一家公司**，
> 指代恰好指向第一家时被它"蒙对"；一旦换成第二家公司或英文，**四类全线 0.0**。
> 更糟的是它会**答错还理直气壮**：问力源的控股股东，单轮系统答成了兴图新科的程家明。
> 详见 `docs/03-优化前后对比分析.md` 第 3.1 节。

**③ RAGAS**（`python evaluate_ragas.py`，本机离线裁判）：
14 道必测题 `context_recall = 1.0`；5 轮验收序列 `context_recall = 1.0`（见 `docs/04`）。

> **硬约束**：全流程只使用本机已下载的模型（qwen2.5:3b / qwen2.5:0.5b / bge-m3 /
> bge-reranker-v2-m3 / PaddleOCR-VL），任何环节都不触发模型下载。

## 系统架构

**多轮问答主链路**（★ = 本工单新增/改造）：

```
用户追问（中文/英文）
   │
   ├─ dialogue ★新   对话状态：焦点公司 focus_company + 上一信息点 last_aspect
   │                 历史：全量留痕 / 送 LLM 的滑动窗口（3 轮）/ 超窗压成摘要
   │
   └─ coref ★新      四层消解（逐层降级，永不静默失败）
        L0 直通判定    已点名公司 / 无代词的完整问句 → 原样放行（零开销）
        L1 规则检测    定位代词与省略的 span + 候选实体
        L2 实体判定    qwen2.5:0.5b 在候选集内二选一（唯一候选时跳过）
        L3 生成        qwen2.5:3b 生成独立完整问题
            └─ 校验器 6 条不过 ─┐
        L4 规则兜底    ◄────────┘ 确定性模板（保证一定有可用的问题）
            无候选实体 → unresolved：明确反问，**不猜**
   │
   ▼  改写后的独立问题
【工单3 原有链路】doc_router 文档路由 → 混合检索（向量+BM25→RRF）
   → bge-reranker 精排 → context 组装（表格还原整表 / 组织结构图注入子树）
   → qwen2.5:3b 生成 + 三重校验重试 + 抽取式降级
   │
   ▼
答案 + [n] 引用（哪份 PDF / 哪一页 / 表格行 / **组织结构图节点路径**）+ 分阶段耗时
```

**离线侧新增**：组织结构图（招股2 第 39 页）是**矢量绘制**，用 PyMuPDF 读取 29 个节点框 +
36 条连线，按「总线规则 / T 型接头 / 二框几何定向」重建层级树，
校验 29 节点 / 28 边 / 单根（不满足即抛错），再增量入到工单5 自己的 collection。

**关键设计**：

- **不做端到端自由改写**：实测 3b 会把「他」换成「这个公司」（代词换代词的无效替换），
  0.5b 会把指令原样吐回。改拆成**受约束子任务**（判定 / 填空 / 模板补全）后两个模型都可靠——
  这是本工单最重要的选型依据，实测数据见 `docs/05` 第二节。
- **缓存 key 含「改写后问题 + 焦点公司」**：同一句「他参与的哪个工程获奖了？」
  在不同会话里指不同公司，沿用旧 key 会让答案串味。
- **删掉工单3 硬编码的消歧**：那是单文档时代的产物，多文档下会答成另一家公司。

## 多轮专项：为什么这样设计

| 工单要求 | 本项目实现 |
| --- | --- |
| 维护对话历史 | `DialogueState`（全量留痕 + 焦点公司 + 上一信息点 + 会话表 LRU） |
| 每轮先补全成独立问题 | `coref.resolve` 四层消解，改写后的问题才进检索 |
| 历史长度控制 | 滑动窗口 3 轮 + 超窗摘要 + 单会话 50 轮上限 |
| 指代消解 | 人称/指示/零指代；中英文各一套词表与提示词 |
| 省略补全 | 「那 X 呢」→ 实体换成 X + 信息点继承 `last_aspect` |
| 话题切换 | 点名新公司即更新焦点，旧焦点不残留 |
| LLM 做 Query Rewriting | L2 判定（0.5b）+ L3 生成（3b），提示词见 `docs/05` 第四节 |
| 容错：指代无法解析 | `unresolved` + 明确反问：**不猜** |
| ≤3 秒 | 逐轮实测全达标；**未降低检索质量换延迟**（Top-K 与重排配置未动） |

**两个实测失败模式已固化成回归测试**（`tests/test_coref_resolve.py`）：
① 3b 把「他」换成「这个公司」（代词换代词）；② 0.5b 把指令原样吐回（复述指令）。
**第三个是跑评测才发现的**：3b 塞进一个不存在的公司名（Microsoft）并吃掉原文的 "the"，
旧校验器全票放行、导致检索 0 命中——现已由「最小编辑」校验拦住（见 `docs/05` 第 3.3 节）。
