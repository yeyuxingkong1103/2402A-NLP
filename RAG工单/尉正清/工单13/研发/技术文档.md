## 四、核心实现要点

### 1. 阶段埋点支持嵌套，并自检「有没有漏测」

`perf.stage()` 记录 `depth`，所以「检索」和它内部的「稀疏打分」能区分开。
每条 trace 额外算 `unaccounted_seconds = 总耗时 − 顶层阶段之和`，
实测 0.0% —— 埋点没有盲区。

开销：`time.perf_counter()` 是纳秒计数器，远小于被测量的毫秒级阶段，
不会扭曲结论（这点和 cProfile 不同）。

### 2. 连接复用至少要按线程隔离

`requests.Session` **不是线程安全的**。uvicorn 把同步端点丢进线程池执行，
所以用 `threading.local()` 让每个线程各持一个 Session ——
连接池按线程独立维护，线程数固定，不会无限增长。

### 3. 稀疏打分的倒排索引

**优化前**：对每篇文档遍历查询词 ——
`score[d] = Σ_t q[t] × doc[d].get(t, 0)`，7,009 篇 × 每篇十余次字典查找。

**优化后**：建 `term → {文档下标: 权重}` 的倒排表，只遍历查询词命中的文档。
复杂度从 O(文档数 × 查询词数) 降到 O(各查询词倒排链长度之和)。

**顺带解决并发退化**：原实现是纯 Python 双重循环、全程持 GIL，
并发时请求互相排队（8 并发下检索段从 0.4s 涨到 2.4s）。

### 4. 关掉推理模型的思维链

`deepseek-flash` 的 `reasoning_content` 与 `content` **共用 `max_tokens`**：
额度被吃光时正文返回**空串且 HTTP 仍是 200**。而且思考长度随问题波动极大，
是延迟方差的主要来源。

`reasoning_effort: none` 走请求体的原始字段（**不能**用 OpenAI SDK 的具名参数，
那个会被 SDK 按 OpenAI 类型校验拦下，官方取值只认 low/medium/high）。

### 5. 启动预热

不在启动时打一枪，**第一个真实用户**要替整个进程付 CUDA 上下文初始化的账
（实测首请求 9.68s vs 稳态 0.4s）。预热把这份成本挪到启动阶段（实测 2.7s）。

## 五、使用方法

```bash
# 起服务（启动时自动预热）
D:/Anaconda/envs/rag_gd/python.exe 研发/api.py --port 8000

# 单次提问
curl -X POST http://127.0.0.1:8000/query \
     -H "Content-Type: application/json" \
     -d '{"question":"平安银行2019年末的拨备覆盖率是多少？"}'
# 返回：request_id / retrieve_seconds / elapsed / recall_count / stages

# 或一键跑完整对比
bash 部署/start.sh
```

**优化开关**（对比复现用）：

```bash
# 回到优化前
PERF_OPT=off LLM_REASONING_EFFORT= D:/Anaconda/envs/rag_gd/python.exe 研发/api.py
```

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 高并发下延迟仍会涨 | 并发 8 之后吞吐封顶 —— 瓶颈在**外部大模型服务**的限流，本地优化改变不了 |
| cProfile 的绝对耗时不可用 | 插桩放大 7 倍（实测）；只用于定位热点函数 |
| 阶段埋点覆盖单进程 | 本系统是单体；若将来拆成微服务，需要补分布式追踪 |
| `PERF_OPT=off` 只为对比 | 生产环境不要设它，关了会慢 3.7 倍 |
