## 1. document.py — 文档处理

### `load_pdf(pdf_path) -> (list, list)`

解析 PDF，返回文字页列表与表格块列表。

| 参数 | 类型 | 说明 |
|---|---|---|
| `pdf_path` | str \| Path | PDF 文件路径 |

**返回**：`(text_pages, table_blocks)`

```python
text_pages   = [{"page": 22, "text": "中文名称 武汉兴图新科电子股份有限公司 ..."}]
table_blocks = [{"page": 221, "table": "| 项目 | 2018年度 |\n| --- | --- |\n..."}]
```

### `parse_pdf_tables(pdf_path) -> list[dict]`

只解析表格，转成 Markdown 字符串。

### `split_text(text, chunk_size=500, overlap=80) -> list[str]`

固定长度滑窗切分，优先在换行处断开（避免把金额数字切成两半）。

> 若 `overlap >= chunk_size` 会自动收敛为 `chunk_size - 1`，防止步长非正造成死循环。

### `build_chunks(text_pages, table_blocks) -> list[dict]`

合并为带页码与类型的块。

```python
[{"text": "...", "page": 22, "type": "text"},
 {"text": "| 项目 | ...", "page": 221, "type": "table"}]
```

---

### `parse_pdf_tables(pdf_path, junk_lines=()) -> list[dict]`

抽取表格并转成 Markdown，**同时带上表格上方的标题**。

```python
[{"page": 157,
  "caption": "(一)关联方及关联关系 1、存在控制关系的关联方",
  "table": "| 关联方名称 | 持股比例 | 与本公司关系 |"}]
```

> 工单3 的核心：表格单元格里没有「关联方」这个词，它在标题里。不带标题的表格块
> 会被文档里其它同类表格淹没。`junk_lines` 是页眉页脚行集合，由 `load_pdf` 传入。

### `company_name(pdf_path, head_pages=3) -> str`

从 PDF 开头几页提取发行人公司名（出现次数最多的「XX股份有限公司」），用于多文档路由。

## 1.5 image_parser.py — 图像内容解析（工单4 新增）

### `chart_pages(pdf_path, min_side=250) -> list[int]`

挑出含图表的页：有较大位图的页、出现「结构图/示意图/如下图」字样的页，
**以及这些页的下一页**（图常被放在引言之后）。返回页码升序列表。

### `describe_page(pdf_path, page_no, retry=2) -> str`

把该页渲染成 PNG，交给多模态模型转写成文字（组织结构图写层级、统计图写数值与极值）。

### `parse_pdf_images(pdf_path, limit=40, progress=None, cache_dir=None) -> list[dict]`

带缓存的入口。返回可直接入库的块：

```python
[{"page": 39, "type": "image", "text": "【第39页 图表】销售部下属：电话及网络销售部……"}]
```

> 缓存按**页**增量维护（落在知识库缓存目录的 `*_images.json` 里）。选择规则变宽或某页
> 因网络抖动失败时，重跑只补解析缺的页 —— 实测约 18 秒/页，全量重跑代价高。

## 1.6 dialogue.py — 多轮对话（工单5 新增）

### `Conversation(companies=None)`

一次会话的上下文。`companies` 是已加载文档对应的公司名 —— 主体识别只认这些，
避免把「国信证券股份有限公司」这类中介机构当成提问主体。

| 方法 | 说明 |
|---|---|
| `.resolve(question)` | 把带指代/省略的问句改写成自足问题，返回 `{"resolved", "strategy", "company"}` |
| `.add_turn(question, resolved, answer)` | 记录一轮对话 |
| `.reset()` | 清空上下文（界面「清空对话」按钮调用） |
| `.size` | 已记录轮数 |
| `.current_company` | 当前话题主体 |

改写策略按优先级：

| 优先级 | 策略 | 例子 |
|---|---|---|
| ① | 省略补全 | 「那武汉力源…呢？」→「武汉力源…**的法定代表人是谁**？」 |
| ② | 原样 | 问题已点明公司名 |
| ③ | 指代消解 | 「**他**参与的哪个工程…」→「**武汉兴图新科…**参与的哪个工程…」 |
| ④ | 话题延续 | 既无公司名也无代词时补上当前主体 |

## 1.7 fulltext.py — 全文检索（工单6 新增）

### `FullTextIndex(title_weight=2.0, body_weight=1.0)`

倒排索引。中文用字符二元组建索引，无需分词库。

| 方法 | 说明 |
|---|---|
| `.build(chunks)` | 建索引；每块拆成「标题」（表格/图像块取题注，文本块取首行）与「正文」两路 |
| `.search(query, top_k, mode="and", fuzzy=0, phrase=True)` | 检索 |

查询语法：

| 类型 | 写法 | 说明 |
|---|---|---|
| 布尔 | `军用 AND 收入`、`-民用`、`!排除` | AND / OR / NOT |
| 短语 | `"军用领域"` | 引号内整串匹配，命中额外加权 |
| 模糊 | `注册资~1` | 编辑距离容错 |

### `tokenize(text) -> list[str]`

中文切二元组、英文切整词。

## 1.8 rerank.py — 重排算法（工单6 新增）

四种重排器，统一接口 `rerank(query, candidates, top_k) -> [(chunk, score)]`：

| 类 | 原理 |
|---|---|
| `TFIDFReranker` | 本地 TF-IDF 余弦相似度，毫秒级 |
| `FeedbackReranker` | 按 `feedback.jsonl` 里的 👍/👎 加权减权，调整幅度设上下限 |
| `LLMReranker` | 把候选编号交给大模型排序，最准但需一次额外调用 |
| （交叉编码器） | 见 `vector_store.rerank`，工单2 引入 |

`available()` 列出可选项，`build(name, chat, index)` 按名构造。

## 2. query_understanding.py — Query 理解

|---|---|---|

| `sub_questions` | list[str] | 拆出的子问题，拆不开则为 `[]` |
| `entities` | list[str] | 提取到的实体 |
| `numbers` | list[str] | 提取到的数字 |

### `detect_lang(text) -> str`

## 3. vector_store.py — 向量检索

### `BGEM3VectorStore(model_path=None, use_fp16=True)`

构造时加载本地 BGE-M3（自动使用 GPU，若无则回退 CPU）。

### `.build(chunks, batch_size=16) -> None`

对全部块编码，建立索引。

### `.search(query, top_k=5) -> list[tuple[dict, float]]`

混合检索。返回 `[(chunk, score), ...]`，按相关性降序。

> 融合方式为 RRF（Reciprocal Rank Fusion）：分别把稠密分与稀疏分转成名次，
> 按 `权重 / (60 + 名次)` 相加。不直接相加分数，避免两种分数量纲不同导致
> 稀疏分靠一次偶然的词汇重叠顶掉语义分。

### `.save(out_dir) -> None` / `.load(in_dir) -> bool`

知识库持久化与加载。落盘文件：`dense.npy`、`chunks.json`、`sparse.json`。

## 4. rag_engine.py — 答案生成

### `chat(prompt, system=..., temperature=0.0, max_tokens=4096, timeout=30) -> str`

大模型调用封装。

> 失败时**抛出 `LLMError`**，不返回错误文案——否则错误信息会被当成答案一路传到界面和评估模块。
>
> 空正文会自动**加大额度重试两次**（`max_tokens` 翻倍，上限 16384）。两种成因：
> ①推理模型的 reasoning token 先吃掉额度；②实测同参数偶发直接返回空串，
> 与额度无关，纯服务端抖动。工单7 一轮评估有 40+ 次调用，只重试一次不够用。

### `RAGEngine(vector_store, top_k=8, mode=..., alpha=..., rerank_name=..., timeout=None)`

| 参数 | 说明 |
|---|---|
| `timeout` | 单次大模型调用超时（秒）。缺省取 `config.LLM_TIMEOUT`（30s）；评估脚本会放宽到 120s，理由见下 |

> 评估时放宽超时是为了**公平**：纯 LLM 对照回答要跑推理，30 秒会被截断，
> 那会让 RAG 显得比实际更好。被测系统本身仍按 30 秒配置运行。

### `.retrieve(question, use_query_understanding=True) -> (hits, qu)` — 工单7 抽出

构造多路查询并召回，返回 `(召回结果, 查询理解结果)`。

| 参数 | 说明 |
|---|---|
| `hits` | `[(chunk, score), ...]` |
| `qu` | `understand()` 的原始返回 |

> 抽出来是为了让评估脚本能测到**真正在用的那条检索路径**。若另起一条
> 「只用原始问句」的简化路径去测检索，测的就不是系统真实行为——
> Query 理解会做改写和子问题拆解，对召回结果影响很大。

### `.answer(question, use_query_understanding=True) -> dict`

完整 RAG 链路（内部调用 `retrieve()`）。

| 返回字段 | 说明 |
|---|---|
| `answer` | 答案文本 |
| `contexts` | `[(chunk, score), ...]`，检索到的上下文 |
| `retrieve_seconds` | 检索段耗时（秒），工单7 新增，评估时单列 |
| `elapsed` | 端到端耗时（秒） |
| 其余字段 | 透传 `understand()` 的结果 |

### `.answer_without_rag(question) -> dict`

纯 LLM 回答，不检索。用于工单要求的对比分析。

---

### `rerank(query, candidates, top_k=8, max_chars=400) -> list`

交叉编码器重排序（`vector_store.py`）。对候选逐对打分后取前 `top_k`。

| 参数 | 说明 |
|---|---|
| `candidates` | `[(chunk, score), ...]`，来自 `search()` 的召回结果 |
| `max_chars` | 送检正文长度上限。模型只看 512 token，截断可显著提速（1.0s → 0.5s） |

> 由 `config.RERANK_ENABLED` 控制是否启用，**默认关闭**。实测在本任务的
> 财务表格上为负收益，详见 `优化/优化说明.md`。

## 5. evaluator.py — RAG 评估裁判

### `_judge(question, context, answer) -> dict`

LLM-as-Judge 打分，返回 `{"grounded": 0/1, "relevant": 0/1, "reason": str}`。

| 指标 | 含义 |
|---|---|
| `grounded` | 回答中的事实性内容能否在给定上下文中找到依据（衡量有没有编造） |
| `relevant` | 回答是否正面回答了问题 |

`JUDGE_PROMPT` 是裁判提示词，单独导出便于复核打分口径。

> **工单7 里这个模块只承担裁判职责。** 批量评估的入口是 `测试/eval_ccf.py`
> （10 道题 + 确定性检索指标 + RAG/纯 LLM 对照）。
> 本文件原有的 `evaluate()` / `report()` / `main(pdf_path)`
> ——「传一个 PDF 路径跑一遍」那套 —— 在本工单里已无人调用，
> 且默认拿招股说明书 PDF 配年报题目，留着是个坑，故已移除。

## 8. 测试与评估模块（工单7 新增）

### 8.4 `测试/eval_ccf.py` — 检索与评估主脚本

```
python eval_ccf.py                 # 完整跑（含大模型）
python eval_ccf.py --no-llm        # 只跑检索指标，秒级出结果
python eval_ccf.py --ids 1,2,10    # 只跑指定题号
python eval_ccf.py --timeout 180   # 放宽单次调用超时
```

指标定义见 `设计/设计说明.md` 第四节。结果写入
`测试/result_ccf_eval.json`（`--tag` 可加后缀保留多组）。

> `--no-llm` 且未指定 `--tag` 时，结果自动写到 `result_ccf_eval_retrieval.json`，
> 不会覆盖完整评估的结果 —— 完整评估要跑十几分钟，
> 被一个几秒钟的检索-only 跑覆盖掉就白等了。

**结果 JSON 结构**：

| 字段 | 说明 |
|---|---|
| `kb` / `chunks` / `docs_in_kb` / `top_k` | 本次评估的知识库与检索配置 |
| `summary` | 汇总指标，含失败题清单 |
| `rows[]` | 逐题明细 |
| `rows[].retrieval` | 6 个检索指标 |
| `rows[].hits[]` | Top-K 召回块的 `doc` / `page` / `type` / `score` / `preview` |
| `rows[].rewrite` / `sub_questions` / `entities` | Query 理解结果 |
| `rows[].rag_answer` / `rag_seconds` / `judge` | RAG 回答、耗时、裁判结果 |
| `rows[].plain_answer` / `plain_seconds` / `plain_judge` | 纯 LLM 对照 |
| `rows[].*_error` | 单题调用失败时记录原因，不静默跳过 |

> 单题失败不影响整轮：任何一次大模型调用出错都只会记进 `*_error` 并继续跑，
> 失败题在报告里如实列出。
