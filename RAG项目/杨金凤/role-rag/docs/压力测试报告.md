# 压力测试报告

## 环境
WSL2 Ubuntu / Python 3.12 / locust 2.46.5 / FastAPI + uvicorn / Milvus + Redis + DeepSeek API

## 结果

| 场景 | 并发 | 时长 | 请求数 | 失败 | QPS | 平均响应 | P95 |
|---|---|---|---|---|---|---|---|
| GET /health | 50 | 30s | 2328 | 0 | 74.68 | 1ms | 3ms |
| POST /chat | 3 | 120s | 6 | 0 | 0.06 | 45.6s | 50s |

## 结论
1. /health 吞吐 74.68 QPS，P99 < 5ms，服务框架性能充足。
2. /chat 单次约 45 秒，瓶颈在 DeepSeek API（生成约 30s）+ 检索/rerank（约 10s）。
3. 3 并发下响应时间与单次相近，DeepSeek 可并行处理，并发不是瓶颈。
4. 优化方向：流式输出已实现（SSE），本地部署大模型可大幅降延迟（需 GPU）。

## 替代说明
用 locust 替代 JMeter：本地 WSL 装 Java 遇 apt 镜像问题，locust 与项目 Python 栈统一，指标等价。

## 流式首 token 延迟（TTFT）

| 指标 | 值 | 说明 |
|---|---|---|
| 平均 TTFT | 10.84 秒 | 串行 5 次 |
| P95 TTFT | 17.93 秒 | 最慢一次 |
| 平均总耗时 | 29.25 秒 | 完整回答 |

### 首 token 前的链路耗时

| 步骤 | 耗时 |
|---|---|
| Query 改写（DeepSeek） | 1-3 秒 |
| BGE-M3 编码 | 0.5-1 秒 |
| 检索（向量 + BM25） | 0.3-1 秒 |
| **reranker 精排（CPU）** | **5-8 秒** |
| DeepSeek 首 token | 1-3 秒 |

### 结论

虽然完整回答需约 29 秒，但流式输出让用户首字延迟约 10.8 秒。
瓶颈在 **CPU 上的 reranker 精排**，GPU 部署后可降至 1-2 秒。
