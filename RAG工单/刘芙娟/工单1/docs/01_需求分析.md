# 01 需求分析

> 面向群众的医疗知识问答系统 · MVP 基线版
> 版本：v1.0　编制日期：2026-09-20
> 上游依据：`.specify/memory/constitution.md` v1.0.0

---

## 1. 项目定位与问题陈述

### 1.1 一句话定位

一个**只依据自有权威语料作答、每句话都能回原文核对、答不出就明确拒答**的医疗知识问答系统，面向"有健康疑问但不需要或不能立刻就医"的普通人。

### 1.2 要解决的问题：可信度与可验证性的双重失效

用户在面对健康疑问时，现有的四种获取方式各有硬伤：

| 方式 | 它给出的 | 它给不出的 |
|---|---|---|
| 通用 AI 问答 | 流畅、像那么回事的回答 | **可靠依据**——无法判断结论从哪来，可能凭空生成剂量、指南年份、文献 |
| 网络问诊 | 一个"医生"的回答 | **真实资质**——回答者的执业身份、专业方向无法核验 |
| 搜索引擎 | 大量相关页面 | **风险判断**——信息互相矛盾，且不告诉你"现在该不该去医院" |
| 翻书/翻指南 | 权威原文 | **检索效率**——知道有答案，但不知道在哪一页 |

四者的共同缺口是：**用户拿到的是"信息"，但无法判断这个信息的来路、可信度，以及自己下一步该做什么。**

本项目的解法不是"答得更好"，而是把回答降级为**对原文的定位与转述**：

- 每一处知识性陈述必须能回原文核对 → 解决"可验证性"
- 检索不到就拒答，绝不补全 → 解决"可信度"
- 每条回答附带风险分级与行动建议 → 解决"该不该行动"

### 1.3 成功判据

MVP 成功的标志不是"回答得多"，而是：

1. 抽查任意一条知识性回答，都能在 `data/source_data` 的原文中逐字找到出处；
2. 提出语料未覆盖的问题时，系统**拒答而不是编造**；
3. 描述紧急症状时，第一句是分诊提示而不是知识解释。

## 2. 用户画像与反画像

### 2.1 首要用户：有健康疑问的普通人（P0）

- **状态**：出现了某种不适、或在体检报告上看到某个指标异常，想先弄明白"这是什么""严不严重""要不要去医院"
- **特征**：非医学背景，不具备辨别医学信息质量的能力，容易被"看起来很专业"的表述说服
- **核心诉求**：可信、能查证、知道下一步做什么
- **典型提问**：「体检说甲状腺结节 3 类是什么意思」「最近总是凌晨醒，需要看医生吗」

### 2.2 次要用户：医学生与科普创作者（P1）

- **状态**：需要快速查证某个知识点、某条指南表述、某个定义
- **特征**：有专业判断力，**恰恰因此更看重出处**——他们要的是"哪份文件的哪一段这么写的"
- **核心诉求**：定位速度（比翻 PDF 快）+ 引用准确（能直接引用）
- **典型提问**：「高血压的诊断阈值在指南里怎么定义的」

这两类用户的诉求在本项目的解法下**高度重合**：都要求"原文可核对"。因此 MVP 不需要为两类人做差异化功能，一套"检索 → 引用 → 分级"链路同时服务双方。

### 2.3 反画像：明确不服务的对象

| 不服务 | 原因 |
|---|---|
| **急症患者** | 见 §5 紧急响应机制。系统的定位是让急症用户**尽快离开系统去就医**，而不是在本系统里获得解答 |
| **寻求诊断的患者** | 不做个体化诊断结论 |
| **寻求处方/调药的患者** | 不做处方与剂量调整建议 |
| **把它当医生替代品的人** | 每次回答末尾强制免责声明，不承担诊疗职能 |

> 反画像不是"暂时不做"，而是**产品定位上就不做**。任何后续版本都不应改变这一点。

## 3. 核心机制：三个回答要素

每条回答由三部分构成，缺一不可：

### 3.1 风险分级（回答"该不该行动"）

系统对每次提问给出一个风险等级。等级**不来自模型判断**，而来自知识库原文的表述与紧急词表命中（见 §5）。

| 等级 | 含义 | 触发条件（示例） |
|---|---|---|
| 🔴 **立即就医** | 存在需要紧急处置的可能 | 紧急词表命中；原文标注为急症/危重 |
| 🟡 **尽快就诊** | 建议在近期由医生评估 | 原文表述为"需就医""建议专科评估" |
| 🟢 **可观察** | 通常是常见现象，可自行观察变化 | 原文表述为常见/自限性，且无危险信号 |

**等级必须有原文依据**。若检索结果不足以支撑任何等级判断，走拒答流程，不猜。

### 3.2 知识性回答（回答"这是什么"）

- 内容**严格来自检索到的原文段落**，不使用模型内部知识补充、补全或"顺带一提"
- 每一处知识性陈述后附引用标记，格式为「来源文件名 + 页码/条款」
- 原文中的**通用处理原则可以转述**（如原文写"多数上呼吸道感染可自愈，建议休息、多饮水"），但必须附引用
- 不输出个体化诊断结论、处方、剂量调整建议、就医科室推荐

### 3.3 引用与来源卡片（回答"凭什么可信"）

- 回答下方列出全部引用来源，每条给出：文件名、页码/条款、原文段落
- 用户可直接展开原文段落核对，不需要离开页面
- 引用粒度：**段落级**（既精确又不断章取义，且前端展示成本最低）

## 4. MVP 功能清单（用户视角）

MVP 交付形态：**Web 应用**，浏览器打开即用。对话模式：**单轮问答**（每次提问独立检索、独立回答，不携带上一轮上下文）。

### F1 提问

- 用户在输入框输入健康疑问并提交
- 输入为空或纯空白时，提示"请输入你的问题"，不发起检索
- 提问中不要求用户注册、登录或填写任何个人信息

### F2 获得带引用的回答

- 回答区展示 §3 的三个要素：风险等级、知识性回答（含行内引用标记）、来源卡片
- 回答生成过程中有明确的加载状态
- 知识性陈述**必须**带引用标记；任何一处缺失即为缺陷

### F3 展开查看来源原文

- 用户点击引用标记或来源卡片，就地展开对应原文段落
- 展示内容为 `data/source_data` 中的**原始文本**，非系统转述
- 用户能据此自行判断系统转述是否忠实

### F4 紧急症状前置提示

- 当提问命中紧急判定（见 §5）时，回答的**第一句**逐字为：
  > 请立即就医或拨打急救电话。以下信息仅供参考。
- 该句必须出现在任何其他内容之前，不被解释、铺垫或知识性内容前置
- 即使用户追问，也不省略、不改写、不推迟

### F5 免责声明

- 每次回答的**末尾**逐字附加：
  > 以上为基于知识库的参考信息，不能替代执业医师的当面诊断。
- 拒答回答同样附加

### F6 拒答与兜底

- 当检索为空、最高相似度低于阈值、或证据不足以支撑结论时，**不生成知识性内容**
- 返回固定兜底话术，引导用户咨询专业医生，**逐字为**：

  > 这个问题在现有知识库中找不到可以依据的原文，我无法给出有依据的回答。建议你咨询专业医生。

- 拒答是**设计内的正常输出**，前端不得呈现为错误、异常或"系统故障"

> **该文本的来历（2026-09-27 补）**：本节此前只写"返回固定兜底话术"却**从未给出文本**，
> 而 `docs/02` §344 又要求"四条拒答路径共用同一套兜底话术"—— 两边都指向一个不存在的
> 常量。`specs/006-medical-qa-input` 落地时首次定稿（由人工裁决），并写入
> `backend/api/__init__.py` 的 `REFUSAL_FALLBACK`。
>
> ⚠️ 与"能力未就绪"文案**不可混用**：若检索/生成能力尚未建成，返回本话术会让用户
> 以为"知识库里没有这个问题"，而真相是功能没做（`docs/05` §3.1.4 规则 3 禁止这种误导）。
> 该场景另见 `CAPABILITY_NOT_READY`。

### F7 反馈入口（轻量）

- 每条回答提供"引用是否对得上原文"的反馈按钮
- MVP 阶段仅记录，不做自动学习
- 目的是让"引用是否真实"这一核心假设可被持续观测

### 用户旅程（正常路径）

```
提问 → 紧急判定（未命中）→ 检索 → 命中且高于阈值
  → 组装回答（风险等级 + 带引用的知识内容）
  → 附加免责声明 → 展示
→ 用户点击来源卡片，回原文核对
```

### 用户旅程（拒答路径）

```
提问 → 紧急判定（未命中）→ 检索 → 为空或低于阈值
  → 返回兜底话术 + 引导就医 → 附加免责声明 → 展示
```

## 5. 紧急响应机制

### 5.1 判定方式：词表兜底 + 模型补充（两段式）

1. **第一段：紧急词表命中**。维护一份紧急症状词表（如胸痛、呼吸困难、意识模糊、严重出血等）。命中即判定为紧急。
2. **第二段：模型补充判定**。第一段未命中时，由模型对提问做一次紧急等级判断；判定为紧急则同样触发。

两段**任一命中即触发**前置话术。

### 5.2 为什么是两段式

- 词表单独使用会**漏检口语化表达**（如"我爸突然说不上来话"），而漏检在紧急场景是安全事故
- 模型单独使用则**不可溯源**，与本项目"结论必须有依据"的精神冲突，且存在误判风险
- 两段式的效果是：**确定的部分由词表保证绝不漏，模糊的部分由模型尽力覆盖**

### 5.3 硬约束

- 紧急话术的**第一句位置**与**逐字文本**是不可协商的（对应 constitution IV）
- 紧急判定一旦触发，后续知识性内容仍须遵守引用与拒答规则——前置话术不豁免其他约束
- 紧急场景下**不输出**任何可能被误读为"可以先在家处理"的建议

## 6. 非功能需求

### 6.1 可信与可审计

| 编号 | 需求 |
|---|---|
| N1 | `data/source_data` 中的原文是**唯一知识依据**，系统不得使用模型内部知识作答 |
| N2 | 任何知识性陈述可回溯到具体原文段落，可被人工逐条核对 |
| N3 | 检索参数（相似度阈值、top-k、切分粒度）必须显式配置，不得依赖库的默认值 |
| N4 | 拒答行为可复现：同一提问在相同语料与参数下，拒答判定一致 |

### 6.2 安全

| 编号 | 需求 |
|---|---|
| N5 | 不输出个体化诊断结论、处方、剂量调整建议、就医科室推荐 |
| N6 | 不基于用户的心理脆弱状态（焦虑、恐惧、急迫）推送特定医疗建议、机构、产品或药品 |
| N7 | 紧急话术逐字前置、免责声明逐字结尾，均为**可断言的确定性行为** |
| N8 | 密钥与凭据只走环境变量，不得硬编码进源码、配置、测试、文档、日志或错误堆栈 |

### 6.3 环境与可复现

| 编号 | 需求 |
|---|---|
| N9 | 唯一受支持的运行时是 `D:/zg6_Project/9/med_rag/rag/python.exe`（Python 3.12.14） |
| N10 | 依赖清单以根 `requirements.txt` 为唯一权威来源，与 `rag/` 实际安装内容保持一致 |
| N11 | 缺失必需密钥时启动失败并非 0 退出，不得静默降级 |

### 6.4 性能与体验

| 编号 | 需求 |
|---|---|
| N12 | 单轮问答端到端响应时间：正常路径目标 ≤ 10 秒，拒答路径应显著更快 |

## 7. 范围边界

### 7.1 MVP 做

- Web 单页问答界面（提问区 + 回答区 + 来源卡片）
- 单轮检索问答链路：检索 → 阈值判定 → 带引用的回答组装 / 拒答
- 两段式紧急判定与前置信术
- 风险三级分级
- 段落级引用与原文展开
- 免责声明
- 引用准确性反馈入口（仅记录）
- 语料入库的最小流水线（解析 → 切分 → 向量化 → 索引）

### 7.2 MVP 不做

| 不做 | 理由 |
|---|---|
| 多轮对话 / 上下文记忆 | 单轮即可覆盖目标场景；多轮会让"紧急话术前置"的断言复杂化，MVP 阶段不值得引入该风险 |
| 用户账号、登录、历史记录 | 与核心价值无关；少收集个人信息也降低合规负担 |
| 急症分诊与急救指导 | 反画像。急症用户的正确路径是拨打急救电话，不是在本系统里得到指导 |
| 个体化诊断、处方、剂量计算 | 安全红线 |
| 就医科室推荐 | 本质是个体化分诊，超出"信息参考"边界 |
| 图片 / 语音输入 | 不服务于核心价值，且引入 OCR/ASR 的不确定性 |
| 在线问诊、挂号、药品购买对接 | 涉及商业导流，与 N6 冲突 |
| 用户健康档案、个性化推荐 | 需要长期存储敏感数据，MVP 无必要 |
| 自动学习 / 从反馈中更新模型 | MVP 阶段反馈仅用于观测 |
| 多语言 | 语料为中文，用户为中文用户 |
| 语料自动抓取与自动入库 | 语料入库必须经人工确认（见 §8.2） |

> **关于「用户账号、登录、历史记录」一行的注记（2026-09-27 补）**
>
> 该条的「历史记录」指的是**面向用户的会话历史** —— 用户能回看自己问过什么、
> 系统能按用户串起多轮对话。**这与管线侧的提问留存不是一回事**：
>
> `specs/007-query-embedding` 落地后，每次通过校验的提问会被写入
> `data/questions/{yyyymmdd}.jsonl`（问题原文 + 时间 + 向量 + 编码指纹）。
> 它的用途**限定为两项**：检索质量评估（用真实提问检验检索效果）、
> 语料缺口分析（哪些问题知识库覆盖不到）。它不建立用户画像、不做跨会话关联、
> 不向用户回显，记录里**不含任何身份信息**（无 IP、无 UA、无会话标识、无账号）。
>
> ⚠️ **这里有一处张力，不因上述限定而消失**：留存用户医疗提问**确实**扩大了
> 个人健康信息的存储面，而本节给这些条目的理由正是"少收集个人信息也降低
> 合规负担"。限定的是**用途**，不是**体量** —— 记录会持续累积。
>
> **可退出手段**：`python -m backend.query_embed purge --before <日期> [--yes]`
> 按日期清理；该目录已列入 `.gitignore`，MUST NOT 进版本库。
> 若将来要收紧（例如改为只留向量不留原文），改动点集中在该特性的
> `backend/query/store.py` 与 `specs/007` 的对应规格。

### 7.3 暂缓但预留

- **混合检索（BM25 + 向量）**：MVP 采用纯向量检索。若上线后因医疗术语、药品名、指南编号等精确字符串召回不足导致拒答率偏高，**第一优先级是补 BM25，而不是放宽相似度阈值**——放宽阈值会使"无据不答"失效，属于倒退而非优化。
- **重排（rerank）**：在混合检索仍不足时再评估。
- **多轮对话**：在单轮的引用准确率与拒答行为被验证稳定之后再评估。

## 8. 语料准入标准

`data/source_data` 当前为空，用户将陆续放入自有资料。在此之前，任何语料入库必须满足以下标准并**经人工确认**。

### 8.1 权威等级

由高到低，高等级语料优先入库：

1. **国家级**：国家卫生健康委员会发布的诊疗方案、技术规范、行业标准
2. **学会级**：中华医学会及各专科分会发布的临床指南、专家共识
3. **教材级**：规划教材、权威教科书
4. **科普级**：权威机构发布的面向公众的健康科普材料

MVP 阶段建议**只入库 1-2 级**。等级越低的语料越容易与临床表述冲突，且科普文本的"建议就医"表述边界模糊，会干扰风险分级。

### 8.2 入库硬性要求

| 要求 | 说明 |
|---|---|
| 来源可识别 | 每份语料有明确的发布机构与年份 |
| 文本可提取 | 能获得结构化程度足够的文本，段落边界可保留（段落级引用依赖此项） |
| 页码可保留 | 引用需标注页码/条款，因此解析时不得丢失页码信息 |
| 覆盖可描述 | 入库时记录该文件覆盖的疾病/主题范围，便于判断"该不该拒答" |
| 人工确认 | 任何新增语料必须经人工确认后方可入库，不做自动抓取 |

### 8.3 待明确

- 语料的具体来源、授权范围与使用限制
- 首期入库的主题范围（建议先从**单一口语化高频主题**切入，而非全科铺开，以便尽早暴露链路问题）

| 项 | 决定 | 备注 |
|---|---|---|

## 11. 验收标准

MVP 通过验收需同时满足：

1. **引用真实性**：抽样 20 条知识性回答，全部能在语料原文中找到对应段落，且转述无实质偏离
2. **拒答正确性**：构造 10 个语料未覆盖的提问，系统全部拒答，无一例使用模型内部知识作答
3. **紧急话术**：构造 10 个紧急症状描述（含词表命中与仅模型命中两类），第一句均为指定逐字话术
4. **免责声明**：正常回答与拒答回答的末尾均为指定逐字文本
5. **安全边界**：构造寻求诊断、处方、调药的提问，系统不输出个体化结论
6. **无硬编码密钥**：仓库全文检索无任何密钥字面量，`.env` 已在 `.gitignore` 中
7. **可复现**：同一提问在相同语料与参数下重复执行，回答与拒答判定一致
