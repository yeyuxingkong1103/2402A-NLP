# 多轮 Query 理解专项说明（工单 05）

**工单编号：人工智能NLP-RAG-Query理解优化**

工单要求「把省略/指代后的短问题**补全成完整独立问题**，补全后再走 RAG 检索 + LLM 生成」。
本文档说明这件事在本系统里**怎么做、为什么这么做、以及哪些路实测走不通**。

涉及代码：`src/coref.py`（消解）、`src/dialogue.py`（状态）、`src/rag.py`（接入，`ask_turn`）

---

## 一、四层消解结构（逐层降级，永不静默失败）

```
用户追问
   │
   ├─ L0 直通判定 ── 已点名公司 / 无代词的完整疑问句 ──────────► 原样放行（零开销）
   │
   ├─ L1 规则检测 ── 定位代词/省略的 span 与候选实体（不定夺）──► Span
   │
   ├─ L2 实体判定 ── 候选集内二选一（qwen2.5:0.5b，受约束子任务）
   │
   ├─ L3 生成    ── 生成独立完整问题（qwen2.5:3b）
   │        │
   │        └─ 校验器不过 ──┐
   │                        ▼
   └─ L4 规则兜底 ── 模板拼接（确定性，保证一定有可用的问题）
            │
            └─ 连模板都给不出（无候选实体）──► unresolved：明确反问，**不猜**
```

| 层 | 触发 | 实测耗时 |
| --- | --- | --- |
| L0 直通 | 5 轮验收里的 Q1、Q5 都走这层 | 0ms |
| L2 判定 | 候选 >1 家时才调 | 0.05–0.25s |
| L3 生成 | 指代填空 / 省略补全 | 0.1–0.5s |
| L4 兜底 | 校验不过或超时 | 微秒级 |

**唯一候选时跳过 L2**（只有一家公司可选，再问模型就是浪费一次调用）。

## 二、为什么是「四层」而不是「把历史丢给 LLM 自由改写」

这是本工单最重要的选型依据，来自**实测**（设计文档 §2.2，本机 qwen2.5:0.5b / 3b）：

| 任务形式 | 0.5b | 3b | 热态耗时 |
| --- | --- | --- | --- |
| 直接改写整句（history + question → 独立问题） | ✗ 原样吐回 | ✗ 「他」→「这个公司」 | 0.1–0.2s |
| 只判定「指哪家公司」（开放） | ✓ | ✓ | 0.2s |
| 二选一约束（给定候选公司） | ✓ | ✓ | 0.05–0.2s |
| 填空替换代词 | ✓ | ✓ | 0.1–0.2s |
| 省略补全「那 XX 公司呢？」 | ✗ 复述指令 | ✓ 完整正确 | 0.49s |
| 英文指代（he / this company） | ✗ 原样吐回 | ✓ | 0.29s |

**结论**：瓶颈是**任务粒度**，不是模型能力。
「最省事的那条路」（把 history 给 LLM 让它自由改写）实测失败；
拆成受约束子任务后两个模型都可靠；而生成类任务（省略补全）只有 3b 能做。
所以本系统**不做端到端改写**，而是「规则定位 + LLM 受约束改写 + 规则兜底」。
分工也是实测定的：**判定用 0.5b，生成用 3b**。

## 三、实测失败模式与校验器拦截（这是本设计的防线）

### 3.1 失败模式一：代词换代词的无效替换（3b）

> 输入：`他参与的哪个工程荣获了国家科技进步一等奖？`（焦点＝武汉兴图新科）
> 3b 输出：`这个公司参与的哪个工程荣获了国家科技进步一等奖？`

「他」被换成了**另一个代词**，检索照样不知道指谁。
**校验器第 4 条**拦截：指代类型的结果中不得再出现同类代词 → 判定不合格，转 L4 规则替换。

### 3.2 失败模式二：复述指令（0.5b）

> 0.5b 直接把系统提示词吐回来：
> `把下面括号里的代词替换成正确的公司全称，其余字不变，只输出结果`

**校验器第 5 条**拦截：与指令模板的 **4-gram 重合率 > 0.5** 判为复述指令。

### 3.3 失败模式三：塞入不存在的实体并吃掉原文（3b）★ 评测期发现

这条是**跑了三方评测才暴露的**，也是本工单唯一一轮「多轮输给单轮基线」的原因
（`d2_person_pronoun_en`）：

> 输入：`Which project did he participate in that won the National Science and Technology Progress Award?`
> 3b 输出：`Which project did Microsoft participate in that won t武汉兴图新科电子股份有限公司
> National Science and Technology Progress Award?`

它同时做了两件坏事：**塞进一个不存在的公司名**（Microsoft），
**并吃掉了原文的 "the"**。而旧校验器只检查「含候选实体 + 无残留代词 + 非空非超长」——
**全票通过**。后果是检索一无所获（0 命中），同一题单轮基线反而命中。

**修复**：L3 的指令本就写着「其余文字保持不变」（规则 1），故把这条约束落成**可执行的校验**：

```
第 6 条（最小编辑）：原文去掉代词后的文字，必须以**子序列**形式保留在改写里。
   实现：去空白与标点（_content_chars）后做子序列判定（_is_subsequence）——
   允许中间插入替换进去的公司全称，但不允许丢失或改写原文内容。
   只对替换类 span（person / demonstrative / zero）生效；
   ellipsis 是模板补全，句子结构本就不同（由 rule_fallback 负责）。
```

修复后该轮改为走 L4 规则替换（`coref_rule`），**确定性且正确**；
回归测试固化在 `tests/test_coref_resolve.py::test_validator_rejects_non_minimal_edit_with_hallucinated_entity`。

> **教训**：校验器只能拦住「你想到的」坏输出。这里漏的不是规则写错，而是
> **没想到模型会一边塞新实体、一边吃掉原文**——所以评测必须逐轮看，
> 只看总数（0.9375）是发现不了「唯一输给基线的那一轮」的。

### 3.4 校验器全量清单（`src/coref.py::validate_rewrite`）

1. 非空、长度 ≤ `REWRITE_MAX_CHARS`（120）；
2. 不等于原文（`passthrough` 除外）；
3. 指代消解必须含**某个候选实体**；
4. **不得残留同类代词**（失败模式一）；
5. **不得复述指令**（4-gram 重合率，失败模式二）；
6. **最小编辑**：不得丢失/改写原文内容（失败模式三）。

任何一条不过 → L4；L4 也给不出 → `unresolved` → 明确反问。**永不静默放行坏改写。**

## 四、提示词全文

受约束子任务，不是自由改写。判定用（`_JUDGE_SYS_ZH` / `_JUDGE_SYS_EN`）：

```
你是对话指代判定器。给定对话历史和当前问题，判断当前问题里的代词指的是哪家公司。
候选公司只有：{cands}
只输出公司全称，不要任何解释。若无法判断，只输出：无法判断
```

```
You resolve pronouns to a company. Given the dialogue history and the current question,
decide which company the pronoun refers to.
Candidates: {cands}
Output ONLY the full company name. If undecidable, output only: 无法判断
```

生成用（`_GEN_SYS_ZH` / `_GEN_SYS_EN`）：

```
你是多轮对话查询改写器。把用户当前问题改写成不依赖上下文、可独立检索的完整问题。
规则：
1. 只把代词（他/她/它/这个公司/该公司/其）替换成正确的公司全称，其余文字保持不变。
2. 只输出改写后的一句话，不要解释，不要加引号，不要重复本指令。
3. 改写结果必须包含完整的公司全称。
```

```
You rewrite a follow-up question into a standalone question that does not depend on context.
Rules:
1. Replace pronouns (he/she/it/this company/the company) with the correct full company name; keep the rest unchanged.
2. Output ONLY the rewritten question. No explanation, no quotes, no repeating these instructions.
3. The result must contain the full company name.
```

**注意**：用户消息里另带一行**提示**（代词指谁、或「新公司是 X，沿用上一轮信息点 Y」），
故「对话历史」是以**结构化提示**的形式给出的，而不是把原始多轮对话整段塞进 prompt ——
后者实测会让 3b 回到自由改写的失败路径（§2.2）。

## 五、对话状态：焦点公司 + 上一信息点

`DialogueState` 只有两个关键量（`src/dialogue.py`）：

| 字段 | 含义 | 为什么需要 |
| --- | --- | --- |
| `focus_company` | 当前在说哪家公司，**只在用户点名公司时更新** | Q2「他」、Q3「这个公司」能指回兴图新科的机制 |
| `last_aspect` | 上一轮问的**信息点**（如「法定代表人」） | Q4「那武汉力源…呢？」补全成「…的法定代表人是谁？」的模板来源 |

历史长度控制（工单硬性要求 1「滑动窗口 + 摘要」）：

- `turns` **全量保留**（评测与逐轮留痕需要，不删）；
- `recent_turns` 是送 LLM 的**滑动窗口**（默认 3 轮）；
- 超出窗口的轮次压成**结构化摘要**（「哪家公司：问了什么」，规则拼接，零延迟）；
- 会话表 LRU（上限 64），单会话硬上限 50 轮。

**指代无法解析时不猜**（硬性要求 8）：无候选实体 → `mode=unresolved`，
系统明确反问「我不确定您指的是哪家公司，请补充公司名称」，
UI 侧同时给出提示（见 `app.py` 的多轮页）与 `st.warning`。
`tests/test_multiturn_rag.py` 与 `tests/test_acceptance.py` 都固化了这条行为。

## 六、接入 RAG 链路的三处关键改动

1. **删掉工单3 硬编码的消歧**：`query_rewrite.disambiguate()` 原先把
   `该公司|本公司|公司|其|发行人|兴图新科` 一律替换成「武汉兴图新科」。
   多文档下这会**理直气壮地答错**（`docs/03` 第 3.1 节有逐轮实证：
   问力源的控股股东，单轮基线答成了兴图新科的程家明）。现由 `coref` 基于焦点消解。
2. **缓存 key 加上「改写后问题 + 焦点公司」**：同一句「他参与的哪个工程获奖了？」
   在不同会话里指的是不同公司，沿用旧 key 会让答案**串味**。
3. **`total_ms` 计入改写耗时**：否则时延指标会系统性少算约 200ms/代词轮，
   3 秒验收就失真了（这条是 Task5 修复项）。

## 七、走不通 / 降级 / 踩坑记录（如实）

| # | 现象 | 处理 |
| --- | --- | --- |
| 1 | 端到端自由改写失败（3b 代词换代词、0.5b 复述指令） | **放弃该路线**，改四层结构（§2.2 实测） |
| 2 | 3b 塞入不存在实体并吃掉原文（3.3 节） | 新增校验第 6 条「最小编辑」，转 L4 |
| 3 | 英文轮改写通过率低于中文，3/20 轮降级到 L4 | **接受**：L4 是确定性正确路径，只是措辞不最优；`指代实体准确率` 仍是 1.0 |
| 4 | 省略句式正则过宽，把「注册资本是多少？」这类**完整问题**也当成「X 呢」的省略句 | 加实体护栏：实体槽必须**基本就是公司名本身**（`raw == 公司全称`，或允许多余 ≤4 字）才认作省略，否则不算（`src/coref.py::_match_ellipsis`） |
| 5 | 「其」单字误伤（其中/其他/尤其/如实） | 用构词排除：`(?<![尤其中何如])其(?![中他实它次余])` |
| 6 | 「该公司」被更短的「其」抢先命中 | 代词命中按「起点升序 + 同起点取更长」排序 |
| 7 | 会话表是**进程级**的，UI 若用固定 id 会让两个标签页共用一段对话历史 | UI 侧改为每个浏览器会话一个 uuid（`app.py::_mt_state`） |
| 8 | 重新生成若只回退答案、不重建状态，被丢弃那轮的焦点会残留 | 回退时从剩余轮次重建 `focus_company` 与 `last_aspect` |
| 9 | 英文提问回了**中文**答案：答案语言取自 `analysis["lang"]`，而它是纯 ASCII 占比口径，问句里嵌了中文公司全称时占比只有 0.58，被判成 zh，语言守卫也不触发 | 新增 `rag.answer_lang()`，一律按**用户原始提问**（剥离公司名后复判）定答案语言；代价是英文轮的中文专名被模型音译，如实记录为已知限制（`docs/技术文档.md` §10 第 10 条） |

## 八、延迟预算（工单硬性要求 7）

| 手段 | 效果 |
| --- | --- |
| L0 直通 | 完整问题（验收序列 Q1/Q5）**零改写开销** |
| 唯一候选跳过 L2 | 少一次 LLM 调用 |
| 改写缓存 | 同 `(原问题, 焦点)` 不重复调用 |
| 模型常驻 | `OLLAMA_KEEP_ALIVE=30m`，热态 0.05–0.5s（冷启动 1.76s/3.26s 必须避免） |
| 判定/生成分模型 | 0.5b 判定 + 3b 生成 |

**实测结果**（`docs/06` 与 `docs/03`）：5 轮验收逐轮最大 1998ms；
20 轮评测 p50 1301.5ms / p90 2407.1ms，**≤3s 占比 1.0**。
多轮引入的成本是 p90 +645ms——**没有通过降低检索质量来换延迟**
（`FINAL_TOP_K` / `RERANK_INPUT_TOP_K` 未动）。
