### 3.0 页码口径（**全仓库强制，先读这一节**）

**裁定：一切对外的页码一律使用 1-based 物理 PDF 页码。**

| 规范 | 要求 |
| --- | --- |
| 索引 ↔ 页码 | pymupdf `d[i]` 的物理页码 = `i + 1` |
| 解析产物 | `pdf_parser` 输出的 `page` 字段必须是 **1-based 物理页码** |
| 引用文本 | `[文件名: 页码]` 与 `page` 字段**同一口径**（1-based 物理页码） |
| 取页校验 | 用 `d[page - 1]` 回读原页 |
| 禁止 | 不得用 0-based 索引充当页码；**不得用印刷页码（页脚或页眉）做引用，也不得用它反推页码** |

**为什么必须写死这条：本 PDF 存在三套编号，其中两套数值完全相同，极易混用。**

| 编号体系 | 物理第 129 页 | 物理第 130 页 | 与 1-based 物理页码的关系 |
| --- | --- | --- | --- |
| ① 1-based 物理页码（**唯一采用**） | 129 | 130 | — |
| ② 0-based 索引 `d[i]` | 128 | 129 | 物理页码 − 1 |
| ③ 印刷页码（PDF1：页脚 `1-1-N`；PDF2：**页眉第 2 行裸数字**） | `1-1-128` / `128` | `1-1-129` / `129` | 物理页码 − 1 |

> **PDF2 印刷页码实测（captain 逐页复核 + T3 独立复算）**：PDF2 每页第 1 行是运行标题
> `武汉力源信息技术股份有限公司 … 招股意向书`，**第 2 行是裸数字 = 物理页码 − 1**：
> 物理 1→`0`、22→`21`、24→`23`、157→`156`、158→`157`、340→`339`、350→`349`；
> **全量校验：350 页中第 2 行 ≠ 物理−1 的页数 = 0（无例外）**。
> ⚠️ 但**禁止**无脑删「独立成行的裸数字」——PDF2 正文存在大量合法的独立数字行（项目序号 `1`、`2`…），
> 清洗必须用「**位置 + 值**」双判据：仅当该行位于页首若干行、且其值 == 物理页码 − 1 时才剔除。
> 也不能把「印刷页码 = 物理 − 1」当通用公式（PDF1 在页脚、PDF2 在页眉块，形式与位置都不稳定）。
> 实现见 `研发/app/core/text_utils.py::strip_printed_page`（参数化 page + head_lines 双判据）。

### 8.8 【重大发现】表格跨页是常态，不是边界情况（全量实测）

T0 对两份 PDF 做了**逐页全量** `find_tables()` 扫描（页数 548 + 350，耗时 63.95 s + 19.63 s，原始数据 `部署/日志/table_scan.json`）：

| 指标 | 招股说明书1.pdf | 招股说明书2.pdf |
| --- | --- | --- |
| 总页数 | 548 | 350 |
| **含表页数** | **312（56.9%）** | **134（38.3%）** |
| 连续含表页段数 | 50 段 | 18 段 |
| **最长连续含表页段** | **28 页** | **17 页** |
| 相邻两页都含表的「连续对」 | 252 对 | 99 对 |
| 首行形如续表（首格空/`None`）的页 | 45 页（示例 21 / 66 / 73 / 76–78 / 81 / 87 / 89 / 91 / 131 / 137） | 79 页（示例 1 / 22 / 34 / 43 / 47–52 / 54 / 56） |
| 与前一页首行完全相同的页（重复表头） | 21 页（示例 57→58、58→59、165→166、271→273、276→278） | 10 页（示例 204→205、208→211、212→213、216→219） |

**两个必须写进解析器的结论：**

1. **表格并不稀疏**：PDF1 有 56.9% 的页含表，最长连续 28 页都有表。
   之前「表格稀疏、逐页扫描即可」的说法只对**前 60 页**成立（该区间确有 34 页无表），
   **不能**据此设计解析器 —— 必须逐页扫描，且要能连续处理几十页的表。
2. **跨页表格必须专门处理**：252 / 99 对相邻含表页里，
   - 有 **45 页（PDF1）/ 79 页（PDF2）** 的首行以空首格开头 → 这是**同一张表被切页后的续表**，
     且**没有重复表头**（实测物理第 131 页首行为 `['', '军种五', '2,727.20', …]`，表头只在第 130 页）。
     若按页独立切块，续表块会**丢掉列含义**，反而污染检索（例如把「军种五」当成某列的首格值）。
   - 另有 **21 页（PDF1）/ 10 页（PDF2）** 是**重复表头**形式（本页表头与上一页首行完全相同）→ 需要**去重**，
     否则同一张表会产生多份表头块，BM25 词频被虚增。

**对解析器的具体要求（供 architect / parser 落地）**

- 检测续表：本页表首行首格为空/`None` 且上一页也含表 → 判定为同一逻辑表，**继承上一页表头**。
- 合并策略：可把「表头页 + 续表页」合并为一个逻辑表块，元数据记 `page_start` / `page_end`（均为 1-based 物理页码），
  **对外引用仍取一个真实物理页码**（建议取 `page_start`，或包含被问数据行的那一页）。
- 重复表头：若本页首行与上一页首行完全相同且上一页以数据行结尾，则视为表头重复，**去重保留一份**。
- 反向校验：以上规则必须用 §3.0 的锚点页（129/130/131）做回归 —— 物理 130 有表头、物理 131 是续表且无表头。

> **T3 实测补充（防止两类误判，均为全量审计发现）**
> ① 「首行是否数据行」**不能**用「含任意数字」判定：招股书表头大量含年份（`'2010 年1-6 月'`、`'2019 年度'`），
> 会把真表头误判为数据行，进而用 `列1..列N` 合成列名替换真表头。
> 正确判据：至少 1 个**纯数值单元格**（金额/百分比/小数， regex 见 `table_parser._NUMERIC_CELL`）。
> ② 「重复表头」**必须逐格精确比较**，不得给容差：曾容忍 1 格差异，导致数据行被当成重复表头整行丢弃（数据丢失）。

### 14.6 三个实测根因与修法（引用可回溯从 8/12 → 14/14）

1. **提示词示例页码被照抄**：旧模板写「例如 `[招股说明书1.pdf: 129]`」，3B 模型把 129 当答案页码 →
   题 957 引用 p129（该页根本没有「重要供应商」句）。修法：模板去掉一切示例数字；`citation.parse/attach`
   只接受**落在本次返回块内**的引用，未命中即丢弃（`citation.attach_dropped`）。
2. **表格块引用被判「无支撑」**：表格证据是 Markdown 表（`| 注册资本 | 5,520.00 万元 |`），与页正文文本层
   天然不同 → 题 531/543 被判非法。修法：证据文本 = **引用块内容 ∪ 引用页正文**（`evidence_text_for`），
   并以「答案能否在引用处核实」为硬判据（`answer_support_check`）。
3. **小模型只回引用/照抄标签**：出现 `引用：[招股说明书1.pdf: 22]`（无正文）、`[文件名: 94 / 类型: 正文]`、
   `[1] 招股说明书1.pdf: 129 / 类型: 正文` 等形态。修法：解析器容忍标签回声（按页码回查块）；

| dict（JSONL/HTTP/评估产物回读的形态） | **False（静默）** | **True** |
| 带 `.content` 的对象 | True | True |
| 纯文本字符串 | （未支持） | **True** |
| 带换行变体「拟使用本次发行募集资\n金15,000 万元…」 | **False** | **True** |

### 19.1 缺陷与根因（实测复现，非偶发噪声）

* 现象：`部署/日志/app.log` 出现**非法 JSON 行**——行被**从中间截断**或**两记录粘连**
  （captain 实测 29/244,462 = 0.0119%；devops 独立实测 37/283,943 = 0.013%，比例随并行进程数上升）。
* 根因：`研发/app/core/logging_conf.py` 用文本模式 `open(path, "a", encoding="utf-8")` + `write` + `flush` 落盘。
  文本模式 = TextIOWrapper + BufferedWriter，**超过写缓冲（`io.DEFAULT_BUFFER_SIZE` = 8 KB）的长记录会被拆成多次底层 `write`**；
  多进程各持独立句柄追加同一文件时，两次 `write` 之间会插入其它进程的输出 → 撕裂。
* 复现（4 进程 × 400 行 × 16 KB，`部署/脚本/stress_log_concurrency.py --strategy legacy`）：实写 1,155 行、**非法 57 行 = 4.94%**。

### 19.2 修复：O_APPEND + 每行单次 write + **跨进程文件锁**

| 环节 | 修复后 |
| --- | --- |
| 句柄 | `open(path, "ab", buffering=0)` → `io.FileIO` + `O_APPEND`，无缓冲 |
| 写一行 | `handle.write((line + "\n").encode("utf-8"))`，**只调用一次 write** |
| 跨进程互斥 | Windows `msvcrt.locking(fd, LK_LOCK, 1)`（锁第 0 字节）/ POSIX `fcntl.flock(LOCK_EX)`，写入前后加/解锁 |
| 进程内互斥 | `threading.Lock`（不变） |
| 字段/格式 | **完全未变**（12 个公共字段、摘要规则、事件名、三文件路由、级别默认值都没动） |

**关键反证（重要，避免后人只做一半）**：只改「O_APPEND + 单次 write」**不加锁**仍然失败 ——
同参数实测 **非法 131/1,211 = 10.8%**（Windows 内核会把较大的 `WriteFile` 拆块写盘，两个进程的块仍可互相插入）。
加锁后同参数 **0/1,600**。**所以锁是必需项，不是优化项。**

### 20.2 修法一：字段型问句「成句化」（`generator.field_statement_answer`，通用规则）

触发（**窄**，实测只命中题 531/543）：

1. `understand()` 的 `field_type` 有字段关键词出现在**问句**里（如 `法定代表人`）；
2. 非枚举清单题（`哪些|包括|分别|…`）、**问号 ≤1**（多问句必须把小问全答上，不能压成单值句）；
3. 现有答案对该字段只有「**：**」或**表格式**赋值（`separator`），**没有判断动词**（`copula`）→ 判为「未成句」；
4. 在候选块（已落地引用的块优先，其次 top-k ∪ 支持块）里找到**同一取值**的原话（去空白后逐字一致）。

渲染：`{字段}{是|为}{取值}。` —— 问人/问物（是谁）用「**是**」，问数值（是多少）用「**为**」（中文规范答法）；
取值一律**逐字**来自证据块，**不新增任何事实**；找不到同值原话则**不改写**（宁可不改）。
实测：531 → `法定代表人是程家明。`｜`[招股说明书1.pdf: 52]`；543 → `注册资本为5,520.00 万元。`｜`[招股说明书1.pdf: 22]`。

**连带修掉的真实缺陷（引用校验与「成句化」冲突）**：
判分要求的判断动词「是」恰好把「法定代表人」（5 字）与「程家明」（3 字）两段原话**断开**，
引用的「≥6 字连续原话」判定只看得到 4 字 → 引用被判「答案不在引用处」（实测 `citation_valid=0`，答案本来是对的却无法落地引用）。
新增 `citation.field_statement_supported()`（**严到不可用于编造**）：
① 整句必须**全匹配**「字段 + 是/为 + 取值」（长答案塞不进来）；② **字段名与取值都必须在引用处逐字出现**（去标点空白后）；
③ 两者在引用处**先后顺序一致**。任一不满足仍走原判定。→ 该容忍只在「连续原话不足」时启用，不放松任何其它情形。

### 20.3 修法二：尾句裁剪 + 行业地位原话锚定（`generator.trailing_clause_trim` / `position_anchor_answer`，通用规则）

**尾句裁剪**（题 957 类：正确答案 + 多余尾句）：枚举题不裁；**只裁尾部**（从句尾起丢掉「与问题无任何实词重叠」的子句，
遇到有关子句立刻停）；**数值型问题下含数字的尾子句一律保留**（数字很可能就是答案，如题 1 的 `1,670万股`）；
安全网 = 问题所问的字段词/方位词必须仍在保留文本里，且保留文本必须能被某个候选块**按引用校验同一条判据**核出，
否则放弃（宁可不裁）。裁完把悬空逗号收成句号。

**行业地位原话锚定**（修掉小模型改写导致的**运行间不稳定**）：题 957 在不同运行里被写成三种措辞，
其中「武汉兴图新科电子股份有限公司在军队视频指挥领域已经成为重要供应商。」把结论倒装，第⑤步相似度只有 **0.23** → 判否。
新规则：问句含 `领域/行业地位/市场地位/重要供应商`（非枚举）时，取候选块里**含问题主体词（供应商…）与问题限定词（领域…）**
且是地位句形态（`已经成为|已成为|重要供应商`）的**最短**原话句，逐字替换答案正文并落到该句所在页，再由尾句裁剪收干净。
→ 题 957 稳定输出 `公司目前已经成为军队视频指挥控制领域的重要供应商。`｜`[招股说明书1.pdf: 181]`（三次运行完全一致）。

**两个阶段的顺序（踩过的坑）**：最初把这两个阶段放在「碎片答案扩句」**之前**，
结果扩句阶段又把答案拉回整页/整句（实测 531 的整页倾倒会在扩句阶段复现），
故两者已移到**扩句之后**，作为「最后一道答案整形」，随后只做「已通过校验的引用重建」。

## §22 t19：日志可审计性修复 —— `generation.done` 的 `retry` 死字段 + `trace_id` 100% 为 null（engineer，2026-10-04）

### 22.1 缺陷（本次全量实测复核，非推测）

| 项 | 修前实测 | 性质 |

### 22.2 修法（选②：改为真值并更名，不删字段）

（保留 `retry` 老名字即使值正确，仍会被「按名字推断语义」的读者当成布尔开关）。

## §24 t21：英文提问可答性（跨语言闸门）+ 多轮字段型指代（A4）修复（engineer，2026-10-04）

### 24.1 缺陷（tester 冻结版全量三级发现的回归）

英文提问（`language=en` 标注正确）被**可答性闸门**判为不可答，一律 `unknown=True / reason=low_coverage / cites=[] / first_token_ms=0`：

```
What is the registered capital of Wuhan Xingtu Xinke Electronics Co., Ltd.?   → 不清楚（low_coverage）
Who is the legal representative of Wuhan Xingtu Xinke Electronics Co., Ltd.?  → 不清楚（low_coverage）
How many shares will Wuhan Liyuan Information Technology Co., Ltd. issue?     → 不清楚（low_coverage）
中文对照：武汉兴图新科电子股份有限公司注册资本是多少？                          → 正常作答（p22）
```

**根因（实测坐实）**：`decide()` 的主判据 `keyword_coverage`（阈值 0.45）是**词面 token 覆盖率**——
英文 query 与中文语料天然无词面交集，实测 coverage 仅 **0.33~0.50**（多数低于阈值）→ 必然拒答；
即使覆盖率侥幸过线，t15 的中文三条守卫（中文公司名 ≥4 字重叠 / 中文实词存在性 + 同块共现）对英文问句
同样天然失效。**t15 的守卫与 t21 的语言感知是叠加关系，不是二选一。**

### 24.2 修法一：语言感知的可答性判据（`answerability.py` + `language.py` + `config.py`）

**中文路径一字未改**（阈值 0.45 与三条守卫都原样保留）。拉丁（英文）问句改走**语言无关**的三层判据：

| 层 | 判据 | 说明 |
| --- | --- | --- |
| ① 实体落地 | 问句点名的拉丁专名必须出现在**证据**或**该题语料**里（含「词级容忍」：专名里任一 ≥4 字非停用词命中语料拉丁文本即算落地） | 与中文主体守卫同源、跨语言。**只在语料确实提供过拉丁实体名时**才用「查无此名」拒答——`招股说明书2.pdf` 语料里没有拉丁公司名，否则会连正确问题一起误拒 |
| ② 主题落地 | 英文问句经 `language.EN_ZH_TOPIC_TERMS`（领域通用映射表：`registered capital→注册资本`、`raised funds→募集资金`、`legal representative→法定代表人` …）映射到中文词，至少一个必须**出现在 top-3 证据块**里 | 等价于中文侧「覆盖率」，但用领域词而非字面 token；**不针对任何具体问句写死答案** |
| ③ 向量底线 | 问句既无实体、也映射不到领域词时，要求 top-3 最大向量相似度 ≥ `RAG_ANSWER__MIN_VECTOR_SIMILARITY_EN`（默认 0.45） | bge-m3 多语言向量；实测英文正样本 0.52~0.57 |

英文侧的守卫（`guard_evidence_latin`）：**年份存在**（与中文同判据）+ **要数值时证据里有可比对数值**。
→ **没有降低任何中文阈值**：`min_keyword_coverage` 仍为 0.45，中文 6 条负例仍全部拒答（见 24.4）。

### 24.3 修法二：多轮字段型指代（A4）—— 一个键名不一致导致的真缺陷
