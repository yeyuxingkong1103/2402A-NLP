## 一、问题分类体系

金融年报语料上，RAG 系统的检索失败不是随机分布的，而是集中在几类可预期的模式上。
下表是本工单的分析框架，每一类都给出：现象 → 根因 → 证据 → 改进方向。

| 编号 | 问题类别 | 典型表现 |
|---|---|---|
| P1 | 文件名编码导致的元数据错误 | 文档名乱码，引用来源无法辨认 |
| P2 | 长文档中的信息稀释 | 目标信息存在但召不回 |
| P3 | 数值类问题张冠李戴 | 数字对但年份/口径错 |
| P4 | 跨文档归纳覆盖不全 | 归纳型问题只答出一部分 |

## 二、逐类分析

### P1　文件名编码导致的元数据错误

**现象**
`ccf_competition/pdf/` 下的年报文件名在 Windows 资源管理器中显示为
`2020-02-14__ƽ�����йɷ����޹�˾__000001__ƽ������__2019��__��ȱ���.pdf`。
若直接读取文件名作为文档标识，引用来源会显示成乱码，
用户无法判断答案出自哪家公司。

**根因**
压缩包内的文件名是 GBK 编码，被按 UTF-8 解码后产生替换字符。
Python 的 `os.listdir()` 在 Windows 上返回的是已解码字符串，
直接使用就得到了损坏的名称。

**证据**
`analyze_problems.py` 的 `_is_garbled()` 检测「� / 锟 / 斤 / 拷」等替换字符标记；
`results/corpus_stats.json` 中若出现含这些标记的文档名，即为命中该类问题。

**改进方向**
`prepare_corpus.py` 的 `decode_garbled_filename()` 做了两件事：
1. 按 `__` 切分文件名，识别出「日期 / 公司名 / 代码 / 简称 / 年份 / 报告类型」六个字段；
2. 对疑似乱码的公司名字段，尝试 `latin-1 → gbk` 回转编码还原，失败时用**股票代码**兜底
   （`000001` → 平安银行，`601318` → 中国平安，映射表内置）。

最终还是拿不到中文名时，退化为「代码 + 年份」的标识（如 `000001_2019`），
保证引用来源至少有唯一且可读的标识。

### P2　长文档中的信息稀释

**现象**
目标信息确实在年报里，但检索不到或排在很后面。

**根因**
单份年报 300~400 页、数十万字。目标信息是一个段落（如董事长致辞里的三句话），
在全文中占比不到 0.1%。固定窗口分块会把本来连续的论述切成多块，
每块单独看都不完整，与问题的语义相似度都不够高。

此外年报中大量内容是**财务附注与审计程序**，与「盈利增长的关键因素」这类问题
语义上很接近（都涉及财务词汇），构成大量干扰项。

**证据**
`analyze_problems.py` 统计：
- 检索命中但 `context_precision` 偏低的题目 —— 召回了但排序不好；
- 目标文档被召回但目标页未被召回 —— 典型的稀释表现。

**改进方向**
1. **章节结构感知分块**（工单02 已实现）——按年报的章节层级切分，
   并在 chunk 头部注入章节路径，把「第五节 业务与技术」这类结构信号变成检索信号；
2. **提高召回深度** —— `recall_k` 从 20 提到 30 再重排，缓解稀释；
3. **混合检索**（工单06 已实现）—— 年报里有大量专有名词（「逾越者联盟」、
   「拨备覆盖率」），这类词向量检索弱、BM25 强，混合后能捞回来。

### P3　数值类问题张冠李戴

**现象**
答案里的数字是对的（确实在文档里出现过），但对应的年份、主体或口径错了。
例如问「2019 年营业收入」，答成 2018 年的数字。

**根因**
这是**生成阶段的错误**，不是检索阶段的。
年报的财务数据密集排列，同一张表里有 2019/2018/2017 三列；
同一页里有母公司报表和合并报表两套数字。
LLM 在上下文里看到多个相近数字时，容易对应错行。

**证据**
`analyze_problems.py` 的 `number_supported()` 检查：
答案中出现的每个数字是否能在检索上下文中找到。
若数字都在上下文中，但答案与参考答案不符 —— 判定为「对错号」类错误。

**改进方向**
1. **表格整表入库**（工单03 已实现）—— 把表格保留行列结构转成 Markdown，
   LLM 能看到表头与数据行的对应关系，而不是一串孤立数字；
2. **生成 Prompt 强化**（工单02 已实现）—— 要求「数值逐字核对」
   「若资料给出多期数据，按期间分行列出」；
3. **更彻底的做法**：把数值类问题路由到 Text-to-SQL / 结构化检索，
   而不是靠 LLM 读上下文。这是后续可探索的方向。

### P4　跨文档归纳覆盖不全

**现象**
归纳型问题（如 S4「这些银行和保险公司面对经济周期的共同策略与差异化策略」）
只能答出一部分，漏掉若干家公司或若干个维度。

**根因**
这是**架构性缺陷**，不是参数问题。
标准 RAG 是「一次检索 → 一次生成」：召回的片段无论多少，都只覆盖查询的局部。
而归纳型问题的答案需要**遍历全部 9 份年报**，
在扁平向量空间里没有任何一个片段能代表「全体」。

**证据**
`analyze_problems.py` 统计 `retrieved_docs` 的文档分布：
归纳型题目若只命中 1~2 份文档（而问题涉及 9 份），即为命中该类问题。

**改进方向**
这正是**工单08 引入 Graph RAG 的直接动机**：
把文档建成知识图谱后，用社区检测把「银行」「保险」分成不同簇，
对每个簇生成摘要，再在摘要上做全局检索——
从「找最相似的片段」变成「遍历主题簇并归纳」。
工单08/09 的对比实验会量化这一类问题的改善幅度。

### P5　表格数据丢失

**现象**
问题问的是表格里的内容，检索完全找不到，或找到的片段里数字缺失。

**根因**
两个层次：
1. **解析层**：`page.get_text()` 按阅读顺序抽文字，
   表格的行列结构会被压平成文字流，`|` 分隔关系丢失；
   部分表格甚至是**图片**或矢量绘制，文本层根本取不到。
2. **分块层**：固定窗口分块会把一张表切成上下两半，
   表头与数据行分离，两半都失去了完整语义。

**证据**
`analyze_problems.py` 检查目标答案所在的页是否含表格，
以及该页的文本层字符数与实际内容量的落差——
文本层字符数远小于视觉内容量，即为「表格/图片未入库」。

**改进方向**
- 表格：pdfplumber 抽取 → Markdown 保留表头对应 → **整表作为单个 chunk 不切分**
  （工单03 已实现）；
- 图片：整页渲染 → 多模态模型读图（工单04 已实现）；
- 验证方式：工单03/04 的消融实验（含表格 vs 不含表格）直接量化收益。

### P6　同名章节跨公司串扰

**现象**
检索到的是**另一家公司**年报里的相似章节。
例如问平安银行的风险管理，召回了招商银行的风险管理章节。

**根因**
9 份年报的结构高度相似，都包含「公司治理」「风险管理」「财务报表」等章节，
段落措辞也高度模板化（监管要求的固定表述）。
在扁平向量空间里，这些段落的嵌入向量**几乎重合**，
向量检索无法区分「平安银行的风险管理」和「招商银行的风险管理」。

**证据**
`analyze_problems.py` 统计 `retrieved_docs` 中与 `reference_doc` 不一致的比例。
若同一题目召回了 3 家以上公司的同名章节，即为命中该类问题。

**改进方向**
1. **元数据过滤**：识别出问题中的主体公司后，
   在向量检索时用 `where={"doc": "平安银行2019年年度报告"}` 做前置过滤
   （`VectorStore.search` 已支持 `where` 参数）；
2. **查询改写补全主体**（工单05 已实现）—— 把「风险管理体系如何体现」改写成
   「**平安银行的**风险管理体系如何体现」，让主体进入向量空间；
3. **图谱约束**：知识图谱中「平安银行」是明确节点，
   图检索天然带主体约束，不会串到别家（工单08 的收益之一）。

## 五、结论

本工单暴露的六类问题中：

- **P1、P2、P3、P5、P6 是工程问题**，通过解析、分块、检索层面的改进可以显著缓解，
  工单02~06 已经分别处理了其中大部分；
- **P4 是架构问题**，标准 RAG 的「一次检索一次生成」范式在归纳型问题上存在天花板，
  必须引入图谱与全局检索才能突破——这直接引出工单08。

这套「先测出问题、再针对性改」的路径，构成了 07 → 08 → 09 三个工单的演进逻辑。
