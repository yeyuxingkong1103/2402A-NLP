# 工单05 · Query 理解优化（多轮对话 + 指代消解）

> 工单编号：**人工智能NLP-RAG-Query 理解优化任务**
> 在工单01→04 的问答系统上实现**多轮对话**：让「他 / 这个公司 / 那力源呢？」
> 这类追问也能被正确检索与回答。

---

## 一、工单要求与本次难点

工单要求「在招股说明书的检索问答的基础上，实现**多轮对话**」，并给出 5 轮示例：

| 轮 | 问题 | 形态 |
|---|---|---|
| Q1 | 报告期内，武汉兴图新科电子股份有限公司来自军用领域的收入分别是多少？ | 完整 |
| Q2 | **他**参与的哪个工程荣获了国家科技进步一等奖？ | 代词「他」 |
| Q3 | **这个公司**的法定代表人是谁？ | 代词「这个公司」 |
| Q4 | **那**武汉力源信息技术股份有限公司**呢**？ | 话题切换 + **省略问点** |
| Q5 | 武汉力源…组织结构图中，哪个销售部的销售处最多？有哪些销售处？ | 完整（图题） |

验收：① 准确率 ≥90%；② 这 5 问都能检索出答案；③ 交互友好（支持多轮对话与**用户反馈**）；
④ 中英双语。性能：响应 ≤3 秒。备注：代码注释需含工单编号。

**难点不在"记住历史"，而在"追问会让检索静默退化"。** 检索链路完全依赖问题里的**字面内容**：

1. `route()` 按公司专名做 `doc_name` 硬过滤（`retriever.py:487`）。「他」「这个公司」
   匹配不到任何专名 → 退化成**全库检索**，工单03 辛苦建立的两文档隔离当场失效。
2. `build_context(hits, query=...)` 用 `_tokens(abstract_query(query))` 选窗口
   （`retriever.py:665`）。问「那力源呢？」时查询词几乎为空 → `best_window` 退化成
   `text[:width]` 截开头（`retriever.py:624`）→ **可能正好切掉答案，而且不报错**。

所以本工单的核心是：**把追问改写成不依赖上下文的独立问题**，并且把这个改写结果
**同时**喂给 `retrieve()` 与 `build_context()`。

## 二、六个关键设计判断

### 2.1 规则优先 + LLM 兜底（不是纯 LLM 改写）

指代与省略在**本场景里是有限、可枚举的**（他/她/它/该公司/这个公司/其 + 「那X呢？」），
用确定性规则处理有三个直接好处：

| | 规则层 | LLM 兜底 |
|---|---|---|
| 延迟 | **0 ms**（纯字符串变换） | 一次 qwen3 调用 ≈1–2 s，直接吃 ≤3s 预算 |
| 可测 | 可写成单测断言（本工单 45 条） | 输出不稳定，只能验调用契约 |
| 可演示 | 界面上直接写「依据：上一轮焦点实体『武汉兴图新科…』」 | 只能给一个理由文本 |

实测：**工单 5 轮剧本 + 4 组扩充用例共 15 轮，规则层 100% 覆盖，LLM 兜底调用 0 次**
（`rewrite_llm_calls = 0`）。兜底只在规则**认不出**的疑似指代/省略时才发动，
且失败时**回退原问题并如实标注** `method="llm-failed"`（不静默丢弃）。

### 2.2 问点继承用**槽位模板**，不用 `abstract_query` 的残句

Q4 要继承上一轮的「问什么」。最省事的做法是拿 `abstract_query(上轮问题)` 去掉公司名当残句，
但它会**削断句子**：

| 上一轮改写后的问题 | `abstract_query` 残句 | **槽位模板**（本方案） |
|---|---|---|
| `武汉兴图新科电子股份有限公司法定代表人是谁？` | `法定代表人是谁？` ✓ | `⟦公司⟧法定代表人是谁？` ✓ |
| `What is the registered capital of Wuhan Xingtu Xinke Electronics Co.,Ltd.?` | `What is the registered capital of?` ✗ **介词悬空** | `What is the registered capital of ⟦公司⟧?` ✓ |
| `根据武汉兴图新科电子股份有限公司招股意向书，…上游涉及哪些企业？` | `招股意向书，…` ✗ **丢了「根据」** | `根据⟦公司⟧招股意向书，…` ✓ |

槽位模板顺带把**英文多轮**从「只能靠模型」变成「规则可解」——
因为 `doc_profiles.entity_names` 里本来就配了英文全称。功能验收④（多语言）一并拿下。

### 2.3 决策顺序：**先判省略式追问，再判「点名即消解」**

```
① 省略式追问（点名了公司、但剥掉专名后什么都没剩） → 继承问点模板   rule-switch
② 否则若本轮点名了公司                          → 不改写（点名即消解）  none
③ 否则若有代词且会话有焦点实体                    → 代词消解          rule-coref
④ 否则若疑似指代/省略但规则没解出                 → LLM 兜底 → 失败则 llm-failed
⑤ 否则完整问题                                 → 原样透传            none
```

**① 必须在 ② 之前**：Q4「那武汉力源信息技术股份有限公司呢？」**确实点名了公司**，
若先判 ② 就会短路成"不改写"，白白丢掉问点继承 —— 而这正是本工单的核心考点。

② 这条不变量顺手解掉另外两个坑：**「一句话里既有实体又有代词」的歧义句**（不猜，原样透传）、
以及 **Q5 被误判成省略式追问**。

「省略式」的判据是**「剥完只剩空」**而不是模式匹配：剥掉引导语（`那/那么/请问/and/what about`）
→ 剥掉尾部语气词与标点 → 剥掉全部标点空白与句末虚词，结果为空才算纯省略：

| 输入 | 去专名后剩什么 | 判定 |
|---|---|---|
| `那武汉力源信息技术股份有限公司呢？` | `""` | **省略式** ✔（Q4） |
| `那力源呢？`（短别名） | `""` | 省略式 ✔ |
| `武汉力源…组织结构图中，哪个销售部的销售处最多？…` | `组织结构图中哪个销售部…` | 非省略 ✔（Q5 原样不动） |

> 短别名 `力源 / 兴图` **只放在 resolver 内部的私有表**，绝不写进 `doc_profiles.entity_names`——
> 加进去会改变 `abstract_query()` 的行为 → 改变已交付 16 题的查询视角 → 直接威胁「16/16 无回归」。

### 2.4 改写结果**双向注入**，语言指令按**用户原话**判

- `retrieve(改写后)` **与** `build_context(query=改写后)` 必须一起换（理由见 2.1 的难点 2）。
- 展示层**同时给出原句与改写句** —— 「Query 理解」这一步在界面上可见，不用口头解释。
- 语言指令（「请用中文回答 / Answer in English」）**按用户原话**判，不按改写后的问题判：
  否则英文提问被改写成中文全称后，指令变成「请用中文回答」，**多语言验收当场挂**。
  英文轮次的代词消解用**英文规范名**，否则会产出「Who is 武汉兴图新科电子股份有限公司？」这种中英混句。

### 2.5 history 与 context **共享** `num_ctx` 预算，且带硬闸门

`num_ctx=4096` 且**超窗静默截断**（不报错）。实测 16 题的上下文平均 2055 字、最大 2470 字
（表格题），`num_predict=200` → 提示词可用约 3896 token，**留给 history 的余量只有约 1000 token**。

所以：
- `history_messages()` 与本次 context **共享** `session_prompt_budget_chars=2600` 的预算，
  超了就从**最旧的一轮**整轮丢弃（不能只丢 user 留 assistant —— 那会拼出没有提问的回答），
  并在响应里如实标注 `history_chars` / `history_dropped`；
- **默认只把「改写后的问题」放进 history，不放答案**：5 轮剧本没有任何一轮需要读到上一轮的
  答案文本（Q2/Q3 靠代词消解、Q4 靠问点继承），放进去只是白占 prefill（每 100 字 ≈25 ms）。

实测：多轮 15 轮里 history 平均 **31 字**、丢弃 **0 轮**、上下文最大 2365 字。余量充足。

### 2.6 带 `session_id` 时**完全绕过响应缓存**（读与写都绕）

现有 `_CACHE` 的语义是「同一问题 + 同一剖面 → 同一答案」。多轮下同一句话因上下文不同答案不同，
缓存语义不成立。更要紧的是**反向污染**：会话答案写进公共缓存后，单轮路径（对比页、既有 16 题）
会读到带 `turn_index/rewritten` 的响应，而 `cached=True` 会让 TTFT 变成一个虚假的好数字。
流式路径本来就没有缓存，多轮演示走流式 —— 绕过不损失任何东西。

## 三、实现

### 3.1 `app/core/session.py` —— 会话记忆（服务端）

`Turn(question, rewritten, answer, focus_entity, intent_template, doc_key, ts)`；
`SessionStore.get_or_create / append / history_messages / intent_template / focus_entity / stats`。

- **为什么放服务端**：指代消解需要的不是对话文本，而是**结构化状态** ——
  会话焦点实体（「他」指谁）与问点模板（「那力源呢？」继承哪个问法）。
  这两样从 `[{role,content}]` 里反解既脆弱又不可靠。
- **为什么不用 Redis**：本工单主题是 Query 理解，与存储介质无关；引入 Redis 只是把
  「进程重启即失效」换成「redis 重启即失效」，换来一个新依赖。**进程内存储是刻意的选择**，
  并把这个限度写进文档（见第五章）。
- `threading.RLock` 保护（`api/evaluate` 走 `asyncio.to_thread`），**锁内绝不 `await`**；
  TTL 惰性清理，不引入后台任务。
- **过期必须可观测**：`get_or_create()` 返回 `reason ∈ {new, expired, evicted, active}`，
  于是「TTL 过期」和「被 LRU 逐出」能分开报告 —— 前者是验收③要演示的东西。
  只报「新建了会话」是**拍不出证据**的。

### 3.2 `app/core/query_understanding.py` —— 改写器

规则层是本工单的主体。两处**防误伤**必须写对，否则是静默出错：

- **「其」**：裸替换会把「其中」拆成「武汉兴图新科电子股份有限公司**中**」——**而且不报错**，
  检索只是悄悄变差。所以用前后视排除 `其中/其他/其余/其间/尤其/及其/其实`。
  「他」排除「他人」，「它」排除「其它」；英文**不做裸 `it`**（"is it possible" 会误伤），交给兜底。
- **代词后的「的」一起吃掉**：`他的法定代表人是谁？` 与 `这个公司的法定代表人是谁？`
  必须改写出**同一个串**「武汉兴图新科电子股份有限公司法定代表人是谁？」——
  与单轮题库 id=531 的题面**逐字相同**。差一个「的」就是不同的查询串 → 稠密向量不同 →
  排序可能与已验收的 16/16 漂移。招股书原文本来就用「公司法定代表人」这种不加「的」的写法。

LLM 兜底（`LLMRewriter`）用 `fmt="json"`、`temperature=0.0`，**不传 `num_ctx`** ——
改 Ollama 的上下文长度会触发**模型重载**（实测冷启动 7.2 s），为"省 tokens"击穿 ≤3s 预算不划算。

### 3.3 `app/core/multiturn.py` —— 轮次组装（API 与评测共用）

`prepare_turn / refresh_history / commit_turn / turn_fields`。

**为什么要单独成一个模块**：API（`app/api/chat.py`）与评测脚本（`scripts/eval_multiturn.py`）
都要走同一段流程。各写一份的话，「脚本绿了、接口没接上」这类静默失败就会漏网 ——
而那正是最该被自动化抓住的一类问题。所以做成**纯函数 + 显式传参**，两边共用，不持有全局信号量。

### 3.4 API 接线（`app/api/chat.py`）

带 `session_id` 时多走三步：`改写 → 用改写后的问题检索/选窗口 → 生成时带 history → 写回本轮`。
改写若走 LLM 兜底**必须在同一个 `asyncio.Semaphore` 内** —— 否则两次 qwen3 推理会在
8GB 显存上互抢，把 `max_concurrency=1` 的意义作废。改写耗时单独记 `rewrite_ms` 并入 TTFT 口径，
**不藏进 `retrieval_ms`**。

SSE 的 `meta` 事件新增整块 `rewrite`：

```json
"rewrite": {"original": "那武汉力源信息技术股份有限公司呢？",
            "rewritten": "武汉力源信息技术股份有限公司法定代表人是谁？",
            "method": "rule-switch",
            "resolved_entity": "武汉力源信息技术股份有限公司",
            "carried_intent": "法定代表人是谁？",
            "evidence": "话题切换 + 继承上一轮问点「…法定代表人是谁？」"}
```

前端把它渲染成「改写 chip」，观众自己就能看见 Query 理解这一步。新增
`GET/DELETE /api/session/{id}` 用于演示会话状态与隔离。

### 3.5 前端（多轮对话页）

**纯追加**：单轮问答页的 `ask()/compare()` 一行没动（它们承载工单01-04 的既有演示，
重构的风险远大于收益）。多轮走独立的一套：`askTurn()` / `renderRewrite()` / `turnStore`。
每轮各自的反馈按钮用**事件委托 + `Map<turnIdx, …>`**，不引入第二个 `lastAsk`。
会话 id 存 `sessionStorage`（不是 `localStorage`）—— 两个标签页天然各自会话，
这就是「会话隔离」演示的素材。

## 五、口径声明（看数字前必须知道的三件事）

### 5.1 Q4 的问点继承**有歧义**，本方案按「最近一轮」取

「那武汉力源信息技术股份有限公司呢？」也可以理解为继承 Q1 的「军用领域收入」。
本方案取**上一轮**的问点（= 法定代表人）—— 这是对话的默认解释，也与工单把 Q4 排在 Q3
之后的编排一致。gold 与判据都按这个口径写死在 `eval/multiturn.json` 里，**可复核**。

### 5.2 TTFT 口径：含改写，且改写为 0

多轮的 TTFT 从**用户按下发送**算起，包含 `改写 + 检索 + prefill + 首 token`，
并单独给出 `rewrite_ms`。规则改写是纯字符串变换，实测 P50 = 0 ms —— 多轮没有额外开销。
若某轮触发 LLM 兜底，`rewrite_ms` 会显著变大并如实显示（本报告 0 次触发）。

### 5.3 会话存在内存，进程重启即失效

这是**刻意的**（见 3.1）。验收时如果要演示 TTL，用环境变量把 TTL 调小即可：

```bash
SESSION_TTL_SECONDS=20 $PY -m uvicorn app.main:app --host 0.0.0.0 --port 8080
```

静置超过 TTL 后再追问，界面会出现黄色提示「会话已过期（TTL）—— 已按单轮处理并新建了会话」，
且该轮 meta 里 `session_expired=true`。

### 5.4 Q5 与单轮题库 id=5 **不是同一题**

- id=5 问：「销售部**有几个部门**构成，其中大客户销售部**有几个销售处**构成？」
- Q5 问：「**哪个**销售部的销售处**最多**？**有哪些**销售处？」

两者答案重叠但**判据不通用**：Q5 的答案里没有「4个部门」这个字面，复用 id=5 的关键词
会把 Q5 误判成未命中。所以 Q5 在 `multiturn.json` 里单独写判据
（`rule_type="all"`：`大客户销售部` + 6 个处名，一个都不能少 —— 只报处名不算回答了"哪个最多"）。

## 六、顺带修掉的两处既有缺陷

| 缺陷 | 后果（静默） | 修法 |
|---|---|---|
| `app/schemas.py:EvalItemOut` **缺 7 个字段**（`reference_answer` / `evidence_page` / `error` / `no_rag_rule_hit` / `routed_doc` / `route_matched` / `route_fallback`），而 `app.js` 的「答案对照（逐题展开）」与逐题表正在渲染它们 | pydantic v2 `extra="ignore"` → **静默丢弃**，接口照常 200，页面显示「人工参考答案（undefined）」、逐题表的「纯LLM命中」列一律「未命中」、「路由」列一律「—」（**看着像模型全错、路由没生效**） | 补齐这 7 个字段（只加字段，不改逻辑），并在单测 T20 里用**反射**断言字段齐全，防止再漏 |
| `eval/questions.json` 里 id=5 的判据写死 `"4个部门"` | 模型有时答「销售部由**4**个部门构成」、有时答「由…**四个**部门构成」——后者**语义完全正确**却因一个字被判未命中（实测同一系统两次跑，一次 16/16、一次 15/16） | 给判据加**同义写法**：`"4个部门\|四个部门"`，`keyword_hits` 按 `\|` 取或。**不做中文数字→阿拉伯数字的全局归一化**，因为那会波及全部题目（例如「一体化工程」里的「一」），改动面与收益不成比例 |

> 第二条与工单04 文档 §5.1 记的是**同一类问题**：判据写得太死，把**正确的回答**判成错。
> 这正是「规则化命中」这一轨的用法 —— 它必须贴着问题的实际问法写；写成"更严格的额外要求"，
> 得到的是**假阴性**。

## 七、已知限度与推迟项

1. **会话不持久**：进程重启即丢（见 5.3）。要跨重启保留需换 Redis/SQLite，与本工单主题无关。
2. **规则层覆盖的是"本场景的指代"**：`他/她/它/他们/该公司/这家公司/这个公司/其/本公司/发行人`
   \+ 「那X呢？」。更绕的省略（「从中选一个最好的」）会落到 LLM 兜底或原样透传 ——
   兜底失败时**如实标 `llm-failed`**，不假装成功。
3. **英文只做「话题切换 + 槽位继承」**，裸 `it/this one` 走兜底（`it` 在英文里误伤率太高）。
4. **多轮评测的判据靠人工 gold**：15 轮的 `gold_rewritten` 是人工核定并写进
   `eval/multiturn.json` 的，可逐条复核。这是主口径不用 LLM 打分的原因 ——
   **可复核**比"看起来更智能"重要。
5. **未做多轮版的 LLM judge 默认开启**：`--judge` 可选，默认关（可复现优先，同工单01/04）。
6. **多轮评测目前只走 CLI**，没有做 `/api/evaluate/multiturn` 接口与评估页按钮 ——
   验收证据靠脚本 + 归档报告已经足够（本目录 `eval报告/mt-*.json`）。
7. **演示视频**需人工录制（见 `docs/工单05-演示截图清单.md`）。
