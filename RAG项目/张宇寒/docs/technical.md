# 技术文档

## 项目分工

- `run.py`：启动FastAPI网页服务和原有Celery后台任务。
- `backend/app`：认证、在线问答、模型调用、记忆、存储和用户材料处理。
- `frontend`：知途页面，由后端直接提供，不需要另起前端开发服务。
- `data_pipeline`：公共资料处理，与网页启动分开。

在线问答从已有知识库检索法律资料，再组织依据、参考分析和处理建议。
公共知识库只建立和持久化一次，日常启动直接连接；新增资料或重建另行执行管理命令。

## 存储与安全约定

Milvus存储向量和检索记录，MySQL存储用户、会话和业务记录，Redis承担缓存、短期状态及后台任务相关用途。
MinIO是对象存储，也是当前Milvus部署的依赖；不能把它当作可以随意删除的临时目录。
MySQL、Redis、etcd、MinIO、Milvus使用`docker-compose.yml`中指定的持久化外部卷。
不要执行数据卷删除或在没有备份时升级存储版本。

公共Milvus数据库为`default`，向量字段为`embedding`，维度为1024。
保持现有模型、集合字段和维度兼容；相同维度不等于不同嵌入模型的向量可以混用。
更换嵌入模型需要单独评估和重建索引，不能只改模型名称。

| 集合 | 主键 | 正文 |
|---|---|---|
| civil_code_articles | id | article_content |
| civil_interpretations | id | content |
| civil_cases | case_id | summary |
| civil_elements | serial_number | case_summary |
| civil_evidence | evidence_id | content |
| civil_processes | process_id | content |
| civil_questions | question_id | content |
| civil_citations | citation_id | content |

Web启动会验证公共集合结构，不执行公共重建或入库。用户身份和会话范围必须在服务端检查，不以浏览器传来的ID作为唯一授权依据。
密钥保留在本地配置，不写入页面、日志或文档。

## 一套流程

`main.py → load.py读取 → parse.py解析 → clean.py检查 → index.py保存`

普通文件直接读，扫描页用本地OCR。只有明确选择`auto-vision`或`vision`，才允许将页面发给现有多模态模型。
默认不生成向量、不连接数据库。用户上传入口不变。

## 现有资料

资料继续放在`data/public`原来的七个分类目录。
`parse.py`中的`SOURCE_FILES`指定各分类的来源文件，不会自动扫描新放进去的任意文件。
现有完整库处理仍会生成法律要件和引用关系，不改变集合名称、主键和正文格式。

在项目根目录运行：

```powershell
& "D:\Program File\conda\envs\legal_rag\python.exe" -m data_pipeline.main
```

结果写入`data/processed`。这是处理命令，不是启动问答服务的命令。

## 新增一份资料

明确指定文件和分类，不用修改来源清单。以下路径需要换成实际文件地址：

```powershell
& "D:\Program File\conda\envs\legal_rag\python.exe" -m data_pipeline.main --file "data/public/civil_code_articles/新增条文.pdf" --collection civil_code_articles --output-dir "data/processed/新增条文"
```

扫描页自动调用RapidOCR；失败时尝试Tesseract。Tesseract需要本地程序和对应语言包。
普通文字PDF使用pypdf，文字表格使用pdfplumber。Word、JSON、Excel继续使用原来的读取方式。

希望先OCR、遇到明显问题再使用多模态时，在上述命令末尾增加`--pdf-method auto-vision`。
这个选项也适用于图片；未选择时默认只在本地读取，不会自动上传。
空OCR结果、识别异常、乱码替换字符和`【看不清】`标记会触发补读。
对于同页既有文字又有图片的PDF，会对整页做OCR；去掉空白后的识别字数不足原文字层的80%时，也视为疑似漏读。
这个比例只是检查线索，不是完整性证明；短条文不会仅仅因为字少就被判为不完整。
补读仍然明显少于原文字层时，停止保存，提示人工核对。

原有`--pdf-method vision`仍保留，它直接使用多模态，不执行OCR优先策略。
复用现有API密钥、多模态模型名称、输出上限和超时配置，不需要MinerU Token或本地MinerU模型。
多模态是云端调用，会上传页面图像、消耗接口额度；敏感文件须先确认使用权限。

模型报错、输出截断、空结果或明确表示看不清时停止保存。
默认本地OCR得到明显乱码或看不清标记时也停止，不把坏文字当成有效法律记录。
处理成功不代表识别内容全部正确，金额、条文编号、日期和表格仍应抽查。
资料必须符合现有解析器的格式；任意判决书不会自动变成合格案例记录。
单份资料只供预览，不允许直接追加入库或重建库。它不自动生成完整库的要件与引用关系，证据中的案例编号需在完整数据中共同校验。
不指定输出目录时，单份结果保存到`data/processed/previews/文件名-内容摘要`，不会覆盖完整库输出。

## 数据库保护

- 不加参数：只处理和保存，不修改数据库。
- `--append`：完整来源资料明确追加入库，不删除旧集合。当前不是幂等同步，不能重复追加同一批资料；只应对编号不与已有资料冲突、关联完整的新批次使用。
- `--rebuild`：用完整来源资料重建公共集合，会替换旧数据。单份文件禁止使用此选项。

首次接入新资料，先检查处理结果，不要直接加上入库参数。
不同资料使用不同`--output-dir`，否则同一分类的处理结果文件会覆盖。
已有数据库中的资料继续用于问答，不需要因为此次代码修改重新入库。

入库前会重新检查整批记录的主键、正文和引用关系，并核对需要保存的字段长度。
主键和正文必须是字符串，数字主键、列表正文等错误类型会在模型调用和数据库连接之前被拦住。
主键上限128字节、正文沿用原来的50,000字节上限、其他文本字段上限2,048字节；这些都是UTF-8字节数，不是字符数。
超过限制现在会报错，不再自动截短法律正文。默认预览仍能保存原文，便于你检查和整理。
2026-09-18只读检查现有`data/processed`结果时，案例18条、要件37条、证据11条、流程2条，共68条正文超过50,000字节。
因此这些结果不能直接按新检查重新入库，须先整理超长记录；本轮没有改写它们，也没有影响数据库中的旧资料。
嵌入模型返回空向量、错误数量、错误维度、非数字、NaN或无穷大时阻止这一集合写入。
追加到已有集合前会核对主键和向量维度；新建集合明确使用原集合对应的主键、正文字段和AUTOINDEX/COSINE，不在配置失败后创建未知结构的集合。
现有重建流程按集合逐个替换，不是八个集合一起原子替换；后面的集合失败时，前面已完成的集合不会自动回滚。不要把这些校验当作整库事务或备份。

## 文件与兼容

### 初学者建议阅读顺序

1. 先看`load.py`顶部的`extract_content()`：检查文件，再按后缀选择读取方法。`load()`只是在它的结果中取出文字。
2. 再看`index.py`顶部的`build_public_records()`和`process_public_file()`：读取、解析、检查、保存。这两个入口不入库。
3. 然后看`read_scanned_image()`：图片和PDF共用OCR/多模态选择，不再各写一遍。
4. 最后看`_public_rows()`和两个入库函数：生成向量、保留允许保存的字段、写入数据库。

`closing`是Python自带的资源关闭工具：成功或报错都会调用图片的`close()`，不是新服务，也不需要安装。
本轮只是保守去重：保留所有读取格式、分页/表格结果、旧函数入口和安全检查，没有新增数据处理文件。

主要看`main.py`、`load.py`、`parse.py`、`clean.py`、`index.py`。
`embedding.py`只在入库时生成向量；`chunk.py`保留分块能力和旧用户文件调用。
`public_main.py`的旧命令转到`main.py`；其`process_public_data()`函数保留历史分块和统计报告输出，避免旧调用失效。
已移除MinerU接入代码和配置，没有删除已下载的模型或独立环境。

本轮沿用旧项目公共切块：条文按条、案例按记录，不新增集合，不接入公共父子块在线检索。
固定切块、父子块辅助函数仍保留，但不能据此宣称公共入库已使用父子块。
旧的嵌入文本粗略长度限制也暂时保留：按字符数估算token并限制到约6,000字符，不是真实分词计数。
完整正文保存不等于长案例每一段都参与了向量生成，这个限制需要后续单独优化。

## 基础在线检索

主要看`backend/app/rag/search.py`的`VectorRetriever.search_public()`和`ProcessingPipeline`。
公共知识统一从现有Milvus八集合检索，不再用`data/processed`中的本地JSON抢先回答；本地处理结果修改后，未入库的数据不会自动成为公共回答依据。
无需因本轮代码修改重新入库。Milvus不可用或集合加载失败时，记录检索故障，不把它解释成不存在相关法律。

明确条号时使用精确过滤查询，跳过嵌入接口；没有匹配就不拿其他条文冒充。
民法典条号只查询对应条文库；指定司法解释自身条号时，须用`《完整文件名称》`明确文件，并核对文件身份及自身条号。
未识别的法律名称、含糊的司法解释名称不会默认转换成民法典条号；简称可能无法匹配，需补充完整名称。
普通问题先批量生成查询向量，再用关键词包含匹配和向量检索召回，条文库也允许向量检索。
最多使用原问题和一种改写，最多选择配置数量的集合（当前为6），集合之间最多4个并发任务。
关键词每集合最多取4条；重点集合每种表达最多取4条向量结果，非重点集合取1条；配置中更小的上限仍有效。
向量数量、1024维度与有限数字校验不通过时停止，不发送坏向量。

重复来源合并后用加权RRF排序；RRF分数不是相关性、置信度或法律正确率。
非精确候选按配置上限进入重排（当前10条），精确依据单独保留，但不阻止其他候选重排。
重排分数优先于向量分数；低重排分数不能被旧高分覆盖。单条候选也由接口评分，不人为赋1.0。
接口故障保留原候选、标注降级并触发低置信度提醒；不伪造成功的重排分数。
证据筛选当前最多8条、非精确公共资料相关性阈值0.55；阈值只是工程筛选参数，需要实际题集校准。

查询结果保留条号、案号、法律名称等来源字段，移除向量和重复正文。
民法典条文及司法解释不在证据、上下文和回答提示词阶段按固定字符数截断；超出上下文预算时整条跳过，并计入丢弃统计。
回答分支、最终来源列表及依据数量统一使用实际进入上下文的资料，预算剔除的资料不冒充已使用依据。
案例等长资料仍受原字符限制，截短时标注`【节选，非完整原文】`，不表示案例全文已参与回答。
现有用户资料隔离、可选联网入口和问答workflow继续保留，不扩展上传、文书等功能。
准确性和真实耗时仍须用法律题集及真实接口验收；现有数据的超长向量文本问题、法律时效核验和生成答案质量不是本轮已经解决的事项。
