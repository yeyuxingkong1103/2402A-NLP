# 02 · 总体架构

> **定位**：系统分层、模块划分、技术栈、数据流。**一条链路：文档 → 知识库 → 检索 / 问答 → 前端展示。**

## 一、系统分层

```text
┌──────────────────────────────────────────────────────────────┐
│  呈现层   静态前端                                             │
│           上传｜任务进度｜文档列表｜向量库查看｜问答            │
├──────────────────────────────────────────────────────────────┤
│  接口层   FastAPI                                              │
│           文件接入｜任务控制｜文档浏览｜问答接口                │
├──────────────────────────────────────────────────────────────┤
│  服务层   任务驱动 + 构建编排 + 检索编排 + 问答编排            │
│           本地状态｜后台执行｜引用返回｜兜底策略                │
├──────────────────────────────────────────────────────────────┤
│  管线层   MinerU 解析 → 清洗 → 分块 → 向量化 → 入库            │
│           PDF / Markdown / 结构块 → Chunk → Dense / Sparse    │
├──────────────────────────────────────────────────────────────┤
│  数据层   Qdrant 向量库 ｜ 本地状态文件 ｜ 上传文件目录         │
├──────────────────────────────────────────────────────────────┤
│  外部依赖 MinerU ｜ BGE-M3 ｜ Ollama ｜ 可选 VLM 接口          │
└──────────────────────────────────────────────────────────────┘
```

## 二、模块划分

| 模块 | 职责 |
|---|---|
| 文档接入 | 接收 PDF 上传、保存文件、创建文档记录 |
| 任务调度 | 管理构建任务状态、驱动后台执行、暴露任务查询 |
| 构建流水线 | 完成解析、清洗、分块、向量化和入库 |
| 检索问答 | 生成查询向量、执行混合检索、拼装证据、生成答案 |
| 向量库浏览 | 展示已入库文档、类别和向量数据概况 |
| 前端展示 | 提供上传、任务查看、文档查看和问答入口 |

## 三、关键技术选型

| 环节 | 选型 | 关键决策 |
|---|---|---|
| 前端 | 原生 HTML / CSS / JavaScript | 轻量、可本地直接运行，不依赖前端框架 |
| 接口层 | FastAPI | 提供接口、静态资源挂载和健康检查 |
| 解析 | MinerU | 提取 PDF 结构化内容，失败时回退到 `pypdf` |
| 清洗 | 结构化文本清洗 | 去除冗余空行和噪声，保留可追溯内容 |
| 分块 | 语义分块 | 保留页码、类别和来源片段，避免丢失上下文 |
| 嵌入 | BGE-M3 | 同时生成 dense 和 sparse 表示 |
| 向量库 | Qdrant 本地模式 | 适合混合检索，支持命名向量和融合查询 |
| 检索 | dense + sparse + RRF | 提升混合型 PDF 的召回能力 |
| 问答 | Ollama | 本地生成答案，默认模型为 `deepseek-r1:7b` |
| 状态存储 | 本地 JSON | 记录文档、任务和 chunk 元数据 |
| 可选视觉能力 | OpenAI 兼容 VLM | 仅在配置开启时用于图像、表格等块的补充处理 |

## 四、数据流

### 入库流

```text
PDF 上传 → 本地保存 → 创建文档与任务 → MinerU 解析
→ 清洗 → 分块 → 生成 dense / sparse 表示 → Qdrant 入库
→ 更新任务状态 → 前端展示结果
```

### 问答流

```text
用户提问 → 生成查询向量 → Qdrant 检索 → RRF 融合
→ 取 Top-K 证据片段 → 构造带引用约束的 prompt
→ Ollama 生成回答 → 返回答案、引用来源和页码
```

### 任务流

```text
PDF 上传 → 创建文档记录 → 创建构建任务 → 用户触发构建
→ 后台执行流水线 → 前端轮询任务状态
```

## 五、数据对象

### Document

- 文档标识
- 文件名
- 文件路径
- 当前状态
- 创建时间

### BuildTask

- 任务标识
- 关联文档
- 当前步骤
- 进度
- 状态
- 失败信息

### Chunk

- 块标识
- 关联文档
- 页码
- 类别
- 文本内容
- 来源片段

### Citation

- 关联文档
- 文件名
- 页码
- 类别
- 文本内容
- 相关性分数

## 六、错误处理

- 非 PDF 文件直接拒绝。
- 解析失败时回退到备用文本提取。
- 缺少有效页码的内容不允许入库。
- 向量库不可用时，构建流程标记失败。
- 问答模型不可用或无结果时，返回兜底信息。
- 检索结果为空时，返回“知识库中未找到相关依据”。

## 七、验收标准

- PDF 上传后可以创建文档和任务记录。
- 构建流程能跑通解析、清洗、分块、向量化和入库。
- 向量库能列出文档和类别。
- 问答接口能返回答案和引用。
- 没有依据时能正确兜底。
- 前端可以展示基本操作入口和结果。

## 八、后续优化方向

- 增加更细的任务日志。
- 增加重试和超时控制。
- 增强视觉块处理能力。
- 引入 reranker 提升检索质量。
- 扩展评测集和回归测试。
