## 二、分层与依赖方向

```text
api（路由）  →  chat / retrieval（能力层）  →  db / models（访问层）
                        ↓
                 ingest / pipeline / crawler（离线链路）

规则：
1. 路由层不写业务逻辑，不直接访问数据库
2. 能力层（chat / retrieval）不反向依赖 api
3. 数据库访问统一走 db/，service 里不裸写 SQL
4. 外部服务（embedding / reranker / llm）统一放 models/，便于替换与 Mock
5. 离线链路（crawler → ingest → pipeline → db 导入）与在线链路解耦
```

## 三、命名规则

### 3.1 见名知意（硬性）

函数名、类名、变量名、常量名必须读名知义。

```python
❌ _file_hash        ✅ calculate_file_sha256
❌ temp_entries      ✅ list_temporary_directories
❌ data2 / d / tmp   ✅ manifest_path / package_directory
❌ process()         ✅ process_raw_directory()
```

### 3.2 禁止歧义用词

| 概念 | 唯一用词 | 禁止 |
|---|---|---|
| 文档进知识库的全过程 | `ingest` | pipeline、处理 |
| 在线召回与排序 | `retrieval` | 搜索、search（作目录名时） |
| 采集→解析→切块→打包的编排 | `offline_ingest` | pipeline |
| 数据包（记录模型 / 校验 / 发布） | `package` | dataset、pipeline |
| 法域与时效筛选 | `filter` | 筛选、precheck |
| 调用大模型产出回答 | `chat` / `generation` | 推理、inference |
| Redis 会话上下文 | `short_term_memory` | 上下文、context |
| 法条 / 款 / 项 | `article` / `paragraph` / `item` | 条文片段、clause |
| 聊天会话（业务） | `chat_session` | session（与数据库 Session 混淆） |

**禁止出现裸的 `pipeline` 作为目录或文件名**——它无法说明是哪条链路。

### 3.3 同一实体只允许一处定义

```text
数据库实体：只在 app/db/sql_models.py 定义
领域术语：  只在 docs/CONTEXT.md 定义
提示词：    只在 docs/提示词.md 定义（或代码内单一常量文件）
禁止同名实体出现在两个文件里（历史上出现过 Document 两套定义，字段还不一致）
```

### 3.4 文件规模

```text
单文件 ≤ 300 行；超过就按职责拆分，不按行数机械拆
一个文件一个主职责
```

### 3.5 注释要求

目标：**任何人拿到代码，都能看懂这块在做什么、为什么这么做。**

```python
# ✅ 说明意图与原因
# robots.txt 只读一次并缓存，且不占用页面请求的限速配额，
# 否则紧随其后的首个页面请求会被自己的限速拦下

# ❌ 复述代码
# 保存白名单
self._whitelist = whitelist
```

要求：模块开头写职责说明；非平凡函数写职责与失败行为；关键"为什么"必须写。

## 四、测试约定

```text
一个模块一个测试脚本：tests/test_<模块名>.py
只写有效测试：覆盖"错了会真出问题"的行为
禁止测试文件之间互相 import（共享夹具放 tests/conftest.py）
禁止无效测试：如断言某个库能被 import、断言 getter 返回刚赋的值
```

示例（数据包模块）：

```text
tests/test_package_module.py
  ├── 合法数据包通过校验
  ├── 缺文件 / 缺清单被拒绝
  ├── 文件被篡改被拒绝
  ├── 路径逃逸被拒绝
  ├── 引用断裂被拒绝
  └── 发布失败不留半成品
```

## 七、仓库纪律（长期规则，犯错过才写下的）

```text
1. backend/ 根目录只允许这些内容：
     app/  tests/  requirements.txt  pyproject.toml  pytest.ini  .env.example
   禁止出现：临时脚本、验收脚本、日志、报告、备份文件（历史上堆过 20+ 个）

2. 临时脚本放哪：
   · 一次性验收/调试脚本 → 项目根，**用完即删**，不进仓库
   · 长期运维脚本（健康检查、迁移）→ scripts/，迁移脚本放 scripts/migrations/
     并在该目录 README 里写清每个迁移做了什么、执行顺序、是否已对当前库执行过

3. 报告放哪：
   · 评测报告与验收记录 → 项目根 reports/（JSON 机器可读 + Markdown 人可读）
   · 禁止把报告写进 backend/

4. 删除纪律（删任何文件/函数前）：
   · 必须 grep 确认零引用，**连 tests/ 一起 grep**，并在报告里贴出证据
   · 优先删"重复实现"与"转发垫片"；框架回调（路由函数、Pydantic 校验器、
     HTMLParser 回调、property）不算死代码，不要删
   · 删除数据行必须有精确条件（如 LEFT JOIN 判定孤儿），禁止"看起来像测试就删"

5. 兼容垫片与聚合入口的区别：
   · 禁止兼容垫片 = 禁止"同一实现留两份"（如真实现 + 转发函数）
   · 允许聚合入口 = 只做 re-export、不含任何逻辑的统一导入入口（如 db/sql_models.py）

6. 数据库变更：
   · 只允许显式迁移（新增列 / 重建表），禁止 drop 已有数据表
   · 重建 Milvus collection 必须显式传参触发，禁止自动 drop

7. **运行环境唯一化**：本项目正式环境是 conda 环境 **`rag`**，所有命令都必须在它里面跑
   （`conda activate rag` 或 `conda run -n rag python ...`）。
   原因：本机 anaconda3 base 环境装的是另一套版本（如 fastapi 0.133.1 / starlette 1.0.1），
   与 `rag`（fastapi 0.104.1 / starlette 0.27.0）不同；`requirements.txt` 锁的是 **rag** 的版本。
   在 base 里跑虽然也能通过测试，但不能代表正式环境，禁止用它做验收结论。

8. 不用 git：版本管理靠"定期备份 + 桌面交付物目录"；
   大规模改动前先备份原文件（拆分、改名、批量删除），验收通过后删除备份

9. **易漂移配置改前必留备份**（含 md5）。以下文件即使只改几行也属于"回答行为的主要开关"：
   · `app/chat/prompt_builder.py` 里的 SYSTEM_PROMPT 常量
   · `.env` / `.env.example`（模型名、阈值、各类开关）
   · `app/chat/guard.py` 与 `app/chat/citation_check.py` 的阈值与词表常量
   · 数据库实体定义与迁移脚本
   背景：实测发生过"提示词被改且没备份"——回答引用率从 10% 退化到 80%，
   因取不到旧文本，只能靠"补回该条要求后行为完全恢复"来间接归因。

10. **评测报告必须记录当轮变量**：写明本轮 `LLM_MODEL`、提示词文件 md5、召回窗口与阈值。
   背景：实测某轮评测与一次 .env 改动同时发生（模型名变化），事后无法区分是哪个变量造成指标差异。
```
