## 1. 需求拆解

工单原文的三条故障现象与四条根因推测，逐条落到**本仓库真实代码**上（本工单基座 = 工单10 交付的
FastAPI 服务 `研发/service/`，RAG 内核来自工单7 的 `研发/app/`）。

| 编号 | 工单原文表述 | 本仓库对应位置 | 本工单处置 |
| --- | --- | --- | --- |
| R1 | 响应延迟从 ~2s 陡增到 10s+（10+ 并发） | `service/api.py` 的 `POST /api/v1/ask` | 压测复现 + 定位 + 修复 |
| R2 | 内存随运行时间持续增长 → OOM | `app/core/qa_engine.py` `_memory_cache`、`service/session_store.py`、`app/storage/sqlite_manager.py` | tracemalloc/RSS 剖析 + 加容量上限 |
| R3 | 仅文本问答时 GPU 内存也被大量占用且释放不及时 | `app/core/llm_client.py` 的 `keep_alive="30m"` | 改为可配置 + 统一带 `keep_alive` |
| R4 | 每个请求独立初始化重量级组件 | `app/core/embedder.py::resolve_embedding_backend`（**每次请求都探测 `/api/tags`**） | 探测结果进程级缓存 |
| R5 | 请求处理无队列/限流 | `service/config.py` 有 `max_concurrency=4` 但**全代码零引用** | 有界队列 + 信号量限流 + 429 |
| R6 | 全局缓存/会话未释放 | `qa_engine._memory_cache` 无 TTL、**无锁** | 加锁 + TTL + 容量配置化 |
| R7 | DB/向量库连接池泄漏 | `app/storage/sqlite_manager.py`（单连接已复用，但每请求 3~4 次 fsync）；`app/core/llm_client.py`+`embedder.py` 的 `urllib.request.urlopen` **每请求新建 TCP** | WAL + 批量提交；HTTP 连接池 |
| R8 | 部署与运维文档 | — | `部署/DEPLOYMENT.md`、`部署/OPERATION.md` |

> **诚实性声明（重要）**：R4 在原文语境里指 RAGFlow 的 DeepDoc / 视觉语言模型。
> 本仓库的基座**没有** DeepDoc，也没有「每个请求 new 一个解析器」的写法
> （`QAEngine` 是 `service/api.py` 的模块级单例，索引走 `retriever._BUNDLE_CACHE` 模块级缓存）。
> 因此本工单**不编造**「解析器重复初始化」这一条，而是在真实代码里核实后，
> 如实记录为「未复现 + 证据」，并把 R4 的**真实等价缺陷**（嵌入后端探测未缓存）作为修复项。
> 详见 `优化/瓶颈排查与修复报告.md` §2.1。

## 3. 时长缩减的口径与原因（必须如实标注）

工单原文要求 10 分钟 × 2 场景 + 12 小时 soak。本机现实约束：

1. **_共享约定.md §5.5 硬性约束**：本机曾在提交内存 44.37/47.77 GB（93%）时把浏览器标签页 OOM 顶崩。
   本工单的 API 服务实测私有内存 **2.41~2.44 GB**（工单10 `优化/评估结果/` 实测值），
   是本机崩过的同款规模。压测期间 API 进程 2.4 GB + Ollama 常驻 0.7~2.2 GB + 压测器 ≈ 3.5 GB 级别。
2. 本机可用物理内存实测 **4574 MB**（开工基线），提交比 67%。
3. 因此本工单采取：**并发数不缩（20/10 照原文），时长缩到 180 秒**，
   并在 `测试/测试报告.md` 与 `优化/瓶颈排查与修复报告.md` 中**逐处标注**
   「原文要求 10 分钟，实测 3 分钟」——**不假装跑满 10 分钟**。
4. 12 小时 soak 同样不可能：改为 **15 分钟缩短版 soak**，给出 RSS 增长斜率与 12 小时**外推值**，
   外推结论明确标 `[外推]`。RSS 曲线与 tracemalloc 快照 diff 作为「无增长趋势」的直接证据。

## 5. RAGFlow 语境 vs 本仓库语境（必须在报告里讲清楚）

工单原文描述的是 **RAGFlow**（DeepDoc 解析器、Task Executor、Milvus、Redis 队列）。
本仓库的基座是**工单7 的同源 RAG 系统**（FAISS + BM25 + RRF + 自研轻量重排 + Ollama），
由工单10 包装成 FastAPI 服务。

因此本工单的做法是：
1. **保留** RAGFlow 的架构语义映射：`API Server` ↔ `service/api.py`；`Task Executor` ↔ 本工单新增的
   文档解析工作线程池；`向量数据库` ↔ FAISS 索引（`工单7/研发/data/index/bge-m3_1024`）；`Redis` ↔ 6379 实测可用。
2. **不臆造** RAGFlow 专有代码位置，所有「代码位置（文件:行）」都是本仓库里真实存在的行号。
3. 交付 `部署/docker/docker-compose.yml` 时补上 `--memory` / `--cpus` 资源限制与 Prometheus 监控
   （对应原文「备注2」与产出物3）。
