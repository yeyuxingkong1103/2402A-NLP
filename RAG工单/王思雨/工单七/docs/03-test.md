## 4. 检索结果存在的问题（数据 → 判断，逐条带证据）

### 问题 1｜模板页眉污染，占召回总量 28.7%（系统的账，最主要）

**证据**：80 条召回片段中 23 条的文本落在「跨页重复行首」家族里。最典型的是邮储银行（601658）：该文档 641 个分块中 **191 个**以同一条财务报表附注页眉开头（`中国邮政储蓄银行股份有限公司2019 年度财务报表附注…`）；对 Q06 而言，**8 条召回里 7 条是这种模板页**。

**后果**：这些页眉在向量与 BM25 两个通道上都被高分命中（查询里含公司名，而页眉恰好含公司名），挤占了真正的正文。Q05（Ctx.Pre 0.5）、Q03（0.25）、Q01（0.625）的低精确度都与此直接相关。

**根因**：PDF 逐页抽取会把页眉页脚写进每一页；而本语料的页眉被拆成多条**短行**（14~21 字），检索时既抬高了相似度又贡献了大量同质 token。

### 问题 2｜题面 `xx银行` 指代不明，系统多答（题面的账）

**证据**：Q01、Q02 的答案都并列了 2~3 家公司的内容；Q02 的 Faithfulness 因此只有 0.5。

**判断**：这不是检索故障——`sample_questions.pdf` 的原题用 `xx银行` 占位，系统无法判断指代谁，于是把命中的多家一并作答。**这些内容有原文支撑、无编造**。属于「题面本身需要澄清」的问题，正确处理是让系统反问或按「相关公司并列」输出；工单要求保留原题问法，故此处如实记录，不改题面。

### 问题 3｜两道题的高分答案却拿 0 分指标——是**造题的账**，不是系统的账

**证据**：Q03、Q04 的 Context Recall 都是 **0.0**，但人工复核答案完全正确。

**根因**：Q03/Q04 的 `ground_truth` 抄自 `sample_questions.pdf` 的参考答案，那份参考答案是**分析综述体**（"银行更多关注逾期贷款管理…保险公司侧重长期资产配置…"），而语料原文是**事实陈述体**。RAGAS 的 Context Recall 以 reference 的要点为单位去比对召回片段，措辞体系不同就判为未命中。

**判断**：这是**标准答案的写法**造成的，不是检索没找到。此处**不得**把 0 分算作系统缺陷——同一份召回在 Q05~Q10 那些「答案逐字取自 PDF」的题上都拿到 0.8~1.0 的召回。**经验**：reference 写成元陈述/综述体时，RAGAS 召回会系统性偏低。

### 问题 4｜长枚举型答案拿 0 分 Answer Relevancy（指标口径的账）

**证据**：Q04 的 Answer Relevancy = **0.0**，而该答案（1605 字）逐条引用四家公司原文、无幻觉。

**判断**：`AnswerRelevancy` 由答案反推问题再与原始问题比余弦相似度；答案越长、枚举越多，反推问题越泛化，得分越低。结合 Q04 的 Recall 也为 0，本题的指标不可用；Q04 的正确性以**人工复核**为准。

### 问题 5｜目标页层面的漏召（系统的账，次要）

**证据**：9 道有目标页的题中 7 道命中；Q10（国泰君安）召回到了 p.31 等页而非标准答案所在的 p.16/17，但**答案数字完全正确**。

**判断**：同一事实在年报中会在「董事会报告」「财务报表附注」等多处重复出现，检索命中另一处是**合理**的——页码命中率因此只适合作为诊断参考，不能单独当作召回失败。

## 5. MinerU 主解析路径冒烟验证

`python scripts/mineru_smoke.py` → `results/mineru_smoke.json`

| 项 | 实测 |
|---|---|
| 输入 | 邮储银行 PDF 的第 56–66 页（切出 11 页做成 ASCII 名副本） |
| 走的代码路径 | **`app.ingest.parse_mineru`（生产代码本体，非另写一份）** |
| 耗时 | **57.8 s / 11 页 ≈ 5.3 s/页** |
| 验收判据 | 产物中同时出现「绿色贷款」与「2,433.01」→ **均命中，`ok: true`** |

**由实测得到的两个结论**：
1. **主路径确实可用**，且能正确解析出标准答案所依赖的原文。
2. 按 5.3 s/页外推，语料 **2812 页 ≈ 4.1 小时**——这就是批量建索引使用 `MINERU_ENABLED=0`（降级 pymupdf）的实测依据，而非拍脑袋。

**同时实测出一个必须记录的环境坑**：盘上的中文文件名已被 `U+FFFD` 破坏，MinerU 在临时目录里会把它**二次乱码**，导致它找不到自己刚写出的产物而报 `FileNotFoundError`。修法：先把 PDF 复制成纯 ASCII 名（`data/src/<股票代码>.pdf`）再喂给 MinerU——该修复已落在 `app/ingest.py::parse_mineru` 中，上面的冒烟结果就是修复后跑出来的。
