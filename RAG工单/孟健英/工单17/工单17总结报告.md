## 一、任务描述

在工单十四完成 RAGFlow 部署、6 题 100% 准确率的基础上，系统进入试运行阶段。当模拟 10 个以上用户同时使用时，出现以下故障：

1. **响应延迟飙升**：问答接口平均响应时间从约 2 秒陡增至 10 秒以上
2. **内存泄漏**：API 服务器容器内存使用率持续增长，数小时后触发 OOM
3. **GPU 资源利用不当**：仅文本问答时 GPU 也被大量占用

**目标**：
- 场景 A（20 并发问答）：持续 10 分钟，P95 ≤ 3 秒，异常 0%
- 场景 B（10 并发混合负载）：持续 10 分钟，P95 ≤ 5 秒
- 12 小时稳定运行，内存增长 ≤ 20%

## 三、性能瓶颈定位

### 3.1 优化前基准

**单请求测试：**

```powershell
Measure-Command {
    Invoke-RestMethod -Uri "http://localhost:9380/api/v1/openai/{chat_id}/chat/completions" `
      -Method Post -Headers $headers -Body $body
}
```

**结果：27.9 秒**

### 3.2 日志分析

```
warn api_server models: eino generate failed, failing over to next model
     {"failed_model": "deepseek-v4-flash", "error": "failed to read response:
      read tcp ...->123.125.246.121:443: read: connection reset by peer"}

warn api_server Retrieval failed {"error": "search failed: GetVector failed:
     API request failed with status 429: {\"code\":\"1113\",
     \"message\":\"余额不足或无可用资源包,请充值。\"}"}
```

### 3.3 根因分析

| 层级 | 问题 | 影响 |
|---|---|---|
| **LLM 层** | DeepSeek API `connection reset by peer` | 每次调用失败重试，累计 20+ 秒 |
| **Embedding 层** | 智谱 `embedding-3` 报 429（余额不足） | 检索失败重试 |
| **VLM 层** | DeepSeek VLM `INTERNAL_ERROR` | 图像解析失败重试 |

**三层重试叠加**，单请求 20~30 秒。

### 3.4 瓶颈归属

**独立测试 siliconflow 的 API：**

```powershell
Measure-Command {
    Invoke-RestMethod -Uri "https://api.siliconflow.cn/v1/chat/completions" `
      -Method Post -Headers $headers3 -Body $body3
}
```

**结果：0.72 秒**

**结论**：**LLM 本身快，RAGFlow 内部调用链路有瓶颈**。

## 四、优化方案实施

### 4.1 优化 1：换 LLM

| 项 | 优化前 | 优化后 |
|---|---|---|
| LLM | `deepseek-v4-flash` | `Qwen2.5-7B-Instruct (siliconflow)` |
| API | DeepSeek 官方（连接被重置） | siliconflow（国内节点稳定） |
| 单次调用 | 20+ 秒 | 0.72 秒 |

**配置：**

```
Model providers → OpenAI-API-Compatible
Instance name: siliconflow
API Key: sk-cbzdzkfwzhotyusrqxomuxtyccfewqpalhyrgrwneixgsbgx
Base URL: https://api.siliconflow.cn/v1
Models: Qwen/Qwen2.5-7B-Instruct
```

### 4.2 优化 2：换 Embedding

| 项 | 优化前 | 优化后 |
|---|---|---|
| Embedding | `embedding-3 (ZHIPU-AI)` | `BAAI/bge-m3 (siliconflow)` |
| 维度 | 2048 | 1024 |
| 费用 | 需充值 | 免费（实名后） |
| 稳定性 | 429 余额不足 | 稳定 |

**问题处理：**
- 不同 Embedding 维度不同，**必须重建知识库**
- 知识库 `工业PDF测试2` 删除重建，Embedding 选 `BAAI/bge-m3 (siliconflow)`

### 4.3 优化 3：关闭 VLM

- 用**手动生成的 `page11_caption.txt`** 代替 VLM 图像描述
- 避免 DeepSeek VLM `INTERNAL_ERROR` 和智谱 GLM-4V `429`
- 解析模板：Paper + 禁用视觉模型

### 4.4 优化 4：重建聊天应用

- LLM：`Qwen2.5-7B-Instruct (siliconflow)`
- 知识库：`工业PDF测试2`

## 七、问题分析

### 7.1 为什么优化前 27 秒

| 阶段 | 耗时 | 原因 |
|---|---|---|
| LLM 调用 | 15~20 秒 | DeepSeek 连接被重置，多次重试 |
| Embedding 调用 | 5~8 秒 | 智谱 429 余额不足，多次重试 |
| VLM 调用 | 2~5 秒 | DeepSeek VLM INTERNAL_ERROR |

**三层重试叠加，总耗时 27+ 秒。**

### 7.2 为什么优化后 1.71 秒

| 阶段 | 耗时 | 优化 |
|---|---|---|
| LLM 调用 | 0.7~1 秒 | siliconflow 国内节点，无重试 |
| Embedding 调用 | 0.1~0.3 秒 | bge-m3 免费，无重试 |
| 检索 + 组装 | 0.5~1 秒 | RAGFlow 内部 |

**无失败重试，效率提升 15 倍。**

### 7.3 内存无泄漏的原因

- RAGFlow 使用 Go + Python 混合架构，内存管理良好
- siliconflow API 调用不缓存大量中间结果
- 10 分钟压测内存增长 0.2%，符合稳定运行预期

## 八、经验总结

### 8.1 性能调优方法论

1. **假设-验证-修改**：每次优化只改一个变量，对比数据
2. **分层定位**：LLM 层、Embedding 层、VLM 层分别独立测试
3. **独立基准**：绕开 RAGFlow，直接调 LLM API，确定瓶颈归属

### 8.2 关键教训

- **稳定性优先于功能**：DeepSeek VLM / 智谱 embedding 虽然功能全，但重试率极高
- **国内节点优势**：siliconflow 国内节点比 DeepSeek 官方快 30 倍
- **免费资源的可靠性**：bge-m3 免费且稳定，适合生产环境

### 8.3 进一步优化方向

| 方向 | 预期效果 |
|---|---|
| Prometheus + Grafana 监控 | 实时可视化 |
| Redis 缓存常见问题 | 重复问题 0 秒返回 |
| 连接池优化 | 高并发下更稳定 |
| 请求队列限流 | 防请求堆积 |
| 部署到 Linux 服务器 | 性能再提升 |
