## 2. 逐条排查

### 2.1 瓶颈一「每个请求独立初始化重量级组件」——**本仓库不存在该写法（如实记录）**

工单原文推测「每个请求可能都在独立初始化重量级的文档解析器（DeepDoc）或视觉语言模型」。
本仓库的基座是工单7 的同源 RAG 系统，**没有 DeepDoc、没有 VLM**（本机无任何视觉模型）。
逐点核实构造时机：

| 组件 | 核实结果 | 代码位置 |
| --- | --- | --- |
| `QAEngine` | **模块级单例**，`service/api.py` 里 `RUNTIME = Runtime(...)`，`lifespan` 只调一次 `setup()` | `service/api.py:208`、`service/api.py:214-217` |
| FAISS / BM25 索引 bundle | **模块级缓存 + 锁**：`_BUNDLE_CACHE: dict[str, IndexBundle]` + `_BUNDLE_LOCK` | `app/core/retriever.py:158-159`、`retriever.py:302-311` |
| 语料 id 集合 | 模块级 `_CORPUS_ID_CACHE` | `app/core/retriever.py:426` |
| 多级缓存 | 进程级单例 `_CACHE_SINGLETON` + `_CACHE_LOCK` | `app/core/cache.py:293-304` |
| 重排器 | **无模型**（确定性八特征），无初始化成本 | `app/core/reranker.py` |
| LLM 客户端 | `QAEngine.llm` 属性**惰性解析并缓存**（`_llm_resolved`） | `app/core/qa_engine.py:186-204` |
| **嵌入后端探测** | ❌ **每次调用都重新探测** | `app/core/embedder.py:299` |

**结论**：`R4「每个请求重复初始化解析器/模型」在本仓库不成立，不编造该条。**
逐条核实后**唯一真实存在**的「重复劳动」是**嵌入后端探测**：

```python
# app/core/embedder.py:286-302（基座）
def embed_texts(texts, *, cfg=None, batch_size=16, logger=None):
    ...
    backend = resolve_embedding_backend(config, probe=True, logger=log)   # ← 每次调用都真探
```

而 `resolve_embedding_backend(probe=True)` 内部会发起：

```python
# app/core/embedder.py:101（基座）
data = _http_json(f"{config.llm.ollama_base_url}/api/tags", None, config.llm.probe_timeout_s)
```

⇒ **每一次问答都多打一次 `GET /api/tags`**。20 并发下就是每秒几十次无意义往返。

**证据（实测）**：`测试/测试数据/剖析问答链路_优化前.json` 与 `..._优化后.json`
（`urllib.request.urlopen` 被 monkeypatch 计数，数字见 §3.3）。

### 2.2 瓶颈二「请求处理无队列/限流」——**完全成立且可核实**

```python
# service/config.py:119（基座）
max_concurrency: int = 4
```

**全仓库 grep 实证：这个配置项只有定义那一行，零处引用。**

```powershell
PS> Select-String -Path 研发\service\*.py,研发\app\**\*.py -Pattern 'max_concurrency'
研发\service\config.py:119:    max_concurrency: int = 4        # ← 仅此一处
```

⇒ 服务**没有任何入口限流**：20 个并发请求全部直接冲进业务逻辑，
每个请求要跑「检索 + Ollama 生成」（实测 retrieve 197 ms + generate 1171 ms），
在途请求只会越堆越多 —— 这正是工单原文「平均响应从约 2 秒陡增至 10 秒以上」的机制。

同时 `service/api.py:417` 的 `ask` 是**同步 `def`**，
FastAPI 会把它丢进 anyio 默认 40 线程的线程池；慢请求会把线程池占住，
连新增的探针请求都要排队。

**证据（实测，同一负载下并发升高导致延迟膨胀）**

| 口径 | 并发 | P50 | P95 | RPS |
| --- | --- | --- | --- | --- |
| 冒烟（同一批问句，全部缓存命中） | 3 | 31.24 ms | 58.85 ms | 17.5 |
| 基准 场景A（同一批问句，全部缓存命中） | 20 | **208.57 ms** | **517.40 ms** | 82.0 |

**同一批「缓存命中」请求，并发从 3 提到 20，P50 涨 6.7 倍、P95 涨 8.8 倍**
—— 请求本身没变重，变的是**串行化竞争**。§2.5 给出竞争的四个具体位置。

### 2.3 泄漏点一「全局缓存/会话未释放」——**成立（三处 + 一处竞态）**

#### (a) `qa_engine._memory_cache`：**无锁 + 无 TTL**

```python
# app/core/qa_engine.py:128（基座）
self._memory_cache: "OrderedDict[str, Answer]" = OrderedDict()
```

```python
# app/core/qa_engine.py:487-500（基座）—— 上下文里没有一把锁
def _cache_put(self, key, answer):
    limit = int(getattr(self.cfg.retrieval, "cache_size", 512))
    self._memory_cache[key] = answer
    self._memory_cache.move_to_end(key)
    while len(self._memory_cache) > limit:
        self._memory_cache.popitem(last=False)
```

**两个问题**：

1. **线程不安全**：`OrderedDict` 不是线程安全的；多线程并发 `move_to_end` / `popitem`
   会撞坏内部双向链表（CPython 下表现为偶发 `KeyError` / 结构不一致）。
   而 `ask` 是在线程池里并发执行的 —— 这是**并发下偶发 500 的直接隐患**。
2. **无 TTL**：条目只在容量满时被 LRU 淘汰；问句不重复时缓存只涨不掉。
   且 >**条目的内存代价很大**：`Answer.chunks` / `evidence` 里存的是 `_hit_payload(h)` 的
   **整块全文**（`with_text=True`，每块可达 1200+ 字符 × 10 块），单条 30~60 KB，
   512 条即 **15~30 MB** 常驻。

#### (b) `answer_cache` 表：**只增不减**

```sql
-- app/storage/sqlite_manager.py:61-67（基座）
CREATE TABLE IF NOT EXISTS answer_cache (
    cache_key TEXT PRIMARY KEY, question TEXT NOT NULL, payload TEXT NOT NULL,
    created_at REAL NOT NULL, hits INTEGER NOT NULL DEFAULT 0);
```

基座只有 `INSERT OR REPLACE`（`sqlite_manager.py:185`）、`UPDATE hits`（`:199`）、
`SELECT`（`:210`）—— **没有任何 DELETE、没有过期**。连续运行数小时后表会无限增长
（这是**落盘侧**的「随运行时间持续缓慢增长」，不体现在 RSS 上，但同样会撑爆磁盘）。

#### (c) 会话文件卷：**无上限、无物理删除**

```python
# service/session_store.py:250-257（基座）
def load(self, session_id):
    data = self._read(self._path(session_id))
    if self.ttl_s > 0:
        updated = float(data.get("updated_at") or 0.0)
        if updated and (time.time() - updated) > self.ttl_s:
            data["expired"] = True        # ← 只在返回体里打个标记，文件照样留在盘上
    return data
```

配合 `service/api.py:441` 每个请求都会 `sessions.append(sid, Turn(...))`，
而 `sid` 来自客户端的 `session_id` —— **只要客户端不断用新的 session_id，
会话卷就会无限增长**，并且每次 `append` 都是一次
「读全文件 → 追加 → 序列化 → 写 .tmp → `os.replace`」，**全程持一把全局锁**。

**证据（实测）**：跑完「多用户口径」压测后 Redis db15 的会话键数：

```json
// 测试/测试数据/redis统计_优化后.json
{ "session_keys": 5003, "dbsize": 19552,
  "stats": { "total_commands_processed": 281143, "keyspace_hits": 67695 } }
```

即一轮压测就往会话存储里灌了 **5003 条会话**（`--unique-sessions` 口径）。

### 2.4 泄漏点二「数据库/向量库连接池泄漏」——**部分成立，如实区分**

| 组件 | 核实结果 |
| --- | --- |
| **sqlite** | ❌ **不是泄漏**。`app/storage/sqlite_manager.py:124` 已是**单连接 + 互斥锁 + `check_same_thread=False`**，连接被正确复用，不存在「每请求新建连接」。 |
| **FAISS / 向量库** | ❌ **不是泄漏**。FAISS 是**进程内内存索引**（`IndexFlatIP`），没有网络连接概念；`milvus_store.py` 是可选适配器，`pymilvus` 未安装、未被使用。 |
| **外部 HTTP（Ollama）** | ✅ **成立**。见下。 |
| **sqlite 落盘** | ✅ **成立（瓶颈而非泄漏）**。见下。 |

#### (a) 所有外部 HTTP 都是「每请求新建 TCP」

基座的全部外部 HTTP 调用都用 `urllib.request.urlopen`（**不复用连接**，读完即关）：

| 文件:行 | 调用 | 频率 |
| --- | --- | --- |
| `app/core/llm_client.py:92` | `_http_json`（探测/预热） | 每次探测 |
| `app/core/llm_client.py:239-245` | `_stream_ollama` | **每次生成** |
| `app/core/llm_client.py:278-283` | `_stream_openai` | 每次生成（openai 后端） |
| `app/core/embedder.py:84` | `_http_json` | **每次嵌入** |

一次问答至少 2 次 Ollama 往返（embed + generate），加上 §2.1 的探测共 3 次，
**20 并发下即 60 次/秒的建连-断连**，产生大量 TIME_WAIT 并抬高尾延迟。

#### (b) 每请求 3~4 次 `commit()`，全部串行在同一把锁上

一次问答的落盘次数（基座，每处都是一次 `commit()` → 默认 DELETE journal + FULL sync → 一次 fsync）：

| 方法 | 行号 | 每请求次数 |
| --- | --- | --- |
| `record_qa` | `sqlite_manager.py:155` | 1 |
| `save_answer_cache` | `sqlite_manager.py:190` | 1（缓存未命中时） |
| `bump_cache_hit` | `sqlite_manager.py:200` | 1（缓存命中时） |
| `touch_session` | `sqlite_manager.py:176` | 1 |

四处**都在 `with self._lock:` 里**（`sqlite_manager.py:144/168/184/198`）——
即 20 个并发请求会在这一把锁上排成一队做 fsync。

### 2.5 附加发现：**真正的 OOM 崩溃根因**（工单原文「内存泄漏与崩溃」）

工单原文：「API 服务器的容器内存使用率随运行时间持续缓慢增长，
在连续运行数小时后触发内存限制（OOM Killer），导致服务崩溃重启。」

**核实**：工单10 交付的 `部署/docker/docker-compose.yml` 给 `rag-api` 的限制是：

```yaml
deploy:
  resources:
    limits:
      cpus: "${API_CPUS:-2.0}"
      memory: ${API_MEMORY:-2g}     # ← 2 GB
```

而工单10 **自己实测**的 API 私有内存峰值是 **2.41~2.44 GB**
（`工单10/优化/评估结果/`），本工单开工时实测 API 进程私有内存 **2429.78 MB**。

> **上限（2 GB）比实测占用（2.4 GB）还小** ⇒ 容器一进入稳定运行就贴着 limit 跑，
> 任何一点堆积都会触发 OOM Killer 重启。**这就是原文「崩溃重启」的直接根因之一。**

**另一个隐藏原因**：Compose V2 在**非 swarm 模式**下 `deploy.resources` **不生效** ——
必须显式写 `mem_limit` / `cpus`。工单10 的 compose **只有** `deploy.resources`，
所以「配了限额却仍被 OOM」与「限额其实没生效」两种情况都可能出现。

**修复**：本工单把默认上限提到 **3g**（实测 2.4 GB + 20 % 余量），
并显式补齐 `mem_limit` / `memswap_limit` / `cpus`（见 `部署/docker/docker-compose.yml`）。

### 2.7 附加发现：**磁盘泄漏 16.2 GB**（上传无去重 + 日志无轮转）

内存之外，本工单在**落盘侧**发现了同构且量级更大的泄漏，实测证据见
`测试/测试数据/存储卷取证_清理前.json` 与 `部署/卷/清单_暂停时快照.md`。

#### (a) 上传路径无内容去重 —— **99.61 % 是重复字节**

```python
# service/task_queue.py::submit（基座/优化前）
target = self.upload_dir / f"{task_id}__{safe}"
target.write_bytes(content)          # ← 每次都落一份完整副本，没有任何内容比对
```

文件名前缀是**每次新生成的 task_id**，所以同一份 PDF 上传 N 次就留 N 份副本。

**实测证据（只读扫描，`研发/剖析/分析存储卷.py`）**：

| 指标 | 实测值 |
| --- | --- |
| `部署/卷/uploads` 文件数 | **2304** |
| 占用 | **15430.2 MB（15.07 GB）** |
| 按「原始文件名 + 字节数」归并后的**唯一内容组** | **10 组** |
| 被判定的重复浪费 | **15369.9 MB（99.61 %）** |
| 抽样 SHA256（每组取 8 份） | **内容全同 = True**（3 组抽样全部一致） |
| 单组最大重复 | 中信证券年报 **250 份 × 9.66 MB**，浪费 2404.2 MB |
| 存储卷合计（uploads+logs+sessions+runtime） | **16210.3 MB（16.2 GB）** |

#### (b) 业务日志无轮转 —— **单文件 600 MB 且只增不减**

```python
# app/core/logging_conf.py（基座）
self._handles = {
    "app": _open_append_atomic(self.log_dir / "app.log"),      # ← 裸句柄：无 maxBytes、无 backupCount
    "error": _open_append_atomic(self.log_dir / "error.log"),

```

**关于 F9 的诚实说明**：工单10 的 API **没有上传/解析端点**，
所以「优化前」的对照口径是本工单**如实重建**的反模式 ——
**同一个 `parse_pdf()` 函数**，优化前在请求线程里同步跑完才返回（`parse_sync`），
优化后进有界队列由工作线程池消费（`ParseQueue`）。
两者唯一差别是「在哪个线程跑、有没有队列」，**不是伪造的性能差异**。

### 5.3 资源泄漏验收（**12 小时不可行的如实说明**）

- **原文要求**：连续运行 12 小时后 RSS 增长 ≤20 %。
- **本机现实**：API 进程私有内存实测 **2.41~2.44 GB**；本机可用物理内存开工基线 **4472~4574 MB**；
  `_共享约定.md §5.5` 记录过两次 OOM 事故（提交内存冲到 93 %/96 %，浏览器标签页被顶崩）。
  连续 12 小时压测在本机**不具备可行性**。
- **本工单做法**：跑**缩短版 soak**（`--scenario A --concurrency 8`，
  实测时长见 `测试/测试数据/soak_优化后_场景A_summary.json`），
  给出私有内存/RSS 的**首末窗口增长**与**线性回归斜率**；
  用斜率**外推**到 12 小时。
- **标注**：外推结论一律标 **`[外推]`**，**不得当作实测值引用**。
  实测曲线见 `测试/测试数据/soak_优化后_场景A_mem.jsonl` 与
  截图 `测试/测试截图/内存RSS增长曲线.png`。
- **更强的证据**：`tracemalloc` 快照 diff 的 Top-N（`测试/测试数据/tracemalloc_*.json`）
  —— 判据是「`size_diff_kb` 为正且随轮次持续增长」的调用点。
  修复后这些调用点全部带上界（F5/F6/F8），实测 Top-N 见
  截图 `测试/测试截图/tracemalloc泄漏对象Top20.png`。

### 5.4 时长缩减的口径（**不假装跑了 10 分钟**）

| 项 | 原文 | 实测 | 原因 |
| --- | --- | --- | --- |
| 场景A/B 时长 | 600 s | **180 s** | 本机可用内存 4472~4574 MB；API 私有内存 2.41~2.44 GB；两次 OOM 事故红线 |
| soak | 43200 s（12 h） | **600 s（10 分钟）** | 同上；改用斜率外推并标注 `[外推]` |
| **并发数** | 20 / 10 | **20 / 10（不缩）** | 并发才是瓶颈触发器 |

**并发数一律不缩减**，只缩时长；缩减后仍在报告与测试报告中逐处标注。

## 7. 结论

1. **并发瓶颈是真实的，位置与工单原文的推测不完全一致**：
   不在「模型重复初始化」，而在**入口零限流 + 每请求多一次探测 + 每请求新建 TCP +
   每请求 4 次串行 fsync**（§2.1~§2.2、§2.4）。
2. **崩溃的直接根因找到了**：容器内存上限（2 GB）小于实测占用（2.4 GB）+
   Compose V2 非 swarm 模式下 `deploy.resources` 不生效（§2.5）。
3. **泄漏点全部落地**：答案缓存（无锁/无 TTL）、缓存表（只增不减）、会话文件（无删除）、
   Ollama 显存（`keep_alive="30m"` 且无卸载路径），修复后都有**可配置的上界**。
4. **效果可复现**：场景A 多用户 P95 **3608 → 395 ms**、
   场景B 问答 P95 **8824 → 604 ms**、GPU 显存 **3102 → 947 MiB**，
   全部数据在 `优化/评估结果/` 与 `测试/测试数据/` 可追溯。
5. **未达标/未实测项已在 §6 逐条列出**，不做粉饰。
