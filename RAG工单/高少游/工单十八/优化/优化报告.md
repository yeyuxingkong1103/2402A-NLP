# 文档质量评估 Skill 优化报告

工单编号：人工智能NLP-RAG-实现文档质量评估Skill并集成至智能体工作流

## 1. 优化总览

本工单的优化不是纸面推演，而是「真实跑 → 发现问题 → 改 → 复测」的闭环。全部优化项都由真实运行暴露，且都带回测数据。汇总如下。

| 编号 | 优化项 | 类型 | 关键收益 |
|---|---|---|---|
| O1 | 路由顺序修正，扫描型 PDF 优先走 OCR | 正确性 | 修复 622 份扫描型文档被误拦的缺陷 |
| O2 | SimHash 阈值由 3 校准为 8 | 召回 | 近似重复命中由 0 对提升到 16 对，误报 0 |
| O3 | 非 PDF 子类型标签去重 | 可读性 | 消除 `markdown, markdown` 类重复标签 |
| O4 | 验证脚本临时目录隔离 | 可复现性 | 样本目录文件数不再被污染 |
| O5 | 并行度由经验值改为按核数自适应 | 性能 | 避免 8 进程过度订阅，本机取 4 最优 |
| O6 | 断点续跑 | 性能 | 二次运行 24.97s → <0.1s |
| O7 | 报告列表截断 | 体积 | HTML 简报控制在百 KB 量级，明细仍全量留档 |

## 2. O1 路由顺序修正（正确性）

**问题现象。** 首次在真实数据集上运行时，622 份扫描型 PDF 全部被路由到 `manual_review` 人工复核，OCR 链路形同虚设。

**根因。** 分类路由的最初实现先判「空文本」——`char_count` 为 0 即视为空文档。扫描型 PDF 天然没有可抽取文本，于是被空文档规则先一步拦下，永远走不到按 PDF 类型分派的分支。

**优化。** 调整 `src/classifier.py` 的判定顺序为三段式：

1. 先按内容类型定路由：扫描型必走 `ocr_parser`，文字型走 `text_parser`，混合型走 `hybrid_parser`；
2. 再应用完全重复规则，命中的归入 `dedup_review`；
3. 最后才轮到损坏与空文档兜底。

**回测。** 修正后全量运行路由结果为 `{'ocr_parser': 622, 'text_parser': 1078}`，622 份扫描型文档全部正确进入 OCR 队列，`manual_review` 归零。

## 3. O2 SimHash 阈值校准（召回）

**问题现象。** 初始阈值取 3 时，1700 份真实专利 PDF 的近似重复命中为 0 对，与数据集中确实存在的同族版本（如同一专利的 A/B/C 公开号）不符。

**根因。** 阈值凭经验设定，未在真实数据分布上校准。专利正文较长，即使高度相关的文档，SimHash 汉明距离也普遍偏大。

**优化。** 抽取 120 份真实专利做两两比对，实测**无关文档的最小汉明距离为 17**，据此把 `dedup.simhash_hamming_threshold` 由 3 调到 8——取一个明显低于 17 又能容纳版本微调的值。校准依据写入 `assessment_config.yaml` 注释，换数据集可直接复现。

**回测。** 阈值 8 下，1700 份文件命中近似重复 **16 对**，同时完全重复组仍为 0、无假阳性。召回显著提升且没有以误报为代价。

## 4. O3 标签去重（可读性）

**问题现象。** 非 PDF 文档（如 Markdown）在报告里出现 `markdown, markdown` 的重复标签。

**根因。** 分类时既追加了「格式族」标签，又追加了与格式族同名的「子类型」标签。

**优化。** 在 `src/classifier.py` 中增加判断：仅当子类型名与格式族名不同时才追加子类型标签。PDF 的 `text_pdf / scanned_pdf` 与格式族 `pdf` 不同名，标签不受影响。

**回测。** 单元测试 `test_markdown_and_spreadsheet` 覆盖该路径，标签输出为单一 `markdown`。

## 5. O4 验证脚本隔离（可复现性）

**问题现象。** 边界用例目录的文件数从 6 变成 7，多出一个 `_val_tmp` 产物，导致复现时用例集不确定。

**根因。** `tools/validate_quality.py` 把验证用的临时输出写在了被扫描的样本目录内部，而验证本身又会扫描该目录，形成自污染。

**优化。** 改用 `tempfile.mkdtemp()` 输出到系统临时目录，运行结束 `shutil.rmtree()` 清理。

**回测。** 反复执行验证脚本，样本目录文件数稳定为 6，验证结果可重复。

## 6. O5 并行度自适应（性能）

**问题现象。** 并行度若一味取大，吞吐不再提升甚至下降。

**根因。** 本任务是 I/O 密集型，瓶颈在磁盘读取 PDF，超过磁盘并发能力后，多余进程只增加调度与内存拷贝开销。

**优化与实测。** 固定 500 份子集测得扩展曲线：

| workers | 总耗时(s) | 吞吐(文件/秒) | 加速比 |
|---|---|---|---|
| 1 | 23.9 | 20.92 | 1.00× |
| 2 | 16.8 | 29.90 | 1.42× |
| 4 | 13.2 | 37.91 | 1.81× |
| 8 | 13.5 | 37.31 | 1.77× |

曲线在 4 进程饱和。据此 `scan.workers` 默认取「配置值与 CPU 核数的较小者」，避免过度订阅。详细分析见 `测试/性能测试报告.md`。

## 7. O6 断点续跑（性能）

**问题现象。** 调参后重跑会重新解析全部 1700 份 PDF，每次约 25 秒，迭代成本高。

**优化。** 逐文件结果实时追加写入 `.qcheck/records.jsonl`（每 `flush_every` 条落盘一次），重跑时按 `rel_path` 跳过已完成文件。

**回测。** 首次 24.97 秒；二次运行 1700 份全部跳过，恢复耗时不足 0.1 秒，下降三个数量级。调参迭代从「每次 25 秒」变为「每次几乎瞬时」。

## 8. O7 报告体积控制（体积）

**问题现象。** 1700 份文件的完整明细若全部铺进 HTML，简报体积会失控，质检员难以阅读。

**优化。** 待确认、版本冲突、敏感信息等列表按 `report.top_n_lists` 截断，完整明细仍保留在 JSON 的 `files` 段。

**回测。** 全量运行的 JSON 报告 685 KB、HTML 简报 87 KB，体量可控且不丢数据。

## 10. 结论

七项优化全部落地并回测。其中 O1 修复的是会直接导致 OCR 链路失效的正确性缺陷，价值最高；O2 通过真实数据校准把去重从「形同虚设」变为可用；O5、O6 面向工程效率，让性能与迭代成本都落到可接受的量级。优化后的系统在真实数据集上零失败、指标达标，达到可交付状态。
