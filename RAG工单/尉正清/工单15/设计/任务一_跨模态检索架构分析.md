# RAGFlow 多模态检索架构分析

**工单编号**：人工智能NLP-RAG-优化技术图纸与文本的跨模态检索流程
**源码版本**：附件 `ragflow-main`（RAGFlow v0.23.1）；**运行代码**是镜像
`infiniflow/ragflow:v0.23.1`，两者略有差异，本文行号以附件为准，用于改动时
以 `docker cp` 出来的镜像版本为准（见 `优化/过程问题记录.md`）。

## 一、一次提问的完整检索链路

```
用户提问
  │
  ▼ api/db/services/dialog_service.py:417  retriever.retrieval(...)
  │
  ├─(1) 查询理解与改写 ───────────────────────────────────────────
  │     · 多轮改写   full_question()          dialog_service.py:350
  │     · 跨语言     cross_languages()        dialog_service.py:355
  │     · 关键词抽取 keyword_extraction()     dialog_service.py:368（默认关）
  │     · 切词/加权/同义词  Dealer.question()  rag/nlp/query.py:41
  │
  ├─(2) 多路召回 ────────────────────────────────────────────────
  │     同一问句同时构造两路：BM25 文本路 + 向量路
  │     · 文本路  MatchTextExpr ← Dealer.question()
  │     · 向量路  MatchDenseExpr(vector_column, embedding, 'cosine', topk)
  │                                            rag/nlp/search.py:61
  │     · 两路在 ES 内部用 weighted_sum 融合    rag/nlp/search.py:128
  │       ⚠️ 权重是**写死的** "0.05,0.95"（文本 0.05 / 向量 0.95）
  │
  ├─(3) 重排 ────────────────────────────────────────────────────
  │     rag/nlp/search.py:404-428
  │     · 配了重排模型 → rerank_by_model()      search.py:334
  │       交叉编码器打分，与 BM25 分数再加权：
  │       sim = (1-w)·token_similarity + w·rerank_score
  │     · 没配 → rerank()                       search.py:295
  │       sim = tkweight·token_similarity + vtweight·vector_similarity
  │       （hybrid_similarity，rag/nlp/query.py:176）
  │
  ├─(4) 阈值过滤 + 分页 ─────────────────────────────────────────
  │     valid_idx = [i for i in 排序 if sim[i] >= similarity_threshold]
  │                                            rag/nlp/search.py:437
  │     注意：**重排在阈值之前**（404 在 437 前面），所以重排能把
  │     本来要被阈值滤掉的块拉回来。
  │
  └─(5) 组装 Prompt ─────────────────────────────────────────────
        kb_prompt() 把命中的块拼成 "ID: 0 / Title / Content" 段落
                                            dialog_service.py:448
        套进助手提示词的 {knowledge}          dialog_service.py:461
```

### 检索请求里带了哪些字段

`rag/nlp/search.py:95` 的 `src` 列表决定每块取回什么，与图文相关的有：

| 字段 | 含义 |
|---|---|
| `content_with_weight` | 块的正文（图和表的描述也在这） |
| `img_id` | 块关联的图片标识（图片型内容才有） |
| `position_int` / `page_num_int` / `top_int` | 位置戳：页码与版面坐标 |
| `content_ltks` / `title_tks` | 切词结果，BM25 用 |

## 二、图是怎么进到检索里的

RAGFlow **没有独立的多模态向量索引** —— 图片先被转成文字，再和正文一样走
同一套文本检索。链路是：

```
解析阶段（离线）
  deepdoc/parser/pdf_parser.py  _extract_table_figure()
     把版面识别为 figure 的区域裁出来，连同 OCR 出来的图注一起产出
        ↓
  deepdoc/parser/figure_parser.py:84  vision_figure_parser_pdf_wrapper()
     触发条件：LLMBundle(tenant_id, LLMType.IMAGE2TEXT) 构造成功
        ↓
  deepdoc/parser/figure_parser.py:112  VisionFigureParser.__call__()
     把每张图交给多模态模型描述，描述文本 + 图注 一起成为块的正文
        ↓
  rag/app/naive.py:1031  tokenize_chunks_with_images()
     与普通文本块同等对待地入库、切词、向量化
```

**结论**：所谓「跨模态检索」，在这个版本的 RAGFlow 里就是
**「图片先变成一段文字，再按文字检索」**。因此图纸上的信息能不能被检索到，
取决于两件事：**描述生成得好不好**，以及**检索时能不能定位到那一块**。

## 三、识别出的瓶颈

### 瓶颈1（对应工单「故障1 检索无关」）：查询里的泛词把不相干的文本块顶上来了

复现：问「在文件中第11页图3中，编号13的部件相对于编号12的部件…」。

`Dealer.question()`（`rag/nlp/query.py:41`）会把问句切成词并加权，
「部件」「编号」「装置」这类泛词权重不低，而 **ES 侧的融合权重写死为
`0.05 文本 : 0.95 向量`**（`search.py:128`）。于是：

| 排名 | 命中块 | 相似度 | 内容 |
|---|---|---|---|
| 1 | 图3 描述 | 0.320 | 图纸几何描述 |
| 2 | 图例说明页 | 0.294 | 列了「图1/图2/图3」各是什么的清单 |
| 3 | **权利要求书** | 0.273 | 「10．按权利要求1所述的装置…」——**提到编号 10~14，但根本没有图** |
| 4 | 部件说明段 | 0.265 | 「落料架10…紧固机构11…保护管12…链条13」 |

第 3 名那种块正是工单说的「返回大量提及部件编号但不含图3 的文本块」。

### 瓶颈2（对应工单「故障2 图文割裂」）：没有任何机制把「图3」绑定到某一块

问句里的「第11页图3」在检索层是**普通文本**。系统并不知道：

- 哪一块讲的是图3；
- 这一块在第几页。

`position_int` / `page_num_int` 虽然取回来了（`search.py:95`），但**没有任何
排序逻辑用到它们**；图号更是只以 OCR 文字的形式零散混在正文里
（本项目实测图注被 OCR 成 `图3 图 2 1` 这种糊成一团的样子），无法可靠匹配。

后果：即便图3 的描述被召回，它也**无法被稳定地排到前面**，只能靠向量相似度
碰运气。第 6 题就是典型 —— 检索到的前几名全是正文段落，图3 的描述压根没进
Top-4，模型只能靠猜（详见 `测试/测试报告.md`）。

### 瓶颈3：图纸描述本身可能张冠李戴

`VisionFigureParser.__call__()`（`figure_parser.py:154`）只把**裁出来的图**
和一段固定提示词交给多模态模型，**不告诉它这是第几页、第几张图**。而
`_extract_table_figure` 会把相邻页的图合并成一块，图注也一起拼进来。实测
第 11 页的图块图注是 `图3 图 2 1`，多模态模型在自己的描述里把标题读成了
「图 2」。**没有任何地方记录这块到底对应哪张图。**

## 四、本次优化的方案设计

围绕上面三个瓶颈，改两处代码 + 一处配置，都只动检索打分，不改索引结构：

### 改动1：解析层给图纸块打「图号 + 页码」标记

`deepdoc/parser/figure_parser.py` 新增 `_mark_figures()`，在图纸描述前加一行：

```
【技术图纸】图3/图2｜第10页｜第11页
```

- **图号**取自 OCR 图注（不是多模态模型自己写的正文 —— 实测它会读错），
  且**全部列出**：一块常跨页或把相邻图注一起吸进来，只取第一个会漏。
- **页码**取自位置戳 `positions`（`pdf_parser.py` 的 `cropout()` 里
  `poss.append((页码, left, right, top, bottom))`）。跨页的每一页都写出来。

这一步解决瓶颈2 —— 图纸块从此**可被确定地定位**。

### 改动2：检索层做查询理解 + 视觉条件加权融合

新增 `rag/nlp/visual_query.py`，在 `rag/nlp/search.py` 的 `retrieval()` 里
算完融合分之后、阈值过滤之前调用：

```python
sim, _ = boost_scores(sim, sres, question)     # search.py:430 附近
```

| 步骤 | 做什么 |
|---|---|
| `parse_visual_refs()` | 从问句里抽图号（`图3`/`附图3`/`图三`）和页码（`第11页`） |
| `visual_score()` | 带 `【技术图纸】图N` 标记、且图号或页码对得上的块，在融合分上加分 |
| **页码当闸门** | 问句写了页码时，标记里不含该页的块**一律不加分**（否则「图例清单」那种块会被误伤） |

这就是工单里写的「对结果进行融合（如**加权分数**…）」—— 视觉条件作为一路
信号，以加权分数的形式并进最终排序分。之所以用标记匹配而不是再跑一路向量
检索：图号是**确定性**信息（问题说图3，就只有图3 那块是对的），字符串匹配
既准又便宜，不必再引入一路召回和它的不确定性权重。

### 改动3：生成侧 —— 提示词模板与思维链档位

- **助手提示词**：明确「题目提到某张附图时，优先采用带【技术图纸】标记、
  图号或页码对得上的那一段描述，再结合正文；两者冲突时以正文为准」，
  并约定「物料依次经过哪些部件」只统计真正穿过或被其作用的零件
  （链条、接点），容器类（落料架、外壳、保护管）不算。
- **思维链档位**：工单14 为压到 ≤3s 一律关掉思维链；本工单性能预算是
  3-5s，而图文题需要把「图纸描述」和「正文部件说明」对照着读，
  完全不给思考就容易在选项间乱跳（实测同一题 B/A/D 反复变）。
  改为外部可配，取 `low`。

### 外部可配项

| 配置 | 位置 | 说明 |
|---|---|---|
| `enabled` / `figure_boost` / `page_boost` / `marker` | `研发/conf/visual_rag.json` → 容器 `/ragflow/conf/visual_rag.json` | 融合权重与开关 |
| 同名环境变量覆盖 | `研发/ragflow/docker/.env` | `VISUAL_RAG_FIGURE_BOOST=0.8` 这样写 |
| `RAGFLOW_REASONING_EFFORT` | 同上 | `none` / `low` / `high` / `max` |
| `RAGFLOW_MAX_TOKENS` | 同上 | 思维链与正文共用的额度下限 |

## 五、优化后的链路（对比）

```
用户提问「在文件中第11页图3中，编号13的部件相对于编号12的部件…」
  │
  ├─ 查询理解：抽到 {figures:[3], pages:[11]}
  ├─ 多路召回：BM25 + 向量（同原流程）
  ├─ 重排：交叉编码器（同原流程）
  ├─ 【新增】视觉条件加权融合：
  │     带「【技术图纸】…图3…第11页…」标记的块 +0.7
  │     标记里没有第 11 页的块 +0（页码闸门）
  ├─ 阈值过滤
  └─ 组装 Prompt（含图纸描述）
```

实测效果：四道图文题的 **Top-1 全部**变成图3 的描述块（优化前最好也只到
第 1、其余在第 3 甚至掉出 Top-4），6 题准确率 5/6 → 6/6。详见测试报告。
