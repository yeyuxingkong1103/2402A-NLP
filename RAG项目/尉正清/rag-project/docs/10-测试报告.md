## 2. RAGAS 质量评测

### 2.1 四个指标

| 指标 | 含义 |
|---|---|
| faithfulness | 回答是否忠于检索到的资料（查幻觉） |
| answer_relevancy | 回答是否切题 |
| context_precision | 检索到的资料有多少是真正有用的 |
| context_recall | 标准答案所需的信息，检索是否都覆盖到了 |

### 2.2 优化前后对比

**方法说明**：最初计划用「优化前采集 vs 优化后采集」对比，但两次采集之间知识库
重建过（新增法条元数据字段与章节标注），两组数据不可比。因此改为**消融实验**：
在**同一知识库**上关闭两项优化（`QUERY_EXPAND_N=1`、`ENABLE_METADATA_ROUTE=false`）
重跑一遍，作为严格可比的无优化基线。

| 指标 | 消融基线<br>（优化关闭） | 优化<br>（查询扩写 + 元数据路） | 变化 |
|---|---|---|---|
| faithfulness 忠实度 | 0.3218 | 0.3228 | +0.0010 → |
| answer_relevancy 答案相关性 | 0.6943 | 0.6950 | +0.0007 → |
| context_precision 上下文精确率 | 0.5578 | 0.5554 | −0.0024 → |
| context_recall 上下文召回率 | 0.4767 | 0.4967 | **+0.0200** ↑ |
| **四项平均** | — | — | **+0.0048** |

> 表中数字取自 `evals/scores_ablated.json` 与 `evals/scores_optimized.json`
> （判分模型 deepseek-flash，各 50 样本）。可用
> `.venv/bin/python -m evals.compare --base ablated --opt optimized` 复算。

### 2.3 分角色表现

| 角色 | answer_relevancy | context_recall |
|---|---|---|
| psychologist 心理医生 | 0.403 → **0.608**（+0.205） | 0.200 → **0.300**（+0.100） |
| lawyer 律师 | 0.864 → 0.819（−0.045） | 0.867 → 0.892（+0.025） |
| financial_advisor 金融理财师 | 0.759 → **0.616**（−0.143） | 0.233 → **0.167**（−0.067） |

### 2.4 结果解读

**整体结论：两项优化未带来显著提升。** 四项平均仅 +0.0048，
且四项中有三项变动幅度在 ±0.003 以内——考虑到 RAGAS 由大模型判分、样本量 50，
这个量级的差异**落在判分噪声范围内**，不足以证明优化有效。
唯一明显的是 context_recall（+0.020），但仍不足以支撑"优化有效"的结论。

**但分角色的差异是真实且显著的**，且方向相反：

| 角色 | 知识库形态 | 扩写的影响 | 推测原因 |
|---|---|---|---|
| 心理医生 | 问答对（问题 → 专业分析） | **大幅有益** | 换个问法能召回语义相同但表述不同的案例，召回面明显扩大 |
| 律师 | 结构化法条（一罪一条） | 基本持平 | 相关性略降、召回略升；法条表述规范，扩写收益与噪声相当 |
| 金融理财师 | 问答 + 长材料混合 | **明显有害** | 扩写引入的变体把"看似相关"的材料顶上来，挤掉了真正贴切的那篇 |

**过程中还证伪了一个假设**：曾试图给「改写后的原问题」1.5 倍权重，
以压制扩写变体引入的噪声。实测该版本四项平均 **−0.0075**，
比不加权的 +0.0073（同一轮判分下的对照值）更差，已回退为等权
（代码中保留了这次实验的记录）。

**一个具体的失败案例**（消融基线召回 1.0，优化后 0.5）：

> 问：「港股和A股的投资逻辑有什么不一样？」
> 基线检索到「沪深港通扩容对A股影响」，覆盖了标准答案中 A 股那一半；
> 优化后被「看好A股韧性」挤出 top-5，该文讲的是市场情绪而非分析逻辑。

**后续建议**（本次未实施，因样本量不足以支撑调参）：

1. **分角色配置扩写条数**——心理角色开 3 条、金融角色关闭，理论上可同时拿到
   两边的好处。但需**留出验证集**，否则是在 50 题上过拟合；
2. 扩写变体只用于**补充召回**而不参与最终排序，例如先按原问题精排、
   再用变体结果补足 top-5 的空位；
3. 扩大评测集到 200 题以上，使 0.02 量级的变化可被检出。

### 2.5 元数据路的评测盲区与定位修正

复核上面那次消融时发现一个方法论问题：**原 50 题评测集中，含法条号的题目为 0**。
题目全是口语化提问（"开车撞了人之后跑了，会被判几年？"），这类问题不会触发
「按条号精确命中」的元数据路。也就是说，消融中把 `ENABLE_METADATA_ROUTE` 关掉
之所以几乎没有影响，是因为**这条路径从未被真正走到**——
§2.2 报告的 +0.0048 实际只反映了查询扩写的作用，
「元数据路未带来显著提升」这个结论对它并不成立。

进一步验证发现，元数据路即便被触发也**排不到前面**。问「民法典第一百八十八条
规定什么」，检索结果如下：

| 路径 | 重排得分 |
|---|---|
| 向量路 第一千一百七十八条 | 2.965 |
| 向量路 第一千零五十八条 | 2.953 |
| 向量路 第一百二十八条 | 2.908 |
| **元数据路 第一百八十八条（正解）** | **2.543（末位）** |

根因是**用语义相似度去排精确事实**。条号是确定性信息，而交叉编码器只看语义，
「诉讼时效」这类主题相近的条文天然比条号本身更"像"问题；再加上扩写出的多个
查询各自贡献向量路得分，累加起来压过了元数据路的单路加权。

**已修正**：识别到明确条号且精确命中时，该条**直接置顶、不参与重排排序**；
未识别到条号的问题仍走纯语义，不误触发。修正后实测：

| 问题 | 置顶结果 |
|---|---|
| 民法典第一百八十八条规定了什么？ | ✓ 《民法典》第一百八十八条 |
| 刑法第一百三十三条怎么规定的？ | ✓ 《刑法》第一百三十三条 |
| 劳动合同法第八十二条 | ✓ 《劳动合同法》第八十二条 |
| 公司股东抽逃出资要承担什么责任？（无条号） | — 走纯语义，未误触发 |

同时补充 6 道条号题（`law-21`~`law-26`）进评测集，ground_truth 直接取自
知识库中的法条原文，使该路径后续可被评测覆盖。

## 6. 测试发现的缺陷

测试过程中发现并修复了 4 个真实缺陷，其中前 3 个为**接口测试用例暴露**，第 4 个在
知识删除接口的回归验证中发现：

### 6.1 数据库写入从不提交（严重）

**现象**：注册接口返回 200 并给出用户 ID，但用同样的账号密码登录返回 401；
通过接口创建的会话在数据库里查不到。

**根因**：`get_db()` 只 `yield` 了 Session，没有提交也没有回滚。
接口里 `flush()` 会分配自增 ID，所以返回值看起来正常，但事务在 Session
关闭时被回滚，数据从未落库。

**修复**：`get_db()` 在请求正常结束时提交、异常时回滚。

**为什么之前没发现**：此前的手工验证脚本走的是另一条会提交的路径
（`session_scope`），掩盖了问题。这正是需要自动化接口测试的原因。

### 6.2 响应先于事务提交（并发下暴露）

**现象**：修复 6.1 后，连续两次注册同一用户名，第二次返回 500 而非 400。

**根因**：FastAPI 的 yield 依赖在**响应发出之后**才执行 teardown。
客户端收到 200 时事务可能尚未提交，紧接着的第二个请求读到旧快照，
"先查后插"的检查失效，撞上唯一索引。

**修复**：在写接口（注册、问答、删除会话）内显式 `commit()`，
保证 200 响应意味着数据已落库；同时捕获 `IntegrityError` 兜底翻译为 400。

### 6.3 长文档内容被误判为水印

**现象**：早期去水印实现把正文也删掉了，正文保留率仅 5%。

**根因**：只按"多页重复出现"判定水印，而正文页眉、重复段落同样满足该条件。

**修复**：增加形态特征校验——只有同时具备旋转、大字号、浅灰低对比或极短
这几种特征之一的重复文本才判定为水印。修复后正文保留率 96%。

> 该逻辑仍在生效：PDF 解析虽已改用 MinerU，但 MinerU 只做解析、**不做水印擦除**，
> 去水印这一步仍由 PyMuPDF 在解析前完成，判定规则未变（`app/core/watermark.py`）。

### 6.4 删除接口返回 200 后数据仍可查到

**现象**：`DELETE /api/update/document` 返回 200「删除成功」，但紧接着 `GET /api/stats`
或再次查询，该 `source` 的切片数仍停在旧值。

**根因**：Milvus 的删除是**最终一致**的，`delete()` 之后不 `flush` 就不会立即对查询可见。
接口按项目一贯的「200 即已生效」口径返回，调用方却看到旧数据。

**修复**：`MilvusStore.delete_by_expr` 在 `delete()` 后补一次 `flush()`，
使删除与写入一样立即可见。

### 7.3 本轮发现并修复的问题

分三批发现，共 **10 个**，均已于当日修复并复验。

**第一批：人工回归，7 个**

| # | 问题 | 修复 |

**第二批：补自动化用例时被测试逮住，2 个**

这两项是 §7.4 的用例写出来**第一次跑就红**的——第 8 项红了 4 条，
第 9 项是在修完第 8 项后继续红的。

| # | 问题 | 修复 |
|---|---|---|
| 8 | **水印「极短」规则误删正文**：`_watermark_like()` 只要文本 ≤ `SHORT_TEXT`(12) 就返回 True，不再看颜色/字号/旋转。正文折行折出的短续行同样很短，在 12 页上重复出现于同一位置即被判为水印整段删除，正文保留率掉到 79%。与 §6.3 记的失败同类 | 「极短」增加 `standalone` 前提——真水印是独立文本对象，在 `get_text("dict")` 里自成一个块；折行续行与上一行同属一个多行块 |
| 9 | **兜底路径从未真正去水印，且报告与实际不符**：`extract_pages()` 把 `file_path`（原文件）传给 `_extract_fallback()`，而水印擦在 `clean_path` 副本上；且 `clean_path` 所在的临时目录在调用前已随 `with` 退出被删除。表现为**报告 `text_removed=12`、正文里水印原样还在** | 兜底路径改读 `clean_path`，并把调用移入 `with` 块内；`_extract_fallback` 参数更名为 `pdf_path` 并注明必须是干净副本 |

> 第 9 项比"漏删"更危险：报告说删了、实际没删，只看报告会误判为已生效。
>
> 它能潜伏至今，是因为只在**兜底路径 + 文档确实带水印**时才显形：
> 主路径（MinerU）读的正是 `clean_path`，去水印正常；而此前对兜底路径的
> 人工验证跑的是不带水印的 WHO 报告（`text_removed=0`）——两个条件从未同时满足。
> 本机 MinerU 可用、平时都走主路径，所以人工验证也照不出来。

**第三批：核对文档数字时发现，1 个**

| # | 问题 | 修复 |
|---|---|---|
| 10 | `install.sh` 装 MinerU 用 `--small-backend onnx`，与 README 的要求相反——README 明确要求确认 `Effective small backend` 是 **`torch` 而不是 `onnx`**，并说明 onnx 是 CUDA torch 装错时的**静默降级**路径。照 `install.sh` 装会恰好得到 README 警告的那个 CPU 状态 | 两处改为 `torch`，并注明装完还需按 README 换 cu126 的 torch；依赖/模型体积由 6.4GB / 2.0GB 更正为实测 7GB / 1.4GB（README 的 2.0GB 一并更正） |

### 7.6 遗留

- **水印判定仍有盲区**：第 8 项修掉了"折行续行"这一类误判，但**独立成块的
  短文本**（如每页重复的页脚、表单里的固定标签）若在多数页同位置出现，
  仍会被判为水印——这类目标与真水印在结构上确实无法区分。
  真要收紧，需要引入位置（是否落在页边距区）或层（是否在单独 OCG/XObject 里）等信号。
  当前选择保守方向：宁可漏删，不误删正文。
- **`uploads/` 会积压**：上传接口把文件落盘到 `uploads/`，
  而删除接口只清 Milvus 与 Redis、**不删文件**，长期跑会攒下孤儿文件。
  是否需要联动删除取决于产品语义（"删知识"是否等于"删原始文件"），
  属接口层决策，**未改**。
  但用例侧已收敛：`TestUpload` 在 teardown 里自行删掉落盘文件——
  在此之前每跑一次回归就多一个孤儿（实测确认：上一轮 full run 后
  `uploads/` 里确实躺着一个没被收走的文件）。

### 最有价值的发现

本次测试最大的产出不是"优化奏效了"，而是**用数据否定了两个想当然的改进**：

1. **查询扩写并非普遍有效**——它在心理角色上提升显著（相关性 +0.205），
   在金融角色上却明显有害（相关性 −0.143）。整体互相抵消。
   "多路召回一定更好"是个未经检验的假设。
2. **给原问题加权是错的**——这个看起来很合理的修正，实测比不加权更差，
   已回退。代码中保留了这次实验的记录，避免后人重蹈。

如果没有 RAGAS 量化评测，这两点都会被"感觉上应该更好了"掩盖过去。

### 局限

- **评测集偏小**：50 题（每角色 15–20 题），0.02 量级的变化无法与判分噪声区分。
  要支撑调参决策，需扩到 200 题以上并留出验证集。
- **问答压测样本少**：仅 10 次（受大模型时延限制），统计意义有限。
- **单机环境**：7.6GB 内存下无法并行跑采集与判分，中途出现过 OOM；
  生产环境应分离这两类任务。
