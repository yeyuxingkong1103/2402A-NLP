# 05 解析提示词设计（MinerU + 视觉模型）

> 产出日期：2026-09-15 | 上游：`docs/01-需求分析.md`、`docs/04-语料清单-农业国标PDF.md`
> 本步对应流水线「文档解析与切分」的**解析**部分，产物：知识卡 JSON → `data/processed/`
> 提示词本体：`configs/prompts/parse_pdf_to_knowledge.md`（主）、`configs/prompts/vlm_transcribe_table.md`（视觉转录）

## 1. 设计取舍（为什么这么写）

| 决策 | 理由 |
| --- | --- |
| 解析阶段**只抽取、不改写**，不做「农户友好表达」改写 | 改写属于生成阶段。解析阶段动一个字，溯源链就断了；且农户口语润色会把「600 倍液」这类数值改写风险带进来 |
| 数值/单位**禁止换算**，只做上标还原 | 换算即引入误差，且换算后的值无法回指原文，违反核心约束 1（高危知识必须可溯源） |
| 缺失字段一律 `null` + `missing_fields`，禁止跨列猜配 | 附录 B 表格列错位时「猜一个剂量」= 直接把错药量给农户，后果最严重 |
| 每条知识强制 `source.section` + `source.page` + `quote` | 核心约束 1、4 要求来源与年份可查；页码用 PDF 物理页，便于回原 PDF 复核 |
| 高危卡强制 `needs_verification_hint = true` | 核心约束 1：高危知识必须带核实提示，由提示词在解析阶段就打好标记，生成阶段只负责呈现 |
| 输出单层 JSON 数组，不用嵌套大类 | 直接对应切分单元（一条知识 = 一个 chunk），减少后续二次拆分 |

## 2. 双通道分流（实测结论，决定提示词怎么用）

这批国标 PDF 的文本层质量**不一致**，同一份文件里同时存在可直接抽取的正文页和完全乱码的附录页。逐页体检结果（`data/raw`，pymupdf 抽取 CJK 字数 < 60 判为异常页）：

| 标准 | 页数 | 需走视觉通道的页 | 典型问题 |
| --- | --- | --- | --- |
| GB/Z 26581-2011 黄瓜生产技术规范 | 21 | p9, p10, p11, p12, p14, p16, p19 | 附录 A/B 记录表与防治方案表：整页 CID 字形码 |
| GB/Z 26583-2011 辣椒生产技术规范 | 21 | p9, p10, p11, p12, p14, p17, p18, p19 | 同上；附录 B 表 B.1 是农药方案主表 |
| GB/Z 26578-2011 大蒜生产技术规范 | 20 | p9, p10, p11, p12, p14, p17, p18, p19, p20 | 附录 B 防治方案表（p18、p20）抽出来是 `!\"#$%&` 类乱码 |

即便文本层**能**抽出字的表格页（如 GB/Z 26581 附录 B），也要走视觉通道：文本层会把整张表压成一列，出现
`110g/667m` / `2~` / `180g/667m` / `2 烟熏` 这种上标拆行 + 单元格顺序丢失，列与值的对应关系无法可靠还原。

本期 3 份里最典型的例子是 GB/Z 26578-2011 大蒜：附录 B 防治方案表落在 **p18/p20，两页都是字形码**，整表只能靠视觉转录。因此**用文本层做关键词统计时，大蒜的「安全间隔期」「每茬最多使用次数」命中为 0——这不代表原文没有**，只是统计口径覆盖不到（对应 `docs/01` 2.2 结论 2 与 7.6 第 7 条的复核要求）。

因此 MinerU 的定位是**通道 A 的正文抽取器**（版式、正文段落、目次），不能指望它解决附录表格；表格与乱码页必须由视觉模型逐页转录（`vlm_transcribe_table.md`）。

## 3. 解析流水线（建议实现顺序）

```
data/raw/*.pdf
   │
   ├─ 步骤 0 文件备案：文件名解析出 std_no / std_name / year → 写入每份文件的行元数据
   │
   ├─ 步骤 1 逐页路由
   │     pymupdf 取每页 CJK 字数；≥60 → 通道 A；<60 或该页含表格标题 → 通道 B
   │
   ├─ 步骤 2A 通道 A（MinerU / pymupdf 输出 markdown）
   ├─ 步骤 2B 通道 B（页面渲染 150–200dpi → 视觉模型 + vlm_transcribe_table.md）
   │
   ├─ 步骤 3 结构化：把该页 markdown 喂给 parse_pdf_to_knowledge.md → 知识卡 JSON
   │     页脚/页眉、乱码页 abort 由 P2/P4 规则处理
   │
   ├─ 步骤 4 校验：JSON schema 校验 + 字段完整率 + 高危卡 source 完整性
   │
   └─ data/processed/<std_no>.jsonl   一行一卡
        data/chunks/                  下一步（切分）才产出
```

## 4. 与核心约束的对应（逐条自查）

| 约束（CLAUDE.md 第四节） | 提示词中的落实 |
| --- | --- |
| 1 高危知识必须带来源和核实提示 | H1–H6；`is_high_risk` / `high_risk_reasons` / `needs_verification_hint` / `source.section+page+quote` |
| 2 检索不到时明确说「暂无」，绝不编造 | 0 节禁令 3/4；P4 乱码页 `abort` 而非猜字；缺失字段进 `missing_fields` |
| 3 答案表达农户友好 | 不在解析阶段做（属生成阶段），避免改写破坏溯源 |
| 4 每条知识标注作物/地域/生育期/年份/来源/权威等级/是否高危 | schema 中的 `crop` / `region` / `growth_stage` / `year` / `source` / `authority_level` / `is_high_risk` —— 与《01-需求分析》7.4 元数据字段表一一对应 |
| 5 不擅自扩大范围 | `in_scope` 字段标注是否属本期作物，范围由 `{{IN_SCOPE_CROPS}}` 注入，不硬编码 |

## 6. 怎么验收这一批解析结果（对应《01-需求分析》10.2/10.3）

- **schema 合规率**：所有卡片能通过字段校验（字段名、枚举值、`null` 规范）。
- **溯源完整率**：100% 卡片有 `source.section` + `source.page`；回原 PDF 抽查 20 张卡，定位必须对得上。
- **高危字段准确率（单独考核，门槛 100%）**：抽检 `dose` / `dilution` / `pre_harvest_interval` / `max_uses_per_season`，逐格与页面图比对。
- **缺失诚实度**：人工核对 10 张卡的 `missing_fields`，确认没有「原文没有但被填上」的值。
