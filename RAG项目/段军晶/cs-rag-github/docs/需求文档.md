## 一、项目背景

### 1.1 业务场景

本公司是一家面向政企客户提供 **IT 服务与数据中心运维** 的服务商，日常业务涉及三类强合规诉求，每一类都对应一份国家标准：

| 业务活动 | 依据标准 | 典型使用人 |
| --- | --- | --- |
| 承接数据中心托管/运维项目，需通过**业务连续性等级评价**（投标资质、年度复审） | GB/T 42581-2023《信息技术服务 数据中心业务连续性等级评价准则》 | 交付工程师、体系专员 |
| 为金融、政务客户处理数据，需通过**网络数据处理安全**合规审计 | GB/T 41479-2022《信息安全技术 网络数据处理安全规范》 | 安全合规专员 |
| 采购/验收外包软件，需对软件质量做**量化评价打分** | GB/T 32904-2016《软件质量量化评价规范》 | 质量管理员、项目经理 |

这三份标准合计 **74 页**，是本项目的全部知识库来源。

### 1.2 现状与痛点

现阶段这三份标准以 PDF 形式存放在共享盘，工程师靠人工查阅，暴露出四个具体问题：

1. **查得慢。** 一次典型查询（"业务连续性第 4 级对恢复时间目标的要求是什么"）需要打开 PDF、翻阅目录、`Ctrl+F` 关键词、跨页比对，平均耗时 3–5 分钟。若关键词与标准原文用词不一致（例如用户问"灾备恢复多久"，标准写的是"恢复时间目标（RTO）"），`Ctrl+F` 直接失效。
2. **引不准。** 投标应答和审计举证必须写明"依据 GB/T 42581-2023 第 X 页第 Y 条"。人工摘录常出现页码写错、条款号对不上，在评标或审计现场被打回。
3. **上手慢。** 新员工不熟悉标准体系结构，不知道某个要求究竟落在哪一份标准的哪一章，只能整个文件夹通读。
4. **版本混。** 三份标准发布年份不同（2016/2022/2023），人工比对时容易张冠李戴。

### 1.3 为什么用 RAG，而不是关键词搜索或模型微调

这是一个典型的**"答案必须能指回原文"**的场景，三条技术路线对比：

| 方案 | 能否解决 | 结论 |
| --- | --- | --- |
| `Ctrl+F` / 全文关键词检索 | 只能命中字面相同的词，解决不了 1.2 中"问法≠原文用词"的问题；且无法返回连续语义段落 | ✗ 不采用 |
| 把标准内容拿去微调大模型 | 微调后模型"记住"但无法给出可靠出处，且标准一旦换版就要重训；本场景最忌讳编造条款 | ✗ 不采用 |
| **RAG（检索增强生成）** | 先检索到原文片段，再让模型**只依据这些片段**作答，答案天然可附原文出处（文档名 + 页码） | ✓ **采用** |

RAG 的检索-生成分离结构，正好把"翻得准"和"说得对"两件事解耦：检索负责**定位原文**，生成负责**讲清楚**，而页码溯源作为元数据贯穿始终，直接命中痛点 2。

### 1.4 项目目标

构建一个私有知识库问答助手：终端用户打开网页 → 加载知识库 → 用自然语言提问 → 得到**带原文出处（文档名称 + 页码）**的答案。系统按 V1（MVP 基线）→ V2（检索增强）→ V3（重排与稳定性）三轮迭代，每轮用同一套评测集量化验证提升。

## 二、用户画像

### 2.1 主要用户

| 画像 | 特征 | 核心诉求 | 对系统的关键要求 |
| --- | --- | --- | --- |
| **A. 交付工程师**（28–40 岁） | 熟悉数据中心运维实操，但记不住标准全文；常在客户现场用笔记本查 | 快速确认"某等级要求的具体指标数值"，用于现场答复和整改 | 答案要**准确**，必须能翻到原文页核对 |
| **B. 安全合规专员**（30–45 岁） | 非技术背景为主，负责应对审计和监管检查 | 确认"某类数据处理行为是否被标准允许/要求" | 答案要**可举证**，出处要能直接写进审计材料 |

### 2.2 次要用户

| 画像 | 特征 | 核心诉求 |
| --- | --- | --- |
| **C. 投标/商务人员** | 需要引用标准条款撰写技术标 | 快速摘取条款原文用于标书 |
| **D. 新入职员工** | 不熟悉标准体系 | 通过问答快速建立对标准结构的认知 |

### 2.3 用户特征对设计的约束

- 用户是**普通终端用户**，不是工程师：界面不能出现检索分数、向量维度、链路节点等内部概念。
- 用户**不关心系统怎么找到的**，只关心**答得对不对、出处是哪一页**。
- 用户可能连续追问（先问"等级怎么划分"，再问"第 4 级呢"），需要**多轮上下文**支撑。

> 这一条直接决定了本项目的核心设计边界：**检索中间的 Trace 信息只写后端日志，供开发调试与评测排查使用，不提供给前端，也不做检索链路可视化页面。**

## 三、功能清单（用户视角）

> 说明：以下均为**用户能直接感知**的功能，不描述内部实现。优先级 P0 为 MVP 必须交付，P1 为增强版本交付。

### F1 加载知识库 `P0`

- **用户场景**：首次使用，或标准文件更新后，需要把 PDF 内容装进系统。
- **功能描述**：用户点击"加载知识库"，系统读取预置的 3 份国标 PDF，完成解析、切分、向量化与入库；页面显示进度与加载结果（成功文档数、总页数、总片段数）。
- **验收点**：加载完成后，3 份文档均可被检索到；重复加载不产生重复数据。

### F2 上传 PDF 扩展知识库 `P1`

- **用户场景**：客户追加了一份地方标准或行业规范，希望一并纳入问答范围。
- **功能描述**：用户上传 PDF 文件，系统按与 F1 相同的流程处理并入库，新文档立即可被检索。
- **验收点**：上传后立即可提问并命中新文档内容；超出大小/格式限制时有明确中文提示。

### F3 自然语言提问 `P0`

- **用户场景**：用户用大白话描述需求，不必使用标准原文术语。
- **功能描述**：用户在输入框输入问题并提交，系统返回基于知识库内容的回答。
- **验收点**：问法为口语化表达时仍能召回正确内容（例如问"灾备多久能恢复"，应召回 RTO 相关条款）。

### F4 查看答案 `P0`

- **用户场景**：用户需要直接可用的结论。
- **功能描述**：以流式或整段方式展示答案正文，语言通顺、结构清晰（涉及多项要求时用列表呈现）。
- **验收点**：答案内容**必须能在知识库原文中找到依据**；知识库中确无相关内容时，明确回复"知识库中未收录相关内容"，**不得编造**。

### F5 查看来源与溯源页码 `P0` ⭐核心功能

- **用户场景**：用户需要核对原文，或把出处写进标书/审计材料。
- **功能描述**：答案下方展示"来源"区域，逐条列出：**源文档名称 + 页码**（可含命中片段摘要）。页码可直达原始 PDF 对应页。
- **验收点**：
  - 每条来源都能对应到真实存在的 PDF 页码；
  - 点击可定位/打开对应 PDF 页；
  - **页码在 V1/V2/V3 各版本中均不得丢失或错位**（硬性要求）。

### F6 多轮追问 `P0`

- **用户场景**：用户先问"数据中心业务连续性分几级"，接着问"那第 4 级有什么要求"。
- **功能描述**：系统记住当前会话上下文，追问时能理解省略的主语。
- **验收点**：省略主语的追问能正确理解意图；会话在有效期内保持上下文，过期后自动清理。

### F7 会话管理 `P1`

- **用户场景**：用户想开一个不相关的全新话题，避免被之前的上下文干扰。
- **功能描述**：提供"新建对话"入口，清空当前上下文。

### F8 高频问题快速响应 `P1`

- **用户场景**：某些问题被反复提问（如"业务连续性分几级"）。
- **功能描述**：对相同问题直接返回缓存结果，显著降低响应时间。
- **验收点**：重复提问的响应时间明显低于首次提问；知识库更新后缓存自动失效，不返回过期答案。

---

### F9 账号登录 `P0`（V1.1 增量）

- **用户场景**：同一台演示电脑上会有不同的人使用；每个人都希望自己的提问与收藏互不干扰。
- **功能描述**：页面顶栏提供「用户登录」入口，输入账号即可登录自己的 AI 助手；账号不存在时自动创建。
- **关键约束**：账号持久化在 MySQL（`users` 表），**不是前端模拟登录**；会话记录登录用户 ID。
- **头像**：登录页可**从相册选一张图片**当头像（浏览器端自动裁成方形并压缩），也可选预设 emoji 或用账号首字；自定义头像图片存 `data/avatars/`，数据库只记地址，换浏览器登录同一账号头像仍在。
- **明确不做**：不做密码、不做加密、不做验证码、不做 token 过期逻辑（本地局域网课程演示口径）。
- **验收点**：输入任意未被占用的账号可登录并自动建号；换浏览器、清除浏览器缓存后重新输入同一账号，历史与收藏仍在。

### F10 历史记录（按会话保留）`P0`（V1.1 增量）

- **用户场景**：上周问过的结论想再翻出来看，甚至接着往下问。
- **功能描述**：左侧栏「历史记录」按会话列出，标题取该会话首个提问的前 12 字；点击可回看整段问答；支持删除整个会话，也支持删除单条问答。
- **关键约束**：持久化在 MySQL（`chat_sessions` / `chat_messages`），**只要用户不主动删除就永远保留**；打开旧会话时把最近若干轮上下文回灌进 Redis，保证「接着问」时省略主语的追问仍能被理解。
- **验收点**：清浏览器缓存 / 换浏览器后历史仍在；打开昨天的会话可直接追问「那第 4 级呢」。

### F11 我的收藏 `P1`（V1.1 增量）

- **用户场景**：某条答案以后要反复引用，希望单独存起来。
- **功能描述**：AI 答案条目提供「收藏」按钮，可收藏 / 取消收藏；左侧栏「我的收藏」Tab 查看当前用户的全部收藏。
- **关键约束**：收藏绑定当前登录用户，存「问题 + 答案 + 溯源」**整条快照**，持久化 MySQL（`user_favorites` 表）；删除历史会话不影响已收藏内容。
- **验收点**：收藏后清除浏览器缓存不丢失；重复收藏同一条不产生重复记录。

### F12 回答身份切换（学生 / 职场）`P0`（V1.1 增量）

- **用户场景**：同一套标准，学生想听「学长讲题」式的轻松解读，职场人想要严谨权威的合规口径。
- **功能描述**：问答区上方提供「学生身份 / 职场身份」切换；学生身份语气轻松亲切、先给结论再分点展开；职场身份严谨简洁、沿用规范术语并交代适用范围与例外情形。
- **关键约束**：**只新增 `role` 入参并分支设置不同的 system 提示词**，不改变检索、分块、重排、生成的原有逻辑；两套提示词的防幻觉红线（只依据参考资料 / 未找到即明说 / 数值等级不得改写换算近似 / 不自行撰写引用）**逐字相同**，因此两种身份的**事实与数值完全一致，只是讲法不同**。
- **验收点**：同一问题切换身份后答案口吻明显不同；同一问题在两种身份下不会命中同一份查询缓存（缓存 Key 已加入身份维度）。

## 四、非功能需求

### N1 溯源准确性（最高优先级）

- 每一条答案都必须携带来源文档名称与页码，**不允许出现"无出处"的答案**。
- 页码必须来自 PDF 解析阶段产生的原始版面元数据，不得由生成模型"推测"。
- 该要求在 V1/V2/V3 三轮迭代中**均不得降级**。

### N2 答案忠实性（防幻觉）

- 生成模型只能依据检索到的原文片段作答。
- 检索结果与问题无关时，必须**明确拒答**，不得基于参数化知识编造标准条款。
- 以评测集量化验证：`faithfulness`（忠实度）与安全集 `refusal_accuracy`（拒答准确率）作为硬指标。

### N3 响应性能

| 场景 | 目标 |
| --- | --- |
| 首次提问（未命中缓存） | ≤ 8 秒出完整答案 |
| 命中缓存的重复提问 | ≤ 1 秒 |
| 知识库加载（3 份 PDF 全量） | 一次性操作，允许数分钟，需提供进度反馈 |

> 注：当前运行环境为 **CPU 推理（无 GPU）**，向量化与重排均为 CPU 计算，上述目标已按 CPU 条件设定。

### N4 并发能力

- 支持**不少于 20 个并发**问答请求不出现错误（需用 JMeter 压测验证，见 N7）。
- 单个请求异常不得导致整个服务不可用。

### N5 可观测性

- 后端使用 Python 原生 `logging`，完整记录：服务请求、检索中间过程（用户原始问题、命中片段、相似度分数、命中页码）、错误堆栈。
- 日志**仅保存在服务端**，用于开发调试与评测排查。
- **不对前端提供任何 Trace 查询接口，前端不展示检索链路细节。**

### N6 数据安全

- 所有 API 密钥、数据库口令存放于 `.env`，**禁止硬编码进代码**，`.env` 不纳入版本控制。
- 知识库内容为企业内部资料，服务仅在本机/局域网内提供，不对外网暴露。

### N7 可测试性与可压测性

- 所有对外接口需提供完整接口文档（含请求示例），可供 Postman / APIPost 直接导入调试。
- 接口需支持 JMeter 压力测试（本项目**不编写** JMeter 脚本，仅在文档中说明测试方法）。

### N8 可迭代性

- 代码分层清晰：离线处理脚本、后端业务逻辑、API 接口严格分离。
- V2/V3 必须在 V1 代码基础上**增量扩展**，不得推倒重写。

### N9 部署与可移植

- 支持本机与局域网访问。
- 提供完整的部署运行手册，包含环境依赖、启动步骤、验证方法。

## 五、范围边界

### 5.1 本期做什么

| 范围项 | 说明 |
| --- | --- |
| ✅ 知识库范围 | **仅限** `data/source_docs/` 下的 3 份指定 GB/T 标准 PDF |
| ✅ 页码级溯源 | 答案附源文档名 + 页码，为各版本硬性保留项 |
| ✅ 多轮会话 | Redis 实现短期会话记忆 |
| ✅ 三轮迭代 | V1 基线 → V2 混合检索与视觉解析 → V3 重排与查询改写 |
| ✅ 评测体系 | 检索集、生成集、安全集三类评测样本 + RAGAS 量化指标 |
| ✅ 面向普通用户的简洁网页 | 加载知识库、提问、看答案、看来源页码 |
| ✅ 后端 Trace 日志 | 仅服务端记录，用于调试与评测 |
| ✅ 账号登录与用户隔离（V1.1 增量） | 账号即身份（无密码），历史记录与收藏按用户隔离 |
| ✅ 历史记录与收藏持久化（V1.1 增量） | MySQL 存储，清除浏览器缓存不丢失 |
| ✅ 双身份回答（V1.1 增量） | 学生 / 职场两种 system 提示词，检索链路不变 |

### 5.2 本期明确不做

| 不做项 | 原因 |
| --- | --- |
| ❌ **检索链路可视化页面** | 任务书明确排除；用户是普通终端用户，不需要也不理解中间链路 |
| ❌ **Trace 查询 API** | 同上，Trace 仅后端日志内部留存 |
| ⚠️ 用户注册 / 登录 / 权限体系 | **V1.1 增量改造已调整**：新增轻量账号登录（无密码、无鉴权，仅用于区分用户、隔离历史与收藏）；**仍然不做**注册流程、权限体系、多租户 |
| ❌ 密码 / 加密 / 验证码 / token 机制 | 本地局域网课程演示口径，安全复杂度与使用场景不匹配 |
| ❌ 扫描件 / 手写体 OCR 识别 | 本期 3 份 PDF 均为**文本型**（已实测确认），无扫描件场景 |
| ❌ 标准条款号（如 5.2.1）的精确结构化标注 | 条款号层级解析需专门规则工程，本期由页码溯源满足"可核对"诉求，条款号留待后续版本 |
| ❌ 跨标准条款冲突比对 | 属知识推理场景，超出检索增强生成能力边界 |
| ❌ 移动端 App / 小程序 | 本期内网网页版已满足诉求 |

## 八、附录：术语表

| 术语 | 说明 |
| --- | --- |
| RAG | 检索增强生成（Retrieval-Augmented Generation），先检索原文再生成答案 |
| 溯源 | 答案指向原始文档的具体位置，本项目精确到**页码** |
| 知识库块（chunk） | 文档切分后的最小检索单元，携带文档 ID、页码、源文件名等元数据 |
| Trace | 检索过程的中间记录（命中片段、分数、页码），仅后端日志留存 |
| 基线 | V1 版本的评测指标数值，作为后续版本对比的参照 |
| recall@k | 前 k 个检索结果中包含正确内容的样本占比 |
| MRR | 平均倒数排名，衡量正确结果在检索列表中的靠前程度 |
| faithfulness | 答案忠实度，衡量答案是否完全由检索到的原文支撑 |

## 九、增量改造需求（V1.1：登录 / 历史记录 / 收藏 / 双身份）

> 本章记录 V1.1 增量改造的需求与约束。**改造原则：只新增，不重构。**
> 原有全部功能（网络问答、答案溯源页码、多轮追问、缓存加速、PDF 上传与知识库构建接口）完整保留。

### 9.1 需求来源

课程演示场景下，原页面只有「提问 → 回答 → 来源页码」四项能力，缺少演示所需的用户体系与内容留存能力，且回答风格单一。因此在**不动已稳定 RAG 核心**的前提下做增量扩展：

| 序号 | 新增能力 | 用户价值 |
| --- | --- | --- |
| 1 | 账号登录（账号即身份） | 换浏览器 / 清缓存后仍是「我的」助手；不同人的历史与收藏互不干扰 |
| 2 | 历史记录（按会话） | 没删就一直在；点开旧会话可以直接接着问 |
| 3 | 我的收藏 | 有用的问答单独留存，随时回看，不因删除会话而丢失 |
| 4 | 双身份回答 | 学生要易懂、职场要严谨，同一份知识两种讲法 |

### 9.2 新增数据表（4 张，幂等创建）

| 表名 | 用途 | 关键字段与约束 |
| --- | --- | --- |
| `users` | 用户账号 | `username` 唯一；`last_login_at` 记录最近登录 |
| `chat_sessions` | 会话（绑定用户） | 主键 `session_id`（与 Redis 上下文共用）；`title` 取首个提问前 12 字；`message_count` 计数 |
| `chat_messages` | 问答消息（历史真相源） | 自增 `id` 即收藏用的 `message_id`；`sources` 存溯源快照（**已剔除检索分数与 chunk_id**） |
| `user_favorites` | 收藏 | 存问题 + 答案 + 溯源整条快照；`UNIQUE(user_id, message_id)` 防重复；不随会话删除而删除 |

> 既有表 `kb_documents` / `kb_chunks` / `qa_records` **结构不变**；`qa_records` 仍然只服务于后端排查，不对外提供查询接口。

### 9.3 改造边界（红线，验收时逐条核对）

| 禁止改动项 | 实际做法 |
| --- | --- |
| PDF 解析、分块、向量化入库 | 一行未动 |
| Milvus 检索、混合检索、RRF 融合 | 一行未动 |
| 重排（reranker）、查询改写 | 一行未动 |
| 检索生成链路、页码溯源构造 | 一行未动 |
| 评测脚本与评测集 | 一行未动 |
| `/api/chat/query` 既有字段契约 | 只**新增** `role` / `user_id` 入参与 `role` / `message_id` 出参，原字段一个不删不改 |
| 原始 system 提示词 | 原 `SYSTEM_PROMPT` 常量保留，作为默认值继续可用 |

**唯一动到的既有代码**：Redis 查询缓存 Key 增加身份维度（`rag:cache:v{kbver}:r{role}:query:{digest}`），用于避免「先问职场、再切学生问同一句」时命中同一份缓存导致答案口吻串味。该改动不涉及检索、分块、重排、生成任何环节；旧格式 Key 读不到、到期自动清理，无需手工处理。

### 9.4 关键设计决策

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 历史记录存哪 | MySQL（永久），**不是** localStorage | 需求要求「清浏览器缓存不丢失、换浏览器仍在」 |
| 历史与多轮上下文的关系 | MySQL 存长期历史，Redis 存短期上下文；打开旧会话时**回灌**最近若干轮 | Redis 上下文默认 30 分钟过期，不回灌则「接着问」会失去上下文 |
| 收藏存什么 | 问题 + 答案 + 溯源**整条快照** | 只存 ID 的话，知识库重建后收藏会变成空壳 |
| 溯源面板展示什么 | 只展示文档名称、来源段落、页码 | 需求明确禁止展示 Trace、向量分数、重排得分；落库时即已剔除内部字段 |
| 身份如何注入 | 仅在生成答案那一步替换 system 提示词（代码落在 `V1Pipeline._build_messages`，V2/V3 继承生效） | 检索、分块、重排、溯源链路完全不受身份影响，保证「事实一致、只是讲法不同」 |
| 非法身份入参 | 回退默认身份（`student`），不报错 | 演示现场参数传错不应导致整个问答失败 |
| 历史落库位置 | 在 **API 层**旁路写入，不写进 pipeline | pipeline 完全不需要知道「历史记录」这件事，RAG 核心零改动 |

### 9.5 增量验收标准

| 序号 | 验收项 | 判定标准 |
| --- | --- | --- |
| 1 | 登录 | 输入任意未占用账号可登录；同一账号二次登录得到同一 `user_id`；账号持久化于 MySQL |
| 2 | 历史持久化 | 提问后左侧出现会话；清浏览器缓存 / 换浏览器重登后历史仍在 |
| 3 | 会话恢复 | 打开旧会话可回看全部问答，并能直接追问省略主语的后续问题 |
| 4 | 删除 | 可删除整个会话与单条问答；删除会话不影响已收藏内容 |
| 5 | 收藏 | 收藏 / 取消收藏即时生效；重复收藏幂等；换浏览器后收藏仍在；按用户隔离 |
| 6 | 双身份 | 同一问题在两种身份下答案文本不同；**不会**命中同一份缓存；非法 `role` 回退且不报错 |
| 7 | 溯源约束 | 溯源面板只出现文档名称、来源段落、页码；不出现任何分数、chunk_id、Trace |
| 8 | 兼容性 | 不携带 `user_id` 调用 `/api/chat/query` 仍正常返回（curl / JMeter 压测不受影响） |
| 9 | 核心未动 | PDF 解析 → 分块 → 向量化 → 检索 → 重排 → 生成 → 页码溯源链路与评测脚本无改动 |
