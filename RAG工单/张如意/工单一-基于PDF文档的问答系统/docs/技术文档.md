## 一、系统概述

本系统是一个面向招股说明书的 RAG（Retrieval-Augmented Generation，检索增强生成）
问答系统：用户用自然语言提问（支持中英文、支持语音输入），系统先在本地知识库中
检索与问题最相关的文档片段，再把片段作为「参考资料」交给大语言模型，生成**有据可查、
带页码引用**的答案。

与「直接用大模型回答」相比，本系统的答案全部来自《招股说明书1.pdf》原文，
文档中没有的信息会明确拒答，避免金融场景中不可接受的数字幻觉。

### 1.1 工单需求与本系统的对应关系

| 工单要求 | 本系统实现 |
| --- | --- |
| Query 理解：意图识别 / 消歧 / 分解抽象 | `rag_core/query_understand.py` + 流水线第 1 阶段 |
| 文档解析：解析 PDF、提取文字 | `rag_core/pdf_parse.py`（PyMuPDF 文字层；可选 pdfplumber 表格层） |
| 向量检索：文档嵌入向量空间 | `rag_core/embed.py`（BGE 中文向量模型）+ `rag_core/vectorstore.py` |

| 对比分析：基于 PDF 的结果 vs 只用 LLM | `src/compare_rag_vs_llm.py` |
| RAG 评估体系 | `src/run_evaluation.py`（RAGAS 四大指标 + 关键词准确率） |
| 语音输入 | `src/speech_input.py` |
| 稳定性 / 容错 | 各脚本的异常降级、拒答机制、索引/依赖自检 |
| 代码注释含工单编号 | 全部脚本文件头均含「工单编号：人工智能NLP-RAG-基于PDF文档的问答系统」 |

## 三、技术选型

| 组件 | 选型 | 理由 |
| --- | --- | --- |
| 开发语言 | Python 3.10+ | 金融 NLP / RAG 生态最完整，工单共享库 `rag_core` 即为 Python |
| PDF 文字解析 | PyMuPDF（`fitz`） | 速度快、页码准、对中文 PDF 兼容性好；招股书为文本型 PDF |
| PDF 表格解析 | pdfplumber → Markdown | 表格转 Markdown 后 LLM 能读懂行列关系，解决「数字答不准」 |
| 中文分词 | jieba（缺失时单字+二元组降级） | 成熟稳定，用于 BM25 倒排索引与关键词重排 |
| 向量模型 | BAAI/bge-large-zh-v1.5（1024 维） | 中文检索榜单表现优秀，金融/招股书语料适配好；查询侧自动加 BGE 指令前缀 |
| 向量库 | ChromaDB（缺失时自动降级 NumPy 点积库） | 零运维本地持久化；降级策略保证无依赖环境也能跑通 |
| 全文检索 | 自研倒排索引 + Okapi BM25 | 不引入 Elasticsearch，轻量；支持字段加权与布尔/短语/模糊查询 |
| 混合检索 | 向量 + BM25，RRF / 加权 / 投票三种融合 | 语义与关键词互补，专有名词、数字命中率显著提升 |
| 重排 | TF-IDF / LLM / 自适应 / 级联 | 级联重排兼顾精度与 3 秒响应约束（LLM 只处理少量候选） |
| 生成模型 | DeepSeek `deepseek-chat`（OpenAI 兼容接口），Ollama 本地模型备用 | 中文金融文本能力强、价格低；OpenAI 兼容协议便于替换 |
| 服务框架 | FastAPI + uvicorn | 异步高并发、自带 OpenAPI/Swagger（`/docs` 可直接上传 PDF 调试） |
| 前端界面 | 内置 HTML/CSS/JS（零构建） | 无 Node 依赖，开箱即用，降低演示与部署成本 |
| 语音识别 | speech_recognition（Google 在线）/ openai-whisper、faster-whisper（本地） | 在线免模型、离线可断网；两种引擎自动探测降级 |
| 评估 | 自研 RAGAS 四大指标（可切换官方 ragas 包）+ 关键词准确率 | 无 ragas 依赖也能评估；关键词准确率对应工单「准确率」口径 |
| 缓存 | 磁盘缓存（解析结果、LLM 响应） | 重复评测不重复计费；演示时响应更快 |

## 五、核心模块说明

### 5.1 本工单脚本（`src/`）

| 脚本 | 职责 | 关键实现 |
| --- | --- | --- |
| `build_index.py` | 建索引与统计 | 调用 `Pipeline.build_index()`；`--preset` 切换分块/表格策略；`--no-rebuild` 增量追加；统计写入 `results/index_stats.json` |
| `qa_cli.py` | 问答引擎入口 | 单问 `-q`、交互 `-i`、语音 `--voice`；支持 `--top-k/--strategy/--reranker/--show-context`；耗时与 3 秒预算比对 |
| `compare_rag_vs_llm.py` | RAG vs 纯 LLM | RAG 侧 `Pipeline.ask()`，基线侧 `generator.generate_llm_only()`；按关键词命中判胜负，输出 JSON + Markdown |
| `run_evaluation.py` | RAG 评估 | `evaluate.EvalRecord` 采集、`evaluate_records()` 算四大指标、`keyword_accuracy()` 算准确率、`save_report()` 落盘；含人工参考答案初稿与 `--answers` 覆盖机制 |
| `serve.py` | Web 服务 | `uvicorn.run("rag_core.api:app")`；打印界面/文档/健康检查地址；启动前做索引与 API Key 自检 |
| `speech_input.py` | 语音输入 | `listen_once()` 供 `qa_cli --voice` 复用；在线识别（Google）与本地 Whisper 双引擎；依赖缺失时打印安装命令并降级 |

### 5.2 共享核心模块（`rag_core/`，本工单直接复用）

| 模块 | 说明 |
| --- | --- |
| `pdf_parse.py` | 三层解析：L1 文字（PyMuPDF，去页眉页脚、合并硬换行）、L2 表格（pdfplumber → Markdown）、L3 图像（落盘供多模态描述）；解析结果按 mtime+参数做磁盘缓存 |
| `chunk.py` | 四种分块策略。工单01 默认 `fixed`（固定窗口+重叠）；`structure` 会在块首注入章节路径提升命中率；表格/图像块整体保留不切碎 |
| `vectorstore.py` | 统一门面：`add_chunks / search / count / reset`；Chroma 不可用时降级为 NumPy 矩阵点积（余弦） |
| `bm25.py` | 自实现倒排索引 + BM25（k1=1.5, b=0.75），字段加权（正文 1.0 / 章节 1.6 / 标题 2.0），支持布尔、短语、通配符与编辑距离查询 |
| `retriever.py` | 三种检索策略（vector / fulltext / hybrid）与三种融合（weighted / rrf / vote）；`format_context()` 拼装带来源标注的上下文 |
| `rerank.py` | TF-IDF 重排（数字与实体加权）、LLM 列表级重排、自适应重排（沉淀用户反馈）、级联重排（TF-IDF 粗排 → LLM 精排） |
| `query_understand.py` | 意图识别（数值/实体属性/关系/列表/比较/图表…）、实体抽取、指代消解（多轮）、问题分解与抽象 |
| `generator.py` | RAG 生成（严格依据上下文 + 拒答 + 引用解析）与纯 LLM 基线；中英文自动切换 Prompt |
| `evaluate.py` | RAGAS 四大指标的自实现 + 官方 ragas 适配层；检索层指标 Hit Rate / MRR / Recall@k；关键词准确率；报告落盘与格式化 |
| `pipeline.py` | 把「解析→分块→建索引→检索→生成」串成流水线，`PRESETS` 定义各工单能力档位 |

### 5.3 流水线预设与本工单

| 预设 | 分块 | 表格 | 检索 | 重排 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `wo01_baseline`（默认） | fixed | 否 | vector | none | 工单01 基础版，建索引最快 |
| `wo02_optimized` | structure | 否 | vector | tfidf | 工单02 优化版 |
| `wo03_table` | structure | 是 | vector | tfidf | 开启表格解析，满足「表格数据」验收 |
| `wo06_hybrid` | structure | 是 | hybrid(RRF) | cascade | 效果最好，Web 服务默认；耗时略高 |

> 三个脚本均支持 `--preset` 切换，便于在第 2 步就对比不同方案。索引里同时包含
> 向量与 BM25，因此用 `wo06_hybrid` 提问无需重新建索引（但分块内容不同，
> 建议「用哪个预设提问，就用哪个预设建索引」）。

## 六、Query 理解设计

工单要求「意图识别、消歧、分解与抽象」，实现分四步（`query_understand.understand()`）：

| 能力 | 实现方式 | 示例 |
| --- | --- | --- |
| 意图识别 | 规则优先（正则模式表），覆盖数值查询、实体属性、关系查询、列表查询、比较查询、图表查询、操作指令、闲聊 8 类 | 「注册资本是多少」→ 实体属性；闲聊「你好」→ 不检索，直接返回引导语 |
| 消歧 | ① 指代词识别（他/该公司/这个公司…）；② 多实体检测并提示歧义，按全部实体并行检索 | 「那武汉力源呢？」→ 结合上文补全为完整问题 |
| 分解 | 规则先判断是否含并列结构（并/以及/分别），复杂问题再调 LLM 拆成 ≤4 个可独立检索的子问题，多路检索后按 chunk 去重合并 | 「A 的 X 和 B 的 Y 分别是多少」→ 两个子问题 |
| 抽象 | 实体抽取（公司类实体正则）+ 把口语化问题改写成自包含检索式 | 「他参与的哪个工程获一等奖？」→ 替换为完整公司名 |

工单01 默认预设 `wo01_baseline` 关闭 Query 理解（`use_query_understanding=False`），
以保证基线纯净；使用 `--preset wo03_table` / `wo06_hybrid` 即自动开启。

## 七、Prompt 设计说明

生成侧 System Prompt 位于 `rag_core/generator.py`，核心规则：

| 规则 | 目的 |
| --- | --- |
| 1. 只依据【参考资料】作答，不用外部知识、不做常识推测 | 从机制上杜绝幻觉 |
| 2. 先定位后作答（先在内部确认信息出现在哪个片段） | 提升数字类问题的准确率 |
| 3. 数值逐字核对，多期数据按期间分行列出 | 招股书大量金额/比例/年份，防止张冠李戴 |
| 4. 表格类资料按行读取，注意表头与数据行对应 | 表格数据易串行 |
| 5. 资料不足时固定回复「根据提供的文档内容，未能找到该问题的答案。」 | 明确的拒答口径，便于程序判定 `refused` |
| 6. 先结论后细节，不复述问题 | 答案简洁 |
| 7. 末尾用【来源】片段X（第Y页）标注 | 可溯源，程序解析为结构化 citations |

其他 Prompt：

| Prompt | 位置 | 用途 |
| --- | --- | --- |
| 纯 LLM 基线 System | `generator.generate_llm_only()` | 对比实验的对照组：只有「你是一个乐于助人的助手」，不提供任何文档 |
| 论断分解 | `evaluate.split_claims()` | 把答案/参考答案拆成原子论断，供忠实度与召回计算 |
| 支撑判定 | `evaluate._judge_support()` | 逐条判断论断能否被上下文支撑 |
| 反向生成问题 | `evaluate.answer_relevancy()` | 由答案反推问题，与原问题算相似度 |
| 片段相关性判定 | `evaluate._judge_relevance()` | 上下文精度的相关性标注 |
| 多轮改写 | `query_understand._REWRITE_SYS` | 指代消解，把省略句补全为自包含问题 |

工程约束：所有判分类 Prompt 温度设为 0；生成答案 `max_tokens=1500`，判分类更小；
`llm.chat()` 带磁盘缓存，重复评测不重复计费。

## 八、性能与稳定性设计

### 8.1 3 秒响应时间

| 阶段 | 典型耗时 | 优化手段 |
| --- | --- | --- |
| Query 理解 | 规则通道 < 5 ms（仅复杂问题调 LLM） | 规则优先，避免无谓 LLM 调用 |
| 检索（向量+BM25+融合） | 本地 < 100 ms | 索引常驻内存；NumPy 点积/Chroma HNSW |
| 重排 | TF-IDF < 50 ms；级联重排含 1 次 LLM 调用 | 只对少量候选调用 LLM；可用 `--reranker tfidf` 换取更低延迟 |
| 生成 | 1~2.5 s（取决于 API） | 上下文截断到 4000 字符、`max_tokens` 限制、LLM 磁盘缓存 |

实测值记录在 `results/evaluation.json` 的 `latency_avg / latency_p95 / latency_max`，
对比实验中两侧耗时见 `results/rag_vs_llm.json` 的 `summary`。

### 8.2 容错与高可用

| 风险 | 处理 |
| --- | --- |
| 用户输入为空/超长/乱码 | CLI 过滤空输入、超长截断到 500 字；Web 端空输入不发送 |
| 问题与文档无关 | Query 理解判为闲聊 → 直接引导语；检索无上下文 → 固定拒答话术 |
| 单题问答异常（网络/限流） | `qa_cli` / `compare_rag_vs_llm` / `run_evaluation` 逐题捕获异常，不中断整轮任务 |
| 索引缺失 | 启动自检并打印修复命令（`build_index.py`） |
| 缺少 `chromadb` | 自动降级为 NumPy 向量库 |
| 缺少 `jieba` | BM25 降级为「单字 + 二元组」分词 |
| 缺少 `ragas` | 使用 `evaluate.py` 内置同口径实现 |
| 缺少语音依赖/麦克风 | 打印安装命令，建议改用 `--file` 音频文件；`qa_cli --voice` 自动退回键盘输入 |
| LLM 不可用 | `llm.get_client()` 明确报错；检索与评估的规则回退路径仍可运行 |
| PDF 解析失败 | `build_index.py` 捕获异常并提示常见原因（加密/损坏/缺依赖） |
| 生成被判分依赖缺失 | `run_evaluation.py` 自动降级为不依赖向量模型的指标子集 |

## 十、已知限制与后续演进

1. **表格解析默认关闭**：pdfplumber 逐页解析数百页 PDF 较慢，按需用
   `--with-tables` 开启；表格相关问题的召回质量可进一步用表格专项检索优化（工单03）。
2. **上传接口只增量写入向量库**：通过 `/api/upload` 新增的 PDF 不会同步更新 BM25
   倒排索引，若需全文检索同步命中，请重新运行 `build_index.py`。
3. **参考答案为人工初稿**：`run_evaluation.py` 内置的关键词/参考答案需按实际文档校准，
   支持 `--answers` 传入修正版 JSON。
4. **首次运行耗时较高**：嵌入模型下载与 PDF 解析只在首次发生，之后走磁盘缓存。
5. **多轮对话的会话状态在内存**：进程重启后丢失，生产化可改用 Redis（工单10 部署）。
