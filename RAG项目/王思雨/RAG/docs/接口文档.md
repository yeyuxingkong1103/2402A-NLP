## 1. 接口约定

| 项目 | 值 |
|---|---|
| 服务地址 | `http://127.0.0.1:8000`（由 `.env` 的 `API_HOST` / `API_PORT` 控制） |
| 请求格式 | `application/json`（上传接口为 `multipart/form-data`） |
| 响应格式 | `application/json`（问答流式为 `text/event-stream`） |
| 字符编码 | 全部 UTF-8 |
| 交互文档 | 启动后访问 `/docs`（Swagger UI）或 `/redoc` |
| 鉴权 | 教学版：`/auth/login` 返回 token，但各接口暂未强制校验（见设计文档 16.4） |

### 1.1 GET /health

健康检查：返回服务状态与三项依赖（Milvus / MySQL / Redis）的连通情况。
前端「后台」页用它显示依赖状态，也是排查配置是否填对的最快手段。

**Request**：无参数、无请求体

**Response 200**

```json
{"status": "ok", "milvus": true, "mysql": true, "redis": true}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | string | 固定为 `ok`；只要服务能响应就是 ok |
| `milvus` | bool | Milvus 是否可连（实际执行一次列集合探测） |
| `mysql` | bool | MySQL 是否可连（实际执行一次查角色表探测） |
| `redis` | bool | Redis 是否可连（实际执行一次读短期记忆探测） |

**示例**

```bash
curl http://127.0.0.1:8000/health
# {"status":"ok","milvus":true,"mysql":true,"redis":true}
```

**说明**：三个布尔值**各自独立探测**，某一项探测抛异常只会让那一项为 `false`，
不影响其他两项，也不影响接口本身返回 200——它报告的是"探测结果"，
而不是"服务是否可用"。所以这里**没有 500**。

| 状态码 | 说明 |
|---|---|
| 200 | 探测完成（依赖全挂也是 200，从 `milvus`/`mysql`/`redis` 三个字段读实际状态） |

## 2. 认证接口

### 2.1 POST /auth/register

用户注册。

**Request Body**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `username` | string | 是 | 1~64 字符 | 用户名，全局唯一 |
| `password` | string | 是 | 6~128 字符 | 密码明文，服务端只存哈希 |

```json
{"username": "zhangsan", "password": "pwd123456"}
```

**Response**

| 状态码 | 说明 | 响应体 |
|---|---|---|
| 200 | 注册成功 | `{"user_id": 12, "username": "zhangsan", "msg": "注册成功"}` |
| 400 | 用户名已存在 | `{"detail": "用户名已存在"}` |
| 422 | 参数不合法（长度不符） | Pydantic 标准校验错误 |
| 500 | 服务端异常 | `{"detail": "..."}` |

### 2.2 POST /auth/login

用户登录。

**Request Body**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `username` | string | 是 | 用户名 |
| `password` | string | 是 | 密码明文 |

**Response**

| 状态码 | 说明 | 响应体 |
|---|---|---|
| 200 | 登录成功 | `{"user_id": 12, "username": "zhangsan", "token": "<64位十六进制>"}` |
| 401 | 用户名或密码错误 | `{"detail": "用户名或密码错误"}` |
| 500 | 服务端异常 | `{"detail": "..."}` |

> `token` 是 `sha256(user_id + PASSWORD_SALT)`，教学版，生产应换 JWT。

**示例**

```bash
curl -X POST http://127.0.0.1:8000/auth/login   -H "Content-Type: application/json"   -d '{"username":"zhangsan","password":"pwd123456"}'
# {"user_id":12,"username":"zhangsan","token":"389af7d3...（64 位十六进制）"}
```

## 5. 会话接口

创建会话。

**Request Body**

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `user_id` | int | 是 | — | 所属用户编号 |
| `role_id` | int | 是 | — | 使用的角色编号 |

| 状态码 | 说明 | 响应体 |

**示例**

```bash
curl -X POST http://127.0.0.1:8000/conversation   -H "Content-Type: application/json"   -d '{"user_id":12,"role_id":1,"title":"接口测试会话"}'

```

| 状态码 | 说明 | 响应体 |
|---|---|---|
| 200 | 查询成功（无会话也返回空数组） | `{"conversations": [...]}` |
| 500 | 服务端异常（查库失败） | `{"detail": "..."}` |

**示例**


### 5.3 DELETE /conversation/{conversation_id}

删除会话，**并级联删除该会话下的全部消息**（第 9.6 步起）。
只能删自己的——SQL 用 `WHERE id=? AND user_id=?` 双条件。

**Path 参数**：`conversation_id` (int)
**Query 参数**：`user_id` (int, 必填) — 用于校验归属

**删除范围**（第 9.6 步修复前后对比）：

| 表 | 第 9.6 步之前 | 第 9.6 步之后 |
|---|---|---|
| `conversations` | 删除该会话行 | 删除该会话行 |
| `messages` | **不删**，变成孤儿，`GET /message/{id}` 仍能查到内容 | 同一事务内一并删除 |

**事务与归属校验**：先 `SELECT ... WHERE id=? AND user_id=? FOR UPDATE` 确认归属并加行锁，
确认是自己的才会往下删；不是自己的直接返回 0，**一条消息都不会动**。
两条 `DELETE` 在同一事务里提交，任一步失败整体回滚。

| 状态码 | 说明 | 响应体 |
|---|---|---|
| 200 | 删除成功（会话与消息都已删除） | `{"msg": "deleted"}` |
| 404 | 会话不存在或不属于该用户（**未删除任何数据**） | `{"detail": "会话不存在或不属于该用户"}` |

```bash
curl -X DELETE "http://127.0.0.1:8000/conversation/28?user_id=40"
# {"msg":"deleted"}

# 重复删除或越权删除，都是 404，且不会误删别人的消息
curl -X DELETE "http://127.0.0.1:8000/conversation/28?user_id=999"
# {"detail":"会话不存在或不属于该用户"}
```

## 6. 消息接口

### 6.1 GET /message/{conversation_id}

按编号升序返回会话内的消息。

**Path 参数**：`conversation_id` (int)
**Query 参数**：`limit` (int, 默认 50) — 最多返回条数

**Response 200**

```json
{
  "messages": [
    {"message_id": 1, "role": "user", "content": "变压器漏油怎么处理",
     "created_at": "2026-09-29 21:08:52"},
    {"message_id": 2, "role": "assistant", "content": "安全提醒……",
     "created_at": "2026-09-29 21:08:58"}
  ]
}
```

**说明**：`role` 是说话方（`user` / `assistant`），与业务角色（电力维修专家）不是一回事。
按 `message_id` 升序返回，便于前端直接按顺序渲染。

| 状态码 | 说明 | 响应体 |
|---|---|---|
| 200 | 查询成功（无消息返回空数组） | `{"messages": [...]}` |
| 500 | 服务端异常（查库失败） | `{"detail": "..."}` |

**示例**

```bash
curl "http://127.0.0.1:8000/message/8?limit=50"
# {"messages":[{"message_id":1,"role":"user","content":"变压器漏油怎么处理",...},
#              {"message_id":2,"role":"assistant","content":"**结论：** ...",...}]}
```

## 7. 问答接口

### 7.1 POST /chat

核心问答接口。非流式返回完整结果，流式见第 11 节。

**Request Body**

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `user_id` | int | 是 | — | 用户编号，决定读写谁的记忆 |
| `role_id` | int | 是 | — | 角色编号，决定用哪份系统提示词 |
| `conversation_id` | int | 是 | — | 会话编号，消息落库用 |
| `query` | string | 是 | — | 用户问题 |
| `stream` | bool | 否 | `false` | 是否流式返回 |

```json
{"user_id": 12, "role_id": 1, "conversation_id": 8,
 "query": "变压器漏油怎么处理", "stream": false}
```

**Response 200（非流式）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `answer` | string | 后处理后的回答正文 |
| `sources` | array | 引用来源，每项 `{source, summary, score}` |
| `rewritten_query` | string | 实际用于检索的问题（无历史时等于原问题） |
| `cache_hit` | bool | 是否命中缓存 |
| `conversation_id` | int | 会话编号（回显） |
| `usage` | object | `{prompt_tokens, completion_tokens, total_tokens}` |
| `long_memory_used` | int | 本轮实际带入的长期记忆条数（第 9 步加入，前端据此展示「长期记忆 N 条」标签） |

**内部行为**（前端不需要感知，但影响响应时间）：
1. 取该用户短期记忆（Redis）
2. 有历史则做查询改写（调 LLM，约 3~5 秒）
3. 查答案缓存：**命中则跳过第 4 步的检索与大模型生成，但仍执行第 5 步的写回**
4. 检索知识库 + 长期记忆 → 重排 → 调大模型生成（约 10~20 秒）
5. 写回 MySQL / Redis / Milvus 三处

> **第 9.7 步修正**：第 3 步命中缓存时过去会直接 `return`，于是这一轮不写 MySQL、
> 不进 Redis 短期记忆、不写 Milvus 长期记忆，导致下一轮的 history 缺一段、多轮对话断片。
> 现在命中缓存**只跳过第 4 步**（昂贵的检索与生成），第 5 步照常执行，
> 两条路径的副作用完全对称。详见设计文档 16.9.8。

**`cache_hit=true` 时这几个字段的含义**：返回的是缓存里上一轮存下的完整结果，
所以下列字段**来自缓存**，反映的是**首次回答那一次**的情况，不是本次重新算的：

| 字段 | cache_hit=true 时的来源 |
|---|---|
| `answer` | 缓存中首次回答的正文（第 9.7 步起会用它写入本轮的消息与记忆） |
| `sources` | 缓存中首次回答的引用来源 |
| `rewritten_query` | 缓存中首次回答的改写结果 |
| `usage` | 缓存中首次回答的 token 用量（本次没有真实消耗） |
| `conversation_id` | 本次传入的会话编号（原样回显） |
| `cache_hit` | `true` |
| `long_memory_used` | 缓存中首次回答时的长期记忆条数 |

| 状态码 | 说明 |
|---|---|
| 200 | 成功 |
| 422 | 参数不合法（如 `query` 为空） |
| 500 | 问答链路异常 |

## 8. 知识库接口

### 8.1 POST /kb/upload

上传 PDF 并解析。本接口只解析不入库，入库请调 `/kb/rebuild`。

**Request**：`multipart/form-data`，字段名 `file`

```bash
curl -X POST http://127.0.0.1:8000/kb/upload -F "file=@标准文档.pdf"
```

**Response 200**

```json
{"file_name": "GBT 27743-2025 变压器专用设备检测方法.pdf",
 "status": "parsed", "pages": 15, "chunks": 76}
```

| 字段 | 说明 |
|---|---|
| `status` | 固定 `parsed`（只解析，未入库） |
| `pages` | 解析出的页数 |
| `chunks` | 语义切分出的块数 |

文件会保存到 `.env` 的 `PDF_DIR` 目录。

| 状态码 | 说明 | 响应体 |
|---|---|---|
| 200 | 解析完成（**只解析未入库**） | `{"file_name": "...", "status": "parsed", "pages": 15, "chunks": 76}` |
| 422 | 没带 `file` 字段 | `{"detail": [...]}` |
| 500 | 写文件或解析失败 | `{"detail": "..."}` |

**示例**

```bash
curl -X POST http://127.0.0.1:8000/kb/upload -F "file=@GBT_27743.pdf"
# {"file_name":"GBT_27743.pdf","status":"parsed","pages":15,"chunks":76}
```

### 8.2 POST /kb/rebuild

触发知识库重建：离线增强 + 全量向量入库，后台执行，立即返回。

**Response 200**

```json
{"status": "started", "msg": "重建任务已在后台执行，请稍后用 /kb/status 查询"}
```

> 实测重建耗时约 75 秒（增强 55 秒 + 入库 20 秒），因此用 `BackgroundTasks` 异步执行。
> 任务在服务进程内运行，服务重启任务即丢失（见设计文档 16.5）。

**Request**：无参数、无请求体

| 状态码 | 说明 | 响应体 |
|---|---|---|
| 200 | 任务已提交（**不代表已重建完成**，需轮询 `/kb/status`） | `{"status": "started", "msg": "..."}` |
| 500 | 提交失败 | `{"detail": "..."}` |

**示例**

```bash
curl -X POST http://127.0.0.1:8000/kb/rebuild
# {"status":"started","msg":"重建任务已在后台执行，请稍后用 /kb/status 查询"}
```

## 9. 评测接口

### 9.1 GET /eval/result

读取 `data/ragas_result.json`（由 `python -m eval_ragas` 产出），返回完整评测结构。

**Request Body / Query 参数**：无

**Response 200（有评测结果）**

```json
{
  "timestamp": 1759213200,
  "model": "deepseek-v4-flash",
  "embedding": "bge-m3",
  "summary": {
    "faithfulness": 0.3125,
    "answer_relevancy": 0.8146,
    "context_precision": 0.5281,
    "context_recall": 0.9333
  },
  "details": [
    {
      "question": "绝缘油中溶解气体的气相色谱测定中，样品中溶解的气体是怎么获得的？",
      "answer": "**结论：** 对一定体积的油样通过顶空取气或真空脱气……",
      "ground_truth": "对一定体积的油样通过顶空取气或真空脱气获得样品中溶解的气体……",
      "faithfulness": 0.339,
      "answer_relevancy": 0.7842,
      "context_precision": 0.5333,
      "context_recall": 1.0
    }
  ]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `timestamp` | int | 评测时间戳（秒） |
| `model` | string | 评估用大模型名称，来自 `.env` 的 `LLM_MODEL` |
| `embedding` | string | 评估用向量模型名称，固定 `bge-m3` |
| `summary` | object | 四项指标的**均分**，字段见下表 |
| `details` | array | 逐条明细，每条对应评测集里的一条问题 |

`summary` 与 `details` 里的单条使用同一组字段名：

| 字段 | 类型 | 说明 |
|---|---|---|
| `faithfulness` | float | 忠实度：回答是否忠于检索到的上下文 |
| `answer_relevancy` | float | 答案相关度：回答是否切题 |
| `context_precision` | float | 上下文精确率：检索到的上下文是否精准 |
| `context_recall` | float | 上下文召回率：该召回的依据是否都召回了 |
| `question` | string | 评测问题（仅 `details` 有） |
| `answer` | string | 系统回答（仅 `details` 有） |
| `ground_truth` | string | 参考答案，人工从 PDF 原文摘录（仅 `details` 有） |

**Response 200（还没跑过评测，文件不存在）**

```json
{"timestamp": 0, "model": "", "embedding": "", "summary": {}, "details": []}
```

> 说明：路由挂了 `response_model=schemas.EvalResp`。handler 在文件不存在时返回
> `{"summary": {}, "details": []}`（第 10 步规格要求的形式），
> 经模型序列化后，`summary: {}` 会被补成四个 0.0 的完整结构，
> 前端因此总能拿到形状一致的数据，只需判断 `details.length === 0` 即可显示空态。

| 状态码 | 说明 |
|---|---|
| 200 | 成功（没跑过评测也返回 200 与空结构，不是错误） |
| 500 | 结果文件存在但内容不是合法 JSON |

## 10. 缓存接口

### 10.1 GET /cache/clear

清空**指定用户**的短期记忆与答案缓存（第 8.5 步起按用户精确清理）。

**Query 参数**：`user_id` (int, 必填)

**Response 200**

```json
{"msg": "cleared", "cache_keys": 3, "short_memory": true}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `msg` | string | 固定 `cleared` |
| `cache_keys` | int | 实际删除的缓存键数量 |
| `short_memory` | bool | 短期记忆是否清除成功 |

**清理范围**：
- 答案缓存：`cache:rag:answer:{user_id}:*`（用 Redis `SCAN` 游标遍历，不用 `KEYS`）
- 短期记忆：`mem:short:{user_id}`

**只清该用户**：键结构里含 `user_id` 段，因此可以按前缀精确匹配，不会误删其他用户的缓存。

**缓存键结构**（第 8.5 步起）：

```
cache:rag:answer:{user_id}:{role_name}:{归一化后的原始问题}
```

`归一化` = 去中英文标点 + 合并连续空白 + 转小写。
因此 `变压器漏油怎么处理`、`变压器漏油怎么处理？`、`变压器漏油，怎么处理！`
会命中同一个缓存条目。

| 状态码 | 说明 |
|---|---|
| 200 | 清理完成 |
| 422 | 缺少 `user_id` 参数 |
| 500 | Redis 不可用等异常 |

> **实现说明**：该路由挂的是 `response_model=schemas.ClearCacheResp`（第 9 步起）。
> 第 8.5 步时 `schemas.py` 不允许改动，`MsgResp` 只有 `msg` 一个字段，
> 挂上会把 `cache_keys` 与 `short_memory` 过滤掉，因此当时暂时不挂；
> 第 9 步新增了 `ClearCacheResp`，两个字段已纳入模型，问题解决。

### 10.2 GET /cache/stats

统计 Redis 里的答案缓存与短期记忆，供后台页只读展示（第 9.5 步新增）。

**Query 参数**：无

**Request**

```bash
curl http://127.0.0.1:8000/cache/stats
```

**Response 200**

```json
{
  "total_keys": 3,
  "by_user": {"40": 2, "41": 1},
  "short_memory_users": 12
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `total_keys` | int | `cache:rag:*` 答案缓存键总数 |
| `by_user` | object | 按用户分组，键是 `user_id` 的字符串形式，值是该用户的缓存键数量 |
| `short_memory_users` | int | 存在短期记忆的用户数，即 `mem:short:*` 的键个数 |

**统计范围**：

| 扫描模式 | 用途 |
|---|---|
| `cache:rag:*` | 答案缓存。按冒号切分后**第 4 段**是 `user_id`（键形如 `cache:rag:answer:40:power_repair_expert:问题`），据此分组 |
| `mem:short:*` | 短期记忆，一个用户一个键，键的个数就是有记忆的用户数 |

**两个实现要点**：

1. 用 **Redis `SCAN`**（`count=200`）分批遍历，**不用 `KEYS`**。
   `KEYS` 会一次性遍历整个键空间并阻塞 Redis 单线程，键多了会拖垮服务。
2. 同一台 Redis 上可能还有别的应用的键（实测本机 83 个键里有大量
   `chat:history:*`、`user:sessions:*` 属于其他项目），所以**模式前缀必须写准**，
   只扫 `cache:rag:*` 与 `mem:short:*`，不能图省事扫 `*`。
   切分后第 4 段不是数字的键会被跳过，不计入 `by_user`。

| 状态码 | 说明 |
|---|---|
| 200 | 统计成功（没有缓存时返回 `{"total_keys": 0, "by_user": {}, "short_memory_users": 0}`） |
| 500 | Redis 不可用等异常 |

## 11. 流式接口（SSE）

`POST /chat` 传 `{"stream": true}` 时，返回 `Content-Type: text/event-stream`。

### 11.1 帧结构

```
data: <正文片段>

data: <正文片段>

...

data: {"sources": [...], "usage": {...}, "conversation_id": 8, "long_memory_used": 2}

data: [DONE]

```

（实际传输中每帧以 `\n\n` 结尾，上面的空行即表示该分隔）

| 帧类型 | 内容 | 说明 |
|---|---|---|
| 正文帧 | 纯文本片段 | 已做行内后处理，可直接拼接显示 |
| 结束信息帧 | JSON 字符串 | 含 `sources` / `usage` / `conversation_id` / `long_memory_used` |
| 错误帧 | `{"error": "..."}` | 生成过程中断时推送 |
| 结束标记 | `[DONE]` | 总是推送，包括出错之后 |

### 11.2 关键约定

- 每帧以 `\n\n` 结尾（SSE 规范要求空行分隔）
- `[DONE]` 一定出现：正常结束时推；出错时先推错误帧、再推 `[DONE]`，
  保证前端读取循环能退出
- 流式不走缓存（避免缓存半截答案）
- 流式的结束 JSON 不含 `rewritten_query` 与 `cache_hit`

### 11.3 演示

```bash
curl -N -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -d "{\"user_id\":12,\"role_id\":1,\"conversation_id\":8,\"query\":\"绝缘油气相色谱分析步骤\",\"stream\":true}"
```

实测输出 24 帧：22 个正文帧 + 1 个结束信息帧 + `[DONE]`。

## 12. 错误码统一说明

| 状态码 | 触发场景 | 响应体格式 |
|---|---|---|
| 200 | 成功 | 各接口自定义 |
| 400 | 参数合法但业务拒绝（如用户名已存在） | `{"detail": "用户名已存在"}` |
| 401 | 认证失败（用户名或密码错误） | `{"detail": "用户名或密码错误"}` |
| 404 | 资源不存在或无权访问 | `{"detail": "用户不存在"}` |
| 422 | 参数格式或长度不合法（Pydantic 校验失败） | FastAPI 标准校验错误结构 |
| 500 | 服务端异常（数据库、模型、向量库故障） | `{"detail": "<异常信息>"}` |

**说明**：
- 业务错误统一用 FastAPI 的 `detail` 字段，没有自定义 `error` 字段；
  统一 `{"error": "..."}` 结构目前只用于**流式的错误帧**（因为 SSE 帧无法携带状态码）。
- **500 响应不包含 Python 堆栈**，只有异常信息；完整堆栈记在 `logs/app.log`。

`search_long_memory` 返回 `[{question, answer, score}]`，**只返回该 user_id 自己的记忆**。

### 14.7 ask 新签名（rag.py）

第 6 步起 `ask` 签名改为：

```python
ask(query, user_id, role_id, conversation_id, top_k=None, stream=False)
```

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `query` | str | — | 用户问题 |
| `user_id` | int | — | **必填**，用户编号，用于读写记忆 |
| `role_id` | int | — | **必填**，角色编号 |
| `conversation_id` | int | — | **必填**，会话编号，消息落库用 |
| `top_k` | int | `None` | 检索条数 |
| `stream` | bool | `False` | 是否流式 |

**返回（stream=False）** 在原字段基础上新增：

| 字段 | 说明 |
|---|---|
| `conversation_id` | 本轮所属会话 |
| `history_used` | 实际带入的历史条数 |
| `long_memory_used` | 实际带入的长期记忆条数 |

**返回（stream=True）**：逐段 yield 正文，最后 yield 的 JSON 新增 `conversation_id` 与 `long_memory_used`。

## 18. 前端调用说明

本节面向 `frontend/` 里的前端代码，说明三件容易踩坑的事：请求头、SSE 解析、缓存键与来源字段。

### 18.1 统一请求头 X-User-Id

除 `/auth/register`、`/auth/login`、`/health` 之外，前端所有请求都带上当前用户编号：

```
X-User-Id: 40
```

由 `frontend/src/api.js` 的 axios 请求拦截器从 `localStorage.getItem('user_id')` 取，
未登录时不带。

> **注意**：第 8 步起后端**不校验**该请求头（教学版，见设计文档「已知局限」）。
> 各接口真正使用的还是 URL 或 body 里的 `user_id` 字段，请求头只是为了让浏览器侧
> 有一个统一的用户标识位置，方便后续换成真正的鉴权中间件。

### 18.2 基础地址与代理

前端 `baseURL = '/api'`，由 Vite 开发服务器代理到后端：

```
浏览器请求  /api/kb/status
   ↓ Vite 代理（去掉 /api 前缀）
后端请求    http://127.0.0.1:8000/kb/status
```

因此浏览器侧不产生跨域。生产部署时把 `/api` 反向代理到后端即可，前端代码不用改。

### 18.3 SSE 流式解析规则

`POST /chat` 传 `{"stream": true}` 时返回 SSE。**不能用 `EventSource`**，因为它只支持 GET，
而本接口需要 POST body。前端用 `fetch` + `response.body.getReader()` 手写解析，
实现见 `frontend/src/api.js` 的 `chatStream()`。

解析规则：

1. 用 `TextDecoder` **以 `{stream: true}` 方式增量解码**。
   一个汉字占 3 字节，可能被切在两次 `read()` 之间，不用增量解码会出现乱码或抛
   `UnicodeDecodeError`（联调时实测踩到过）。
2. 把已解码文本按 `\n\n` 切帧，**最后一段留到下一轮**，因为它可能不是完整帧。
3. 跳过不以 `data: ` 开头的行。
4. 去掉 `data: ` 前缀后的内容分三种：
   - 等于 `[DONE]` → 收尾（`onEnd(null)`）；
   - `JSON.parse` **成功** → 这是结束信息帧，含 `sources` / `usage` / `conversation_id` /
     `long_memory_used`，交给 `onEnd(payload)`；若含 `error` 字段则交给 `onError`；
   - `JSON.parse` **失败** → 这是正文片段，交给 `onChunk(text)` 追加显示。

> 判定顺序不能反：正文片段里可能包含 `{`、`"` 等字符，但不会是合法 JSON；
> 而结束信息帧一定是合法 JSON。所以「能解析成 JSON」就等于「这是结束帧」。

前端把 `chatStream()` 的返回值设计成 `AbortController`，页面上的「停止」按钮调
`ctrl.abort()` 即可中断生成；`abort` 触发的 `AbortError` 不算错误，不弹提示。

### 18.4 来源字段说明

结束信息帧里的 `sources` 是一个数组，每项结构：

| 字段 | 类型 | 说明 |
|---|---|---|
| `source` | string | 来源文件名，如 `GBT 17623-2026 绝缘油中溶解气体组分含量的气相色谱测定法.pdf` |
| `summary` | string | 该片段的摘要（父块文本截断） |
| `score` | float | 重排后的相关度分数，0~1，越大越相关 |

`frontend/src/views/Chat.vue` 把它挂在对应的助手消息上，用 `el-collapse` 折叠展示；
气泡下方的「长期记忆 N 条」标签来自同一个帧的 `long_memory_used`。

> **重要**：`sources` **只在流式/非流式当次响应里存在**，`messages` 表没有这一列，
> 所以 `GET /message/{conversation_id}` 拿不到来源。前端历史页因此只展示问答正文。

### 18.5 缓存键说明

答案缓存的键结构（第 8.5 步起）：

```
cache:rag:answer:{user_id}:{role_name}:{归一化后的原始问题}
```

| 要点 | 说明 |
|---|---|
| 位置 | 键里含 `user_id` 段，所以「清空缓存」能按用户精确清理，不会误删别人 |
| 归一化 | 去中英文标点 + 合并连续空白 + 转小写，同一问题的不同标点写法命中同一条 |
| 命中范围 | 键里含 `role_name`，同一问题在不同角色下是两条缓存，不会串角色 |
| 只走非流式 | 流式问答**不读也不写**缓存，避免缓存到半截答案 |
| 前端影响 | 命中缓存时 `cache_hit=true` 且响应明显变快，前端目前不额外提示 |
