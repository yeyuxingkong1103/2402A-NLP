## 背景与定位

本特性实现 `docs/05_接口设计.md` 检索链路的第一步：**把用户问题变成与知识库同一空间的向量**。

用户给出的链路是「输入 → 向量化 → 语义检索 → 生成提示词 → 生成答案」。本特性做前两步，交付**向量**，不交付检索结果。

### 上游已经为这件事留好了接口

`backend/embed/model.py` 的模块文档字符串写得很明确：

> BGE-M3 编码器 —— **全项目唯一的编码口径定义**（D3）。批处理脚本（S5）与**将来的后端查询（读路径）共用本模块**，口径只有一处，"抄错口径"的风险因此为零。

它已经提供了 `Encoder.encode_query(text)`，并且 `MODEL_DIR` 的默认值就是 `E:\资料\BAAI--bge-m3`。

**因此本特性最重要的约束不是"实现向量化"，而是"不要重新实现一遍"** —— 见下方《本特性最大的风险》。

### 本特性最大的风险：向量空间漂移

`docs/04_数据管线设计.md` §8 把"向量空间漂移"列为头号风险。它的失效方式是**静默的**：

- 用同一模型但不同口径（比如换了 pooling、忘了 L2 归一化、改了 `max_length`）编码查询，
  向量仍然合法、维度仍然对、余弦相似度仍然算得出来；
- 但排序结果会**悄悄变差**，没有任何异常、没有任何报错；
- 用户看到的是一份看起来正常、实则依据不相关的回答。

正因如此，本特性把**指纹比对**做成了硬门禁：查询向量的编码参数 MUST 与 `data/index_manifest.json` 里记录的 `embed` 指纹逐字段一致，不一致必须**拒绝并报错**，而不是继续算。

> **注意**：本次交付的向量**本期不会被任何东西消费**（检索模块尚未实现）。因此漂移的代价不会立刻显现，只会在检索接入时集中爆发 —— 这正是"现在就要把门禁做进去"的理由。等到那时才发现口径不一致，要回头重算全部查询向量，且无从判断历史上哪些回答是错的。

### 三项前置裁决（2026-09-27 已确认）

规格起草时发现三处**需要人工裁决**的分叉。按"严禁私自做决策"的约定提交裁决，结论如下：

| 编号 | 议题 | 分叉点 | 裁决 |
|---|---|---|---|
| **D1** | 向量化在哪发生 | 服务端在线 / 离线脚本 | **服务端在 `POST /ask` 内同步完成**，权重启动期加载并常驻 |
| **D2** | 向量如何落盘 | 一问题一文件 / 单文件追加 / 共享矩阵 | **单文件追加 JSONL，向量内联为数组**，按日期切分 |
| **D3** | 问题原文的留存边界 | 与 `docs/01` §7.2「不做历史记录」的张力 | **全文留存 + 三条约束**：§7.2 加注记、提供按日期清理入口、目录不入版本库 |

**D1 的代价必须写清**：BGE-M3 权重**2.27 GB**，加载后常驻内存。这意味着服务的内存占用会显著上升，且启动时间变长（要等权重加载完才能监听端口）。换来的是与 `docs/02` §10 部署视图（"BGE-M3 权重加载 常驻内存"）、`docs/05` §2.4 延迟预算（已为查询向量化预留 0.3 s）一致，且检索模块接入时不必再改一次服务端。

**D3 的张力不会因为做了三条约束就消失**。诚实地说：留存用户医疗提问**确实**扩大了个人健康信息的存储面，而 `docs/01` §7.2 给「不做历史记录」的理由正是"少收集个人信息也降低合规负担"。三条约束做的是**把这件事显式化并给出退出手段**，不是把它变成没有代价的事。

> **D2 的体量估算已在 Phase 0 实测修正**：起草时写的是"每行约 10 KB"，实测单条向量序列化后是 **21,175 字节**（1024 个 float32，每个约 19 字符），加上问题原文与元数据，**每行约 21–22 KB**。
> 按每天 100 问算 ≈ **2.1 MB/天、64 MB/月**。仍是 MB 级，不改变 D2 的成立（追加写与可读性的收益仍在），但那个数字得按实测写。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 提问被完整留存下来 (Priority: P1)

用户在"医知源"界面提交一个问题。服务端在应答的同时，把这次提问**原样留存在磁盘上**：问题文本、本次回答的标识、提交时刻。事后可以按标识找到"当时到底问了什么"。

**Why this priority**: 这是后续所有离线分析（检索质量评估、语料缺口分析）的唯一数据来源。没有它，检索模块接入后拿不到任何真实问题来验证效果，只能自己造样例 —— 而造出来的样例天然避开了真实用户的表达方式。

**Independent Test**: 提交 3 个不同的问题，检查磁盘上出现 3 条记录，每条含问题原文、可关联标识与时间戳，且与界面提交的内容逐字一致。

**Acceptance Scenarios**:

1. **Given** 服务已启动，**When** 用户提交"我最近血压有点高，多少算高血压？"，**Then** 磁盘上出现一条记录，问题原文与该字符串**逐字相同**（含标点，不含首尾空白）。
2. **Given** 已提交过若干问题，**When** 按回答标识检索留存记录，**Then** 能找到唯一对应的那一条，且其问题原文与服务端日志中记录的完全一致。
3. **Given** 用户提交了空问题或超长问题（被校验拒绝），**When** 检查留存记录，**Then** **不新增**任何记录 —— 被拒绝的输入不进入留存。
4. **Given** 提问被留存，**When** 检查记录内容，**Then** 除问题原文与标识外**不含**任何用户身份信息（无 IP、无 UA、无会话 ID）。

---

### User Story 2 - 每个问题得到与知识库同一空间的向量 (Priority: P1)

留存下来的问题被编码成一个 1024 维向量。这个向量与知识库里文档 chunk 的向量**出自同一模型、同一口径**，因此二者之间的余弦相似度是有意义的。

**Why this priority**: 这是整个检索链路的地基。向量空间不一致，后面无论怎么调阈值、调 top-k 都是在错误的基础上调参。

**Independent Test**: 取一条问题与一条已知的文档 chunk 文本，分别编码后计算余弦相似度；用同一口径手工复算，结果应一致；且向量满足 L2 范数为 1。

**Acceptance Scenarios**:

1. **Given** 一个问题已被留存，**When** 它被向量化，**Then** 得到一个 1024 维、float32、L2 范数为 1 的向量。
2. **Given** 同一问题被向量化两次，**When** 比较两次结果，**Then** **逐位完全相同**（确定性编码，无随机性）。
3. **Given** 问题向量与知识库中的文档向量，**When** 计算余弦相似度，**Then** 结果落在 [-1, 1] 且与内积一致（归一化向量的性质）。
4. **Given** 向量化结果已落盘，**When** 重新读取，**Then** 与写入前的值逐位相同，无精度损失。

---

### User Story 3 - 向量空间不一致时拒绝而非静默 (Priority: P2)

运维换了模型权重、改了截断长度，或者索引用的是另一套编码参数。系统在计算查询向量之前就发现这件事，**明确拒绝并指出哪一项对不上**，而不是照常算出向量、让后面的检索悄悄给出错误的排序。

**Why this priority**: 这是本特性唯一防的是"静默劣化"。它不产生任何用户可见的功能，因此排 P2；但它是唯一一个**事后无法补救**的东西 —— 一次静默漂移会让一批查询向量全部作废，而当时没有任何人知道。

**Independent Test**: 手工改动索引清单里记录的某一项编码参数，重新运行向量化；期望它以非 0 状态失败，并在错误信息中点出该参数的两个值。

**Acceptance Scenarios**:

1. **Given** 查询侧编码参数与索引清单记录的一致，**When** 运行向量化，**Then** 正常完成。
2. **Given** 索引清单记录的 `max_length` 被改为另一个值，**When** 运行向量化，**Then** 以非 0 状态失败，错误信息点出参数名与两个取值。
3. **Given** 索引清单不存在或无法解析，**When** 运行向量化，**Then** 明确失败并说明原因，**MUST NOT** 跳过校验继续。
4. **Given** 校验失败，**When** 检查磁盘，**Then** **没有**产生任何新的向量产物（校验先于写入）。

---

### User Story 4 - 脚本可独立运行，也可被服务调用 (Priority: P3)

运维可以单独对已有的问题记录重新做一遍向量化（比如换了机器、换了权重之后重建）；服务在请求路径上也能调用同一份实现，不必为此维护第二套编码逻辑。

**Why this priority**: 排 P3 是因为它不影响本期的功能正确性。但它是**防止"两份实现漂移"的结构性保证** —— 一旦服务端自己抄一份编码代码，向量空间漂移就从"可能发生"变成"迟早发生"。

**Independent Test**: 用同一份实现分别以"批处理"和"单条查询"两种方式编码同一段文本，结果逐位相同。

**Acceptance Scenarios**:

1. **Given** 磁盘上已有若干问题记录，**When** 独立运行向量化脚本，**Then** 它们全部被向量化，并在终端给出可读的汇总。
2. **Given** 脚本被重复运行，**When** 比较两次的产物，**Then** 已处理过的记录**不会**被重复追加（幂等）。
3. **Given** 同一段文本，**When** 分别通过批处理路径与单条查询路径编码，**Then** 两个向量逐位相同。

---

### Edge Cases

- **问题超短**：单个字符（如"痛"）是合法的（下限为 1），必须能编码，不得因过短而失败。
- **问题超长**：合法上限 200 字符，远低于模型的截断长度，不应触发截断；若确实发生截断，必须可见（而非静默丢弃尾部）。
- **纯中文 / 中英混排 / 全角标点**：均须正常编码。
- **模型权重不可用**：目录不存在、权重文件缺失或明显残缺（远小于预期体积）时，必须在**加载阶段**就明确失败，并在错误信息中给出路径与实际体积。
- **磁盘不可写**：留存目录不存在或只读时，必须给出可读的错误，且**不得**让用户的提问请求因此失败（见 FR-011）。
- **并发提交**：多个请求同时到达时的追加写不得互相破坏（不得出现半行记录）。
- **服务重启**：重启后新记录追加在原有记录之后，不覆盖、不截断已有内容。
- **重复提交同一问题**：视为两次独立的提问，各自留存（不去重）—— 重复提问本身是有意义的观测信号。
- **编码失败但留存成功**：必须把失败**显式记录下来**并可从留存记录中区分出"未向量化"的条目，MUST NOT 静默当作成功。

## Requirements *(mandatory)*

### Functional Requirements

#### 提问留存

- **FR-001**: 服务端在收到**通过校验**的问题后，MUST 把该问题原文留存到 `data/` 目录下。
- **FR-002**: 每条留存记录 MUST 包含：问题原文、本次回答的唯一标识、提交时刻。问题原文 MUST 与界面提交内容在**去除首尾空白后逐字相同**。
- **FR-003**: 留存记录 MUST NOT 包含任何用户身份信息（IP、User-Agent、会话标识、账号等）。系统不收集个人信息（`docs/01` §7.2）。
- **FR-028**: 系统 MUST 提供按日期清理留存记录的入口（裁决 D3）。
- **FR-029**: 留存目录 MUST 列入版本控制忽略清单，MUST NOT 进入仓库（裁决 D3）。
- **FR-030**: `docs/01_需求分析.md` §7.2 MUST 增加注记，说明「不做历史记录」指的是**面向用户的会话历史**，与管线侧的提问留存不是一回事；并说明留存的用途限定与清理方式（裁决 D3）。
- **FR-004**: 留存 MUST 采用**追加写**，MUST NOT 覆盖或截断已有记录（`docs/05` §3.2 的既有约定）。
- **FR-005**: 被校验拒绝的输入（空、纯空白、超长）MUST NOT 进入留存。
- **FR-006**: 留存 MUST 在提问应答流程中完成，且**不得**使提问的响应时间超出 `docs/05` §2.4 的延迟预算。
- **FR-007**: 并发写入 MUST NOT 产生结构损坏的记录（不得出现半行、交叉行）。

#### 问题向量化

- **FR-008**: 问题 MUST 使用 `E:\资料\BAAI--bge-m3` 目录下的 BGE-M3 模型编码。
- **FR-009**: 编码口径 MUST 复用既有实现，MUST NOT 另行实现一套。该口径当前为：最后一层 CLS 向量（第 0 个 token）+ L2 归一化，1024 维，float32。
- **FR-010**: 编码 MUST 是确定性的 —— 同一输入编码两次，结果逐位相同。
- **FR-011**: 向量化失败 MUST NOT 使提问请求失败。但 MUST 显式记录失败（日志 + 留存记录中的状态），MUST NOT 静默当作成功（constitution 代码规范：不得用 try/except 吞掉失败条件）。
- **FR-031**: 向量化 MUST 在提问应答流程内同步完成（裁决 D1）。模型权重 MUST 在服务启动期加载并常驻，MUST NOT 在请求路径上重复加载。
- **FR-032**: 服务端 MUST 复用与独立脚本**完全相同**的编码实现（FR-012），MUST NOT 在服务端另写一套编码逻辑。
- **FR-012**: 向量化 MUST 支持**单条查询**与**批量处理已留存记录**两种调用方式，且两种方式对同一文本的结果 MUST 逐位相同。
- **FR-013**: 批量处理 MUST 幂等：重复运行 MUST NOT 重复处理已完成的记录。

#### 向量空间一致性门禁

- **FR-014**: 计算查询向量之前，MUST 校验查询侧编码参数与知识库索引所记录的编码参数一致。
- **FR-015**: 校验项 MUST 至少覆盖：模型目录、权重文件、权重字节数、配置文件摘要、截断长度、池化方式、归一化方式、数据类型、维度、口径版本。
- **FR-016**: 任一项不一致时 MUST 以**非 0 状态失败**，并在错误信息中点出**参数名与两个取值**，MUST NOT 继续计算。
- **FR-017**: 校验 MUST 先于任何写入 —— 校验失败时 MUST NOT 产生新的向量产物。
- **FR-018**: 索引参数记录缺失或无法解析时 MUST 明确失败并说明原因，MUST NOT 跳过校验。

#### 向量落盘

- **FR-019**: 向量化结果 MUST 保存到 `data/` 目录下，且 MUST 能与对应的留存记录关联（按回答标识）。
- **FR-020**: 落盘的向量 MUST 可无损读回 —— 读回值与写入值逐位相同。
- **FR-021**: 落盘产物 MUST 记录产生它的编码参数（使其在编码参数变化后可被识别为过期）。
- **FR-033**: 留存与向量 MUST 合并写在**同一个追加文件**里：一行一条记录，向量以数值数组内联在该行内（裁决 D2）。一个文件按日期切分，MUST NOT 每条记录一个文件。
- **FR-034**: 单条记录 MUST 自包含 —— 仅凭一行即可还原"哪个问题、什么时候问的、向量是多少、用什么口径算的"，MUST NOT 需要读取其它文件才能解释该行。

#### 工程约束

- **FR-022**: 向量化脚本 MUST 保存在 `d:\zg6_Project\9\med_rag\backend` 目录下，入口唯一。
- **FR-023**: 单个源码文件 MUST NOT 超过 300 行；超出时 MUST 拆分为模块（constitution 与既有 `docs/05` §5 的 CLI 约定）。
- **FR-024**: 全部命令 MUST 以 `D:/zg6_Project/9/med_rag/rag/python.exe`（Python 3.12.14）运行（constitution 原则 I，NON-NEGOTIABLE）。
- **FR-025**: 标识符 MUST 使用 snake_case；函数签名 MUST 带类型注解，公开函数 MUST 带返回类型注解。
- **FR-026**: 模型权重 MUST 以本地文件方式加载，MUST NOT 触发任何网络下载（`local_files_only`）。
- **FR-027**: 本特性 MUST NOT 新增外部依赖；若确需新增，MUST 只装入 `rag/` 并同步登记到根 `requirements.txt`。

### Key Entities

- **提问记录（AskRecord）**：一次被接受的提问。属性：回答标识、问题原文、提交时刻、向量化状态（未处理 / 已完成 / 失败及原因）。
- **查询向量（QueryVector）**：由提问记录编码得到的 1024 维 float32 向量，L2 范数为 1。
- **编码指纹（EmbeddingFingerprint）**：一组能唯一确定"向量空间"的参数。索引侧与查询侧各持一份，二者一致才允许编码。
- **向量化结果（VectorArtifact）**：落盘的向量及其元数据（关联的回答标识、产生它的编码指纹）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 提交 N 个问题后，磁盘上恰好新增 N 条留存记录，问题原文与提交内容逐字一致的比例为 **100%**。
- **SC-002**: 被校验拒绝的输入产生的新增留存记录数为 **0**。
- **SC-003**: 留存记录中可识别到用户身份信息的字段数为 **0**。
- **SC-004**: 同一问题编码两次，结果逐位相同的比例为 **100%**。
- **SC-005**: 批量路径与单条查询路径编码同一文本，结果逐位相同的比例为 **100%**。
- **SC-006**: 编码参数被人为改动后，向量化以非 0 状态失败的比例为 **100%**，且错误信息中点明了不一致的参数名。
