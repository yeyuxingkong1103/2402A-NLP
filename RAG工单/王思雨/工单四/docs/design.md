## 3. ★图像内容解析（工单四核心）

### 3.1 为什么必须要图像解析——工单 16 题里的硬证据

工单指定的 16 个问题中，**id=6 的答案完全只存在于图像里**（已实测核对）：

| 题号 | 问题 | 图像（本项目页码口径 = page_idx+1） | 文字层是否有答案 |
|---|---|---|---|
| id=6 | 2008年中国IC市场应用结构与增长图中，**增长率最快**的是哪个行业？**负增长**的是哪个行业？ | 《招股说明书2》P72 应用结构与增长图 | **完全没有**。实测在全文 `text` + `table_body` 字段中检索：`IC卡` 出现 **0** 次，`-2.0` 出现 **0** 次；唯一的 `14.0` 是 P318 讲电度表行业，与本图无关。正文只有"工业控制增长率 10.5%，位列第二，仅次于汽车电子"，推不出"汽车 14.0%"，更推不出"IC卡 -2.0%" |
| id=5 | 销售部有几个部门构成，其中**大客户销售部有几个销售处**构成？ | 《招股说明书2》P39 内部组织结构图 | **文字层可答**：P40 正文写明"销售部下设渠道销售部、电话及网络销售部、大客户销售部和国际贸易部"（4 个）；P113 正文写明"在北京、广州、成都、深圳、武汉、珠海各设有 1 家销售处"（6 个）。**此处如实标注为文字可答**，组织结构图提供的是同一事实的图形表述，不把它算作图像独有证据 |

**结论**：id=6 单独构成硬性证据——不做图像解析，工单自己列出的第 6 题就无解。id=5 则用于演示图像链路输出的层级关系与正文一致性（两条独立路径给出同一答案，可交叉验证）。

### 3.2 三段式图像解析

**第一步：Chinese-CLIP 零样本语义分类（多模态模型）**

用中文 CLIP（`OFA-Sys/chinese-clip-vit-base-patch16`，本地路径 `D:/模型/chinese-clip-vit-base-patch16`）对 11 类候选标签做零样本匹配，得到图像语义类型与置信度。选中文 CLIP 而非原版 OpenAI CLIP：招股说明书是中文文档，提示词也只有中文，中文 CLIP 的文本编码器才对齐。

实测：组织结构图 0.999、饼图 0.823、折线图 0.878。

**第二步：PaddleOCR 读出图内文字（3× 放大）**

MinerU 已把图渲染成位图，但图内小字与符号需要单独 OCR。**关键实测坑**：1× 分辨率下图表里的负号会读丢——`-2.0%` 被识别成 `2.0%`，导致 id=6 的"负增长"无从判断；把图放大 3× 后再 OCR 才能稳定读出 `-2.0%`。该放大倍数由 `OCR_SCALE=3.0` 控制。

同时用水印词表过滤噪声：招股说明书的斜向水印不在文本层，OCR 会把"八维教育 / 人工智能刘敏 / rengongzhinengliumin"读成独立文本行，混进正文会污染检索（词表见 `config.WATERMARK_TOKENS`）。

**第三步：像素级几何还原层级关系**

"大客户销售部有几个销售处"这类问题的难点不是认字，而是**判断从属关系**。组织结构图的画法有固定规律：

> 父块下方引出一条**横总线**，总线上挂多条**下垂竖线**接到各个子块。

据此在二值图上：
1. 找出所有"挂着 ≥2 条下垂竖线的横线段"→ 每条总线横跨的范围即一组兄弟节点；
2. 两端都有上延竖线的横线是方框边线，排除；
3. 父块 = 总线上方、横向中心最接近总线中心、且纵向最靠近总线的文本块。

实测（《招股说明书2》P39 内部组织结构图）：

```
【图内层级】销售部 下辖：电话及网络销售部、渠道销售部、大客户销售部、国际贸易部（共 4 个）
【图内层级】大客户销售部 下辖：珠海销售处、深圳销售处、北京销售处、武汉销售处、广州销售处、成都销售处（共 6 个）
```

**子节点的横向判定用"与总线有交叠"而非"中心落在总线内"**：最外侧节点的中心常在总线端点之外（实测珠海销售处中心 x=486，落在总线起点 502 左侧 16px），用中心判定会漏掉它，答案就从 6 个变成 5 个。

### 3.3 图像块的结构

```
【所在位置】《招股说明书2》第 39 页，图前正文：截至本招股意向书签署日，本公司内部组织结构如下图：
【图像语义】类型：组织结构图（CLIP 置信度 0.999）
【图内文字】股东大会 | 薪酬与考核 | 委员会 | 监事会 | 董事会 | … | 成都销售处
【图内层级】销售部 下辖：电话及网络销售部、渠道销售部、大客户销售部、国际贸易部（共 4 个）
【图内层级】大客户销售部 下辖：珠海销售处、深圳销售处、北京销售处、武汉销售处、广州销售处、成都销售处（共 6 个）
```

整段文本作为一个独立块入库（向量 + BM25 双通道可检索），`block_type=image`、`image_type` 记录 CLIP 判定结果，前端据此回显原图供人工核对。

**层级还原只对 CLIP 判定为「组织结构图」的图启用**：饼图/柱状图的图形元素（扇区、柱条）会被误判成总线，实测在 IC 市场图上产出 8 条无意义关系，必须按类型关闭。

## 4. 其余处理链路

### 4.1 PDF 解析（`backend/parse.py`）

MinerU（pipeline 后端，`-l ch -t True`）产出 `content_list.json`，其中：
- `text` / `header` → 正文与标题（编号式章节名如"三、""（二）"也判为标题）；
- `table` → 逐行拍平成 `[表] 表题｜章节｜行名｜列名: 值` 的行块（**表格内容在 `table_body` 字段，不在 `text` 里**）；
- `image` / `chart` → **图像任务**，带图像文件路径、页码与图前正文（作语境与题注）。

兜底链：MinerU 失败 → pymupdf 正文 + pdfplumber 表格 + pymupdf 整页渲染图 → 文本层为空则 PaddleOCR。
`--no-mineru` 可直接跑兜底链做回归。

### 4.2 语义分块（`backend/chunking.py`）

段落按中英文句末标点切句，逐句编码；相邻句与当前块**语义中心**（缓冲内向量均值）相似度低于 `SEM_THRESHOLD`（0.62）即切块，超长（>700 字）也切。
图像块、表格行、标题为**硬边界**：各自独立成块且不与段落混合，保证定位精确、不被稀释。
短于 `MERGE_MIN`（150 字）的纯文本块向后合并，避免"章节名+公司名"这类碎块挤占检索前排。

### 4.3 向量化与向量库（`backend/store.py`）

bge-m3 本地路径加载，L2 归一化后内积等价余弦 → Milvus `IVF_FLAT` + `IP` 度量，维度 1024。
检索显式用 `consistency_level="Strong"`：默认 Bounded 会导致刚写入的数据读不到。
`MilvusClient` 没有 `flush`，写入即可查靠的就是上面的强一致读。

### 4.4 关键词检索（BM25）

jieba 分词，英文与数字整体保留，使 `1,670`、`25.04%`、`-2.0%` 这类串能精确命中——这正是向量检索的短板。

### 4.5 混合检索与 RRF 融合

两通道用线程池并行召回（编码走 GPU、BM25 走 CPU，可真正并行），各取 Top-20。
融合用 **RRF**（`score = Σ 1/(k+rank)`，k=60）而不是加权归一化：两路分数量纲不同（向量 IP vs BM25 无界分），归一化会被单路极值带偏；RRF 只用排名，无需调参。实测对比见 `docs/optimization.md`。

图像块额外乘 `IMAGE_BOOST=1.15`：图块数量远少于正文块，不加成会被大量正文块用排名压下去，图文类问题永远挤不进重排候选。

### 4.6 重排

`bge-reranker-v2-m3` 成对打分，(问题, 候选块) → 归一化分 → Top-6。打分输入截断到 512 字（整表块可达数千字，不截断时成对打分要按最长样本填充，实测重排耗时从 300ms 量级涨到 960ms），但返回给大模型的仍是片段全文。

### 4.7 生成

DeepSeek（OpenAI 兼容接口），`temperature=0` 保证可复现，`max_tokens=800`。提示词强制：语言跟随提问、数字比例不得改写、多份资料范围相近时只取最匹配的一份（防跨表合并）、资料无据时明确拒答。**图像块在提示词里单独说明"来自文档插图，可直接作为依据"**，否则模型倾向忽略它。

### 4.8 缓存

键 = 前缀 + **rag.py 源码哈希前 8 位** + 语言 + 问题 md5。用源码哈希而非手写版本号：手写版本号迟早会忘——实测踩过一次，给返回体新增降级字段后忘升版本，旧缓存把无该字段的结构原样返回，**降级结果不带提示地被静默返回**。条目内另存写入时指纹做双保险。

### 4.9 评估（两个互补口径）

| 脚本 | 口径 | 用途 |
|---|---|---|
| `scripts/test_questions.py` | 关键词命中率 + **负样本** + 枚举个数三重判据 | 准确率（≥90%）、响应时间 |
| `scripts/eval_ragas.py` | faithfulness / answer_relevancy / context_precision / context_recall | 生成质量与上下文质量 |

判分器必须用**已知错误答案回验**（`--selfcheck`）：只查"该有的有没有"抓不到"多答无关内容"——工单三实测自动判分 14/14 满分、人工复核才发现混入 2 家无关企业。故每题配置 `expect_not` 负样本，且枚举题核对条目个数（模型把 6 个销售处写成 5 个时关键词仍会全中）。

```jsonc
}
```

**检索精确度口径（必须声明，否则会被当成准确率）**：
`retrieval_precision` = 返回的 N 条上下文中，**重排分 ≥ 0.5 的相关块所占比例**。这是**无标注在线代理口径**——线上没有标准答案可比。
带标注的口径（答案是否命中标准答案关键词、来源是否落在正确文档与页码）由 `scripts/test_questions.py` 离线计算，两个数字都写进 README，不混为一谈。

## 7. 非功能设计

### 7.1 准确率 ≥ 90%

- 检索侧：混合双通道 + RRF + 交叉编码重排 + 图像块加成；
- 生成侧：提示词强制数字/比例/名称与资料逐字一致、防跨表合并、无据拒答；
- 评测侧：三重判据（关键词命中率 / 负样本 / 枚举个数），并用已知错误答案回验判分器。
- 目标：16 题 ≥ 15 题正确。实测结果见 `README.md`。

### 7.2 响应时间 ≤ 3 秒

耗时构成（本地实测）：检索 + 重排 300~600 ms，DeepSeek 生成 1.5~3.5 s（随答案长度变化）。
- 缓存命中路径**不调用大模型**，耗时约 5~30 ms；
- 生成走 `LLM_TIMEOUT=20s` 快速失败，超时即降级返回检索原文，不会把接口挂死；
- 首字延迟：检索一完成即可推送片段（流式接口留待需要时启用，工单四未要求流式，故未实现）。
- **如实说明**：端到端 P50 受大模型生成时间主导，实测分布与是否达标见 `README.md`；不达标则如实标注，不用缓存命中数据冒充。

### 7.3 容错

`tests/test_faults.py` 注入 7 类故障，**真的把依赖打断**再观察（不是只读代码判断有没有 try）：

| 场景 | 期望行为 |
|---|---|
| Milvus 不可用 | 退回 BM25 单通道作答 + 显式降级提示（注意 `MilvusClient()` 在**构造阶段**就抛异常，不在 `load()` 里兜住就会绕过所有内层兜底） |
| Redis 不可用 | 缓存静默失效，问答不受影响 |
| DeepSeek 不可用（含 402 余额不足 / 超时） | 返回检索原文 + "生成服务不可用"提示 |
| 向量模型不可用 | 向量通道空手而归，BM25 撑住，降级可见 |
| 重排模型不可用 | 按融合分兜底排序，仍返回 Top-N |
| 索引文件缺失/损坏 | 提示"请执行 scripts/ingest.py 重建索引"，不抛栈 |
| 用户输入错误（空 / 超长 / 纯符号） | 中文友好提示 + 明确错误码 |

### 7.4 多语言

中文按字符占比自动判定（中文字符 > 15% 为 zh，否则 en），也可由前端显式指定。
提示词按语言给出 `用中文作答` / `Answer in English`。中英混合提问按中文处理。

### 7.5 并发与资源

- FastAPI + uvicorn，同步接口跑在线程池；检索两通道已用线程池并行；
- bge-m3 / reranker / CLIP / PaddleOCR 均为**进程内单例**，只加载一次并常驻，避免每请求重复加载；
- Milvus 客户端、Redis 客户端带超时（10s / 0.5s），依赖变慢不会拖垮接口；
- 离线入库**串行**处理文档：本机 GPU 仅 8 GB，并行解析会被系统杀掉；
- 服务启动即预热（`backend/rag.py: warmup`），避免首个请求多等十几秒被当成卡死；
- 工单四未给并发 QPS 指标，故不设并发承诺；压测数据如实报告（`results/`）。
