## 1. 先量瓶颈，再动手

优化前对单次提问逐段实测（解析链路已预热，单跑无并发）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 查询向量化（bge-m3） | 41 ms | 4% |
| Milvus 向量检索 | 46 ms | 5% |
| BM25 关键词检索 | 16 ms | 2% |
| **bge-reranker-v2-m3 重排（25→6）** | **960 ms** | **82%** |
| 检索小计 | 约 990 ms | |
| DeepSeek 生成 | 约 1050～1250 ms | |

**结论：检索侧的时间几乎全在重排上**，向量化与检索本身都在百毫秒以内。所以优化重点放在重排，而不是盲目调 `top_k`。

## 2. 优化点（按影响排序）

### 优化点 1（正确性，最重要）：修掉章节语境的"张冠李戴"

**问题**：工单 id 4 的答案混入 `佰力电子`、`盈硅电子` 两家企业——它们出自 P158 的「**3、报告期内曾为关联方但目前已不存在关联关系的公司**」表，而问题问的是「不存在**控制关系**的关联方」。自动关键词判分没抓到（它只要求正确字段都出现，多出的不管），是人工复核发现的。

**根因**：这些块的章节语境被错标成了上一节的「2、不存在控制关系的关联方」。再往下追，是 MinerU 没有把 "3、报告期内曾为关联方…" 标成标题（`text_level` 为空），于是章节名一路沿用上一节 —— 而错标的语境恰好与问题用词高度重合，重排自然把它排到了正确表前面。

**修法**（`pdf_parser.py`）：
1. 除 MinerU 的 `text_level` 外，**按编号式章节名的写法补判标题**（`第X节/章`、`三、`、`（二）`、`3.` 等，且长度 ≤ 40 字）。
2. 章节语境加**页跨度上限** `SECTION_SPAN=3`：超过 3 页未刷新即失效，宁缺勿错。

**效果**：P158 的表现在带正确语境「3、报告期内曾为关联方但目前已不存在关联关系的公司」；id 4 的答案只剩正确 7 家，且模型主动标注了来源「招股说明书2 P157 表2」。

```
优化前：…不存在控制关系的关联方企业有：佰力电子、盈硅电子、融冰投资、武汉博润、上海博润、
        听音投资、联众聚源、力源贸易、普芯达          ← 多 2 家无关企业
优化后：根据资料1（招股说明书2 P157 表2），…不存在控制关系的关联方企业有：融冰投资、武汉博润、
        上海博润、听音投资、联众聚源、力源贸易、普芯达  ← 正确
```

### 优化点 2（正确性）：给资料打出处标签 + 禁止跨表合并

**改动**（`rag_core.generate`）：
- 拼给大模型的每份资料都加前缀 `[资料N｜来源：招股说明书2 P157 表2 第1行]`，让模型能分辨"范围相近但不同"的表。
- 提示词新增一条：*"若多份资料内容相近但范围不同，只采用与问题问法最匹配的一份，不要把不同资料的条目合并作答。"*

优化点 1 治的是"检索排错序"，优化点 2 治的是"即使都召回也答错"——两道一起上，id 4 才稳定正确。

### 优化点 3（性能）：重排只喂需要判断的文本

**改动**（`retriever.rerank` + `RERANK_MAX_CHARS=512`）：送进重排打分器的文本截断到 512 字，**返回给大模型的仍是片段全文**。

理由：整表块可达数千字（如 P24 发行情况表 14 行），成对打分要按最长样本填充，填充开销被放大。重排只需要判断"这段和问题相不相关"，512 字足够。

**实测**：重排 960ms → **660ms**（↓31%）。三次重复取均值，单跑无并发。

> 过程中的一个测量教训：中途复测重排得到 978ms，看起来"优化无效"。实际是当时 FastAPI 服务还在后台跑着，**同机加载了两份 bge-m3 + 两份重排模型**，8G 显存被挤爆导致读数失真。停掉服务后复测才得到 660ms。**同一台机器上不要一边压测一边留服务常驻。**

### 优化点 4（构建时间）：分块只编码需要比较的单元

**改动**（`chunking.py`）：表格行块与整表块是**硬边界**，一定会切块，它们的向量从不参与相似度比较，因此不参与分块阶段的编码。

**实测**：语义单元共 12,145 个，其中表格单元 5,721 个不参与比较，**需要编码的从 12,145 个降到 6,424 个**；**索引重建时间从约 50 分钟降到约 8 分钟**（↓84%）。

> 这个改动引入过一个 bug：表格单元的向量是 `None`，而 `None` 会被 numpy 当成 0 维数组参与矩阵乘，直接抛
> `ValueError: matmul: Input operand 1 does not have enough dimensions`。修法是在算相似度前对 `vec is not None` 短路。

### 优化点 5（可用性）：修掉单文档重建的静默数据丢失

**问题**：`/parse` 的 `only` 参数原实现会把索引**只**建成指定文档——另一篇被挤出索引，后续提问直接查不到，且不报错。

**修法**（`rag_core.build_index`）：`only` 的语义改为"**强制重新解析该篇**"，索引始终包含全部文档；同时指定不存在的文档时明确报错，不再静默产出空索引。

### 优化点 6（响应时间）：Redis 缓存热点问题

相同问题第二次提问直接命中缓存。实测同一问题：第 1 次 **2.416s**（未命中）→ 第 2 次 **0.00s**（命中），两次答案完全一致，`TTL=86400s`。键为 `gd3:ask:<lang>:<md5(问题)>`。

### 优化点 7（响应时间）：服务启动预热，消除冷启动长尾

**问题**：服务重启后的**第一个未缓存提问实测要 21.5 秒**——不是检索慢，而是 bge-m3 与重排模型在这一刻才懒加载。用户看到的就是"系统卡住"，这直接违反"响应 ≤ 3 秒"的验收观感。

**修法**（`rag_core.warmup` + FastAPI `lifespan`）：服务启动时就把块列表、BM25 索引、Milvus 连接、两个本地模型全部载入，日志打印 `[启动预热] {'ok': True, 'chunks': 6776}`。预热失败只打印不阻断启动，首个请求会再试一次。

**效果**：预热后连续三个**未缓存**问题的端到端耗时分别为 **2.63s / 2.55s / 2.25s**，冷启动长尾消失。

### 优化点 8（判分口径）：给判分器加负样本，堵住"假满分"

**问题**：首轮自动判分 accuracy = 1.0，但人工复核发现 id 4 混入 2 家无关企业。旧口径"关键字段都在即通过"只能看见漏答，看不见多答——而 RAG 最典型的错误恰恰是"检索到范围相近的不同表，把条目合并作答"。

**修法**：`tests/test_questions.json` 为 5 道枚举型题补 `expect_not` 负样本清单；`app/evaluate_ragas.py` 判定改为 `_has(expect) and _has_not(expect_not)`，并单独记录 `neg_pass`。

**关键动作**：改完先拿**首轮那条错误答案**回判，确认它会被判 False——**判分器本身也必须先验证有效，否则只是换一个方式假通过**。

**效果**：加严后 14 题仍 **accuracy 1.0 / neg_pass_rate 1.0**，负样本通过率单独可见。详见 `03_test.md` §7。

### 优化点 9（容错）：让 Milvus 停机真的降级到 BM25

**问题**：文档里一直写着"Milvus 不可用时向量通道返回空、BM25 通道仍有结果"，**停机实测后证明是假的**。`MilvusClient()` 在**构造阶段**就抛异常，异常从 `_load()` 直接冒到最外层，`vector_search` 内部的 `except` 分支根本没机会执行——用户看到的是"系统繁忙"，**全程没有走 BM25**。

**修法**（`rag_core._load` + `vector_store.vector_search`）：
- `_load()` 自己兜住连接异常，连不上就把 client 置空，让 BM25 把问答撑起来；**每 60 秒最多重连一次**，避免每次提问都白等 10 秒超时，Milvus 恢复后也能自愈；
- `vector_search` 增加 `client is None` 短路，直接返回空。

**效果**：停掉 Milvus 容器后，仅凭 BM25 仍答出正确答案（1,670万股 / 25.04%，命中 `招股说明书2 P22 表1 第3行`），稳态 **1.92s**，`error=None`。`docker start` 后 50 秒自愈，恢复两条通道。

**同时暴露的真实代价**：BM25 单通道下检索质量确实下降——问"兴图新科法定代表人"时答案混入了真实存在但不相干的关联实体「武汉兴图投资有限公司」（发行人股东，持股19.28%，法定代表人同为程家明）。**不是编造**，是纯关键词通道分不清"兴图新科"与"兴图投资"。降级只是保底，向量通道不可替代。

### 优化点 10（可观测性）：把降级模式显式标出来

承优化点 9：既然降级后质量会实打实下降，就**不能静默返回**。`answer()` 现在返回 `retrieval_mode`（`hybrid` / `bm25_only` / `vector_only`）、`degraded`、`degraded_reason` 三个字段，前端在答案上方显示橙色横幅。

同一条规则也用在生成侧：DeepSeek 失败时返回"生成服务暂不可用，以下为检索到的原文片段，请自行查阅。" + **完整的来源片段**，而不是只回一句报错把检索结果丢掉。

### 优化点 11（可观测性）：修掉故障源误报

**问题**：故意把 `EMBED_MODEL_PATH` 指错后，日志打的是 `[检索降级] Milvus 不可用：ValueError: Path ... not found`——**向量模型的问题被报成了 Milvus 的问题**。根因是"问题编码"和"Milvus 检索"挤在同一个 `try` 里，共用一个 except 文案。这种日志会把排障直接带偏。

**修法**：拆成两段独立兜底，分别打 `[检索降级] 向量模型不可用：...` 与 `[检索降级] Milvus 检索失败：...`。

### 优化点 12（可观测性）：索引损坏给出可操作提示

**问题**：实测把 `bm25.pkl` 写成随机字节后，返回的只是一句"系统繁忙或依赖服务暂时不可用"——用户完全无从知道该重建索引。

**修法**：`_load()` 对索引载入单独兜底，损坏时抛 `RuntimeError("索引文件已损坏（UnpicklingError），请执行 python -m app.rag_core 重建索引")`，文件缺失仍走原来的"尚未构建"提示。

### 优化点 13（可用性）：修好扫描件的 OCR 兜底

**问题**：用真实页面渲染合成纯图 PDF（文本层 0 字符）实测 OCR 兜底，**直接失败**：

```
RuntimeError: (NotFound) Cannot open file C:\Users\雨子/.paddleocr\whl\det\ch\ch_PP-OCRv4_det_infer/inference.pdmodel
```

**但文件确实存在**（166 KB）。所以不是缺模型，是 **Paddle 的 C++ 推理层打不开中文路径**——与 MinerU 的 fasttext 属于同一类问题（见记忆 `mineru-fasttext-chinese-path`）。PaddleOCR 2.7.3 把缓存目录写死为 `os.path.expanduser("~/.paddleocr/")`，没有环境变量可改。

**修法**：把模型复制到纯英文路径 `C:/paddleocr_models/`，构造时用 `det_model_dir` / `rec_model_dir` / `cls_model_dir` 显式传入（新增配置项 `PADDLEOCR_MODEL_DIR`）；一个目录都不存在时给出**带复制命令的中文提示**，而不是抛原始 Paddle 报错。

**效果**：扫描件走通 `文本层为空 → PaddleOCR` 分支，2 块 / 1366 字 / 8.8s，识别内容正确。
**副产物**：OCR 结果里同样出现了 `八维教育`、`人工智能刘`、`rengangzhinen` 等水印字样——**从图像侧再次证实水印确实印在页面上**，而非解析器产生的假象。

### 优化点 14（缓存一致性）：缓存键加入结构指纹

**问题**：加了 `retrieval_mode` / `degraded` 字段后，无头浏览器实测显示 `检索通道=—`——该答案来自**加字段之前写入的缓存**，旧结构被原样返回。这不只是少个字段：**降级结果会不带任何提示地被静默返回**，前端永远显示不出警告。

**修法**：缓存键改为**结构指纹** `gd3:ask:<指纹>:<lang>:<md5>`，指纹取构造返回体的 `app/rag_core.py` 源码 md5 前 8 位。
**为什么不手写版本号**：第一版用的是手写 `CACHE_VERSION`，那就等于把同一个坑留到下次——加字段时同样会忘。
交给源码哈希就不需要任何人记得做这件事。另在条目里存一份 `_fp`，读时比对，对不上按未命中。

**效果**：改源码后指纹自动从 `563777d2` 变为新值（已实测），旧条目自然失效；往返实测新字段（`retrieval_mode` / `degraded`）在缓存里完整保住。已清理 11 条旧格式键并复验。

### 附：水印词表的完整内容与提取方法（供换 PDF 时重扫）

**水印原文**（斜向重复铺满页面）：`八维教育` + `人工智能 rengongzhineng`，另含人名 `刘敏` 的碎片。

**当前词表**（`app/table_struct.py`，针对这两篇实测得出）：

| 类别 | 内容 | 处置位置 |
|---|---|---|
| 拉丁基准串 | `rengongzhinengliumin` | 长度≥3 的拉丁词，若整体是其子串或 `SequenceMatcher` 相似度 > 0.6 即删（可捕获 `thinengliumin` 这类 OCR 变体） |
| 紧贴噪声 | 紧贴中文或紧贴数字的小写拉丁串 | 正则删除；纯数字 `2010年` 与大写英文 `C39`/`IC`/`P&S`/`A股` 不受影响 |
| 中文水印（任意位置删） | `八维教育`、`维教育`、`维教`、`八维`、`数育` | 干净文本层中出现 **0** 次，可放心全删 |
| 中文水印（仅首尾删） | `人工智能` | 正文中有 **5 处**合法出现，只能删单元格首尾的 |
| 保留词表 | `ms`/`mbps`/`mp4`/`ios`/`mb`/`hz` 等约 20 个 | 防止把合法单位与技术词误删 |

### 附：两个本地模型也在中文路径下（下次提速时的隐患）

`D:/模型/bge-m3` 与 `D:/模型/bge-reranker-v2-m3` 同样位于中文目录。**当前没出问题**——
两者都走 Python 层（transformers / FlagEmbedding），而这些库在 Python 侧处理路径，不受影响。

**但这是运气，不是安全**：本项目已经因为中文路径栽过 4 次（MinerU 的 fasttext、torch ONNX 导出、
onnxruntime 量化、PaddleOCR 的 C++ 推理层）。**其中 PaddleOCR 就是"读输入文件"这一侧，与模型目录场景完全同类。**
一旦为了提速换成 ONNX Runtime / TensorRT / OpenVINO 版重排或向量模型，大概率立刻重踩。

**推荐做法**（需要时执行，**本次未动用户磁盘**）：

```cmd
:: 用目录联接（junction），零拷贝、秒完成，不占额外空间
mklink /J D:\models\bge-m3            D:\模型\bge-m3
mklink /J D:\models\bge-reranker-v2-m3 D:\模型\bge-reranker-v2-m3
```

然后把 `.env` 改成：

```ini
EMBED_MODEL_PATH=D:/models/bge-m3
RERANK_MODEL_PATH=D:/models/bge-reranker-v2-m3
```

> 注意：`.env` 里**必须用正斜杠**，写成 `D:\models\bge-m3` 时 `\b` 会被当成退格符（见 `05_deploy.md` §5）。
