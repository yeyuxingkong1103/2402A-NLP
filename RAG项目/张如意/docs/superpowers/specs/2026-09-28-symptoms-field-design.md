## 1. 背景与问题

农户描述症状而不说病名时（"叶子上有弯弯曲曲的白色隧道"），系统目前给不出答案，
或更糟——给出**别家病虫害的用药方案**。

现状事实（2026-09-28 现算）：

| 事实 | 出处 |
| --- | --- |
| `symptoms` 字段已在 schema 中，但 247 张卡**全为 `null`** | 三个解析脚本均硬编码 `"symptoms": None` |
| 三份国标正文/附录B **没有任何症状描述**，只有防治适期与防治指标 | CLAUDE.md 六·3 |
| 症状问句无病虫害实体 → 走不了 `coverage_check` 实体路径，只吃语义分数 | `src/retrieve/search.py` |
| 「蒜苗白色弯曲斑道」实测 rerank **0.0164 < 闸门 0.1** → 兜底 | `eval/失败复核清单.md` #5 |
| 「辣椒茎基黑褐斑+整株萎蔫」top-1 是 c03 早疫/晚疫**方案卡**（会给出别家药方） | 同上 #2 |

目标：让症状型问法能命中正确的卡，**且不引入编造**。

## 2. 来源（侦察结论）

**结论：症状描述在官方标准体系里基本不写——不是这三份国标的偶然缺失，是系统性的**
（标准的读者是植保员，症状识别在标准体系里被当成教材/图册的活）。

| 层级 | 查到的来源 | 有症状描述吗 |
| --- | --- | --- |
| 一级·国标 | GB/T 17980 系列《农药 田间药效试验准则》（2026 新版，分册精准：第26部分 黄瓜霜霉病、第30部分 黄瓜白粉病、第32部分 辣椒疫病、第33部分 辣椒炭疽病、第17部分 豆类蔬菜叶螨） | 有**病情分级标准**，是给试验分级用的，不是农户看病用的描述 |
| 一级·国标 | 测报调查规范（GB/T 15790~15803 系列） | 含症状识别，但**全是大田作物**（稻/麦/棉），蔬菜一份没有 |
| 一级·地方标准 | 山东 DB37/T 4474 系列《蔬菜病虫害绿色防控技术规程》、DB37/T 2499 大蒜根蛆等 | 公开摘要显示以防控原则+防治方法为主，未见症状章节（⚠️ 未逐份核实全文） |
| 一级·部委 | 全国农技中心《2025年设施黄瓜病虫害绿色防控技术方案》 | 无症状识别，只有防控对象+措施+药剂 |
| 二级·期刊/网站 | 《河南农业》《中国蔬菜》《北方园艺》等；中国农科院、各地农牧局网站；科普中国 | **有**成段症状描述 ✅ |

**试采验证（2026-09-28）**：3 个目标病虫害（大蒜豌豆潜叶蝇、大蒜蓟马、辣椒茶黄螨）
**3/3 全部找到可引用的症状文本**，含「与病毒病的区分」这类防误判内容。

**出处质量分档（采集时按此优先级）**：

1. **期刊文献**（有刊名/年/期/页）——首选
2. **政府/农科院网站**（机构+URL+访问日期）——可引用，但**会漂**，必须存快照
3. **科普中国类**——权威性中等，仅作补充

**平台事实**：地方标准有全国统一免费入口 `dbba.sacinfo.org.cn`，
但各省开放程度不一（广西/青海/辽宁只给目录）。

## 3. 数据形态与 schema

**产物文件**：`data/processed/symptoms.jsonl`（一行一条症状知识，与 247 张卡并列但**独立存在**）。
原始快照另放 `data/external/symptoms_raw/`。

> ⚠️ **不能**放 `data/external/` 根下——那里按项目定义是"不进语料统计、不进索引"，
> 而这份东西是**要进索引**的。

```jsonc
{
  "symptom_id": "sym-dasuan-wandouqianye-01",
  "card_id": "GBZ26578-2011-p20-c09",   // 挂到哪张卡，必须是 247 张之一
  "crop": "大蒜",
  "pest": "豌豆潜叶蝇",                   // 目标卡的 subtype，用于校验挂对没有
  "symptom_text": "幼虫孵化后在叶片表皮下潜食叶肉，仅留上下表皮，形成白色或灰白色弯曲的蛇形虫道，虫道内有黑色细小虫粪",
  "part": ["叶片"],                      // 为害部位，原文写了才填
  "source": {
    "kind": "journal",                   // journal / gov_site / book / hotline
    "title": "河南省大蒜田豌豆植潜蝇的发生及绿色防治",
    "publisher": "《河南农业》2023年第13期",
    "url": null,
    "accessed": "2026-09-28",
    "quote": "原文 ≤200 字"
  },
  "authority_level": 2,
  "needs_human_review": true
}
```

### 3.1 五条硬规则

1. `symptom_text` **逐字照抄，不改写、不概括**（核心约束 6 照旧适用）。
   允许**按句截取连续片段**（不取全段），截掉的部分必须在快照里写明并说明理由。
   ⚠️ **但「与别的病害区分」这类鉴别内容不进 `symptom_text`**（2026-09-28 用户裁决，
   修正本 spec 初稿的「鉴别内容一起抄」）：
   鉴别段必然写出**别的病害名**，而这些字进的是目标卡的**检索字段**——辣椒茶黄螨卡上
   出现「病毒病」字样，就可能把问"是不是病毒病"的农户拽到茶黄螨的**用药方案**上，
   正是本项目最要防的错药（病毒病在辣椒语料里无方案，正确行为是 b6.2 正文）。
   鉴别内容**留在快照里**（`data/external/symptoms_raw/*.md`）供人工查阅；
   结构化保留（`differential` 字段）列为铺开阶段的候选，本批不做。
   同理：症状文本里顺带提到其他病害名的句子（如「该虫还可传播茄科植物病毒病」）
   也按句截掉，快照记明。
2. `card_id` 必须真实存在；挂空/挂错由脚本拦（§11）
3. 一条一行：同病虫害多来源 = 多行；同来源写多个病虫害 = 拆多行
4. 挂卡规则（沿用 2026-09-27 已定）：
   - 该病虫害**有附录B 方案卡** → 症状挂**方案卡**（#3→c09、#5→c09、#6→c10、#8→c05、#9→c01）
   - 只在**正文提到过**（无方案） → 症状挂**正文卡**（#2 疫病只在辣椒 6.2 列名 → 挂 b6.2）
5. **不动卡片本体**，也不进 `data/raw` 语料口径

### 3.2 两个已定的挂法细节

- **一个病虫害有多张卡时：能挂都挂**（召回优先）。理由：农户问"种蝇怎么治"，
  答不出比答错更糟；多挂的后果可控，精排会把不最贴的压下去。
  挂法：症状贴近哪张挂哪张，分不清多行都挂，**带虫态就挂对应虫态卡**
  （种蝇有 c03 播种前 / c05 成虫 / c06 幼虫三张）
- **`part` 字段留，`stage` 砍**。`part` 是**枚举**，取值只有这九个：
  `叶片 / 茎 / 茎基部 / 根 / 鳞茎 / 果实 / 心叶 / 花 / 全株`（原文写了才填）。
  "叶子上有白点"这类问法用得上；`stage` 原文基本不写，硬填是编造。
  ⚠️ 枚举可扩，但**扩了必须同步** `scripts/validate_symptoms.py` 与本表

## 4. 切分 / 索引 / 检索三层怎么用

### 4.1 切分层（`build_chunks.py`）

chunk 新增**两个字段 + 一个 meta 标记**，**`embed_text` / `bm25_text` 原地不动**：

| 字段 | 内容 | 给谁用 |
| --- | --- | --- |
| `sym_text`（新） | 挂到本卡的所有症状文本拼接 | 编码时合并进两路 |
| `symptoms`（新） | 结构化条目数组（含来源） | 答案层展示与溯源 |
| `meta.has_symptoms`（新） | 有无症状（bool） | 统计 / 后续可能的过滤 |

**为什么不直接写进 `embed_text` / `bm25_text`**：

> `search.py` 在模块导入时会用正则扫 `chunks.jsonl` 的 `bm25_text`，
> 现算出 `_MENTIONED` / `_MENTION_CROPS` 两张表，那是 `coverage_check`
> 第三档「本作物正文提到过」的**唯一判据**。症状文本是**外部来源**，不是国标语料——
> 写进 `bm25_text` 就等于把"手册里提到过"记成"国标正文提到过"。
> 症状文里一句「与灰霉病区分」，就能让某作物的灰霉病从「完全没提过」
> 升成「正文提到过」，**硬兜底悄悄变成 ok_noplan**。
> 评估集（当时 255 条，现 259 条）的兜底指标会因此漂移，而且漂得没道理。

### 4.2 索引层

- `embed_chunks.py`：两行改动——`dense_in = embed_text + sym_text`、
  `sparse_in = bm25_text + sym_text`；`embedding_meta` 记
  `"symptom_source_field": "sym_text"` 以便追溯
- `build_milvus_index.py`：schema 加 `sym_text`(VARCHAR 2048) + `has_symptoms`(BOOL)；
  **不加新标量倒排索引**（没有路由用它）；重建照旧 `--recreate`
- 向量维度、索引类型、**203 实体数**都不变

### 4.3 检索层（`search.py`）

**初版口径：一行不改。** 症状问句没有实体 → 本来就走不了实体路径，纯吃分数；
症状文本进两路后 rerank 分自然抬起来。实体表仍从卡本体现算 → 兜底档位不受影响。

这是**故意的**：先不动判定逻辑，看纯语义能不能把 #5/#6/#8 抬过闸门。
改前改后各跑一次 `run_eval.py` 快照对比（项目既有做法）。

⚠️ **该口径已于 2026-09-29 有据推翻（Task 7 受控对比的结论）**

**实测：纯语义抬不动闸门。** 改后 collected 四条症状用例**只召回 1 条**
（#9 池外→rank 4，唯一实证有效）；**#5 的闸门分 0.0164 与改前逐位相同**。

**根因是结构性的，不是调参问题**：闸门（`rerank_gate`）与排序（`rerank_sort`）
打分的都是 `card["bm25_text"][:200]`，而症状按 §4.1 的设计**不进 `bm25_text`**；
更彻底的是 `hybrid()` 的 `output_fields` 根本没把 `sym_text` 取回来——
**重排器物理上看不到症状**。症状只能影响"谁进候选池"，影响不了"打多少分"，
而闸门比的是池内最高分。

**新口径**：把 `sym_text` 纳入**重排 passage**——
`hybrid()` 取回 `sym_text`；`rerank_gate` / `rerank_sort` 的 pair 改为
`bm25_text[:200] + " " + sym_text[:200]`（**两处必须同口径**——代码里写着这条不变量）。
理由：`bm25_text` 仍保持卡本体口径（实体表不受污染），而重排是**查询↔文档相关性**判断——
症状文本正是"农户的描述"与"这张卡"之间的桥，它天然属于重排，不属于实体表。

⚠️ **代价**：198 张无症状卡的 passage 逐字节不变（**追加**而非前置，正是为此）；
5 张卡的 pair 变长，**可能影响它们在别的问句下的排序** → 必须再跑一次受控对比。
（这同时补上了 §5.4 与 §15.2 警告① 留下的那个洞。）
具体预期与回归底线见 §4.3.1。

#### 4.3.3 ✅ 用户裁决：判据收窄为「**无语料实体 且 无意图**」，两层共用同一个函数

**裁决（2026-09-29）**：症状问法 ＝ **无语料实体** **且** **无意图**。
判据实现为 `search.py` 的 `is_symptom_query(q)`（**唯一一处**），
**检索层（重排 passage）与生成层（【症状对照】段）共用它**——
`answer.py::_is_symptom_query` 只保留「延迟导入 + 保守兜底」，不再自己实现一遍。

为什么必须两件都占：农户描述现象（「蒜苗叶子上有一条条白色弯曲的斑道，是什么危害？」）
既说不出病名、也不带任何问法模式；而「种辣椒打药…换着用不同的药」**没有病名，却被
`chemical_control`（「打药」）认领**——它问的是**施药规矩**（正文 6.3.4.4），不是症状描述。
**意图是"这是个问句、不是一段描述"的证据。**

**④（收窄）实测——两条预注册期望都兑现**：

## 5. 生成层与答案措辞

**数据通路**：`answer.py` 已在模块导入时建 `_CARDS[chunk_id] = chunk["card"]`（`answer.py:54-57`），
照同一处再建 `_SYMPTOMS[chunk_id] = chunk.get("symptoms") or []`。检索层不参与。

### 5.1 三条渲染规则

1. **症状段永远逐字、不过模型**。高危卡本来就走模板；普通卡虽走 DeepSeek，
   但症状段单独模板渲染——引文不过模型就不会被改写
2. **触发条件：问句里没有病虫害实体**（农户在描述现象、没说出病名）。
   有病名的问法（"黄瓜霜霉病打什么药"）**答案零变化**——这条性质容易验证，
   也是回归安全绳。
   判据 ＝ `extract_entities(query)` **再过一道语料验证闸**：
   `extract_entities(q) & (_MENTIONED | set(_CARD_CROPS))` 为空才算症状问法
   （两个名字都取自 `src/retrieve/search.py` 模块级，**只读不改**）。
   ⚠️ **判据的输入必须是归一化后的问句 `q2`，不是原始问句**（2026-09-28 最终审查发现）：
   检索层是在 `q2` 上做 `coverage_check` 的（`search.py` 先 `normalize()` 再判定），
   若这层拿原始问句去判，「大蒜**小白虫**打什么药」（小白虫→蓟马）、
   「大蒜**蒜蛆/黑蛆/根蛆**打什么药」（→种蝇）都会被判成症状问法——
   农户点了病名却拿到对照口吻，"有病名的问法答案零变化"这条安全绳**恰好断在
   口语映射表存在的意义上**。两个判据必须是**同一把尺子、同一个输入**。
   ⚠️ **不能只用 `extract_entities` 的原始输出**（2026-09-28 实现期发现）：
   已知实体表全落空时它会退回贪心正则 `[一-鿿]{2,6}(?:病|虫|…)`，
   把「是什么虫」「白色的虫」这类**散文噪声**当成实体——而
   「…是什么虫害？」「…是什么病？」恰是农户描述症状的**典型句式**
   （试点 collected 用例全是这个句式）。用它做判据，症状段对这些问句永远不触发，
   功能对它自己的目标用户失效。这道闸与 `search.py` `coverage_check` 用的是
   **同一个谓词**，两边不会漂。
3. **来源分开标**：症状来源（二级）与卡片来源（国标）各标各的，不混

### 5.2 答案形态（以 #5 大蒜豌豆潜叶蝇为例）

```
【结论】你描述的症状与下面这张卡（大蒜 豌豆潜叶蝇）记载的相符，请对照确认：
【症状对照】
  【豌豆潜叶蝇】叶片表皮下潜食叶肉，形成白色或灰白色弯曲的蛇形虫道，虫道内有黑色细小虫粪
  —— 来源：《河南农业》2023年第13期（农技文献，非国标）
【用药方案】（数值逐字来自国标原文）
  方案一：10%落灭津SC 30 g/667m² 对水喷雾，施药间隔7 d
  方案二：98%杀螟丹SPX 30 g/667m² 对水喷雾，施药间隔5 d~7 d
【来源】GB/Z 26578-2011 附录B 表B.1（p20）
【核实提示】（现有强制注入，措辞加一句"是否为你田里的情况请对照症状确认"）
```

**症状段位置**：放【结论】之后、【用药方案】之前。
理由：农户先确认"是不是这个病"，再看药方；放最后农户可能直接照着打药，不看症状。

### 5.3 核心措辞决定：不下诊断，只做对照

「你描述的症状与…**相符**」而不是「这是豌豆潜叶蝇」。

理由就是 #2 的教训：农户描述"茎基黑褐斑+萎蔫"可能是疫病也可能是别的，
系统一旦用肯定口吻下诊断，后面所有内容（尤其药方）就都建立在一个未经确认的判断上。
改成对照口吻后，**农户自己是最后一道校验**，而校验所需的信息（症状原文）就摆在答案里。

### 5.4 诚实定位：本机制不能自动修好 #2

它做两件事——把症状判断权交回农户、让症状可见可核对。
至于 c03（早疫/晚疫方案卡）会不会被 b6.2 压下去，是**实测问题**（见 §13 风险登记）。
假如没压下去，至少农户看到的是「症状对照：早疫/晚疫的症状…」，而不是默默拿到错药方。

## 10. false_fb 拆分（**必须与 symptoms 同批做**）

`eval/run_eval.py` 里 `false_fb` **一个计数器被两处复用**——正例分支的「误兜底」
与 noplan 分支的「该放宽却兜底」，而报告里「误兜底 X/正例数」读的正是它。
今天两处都是 0 所以看不出来，一旦有条目触发「该放宽却兜底」，误兜底那行就会报错数。

**修法**：

- 拆成 **`false_fb_positive`**（正例分支误兜底）与 **`false_fb_noplan`**（noplan 分支该放宽却兜底）
- 报告「误兜底 X/正例数」**只读 `false_fb_positive`**

**为什么必须同批**：症状落地会大量产生 noplan 分支判定，计数器不拆开，这份报告的数就不可信。

（决策来源：用户 2026-09-27 定，见 CLAUDE.md 二·待修）

#### 11.1.1 `pest` 校验：独立词元，不用子串（2026-09-28 实现期发现并修正）

规则：`pest` 必须作为**独立词元**出现在目标卡的 `subtype` **或** `source.quote` 里
（词元 = 按 `、，,;；:：|｜/` 切分后的整词）。

**子串匹配两个方向都不成立**：

| 方向 | 现象 | 后果 |
| --- | --- | --- |
| **假阳性**（更严重） | `pest="疫病"` 挂在 `早疫病、晚疫病` 方案卡上，子串法**放行** | 疫病症状安到早/晚疫卡上 → **错药方流到农户手里**，正是本模块存在的理由 |
| **假阴性** | 正文卡的 `subtype` 就是章节号（b6.2 → `"6.2"`），病虫害名只出现在 `quote` 里 | 试点第 1 条被自己的校验器拒收；所有正文卡（只在 6.2 列名、无方案那类）都挂不上 |

`quote` 是与 `subtype` **并列**的词元来源，不是"不确定时的二次确认"——正文卡没有别的
可比对象，quote 是它唯一能证明"症状挂对了病虫害"的依据。`quote` 本身逐字来自原文
（≤200 字），所以拿它做判据不引入外部知识。

实测（2026-09-28）：b6.2 的 quote 含独立词元「疫病」✓；c03 的「早疫病、晚疫病」不含裸
「疫病」→ 仍被正确拒收 ✓；试点 5 条全过 ✓。两条方向性用例锁在 `tests/test_symptoms.py`
（`test_子串不算数_疫病挂不到早晚疫卡` / `test_正文卡按quote认病虫害`）。

不改计划，怎么实现都错。

| # | 计划错在哪 | 后果 | 修法 | 谁抓到的 |
| --- | --- | --- | --- | --- |
| ① | `pest` 校验用**子串**匹配 | 两个方向都不成立：假阳性「疫病」挂上「早疫病、晚疫病」方案卡＝**错药**；假阴性——正文卡 subtype 是章节号，合法条目被自己的校验器拒收 | **独立词元 + `quote` 兜底**（quote 与 subtype 并列作词元来源） | 实现者自查（进审查前） |

### 18.1 方法论：实现者停下来问，比"做完再报"值钱

①② 是**实现者当场停下来说「这跟计划对不上」**，而不是硬着头皮按计划做完再报告。
如果硬做完，它们会**掩盖在"任务完成"的绿灯报告里**，一路过审，直到铺开
（20+ 条症状、更多作物）才暴露——那时的返工成本远不是现在这个量级。

**写给下一次的四条**：

1. **计划给的代码不是免检品。** brief 里的代码块写着"逐字实现"，但实现者仍要判断它是否自洽——
   本批两条最严重的缺陷，恰恰藏在"照做就对"的代码块里。
2. **测试喂的形状必须等于生产形状。** ③ 漏网是因为新测试全用**单结果**，而生产是 topk=3 混合。
   回归测试要按真实调用形状写，否则绿灯只证明"单结果路径没坏"。
3. **单测绿 ≠ 集成对。** ④ 两条判据各自都写对了，错的是**喂进去的输入不是同一个**——
   这类缺陷只有把两个组件放在一起跑才现形。
4. **每层审查抓的东西不同。** ①② 靠实现者，③ 靠任务审查，④⑤ 靠最终全量审查。
   最终审查不是走过场：它拿真实数据（口语映射表、真实卡片）渲染，才碰到前几层碰不到的地方。

### 18.3 回归底线与「已有信号优先」（2026-09-29 重排 passage 改动）

**一、机制会潜伏。** 「症状信号漏进非症状问句」这条通路，在 **5 张卡**时碰巧只撞出
**1 条** auto 用例；铺开到 **25 张卡**后症状文本更多更长，撞出更大事故**只是时间问题**。
这次不修，铺开后必出大事。

**二、「逐位不变」比「没有明显回退」值钱。** 前者把"我没看出问题"换成"**我证明没变**"；
**弱断言抓不住回归，因为"明显"是主观的**。这次强断言证明**失败**，恰恰是它的价值——
改动的两条预注册期望里，①（五条症状用例修好）5/5 全中，②（**auto 232 逐位不变**）**破了**，
而破的正是安全侧那条「问技术拿到药方」（技术问句的附录B 池被症状文本抬过闸门 0.1156）。

**三、优先用系统里已有的信号，不新增知识。** 收窄症状判据用的是 `chemical_control` 等
**意图标签——它本来就在**，只是症状判据此前**只看实体、不看意图**。修法 ＝
**症状问法 ＝ 无语料实体「且」无意图**，检索层与生成层共用一个实现
（`search.py::is_symptom_query`），两层从此结构上不可能漂。
零新增知识、零新增组件——只把一个**已经存在的判断**接了过来。

**收窄的实测爆炸半径（2026-09-29，259 条全扫）**：生成层口径 **168 → 133**，翻掉 **35 条**
（chemical_control 21 / control_principle 6 / physical_control 3 / fertilizer 2 /
chemical_rules 2 / irrigation 1，**基本都是技术问句**）；**其中期望卡恰是那 5 张症状卡的：0 条**
——收窄**按构造**伤不到战果。**重排层**则是从 ③ 的 259 条全拼收成 133 条拼（**126 条开关被撤**），
实际分数只在池内含症状卡的问句上变化。

⚠️ **铺开多作物症状层时必须重扫这一面**：35 条这个数会随症状卡数量增长；
且**尾带问药句的真症状描述**（本轮 4 条）会一并被划进"技术问句"，届时要重新裁决。

**四、能用结构保证的，不靠纪律保证。** 收窄后检索层与生成层**共用一个实现**
（`search.py::is_symptom_query`）——**不是"两边各自记得用同一把尺子"，而是根本只有一份**。
这解掉的正是 §18.1 第 2 条那类问题（「测试喂的形状必须等于生产形状」）：
当"一致"由结构保证时，它**不可能**不一致，也就没有"忘了同步"这回事。

同一手法在本批用了三次，都是同一个思路：
- `_sym_block()` —— 生成层两个分支（高危组内 / 提前成块）不再各拼一遍
- `_rerank_passage()` —— 闸门与排序的 pair 从此同口径（原来靠 :565 的注释提醒）
- `is_symptom_query()` —— 检索层与生成层共用一份判据（原来各写各的）

**判据**：当两处代码**必须保持一致**时，先问"能不能让它俩变成一处"；
只有变不成一处时，才退而求其次去写注释、加测试。
