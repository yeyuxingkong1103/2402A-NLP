# Phase 1 Data Model: 医知源 · 提问输入链路与前端骨架

**Feature**: `006-medical-qa-input` | **Date**: 2026-09-27

本特性**没有持久化**（系统不做历史记录，`docs/01` §7.2）。因此这里定义的全部是**进程内的传输模型**：请求体、流事件、终帧。

终帧的字段**原样复用** `docs/05` §3.1.3 的契约，不新增、不改名——这是 SC-009 的验证对象。

---

## 1. `AskRequest` —— 提问请求体

| 字段 | 类型 | 必需 | 约束 | 来源 |
|---|---|---|---|---|
| `question` | string | ✅ | 去除首尾空白后长度 1–200（闭区间） | `docs/05` §3.1.2 |

**校验规则**（`backend/api/validate.py`）：

| 输入 | 判定 | 结果 |
|---|---|---|
| 缺失 / 非字符串 | 非法 | 422 `INVALID_QUESTION` |
| 去空白后长度 == 0 | 非法 | 422 `INVALID_QUESTION` |
| 去空白后长度 > 200 | 非法 | 422 `INVALID_QUESTION` |
| 去空白后 1 ≤ 长度 ≤ 200 | 合法 | 进入流式应答 |

**关于"去除首尾空白"的口径**：使用 Python 的 `str.strip()` 语义（含全角空格 U+3000、制表符、换行）。判定用的是**去空白后的长度**，但**存入日志与后续检索的是去空白后的字符串**——否则同一问题因首尾空格不同会被当作两个不同的 query。

**为什么上限是 200**：`docs/05` §3.1.2 已裁决，理由是 M1 定义的是单轮、非专业的口语化提问。本特性沿用，不重新讨论。

---

## 2. 流事件（SSE）—— 运行时的核心模型

一次 `POST /ask` 的 200 响应体是**一串按序到达的事件**。事件类型由 SSE 的 `event:` 字段承载，`data:` 是单行 JSON。

### 2.1 事件序列

```text
status      →  citations  →  token*  →  done
   │              │            │         │
   │              │            │         └─ 终帧：docs/05 §3.1.3 完整响应体
   │              │            └─────────── 正文增量，可 0..n 次
   │              └──────────────────────── 引用片段批次（按 score 降序），恰好 1 次
   └─────────────────────────────────────── 接收确认，携带 answer_id，恰好 1 次
```

**硬性顺序约束**：`status` 必须第一，`done` 必须最后，`citations` 恰好一次且在全部 `token` 之前。

### 2.2 `event: status`

| 字段 | 类型 | 说明 |
|---|---|---|
| `answer_id` | string (UUID) | 本次回答的唯一标识。**必须在首帧出现**，理由见 research R10 |
| `state` | enum | 本期恒为 `accepted` |

**为什么首帧只带这两个字段**：首帧的职责是"让客户端确认服务端已开始处理"，不是传递业务数据。塞入更多字段会让"接收确认"与"业务结果"在同一帧混合，前端就必须等首帧才能决定是否显示加载态。

### 2.3 `event: citations`

| 字段 | 类型 | 说明 |
|---|---|---|
| `citations` | array | 引用片段数组，**按 `score` 降序** |

单条引用片段的结构（= `docs/05` §3.1.3 的 `citations[]` 元素）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `citation_id` | int | 从 1 起，与正文中的 `【n】` 标记一一对应 |
| `file_name` | string | 来源文件名 |
| `page_start` | int | 起始页码 |
| `page_end` | int | 结束页码（跨页 chunk 时 > `page_start`） |
| `section` | string \| null | 章节标题 |
| `block_type` | string | `text` / `table` / `image` / `page_footnote` |
| `text` | string | 原文片段 |
| `score` | float | **余弦相似度分数，排序依据** |

**本期取值**：`citations: []`（空数组）。**仍然发送该事件**，而不是省略——让前端的事件处理路径从第一天起就是完整的，避免接入时才暴露"空数组分支从没跑过"。

**排序规则的落点**：降序排序由**服务端**完成（`docs/05` §4.2：`RetrievalResult.passages` 按 score 降序）。前端 MUST NOT 重新排序——见下文 §4。

### 2.4 `event: token`

| 字段 | 类型 | 说明 |
|---|---|---|
| `text` | string | 正文增量片段 |

**顺序约束（FR-030 的落点）**：若紧急前置话术存在，它 MUST 是**第一个 `token` 事件的内容**，且在此之前 MUST NOT 出现任何 `token` 事件。

> **一处必须在 plan 中言明的细化**：`citations` 事件**允许**出现在紧急话术之前。规格 FR-030 的措辞是"MUST NOT 在流中插入任何先于它的内容"，其本意是**回答正文**不得有内容先于话术——`docs/05` §3.1.1 担心的是"用户看到的第一句不是那句话"，而引用卡片不是"回答的第一句"。且用户明确要求引用片段先展示。二者不冲突：**引用区在答案区下方渲染，用户视线的第一处正文文字仍是话术。**

**本期取值**：1 个 `token` 事件，内容为"能力未就绪"文案。它走的是与将来真正答案**完全相同**的通道 —— 若本期不发，前端的 `appendToken` 与终帧纠正逻辑就是从未执行过的死代码。详见 [contracts/sse.md](./contracts/sse.md) §2.3 的修正说明。

### 2.5 `event: done` —— 终帧

`data` 是 `docs/05` §3.1.3 响应体的**逐字段复用**：

| 字段 | 类型 | 本期取值 | 说明 |
|---|---|---|---|
| `answer_id` | string (UUID) | 与 `status` 帧一致 | 同一性可校验 |
| `is_refusal` | boolean | `true` | 本期未产出知识性回答 |
| `emergency` | object | `{"triggered": false}` | 本期无紧急判定模块 |
| `risk_level` | enum | `"none"` | `docs/05` §3.1.6：拒答 → `none` |
| `answer_text` | string | 未就绪文案 + `\n\n` + 免责声明 | 见下 §3 |
| `citations` | array | `[]` | 与 `citations` 事件一致 |
| `disclaimer` | string | 免责声明逐字文本 | 单独返回供前端独立样式处理，**非用于拼接** |

**契约不变量**：`done.answer_id == status.answer_id`（同一性保证，前端可断言）。

## 3. 逐字话术常量

三句话术 MUST 以常量定义在**唯一一处**，且 MUST 逐字匹配 `docs/01` 的锁定文本。

| 常量 | 文本 | 本期是否发出 | 权威来源 |
|---|---|---|---|
| `EMERGENCY_PREAMBLE` | `请立即就医或拨打急救电话。以下信息仅供参考。` | ❌（无紧急判定模块） | `docs/01` §F4、constitution 原则 IV |
| `DISCLAIMER` | `以上为基于知识库的参考信息，不能替代执业医师的当面诊断。` | ✅（所有路径末尾） | `docs/01` §F5、constitution 原则 V |
| `REFUSAL_FALLBACK` | `这个问题在现有知识库中找不到可以依据的原文，我无法给出有依据的回答。建议你咨询专业医生。` | ❌（本期无"检索过且为空"这一事实） | 本特性定稿，待回填 `docs/01` §F6 |

**本期实际发出的未就绪文案**（不是拒答话术，理由见 research R5）：

```text
你的问题已收到。医知源的向量检索与大模型生成能力正在接入中，本期暂不能给出答案。
```

**为什么三句常量与本期的未就绪文案要放在同一处**：`docs/05` §4.4 要求"全仓检索这两句逐字文本，只应命中一个函数"——把它扩展到本特性，就是**全部面向用户的固定文案只有一处定义**。分散会让"改了一句、漏改一处"成为必然。

**拼接规则**：`answer_text = 正文或兜底文案 + "\n\n" + DISCLAIMER`。本期无前置话术分支。

## 4. 前端渲染模型

### 4.1 引用区排序

前端 MUST 按服务端给出的顺序**原样渲染**，MUST NOT 重新排序。

**理由**：排序依据是余弦相似度，而相似度是**服务端算出来的**。前端重排意味着排序规则在客户端被复刻了一遍——两份实现必然漂移，且漂移时**没有任何测试能发现**（服务端测试全绿，前端只是显示顺序不同）。

因此前端对 `citations` 数组的唯一处理是 `map` 到 DOM 节点，不调用任何 `sort`。

### 4.2 两区布局约束

```text
┌─ 问答详情区 ─────────────────────────┐
│  ┌─ 答案正文区 ──────────────────┐  │   ← 在上
│  │  token 事件按到达顺序追加       │  │
│  └────────────────────────────────┘  │
│  ┌─ 引用片段区 ──────────────────┐  │   ← 在下（FR-027）
│  │  [1] 文件名 第12页  0.71       │  │
│  │  [2] 文件名 第8页   0.65       │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

**正文追加的渲染纪律**：每个 `token` 到达即追加到**同一个文本节点**，不重建 DOM。这既是为了流畅，也是为了顺序——重建 DOM 会让"先渲染后重排"成为可能，而那正是 FR-030 要防的。

### 4.3 界面状态机

| 状态 | 进入条件 | 界面表现 | 出口 |
|---|---|---|---|
| `idle` | 初始 / 请求结束 | 输入可用，发送可点 | 用户提交 |
| `submitting` | 提交瞬间 | 发送置灰，输入锁 | 首帧到达 / 失败 |
| `streaming` | 收到 `status` | 显示进行中，答案区开始接收 | `done` / 失败 |
| `done` | 收到 `done` | 输入解锁，显示结果 | 用户再次提交 |
| `failed` | 连接失败 / 超时 / 422 | 明确可读的错误提示（FR-014） | 用户重试 |

**`submitting` 与 `streaming` 必须分开**：二者对用户的含义不同——前者是"请求还没被接受"，后者是"已经被接受、正在处理"。合并会让"服务没起来"和"服务在算"看起来一模一样，而 FR-012/FR-014 要求它们可区分。

## 5. 实体关系

```text
AskRequest (1) ─── 触发 ───▶ 一次流式应答
                                  │
                    ┌─────────────┼──────────────┬─────────────┐
                    ▼             ▼              ▼             ▼
                 status       citations       token*         done
                 (answer_id)  (Citation[])  (增量文本)   (AskResponse)
                    │                                          │
                    └────────── answer_id 同一性 ──────────────┘
```

- `AskRequest` 与 `AskResponse` **无持久化**，进程内一次问答结束即释放。
- `Citation` 本期为空集，但结构已定，后续由 `specs/004`/`specs/005` 的产物供给。
- `NavItem`（导航项）是纯前端模型，不进服务端：`{id, label, panel, default}`。
