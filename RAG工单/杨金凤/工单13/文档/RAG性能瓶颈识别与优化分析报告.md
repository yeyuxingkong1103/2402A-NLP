# RAG 性能瓶颈识别与优化 —— 性能瓶颈分析报告

- **工单编号**：人工智能NLP-RAG-RAG性能瓶颈识别与优化
- **项目名称**：RAG 性能瓶颈识别与优化
- **日期**：2025 年

---

## 1. 任务目标

对已搭建的 RAG 系统进行性能分析，识别检索返回时间过长的瓶颈，并优化至 3 秒以内。

---

## 2. 分析方法

按照工单要求，对 RAG 流程的每个阶段逐一计时：

| 阶段 | 说明 |
| --- | --- |
| Query 改写 | LLM 将问题改写成检索友好查询 |
| 检索 | 向量检索 + BM25 混合检索 |
| 精排 | BGE Reranker 对候选块重排序 |
| LLM 生成 | Qwen2.5-7B 基于上下文生成回答 |

每个阶段独立测量进入/退出时间戳，分析 5 个问题的平均耗时。

---

## 3. 瓶颈诊断结果

### 优化前（基线）

| 阶段 | 平均耗时 | 占比 |
| --- | --- | --- |
| Query 改写 | 0.00s | 0% |
| 检索 | 0.08s | 0.7% |
| 精排 | 0.05s | 0.5% |
| LLM 生成 | 10.70s | 98.8% |
| **总计** | **10.83s** | **100%** |

**结论**：瓶颈 98.8% 集中在 LLM 生成阶段，检索和精排几乎不耗时。

### 为什么 LLM 生成这么慢？

| 因素 | 影响 |
| --- | --- |
| max_new_tokens=512 | 一次生成最多 512 token，耗时随长度线性增长 |
| 上下文 4 块 + 每块 800 字 | 输入 prompt 很长，首 token 延迟高 |
| Prompt 规则复杂 | 600+ 字的系统提示，增加输入 token |
| Qwen 4-bit 量化推理 | 单次生成约 1-3 token/秒 |

---

## 4. 优化方案

针对瓶颈做 3 轮渐进优化：

### 第 1 轮优化

| 优化项 | 原值 | 新值 | 效果 |
| --- | --- | --- | --- |
| max_new_tokens | 512 | 200 | 生成时间 -60% |
| 上下文块数 | 4 | 2 | 输入减半 |
| 每块截断 | 800 字 | 500 字 | 输入再减 |
| Prompt | 600 字 | 200 字 | 输入再减 |

结果：10.83s → 5.42s（提升 49.9%）

### 第 2 轮优化

| 优化项 | 原值 | 新值 | 效果 |
| --- | --- | --- | --- |
| max_new_tokens | 200 | 128 | 生成时间 -35% |
| 上下文块数 | 2 | 1 | 输入再减半 |
| 每块截断 | 500 字 | 300 字 | 输入再减 |

结果：5.42s → 4.89s（累计提升 54.9%）

## 6. 结论与限制

### 优化效果

- 总耗时从 10.83s 降到 4.89s，提升 54.9%
- 检索和精排本已高效（占总耗时 1.2%）
- 优化全部集中在 LLM 生成阶段

### 未完全达到 3s 目标

- 当前 4.89s 仍超 3s 目标
- **根本原因**：Qwen2.5-7B 4-bit 量化在单卡 RTX 3090 上的推理速度约 3-5 token/秒，生成 128 token 需约 4s

### 进一步优化空间

1. 换用更小的模型（Qwen2.5-1.5B 或 3B）
2. 使用 vLLM 等高性能推理引擎
3. 升级到更高算力的 GPU

### 权衡说明

- 优化后回答更简短，可能损失部分信息完整性
- 生产环境应根据"响应速度 vs 回答质量"的平衡选择参数
