# docs/ 文档索引

> 本目录是项目的唯一文档来源。**任何开发动作以本目录文档为依据，不以聊天记录或历史计划为依据。**

---

## 一、文档清单与用途

| 文档 | 用途 | 权威性 |
|---|---|---|
| **开发路线图.md** | 做什么、什么顺序、什么算完成（阶段 → 任务 → 验收） | ⭐ **最高**：与其他任何计划冲突时以此为准 |
| **目录与命名约定.md** | 代码放在哪、怎么命名、怎么分层 | ⭐ **最高**：目录与命名以它为准 |
| 需求文档.md | 业务范围、功能需求、验收标准 | 高（与路线图冲突时以路线图为准） |
| 技术栈与架构文档.md | 技术选型、双链路架构、数据与记忆设计 | 高 |
| 接口文档.md | 接口契约（路径、请求、响应、错误码） | 高：**实现必须与之一致** |
| 测试文档.md | 测试范围与方法 | 中 |
| 部署文档.md | 部署步骤与环境要求 | 中 |
| CONTEXT.md | 领域术语表（统一用词） | 高：**术语以它为准** |
| 提示词.md | 回答提示词（系统提示词正文与版本记录） | 高（待从桌面移入） |
| archive/ | 历史计划与规格（已归档，仅供追溯） | 低：**不作为开发依据** |

---

## 二、开工前必读顺序

```text
1. 开发路线图.md        —— 知道自己要做哪一步、做完的标准是什么
2. 目录与命名约定.md     —— 知道代码该写在哪、叫什么名字
3. 需求文档.md          —— 确认业务范围（哪些做、哪些不做）
4. 接口文档.md          —— 实现接口前必须核对（路径、响应结构、错误码）
5. CONTEXT.md           —— 统一术语，避免自造词
```

---

## 三、文档权威顺序（冲突时的裁决规则）

```text
开发路线图.md  >  目录与命名约定.md  >  需求文档.md  >  技术栈与架构文档.md
              >  接口文档.md  >  测试文档.md  >  部署文档.md  >  CONTEXT.md
              >  archive/（不与任何文档比较，仅供回溯）
```

---

## 四、文档维护规则

```text
1. 代码与文档不一致时，先修文档还是先修代码？
   → 以"能跑通并经测试验证"的一侧为事实基础，另一侧对齐；并在本文档的变更记录中写明。

2. 每次改动功能，必须同步更新：
   - 开发路线图.md 中对应任务的状态与证据
   - 接口文档.md（若接口契约变化）
   - CONTEXT.md（若引入新术语）

3. 计划类文档只允许存在一份：开发路线图.md。
   新的想法先写进路线图的"待评估"区，不另起计划文件，避免再次出现"三套目录说法"。

4. 历史计划统一移入 archive/，不再修改，只作追溯。
```
