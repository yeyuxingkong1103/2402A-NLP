# 部署优化说明

**工单编号**：人工智能NLP-RAG-金融问答系统部署

记录容器化过程中做的几处优化，都带实测数据；最后列出**明知可优化但本次没做**的项及原因。

---

## 一、基础镜像：换掉 CUDA 镜像，构建从「拉不动」到 11MB/s

这是本工单收益最大的一处改动，起因是原方案根本走不通。

| 方案 | 基础层体积 | 主要下载通道 | 实测结果 |
|---|---|---|---|
| `pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime` | ~3.5GB | Docker registry 加速器 | 10 分钟零进度，TLS handshake timeout |
| `nvidia/cuda:12.6.3-cudnn-runtime-ubuntu22.04` | ~2GB | Docker registry 加速器 | 反复超时；且带 Python 3.10，与开发环境 3.11 不符 |
| **`python:3.11-slim` + pip 装 torch** | **189MB** | **pip 清华源** | **能跑通；速度波动大，见下** |

清华源实测速度波动明显：torch 主体（906MB）约 11MB/s，
`nvidia-cudnn-cu12`（665MB）掉到 703kB/s。即便如此，**全程可完成**，
而加速器拉 CUDA 基础镜像连"开始下载"都做不到 —— 差别在可用与不可用，不在快慢。

**依据**：Linux 上 PyPI 的 torch 轮子自带 CUDA 12 运行时
（依赖里的 `nvidia-cuda-runtime-cu12`、`nvidia-cudnn-cu12` 等）。
容器用 GPU 只需「宿主机驱动 + 容器内 CUDA 用户态库」，前者由
NVIDIA Container Toolkit 在 `--gpus all` 时注入，后者 pip 已提供 ——
**根本不需要 CUDA 基础镜像**。

附带收益：Python 版本自动对齐到 3.11（与开发环境 `rag_gd` 的 3.11.16 一致），
省掉了在 Ubuntu 22.04 上装 Python 3.11 的麻烦（deadsnakes PPA 或 conda）。

## 二、模型瘦身：4.3GB → 2.1GB

`bge-m3` 目录构成实测：

| 内容 | 体积 | 是否必需 |
|---|---|---|
| `pytorch_model.bin` | 2.2GB | ✅ FlagEmbedding 加载的就是它 |
| `onnx/` | 2.2GB | ❌ onnxruntime 用的，本项目不加载 ONNX |
| `imgs/` + `long.jpg` | 1.2MB | ❌ README 配图 |
| `.cache/` | 64KB | ❌ |

`model-init` 服务复制时排除后三项，**灌卷体积减少 51%**。

排除逻辑写在 compose 的 `command` 里而不是 Dockerfile 里 ——
模型不进镜像，瘦身动作应该发生在「往卷里灌」这一步。

## 三、Dockerfile 分层：把最大的依赖单独放一层

```dockerfile
RUN pip install --no-cache-dir torch==2.5.1     # 第 5 层，约 2.5GB
COPY 研发/requirements.txt /app/requirements.txt
RUN pip install --no-cache-dir -r /app/requirements.txt   # 第 7 层
COPY 研发/*.py /app/                            # 第 8 层
```

torch 及其 CUDA 依赖约 2.5GB，是最大的一块。把它单独放在**依赖清单之前**，
好处是：改 `requirements.txt` 或改代码时，torch 这一层直接命中缓存，
不用重新下载 2.5GB。

反过来如果把代码 `COPY` 放在 `pip install` 之前，任何一次改代码都会
让后面所有层失效，每次构建都要重装一遍依赖。

## 四、压掉误导性告警

`TRANSFORMERS_VERBOSITY=error` + `TOKENIZERS_PARALLELISM=false`。

transformers 默认会打一条 XLMRobertaTokenizerFast 的性能提示。
它无害，但混在启动日志里像异常，而验收标准明确要求
「容器运行过程中无异常日志输出」。压掉之后
`grep -iE "traceback|exception|error|critical"` 扫日志是干净的。

---

## 五、健康检查的 start-period 给到 180 秒

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=180s --retries=3 ...
```

首次启动要加载 BGE-M3（约 3.2GB 显存）并读入 7009 块的知识库。
`start-period` 给小了会导致容器刚起就被判不健康、被编排系统反复重启。
180 秒是按实测留了余量。

## 六、实测发现并修复的缺陷：`kb-builder` 在容器里找不到语料

**怎么发现的**：容器化完成后逐条试 compose 里的服务，`kb-builder` 起不来。
定位到 `研发/ccf_docs.py` 第一行路径写死了 Windows 路径：

```python
CORPUS_DIR = Path(r"D:\BW\RAG 工单\附件\ccf_competition")
```

而 `docker-compose.yml` 把语料挂到 `/corpus` 并设了 `CORPUS_DIR=/corpus` 环境变量 ——
**这个环境变量根本没人读**。实测确认：

```
环境变量 CORPUS_DIR = /corpus
代码里实际用的路径 = D:\BW\RAG 工单\附件\ccf_competition   ← 容器里不存在
这个路径存在吗 -> False
解析到 0 份文档
```

后果：`kb-builder` 服务（换语料时重建知识库用）在容器里必然失败，
而它是验收项「支持容器间数据共享」的落地方式。

**修复**：

```python
CORPUS_DIR = Path(os.getenv("CORPUS_DIR", r"D:\BW\RAG 工单\附件\ccf_competition"))
```

同时统一了 `CORPUS_DIR` 的语义 —— 三处原本不一致：
代码指的是「含 pdf/ 与 txt/ 的那一层」，compose 的默认值却指它的父目录。
现在统一成前者（`.../附件/ccf_competition`），compose 默认值、`.env.example`、
部署文档同步改齐。

**验证**：修复后容器内 `ccf_docs.available()` 解析到 **9 份文档**（修复前 0 份）。

> 这类问题只有真的把服务跑一遍才会暴露 —— 文档、compose、代码三处看起来
> 都「说了同一件事」，但实际语义不一致，静态检查发现不了。

## 七、明知可优化但本次没做

| 项 | 收益 | 不做的原因 |
|---|---|---|
| 多阶段构建 | 可去掉 build 工具链，省几百 MB | 本项目没有编译步骤（依赖都是 wheel），收益接近零 |
| 换 distroless / alpine 基础 | 再省约 50MB | torch 与 CUDA 运行时依赖 glibc，alpine 用 musl，装不上；收益也不值这个风险 |
| 模型量化（fp16 → int8） | 显存从 3.2GB 降到约 1GB | 会改变检索质量，而本工单只做部署，不该动检索链路；且 6GB 显存当前够用 |
| 只在 CPU 上跑，彻底去掉 CUDA | 镜像从 3.40GB 降到约 1.5GB | 检索延迟会明显上升，金融问答的交互体验变差；且宿主机有 GPU |
| 镜像推送到私有 Registry | 便于多机分发 | 工单未要求，且需要目标 Registry 地址与凭据 |
| Nginx 反代 + HTTPS | 生产必备 | 验收标准未要求；已在《部署文档》常见问题里提示 |

判断标准是**这个工单的验收标准**：以上几项要么收益与风险不匹配，
要么会越界改动被测系统。列在这里是为了说明「不是没想到」，而不是遗漏。
