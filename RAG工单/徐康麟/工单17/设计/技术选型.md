## 1. 选型总约束

1. **零新增运行时依赖**：本机 pip 通道不通（`_共享约定.md §2`：`pip install` 会写进只读的工单1 venv，
   必须 `--target`，且网络路径实测挂死）。所有新增能力用**标准库**实现。
2. **单进程**：禁止 `multiprocessing` / `ProcessPoolExecutor` / `joblib` / `Pool(`。
   并发只用 `threading` 与 `concurrent.futures.ThreadPoolExecutor`。
3. **可开关**：所有性能改动受 `PERF_ENABLED` 总开关控制，可一键回到基座行为。
4. **阈值配置化**：见 `部署/配置/.env.example` 的 `PERF_*` 段。

## 2. 逐项选型与对比

### 2.1 压测工具：自研 `load_runner.py` vs jmeter vs locust

| 方案 | 可用性 | 结论 |
| --- | --- | --- |
| Apache jmeter | **未安装**（`Get-Command jmeter` 无结果） | 原文要求，但本机不可用 |
| locust | 未安装；需 `pip install locust` + gevent | 违反零依赖纪律 |
| **自研 `load_runner.py`** | 仅用 `threading` + `urllib` + `statistics` | ✅ **选用** |

**为什么自研够用**：本工单要的是「并发用户数 / 持续时长 / 思考时间 / 分位延迟 / 吞吐 / 失败率 / 明细留痕」，
这七项用 `ThreadPoolExecutor` + 每请求一行 JSONL 即可完整覆盖；
GIL 对 I/O 型压测客户端无影响（客户端只等 HTTP 响应）。
**额外收益**：可内建**熔断**（jmeter 需插件），符合本工单的资源纪律。

### 2.2 HTTP 客户端：`http.client` 连接池 vs `requests.Session` vs `urllib`

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| `urllib.request.urlopen` | 基座现用；**每次调用新建连接**，无 keep-alive | 优化对象 |
| `requests.Session` | `requests` 已装，Session 自带连接池 | 可用，但**引入一层依赖**且流式逐行读要 `iter_lines`，对 Ollama 的 NDJSON 需额外适配 |
| **`http.client.HTTPConnection` 自建池** | 标准库，HTTP/1.1 默认 keep-alive，`response.readline()` 直接支持 NDJSON 流式 | ✅ **选用** |

连接池规模：`PERF_HTTP_POOL_MAX_IDLE`（默认 8）、`PERF_HTTP_POOL_TIMEOUT_S`（默认 60）。

### 2.3 限流：有界信号量 + 有界等待队列 vs `asyncio.Semaphore` vs 无

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 无（基座） | 20 并发全部直冲，线程池与 Ollama 排队 | 优化对象 |
| 纯 `asyncio.Semaphore` | 只能约束「进入路由的协程数」，但协程 `await run_in_threadpool` 后线程池仍可能被塞满 | 不够 |
| **`threading.BoundedSemaphore` + 等待位计数** | 在途 + 排队 双上限；超出立即 `429` | ✅ **选用** |

参数：`PERF_MAX_INFLIGHT`（默认 **8**）、`PERF_QUEUE_MAX`（默认 **32**）、`PERF_ACQUIRE_TIMEOUT_S`（默认 30）。

> 为什么 `max_inflight` 默认是 8 而不是 20：Ollama 单实例在单张 RTX 2060 上串行推理，
> 放 20 个并发的唯一后果是排队变长、P95 变差。降到 8 让**请求在入口快速失败（429）或快速完成**，
> 而不是全都在服务内部等 10 秒。这是「限流优于堆积」的直接体现，实测数据见 `优化/评估结果/`。

### 2.4 剖析：cProfile + tracemalloc vs py-spy vs memory-profiler

| 方案 | 可用性 | 结论 |
| --- | --- | --- |
| py-spy | 未安装 | 不可用 |
| memory-profiler / objgraph | 未安装 | 不可用 |
| **`cProfile` + `pstats`** | 标准库 | ✅ 用于「相对占比」定位 |
| **`tracemalloc` + `gc.get_objects()`** | 标准库 | ✅ 用于「泄漏对象 Top-N」定位 |
| **`threading.enumerate()` + `sys._current_frames()`** | 标准库 | ✅ 用于「线程阻塞在哪」定位 |

cProfile 会带来 2~5× 开销，因此**只用于占比分析**；绝对性能结论一律以压测器的客户端计时为准。

### 2.5 进程内单例：模块级懒加载 + `RLock` 双检锁 vs `functools.lru_cache`

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| `functools.lru_cache` | 无 TTL 控制（Python 3.11 无 `ttl` 参数），且缓存 `Exception` 语义复杂 | 不用 |
| **`service/singletons.py` 手写双检锁 + TTL** | 可配 TTL、可 `reset()`（测试要重置）、可统计命中 | ✅ **选用** |

### 2.6 解析任务队列：进程内有界队列 vs Redis 队列 vs Celery

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| Redis LIST 队列 | `MiniRedis` 已能 `RPUSH`/`BLPOP`；但需要独立的 Task Executor 进程 | 本机单进程，**做了但默认关闭**（`PERF_PARSE_BACKEND=memory`） |
| Celery / RQ | 需 `pip install` | 违反零依赖 |
| **进程内 `queue.Queue(maxsize=N)` + worker 线程池** | 与「API Server 不阻塞」语义等价，队列有界可返回 429 | ✅ **选用** |

保留 `PERF_PARSE_BACKEND=redis` 分支，容器部署时可直接切到 Redis 队列
（`部署/docker/docker-compose.yml` 里 `PERF_PARSE_BACKEND=redis`）。

### 2.7 sqlite 优化：WAL + `synchronous=NORMAL` vs 换库

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 保持默认 DELETE journal + FULL sync | 每 `commit()` 一次 fsync | 优化对象 |
| **WAL + `synchronous=NORMAL`** | 写不阻塞读；fsync 次数显著降低 | ✅ **选用** |
| PostgreSQL / MySQL | 引入服务与依赖 | 违反纪律 |
