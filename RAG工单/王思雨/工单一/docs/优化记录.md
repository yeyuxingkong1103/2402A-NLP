## 1. 向量化：批内变长 padding（最大单项收益）

### 现象

建索引卡在"向量化并写入 Milvus"这一步，GPU 满载但 6 分钟无进展。

### 定位

逐批打点后发现单批耗时极不均匀：

```
batch 0/831    编码 70.1s
batch 64/831   编码  4.1s
batch 128/831  编码  3.6s
batch 192/831  编码 55.0s
```

### 原因

`sentence-transformers` 编码时会把**同一批内所有样本 padding 到该批最长长度**。原始分块按页码顺序排列，一个 8000 字的表格块混进某批后，整批 64 条都要按 8000 token 计算，单批从 3.6s 恶化到 70s。

### 修改

1. **全局按内容长度排序后再分批**（`app/store.py::index_chunks`）——同批长度接近，padding 浪费最小；
2. **限制编码长度** `EMBED_MAX_TOKENS=1024`（bge-m3 默认 8192，对分块检索没有必要）；
3. **超大表格按行切分**（`app/rag.py::_split_big_table`），每片重复表头，单片不超过 1200 字。

> ⚠️ 第 1 点最初只在批内排序（先切 64 条再排序），**没有效果**——因为排序范围必须覆盖全部分块。改为全局排序后收益才显现。

### 效果

| 指标 | 前 | 后 |
|---|---|---|
| 步骤 3 向量化入库 | 295.9s | **94.0s** |
| 单独测 872 条向量化 | 数分钟（未跑完） | **34.6s** |

## 2. 生成：关闭长推理（精度与延迟双赢）

### 现象

1. 首字延迟 P50 3.21s，仅 30% 达标；
2. 10 题中有 1 题（id=33）返回**空答案**；
3. LLM Query 改写稳定失败，日志 `[Query理解降级] LLM 改写失败：AttributeError`。

### 定位

直接测 API 响应体，发现 `deepseek-v4-flash` 是**推理模型**：

```
max_tokens=600 基线：  reasoning_tokens=600  content_len=0   ← 预算被推理吃光，正文为空
```

`max_tokens=300` 时更严重，推理占满额度，`content` 返回空字符串 → JSON 解析报 `AttributeError`。

### 修改

| 参数 | 实测结果 |
|---|---|
| 基线（无参数） | 5.23s，600 reasoning tokens，**content 为空** |
| `reasoning_effort=minimal` | 4.48s，600 reasoning tokens，**仍为空** |
| `enable_thinking=false` | 3.53s，351 reasoning tokens，内容完整 |
| `thinking={'type':'disabled'}` | 2.14s，无 reasoning tokens，内容完整 |
| **`reasoning_effort="none"`** | **1.57s**，无 reasoning tokens，内容完整 ✅ |

选用 `reasoning_effort="none"`（配置项 `LLM_REASONING_EFFORT`）。理由：RAG 生成的任务是"从给定资料里摘取并组织"，属抽取式，不需要长推理；关掉后**又快又准**（空答案消失）。

同时把 Query 改写的 `max_tokens` 从 300 提到 1200，并显式处理空回复，使其在降级前有机会成功。

### 效果

| 指标 | 前 | 后 |
|---|---|---|
| 单次生成 | 5.23s | **1.57s** |
| 空答案 | 1/10 题 | **0** |

## 3. 检索精度：关键事实命中率 60% → 100%

### 现象

id=260（军用领域收入）与 id=33（收入占比）答不出，答案称"资料中未找到"。

### 定位（逐层排除）

第一步就踩了个坑：用 `content like "%6464%"` 查 Milvus 返回 0 条，差点误判为"数据没入库"。
实际上 **Milvus 的 `like` 只支持前缀匹配**，`%x%` 这种子串写法永远匹配不到。改用 Python 侧全量扫描后确认：数据在库里。

继续定位，发现真正原因有三层：

1. **正确答案所在的分块排第 7 名，被 top6 截掉**。
   把候选池放大到 40/60/80 重测，它稳定排第 7，分数 0.9566，而第 6 名 0.9621——**几乎并列**。
   根因是 bge-reranker-v2-m3 对这批候选的分数被压缩在 0.9507~0.9900，区分度很弱。
   （注：sigmoid 是单调变换，改用 logits 不会改变名次，此路不通。）

2. **招股书大量重复段落挤占名额**。同一段内容会在"重大事项提示""风险因素""业务与技术"反复出现，
   前 6 名里常有两三条是重复段落。

3. **表格块没有语境**。表格内容是 `国防领域 | 4,627.14 | 94.34%` 这样的裸数字，
   既没有"军用领域"也没有"收入"，BM25 和向量都命中不了。

### 修改

| 修改 | 说明 |
|---|---|
| 表格前置章节标题 | `_blocks_from_content_list` 跟踪最近的 `text_level` 标题，拼到表格内容前 |
| 近重复去重 | `dedup_near()`：字符 4-gram Jaccard ≥0.75 判为重复，按重排分保留靠前的 |
| 扩大候选池 | `RETRIEVE_TOP_K` 20→80，`FUSION_TOP_N` 24→60 |
| 重排后取 8 条 | `RERANK_TOP_K=6→8`（去重后） |
| 分块更聚焦 | `CHUNK_MAX_CHARS` 900→600，`SEMANTIC_BREAK_PERCENTILE` 25→50 |
| 提示词强化 | 明确要求"通读全部资料再作答""数字必须完整列出，多期间的不得遗漏" |

### 效果

| 指标 | 前 | 后 |
|---|---|---|
| 关键事实命中率 | 60% (12/20) | **100% (20/20)** |
| id=260 | 0/4 | **4/4** |

## 4. Milvus 一致性问题（正确性缺陷，非性能）

### 现象

删除文档后 `list_documents()` 仍返回该文档；`row_count` 也仍为 7。

### 原因

Milvus 默认 `consistency_level=Bounded`，删除/写入后立即读取会读到旧数据。

### 影响

**用户上传完 PDF 立刻提问会检索不到内容**——这是会直接导致演示失败的问题。

### 修改

建集合时显式 `consistency_level="Strong"`，并在所有 `query`/`search` 调用上同样指定。
本系统语料规模在万级以内，强一致无性能负担。

### 效果

| 操作 | 前 | 后 |
|---|---|---|
| 删除后立即查询 | 仍返回 7 条 | **0 条** |

## 5. 索引噪声：重复页眉页脚

### 现象

MinerU 输出的 5998 个块中，有 1092 个 `header`（每页重复的"武汉兴图新科电子股份有限公司""招股意向书"）、
534 个 `page_number`、10 个 `footer`。

### 影响

这些块内容完全相同却重复上千次，会严重污染 BM25 词频统计，并占用向量库空间与召回名额。

### 修改

`_blocks_from_content_list` 只保留 `text` 类型块，丢弃 `header`/`footer`/`page_number`。
（`text_level` 非空的 `text` 是章节标题，作为 `title` 保留。）

### 效果

| 指标 | 前 | 后 |
|---|---|---|
| 进入索引的块数 | 5998 | 4174 |
| 噪声块 | 1636 | **0** |

## 6. 重排性能

### 修改

1. **单次前向**替代分批（候选只有十几对，分批反而增加 Python/GPU 同步开销）；
2. **按片段长度排序**后再编码，减少 padding 浪费。

### 效果

| 指标 | 前 | 后 |
|---|---|---|
| 重排耗时 | 1.00s | **0.89s** |
| 重排前向次数 | 2 批 | 1 次 |

### ❌ 失败的尝试（记录以免重蹈）

把重排的 `max_length` 从 512 降到 384，重排确实更快，但**关键事实命中率从 100% 掉回 80%**。
原因：正确答案所在分块的关键数字（"军用领域收入 6,464.51 万元…"）恰好在段落**尾部**，
截断到 384 token 后被切掉，模型看不到。**已回退到 512。**

> 教训：交叉编码器的输入截断会静默丢掉答案，必须用端到端准确率而不是单看检索指标来验证。

> 本节是"失败尝试"合集的起点，后续还有：§10.1（收 top_k 想省时间，结果只掉准）、
> §10.3（分桶重排，无效）、§10.5（换小模型，答案跌出池子）、
> §13（ONNX int8 量化，比现有 GPU 路径慢 22 倍）。
> **这些页比任何一个漂亮的指标都更值得留**——它们记录的是别人不用再踩一次的坑。

## 7. 冷启动

### 现象

评测第一题 `understand` 阶段耗时 **16.4s**，后续题目只要 0.08s。

### 原因

首次调用需要加载 bge-m3、bge-reranker-v2-m3 并初始化 CUDA 上下文。

### 修改

FastAPI 用 `lifespan` 在启动时预热（`app/main.py::warmup`）：

1. 编码一句占位文本 → 触发 bge-m3 加载；
2. `rag.tokenize("预热")` → 触发 **jieba 词典加载**；
3. 对占位候选调一次 `rerank()` → 触发 bge-reranker 加载**并完成一次真实前向**；
4. 连接 Milvus、构建 BM25。

> ⚠️ 踩过的坑：一开始只加载模型、不跑推理，重启后首个请求仍要 4.09s；
> 补上真实前向后仍偏高，再看阶段拆解发现 `understand` 从稳态 0.08s 涨到 0.578s——
> 是 **jieba 词典首次加载**被算进了首个请求（`tokenize` 是惰性导入的）。
> 加上 jieba 预热后，首个请求降到 2.99s。

### 效果

| 指标 | 前 | 后 |
|---|---|---|
| 首个请求额外开销 | 16.4s（未预热） | **2.99s（与稳态基本持平）** |
| 首个请求 `understand` 阶段 | 0.578s | **0.307s** |

## 8. 响应时间：最终实测

完整 10 题测试（本机 RTX 4060 Laptop）：

| 阶段 | 均值 | P50 | 最大 |
|---|---|---|---|
| Query 理解（本地规则） | 0.084s | 0.086s | 0.105s |
| 双路召回 | 0.034s | 0.000s | 0.095s |
| 重排 | 0.974s | 1.001s | 1.044s |
| **检索小计** | **1.092s** | 1.129s | 1.202s |
| **生成** | **1.781s** | 1.807s | 2.448s |
| **首字延迟** | 2.592s | 2.616s | 2.835s |
| **总耗时** | 2.873s | 2.900s | 3.296s |

**结论**：检索链路稳定在 ~1.1s（其中重排占 ~0.97s），生成 ~1.8s。
首字延迟稳定满足 ≤3s；完整答案时长在 2.9s 附近，受 DeepSeek 接口波动影响偶有超出。

### 无法用代码消除的抖动

单次实测中出现过一个 7.87s 的离群点（id=207）：该题答案只有 65 字，
但生成阶段耗时 6.68s，首字在 2.46s 已到达。这属于 **DeepSeek 服务端响应波动**，
本地无法优化，如实记录在测试报告中。

## 9. 已知优化路径（未采纳，保留供后续决策）

这里放的是**已经想过、评估过、但不采用**的路径。
"不采用"是当下的取舍，不等于"不够好"——动机、成本、数据都写在这里，
后续要重新决策时不必从零论证。

| 路径 | 未采纳原因 |
|---|---|
| 表格块用 LLM 生成摘要再入库 | 502 张表 × 1 次调用，索引时间与成本大幅上升，超出工单范围 |
| 换更强的重排模型 | 工单指定 bge-reranker-v2-m3，不替换 |
| 用语义缓存（向量相似问题命中） | 工单只要求 Redis 缓存，语义缓存属额外功能 |
| 把 `reasoning_effort` 也用于 RAGAS 判官的高质量模式 | 实测开推理时半数样本返回空 → NaN，反而不可用（详见测试报告） |
| 重排模型 ONNX int8 量化 | **实测比现有 GPU fp16 慢 22 倍**（19.7s vs 0.88s），且排序有偏移。已判死，非配置问题。详见 §13 |
| **降 `FUSION_TOP_N` 60 → 30** | **数据最好的一条，但动机已消失**。见 §9.1 |

### 9.1 降 `FUSION_TOP_N` 60 → 30（数据最好的一条，仍不落地）

先说清楚这条路径为什么存在：`rerank()` 实际吃的是 `rrf_fuse` 截断后的 **`FUSION_TOP_N=60` 条**，
`RERANK_POOL` 只截断输出。**送进模型的条数才是重排耗时的决定量**——这是 §10.2 当时漏测的杠杆。

**重排耗时与准确率（真跑重排，10 题均值）**：

| FUSION_TOP_N | 重排耗时 | 含答案片段仍在输入 | 含答案片段仍在最终 top-8 |
|---|---|---|---|
| 14 | 0.201s | 8/10 | 8/10 |
| 20 | 0.297s | 8/10 | 8/10 |
| **30** | **0.445s** | **10/10** | **10/10** |
| 45 | 0.667s | 10/10 | 10/10 |
| 60（当前） | 0.889s | 10/10 | 10/10 |

**端到端确认（配对设计：同题目、同轮数、同生成参数，只变这一个变量）**：

| FUSION_TOP_N | 关键事实命中 | 命中率 | 首字延迟中位数 |
|---|---|---|---|
| 60（当前） | 60/60 | 100% | 2.300s |
| **30** | **60/60** | **100%** | **1.822s** |

完整实验过程见 §10.6，可复现脚本 `scripts/bench_fusion_depth_e2e.py`。

**为什么不落地**（三条，任一条单独成立即足够）：

1. **动机已经消失。** 首字口径下 2.30s 本就达标，省下 0.478s 不再有验收压力作为收益，
   剩下的只是"更快一点"，代价却是引入一个未充分验证的参数；
2. **验证成本 > 收益。** 要真正确认 30 这个临界点，至少需扩到 30~50 题，
   覆盖表格专类、长尾数字题、多跳题，以及**答案不在文档里的干扰题**
   （看系统会不会硬答）——是半个工单的工作量；
3. **10 题全 100% 没有余量**，只能读作"没测出损失"，**不能读作"不降"**。

**若后续扩了题量、命中率无显著下降，可切 30 —— 改环境变量即可回滚**：

```
.env:  FUSION_TOP_N=30      # 启用；改回 60 即回滚，无需改代码、无需重建索引
```

> 注意切之前要确认一件事：现有《测试报告》全部数字都是在 60 下测的，
> 切换后那些数字不再对应当前配置，需要重测或至少在报告里标注。

## 10. 六组对照实验（响应时间 vs 准确率的取舍）

> §10.1~§10.5 是 2026-10-06 的原始五组；§10.6 是 2026-10-07 补的第六组，
> 补的是当时**参数理解有误、因而漏测**的那条杠杆。§10.2 的解释已同步更正。

工单要求「完整答案 ≤3 秒」与「问答准确」两条同时成立。实测下来这两条**正面冲突**，
下面是三组对照实验的结论。所有实验都固定 `temperature=0`（见 §11），排除生成随机性。

### 10.1 实验一：最终片段数 top_k 扫描（2 组 × 10 题）

| RERANK_TOP_K | 关键事实命中 | 上下文规模 | 检索耗时 | 生成耗时 | 首字 | 总耗时 |
|---|---|---|---|---|---|---|
| 3 | 75% | 3.0 条 / 1270 字 | 1.22s | 1.73s | 2.72s | 2.95s |
| 4 | 75% | 4.0 条 / 1677 字 | 1.25s | 1.75s | 2.80s | 3.00s |
| 6 | 80% | 6.0 条 / 2560 字 | 1.22s | 1.64s | 2.63s | 2.85s |
| **8（采用）** | **100%** | 7.8 条 / 3488 字 | 1.23s | 1.75s | 2.68s | 2.98s |

**结论（与直觉相反）**：检索耗时与生成耗时**与 top_k 无关**——四组全部落在噪声范围内
（检索 1.22~1.25s，生成 1.64~1.75s）。而准确率随 top_k 单调上升。

原因：重排始终跑同样的候选池（`RERANK_POOL=14`），top_k 只决定最后截几张进上下文；
而生成阶段的耗时由**输出长度**决定，不由输入上下文长度决定。

> ❌ **被数据否定的方案**：原本设想"把 top_k 收到 3~4，precision 上去、生成也会变快"。
> 实测是把准确率从 100% 砍到 75%，却一秒都没省下。**未采纳。**

### 10.2 实验二：重排输出条数 RERANK_POOL（3 组 × 10 题）

| RERANK_POOL | 关键事实命中 | 重排耗时 |
|---|---|---|
| 10 | 100% | 1.11s |
| 12 | 100% | 1.14s |
| 14（采用） | 100% | 1.09s |

**结论**：耗时与这个参数无关。但原因**不是**原稿写的 padding：

`rrf_fuse()` 先按 `FUSION_TOP_N=60` 截断，`rerank(query, fused, top_k=RERANK_POOL)` 拿到的是
**全部 60 条**，逐条打分后才把结果截到 `RERANK_POOL` 条。也就是说 **`RERANK_POOL` 只控制输出条数，
不控制送入模型的条数**。本组实验实际测的是"输出截断位置对耗时有无影响"，答案当然是无影响。

> **更正（2026-10-07）**：原稿把原因归给 padding，并据此推断"池子里有一个 992 字表格块，
> 所以 10 对和 14 对代价一样"。10 对和 14 对代价一样，是因为**两者送进模型的对数都是 60**。
> 真正能改变重排耗时的是 `FUSION_TOP_N`（送入条数），当时**没有测**。补测见 §10.6。

### 10.3 实验三：按长度分桶重排

顺着上面的分析，试了把候选按长度排序后分桶做多次前向（桶大小 3/5/14），每桶内长度接近、padding 更少：

| 桶大小 | 重排耗时（5 次中位数） |
|---|---|
| 3 | 0.701s |
| 5 | 0.667s |
| 14（等于不分桶） | 0.672s |

**结论**：三者都在噪声范围内，**分桶无效**——多跑的几次前向调用开销，抵消了 padding 的节省。
已**回退该改动**，不保留这个没有收益的配置项。

> 附带纠正一个测量错误：这组实验最初测出"不分桶 0.93s、分桶后 0.66s，提升 30%"，
> 差点当成有效优化写进记录。复核发现那次测量期间有并发进程占用 GPU。
> 用"丢弃首次 + 重复 5 次取中位数"重测后，真实值是 **0.67s**，差异消失。
> **凡是要写进报告的提速数字，必须排除并发干扰并重复测量。**

### 10.4 实验四：要不要重排（决定性对照，2 组 × 3 轮 × 10 题 = 各 60 样本）

| 配置 | 关键事实命中 | 重排耗时 | 首字 | 总耗时 | 总≤3s 达标率 |
|---|---|---|---|---|---|
| **重排开启（采用）** | **100%**（60/60，三轮均 100%） | 1.06s | 2.77s | 3.10s | 50% |
| 重排关闭 | 80%（48/60，三轮均 80%） | 0.04s | **1.71s** | **1.98s** | **100%** |

**结论**：
- 重排确实值那 0.67s——**换来 +20 个百分点**的关键事实命中率，且三轮稳定复现；
- 但它**正好吃掉 3 秒预算**：开重排总耗时 P50 约 3.0s，关掉只有 1.98s。

**这是本系统最核心的一组取舍**：`bge-reranker-v2-m3` 是工单指定组件，因此**默认开启**；
若验收方以"完整答案 ≤3 秒"为硬指标，则应关闭重排（配置项 `RERANK_TOP_K` 之外，
可在 `retrieval.retrieve(use_rerank=False)` 或前端选项里切换），代价是准确率降到 80%。

> 本节的 100% vs 80% 是**同一批题、同一判定标准、各 60 个样本**的结果，
> 非单次抽样，可复现。

### 10.5 实验五：换更小的重排模型（未采纳）

本机同时装有 `D:/模型/bge-reranker-base`（278M，约为 v2-m3 的一半），试作提速：

| 重排模型 | 重排耗时 | 该题答案片段在池中的名次 |
|---|---|---|
| bge-reranker-v2-m3 | 0.950s | 第 6、7 名（进入上下文） |
| bge-reranker-base | **0.299s** | **跌出前 14 名** |

**结论**：base 快 3.2×，但在关键题上直接把含答案的片段排到了候选池之外。**不采纳**，
继续用工单指定的 `bge-reranker-v2-m3`。

### 10.6 实验六：重排输入条数（**被 §10.2 漏掉的那条杠杆**）

#### 缘起

§10.2 的结论"耗时与候选池大小无关"是对的，但**当时的解释错了**（已于 2026-10-07 更正）。
真正的原因是：`rerank()` 收到的是 `rrf_fuse` 截断后的 **`FUSION_TOP_N=60` 条**，
`RERANK_POOL` 只截断输出。也就是说，**能改变重排耗时的参数一直没被扫过**。

#### 实测（真跑重排，10 题均值）

| FUSION_TOP_N | 重排耗时 | 含答案片段仍在输入 | 含答案片段仍在最终 top-8 |
|---|---|---|---|
| 14 | 0.201s | 8/10 | 8/10 |
| 20 | 0.297s | 8/10 | 8/10 |
| **30** | **0.445s** | **10/10** | **10/10** |
| 45 | 0.667s | 10/10 | 10/10 |
| 60（当时配置） | 0.889s | 10/10 | 10/10 |

注意 14 与 20 两行：**答案片段的 RRF 名次比它的重排名次低得多**
（有两题在 RRF 排到 20 名以外，重排后才升到第 6 名）。所以"反正重排会把对的排上来，
少送几条没关系"是错的——送不进去就永远排不上来。**30 是这道题的临界点。**

#### 端到端确认（配对设计：同题目、同轮数、同生成参数，只变 FUSION_TOP_N）

代理指标（片段进没进上下文）不等于验收指标（关键事实命中率），故按 §3.1 协议补跑：

| FUSION_TOP_N | 关键事实命中 | 命中率 | 首字延迟中位数 |
|---|---|---|---|
| 60（当时配置） | 60/60 | 100% | 2.300s |
| **30** | **60/60** | **100%** | **1.822s** |

3 轮 × 10 题两组配对，**首字延迟中位数缩短 0.478s（−20.8%），准确率无可测差异**。
`scripts/bench_fusion_depth_e2e.py` 可复现。

**结论与边界（如实标注）**：

- 这是一条**无需新依赖、不动模型、可逆**的提速路径，比换推理服务或量化重排都更划算；
- **但它不是"白捡"**：深度降过头（14/20）会直接掉到 8/10 命中，说明这条杠杆有真实代价，
  30 只是当前 10 题下的安全点；
- **10 题全部 100% 意味着没有余量去发现小回归**——"没测出损失"只能读作
  "在这 10 题、3 轮配对设计下没测出损失"，**不能读作"准确率一定不降"**。
  要更牢靠，需要扩大题量或引入英文/表格专类问题；
- **决策：不落地。** 默认配置保持 60，本条转入 §9「已知优化路径」留档。
  核心理由是**动机已消失**——首字口径下 2.30s 本就达标，省下 0.478s 不再有验收压力作为收益，
  代价却是引入一个在 10 题上没有余量验证的参数。完整处置理由与回滚方式见 §9.1。

## 11. 生成温度：消除"答案漏列数字"的随机性

测准确率时发现同一配置、同一批题的命中率在 80%~100% 之间跳动，一度怀疑检索不稳定。
定位后确认是**生成侧**问题：`llm_chat` 默认 `temperature=0.2`，
遇到"军用领域收入分别**是多少**"这类需要连列 4 个数字的问题时，
模型有时只列出 3 个，导致关键事实判定为漏项。

改为 `temperature=0.0` 后，重排开启组连续三轮 **60/60 = 100%**，完全稳定。

**结论**：事实型问答系统不应保留采样随机性，`temperature=0` 既提升准确性也让评测可复现。

> 附带教训：在 `temperature≠0` 的情况下比较两种检索配置，
> 会把生成随机性误判成检索质量差异。本项目就因此一度得出"重排没有价值"的错误结论
> （单轮 10 题、两组都是 80%）。**做检索对照实验前，先把生成固定住。**

## 12. 一个由此发现的缺陷：扫描件会静默入库 0 条

准备容错测试时，把招股书第 129 页渲染成位图、再组成无文本层的 PDF 模拟扫描件，实测：

```
pymupdf 提取文本长度：0
parse_with_fast 得到块数：0
→ 原实现会把 0 个块"成功"入库，用户得到一个静默的空知识库，还以为上传成功了
```

**修复**：`parse_pdf` 在两条解析路径都取不到文本时直接抛错，并给出可操作的提示
（`该 PDF 未提取到任何文本，可能是扫描件（无文本层）…`），
由建索引任务捕获后把状态置为 `failed` 并在前端明确展示。

**补强（2026-10-07）**：原修复只在解析层设了一道闸门，换个入口就会绕过。
现在在**写入层**（`store.index_chunks`）加了第二道：收到空分块直接抛 `ValueError`，
且**发生在按 doc_id 删除旧数据之前**——否则空解析不仅静默成功，还会顺手清空该文档已有索引。
闸门放在写入层，网页上传 / 直连 API / 批量导入脚本三条入口共用同一道关，
新加入口不会绕过。回归测试 `tests/test_empty_parse_guard.py`（6 条，含 HTTP 层）钉住它，
并用**变异验证**确认：临时移除写入层守卫后，`test_index_chunks_rejects_empty_before_touching_storage`
确实变红，恢复后全绿——即这条测试真的在拦，不是摆设。

## 13. ❌ 一次失败的技术尝试：重排模型 ONNX int8 量化

这一节记录**没做成的事**，因为它的价值不比做成的低：它把一个"看起来显然能省一半时间"的
方案彻底排除掉了，并且暴露了一个很容易犯的**基线混淆**错误。

### 想法

重排占检索耗时的大头（约 0.88s / 1.1s）。设想把 `bge-reranker-v2-m3` 导出成 ONNX 再动态
int8 量化，"0.6B 的 CrossEncoder 在 CPU 上量化后典型能快 2–3 倍，0.88s → 0.3s 量级"，
从而在不砍重排、不掉准确率的前提下压掉完整答案时长。

### 实测（真实候选池，10 题 × 60 对，`scripts/bench_rerank_onnx.py`）

| 后端 | 重排耗时（10 题均值） | 相对基线 |
|---|---|---|
| **torch + CUDA fp16（线上现状）** | **0.880s** | — |
| ONNX Runtime int8（CPU） | 19.720s | **慢 22.4×** |

补充单点探针（`n` 对 × 512 token 一次前向）：

| 批大小 | ONNX fp32 (CPU) | ONNX int8 (CPU) |
|---|---|---|
| 1 对 | 0.630s | 0.459s |
| 4 对 | 3.067s | 1.842s |
| 16 对 | 10.458s | 4.847s |

精度侧同样不划算：int8 与 fp16 的**分数最大偏差 0.145**（sigmoid 后，量级很大）、
秩相关 0.9734、**最终 top-8 平均只重合 7.3/8**，含答案片段的名次 10 题里有 3 题变化
（其中 id=260 从第 6 名掉到第 9 名，会跌出最终 8 条上下文）。

### 为什么"快 2–3 倍"和"0.88s"不能放在一起比

**两个数字来自不同的基线。**

- "CPU 量化后快 2–3 倍"——比的是 **CPU fp32**。实测确实成立：0.630s → 0.459s（1 对）、
  10.458s → 4.847s（16 对），约 2×；
- "0.88s"——是 **GPU fp16** 上的数字。

把"相对 CPU fp32 的 2×"套到"GPU fp16 的绝对值"上，结论就完全反了：
**CPU int8 比 GPU fp16 慢 22 倍**。量化省下的是 CPU 内部的开销，
它改变不了"CPU 打不过 GPU"这个量级差。

> **教训**：说"加速 N 倍"时，必须同时说清**相对谁**。凡是这类论断，先把基线的
> 设备、精度、批大小写全，再去比。本项目这一条如果只写"int8 快 2×"就写进文档，
> 下一个工程师会照着做，然后得到一个 20 秒的重排。

### 顺带说明：中文路径在这里连打了两次

1. `torch.onnx.export` 在中文路径下建临时文件失败
   （`Could not open file or directory: D:/模型/…/Constant_586_attr__value`）；
2. `onnxruntime.quantization` 的中转目录取自 `%TEMP%`，而本机 `%TEMP%` 也在中文用户名下
   （`C:/Users/雨子/AppData/Local/Temp/ort.quant.xxx`）——**只改工作目录不够**，
   还得覆盖 `TMP`/`TEMP`/`TMPDIR` 与 `tempfile.tempdir`。

两处都已固化进 `scripts/export_reranker_onnx.py`，详见《技术文档》§7.9。
**产物本身放在中文目录是可以正常加载的**（已实测），出问题的只是工具写中转文件时的路径。

### 结论

**不采纳。** 重排的提速走 §10.6 那条路（少送候选进模型），不是量化。
ONNX 产物（fp32 2.27GB / int8 570MB）与两个脚本保留在仓库里，
**默认不启用**，供后续在有 GPU 版 onnxruntime（CUDA/TensorRT provider）的机器上重新评估。
