# 过程问题记录

- 工单编号：人工智能NLP-RAG项目-LightRAG优化
- 说明：记录本工单研发过程中遇到的关键问题、根因与解决方式（均为真实调试过程）。

---

## 问题 1：Q1「发行股数/占比」答案抽取错误

- **现象**：问“本次发行股数是多少，占发行后总股本的比例是多少”，系统返回了股东/持股信息，而非发行股数与占比。
- **根因**：通用“持股/股东”抽取器（`_stake_answer`）抢先命中，把“持股比例”误当成“发行占比”。
- **解决**：新增 `_issue_answer` 抽取器，用表格行模式（“发行股数及占发行后总股本比例 1,670万股，占……25.04%”）精确匹配，并**排在通用持股抽取器之前**。
- **验证**：Q1 两系统答案均为“本次发行股数为1,670万股，占发行后总股本的比例为25.04%”，综合分 0.9647。

## 问题 2：Q4 关联方清单不完整

- **现象**：问“不存在控制关系的关联方企业有哪些”，只返回了部分关联方。
- **根因**：关联方表格跨多个切片，单块解析只能拿到片段；且表头噪声（“关联方名称/关系/…”）混入结果。
- **解决**：`_related_party_answer` **跨全部候选句聚合**清单，并用 `_RELATED_HEAD_RE` 剥离表头噪声，去重后输出。
- **验证**：Q4 综合分 LightRAG 0.9580 > RAG 0.9515。

## 问题 3：Q260「军用领域收入序列」召回缺失

- **现象**：问“报告期内来自军用领域的收入分别是多少”，图遍历召回不到承载数值的表格块，答案缺失。
- **根因**：该数值表格块未与强实体绑定，仅靠“图上实体→来源块”会漏召。
- **解决**：在 LightRAG 检索中，候选池除图召回块外，**并入 BM25 Top-60（字面）与稠密 Top-60（语义）**，实现图召回与字面/语义召回互补（`LR_KEYWORD_TOP_K`/`LR_DENSE_TOP_K`）。
- **验证**：Q260 上下文精确率由 RAG 0.25 提升至 LightRAG 0.33，综合分 +0.0167。

## 问题 4：TC-02「募投项目清单」被通用指标抽取器抢占

- **现象**：问“本次募集资金拟投资哪些项目”，返回了整张财务表原文，而非项目名称清单。
- **根因**：通用 `_metric_answer` 抽取器在抽取器链中位置靠前，抢先把含金额的表格块原样吐出。
- **解决**：新增领域清单抽取器 `_project_answer`，并把**领域清单类抽取器整体前移到通用指标类之前**（顺序：结构/字段/关系 → 领域清单 → 指标序列 → 通用兜底）。
- **验证**：TC-02 输出“仓储及物流中心、研发中心、电子商务平台、扩充产品种类和数量、其他与主营业务相关的营运资金”。

## 问题 5：募投项目表存在两种版式

- **现象**：力源信息（单列式）与兴图新科（多列式、且首个项目名跨行断开）的募集资金运用表解析结果不一致。
- **根因**：单列式表头为“序号 项目名称 计划总投资”，多列式表头含“项目名称 项目总投资 募集资金投资”，且首个项目名被拆到多行（“基于云联邦架构的军用视频指”/“1 20,658.33 …”/“挥平台升级及产业化项目”）。
- **解决**：`_proj_table` 以“按行解析编号表格”为主，跨行断名按前后行拼接补齐；表格不可得时依次退化为“引号罗列”（`_proj_quoted`）与“后缀模式”（`_proj_narr`）两种叙述型解析。
- **验证**：两家公司募投项目均能正确汇总。

## 问题 6：TC-08 域外问题「假通过」

- **现象**：功能测试 TC-08（域外天气问题）原先被判定通过，但传统 RAG 实际返回了“适合中国市场”的无关业务片段。
- **根因**：测试断言过宽，未检查是否“显式拒答”。
- **解决**：把断言改为**检查拒答短语**（“未在 / 未找到 / 无法 / 换一种问法 / 不相关”）。修正后：LightRAG 正确拒答（PASS），传统 RAG 返回无关片段（FAIL）。
- **验证**：功能测试 RAG 9/10、LightRAG 10/10，该差异如实反映图结构检索的域外鲁棒性。

## 问题 7：冷/热响应时间口径不对称

- **现象**：性能基准中 LightRAG 看似明显更快，疑似口径不公。
- **根因**：`_clear_cache` 只清了 RAG 的向量缓存，未对称清 LightRAG 的查询缓存，导致两者冷/热不可比。
- **解决**：`_clear_cache` 对两系统**对称清理**：RAG 清 `HybridRetriever._vec_cache → VectorRetriever.Embedder._cache`；LightRAG 清 `LightRAGRetriever._qcache + Embedder._cache`。
- **验证**：冷启动 RAG 2.33s / LightRAG 2.21s，差异合理（源于 LightRAG 的多路查询批量编码优化）。

## 问题 8：图证据在前端不显示（键名不一致）

- **现象**：LightRAG 检索证据中的“实体/关系/主题”在界面上空白。
- **根因**：检索器输出的键为 `source/target/title`，而界面渲染按 `src/tgt/name` 读取，键名不匹配。
- **解决**：统一 `app.py` 渲染使用检索器实际输出的键（`source`/`target`/`type`/`desc`、`title`/`summary`）。
- **验证**：界面正常展示图证据（见 `演示/07_full_conversation.png`）。

## 问题 9：本地 1.5B 模型 JSON 输出不稳定

- **现象**：LLM 抽取返回残缺/带代码块的 JSON，直接 `json.loads` 频繁失败。
- **根因**：小参数量模型指令遵循弱，输出格式漂移。
- **解决**：`_parse_json_loose` **三级容错解析**：① 剥离 ```json 代码块后直接解析；② 平衡括号截取第一个完整对象；③ 正则兜底逐条抽取 `{...}` 对象；并对字段名做多别名兜底（name/ame/实体、type/ype/类型…）。
- **验证**：150 块 LLM 抽取累计产出 351 条，未因解析失败中断。

## 问题 10：主题（社区）粒度过粗

- **现象**：早期用“连通分量”做主题，招股说明书实体图高度连通，全图被并成 1~2 个巨簇，全局检索失去区分度。
- **根因**：连通分量不适合高连通图。
- **解决**：改用 **Louvain 社区发现**（`networkx.community.louvain_communities`，seed=42），回退贪心模块度、再回退连通分量；并对全局检索贡献做 `1/(1+ln(1+size))` 衰减。
- **验证**：生成 20 个粒度适中的主题，全局检索命中主题可用于概念级扩展。

---

## 小结

上述问题覆盖了**图谱构建（类型/抽取/主题）**、**检索召回（表格块漏召/融合）**、**答案抽取（抽取器冲突/版式差异）**、**评估口径（冷热对称/断言）**与**前端展示**五个层面。解决后：功能测试 LightRAG 10/10，RAGAS 综合分 RAG 0.9024 / LightRAG 0.9043，响应时间均 < 3s。
