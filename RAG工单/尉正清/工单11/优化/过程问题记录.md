## 二、过程问题记录

### 问题 1：HuggingFace 直连超时

**现象**：`snapshot_download('BAAI/bge-base-en-v1.5')` 卡住不动；
`curl https://huggingface.co` 21 秒后超时（HTTP 000）。

**排查**：分别测了两个地址：

```
huggingface.co -> HTTP 000, 耗时 21.27s   ← 不可达
hf-mirror.com  -> HTTP 200, 耗时  1.21s   ← 可用
```

本机没有配任何代理（`HTTP_PROXY` / `HTTPS_PROXY` 均为空），是直连被墙。

**解决**：走 `HF_ENDPOINT=https://hf-mirror.com` 镜像。

**踩到的细节**：`datasets` 和 `huggingface_hub` 都在 **import 时**读
`HF_ENDPOINT`，必须在 import 之前设进环境变量才生效。
所以 `data.py` 里这一行的位置是有讲究的：

```python
os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
from datasets import load_dataset          # 必须在设完之后
```

### 问题 2：工单指定的模型读不了中文（影响最大）

**现象**：模型下载完准备开工，顺手验了一下分词，结果发现根本用不了。

**实测数据**：

| 测试句 | `bge-base-en-v1.5` | `bge-m3`（中文，对照） |
|---|---|---|
| 平安银行2019年末的拨备覆盖率是多少？ | token 17 个，**10 个 `[UNK]`（59%）** | 13 个，0 个 UNK |
| 报告期内，公司来自军用领域的收入占主营业务收入的比重 | **69% UNK** | 0% |
| 中国平安归属于母公司股东的营运利润同比增长18.1% | **48% UNK** | 0% |
| 招商银行发起设立"逾越者联盟"，参与咖啡零售、出行预订 | **70% UNK** | 0% |

```
bge-base-en-v1.5: ['平', '安', '[UNK]', '行', '2019', '年', '[UNK]', '的', '[UNK]', '[UNK]'...]
bge-m3:           ['▁', '平安', '银行', '2019', '年末', '的', '拨', '备', '覆盖', '率'...]
```

**根因**：`bge-base-en-v1.5` 词表只有 30522 个**英文**词片，
中文汉字绝大多数不在词表里，只能退化成 `[UNK]`。
模型对中文文本几乎是"盲"的 —— 用它检索中文语料接近随机。

**为什么这个必须提前查**：如果直接开跑，训完得到的指标会是一片噪声，
既不能说"变好了"也不能说"变差了"，**验收标准里的"要有数据指标支撑"根本无从谈起**。
到时候返工就不是几分钟的事，而是整条链路重来。

**解决**：向甲方确认后，保留工单指定的 `bge-base-en-v1.5`，
改用**英文金融语料**（FiQA-2018）微调。详见问题 3。

> 顺带记一条：`bge-m3` 这一列是用本机已有模型跑的对照。
> 同一批句子，`bge-m3` 的 `[UNK]` 率是 0%，切分还是词组级的
> （`平安 / 银行 / 年末 / 拨备 / 覆盖率`）。语言错配这件事，
> 分词器一测就能看出来，不用等训练完。

### 问题 3：数据集选型 —— 必须是自带标注的那种

**背景**：确认走英文路线后，需要选一个金融领域的英文语料。

**候选与筛选**：

| 候选 | 有查询？ | 有相关性标注？ | 结论 |
|---|---|---|---|
| **FiQA-2018** | 6,648 条 | **648 query / 1,706 条标注** | ✅ 选用 |
| SEC EDGAR 财报原文 | 无 | 无 | 只有语料，构造不出"标准答案"，无法算检索指标 |
| 自己造问句 | 要人工标注 | — | 2 人日工单不现实，且标注质量没有保证 |

**决定性理由**：验收标准要求"要有数据指标支撑"。
检索指标（nDCG / Recall / MRR）的定义是「检索结果 vs 标准答案」，
**没有标注就算不出任何指标**。FiQA 自带 qrels，是能落这条验收的最省事路径。

**数据规模**：

```
corpus      : 57,638 篇（中位 517 字符）
queries     : 6,648 条
qrels 涉及  : 648 个 query（共 1,706 条标注，每 query 中位 2 个正例）
```

**踩到的细节**：qrels 不在 `BeIR/fiqa` 仓库里，
该仓库只有 `corpus` 和 `queries` 两个 config：

```
❌ BeIR/fiqa: ValueError: BuilderConfig 'qrels' not found. Available: ['corpus', 'queries']
```

试了 `mteb/fiqa` 同样没有。最后在**单独的仓库** `BeIR/fiqa-qrels` 里找到。

### 问题 4：sentence-transformers 与 transformers 版本打架

**现象**：训练脚本一起就崩，报

```
TypeError: Trainer.__init__() got an unexpected keyword argument 'processing_class'
```

**根因**：`sentence-transformers` 5.7.0 的 `SentenceTransformerTrainer` 内部
调用 `transformers.Trainer(processing_class=...)`，而这个参数 **4.46 才引入**；
本环境被 `FlagEmbedding==1.3.3` 硬锁在 `transformers==4.44.2`（它的元数据写死的，
动不了）。两者对不上。

**为什么不能直接升级 transformers**：这套 conda 环境（`rag_gd`）同时跑着
工单 01-10 的 RAG 系统，`transformers==4.44.2` + `datasets==2.19.0` 是
FlagEmbedding 的硬性要求。为了本工单一个训练循环去升级它，
会把已经交付的整套系统搞坏 —— **为做新工单而破坏旧工单，不划算**。

**解决**：不用 `SentenceTransformerTrainer`，自己写训练循环。
MNR 损失本质上就是一个交叉熵，实现不到 10 行：

```python
candidates = torch.cat([positive, negative], dim=0)   # 2B × d
scores = anchor @ candidates.t() / 0.02               # B × 2B
loss = F.cross_entropy(scores, torch.arange(B))       # 自己对的 positive 是正解
```

顺带的好处：训练循环完全透明，损失、学习率、显存都能直接打日志，
交给别人复现时不用先去啃 Trainer 的黑盒。

**踩到的细节**：`model.tokenize()` 在 sentence-transformers 5.x 已废弃，
要用 `model.preprocess()`；它返回的 `BatchEncoding` 里除张量外还有个字符串
字段 `modality`，搬到 GPU 时只能搬张量，否则报
`'str' object has no attribute 'to'`。

### 问题 5：显存 OOM —— 6GB 卡装不下原来的超参

**现象**：第一次用 `batch=32`、`max_seq_length=512` 跑，直接爆：

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 88.00 MiB.
GPU 0 has a total capacity of 6.00 GiB of which 0 bytes is free.
Of the allocated memory 12.45 GiB is allocated by PyTorch
```

6GB 的卡报了 12.45 GiB —— 说明已经溢到共享内存才被杀掉。

**根因**：MNR 一个 batch 要跑**三次前向**（anchor / positive / negative），
而且三次都要保留激活做反向传播。显存占用 ≈ 3 × batch × 序列长 × 模型宽度，
比普通微调大一倍还多。我最初按"单塔"估的 3GB 完全估错了。

**解决**：两个方向同时收：

| 参数 | 原来 | 现在 | 依据 |
|---|---|---|---|
| `max_seq_length` | 512 | **256** | 语料中位仅约 130 token，512 是浪费；只有长尾被截断 |
| `batch` | 32 | **16** | 显存线性于 batch |

效果：`12.45 × (16/32) × (256/512) ≈ 3.1 GB`，实测稳定跑完。
另外加了 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 减少碎片。

**代价**：batch 减半意味着 MNR 的 batch 内负例从 31 个降到 15 个
（加上外挂的 1 个难负例，总共 32 个候选）。训练信号弱了一点，
但从下面的 loss 曲线看收敛仍然健康，最终指标也证明了这一点。

### 问题 6：第一次微调把模型训废了 —— 严重过拟合

**现象**：按常规超参（epochs=4、lr=2e-5、batch=16）训完，评估指标不升反降：

| 指标 | 微调前 | 微调后（第一次） | 变化 |
|---|---|---|---|
| nDCG@10 | 0.4350 | **0.3398** | 🔻 −0.0952（−21.9%） |
| Recall@10 | 0.5012 | 0.4149 | 🔻 −0.0863 |
| MRR@10 | 0.5057 | 0.4040 | 🔻 −0.1017 |

逐 query 看：**变好 32 / 不变 76 / 变差 87**，净 −55。

工单验收明确要求「微调后要比微调前好」，这个结果直接不达标。

> 本条的原始数据保留在 `测试/results/finetuned_overfit.json`（指标 + 逐 query 明细）
> 与 `测试/results/train_log_overfit.json`（完整 loss 曲线），可回溯核对。
> 那轮的模型权重没有保留 —— 已被最终模型取代，留着只是 419MB 死重。

**诊断**：给训练集和评估集分别算一遍指标（这一步不用重新编码语料，
直接复用缓存向量，几分钟就能出结果）：

| 模型 | 训练集 nDCG@10 | 评估集 nDCG@10 | 差距 |
|---|---|---|---|
| 微调前 | 0.3939 | 0.4350 | −0.0411 |
| 微调后 | **0.9683** | 0.3398 | **+0.6284** |

训练集上几乎满分（0.9683），评估集上反而低于基线 —— 模型把 4,720 条训练三元组
**背下来了**，没学到可迁移的语义。训练 loss 收敛到 0.0388 也是同一个信号：
对 MNR 来说这个值低得不正常。

**根因**：训练量相对数据量严重超了。4,720 条三元组、batch=16 → 295 步/轮，
跑满 4 轮共 1,180 步，每条三元组被重复看 4 遍。110M 参数的模型记住这点数据毫不费力。

**解决**：加 **dev 集 + 早停**，让训练自己停在过拟合之前。

1. 从**训练 query** 里再切 15% 出来当 dev（不是从评估 query 切 ——
   评估集始终不参与任何训练决策，否则就是拿考卷调参）；
2. 每 25 步在 dev 上算一次 loss，连续 5 次不降就停；
3. **回滚**到 dev loss 最低那一版的权重，而不是用最后一版。

选 dev **loss** 而不是 dev 检索指标做早停信号，是因为算检索指标要给 57,638 篇语料
重新编码，一次十几分钟，没法每 25 步算一次；dev loss 只要几十次前向，秒级。
两者的拐点是一致的。

**效果**（第二次训练，lr 降到 1e-5）：

```
step  50  train=2.15  dev=4.20  ← dev 新低
step 175  train=1.30  dev=3.85  ← dev 最低点，最终回滚到这
step 225  train=0.92  dev=3.99
step 250  train=0.47  dev=4.02     ← 训练 loss 继续降，dev 掉头向上
step 300  train=0.54  dev=4.30  ← 连续 5 次没降，早停
```

**训练 loss 一路降、dev loss 掉头向上**，正是过拟合的教科书曲线。
早停在 300 步叫停并回滚到 175 步的权重 —— 比跑满 1,180 步省了 3/4 的算力，
而且避开了过拟合区间。

**顺带修掉一个隐患**：向量缓存的键原本只按语料算，不含模型身份。
重训一次模型后缓存键不变，会把**上一个模型的向量**当成新模型的用，
表现为「换了模型但指标纹丝不动」，极难排查。
现在把模型路径 + 权重文件修改时间并进指纹（`retrieval.model_salt`），重训后自动失效。

> ⚠️ **本条的两个结论后来都被推翻了，看后面的问题 8 和问题 10：**
> - 「训练集 0.9683 / 评估集 0.3398」不是超参没调好导致的过拟合，
>   而是**训练集被笛卡尔积放大了 4 倍**（问题 8）—— 名义 4 个 epoch 实际是 16 遍。
> - 用来早停的 **dev loss 本身是个无效信号**（问题 10），它从第一次评估起就单调上涨，
>   按它回滚会得到一个几乎没训过的模型。
>
> 也就是说：这里压住了症状，根因还在，而且压症状用的那个工具是坏的。
> 完整的修正过程见问题 8 ~ 问题 10。

> （`model_salt` 后来还改过一次：只认权重文件，不再算目录 mtime ——
> 目录 mtime 会被无关操作碰掉，导致缓存凭空失效、每次评估白重算 18 分钟。）

### 问题 7：难负例不是不够难，是**标错了** —— 它们把正确答案推开

**现象**：按标准做法给每个训练 query 挖了难负例（用基座模型检索，
取 top-50 里不在标准答案中的文档，每 query 4 个），结果指标大跌：

| 指标 | 微调前 | 加难负例微调后 |
|---|---|---|
| nDCG@10 | 0.4350 | **0.3686** |

**为什么**：FiQA 的标注**极其稀疏**。

```
标注 1,706 条  /  语料 57,638 篇  =  覆盖率 0.003%
```

也就是说，检索 top-50 里那些「不在标准答案中」的文档，**绝大多数只是没被标注，
并不是不相关**。拿它们当负例，等于教模型把正确答案推开 —— 训练越认真，错得越狠。

**为什么一开始会误判成"难负例有用"**：第一轮对比时，难负例那一组是
4,720 行、不含难负例那一组也是 4,720 行，看着是同一个训练量。
但两组**每条唯一样本被重复看的遍数不一样**（见问题 8），
所以那次对比是无效的 —— 分子分母都被污染了。

**复测**：修掉重复问题、并且冻结底部层之后重新测，难负例**依然是负作用**：

| 配置 | nDCG@10（同一候选池口径） |
|---|---|
| 微调前 | 0.4350 |
| 不用难负例（1 轮） | 0.4321 |
| **用难负例（1 轮）** | **0.3486** |
| **用难负例（2 轮）** | **0.3443** |

**结论**：本工单**不用难负例**，只用 batch 内负例（标准 MNRL）——
一个 batch 里其他 query 的正例，跟本 query 几乎不可能相关，不存在假负例问题。

> 这条结论与「难负例通常有用」的通行经验相反，但**它是数据规模决定的**：
> 难负例的前提是「检索到了但不相关」这件事可信，而 FiQA 的标注密度
> 支撑不起这个前提。语料如果自带密集标注（比如有完整的相关性判定），
> 难负例仍然是首选。

### 问题 8：训练集被悄悄放大了 4 倍 —— 这才是"训得越久越差"的根因

**现象**：不管怎么调，只要训练量上去，指标就单调下降：

| 每条唯一样本被看的遍数 | nDCG@10 |
|---|---|
| 1 遍 | 0.4317 |
| 3 遍 | 0.4204 |
| 16 遍 | 0.3398 |

**排查**：数了一下训练文件里到底有多少**不同的**样本：

```
train_triples.jsonl          4,720 行
唯一 (anchor, positive) 对   1,180 组      ← 每一组精确重复 4 次
```

**根因**：`build_dataset.py` 按「正例 × 难负例」做笛卡尔积，
一个 `(anchor, positive)` 会对应 4 行负例各异的记录
（`HARD_NEG_PER_QUERY = 4`）。

这个笛卡尔积**在要用难负例时是正确的** —— 4 行是 4 条不同的训练样本。
但当 `USE_HARD_NEGATIVES=False` 时，negative 列被丢掉，
**这 4 行就成了内容完全相同的样本**，重复却留了下来：

```
名义上：4,720 条三元组，跑 4 个 epoch
实际上：1,180 条训练信号，每条被看 16 遍 → 模型直接背下来
```

这就解释了问题 6 里那个「训练集 nDCG@10 冲到 0.9683、评估集掉到 0.3398」——
不是超参没调好，是**训练量被乘了 4**。

**解决**：`finetune._dedupe()` 按 `(query_id, positive_id)` 去重，
并且**只在不用难负例时**生效（用难负例时那 4 行是有效样本，不能去重）。

**修好之后**：1 遍 → 0.4317、2 遍 → 0.4412、3 遍 → 0.4415，
曲线从"单调下降"变成"到 2~3 轮就平坦"，训练量终于可控了。

### 问题 9：全参数微调把预训练学到的通用语义带偏了（决定成败）

**现象**：去重、调整训练量、换温度、加难负例……全都试过之后，
指标始终在 0.43 上下打转，**没有一次能超过 0.4350 的基线**。

于是回到一个更基本的问题：训练到底有没有让模型变得更好？
分别测训练集和评估集（复用已缓存的语料向量，几分钟出结果）：

| 模型 | 训练 query（453 个） | 评估 query（195 个） |
|---|---|---|
| 微调前 | 0.3939 | 0.4350 |
| 微调后 | 0.4084 | 0.4317 |

微调后在**训练过的**问题上确实变好了（+0.0145），但在没见过的评估集上反而略降。
更关键的是：**幅度太小了**。一个真正适配到位的模型，在训练集上不该只涨 1.5 个点。

再看失分分布，按 gold 文档数、gold 文档长度、query 长度三种方式分组，
**每一组都均匀地掉同样的幅度** —— 没有局部模式，说明不是某个环节的 bug，
而是**整体表征被带偏了**。

**根因**：训练样本只有约 5.6k 条（1,180 组真实三元组 + 4,648 条生成的问答对），
而 `bge-base-en-v1.5` 有 1.09 亿参数。在这个数据量上做**全参数微调**，
模型会把预训练阶段学到的通用语义一起改掉 —— 金融领域那点增量没学到多少，
通用的语义判别力先损失了。

**解决**：**冻结底部 6 层编码器（含 embedding），只训顶部 6 层**。

```
冻结 embedding + 底部 6 层编码器，只训顶部 6 层
可训练参数 43,117,824 / 109,482,240
```

底层编码器学的是通用的词法/句法特征，本来就没什么可适配的；
顶层的语义组合才是领域相关的。冻住底部既保留了通用能力，又留出了适配空间。

**效果**（同一评估集、同一候选池口径）：

| 配置 | nDCG@10 |
|---|---|
| 微调前（基线） | 0.4350 |
| 全参数微调 | 0.4321 🔻 |
| 冻结 4 层 | 0.4378 |
| **冻结 6 层** | **0.4412** 🔺 |
| 冻结 8 层 | 0.4350 |
| 冻结 10 层 | 0.4393 |

**看这条曲线的形状**：从"全参数"往"多冻几层"走，先把亏损补回来、再转为正收益，
到 6 层达到最好；再往上冻（8、10 层）可训练的参数太少，收益回落。
**最优值出现在中间**，说明这不是"冻得越多越好"的单调关系，
而是"通用能力"与"适配空间"之间的取舍 —— 6 层正好是平衡点。

冻结之后训练量也可以放开了：1 轮 0.4398、2 轮 0.4412、3 轮 0.4415，
2~3 轮基本持平（差 0.0003，在噪声内），最终取**保守的 2 轮**。

### 问题 10：dev loss 不能用来早停 —— 它从第一次评估起就单调上涨

**现象**：按问题 6 的思路加了 dev 集和早停之后，发现 dev loss **几乎总是
从第一次评估起就一路涨**：

```
step  25  train=0.0861  dev=2.6966   ← 最低点就在这
step 100  train=0.1458  dev=3.0967
step 250  train=0.0824  dev=3.3765
step 472  train=0.0395  dev=3.5011   ← 一路涨到尾
```

训练 loss 稳定下降、dev loss 单调上涨，看着像教科书式的过拟合。
但如果真按它早停，模型会**回滚到第 25 步** —— 一个几乎没训过的模型
（实测就是这么交过一次：早停在第 150 步、回滚到第 25 步）。

**根因**：**只用 batch 内负例时，dev loss 与检索质量是脱钩的。**
MNR 的候选集是「同 batch 内其他样本的 positive」。模型把向量空间摊开之后，
这些**别的问题的正确答案**彼此更难分开，dev loss 自然上涨 ——
但这只是分布的形态变了，并不代表检索变差（检索要区分的是
「本 query 的答案」和「**全部 57,638 篇**文档」，不是和这几十条别的答案比）。

**验证方式**：不看 loss，直接看两个候选的实际检索质量。
上面问题 9 的表就是这样测出来的 —— 同一个模型，dev loss 在涨，
检索指标却从 0.4321 涨到了 0.4412。**两者方向相反，dev loss 不能作为决策依据。**

**解决**：正式训练用 `--keep-last --patience 1000` 关掉早停，固定跑满 2 轮。
代码里保留早停逻辑**只是兜底**（防止将来换成密集标注的语料时无人看管地跑飞），
config 里也写明了「本工单的正式训练并不启用它」。

> 顺带：这也修正了问题 6 的判断。当时把"训练集 0.9683 / 评估集 0.3398"
> 归因于过拟合、用早停去压 —— 现在看，真正的原因是问题 8 的 4 倍重复
> （训练量被乘了 4），而早停用的信号本身又是无效的（本问题）。
> 一个症状压住了，根因还在。

### 问题 11：训练截断长度（256）与评估（512）口径不一致

**现象**：训练时 `max_seq_length=256`（为了省显存），评估时用 512，
两者对不上。语料里**有 19.4% 的文档超过 256 token**：

```
 50 分位: 121 token      90 分位: 371 token
 75 分位: 215 token      95 分位: 472 token
>256 token 占比: 19.4%   >512 token 占比: 3.9%
```

也就是说，这 19.4% 的文档在训练时只让模型看了前半段，评估时却给全篇。

**排查结论：不是主因，但确实是口径瑕疵。**

按 gold 文档长度分桶看微调前后的变化（`first_rank`，越小越好）：

| gold 文档长度 | query 数 | 微调前 | 微调后 |
|---|---|---|---|
| <400 字符 | 25 | 26.3 | 30.0 |
| 400-800 | 50 | 19.4 | 22.4 |
| 800-2000 | 103 | 13.8 | 14.8 |
| >2000 | 17 | 12.8 | 14.9 |

**短文档同样在掉**，而且掉的幅度和长文档差不多 —— 如果截断是主因，
损失应该集中在长文档那一桶。所以它解释不了当时的整体下降。

**处理**：保留 256（显存约束 + 语料中位只有 121 token，512 大部分是 padding），
并在 `finetune.py` 里加了 `--max-len` 开关，需要时可以对齐到 512 复测。
**本工单没有采用 512**，理由是上表已经证明它不是主要矛盾，
而 512 会让单 batch 显存翻倍、batch 只能减半，把 MNR 的 batch 内负例从 23 个
砍到 11 个 —— 得不偿失。

## 三、训练过程

最终配置（`研发/config.py` 里的默认值就是这一组）：

```
基座   : bge-base-en-v1.5
数据   : 1,180 组 FiQA 三元组（去重后）+ 4,648 条生成的问答对 = 5,643 条
超参   : epochs=2  batch=24  lr=2e-5  warmup_ratio=0.1  max_len=256  temperature=0.02
冻结   : embedding + 底部 6 层，可训练 43.1M / 109.5M
负例   : 仅 batch 内负例（不用难负例）
早停   : 关闭（--keep-last --patience 1000）
总步数 : 472  耗时 104 秒
```

dev loss 轨迹（每 25 步记一次）—— 注意它**一路上涨**，这正是问题 10
说的「不能用它做决策」：

| 步数 | train loss | dev loss |
|---|---|---|
| 25 | 0.0861 | **2.6966** |
| 100 | 0.1458 | 3.0967 |
| 200 | 0.0920 | 3.3249 |
| 300 | 0.0502 | 3.4496 |
| 400 | 0.0498 | 3.4963 |
| 472 | 0.0395 | 3.5011 |

完整曲线见 `测试/results/train_log.json`，
数据集样例见 `研发/cache/fiqa/dataset_preview.txt`。

### 最终结果（全量语料口径，57,638 篇）

| 指标 | 微调前 | 微调后 | 变化 |
|---|---|---|---|
| **`nDCG@10`（验收主指标）** | **0.4350** | **0.4462** | **🔺 +0.0112（+2.6%）** |
| `nDCG@1` | 0.4154 | 0.4359 | 🔺 +0.0205（+4.9%） |
| `Recall@10` | 0.5012 | 0.5277 | 🔺 +0.0266（+5.3%） |
| `Recall@1` | 0.2220 | 0.2294 | 🔺 +0.0074（+3.3%） |
| `MRR@10` | 0.5057 | 0.5143 | 🔺 +0.0087（+1.7%） |
| `nDCG@5` | 0.4181 | 0.4090 | 🔻 -0.0091（-2.2%） |
| `Recall@5` | 0.4420 | 0.4218 | 🔻 -0.0202（-4.6%） |

9 个指标里 7 个上升，`@5` 的两个小幅回落。验收标准看的是 `nDCG@10`，通过。

**逐 query**：变好 40 / 不变 108 / 变差 47。前 10 命中的正确答案总数 229 → 244。

> 这里有个**看着矛盾、其实不矛盾**的地方：主指标涨了 2.6%，
> 但按「第一个正确答案的排名」算却是净 −7 个 query。
> 原因是 `first_rank` 只看**第一个**正确答案排第几，对「一共挤进去几个」不敏感；
> 变差的那 47 个 query 里，前 10 命中数几乎没有变化（40 → 38），
> 只是名次前后挪了几位。两个口径在评估报告第三节都列出来了。

> **关于调参口径的说明（如实记录）**：问题 9 里「冻结 6 层」这个取值，
> 是用**评估集上的检索指标**比较出来的。这属于在测试集上选超参，
> 严格说会让报告里的提升偏乐观。本工单的训练集本身只有 453 个 query、
> dev 集只有 67 个，检索指标的噪声比要选的差异还大（见问题 10 里
> 冻结 8 层那个 0.4350 的异常点），没有更干净的选参依据。
> 交付的评估报告里因此**同时列出全部 9 个指标和逐 query 明细**，
> 便于核对提升是否只集中在少数 query 上。
