# 多路召回说明

> 日期：2026-09-17
> 状态：已实现并**实测增益**（结论与直觉相反，见 §五）
> 开关：`RAGLORA_MULTI_RECALL=1`（默认开）

---

## 一、三路的分工

```
问题 ──┬─→ 路1 向量库（Milvus/Qdrant）  语义相似
       ├─→ 路2 MySQL  kb_documents      文档级结构匹配
       └─→ 路3 Neo4j  Article 图节点     法条关系（精确 / 引用）
                    ↓
              RRF 融合 ──→ 精排 ──→ 生成
```

**三路不是「同一个东西查三遍」，而是各补对方短处**：

| 短板 | 由哪一路补 |
|---|---|
| 向量检索**不擅长精确定位**（问「民法典第五百七十七条」，它返回第二百四十七条、第一千零五十七条 —— 数字形近、语义相近，但**不是那一条**） | 图谱路精确命中 |
| 向量检索**答不出「某文档在不在库」**（只会返回一堆弱相关条文） | MySQL 路直接判定，还能识别**语料缺口** |
| 图谱路**没有正文**（只存关系） | 回向量库按 `(law_name, article_no)` 补齐 |

## 二、⚠️ 设计假设被实测推翻（必读）

设计文档 §3.4 原写：「法条间的『依据《X》第Y条』是强模式，正则抽取可达高准确率、成本近零」。

**实测结果：这个模式在本语料中不存在。**

| 抽样 1500 条法律 chunk | 覆盖率 |
|---|---:|
| 「依据《X》第Y条」 | **0%** |
| 剥掉自我标识后的跨法引用 `《X》` | **1.9%**（29/1500，共 38 处） |
| 含《书名》的 chunk | 100%（但**每条开头的 `《本法名》第X条规定，` 是它自身的标识，不是引用**） |

也就是说：按原假设建图会得到一个**接近空的图**。

**因此改为两类边**：

| 边类型 | 含义 | 覆盖 | 实测条数 |
|---|---|---:|---:|
| `CITES` | 跨法引用（正文里提到其它法律） | 稀疏 | **365** |
| `ADJACENT` | 同法相邻条文（第N条 ↔ 第N+1条） | **100%** | **14137** |

> 176 部法律条文编号**全部连续**，所以相邻边能建满。

## 三、图谱路的适用范围（有限制）

| The collection | 能否建图 | 原因 |
|---|---|---|
| `kb_legal` | ✅ 14313 节点 | 按「第X条」切分，带 `law_name` / `article_no` |
| `kb_medical` | ❌ **0 节点** | PDF 指南按段落切分，**没有条文号**，无法做图 |

**这不是 bug，是语料结构差异。** 代码会在遇到无条文号的语料时明确记 warning 并返回 `note`，
不会假装「建了图但没生效」。

## 四、实测踩到的三个坑

### 坑 1：中文数字字符类漏了「千」

```python
# ✗ 漏「千」
re.compile(r"第([一二三四五六七八九十百零〇\d]+)条")
# ✗ 结果：'第一千一百四十七条' 解析不出条号（返回空列表）
```

**影响面被低估过**：民法典共 **1260 条**，意味着**所有 1000 条以上的法条图谱路静默失效**
—— 不报错、不告警，只是查不到。修复后「指名法条」类问题命中率从 **30% → 100%**。

### 坑 2：文档名不能靠正则「猜」

```python
# ✗ 初版：贪婪匹配把整句当成了文档名
r"([一-龥]{2,20}(?:法|规定|办法|指南))"
#   输入「劳动法对试用期是怎么规定的」-> 抽出「劳动法对试用期是怎么规定」
```

改为**与库中真实文档名做包含匹配**（库里只有 178 份文档，逐个比对成本可忽略，且不会猜出不存在的名字）。

### 坑 3：跨路的 `source` 口径不一致

| 路 | `source` 的值 |
|---|---|
| 向量路 | **文件名** `中华人民共和国民法典.txt` |
| 图谱路 | **法律名** `中华人民共和国民法典`（无扩展名） |

直接比对会让「指名文档加分」**静默失效**，图谱路命中排不上来。
修法是加归一化函数 `_bare_name()` 做双向包含匹配。

### 坑 4（设计缺陷，非实现 bug）：文档限定路不能作为独立一路计票

初版把「在指名文档范围内再检索一次」作为**独立一路**参与 RRF。但它是
「向量检索 + source 过滤」，与路 1 高度重叠 —— **同一条会在两路各得一次票、分数翻倍**，
实测把图谱路的精确定中**挤出了前三**（问「民法典第五百七十七条」时图谱命中从第 1 位掉到前 3 之外）。

已改为：**只对「向量 + 图谱」两路做 RRF**，文档限定路的作用降为
①**补充**路 1 漏掉的命中 ②对指名文档内的命中**加分**（`DOC_BOOST=1.5`）。

## 五、实测增益（关键：结论与直觉相反）

### 5.1 在现有 43 题 QA 集上：**没有改善**

```bash
python scripts/eval_multirecall.py --topk 5
```

| 角色 | 题数 | 单路命中 | 多路命中 | 变化 |
|---|---:|---:|---:|---:|
| medical | 20 | 100.0% | 100.0% | +0.0pp |
| legal | 20 | 85.0% | 85.0% | +0.0pp |
| **合计** | **40** | **92.5%** | **92.5%** | **+0.0pp** |

**多路改善 0 题，多路变差 0 题。** top-20（进精排的候选池）结果同样如此。

原因：向量路单独就已达到 92.5%，而剩余 7.5% 的失败题是**语料缺口**
（劳动法 / 劳动合同法不在 176 部法律中），**任何检索路径都救不了**。

### 5.2 在「指名法条」类问题上：**提升 70 个百分点**

现有 QA 集**没有**「某法第X条规定了什么」这类问题 —— 而那正是图谱路的用武之地。
随机抽 10 条民法典真实条文构造问题：

| 场景 | 单路向量 | 多路召回 |
|---|---:|---:|
| 「《民法典》第X条规定了什么？」 | **3/10 = 30%** | **10/10 = 100%** |

**这才是图谱路的实际价值边界**：它不是提升「语义问答」的召回率，
而是让**精确定位**成为可能。

### 5.3 开销

| | 单路 | 多路 |
|---|---:|---:|
| 平均耗时 | 114 ms | 117 ms（**+2%**） |

> ⚠️ 初版得出过「多路快 70%」的**错误结论** —— 因为先跑的那一路承担了 bge-m3 的模型加载耗时。
> 脚本已加预热，数字才是可信的。**这类测量假象比功能 bug 更危险：它会让你以为优化生效了。**

## 六、结论：这个特性该怎么讲

**诚实的结论是：多路召回的价值是「补能力」，不是「提指标」。**

- ✅ **让系统能回答以前答不了的问题**（指名法条、文档在不在库）
- ✅ **能识别语料缺口**（MySQL 路判定「劳动法未收录」，可用于防幻觉）
- ❌ **不提升通用语义问答的召回率**（实测 0.0pp）
- 💰 开销可忽略（+2%）

> 答辩时**不要**声称「多路召回提升了检索效果」—— 实测数据不支持。
> 正确的说法是：「多路召回扩展了系统的能力边界（精确定位 + 语料缺口识别），
> 在通用语义问答上与单路持平，开销 +2%。」

## 七、已知限制

| 限制 | 说明 |
|---|---|
| **图谱不适用医疗语料** | 指南 PDF 无条文号，`kb_medical` 建出 0 节点 |
| **跨法引用稀疏** | `CITES` 边仅 365 条（覆盖 1.9% 的 chunk），对检索贡献有限 |
| **权重未调参** | `MULTI_RECALL_WEIGHTS`（vector 1.0 / graph 1.2）与 `DOC_BOOST=1.5` 是**先验设定**，未做网格搜索 |
| **图谱需 Neo4j 常驻** | 约 1.5GB 提交量；`MULTI_RECALL_ENABLED=0` 可完全绕开 |
| **图谱需手工重建** | 新增文档后要重跑 `graph_store.build_graph()`，目前没有增量更新 |
| **「相邻条文」边价值未验证** | 14137 条边占绝大多数，但**未单独测过它对检索的贡献**；向量检索本身可能已召回相邻条文 |
