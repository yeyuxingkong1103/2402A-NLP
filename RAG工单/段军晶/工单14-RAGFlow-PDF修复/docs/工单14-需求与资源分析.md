## 一、项目背景与目标

### 1.1 业务背景

公司要快速搭建一套 RAG 系统，用于**中文工业技术文档的多模态推理问答**。数据集为 IMDR / ITMQ（工业制造领域多模态理解与推理数据集，共 10,096 个问题），问题分三类：**纯文本问题、纯图像问题、文本-图像混合问题**。

该数据集有两个关键领域特征，也是本工单难点的来源：

1. **文档以"不可编辑的图片型 PDF"形式提供**——无文本层、分辨率低、格式不一、版面复杂。
2. **问题大量为交错的文本-图像类型**——需同时理解文字描述与工程图纸，并做机械原理推理。

### 1.2 核心技术问题

RAGFlow 的默认解析流水线在这类图片型 PDF 上会**丢失图文信息、错配图文关联**，导致问答不准。本工单要求定位缺陷并修复，使工单规定的 6 个测试问题准确率达到 100%。

### 1.3 目标文档实测特征

对目标文档 `CN100342976C.pdf` 的实测结果（静电除尘器专利，专利号 ZL 01813417.3，授权公告号 CN 100342976 C）：

| **文本层** | **`pdftotext` 提取结果为 0 字符——纯图片型 PDF** |

### 3.3 源码与镜像的关系（部署路线选择）⚠️

本节决定两件事：**怎么部署**，以及 **D3「调整后的实现代码」能否交付**。

#### 3.3.1 版本一致性（好消息）

| 来源 | 版本 |
|------|------|
| `pyproject.toml` | `version = "0.23.1"` |
| `docker/.env:157` | `RAGFLOW_IMAGE=infiniflow/ragflow:v0.23.1` |

源码版本与镜像 tag **完全一致** → **阅读这份源码得出的结论，就等于运行时真实行为**，不会出现"分析的代码和实际跑的代码不是一套"的错位。这是撰写 D1 技术文档的必要前提。

> 附带说明：该源码树由 `ragflow-main.zip` 解压而来，**不含 `.git` 目录**，因此无法提供 commit hash。以 `v0.23.1` 作为版本锚点即可——它与镜像 tag 一致，比 commit hash 更直观。

#### 3.3.2 陷阱一：Docker 不挂载源码，改代码不生效

`docker/docker-compose.yml` 中 ragflow 服务的 volumes **仅**挂载以下内容：

```yaml
volumes:
  - ./ragflow-logs:/ragflow/logs
  - ./nginx/ragflow.conf:/etc/nginx/conf.d/ragflow.conf
  - ./nginx/proxy.conf:/etc/nginx/proxy.conf
  - ./nginx/nginx.conf:/etc/nginx/nginx.conf
  - ./service_conf.yaml.template:/ragflow/conf/service_conf.yaml.template
  - ./entrypoint.sh:/ragflow/entrypoint.sh
```

**未挂载 `rag/`、`deepdoc/`、`api/`、`common/`**——这些 Python 源码由 `Dockerfile` 在构建阶段 `COPY` 进镜像（`Dockerfile:188-199`）。

**后果**：在本地源码树中修改 `rag/app/naive.py` 等文件后，**容器内运行的仍是镜像内的原始代码，改动完全无效**。

这直接关系到 **D3 的交付**：若全程仅在 Web UI 调整配置、运行官方镜像，则拿不出"能生效的调整后实现代码"。

#### 3.3.3 陷阱二：用这份源码重新构建镜像会失败

```dockerfile
Dockerfile:168   COPY .git /ragflow/.git
Dockerfile:170   RUN version_info=$(git describe --tags --match=v* --first-parent --always); \
                     ...; echo $version_info > /ragflow/VERSION
```

但该源码树不含 `.git` 目录（已确认）。因此：

- `COPY .git` 因找不到源文件而**构建失败**；
- 即便手动创建空的 `.git`，`git describe` 亦会失败。

→ **"改源码 → 重新 build 镜像"这条路径开箱即用不可行**，需先修改 Dockerfile（删除或替换上述两行）。此外完整构建还需安装 Node 并执行前端 `npm run build`，耗时较长。

#### 3.3.4 部署路线对比

| 路线 | 做法 | 优点 | 缺点 | 评价 |
|------|------|------|------|------|
| **A. 官方镜像 + 按需挂载** | 运行 `infiniflow/ragflow:v0.23.1`；确需改代码时，把改动的源码文件以 volume 挂载覆盖镜像内同名文件 | 部署快；改动可真正生效；D3 可交付 | 需自行维护挂载配置 | **推荐** |
| B. 本地源码启动 | 本地 venv 启动 `api` 服务与 `rag/svr/task_executor.py`，依赖服务仍由 Docker 提供（Redis / MySQL / MinIO / ES） | 改动即时生效，调试方便 | 环境搭建成本高，依赖版本易出问题 | 需大量改代码时可选 |
| C. 修改 Dockerfile 后重新构建 | 先移除 `.git` 相关两行，再执行 build | 产物干净、可复现 | 构建慢；需 Node 工具链；2 人日工期下不划算 | 本工单不推荐 |

**建议采用路线 A**：以官方镜像快速跑通环境，把这份源码作为**只读分析对象**用于撰写 D1 技术文档；一旦确认必须在代码层改动，再通过 volume 挂载覆盖对应文件，使改动生效且 D3 可交付。

### 3.4 模型资源（4 类，**决定性**）

| 模型 | 用途 | 关键性说明 |
|------|------|------------|
| **Embedding** | 向量化 | 必须选中文优化模型。v0.23.1 检索为向量 + 关键词混合，Embedding 选错影响全盘 |

| **Image-to-text（VLM）** | **图纸转文字** | ⚠️ **本工单的生死线，见第四章** |

**代码位置（PDF 路径，已核实）**：

```
rag/app/naive.py:825       .pdf$ 匹配
→ rag/app/naive.py:835     parser = PARSERS["deepdoc"] = by_deepdoc
→ rag/app/naive.py:57-69   by_deepdoc() 调用 vision_figure_parser_pdf_wrapper(tbls, sections, **kwargs)
→ deepdoc/parser/figure_parser.py:85-123   真正的 PDF 图/表 VLM 增强入口
```

> ⚠️ 注意：`rag/app/naive.py:911-917` 那段同名的 `LLMType.IMAGE2TEXT` 分支位于 **markdown 分支**（处理 `.md/.markdown/.mdx`），**不是 PDF 路径**。写技术文档时不要引错。

**VLM 的真实作用是"增强"而非"开关"**：

```python
# deepdoc/parser/figure_parser.py:91-96, 123
try:
    vision_model = LLMBundle(kwargs["tenant_id"], LLMType.IMAGE2TEXT)
except Exception:
    vision_model = None
if vision_model:
    ...          # 增强块
return tbls      # ← 拿不到模型时原样返回，图片对象仍在
```

未配置 image2text 模型时，函数**跳过增强并原样返回 `tbls`**，图项随后被 `tokenize_table`（`rag/nlp/__init__.py:375-406`）正常消费，生成 chunk：`content_with_weight` = 图注/图内文字、`image` = 裁剪图、`doc_type_kwd = "image"`、上传后写 `img_id`。**图纸不会被丢弃。**

**真正的丢弃条件与 VLM 无关**（`deepdoc/parser/pdf_parser.py:901-903`）：

```python
txt = "\n".join([b["text"] for b in bxs])
if not txt:
    continue          # 图内无任何文字、且无图注 → 才丢弃
```

**准确结论**：

| 情形 | 结果 |
|------|------|
| 有图注，或图内 OCR 出文字 | ✅ 图纸**会入库**，内容 = 图注 + 图内文字 |
| 图内无文字且无图注 | ❌ 不产出任何 chunk（**与是否配 VLM 无关**） |
| 配了 VLM | 在图注**之前**额外拼一段 VLM 语义描述（`figure_parser.py:248-251`） |

**对本工单的推论**：第 7 页页底有"图 1"图注，图内还有 `6`/`6'`/`6''`/`X1`/`h1`/`D`/`4`/`5`/`7`/`10` 等标注——只要 OCR 能识别，图纸就有内容入库，**不配 VLM 也不丢**。

但 **Q3（部件 4 相对部件 5 的位置关系）是纯空间问题**，OCR 文字里不含"左/右"这类关系信息：

- **Q3**：必须依靠 VLM 描述或人工转写 → **VLM 是 Q3 的必要条件**
- **Q4 / Q5 / Q6**：可能靠"OCR 文字 + 图注 + 第 6 页正文"达成 → **VLM 是强力增强项，非必需**

> 缓解因素：VLM 调用发生在**解析/索引阶段**，不占用查询时的 3 秒预算。

## 四、关键发现（需在交付文档中体现）

### 4.1 图纸是关键瓶颈，但"信息丢失"的位置与直觉不同

6 题中 4 题依赖第 7 页工程图。经源码核实，**"信息丢失"并不发生在"未配置 VLM"上**——未配 VLM 时图纸仍会入库（见 3.4），只是没有语义描述。真正的信息流失发生在**更上游**：

| # | 流失环节 | 位置 | 说明 |
|---|----------|------|------|
| 1 | **OCR 置信度过滤** | `deepdoc/vision/ocr.py:738-744` | 识别得分 < `drop_score = 0.5` 的文本行**整条丢弃**。图纸细线小字极易低分 → 切片里连错字都没有 |
| 2 | **图区图文高度差过滤** | `deepdoc/parser/pdf_parser.py:310-314` | 字高与框高差比 ≥0.7 的字符被踢进 `lefted_chars`——而 `lefted_chars` **全仓无任何读取处**（写了不用），等于永久丢失 |
| 3 | **图组文本为空即丢弃** | `deepdoc/parser/pdf_parser.py:901-903` | 图内无文字且无图注 → 不产出 chunk |
| 4 | **跨页合并逻辑不可达** | `deepdoc/parser/pdf_parser.py:586-588` | `_concat_downward` 在首行就 `return`，其后 590-688 行的 XGBoost 跨行/跨页拼接**是死代码** |
| 5 | **列感知阅读顺序未启用** | `rag/app/naive.py:576` | `_final_reading_order_merge` 在 naive 路径被**注释掉** |

至于 VLM：它的作用是**补 OCR 拿不到的信息**——尤其是 Q3 问的空间关系（"部件 4 在部件 5 左侧"）。**VLM 是 Q3 的必要条件，是 Q4~Q6 的增强项**（详见 3.4）。

### 4.2 `knowledge_graph` 没有独立分块器（工单陷阱）

工单第一问的措辞暗示 `knowledge_graph` 有独立分块策略，**实际并非如此**：

```python
# rag/svr/task_executor.py:83-100
FACTORY = {
    "general": naive,
    "naive": naive,    "paper": paper,   "book": book,
    "presentation": presentation,        "manual": manual,
    "laws": laws,      "qa": qa,         "table": table,
    "resume": resume,  "picture": picture,
    "one": one,        "audio": audio,   "email": email,
    "knowledge_graph": naive,     # ← 关键：KG 复用 naive 分块器
    "tag": tag,
}
```

- `rag/app/` 下**不存在** `knowledge_graph.py`
- `ParserType.KG = "knowledge_graph"` 仅定义在 `common/constants.py:107`
- 图谱构建在独立的 `graphrag/` 模块，是与分块并列的**独立阶段**，不是分块策略

技术文档必须点明这一点，否则会被判定为未读代码。

## 五、优先级与执行顺序建议

真正的工作量集中在一条链路上：

> **配好 image2text 模型 → 让第 7 页图纸被 caption → 图纸标注以可检索文本入库 → Q3~Q6 才有解**

Q1 / Q2 只要 OCR 正常 + 检索正常即应通过。建议顺序：

| 步骤 | 动作 | 目的 |
|------|------|------|
| 1 | 跑一遍**基线**，6 题原始结果全部记录 | 建立对照，为"原因分析"留证据 |
| 2 | 检查**解析后的切片中，第 7 页图纸到底有没有内容** | **这一步决定后续 80% 的方向** |
| 3 | 未配置 VLM 则先配置，再判断是调参数还是必须补能力 | 区分"参数问题"与"架构问题" |
| 4 | 逐项优化，**每轮只改一个变量**并记录得分 | 否则无法归因，无法交付"优化方案及效果" |

**风险提示**：2 人日工期下，第 2 步的结论若指向"必须补 VLM 能力"，则时间主要消耗在解析层而非参数调优，需尽早开工。
