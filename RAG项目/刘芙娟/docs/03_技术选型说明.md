## 0. 评估框架

每个选型按三个维度评估，缺一不可：

| 维度 | 追问 | 否决门槛 |
|---|---|---|
| **能力** | 它能做到什么？在**中文医疗语料**这个具体场景下，它的长板是否正好压在我们的短板上？ | 不能满足任何一条 NON-NEGOTIABLE 需求 → 直接否决 |
| **需求** | 它对应 M1 中的哪些编号需求？是必需项还是加分项？ | 只服务加分项却引入硬依赖 → 降级 |
| **成本** | 部署复杂度、授权许可、运维负担、锁定程度、迁移代价 | 授权与合规不可接受 → 直接否决 |

### 一个前置的取舍原则

本项目的成本结构是**非对称**的：多花一周工程时间可以接受，答错一条剂量建议不可接受。

因此本项目的选型普遍**偏向"可审计、可替换、可断言的笨办法"**，而不是"更聪明但更难解释的办法"。这解释了后文若干看起来保守的选择（不用 LangChain、不用 Agent 框架、不依赖库默认参数、话术用字符串拼接而非模型生成）。

### 需求 → 选型驱动关系

| M1 需求 | 驱动的选型 | 约束强度 |
|---|---|---|
| 段落级引用、页码可保留（§3.3、§8.2） | PDF 解析 | **硬约束**（决定 MinerU 必须取结构化产物而非 Markdown） |
| 只依据自有中文语料作答（N1） | 向量化模型 | **硬约束**（中文语义检索能力是核心） |
| 引用可回溯到段落、可带元数据过滤（N2） | 向量库 | **硬约束**（必须支持标量元数据） |
| 拒答可复现、参数不依赖默认值（N3、N4） | 全部 | **硬约束** |
| 端到端 ≤10s、拒答路径不调模型（N12、N13） | 生成模型、向量库 | 强约束 |
| 紧急话术逐字前置、免责声明逐字结尾（N7） | 生成模型、后端 | **硬约束**（决定了话术不能交模型生成） |
| 密钥零硬编码、缺失即失败（N8、N11） | 全部 | **硬约束** |
| 单一运行时、依赖可复现（N9、N10） | 全部 | **硬约束** |

## 1. PDF 解析：MinerU

**结论**：采用 MinerU **本地部署**（pipeline 后端），解析结果取**结构化中间产物**而非 Markdown；权重目录由部署者提供绝对路径。

### 能力

| 能力项 | 评价 |
|---|---|
| 中文文档版面分析 | 强。对中文指南常见的双栏、页眉页脚、图表混排处理成熟 |
| 阅读顺序还原 | 强。输出按阅读顺序排列的内容块序列，而非按坐标散点 |
| 表格 / 公式 | 强。表格还原为结构化表示，公式转 LaTeX |
| **页码保留** | **关键能力**。结构化产物中每个内容块带页级索引，可换算出物理页码 |
| 离线运行 | 支持。权重可预下载，通过配置指向本地目录，运行时不联网 |
| 结构化输出 | 输出多种格式，其中扁平的内容块列表最适合下游程序消费 |

**页码保留是本项目选择 MinerU 的决定性理由**。需求 §8.2 明确要求"解析时不得丢失页码信息"，而绝大多数解析方案（含 MinerU 自身的 Markdown 输出）在这一项上不达标。详情见 `02_架构图.md` §3。

### 需求映射

- 支撑：N2（可回溯到原文段落）、N18（引用真实性可测）、需求 §8.2（页码可保留、段落边界可保留）
- 支撑：F3（展开查看原文段落——段落边界完整是前提）
- 不支撑任何安全类需求（解析层不承担安全职责）

### 成本

| 成本项 | 评估 |
|---|---|
| 部署复杂度 | **中高**。需预下载权重、配置本地模型源、首次运行需确保无网络依赖 |
| 硬件 | 有 GPU 则快；CPU 可跑但慢。属**离线**成本，不进入在线链路的响应时间 |
| 运行频率 | 低。语料仅在人工确认后入库，解析是一次性动作 |
| 授权 | **⚠️ AGPL-3.0**，见下方风险 |

**成本上可接受的关键理由**：解析在离线链路上，慢不影响 N12；M1 §7.2 明确不做自动抓取与自动入库，解析频率以"月"计。

### 备选与不选理由

| 备选 | 能力 | 不选的理由 |
|---|---|---|
| **PyMuPDF / pdfplumber** | 文本抽取快、页码天然精确 | 无版面分析能力，中文指南的双栏、表格会串行错乱；**且 PyMuPDF 同样是 AGPL-3.0**，换它并不能解决授权问题——它只换来更差的解析质量 |
| **PaddleOCR / PP-StructureV3** | 中文 OCR 强，Apache-2.0 许可更宽松 | 定位偏"扫描件 OCR"，对**原生数字版 PDF** 的结构化还原不如 MinerU；本项目语料以官方发布的数字版指南为主。**列为扫描件兜底方案** |
| **Marker** | 转换质量不错，速度快 | 中文版面与表格处理弱于 MinerU；社区对中文医疗文档的验证案例少 |
| **Unstructured** | 接口统一、集成度高 | 中文版面分析依赖底层引擎，自身不提供；等于多一层封装却没换来能力 |
| **Docling** | MIT 许可最友好，结构输出规范 | 中文复杂版面（双栏指南、跨页表格）的实测表现弱于 MinerU；许可优势在本项目不构成决定性收益 |

**关于许可的诚实结论**：AGPL-3.0 是本次选型中**唯一一个未完全消解的授权风险**。它的实际影响取决于分发方式——本项目 V1 是内部运行的服务、不对外分发软件本体，AGPL 的网络服务条款主要约束"修改后对外提供服务并拒绝提供源码"的情形，风险相对可控。但若未来要闭源分发或商用，**必须重新评估**，届时的首选替代是 PaddleOCR/PP-StructureV3 或商业授权。

> 这一条不是"先记着以后再说"。它是本项目技术债清单上的第一项，且**如果产品形态从"自建服务"转向"可分发软件"，它会立刻变成阻塞项**。

### 部署时必须由人工填写

| 配置项 | 说明 |
|---|---|
| `MINERU_MODELS_DIR` | 本地权重目录的**绝对路径**，由部署者提供 |
| `MINERU_MODEL_SOURCE` | 置为 `local`，强制离线加载，禁止运行时下载 |
| 表格跨页合并策略 | 需显式设定。合并则沿用首页页码，不合并则保持页级保真 |

## 2. 向量化：BGE-M3

**结论**：采用 `BAAI/bge-m3` 本地部署，V1 **只使用其稠密向量**（1024 维）。

### 能力

| 能力项 | 评价 |
|---|---|
| 中文语义检索 | 强。在中文检索基准上属第一梯队，显著优于同量级通用多语言模型 |
| 多粒度输出 | 同时产出稠密向量、稀疏词权重、多向量表示 |
| 长文本 | 支持长序列输入，足够覆盖 300–500 字的 chunk |
| 离线运行 | 支持。权重可指向本地目录 |
| 授权 | **MIT**，可自由商用与修改，无 copyleft 传染 |

**选它的决定性理由**：本项目语料是**中文医疗指南**，检索失败的主要形态是"用户用口语提问、原文用专业表述"（如用户问"血压多高算高"，原文写"诊断阈值"）。BGE-M3 的中文语义对齐能力直接决定这条链路的成败。

**多粒度输出是留给 V2 的期权**：V1 只用稠密向量，但同一个模型已经能产出稀疏权重，V2 补 BM25/混合检索时**不需要更换或新增模型**——这是选 BGE-M3 而非纯稠密模型的额外收益。

### 需求映射

- 核心支撑：N1（只用自有语料作答——检索命中率是"有据可答"的前提）
- 支撑：N3、N4（模型与参数必须显式锁定，同一 query 必须产出同一向量）
- 支撑 V2 路线：M1 §7.3 预留的混合检索优先级

### 成本

| 成本项 | 评估 |
|---|---|
| 部署复杂度 | 低。权重目录 + 一次加载，无服务化需求 |
| 内存占用 | 中。常驻内存，需在部署时预留 |
| 推理延迟 | **CPU 可接受，GPU 更快**。查询侧只编码 1 条短文本，不是瓶颈；入库侧批量编码，属离线成本 |
| 授权 | 无成本 |

### 备选与不选理由

| 备选 | 不选的理由 |
|---|---|
| **bge-large-zh-v1.5** | 中文专用、性能接近，但**不支持多粒度**，V2 走混合检索时必须换模型 → 整库重建。BGE-M3 用一点冗余换掉了未来的迁移成本 |
| **multilingual-e5-large** | 需要给 query 和 passage 加不同的前缀指令，**任何一侧漏加都会静默劣化召回**——这种"默认值陷阱"与 N3 的精神冲突 |
| **OpenAI text-embedding-3** | ① 数据出境，与医疗场景合规要求冲突；② **API 化会把"知识依据封闭在自有语料"这条原则撕开一个口子**；③ 语料一旦入库就与模型版本绑定，第三方模型静默升级会让 N4 失效 |
| **国产 API 向量服务** | 同样存在数据出境与版本漂移问题，且引入网络依赖，让离线可复现性归零 |

> **共同的不选理由**：向量模型是"语料入库即固化"的一环。**用 API 模型等于把审计基线交给一个会随时变更的外部服务**——今天入库的向量和明天的查询向量可能不在同一空间，而系统不会有任何报错。本地模型是这个项目唯一自洽的选择。

## 3. 向量库：Milvus

**结论**：采用 Milvus，V1 使用 **FLAT 索引 + COSINE 度量**。部署形态待 Windows 兼容性实测后确定（见风险）。

### 能力

| 能力项 | 评价 |
|---|---|
| 标量元数据过滤 | 强。每条向量可携带文件名、页码、章节等字段，支持按字段过滤 |
| 度量方式 | 支持 COSINE，与归一化后的 BGE-M3 输出匹配 |
| 索引类型 | FLAT（精确）/ IVF / HNSW 可选。小语料下 FLAT 可做到**零召回损失** |
| 混合检索 | 2.5+ 版本内置全文检索与稀疏向量能力，**V2 补 BM25 时是配置变更而非新增依赖** |
| 授权 | Apache-2.0 |

**选它的决定性理由之一是 V2 的升级路径**。M1 §7.3 把"补 BM25"列为拒答率偏高时的第一优先级。若 V1 选了一个不支持原生混合检索的库，V2 就得做一次数据迁移 + 依赖替换；Milvus 让这件事收敛为"加一个字段和一个索引"。

**选它而非更轻量方案的直接理由**：本项目要求引用卡片展示 `file_name` + `page` + 原文段落，且未来要按文件过滤。**元数据过滤是一等公民，不是附加项**——纯向量索引库需要自己维护向量 ID 到元数据的映射，等于手写一个半成品数据库。

### 需求映射

- 硬支撑：N2（引用可回溯——元数据字段承载文件名与页码）
- 硬支撑：N3、N4（索引类型、度量方式、`top_k` 全部显式声明，不用默认值）
- 支撑：N13（检索为空时直接拒答，不调模型——需要明确的"空结果"语义）
- 支撑：F3（来源卡片展开原文——`text` 字段直接取用，不需回表）

### 成本

| 成本项 | 评估 |
|---|---|
| 部署复杂度 | **V1 的最大不确定项**，见风险 |
| 运维负担 | 若走容器化部署，会引入额外的中间件依赖，对单机 MVP 偏重 |
| 语料规模 | V1 预计数千 chunk 量级，**远低于任何方案的性能瓶颈** |
| 授权 | 无成本 |

### 备选与不选理由

| 备选 | 不选的理由 |
|---|---|
| **FAISS** | 无元数据存储、无服务化、无混合检索。会退化为"自建元数据映射层"，且 V2 混合检索需自己实现 |
| **Chroma** | 上手最快，元数据支持好，但**原生混合检索能力弱**，V2 的 BM25 路径要另想办法 |
| **LanceDB** | 嵌入式、部署轻、原生 BM25，**在本项目的 Windows 单机场景下其实是很有竞争力的替代**。未选的原因是与既定技术栈一致性的收益，以及 Milvus 的分布式演进空间 |
| **pgvector** | 需要一个 PostgreSQL 实例，对"单机 + 一份指南"的场景是过度设计；且混合检索需自行拼 SQL |
| **Qdrant** | 能力与 Milvus 接近，元数据过滤体验更好，选谁都成立。区别主要在生态与后续演进 |

> ⚠️ **本节结论的诚实说明**：Milvus 与 LanceDB/Qdrant 在本项目当前规模下**能力差距不足以构成决定性理由**。选择 Milvus 更多是权衡了既定技术栈与 V3 演进空间。如果 Windows 兼容性实测不通过，**换库的代价是可接受的**，不应为了保 Milvus 而牺牲部署可行性。

### ⚠️ 风险：Windows 部署形态未证实

**这是本次选型中唯一一个"结论可能被推翻"的项。**

Milvus 的嵌入式模式（Lite）是否支持 Windows 原生运行，**多份资料相互矛盾**：既有明确指向不支持的社区议题，也有指向新版本已支持的说明。**在实测确认之前，本项结论不成立。**

实测步骤（M3 首个任务）：

```
D:/zg6_Project/9/med_rag/rag/python.exe -c "import milvus_lite; print('ok')"
```

| 实测结果 | 处置 |
|---|---|
| 可导入且能建库写入 | 采用嵌入式模式，零额外进程，方案不变 |
| 不可用 | 二选一：① 容器化部署 Milvus Standalone（接受额外中间件，换取 V2 混合检索路径）；② 换 LanceDB / Qdrant（保留轻部署，混合检索另行实现）。**若选择②，需回写本文档与 `02_架构图.md` §7 的数据模型** |

## 4. 生成模型：DeepSeek-V4-Flash（经中转站）

**结论**：经 `https://api.agicto.cn/v1` 调用 `deepseek-v4-flash`，OpenAI 兼容协议。密钥由部署者填写。

### ⚠️ 先声明两项未证实事项

本文档的原则是**不把未验证的东西写成结论**。以下两项在选型落地前必须由部署者确认：

| 事项 | 状态 | 确认方式 |
|---|---|---|
| `deepseek-v4-flash` 的模型 ID 与可用性 | **中高置信但未从官方主站证实**。多份独立来源指向该模型存在，但未取得官方模型列表的直接确认 | 部署时调用中转站的 `/models` 端点列出实际可用模型，以返回结果为准 |
| 中转站是否稳定支持流式输出 | **存疑**。有资料反映中转类服务存在"无可用通道"等静默失败 | 部署时做一次连通性与流式冒烟测试 |

若实测发现模型 ID 不可用，**处置是替换 `LLM_MODEL` 环境变量，而不是改代码**——这正是选择 OpenAI 兼容协议作为接口契约的理由。

### 能力

| 能力项 | 评价 |
|---|---|
| 中文生成质量 | 强，中文语境下的表述自然度与指令遵循属第一梯队 |
| 接口协议 | OpenAI 兼容，`/chat/completions` + Bearer 认证，**可替换性极强** |
| 结构化输出 | 支持 JSON 模式与函数调用，可用于约束输出格式 |
| 成本 | 同类模型中性价比较高；**具体单价未证实**，以中转站实际计费为准 |
| 上下文窗口 | 足够容纳系统提示词 + top-5 检索段落 + 问题 |

### 需求映射

**生成模型在本项目里承担的责任比通常的 RAG 小得多**，这是刻意的架构选择：

| 需求 | 是否由模型承担 |
|---|---|
| 紧急话术前置（N7） | ❌ **由代码字符串拼接**，模型无权生成 |
| 免责声明结尾（N7） | ❌ **由代码字符串拼接**，模型无权生成 |
| 拒答兜底话术（F6） | ❌ 固定文本，模型不参与 |
| 风险等级判定（§3.1） | ❌ 由原文表述 + 紧急词表决定 |
| 知识性回答的**转述** | ✅ 模型承担 |
| 紧急判定的**第二段补充** | ✅ 模型承担 |

**这张表是本节最重要的一行**。模型只做两件事：把检索到的原文转述成通顺的中文，以及对词表漏检的口语化表达做补充判断。所有需要"逐字精确、可断言、不可协商"的输出，全部由确定性代码产出。

**这样设计的收益**：即便模型被替换、被降级、甚至输出格式失控，N7 的两条断言仍然成立。系统对生成模型的依赖被压缩到"写得好不好"而非"对不对"。

### 成本

| 成本项 | 评估 |
|---|---|
| 部署复杂度 | **低**。纯 HTTP 调用，无本地算力要求 |
| 调用频率 | 低。**拒答路径完全不调用模型**（N13），且系统设计上拒答是常态输出 |
| 费用 | 按 token 计费。V1 单次调用约输入数千 token + 输出数百 token |
| 延迟 | 是 N12（≤10s）的主要占用项，需设置超时并在前端给出明确反馈（N14） |

### 备选与不选理由

| 备选 | 不选的理由 |
|---|---|
| **本地部署开源模型** | 数据完全不出机，合规最优，但**需要 GPU 与运维成本**，且中文医疗转述质量需实测。**这是本项目在数据合规升级时的首选迁移路径** |
| **Qwen 系列** | 中文医疗术语强、合规叙事最完整、支持私有化部署，**综合竞争力最强**。未选是因为本项目 V1 不接触患者数据（见下方合规边界），且用户已确定成本更优的方案。切换代价仅是 base_url + 模型名 + 密钥 |
| **GLM-4-Flash** | 有免费额度，可作为零成本兜底或辅助模型（如承担紧急判定第二段这类轻量任务），但主力生成能力弱于选定方案 |
| **Kimi / Moonshot** | 长文本见长，本项目检索段落远未触及长上下文需求；作为 grounded 生成器无明显优势 |
| **ERNIE** | 认证方式非标准（access_token 而非 Bearer），集成成本最高，与"可替换性"目标相悖 |
| **直接调用 DeepSeek 官方 API** | 无中转层的可用性与隐私不确定性，是更干净的选择。**若部署者对中转站存疑，应优先考虑此项** |

### ⚠️ 中转站的两个真实风险

**风险一：可用性。** 中转站是链路上的单点。若其不可用，模型补充判定会降级（架构 §5 已设计降级路径：退回仅词表判定，方向偏保守），但正常路径的知识转述会失败。**必须在部署时验证，并明确失败时的用户可见行为**（N14：给出明确提示，不得无限加载）。

**风险二：隐私与合规。** 中转站是第三方，**模型真实性与数据处理方式均无法审计**。这对本项目 V1 是可接受的，但边界必须写死：

> **合规边界（V1 不可逾越）**：本系统只向 LLM 发送**公开指南原文段落 + 用户提问**，不发送任何患者标识信息、病历数据或个人健康档案。用户提问本身即可能包含个人健康描述，因此在 M1 §7.2 已明确**不收集用户账号与历史记录**的约束下，系统不承担长期存储责任。
>
> 另需注意：依据国内生成式 AI 服务的监管要求，**调用已备案模型构建生成式 AI 应用，应用方自身仍有登记义务**。中转站的存在会使得"实际接收数据的实体"难以对应到具体备案。**若产品从内部演示转向对外提供公众服务，此项必须先解决，届时正确路径是改用可备案的官方 API 或本地部署。**

## 5. 后端：FastAPI

**结论**：FastAPI + Uvicorn，通过 `rag/python.exe` 运行。

### 能力

| 能力项 | 评价 |
|---|---|
| 异步 I/O | 原生 async。本项目链路上有两次外部等待（LLM 调用、向量库查询），异步能避免线程阻塞 |
| 请求/响应建模 | 基于类型注解的自动校验与序列化，**与 N15（函数签名带类型注解）的代码规范天然契合** |
| 自动文档 | 自动生成 OpenAPI 文档，接口契约可被前端直接消费，减少前后端对齐成本 |
| 生态 | OpenAI SDK、向量库 SDK 均为 Python 优先，无需跨语言适配 |
| 启动期校验 | 生命周期钩子适合放置"必需配置缺失即非 0 退出"的逻辑（N11） |

**选它的决定性理由**：`03_架构图.md` §2.2 定义的统一回答体是一个**有嵌套结构的数据契约**（含 `emergency`、`risk_level`、`citations` 数组）。用 Pydantic 模型定义它，可以在编译期（类型检查）与运行期（请求校验）双重保证契约不被悄悄改坏。这是 Flask 需要额外引入 marshmallow 才能达到的效果。

### 需求映射

- 支撑：N15（类型注解规范）、N11（启动期配置校验 + 非 0 退出）
- 支撑：N14（超时与明确错误反馈——统一异常处理）
- 支撑：N12（异步并发，避免外部等待期间阻塞）

### 成本

| 成本项 | 评估 |
|---|---|
| 学习/开发成本 | 低。团队熟悉 Python |
| 部署复杂度 | 低。单进程 Uvicorn，无额外中间件 |
| 性能 | V1 无并发压力，性能非选型因素 |

### 备选与不选理由

| 备选 | 不选的理由 |
|---|---|
| **Flask** | 同步模型，在 LLM 调用期间会阻塞工作线程；需额外引入序列化库才能达到同等的契约保证 |
| **Django** | 自带 ORM、Admin、模板等，本项目均不需要，属重大过度设计 |
| **Node.js / Go** | 需要跨语言调用 Python 侧的向量模型与解析工具，引入进程边界与序列化开销，得不偿失 |

## 6. 前端：原生 HTML/CSS/JS（2026-09-27 修订，原选型为 Streamlit）

> **本节已变更。** 原结论是 Streamlit 单页应用、定位快速演示。改动发生在

>「原选型：Streamlit（已废止）」中 —— 它的分析没有错，只是被新的诉求推翻了。

**结论**：原生 HTML/CSS/JS 静态资源，存放于 `frontend/`，由后端在 `127.0.0.1:8000`
**同源**提供，**无构建工具链、无独立前端进程**。

### 推翻原选型的三条诉求

原选型明确把"UI 表现力"排除在成功判据之外，因此 Streamlit 的布局局限可以接受。
新诉求把这三件事变成了硬需求：

| 诉求 | Streamlit 的问题 |
|---|---|
| 定制蓝白配色 + 左右两栏（左导航 / 右详情） | 无细粒度样式控制；布局由组件流决定 |
| 导航栏可持续追加新的功能界面 | 单页结构，多"页面"要靠侧栏 radio + 条件渲染拼 |
| **正文流式追加 + 引用卡片按分数降序呈现** | 流式的逐块追加渲染不是它的使用模型 |

其中第三条是决定性的：`docs/05` §3.1.1 已改为 SSE 流式，前端必须按事件到达顺序
逐块追加正文。这是"自己控制 DOM"的能力，而 Streamlit 的定位恰恰是不让你控制 DOM。

### 代价与对冲

| 代价 | 对冲 |
|---|---|
| 需自己写交互与状态管理 | 界面只有"提交问题 + 渲染结果"，状态机五个状态（`idle/submitting/streaming/done/failed`），量很小 |
| 无组件库，可访问性要自己做 | 用原生语义元素 + `aria-live`、`aria-current`、`role="alert"` |
| 无构建工具链 ⇒ 无类型检查 | 单文件 ≤300 行（constitution 级约束）、验收脚本覆盖渲染与解析逻辑 |

**不选 React/Vue 的理由**：与 `constitution` 原则 I「单一 Python 运行时」的治理精神
相冲突 —— 为几个静态页面引入 Node 工具链，会让"环境锁定"退化成"锁一个、放一个"。

## 7. 编排层：不使用 LangChain / LlamaIndex

这一项选型的结论是**"不引入"**，因此单独说明。

### 不选的理由

| 理由 | 说明 |
|---|---|
| **与"强制溯源"原则冲突** | 本项目的核心是每一处陈述都能落到具体段落。框架的检索链把"检索 → 组装 → 生成"封装为黑盒，**中间态的可见性下降，与 N2 的可审计要求方向相反** |
| **默认值不可控** | 框架自带大量默认参数（切分、检索、提示词模板）。N3 要求参数显式配置，**框架的默认值恰恰是最难发现和覆盖的一类隐式配置** |
| **版本漂移风险** | 此类框架迭代快、破坏性变更频繁。一个静默的行为变更可能让"拒答"变成"勉强回答"，而**这种劣化不会报错，只会悄悄发生** |
| **依赖膨胀** | 为几条线性流程引入庞大的传递依赖树，与 constitution 原则 I 的依赖治理精神相悖 |
| **本项目流程足够简单** | 链路是：向量化 → 检索 → 判定 → 组装提示词 → 调用 → 校验 → 拼装。**用约数百行显式代码即可完整表达**，且每一行都可读、可测、可断点 |

### 反而带来的收益

自己写这段流程意味着：**拒绝决策、阈值比较、引用校验全部是显式的普通函数**。这让 N17、N18 要求的断言类测试可以直接针对函数写，而不需要通过框架的抽象层去"模拟"。

### 使用的库（最小的胶水层）

| 库 | 用途 |
|---|---|
| `pymilvus` | 向量库客户端 |
| `FlagEmbedding` 或 `sentence-transformers` | BGE-M3 加载与编码 |
| `openai` | 调用 OpenAI 兼容端点（中转站） |
| `pydantic` | 数据契约与配置校验 |
| `python-dotenv` | `.env` 载入环境变量 |

**全部为窄职责库，无框架级抽象。**
