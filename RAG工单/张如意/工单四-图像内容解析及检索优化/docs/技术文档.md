## 1. 问题背景：为什么必须做图像解析

招股说明书中的高价值信息大量以**图形**承载，典型有三类：

| 图形 | 承载的信息 | 文本层能否取到 |
|------|-----------|----------------|
| 组织结构图 | 部门层级、下属机构数量 | 只能取到零散节点名，**取不到隶属关系** |
| 市场结构/增长图 | 各行业规模、增长率（含负值） | 只能取到题注，**取不到数值** |
| 流程图/示意图 | 业务流程先后顺序 | 几乎取不到 |

本工单的两个问题正是典型：

* **id 5**：销售部有几个部门构成，大客户销售部有几个销售处构成？
  → 答案在《招股说明书2》第 39 页「公司组织结构图」里，图是**矢量绘制**。
* **id 6**：2008 年中国 IC 市场应用结构与增长图中，增长率最快 / 负增长的是哪个行业？
  → 答案在第 72 页「2008 年中国 IC 市场应用结构与增长」图中，需要读出条形图每个行业的百分比。

实测（详见 `docs/图像问题定位分析.md`）：
第 39 页文本层只有 `财/务/部`、`销/售/部` 这样**逐字竖排、按文本框位置排列**的字符，
既没有层级，也没有数量；第 72 页文本层能取到题注与一段"工控增长率 10.5%，位列第二"的正文，
但"谁最快、谁负增长"必须看图。**结论：不做图像语义解析，这两问在原理上无解。**

## 2. 多模态解析技术选型：CLIP 与多模态大模型的取舍

工单备注要求「使用多模态模型（CLIP 或多模态大模型）实现」。二者能力互补，本项目**级联使用**。

### 2.1 能力对比

| 维度 | CLIP（判别式） | 多模态大模型 VLM（生成式） |
|------|----------------|---------------------------|
| 代表模型 | `OFA-Sys/chinese-clip-vit-base-patch16`、`openai/clip-vit-base-patch32` | Qwen-VL / GPT-4V 类 OpenAI 兼容接口、Ollama `qwen2.5-vl:7b` |
| 输出形态 | 类别标签 + 置信度（top-n） | 自然语言 / 结构化 JSON |
| 能回答"销售部有几个下属部门"吗 | **不能**：分类器只输出"这是组织结构图"，不产出图内关系 | **能**：按层级树/JSON 模板逐条读出 |
| 能回答"哪个行业负增长"吗 | **不能**：无法输出图内数值 | **能**：`extract_chart_data` 逐类读出并标出负值 |
| 单图成本 | 本地推理，CPU 数十~数百 ms | API 调用或本地大模型，1~10 s |
| 依赖 | `torch` + `transformers`（较重） | `openai` 客户端 + 可用多模态端点（或 Ollama） |
| 失败影响 | 只是拿不到标签，可降级 | 拿不到描述，图像块不入库 |

### 2.2 为什么不是"二选一"

* **只用 CLIP**：只能把图**分类**并做图文匹配，无法把图中层级与数值**转成可检索文本**。
  对 id 5 / id 6 这类问题，CLIP 单独的准确率为 0——它永远不会输出"6 个销售处"。
* **只用 VLM**：可行但代价高。招股书里有大量**无检索价值**的图（产品照片、地图、封面 logo），
  对每一张都调用 VLM 会显著增加费用与时间；而且不同图需要不同 prompt，没有分类就无从分派。
* **级联（本方案）**：
  1. **CLIP 做粗筛/路由**：判定图属于 `组织结构图` ⟶ 走层级树 prompt；`柱状图/饼图/折线图` ⟶ 走图表结构化 prompt；
     `产品图/地图` 且置信度高 ⟶ 跳过精解析，节省算力；
  2. **VLM 做精读**：按选定 prompt 生成可检索文本；
  3. 兜底：CLIP 不可用时（无 torch/transformers），全部按通用 prompt 交给 VLM，
     并在描述中保留类型判断（`extract_chart_data` 自身会输出 `type` 字段）。
     该降级路径已实现于 `image_semantic_parse.decide_kind()` 与
     `rag_core.image_parse.enrich_image_blocks()`。

对应代码：

```python
# src/image_extractor.py         CLIP 零样本分类（粗筛）
# src/image_semantic_parse.py     decide_kind()：CLIP 标签/题注 → prompt 类型
#                                 parse_image()：VLM 精读 + 图表结构化抽取
```

### 2.3 VLM 后端选择

`rag_core.image_parse.VLMImageParser` 已内置后端优先级，本项目直接复用：

1. 环境变量 `RAG_VLM_MODEL` 指定的 OpenAI 兼容多模态接口（生产推荐：qwen-vl-max 等）；
2. 本地 Ollama 视觉模型（离线/内网环境：`qwen2.5-vl:7b` 等），探测不到再回退到 1。

温度固定 `0.0`：图表读数属于事实抽取任务，采样温度必须为 0，避免"读出一个不存在的数据"。

## 3. 矢量图 vs 位图：抽取难点与对策

### 3.1 三类"图"，三种命运

| 类型 | PDF 内部形态 | `page.get_images()` | 对策 |
|------|--------------|---------------------|------|
| **内嵌位图**（截图、照片、扫描件） | 独立 XObject，有 xref | ✅ 能取到 | 按 xref 导出 PNG |
| **矢量图**（组织结构图、部分图表） | 只有路径/直线/填充指令（`get_drawings()`） | ❌ 取不到 | **整页渲染成位图**（回退策略） |
| **水印/背景切片** | 小尺寸 XObject，每页重复 | ⚠️ 能取到但无价值 | 按"尺寸 + 重复度"过滤 |

### 3.2 本项目的实测数据（《招股说明书2.pdf》，350 页）

| 现象 | 实测值 | 影响 |
|------|--------|------|
| 水印切片 | 143×127 的「八维教育」切片，**每页 15 个，全文档 5250 个** | `rag_core.extract_images(min_size=120)` 拦不住（143>120），每页都被判为"有内嵌图" |
| 第 39 页组织结构图 | 31 个矢量绘图对象；0 张真实内嵌图；文本层 323 字 | 唯一正确取图方式是**整页渲染** |
| 第 72 页 IC 市场图 | 2 张真实内嵌位图（638×479 饼图 + 525×473 条形图）+ 15 个水印 | 需要"过滤水印后取真图" |
| 尾页扫描件 | 343~349 页存在 2480×~400 的整页位图 | 属正常大图，保留但不做重点解析 |

### 3.3 `_page_looks_like_figure` 的两个缺口与补强

`rag_core.pdf_parse._page_looks_like_figure` 的判据是
`文字 < 200 字 且 绘图对象 > 20`。直接使用会在本工单踩两个坑：

1. **文字阈值漏判**：第 39 页组织结构图有 323 字的**竖排节点文字**（`财\n务\n部`…），
   超过 200 字阈值，函数返回 `False`，矢量图回退**不会触发**。
2. **水印导致永不回退**：水印切片让 `got=True` 恒成立，
   即便页面判定通过，`extract_images` 也不会走整页渲染分支。

工单04 的 `src/image_extractor.py` 做了三点补强：

```python
# 判据 a：题注关键词 + 矢量绘图对象（招股书图表的标准特征）
# 判据 b：等价 rag_core 的原始启发式（正文稀疏 + 绘图多）
# 判据 c：绘图对象密集（≥25）且汉字量不大 —— 兜住"整页是图但节点文字多"的情况
def detect_figure_page(page) -> tuple[bool, str]: ...

def is_watermark(xref, counts, n_pages) -> bool:
    # 全文档重复次数 ≥ max(5, 30% 页数) 的 xref 判为水印
```

并且**先过滤水印，再判断"该页是否有可用内嵌图"**，然后才决定是否整页渲染——
第 39 页因此能被正确识别并渲染为 `p39_fullpage.png`（200 dpi，1654×2339）。

> 为什么渲染 200 dpi 而不是 150：150 dpi 下图中 7~9 号小字（如"－2.0%"）会糊成一片，
> VLM 读数错误率明显上升。200 dpi 是"清晰度 / 体积"的折中（单页 PNG 约 300~600 KB）。

### 3.4 竖排文字：文本层"看得见、读不懂"的典型

第 39 页的节点名在 PDF 文本层是逐字换行：

```
销
售
部
...
大
客
户
销
售
部
```

`rag_core.pdf_parse.clean_text()` 会把它们拼回"销售部""大客户销售部"，
**但节点之间的父子关系只存在于图形坐标里**——文字流里 6 个销售处只是顺序罗列，
无法判断它们挂在"大客户销售部"下面还是"销售部"下面。
这正是"文本层取不到"的精确定义：**字符在，结构不在**。
唯一的还原途径是把整页像素交给多模态模型，让它按图形连线重建层级。

## 4. 图表转结构化数据的 Prompt 设计

三条 prompt 分工（见 `rag_core/image_parse.py` 与本工单 `image_semantic_parse.py`）：

| prompt | 用途 | 输出 |
|--------|------|------|
| `_ORG_PROMPT` | 组织结构图 → 层级树 | Markdown 缩进树，逐字抄录节点名，不清晰处标注 |
| `_CHART_PROMPT` | 通用图表 → 语义描述 | Markdown：图类型/标题/「类别：数值」清单/最值结论 |
| `extract_chart_data` prompt | 图表 → 结构化 JSON | `{type,title,x_axis,y_axis,series:[{name,data:{...}}],notes}` |

### 4.1 关键设计点

1. **反幻觉三原则**：数值必须是图中实际标注；读不出填 `null`；不清晰就写"无法识别"。
   禁止估算和常识补全——招股书问答里"编一个数字"比"拒答"严重得多。
2. **穷举要求**：明确写"所有类别/年份都要列出，一个都不能漏"。
   图表问题最常见的失败模式就是漏读一个系列（例如漏掉负增长的那根柱子）。
3. **最值显式化**：要求指出最大/最小/增长最快/负增长，直接对齐 id 6 的提问方式。
4. **组织结构图单独建模**：用缩进树而非自然语言，因为"父子关系"是树结构，
   自然语言描述（"销售部包含若干部门"）会丢层级、且无法稳定计数。
5. **只输出目标格式**（Markdown / JSON），避免解释性文字污染解析结果。

### 4.2 后处理：把"计数"从模型手里拿回来

模型输出层级树后，`tree_to_facts()` 解析缩进得到父子关系，自动生成确定性事实：

```
销售部 的直接下级（4 个）：电话及网络销售部、渠道销售部、大客户销售部、国际贸易部
大客户销售部 的直接下级（6 个）：珠海销售处、深圳销售处、北京销售处、武汉销售处、广州销售处、成都销售处
```

* **数量由树结构统计得出，不依赖模型"数数"**，从根本上消除计数幻觉；
* 节点名在文本中密集出现，BM25 对"销售部""大客户销售部""销售处"的命中率显著提升。

同理，`chart_data_to_text()` 把 JSON 展平为「类别：数值」行，
并自动计算 **最大值 / 最小值 / 负值类别清单**——id 6 的"增长率最快/负增长"因此有了确定性的候选答案。

### 4.3 解析失败的降级

* VLM 返回空 → 记录 `error`，该图**不生成图像块**（宁缺毋滥，避免空块占位）；
* `extract_chart_data` 返回 `_error` → 仅使用自然语言描述；
* 全部失败 → 输出提示"未做多模态解析，图中信息不可检索"，便于排查。

## 5. 图像 chunk 的检索策略

### 5.1 入库文本的组装

`build_retrieval_text()` 把一张图编码成一段结构化文本，再作为一个 chunk 入库：

```
[图像] 《招股说明书2》第39页｜类型：组织结构图｜标题：1、公司组织结构图｜来源：矢量图整页渲染
【图像语义描述】
<层级树 / 图表描述>
【图表结构化数据】
图标题：…；增长率 —— IC卡：-2.0，工控：10.5，…
增长率 中的最大值：汽车（14.0）；最小值：IC卡（-2.0）
增长率 中为负值的类别：IC卡
【层级隶属关系（由层级树自动展开）】
销售部 的直接下级（4 个）：…
```

四段的职责：头信息负责**溯源与类型过滤**，描述段负责**语义召回**，
数据段负责**数值问答**，层级段负责**计数问答**。

### 5.2 为什么不切分图像块

`rag_core.chunk._block_to_single_chunk()` 对 `type != text` 的块整块保留、不再切分。
这是刻意的：层级树/表格一旦被窗口切开，父子关系与表头-数据对应关系就被破坏，
"4 个部门""6 个销售处"会变成无法回答的碎片。
代价是图像块较长（约 500~1500 字），但图像块总量很小（本工单约 8~15 个），
对检索速度与召回池影响可忽略。

### 5.3 检索链路

沿用 `PRESETS["wo04_image"]`：`structure 分块 + hybrid(向量+BM25, rrf 融合) + cascade 重排`。

* **向量通道**：语义描述与问句的语义匹配（"销售部有几个部门" ↔ "层级隶属关系"）；
* **BM25 通道**：节点名/数值的精确匹配（"大客户销售部""销售处""14.0%"），
  中文分词由 `rag_core.bm25.tokenize` 完成；
* **RRF 融合**：对分数量纲不敏感，避免向量相似度与 BM25 分数不可比的问题；
* **级联重排**：TF-IDF 粗排 + LLM 精排的级联，图像块与文本块**同池竞争、无类型特权**。
  不给图像块加权是刻意的：加权会让所有问题都优先塞入图像块，反而稀释文本/表格的精度。

### 5.4 索引组织

| 索引 | collection | 内容 | 用途 |
|------|-----------|------|------|
| A（对照） | `wo04_text` | 文本 + 表格 | 工单03 水平 |
| B（实验） | `wo04_multimodal` | 文本 + 表格 + 图像语义块 | 工单04 完整版 |

两个索引共用同一份分块/检索/生成配置，唯一变量是"图像块是否入库"，
且 BM25 索引**按 collection 分文件保存**（`data/index/bm25_wo04_*.pkl`），
避免 `BM25Retriever.save()` 默认路径 `bm25.pkl` 造成的互相覆盖。

## 6. 消融实验设计（核心证据）

`src/compare_with_without_images.py` 执行 A/B 对照，评测 16 问：

* 变量控制：分块策略、检索参数（hybrid/rrf/cascade）、生成模型、问题集、判分口径全部相同；
* 判分口径：**答案要点全命中才算对**（数字写法容错：全角/半角、空格、破折号归一化）；
* 核心假设：
  * H1：id 5、id 6 在 A 组必错（信息不在文本层/表格层）；
  * H2：B 组两问答对，且总准确率提升；
  * H3：其余 14 问准确率不下降（图像块不构成干扰）；
  * H4：检索耗时基本不变（图像块数量远小于文本块）。

产出：`results/image_ablation.json` / `.md`，含总体对比表、逐题对照、两问的答案全文对照。

> 注意：id 5 的第一半（销售部 4 个部门）在正文第 40 页有一段文字描述
> （"销售部下设渠道销售部、电话及网络销售部、大客户销售部和国际贸易部"），
> 因此 A 组有可能答对第一半；但"大客户销售部有几个销售处"在正文中**完全没有对应描述**，
> A 组必然答不全。消融实验的判分要求两个数字都命中，故 A 组该题为错。

## 7. 性能与稳定性

### 7.1 响应时间

| 阶段 | 典型耗时 | 说明 |
|------|----------|------|
| 查询向量化 | 10~40 ms | bge-large-zh-v1.5，本地 |
| 向量检索 + BM25 + RRF + 级联重排 | 30~300 ms | 本地，随语料规模增长 |
| LLM 生成 | 1~8 s | DeepSeek API 网络往返 |
| **检索端到端（不含生成）** | **< 1 s，满足 ≤3 s** | 评测脚本分别统计两个口径 |

端到端 ≤3 s 的工程手段（已在共享库中就绪）：

1. `rag_core.llm` 的**磁盘缓存**：相同问题第二次提问直接命中缓存（毫秒级），
   评测/演示重复提问时可稳定达标；
2. **本地 Ollama 生成模型**（`config.OLLAMA_LLM_MODEL=qwen3:4b`）：无网络往返，可压到 3 s 内；
3. **流式输出**：首 token 时间 < 1 s，用户感知延迟大幅下降。

评估脚本同时输出 `retrieval_latency`（检索）与 `total_latency`（含生成）两项，
并统计 ≤3 s 的题目数，便于对照验收标准。

### 7.2 稳定性设计

* **单图容错**：任一张图抽取/渲染/解析失败只影响该图，不中断整批（`try/except` 逐张隔离）；
* **断点续跑**：语义解析结果**逐张落盘**到 `results/cache/semantic_cache.json`，
  进程中断后重跑自动命中缓存，不重复消耗多模态算力；
* **降级路径**：CLIP 不可用 → 全部走通用 prompt；VLM 不可用 → 图像块不入库并给出明确提示；
* **索引一致性**：建索引后校验 `向量条数 == BM25 文档数 == chunk 数`，不一致时脚本会显式打印；
* **服务健康检查**：`serve.py` 提供 `/api/health`（向量条数/BM25 篇数/图像数/运行时长）。
