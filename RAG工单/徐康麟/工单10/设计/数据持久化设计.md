## 2. 为什么运行期数据必须与索引卷分开（**实测踩坑**）

索引是**构建产物**，在容器里以 `:ro` 只读挂载 —— 这样能防止运行期误写坏索引。
但工单7 的 `QAEngine` 默认把 `qa_runtime.sqlite3` 放在 `cfg.paths.index_dir` 下：

```python
db_path = Path(app_cfg.paths.index_dir) / "qa_runtime.sqlite3"   # 工单7 原逻辑
```

**后果**：容器里 `index_dir` 是只读挂载 → 写 sqlite 会 `EROFS: read-only file system`。
本机等价验证时这个坑**真实复现了**（`DEPLOY_RUNTIME_DIR` 没设 → 回落到索引目录 → 索引目录里
真的多了 `qa_runtime.sqlite3` 和 `rag.sqlite3`，并把只读语义检查测挂）。

**解法**（`研发/service/api.py::Runtime.setup`）：

```python
db_dir = Path(self.deploy.runtime_dir)          # 独立可写卷：/app/data/runtime
if not _writable(db_dir):                       # 真实写探针，不是 stat
    fallback = Path(app_cfg.paths.index_dir)    # 兜底（裸 docker run 未挂 runtime 卷时）
    self._warn("api.runtime_dir_not_writable", path=str(db_dir), fallback=str(fallback))
    db_dir = fallback
db_path = db_dir / "qa_runtime.sqlite3"
```

并把 DEPLOY_RUNTIME_DIR 写进 `.env.example`、compose 与本地等价验证脚本，
健康检查里加 `checks.volume_runtime` 子项（**写探针**，不是 stat）—— 下次同类问题会立刻暴露。

## 3. 容器间数据共享的两条通路

```
                    ┌─────────────────────── 共享通路 ①（卷，最终一致）───────────────────────┐
                    │                                                                          │
  rag-api ──写──▶ rag-session 卷（/app/sessions/*.json）──读──▶ rag-ui / 新扩容的副本容器      │
                    │                                                                          │
                    └──────────────────────────────────────────────────────────────────────────┘
                    ┌─────────────────────── 共享通路 ②（Redis，实时）─────────────────────────┐
                    │                                                                          │
  rag-api ──写──▶ redis LIST  rag:finqa:session:<id>  (TTL 86400)  ──读──▶ rag-ui / 副本容器   │
                    │                                                                          │
                    └──────────────────────────────────────────────────────────────────────────┘
```

| 通路 | 一致性 | 依赖 | 降级行为 |
| --- | --- | --- | --- |
| ① 卷（JSON 文件） | 最终一致（`os.replace` 原子替换写） | 无（Docker 自带） | **永不可用不了** —— 这是"数据不丢失"的硬保障 |
| ② Redis LIST | 实时 | redis 容器 | 连续失败 3 次 → 熔断 30 s → 全程走通路 ①，`/health` 报 `backend=file` + 原因 |

**双写策略**：`SharedSessionStore.append()` **先写文件卷、再尽力写 Redis**。
顺序不能反 —— 若先写 Redis 而 Redis 卡住，文件卷就少了一轮对话，"不丢数据"就破功了。

**水平扩展含义**：新增一个 `rag-api` 副本时，只要挂上同一个 `rag-session` 卷 + 连同一个 Redis，
就能读到全部既有会话 —— 这正是验收里"便于扩展和维护"的落点。

## 4. 原子性与容错（为什么不丢数据）

| 场景 | 处理 |
| --- | --- |
| 写会话时容器被 `kill -9` | 先写 `<id>.json.tmp` 再 `os.replace()` 原子替换 → **磁盘上永远只有完整 JSON**，不会出现半截文件 |
| 会话文件损坏（人工编辑/磁盘错误） | `FileSessionStore._read` 捕获 `JSONDecodeError` → 按空会话处理并标记 `corrupt: true`，**不让问答 500** |
| 会话 id 含路径穿越字符（`../`） | `_path()` 做文件名消毒（只允许 `alnum -_.`，截断 80 字符） |
| 会话超过 `DEPLOY_SESSION_MAX_TURNS`（默认 20） | 只保留最后 N 轮（`ltrim` / 列表切片），防止单文件无限增长 |
| 会话过期 `DEPLOY_SESSION_TTL_S`（默认 86400） | 读时比对 `updated_at` 标记 `expired`（不物理删除，便于排障） |
| 日志卷不可写 | entrypoint **直接退出 exit 78**（EX_CONFIG）—— 日志是验收证据，不能悄悄丢 |
| 运行期卷不可写 | 问答**继续可用**，仅不记历史，写 WARNING 日志并降级到索引目录 |

## 5. 备份与恢复（运维视角）

```powershell
# 备份：索引（一次性，91MB）+ 会话 + 运行期 sqlite + Redis AOF
docker run --rm -v rag-finqa-session:/data -v ${PWD}/备份:/backup alpine `
    tar czf /backup/session-$(Get-Date -Format yyyyMMdd).tar.gz -C /data .
docker run --rm -v rag-finqa-runtime:/data -v ${PWD}/备份:/backup alpine `
    tar czf /backup/runtime-$(Get-Date -Format yyyyMMdd).tar.gz -C /data .

# 恢复：把 tar 解回一个新卷
docker volume create rag-finqa-session-restore
docker run --rm -v rag-finqa-session-restore:/data -v ${PWD}/备份:/backup alpine `
    tar xzf /backup/session-20261012.tar.gz -C /data
```

> 索引不需要频繁备份：它由工单7 的语料 + 建索引流程可重建（`index_manifest.json` 里记录了
> `source_hashes`，可校验语料是否被换过）。

## 6. 卷的生命周期与回滚

| 操作 | 命令 | 卷 | 数据 |
| --- | --- | --- | --- |
| 停服务（**默认**） | `pwsh -File 部署/脚本/down.ps1` | **保留** | ✅ 不丢 |
| 删容器重建 | `docker compose up -d --force-recreate` | 保留 | ✅ 不丢 |
| 删除镜像 | `docker rmi rag-finqa:1.0.0` | 保留 | ✅ 不丢 |
| 显式删卷（⚠️） | `pwsh -File 部署/脚本/down.ps1 -RemoveVolumes` | 删除 | ❌ 需二次确认（输入 `yes`） |

**回滚语义**：`down.ps1` 只停容器不删卷，因此"回滚到上一个镜像版本"只需
`docker compose up -d` 换标签重建 —— 会话/日志/运行期数据全在，用户无感。
