## 2. Dockerfile 逐段说明（为什么这么写）

### 2.1 阶段一 `builder`

```dockerfile
FROM python:3.11-slim AS builder
RUN ... apt-get install build-essential python3-dev ...     # 只为编译 wheel
COPY 部署/docker/requirements.txt ./requirements.txt
RUN pip wheel --wheel-dir /wheels -r requirements.txt        # 产出 .whl，不装进本阶段
```

**动机**：`faiss-cpu` / `numpy` / `pymupdf` 在无预编译 wheel 时需要 gcc/g++。
若在最终镜像里装编译链，会额外带入 **gcc/g++/make/python3-dev 约 300~400 MB**（真实实测见
`优化/评估结果/镜像体积对比.json`）。多阶段把这些留在 builder，runtime **一个字节都不带**。

**国内镜像源**：APT 与 pip 全部改清华源（`ARG PIP_INDEX_URL`）——
本机在未提权沙箱下访问 pypi 官方源曾出现长时间无响应，属实测踩坑（`部署/过程问题记录.md` 问题3）。

### 2.2 阶段二 `runtime`

```dockerfile
FROM python:3.11-slim AS runtime
ENV TZ=Asia/Shanghai LANG=C.UTF-8 LC_ALL=C.UTF-8
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 PYTHONIOENCODING=utf-8 PYTHONUTF8=1
RUN apt-get install -y --no-install-recommends tzdata fonts-wqy-zenhei libgomp1 ca-certificates
RUN groupadd -g 10001 rag && useradd -u 10001 -g 10001 -m -s /bin/bash rag
COPY --from=builder /wheels /wheels
RUN pip install --no-index --find-links=/wheels -r /tmp/requirements.txt
COPY 研发/app ./app
COPY 研发/service ./service
COPY 部署/docker/entrypoint.sh /usr/local/bin/entrypoint.sh
COPY 部署/docker/healthcheck.py /usr/local/bin/healthcheck.py
VOLUME [...]
USER rag
EXPOSE 8200 8201
HEALTHCHECK --interval=30s --timeout=5s --start-period=90s --retries=3 CMD ["python","/usr/local/bin/healthcheck.py"]
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["uvicorn","service.api:app","--host","0.0.0.0","--port","8200"]
```

逐条理由：

| 指令 | 理由（都是踩过坑的） |
| --- | --- |
| `TZ=Asia/Shanghai` + `tzdata` | 日志时间戳必须与业务/验收时间对得上；slim 镜像默认没有 tzdata |
| `fonts-wqy-zenhei` | 中文年报文本、中文日志渲染不能出豆腐块；wqy 文泉驿开源可商用 |
| `libgomp1` | **faiss 运行时依赖 OpenMP**，缺了会在 `import faiss` 时报 `libgomp.so.1: cannot open shared object file` |
| `PYTHONUNBUFFERED=1` | 不加则 stdout 被块缓冲，`docker logs` 长时间空白 —— 直接违反"运行过程无异常日志输出"的可观测前提 |
| `PYTHONDONTWRITEBYTECODE=1` | 容器内不需要 `.pyc`；只读挂载的代码目录也能避免写失败 |
| `--no-index --find-links=/wheels` | **离线安装**：保证 runtime 阶段不再联网（构建可复现 + 不受网络抖动影响） |
| `useradd -u 10001`（固定 uid） | 绑定挂载的宿主目录属主可预测；不同机器上 uid 不漂移 |
| `VOLUME` 声明 | 即便有人用 `docker run` 裸跑（不用 compose），日志/会话/索引也会自动落到匿名卷而不是容器可写层 |
| `start-period=90s` | 基座实测冷启动 **27.3 s**（全文索引 20.1 s + 实体标注 2.1 s + 索引载入），给足余量 |
| `ENTRYPOINT` + `CMD` 分离 | UI 容器直接覆盖 `command` 即可复用同一镜像，无需第二个 Dockerfile |

### 2.3 为什么 `healthcheck.py` 用标准库而不是 `curl`

`python:3.11-slim` 不自带 curl；为探活装一个 curl 属于"为一行命令引入一个包"。
`urllib.request` 是标准库，脚本 30 行，且**能自己决定退出码语义**（0=healthy / 1=unhealthy）。
同时它对异常做了全兜底，不会把栈打到容器日志里污染"无异常日志"这条验收。

## 3. 依赖闭包（`部署/docker/requirements.txt`）

```
numpy==1.26.4          # 向量读取（vectors.npy）与相似度运算
faiss-cpu==1.8.0       # 工单7 索引是 faiss:IndexFlatIP，必须装
fastapi==0.109.0       # 对外 API
uvicorn[standard]==0.27.0  # ASGI 服务器（standard 带 uvloop/httptools，Linux 上更快）
pymupdf==1.24.14       # app.core.pdf_parser 顶层依赖 fitz
jieba==0.42.1          # 中文分词（BM25/查询理解）
redis==5.0.8           # 会话跨容器共享（可选依赖，缺失自动降级文件卷）
```

**故意不装**（这是体积优化的最大一笔，约 2~3 GB）：

| 未装 | 原因 |
| --- | --- |
| `torch` / `transformers` / `open_clip_torch` | 只在 `app/core/multimodal_encoder.py` 里**延迟导入**（该模块负责本地 CLIP 编码）；本方案图文向量统一由**宿主机 Ollama** 提供 |
| `sentence-transformers` | 只在 `embedder.py` / `retrieval_strategy.py` 的 `cross_encoder` 分支里延迟导入；默认链路走 Ollama 嵌入 |
| `streamlit` | 工单7 的 Web 界面有**纯标准库兜底实现**（`app/ui/serve_fallback.py`），无需 streamlit |
| `pandas` / `matplotlib` | 业务链路的解析与统计均用标准库 + numpy 实现，未依赖 |

> 校验方式：`测试/测试脚本/test_07_部署制品.py::test_requirements覆盖业务代码真实import`
> 会扫描 `研发/app` 与 `研发/service` 的**顶层 import**，确保镜像里没漏装必需包
> （延迟导入/可选依赖已在测试里显式白名单化）。

## 4. 一个镜像跑两个服务

```yaml
rag-api:  command: ["uvicorn","service.api:app","--host","0.0.0.0","--port","8200"]
rag-ui:   command: ["python","/app/app/main.py","--serve","--host","0.0.0.0","--port","8201"]
```

**为什么**：UI 与 API 必须共享同一份业务代码与同一份索引；两个 Dockerfile 会带来
"版本漂移"风险（UI 修复没同步到 API）。一个镜像换命令行，从结构上消除这种可能。

## 5. 构建产物与层复用

| 层 | 变化频率 | 说明 |
| --- | --- | --- |
| apt 系统包 | 极低 | 放在最前，缓存命中率最高 |
| pip wheel 安装 | 低（改 `requirements.txt` 才变） | 与源码分离，改代码不必重装依赖 |
| `COPY 研发/app` / `研发/service` | **高** | 放在最后，日常改代码只重建这一层 |

`优化/评估结果/镜像体积对比.json` 里给出了"改一行源码重建"与"全量冷构建"的耗时差（真实实测）。

## 6. 单机验证 `docker run`（不使用 compose）

```powershell
docker build -f 部署/docker/Dockerfile -t rag-finqa:1.0.0 .

docker run -d --name rag-api `
  -p 8200:8200 `
  -e RAG_LLM__OLLAMA_BASE_URL=http://host.docker.internal:11434 `
  --add-host host.docker.internal:host-gateway `
  -v rag-finqa-index:/app/data/index:ro `
  -v rag-finqa-log:/app/logs `
  -v rag-finqa-session:/app/sessions `
  -v rag-finqa-runtime:/app/data/runtime `
  --memory 2g --cpus 2 `
  --restart unless-stopped `
  rag-finqa:1.0.0

docker inspect --format '{{.State.Health.Status}}' rag-api
Invoke-WebRequest http://127.0.0.1:8200/health -UseBasicParsing
```

> 这一步对应验收标准 2.1「使用 `docker run` 命令能够成功启动容器，并在指定端口提供服务」。
> compose 只是把这串参数文件化，两者产出的容器完全一致。
