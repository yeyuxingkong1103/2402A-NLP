## §2 方案设计

### 2.1 先说清楚「多轮」到底难在哪

前四份工单做的都是**单轮**：一句话进来，理解它、检索它、回答它，下一句话和它没有关系。
多轮要解决的，是下面这两种**单独拿出来就没法检索**的话：

```
Q2  他参与的哪个工程荣获了国家科技进步一等奖？
    ↑ 没有上下文，「他」在库里检索不到任何东西

Q4  那武汉力源信息技术股份有限公司呢？
    ↑ 有主体、没有谓词。系统不知道要问「法人？注册资本？发行股数？」
```

所以要做两件事：

* **指代消解**：把「他 / 这个公司 / 该公司 / 其」换成前文真正指代的那家公司。
* **省略补全**：把上一轮问的「事」（谓词）搬到这一轮的新主体上。

### 2.2 三层结构（每层只做一件事）

```
┌─ 第 1 层：会话状态  src/session.py ────────────────────────────┐
│  记住每轮的语义槽位：主体(subject) / 话题(topic) /               │
│  消解后问句(resolved)。存「原话 + 答案」是不够的 ——               │
│  真正要传承给下一轮的是这三个槽位。                              │
└────────────────────────────────────────────────────────────┘
                              ↓
┌─ 第 2 层：上下文消解  src/dialogue.py ─────────────────────────┐
│  输入：本轮原话 + 会话状态                                       │
│  输出：一个**自包含的检索式**（如「武汉力源…的法定代表人是谁」）   │
│  四种模式（也是消融的四个臂）：                                   │
│    off       不看历史（工单前行为）                              │
│    concat    把历史原话拼上去（朴素做法）                        │
│    rule      纯规则消解，一次 LLM 都不调                        │
│    rule+llm  规则优先 + 规则不确定时 LLM 兜底 ← 交付配置         │
└────────────────────────────────────────────────────────────┘
                              ↓
┌─ 第 3 层：检索层的两道主体消歧（本工单新增，见 §4）──────────────┐
│  doc_filter      硬排除「不是本轮主体」的那份文档                 │
│  subject_first   同文档内，含主体名的块排序置顶 + 放宽绝对闸门    │
└────────────────────────────────────────────────────────────┘
```

**为什么必须有第 3 层**：这是本工单最重要的一个发现——
光把检索式写对，**召回回来的内容仍然是别人的**。详见 §4.2 / §4.3，那里有完整的数据。

### 2.3 一个刻意的设计约束：不传 session_id 就完全是单轮

`/api/ask` 只有在请求体里带了 `session_id` 时才走多轮。
不带的话，行为与工单1~4 **逐字节一致**。

理由有二：
1. 前三份工单的所有评测结论、消融基线都必须继续成立，多轮不能悄悄改变既有语义；
2. 界面上可以直接 A/B：同一句话，开关一下就有对照。

| 文件 | 职责 | 工单编号注释 |

| `src/rag.py` | `answer()`/`answer_stream()` 透传 session/mode；`_dialogue_doc_filter()`、`_dialogue_subject_terms()`、`_record_turn()` | ✅ |

| `main.py` | `/api/ask`、`/api/ask/stream` 支持多轮；新增 3 个会话接口 | ✅ |
| `static/index.html` | 多轮开关 / 模式选择 / **上下文面板** / 一键连播 5 轮 / 清空上下文 | ✅ |

三个值得单独说一句的实现点：

**（1）省略补全用「上一轮的完整问句换主体」，而不是「主体 + 话题」拼句子**
`src/dialogue.py::_reuse_pattern()`。
拼句子会丢掉疑问焦点（实测拼出「武汉力源信息技术股份有限公司**占比**」这种半截式子）；
把上一轮「武汉兴图…的法定代表人是谁？」整句换主体，得到的是结构完全对齐的新问句。

**（2）规则可信度用「试检索依据分」判定，够了就不调 LLM**
规则候选先拿去试检索一次，依据分 ≥ 0.75 就认为规则搞定了（`MULTITURN_RULE_MIN_EVIDENCE`）。
这样 `rule+llm` 在规则能搞定的时候**根本不调 LLM**，响应时间和纯规则一样快。
实测 23 轮里多轮层真正触发 LLM 兜底的只有 D5 第 2 轮。

**（3）轮次回写收归在 `rag.answer()` 内部**
`_record_turn()`。会话状态是「系统理解了什么」的权威记录，漏写会让下一轮无从消解，
而这类疏漏是**静默**的——不报错，只是答案慢慢变差。放在链路内部，任何入口都忘不掉。

## §4 踩坑记录（这一节是本文档最有价值的部分）

下面每一个问题都是**实测定位到的**，不是设计推演。每一个都给出证据数据。

### 4.1 消融实验一开始「四臂全是 100%」——实验本身是无效的

**现象**：`T0 off`（完全不做多轮）在 5 轮原题上也是 100%，四臂无差别。

**根因**：`report_wot5.py` 调 `rag.answer()` 时**没传 `mode`**，于是每一臂都用
`config.MULTITURN_MODE` 的默认值（rule+llm）。看 `T0` 臂的检索式就露馅了——
它明明应该保留「他」，实际却是消解后的「武汉兴图新科电子股份有限公司参与的…」。

**修法**：显式传 `mode`。修完 `T0` 立刻掉到 43.5%。

**教训**：消融脚本改了配置却没生效，这类 bug **不会报错、只会让实验看起来很成功**。
判据是「对照臂是否出现了应有的失败」——如果连 `off` 都满分，先怀疑实验而不是庆祝。

### 4.2 力源法定代表人答成「宋丽萍」——同一份文档里也有主体不符的块

**现象**：第 4 轮「那武汉力源信息技术股份有限公司呢？」答成**宋丽萍**。

**两层根因**：
1. 生成阶段喂的是用户**原话**「那武汉力源…呢？」（没有谓词），模型不知道在问什么；
2. 更硬的：力源的召回里混进了**兴图新科**的块，占了 5/8 个上下文名额，
   把正确答案挤出 top-8。

**第二层的修法**：`doc_filter`——多轮确定主体后**硬排除**另一份文档。
注意 `doc_hint`（工单2 已有的能力）**不管用**：它只是「加池 + 加分」，不排除。

### 4.3 `doc_filter` 写好了却不生效——它被 CLIP 通道绕过了

**现象**：明明传了 `doc_filter=['liyuan']`，召回里还是出现了 `xingtu p534`。

**根因（很值得记）**：`doc_filter` 原本放在检索流程的 **3b** 步，
而 **3c CLIP 跨模态召回在它之后**，会把图像块**追加**进候选池，追加动作不看 `doc_filter`。
于是「法定代表人」这类问题会命中华东另一家的**证照照片**——营业执照上就印着法定代表人，
CLIP 语义天然相近——把刚排除掉的文档又放了回来。

**修法**：排除动作必须发生在**所有**入池通道（稠密 / 稀疏 / doc_hint / CLIP）都跑完之后。
代码里已注明这个位置要求。

### 4.4 权威页被闸门砍掉，干扰块却 BM25 满分（本工单最硬的一个问题）

修完 4.2/4.3 后，**T4 反而从「对」变成「错」**——这说明之前是**靠运气蒙对的**，
现在池子干净了，问题才真正暴露出来。

开闸门看全部候选（`apply_gate=False`），数据是这样的：

| 排名 | 页 | 依据分 | 内容 | 是否权威 |
|---|---|---|---|---|
| 1 | **p26** | **0.787** | `(六)申请上市证券交易所：深圳证券交易所 法定代表人：宋丽萍` | ❌ **干扰项** |
| 2 | p343 | 0.752 | 董事监事声明的签名栏（含「赵马克」） | △ 能蒙对，不是权威页 |
| 4 | p23 | 0.730 | 「12、信息披露…负责人：王晓东」 | ❌ 同页另一块 |
| 5 | **p23** | **0.722** | **`一、发行人的基本情况 …4、法定代表人：赵马克`** | ✅ **权威块** |

两个致命点：

1. **权威块 0.7219 < 闸门 0.75 → 被砍掉**。它和低排名的块一起消失了。
2. **干扰块 p26 BM25 归一后满分 1.0，排第一**。它字面完美匹配「法定代表人」，
   但它答的是**深交所**的法定代表人。稠密向量也救不了——p26 通篇在讲
   「法定代表人：宋丽萍」，语义上确实"更像"。

**这不是调参能解决的问题**，是判据缺失：问「X 的法定代表人」，答案所在块**必然同时出现 X 和「法定代表人」**，
而这一点只有多轮层知道（主体可能是继承来的）。

**修法（两步，都有明确理由）**：

| 步骤 | 做法 | 理由 |
|---|---|---|
| ① 主体一致性排序主键 | 「块文本是否含本轮主体名」作为**排序主键**，先分组、组内再按分排序 | 「主体对不对」是硬条件，不是可权衡的偏好，所以不给可调权重 |
| ② 放宽绝对闸门 | 主体已锁定时闸门 0.75 → **0.70** | 0.75 是工单2 为**多文档通用场景**设的离题防线；主体已锁定时离题风险已被前置条件消除，再拿通用闸门砍，砍掉的是真正相关但表述偏长的权威块 |

**修完的效果**（同一个问题，同一个检索式）：

```
引用页：liyuan p23 (0.7296) / liyuan p23 (0.7219) / liyuan p15 (0.7076)
        / liyuan p26 (0.7872) / liyuan p343 (0.7516)
答案：  武汉力源信息技术股份有限公司的法定代表人是赵马克。[第23页][第15页]
```

分最高的干扰块 p26 被**压到第 4 位**，权威页 p23 置顶。
**答案从「靠 p343 签名栏蒙对」变成「靠权威页答对」**——这才是可交付的质量。

消融也印证了这两步的分量（§7 实验 B）：
关掉 `doc_filter` → 100% 掉到 **69.6%**；关掉 `subject_first` → 掉到 **73.9%**。

### 4.5 QU 改写把答案写进检索式

**现象**：改写结果出现「武汉兴图新科电子股份有限公司的法定代表人**是何伟**」——
答案被"猜"进了检索式。这类改写会让检索只找得到已知答案，**失去查证意义**。

**修法**：`query_understanding.py::_leaks_answer()` 做确定性丢弃 + 回落原话。
首版正则 `[\u4e00-\u9fa5A-Za-z0-9]{2,12}` 漏了数字里的逗号/小数点，放宽为 `\S{2,16}` 后 6/6 用例通过。

### 4.6 话题表缺「控股股东」，被「持股比例」误判成「占比」

问「控股股东是谁？**持股比例**是多少？」时，话题被判成**占比**。
下一轮省略补全就拼出「XX**占比**」这种没谓词的式子，实测漏答。

修法：`_TOPIC_TABLE` 补 `控股股东/实际控制人/控制人`，且**必须排在「占比」之前**
（否则「比例」二字先被「占比」抢走）。

### 4.7 评测集自身的标注错误（如实记录）

D4 第 3 轮我最初在 `must_have` 里要求了「25.04%」，实测判 NG。

核查后确认是**标注与继承语义不一致**：上一轮只问了「发行股数是多少」，
本轮省略补全继承的谓词就只有股数，问不到比例——系统没错，是我的要求不存在。
已修正 `must_have`，并在评测集里写明原因。

**不放水原则**：这一处是标注错误，其他失败一律保留并归因（见 §9 已知局限）。

## §6 评测结果

**评测集**：`data/eval/questions_wot5.json` —— 5 场对话 / **23 轮**
（工单原题 5 轮 + 4 场追加设计：指代链、省略追问、长链路、规则兜底用例）

## §7 消融实验

脚本：`scripts/ablation_dialogue.py`，产物 `data/eval/工单5_多轮消融_*`。
两组都是**单变量**，各跑 23 轮 × 每臂。

### 实验 A：消解方式 —— 回答「多轮到底有没有用」

| 臂 | 模式 | 说明 | 准确率 | 主体 | 关键事实 | 答案页 |
|---|---|---|---|---|---|---|
| **T0** | `off` | 完全不看历史（**工单前系统的行为**） | **43.5%** (10/23) | 60.9% | 60.9% | 56.5% |
| T1 | `concat` | 把历史原话拼上去，不做消解 | 69.6% (16/23) | 91.3% | 69.6% | 65.2% |
| T2 | `rule` | 纯规则消解，零 LLM 成本 | 87.0% (20/23) | 91.3% | 87.0% | 91.3% |
| **T3** | `rule+llm` | 规则优先 + LLM 兜底（**交付配置**） | **100%** (23/23) | 100% | 100% | 100% |

**单调递进 43.5% → 69.6% → 87.0% → 100%**，每一层都实打实贡献。

`T0` 的失败模式很有代表性，值得单独看：

* 「他」「这个公司」没被替换 → 检索式带代词，且**主体判定错** → 答案串到另一家公司
  （问兴图的法人答成力源的赵马克，反之亦然）；
* 「那X呢」没有谓词 → 检索「那武汉兴图新科电子股份有限公司呢」→ 召回一堆财务数据块
  → 模型开始**编造财务指标**（完全答非所问）；
* 连**单轮自包含题**也受影响（D3 T1「兴图的法定代表人是谁」→「资料中没有相关内容」），
  因为没有 `doc_filter`，力源噪音占满了上下文名额。

`T1 concat` 的失败则是**语义稀释**：检索式变成
「…的法定代表人是谁？武汉力源…的法定代表人是谁？」，两句话搅在一起，哪句都没匹配好。

### 实验 B：子优化项 —— 回答「哪一步在起作用」

在 T3 的基础上逐个关掉本工单新增的检索层优化：

| 臂 | 说明 | 准确率 | 答案页 |
|---|---|---|---|
| **B0** | 全开（交付配置） | **100%** (23/23) | 100% |
| B1 | 关 `doc_filter`（不硬排除另一份文档） | **69.6%** (16/23) | 78.3% |
| B2 | 关 `subject_first`（不做同文档内主体消歧） | **73.9%** (17/23) | 78.3% |

这两项都不是拍脑袋加的：B1 对应 §4.2、B2 对应 §4.4，关掉它们就能在
**同一批题上复现当初定位到的那个问题**。

### T2 与 T3 的关系（说清楚，避免误读）

D1~D4 上 T2、T3 **行为完全一致**（规则全解对了，LLM 兜底一次都没触发）。
差别只来自 D5——那是**专门设计的规则解不了的用例**：

```
D5：  1) 兴图的法定代表人是谁？            → 程家明
      2) 那另一家呢？                      → 需要理解「另一家 = 上一家之外的那家」
      3) 他的控股股东是谁？持股比例是多少？   → 验证第 2 轮补出的主体能否继续传承

T2 rule      33.3%（1/3）  ← 「另一家」不在指代词表里，规则降级
T3 rule+llm  100%（3/3）   ← LLM 读上下文推出「力源」，且主体正确传承到第 3 轮
```

> 顺带一个诚实的记录：在 D1 上 T3 曾出现过 19/20、T2 是 20/20。
> 核查后确认那一次失败是**生成层的偶发笔误**（把「扩充」写成「充扩」），
> 且该轮 `llm_used=False`——规则没触发 LLM。所以**不是 T3 比 T2 差**。

## §9 已知局限与遗留

### 9.1 指代只回溯「公司」，不回溯「上一轮答案里的人名」

例：上一轮答完「赵马克」，这一轮问「**他**持有多少股份？」
系统会把「他」解析成上一轮的**主体**（力源公司），而不是答案里的赵马克，
于是检索式变成「力源的法定代表人持有的股份比例」→ 答偏。

这是明确的边界，**不是 bug**：当前会话只存主体/话题槽位，没有把答案中的实体也抽出来。
要支持需要在会话里再加一层「上轮提到的实体」槽位。

### 9.2 「另一家」这类表达依赖 LLM 兜底

`rule` 模式下「那另一家呢？」会降级（§7 D5）。
`rule+llm` 能解，但**多花一次 LLM 往返**（实测该轮 1.86 s，仍在 3 s 内）。

### 9.3 生成层的偶发笔误会影响评测数字

如 §7 末尾记录的「扩充 → 充扩」。这类失败与多轮设计无关，
但会被确定性判据记成 NG。看到单轮偶发 NG 时，先核对该轮 `llm_used` 与检索式是否一致。

### 9.4 英文：能问答，但**多轮消解不支持**（实测，非推断）

工单验收要求「支持中英文」，这里如实说明边界。三组实测：

| # | 输入 | 实测结果 |
|---|---|---|
| 1 | `What is the registered capital of Wuhan Xingtu Xinke Electronics Co., Ltd.?` | ✅ 正确。QU 把它改写成中文检索式「武汉兴图新科电子股份有限公司的注册资本」，答 5,520 万元，英文作答 |
| 2 | 上一轮问兴图注册资本，再问 `Who is its legal representative?` | ⚠️ 答对（程家明），但**是蒙的**：消解层 `coref=false`、`subject=''`，两道主体消歧都没启用，靠 QU 改写默认落到第一份文档 |
| 3 | 上一轮问力源（英文名 `Wuhan P&S Information Technology Co., Ltd.`），再问 `Who is its legal representative?` | ❌ 系统明确答「**无法确定『其』指代的对象**」 |

第 3 组是决定性证据：英文代词（`its` / `it` / `that company`）**不在**指代正则里
（`他|她|它|他们|该公司|这家公司|这个公司|…`），英文的指代与省略**不会被识别**。

另外第 3 组还暴露一个更基础的问题：**英文公司名 → 中文主体的映射不可靠**——
「Wuhan P&S Information Technology Co., Ltd.」（力源的英文名）被改写成了
「武汉兴图新科电子股份有限公司」，直接答成"资料中没有相关内容"。

**结论**：英文**自包含问题**可以正常问答（走同一链路，QU 会译成中文检索式）；
英文的**多轮指代/省略目前不支持**。要支持需要两件事：
① 指代/省略各加一组英文正则并按语种分流；② 补一份英文公司别名表。

**联调中发现并修掉的两个真问题**：

1. `/api/session/stats` 被 `/api/session/{session_id}` 抢先匹配（FastAPI 按声明顺序），
   返回「会话 stats 不存在」。修法：把 `stats` 声明在路径参数之前。
2. `retrieval_query` 是 `@property`，不在 `to_dict()` 里，界面拿不到「实际生效的检索式」。
   修法：`to_dict()` 补回该派生字段（它与 `rewritten` 可能不同——命中答案泄漏时会被丢弃并回落）。
