# 研发说明

## 1. 研发目标

系统采用“离线建库 + 在线问答”双链路设计：离线链路把文档变成可检索知识，在线链路根据问题召回证据并生成带来源的回答。API 层只负责协议适配和范围控制，核心业务集中在可复用的服务类中。

## 2. 核心研发链路

### 2.1 离线链路

1. `parser.py` 根据扩展名或显式策略解析文件；
2. `dataset_cleaner.py`、`dataset_dedup.py` 处理 JSONL 数据质量和重复问题；
3. `chunker.py` / `chunk_strategies.py` 按策略生成文本块；
4. `embedding.py` 调用 BGE-M3、HTTP 或 Mock Embedding；
5. `indexer.py` 将向量写入 Milvus，将文档和块元数据写入 MySQL；
6. SHA256 和内容哈希用于避免重复索引，`force_reindex` 可覆盖默认去重行为。

### 2.2 在线链路

1. `security_middleware` 建立请求身份并执行鉴权、限流；
2. `ChatService` 统一编排历史加载、Query 改写、召回、重排、Prompt、LLM 和后处理；
3. `HybridRetriever` 合并 Dense 和 BM25 结果，按知识库、租户等条件过滤；
4. `RerankingRetriever` 按配置进行精排和阈值判断；
5. `RAGStreamingPipeline` 将相同业务链路适配为 SSE；
6. `chat_memory.py` 将会话轮次保存至 Redis，并通过 `MemoryManager` 归档长期记忆。

## 3. 设计原则

- **统一业务入口**：`/chat` 和兼容接口最终复用 `ChatService`，避免两套问答逻辑漂移；
- **依赖可替换**：Embedding、LLM、Reranker、Vector Store 都通过构建函数按环境变量选择；
- **失败可解释**：依赖不可用返回 503，参数错误返回 400，避免把基础设施问题伪装成业务错误；
- **范围由服务端决定**：用户、租户、知识库和会话访问范围不信任请求体；
- **先证据后生成**：没有足够相关上下文时走拒答/兜底，不让模型凭空回答；
- **配置外置**：密钥、地址、模型和阈值通过 `.env` 管理，敏感配置不进入源码。

## 4. 数据模型

### 文档与知识库

- `knowledge_bases`：知识库名称、租户、所有者、设置和状态；
- `documents`：文档 ID、文件名、SHA256、来源、状态和所属知识库；
- `document_chunks`：文本块、块哈希、页码、来源和所属文档；
- Milvus 文档集合：块 ID、向量和用于过滤的租户/知识库/角色字段。

### 会话与记忆

- `sessions`：会话身份、角色、状态和时间；
- `role_switch_logs`：角色切换审计记录；
- Redis `session:<id>:messages`：短期消息列表；
- Milvus 长期记忆集合：用户偏好、重要事实和跨会话摘要。

## 5. 配置分层

| 配置类别 | 关键变量 |
|---|---|
| 应用 | `APP_ENV`、`API_HOST`、`API_PORT`、`API_PREFIX` |

| RAG | `RAG_TOP_K`、`RAG_RERANK`、`RAG_SIMILARITY_THRESHOLD` |

## 6. 当前实现边界

- Mock 模式适合开发，但不能作为生产答案质量依据；
- Redis 和 MySQL 是会话管理的必要依赖，缺失时会话接口降级为 503；
- 外部 Embedding 使用 Milvus 时，需要保证向量维度与集合 Schema 一致；
- 多进程部署时，内存中的限流计数不是全局共享，应在高并发生产环境前置网关限流；
- `docs/` 中部分阶段文档是方案或历史记录，实施状态以当前 `app/` 代码为准。
