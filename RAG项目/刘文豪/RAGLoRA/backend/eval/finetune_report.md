# bge-m3 嵌入微调评估报告

> 日期：2026-09-20
> 训练对：2390 条（LLM 从语料生成）　可训练参数：50.4M / 567.8M（8.87%）
> 训练：5 epoch / 375 步 / 236 秒，loss **0.4762 → 0.2671 → 0.2228 → 0.2001 → 0.1819**

---

## 一、结论（先说结果）

**微调没有提升检索指标 —— 但这不是微调的问题，是评测集没有提升空间。**

| 语料规模 | 原模型 | 微调后 | 变化 |
|---:|---:|---:|---:|
| 800 条 | 75.0% | 75.0% | **+0.0 pp** |
| 14319 条（全量） | 85.0% | 85.0% | **+0.0 pp** |

逐题比对：**改善 0 题，变差 0 题**（两次实验、两种规模均如此）。

---

## 二、为什么没有提升：可提升空间本来就是 0

### 2.1 那 15% 的失败全是语料缺口

20 道法律题里失败的 3 题是：

| # | 问题 | 期望来源 |
|---:|---|---|
| 4 | 劳动合同应当以什么形式订立？ | 中华人民共和国劳动合同法 |
| 5 | 试用期最长可以约定多久？ | 中华人民共和国劳动合同法 |
| 14 | 公司拖欠工资，员工可以怎么维权？ | 中华人民共和国劳动法 |

而全量语料 176 部法律中，**`law_name` 含「劳动」的条数为 0**：

```
law_name 含「劳动法」     -> count(*) = 0
law_name 含「劳动合同法」  -> count(*) = 0
law_name 含「劳动」       -> count(*) = 0
```

**《劳动法》《劳动合同法》根本不在知识库里。** 这三题不可能被任何检索模型救活 ——
问题不在「找得准不准」，而在「文档不存在」。

### 2.2 可回答的题目本来就是 100%

去掉这 3 道语料缺口题，剩下 **17 题原模型全部命中（17/17 = 100%）**。

**没有可提升的空间。** 微调在一个已经满分（在可回答范围内）的基准上无法体现收益。

---

## 三、微调本身是成功的（技术层面）

「指标没变」不等于「训练没生效」。实测确认权重确实改变了：

| 检查 | 结果 |
|---|---|
| 有差异的张量 | **30 / 391** |
| `encoder.layer.0`（首层，应冻结） | 差异 **0.000000** ✓ |
| `encoder.layer.23`（末层，应训练） | 差异 **0.003147** ✓ |
| 编码结果 | 余弦相似度 **0.985**（确实变了） |
| 训练 loss | 0.4762 → **0.1819**（稳定下降） |

冻结策略按设计生效：只有末 4 层 + 池化被训练，其余 361 个张量原封不动。

---

## 四、⚠️ 为什么没用 peft / LoRA

环境里的 `peft 0.19.1` **装了但用不了**：

```
ImportError: cannot import name 'EncoderDecoderCache' from 'transformers'
```

peft 0.19 需要更新的 transformers，而本项目锁定 `transformers==4.39.3`
（升级会破坏版本链 —— 本项目已因 FlagEmbedding / ragas 踩过两次同类问题）。

因此改用**层冻结**：只训练最后 N 层，其余 `requires_grad = False`。
与 LoRA 同属参数高效方法，且**零新增依赖**。

优化器用 **SGD 而非 AdamW**：bge-m3 有 5.7 亿参数，AdamW 的动量+方差状态
是参数量的 2 倍（fp32 下约 4.5GB），本机 8G 显存下不可行。

---

## 五、池化方式：实测后确认不改

`bge-m3/1_Pooling/config.json` 声明的是 **CLS 池化**：

```json
{"pooling_mode_cls_token": true, "pooling_mode_mean_tokens": false}
```

而 `embed.py` 用的是 **mean pooling** —— 生产链路一直在用与模型设计不符的池化。

**已实测两者差异**：

| 池化 | 来源命中率（800 条语料） |
|---|---:|
| CLS | 75.0% |
| mean | 75.0% |

**完全相同。** 该偏离经实测不构成本问题，不需要改生产配置。
（复现：`python scripts/check_pooling.py`）

---

## 六、诚实的结论与建议

**对本项目而言，嵌入微调没有带来可测量的检索提升。** 原因明确：
**评测集的可提升空间是 0**（失败题全是语料缺口，可回答题已 100%）。

要真正评估微调的收益，需要先满足其中一个条件：

1. **补上语料缺口** —— 把《劳动法》《劳动合同法》等加进知识库，
   让评测集有 20 道**可回答**的题；或
2. **构造更难的评测集** —— 当前 20 题相对 14319 条语料偏简单，
   可以加「易混淆」题（如同法不同条文、相似表述），这类题才有区分度。

**答辩时的正确说法**：

> 「嵌入微调的技术链路已跑通（层冻结 + InfoNCE，loss 0.48→0.18，权重确认改变），
> 但**在当前评测集上测不出检索提升** —— 因为剩余失败全是语料缺口
> （劳动法不在 176 部法律中），可回答的 17 题基线已是 100%。
> **没有提升空间的情况下，我们不把『指标持平』包装成优化成果。**」
