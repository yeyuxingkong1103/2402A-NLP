## 4. 链路对照（性能维度）

| 链路 | 平均耗时 | 最大耗时 | 是否满足 ≤ 3 s |
|---|---|---|---|
| **optimized**（优化后 + 抽取式） | **0.29 s** | **0.53 s** | ✅ |
| baseline_extractive（优化前检索 + 抽取式） | 1.08 s | 11.82 s | ❌（单题超时） |
| optimized_llm（优化后检索 + 本地 LLM 生成） | 4.87 s | 8.92 s | ❌ |

**结论**：延迟瓶颈不在检索，而在**答案生成**。本地小模型逐题生成需 3~9 s；
改为**抽取式合成**后，全链路稳定在亚秒级。

> 注：上表为 `python evaluate.py --ablation` 消融实验**同一轮**运行的结果，用于三条链路的横向对照；交付默认链路的独立评测为平均 0.41 s、最大 2.46 s（见 `研发/output/eval_results.json`）。两者差异来自机器负载波动，均满足 ≤ 3 s。

## 5. 冷启动与预热

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 进程级模型加载（向量库 + BM25 + Chinese-CLIP 权重 399 个张量） | 13.58 s | 一次性开销，与单题响应无关 |
| 单题问答（预热后） | 0.20 ~ 2.46 s | 计入验收 |

系统提供 `QAEngine.warmup()`：启动后先跑通一次完整链路，把 FAISS/BM25/CLIP 的
进程级冷启动开销前置，保证**计时口径只反映真实查询性能**（≤ 3 s）。

---

## 6. 性能设计要点

1. **离线预计算**：文本向量库、BM25 语料、CLIP 图像向量均在 `build_kb.py` 构建期固化，
   在线不做任何 embedding 重建；
2. **确定性 Query 理解**：jieba 分词 + 正则规则，毫秒级，不调用大模型；
3. **单例复用**：向量库 / BM25 / CLIP 模型进程内单例，Streamlit 侧以 `st.cache_resource` 缓存；
4. **惰性导入**：`RecursiveCharacterTextSplitter`（仅建库需要）改为函数内导入，
   避免检索链路承担 `sentence_transformers → transformers → torch` 的导入开销；
5. **默认抽取式合成**：`ANSWER_MODE=extractive`，规避 LLM 生成的秒级延迟与幻觉。

| 资源 | 观测值 |
|---|---|
| 常驻内存 | 约 380 ~ 500 MB（CLIP CPU 推理 + FAISS 常驻） |

| 并发 | 检索链路无共享可变状态，FAISS/BM25 只读，支持多用户并发问答 |

---

## 8. 结论

1. 单题响应时间平均 **0.41 s**、最大 **2.46 s**，**全部 16 题达标**（≤ 3 s）；
2. 抽取式合成是把响应时间从「秒级」压到「亚秒级」的关键；
3. 进程级冷启动 13.58 s 为一次性开销，已通过预热机制与验收口径隔离；
4. 资源占用可控，无 GPU 依赖，满足长时间稳定运行要求。
