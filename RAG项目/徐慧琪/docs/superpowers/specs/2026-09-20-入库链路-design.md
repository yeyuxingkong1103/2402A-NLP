## 一、背景与本子项目的定位

技术方案把系统切成五块，入库链路是唯一没有前置依赖的一块：纯 Python、不碰 MySQL/Redis/Milvus，且产出决定后续所有环节的对错。AC-1 是硬门槛（条号连续性 + 条数合计 1260 + 逐字命中 + 字段非空，**不过即中断入库**），所以先做它。

**技术方案中已被实测推翻的三处表述**（本设计以实测为准）：

| 技术方案原文 | 实测结论 |
|---|---|
| 3.1「中册行首条号 537 处，比官方 577 差 40 条，须查清」 | **不成立**。中册 md 行首条号实测就是 577，零缺号。619 = 577 行首 + 42 处条内引用（如「依照本法第五百八十四条」）。537 是测量错误 |
| 3.1「上册 PDF 需 OCR 分支兜底」 | 上册 PDF **有完整文本层**（39,731 字符），91 页 MinerU pipeline 直抽可用 |
| 3.2 流程⑤「层级还原」隐含按 markdown 层级判 | **不可行**。见第四节：MinerU 会把「条」误标成 `##` 标题、把标记转义成 `\##`、给 docx 标题加 `**`。层级必须按词元判定 |

## 四、数据流与核心规则

```
上册.pdf  ──► MinerU(pipeline) ──┐
中册.md   ──► [md→docx 合成] ──► MinerU ──┼─► ①产物规整 ─► ②层级还原 ─► ③清洗
下册.docx ──► MinerU(office)  ──┘                                          │
                                          PaddleOCR-VL 兜底（触发式）◄─────┤
                                                                          ▼
                                                       ④父子切分 ─► ⑤校验 ─► jsonl
```

### 4.1 为什么中册要绕一圈 docx

MinerU 的 `-p` 实测只接受 pdf / image / docx / pptx / xlsx；喂 `.md` 直接报
`Error: No supported documents found`。故中册经 `md → docx（python-docx 逐行成段）→ MinerU` 往返。

**已实测无损**：往返后 577 条零缺号，编=2 / 分编=3 / 章=35 / 节=10，与直读原始 md 的测量逐项吻合。

### 4.2 产物规整

产物目录名随输入类型变化（pdf → `txt/`、docx → `office/`），**必须 rglob 递归定位，不能写死路径**。
每次解析保留全部产物，便于回溯。

### 4.3 归一化与层级还原（本设计的核心）

```python
LEAD_CHARS = "\\#*`> \t　"          # 剥 \  #  *  `  >  空白（含全角空格）

# 顺序重要：分编必须在「编」之前判，否则「第一分编」被「第X编」提前吃掉
LEVEL_PATTERNS = [("条", …条), ("分编", …分编), ("编", …编), ("章", …章), ("节", …节)]

def classify(line):
    text = line.strip().lstrip(LEAD_CHARS).strip()
    for name, pat in LEVEL_PATTERNS:
        if m := re.match(pat, text):
            return name, cn2int(m.group(1)), text
    return None, None, text
```

**四个坑全部来自实测，不是预防性设计：**

| 现象 | 实例 | 若不处理的后果 |
|---|---|---|
| 条被误标成标题 | `## 第二百一十条不动产登记，…` | 按行首抽会漏 **10 条**（210/261/348/366/373/393/395/400/401/412）并误报缺号 |
| 标记被转义 | `\## 第三编 合同` | 中册编/章/节全部识别失败（编=0 章=0 节=0） |
| 标题加粗体 | `# **第五编 婚姻家庭**` | 下册编/章识别失败 |
| 引用块前缀 | `> 本册范围：第三编 合同…` | 头部元信息被误判成层级行 |

**统一剥掉后按词元判定，完全不依赖 `#` 层级** —— 所以同一套规则对三个解析路径都成立。

另：**条的切分不依赖分隔符**。MinerU 的 PDF 路径输出 `第一条为了保护…`（无空格），
docx 路径输出 `第一千零四十条 本编调整…`（有空格）。正则取匹配结束位置切正文，两者都兼容。

### 4.4 上册边界重叠的处理

上册 PDF 实测 466 条，比官方 462 多 4 条（463~466）——来自按页抽取导致的边界共用页
（该页含第三编起始标题），与《数据来源说明》描述一致。

**规则：上册只取 1~462，463~466 丢弃；中册 md 从 463 起完整覆盖。**
依据《数据来源说明》「若需严格不重叠的边界，以 md/docx 为准」。
**丢弃动作必须写进 verify_report.md，不得静默。**

### 4.5 父子切分（技术方案 4.1）

| 对象 | 角色 | 内容 | 向量 |
|---|---|---|---|
| 条 | 父块 | 该条完整原文 | 否（本期不向量化） |
| 款 | 子块 | 条内自然段（句末标点收尾、非「（一）」开头） | 待下一子项目 |
| 项 | 子块 | 行首「（一）（二）…」 | 待下一子项目 |
| 叶块 | 子块 | 单条 > 800 字或单款 > 500 字，按句/分号切 | 待下一子项目 |

overlap = 0（FR-2.4）。子块带 `parent_id` 回指父块。

## 五、模块划分

严格按技术方案 8.1，`backend/app/ingest/` 下：

| 文件 | 职责 | 预计行数 |
|---|---|---|
| `parse_mineru.py` | MinerU subprocess 调用 + 产物规整（rglob 定位） | 120~200 |
| `ocr_paddle.py` | PaddleOCR-VL 兜底，触发式 | 120~200 |
| `structure.py` | 归一化 + 层级还原（4.3） | 200~280 |
| `chunk.py` | 父子切分 + 叶块规则 | 150~250 |
| `verify_ingest.py` | 条号连续性 / 条数合计 / 逐字命中 / 字段非空 | 150~250 |
| `run_ingest.py` | 流程编排（不含业务规则） | 80~150 |

外加 `tools/check_style.py`（≤300 非空行 + 无注释行统计），技术方案 11 章要求它作为验收证据。

> **与 8.1 的两处差异**：①8.1 把编排放在 `app/chains/ingest_chain.py`，但本期不引入 LangChain
> （不向量化、无链式组件），用一个不含业务规则的 `run_ingest.py` 做纯编排更合 2.2 的
> 「链只做编排，规则放可单测模块」；②8.1 的 `app/ingest/embed.py` 本期不建，见 3.3。

**约束落地**：每个文件顶部写清「这个文件为什么存在」；注释解释**为什么**而非复述代码；全中文注释；
超 300 非空行必须拆，禁止靠压缩空行规避。

## 六、错误处理

| 情形 | 动作 | 依据 |
|---|---|---|
| MinerU 子进程失败/超时 | 重试 1 次；仍失败则该册中断并记报告，**不静默跳过** | 3.4 |
| 条号不连续 | **中断入库**，输出缺号清单 | 3.4 硬门槛 |
| 条数合计 ≠ 1260 | **中断入库** | 3.4 |
| 上册 463~466 | 已知重叠，丢弃 + 记报告，不算失败 | 数据来源说明 |
| 逐字命中失败 | 记录未命中条目 → 人工复核（不中断） | 3.4 |
| 字段非空失败 | **中断入库** | 3.4 |
| OCR 触发失败 | 该页记入报告，MinerU 结果继续用 | 3.2 ④「以 MinerU 为准，OCR 只补缺」 |

> 逐字命中校验的降级：技术方案 3.4 要求「每册条文在对应官方 PDF 中逐字命中」，
> 但中册/下册 PDF 在回收站未恢复。**本期只对上册做逐字命中**，中/下册记为「待 PDF 恢复后补验」，
> 并写进 verify_report.md。这是已知的能力降级，不是遗漏。

**逐字命中的比对口径**（实施期修正，已用真实数据验证）：比对基线要做**两步**清洗，
缺一不可，都是口径问题、不改正文一字。

1. **去全部空白字符**（含换行、全角空格）。MinerU 已把 PDF 硬换行合并成整行，
   而 PDF 原文那些位置是换行符，直接比会全数失配。
2. **去页码**。PDF 文本层会把页码混进正文中间——实测上册第 28 条是
   `…（三）其他近亲属；12（四）其他愿意担任…`、第 38 条是
   `…尊重被监护人真实意愿的15前提下…`，其中的 `12` / `15` 都是页码。

**只做第 1 步会误报 36 条"未命中"**；两步都做则上册 462/462 全中。
误报方向容易看反：MinerU 其实已正确去掉页码，是基线带着噪声反过来说它错了。

页码判据：全库 1260 条里只有第 1260 条（附则）含半角数字（`2021年1月1日`），
其数字后必跟 年/月/日。故用 `(?<![0-9])[0-9]{1,3}(?![0-9年月日])` 剔除。
换别的话语料时这条判据要重新验证——它依赖「正文不含半角数字」这一事实。

## 七、PaddleOCR-VL 的定位

技术方案 3.2 ③ 定的是**触发式**：只对 MinerU 判定「无文本层 / 低置信度 / 表格错乱」的页触发。

三册语料文本层都干净，**OCR 预计一次都不触发**。代码路径完整实现并接线，但：
**触发与否、触发了几页、补了什么，必须记进 verify_report.md**，
避免「跑了但没生效」被当成已验证。

## 八、测试策略

入库链路最大的优势是主体逻辑可脱离外部服务单测。**用真实语料做夹具**（三册共 650KB，可整份进测试），不造数据。

| 测试对象 | 用例 |
|---|---|
| `classify()` | 三册真实样本 + 四个已知坑（`## 第X条` / `\##` / `**` / `>`）+ 断言「第一分编」不被「编」吃掉 |
| `cn2int()` | 一 / 十 / 十五 / 百 / 一千零四十 / 一千二百六十 边界 |
| 条号连续性 | 三册各跑一遍断言零缺号；**构造一个缺号用例断言中断** |
| 父子切分 | 抽多款条（如第 1041 条）断言款被拆开且 `parent_id` 指回父块 |
| 全量回归 | 跑通 `run_ingest.py` 后断言 1260 条、区间边界正确、上册 463~466 已丢弃 |

**缺号中断必须有反向用例** —— 3.4 的硬门槛如果只有正向用例，等于没验。
