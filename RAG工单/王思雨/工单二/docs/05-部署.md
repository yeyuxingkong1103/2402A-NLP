## 4. `.env` 配置

```bash
copy .env.example .env        # Windows
cp   .env.example .env        # Git Bash / Linux
```

然后编辑 `.env`：

| 变量 | 说明 | 示例 |
|---|---|---|
| `DEEPSEEK_API_KEY` | **必填**。DeepSeek 密钥，代码只从环境变量读，不硬编码 | `sk-xxxxxxxx` |
| `LLM_BASE_URL` | DeepSeek OpenAI 兼容接口基址 | `https://api.deepseek.com` |
| `LLM_MODEL` | 对话模型 | `deepseek-chat` |
| `EMBED_MODEL_PATH` | bge-m3 本地路径 | `D:/模型/bge-m3` |
| `RERANK_MODEL_PATH` | bge-reranker-v2-m3 本地路径 | `D:/模型/bge-reranker-v2-m3` |
| `DEVICE` | 推理设备 | `cuda` 或 `cpu` |
| `MILVUS_URI` | Milvus 地址 | `http://localhost:19530` |
| `MILVUS_COLLECTION` | 优化后方案的集合名 | `gd2_opt_chunks` |
| `MILVUS_COLLECTION_BASE` | 优化前基线的集合名 | `gd2_base_chunks` |
| `REDIS_URL` | Redis 地址 | `redis://localhost:6379/0` |
| `PDF_PATH` | 知识库路径 | `data/招股说明书1.pdf` |
| `MINERU_LANGFIX_DIR` | MinerU 中文路径补丁目录（见 §7） | `C:/mineru_models/langfix` |
| `BASE_CHUNK_SIZE` 等 | 分块与检索调参入口，改这里即可，无需改代码 | 见 `.env.example` |

**三个必须注意的点**

1. **路径一律用正斜杠**。写成 `D:\模型\bge-m3` 时 `\b` 会被解析成退格符，模型路径就找不到了。
2. **`DEEPSEEK_API_KEY` 用系统环境变量也可以**，而且优先级高于 `.env`（`load_dotenv(override=False)`）。
   ```bash
   # Git Bash 临时生效
   export DEEPSEEK_API_KEY=sk-xxxxxxxx
   ```
3. **`.env` 已在 `.gitignore` 中**，不要提交到版本库。

`docker-compose.yml` 里 **Milvus 版本为 `v2.6.2`**，与本机已缓存镜像一致，避免联网重新拉取。

> **⚠️ 本机（当前开发机）请勿执行 `docker compose up -d`**
>
> 本机的依赖服务已经在跑，直接复用即可，**不要**再启动本编排：
>
> | 服务 | 本机现状（已实测确认） | 本编排会映射的端口 | 结果 |
> |---|---|---|---|
> | Milvus | 容器 `rag-milvus` 已在 19530 运行（healthy） | `19530` / `9091` | **端口冲突，启动失败** |
> | Redis | Windows 原生 Redis 5.0.14.1 已在 6379 运行 | `6379` | **端口冲突，启动失败** |
>
> 也就是说本机根本没有启动这一步：`docker ps` 看到 `rag-milvus` 是 healthy、
> `python -c "import redis; redis.Redis.from_url('redis://localhost:6379/0', protocol=2).ping()"` 返回 `True` 即可直接进入下一步。
>
> **这份编排是给"干净机器"部署用的**（新环境没有现成 Milvus/Redis 时执行 `docker compose up -d`）。
> 只有在确认 19530 / 6379 上没有任何服务时，才执行它。

## 6. 构建索引

```bash
python -m src.rag_pipeline
```

预期输出：

```json
{"parser": "mineru", "baseline_chunks": 1136, "optimized_chunks": 2137}
```

- `baseline_chunks`：优化前基线的固定长度分块数；
- `optimized_chunks`：优化后的语义分块数；
- `parser`：实际生效的解析器（`mineru` 或降级后的 `fast`）。

首次运行会调用 MinerU 解析 548 页 PDF（数分钟），产物缓存在 `data/parsed/`，
**再次运行会直接复用，不会重跑**。

> **本机现状**：索引**已经建好**，演示时**不需要**再执行这一步
> （`data/index.json`、`data/bm25.pkl` 都在，两个 Milvus 集合均可正常检索）。
> 如果确实要重建，实测总耗时约 **3.2 分钟**（`190.8 s`：语义分块 102 s + 两套向量入库 134 s + BM25 1.4 s），
> 且**不会重跑 MinerU**——解析产物 09:43 比 PDF 09:27 新，命中缓存，`parse_pdf` 实测 0.07 秒。
> **演示现场不要跑这条命令**，避免占用 3 分钟又不产生新内容。

## 7. 中文路径问题（本机必读）

本机用户名为中文（`C:\Users\雨子\...`），MinerU 依赖的 fasttext C 扩展**打不开非 ASCII 路径**，
会报 `Failed to load FastText model ... cannot be opened for loading!`。

修复方式（已在本机完成）：

- `C:\mineru_models\langfix\lid.176.ftz`：fasttext 语言识别模型在纯 ASCII 路径下的副本；
- `C:\mineru_models\langfix\sitecustomize.py`：用 meta_path 钩子把 `LOCAL_SMALL_MODEL_PATH` 指向上面的副本；
- `src/pdf_parser.py` 启动 MinerU 子进程时把该目录注入 `PYTHONPATH`。

**为什么不直接在代码里 monkeypatch**：MinerU CLI 用 `multiprocessing spawn` 起子进程，
在父进程里打补丁对子进程无效，必须通过 `PYTHONPATH` 让子进程在启动时自己加载 `sitecustomize`。

换机器部署时：把 `C:\mineru_models\langfix\` 整个目录拷到 ASCII 路径下，并同步修改 `.env` 的 `MINERU_LANGFIX_DIR`。

## 8. 启动后端

```bash
uvicorn src.main:app --host 0.0.0.0 --port 8000
```

- 开发时热重载加 `--reload`；
- 生产部署建议：`uvicorn src.main:app --host 0.0.0.0 --port 8000 --workers 1`
  —— **worker 数保持 1**：向量模型与重排模型各占一份显存，多 worker 会重复加载、成倍吃显存；
  并发能力靠 FastAPI 的异步事件循环与模型内部批处理，而不是多进程。

**接口一览**（只做工单要求的三件事，未做知识库管理后台等后台功能）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ask` | 单模式问答：`{question, mode, use_cache}`，`mode` 取 `optimized`（默认）或 `baseline` |
| POST | `/api/compare` | 同一问题跑优化前与优化后，返回 `{before, after}` |
| GET | `/api/health` | 依赖探测：`api` / `llm_key` / `pdf` / `index` / `milvus` / `redis` |

索引构建**不做成接口**：它属于运维动作，用 `python -m src.rag_pipeline` 执行即可。

**冒烟测试**

> ⚠️ **不要把中文写在 `-d '...'` 里。** 在 Windows 的 Git Bash 中，命令行会把中文参数按本地代码页编码，
> 服务端收到乱码问题后会**正常地返回「资料中未找到相关信息」**——看起来像检索坏了，实际是调用方式的问题。
> 正确做法：先把 JSON 写成 UTF-8 文件，再用 `--data-binary @文件` 发送。

```bash
# 1) 用 Python 写请求体，确保是 UTF-8
python -c "import pathlib;pathlib.Path('q1.json').write_text('{\"question\":\"武汉兴图新科电子股份有限公司注册资本是多少？\"}', encoding='utf-8')"
curl -X POST http://localhost:8000/api/ask -H "Content-Type: application/json" --data-binary @q1.json

# 2) 前后对比同理
python -c "import pathlib;pathlib.Path('q2.json').write_text('{\"question\":\"报告期内，武汉兴图新科电子股份有限公司来自军用领域的收入分别是多少？\"}', encoding='utf-8')"
curl -X POST http://localhost:8000/api/compare -H "Content-Type: application/json" --data-binary @q2.json
```

> 更省事的办法：直接用浏览器界面（`npm run dev` → <http://localhost:5173>）。演示时推荐这种方式。

接口文档：<http://localhost:8000/docs>（FastAPI 自动生成）。

## 10. 高可用与资源消耗控制

| 手段 | 位置 | 说明 |
|---|---|---|
| 连接复用 | `retrieval.milvus_client()` / `_cache()` 中的 `_REDIS` | Milvus 客户端与 Redis 客户端各只建一次，避免每请求重建连接 |
| 模型常驻 | `retrieval._MODELS` | bge-m3 与重排模型懒加载后常驻显存，不重复加载 |
| 索引常驻 | `rag_pipeline.STATE` | BM25 与块列表首次提问时载入内存，之后不再读盘 |
| 缓存 | Redis `rag:{mode}:{md5}`，TTL 一天 | 高频问题命中缓存后只剩一次读，是「3 秒」目标的主要保障 |
| 超时控制 | `LLM_TIMEOUT`（默认 20 秒）、Redis `socket_timeout=0.5` 秒、MinerU `timeout=5400` 秒 | 任一依赖卡死都能快速失败而不是挂住请求 |
| 检索规模控制 | `VEC_TOP_K` / `BM25_TOP_K` / `FUSION_TOP_K` / `RERANK_TOP_N` | 全部在 `.env` 可调，高并发时下调候选数即可线性降本 |
| 输出规模控制 | `max_tokens=512`、只送 5 条上下文 | 直接压低生成耗时 |
| 并发 | FastAPI + uvicorn（async 事件循环） | 检索与生成的阻塞调用不阻塞事件循环的调度；高并发下用 `--workers 1` + 上游 Nginx 限流 |
| 限流 | 建议在上游（Nginx / 网关）配置 | 本项目不实现用户体系与鉴权，限流放在网关层更合适 |
| 降级 | 解析三级降级、Milvus/Redis 失败降级 | 单点故障不影响整体可用性，异常统一转成中文友好提示 |

**显存占用参考**：bge-m3 约 2～3 GB，bge-reranker-v2-m3（fp16）约 1～2 GB，
两个模型在 `DEVICE=cuda` 下合计约 4～5 GB。

**无 GPU 部署**：`.env` 里 `DEVICE=cpu` 即可跑通，代价是建索引与检索明显变慢（约 5～10 倍），
此时建议把 `--workers` 设为 1 并适当下调 `VEC_TOP_K` / `FUSION_TOP_K`。

## 11. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 「知识库尚未构建」 | `data/index.json` 不存在 | 执行 `python -m src.rag_pipeline` |
| 解析器名是 `fast` 而不是 `mineru` | MinerU 失败并降级（多为中文路径补丁未生效） | 检查 `C:\mineru_models\langfix\` 是否存在，`.env` 的 `MINERU_LANGFIX_DIR` 是否正确 |
| 「系统繁忙或依赖服务暂时不可用」 | Milvus 没起或集合不存在 | `docker compose ps` 看 milvus 是否 healthy，必要时重建索引 |
| Redis 连接失败但不影响问答 | 本机 Redis 版本较老 | 正常降级行为；如要恢复缓存，确认 Redis 在跑（协议已固定 RESP2 以兼容 Redis 5.x） |
| 刚写入的向量查不到 | Milvus 一致性级别 | 代码已在检索时指定 `consistency_level="Strong"`；自定义客户端时勿用默认 Bounded |
| 前端报「请求失败」 | 后端没起或端口不是 8000 | 确认 `uvicorn` 在 8000 端口，且 `vite.config.js` 的代理目标一致 |
| `RuntimeError: 未配置 DEEPSEEK_API_KEY` | 密钥缺失 | 在 `.env` 里填 `DEEPSEEK_API_KEY`，或设为系统环境变量 |
