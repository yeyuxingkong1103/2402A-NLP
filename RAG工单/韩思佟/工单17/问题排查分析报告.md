### 2.3 代码静态分析结论（**核心发现**）

以下全部为源码事实，均标注了文件与函数。

#### 瓶颈一：请求链路缺少限流/队列，`thread_pool_exec` 每次新建线程池

- API 框架是 **Quart（异步 ASGI）**，不是 Flask：`api/apps/__init__.py:59 app = Quart(__name__)`，
  入口 `api/ragflow_server.py`（`app.run(host=settings.HOST_IP, port=settings.HOST_PORT)`），
  启动脚本 `docker/launch_backend_service.sh:99` → `$PY api/ragflow_server.py`（**没有 gunicorn/uwsgi**）。
- 所有阻塞的同步 DB/IO 调用统一用 `await thread_pool_exec(...)` 卸载：
  ```python
  # common/misc_utils.py:116-132
  def _thread_pool_executor():
      max_workers_env = os.getenv("THREAD_POOL_MAX_WORKERS", "128")
      ...
      return ThreadPoolExecutor(max_workers=max_workers)

  async def thread_pool_exec(func, *args, **kwargs):
      loop = asyncio.get_running_loop()
      if kwargs: func = functools.partial(func, *args, **kwargs)
      return await loop.run_in_executor(_thread_pool_executor(), func)
  ```
  ⚠️ **`_thread_pool_executor()` 在每次调用时都新建一个 ThreadPoolExecutor**，不是全局单例。
  高并发下每次都新建 128 线程的池 → 线程数量爆炸、上下文切换开销大、池不被复用。
  这就是「10 并发就把响应从 2s 拉到 10s」的直接原因之一。
- 请求入口中大量使用它，例如 `api/apps/document_app.py:670`、`api/apps/chunk_app.py:198/221/263/340`。

#### 瓶颈二：重量级组件没有单例/缓存，每个请求都可能重复初始化

```python
# api/db/services/tenant_llm_service.py:136 model_instance()
# → 对每种 LLMType 直接 new 一个客户端
# api/db/services/tenant_llm_service.py:378 LLM4Tenant.__init__
self.mdl = TenantLLMService.model_instance(tenant_id, llm_type, llm_name, lang=lang, **kwargs)
assert self.mdl, "Can't find model for {}/{}/{}".format(tenant_id, llm_type, llm_name)
```
- **`LLMBundle` 没有任何缓存**：全仓库没有 `@lru_cache` / `_model_cache` / `get_model` 之类的模型单例，
  `model_instance` 每次调用都新建客户端（`EmbeddingModel[factory]` / `RerankModel[factory]` /
  `CvModel[factory]` / `ChatModel[factory]`）。
- 真正的单例机制只有 `common/decorator.py:18 singleton`，只用在 `RedisDB`（`rag/utils/redis_conn.py:60`）
  和 `BaseDataBase`（`api/db/db_models.py:396`）。
- **deepdoc 解析器也没有单例**：`RAGFlowPdfParser.__init__` 每次都 `OCR()` + `LayoutRecognizer()` +
  `TableStructureRecognizer()`；好在 ONNX session 有全局缓存兜底
  （`deepdoc/vision/ocr.py:71 load_model()` 的 `loaded_models` 字典按「模型路径+device_id」复用）。
  → 这解释了"未触发重新解析文档时 GPU 内存也被占用且释放不及时"：模型被反复加载/持有。

#### 泄漏点一：数据库/向量库/Redis 连接未显式配置池上限

```python
# api/db/db_models.py:396 @singleton BaseDataBase
pool_config = {'max_retries': 5, 'retry_delay': 1}
database_config.update(pool_config)
self.database_connection = PooledDatabase[settings.DATABASE_TYPE.upper()].value(db_name, **database_config)
```
- ORM 是 **Peewee + playhouse.pool**（`api/db/db_models.py:30-32`），带重试子类
  `RetryingPooledMySQLDatabase`（:242，指数退避，错误码 2013/2006）与 `RetryingPooledPostgresqlDatabase`（:315）。
- ⚠️ **只设置了 `max_retries`/`retry_delay`，没有显式设置 `max_connections` / `stale_timeout`**，走 playhouse 默认值。
  高并发时连接数不受控，且连接可能被长期持有。
- Redis：`rag/utils/redis_conn.py:125 __open__()` 直接 `redis.StrictRedis(**conn_params)`，
  **没有显式传 `connection_pool` / `max_connections`**（靠 redis-py 内部默认池）。
- 向量库连接池封装在 `common/doc_store/es_conn_pool.py` / `infinity_conn_pool.py`，实例挂全局 `settings.docStoreConn`。
- 连接释放：`api/apps/__init__.py:315 @app.teardown_request → close_connection()`。

#### 泄漏点二：中间对象/张量没有主动释放

- 全仓库 **没有 `torch.cuda.empty_cache()`**（已 grep 确认）。
- 仅有的释放代码是 ONNX 侧：
  ```python
  # deepdoc/vision/recognizer.py:410
  def close(self):
      logging.info("Close recognizer.")
      if hasattr(self, "ort_sess"):
          del self.ort_sess
      gc.collect()
  ```
  以及 `deepdoc/vision/ocr.py:361 / 501` 各一处 `gc.collect()`。
- Task Executor 侧只有内存诊断钩子：`rag/svr/task_executor.py:1358-1363`，
  环境变量 `TRACE_MALLOC_ENABLED=1` 或信号 `SIGUSR1/SIGUSR2` 触发
  `start_tracemalloc_and_snapshot` / `stop_tracemalloc`（`common/signal_utils.py`）。

#### 监控现状

- **没有 Prometheus 客户端代码、没有 `/metrics` 端点**（`prometheus` 只出现在 `docker/docker-compose*.yml` 的注释里）。
- 现有可观测能力：Langfuse tracing（`api/db/services/dialog_service.py:294-306`、`tenant_llm_service.py:391-402`）、
  Executor 心跳 `rag/svr/task_executor.py:1245 report_status()` → `REDIS_CONN.zadd(CONSUMER_NAME, heartbeat, now_ts)`（30s 一轮，
  `WORKER_HEARTBEAT_TIMEOUT=120s` 清理僵尸 worker）、`api/utils/health_utils.py:135 get_redis_info()`。

### 2.4 根因汇总

| 编号 | 根因 | 代码位置 | 对应现象 |
|---|---|---|---|
| R1 | `thread_pool_exec` 每次新建 ThreadPoolExecutor，非单例 | `common/misc_utils.py:116` | 并发延迟飙升 |
| R2 | 无请求限流/内存队列，检索+生成链路全同步等待 | `api/apps/*.py` 请求入口 | 高并发请求堆积 |
| R3 | `LLMBundle`/`model_instance` 无模型单例缓存 | `api/db/services/tenant_llm_service.py:136/378` | 重复初始化、GPU 占用不释放 |
| R4 | DB 连接池未设 `max_connections`；Redis 未设连接池上限 | `api/db/db_models.py:396`；`rag/utils/redis_conn.py:125` | 连接泄漏 |
| R5 | 无显式张量/中间对象释放 | `deepdoc/vision/recognizer.py:410`（仅此） | 内存缓慢上涨 → OOM |
