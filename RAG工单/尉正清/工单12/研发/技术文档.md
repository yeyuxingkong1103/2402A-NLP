## 一、系统架构

本工单在已交付的 RAG 系统（工单 01-10）之上，并行接出一条 LightRAG 的
知识图谱链路，在**同一批语料、同一批问题**上对比两条路的检索与回答质量。

```
                 ┌──────────────── corpus.py（统一解析，只做一次）────────────────┐
                 │  document.load_pdf → 文字页 + 表格                            │
   两份招股书 ───→│  image_parser     → 74 页图表转文字                           │
                 └───────┬──────────────────────────────────┬───────────────────┘
                         │ chunks 2,232 块                   │ 逐页带标记的整篇文本
                         ▼                                   ▼
             ┌───────────────────────┐           ┌───────────────────────────┐
             │ RAG 向量库（rag_gd）  │           │ LightRAG 图谱（rag_gd1）  │
             │ BGE-M3 稠密+稀疏      │           │ 切 494 块 → LLM 抽实体关系 │
             │ RRF 融合 → Top-8      │           │ → neo4j（5,300 / 8,301）  │
             └───────────┬───────────┘           │ mix 双层检索              │
                         │                       └─────────────┬─────────────┘
                         └──────────────┬──────────────────────┘
                                        ▼
                          16 题 × 2 套 → RAGAS 四指标 + 对比报告
```

## 四、核心实现要点

### 1. `reasoning_effort=none` —— 关掉思维链（**最关键的一条**）

`deepseek-flash` 是推理模型，思维链和正文共用 `max_tokens` 额度。
实测单次实体抽取要烧掉约 10,800 个 reasoning token、耗时 **33 秒**，
而 `max_tokens` 给 4096/8192 时正文直接是**空串**（HTTP 仍是 200，不报错）。

建图要上千次调用，按 33 秒/次算要 4.5 小时，工单跑不完。
加上 `reasoning_effort=none` 之后：**1.9 秒，思维链归零，正文照常产出**。

⚠️ 这不只是性能优化，更是**对比公平性**要求：RAG 与 LightRAG 必须跑完全相同的
大模型配置，否则指标差异里混着「谁的模型配置更强」。所以 `config.LLM_REASONING_EFFORT`
对两条路同时生效（`rag_engine._request` 也读同一个开关）。

**踩到的细节**：该参数走 `extra_body` / 原始 JSON 字段，不能走 OpenAI SDK 的
具名参数 —— 那个会被 SDK 按 OpenAI 类型校验拦下（官方取值只认 low/medium/high）。

### 2. 招股书定制的抽取 schema

见 `设计说明.md` 第 2.3 节。要点是**换类型表 + 追加四条专用规则**，
其中「自称消解」（把「本公司」「发行人」还原成全称）是招股书场景最要紧的一条。

### 3. 关掉两个会放大调用量的开关

| 参数 | 默认 | 本工单 | 依据 |
|---|---|---|---|
| `entity_extract_max_gleaning` | 1 | **0** | 追问式二次抽取让每块调用翻倍；招股书格式规范，首轮召回已够全 |
| `force_llm_summary_on_merge` | 8 | **9999** | 招股书里公司名反复出现，按默认阈值会触发上千次摘要调用 |

### 4. 上下文切片：让两个系统的 context 可比

`only_need_context=True` 返回的是**一整块**（实测 6.4 万字符），里面混着
知识图谱的实体/关系 JSON 与召回原文。`query.split_lightrag_context()`
按灌入时打的页码标记（`【招股说明书X.pdf 第 N 页】`）把它切成小段：

- 检索结果对比要**按页算命中率**，不切开拿不到页码；
- RAGAS 的 `context_precision` 是**按每条上下文**判相关的，
  RAG 那边是 8 条、这边是 1 条 6 万字的，两边根本不是一个口径。

图谱数据不放进 contexts（另一种模态，混进来就没法同口径比较），
单独统计字符数后在报告里说明。

### 5. 环境自检

`query.py` 启动时先探依赖，跑错环境给一句人话提示而不是一堆 ImportError：

```
[环境不对] 这条路需要 `FlagEmbedding`，但它不在当前 Python 里。
           请改用 rag_gd 环境运行：
           D:/Anaconda/envs/rag_gd/python.exe query.py --kb rag "问题"
```

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 第 110 页图表解析失败 | 多模态模型返回空内容，该页在知识库中缺失 |
| LightRAG 上下文远多于 RAG | 实测 24~32 段 vs 8 段，RAGAS 评估时两边都截到前 8 段拉齐口径 |
| RAGAS 指标有波动 | 四个指标都由大模型判分，同一份数据换次运行会小幅波动，差异 < 0.05 不宜过度解读 |
| 标准答案由人工整理 | 工单没给标准答案，`testset.gold_answer` 是人工从原文逐句核对后写入的，来源页可回溯 |
| 两个 conda 环境 | 依赖冲突所致，见 `优化/过程问题记录.md` 问题 2；对比在结果层做，不要求同进程 |
