## 2. 优化前后架构对比

### 2.1 优化前（基线，`mode=baseline`）

```
PDF ──PyMuPDF 逐页取纯文本──> 按 500 字硬切分块 ──bge-m3 编码──> Milvus 单集合
                                                                       │
用户提问 ──bge-m3 编码──> 仅向量检索 Top-5 ────────────────────────────>│
                                                                       ▼
                                                              DeepSeek 直接生成答案
```

特征与局限：

| 环节 | 优化前做法 | 直接后果 |
|---|---|---|
| 解析 | PyMuPDF 纯文本抽取 | 表格塌成散落的单元格文本，表头与数据错位；章节结构丢失 |
| 分块 | 固定 500 字硬切 | 一句话被切断、数字与它的说明分家 |
| 检索 | 仅 bge-m3 向量检索 | 精确数字（6,464.51）、专有名词（《某视频技术规范1.0》）容易被近似语义淹没 |
| 重排 | 无 | 召回的 5 条按向量相似度直接进提示词，噪声上下文稀释答案 |
| 缓存 | 无 | 每次提问都重新编码与生成，重复问题延迟高 |
| 容错 | 无 | 依赖异常直接 500，用户看到堆栈 |

### 2.2 优化后（`mode=optimized`）

```
PDF ──MinerU（版面还原+表格识别）──> 语义分块（bge-m3 相似度切边界）
   └─失败则 PyMuPDF/pdfplumber ──>  └─文本层为空则 PaddleOCR　
                                              │
                          ┌───────────────────┴───────────────────┐
                          ▼                                       ▼
                  bge-m3 向量 → Milvus 集合               BM25 关键词索引（jieba 分词）
                          └─────────── 加权融合（各通道归一化后按权重相加）───────────┘
                                              │
                                    bge-reranker-v2-m3 交叉编码精排 Top-5
                                              │
                     Redis 缓存（问题+模式 → 答案，TTL 1 天） ──> DeepSeek 生成（中英文同语言作答）
```

### 2.3 两套索引并存

基线索引与优化索引写在**两个独立集合**（`gd2_base_chunks` / `gd2_opt_chunks`），
`/api/compare` 对同一问题分别走两条链路，把「同题两答案 + 两耗时」并排返回，
这样「优化前后对比」是**同一进程、同一模型、同一批问题**下的实测对照，而不是两套环境的间接比较。

## 3. PDF 解析优化

工单要求「从 PDF 解析处理层面优化」，指定栈为 **MinerU 为主，PyMuPDF / pdfplumber / PaddleOCR 兜底或 OCR**。
实现为四级降级链（`src/pdf_parser.py`）：

| 顺序 | 解析器 | 触发条件 | 产出 |
|---|---|---|---|
| 1 | **MinerU pipeline** | 默认 | 版面还原的块序列：正文、章节标题、表格（HTML） |
| 2 | **PyMuPDF + pdfplumber** | MinerU 抛任何异常（含中文路径、超时、OOM） | 段落文本 + 页内表格 |
| 3 | **PaddleOCR** | 前两级提取文本合计 < 200 字符（判定为扫描件） | 前 20 页位图 OCR 文本 |
| — | 明确报错 | 三级都拿不到文本 | 返回「文件未损坏？或改用带文本层 PDF」的友好提示 |

**MinerU 关键实现点（三处踩坑，均已处理）**

1. **表格内容在 `table_body`（HTML），不在 `text`**。
   只读 `text` 会丢掉全部 502 张表格。因此 `html_table_to_text()` 按 `<tr>`/`<td>` 还原为
   `发行股数 | 1,840.00万股 | ...` 这样的行内文本。
2. **表格缺语境就检索不到**。表体往往只有「国防领域 | 4,627.14 | 94.34%」这类裸数字，
   既没有「军用领域」也没有「收入」。实现时把**最近的章节标题**与**表题**拼在表体前，
   表格块才能同时被向量与 BM25 命中。
3. **中文路径会让 MinerU 直接失败**。本机用户名为 `C:\Users\雨子\...`，fasttext 的 C 扩展打不开非 ASCII 路径，
   报 `Failed to load FastText model ... cannot be opened for loading!`。
   修复：`C:\mineru_models\langfix\` 下放 `lid.176.ftz` 副本与 `sitecustomize.py`，
   启动子进程时把该目录注入 `PYTHONPATH`（MinerU CLI 用 spawn 起子进程，在父进程里 monkeypatch 无效）。

**解析产物复用**：MinerU 解析 548 页耗时以分钟计，产物（`*_content_list.json`）比 PDF 新时直接复用，
避免每次启动重建索引都重跑解析。

## 4. 语义分块优化

### 4.1 优化前：固定长度

```python
for j in range(0, len(text), 500):   # 按固定字符硬切，不看句子边界
```

问题：切断句子、数字与单位分家、表头与数据错位。

### 4.2 优化后：基于 bge-m3 的语义边界

算法（`src/rag_pipeline.py::semantic_chunks`）：

1. 把每个解析块拆成**语义单元**：表格整体作为一个单元；短块整体作为一个单元；长块按中英文句末标点切句。
2. **一次性批量编码**全部单元（bge-m3，L2 归一化）。
3. 顺序扫描，任一条件成立就在当前位置切块：
   - 当前块长 + 下一单元 > `SEM_CHUNK_MAX`（默认 700 字）——**长度上限兜底**；
   - 当前块向量中心与下一单元的余弦相似度 < `SEM_THRESHOLD`（默认 0.62）——**语义断裂**；
   - 遇到章节标题或表格——**结构边界必须成界**。
4. 章节标题不进块，而是作为**下一块的首行语境**；表格独立成块。
5. 块记录 `page_no` / `page_end`（起止页），使检索结果可按页回溯源，这才使「检索精确度」可量化（§9）。

**为什么用「块中心 vs 下一句」而不是「相邻句 vs 相邻句」**：前者衡量的是「新句子是否还属于当前主题」，
与分块目标一致；后者只衡量局部连贯性，容易被同一段内的过渡句误导。
`SEM_THRESHOLD` 与 `SEM_CHUNK_MAX` 都是 `.env` 可调参数，调参过程见 `04-优化.md`。

## 5. 混合检索优化

工单要求「从检索优化层面」提升准确率。单一向量检索对**精确数字与专名**天然弱势，
单一关键词检索对**同义改写**天然弱势，因此采用两路召回 + 加权融合。

| 通道 | 实现 | 召回数 | 擅长 |
|---|---|---|---|
| 向量 | bge-m3（本地 `D:\模型\bge-m3`）→ Milvus，`IP` 度量 | `VEC_TOP_K=10` | 语义相近、同义改写、中英跨语言 |
| 关键词 | BM25（`rank_bm25` + `jieba` 分词） | `BM25_TOP_K=10` | 精确数字、比例、专有名词、标准编号 |

**融合规则**（`src/retrieval.py::fuse`）：

1. 两个通道的原始分**各自 min-max 归一化到 0~1**——BM25 分数是无上界的实数，向量分是余弦值，不归一化无法相加；
2. 同一块命中两路时**分数叠加**：`score = VEC_WEIGHT × vec_norm + BM25_WEIGHT × bm25_norm`；
3. 按融合分降序取 `FUSION_TOP_K=12` 条进入重排。

**Milvus 使用要点**：写入后 `flush()`，检索时显式指定 `consistency_level="Strong"`。
默认的 Bounded 一致性会导致**刚写入的向量查不到**，表现为「索引明明建好了却检索为空」。

## 6. 重排优化

融合阶段用的是**双塔**（问题与文档分别编码），只能算粗排。工单指定 **bge-reranker-v2-m3**
（本地 `D:\模型\bge-reranker-v2-m3`）做**交叉编码**精排：

- 对 12 条候选逐条构造 `(问题, 块文本)` 对，送入重排模型输出 0~1 相关度；
- 取 `RERANK_TOP_N=5` 条作为最终上下文送入 DeepSeek。

代价是 12 次前向，收益是候选顺序被显著纠正——这正是「检索精确度」提升的主要来源之一，
量化结果见 `03-测试.md` 与 `04-优化.md`。

## 7. Redis 缓存与交互设计

### 7.1 缓存

- 缓存键：`rag:{mode}:{md5(question)}`——按模式隔离，基线与优化的结果不会互相污染。
- 值：完整答案体（含 `contexts`），`TTL=86400` 秒。
- 写入时**剔除 `elapsed` 字段**：耗时是变量，缓存后回放旧耗时会失真；命中时按实际读取耗时重新计时。
- 降级：Redis 连不上时 `_cache()` 静默返回 `None`（按未命中处理），**绝不阻断问答**。
- 客户端 `protocol=2`：本机 Redis 5.x 不支持 RESP3，用默认协议握手会失败。

### 7.2 界面（Vue 3 + Vite，`frontend/`）

只有四件事，与工单功能验收「清晰、简洁」对齐：

1. 提问输入框 + 提问按钮；
2. 中/英语言切换（同时切换界面文案与题库）；
3. 答案展示：答案正文、总耗时（**超过 3 秒标红**）、检索/生成分阶段耗时、缓存命中标记、命中片段（页码 + 相关度）；
4. 「优化前后对比」按钮：并排展示优化前与优化后的答案与耗时。

工单 10 个问题以标签形式列在输入框下方，点击即填入，便于演示时逐条提问。
`/api` 由 Vite 代理到 `http://localhost:8000`，避免跨域。

## 8. 3 秒响应、高可用与容错方案

### 8.1 3 秒预算

| 阶段 | 主要成本 | 控制手段 |
|---|---|---|
| 问题编码 | bge-m3 单条前向 | 模型常驻显存（懒加载单例，不重复加载） |
| 向量检索 | Milvus 单次查询 | 只取 10 条；连接复用 |
| 关键词检索 | BM25 内存打分 | 索引常驻内存，毫秒级 |
| 重排 | 12 对交叉编码 | 候选数与 `RERANK_TOP_N` 可调；GPU 上半精度 |
| 生成 | DeepSeek API | 上下文只送 5 条、`max_tokens=512`、`temperature=0`、`timeout=20s`、失败重试 1 次 |

分阶段耗时由接口返回（`retrieval_ms` / `generate_ms` / `elapsed`），前端与评测脚本都能看到，
**是否达标以实测为准**，实测数据见 `03-测试.md`。

### 8.2 高可用

- 解析、索引、检索、生成各环节**独立降级**，任一环节失败不影响其他环节；
- MinerU → PyMuPDF/pdfplumber → PaddleOCR 三级解析降级；
- Milvus 不可用时 `vector_search` 返回空并打印原因；两路召回全空时抛出可读错误，由 `answer()` 转成友好提示；
- Redis 不可用时静默跳过缓存；
- 索引与 BM25 落盘（`data/index.json`、`data/bm25.pkl`），服务重启只需重连 Milvus，不需重建索引；
- 模型单例常驻，避免长跑过程中显存抖动与重复加载。

### 8.3 容错清单

| 异常 | 处理 | 用户看到 |
|---|---|---|
| 空问题 | `answer()` 前置校验 | 「请输入需要查询的问题。」 |
| 超长问题（>500 字） | 前置校验 | 「问题过长，请控制在 500 字以内。」 |
| PDF 缺失 | `parse_pdf()` 首行校验 | 「知识库文件不存在：xxx.pdf」 |
| PDF 解析失败 | 三级降级后仍为空 | 「PDF 解析失败：未提取到任何文本，请确认文件未损坏」 |
| 索引未构建 | 捕获 `FileNotFoundError` | 「知识库尚未构建，请先执行 python -m src.rag_pipeline」 |
| Milvus 不可用 | 检索层降级 | 「系统繁忙或依赖服务暂时不可用，请稍后重试。」 |
| Redis 不可用 | 静默跳过 | 无感（只是不再走缓存） |
| DeepSeek 超时/缺 Key | 生成层异常捕获 | 「未配置 DEEPSEEK_API_KEY…」/ 「系统繁忙…」 |
| 检索不到内容 | 提示词内约定拒答 | 「资料中未找到相关信息」 |

## 9. 准确率 90% 与「检索精确度」验收方案

### 9.1 判分口径

- **回答准确率** = 答对题数 / 总题数。判「答对」的标准：答案中**同时包含该题全部关键字段**
  （`data/eval/questions.json` 的 `expect`，如 id 260 要求同时出现 4 个金额）。
  比对前去掉空白与中英文逗号并转小写，避免 `5,520` 与 `5520` 这类格式差异被误判为答错。
- **检索命中率（检索精确度）** = 检索到的上下文**覆盖了标准答案出处页**的题数 / 总题数。
  工单问题的出处页已逐条核对写入题库的 `source_pages`，这是「检索精确度」可量化的前提。
- **RAGAS 四项指标**（工单指定评估框架）：`faithfulness`、`answer_relevancy`、
  `context_precision`（`LLMContextPrecisionWithReference`）、`context_recall`（`LLMContextRecall`）。
  判官模型用 DeepSeek（OpenAI 兼容接口），嵌入模型用本地 bge-m3。

### 9.2 题库核验

`data/eval/questions.json` 中 10 条 `ground_truth` **逐条取自 PDF 原文**，
核验方式与结论记录在 `03-测试.md`，不在文档里替未核对的数字背书。

### 9.3 对比流程

`python -m src.evaluate` 依次跑 `baseline` 与 `optimized` 两种模式：

- 每题都**关闭缓存**，测的是真实端到端耗时；
- 输出每题的答案、是否答对、是否命中出处页、端到端耗时与分阶段耗时；
- 输出两种模式的准确率、检索命中率、平均/最大响应时间、3 秒内完成比例、RAGAS 四项指标；
- 完整结果落盘 `results/eval_<时间戳>.json`。

未达 90% 时的调参动作记录在 `04-优化.md`（chunk 大小、top_k、重排候选数、BM25 权重、缓存策略）。

## 10. 中英文问答方案

- **向量侧**：bge-m3 是多语言模型，中英文落在同一语义空间，因此**英文问题可直接检索中文文档**，
  不需要额外做翻译或双语索引。
- **生成侧**：提示词明确要求「用与问题相同的语言作答」，中文问→中文答，英文问→英文答。
- **判分侧**：工单的 10 个问题为中文，准确率按中文题计算；
  另备 3 个英文问题在 `data/eval/questions.json` 的 `en_questions` 中，用于演示多语言能力。
- **界面侧**：中/英切换同时切换界面文案与题库。
