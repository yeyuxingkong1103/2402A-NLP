## 一、背景与目标

### 1.1 基线暴露的靶点

V1 基线（`recall@5 = 0.9167`、`MRR = 0.7250`、`faithfulness = 0.7194`、`refusal_accuracy = 0.9167`）暴露了两类可量化的弱点，直接对应 V2 的两个改动：

| 基线弱点 | 出处 | V2 对策 |
| --- | --- | --- |
| **专业术语查询完全失败**：R09「功能充分性属于哪个质量特性的子特性？」未命中第 7 页 | 基线报告 4.1 | 引入**稀疏检索**（词面精确匹配），经 RRF 与稠密通道融合 |
| **图像语义完全缺失**：第 6 页「图 2 软件质量模型」仅存图注 10 字，图内信息未入知识库 | 基线报告 4.5 | 引入**视觉模型**解析图表，描述并入知识块 |
| **短文本被长噪声前缀稀释**：R08 正确块相似度仅 0.6665，排第 5 | 基线报告 4.2 | V2 部分缓解（稀疏通道）；彻底改善留待 V3 重排 |

> R08 / G04 / S12 三个样本指向**同一个知识块**（`d1b17a6c548cd4dc_0008`，第 6 页），说明该块的表征质量是全链路瓶颈。V2 的视觉解析正对此块。

### 1.2 V2 目标

1. 增加**稀疏检索通道**，与稠密通道经 **RRF 融合**，提升召回与排序
2. 用**视觉模型解析 PDF 图表**，将图内语义补充进知识库
3. 完善**后端 Trace 日志**，完整记录两路独立召回结果、分数与页码
4. 在**同一套评测集**上评测 V2，与 V1 基线对比并**给出归因**

### 1.3 明确不做

| 不做 | 原因 |
| --- | --- |
| 重写 V1 代码 | ADR-010：迭代是逐轮增强，且 V1 必须保留可运行以复核基线 |

| 改动 API 契约（新增/删除请求参数） | ADR-010「仅允许新增响应字段」 |

## 二、已实测证实的技术前提

> 以下均为 2026-09-20 在本机实跑验证的结论，非文档推断。这些前提是方案成立的基础。

### 2.1 一次 forward 可同时产出稠密与稀疏

手动 forward 得到的 CLS 池化向量，与 `sentence-transformers` 的 `encode(normalize_embeddings=True)` 输出**逐元素完全相同**：

| 文本 | 最大逐元素差 | 余弦 |
| --- | --- | --- |
| 数据中心业务连续性分为几个等级？ | 0.000e+00 | 1.000000 |
| 功能充分性属于哪个质量特性的子特性？ | 0.000e+00 | 1.000000 |

**意义**：V2 无需为稀疏通道做第二次推理，在线与离线均只付一次前向计算成本。稠密结果与 V1 完全一致，保证两版本可比。

依据：`1_Pooling/config.json` 为 `pooling_mode_cls_token: true`，`modules.json` 末级为 `Normalize`。

### 2.2 不需要安装 FlagEmbedding

`D:/桌面/模型/bge-m3` 目录内含 `sparse_linear.pt`（3516 字节，`weight` shape `(1, 1024)` + `bias`），可直接用 `torch.load` 加载为线性层。

| 问题 | 权重最高的 token |
| --- | --- |
| 数据中心业务连续性分为几个等级？ | 等级 0.3162、连续 0.2913、业务 0.2462、中心 0.2303 |

## 四、模块设计

### 4.1 新增文件

#### `backend/rag_pipeline/rrf.py`

**职责**：RRF（Reciprocal Rank Fusion）融合，纯函数、无 I/O、无副作用。

**接口**：

```python
def fuse(
    channels: Sequence[Sequence[str]],   # 各通道的 chunk_id 有序列表（按名次）
    *,
    k: int | None = None,                # None → 读 settings.rrf_k
    top_k: int,
) -> List[Tuple[str, float]]:            # [(chunk_id, rrf_score), ...] 降序
```

**融合公式**：

```
score(chunk) = Σ_c  1 / (k + rank_c(chunk))
```

`rank_c` 为该 chunk 在第 c 通道中的名次（从 1 开始）。未出现在某通道则不计该项。

**设计要求**：

- **k 值必须取自配置 `settings.rrf_k`（默认 60），不得硬编码**
- RRF 是**基于名次**的融合，天然免疫不通道分数尺度不一致的问题（稠密为余弦相似度、稀疏为内积），因此**不使用** `settings.hybrid_sparse_weight`（该配置项为早期加权融合设想所留，RRF 方案下不适用，实现时保持未读取状态并在 ADR 中说明）
- 名次并列时按 chunk_id 稳定排序，保证结果可复现

#### `backend/rag_pipeline/v2_pipeline.py`

**职责**：V2 检索链路，实现与 V1 **完全一致**的对外契约（`answer()` / `retrieve()` / `get_pipeline()`），使 `get_pipeline_by_name("v2")` 与评测脚本、API 层无需改动即可使用。

**与 V1 的唯一差异在检索环节**：

| 环节 | V1 | V2 |
| --- | --- | --- |
| 问题编码 | 稠密 1 次 | 一次 forward 同时得稠密 + 稀疏 |
| 检索 | 稠密 top-5 | 稠密 top-20 + 稀疏 top-20 → RRF → top-5 |
| 会话 / 缓存 / 生成 / 溯源 | 完全相同 | 完全相同 |

#### `scripts/vision_caption.py`

**职责**：离线视觉解析，把图像块的图内语义转成中文描述，幂等可重跑。

**流程**：

1. 读取 `data/parsed/<stem>.parsed.json`，筛出 `type == "image"` 的块
2. 按 2.3 的路径规则定位图片文件
3. 对每个图片调用 `VisionLLM.describe_image(image_path, caption=..., context=...)`
   （既有签名：`describe_image(image_path: Path, *, caption: str = "", context: str = "", prompt: Optional[str] = None) -> str`；`context` 传该图片所属章节标题）
4. 结果写入 `data/parsed/<stem>.vision.json`，以**图片文件哈希**为键

**幂等设计**：`.vision.json` 已存在的哈希直接复用，不重复调用 API。`--force` 可强制重跑。

**异常兜底**：单张图解析失败（超时、限流、返回为空）**不中断整体流程**，记录告警并在缓存中标记为空；缺失描述的图片块退回为「仅图注」（即 V1 行为），不得因单点失败导致整库重建失败。

### 4.2 修改文件

#### `backend/embedder.py`

- **实现 `encode_sparse()`**（当前为 `raise NotImplementedError`）
- 新增**一次 forward 同出稠密+稀疏**的内部路径，复用 `SentenceTransformer` 已加载的 `auto_model`，避免二次加载 2.3 GB 权重导致内存翻倍
- 保留 `encode()` 的现有行为不变（V1 仍在使用）

**稀疏编码算法**：

```
hidden = auto_model(**encoded, output_hidden_states=True).last_hidden_state
raw    = sparse_linear(hidden).squeeze(-1)          # (batch, seq)
raw    = raw * attention_mask                        # 屏蔽 padding
w      = relu(raw)                                   # 负权重归零
sparse = {token_id: max(w[i] for i where input_ids[i] == token_id)}
```

**必须过滤特殊噪声 token**：实测 `<s>`（id 0）、`</s>`（id 2）、`<pad>`（id 1）也会获得 0.16~0.20 的权重。这些 token 在**任何**文本中都出现，只贡献常量偏置、无区分度，属纯噪声，必须显式排除。

#### `backend/db/milvus_client.py`

- 建集合启用稀疏字段：`create_collection(enable_sparse=True)`（代码已在 `milvus_client.py:111-115`、`127-132` 预留字段定义与 `SPARSE_INVERTED_INDEX` + `IP` 索引，当前默认 `False`）
- 新增 `search_sparse(query_sparse, top_k)`，与既有 `search_dense()` 对称
- `insert_vectors(..., sparse_embeddings=...)` 已支持写入，无需改动

#### `scripts/chunk_split.py`

见 5.4 截断兜底。

#### `backend/config.py` / `.env.example`

见第六章配置变更。

#### `backend/api/query.py`

将硬编码的 `from backend.rag_pipeline.v1_pipeline import get_pipeline` 改为按配置选链路：

```python
get_pipeline_by_name(settings.pipeline_version)
```

响应契约不变。

### 4.3 刻意不改动的文件

**`backend/rag_pipeline/v1_pipeline.py` 一个字都不改。**

理由：重灌知识库后**索引内容已变**（图像块 content 追加了视觉描述）。只要 V1 代码保持原样，V1 在新索引上的任何指标变化就能**干净归因到索引改动**；若顺手重构了它，就再也分不清指标波动来自代码改动还是索引改动。

这是对 ADR-010「公共逻辑抽到共享模块」的**有意偏离**，取舍会在 ADR 中记录：V2 与 V1 之间存在部分重复代码，换来的是基线可归因性。

## 五、关键实现细节

### 5.1 稀疏向量的形式

- 输出 `{token_id: weight}`，token_id 为 BGE-M3 词表中的整数 id
- Milvus `SPARSE_FLOAT_VECTOR` 的索引为 `uint32`，**token_id 可直接使用**，无需额外映射
- 未出现的维度不存储（真正的稀疏），实测单条查询非零维度约 11~12 个

### 5.2 检索参数

| 参数 | 取值 | 来源 |
| --- | --- | --- |
| 稠密候选数 | 20 | `settings.retrieve_candidate_k`（.env 已有） |
| 稀疏候选数 | 20 | 同上 |
| 融合后 top_k | 5 | `settings.retrieve_top_k`（.env 已有） |
| RRF k | 60 | `settings.rrf_k`（.env 已有，**不得硬编码**） |

> 上述四个配置项在 V1 阶段已定义但**从未被任何业务代码读取**（除 `retrieve_top_k`）。V2 是它们首次真正生效的版本。

### 5.3 稀疏通道的度量

稀疏向量使用 **IP（内积）** 度量 —— BGE-M3 的 lexical weights 非负且不归一化，内积即为加权词匹配得分，这是 BGE-M3 稀疏表示的标准用法。

### 5.4 截断兜底（避免 content 超限）

**真正的字段上限在 Milvus，不在 MySQL**：

| 存储 | 字段类型 | 上限 | 是否构成约束 |
| --- | --- | --- | --- |
| MySQL `kb_chunks.content` | `MEDIUMTEXT` | 约 16 MB | 否 |
| **Milvus `content` 标量字段** | `VARCHAR(8192)` | **8192** | **是**（`_MAX_LEN_CONTENT`） |
| `CHUNK_MAX_CHARS` | 应用层截断 | 2000 | 是（当前实际生效） |

**适用范围**：本节的截断兜底针对**独立块（表格 / 图片）**，即 `_standalone_block()`（`chunk_split.py:178-196`）。

正文块不受影响 —— 正文由 LangChain 按 `chunk_size=500` 切分，产出长度天然受限，且现有代码未对其做二次截断。

**问题**：`chunk_split.py:190` 现有截断 `content[: settings.chunk_max_chars]` 发生在**追加视觉描述之前**；若先追加再截断，硬切片可能把描述拦腰截断，甚至在极端情况下把描述整段切掉。

**设计：保护性截断，保证图注完整、描述按额度分配**

```
原始图注 caption
视觉描述 desc

若 len(caption) + len(desc) <= chunk_max_chars:
    content = caption + "\n[视觉解析] " + desc
否则:
    预算 = chunk_max_chars - len(caption) - len(标记串)
    content = caption + "\n[视觉解析] " + desc[:预算] + "…（描述已截断）"
```

**配套兜底**：

1. **向量化用完整 content** —— 保证检索质量不因存储字段限制受损

2. **⚠️ Milvus 侧的既有截断是失效的，已修复（2026-09-20 实测发现）**

   原实现为 `milvus_client.py` 中的 `str(contents[i])[:_MAX_LEN_CONTENT]`，
   **按字符切片**；而 Milvus 的 `VARCHAR(max_length=8192)` 按 **UTF-8 字节**计数。
   一个中文字符占 3 字节，因此对中文内容切片到 8192 字符实际是 **24576 字节**，
   Milvus 直接拒绝整条插入：

   ```
   MilvusException(code=1100,
       message=length of varchar field content exceeds max length,
       row number: 0, length: 24576, max length: 8192)
   ```

   注意这是**整条插入失败**，不是静默截断。触发阈值是 **2730 个中文字符**
   （8192 ÷ 3）；当前 `CHUNK_MAX_CHARS=2000`（=6000 字节）尚未触达，
   因此该缺陷此前一直潜伏，一旦调大配置就会全面写不进去。

   **已修复**：新增 `_truncate_utf8(text, max_bytes, field=...)`，按字节截断
   （`errors="ignore"` 避免在多字节字符中间切断时抛异常），并在截断时记 WARNING。
   回归测试见 `tests/test_milvus_sparse.py::test_超长中文_content_写入时被截断到字节上限`。

3. **⚠️ 写入后必须 flush，否则新数据静默不可检索（2026-09-20 实测发现并修复）**

   实测：同一进程内先 `insert` 再 `search`，**不 flush 时命中数为 0**；
   `flush` 后立刻命中。Milvus 在默认一致性级别下，新写入的数据要等自动 flush
   之后才进入可检索状态。

   该失败是**静默的** —— 不报错，只是少召回甚至完全查不到，
   属于本项目 ADR-013 记录过的最难察觉的一类故障。

   原代码库中**没有任何 flush 调用**。V1 之所以未暴露此问题，仅因为知识库是
   提前一天灌入的，期间已被自动 flush。

   **已修复**：新增 `flush_collection()`，并在 `insert_vectors()` 写入完成后调用。

4. **本次需新写的是 `chunk_max_chars`（2000）这一层** —— 即上面公式中的保护性截断，
   保证追加视觉描述后不会出现「图注被保留而描述被整段切掉」的情况。

5. 截断发生时记录 **WARNING 日志**（含 chunk_id、原长度、截断后长度），便于排查

### 5.5 Trace 日志要求（V2 强化）

V2 第 1 项要求「后端内部完善 Trace 日志」。**必须在融合前保存两路独立召回结果**，逐通道记录：

| 记录项 | 内容 |
| --- | --- |
| 用户原始问题 | 原样记录（含多轮追问时的上下文轮数） |
| 稠密通道召回 | 命中 chunk_id 列表 + **每条相似度分数** + **每条页码** |
| 稀疏通道召回 | 命中 chunk_id 列表 + **每条内积分数** + **每条页码** |
| RRF 融合结果 | 融合后 top_k 的 chunk_id + RRF 分数 + 页码 + **该块在两路中的原始名次** |
| 最终送入生成的上下文 | chunk_id + 文件名 + 页码 |

**关键约束一：两路结果必须在「融合前」分别记录。** 若只记录融合后的结果，将无法回答「某个块是靠稠密还是靠稀疏被召回的」——而这正是 V2 归因分析的核心问题。

**关键约束二：分通道的页码取自 Milvus 的冗余标量字段，而非 MySQL。**
MySQL 的元数据回填发生在 RRF 融合**之后**，因此融合前拿不到 MySQL 的页码。此时页码来源是 Milvus 中冗余保存的 `page_no`（`search_dense()` 的返回结构已含该字段）。

这与 ADR-005 的分工一致 —— Milvus 的 `page_no` / `content` 本就是「用于检索结果快速回显与日志记录」，**对外返回的溯源信息仍以 MySQL 为准**。因此：

- **Trace 日志**中的页码 → 用 Milvus 的 `page_no`（仅后端可见）
- **响应体源码**中的页码 → 用 MySQL 回填值（用户可见，权威）

实现时 `search_sparse()` 的返回结构应与 `search_dense()` 对称，包含 `chunk_id` / `score` / `page_no` / `doc_id` / `content`。

日志 stage 命名建议：`v2_dense_retrieve` / `v2_sparse_retrieve` / `v2_rrf_fuse`（`backend/logging_config.py:173` 已预留 `hybrid_rrf` 作为 stage 取值示例）。

**Trace 仅写入服务端日志文件**，不提供查询接口、不向前端返回（N5 约束）。

## 七、数据重建流程

V2 引入稀疏字段后，**Milvus 集合必须重建**（加字段需 drop 重建），现有 127 条向量需重灌。

```bash
# ① 视觉解析（6 次 qwen-vl-plus 调用，结果缓存到 .vision.json）
.venv/Scripts/python.exe -m scripts.vision_caption

# ② 重新分块（追加视觉描述 + 保护性截断）
.venv/Scripts/python.exe -m scripts.chunk_split --force

# ③ 重建集合并灌入稠密 + 稀疏向量
.venv/Scripts/python.exe -m scripts.embedding_store --rebuild
```

**不需要重跑 MinerU**（复用已有 `.parsed.json` 与图片文件），因此总耗时约 2 分钟向量化 + 6 次视觉 API 调用，而非全量重建的 10 分钟以上。

**安全性**：

- 该 Milvus 实例上有 7 个集合，重建**只 drop `cs_kb_chunks`**，其余 6 个来自其它项目的集合不受影响
- 数据可完整重建（源 PDF 与解析产物均在）

## 八、评测与归因方案

### 8.1 三点评测

| # | 评测点 | 索引 | 检索 | 命令 | 隔离出的贡献 |
| --- | --- | --- | --- | --- | --- |
| 1 | **原始基线**（已有） | 旧（无视觉描述） | 纯稠密 | — | 参照系 |
| 2 | **V1 重跑** | **新**（含视觉描述） | 纯稠密 | `--pipeline v1 --tag v1_enriched` | **视觉解析的净贡献** |
| 3 | **V2** | **新** | 稠密 + 稀疏 + RRF | `--pipeline v2 --tag v2` | 视觉解析 + 混合检索的总贡献 |

**归因逻辑**：

- 点 2 − 点 1 = 视觉解析带来的变化（检索方法未变，只有索引内容变了）
- 点 3 − 点 2 = 混合检索带来的变化（索引相同，只有检索方法变了）

该设计的成立前提是 **`v1_pipeline.py` 保持不修改**（见 4.3）—— 否则点 2 与点 1 的差异将混入代码改动因素，归因失效。

### 8.2 重点观察样本

| 样本 | 基线表现 | V2 期望 |
| --- | --- | --- |
| **R09**（功能充分性） | 完全未命中 | 稀疏通道提供「功能充分性」词面信号，期望进入 top-5 |
| **R08 / G04 / S12**（软件质量特性，同一知识块） | 排名第 5 / 忠实度 0.625 / 误拒答 | 第 6 页图 2 的视觉描述入索引后期望明显改善 |
| **R12**（GB/T 16260.1 标准号） | 命中（RR 0.50） | 稀疏通道对标准编号敏感，期望名次前移 |

### 8.3 评测口径

沿用 ADR-007：`recall@k` / `MRR` / `refusal_accuracy` **自算**（确定性、可复现），`faithfulness` 走 **RAGAS**。三者均在**同一套评测集**（`eval/测试数据集.json`）上运行，与基线直接可比。

## 十一、风险与回退

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 集合重建，现有 127 条向量作废 | 检索中断若干分钟 | 可完整重建；重建期间避免提供服务；不影响其它项目集合 |
| V2 指标不如 V1 | 迭代失败 | `PIPELINE_VERSION=v1` 一行回退，接口与前端零变化；如实记录而非调参凑数 |
| 视觉描述质量差 | 引入噪声反而拉低指标 | 描述缓存于 `.vision.json` 可人工审校；`VISION_ENABLED=false` 可整体关闭 |
| 稀疏通道引入无关命中 | 精度下降 | RRF 的 k=60 使单通道高名次不足以主导融合；必要时调整 `RETRIEVE_CANDIDATE_K` |
| 内存翻倍（同时持有 ST 与 transformers 两份模型） | CPU 环境 OOM | 复用 `SentenceTransformer.auto_model`，全程只加载一份权重（已按此设计） |
| 截断导致描述失真 | 个别块语义不完整 | 触发时记录 WARNING；描述预算优先于图注之后的尾部内容 |
