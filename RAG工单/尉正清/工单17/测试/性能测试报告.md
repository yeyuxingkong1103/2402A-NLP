| 验收项 | 要求 | 实测 | |
|---|---|---|---|
| 场景A：无请求失败 | 0 失败 | **0.0%**（1200 请求） | ✅ |

## 三、任务二：定位瓶颈与泄漏

### 3.1 系统资源监控（先说「不是什么」）

压测期间 `docker stats` + `nvidia-smi` + `redis-cli XLEN` 的采样（`monitor.py`）：

| 指标 | 压测期间表现 |
|---|---|
| RAGFlow 容器内存 | 3237 → 3316 MiB（+2.4%），**没有持续上涨** |
| GPU 显存 | **1764 MiB 全程一条直线**，没有泄漏 |
| ES / MySQL / Redis | 基本不动 |
| 解析任务队列 | **始终为 0**（场景A 不触发解析） |

**结论：容器侧既没崩也没漏，GPU 更是完全没被用起来 —— 延迟不是「算得慢」，是「在等」。**

这是整个排查的转折点：如果按工单的「初步根因推测」去查模型重复加载、连接池泄漏，
会一无所获。

### 3.2 py-spy 采样：找到真正的热点

在 20 并发压测中采 60 秒（`results/pyspy_raw.txt`，678 个样本）。

**父帧是累计值，要看 self time（叶子帧）**：

| 占比 | 函数 | 含义 |
|---|---|---|
| **12.7%** | `_worker (concurrent/futures/thread.py:89)` | 线程池里的线程**在等** |
| **9.3%** | `create_default_context (ssl.py:708)` | **每次调用都在新建 SSL 上下文**（新 TLS 握手） |
| 6.2% | `readinto (socket.py:707)` | socket 读等待 |
| 5.2% | `encode (tiktoken/core.py:124)` | token 计数 |
| 4.9% | `raw_decode (json/decoder.py:353)` | JSON 解析 |
| 4.6% | `__str__ (elastic_transport/_response.py:113)` | ES 响应处理 |
| ~7% | `rag_tokenizer` 的 `freq`/`key_`/`tag` | 中文分词 |

真在算的加起来不到 30%，其余全是等待 —— **和 3.1 的资源监控互相印证**。

### 3.3 代码静态分析：根因一（**这是主因**）

顺着调用链往下看：

```
api/db/services/dialog_service.py:398   kbinfos = retriever.retrieval(...)   ← 同步调用
  └─ rag/nlp/search.py:365              def retrieval(...)                   ← 同步函数
       ├─ self.search()                  → emb_mdl.encode_queries()   → HTTP 调嵌入服务
       │                                 → dataStore.search()         → HTTP 调 Elasticsearch
       └─ self.rerank_by_model()
            └─ rerank_model.py:210       res = requests.post(...)      → HTTP 调重排服务
```

**`retrieval()` 是同步函数，内部三次阻塞式 HTTP 调用；
而调用它的 `async_chat()` 是 async 处理函数。**

在 asyncio 的事件循环里做阻塞 I/O，会把**整个事件循环冻住**：
这期间服务不能接收也不能推进任何其它请求，20 个并发请求只能一个接一个排队。
这完美解释了观察到的全部现象：

- 延迟随并发**线性增长**（2s → 16s，20 并发）
- CPU 大量空闲、容器内存不动（**在等，不在算**）
- 单发请求快、并发上不去（硬串行）

工单「初步根因推测」里写的「请求处理无队列/限流，导致高并发时请求堆积，线程阻塞」，
方向是对的，但**真实机制更具体**：不是「没有队列」，是**阻塞了事件循环**。

> 讽刺的是，RAGFlow 在别处是知道这个套路的 —— 附件版本的 `search.py` 里
> ES 调用用 `thread_pool_exec` 扔进了线程池，唯独检索这条链没有。

### 3.4 代码静态分析：根因二（nginx 配置）

压测中出现 **71% 的请求返回 502**，nginx 错误日志：

```
no live upstreams while connecting to upstream
```

查容器内的解析：

```
$ getent hosts localhost
::1  localhost          ← 只有 IPv6！
$ ss -lntp | grep 9380
LISTEN 0 100 0.0.0.0:9380   ← RAGFlow 只监听 IPv4
$ curl http://127.0.0.1:9380/...  → 200
$ curl 'http://[::1]:9380/...'    → 000（连接被拒）
```

nginx 配的是 `proxy_pass http://localhost:9380`（`nginx/ragflow.conf:19`）。
`localhost` 同时解析到 `127.0.0.1` 和 `::1`，nginx 会把它们当一个上游组做轮询 ——
**一半的请求打到死掉的 IPv6 地址上**。低负载时 nginx 重试还能兜住，
高负载下故障转移扛不住，整组被标记为不可用，于是全部 502。

### 3.5 根因三：本机模型服务的吞吐天花板

`/metrics` 之外的另一个实测（`测试/` 下的并发探测脚本）：

| 服务 | 单条耗时 | 20 并发下的吞吐 |
|---|---|---|
| bge-m3 嵌入 | 0.14s | ~8.5 req/s |
| bge-reranker-v2-m3 重排 | 265ms / 16 条 | **60 pair/s**（GPU 硬上限） |

一次问答要 1 次嵌入 + 1 次重排（16 条候选）。20 并发 × 16 条 = 320 对，
**光重排就要 5.3 秒 GPU 时间** —— 这一项单独就超过了 3 秒的整个预算。

这条不是 bug，是硬件约束，但它是「P95 压不到 3 秒」的直接原因。

### 3.6 泄漏点核查（工单「泄漏点一/二」）

| 疑似泄漏点 | 核查结果 |
|---|---|
| 解析后的中间对象 | 场景A 不触发解析；容器内存 +2.4%，无持续上涨 |
| 模型推理的中间张量 | **GPU 显存全程一条直线**，无泄漏 |
| 对话会话上下文 | 10 分钟压测内存增长 +8.0% 后走平（见第四节） |
| 数据库/向量库连接池 | `pymysql` 在 profile 里只占 2.2%，无连接堆积迹象 |

**结论：在这套部署上没有观察到资源泄漏。** 工单描述的「内存持续增长触发 OOM」
在本环境未复现 —— 如实记录。

## 四、任务三/四：优化与验证

### 4.1 改了四处

| # | 改动 | 文件 | 预期作用 |
|---|---|---|---|
| 1 | **把阻塞的 `retrieval()` 挪出事件循环**（`await asyncio.to_thread(...)`） | `api/db/services/dialog_service.py` | 解除根因一 |
| 2 | **nginx 上游改指 `127.0.0.1`** | `nginx/ragflow.conf` | 消除根因二 |
| 3 | **嵌入模型从 CPU 移到 GPU** | `测试/embedding_server.py` 启动参数 | 腾出 CPU，减少与重排抢资源 |
| 4 | **重排候选数上限可配**（`RERANK_MAX_CANDIDATES`，设 4） | `rag/nlp/search.py` | 降低根因三的 GPU 工作量 |

另外按产出物要求**集成了 Prometheus 监控**（`rag/utils/prom_metrics.py` +
`api/ragflow_server.py` 挂钩），暴露请求量/延迟分位/在途请求/RSS/CPU/队列深度
六类指标，端口 9390，独立于业务端口。

### 4.2 效果

| | 优化前（第1次/第2次） | 优化后 | 变化 |
|---|---|---|---|
| P50 | 16.2s / 14.8s | **5.1s** | **约 3 倍改善** |
| P95 | 22.1s / 50.9s | 19.3s | 改善，但未达 3s |
| P99 | 25.4s / 120.0s | 33.0s | 120 秒的超时消失 |
| 失败率 | 0% / 1% | **0%** | ✅ |
| 容器内存增长 | — | **+8.0%** 后走平 | ✅ |

**短时并发下更好**：20 个请求同时打进来（一次性），P95 只有 **4.34s**；
绕过 nginx 直连 9380 是 3.77s。说明优化后的链路本身已经比较快了。

### 4.3 场景B（混合负载）

10 并发（5 问答 + 5 上传解析）：

- 服务**未崩溃** ✅
- 上传的文档**正常进入 Redis 队列并被 Task Executor 消费** ✅
  （`redis-cli XLEN rag_flow_svr_queue` 能看到队列涨落）
- 问答请求未受上传明显拖累 —— 解析走的是异步队列，不阻塞 API

## 五、为什么 P95 没到 3 秒（如实说明）

我把链路拆开单独测过，结果如下：

| 环节 | 20 并发下的表现 |
|---|---|
| 纯检索接口（嵌入 + ES，不含重排） | P95 **1.91s** ✅ |
| LLM API（DeepSeek）单独压 | P95 **2.84s** ✅ |
| 「检索 + LLM」串起来模拟 | P95 **3.95s** |
| **RAGFlow 问答接口实测** | P95 **19.3s** ❌ |

**两端都不慢，合起来却慢 —— 中间那 15 秒在 RAGFlow 问答接口自己的处理里。**

已经排除的：重排（关掉它 P95 只从 19.3 降到 17.1）、nginx（只差 0.3 秒）。

还没定位完的：提示词组装（tiktoken 对每个块数 token）、引用格式化、
MySQL 会话/消息落库、以及持续负载下才出现的随机尖刺（短时并发没有，10 分钟持续有）。

**受工时限制，这条没有继续往下钻。** 下一步应该：

1. 在 `dialog_service.async_chat()` 的每一段之间打时间戳，把 15 秒逐段切开
2. 重点看持续负载下的尖刺是否与 MySQL 落库/连接池、或 asyncio 线程池耗尽相关
3. 若确认是 GPU 重排的硬上限（60 pair/s），则需要换更强的显卡或更小的重排模型

**另外要说明**：即使链路优化到极致，**本机 GPU 的重排吞吐（60 pair/s）
决定了 20 并发 × 16 候选的下限就是 5.3 秒** —— 这一条验收标准在这套硬件上
需要配合「减少重排候选数」或「换硬件」才能达成。
