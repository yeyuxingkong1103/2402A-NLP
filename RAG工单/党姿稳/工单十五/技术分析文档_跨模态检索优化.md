## 一、工单背景与问题定义

IMDR 工业专利数据集中的专利文档是典型的"文本-图像混合"文档：一篇专利既包含大段说明书正文、权利要求书、著录项，也包含以"说明书附图"形式独立成页的技术图纸（图1、图2、图3……）。图纸页的可提取文本极少，真正表达工艺信息的是图内的部件编号（如 10、11、12、13、14）以及编号之间的**空间关系**（内/外、上/下）与**物料流经顺序**。这类信息在纯文本检索框架下天然是"低信号"的。

工单在问题定义中给出两个典型故障：

- **故障 1（检索无关）**：检索只用文本语义相似度。用户问题"第11页图3中编号13的部件相对于编号12的位置关系"送入向量检索后，命中的是大量**提到"部件""编号"字样但并不含该图纸**的正文块（如权利要求书、具体实施方式段落），真正承载图3的图纸页反而被排在后面甚至检索不到，导致 LLM 上下文里没有图纸信息。
- **故障 2（图文割裂）**：即使检索到了包含图3的页面，系统也只是把它当作一段**文本**参与向量匹配。查询词"编号13""位置关系"与图纸的**图像特征**之间没有建立关联通道，LLM 拿到的仍是文字，无法真正"看图"。

本工单的任务一要求先剖析 RAGFlow 的多模态检索架构（第二章），任务二要求据此设计优化方案（第三章），并在本机复现验证（第四章）。

## 二、RAGFlow 原有检索流程剖析

### 2.1 检索入口与调用链

RAGFlow 的检索主类为 `Dealer`，定义于 `rag/nlp/search.py:37`，其构造函数 `Dealer.__init__`（`rag/nlp/search.py:38`）在 `rag/nlp/search.py:39` 实例化查询处理器：

```python
self.qryr = query.FulltextQueryer()   # rag/nlp/search.py:39
```

从问题到检索的完整调用链（以对话场景为例）：

1. **API / 对话服务入口**。`api/db/services/dialog_service.py` 中先对多轮对话做问题改写，随后发起检索：
   - `questions = [await full_question(...)]`（`api/db/services/dialog_service.py:350`，仅多轮且开启 `refine_multiturn` 时）；
   - `cross_languages(...)`（`:355`，跨语言时）；
   - `questions[-1] += await keyword_extraction(chat_mdl, questions[-1])`（`:368`，开启 `keyword` 时把抽取的关键词拼到问题尾部）；
   - 核心检索调用 `kbinfos = await retriever.retrieval(" ".join(questions), embd_mdl, tenant_ids, dialog.kb_ids, 1, dialog.top_n, dialog.similarity_threshold, dialog.vector_similarity_weight, ..., rerank_mdl=rerank_mdl, rank_feature=label_question(...))`（`api/db/services/dialog_service.py:417-431`）。
2. 检索后处理：`retrieval_by_toc`（`:433`）、`retrieval_by_children`（`:436`）；开启知识图谱时追加 `settings.kg_retriever.retrieval(...)`（`:443`）。
3. **其它入口**均复用同一个 `retriever.retrieval`：
   - SDK 检索 `api/apps/sdk/dify_retrieval.py:138`（Dify 兼容接口，`use_kg` 时 `:153` 调图谱检索）；
   - Agent 检索工具 `agent/tools/retrieval.py:177`（图谱 `:205`、`:218`）；
   - SDK 会话 `api/apps/sdk/session.py:1101`、文档块检索 `api/apps/sdk/doc.py:1562`、`api/apps/chunk_app.py:418`；
   - 独立 Search App 的检索配置存于 `Search.search_config`（默认值见 `api/db/db_models.py:994-996`）。
4. `retriever` 即 `Dealer.retrieval`（`rag/nlp/search.py:363`），其内部调用 `Dealer.search`（`:75`）与重排逻辑（`:406` / `:423`）。

### 2.2 查询理解与重写

RAGFlow 的"查询理解"由 `FulltextQueryer`（`rag/nlp/query.py:27`）承担，构造函数实例化了两个子处理器（`rag/nlp/query.py:29-30`）：`term_weight.Dealer`（词权重）与 `synonym.Dealer`（同义词）。

- **分词与词权重**：`FulltextQueryer.question(txt, tbl="qa", min_match=0.6)`（`rag/nlp/query.py:41`）。中文分支中先做繁简/全半角归一（`:47`），再 `self.tw.split(txt)`（`:99`）切词，对每个词用 `self.tw.weights([tt])`（`:103`）计算权重，并逐词查询同义词 `self.syn.lookup(tt)`（`:104`）。最终把词、权重、同义词编成 ES `query_string` 语法串，返回 `MatchTextExpr`（`:171-173`）。检索侧在 `rag/nlp/search.py:115` 调用 `self.qryr.question(qst, min_match=0.3)` 得到 `matchText, keywords`。
- **关键词抽取（LLM 版）**：`keyword_extraction`（`rag/prompts/generator.py:188`）使用模板 `rag/prompts/keyword_prompt.md`，把 LLM 抽出的关键词**直接拼接到原问题尾部**再检索（`api/db/services/dialog_service.py:368`），并不重写问题语义。
- **多轮问题改写**：`full_question`（`rag/prompts/generator.py:218`）用模板 `full_question_prompt.md` 把带指代的多轮问题补全为完整单轮问题；`cross_languages`（`:252`）做跨语言翻译。
- **图谱场景专用重写**：`KGSearch.query_rewrite`（`graphrag/search.py:46`）用 `minirag_query2kwd` 提示词从问题中抽取"答案类型关键词"与"实体"（返回 `type_keywords, entities_from_query`），供知识图谱检索用（`graphrag/search.py:162`）。

**关键结论**：RAGFlow 的查询理解只做**分词、词权重、同义词扩展、多轮补全、关键词拼接、跨语言翻译、图谱实体抽取**。全流程中**没有任何针对"图3""第11页""如图""附图"这类视觉引用的识别、拆解或改写逻辑**（`rag/nlp/query.py:41` 与 `rag/prompts/keyword_prompt.md` 都只把问题当普通自然语言文本处理）。"图3""第11页"进入检索器后，会跟其它词一样被切成 token，"图""页"等单字权重低，几乎不产生区分度——这正是故障 1 的根源之一。

### 2.3 多路召回

RAGFlow 的召回实际是"**一路向量 + 一路全文**"，两路都在 `Dealer.search`（`rag/nlp/search.py:75`）里组装：

- **全文召回（BM25/query_string）**：`matchText, keywords = self.qryr.question(qst, min_match=0.3)`（`rag/nlp/search.py:115`）得到 `MatchTextExpr`。`MatchTextExpr` 定义于 `common/doc_store/doc_store_base.py:56`，携带 `fields`、`matching_text`、`topn`、`extra_options`。在 ES 侧它被翻译成 `query_string`（`rag/utils/es_conn.py:91-99`，`type="best_fields"` 并设 `minimum_should_match`、`boost`）。
- **向量召回（embedding + 向量库）**：`matchDense = await self.get_vector(qst, emb_mdl, topk, req.get("similarity", 0.1))`（`rag/nlp/search.py:123`）。`Dealer.get_vector`（`:53`）对**问题文本**调用 `emb_mdl.encode_queries(txt)`（`:54`）编码，返回 `MatchDenseExpr`（`common/doc_store/doc_store_base.py:70`），向量列名为 `q_{dim}_vec`（`rag/nlp/search.py:60`）。在 ES 侧翻译为 kNN 查询（`rag/utils/es_conn.py:106-112`）。

两路结果结构：ES 返回命中文档，经 `self.dataStore.get_doc_ids(res)`、`get_fields(res, src + ["_score"])` 等转成 `Dealer.SearchResult`（`rag/nlp/search.py:164-172`），其中 `field` 里含 `content_with_weight`、`content_ltks`、`img_id`、`position_int` 等字段（默认 `src` 列表见 `rag/nlp/search.py:92-96`）。

注：`search.py` 的 `src` 默认字段中包含 `img_id`，说明 RAGFlow 在检索阶段就会把"图片引用"随块一并取出，但这只是**取回字段**，不是"图像向量召回"。

### 2.4 融合与重排

**（1）向量库侧融合**。RAGFlow 把全文表达式与向量表达式**合并成一个 hybrid 请求**下发，而不是在应用层分别召回后再合并：

```python
fusionExpr = FusionExpr("weighted_sum", topk, {"weights": "0.05,0.95"})   # rag/nlp/search.py:128
matchExprs = [matchText, matchDense, fusionExpr]                          # rag/nlp/search.py:129
```

- `FusionExpr` 定义于 `common/doc_store/doc_store_base.py:120`。
- **ES 侧**：`rag/utils/es_conn.py:83-89` 解析 `weighted_sum` 的 `weights`，第 2 项作为 `vector_similarity_weight`（默认 `0.5`，`:81`），随后把全文 `query_string` 的 `boost` 设为 `1.0 - vector_similarity_weight`（`:99`）——即 `.05,.95` 近似"文本权重 0.05、向量权重 0.95"的加权混合；同时 `rank_feature`（如 PAGERANK、tag）以 `should` 子句加入（`:114-118`）。
- **Infinity 侧**：`rag/utils/infinity_conn.py:207-210` 对 `weighted_sum` 融合设置 `normalize="atan"`，由向量库在融合前对每路分数归一。
- 若首轮命中为 0，`Dealer.search` 会降低 `min_match` 并放宽相似度阈值重试（`rag/nlp/search.py:136-148`）。

**（2）应用层重排。** `Dealer.retrieval`（`rag/nlp/search.py:363`）在拿到 `sres` 后做二次排序：

- 若传入 `rerank_mdl`：调用 `self.rerank_by_model(rerank_mdl, sres, question, 1 - vector_similarity_weight, vector_similarity_weight, ...)`（`rag/nlp/search.py:406-413`）。`rerank_by_model`（`:334`）用 `rerank_mdl.similarity(query, texts)`（`:351`）对每个候选块打分，最终分 `= tkweight*tksim + vtweight*vtsim + rank_fea`（`:355`）。
- 否则：Infinity 直接用向量库归一后的 `_score`（`:415-419`）；ES 走 `Dealer.rerank`（`:295`），它调用 `self.qryr.hybrid_similarity(...)`（`:327`）做"词相似度 + 向量相似度"加权（默认 `tkweight=0.3, vtweight=0.7`，`:295-296`）。
- **rerank 模型接入点**在 `rag/llm/rerank_model.py`：`Base`（`:28`）定义统一接口 `similarity(query, texts) -> (rank, token_count)`（`:36`）；具体厂商实现如 `HuggingfaceRerank`（`:387`，`similarity` 于 `:414`，走本地 `127.0.0.1/rerank`）、`JinaRerank`（`:56`）、`LocalAIRerank`（`:109`）等。它们都返回一个与 `texts` 等长的相关性分数组。
- **权重参数落地**：`retrieval(..., vector_similarity_weight=0.3, ...)`（`rag/nlp/search.py:372`）是默认值；对话侧来自 `dialog.vector_similarity_weight`（`api/db/services/dialog_service.py:425`），默认 `0.3`（`api/db/db_models.py:868`）；相似度阈值 `similarity_threshold` 默认 `0.2`（`:867`），最终在此阈值上过滤（`rag/nlp/search.py:438`）。

### 2.5 多模态支持现状（图像语义检索能力）

这是本次最关键的结论。RAGFlow 的"多模态"**不是图像语义向量检索**，而是"**索引期图像转文本 + 检索期回传图片引用**"：

1. **索引期：图像 → 文本（可选）**。解析时可由 VLM（`LLMType.IMAGE2TEXT`，见 `common/constants.py:75`）对图片生成文字描述，并**追加到 chunk 的文本里**。例如 `deepdoc/parser/figure_parser.py:126` 的 `vision_figure_parser_docx_wrapper_naive`，在 `:149/:234` 用 `vision_llm_figure_describe_prompt()`（`rag/prompts/generator.py:322`，模板文件 `rag/prompts/vision_llm_figure_describe_prompt.md`）生成描述，然后 `chunks[idx]['text'] += description`（`deepdoc/parser/figure_parser.py:168`）。`rag/app/picture.py` 同样把图片交给 `cv_mdl.describe(...)` 再 `tokenize`（`rag/app/picture.py:80-87`），图片本体则存入 `doc["image"]`（`:66`）。**注意：这一步产出的仍是纯文本，之后与普通文本一样被当作字符串编码。**
2. **图像存储与回传**。索引时若 chunk 带 `image`，`rag/svr/task_executor.py:299-317` 的 `upload_to_minio` 会调用 `image2id`（`rag/utils/base64_image.py:32`）把图片上传到 MinIO，并把 `d["img_id"] = f"{bucket}-{objname}"`（`base64_image.py:74`）；无图则 `d["img_id"] = ""`（`task_executor.py:314`）。检索时 `img_id` 作为 `image_id` 随块返回（`rag/nlp/search.py:471`），`chunks_format` 再把它暴露给 API/前端（`rag/prompts/generator.py:40`，字段 `"image_id"` 于 `:50`），供前端**渲染展示**。
3. **向量编码只有文本**。索引时的 `embedding()`（`rag/svr/task_executor.py:569`）只对 `content_with_weight` 文本编码，写入 `q_%d_vec`（`:619`）；`Dealer.get_vector`（`rag/nlp/search.py:53`）也只编码问题文本。检索、融合、重排全程**不涉及图像向量**。
4. **存在但未接线的图像向量能力**。`rag/llm/embedding_model.py` 中有 `JinaMultiVecEmbed`（`:354`），其 `encode` 支持传入图片 bytes 并请求 jina-embeddings-v4 的图像向量（`:377`）。但全仓库检索无任何地方实例化或调用它（仅类定义处出现一次）。

**结论**：RAGFlow 原生**不支持图像语义检索（图文联合向量检索 / CLIP 式跨模态向量）**。它最多支持"用 VLM 把图转成文字描述后并入该块文本"，再走普通文本向量；图片本体的作用仅是在结果里回传 `image_id` 供界面显示。因此对"编号13 相对编号12 的位置关系"这类问题，只要 VLM 未开启或描述不到位，检索与排序阶段就完全无法利用图像的视觉结构——这正是故障 2 的架构性根因。

### 2.6 瓶颈定位

| 故障 | 对应源码位置 | 根因 |
|---|---|---|
| 故障 1：检索无关、漏掉图纸页 | `rag/nlp/query.py:41`（`question`）、`rag/nlp/search.py:115`（调用处）、`rag/nlp/search.py:123`（向量只编码文本）、`rag/prompts/keyword_prompt.md` | 查询理解只做分词/词权重/同义词/关键词拼接，**不识别视觉引用**；"图3""第11页"退化为低权重普通词，图纸页与正文块在同一个文本向量空间里被同等对待，图纸页无任何加成 |
| 故障 2：图文割裂 | `rag/nlp/search.py:471`、`rag/prompts/generator.py:50`、`rag/svr/task_executor.py:569`、`deepdoc/parser/figure_parser.py:168`、`rag/llm/embedding_model.py:354` | 图像只在索引期被 VLM 转成文本追加到 chunk（且默认无 IMAGE2TEXT 模型时不启用），检索/融合/重排全用文本向量；`img_id` 仅回传展示；图像向量类 `JinaMultiVecEmbed` 存在但**未接线**。视觉结构（位置、流向）无通道进入检索 |

## 三、本次优化的技术方案设计

本机在 `工单十五/` 用 Python 复现了 RAGFlow 的检索链路（同样的"向量 + 全文"骨架），并针对工单任务二的各点做了增强。全部超参集中在 `config.py`，可外部配置。

### 3.1 优化查询理解：识别视觉引用并定位图纸块

对应文件 `query_understanding.py`：

- `parse_visual_refs(query)`（`query_understanding.py:17`）：用正则 `config.FIG_REF_RE`（`config.py:89`，`图\s*([0-9]{1,2})`）抽图号、`config.PAGE_REF_RE`（`config.py:88`，`第\s*([0-9]{1,3})\s*页`）抽页码，并匹配视觉关键词表 `VISUAL_REF_KEYWORDS`（`config.py:87`）。返回 `{has_visual, labels, pages, keywords}`——这补齐了 RAGFlow 完全没有的"视觉引用识别"。
- `locate_figures(refs, chunks)`（`query_understanding.py:38`）：遍历 `type=="figure"` 的图纸块，按图号（`c["labels"]`）或页码（`c["page_no"]`）命中，返回块下标列表——把"图3/第11页"精确定位到具体图文块。
- `build_figure_query(query, refs, chunks, figure_hits)`（`query_understanding.py:54`）：构造"**图像增强查询**"——把问题原文与命中的图纸块的图像描述文本拼接（`f"{query}\n【图纸内容参考】{desc}"`，`:70`）。图纸描述由解析链路（工单十四）生成并写入图形块正文（见 `chunker.py:141` 的 `build_figure_chunks`：汇聚 VLM 描述、图内 OCR 标注、说明书对应段落）。

### 3.2 多路召回融合：四路加权

对应文件 `cross_modal_retriever.py`，主入口 `retrieve(query, index, optimized=True)`（`cross_modal_retriever.py:76`）。四路召回：

1. `text_vector`：原始问题文本向量，`vector_search(query, index["embeddings"], VECTOR_TOP_K)`（`:86`，`VECTOR_TOP_K=30`）。
2. `bm25`：全文检索，`bm25_search(query, index["bm25"], BM25_TOP_K)`（`:87`，`BM25_TOP_K=30`），BM25 实现于 `bm25.py:33`。
3. `figure_vector`：**图像增强查询**的向量召回，`vector_search(enhanced, ...)`（`:89`，`FIGURE_TOP_K=12`）。仅当构造出增强查询时才启用（`:88`）。
4. `figure_label`：图号/页码**精确匹配路**，`label_route(refs, chunks, figure_hits)`（`:91`，函数于 `:30`）——把被引用的图纸块给满分、并把提及该图号的文本块给 0.6 倍的次高分。

融合采用**加权分数融合** `fuse(routes, weights)`（`cross_modal_retriever.py:51`）：每路先 `normalize_route`（`:41`）归一化到 [0,1]（异源分数可加），再乘权重累加。权重即 `config.ROUTE_WEIGHTS`（`config.py:77-80`）：

```python
ROUTE_WEIGHTS = {"text_vector": 0.35, "figure_vector": 0.35,
                 "bm25": 0.15, "figure_label": 0.15}
```

**权重设计理由**：文本向量与图像增强向量是两条最主要的语义通道，各给 0.35，保证"问题语义"与"图纸语义"两个方向都被检索到；BM25 给 0.15 兜底精确词匹配（部件名、图号等）；图号精确匹配给 0.15，作为对"图3"这类强引用信号的确定性补强，避免纯语义路径漏召。四路权重之和为 1，便于解释与调参。

### 3.3 图文联合向量检索：以文代图的"图像增强查询"

工单要求的"图文联合向量检索"，本机因为无法部署 CLIP 类双塔模型，采用**工程等价的"以文代图"方案**：先用 VLM/规则把图纸转成图像描述文本（`figure_describer.py`），再把这描述拼进查询，使"编号13""位置关系""流经顺序"等查询词与图纸描述在**同一个文本向量空间**中对齐。关键实现：

- 图纸描述生成：`figure_describer.py` 的 `PROMPT`（`:14`）明确要求 VLM 输出"部件编号指向的部件名称、相对位置关系、箭头气流/运动方向及先后顺序"；`describe_with_vlm`（`:54`）调 Qwen2-VL-2B；不可用时退化为 `rule_description`（`:80`）。
- 图纸块构造：`chunker.py` 的 `build_figure_chunks`（`:141`）把"图号 + 描述 + 图内标注 + 说明书对应段落"拼成一条可检索文本，`link_description`（`:46`）负责在说明书里按"图N所示/显示"锚点抽取对应段落。
- 检索侧据此生成 `figure_vector` 路（`cross_modal_retriever.py:89`）与 `figure_label` 路（`:91`）。

由此，"图3 的图像描述文本"成为**强化的检索条件**，与原始问题一同参与向量检索——这就是本机对"图文联合向量检索"的落地形式。

### 3.4 引入重排模型

对应文件 `reranker.py`，用 `bge-reranker-base` Cross-Encoder 做跨模态重排：

- `load_reranker`（`reranker.py:14`）惰性加载 `CrossEncoder(config.RERANK_MODEL_PATH)`（`config.py:44`）。
- `rerank(query, candidates, chunks, top_k)`（`reranker.py:32`）：对每个候选块，用 `score_pairs`（`:25`）计算问题与块文本的逐对相关性分，再做**加权综合**：

```python
combined = RERANK_WEIGHT * n_rerank + FUSION_WEIGHT * n_fusion   # reranker.py:54-55
```

其中 `n_rerank`、`n_fusion` 分别是归一化后的重排分与融合分（`:50-51`）。`RERANK_WEIGHT=0.65`、`FUSION_WEIGHT=0.35`（`config.py:82-83`），由 `RERANK_ENABLED`（`config.py:81`）总开关控制。设计理由是：重排分占主导以体现 Cross-Encoder 的精细语义判断，但保留 0.35 的融合分，使多路召回的信号不至于被完全丢弃。

### 3.5 优化提示工程

- 生成侧系统提示 `SYSTEM_PROMPT`（`generator.py:13`）明确写入："**当问题涉及图纸时，请结合以下技术图纸的描述进行分析**"，并逐项要求结合：部件编号指向的部件名称、部件间相对位置关系、物料/气流的流经顺序、调整某部件需操作哪个部件；还规定"图纸描述与说明书正文不一致时，以图纸描述中明确写出的空间关系为准"，并要求"先用不超过 80 字说明判断依据并引用片段编号，再输出 `答案：X`"。这直接把 LLM 的注意力导向图纸块中的结构化视觉信息。
- 上下文的组装 `assemble_context`（`cross_modal_retriever.py:135`）**把图纸块排到最前并显式标注类型**（`c["type"] != "figure"` 排序，`:138`；抬头含块号、来源页、类型中文名 `TYPE_LABEL`，`:132/:141`），减少长上下文里图纸块被淹没的问题。
- 最终送 LLM 的块数 `FINAL_TOP_K=6`（`config.py:72`），上下文上限 `CONTEXT_MAX_CHARS=12000`（`config.py:74`）。

### 3.6 被引用图纸块的加成（防止精确引用被语义淹没）

在融合+重排之后，`_apply_label_boost(ranked, chunks, figure_hits)`（`cross_modal_retriever.py:107`）对被图号/页码精确命中的图纸块再加 `FIGURE_LABEL_BOOST=0.30`（`config.py:84`），确保"被引用的图纸"稳定进入 Top-3。

### 4.4 第 2 题：优化前失败、优化后修复

- 问题："本发明的分散装置包含以下哪个组件？" 标准答案 A（链条）。
- **优化前**：预测 D。`llm_raw` 为"依据片段 `CN100347506C.pdf#p7#t1`，落料架内侧面上设有栓钉，未提及链条、螺旋叶片、振动筛或旋转刮板，故均不符。答案：D。" 查看优化前 Top 片段（`results.json` 中题 2 的 `top_chunks`）：`p7#t1、p1#biblio、p6#t0、p4#t0、p4#t1、p1#t1`——**没有一块提到"链条"**。而真正含答案证据的 `CN100347506C.pdf#p5#t0`（原文："……该分散装置具有一链条……"）未被召回进上下文。模型只能"看不到证据就乱选"，答 D。
- **环节定位**：这是**召回/排序**环节的问题，不是查询理解：该题 `refs.has_visual=false`，四路里的 `figure_vector`、`figure_label` 均未启用，优化前后都只跑 `text_vector`+`bm25`。差别在于（a）融合权重由等权 0.5/0.5 变为 `ROUTE_WEIGHTS` 的 0.35/0.15，（b）启用了 `bge-reranker-base` 重排。
- **优化后**：预测 A。`p5#t0` 由"未进入 Top-6"升到**第 5 名（分 0.8118）**，进入上下文，`llm_raw` 为"依据片段 `CN100347506C.pdf#p5#t0` 和 `#p7#t0`，说明书明确记载分散装置具有一链条，链条上可设接点，用于使散料减速和分散。答案：A。" 说明**重排把含证据的块拉回了上下文**，模型随即答对。
- **结论**：第 2 题由**引入 Cross-Encoder 重排**（`reranker.py`）修复。

### 4.5 第 5 题：从连续失败到修复

- 问题："根据第11页图3，散料从部件14进入后，下一步会经过哪个部件？" 标准答案 C（部件13）。
- **检索侧不是瓶颈**：该题图纸块 `CN100347506C.pdf#p11#fig` 在轮次一、二、三的优化前后**始终是第 1 名**（`figure_hit_rank=1`），即图纸信息一直都在上下文里。因此加权重、加图号 Boost、换更重的重排模型对该题都无增益。
- **失败轨迹**：轮次一预测 **A（部件10）**、轮次二预测 **B（部件11）**，均与标准答案 C 不符。
- **真正根因有三**：
  1. **图内视觉结构未被捕获**。`p11#fig` 的图内 OCR 只给出**无序**的标注串"01816120.0 说明书附图第3/3页 14 10 12 13 图3 11"，既没有箭头指向也没有流经顺序。工单在 VLM 提示词（`figure_describer.py:14`）里特意要求"按顺序先经过哪个部件、再经过哪个"，但规则化描述给不出这条信息。
  2. **文本证据存在顺序歧义**。说明书原文是"通过输入管14导入落料架10里的散料通过这些链条或接点而实现减速和分散"，字面顺序是 14 → 10；而出题口径期望 14 → 13（链条才是对散料起作用的分散执行件）。模型据字面选了 10。
  3. **提示词未消歧**。`SYSTEM_PROMPT`（`generator.py:13` 起）虽要求分析"流经顺序"，但没有定义"下一步"到底指"物理上直接相邻的容器"还是"功能上的下一处理部件"。
- **轮次三的修复措施**（两处，均为通用改动、不含具体部件编号）：
  1. **图纸块内部改为权威信息前置**（`chunker.py:154` 起）：顺序调整为「说明书正文中关于图N的文字描述（权威依据）→ 图内 OCR 标注 → 视觉模型自动生成的图形描述（辅助信息）」。检索命中排名不变，但模型读到的**第一段就是权威正文**。
  2. **Prompt 增加两条消歧规则**（`generator.py:25-27`）：一是图纸块内"说明书正文描述"为权威依据、与自动生成的图形描述冲突时一律以正文为准；二是判断流经顺序时须区分"**物料被导入的容器**"与"**物料实际流经并对其起作用的部件**"，后者才是答案。规则只描述判别原则，未出现"14""13""链条"等任何题干关键词，不构成答案泄露。
- **修复效果**：`llm_raw` 变为"依据 `CN100347506C.pdf#p11#fig`：散料经输入管14导入落料架10后，通过链条13或接点实现减速和分散，故下一步经过部件13。答案：C"——**由错转对**，轮次三 6 题全对。
- **结论**：第 5 题的修复点在**图纸块文本组织顺序 + Prompt 消歧**，与召回/排序无关。这也说明"检索排名第 1"不等于"信息可用"，块内的组织方式与提示口径同样是准确率的决定因素。

### 4.6 轮次二的负面结果：VLM 描述在本机受限分辨率下产生幻觉

轮次二在轮次一的基础上追加了本地 VLM（`Qwen2-VL-2B-Instruct`）生成的图形描述，结果**准确率不升反降**（83.3% → 66.7%，第 4、5 题同时答错）。这是一次值得记录的负结果。

`data/figure_descriptions.json` 中的原始证据：

- **第 11 页（图3）**："图中箭头标示的气流或运动方向，按顺序依次是：**10→13→12→14→11**。"——该顺序与说明书正文（14 输入、链条 13 分散）直接冲突，且本机分辨率不足以支撑对箭头方向的判读，属臆造。
- **第 10 页**："图中显示了 **9 个孔**，每个孔都位于不同的位置……此外，还有一个 **8 号孔**"——该页实际 OCR 标注中既无 8 号孔，也没有 9 个孔的标注。
- **第 9 页**：对 2、3、4、5、6 号部件连续给出几乎完全相同的描述"这个部件可能是装置的底座或支撑部分，用于稳定装置"，说明模型并未真正分辨各部件。

**根因**：

1. **分辨率受限**。本机为纯 CPU（i5-1340P，仅 AVX2、无 AVX512/AMX），为把单图推理耗时压到可接受范围，图像被压缩到 `config.py:53` 的 `VLM_MAX_PIXELS = 640×28×28`（约 50 万像素）量级，部件编号在视觉 token 化后难以辨识。
2. **算力约束下的折中配置**。工单建议的 bf16 在本机实测比 fp32 慢约 41 倍，而 fp32 的 2B 权重约占 8.8 GB（整机 16 GB 内存），只能采用 fp32 视觉塔 + 语言塔动态 int8 量化的权宜方案，进一步削弱了细粒度识别。
3. **优先级被写反**。轮次二的 `SYSTEM_PROMPT` 规定"以图纸描述中明确写出的空间关系为准"，且 VLM 描述被放在图纸块**首位**，于是幻觉描述压过了权威的说明书正文——错误的不是 VLM 输出了幻觉，而是**幻觉被赋予了高于领域语料的优先级**。

**三条启示**：

1. CPU 受限场景下，通用 VLM 自动生成的图纸描述可靠性可能低于"规则化描述 + 说明书正文"，不能无条件信任；
2. 任何模型生成的辅助描述都不得获得高于领域权威语料的优先级——**权威顺序必须在图纸块内容与 Prompt 两处同时保证**，只改一处仍会被绕过；
3. 该负结果把"准确率瓶颈在检索"这一假设彻底排除（图纸块始终第 1 名），把优化方向收敛到**数据/描述质量**与**提示消歧**上，直接催生了轮次三的两项修复。

## 五、结论与后续优化建议

**真实结论**：

1. RAGFlow 原生的检索是"**文本向量 + 全文（query_string/BM25）**"的混合检索，向量库侧用 `weighted_sum`（ES 权重 `.05,.95`；Infinity 用 atan 归一）做融合（`rag/nlp/search.py:128`、`rag/utils/es_conn.py:83-99`、`rag/utils/infinity_conn.py:207-210`），应用层再用 `hybrid_similarity` 或外部 rerank 模型二次排序（`rag/nlp/search.py:295/334/406`）。它**没有**针对视觉引用的查询理解，也**没有**原生的图像语义向量检索：图像只在索引期被可选地转成文本追加进 chunk（`deepdoc/parser/figure_parser.py:168`），图片本体仅以 `img_id` 回传展示（`rag/nlp/search.py:471`、`rag/prompts/generator.py:50`）。
2. 本机的优化方案（`cross_modal_retriever.py` 四路召回加权融合 + `query_understanding.py` 视觉引用识别与图像增强查询 + `reranker.py` 跨模态重排 + `generator.py` 定向提示 + `_apply_label_boost` 图纸加成）在轮次三把整体准确率由 **83.3%（5/6）提升到 100.0%（6/6）**，纯文本题由 50.0% 提升到 100.0%，4 个图文问题的图纸块在优化后**全部命中第 1 名**（优化前为第 1～2 名）。
3. 三处增量的来源分别是：第 2 题由**引入 Cross-Encoder 重排**修复（含答案证据的 `p5#t0` 被拉回上下文）；第 4、5 题由**图纸块权威信息前置 + Prompt 消歧**修复。检索侧的排查显示，这 4 个图文问题的图纸块在基线时即已在 Top-3，甚至多数已是第 1 名——**"检索排名第 1"并不等于"信息可用"**，块内文本的组织方式与提示口径同样是准确率的决定因素。
4. 诚实说明：本机"优化前"基线运行在工单十四产出的图文块索引之上，并不等价于 RAGFlow 的原始管线（后者默认没有图纸块、也不做视觉引用识别），因此本报告中的增益幅度不能直接外推到 RAGFlow 原生系统。
5. 轮次二证明了一个反直觉的事实：在 CPU 受限的本机，给图纸块**追加自动生成的视觉描述反而会降低准确率**。诊断结论是模型幻觉叠加优先级写反，而非检索失效（详见 4.6）。

**后续可继续优化的方向**：

1. **真正的图像向量检索**：部署 CLIP/SigLIP 或 jina-embeddings-v4 类双塔模型，对图纸页生成图像向量（RAGFlow 中对应的未接线能力是 `rag/llm/embedding_model.py:354` 的 `JinaMultiVecEmbed`），检索时把文本查询编码到同一空间做图文联合召回——从架构上根治视觉信息只能靠旁路描述进入上下文的问题。
2. **让 VLM 描述真正可用且聚焦结构**：本机 `Qwen2-VL-2B` 在 640×28×28 像素级下产出幻觉（4.6）。可行路径是提高入图分辨率与算力预算（换 GPU 或更大内存机器），并在提示词中强化"箭头方向、部件包裹关系、流经顺序"；在算力不足时，宁可保留规则化描述也不叠加不可靠的自动描述。
