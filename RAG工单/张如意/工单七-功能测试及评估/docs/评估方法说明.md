# 评估方法说明

> 工单编号：人工智能NLP-RAG-功能测试及评估

本文件说明本工单使用的评估指标体系、计算方法与判读标准。
实现代码在 `rag_core/evaluate.py`，按 RAGAS 论文（Es et al., 2023）的方法论实现；
若环境中安装了官方 `ragas` 包，可通过 `evaluate_records(..., use_ragas=True)` 切换到官方实现，
两者指标口径一致。

---

## 一、为什么需要多个指标

单个指标无法刻画 RAG 的质量。典型的失效模式与对应指标：

| 失效模式 | 表现 | 能发现的指标 |
|---|---|---|
| 检索没找对 | 答案凭空编造 | `context_recall`、`hit_rate` |
| 检索找对了但排序差 | 关键信息排在很后面，被截断 | `context_precision` |
| 检索对、答案编造 | 上下文里有，模型不用 | `faithfulness` |
| 检索对、答案跑题 | 答非所问 | `answer_relevancy` |
| 都对但数字错了 | 年份/口径张冠李戴 | `answer_correctness` |

因此本工单同时报告五个 RAGAS 指标 + 三个检索层指标。

---

## 二、RAGAS 五大指标

### 2.1 Faithfulness（忠实度）

**定义**
```
Faithfulness = 答案中能被检索上下文支撑的论断数 / 答案中的论断总数
```

**计算方法**
1. 用 LLM 把答案拆解为若干「原子论断」（不可再分、可独立判断真伪的事实陈述）；
2. 逐条判断该论断能否由检索到的上下文支撑（严格判定：上下文直接包含，
   或可由上下文严格推出；包含上下文中没有的具体数字即判为不支持）；
3. 计算支撑比例。

**判读**
- 1.0 ＝ 答案每一句都有出处，零幻觉
- < 0.7 ＝ 存在明显的编造，需要检查 Prompt 的拒答机制

**本项目的实现要点**
`_judge_support()` 一次性把所有论断与上下文一起交给 LLM 判断，
比逐条调用省 N-1 次请求；LLM 不可用时回退到
`_rough_supported()`（要求数字全中 + 实词重合率 ≥ 0.5）。

---

### 2.2 Answer Relevancy（答案相关性）

**定义**
```
Answer Relevancy = 由答案反向生成的问题 与 原问题 的平均余弦相似度
```

**计算方法**
1. 把答案交给 LLM，让它反向生成 3 个「正好能被该答案回答的问题」；
2. 用嵌入模型算这 3 个问题与原问题的余弦相似度；
3. 取平均。

**原理**
如果答案切题，反推的问题应当与原问题高度相似；
如果答案跑题或全是套话（「综上所述，该公司经营良好」），
反推出来的问题就会发散，相似度下降。

**判读**
- ≥ 0.85 ＝ 答案紧扣问题
- < 0.70 ＝ 答案空泛或答非所问

---

### 2.3 Context Precision（上下文精度）

**定义**
```
Context Precision@K = Σₖ (precision@k × relₖ) / 相关片段总数
```
其中 `precision@k` 是前 k 个片段中相关片段的占比，`relₖ` 表示第 k 个片段是否相关。

**计算方法**
1. 用 LLM 逐条判断每个检索片段对回答该问题是否有用
   （有参考答案时以「能否支撑参考答案」为准绳）；
2. 按上式加权求和。

**为什么用这个公式而不是简单的 precision**
它**对排序敏感**：相关片段排得越靠前，累加的 `precision@k` 越大。
这正对应 RAG 的实际需求——上下文窗口有限，重要的必须排在前面。

**判读**
- ≥ 0.80 ＝ 排序质量好（工单09 的目标线）
- < 0.60 ＝ 大量噪声片段挤占了上下文

---

### 2.4 Context Recall（上下文召回）

**定义**
```
Context Recall = 标准答案的论断中，能被检索上下文支撑的比例
```

**计算方法**
1. 把**参考答案**拆解为原子论断；
2. 逐条判断能否由检索到的上下文支撑；
3. 计算比例。

**注意**
该指标**必须有参考答案**才能计算，无参考答案时返回 NaN 并从均值中剔除。

**判读**
- ≥ 0.90 ＝ 该找的信息基本都找到了（工单09 的目标线）
- < 0.70 ＝ 检索有系统性遗漏，需要提高召回深度或改分块策略

**与 Context Precision 的关系**
召回看「找全没有」，精度看「排好没有」。
两者要一起看：召回低说明检索不行，召回高但精度低说明重排不行。

---

### 2.5 Answer Correctness（答案正确性）

**定义**
```
Answer Correctness = 0.7 × 事实重叠 + 0.3 × 语义相似
```
（权重与 RAGAS 官方实现一致）

**计算方法**
- 事实重叠：参考答案的论断中，能被**生成的答案**覆盖的比例；
- 语义相似：答案与参考答案的嵌入向量余弦相似度。

**为什么事实权重大于语义**
语义相似度高但数字错（「1,379.58 亿」vs「1,397.58 亿」）在金融场景是严重错误，
因此以事实论断的覆盖为主。

## 三、检索层指标

这三个指标不依赖 LLM，纯计算，可在无 API Key 的情况下运行。

### 3.1 Hit Rate@k

命中正确文档的题目比例。前置条件是每道题标注了 `reference_doc`。

```
Hit Rate = 检索结果中包含正确文档的题目数 / 总题目数
```

### 3.2 MRR（Mean Reciprocal Rank）

正确文档首次出现位次的倒数均值。

```
MRR = mean(1 / 正确文档的首次排名)
```

排第 1 得 1.0，排第 2 得 0.5，排第 5 得 0.2。
衡量「用户多快能看到正确结果」。

### 3.3 Recall@k

正确文档被召回的比例，衡量召回覆盖面。

## 四、准确率的口径说明

工单01/02/06 的验收标准提到「准确率 90% 以上」。「准确率」在 RAG 里没有唯一定义，
本工单明确采用**关键词命中式准确率**（`evaluate.keyword_accuracy`）：

对每道题预设若干「答案必须包含的关键信息点」（如 `["1,379.58亿元", "18.2%"]`），
答案命中**全部**关键点才判为正确：

```
准确率 = 全部关键点都命中的题目数 / 总题目数
```

**为什么用这个口径**
- 可自动化、可复现，不依赖人工评分；
- 金融问答的核心是可验证的事实点（数字、名称），关键词是合理的代理；
- 判定严于「部分命中」，避免高估。

**局限**
同义表述（「1,379.58亿」vs「1379.58亿元」）会误判为未命中，
因此 `run_evaluation.py` 支持通过 `--answers` 传入校准后的关键点表。

## 五、指标汇总与报告

`evaluate_records()` 返回的汇总字典包含：

```json
{
  "n": 10, "evaluator": "builtin",
  "faithfulness": 0.0, "answer_relevancy": 0.0,
  "context_precision": 0.0, "context_recall": 0.0,
  "answer_correctness": 0.0,
  "hit_rate": 0.0, "mrr": 0.0, "recall_at_k": 0.0,
  "latency_avg": 0.0, "latency_p95": 0.0, "latency_max": 0.0
}
```

用 `format_summary()` 渲染成对齐的文本表格（按东亚字符显示宽度对齐），
`save_report()` 落盘为「汇总 + 逐题明细」的 JSON。

## 六、性能开销提示

一次完整评估（10 道题 × 5 个指标）大约需要：

| 指标 | LLM 调用次数/题 | 说明 |
|---|---|---|
| faithfulness | 2 | 拆论断 + 判支撑 |
| answer_relevancy | 1 | 反向生成问题 |
| context_precision | 1 | 批量判相关性 |
| context_recall | 2 | 拆论断 + 判支撑 |
| answer_correctness | 2 | 拆论断 + 判覆盖 |
| **合计** | **约 8 次/题** | 10 题约 80 次调用 |

`rag_core.llm` 带磁盘缓存（键为模型 + 消息 + 温度），
**重复跑同一批问题不会重复计费**，可以放心迭代。
