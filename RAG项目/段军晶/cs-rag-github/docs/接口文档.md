## 一、基础信息

### 1.1 服务地址

| 部署方式 | 地址 |
| --- | --- |
| 本机访问 | `http://127.0.0.1:8000` |
| 局域网访问 | `http://<本机局域网IP>:8000` |

> 监听地址与端口在 `.env` 中配置：`APP_HOST`（默认 `0.0.0.0`，即允许局域网访问）、`APP_PORT`（默认 `8000`）。

### 1.2 通用约定

| 项 | 说明 |
| --- | --- |
| 请求编码 | UTF-8 |
| 请求体格式 | `application/json`（文件上传接口除外） |
| 响应格式 | `application/json`，中文不转义 |
| 认证方式 | 无密码、无 token、无鉴权（内网/局域网演示口径）。前端提供账号登录以便区分用户，登录成功后由前端在请求中携带 `user_id` 标记身份；不携带 `user_id` 时行为与改造前完全一致 |
| 字符集 | 请求与响应均使用 UTF-8 |

### 1.3 通用错误响应

所有错误统一返回如下结构：

```json
{
  "detail": "错误说明（中文）"
}
```

| HTTP 状态码 | 含义 | 典型场景 |
| --- | --- | --- |
| `200` | 成功 | — |
| `400` | 请求参数错误 | 问题为空、文件类型不支持 |
| `403` | 无权限访问该资源 | 访问他人的会话历史 |
| `404` | 资源不存在 | 会话 / 问答已被删除、账号不存在 |
| `409` | 资源冲突 | 知识库正在构建中，重复触发 |
| `413` | 请求体过大 | 上传文件超过 50 MB |
| `500` | 服务内部错误 | 依赖服务不可用、模型调用失败 |

> **注意**：`500` 错误对外只返回可理解的中文提示，完整异常堆栈记录于服务端日志（`logs/rag_service.log`），不通过接口返回。

## 二、接口详情

### 2.1 健康检查

**`GET /api/health`**

检查服务本身与三个依赖组件（Milvus / MySQL / Redis）的连通状态。部署验证与压力测试均可使用本接口探活。

**请求示例**

```bash
curl http://127.0.0.1:8000/api/health
```

**响应示例**

```json
{
  "status": "ok",
  "app": "计算机专业知识库 RAG 问答助手",
  "dependencies": {
    "milvus": true,
    "mysql": true,
    "redis": true
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | string | 服务状态，固定为 `ok` |
| `dependencies.milvus` | bool | Milvus 是否可连接 |
| `dependencies.mysql` | bool | MySQL 是否可连接 |
| `dependencies.redis` | bool | Redis 是否可连接 |

---

### 2.2 构建知识库

**`POST /api/kb/build`**

触发知识库构建。完整的处理链路为：

```
MinerU 版面解析 → LangChain 文本分块 → BGE-M3 向量化 → 写入 Milvus + MySQL
```

> **为什么是异步接口**：本项目运行在 CPU 环境，3 份 PDF（74 页）的完整构建包含版面解析与向量化，**耗时可达数十分钟**。若同步执行会直接触发 HTTP 超时，因此本接口**立即返回**，实际进度请通过 `GET /api/kb/status` 轮询。

**请求参数**

| 字段 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `force` | bool | 否 | `false` | 是否强制重新构建。为 `false` 时，已解析过的文档会跳过（增量构建） |

**请求示例**

```bash
curl -X POST http://127.0.0.1:8000/api/kb/build \
  -H "Content-Type: application/json" \
  -d '{"force": false}'
```

**响应示例**

```json
{
  "accepted": true,
  "message": "构建任务已启动，请轮询 /api/kb/status 查看进度",
  "stage": "parsing"
}
```

**错误响应**

| 状态码 | 场景 |
| --- | --- |
| `409` | 知识库正在构建中，请等待当前任务完成 |

---

### 2.4 上传 PDF

**`POST /api/kb/upload`**

上传 PDF 文件到知识库源目录。

> **不会自动解析**：上传后需再调用 `POST /api/kb/build` 才会纳入检索范围。这样设计是因为 CPU 环境下解析耗时较长，若在上传请求内同步完成会触发超时；且连续上传多个文件时逐个触发解析会造成资源争抢。

**请求格式**：`multipart/form-data`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `file` | file | 是 | 待上传的 PDF 文件，**单文件上限 50 MB** |

**请求示例**

```bash
curl -X POST http://127.0.0.1:8000/api/kb/upload \
  -F "file=@D:/资料/GBT 12345-2024 某某标准.pdf"
```

**响应示例**

```json
{
  "accepted": true,
  "file_name": "GBT 12345-2024 某某标准.pdf",
  "file_size": 1048576,
  "duplicated": false,
  "message": "「GBT 12345-2024 某某标准.pdf」上传成功，点击「加载知识库」后即可提问"
}
```

**错误响应**

| 状态码 | 场景 |
| --- | --- |
| `400` | 文件类型不是 PDF |
| `413` | 文件超过 50 MB |

### 2.6 新建会话

**`POST /api/chat/session`**

创建一个新的对话会话。多轮追问时需要携带同一 `session_id`，系统据此维护上下文。

**请求示例**

```bash
curl -X POST http://127.0.0.1:8000/api/chat/session
```

**响应示例**

```json
{
  "session_id": "3f8a1c9d2e4b5a6f7c8d9e0f1a2b3c4d"
}
```

> 会话有效期默认为 1800 秒（30 分钟），在 `.env` 中通过 `SESSION_TTL_SECONDS` 调整。超时后上下文自动清理。

### 2.7 提问（核心接口）

**`POST /api/chat/query`**

基于知识库回答问题，并返回**来源文档与页码**。

**请求参数**

| 字段 | 类型 | 必填 | 限制 | 说明 |
| --- | --- | --- | --- | --- |
| `question` | string | 是 | 1-500 字 | 用户问题 |
| `session_id` | string | 否 | — | 会话 ID。不传则自动新建；传入可保持多轮上下文 |
| `top_k` | int | 否 | 1-20 | 检索片段数量，默认取服务端配置 |
| `role` | string | 否 | `student` / `workplace` | **回答身份（V1.1 新增）**。`student` 学生（轻松易读）、`workplace` 职场（严谨权威）。该参数**只影响生成答案时使用的 system 提示词**，检索、分块、重排、溯源链路完全不受影响；非法值自动回退 `student` 且不报错 |
| `user_id` | string | 否 | — | **登录用户 ID（V1.1 新增）**。传入则本次问答写入该用户的历史记录（MySQL 持久化）；不传则不写历史，行为与改造前一致（兼容 curl / JMeter 压测） |

**请求示例**

```bash
curl -X POST http://127.0.0.1:8000/api/chat/query \
  -H "Content-Type: application/json" \
  -d '{
    "question": "数据中心业务连续性分为几个等级？",
    "session_id": "3f8a1c9d2e4b5a6f7c8d9e0f1a2b3c4d"
  }'
```

**响应示例**

```json
{
  "session_id": "3f8a1c9d2e4b5a6f7c8d9e0f1a2b3c4d",
  "answer": "数据中心业务连续性等级由低到高划分为五个等级……",
  "sources": [
    {
      "file_name": "GBT 42581-2023 信息技术服务 数据中心业务连续性等级评价准则.pdf",
      "page_no": 7,
      "page_nums": [7],
      "chunk_id": "b2c3d4e5f6071829_0012",
      "score": 0.7412,
      "summary": "业务连续性等级划分……（命中片段摘要）",
      "content_type": "text",
      "section_title": "5 业务连续性等级"
    }
  ],
  "pipeline": "v1",
  "latency_ms": 4213,
  "cached": false,
  "role": "student",
  "message_id": 128
}
```

**响应字段说明**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `session_id` | string | 会话 ID，后续追问请原样回传 |
| `answer` | string | 生成的答案正文 |
| `sources` | array | **来源列表（核心）**，每条含文档名称与页码 |
| `sources[].file_name` | string | 来源文档名称 |
| `sources[].page_no` | int | **主页码**（1 基），前端展示用 |
| `sources[].page_nums` | int[] | **完整页码列表**，跨页片段为多值，如 `[7, 8]` |
| `sources[].chunk_id` | string | 命中的知识块 ID |
| `sources[].score` | float | 检索相似度分数 |
| `sources[].summary` | string | 命中片段摘要，便于用户快速核对 |
| `sources[].content_type` | string | 片段类型：`text` / `table` / `image` |
| `sources[].section_title` | string | 所属章节标题 |
| `pipeline` | string | 处理该问题的链路版本（`v1` / `v2` / `v3`） |
| `latency_ms` | int | 端到端耗时（毫秒） |
| `cached` | bool | 是否命中查询缓存 |
| `role` | string | **（V1.1 新增）** 本次实际生效的回答身份（非法入参已回退为 `student`） |
| `message_id` | int \| null | **（V1.1 新增）** 本次问答在历史记录中的消息 ID；未携带 `user_id` 时为 `null`。收藏接口需要回传该值 |

**关于 `page_no` 与 `page_nums` 的双字段设计**

这是本项目页码溯源的关键实现（详见《技术决策记录》ADR-006）：

- 一个知识块可能由**多个相邻内容块合并**而成，而这些内容块可能跨越两页
- 若只记录单页码，用户翻到该页可能**找不到答案的后半部分内容**
- 因此同时保存主页码（`page_no`，前端展示）与完整页码列表（`page_nums`，保真溯源）

前端展示建议：`page_nums` 连续时显示为「第 7-8 页」，单页时显示「第 7 页」。

**无相关内容时的响应**

当知识库中确实没有相关信息时，系统**明确拒答而非编造**：

```json
{
  "session_id": "3f8a1c9d2e4b5a6f7c8d9e0f1a2b3c4d",
  "answer": "根据现有知识库，未找到相关内容。",
  "sources": [],
  "pipeline": "v1",
  "latency_ms": 850,
  "cached": false
}
```

**错误响应**

| 状态码 | 场景 |
| --- | --- |
| `400` | 问题为空 |
| `403` | 携带的 `session_id` 归属其他用户（服务端会改为新建会话，不会泄露他人内容） |
| `500` | 问答服务处理失败（详情见服务端日志） |

## 三、典型调用流程

### 3.1 首次使用：构建知识库

```
① GET  /api/kb/status          → 确认知识库为空（doc_count = 0）
② POST /api/kb/build           → 触发构建（立即返回）
③ GET  /api/kb/status          → 每 2 秒轮询，直至 running = false && stage = "done"
④ POST /api/chat/query         → 开始提问
```

### 3.2 日常问答：多轮对话

```
① POST /api/chat/session       → 取得 session_id
② POST /api/chat/query         → 提问，携带 session_id
③ POST /api/chat/query         → 追问（如「那第 4 级呢」），沿用同一 session_id
④ POST /api/chat/clear         → 话题结束，清空上下文
```

> **多轮对话示例**：
> - 第一问：「数据中心业务连续性分为几个等级？」
> - 第二问：「那第 4 级有什么要求？」← 省略了主语，依赖会话上下文理解

## 四、Postman / APIPost 调试说明

### 4.1 导入方式

本项目未提供 Postman Collection 文件，按以下步骤手工配置即可（共 8 个接口）：

1. 新建 Collection，命名为「RAG 知识库问答助手」
2. 添加环境变量 `baseUrl` = `http://127.0.0.1:8000`
3. 按本文档第二节逐个添加请求，URL 使用 `{{baseUrl}}/api/...`
4. `POST` 类接口在 **Body → raw → JSON** 中填写请求体
5. 上传接口在 **Body → form-data** 中添加 key 为 `file`、类型为 `File` 的字段

### 4.2 建议的调试顺序

| 顺序 | 接口 | 预期结果 |
| --- | --- | --- |
| 1 | `GET /api/health` | 三项依赖均为 `true` |
| 2 | `POST /api/kb/build` | `accepted: true` |
| 3 | `GET /api/kb/status` | 轮询至 `stage: "done"`，`doc_count: 3` |
| 4 | `POST /api/chat/query` | 返回答案且 `sources` 非空，含 `file_name` 与 `page_no` |
| 5 | `POST /api/chat/query`（换个问题） | 验证溯源页码随问题变化 |

### 4.3 验证要点

调用问答接口后，**务必核对 `sources` 中的页码是否与 PDF 实际内容一致**（打开源 PDF 翻到对应页比对）。这是本项目最核心的验收点。

## 五、JMeter 压力测试说明

> 按任务书要求，本项目**不编写** JMeter 脚本，以下仅说明测试方法。

### 5.1 测试目标接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/chat/query` | POST | 主要压测对象（耗时最长，涉及检索与生成） |
| `/api/health` | GET | 探活基线，用于排除网络因素 |
| `/api/kb/status` | GET | 轻量读接口 |

### 5.2 建议的线程组配置

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| 线程数（用户数） | 20 | 对应非功能需求 N4「不少于 20 并发」 |
| Ramp-Up 时间 | 20 秒 | 逐步加压，避免瞬时冲击 |
| 循环次数 | 10 | 或使用「永远」+ 调度器限定持续时间 |
| 超时设置 | 60000 ms | 生成模型耗时较长，超时不宜设置过短 |

### 5.3 请求配置

```
方法：POST
路径：/api/chat/query
Body Data（JSON）：
{
  "question": "数据中心业务连续性分为几个等级？",
  "session_id": "${__UUID()}"
}
HTTP 信息头管理器：
  Content-Type: application/json
```

> **注意**：压测时建议为每个线程使用**不同的 `session_id`**（如上使用 JMeter 函数 `__UUID()`），否则多个线程共用同一会话会导致上下文串扰。

### 5.4 观察指标

| 指标 | 位置 | 关注点 |
| --- | --- | --- |
| 平均响应时间 | 聚合报告 | 问答接口在 CPU 环境下会明显高于普通接口 |
| 90% / 95% 响应时间 | 聚合报告 | 反映长尾情况 |
| 错误率 | 聚合报告 | 应接近 0，非 0 需查服务端日志 |
| 吞吐量（TPS） | 聚合报告 | 结合 CPU 使用率判断瓶颈 |

### 5.5 压测注意事项

1. **缓存会干扰结果**：相同的 `question` 会命中 Redis 查询缓存，响应时间骤降。测真实负载时需使用**不同的问题**，或先在 `.env` 中将 `CACHE_TTL_SECONDS` 设为 0。
2. **生成模型是外部依赖**：响应时间受 DeepSeek 接口响应速度影响，压测结果不能完全代表本服务的处理能力。如需纯本地压测，可将测试目标换成 `/api/kb/status`。
3. **CPU 环境限制**：本机无 GPU，向量化与检索均为 CPU 计算，并发能力受限。20 并发是当前硬件条件下的验证目标，不是容量上限承诺。
4. **压测前确认知识库已构建完成**，否则检索为空，测不出真实链路耗时。

### 7.6 流式提问（答案边生成边返回）

**`POST /api/chat/stream`**

请求体与 `/api/chat/query` **完全一致**（`question` / `session_id` / `top_k` / `role` / `user_id`），响应为 SSE 流。

> 为什么要它：生成用的是推理模型，一次完整回答需要十几秒到一分钟；流式让答案「边生成边显示」，
> 用户不必盯着空白等。检索一完成就先把溯源推给前端，用户立刻能看到「命中了哪几页」。

**事件格式**（`Content-Type: text/event-stream`，每条 `data:` 是一个 JSON）：

| type | 载荷 | 说明 |
| --- | --- | --- |
| `meta` | `session_id` `sources` `role` `pipeline` `cached` | 检索完成，前端可立即渲染溯源与身份标签 |
| `delta` | `text` | 答案增量（一段文字），前端追加显示 |
| `done` | `session_id` `answer` `latency_ms` `cached` | 生成结束；此刻会话历史与查询缓存已写好 |
| `saved` | `message_id` | 历史记录已落库，前端收藏按钮用它 |
| `error` | `detail` | 出错（中文提示） |

**响应示例（节选）**

```
data: {"type":"meta","session_id":"abc…","sources":[{"file_name":"GBT 41479-2022 ….pdf","page_no":12,"page_nums":[12],"summary":"…","section_title":"7 数据出境"}],"role":"student","pipeline":"v3","cached":false}

data: {"type":"delta","text":"数据出境前应当"}

data: {"type":"delta","text":"进行安全评估……"}

data: {"type":"done","session_id":"abc…","answer":"数据出境前应当进行安全评估……","latency_ms":53292,"cached":false}

data: {"type":"saved","message_id":251}
```

**调用示例**

```bash
curl -N -X POST http://127.0.0.1:8000/api/chat/stream -H "Content-Type: application/json" -d "{\"question\": \"数据出境有什么要求？\", \"role\": \"student\", \"user_id\": \"<user_id>\"}"
```

**说明**

- 检索、分块、重排、溯源、缓存、历史落库的规则与 `/api/chat/query` **完全一致**（复用同一套实现），唯一区别是生成那一步改成流式。
- **原 `/api/chat/query` 一字未改**：评测脚本、JMeter 压测、外部调用方不受影响；前端在流式不可用时会自动回退到它。
- 模型内部的推理过程（`reasoning_content`）**不会出现在任何事件里**，前端只看到正式答复的增量。
- 重复提问命中缓存时，事件序列为 `meta(cached=true)` → 一个完整 `delta` → `done` → `saved`。

**流程 C：第二天打开旧会话接着问**

```bash

curl "http://127.0.0.1:8000/api/history/sessions?user_id=<user_id>"
# 2. 打开会话（自动回灌上下文，restored_turns 为回灌轮数）
curl "http://127.0.0.1:8000/api/history/sessions/<session_id>?user_id=<user_id>"
# 3. 直接追问（省略主语也能听懂）
curl -X POST http://127.0.0.1:8000/api/chat/query -H "Content-Type: application/json" -d "{\"question\": \"那第 4 级呢？\", \"session_id\": \"<session_id>\", \"user_id\": \"<user_id>\"}"
```
