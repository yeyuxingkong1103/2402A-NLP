# 基于 RAG 的心理医生多角色陪伴系统 —— 项目讲解文档

> 用途：向老师/评审讲解本项目使用。按本文档顺序讲即可，每节标注了对应源码文件，讲解时可同步打开代码。

---

## 一、项目概述（开场白，约 2 分钟）

### 一句话介绍

本项目是一个**基于 RAG（Retrieval-Augmented Generation，检索增强生成）的心理医生多角色陪伴系统**：用户可以选择三位不同流派的心理医生进行对话，系统在回答前会先从对应的心理学知识库中检索相关内容，再交给大模型组织语言，实现**可溯源、低幻觉、有人格、有记忆、有安全兜底**的心理陪伴服务。

### 与普通聊天机器人的三个核心区别

1. **多角色人格隔离**：三位医生（人本共情、CBT 认知行为、正念情绪调节）各自拥有独立的人设、知识库、生成参数，知识互不串味。
2. **检索增强生成（RAG）**：回答基于真实心理学书籍内容，命中片段会作为引用来源返回，可溯源，大幅降低幻觉。
3. **安全兜底**：内置危机检测（覆盖直接与委婉的高危表达），一旦命中，无论模型输出什么，都会强制补充心理援助热线转介提示——"宁可重复，不可漏送"。

### 三位医生角色

| 角色 | 流派 | 知识库（示例书单） | 风格差异 |
|---|---|---|---|
| 林知暖 | 人本共情倾听型 | 《少有人走的路》《动机与人格》《人的潜能和价值》《自我的发展》 | 温暖共情，temperature 较高（约 0.8），回答更开放 |
| 陈认知 | CBT 认知行为治疗型 | 《思维改变生活》（扫描版，走 OCR）《30天认知训练营》《掌控习惯》 | 理性结构化，temperature 较低（约 0.5），爱用"想法—情绪—行为"框架 |
| 周正念 | 正念情绪调节型 | 《积极心理学》《练习一个人》《幸福的最小行动》 | 引导觉察当下、呼吸与身体扫描练习 |

## 二、技术栈速报（约 1 分钟）

| 层次 | 选型 | 说明 |
|---|---|---|
| Web 框架 | FastAPI + Uvicorn | 异步非阻塞，支持 SSE 流式输出 |
| ORM / 数据库 | SQLAlchemy (async) + MySQL (端口 **3307**) | 用户、角色、会话、消息元数据 |
| 缓存 | Redis | 限流、短期记忆、会话写锁 |
| 向量数据库 | Milvus | 知识向量 + 长期记忆摘要，按角色分区 |
| 嵌入模型 | **BGE-M3**（本地，1024 维） | 文本向量化，单例懒加载 |
| 重排模型 | **BGE-Reranker-v2-M3**（本地交叉编码器） | 检索精排 |
| 大模型 | DeepSeek（在线 API） | 最终回答生成、Query 改写、记忆摘要 |
| 文档解析 | MinerU / PyMuPDF / pdfplumber / PaddleOCR | 四级降级链，扫描件走 OCR |
| 评测 | RAGAS（Recall@K、MRR 等）+ LLM-as-Judge 双引擎 | 检索与生成质量评测 |

## 三、整体架构（约 3 分钟）

### 分层结构

```
┌─────────────────────────────────────────────┐
│  api 层   src/api/v1/         路由入口，极薄：限流→鉴权→校验→转交 │
├─────────────────────────────────────────────┤
│  services 层  src/services/   业务编排：rag/retrieval/memory/  │
│                                conversation/crisis/llm/knowledge │
├─────────────────────────────────────────────┤
│  rag 层    src/rag/           纯函数组件：parser/chunker/      │
│                                embedder/retriever/prompt        │
├─────────────────────────────────────────────┤
│  db 层     src/db/            MySQL / Redis / Milvus 封装     │
└─────────────────────────────────────────────┘
        core 层（config/security/logging/exceptions）横向支撑
```

**设计原则**：api 层只做入口校验，业务全下沉 services；rag 层全是纯函数，可独立单测；请求方向 `api → services → rag → db` 严格单向依赖。

### 两条链路（讲解主线）

**离线链路**（问答之前完成，`scripts/ingest_knowledge.py` 触发）：

```
PDF 文档 → parser 解析（四级降级+OCR）→ chunker 分块 → embedder 向量化(BGE-M3)
        → Milvus 入库（按 persona_id 分区）+ MySQL 写知识元数据
```

**在线链路**（用户每次提问，`POST /api/v1/chat`）：

```
① 用户请求（限流/鉴权/校验角色）
② 准备：建会话 + 取历史 + 危机检测（不依赖检索，先发 SSE meta 事件）
③ 检索漏斗：Query 改写 → BGE-M3 向量化 → Milvus 混合召回 → Reranker 重排 → 阈值过滤
④ 生成：prompt 拼装（人设+三层记忆+知识片段）→ DeepSeek 流式生成
⑤ 落库：MySQL 存消息 + Redis 写短期记忆 + 满 20 轮沉淀长期记忆到 Milvus
   ※ 命中危机 → 回答末尾强制补转介提示
```

### 三个存储各管什么（常见误区澄清）

| 存储 | 存什么 | 不存什么 |
|---|---|---|
| MySQL | 用户/角色/会话/**每一条聊天消息**（最终事实来源） | 不存向量 |
| Redis | 短期记忆（最近 10 轮，TTL 24h）、限流计数、会话写锁 | 不做持久化事实 |
| Milvus | 知识向量库 + 长期记忆**摘要**向量 | **不存原始聊天消息**——只有会话满 20 轮触发摘要后才有一条摘要向量进来 |

> 老师若问"为什么聊天记录在 Milvus 里搜不到"：消息本来就不进 Milvus，消息在 MySQL `messages` 表；Milvus 只存知识和长期记忆摘要。

## 五、启动方式与初始化流程（约 2 分钟）

### 正确启动方式

```bash
bash scripts/run.sh            # 常规启动（后台运行，写 PID 文件）
bash scripts/run.sh --reload   # 开发模式热重载
bash scripts/shutdown.sh       # 停止服务
```

> **为什么不能 `python main.py` 直接跑**：run.sh 负责①加载 .env（MySQL 3307/Redis/Milvus/DeepSeek 配置）；②使用指定虚拟环境；③设置 PYTHONPATH；④写 PID 文件供 shutdown.sh 精确停止；⑤记录日志到 logs/；⑥前置检查 MySQL/Redis/Milvus 是否就绪。

### lifespan 启动初始化（`src/main.py`）

服务启动时依次做四件事，**任一依赖失败只降级不崩溃**（`/health` 会报 degraded）：

1. **MySQL**：自动建表 + 播种三位医生角色数据
2. **Milvus**：自动建 Collection（知识库 + 长期记忆）
3. **Redis**：探活
4. **模型预热**：预加载 BGE-M3 和 BGE-Reranker，避免首次请求超时

### 健康检查与接口文档

```bash
curl http://127.0.0.1:8000/health   # 检查各依赖状态
# 浏览器打开 http://127.0.0.1:8000/docs 查看交互式 API 文档
```

## 六、离线链路详解：知识库怎么灌进向量库（约 5 分钟）

入口：`scripts/ingest_knowledge.py` → `src/services/knowledge_service.py` 的 `ingest_file`。

四步流水线，每一步对应 rag/ 下一个纯函数组件：

### 第 1 步：parser 解析（`src/rag/parser.py`）——四级降级链

| 优先级 | 工具 | 适用场景 | 运行环境 |
|---|---|---|---|
| 1 | MinerU (tier=flash) | 文本型 PDF 高质量解析 | 独立 venv `.venv-mineru/bin/mineru` |
| 2 | PyMuPDF | 经典 PDF 文本层提取 | 主环境 |
| 3 | pdfplumber | PyMuPDF 失败后的回退 | 主环境 |
| 4 | **PaddleOCR (lang=ch)** | 扫描件兜底，逐页识别 | 独立 venv `.venv-paddle/bin/python` |

**触发 OCR 的判定条件**：
- 全文文本层总字符数 < `OCR_MIN_TEXT_LAYER_CHARS`（默认 100）；或
- 页数 ≥ 10 且有效文本页占比 < 5%（捕捉"前几页有封面、正文全是图"的扫描书）

**关键讲解点**：
- 为什么要四级？——三位医生的书里有**扫描版**（如《思维改变生活》），纯图片 PDF 普通解析器拿不到文字，必须 OCR 兜底
- 为什么 OCR 放独立 venv？——PaddleOCR/MinerU 依赖重，torch 版本与主环境冲突；子进程调用，主环境没装也能自动跳过降级，不会崩
- OCR 逐页流式处理 + 增量写盘，防止大文档内存爆掉

### 第 2 步：chunker 分块（`src/rag/chunker.py`）

- 支持 6 种分块策略，默认 **paragraph 按段落切**
- `chunk_size` 默认 512 token，`overlap` 80 token——overlap 防止一段知识被从中间切断导致语义不完整

### 第 3 步：embedder 向量化（`src/rag/embedder.py`）

- **BGE-M3**，输出 1024 维向量
- 单例懒加载：全进程共享一个模型实例，避免重复初始化占用显存

### 第 4 步：Milvus 入库（`src/db/milvus.py`）

- Collection：`persona_knowledge`
- **`persona_id` 作为分区键**——检索时 `expr='persona_id == X'` 严格过滤，三位医生知识互不串味（这是多角色隔离的物理层保证）
- 同时在 MySQL 写知识文档元数据（书名、块数、状态）

## 七、在线链路详解：用户发一句话后发生了什么（约 10 分钟，重点）

### 7.1 入口层（`src/api/v1/chat.py`）

控制器**极薄**，只做四件事：限流（Redis，30 次/分钟）→ JWT 鉴权 → 校验角色状态 → 转交 `rag_service.answer` / `answer_stream`。

### 7.2 核心编排（`src/services/rag_service.py`）

**prepare_basic（轻量上下文准备）**
- 建会话（或复用）+ 取历史消息 + **危机检测**
- 这三步不依赖检索，所以 SSE 流式里**先发 meta 事件**让前端立刻拿到 `conversation_id` 渲染骨架——降低首字延迟

**_retrieve_and_build（检索与提示词拼装）**
- `retrieval_service` 先做 **Query 改写**（LLM 把口语化问题改写成适合检索的形式），再调检索漏斗
- `memory_service` 取长期记忆（Milvus 摘要向量检索）
- `prompt.py` 把 **角色人设 + 三层记忆 + 命中的知识片段** 拼进提示词

**answer_stream（流式生成）**
- SSE（Server-Sent Events）：FastAPI StreamingResponse + 生成器，边生成边 yield token
- 事件顺序：先 `meta` 事件（conversation_id）→ 再逐段 `delta` 内容事件 → 最后 `done` 事件（含引用来源 references）

**危机后处理**
- 若本轮命中危机词，无论模型输出什么，回答末尾**强制补充**转介提示（心理援助热线 12356 等）——"宁可重复，不可漏送"

**_persist（落库）**
- MySQL `messages` 表存两条消息（用户 + 助手，助手消息带引用来源），`conversation_service.add_message` 每次 commit
- Redis 写短期记忆（最近 10 轮，TTL 24h）
- 会话消息数每满 **20 轮**触发：把之前的消息发给 LLM 生成**摘要** → BGE-M3 向量化 → 存入 Milvus `user_long_term_memory`

### 7.3 检索漏斗（`src/rag/retriever.py`，最出彩的部分）

四阶段"**先宽后窄**"：

```
① 向量化      BGE-M3 把 query 编码为 1024 维向量
② 混合召回    Milvus 稠密检索(HNSW/COSINE) + BM25 稀疏检索 双路召回 top_k≈20 条
              用 RRF（倒数排名融合）合并两路结果
③ 重排        BGE-Reranker-v2-M3 交叉编码器对 20 条逐条精排，截断到 top_n=5
④ 阈值过滤    重排分数低于 0.35 的丢弃，只留真正相关的
```

**设计理由（必背）**：
- 为什么混合检索？——纯向量检索对专有名词、医学术语弱（语义相近但字面不同会误召回），BM25 关键词路正好互补；混合路故障时**自动降级纯稠密**，不影响可用性
- 为什么先召回 20 条再重排？——便宜的向量/BM25 检索保证**不漏**（高召回），昂贵的交叉编码器精排保证**不滥**（高精度）。交叉编码器精度高于双编码器但计算贵，只在窄候选集上用
- 阈值过滤兜底：宁可少引用，不可引用无关内容

### 7.4 三层记忆体系（`src/services/memory_service.py`）

| 层 | 存储 | 容量/时效 | 作用 |
|---|---|---|---|
| 会话历史 | MySQL | 全量持久 | 完整对话记录，事实来源 |
| 短期记忆 | Redis List | 最近 10 轮，TTL 24h | 快速读取近期上下文 |
| 长期记忆 | Milvus | 每 20 轮一条摘要向量 | 跨会话"记得用户说过什么" |

**降级设计**：Redis 短期记忆丢失时，`get_short_term` 会自动从 MySQL 回填最近消息——MySQL 是最终事实来源。

### 7.5 危机检测（`src/services/crisis_service.py`）

- 词库匹配，**同时覆盖直接表达与委婉表达**，例如：直接类"自杀""结束这一切"，委婉类"了结这一切""离开这个世界"
- 两级动作：检测（prepare_basic 阶段，决定是否走安全分支）+ 后处理（生成后强制补转介话术）
- 对应有 pytest 单测（`tests/test_unit_crisis.py`），覆盖直接与委婉两类高危表达

## 九、设计亮点总结（约 3 分钟，挑 3~4 个讲）

1. **三角色严格隔离**：persona_id 是 Milvus 分区键，检索严格过滤；每个角色 temperature / max_tokens 独立调优。
2. **检索漏斗先宽后窄**：混合召回保召回、交叉编码器精排保精度、阈值过滤防滥引；混合路故障自动降级纯稠密。
3. **四级解析降级链**：MinerU → PyMuPDF → pdfplumber → PaddleOCR，扫描件也能入知识库；重依赖独立 venv 隔离。
4. **全链路降级不崩溃**：MySQL/Redis/Milvus 任一挂掉只降级（/health 报 degraded）；Redis 挂了限流放行+记忆从 MySQL 回填；Milvus 挂了检索为空但对话照常。
5. **安全兜底**：危机词库覆盖直接+委婉表达，命中后强制转介，宁可重复不可漏送，有单测保证。
6. **并发安全**：Redis SET NX 实现会话写锁，同一会话同一时刻只允许一条问答在途，防消息乱序与计数覆盖。
7. **SSE 流式**：先 meta 后内容的两段式事件流，首字延迟从数秒降到数百毫秒。

## 十、老师可能追问的问题（FAQ）

| 问题 | 推荐答法 |
|---|---|
| 为什么不用 LangChain / LlamaIndex？ | rag/ 层自己写更可控：检索漏斗、混合检索权重、阈值、Query 改写都是按本场景调优的；框架封装太厚看不清内部。且 rag/ 是纯函数，可独立单测 |
| 长期记忆怎么沉淀的？ | 会话每满 20 轮，把之前的消息发给 LLM 生成摘要，摘要用 BGE-M3 向量化后存入 Milvus long_term_memory；下次提问时与当前问题一起检索 |
| 流式怎么实现的？ | FastAPI StreamingResponse + 生成器 yield SSE 事件；先发 meta（conversation_id）再逐段发内容，最后 done 附带 references |
| OCR 为什么独立 venv？ | PaddleOCR/MinerU 依赖重，torch 版本与主环境冲突；子进程调用，未安装时自动跳过降级 |
| 评测怎么做的？ | RAGAS（Recall@K、MRR 等）；langchain-community 版本不兼容时 eval_service 双引擎回退到内置 LLM-as-Judge（DeepSeek 打分） |
| 消息在 Milvus 里怎么搜不到？ | 消息本来就不进 Milvus——聊天消息存 MySQL `messages` 表；Milvus 只存知识向量和长期记忆摘要 |
| MySQL 连不上/看不到数据？ | 端口是 **3307** 不是默认 3306；库名 `rag_roleplay`；消息表名是 `messages` |
| 并发怎么处理？ | Redis SET NX 会话写锁 + API 限流 30 次/分钟 + FastAPI 异步非阻塞 |
| 密码怎么存的？ | bcrypt 哈希；JWT 鉴权（core/security.py） |
