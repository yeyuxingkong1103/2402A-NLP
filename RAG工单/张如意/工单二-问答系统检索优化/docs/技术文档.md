## 1. 系统概述

本系统是在工单01「基于 PDF 文档的问答系统」之上的**检索准确率优化版**。
在保持问题集、语料、评估口径不变的前提下，从 PDF 解析、分块、检索、重排、
生成五个层面对检索链路做系统性优化，并配套四组可复现的对比实验。

| 维度 | 工单01 基线 | 工单02 优化后 |
|---|---|---|
| 分块 | fixed 固定窗口 | **structure** 章节结构感知 + 章节路径注入 |
| 检索 | 单路向量 | **hybrid** 向量 + BM25，RRF 融合 |
| 重排 | 无 | **cascade** TF-IDF 粗排 → LLM 精排 |
| 生成 | 朴素 Prompt | **优化 Prompt**（定位/核对/按行读表/拒答/溯源） |
| 评测 | 文档级指标 | **证据片段级**指标 + RAGAS 自实现指标 + 分阶段耗时 |

## 4. 关键模块实现

### 4.1 评分基准（`common.py::ANSWER_KEYS`）

每个问题固化五个字段，避免评测口径随实现漂移：

| 字段 | 用途 |
|---|---|
| `required` | 必备要点，**全部命中**才算答对（准确率判定的唯一依据） |
| `detail` | 加分要点，用于覆盖率统计，不影响对错 |
| `evidence` | 检索层证据关键词，用于证据命中率 / Recall@k |
| `primary` / `pages` | 首要证据词（MRR）与证据真实页码（页码命中率、溯源核对） |
| `ground_truth` | 参考答案，供 RAGAS 口径的 context_recall / answer_correctness 使用 |

要点与页码均逐字核对《招股说明书1.pdf》原文，例如 id 543 对应第 52 页
「注册资本：5,520 万元」、id 531 对应同页「法定代表人：程家明」。

### 4.2 索引构建与缓存（`common.py::build_index`）

- 每个分块策略一个**独立 collection**（`wo02_fixed` / `wo02_recursive` /
  `wo02_semantic` / `wo02_structure`），向量库与 BM25 索引成对生成，互不干扰；
- 索引清单 `data/index/{collection}.wo02.json` 记录
  `(策略, size, overlap, n_chunks, PDF mtime, 构建耗时, 块长分布)`；
  下次运行若清单与请求一致且向量库条数吻合，直接复用（秒级启动），
  参数变更 / PDF 更新 / 索引被删都会自动重建；
- BM25 索引按 collection 单独落盘（`{collection}_bm25.pkl`），
  由 `Retriever(collection, bm25_path=...)` 装载，避免多实验互相覆盖。

### 4.3 检索器装配的一个坑（`common.py::get_retriever`）

`rag_core.retriever.Retriever.get_reranker()` 只会为**级联重排器**自动拟合 IDF，
直接使用 `TFIDFReranker` 时其 IDF 恒为常数，数字/实体加权形同虚设。
因此本工单在装配时显式执行 `rr.fit(bm25.docs)`，保证 TF-IDF 打分真实有效。

### 4.4 为什么自建「证据片段级」指标

`rag_core.evaluate.retrieval_metrics` 的判断依据是「检索结果里有没有出现参考文档名」。
本工单语料只有一份《招股说明书1.pdf》，该口径恒为 100%、无区分度。
因此 `common.py::retrieval_evidence_metrics` 下沉到片段级：

- **证据命中率**：Top-k 中出现任一 `evidence` 关键词；
- **证据 MRR**：首个命中证据的排名倒数；
- **证据 Recall@k**：Top-k 覆盖的 `evidence` 词比例；
- **页码命中率**：Top-k 命中证据所在页码（±1 页容差）。

全部为纯计算指标，不依赖 LLM，可离线复跑。

### 4.5 生成 Prompt（`common.py::PROMPT_OPT_SYS`）

优化版 System Prompt 的七条规则：只依据资料作答 → 先定位后作答 →
数值逐字核对与分期列出 → 表格按行读 → 不足则拒答 → 简洁输出 →
标注来源。另备英文版 Prompt，由 `build_messages()` 按提问语言自动切换。

## 5. 数据流：一次问答的完整时序

```
用户问题
  │
  ├─(1) 检索  Retriever.retrieve(strategy, recall_k, reranker, fusion)
  │       ├─ 向量通道：VectorStore.search → BGE 编码 → 余弦相似度 Top-20
  │       ├─ 词法通道：BM25Retriever.search（仅 hybrid）
  │       ├─ 融合：RRF  score = Σ 1/(60 + rank)
  │       └─ 重排：CascadeReranker
  │              ├─ 一级 TF-IDF（数字 ×2.0 / 实体 ×1.8）→ Top-10
  │              └─ 二级 LLM 列表级打分 → Top-5
  │
  ├─(2) 组装上下文  Retriever.format_context(docs)
  │       带「[片段i] 来源：《文档》第X页 章节：…」标注，供模型引用
  │
  ├─(3) 生成  llm.chat(优化 Prompt + 上下文)
  │       温度 0、限制输出长度、磁盘缓存命中则零延迟
  │
  └─(4) 返回  答案 + citations + 分阶段耗时（timings）
```

`answer_question()` 在 (1) 与 (3) 分别计时，输出
`retrieval_seconds / timings.rerank / generate_seconds / total_seconds`，
为《优化方案.md》3.6 的 3 秒预算分解提供数据。

## 6. 性能设计（3 秒响应约束）

| 阶段 | 预算 | 手段 | 实测来源 |
|---|---|---|---|
| 检索 | < 0.3 s | 向量库持久化 + 批量编码；BM25 自实现倒排，无外部服务 | `results/retrieval_comparison.json` 的 `retrieval_seconds` |
| 重排 | < 1.0 s | 级联：TF-IDF 零成本粗排把候选压到 10 条，LLM 只处理这 10 条 | 同上 `rerank_seconds` |
| 生成 | 剩余预算 | ① `llm.chat` 磁盘缓存（相同问题/上下文直接命中）；② Prompt 约束「简洁、先结论」控制输出长度；③ Web 端可换流式返回降低首字延迟 | 同上 `generate_seconds` |
| 冷启动 | 一次性 | 解析 JSON 缓存 + 索引清单缓存，二次启动跳过分块与编码 | 索引清单 `build_seconds` |

> 说明：准确率与延迟是一对矛盾。工单同时要求「准确率 ≥90%」与「≤3 秒」，
> 因此本方案在检索链路用「级联重排」换精度、用「缓存 + 输出约束」换生成时间，
> 而不是无脑堆叠大模型调用。

## 7. 稳定性与容错实现

| 场景 | 机制 | 代码位置 |
|---|---|---|
| 解析失败 / 缓存损坏 | 清缓存重试一次，仍失败抛出带路径的可读错误 | `common.parse_document` |
| 索引参数变更 / 缺失 | 清单比对，自动重建；清单损坏时忽略并重建 | `common.build_index` |
| BM25 装载失败 | 捕获异常，降级为纯向量检索 | `common.get_retriever` |
| 检索异常 | 单题捕获，空上下文 + 拒答，评测继续 | `common.answer_question` |
| 生成异常（网络/未配 Key） | 返回兜底话术并记录，不中断批量实验；脚本启动前显式校验 Key | `common.generate_answer` / `require_llm_key` |
| 服务异常 | 全局异常转结构化 HTTP 错误；健康检查与指标接口 | `serve.py` |
| 端口占用 | 捕获 OSError，提示换端口 | `serve.py::main` |

## 8. 多语言支持

- 提问语言自动判定（中文字符占比 < 15% 视为英文，口径与
  `rag_core.generator` 一致）；
- 英文提问使用英文 System Prompt（同样的七条规则），要求答案用英文返回；
- 中英混排术语（如 C4ISR、BGE）不做翻译，保持原文以便核对；
- 验证方式：`src/serve.py` 界面直接输入英文问题，或用
  `common.build_messages(question, ctx, "optimized")` 检查 System Prompt 切换。

## 9. Web 服务与接口

```bash
python src/serve.py                # 默认 0.0.0.0:8000
python src/serve.py --port 8080 --no-build
```

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 对比问答界面（内置 HTML，零前端构建） |
| GET | `/api/health` | 健康检查：两套索引的向量条数、运行时长 |
| GET | `/api/metrics` | 请求数 / 错误数 / P50、P95、最大延迟 |
| GET | `/api/questions` | 工单预置 10 问（界面上一键提问） |
| POST | `/api/ask` | `{question, mode, top_k}`，mode ∈ {optimized, baseline} |
| POST | `/api/compare` | `{question, top_k}`，并排返回优化前 / 优化后答案 |

`/api/ask` 响应示例（节选）：

```json
{
  "mode": "optimized",
  "mode_label": "优化后（工单02）",
  "answer": "报告期内，公司来自军用领域的收入分别为6,464.51万元、14,414.16万元、18,780.67万元和4,627.14万元。\n【来源】片段1（第129页）",
  "retrieval_seconds": 0.18, "rerank_seconds": 0.72, "generate_seconds": 2.05,
  "total_seconds": 2.95,
  "pages": [129, 128, 130, 52, 95],
  "check": {"正确": true, "命中": ["6464.51", "14414.16", "18780.67", "4627.14"], "漏答": []}
}
```

`check` 字段由 `common.check_answer()` 做纯关键词核对（不调 LLM），
演示时可直接展示「优化前漏答 / 优化后全中」的对比。

## 10. 运行与常见问题

| 现象 | 原因与处理 |
|---|---|
| `未检测到环境变量 DEEPSEEK_API_KEY` | 未配置模型 Key；按提示设置后重跑（分块实验不需要 Key） |
| `未找到源 PDF` | 附件未就位；确认 `D:\工单\RAG 工单\RAG 工单\附件\招股说明书1.pdf` 存在 |
| 首次运行很慢 | 正常：需解析 548 页 PDF 并编码全部块；后续运行命中缓存 |
| semantic 策略特别慢 | 该策略需逐句编码，属预期现象（报告中已作为取舍依据） |
| 准确率 < 90% | 检查是否使用 `--no-generate` 降级、索引是否为最新参数、Key 是否有效 |
| 端口被占用 | `--port` 换端口 |
