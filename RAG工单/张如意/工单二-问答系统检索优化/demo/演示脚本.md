- **讲解词**（对照主表逐列念实测值）：

  > fixed 的块长最规整，但命中率最低 —— 因为它会把这句

### 镜头 5　实验二：检索与重排配置对比（4:20 - 5:40）

- **画面**：终端 + `results/retrieval_comparison.md`，鼠标停在耗时列。
- **操作**：
  ```bash
  python 工单02-问答系统检索优化/src/optimize_retrieval.py
  ```
- **讲解词**：
  > 「四组配置：纯向量、加 TF-IDF 重排、加 LLM 重排、加级联重排。
  > 纯向量依靠语义相似度，遇到数字和公司全称就容易排不准；
  > TF-IDF 重排对数字和实体做了加权，零成本就能把含目标数字的块顶上来；
  > LLM 重排最准，但要把 20 条候选全塞进提示词，重排耗时明显上升；
  > 级联重排先用 TF-IDF 压到 10 条再让 LLM 精排，
  > 精度接近 LLM 重排，耗时接近 TF-IDF —— 这就是 3 秒约束下的答案。」

## 三、口播数字使用规范

- 所有具体数值（准确率、耗时、命中率）**必须以屏幕上实际输出的报告为准**，
  不可照抄本脚本或文档中的示例；
- 若优化后准确率低于 90%，不要回避：现场打开 `docs/验收对照表.md`，
  按「准确率 < 90% 的排查清单」逐项检查（Key、索引参数、降级开关），
  排查过程本身就是很好的工程能力展示；
- 耗时口播保留两位小数，并说明统计口径（均值 / P95，系统侧 / 端到端）。

## 四、录制应急方案

| 突发情况 | 处理 |
|---|---|
| 模型接口超时 | 报告有 `--skip-ragas` 与缓存机制；重跑一次通常秒级命中缓存 |
| 首次跑索引太慢 | 提前预热（见 1.1 第 ④ 步），录制时命中索引缓存 |
| 中文乱码入镜 | 先执行 `chcp 65001` 与 `set PYTHONIOENCODING=utf-8` |
| 端口被占用 | `python src/serve.py --port 8081` |
| 现场网络不可用 | 演示分块实验（无需 LLM）＋ 已生成的 `results/*.md` 报告 |
