## 三、关键设计决策

下面每一条都是**实测数据推翻了原本写法**才定的，具体数据见 `测试/验证报告.md` 第四节。

### 3.1 为什么把「解析」和「判定」分开（本设计的核心）

**问题**：1700 份文档解析一遍要 51.6 秒。而任务四是「验证与**调优**」——
调阈值是家常便饭（扫描页占比调一下、SimHash 距离调一下、长度区间调一下）。
如果每次都从头解析，每调一次参数等一分钟，调优根本没法做。

**做法**：缓存里存的是**事实**，不是**结论**。

```
解析阶段（慢，落盘）        判定阶段（快，每次现算）
  ├ 字符数                    ├ 是扫描型还是文字型   ← pdf_type 阈值
  ├ 每页字符数                ├ 打什么标签           ← tags.rules
  ├ 每页图片覆盖率            ├ 算不算重复           ← simhash_distance
  ├ SimHash 指纹              ├ 长度落在哪个区间     ← length.bins
  └ 敏感信息命中              └ 哪条命中要过滤       ← 正则上下文判据
```

**效果**：改判定类阈值后重出报告 **2.4 秒**（实测），不用重解析。

**边界**：抽取类配置（敏感信息正则、SimHash 取样长度、shingle 长度）
在解析阶段就固化了，改了要 `--refresh`。这条边界写在 `SKILL.md`、配置注释和
`Checkpoint.reset()` 的 docstring 里，三处都提，因为它容易被踩。

### 3.2 为什么 PDF 分流要「字符数 **且** 图片铺满」两个条件

工单原文只说「每页字符数低于阈值就算扫描页」。**照做会错 298 份**（实测）。

原因是**专利的附图页**：整页只有「图1」「图2」几个字，字符数当然低，
但它是数字排版的原生页，不需要 OCR。

加上第二个物理判据就分开了：

| | 图片覆盖率 | 说明 |
|---|---|---|
| 扫描页 | ≈ **1.00** | 整张位图铺满页面 |
| 附图页 | **0.32 ~ 0.44** | 图只占版面中间一块 |

两个条件缺一不可：**只看字符数**会把附图页算进来（298 份误判）；
**只看图片覆盖率**会把「带整页底图的文字页」算出去。

修完扫描型数量一份没少（622），误判的 298 份全部归位。

> 实现上还踩了一个坑：取图片面积先用的 `get_text("dict")` 的图片块，
> 有 4 份真扫描件取到的 blocks 是**空的**（面积算成 0.00），被判成文字型 ——
> 送去抽文字只会得到空白。换 `get_image_info()` 才正常。
> **这个是渲染成 PNG 肉眼看才发现的**，光看统计数字发现不了。

### 3.3 为什么 SimHash 用 3 字滑窗而不是按单字

初版按单字切中文，理由写在注释里：「不引分词器，按字切对这个用途足够了」。
**实测被数据打脸**：阈值 5 捞出的 19 对里，标题对得上的只有三分之一，准确率 38%。

根因是**单字熵太低**：「的、一、是、在」这类字每份中文文档里都是常客，
两份毫不相干的专利也能有 92% 的位相同。

改 3 字滑窗后，比的是「短语」而不是「用字偏好」，准确率提到 **94%**。
距离分布也从「平滑衰减、无空档」变成「有明确空档」（阈值 10→11 处准确率断崖
从 96% 掉到 76%）。

**依然不引分词器** —— 滑窗就够，少一个依赖少一份风险（这个判断本身没错，
错的是「按单字」这个粒度）。

### 3.4 为什么敏感信息要排除「紧邻逗号/小数点」的数字

实测平安年报两条手机号误报：

```
本年提取数18921754811,6892,734      ← 其实是 1,892,175,481.1 被截出 11 位
应收账款21,19362019822,011          ← 同类
```

`(?<!\d)` 数字边界挡不住**逗号千分位**——前面是「数」不是数字，后面是逗号也不是数字。

加一条判据：命中的数字串前后紧邻 `,`/`.`/`%` 就判为「长数字的一截」。

**代价**（写进配置注释了）：「手机号后紧跟半角逗号」会漏。权衡值得 ——
知识库语料里连续 11 位数字绝大多数是财务数字，而中文文档里手机号后面
通常跟全角逗号或空格，不受影响。

### 3.5 为什么主路由取「第一条标签」

一份文档可能命中多条标签（如「扫描型 + 超长」），于是有**两个 route**。
工作流看到「ocr、review」不知道该送哪个解析器。

所以规则**按「最确定 → 最兜底」排序**，第一条命中的标签的 route 就是**主路由**：

```jsonc
"docs": [["<路径>", "Scan_PDF、Long_Document", "ocr"]]
//                                          ↑ 主路由，一份文档只有一个
```

其余标签当参数用（`Long_Document` 提示切块要更碎）。

同时区分两个汇总口径，**混了工作流会算错**：
- `by_route`：所有标签的路由（一份文档可能算几次）→ **统计用**
- `by_primary_route`：每份文档只算第一条 → **路由用**

有单元测试守着：`test_主路由汇总每份只算一次`。

### 3.6 断点续跑

工单备注 3 明确要求「处理 1700 份可能耗时较长，请考虑进度反馈和**支持中断恢复**」。

- 缓存键 = **路径 + 大小 + 修改时间**，文件改过自动重解析（键变了）
- 追加写 `parsed.jsonl`，每 `checkpoint_every`（默认 100）份刷一次盘
- `assess()` 用 `try/finally` 包住解析循环，**Ctrl+C 也会先落盘**再退出

实测：中断后重跑，缓存命中数正确，不重复解析已完成的文件。

### 3.7 错误处理的原则：坏文件不能掀翻整轮

知识库里损坏文件是常态。所以 `parse_one()` 把**任何异常都吞掉**记进 `error` 字段，
继续处理下一个。失败的文档进 `errors` 列表，且**不计入统计口径**
（`chars=None` 而不是 0，两者含义不同）。

验收标准点名要「良好的错误处理机制（如处理损坏的 PDF 文件）」，
单元测试 `test_损坏的PDF不掀翻整轮` 覆盖。

## 四、集成方案

### 4.1 API 端点：URL 是「算出来」的，不是配出来的

工单要求 `POST /v1/document/quality-inspection`。这个前缀不用自己写 ——
RAGFlow 的 `api/apps/__init__.py:243-263` 会自动扫描 `*_app.py`：

```python
page_name = page_path.stem.removesuffix("_app")      # document_app.py -> "document"
url_prefix = f"/{API_VERSION}/{page_name}"           # -> /v1/document
app.register_blueprint(page.manager, url_prefix=url_prefix)
```

所以**只要往 `api/apps/document_app.py` 追加 route 就能得到这个 URL**，
不用改 `__init__.py`、不用注册、不动 DB。

**改动面**：1 个文件追加 2 个 route（约 110 行），不改 RAGFlow 原有任何逻辑。

**为什么用 `subprocess + asyncio.to_thread`**：`assess.py` 是同步阻塞脚本，
1700 份要跑几十秒到几分钟，直接在事件循环里跑会把整个 RAGFlow 卡死。
参考同文件 `run()` 的既有写法。

**为什么 JSON 和 HTML 分两个端点**：一个 HTTP 响应不能既是 JSON 又是 HTML。
JSON 给程序（工作流读路由），HTML 给人（扫一眼待办列表）——
正好对应工单要的「以清晰、可读的格式（JSON 及 HTML 简报）返回」。

### 4.2 工作流：用 agent_canvas，不用 dataflow

| | agent_canvas | dataflow_canvas |
|---|---|---|
| 条件分支 | ✅ 有 `Switch` 组件 | ❌ `rag/flow/pipeline.py:143-164` 只按下游线性推进 |
| webhook 触发 | ✅ | ❌ 明确拒绝（`api/apps/sdk/agents.py:156-157`） |

工单要「**根据分类标签路由到不同的解析器**」，所以必须用 `agent_canvas`。

**工作流结构**：

```
Begin(mode=Webhook)                     ← 接收 {route, path, tags}
    │
Switch:RouteByQuality                   ← 按 begin@route 分流
    ├── "ocr"    → Message:ToOCR        → 送 OCR 解析器
    ├── "text"   → Message:ToText       → 直接抽文字
    ├── "hybrid" → Message:ToHybrid     → 逐页判断
    └── ELSE     → Message:ToReview     → 人工复核（Switch 强制要求 ELSE 分支）
```

**创建方式纯 API，零代码改动**：`POST /v1/canvas/set`，`canvas_category: agent_canvas`。

DSL **已用 RAGFlow 自己的加载器验证**：`agent.canvas.Canvas` 能加载，
`Begin`/`Switch`/`Message` 三个 `component_name` 全部解析成功。

**分支端点为什么是 `Message`**：RAGFlow 的 `Parser` 组件只在 dataflow 里存在，
agent_canvas 里没有解析类组件，所以分支处只能做「路由决策」这件事本身。
要接真实解析器有两个选择（都不需要改 RAGFlow 源码）：

1. 把分支换成 `Invoke` 组件，调另一个 dataflow 画布（OCR 画布 / 文字画布）
2. 让调用方拿到路由结果后，自己去调对应的 dataflow

### 4.3 为什么不用 `CodeExec` 组件跑质检

RAGFlow 有个 `CodeExec` 组件，直觉上「跑个 Python 脚本」正合适。**实际不行**：

1. 它把代码发到**独立的沙箱容器**执行（`agent/tools/code_exec.py:145-191`），
   而本环境**没部署**沙箱（`docker ps` 只有 ragflow/mysql/es/redis 四个容器）
2. 就算部署了，沙箱规格是 **256MB 内存 + 默认 10 秒超时**，
   跟「解析 1700 份 PDF」根本不匹配
3. 沙箱**无持久化**，断点缓存 `parsed.jsonl` 会随沙箱销毁 —— 而断点续跑是
   工单明确要求的能力

所以走「宿主脚本 + 端点 subprocess 调用」，简单可控。

## 六、验证方法的设计

### 6.1 为什么用两个数据集

IMDR 是工单指定的验证集，但它是**单一文档类型**（全是专利）。
只用它会得到一个假象：以为阈值调到 7 就放之四海皆准。

`附件/`（年报 + 招股书）是另一种模板，**在这里默认阈值会产生误报**。
两边的差异本身就是要报告的结论：**阈值取决于语料的模板化程度**，
配置里写明了这一点并给了重扫命令。

### 6.2 为什么标签核对要用「另一个」指标

标签是按「每页可提取字符数」判的。核对时如果还去数字符数，是拿同一个指标
自己证明自己，测出来必然 100%。

所以换成**物理上独立**的信号 —— **图片面积占页面比例**：
字符数是从**文字层**读的，图片覆盖率是从**页面资源**读的，两条路互不相干。
实测区分度极干净（扫描型中位 1.00 / 文字型中位 0.10）。

**再加肉眼抽查**：把 4 份样本渲染成 PNG 逐张看（截图存 `测试/截图/`）。
`CN100408987C.pdf` 那张特别有说服力 —— 它渲染出来**比电子版还干净**，
但一个字符都抽不出来（4376×6665 的高清扫描位图），
正说明「扫描型」的含义是「**没有文字层、必须 OCR**」而不是「画质差」。
