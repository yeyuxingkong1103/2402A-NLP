# 工单02 —— 基于 PDF 文档的问答系统的优化

**工单编号**: `人工智能NLP-RAG-基于PDF文档的问答系统的优化`

## 一、优化了什么

工单01 建的是一个**最朴素的 RAG**:纯文本抽取 + 固定切块 + 纯向量检索 top-k。
它的短板在《招股说明书1》上暴露得很明显 —— 大量关键数据在**表格**里,文字层里
是一堆散落的单元格文本,向量检索根本捞不回来。

本工单在四个层面做优化:

| 环节 | 优化前(工单01) | 优化后(本工单) |
|---|---|---|
| **解析** | pypdf 只抽文字层 | 加 **pdfplumber 表格解析** + `table_to_text()` 线性化 |
| **分块** | 固定 500/50 | 表格块独立切分,并加**文档上下文前缀** |
| **检索** | 纯向量 top-k | **混合检索**(向量 0.5 + BM25 0.5),候选 20 条 |
| **重排** | 无 | **交叉编码器重排**(bge-reranker-base)取 top5 |

## 二、为什么要做混合检索 + 重排

- **纯向量检索的毛病**:把"营业收入 3,393.40 万元"和"营业收入大幅增长"
  编码成很近的向量 —— 语义像,但**数字全错了**。
- **BM25 的补位**:对数字、专有名词、编号这类**字面量**极其敏感,
  向量捞不到的精确匹配它能捞到。两者融合取长补短。
- **为什么还要重排**:混合检索的候选有 20 条,但排序是粗排(向量和 BM25 分数不同量纲,
  加权后排序不可靠)。交叉编码器把 query 和每个候选**拼在一起**过一遍模型,
  精度远高于双塔,代价是慢 —— 所以只用在 top20 → top5 这一步。

## 三、文件说明

| 文件 | 作用 |
|---|---|
| `build_index_opt.py` | 建优化后的索引:文本 + 表格 → `index/doc1_tables` / `index/doc1_opt` |

| `rag_common.py` | 共享内核(表格解析、混合检索、重排都在这) |

| `output/优化结果.json` | 逐题明细 |

## 四、索引说明

| 索引 | 内容 | 块数 |
|---|---|---|
| `index/doc1_tables` | 表格块(pdfplumber 抽取并线性化) | 575 |

对照基线是工单01 的 `工单(1)/index/doc1_text`(1299 块,纯文本)。

## 五、怎么运行

```bash
# 1. 建优化索引
python build_index_opt.py

# 2. 跑对比(需要工单01 先跑出 output/qa_results.json)
python optimize_eval.py
```

## 六、结论

- **表格解析是《招股说明书1》上提升最大的一环** —— 数据类问题从"答不出"到"答对";
- 混合检索 + 重排在**数值题和专有名词题**上提升明显,在纯语义题上提升有限;
- 代价:重排让单次查询延迟增加约 0.3~1s(20 条候选过交叉编码器),换来的是答案准确率的提升。
