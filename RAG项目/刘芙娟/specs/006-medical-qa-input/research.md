# Phase 0 Research: 医知源 · 提问输入链路与前端骨架

**Feature**: `006-medical-qa-input` | **Date**: 2026-09-27 | **Spec**: [spec.md](./spec.md)

本阶段要消解的是规格里"要流式"之外**没定下来的东西**：线上格式、宿主方式、契约字段的落点、以及一个规格起草时没暴露出来的陷阱。

---

## R1. 流式输出的线上格式 → **SSE（`text/event-stream`）+ 命名事件**

**Decision**：采用 SSE，用 `event:` 字段区分三类消息（引用批次 / 正文增量 / 终帧），而不是把类型塞进 JSON 内部。

**Rationale**：

1. 本特性的输出**天然是两段异质的**——引用片段是一次给全的结构化数组，正文是连续的文字流。SSE 的命名事件让这两者在**协议层**就分开，前端不需要"先读一个 type 字段再分派"。
2. 终帧可以承载 `docs/05` §3.1.3 的**完整响应体原样**，使 SC-009（后续模块接入不改前端字段解析）成立——前端解析的是同一套字段名。
3. `curl -N` 可直接观察，排查"到底哪一块没发出来"不需要任何工具。对一个以可审计为核心价值的系统，这不是小便利。

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| NDJSON（`application/x-ndjson`） | 可行，解析更简单。但类型信息必须进 JSON 内部（`{"type":"token",...}`），且浏览器无原生语义、调试可读性略输。**它不是错的选择，只是把"协议层已有表达力"降级成了应用层约定。** |
| 分块裸文本流 | 与 FR-027（引用区与正文区同一次提问内协同）脱节最大：引用只能另开一次请求或用响应头编码，等于把一次问答拆成两次。 |

**被否决的一个细节**：不引入 `sse-starlette`。

`starlette` 的 `StreamingResponse` 已足够（本项目实测 `starlette 1.6.0`）。`sse-starlette` 带来的额外能力（心跳、自动重连管理）在 V1 用不上——请求生命周期只有几秒，且不做自动重连。按 constitution 原则 I（依赖治理），**不装一个用不上的包**。同类裁决在 `specs/003` 的 D2 已有先例（改用环境里已有的 `transformers`，少一层版本耦合）。

## R2. SSE 的请求方法 → **POST + `fetch` + `ReadableStream` 手写解析**

**Decision**：`POST /ask` 返回 SSE 流；前端用 `fetch` 拿 `response.body`，经 `TextDecoder` 按 `\n\n` 切块解析。**不使用 `EventSource`。**

**Rationale**：`EventSource` 只支持 GET，而问题必须放在请求体里——塞进 query string 会同时带来三宗罪：问题原文进服务器访问日志（隐私面扩大）、长度受 URL 上限约束（与 200 字符上限一起变成双重限制）、需要 URL 编码（中文转义后可读性归零）。

手写解析的代码量实测约 25 行，且**这是唯一需要手写的一处**——事件名与 data 的解析规则简单到不需要依赖。

**Alternatives considered**：`EventSource` + GET（隐私与长度双重代价）；引入第三方 SSE 客户端库（为一个 25 行的循环引入依赖，不划算）。

---

## R3. 宿主方式 → **`StaticFiles` 挂根路径，但 API 路由必须先注册**

**Decision**：`frontend/` 作为静态目录以 `html=True` 挂载到 `/`；`POST /ask` 在挂载**之前**注册。

**Rationale**：这是 Starlette 的路由匹配顺序问题——**路由按注册顺序匹配，先注册者优先**。若先挂 `/` 的静态目录，`/ask` 会被静态处理器接走并返回 404（找不到名为 `ask` 的文件），而且这种现象**不会在启动时报错**，只在请求时表现为"接口莫名其妙 404"。

因此装配顺序被写死为：**中间件 → 异常处理器 → API 路由 → 静态挂载**，并在 `backend/api/app.py` 的注释里点明理由。这是 R3 存在的唯一目的。

**Alternatives considered**：API 加 `/api` 前缀再挂根静态目录（能规避顺序问题，但 `docs/05` §2.1 明确"V1 不引入版本前缀"的精神是拒绝仪式性成本，此处同理）；用 nginx 分离（V1 单机无此必要）。

---

## R4. 前端静态资源目录 → **`frontend/`**

**Decision**：静态资源放 `frontend/`，与 `backend/` 平级。

**Rationale**：`docs/02` §379 的既有目录树已预留 `frontend/`。虽然它原本标注的是 Streamlit 应用，但**位置本身是中性的**，沿用它可以避免"目录语义漂移"——改动的是实现方式，不是目录职责。

**已向用户明示**：规格 Assumptions 中写明"若希望并入 `backend/` 请指出"，用户回复"继续"，视为接受。

## R5. 本期 `answer_text` 的落点 —— **规格未暴露的陷阱**

**Decision**：本期**不发出**刚定稿的拒答兜底话术；改发一段明确的"能力未就绪"文案，并以流级事件区分。定稿的兜底话术写入常量并回填 `docs/01` §F6，**待检索能力接入后才首次发出**。

**这是一个必须在 plan 里讲清楚的设计裁决**，因为它的理由不在规格文本里：

`docs/05` §3.1.4 的判定规则 3 原文是：

> 只有"本该能答、但基础设施坏了"才返回 503。**把 LLM 故障伪装成拒答是误导**：用户会以为"这个知识库里没有相关内容"，而实际上是系统坏了。

本期正是这个陷阱的镜像：**检索与生成模块根本不存在**。若直接返回"这个问题在现有知识库中找不到可以依据的原文"，我们就在做 §3.1.4 明令禁止的事——**让用户以为知识库覆盖不足，而真相是能力尚未建成**。二者对用户的含义完全不同：前者意味着"换个问法也许有"，后者意味着"现在问什么都一样"。

**因此**：

| 状态 | 触发条件 | 本期是否出现 | `answer_text` |
|---|---|---|---|
| **能力未就绪** | 检索/生成模块未接入 | ✅ 本期唯一路径 | 未就绪文案 + 免责声明 |
| **拒答** | 检索为空 / 低于阈值 | ❌ 本期不可能出现 | 定稿兜底话术 + 免责声明 |

**代价**：本期无法建立完整的拒答断言（constitution「Development Workflow」要求的那类用例）。这是**有意接受**的——因为本期没有"检索过且为空"这个事实，硬造一个只会得到假绿。

**同时对 D2（按 `docs/05` §3.1.3 字段契约返回）的落实**：终帧的字段名与结构原样对齐，只是其中 `answer_text` 装的是未就绪文案、`citations` 是空数组、`risk_level` 为 `none`。字段契约不变，SC-009 成立。

**已确认（2026-09-27）**：用户采纳本裁决（方案 A）。本期发未就绪文案，拒答兜底话术仅写入常量并回填 `docs/01` §F6，待检索模块接入后首次发出。

## R6. 本期需要哪些必需配置

**Decision**：本期启动期**必需项为空**（仅可选：主机、端口）。`AGICTO_API_KEY` 等 LLM 相关变量在本期标记为**可选**，缺失不阻止启动；待生成模块接入时改标必需。

**Rationale**：constitution 原则 III 要求"缺少必需密钥时 MUST 报错并以非 0 状态退出"，其目的是**让配置缺失在启动时暴露，而不是在线上以降级模式悄悄答错**。本期不存在任何会调用 LLM 的代码路径（FR-025 且无生成模块），因此这些密钥在本期**不是必需的**——把它们标成必需会让服务在一个健康的、完全可用的状态下拒绝启动。

**风险与对冲**：这个判断有生命周期——**生成模块一接入，它立刻失效**。因此：

1. `backend/api/config.py` 的字段定义中，对每个可选密钥 MUST 带注释说明"何时转为必需"；
2. 该模块 MUST 提供 `missing_required()` 以供 `/health`（`docs/05` §3.3）复用，接入时只需改字段的必选性，不改调用方。

**Alternatives considered**：本期就要求 LLM 密钥（让服务无法启动，与"本期是提问通道"的定位矛盾）；完全不建配置模块（后续接入时要补，且 FR-022 已要求启动期一次性加载）。

## R7. 验证方式 → **沿用本项目既有约定，不引入 pytest**

**Decision**：以**逐项对拍 + 边界构造**做验证，脚本产物落 `.smoke_out/`。不引入 pytest。

**Rationale**：这不是本特性自己的选择，是**仓库既有约束**——`specs/005-milvus-ingest/plan.md` 第 145 行原文记录了 `docs/superpowers/plans` 的 Global Constraints **禁止引入 pytest**；`rag/python.exe` 中实测 `pytest` 未安装，而 S3 清洗 23/23、S5 向量化 17/17 的既有验收全部以 `.smoke_out/` 下的脚本完成。

**本特性可复用的现成能力**：`httpx 0.28.1` 已安装，因此验收脚本可以用 `httpx` 起真实请求打真实端口（而非 `TestClient` 进程内调用）——**这恰好是本特性需要的**，因为 SSE 的分块行为必须在真实 socket 上才观察得到。

**Alternatives considered**：装 pytest（违反既有 Global Constraints）；`TestClient`（进程内，无法验证分块边界与 `Transfer-Encoding: chunked` 行为）。

## R8. 紧急话术首块（FR-030）在本期如何可验证

**Decision**：流的事件生成器在结构上**预留"前置块"位置**，并通过故障注入环境变量 `MEDRAG_TEST_PREAMBLE` 在验收时注入一段前置文本，断言它作为**第一个 `token` 事件**到达。

**Rationale**：本期不存在紧急判定模块，`emergency.triggered` 恒为 `false`，FR-030 因此**没有任何可观测行为**。但规格已明确它必须在本期写对（流式顺序后续补不回来）。若不建立断言，这条需求在本期就是一句无人验证的注释。

采用**故障注入**而非 Mock：与 `specs/005` 既有的 `MEDRAG_TEST_FAULT` 环境变量模式一致（该常量定义在 `backend/index/__init__.py`），不引入新范式，且注入开关仅在验收脚本中设置，正常路径不受影响。

**Alternatives considered**：本期不做（违反规格要求）；直接把紧急判定模块也实现了（超出规格范围，用户明确说后续再做）。

## R9. 服务器绑定与运行方式

**Decision**：`uvicorn` 绑定 `127.0.0.1:8000`，入口 `backend/serve.py`，MUST 以 `rag/python.exe` 运行。

**Rationale**：端口来自用户明确要求（`http://127.0.0.1:8000/`）；仅绑回环地址与 `docs/05` §2.2"服务不暴露到公网、鉴权由部署层承担"一致——**绑 `0.0.0.0` 会让一个无鉴权的服务直接暴露在局域网上**，在医疗场景下不可接受。

不引入 `--reload`：热重载会在每次改文件时重启进程并中断正在进行的 SSE 流，调试期看似方便，实际会掩盖流式行为的真实表现。

---

## R10. 首帧携带 `answer_id` 的必要性

**Decision**：流的**第一个事件**是 `status`，携带 `answer_id`。

**Rationale**：SC-004 要求"100% 的被接收提问都能在服务端日志中通过 `answer_id` 定位"。若 `answer_id` 只在终帧出现，那么**流中断（用户关页面、服务崩溃）的那次提问就永远失去了关联标识**——而这恰恰是最需要排查的一类请求（用户会说"我问了但没反应"）。

把它放在首帧，使"服务端已经开始处理"这件事**在客户端可观测**，也让 FR-012（立即可见的接收反馈）有真实依据，而不是靠前端自己编一个"已发送"。
