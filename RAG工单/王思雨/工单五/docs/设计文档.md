## 3. 数据流

### 3.1 离线入库

```
data/raw/*.pdf
   │  MinerU（命中缓存则直接读产物 data/parsed/<doc>/<doc>/auto/*_content_list.json）
   ▼
原始块 (doc, page_no, block_type, text, image_path)
   │  text_clean：剔水印（表格必需）
   │  image_struct：图像/图表块 → OCR 或层级还原
   ▼
清洗后的块
   │  semantic_chunker：句子级语义切块，chunk_size=512，overlap=80
   ▼
分块 (chunk_id, doc, text, source, page_no, page_end, section, block_type, locator)
   ├──▶ Milvus 集合 gd5_chunks（bge-m3 向量，IP 度量）
   ├──▶ BM25 索引 data/bm25.pkl
   ├──▶ data/index.json（分块快照）
   └──▶ data/entities.json（公司名实体表，供 Query 改写用）
```

### 3.2 在线问答（一轮）

```
POST /chat {session_id, question}
   │ 0. 用户问句先落 Redis 历史（改写需要看到"上一轮问了什么"）
   │ 1. 查答案缓存（key = query + 历史摘要 + 召回参数 + 结构指纹）→ 命中则直接返回
   │ 2. Query 改写 + 实体追踪       → rewritten_query, entity
   │ 3. 混合检索：Milvus 向量召回 ∪ BM25 关键词召回 → 加权 RRF 融合 → 水印降权
   │ 4. 重排：bge-reranker-v2-m3 精排 → top_n=6
   │ 5. 生成：DeepSeek，严格基于片段，语言跟随提问
   │ 6. 组装引用（文件名/页码/片段/得分）→ 落历史 + 写缓存
   ▼
{answer, references[], rewritten_query, cached, degraded[], latency_ms}
```

## 5. 多轮对话 Query 理解方案（工单五核心）

### 5.1 要解决的三类问题

| 问题 | 工单原例 | 处理方式 |
| --- | --- | --- |
| 代词指代 | "**他**参与的哪个工程荣获了国家科技进步一等奖？" | 用会话中记录的实体替换"他/这个公司/该公司" |
| 零指代 | "**这个公司**的法定代表人是谁？" | 同上 |
| 实体切换 | "**那武汉力源信息技术股份有限公司呢？**" | 识别新实体 → 更新会话实体 → 把上一轮的问题主题套用到新公司 |

### 5.2 流程

1. **取上下文**：从 Redis `chat:{session_id}:history` 取最近 `HISTORY_TURNS` 轮；从 `chat:{session_id}:entity` 取上一轮实体。
2. **实体识别**：先用 `data/entities.json`（入库时从正文统计出的公司全称表，长名优先匹配），再用正则 `…(股份有限公司|有限(责任)?公司|集团)` 兜底。
3. **实体追踪**：若本轮识别到的实体与上一轮不同，则判定为**切换**，立即更新会话实体；后续轮次的"他/这个公司"指向新公司。
4. **短路优化**：首轮、且问句自带实体、且不含指代词 → 不改写，直接检索（省一次大模型调用，对 3 秒目标很关键）。
5. **大模型改写**：提示词明确"只输出改写后的问句本身"，温度 0，`max_tokens=120`，超时 `REWRITE_TIMEOUT=12s`。
6. **规则兜底**：大模型不可用/超时/返回空 → 用"上一轮问句模板 + 实体替换"的规则改写，并上报 `degraded=["rewrite"]`。

### 5.3 验收 5 问的预期改写结果

| 轮次 | 原始问句 | 改写后（用于检索） | 实体 |
| --- | --- | --- | --- |
| Q1 | 报告期内，武汉兴图新科…军用领域的收入分别是多少？ | 原句（首轮短路） | 武汉兴图新科电子股份有限公司 |
| Q2 | 他参与的哪个工程荣获了国家科技进步一等奖？ | 武汉兴图新科电子股份有限公司参与的哪个工程荣获了国家科技进步一等奖？ | 同上 |
| Q3 | 这个公司的法定代表人是谁？ | 武汉兴图新科电子股份有限公司的法定代表人是谁？ | 同上 |
| Q4 | 那武汉力源信息技术股份有限公司呢？ | 武汉力源信息技术股份有限公司的法定代表人是谁？ | **切换**为武汉力源信息技术股份有限公司 |
| Q5 | 武汉力源信息技术股份有限公司组织结构图中… | 原句（自带实体） | 同上 |

## 6. 检索方案

- **向量通道**：bge-m3 本地编码（1024 维，L2 归一化）→ Milvus `IVF_FLAT` + `IP` 度量，召回 `VEC_TOP_K=20`。
  - 检索时显式 `consistency_level="Strong"`：Milvus 默认 `Bounded` 一致性会导致"刚写入读不到"，且 `MilvusClient` 没有 `flush` 方法可以补救。
- **关键词通道**：jieba 分词 + 英文词/数字补抽，`BM25Okapi` 召回 `BM25_TOP_K=20`。
  - 数字同时索引"带千分位"和"去千分位"两种形态，保证 `14,414.16` 与 `14414.16` 都能命中。
- **融合**：加权 RRF。两路分数量纲不可比，用排名折算才公平。但**必须先在各通道内归一化再加权**：

  ```
  通道内归一化： norm(rank) = (rrf(rank) - rrf(N-1)) / (rrf(0) - rrf(N-1))    # 第1名=1，最后一名=0
  融合：        fusion = VEC_WEIGHT × norm_vec(rank) + BM25_WEIGHT × norm_bm25(rank)
  ```

  > **不能**直接把权重乘在原始 RRF 上。两路各取 20 条、K=60 时 RRF 取值 `[0.0125, 0.0164]`；
  > 乘 0.7 得 `[0.0088, 0.0115]`，乘 0.3 得 `[0.0038, 0.0049]`，**两段区间完全不相交**——
  > 结果是"BM25 排第 1 的块"永远打不过"向量排第 20 的块"，关键词通道被架空（实测目标块直接掉出前 20）。
  > 详见 `docs/优化报告.md` §1.1。
- **水印降权**：命中水印词的块（表格被污染，数字与表头的对应关系不可信）融合分 ×0.5，而不是删除。
- **重排**：bge-reranker-v2-m3 交叉编码精排，取 `RERANK_TOP_N=6`。
  - 打分输入按 `RERANK_MAX_CHARS=512` 截断：整表块可达数千字，不截断会把"成对打分"的 padding 开销放大数倍。

## 7. 缓存方案

| 用途 | Redis 键 | 内容 |
| --- | --- | --- |
| 会话历史 | `chat:{sid}:history` | 最近 N 轮问答（LIST，自动 `LTRIM`） |
| 会话实体 | `chat:{sid}:entity` | 当前讨论的公司，供指代消解 |
| 答案缓存 | `gd5:answer:{结构指纹}:{内容哈希}` | 答案 + 引用 + 改写问句 + 降级项 |
| 用户反馈 | `chat:{sid}:feedback` | 评分与文字意见 |

**缓存键必须带结构指纹**（`redis_cache.fingerprint()`）：对 `config.py / schemas.py / deepseek_llm.py / hybrid_retriever.py / reranker.py / query_rewriter.py` 的源码做哈希。

> 为什么：旧缓存会**静默吞掉新字段**。实测中出现过 `degraded` 字段被旧缓存吞掉，导致"发生了降级却没有任何提示"。用源码哈希自动生成指纹，改代码即自动换键，不需要手工升版本号，也不会遗漏人工升版本的时机。

缓存命中不读写历史以外的状态，但**仍然推进会话历史**，保证多轮连续性不被缓存破坏。

## 8. 评估方案

### 8.1 三组题

| 组 | 会话方式 | 内容 |
| --- | --- | --- |
| `multi_turn` | 同一会话按顺序 | 工单五 5 个问题（原文） |
| `english` | 同一会话 | 3 个英文问题（工单要求中英双语） |
| `standalone` | 每题独立会话 | 2 个单轮变体（验证无历史时也能答） |

### 8.2 判分口径

`correct = 关键字段全含(expect) 且 负样本全无(expect_not)`

负样本是必要的：**关键词判分抓不到"多答无关内容"**。实测（工单三）出现过自动判分满分、人工复核却发现混入 2 家无关企业的情况。因此：
- Q3 的负样本是 Q4 的答案（`赵马克`），Q4 的负样本是 Q3 的答案（`程家明`）—— 专门抓"实体张冠李戴"。
- `scripts/evaluate.py --selftest` 用"已知正确/已知错误"答案回验判分器本身，**判分器不通过就不采信准确率数字**。

### 8.3 ragas 四项指标

`faithfulness`、`answer_relevancy`、`llm_context_precision_with_reference`、`context_recall`，以 DeepSeek 为判官、本地 bge-m3 为嵌入。

工程约束（均为实测踩坑后固化到配置里）：
- `EVAL_MAX_WORKERS=2`：默认 16 并发会打满 DeepSeek 限流，把指标打成 `nan`。
- `bypass_n=True`：DeepSeek 不支持 `n>1`。
- **结果先落盘再算指标**：402 余额不足会让整轮静默作废（16 条里 10 条变 `nan` 也不报错），先落盘才能保住问答结果。
- 指标存在噪声底（约 ±0.05），比较"改前/改后"前必须先量一次噪声底，否则会把噪声当改进。

## 9. 稳定性与容错

| 组件 | 失败时的行为 | 上报方式 |
| --- | --- | --- |
| MinerU | → pymupdf → pdfplumber；扫描页 → PaddleOCR | 日志 + 解析结果标记 `block_type=ocr` |
| Milvus | 向量通道返回空，**仅 BM25 关键词检索** | `/chat` 的 `degraded=["milvus"]`，`/health` 置 degraded |
| BM25 | 关键词通道返回空，仅向量检索 | `degraded=["bm25"]` |
| 重排模型 | **回退到混合检索的原始排序** | `degraded=["rerank"]` |
| Query 改写 | **规则兜底改写** | `degraded=["rewrite"]` |
| DeepSeek | 只回检索到的原文片段，并说明大模型不可用（不编造） | `degraded=["llm"]` |
| Redis | 无历史/无缓存，退化为单轮问答 | `/health` 提示，`/chat` 正常返回 |
| Milvus 写向量化失败 | 与 Milvus 连接失败分开报错，避免"向量模型路径错"被误报成"Milvus 不可用" | 日志区分 |

设计原则：**任何降级都必须出现在响应的 `degraded` 字段里**，不允许静默失效。

## 10. 已知差异：工单 Q5 期望答案与原件不符

**结论：本系统按 PDF 原件作答，不按工单期望答案硬编码。**

- 工单期望答案：「渠道销售部最多，下辖珠海销售处、深圳销售处、北京销售处、武汉销售处、广州销售处」（5 个）
- 招股说明书2 原件：内部组织结构图中，**大客户销售部**下辖 6 个销售处 —— 珠海、深圳、北京、武汉、广州、**成都**

证据（两条独立来源互相印证）：
1. **图像几何证据**：把 `data/parsed/招股说明书2/招股说明书2/auto/images/ec4973106d….jpg` 二值化后做形态学线段检测，「销售处」分发线（y=1350，x=503..1104）向上的唯一竖线位于 **x=777**，落在 **大客户销售部**（x 752..828）范围内；该竖线上端 y=1264 恰为大客户销售部下边。程序化还原出的层级为：`销售部 → 大客户销售部 → 珠海/深圳/北京/武汉/广州/成都销售处`。
2. **正文证据**：招股说明书2 正文载明"公司目前在上海设立有 1 家分公司，在北京、广州、成都、深圳、武汉、珠海各设有 1 家销售处"。

**验收兼容开关**（默认关闭）：`Q5_ACCEPTANCE_COMPAT=true` 时，仅在答案后**追加**一行工单口径对照说明，**不篡改主答案**。见 `.env.example` 与 `backend/config.py`。
