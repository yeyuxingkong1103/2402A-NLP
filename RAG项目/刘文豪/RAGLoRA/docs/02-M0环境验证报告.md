## 二、逐项验证证据

### 2.1 bge-m3：**否决 FlagEmbedding，改用原生 transformers**

**发现的冲突**：`FlagEmbedding 1.3.5` 的依赖声明要求 `transformers>=4.44.2`，而 `rag_env` 是 `4.39.3`。
装它必然触发 transformers 升级，威胁 `sentence-transformers 2.6.1` 等既有包；且它还拖入
`datasets / peft / ir-datasets / sentencepiece / accelerate` 一串新依赖。**与"绝不重复安装、不破坏现有环境"直接冲突。**

**替代表达**：用 rag_env 已有的 `transformers` + `torch` 手写，数学上完全等价。

```
dense  = mean_pooling(last_hidden_state, attention_mask) → L2 normalize
sparse = relu(sparse_linear(last_hidden_state)) * attention_mask
         → 按 token_id 取 max 聚合
```

`sparse_linear.pt` 实测为 `OrderedDict{'weight': [1,1024], 'bias': [1]}`，
`nn.Linear(1024,1).load_state_dict()` 可直接重建，无需 FlagEmbedding 的任何代码。

**实测输出**：

```
[1] 模型加载 OK  5.2s | hidden=1024 | layers=24 | max_pos=8194
[5] dense OK | shape=(2, 1024) | L2范数=[1.0, 1.0]
[6] sparse 权重 OK | max=0.3082

    top12 稀疏词权重（输入："高血压患者应当限制钠盐摄入，每日食盐量不超过5克"）：
      '盐' 0.3082   '压' 0.2762   '钠' 0.2404   '血' 0.1936   '高' 0.1859
      '患者' 0.1790  '限制' 0.1478  '每日' 0.1442  '应当' 0.1322  '克' 0.1303
```

权重精准落在内容词上、虚词近零 —— learned sparse 行为正确。

> ⚠️ **注意**：实测发现 `<s>` 特殊符会带 0.1645 权重。**生产代码必须过滤 `tokenizer.all_special_ids`**，
> 否则稀疏检索会被特殊符噪声污染。

### 2.2 精排：**推翻"常驻 GPU"方案，改为 GPU 分时复用**

**发现的问题**：让 qwen2.5:7b 与精排模型**同时常驻显存**时：

```
nvidia-smi: 总 8188 MiB | 已用 7218 MiB | 空闲仅 740 MiB
ollama    : 4.42 GB（仍在 GPU）
并发生成吞吐: 5.2 tokens/s     ← 独占时是 47.8 tok/s，掉了 9 倍！
```

740MiB 剩余空间放不下 Ollama 的 KV cache，生成被挤向 CPU。一次 200 字回答要 40 秒。

**三种方案实测对比**：

| 方案 | 精排延迟 | 生成吞吐 | 判定 |
|---|---|---|---|
| 精排常驻 GPU | 28 ms | **5.2 tok/s** | ❌ 不可用 |
| 精排常驻 CPU | 1428–2782 ms | 47.8 tok/s | ⚠️ 可用但每次慢 1.4–2.8 秒 |
| **权重留 CPU 内存，用时搬 GPU，用完搬回** | **148 + 150 + 115 = 413 ms** | **47.8 tok/s** | ✅ **采用** |

**关键洞察**：精排发生在生成**之前**，两者本就不重叠。原设计让精排常驻 GPU 才制造了争抢。
实测搬运开销仅 148ms（搬入）+ 115ms（搬出），完全可接受。

**GPU 加载实测**：RTX 4060 Laptop，fp16 占 1.06 GB，加载 4.3s，排序正确性 2/2。

### 2.3 Qdrant：嵌入式模式，无需服务端

参考项目用的是 `QdrantClient(path=...)` —— **嵌入式模式，不需要 6333 端口服务**，因此省掉了
Milvus 那套 Docker 依赖，与"绝不重复安装"约束天然契合。

**依赖影响（`pip install --dry-run` 预演）**：

```
Would install h2-4.4.1 hpack-4.2.0 hyperframe-6.1.0 portalocker-3.2.0 pywin32-312 qdrant-client-1.19.0
```

**无任何既有包被升级或降级**，安全。实际安装后 `qdrant-client 1.19.0` 可用。

**混合检索端到端实测**：

```
Q: 高血压吃什么盐比较好？
   1.000000 [指南] 高血压患者应限制钠盐摄入，每日食盐量不超过5克，少吃腌制食品。
   0.666667 [指南] 高血压的诊断标准为收缩压≥140mmHg和/或舒张压≥90mmHg。

Q: 违约了要承担什么责任？
   1.000000 [民法典] 当事人一方不履行合同义务的，应当承担继续履行…违约责任。

带 payload 过滤（只在 消保法 内检索）:
   1.000000 [消保法] 消费者因购买商品受到人身损害的，享有依法获得赔偿的权利。
   0.666667 [民法典] 当事人一方不履行合同义务的…
```

> ⚠️ **重要发现：分数阈值过滤必须用精排分，不能用 RRF 分。**
> RRF 融合分是 `1/(k+rank)` 的量化值，会出现大量并列。实测中无关查询
> "违约了要承担什么责任" 给不相关文档打出了 0.5 分（排名并列），
> "腌菜能不能吃" 也给消保法打出 0.5。**按 RRF 分设阈值会大量误留。**

> ⚠️ 已知无害告警：脚本退出时 qdrant-client 的 `__del__` 会抛
> `ImportError: sys.meta_path is None`。这是解释器关闭时序问题，
> **生产代码里显式调用 `client.close()` 即可规避**。

### 2.5 Redis：**本地原本完全没有服务端**

**彻底排查结论**（用户要求复核后重查）：

| 排查项 | 结果 |
|---|---|
| Windows 服务 | 无 |
| `where.exe redis-server` / `redis-cli` | 未找到 |
| conda 包缓存 | 无 |
| WSL 发行版 | 仅 `docker-desktop`（已停止） |
| 常见安装目录 ×8 | 无 |
| 全盘扫描 c/d/e/f maxdepth 7 | 零个 `redis-server*` / `redis-cli*` / `memurai*` |
| 目录名含 redis | 全是 `Redist`/`Redistributable` 误匹配 |

**只有 Python 客户端 `redis 7.2.1`，服务端从未装过。** 客户端单独无法工作（实测
`ConnectionRefusedError 10061`，6379 端口无监听）。

**解决**：下载 `tporadowski/redis 5.0.14.1` 免安装 zip（12.6MB），解压到 `tools/redis/`。
- 无需 Docker（Docker 守护进程当时未启动，且 Docker Hub 不通）
- 无需管理员权限，不写注册表，删目录即卸载
- 直连 GitHub CDN 被重置，改用镜像 `https://ghfast.top/` 成功

**短期记忆语义逐条验证**：

```
[1] PING -> True                     [2] Redis 5.0.14.1 standalone
[4] 写入 8 轮 -> 16 条               [5] LTRIM 后 -> 12 条, TTL 3600s
[6] LRANGE 最近 2 轮 -> 4 条，顺序正确
[7] conv:1:12 -> 12 条 | conv:2:12 -> 1 条   <- 多用户隔离成立
[8] 10000 次 LPUSH+LTRIM -> 列表恒定 12 条
[9] used_memory 706K / maxmemory 512MB / allkeys-lru
```

> ⚠️ **必须设置 `encoding_errors="replace"`**：Redis 5.0.14.1 (Windows 版) 的 `INFO` 响应
> 含有 GBK 编码的中文路径字节，而 redis-py 7.2.1 默认严格 UTF-8 解码，
> 会抛 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd7`。
> `redis.Redis(..., decode_responses=True, encoding_errors="replace")` 可规避。

## 三、对设计文档的修正（3 处假设被推翻）

| # | 原设计 | 实测修正 | 影响章节 |
|---|---|---|---|
| 1 | 依赖 FlagEmbedding 产出 BGE-M3 稀疏向量 | **不装 FlagEmbedding**，用原生 transformers 手写 dense+sparse | §0.3 / §2.1 / §6 |
| 2 | 精排模型常驻 GPU（预估 2.3GB） | **精排 GPU 分时复用**；常驻会毁掉生成吞吐（46→5.2 tok/s） | §0.4 / §2.2 / §6 |
| 3 | 按融合分设 SCORE_THRESHOLD 过滤 | **阈值必须用精排分**；RRF 分是量化值会大量并列 | §2.2 / §6 |

**显存预算（修正后实测值）**：

| 组件 | 原预估 | 实测 | 说明 |
|---|---|---|---|
| Ollama qwen2.5:7b | 4.7 GB | **4.42 GB** + KV cache | ctx 4096 |
| 精排 | 2.3 GB | **1.06 GB**，且**分时复用** | 用完即释放 |
| bge-m3 嵌入 | 0（CPU） | 0（CPU） | 维持 |
| **生成时峰值** | 7.0 GB | **≈ 6 GB** | 精排已释放，无争抢 |

> 📌 **环境注意事项**：开发机桌面程序（Edge 多进程、WPS、QQ、bilibili、VS Code、
> 安卓模拟器 `Ld9BoxHeadless.exe`）会占用大量显存。Windows WDDM 会在 Ollama
> 需要时驱逐它们，但**建议跑压测/评测时关掉模拟器和多余浏览器**，避免干扰测量。
