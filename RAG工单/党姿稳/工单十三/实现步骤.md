# 工单十三 · 实现步骤（过程跟踪）

> 目标：定位 RAG 检索链路中的性能瓶颈并对应优化，给出优化前后的检索时间对比。
> 验收：每个会话中，用户输入 query 后，**检索结果返回时间 ≤ 3 秒**。

---

## 一、总体思路

先把一次 RAG 请求按工单要求拆成五个阶段，做**阶段级耗时归因**，再用 cProfile 做**函数级**热点确认，找到瓶颈后逐项优化，最后用同一批测试问题、同一套检索参数跑基准测试做前后对比。

```
用户 query
   │
   ├─ 阶段1 查询处理与增强 ────────┐
   ├─ 阶段2 检索（向量+BM25+融合+去冗余）│ ← 「检索结果返回」口径，须 ≤3s
   ├─ 阶段3 上下文组装与提示工程 ───┘
   │
   ├─ 阶段4 LLM 生成
   └─ 阶段5 后处理与响应格式化
```

---

## 二、实现步骤

### 步骤 1：把五阶段定义与性能预算固化到配置

`config.py`：

- `STAGES` 定义五个阶段名，`STAGE_QUERY` / `STAGE_RETRIEVE` / `STAGE_CONTEXT` / `STAGE_GENERATE` / `STAGE_POST` 取下标常量。
- `RETRIEVAL_STAGES = [STAGE_QUERY, STAGE_RETRIEVE, STAGE_CONTEXT]` 明确「检索结果返回」的口径——**不含 LLM 生成**。
- `RETRIEVAL_BUDGET = 3.0` 作为验收阈值，`BENCH_REPEATS = 3` 指定重复轮次。
- 检索超参数（`VECTOR_TOP_K=30`、`BM25_TOP_K=30`、`FINAL_TOP_K=6`、`RRF_K=60`、`MMR_LAMBDA=0.90`、`CONTEXT_MAX_CHARS=12000`）**与工单十二逐项一致**，保证对比只反映性能差异。
- 语料、向量、BM25、图谱实体词典全部复用 `data/` 下工单十二已构建的缓存，**不重复解析 PDF、不重复编码语料**。

### 步骤 2：结构化日志与阶段追踪器

`logger.py`：

- `get_logger()` 提供带时分秒的控制台 logger，同名复用。
- `StageTracer(request_id, query, log_file, persist)`：
  - 构造时生成 12 位 `request_id`，并记录起始 `perf_counter`。
  - `begin(stage)` / `end(stage=None, **metrics)` 用计时栈支持嵌套打点，`end` 可附带业务指标（关键词数、候选块数、生成 token 数等）。
  - `record()` 把每条阶段明细以 JSON Lines 追加到 `data/stage_trace.jsonl`，字段含 `request_id` / `stage` / `seconds` / `query` / `timestamp`。
  - `retrieval_seconds()` 按 `RETRIEVAL_STAGES` 求和，`summary()` 输出总耗时、检索口径耗时、`within_budget` 与阶段明细。

> 有了 `request_id`，同一条请求的五条阶段记录天然串成一条耗时瀑布，出问题时可以直接定位到某一阶段。

### 步骤 3：资源加载与预热

`resources.py`：

- `load_chunks()` / `load_vectors()` / `load_bm25()` / `load_entity_names()` 读工单十二的缓存。
- `load_model()` 单例加载本地 `m3e-base`，`torch.set_num_threads(config.EMBED_THREADS)`、`max_seq_length=256`。`EMBED_THREADS = 16` 是实测出来的：同一查询重复 15 次，1/2/4/8/16 线程的中位耗时分别为 0.634/0.433/0.309/0.077/**0.063** 秒，取满核最快且尾延迟最小（详见 `过程问题记录.md` 问题五）。
- 线程策略相关的两个环境变量（`OMP_WAIT_POLICY=PASSIVE`、`TOKENIZERS_PARALLELISM=false`）写在 `config.py` 顶层——**必须早于 torch 被导入**，早于 OpenMP 线程池初始化，否则不生效。
- `load_entity_names()` 按**长度降序**返回实体名，供最长匹配使用。
- `normalize_matrix()` 把语料矩阵一次性归一化为连续 `float32`。
- `warm_up(model, entity_names)` 在服务启动时先跑一次小批量编码与一次分词，把 BLAS 线程池初始化与 jieba 词典加载的开销从**首个用户查询**上提前付掉。

### 步骤 4：阶段共享实现

`pipeline.py`——两条流水线共用，保证优化前后第 3~5 阶段逐行相同：

| 函数 | 作用 |
|---|---|
| `vector_search_naive()` | 优化前：每次重算全量行范数 + 生成归一化副本 + 全排序 |
| `vector_search_fast()` | 优化后：预归一化矩阵单次点积 + `argpartition` 取 top-k |
| `bm25_search()` | 调 BM25 索引检索 |
| `rrf_fuse()` | 倒数排名融合，多路候选按 `1/(k+rank)` 累加 |
| `mmr_dedup()` | 最大边际相关去冗余，剔除与已选块近乎重复的候选 |
| `assemble_context()` | 按「来源 + 页码 + 正文」拼装上下文并裁剪长度 |
| `build_prompt()` | 组装发给 LLM 的用户提示词 |
| `call_llm()` | 调 DeepSeek 兼容接口，返回答案与生成 token 数 |
| `format_response()` | 去重整理引用并输出结构化响应 |
| `run_tail()` | 阶段三~五的共用流程 |

### 步骤 5：优化前的基线流水线

`baseline_pipeline.py`：

- `extract_keywords_llm(query)` 实打实调一次 DeepSeek 抽取关键词（`temperature=0.0`、`max_tokens=200`），**不做缓存**——这就是未优化时每个用户会话真实会付的那笔开销。
- 阶段二用 `vector_search_naive()`，两路召回**串行**执行。

### 步骤 6：优化后的流水线

`optimized_pipeline.py`，四项优化：

1. **查询理解离线化** — `match_entities()` 用 3355 条图谱实体名做最长匹配（长名优先 + 子串去重），`extract_keywords_local()` 再补 `jieba` 分词并过滤单字与疑问词，全程无网络调用。
2. **向量检索预归一化** — 构造时一次性归一化，查询时只归一化那一条 query。
3. **`argpartition` 取 top-k** — O(n) 选择代替全排序。
4. **查询级缓存 + 冷启动预热** — `_kw_cache` / `_vec_cache` 以 query 原文为键；构造时调 `warm_up()`。

另有一项**被实测否定**的候选优化：双线程并行跑两路召回。实测串行两路中位 0.0031 秒、双线程并行 0.0033 秒，并行反而略慢——预归一化后两路合计才 3 毫秒，还不够付线程创建与切换的固定开销。**因此没有引入**，详见 `过程问题记录.md` 问题六。

> 优化后检索结果与优化前**逐块一致**——改的是「同样的结果怎么算得更快」，不是「用近似换速度」。

### 步骤 7：基准测试

`benchmark.py`：

- `run_system()` 对 16 个测试问题重复 3 轮，逐次记录五阶段耗时与检索口径耗时。
- `summarize()` 把 `round == 0` 单独标为 `cold`（含冷启动）、`round > 0` 标为 `steady`（稳态），**两类分开统计**，不拿冷启动当稳态。
- `compare()` 逐阶段算加速比；`draw_chart()` 画优化前后各阶段均值柱状图并叠加 3 秒预算线。
- `write_report()` 生成 `evaluation/性能对比.md`。
- 逐次明细与汇总写入 `data/benchmark.json`。

### 步骤 8：函数级剖析

`profile_cprofile.py`：

- 只对 2 条查询做剖析（cProfile 自身开销大，样本控制在够用即可）。
- 剖析区间只包住**查询执行循环**，模型加载与流水线构建放在区间外，避免噪声污染热点列表。
- 输出**两张表**：一张只看本工单模块（`project_only=True`），一张是含库调用的全量表。前者才是要看的——全量表会被 `_ssl._SSLSocket.read` / `socket.readinto` 这类网络阻塞调用占满。
- **过滤要用「是 .py 且目录精确匹配」而不是 `startswith`**：内置函数与 C 扩展的 `fname` 是 `<built-in method ...>` 或 `~`，而 `os.path.abspath("~")` 恰好落在当前工作目录上，用 `startswith` 判断会把这些库调用误当成项目代码。
- 保留 `data/before.prof` / `data/after.prof` 原始文件，可用 `python -m snakeviz` 交互式查看调用树。
- **读数陷阱（已写入文档）**：`torch` 路径在 cProfile 下会被严重放大——每个算子都单独插桩记账，几十毫秒的推理能显示成秒级。因此 cProfile 只用来横向比结构与比例，绝对耗时一律以 `benchmark.py` 的实测为准。

### 步骤 9：可视化界面

`app.py` + `start_app.py`：

- 侧栏可选「优化后 / 优化前（基线）」系统、选工单十二的 16 个验收问题或输入自定义问题。
- 主区四个指标卡片：**检索结果返回耗时** / 端到端总耗时 / **达标或超时** / `request_id`。
- 三个标签页：阶段耗时表 + 柱状图（含各阶段在检索口径中的占比）、答案与引用、最近请求的阶段日志。
- `start_app.py` 用 socket 从 8513 起逐端口试探，绑定成功即用该端口启动 Streamlit。

## 六、备注

1. **「检索结果返回」的口径已在配置里写死**：= 查询处理与增强 + 检索 + 上下文组装与提示工程，不含 LLM 生成。验收看的是这个口径。报告中同时保留端到端总耗时一栏，避免误读。
2. **优化手段不牺牲检索精度**：检索超参数（`VECTOR_TOP_K` / `BM25_TOP_K` / `FINAL_TOP_K` / `RRF_K` / `MMR_LAMBDA` / `CONTEXT_MAX_CHARS`）与工单十二逐项一致；第 3~5 阶段两条流水线共用同一份 `run_tail`，逐行相同；向量检索仍是**精确点积**，`argpartition` 只改变"怎么选出 top-k"、不改变选出的是谁（已实测两种实现的返回行号集合完全相同），未引入任何近似索引。需要说明的是，两条流水线阶段一得到的关键词集合不同（在线 LLM 抽取 vs 本地图谱词典 + jieba），因此 BM25 通道的召回结果可能略有差异——本工单考核耗时，检索质量已在工单十二用 RAGAS 完成评估。
3. **冷启动单独统计并显式预热**：验收要求「每个会话」首个 query 也达标，因此 `round == 0` 在报告中单列一栏，且优化后流水线在构造时完成预热。
4. **基线刻意保留了真实开销**：基线的关键词抽取是真调 API，不做缓存。基准测试因此耗时较长（16 问题 × 3 轮），这是拿到可信对比数据必须付的成本。
5. **语料与索引复用工单十二**：本工单只做性能优化，不重建语料、不重新编码，因此启动快、结果与工单十二的 RAGAS 评估口径一致。
6. **验收结论**：优化后「检索结果返回」均值 **0.1035 秒**、P95 **0.2684 秒**、最大 **0.3120 秒**，48/48 次全部在 3 秒内；真正的进程冷启动（新开会话只问一句话）为 **0.3633 秒**，同样达标。优化前同口径的均值为 1.1876 秒、P95 1.5431 秒，且其耗时由网络往返决定——主机负载高时实测 P95 达到 4.8153 秒、达标率跌到 37/48（见 `过程问题记录.md` 问题十四）。
7. **跑基准测试前先腾出 CPU**：本机同时开着 IDE、Docker 与多个聊天软件，实测会显著污染耗时数据。这一点比任何参数调整都更影响结果可信度。
