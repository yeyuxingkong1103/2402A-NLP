### 1.2 索引阶段数据流（Graph RAG 的「建图」）

```
9 份年报 PDF
   │  ① rag_core.pdf_parse.parse_pdf()      PyMuPDF 抽正文 + pdfplumber 抽表格
   ▼
PageBlock[]（doc / page / type / content）
   │  ② rag_core.chunk.chunk_blocks(strategy="structure", size=900)
   │     按「第X节 / 一、/（一）」等标题层级切块，并在块首注入章节路径
   ▼
Chunk[]（chunk_id 形如「平安银行股份有限公司2019年年度报告-tex-00042」）
   │  ③ rag_core.graph_rag.build_knowledge_graph(profile="optimized", resume=True)
   │     逐块调用 LLM：
   │       · 系统提示词给出「实体类型体系 + 关系类型体系 + few-shot 示例」
   │       · 要求指代还原（「本行」→「平安银行股份有限公司」）
   │       · 要求财务指标带报告期（「营业收入（2019年）」）
   │       · 只抽原文明确陈述的关系，description 引用原文短语
   │       · gleaning 二轮补漏（数字、顿号并列实体、表格行列关系）
   │     每抽完一块立即 append 到 extractions_optimized.jsonl（断点续跑）
   ▼
抽取结果 JSON（entities / relations）
   │  ④ KnowledgeGraph.add_extraction()
   │     _norm_name 规范化 → _resolve_alias 别名消解 → 描述累加
   │     → _rebuild_graph 按 (source,target) 合并同向多关系并累加 weight
   ▼
知识图谱（networkx.MultiDiGraph）
   │  ⑤ kg.detect_communities(resolution=1.0)     Louvain 社区检测
   │  ⑥ kg.summarize_communities(top_n=20)        逐社区 LLM 生成 150 字摘要
   ▼
data/graph/kg.json
```

### 1.3 检索阶段数据流（Graph RAG 的「问答」）

```
用户问题
   │
   ├─(A) 局部检索 kg.local_search(question, hops=2)
   │       link_entities()：名称直接匹配 + 别名匹配 + 公司名正则后缀匹配
   │       → 种子实体（按度数排序取前 5）→ 沿出边/入边扩展 2 跳
   │       → 子图（实体属性 + 关系描述）→ _render_subgraph() 渲染成文本
   │
   ├─(B) 全局检索 kg.global_search(question, top_k=3)
   │       在 Community Summaries 上做字符 n-gram 相关性排序
   │       → 命中的社区摘要（含社区涉及实体列表）
   │
   └─(C) 向量兜底（可选）retriever.search(strategy="hybrid", reranker="tfidf")
           图谱与社区都答不了时，回退原文片段（与工单07 同通道，保证口径可比）
   │
   ▼
三段上下文拼接 ──▶ LLM（GRAPH_RAG_SYS 系统提示：优先图谱、数值必须精确、
                    不足时明说「知识库中未找到相关信息」、末尾标注来源）
   ▼
答案 + trace（种子实体 / 子图规模 / 命中社区 / 向量片段）+ 耗时
```

## 二、技术选型

| 环节 | 选型 | 备选 | 取舍理由 |
| --- | --- | --- | --- |
| 图谱存储 | **networkx.MultiDiGraph** | Neo4j / NebulaGraph / ArangoDB | 9 份年报的图谱规模在 10⁴ 节点量级，networkx 纯内存即可，**零部署成本**、可直接 pickle/JSON 落盘、与 Python 生态无缝；Neo4j 的优势在千万级节点与多用户并发 Cypher 查询，本工单用不上。核心库同时保留 `to_neo4j()`，需要时可一键导入。 |
| 图算法 | **networkx.community.louvain_communities** | Leiden（igraph）/ Louvain（python-louvain） | Louvain 已内置在 networkx 中，无需额外依赖；`resolution` 参数可调社区粒度；固定 `seed=42` 保证结果可复现。Leiden 质量更好但需 igraph 依赖，收益对本规模数据有限。 |
| 实体关系抽取 | **LLM 零样本 + 类型体系约束 + few-shot**（DeepSeek） | 微调序列标注模型（BERT+CRF）/ 规则模板 | 金融年报的实体边界与关系类型极其多样，规则模板维护成本高；标注数据从零构建成本更高。LLM 方案无需标注、可随 prompt 快速迭代，且 `description` 字段天然携带原文依据便于人工校验。 |
| 抽取档位控制 | **PromptProfile（baseline / optimized）** | 多套硬编码 prompt | 把「是否给类型体系、是否 few-shot、补漏轮数、实体/关系上限」做成数据类，工单09 的优化对比可直接切 profile，代码零改动。 |
| 社区摘要 | **LLM 摘要（150 字/社区）** | TF-IDF / TextRank 抽取式摘要 | 社区成员是实体名而非连续文本，抽取式摘要在这种「词袋」输入上几乎无效；LLM 能基于关系描述归纳出主题与结论，这正是 Graph RAG 全局问答的基础。 |
| 可视化（静态） | **matplotlib + networkx.draw** | Graphviz / Gephi | 复用核心库 `KnowledgeGraph.visualize()`，自带中文字体探测（SimHei/微软雅黑）；产出 PNG 便于放进文档与视频。 |
| 可视化（交互） | **手写 ECharts 页面 + Canvas 力导向兜底** | pyvis / D3 / Gephi | pyvis 会额外引入依赖且模板陈旧；ECharts 的 `graph` 系列原生支持力导向布局、拖拽、roam 缩放、邻接高亮，交互最完整。**关键取舍**：ECharts 走 CDN，离线环境会加载失败，因此再手写一个零依赖的 Canvas 力导向渲染器作为兜底（8 秒超时或 onerror 自动切换），保证任何环境下可视化页面都能打开。 |
| PDF 解析 | **PyMuPDF（文字）+ pdfplumber（表格）** | pdfminer / camelot / OCR | 复用 `rag_core.pdf_parse` 的三层解析；9 份年报均为可复制文本的电子版，无需 OCR。表格解析对数值型问题至关重要（大量财务指标只出现在表格里）。 |
| 向量兜底 | **bge-large-zh-v1.5 + BM25 + RRF** | 纯图谱检索 | 图谱对「未收录实体」的问题无能为力；保留原文通道可显著降低拒答率，也让工单07/08 的指标对比在**同一套上下文口径**下更具可比性。 |
| 评估 | **rag_core.evaluate（自实现 RAGAS）** | 官方 ragas 包 | 与工单07 使用同一套实现，指标口径完全一致；`--use-ragas` 可在装了官方包时切换。 |
| 服务 | **FastAPI + uvicorn** | Flask / Gradio | 复用 `rag_core/api.py` 的技术栈；自动生成 `/docs` 接口文档；前后端同源部署，前端为单文件 HTML，零构建。 |

## 三、Graph RAG 与传统 RAG 的对比

| 维度 | 传统 RAG（工单01~07 的路线） | Graph RAG（本工单） |
| --- | --- | --- |
| 索引单元 | 文本块（chunk） | 实体 + 关系三元组 + 社区摘要 |
| 检索单元 | 与问题向量最相似的 Top-K chunk | 局部：种子实体 2 跳子图；全局：社区摘要 |
| 索引成本 | 低（只需 embedding） | **高**（每个 chunk 至少 1 次 LLM 抽取，optimized 档位 2 次） |
| 查询成本 | 低 | 中（局部检索是纯图遍历，几乎零成本；全局检索需社区摘要已就绪） |
| 多跳推理 | 弱：需要多个 chunk 恰好都在 Top-K 内 | 强：沿关系显式扩展 2 跳，链路可解释 |
| 全局归纳题 | 几乎不可行：9 份文档的共性无法靠 Top-5 chunk 覆盖 | 可行：社区摘要本身就是「跨文档主题聚合」的产物 |
| 数值精确性 | 依赖 chunk 是否切到数字，且易跨期混淆 | 指标实体带报告期（「营业收入(2019年)」），关系 description 带原文数值 |
| 可解释性 | 只能给出「命中了哪些片段」 | 可展示「答案由哪几个实体、哪几条关系推得」，每条关系带原文依据 |
| 增量更新 | 重新 embedding 新 chunk 即可 | 需要为新 chunk 重新抽取并合并（核心库提供 `incremental_add`） |
| 抗幻觉 | 靠 prompt 约束 | prompt 约束 + 关系必须有原文依据 + 「图谱不足时明说」 |
| 冷启动 | 快 | 慢（本工单 9 份年报的抽取是耗时瓶颈，故设计了 JSONL 断点续跑） |
| 典型擅长问题 | 「某文档第 X 页说了什么」 | 「某公司某指标是多少」「这些机构的共同策略是什么」 |

**本工单的定位**：Graph RAG 不是替代传统 RAG，而是补上后者在**多跳**与**全局归纳**上的短板。
因此 `GraphRAG(mode="hybrid")` 保留了向量兜底通道，形成「图谱优先、原文兜底」的组合。

## 四、知识图谱 Schema 设计

Schema 定义在 `rag_core/graph_rag.py` 的 `FIN_ENTITY_TYPES` 与 `FIN_RELATION_TYPES`，
抽取时通过 prompt 作为**封闭枚举**下发（模型必须从中选择 `type`）。

### 4.1 实体类型体系

| 类型 | 定义 | 设计理由 | 典型实例（来自本语料） |
| --- | --- | --- | --- |
| 公司 | 企业法人主体 | 几乎所有问题都要先定位到主体 | 平安银行股份有限公司、中国平安保险（集团）股份有限公司 |
| 机构 | 监管机构、交易所、行业协会 | 「受监管于」关系的端点；行业分析必备 | 中国人民银行、中国银行保险监督管理委员会、深圳证券交易所 |
| 人物 | 董事、监事、高管、股东 | 董事长致辞、高管类问题的答案来源 | 谢永林、胡跃飞、马明哲 |
| 金融产品 | 贷款、存款、理财、保险、债券、基金 | 业务分析的抓手 | 信用卡、个人住房贷款、万能险 |
| 业务板块 | 零售金融、对公业务、资金同业、资产管理 | 支撑「业务结构优化」类分析题 | 零售金融业务、批发金融业务 |
| 财务指标 | 营业收入、净利润、不良贷款率、拨备覆盖率、资本充足率… | **数值型问题的答案载体**，要求带报告期 | 营业收入（2019年）、拨备覆盖率（2019年） |
| 风险类型 | 信用/市场/操作/流动性风险 | 风险类与周期类问题的答案路径 | 信用风险、市场风险、流动性风险 |
| 行业 | 国民经济行业分类 | 信贷投向分析维度 | 制造业、批发和零售业、房地产业 |
| 地区 | 省、市、自治区 | 区域集中度分析（回答「潜在压力」） | 珠江三角洲、中部地区、香港 |
| 监管政策 | 法律法规、监管规定、标准规范 | 监管口径变化的背景 | 资管新规、巴塞尔协议III |
| 时间 | 年份、报告期、季度 | **锚定报告期，避免不同年份数值串台** | 报告期（2019年）、2020年 |

**为什么是这 11 类而不是更细/更粗？**
- 更细（如把「财务指标」拆成盈利能力/资产质量/资本充足三类）会导致同一指标在不同块被标成不同类，
  合并失败、统计失真；Schema 的价值在于**稳定可合并**。
- 更粗（如只保留「实体/概念」两类）则丢失了「按类型过滤可视化」「按类型统计」的能力，
  也无法在检索时按类型加权。
- 这 11 类同时覆盖了**问答所需的四类信息**：主体（公司/机构/人物）、业务（产品/板块/行业/地区）、
  度量（财务指标/时间）、约束（风险/监管政策），正好对应金融问答的主要问法。

### 4.2 关系类型体系

| 关系 | 定义 | 设计理由 | head → tail 示例 |
| --- | --- | --- | --- |
| 子公司 | A 是 B 的子公司 / 控股子公司 | 集团型年报的基本结构 | 平安银行股份有限公司 → 中国平安保险（集团）股份有限公司 |
| 控股股东 | A 是 B 的控股股东 | 股权结构题的直接答案 | 中国平安保险（集团）股份有限公司 → 平安银行股份有限公司 |
| 参股 | A 参股 B | 区分控制/非控制关联方 | 招商银行股份有限公司 → 招银理财有限责任公司 |
| 投资 | A 投资于 B（含金融资产投资） | 资产投向分析 | 中国人寿保险股份有限公司 → 某某基金 |
| 任职 | A 在 B 担任某职务 | 「董事长/法定代表人是谁」的路径 | 谢永林 → 平安银行股份有限公司 |
| 提供产品服务 | A 向 B 提供某产品或服务 | 业务关系 | 招商银行股份有限公司 → 零售客户 |
| 发行 | A 发行了某金融产品 | 产品发行关系 | 中国平安保险（集团）股份有限公司 → 某某保险产品 |
| 披露指标 | 某报告中披露了某财务指标及其数值 | 把「文档」与「指标」连起来 | 招商银行股份有限公司2019年年度报告 → 营业收入（2019年） |
| **指标数值** | 财务指标在特定报告期的取值 | **数值型问题的核心关系** | 营业收入（2019年） → 报告期（2019年），description 记录 2697.03 亿元 |
| 面临风险 | A 面临某类风险 | 风险类问题路径 | 平安银行股份有限公司 → 信用风险 |
| 受监管于 | A 受 B 监管 | 监管关系 | 招商银行股份有限公司 → 中国银行保险监督管理委员会 |
| 属于行业 | A 属于某行业 | 行业分析维度 | 某企业 → 制造业 |
| 位于地区 | A 位于某地区 | 区域分析维度 | 招商银行股份有限公司 → 珠江三角洲 |
| **同比变化** | 某指标相对上期上升/下降 | **增长率类问题的核心关系** | 营业收入（2019年） → 报告期（2018年），description 记录 +8.51% |
| 提及 | 文档 A 中提及了实体 B | 兜底关系，保证弱相关信息不丢 | 招商银行股份有限公司2019年年度报告 → 某某实体 |

### 4.3 两个关键设计决策

1. **指标实体带报告期（`营业收入（2019年）`）**
   若不带期间，9 份年报里所有年份的「营业收入」会塌缩成同一个节点，
   不同年份的数值被累加到同一段 description 里，数值型问题必然答错。
   带期间后，「营业收入（2019年）」与「营业收入（2020年）」是不同节点，
   各自绑定各自的数值与原文依据。

2. **关系必须有原文依据（`description` 引用原文短语）**
   这既是抗幻觉手段，也是可视化时「点击连线看关系描述」的内容来源，
   更是验收时人工核对抽取质量的最短路径——本工单 `results/extraction_examples.md`
   就是把这个字段当作「原文 → 抽取结果」的对照表来用。

## 五、开发流程

```
① 语料准备      python src/prepare_corpus.py
                 ├─ 还原 GBK 乱码文件名（失败则用股票代码查表）
                 ├─ parse_pdf 解析 9 份年报（文字 + 表格，带磁盘缓存）
                 └─ chunk_blocks(structure, size=900) → data/corpus/chunks.json
                                              → results/corpus_stats.json

② 图谱构建      python src/build_graph.py            ← 最耗时的一步（LLM 抽取）
                 ├─ build_knowledge_graph(profile="optimized", resume=True)
                 ├─ detect_communities(resolution=1.0)
```

## 七、已知限制与改进方向

| 限制 | 影响 | 改进方向 |
| --- | --- | --- |
| 抽取成本高（每块 1~2 次 LLM 调用） | 9 份年报全量抽取耗时较长 | 已用 JSONL 断点续跑；进一步可先用小模型预筛「含实体密度高」的块 |
| `link_entities` 是字符串匹配 + 后缀匹配 | 问题里用简称、代称时可能漏命中 | 接入 embedding 做实体向量链接，或引入金融实体别名词典 |
| Louvain 社区粒度受 `resolution` 影响 | 社区过粗/过细会影响全局检索质量 | 用 `--resolution` 做小规模网格搜索，以 `context_recall` 为选择依据 |
| 社区摘要受 LLM 幻觉影响 | 摘要可能引入原文没有的结论 | 摘要 prompt 已限定「基于给定实体与关系」；研报生成时再以三元组 evidence 交叉校验 |
| 图谱与向量库需分别构建 | 只跑图谱脚本时无向量兜底 | `graph_qa.py` 会自动检测并降级（`--no-retriever` 亦可显式关闭） |
