# OCR 文档解析分流说明

> 日期：2026-09-20
> 开关：`POST /api/kb/ingest` 的 `ocr` 参数（`auto` / `force` / `off`）

---

## 一、为什么要分流

清单要求「文档解析（PDF，OCR，pdfplumber，多模态大模型，MinerU，PDF-OCR-VL）」——
这些工具**适用场景不同**，对每份文档都上最重的解析器是浪费：

| 文档类型 | 正确做法 | 成本 |
|---|---|---|
| **文本层 PDF**（能选中文字） | PyMuPDF 直接抽 | 毫秒级 |
| **扫描件**（无文本层） | 必须 OCR | MinerU 实测 **95 秒/2页** |
| **表格** | pdfplumber（文本层）/ MinerU 表格模型（扫描件） | — |

本项目的医疗指南是文本层 PDF（**页均 2232 字**），
对它跑 OCR 是纯浪费 —— 但如果没有分流，谁来都一样处理。

## 二、分流逻辑

```
PDF ─→ probe_pdf() 抽样前 5 页算页均字符数
        │
        ├─ ≥ 50 字/页 → **文本层** → PyMuPDF（含页眉页脚清洗）
        │
        └─ < 50 字/页 → **扫描件** → MinerU (vlm-engine, GPU)
                                      └─ 失败且允许下载时 → PaddleOCR 降级
```

**阈值 50 字/页**（`RAGLORA_OCR_TEXT_THRESHOLD`）判据说明：
- 真实文本层 PDF 页均 1686–2232 字，离阈值极远
- 真扫描件页均 **0 字**
- 阈值取 50 是留足余量，**不是卡在中间的分界线**

**抽样而非全读**：几百页的 PDF 全读一遍只为算平均字符数不划算。

## 三、⚠️ 引擎选择：MinerU 而非 PaddleOCR（有依据，非偏好）

| 引擎 | 模型位置 | 能否直接用 |
|---|---|---|
| **MinerU** | `D:\MinerU\models`（5.6GB，**已完整**） | ✅ **默认**，零下载 |
| **PaddleOCR** | `~/.paddlex`（**空目录，0MB**） | ❌ 需下载模型 |

`mineru.json` 已配置 `models-dir` 指向本地路径，不会触发联网。

**PaddleOCR 默认关闭**，需显式开启：

```bash
RAGLORA_OCR_ALLOW_DOWNLOAD=1   # 首次调用会联网下载模型
```

这符合项目的「本地优先，下载需授权」原则。

### 跨环境调用

MinerU 装在**独立 conda 环境** `mineru`（依赖与 `rag_env` 冲突），
所以用 `subprocess` 调 `mineru.exe`，不是 import。父项目 `D:\桌面\RAG\mineru_parse.py` 是同一套做法。

## 四、实测验证

### 4.1 类型判定

| 文档 | 页均字符 | 判定 |
|---|---:|---|
| 中国高血压防治指南2024修订版.pdf（98页） | 2232.6 | `text` ✓ |

| 人造扫描件（把上者渲染成图片再拼回 PDF） | **0.0** | `scanned` ✓ |

### 4.2 MinerU 实际解析（人造扫描件，2 页）

```
      服务项目基层高血压管理办公室 国家基层高血压管理专家委员会 通信作者：李静…
```

**该 PDF 的文本层字符数为 0** —— 内容完全是 OCR 恢复出来的，且标题/作者/摘要都正确。

> ⚠️ **95 秒/2 页**是 vlm-engine（多模态大模型）的真实成本。
> 大批量扫描件入库会很慢，这是精度换来的代价，需提前规划。

## 五、已知限制

| 限制 | 说明 |
|---|---|
| **OCR 结果无页码** | MinerU 输出整篇 markdown，切不出原始页码；统一记为页码 0，`format_source` 会退化为「来源文件名」而不会显示错误页码 |
| **MinerU 很慢** | vlm-engine 约 47 秒/页。批量入库扫描件需预留时间 |
| **PaddleOCR 不可直接用** | 模型需下载，默认关闭 |
| **表格提取未接入主链路** | `ocr.extract_tables()` 已实现（pdfplumber），但**尚未并入分块**；扫描件的表格靠 MinerU 的表格模型自动处理 |
| **`.incomplete` 残留** | `D:\MinerU\models\VLM\...\model.safetensors.incomplete`（43MB）是某次中断下载的碎屑，**实测不影响使用**（主模型 2205MB 完整） |

## 六、用法

```bash
# 自动分流（默认）
POST /api/kb/ingest  {"path": "...", "collection": "kb_medical", "ocr": "auto"}

# 强制 OCR（文本层 PDF 也走 OCR，用于对比）
POST /api/kb/ingest  {"path": "...", "ocr": "force"}

# 强制文本层（确认分流开关真的生效）
POST /api/kb/ingest  {"path": "...", "ocr": "off"}

# 换引擎
RAGLORA_OCR_ENGINE=paddleocr     # 需同时设 RAGLORA_OCR_ALLOW_DOWNLOAD=1
```

**测试**：`backend/tests/test_ocr.py`（10 个用例，只测不需 GPU 的部分 ——
MinerU 实跑要占显卡 95 秒，放进默认套件会让测试随显卡占用时红时绿）。

# 附：知识库数据增强的实测结论（2026-09-20）

清单要求「知识库数据增强：提高召回率，摘要，父子块，改写，扩写，知识库优化：去重，删除低质量的文档」。
**先测量再动手，结果三项里两项被实测否决**：

| 项 | 实测 | 结论 |
|---|---|---|
| **去重** | kb_legal 14319 条中**完全相同 0 条、前 60 字相同 0 条**；kb_medical 636 条同样 0 | ❌ **无价值**，语料本来就很干净 |
| **删除低质量文档** | kb_legal 有 654 条 <50 字的短块（4.6%） | ❌ **会删掉合法内容**，见下 |
| **父子块** | kb_legal 仅 **6/14313** 个条文被切成多块；kb_medical 有 **112/113** 页被切成多块 | ⚠️ 仅医疗侧有场景；本次未实现 |
| **摘要** | summary 字段建表时就有，但一直是空的 | ✅ **已实现并跑完** |

## 为什么「按长度过滤短块」是错的

抽样 12 条 <50 字的块，**全都不是垃圾，是完整的短条文**：

> 《中华人民共和国民法典》第一百零五条规定，非法人组织可以确定一人或者数人代表该组织从事民事活动。
> 《中华人民共和国广告法》第十三条规定，广告不得贬低其他生产经营者的商品或者服务。

**按长度过滤会删掉 654 条合法条文。** 长度不是质量的代理指标 ——
法条天然有长有短（「本法自公布之日起施行」就是一条完整的法条）。

## 摘要实现

`scripts/build_summaries.py`：为每个 chunk 生成一句话摘要（≤50 字），写入 Milvus 的 `summary` 字段。

| 项 | 值 |
|---|---|
| 实测速率 | **1.57 条/秒**（qwen2.5:7b） |
| kb_medical 636 条 | **400 秒**，已完成 |
| kb_legal 14319 条（预估） | **约 2.5 小时**，未跑 |

**摘要不参与检索打分** —— 检索仍用正文的 dense + sparse 向量。
它的用途是前端展示来源时便于速览。（要让摘要参与检索需额外的摘要向量字段，那是另一件事。）

**幂等**：脚本只处理 `summary == ""` 的 chunk，重跑不会重复生成。
