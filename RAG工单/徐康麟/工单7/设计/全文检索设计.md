## 二、倒排索引结构

### 2.1 数据结构（`FulltextIndex`，`fulltext_query.py:442-520`）

```python
@dataclass(slots=True)
class FulltextIndex:
    index_dir: str                                       # 来源 bundle 的索引目录（缓存键）
    chunk_ids: list[str]                                 # 行号 → chunk_id（== bundle.order）
    postings: dict[str, dict[str, list[int]]]            # 字段 → 词项 → 行号列表（升序）
    field_tokens: dict[str, list[list[str]]]             # 字段 → 行号 → 该行 token 序列
    vocab: dict[str, set[str]]                           # 字段 → 词表（= postings 的键集合）
    built_ms: float                                      # 构建耗时（实测值，见 §2.4）
```

* **行号（row）是唯一内部坐标**：`postings` 存行号而非 `chunk_id`，整数集合运算比字符串快得多；
  对外返回前用 `idx.chunk_ids[row]` 换回 `chunk_id`。
* `postings[field][term]` 是**升序 int 列表**（按构建时的行序遍历自然有序），
  集合运算时用 `set(...)` 包一层（`rows_with_term()`，`:498`）。
* 三张表都是**内存态派生结构**，**不落盘、不改动既有索引文件**。

### 2.2 构建（`FulltextIndex.build()`，`:454-487`）

```
chunk_ids = [str(cid) for cid in bundle.order]              # 2676 条
for name in ("content", "title", "keywords", "summary"):
    rows = []
    for row, cid in enumerate(chunk_ids):
        if name == "content":
            toks = bundle.bm25.doc_tokens[row]              # ★ 零额外分词开销
        else:
            toks = tokenize(field_text_of(chunk, name))     # 现场分词
        rows.append(toks)
    for row, toks in enumerate(rows):
        for term in set(toks):                              # 行内去重
            postings[term].append(row)                      # 行号升序
    index.field_tokens[name] = rows
    index.postings[name] = postings
    index.vocab[name] = set(postings)
```

**关键设计**：`content` 字段的 token **直接复用** `bundle.bm25.doc_tokens`
（工单4 建 BM25 索引时已分词，行序与 `bundle.order` 一致）⇒ 正文倒排表**零额外分词成本**；
其余三个字段现场分词。这也保证了「全文检索的正文 token」与「BM25 的文档 token」**逐条同口径**。

### 2.3 缓存（`get_fulltext_index()`，`:772-781`）

* 缓存键 = `bundle.index_dir`；进程内单例，构建一次多次复用。
* 缓存命中条件还要求 `all(f in cached.postings for f in fields)`
  —— 若先按 1 个字段构建、后请求 4 个字段，会**重建全量**（4 字段一起建）。
* `clear_fulltext_cache()`（`:784`）供测试与索引重建后调用。

### 2.5 单词条查询与模糊扩展

| 方法 | 签名 | 说明 |
| --- | --- | --- |
| `rows_with_term(term, field_name)` | `-> set[int]` | 取某字段下该词项的全部行号；不存在时返回空集 |
| `fuzzy_expand(term, *, field_name, max_distance=1, limit=8)` | `-> list[str]` | 词表内编辑距离 ≤ `max_distance` 的近词 |

`fuzzy_expand` 的实现细节：

1. 先按**长度差**剪枝：`abs(len(candidate) - len(term)) > max_distance` 直接跳过；
2. 再用 `_bounded_edit_distance()`（带上界的编辑距离 DP）算精确距离；
3. 排序键为 `(距离, -词频, 词)`（`:518`：`scored.append((dist, -len(postings.get(candidate, ())), candidate))`
   ⇒ 同距离时**词频高的优先**，再同则按词项字典序）。因此 `军用~` 返回的是
   「费用 / 应用」这类高频近词，而不是词形最像的词；
4. 取前 `limit` 个（默认 8，`DEFAULT_FUZZY_LIMIT`）。

实测（词表 23607）：

| 查询词 | 扩展结果（前 8） | 词表中真实 ED==1 的候选总数 |
| --- | --- | --- |
| `军用` | 费用、应用、军方、使用、军队、采用、信用、适用 | **58** |
| `发行` | 发行人、发展、执行、发生、履行、发货、运行、银行 | **60** |
| `比例` | 比较、比重、比率、为例、条例、比如、比均、图例 | **20** |

> 正确性校验：用**无界** Levenshtein DP 逐词对照全部 23607 个词项，
> `_bounded_edit_distance()` 在 `limit=1/2` 下与无界结果**零不一致**
> （既不漏判也不误判）。即「带下界的提前退出」是保守的，不影响结果正确性。

## 三、查询 DSL 语法表

| 写法 | 语义 | 实测 AST | 实测布尔命中数（语料 2676 块） |
| --- | --- | --- | --- |
| `甲 乙` | 默认运算符（`fulltext_op`，默认 `OR`） | `(军用 OR 发行)` | —— |
| `甲 AND 乙` / `甲 && 乙` / `甲 且 乙` | 布尔与 | `(项目 AND 军用)` | **0**（因 `项目` 是 OOV，见 §6.1） |
| `甲 OR 乙` / `甲 \|\| 乙` / `甲 或 乙` | 布尔或 | `(项目 OR 军用)` | **55** |
| `NOT 甲` / `-甲` | 布尔非 | `NOT 军用` | **0**（纯负查询守卫，见 §6.2） |
| `非 甲`（**必须带空格**） | 布尔非（中文写法） | `NOT 军用` | 0（同上） |
| `NOT NOT 甲` | 双重否定 ⇒ 还原为正向查询 | `军用` | 55 |
| `甲 AND NOT 乙` | 非纯负查询 ⇒ 正常求值 | `(军用 AND NOT 领域)` | 30 |
| `非甲`（**无空格，不生效**） | 整体作为一个词项 `非甲`；该词不在词表 ⇒ OOV、0 命中。**不会**被解析成 `NOT 甲` | `军用`（实测：`非军用` → AST `军用`、55 命中 —— 因为 jieba 把 `非军用` 切成 `非`+`军用`，`非` 被停用词/长度过滤丢掉，只剩 `军用`） | 55（`非军用`） |
| `(甲 OR 乙) AND 丙` | 括号分组；优先级 **NOT > AND > OR** | `((甲 OR 乙) AND 丙)` | —— |
| `"发行股数"` | 短语匹配：分词后要求在同一字段的 token 序列中**位置相邻** | `"军用领域"` | **15** |
| `军用~` / `军用~1` | 模糊匹配：词表内编辑距离 ≤1 的近词扩展 | `军用~1` | **880** |
| `标题:发行股数` | 字段限定，字段 ∈ `正文`/`标题`/`关键词`/`摘要`（及英文别名） | `title:军用` | **7** |
| `内容:军用` / `正文:军用` | 同上，`content` 的中文别名 | `军用`（`content` 是默认字段 ⇒ 描述串省略前缀） | 55 |
| `"标题:发行股数"` | 字段限定的**短语**：引号包住「字段:值」整体 | `title:"军用"` | **7** |
| `标题:"发行股数"` | 字段限定的**短语**（字段前缀紧邻引号）—— **已支持**，见 §3.1 第 4 条 | `title:"军用"` | **7** |

### 3.1 语法细则与陷阱

1. **冒号两侧不能有空格**。`_FIELD_PREFIX_RE = ^([\u4e00-\u9fffA-Za-z_]+)\s*:\s*(.+)$` 在**单个 token 内**匹配，
   而 `_tokenize_query()` 先按空白切词 ⇒ `标题 : 发行股数` 会被切成 3 个 token，字段限定**失效**，
   退化成三个普通词项（不会报错）。规范写法：`标题:发行股数`。
2. **运算符大小写不敏感**：`_tokenize_query()` 对 ASCII token 一律 `.upper()`，故 `and` / `And` / `AND` 等价；
   中文运算符（`且`/`或`/`非`）**必须独立成词**（两侧有空白或括号）。
3. **`-甲` 的前导减号被拆成 `NOT`**（`while work.startswith("-")`，`:237`），支持 `-甲 -乙`。
4. **处理顺序不可颠倒**（`_term_from_literal()`，`:263-297`）：
   引号（短语）→ `~N`（模糊）→ `字段:`（字段限定）→ 分词分析。
   **`字段:"短语"` 已支持（评审后修正）**：`_tokenize_query()` 在遇到引号时会回看缓冲区，
   若缓冲区内容形如 `字段:`（`_FIELD_PREFIX_ONLY_RE`）就把「字段 + 引号串」合成**一个** token，
   于是 `_term_from_literal()` 能正常解析出 `Phrase(field='title')`。
   修正前它会被切成 `标题:` 与 `"军用"` **两个** token、退化成 `(标题 OR "军用")`（实测命中 662，正确应为 7）——
   这是「字段限定被静默丢掉」的隐蔽缺陷，现已修复并写入回归测试
   （`研发/tests/test_fulltext_query.py`）。
   **两种写法都等价且都推荐**：`"标题:军用"`（引号包住整体）与 `标题:"军用"`（前缀紧邻引号）。
5. **多余 token 不静默丢弃**：`_Parser.parse()`（`:332-338`）若解析完还有剩余 token，
   会把剩余部分按 OR 并入（注释原文：「按 OR 兜底并入，绝不静默丢弃」）。
6. **引号必须成对**（实测）：

   | 写法 | AST | 布尔命中 | 说明 |
   | --- | --- | --- | --- |
   | `"军用领域"` | `"军用领域"` | 15 | 正常短语 |
   | `"军用领域`（只有前引号） | `"军用领域"` | 15 | 前引号吃到串尾 ⇒ 仍按短语处理，**不报错** |
   | `军用领域"`（只有后引号） | `((军用 OR 领域) OR "")` | 205 | 后引号切出一个**空短语** `""`，意外扩大召回 |

   即：**孤立的后引号会产生空短语**（`""`），把结果集并成整库。请务必成对书写。

### 3.2 查询分析（analyzer）—— **本模块最容易踩的坑**

> **设计要点（实测踩过一次，必须写明）**：
> 查询侧若不做与文档侧**同口径**的 jieba 分词，中文自然语言问句（无空格、无运算符）
> 会整体变成一个「词」去查倒排表 ⇒ **恒定 0 命中**。

代码位置：`_analyze_text()`（`:245-260`），被 `_term_from_literal(analyze=True)` 调用。

实测对照（问句：`本次发行股数是多少，占发行后总股本的比例是多少？`）：

| `analyze` | AST / 词项 | 布尔命中行数 |
| --- | --- | --- |
| `False`（整串查表） | `本次发行股数是多少，占发行后总股本的比例是多少？`（**1 个词项**） | **0** |
| `True`（默认，jieba 同口径） | `(发行 OR 股数 OR 多少 OR 股本)` | **285** |

原文示例中的分词结果（模块 docstring 第 251 行写的是
`发行 / 股数 / 发行 / 后 / 总股本 / 比例 / 多少 …`）与本机实测**略有差异**：
实测 `tokenize()` 结果为 `发行 / 股数 / 多少 / 股本`
（`本次`、`比例`、`是多少`、`总股本` 中的部分被 `STOPWORDS` 过滤或按 jieba 切法不同）。
**以实测为准**：4 个正向词项、285 行命中。

退化策略：分词结果为空（例如纯符号、单字）时，保留**整串**作为唯一词项（`:258-260`），
避免把用户输入静默丢掉。

> `parse_fulltext_query(..., analyze=False)` 是有意保留的开关，
> 用于「精确词项匹配」（测试与调试），策略层不会用到它。

## 四、多字段口径

### 4.1 字段 → 取块哪部分文本（`field_text_of()`，`:422-439`）

| 字段 id | 中文名 | 提取规则 | 性质 |
| --- | --- | --- | --- |
| `content` | 正文 | 块的 `content` 字段全文；**不现分词**，直接复用 `bm25.doc_tokens[row]` | 权威（与 BM25 完全同口径） |
| `title` | 标题 | ① 正文中匹配 `\[(表标题\|图标题\|标题)\]\s*(.+)` 的行；② 无匹配则取块的 `section`；③ 再没有则取 `content` 第一行前 60 字 | **派生近似**，非人工标注 |
| `keywords` | 关键词 | 块的 `keywords` 列表 + 正文中正则 `\d[\d,\.]*%?` 匹配到的**前 80 个数字串** | **派生近似**（数字串是为提升数字型提问召回，工单4 依据） |
| `summary` | 摘要 | `content[:220]`（前 220 字符） | **轻量近似，不是人工摘要** |

别名（`FIELD_ALIASES`，`:64-69`）：`正文`/`内容`/`content`/`body` → `content`；
`标题`/`title`/`name` → `title`；`关键词`/`关键字`/`keywords`/`keyword` → `keywords`；
`摘要`/`summary`/`abstract` → `summary`。

### 4.2 默认字段集合与默认加成

| 项 | 默认值 | 说明 |
| --- | --- | --- |
| `DEFAULT_FIELDS` | `("content",)` | 工单最低需求是「只对正文检索」；**策略层默认走这一档** |
| `DEFAULT_FIELD_BOOSTS` | `{"content": 1.0, "title": 1.35, "keywords": 1.20, "summary": 0.90}` | 正文为基准 1.0；标题/关键词加权，摘要**降权** |

> `fulltext_query.search_fulltext` 的 `fields` 参数默认就是 `DEFAULT_FIELDS`（只有正文），
> 但 `FulltextIndex.build` 的 `fields` 默认是**四个字段全建**（`:455`）。
> 即：索引总是全字段的，检索用哪几个字段由调用方决定。

### 4.3 字段加成的实测倍率

问句 `军用`，分别用单字段与四字段检索同一个块，比较 `content` 基准分：

| chunk_id | content | title | keywords | summary | 四字段 | 实测倍率 |
| --- | --- | --- | --- | --- | --- | --- |
| `pdf1-p480-x1` | 6.82450314 | 未命中（`None`） | 8.18940377 | 6.82450314 | 8.18940377 | keywords **×1.20** |
| `pdf1-p485-x0` | 6.18849879 | 8.35447337 | 未命中 | 6.18849879 | 8.35447337 | title **×1.35** |

结论：字段加成**逐位生效**，取值 = 该块命中字段中的**最大加成**（不是累乘）。
`summary` 加成 0.90 因被 `content` 的 1.0 取 max 而观察不到（同一块只要正文命中即回到 1.0）。
`row_boost` 只在 `need_boost` 为真（即 `fields` 中存在加成 ≠ 1.0 的字段）时才计算（`:734`）。

## 五、打分口径

### 5.1 公式（`search_fulltext()`，`:659-765`）

```
① 布尔过滤：rows = evaluate_query(AST)                # 集合运算，得到候选行集合
② 基础分  ：base(row)  = PureBM25.get_scores(正向词项)[row]
③ 字段加成：boost(row) = max{ DEFAULT_FIELD_BOOSTS[f] | f ∈ fields 且 row ∈ postings[f][t], t ∈ 正向词项 }
④ 短语加成：若 row 命中任一短语 ⇒ ×1.1
⑤ value   = base × boost × (1.1 if 短语命中 else 1.0)
⑥ 保底    ：若 value ≤ 0（布尔命中但 BM25 为 0，例如仅模糊扩展命中）
            ⇒ value = 1e-6 × boost
⑦ 阈值    ：score_threshold > 0 时按**绝对分**裁剪（默认 0，不裁剪）
⑧ 排序取前 top_k
```

BM25 本体（工单4 `bm25_index.py::PureBM25`）：
`idf = ln(1 + (N - df + 0.5)/(df + 0.5))`，`k1 = 1.5`，`b = 0.75`
（`研发/data/index/bge-m3_1024/bm25.meta.json` 实测：`count=2676`、`vocab_size=23607`、
`k1=1.5`、`b=0.75`、`avg_doc_len=125.9`、`use_jieba=true`、`table_chunks=618`）。
BM25 只遍历**含查询词的文档**（倒排表驱动），不倒排全库。

### 5.2 与 工单4 `BM25Index.search` 的差别

| 能力 | 工单4 `BM25Index.search` | 工单6 `search_fulltext` |
| --- | --- | --- |
| 查询解析 | `tokenize(query)`，隐式 OR（无语法） | 完整 DSL：布尔 / 短语 / 模糊 / 字段限定 / 括号 |
| 多字段 | 无（只有正文 token） | 4 字段 + 字段加成 |
| 短语邻近 | 无 | 有（×1.1） |
| 模糊匹配 | 无 | 有（词表内 ED ≤ N） |
| 分数阈值 | 无 | 有（`score_threshold`，绝对分口径） |
| 诊断输出 | 无 | `diag` 出参：`query_ast` / `positive_terms` / `boolean_hits` / `fuzzy_expansions` / `oov_terms` / `phrases` / `notes` / `fields` |
| 打分 | `bm25.get_scores(query_tokens)` | `bm25.get_scores(正向词项)` × 字段加成 × 短语加成 |

> `search_fulltext` 的 `score_threshold`（绝对分裁剪）**策略层不使用**
> —— 策略层只把 `StrategyConfig.score_threshold` 用在自己的最后一步（归一化相对口径）。
> 两者同名但口径完全不同，见 `检索策略配置.md` §4。

| 查询 | 字段数 | 5 次耗时（ms） | 中位（ms） | 布尔命中 |
| --- | --- | --- | --- | --- |
| `军用` | 1 | 0.44 / 0.27 / 0.33 / 0.24 / 0.23 | **0.27** | 55 |
| `军用` | 4 | 0.25 / 0.25 / 0.23 / 0.25 / 0.23 | **0.25** | 55 |
| `军用领域 收入 比例` | 1 | 1.14 / 1.01 / 1.03 / 1.05 / 1.01 | **1.03** | 560 |
| `军用领域 AND 收入` | 1 | 0.49 / 0.66 / 0.82 / 0.91 / 0.72 | **0.72** | 30 |
| `军用~` | 1 | 38.65 / 39.50 / 39.15 / 39.77 / 37.40 | **39.15** | 880 |

### 5.4 性能纪律：字段加成**不能**写成 `row in postings[term]`

模块内 `:728-743` 的注释原文记录了这次踩坑：

```
⚠️ 性能纪律（实测踩过一次）：**不要**写成 `for row in rows: row in postings[t]` ——
postings 的值是 list，`in` 是 O(n)，常见词（如「发行」）有上千个命中行，
于是退化成 O(行数 × 词项数 × 命中数) ≈ 千万级比较。改为**正向遍历倒排表累积**。
```

| 写法 | 复杂度 | 量级估计（本例：2676 行、4 字段、常见词上千命中行） |
| --- | --- | --- |
| `for row in rows: term in postings[field][term]`（list 线性查找） | `O(rows × terms × postings_len)` | 2676 × 4 × ~1000 ≈ **千万级**比较 |
| **正向遍历倒排表**（现行实现） | `O(Σ_{term} postings_len(term))` | ≈ **万级**（命中数之和），且与 `rows` 大小无关 |

现行实现（`:736-742`）：

```python
for name in fs:                                  # 只遍历选定字段
    boost_value = float(boosts.get(name, 1.0))
    postings = idx.postings.get(name, {})
    for term in term_set:                        # 正向词项集合
        for row in postings.get(term, ()):       # 正序遍历倒排表
            if row_boost.get(row, 1.0) < boost_value:
                row_boost[row] = boost_value     # 保留最大加成
```

并且只在 `need_boost`（存在 ≠1.0 的字段加成）时才做这一步 —— 默认单字段 `content`（加成 1.0）
的情况下这段循环**整段跳过**，即默认配置下零额外开销。

## 六、已知限制（**如实登记**）

### 6.1 停用词导致词表外词项（OOV）—— 必须显式告知用户

`研发/app/core/text_utils.py:37-45` 的 `STOPWORDS` **刻意停用了若干表格高频词**：
`项目`、`公司`、`本次`、`比例`、`名称`、`合计`、`小计`、`序号`、`金额`、`占比`、`万元`、`年`、`月`、`日` …
这些词**不在 23607 词的倒排词表里**（分词阶段就被过滤掉了）。

后果（实测）：

| 查询 | 结果 | `oov_terms` |
| --- | --- | --- |
| `项目` | **0 命中** | `['项目']` |
| `项目 军用`（默认 OR） | 命中 55（`军用` 那一路的效果） | `['项目']` |
| `项目 AND 军用` | **0 命中**（AND 上 OOV 必然空集） | `['项目']` |
| `军用` | 命中 55 | `[]` |

**机制的显式留痕**（三层，绝不静默）：

1. `FulltextEvalResult.oov_terms`（`:563`）收集词表外词项；
2. `search_fulltext` 的 `diag["oov_terms"]` 回传，并写 `fulltext.oov_terms` **WARNING 日志**（`:705-708`）；
3. 策略层 `search_by_strategy` 把 OOV 追加进 `notes`（`retrieval_strategy.py:532-536`）：
   `全文通道词表外词项：项目（分词停用词或语料中不存在；若该词参与 AND 约束会导致 0 命中）`。

> 这是**真实约束**，不是可绕过的细节：用户问「本次发行股数是多少」时，
> `本次`/`比例` 这类词天然查不到；系统必须告诉用户「哪些词查不到、为什么」，
> 而不是让用户看到「查不到」却不知道为什么。

### 6.2 纯负查询：**守卫已修复（评审发现 → 已实施修复）**

**代码的设计意图**（模块 docstring + `evaluate_query` 的守卫）：

> 「纯负查询（如只输入 `NOT 军用`）在倒排语义下会命中几乎全库，无检索意义 ⇒
> 本实现返回空结果并在 `notes` 中说明，**不静默返回全量**。」

**评审时实测：守卫不触发（已修复）**。原因：早期 `walk()` 在求值 `Not` 节点时会先递归
`walk(cur.child)`，而 `Term` 分支**无条件**把词项追加进 `result.positive_terms`，
没有排除「该词项位于 NOT 子树内」的情况 ——
`Not.positive_terms()` 返回 `[]` 的本意被这个副作用绕过了。
于是守卫条件 `not result.positive_terms` 恒不成立，
`NOT 军用` 返回 **2621/2676** 行、全部 `score = 1e-6`、排序退化为 `chunk_id` 字典序。

**修复方式**：`walk()` 增加 `negated: bool = False` 参数；
`Not` 分支用 `walk(cur.child, not negated)` 翻转，
`Term` / `Phrase` 分支仅在 `not negated` 时收集词项与短语。
（同时修复了双重否定：`NOT NOT 甲` 的 `negated` 翻回 `False`，词项被正常收集。）

| 查询 | AST | `positive_terms` | `rows` | 返回条数（`top_k=5`） |
| --- | --- | --- | --- | --- |
| `NOT 军用` | `NOT 军用` | `[]` | **0** | **0**（`notes` 说明原因） |
| `-军用` | `NOT 军用` | `[]` | 0 | 0 |
| `非 军用` | `NOT 军用` | `[]` | 0 | 0 |
| `NOT NOT 军用` | `军用` | `['军用']` | 55 | 5 |
| `军用 AND NOT 领域` | `(军用 AND NOT 领域)` | `['军用']` | 30 | 5 |

**影响与结论**：
* 纯负查询现在**确实返回空**，并在 `notes` 里给出中文原因，符合「不静默」的设计意图；
* 非纯负查询（含至少一个正向词项）不受影响，`AND NOT` / 双重否定行为正确；
* 修复已写入回归测试：`研发/tests/test_fulltext_query.py` 覆盖
  `NOT` / `-` / `非` 三种纯负写法与双重否定、`AND NOT` 两类正常写法。

### 6.3 `title` / `keywords` 是派生近似，不是人工标注

| 字段 | 派生方式 | 后果 |
| --- | --- | --- |
| `title` | `[表标题]/[图标题]/[标题]` 行 → `section` → 正文首行 60 字 | 实测页眉块会退化成「武汉兴图新科电子股份有限公司 招股意向书 声 明 中国证监会…」这样的长串（**不是**一个干净的标题） |
| `keywords` | 块的 `keywords` 列表 + 正文前 80 个数字串 | 「关键词」含大量数字串，字面命中的语义价值有限 |
| `summary` | `content[:220]` | 只是截断，不是摘要；截断处可能切断句子 |

因此多字段检索的价值主要在**召回面的扩大**（数字型提问靠 `keywords` 命中），
而不是「标题字段一定更准」。**不得声称**这四个字段是文档结构里的权威字段。

### 6.4 其他边界

| 边界 | 行为 |
| --- | --- |
| 未知字段名传入 `fields` | `raise ValueError(f"未知字段：{name!r}（可选：content, title, keywords, summary）")`（`:687-689`） |
| 空查询 / 纯符号 | `parse_fulltext_query` 返回 `None` ⇒ `evaluate_query` 记 `notes=['空查询']` ⇒ 0 命中 |
| `allowed_ids` 与索引无交集 | 布尔命中集被过滤为空 ⇒ 直接返回 `[]`（不报错） |
| 布尔命中但 BM25 为 0 | 保底 `1e-6 × boost`（保证「能被检索到」而不是被丢分丢掉） |
| `fields` 中传入顺序 | 第一个字段成为 DSL 的**默认字段**（`parse_fulltext_query(default_field=fs[0])`）⇒ `fields=("title",...)` 时裸词默认查标题 |

## 七、与 `rank_bm25` / `Whoosh` 的对照

| 能力 | `rank_bm25` | Whoosh | 本实现 | 是否等价 |
| --- | --- | --- | --- | --- |
| BM25 打分 | ✅（BM25Okapi / BM25L / BM25Plus） | ✅ | ✅（自实现 Okapi：k1=1.5, b=0.75，工单4 同源） | **等价**（同族公式；本项目用固定 k1/b，不做参数扫描） |
| 倒排索引 | ❌（每次全量算分） | ✅（磁盘索引 + 分段） | ✅（内存 postings，行号 int 列表） | 功能等价；**本实现不落盘、不持久化**，重启需重建（实测 5.0 s） |
| 布尔查询（AND/OR/NOT） | ❌ | ✅（`And`/`Or`/`Not` 查询对象或 `queryparser`） | ✅（自写递归下降解析器 + DSL） | **等价**（语法不同：本实现用 `甲 AND 乙` 文本 DSL，Whoosh 用对象或 `+`/`-` 语法） |
| 短语匹配（位置邻近） | ❌ | ✅（位置索引） | ✅（`field_tokens` 里做连续切片比较，未建位置索引） | 功能等价；**本实现无位置倒排**，短语匹配是「按行全量扫 token 序列」，长文档多时会慢 |
| 模糊匹配（编辑距离） | ❌（只有词干/停用词过滤） | ✅（`FuzzyTerm`，有 DFA/前缀优化） | ✅（词表全扫 + 有界 ED + 长度剪枝，实测 40 ms） | 功能等价；**性能远不如 Whoosh**（Whoosh 用 Levenshtein automaton，本实现是暴力扫描） |
| 多字段 | ❌（需自己拼 token） | ✅（`Schema` 多字段 + `fieldname:` 语法） | ✅（4 字段 + 字段加成 + `字段:` 语法） | **等价**，且本实现的字段加成是显式可配的 |
| 查询分析器（中文分词） | ❌（需外部先分词） | 需配 `ChineseAnalyzer`（`jieba` 插件） | ✅（与文档侧**同一** `tokenize()`，见 §3.2） | **等价**，且「查询侧与文档侧同口径」是硬保证 |
| 结果可解释性 | 只有分数 | 有 `hit.highlights()` 等 | `diag` 出参 + 策略层 `notes`（含 OOV 提示） | **本实现更贴合本项目的「绝不静默」纪律** |
| 依赖代价 | 需安装（本机装不上） | 需安装（本机装不上） | **零新依赖**（复用 jieba + 自实现 BM25） | —— |

**为什么自实现**：`rank_bm25` / `Whoosh` **在本机装不上**（§1），
且 `pip install --target` 会挂死；同时工单4 已经自实现并验证过 BM25（2676 块 / 词表 23607），
在其上补布尔/短语/模糊/多字段比引入不可用依赖更可靠。

**能力是否等价**：**功能面等价（布尔 / 短语 / 模糊 / 多字段 / BM25 都有）；
工程面不等价**（无磁盘索引、无位置索引、模糊匹配为暴力扫描、无高亮）。
不得写成「等同于 Whoosh」。
