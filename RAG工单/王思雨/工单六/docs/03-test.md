### 2.1 测试中暴露并修掉的问题

| # | 问题 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | 短语匹配永远返回 0 条 | `"本次股票发行后拟在科创板上市"` 命中 0 | 纯短语查询解析后**没有词项**，BM25 在应用短语掩码前就提前返回空 | 把短语内容也加进打分词项 |
| 2 | 模糊匹配永远返回 0 条 | `程加明~` 命中 0 | ① 纯模糊查询同样"无词项"提前返回；② 原实现拿查询词去比对 27019 条分词词表，而 **jieba 把「程家明」切开了，词表里压根没有这个词**，且 3 字人名错 1 字的 ratio 只有 66.7（低于阈值 80） | 改为在**块正文**上做近似子串搜索（`partial_ratio`），并把阈值调到 65 |
| 3 | `rerankers=[]` 无法关闭重排 | 传空列表与传 `["bge"]` 结果完全相同 | `rerankers or DEFAULT_RERANKERS` —— 空列表是 falsy，被兜回默认值 | 改为 `is None` 判断：显式传 `[]` 就是"不重排" |
| 4 | 用户 topK 过小会把金标挤出重排 | `top_k=8` 时正确片段答不出来 | `retrieve` 把用户 `top_k` 同时当成了**融合池大小**，正确片段融合后排第 10，没进重排就被砍 | 融合池固定为 `FUSION_TOP_K=30`，`top_k` 只控制最终返回条数 |
| 5 | 页眉噪声霸占向量召回前排 | 14 字的「武汉兴图新科电子股份有限公司」相似度 0.743 排第一 | 页眉与表格「单位：万元」标注被 MinerU 标成 `text`，成批重复 | 入库时丢弃"长度<40 且重复≥3 次"的块（实测丢 108 块，全是噪声） |
| 6 | MinerU「明明成功却被判失败」 | 实跑 MinerU 返回 False | MinerU 实际产物在 `<out>/<名>/<名>/hybrid_auto/`，而代码写死了旧版 `.../auto/` 路径 | 改为 `rglob` 递归查找 |
| 7 | MinerU 中文用户名下报错 | `lid.176.ftz cannot be opened` | langfix 目录里放的是 `sitecustomize.py`，**必须挂进子进程 PYTHONPATH** 才会被导入；只设 `MINERU_LANGFIX_DIR` 无效 | 子进程 env 注入 PYTHONPATH |

### 3.3 水印污染：第一次排查漏判，第二次才查实

**第一次排查（漏判）**：我只按"仅供/下载/水印/www/侵权"等常见水印词扫描 corpus，命中数为个位数，于是判断"本数据集无水印污染"。
**这个判断是错的**——因为**水印词表猜错了**：这两份 PDF 的水印是机构名「**八维教育人工智能**」再叠下载者姓名，斜向铺满页面。

**第二次排查（查实）**：在挖掘问答素材时，我注意到表格单元格里混着 `rengongzn`、`gliua`、`iumin`、`八维教` 这类碎片，
回头一查才发现：

| 检查项 | 结果 |
|---|---|
| 含「八维」的块 | 54 块，**逐条核实全部是水印插入，无一处合法用法** |
| 含紧邻汉字的拼音碎片 | 774 处 / 305 种（`in` `umin` `reng` `eng` `iumin` `ming` …） |
| **表格块含水印特征** | **261 / 686 = 38.0%** |

破坏形式（水印碎片会**把词切断**）：
```
招股意向书      →  招liumi股意向书        ← 词被劈开，BM25 精确匹配与向量语义同时受损
预计发行日期    →  预计发行日期Liumin
2,886.29        →  八维2,886.29
270.00          →  270.00八维教
```

**清洗规则（词表实测得出，不是猜的）**：只删两类**可确证**的成分——
① 机构名 `八维/八维教/八维教育/八维人工智能`；
② **整段全小写、且紧邻汉字**的 ASCII 串（拼音碎片）。

**为什么只删"整段全小写"**：首版规则写成"紧邻汉字的小写串就删"，实测发现它会削掉**合法英文单词的尾巴**——
`Sony等`→`S等`、`Linux进程`→`L进程`、`Android终端`→`A终端`、`Web服务`→`W服务`（共 9 处误伤）。
改成"按整段 ASCII 串判断，整串全小写才删"后，误伤归零、命中数反而从 701 升到 748。
**为什么不删「教育/人工智能/敏」等中文碎片**：它们完全可能是正文里的合法词，误删代价高于收益。

**清洗效果（实测）**：

| 指标 | 清洗前 | 清洗后 |
|---|---|---|
| 含「八维」的块 | 54 | **0** |
| 表格块含水印特征 | 38.0% | **0.0%** |
| 合法英文（`Farnell`/`Mouser`/`Linux`/`Android`/`IC`/`ERP`/`(A股)`） | 保留 | **保留（零误伤）** |
| 总块数 | 2917 | 2915 |

**清洗对检索的实际影响（实跑 `tests/compare_modes.py` 前后对比）**：

| 配置（k=8） | 清洗前 recall / clean | 清洗后 recall / clean |
|---|---|---|
| hybrid + weighted + bge（默认） | 1.0000 / 0.7391 | **1.0000 / 0.7826** |
| vector + bge | 0.9565 / 0.7826 | 0.9565 / 0.7826 |
| bm25 + bge | 0.9565 / 0.6522 | 0.9565 / 0.6522 |

**如实结论**：水印**没有**伤到召回（`recall` 全程 1.0000 不变）——BM25 与向量对少量杂词是鲁棒的；
但它确实污染了上下文的"洁净度"，`clean` 提升 **+0.0435（23 题里 1 题翻转）**。
**这个幅度在 23 题规模下很小，只能说"不劣于清洗前"**，不足以宣称大幅改善。

**那为什么仍然要清洗？** 理由在**数据质量**而不在这次的端到端指标：
38% 的表格块存在**把词切断**的破坏（`招股意向书`→`招liumi股意向书`），
这类破坏在别的查询分布下（尤其是精确匹配专有名词/数字时）才会显形。
把已知的数据缺陷留在库里、只因为"这次指标没变差"，是拿将来的不确定性换眼前省事。

> **教训**：水印排查的关键不是"扫没扫"，而是**词表对不对**。这次是第二次排查（从数据反推词表）才发现，
> 第一次的"未检出"是**假阴性**。凡是"未检出"的结论，都要问一句"我的词表是怎么来的"。

## 4. 检索层精度对比（混合检索确实提升了召回）

```bash
D:/myconda1/python.exe tests/compare_modes.py
```

指标口径（两个指标必须分开看，混在一起会互相掩盖）：
- `recall`：标准答案的必需字段是否**全部**出现在 top-k 片段里；
- `clean`：在此基础上再要求**负样本字段一个都不出现**。注意 `clean` 会随 k 增大天然变差——上下文越长越容易混进无关内容，**这正是不能只用一个笼统命中率下结论的原因**。

| 模式 | 融合 | 重排 | k=4 recall | k=8 recall | k=8 clean |
|---|---|---|---|---|---|
| vector | — | 无 | 0.8261 | 0.8261 | 0.7391 |
| vector | — | bge | 0.9565 | 0.9565 | 0.7826 |
| bm25 | — | 无 | 0.6087 | 0.8261 | 0.5217 |
| bm25 | — | bge | 0.9565 | 0.9565 | 0.6522 |
| hybrid | weighted | 无 | 0.6957 | 0.8696 | 0.7826 |
| **hybrid** | **weighted** | **bge** | **1.0000** | **1.0000** | 0.7391 |
| hybrid | rrf | bge | 0.9565 | 0.9565 | 0.7826 |
| hybrid | vote | bge | 0.9565 | 0.9565 | 0.7826 |

**结论（三条，都是实测得出）：**

1. **混合检索最优**：`hybrid + weighted + bge` 在 k=4 与 k=8 上都拿到 **recall = 1.0000**，高于纯向量的 0.9565 与纯 BM25 的 0.9565。
2. **重排是刚需**：关掉重排后，hybrid 从 1.0000 掉到 0.8696，vector 从 0.9565 掉到 0.8261，bm25 从 0.9565 掉到 0.8261。工单要求的三个重排器不是装饰。
3. **融合算法之间有差别**：同样开重排，`weighted` 拿满分，`rrf` 与 `vote` 为 0.9565。

> **一次被推翻的错误结论（保留在报告里）**：最初我用"必需字段全含 **且** 负样本不出现"这一个合成指标对比，得到"混合 0.7391 < 纯向量 0.7826"，看起来混合检索**反而更差**。追下去发现是指标被污染：负样本判据会惩罚更大的上下文，而不同模式返回的上下文组成不同。拆开两个指标后结论反转。**教训：指标设计本身要能被质疑，不能拿一个数就下结论。**

### 4.1 重排预筛专项实验（候选池大小 × 截断阈值）

补做的一组调参实验，用来回答"级联重排的预筛阈值该怎么设"：

| 候选池 | 预筛阈值 | 重排器 | 金标命中率 | 单次检索中位耗时 |
|---|---|---|---|---|
| 30 | 12（截断） | tfidf + bge | **0.6087** | 341 ms |
| 30 | 不截断 | tfidf + bge | 0.7391 | 694 ms |
| 30 | — | 仅 bge | 0.7391 | 684 ms |
| 50 | 12（截断） | tfidf + bge | **0.6087** | 322 ms |
| 50 | 不截断 | tfidf + bge | 0.7391 | **1082 ms** |
| 80 | 12（截断） | tfidf + bge | **0.6087** | 325 ms |
| 80 | 不截断 | tfidf + bge | 0.7391 | 1182 ms |

（本表用与 `clean` 列同口径的确定性判分，故基准值 0.7391 低于 `recall` 列的 1.0000。）

**结论：扩大候选池对召回**毫无**帮助（三档池命中率完全相同），却让检索耗时上涨 50~70%；
唯一有害的是"截断"这个动作本身。** 详细归因、以及"如果将来真要预筛该怎么做"，
见专题文档 [`pitfall-tfidf-prescreen.md`](pitfall-tfidf-prescreen.md)。

## 5. 端到端问答与 RAGAS 评估

### 5.0 评估方法与口径（**先读这一节，再读数字**）

#### 5.0.1 本机 RAGAS 判官的噪声底为 **±0.044**（实测）

RAGAS 的四个指标全靠大模型判官打分，**判官本身有非确定性**。本项目实测到的噪声底：

| 对比 | 两轮实测 | 差值 |
|---|---|---|
| `context_recall` | 0.9565 vs 0.9130 | **0.0435** |
| `context_precision` | 0.8390 vs 0.8780 | **0.0390** |

**关键证据**：这两轮运行的**逐题检索上下文逐字比对结果是 23/23 完全相同**（`contexts` 数组一字不差），
也就是说喂给 RAGAS 的输入一模一样，输出却差了约 0.04。这只能来自判官模型的非确定性。

> 比对两轮 contexts 是否逐字相同，只要几秒钟，比"再跑一轮取均值"便宜得多——**应当作为比较任何"改前改后"之前的第一个动作**。
> 本项目在此之前差点把 `0.9565 → 0.9130` 误读成"加了预算兜底导致召回退化"。

#### 5.0.2 召回率口径：**已确认为分层**（单事实类达标 / 多期聚合类列为已知短板）

> **验收口径已于 2026-10-09 经验收方确认为分层**：单事实类满足工单 ≥95%；多期数据聚合类**列为已知短板**，
> 交方案 1 的独立迭代项处理。决定记录与复访触发条件见 `docs/acceptance-recall-alignment.md` §5。
> 本节保留完整推导过程与**未达标项**，避免口径确定后把过程一并抹掉。

工单要求召回率 ≥95%。**在 23 题的"单事实"题集上**，两轮实测为 **0.9565 与 0.9130**，跨在 0.95 两侧，噪声底 ±0.044。

**扩样到 114 题后，这个说法被推翻并要求修正**：真实情况不是"跨在 0.95 两侧"，
而是**召回率高度依赖问题类型**——

| 问题类型 | n | 确定性召回 | RAGAS `context_recall` |
|---|---|---|---|
| 单事实（数字型 / 专有名词型 / 手工题） | 66 | 0.90 ~ 1.00 | 0.25 ~ 1.00 |
| **多期数据聚合型（"各期分别…"）** | **44** | **0.5909** | **0.5909** |

即：**≥95% 的召回只在"单事实"这一类问题上成立；一旦要求把分散在多处的多期数据聚合齐，召回掉到约 59%。**
这是真实的检索短板（该行的确定性召回与 RAGAS 召回**完全相等**，说明不是判官噪声）。详见 §5.5。

**因此本报告按分层口径报告**：单事实类达标、多期聚合类**明确标注为未达标**（不是不报，是分类型报）。
两个口径的召回值及其测法全部列出，不做单点合并。

#### 5.0.2b **报任何 RAGAS 召回数字之前，先跑一遍确定性召回做对照**

这是本项目最便宜、也最容易被忽略的一道自检。两个指标口径不同、**不可合并**，
但**它们的差距本身就是诊断信号**：

| 确定性召回 vs RAGAS 召回 | 含义 | 该修什么 |
|---|---|---|
| **接近**（本例：跨段落型 0.5909 vs 0.5909） | 检索确实没凑齐信息 | **系统的账** → 改检索 |
| **差距大**（本例：专有名词型 0.7778 vs 0.2500） | 检索其实找到了，是 `reference` 写坏了 | **造题的账** → 改评测集 |

本例缺陷的具体形态：`reference` 被写成了**元陈述**——"招股说明书中提及「X」与某公司的客户/供应商关系"。
而 `context_recall` 衡量的是"`reference` 里的断言有多少能被检索上下文支持"，
**元陈述几乎不可能被原文片段逐字支持**，于是判官必然给低分。
→ **`reference` 必须是事实断言**（如"X 是该公司前五大客户之一"），不能写成"文档里提到了 X"。

**代价**：这个对照只要几秒钟（`expect` 字符串是否出现在 top-k 上下文里），
却能避免把"造题的错"当成"系统的错"去调检索——**先做这个对照，再决定要不要动系统**。

#### 5.0.3 各指标口径

| 指标 | 口径 | 是否有判官噪声 |
|---|---|---|
| 准确率 | 关键词判分：`expect` 全含 + `expect_any` 同义组至少一项 + `expect_not` 全不出现 | **否**（确定性） |
| 召回率 | RAGAS `context_recall` | 是（±0.044） |
| 检索层 recall / clean | `tests/compare_modes.py`，关键词判分 top-k 片段 | **否**（确定性） |
| faithfulness / answer_relevancy / context_precision | RAGAS | 是（±0.044） |

### 5.2 第一次评估暴露的问题（重要）

第一轮（`results/eval_20261009_141949.json`）四项指标只有 **6/23 条样本有效**，其余被静默打成 `nan`：

```
faithfulness 1.0 / answer_relevancy 0.9176 / context_precision 0.9161 / context_recall 1.0
n_samples 23, valid_samples 6     ← 均值其实只覆盖了 6 条
```

单独跑 `AnswerRelevancy` 一个指标时是 **23/23 全部有效**。也就是说：**四个指标混在一次 `evaluate()` 里跑，并发翻四倍后会有大量样本静默失败**，而 ragas 默认 `raise_exceptions=False` 不会报错。

**修复**：改成**逐指标串行评估**，一次只测一个指标；并且**分别上报每个指标各自的有效样本数**（`metric_valid`），避免"均值只覆盖少数样本"被掩盖。

### 5.3 最终成绩

以最终一次全量运行 `results/eval_20261009_152345.json` 为准：

| 指标 | 数值 | 有效样本 | 工单目标 | 判定 |
|---|---|---|---|---|
| **准确率**（关键词判分） | **1.0000**（23/23 全对） | 23/23 | ≥ 0.90 | **达标** |
| **召回率**（RAGAS context_recall） | **0.9130** | 23/23 | ≥ 0.95 | **本轮未达标** |
| faithfulness | 0.9638 | 23/23 | — | — |
| answer_relevancy | 0.9544 | 23/23 | — | — |
| context_precision | 0.8780 | 23/23 | — | — |
| 响应时间 p50 / p95 / max | 1530 / 2036 / 2116 ms | 23 题 | ≤ 3000 ms | **达标（0/23 超时）** |

**关于召回率必须说明的一点**：同一套题、同一份代码、**检索上下文逐字相同**的两次运行，`context_recall` 分别得到 **0.9565 与 0.9130**（差 0.0435），`context_precision` 分别得到 0.8390 与 0.8780（差 0.0390）。
输入完全一致而输出不同，说明这部分差异来自 **RAGAS 判官模型自身的非确定性**，本机该指标的噪声底约为 **±0.044**。

因此：**在 23 题的规模下，本项目无法证明召回率稳定 ≥95%**——它落在 0.913~0.957 之间，跨在目标线两侧。
要给出可信结论需把题集扩到 100 题以上以压缩标准误。本项目**不做"稳定达标"的声称**，只给出两个实测值及其噪声底。

作为补充口径，`tests/compare_modes.py` 提供的**确定性召回指标**（关键词判分、不经过大模型、可复现）在同一套题上为 **1.0000**。
两者口径不同（前者要判官逐句判断"回答所需的全部信息是否都在上下文里"，后者只查关键字段是否出现），**不矛盾，但不能混为一个数**。

### 5.5 扩样到 114 题的结案结果（召回率）

按评审建议做的扩样：`tests/questions100.json`，共 **114 题** = 子集A 手工自然题 23 道（原题集）+ 子集B 扩样探针 91 道。
探针题的 `ground_truth` 直接引用原文句子，`expect` 全部经程序校验必须真实存在于语料（校验不通过的一条未收）。

只用 `LLMContextRecall` 单项跑两轮（**该指标不需要生成答案**，只要 question/reference/contexts，因此省掉了全部生成开销）：

| 轮次 | context_recall | 有效样本 | 用时 |
|---|---|---|---|
| 第 1 轮 | **0.5789** | 114/114 | 433 s |
| 第 2 轮 | **0.5819** | 113/114 | 446 s |

两轮差 **0.003**——样本量从 23 提到 114 后，判官噪声对均值的扰动确实被压下来了（23 题时同样两轮差 0.0435）。

#### 5.5.1 但这**不是**同一次测量的置信区间收窄，必须拆开看

0.5789 这个总数**不能直接当作"召回率"**，它把三类性质不同的东西混在了一起：

| 类型 | n | 确定性召回（expect 是否出现在 top-8） | RAGAS `context_recall` | 判读 |
|---|---|---|---|---|
| 跨段落型（多期数据聚合） | 44 | **0.5909** | **0.5909** | **真实短板**：两者完全相等，检索确实没把多期数据凑齐 |
| 专有名词型（客户/供应商名） | 36 | **0.7778** | **0.2500** | **造题口径缺陷**：检索其实找到了实体（0.78），是 reference 写坏了（见下） |
| 手工自然题 | 23 | 0.9565 | 0.9130 | 与 23 题单跑结果**完全一致**（0.9130），验证测量可复现 |
| 数字型 | 7 | 1.0000 | 1.0000 | 正常 |
| 模糊指代型 | 4 | 1.0000 | 0.7500 | 样本太少，不足为据 |

#### 5.5.2 两处必须分开说清的结论

**① 一处是我造题的口径缺陷，不算系统的账。**
专有名词型探针的 `reference` 被我写成了**元陈述**——"招股说明书中提及「X」与某公司的客户/供应商关系"——
而 RAGAS 的 `context_recall` 衡量的是"reference 里的断言有多少能被检索上下文支持"。
元陈述几乎不可能被原文片段逐字支持，于是判官给低分。
**证据**：同批题的**确定性召回是 0.7778**（检索确实把实体捞回来了），而 RAGAS 只有 0.2500。
→ 该子集的 RAGAS 数字**无效**，不能用于任何达标判断；要修得重写 reference 为**事实断言**（如"X 是该公司前五大客户之一"）。

**② 一处是真实的检索短板，必须认。**
跨段落型的 44 道题（如"报告期内应收账款账面价值分别是多少？"，
答案是要 4 个期间的数字**同时**出现在上下文里）：
**确定性召回 = RAGAS 召回 = 0.5909**。两者相等，排除了判官噪声的可能——
**这是检索真的没把这些多期数字凑齐**（这些数据分散在跨页表格的不同块里，top-8 装不下）。

#### 5.5.3 修正后的召回率结论

> **召回到不到 95%，取决于问的是哪一类问题：**
> - **单事实类**（一个数字、一个人名、一个机构名）：召回 **0.91 ~ 1.00**；
> - **多期数据聚合类**（"各期分别是多少"）：召回 **0.5909**，**远低于 95%**。
>
> 因此**本报告不声称召回率达标**，更不给出"整体召回率 = 0.58"或"= 0.93"这类单点数字——
> 两者都是把不同性质的问题混在一起算出来的，会掩盖真实结论。

#### 5.5.4 补召回的**最小验证已做，结论是"补召回救不了"**

按"先定性、再最小验证、再决定要不要投入"的顺序，对多期聚合类问题做了两组规则版补召回原型（**全程不调 LLM**，避免顶穿 3 秒红线）：

| 变体 | 思路 | 触发题数 | 净增召回 | 结论 |
|---|---|---|---|---|
| A. 相邻块续接 | 假设句子被切块边界劈开，追加 `chunk_id ±1/±2` | — | **+1 / 19** | 无效 |
| B. 表格定向补召 | 多期意图下追加一次"限定 `block_type=table`"的 BM25 定向召回 | 35 / 44 | **+0 / 44** | 无效 |

另有一项**否证性**检查：19 道漏召回的题里，**18 道的缺失数字在 top-1 的相邻块里也不存在**——
排除了"只是没把续块带上"这一假设。

**按预设判据（提升显著→推广；不显著→方向要换），结论是：缺的不是补召回，是分块策略本身。**
机制上说得通：表格的**字段名表头与数值行被切进了不同的块**，
于是无论 BM25 还是向量，都无法让"字段名 + 多期数值"同时命中同一个块——
补召回补回来的块里依然没有缺失的数字。**这印证了"多期数据在 ingest 阶段就该按表聚合"的判断。**

#### 5.5.5 另需修正：0.5909 里有我自己的造题错误

进一步排查发现，跨段落型 44 题中有 **8 题是我的模板生成失败**（主题抽取产出废题）：

```
"武汉兴图新科电子股份有限公司，公司分别是多少？"      ← 无主题
"武汉兴图新科电子股份有限公司，相关金额分别是多少？"    ← 主题是"相关金额"
"武汉力源信息技术股份有限公司，产能较分别是多少？"      ← 主题被截断
```

按"题面成立且答案数字确在语料内"筛出有效题后重算：

| 口径 | 确定性召回 |
|---|---|
| 全部 44 题（含 8 道废题） | 0.5909 |
| **仅有效题 38 道** | **0.6579** |

**即：短板是真的（0.66 仍远低于 95%），但 0.5909 这个数字被我的废题放大了。** 两个数都列出，不取好看的报。

#### 5.5.6 改进方向（本次**不做**，属独立工作量）

补召回已被否证；正确方向是**在 ingest 阶段按表聚合分块**——把"表头 + 全部数值行"绑成同一个块，
或给块打上 `表题 + 期数` 的结构标签供检索期聚合。但按 §5.5.4 的机制，这会让**块的粒度变粗**，
进而影响 `FIELD_WEIGHTS`、融合权重与 `top_k` 的既有取值——**"这不是补丁，是重做一轮"**（评审原话），
且会反向影响目前已达标的单事实类指标。**因此本工单不动它**，交由后续迭代，并先在验收口径上对齐。

> 评审建议的"每类固定 25 题"未能完全满足：语料里能干净成题的**数字型**（7）与**模糊指代型**（4）数量不足。
> 宁可如实少放，也不用模板凑数——凑出来的题只会污染指标。

## 5.6 【标准动作】如何验证测试集本身

> 本节讲的不是某个工具，而是**一套可复用的方法**：自造的任何产物（测试集、清洗词表、正则、
> 判分器、指标脚本）在**进评估之前**该怎么验证。工具会随项目变化，方法不会。
> 现有的工具实现见 `tests/validate_questions.py`。

### 5.6.1 为什么要有它：同一个失效模式出现了三次

| 次序 | 事件 | 形态 |
|---|---|---|
| 1 | 水印漏判 | 自拟通用词表扫不出项目特有污染源 → 得出"无污染"**假阴性**；而词表在工单三记忆里已写明 |
| 2 | 8 道模板废题 | 生成的题面不成立（"公司分别是多少？"），**做完没筛就进了评估**，把 0.6579 拉低到 0.5909 |
| 3 | 闸门自身 | 首版闸门漏了 `哪里/哪家/哪个`，把 23 道手工题全判废——**没被验证过的校验工具，和没有校验是同一回事** |

三次的共同点不是"想得不周"，而是**做了但没质检**。因此把它做成可执行脚本，而不是再写一句"下次注意"。

### 5.6.2 方法：两道筛 + 闸门自检

**第一步——定判据（两道筛）**：

```bash
D:/myconda1/python.exe tests/validate_questions.py      # 无参数则检查两个题集
```

| 筛 | 判据 | 拦截目标 |
|---|---|---|
| ① 题面成立 | 有疑问词或问号；去掉公司名后的主题 ≥4 字；主题不在碎片黑名单 | 模板抽取失败产生的废题 |
| ② 答案可核验 | `expect` 每个字段都能在目标文档的语料里找到 | 凭印象写的答案、`doc` 归属错误的题 |

**第二步——**（这一步才是方法的核心）**用已知正反例验收闸门自己。**

任何校验工具都必须先用「**已知合格样本**」和「**已知废样本**」验收；
未经此步，它与一个恒返回 `True` 的摆设没有区别。脚本内建了这段自检（不合格直接 `return 2`，不给出误导性结论）：

| 样本 | 期望 | 实测 |
|---|---|---|
| 23 道手工自然题 | 全部通过 | **23/23 通过** |
| 8 道已知模板废题 | 全部拦截 | **8/8 拦截** |
| 闸门内建自检 | 合格样本过、废样本挂 | **通过** |

> 内建自检第一次跑是**不通过**的——它抓出了我自己在自检 fixture 里没做千分位归一化（假语料与真实语料口径不一致）。
> 这正是"校验器本身也要被校验"的价值。

**第三步——** 只有闸门自检通过，它给出的结论才可信；此时才用它去筛题集。

### 5.6.4 闸门对题集的实际处置

`tests/questions100.json` 经闸门剔除 8 道废题后，**106 题全部通过两道筛**：

| 题集 | 闸门结果 |
|---|---|
| `tests/questions.json`（手工自然题） | 23 / 23 通过 |
| `tests/questions100.json`（含扩样探针） | 106 / 106 通过（已剔除 8 道废题） |

> **注意**：§5.5 里报的 0.5909 是**剔除前**在含废题的 44 题上测的；剔除后的口径为 **0.6579**（38 道有效题）。
> 两个数都保留在报告里，交付题集用干净的那份。
