## 一、先诊断，再优化

优化最怕拍脑袋。动手之前先把**瓶颈量化**，否则很容易优化了一个不重要的地方。

### 1.1 耗时诊断：Query 理解一步就吃掉一半延迟

工单1 交付的系统对 10 道验收题实测（`/api/ask`，逐段计时）：

| 环节 | 平均耗时 | 占比 |
|---|---|---|
| Query 理解（一次 LLM 往返） | **962 ms** | **48%** |
| 向量 + BM25 检索（全量 1261 块） | 26 ms | 1% |
| 答案生成 | 1030 ms | 51% |
| 合计 | 2018 ms | 100% |

**结论：为了「把问题改写成一个检索式」，我们付掉了整个延迟预算的一半。
而改写本身对结果的影响远没有这么值钱。**

### 1.2 检索质量诊断：真正的噪音是「主体名称」，不是「块切得不好」

用「武汉兴图新科电子股份有限公司在哪个领域已经成为重要供应商？」做对照实验，
**只改一个问题里的一个成分**，看纯向量检索的前 8 名落在哪：

| 查询式 | 前 8 名页码 | 是否命中正确答案页 |
|---|---|---|
| 带公司全称 | 22, 52, 532, 61, 53, 209, 1, 67 —— 全是公司基本信息/合同页 | ✗ |
| 去掉公司全称 | 210, 149, 152, 151, 153, 123, 177, 209 —— 回到了行业分析章节 | 邻近 |

同样地，「电子信息行业的下游主要包括哪些行业？」去掉公司全称后，
正确答案页（第 152 页）从**完全检索不到**变成**第 4 名命中**。

**结论：问题不在「块切得好不好」，而在「检索器分不清哪些词有区分度」。**
公司全称在一份只讲这一家公司的招股书里反复出现，出现在 20% 以上的块里，
对检索毫无区分力，却因为词面完全匹配而被向量和 BM25 同时顶到最前面。

## 二、优化方案

按工单2 要求的「pdf 解析的处理 / 分块优化 / 检索优化」三个层面展开，另加一层响应时间优化。

### 2.1 PDF 解析层

| 优化项 | 做法 | 解决的问题 |
|---|---|---|
| 行内标题断行 | 在紧跟在句末标点之后的层级标题（`第X节`/`一、`/`（一）`）前强制断行 | Word 转 PDF 会把标题并进上一行，导致行首标题识别全部失效，后续分块把两个大节混进一块 |
| 表格独立抽取 | 对疑似表格页（一行出现 ≥3 个数字的行 ≥3 行）用 pdfplumber 抽成 Markdown，**只打开一次 PDF、按页批量抽取** | 纯文本行会把「2019年1-6月 / 2018年度 / 2017年度」列头与数值切散，行列对不上 |
| 页眉/页码/填充行去噪 | 逐行正则剔除 | 每页重复的页眉会被 BM25 当成高频关键词命中（两边都做，不计入优化收益） |

### 2.2 分块层

| 优化项 | 做法 | 解决的问题 |
|---|---|---|
| 标题感知打包 | **跨小节累积打包**（小节切换时缓冲过半才断），并把章节路径写进块首 | 逐标题硬断会产生大量 100 字以下的碎块，向量语义不足、BM25 也难命中 |
| 一级标题无条件断块 | `第X节`/`第X章` 级别视为硬边界 | 跨节拼接会让块内出现两个主题，向量被拉扯 |
| 长度上限兜底（两层） | 每个块都过 `_split_long`；`_split_long` 自身能对**无标点长文本**硬切，优先断在 `，、；：` | 招股书里有大量「整段只有逗号」的长枚举，会原样穿透长度检查，导致**入库整批失败** |
| 表格按行拆分 + 重复表头 | 超长 Markdown 表格按行切，每块重复 header + 分隔行 | 从表格中间断开会让行列对不上 |

效果：块数 1767 → 1261，平均块长 259 → 508 字，最长严格 ≤1200。

### 2.3 检索层（本工单收益最大的部分）

**① 混合检索：余弦 + β · BM25 归一（β = 0.30）**

- BM25 项**必须先归一化**：BM25 无上界（本语料实测 0~20+），余弦在 [0,1]，直接相加会被 BM25 淹没。
- **刻意不用 RRF**：RRF 只看排名、无视分数，会把「仅被 BM25 命中的纯关键词噪音」按名次奖励上来；
  且归一化 RRF 的 top1 恒为 1.0，阈值闸门会形同虚设。

**② 无区分度成分过滤（词级 + 短语级）—— 针对 1.2 诊断出的根因**

这是本工单最核心的一项优化，思路是**让语料自己生成停用词表**：

- **词级**：按文档频率（DF）自动识别。阈值 0.20 是实测扫出来的：
  不滤 → 9/10 命中（公司全称把合同表格顶到第一）；0.30 → 9/10；**0.20 → 10/10**；0.15 → 9/10。
- **短语级**（工单2 新增）：中文分词会把「武汉兴图新科电子股份有限公司」切成
  `武汉 / 兴图 / 新科 / 电子 / 股份 / 有限公司` 六个碎片，各自 DF 只有 0.06~0.21 ——
  **都够不着 0.20 的阈值**，于是整串公司名只被剔掉一个「兴图」。
  做法是**迭代式短语合并**（BPE 的思路，但用于"找噪音"而不是"建词表"）：

  > 第 1 轮找出高频相邻二元组 → 就地合并成新 token → 第 2、3 轮在合并结果上重复，
  > 短语逐轮变长。实测 1 轮只能得到「兴图新科」，3 轮长成「兴图新科电子股份有限公司」。
  > 每轮成本 O(全部 token) ≈ 30 万次操作、0.3 秒，构建只在索引加载后做一次并由启动预热触发。

  短语级 DF 阈值取 0.10（短语天然比单词稀有，所以低于词级阈值），最小长度 4 字。

- **兜底**：滤完不足 4 字就退回原串，避免查询被清空导致检索失去条件。

**③ 阈值闸门（只看「依据分」，不看「融合分」）**

采用**双分设计**：

```
依据分 evidence = 余弦 + β · BM25归一            ← 有绝对量纲，闸门只认它
融合分 score    = 依据分 + δ · 文档共识（δ=0.25） ← 含主题先验，只用于排序展示
```

若让闸门看融合分，离题问题会因为先验加分而拦不住。阈值实测校准（本机 10 题 + 3 个离题问题）：

- 10 个真相关问题：top1 依据分 0.9388~1.0542
- 3 个明确离题问题：依据分最高 0.7487
- 两段区间不重叠 → **0.80 落在中间**，离题被拦空、真问题不受影响

### 2.4 响应时间层：Query 理解「高置信直通」

针对 1.1 诊断出的瓶颈，改成 **先花 26ms 试一次检索，再决定要不要花 900ms 调 LLM**：

```
规则归一化 → 试检索(top1) → 依据分 ≥ 0.88？
                             是 → 直通，跳过 LLM（省 ~900ms）
                             否 → 老实调 LLM 做 Query 理解
```

三个保守设计，避免为了快而牺牲质量：

1. 旁路阈值 0.88 **远高于**闸门阈值 0.80，留足余量；
2. 命中指代/比较/多跳/并列复合（它、该、上述、前者、后者、对比、区别、为什么、如何、以及、`X和Y分别`）
   **一律不旁路** —— 这类问题恰恰是 LLM 改写最能帮上忙的地方；
3. 直通只影响「检索式从哪来」，检索与生成完全不变。

实测 10 道验收题**全部命中直通**（首条依据分 0.9126~1.0231，全部 ≥ 0.88），
Query 理解耗时从平均 962ms 降到 **15~42ms**。

## 三、优化前后检索精确度对比

### 3.1 指标口径（客观规则，不含任何模型打分）

| 指标 | 定义 |
|---|---|
| 关键事实命中率 | 每题人工标注的 `must_have` 关键事实（数字/名称，如 `6,464.51`、`程家明`）在召回上下文中的覆盖率 |
| 全部命中题数 | 一题的所有关键事实都命中才算 1（最严格口径） |
| 正确页命中率 | `gold_pages` 是否出现在 top-8 召回中 |
| MRR | 第一个命中正确页码的块的平均倒数排名（1.0 = 每次都在第一位） |

> `gold_pages` 的定义是「**同时包含该题全部关键事实的块**所在的页」，
> 由索引反查得到，**与任何模型输出无关**，因此不依赖 LLM 打分，可被任何人复现。

### 3.2 逐层开启优化的效果

| 配置 | 说明 | 关键事实命中率 | 全部命中 | 正确页命中率 | MRR |
|---|---|---|---|---|---|
| **A0** 朴素 RAG（优化前） | 朴素解析 + 定长 500 字滑窗 + 纯向量 | 0.650 | 6/10 | 0.600 | 0.298 |
| **A1** + 解析层 | 行内标题断行 | 0.650 | 6/10 | 0.600 | 0.298 |
| **A2** + 分块层 | 标题感知分块 + 表格独立成块（检索仍纯向量） | 0.450 | 4/10 | 0.400 | 0.325 |

## 四、结论：收益到底来自哪一层

上表有一组**反直觉但可复现**的结果，需要如实说明。

### 4.1 检索层是决定性的，结构层（解析/分块）几乎不产生收益

按「每行只变一个变量」的受控对照，各层的净贡献是：

| 层面 | 优化项 | 关键事实命中率 | MRR | 判定 |
|---|---|---|---|---|
| 解析层 | 行内标题断行（A0→A1） | +0.000 | +0.000 | 单独无收益 |
| 分块层 | 标题感知分块 · 纯向量下（A1→A2） | **−0.200** | +0.027 | 单独为负 |
| 检索层 | BM25 混合（A2→A3） | **+0.550** | +0.097 | **决定性** |
| 检索层 | DF 过滤（A3→A4） | +0.000 | **+0.285** | **决定性** |
| 分块层 | 标题感知分块 · 完整检索下（A2c→A4） | +0.050 | +0.007 | 边际 |
| 检索层 | 阈值闸门（A4→A5） | +0.000 | +0.000 | 不在这 10 题上体现 |

一句话：**把检索准确率从 60% 拉到 100% 的，是检索层；解析层和分块层的贡献接近 0。**

### 4.2 「分块优化」的贡献为什么这么小（以及它到底贡献了什么）

**先说反直觉的那一格。** 标题感知分块让块更长（508 字 vs 500 字）、语义更集中，
但**纯向量检索恰恰对长块不友好**：块内信息一多，句向量被平均掉，细粒度信号反而模糊。
同时主线索引还多了 381 个数字密集的表格块，在纯向量下会吸引走一部分注意力。
所以 `A1→A2` 的命中率是 **−0.200**。

**再说关键的一格 —— 严格受控对照 `A2c`。**
`A2c` 是「**定长分块 + 与最终版完全相同的检索层（BM25 + 短语级 DF）**」，
它是判断「分块层到底有没有用」最严格的一格：只要分块真的重要，
这一格就应该明显落后于 `A4`。实测结果是：

```
A2c（定长分块 + 完整检索）  命中率 0.950 (9/10)   MRR 0.700
A4 （标题感知分块 + 同检索） 命中率 1.000 (10/10)  MRR 0.707
                             差  +0.050           差  +0.007
```

**分块层在完整检索下的净贡献只有 +0.050 命中率 / +0.007 MRR。**
它丢的那 0.050 全部来自**一道题（id=95）**：定长滑窗把
「全军第一个（视频指挥系统技术标准）」和「视频技术规范」这两个关键事实
**切进了相邻的两个块**，检索只召回其中一块，于是命中率掉到 0.5。
标题感知分块按小节边界打包，恰好把这句话留在了同一块里。

> 需要注意：`A2c` 早期版本曾算出 MRR 0.442，据此一度得出「分块层 +0.265」的结论。
> 复核发现那一版 `A2c` 只挂了词级 DF、没有挂上短语级 DF，等于被用旧口径和 A4 对比，
> 结论不成立。修正为同口径后即上表的 +0.007。**这里保留这个过程，是因为它说明：
> 受控对照一旦没有严格同口径，很容易得出假的因果。**

**所以正确说法是：分块层不是「没用」，而是它的收益上限本来就只有「别把一句话切散」这么大。**
`A2c` 与 `A4` 的 MRR 几乎一样（0.700 vs 0.707）还说明了另一件事 ——
**DF 过滤这一项对分块方式不敏感**，它靠的是「语料级词频统计」，
换个分块方式照样成立。收益来源就是那一句：**让检索器忽略没有区分度的成分。**

### 4.3 阈值闸门的价值不在这 10 题上

A4 → A5 的变化是 0 —— 因为 10 道验收题全部是文档内问题，本来就不该被拦。
闸门的价值体现在**离题问题**上：`如何用 Python 实现快速排序？` 这类问题最高依据分只有 0.7487，
低于 0.80，会被拦空并如实回答「资料中没有相关内容」，而不是让模型自由发挥编造答案。
这正是工单1 里「纯 LLM 对照组 10 题编造 9 题」要防的事。

### 4.4 一句话总结

> 这份语料上，把检索准确率从 60% 拉到 100% 的，不是「把 PDF 切得更好」，
> 而是「让检索器分得清哪些词有区分度」。
> 解析层与分块层的贡献接近 0（分块层在完整检索下也仅 +0.050 命中率），
> 但它们决定了检索层能拿到多好的原料 —— 分块层唯一被证实的作用，
> 是不让一句话里的两个关键事实被切进两个块。

## 五、系统稳定性与容错验证

工单2 的验收项除了「检索精确度」，还有三条与稳定性相关：**高可用性（长时间运行）、
容错机制（用户输入错误 / 文档解析失败）、多语言支持**。这一节把这三条量化。

脚本：`python scripts/load_test.py --concurrency 8 --rounds 2 --soak 400`（需服务已启动）。
产物：`data/eval/工单2_稳定性与容错验证_*.json`。

### 5.1 并发能力：系统层没问题，瓶颈全在上游大模型

一开始用 8 路并发打 `/api/ask`，得到一组很难看的数字（P50 超过 10 秒）。
但「难看」不等于「系统不行」—— 得先判清是谁的问题，所以加了一个
**只检索、不生成**的接口 `/api/search`，把两层拆开测：

| 被测链路 | 并发 | 请求数 | 成功率 | 吞吐 | P50 | P95 | P99 | ≤3s 占比 |
|---|---|---|---|---|---|---|---|---|
| **系统层** `/api/search`（纯本地检索） | 8 | 16 | **100%** | **56.2 rps** | **135.6 ms** | 143.6 ms | **146.0 ms** | 100% |
| **端到端** `/api/ask`（含模型生成） | 8 | 16 | 100% | 0.68 rps | 10 635.6 ms | 12 513.4 ms | 13 468.0 ms | 6.25% |

**端到端为什么慢成这样？** 做个除法就清楚了：

```
单路请求平均耗时        1 268.7 ms
16 个请求 ÷ 8 并发      → 理想墙钟 2.5 s
实测墙钟                23.4 s
串行化系数              23.4 / 2.5 = 9.22  ≈ 并发数本身
```

串行化系数 ≈ 并发数，意思是**上游把 8 个并发请求排成了一队，实际并发度是 1**。
判据很直白：*N 并发时墙钟 ≈ 单次耗时 × 请求数*，而不是 *÷ N*。

所以结论是：

> **本系统的并发能力不是瓶颈**（本地检索 56 rps、P99 146 ms、零失败）；
> **端到端延迟完全由大模型服务侧决定**。
> 想让端到端并发真正上去，只有三条路：换不限并发的模型服务、
> 多 Key 轮询、或把生成改造成异步任务队列 —— 都属于外部依赖或架构级改动，
> 不在本次优化的范围内。

补充一点：压测过程中**没有出现任何 429 / 限流错误**，上游是「排队」而不是「拒绝」，
所以成功率仍然是 100% —— 只是慢。

### 5.2 长时间运行：持续负载下既不变慢也不涨内存

「支持长时间运行」最典型的退化不是崩掉，而是**越跑越慢**（缓存膨胀、句柄/连接泄漏、
索引被反复重建）。所以这里看的不是峰值，而是**漂移**：

| 指标 | 结果 |
|---|---|
| 连续检索次数 | 400 次（`/api/search`，串行） |
| 成功率 | **400 / 400，0 失败** |
| P50 / P95 / P99 / max | 27.3 / 47.7 / 53.1 / 62.5 ms |
| 前 25% 平均延迟 | 31.08 ms |
| 后 25% 平均延迟 | **27.98 ms** |
| **漂移系数** | **0.90**（<1 即后段没有变慢） |
| 进程内存 RSS | 703 220 KB → 704 952 KB，**+1.7 MB（<0.3%）** |

400 次往返之后，延迟没有爬升、内存基本持平，可以认为系统侧没有泄漏或累积退化。

> 说明：这里刻意用本地检索接口做长稳，而不是打大模型链路 ——
> 连续几百次真实生成既烧额度又会撞上游限流，测出来的数字会被污染。

### 5.3 容错：9 类异常输入全部返回结构化错误

工单要求「能够处理常见的异常情况，如用户输入错误或文档解析失败」。
针对输入侧构造 9 个用例，判据是**返回结构化错误，而不是 500 或挂起**：

| 用例 | HTTP | 返回 code | 处理结果 |
|---|---|---|---|
| 空问题 | 200 | `BAD_REQUEST` | question 不能为空 |
| 纯空白（`"   \n  "`） | 200 | `BAD_REQUEST` | question 不能为空 |
| question 非字符串（`12345`） | 200 | `BAD_REQUEST` | question 必须是字符串 |
| 缺字段（`{}`） | 200 | `BAD_REQUEST` | question 不能为空 |
| 超长输入（3000 字） | 200 | `OK` | **截断到 500 字后正常作答**，不是报错 |
| 离题问题（`如何用 Python 实现快速排序？`） | 200 | `OK` | 闸门拦空 → 「资料中没有找到足以回答该问题的内容」 |
| 闲聊（`你好`） | 200 | `OK` | 引导到文档相关问题，不胡答 |
| `/api/compare` 空问题 | 200 | `BAD_REQUEST` | question 不能为空 |
| `/api/compare-opt` 空问题 | 200 | `BAD_REQUEST` | question 不能为空 |

**未兜住的用例：0 / 9。** 三个设计点值得说明：

1. **超长输入选择「截断」而不是「拒绝」。** 用户的诉求仍然要满足，
   只是不能让它撑爆上下文预算 —— 报错会把一个能答的问题变成答不了。
2. **全部返回 HTTP 200 + 业务错误码**，而不是 4xx/5xx。
   前端只判断一个统一的 `code` 字段，不用为「网络错误」和「业务错误」写两套分支。
3. **文档解析失败**走的是上传接口 `/api/upload` 的异常分支：
   解析报错会返回带 `INTERNAL_ERROR` 的结构化响应并回滚索引，
   服务本身不会因为一份坏 PDF 而起不来（索引问题只体现在 `/ready` 里）。

### 5.4 多语言：中英文均以提问语言作答

用同一组问题的中英文版本各问一遍，用「中文字符占比 / 拉丁字母占比」粗判语种一致性：

| 问题 | 中文回答语种比 | 英文回答语种比 |
|---|---|---|
| 注册资本是多少 | 1.000（纯中文） | 0.903 |
| 哪个工程获国家科技进步一等奖 | 0.959 | 0.989 |

英文问答确实用英文作答（保留了 `[第22页]` 这类引用标记，属于设计内行为）。

> **已知缺陷（如实记录）**：英文回答对**中文货币单位**的处理不可靠。
> 同一道题两次运行，一次译成 `5,520.00 million RMB`，
> 另一次则原样保留中文 `5,520万元`。
> 前者是**实打实的错误**：5,520 万元 = 5,520 万 = 55.2 million RMB（55,200,000），
> 译成 `5,520.00 million` 等于放大了 100 倍 —— 数字没错，单位换错了。
> 要修得在 prompt 里补一条单位换算规则，或让生成前先把数字与单位一并结构化抽出；本轮未做。

## 七、已知局限与后续可做的事

1. **DF 过滤依赖"同一份文档内重复"这一前提。**
   它是**单文档语料**的解法：靠"这个词在本语料里到处都是"来判断无区分度。
   换成多文档知识库后，公司名会是有效的区分特征，这套过滤必须关掉或改成文档级 IDF。

2. **主体名称仍未被完全清除。**
   过滤后残留的 `武汉电子股份`（DF 分别 0.109 / 0.062 / 0.142）确实低于阈值 ——
   它们**不算噪音**，属于正常词。要彻底解决得换成**字符级 n-gram 的 DF**
   （已实测：字符 3-gram 全量构建仅 0.17 秒、12 万个，成本可接受），
   本轮因为收益不确定、改动面较大而未纳入。

3. **端到端并发受上游大模型串行化限制。**
   实测 8 路并发时串行化系数 9.22（详见 5.1）：系统侧本地检索能跑到 56 rps / P99 146 ms，
   但生成环节被上游排成一队，端到端 P50 从 1.3 秒涨到 10.6 秒。
   这不是本系统的缺陷，但确实是「高并发」验收项的天花板，
   要突破只能换服务、多 Key 轮询或改异步队列。

4. **响应时间是上游 LLM 延迟主导的。**
   实测某次调用单题生成耗时 7.56 秒（其余 9 题平均 1.02 秒），会把该题总耗时推到 7.9 秒。
   这是模型服务侧的抖动，系统侧已无更多可压缩空间（检索只占 26ms）。
   可控的缓解手段是给生成加超时降级，但那会牺牲答案完整性，本轮未做。

5. **英文回答对中文货币单位的换算不可靠**（详见 5.4）。
   `5,520万元` 曾被译成 `5,520.00 million RMB`，数值放大 100 倍。

6. **分块粒度参数（size / overlap）没有做网格搜索。**
   当前值沿用工程默认（600/80），消融显示分块层的影响远小于检索层，
   所以没有投入预算去精调。
