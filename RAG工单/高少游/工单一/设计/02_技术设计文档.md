# 技术设计文档（RAG 知识库问答系统）

> 工单编号：人工智能 NLP-RAG-基于 PDF 文档的问答系统
> 技术栈：Python 3.10 / LangChain / FAISS / BM25 / Ollama(本地) / Streamlit / RAGAS

本文档描述系统的总体技术设计、模块划分、关键算法与设计决策，面向研发与评审。

---

## 1. 系统目标

针对企业招股说明书 PDF，构建一个**本地化、可离线运行**的检索增强问答（RAG）系统，核心目标：

1. **精准回答**：回答必须基于 PDF 原文，给出关键数值与名称，注明来源页码，不编造。
2. **可对比**：同时提供 RAG（检索增强）与纯 LLM 两种回答链路，量化"检索增强"带来的增益。
3. **快速响应**：从提问到生成答案 ≤ 3 秒。
4. **用户友好**：Streamlit 界面，支持文字/语音提问、检索依据展示、用户反馈。
5. **可评估**：用 RAGAS + 人工命中检查对两条链路做对比评估。

## 2. 总体架构

```
┌──────────────────────────── 离线·构建知识库 ────────────────────────────┐
│  PDF ─→ pdf_parser(文字+表格) ─→ knowledge_base(切片) ─→ bge-m3─────────│
│  ─→ FAISS 向量库(vector_db)                                            │
└────────────────────────────────────────────────────────────────────────┘
┌──────────────────────────── 在线·检索问答 ──────────────────────────────┐
│  提问 ─→ query_understanding(理解) ─→ retriever(向量+BM25+RRF) ─→       │
│  qa_engine(生成) ─→ 答案+页码                                           │
└────────────────────────────────────────────────────────────────────────┘
```

| 模块 | 文件 | 职责 |
|---|---|---|

## 4. 关键设计决策

### 4.1 为什么用混合检索（向量 + BM25）
招股说明书中大量数据是**数字、公司名、专有名词**（如"5,520万"、"程家明"、"某视频技术规范1.0"）。
- 纯向量检索对语义改写友好，但对精确数字/专有名词的匹配较弱；
- BM25 词法检索对精确匹配强，但对同义改写不敏感；
- 因此两者互补，用 **RRF（Reciprocal Rank Fusion）** 融合：`score = Σ 1/(k + rank)`，仅按排名融合，无需归一化向量与 BM25 分数量纲，是业界成熟方案。

### 4.2 为什么分批嵌入
本地 `bge-m3` 若一次性提交超长文档，会触发 Ollama tokenizer 服务 `127.0.0.1:1510` 连接被拒。
`_BatchedEmbeddings` 将大请求切分为**每批 50 条**，保证 2670 个切片稳定完成嵌入。

### 4.3 查询理解的价值
原始问句常含指代（"该公司"）或需拆解（"收入分别是多少"）。
`query_understanding` 让 LLM 输出结构化 JSON（intent/entities/子问题），把消歧后的主问题与子问题一并送入检索，显著提升召回命中。

### 4.4 防幻觉提示词
qa_engine 的 RAG 提示词强制三条铁律：
1. 仅依据参考文档回答，关键数值/名称原样输出；
2. 信息分散时综合判断并注明来源页码；
3. 无信息时明示"依据说明书无法回答"，不得编造。

### 4.5 为什么两种链路都保留
应用评测需要"对照实验"。纯 LLM（无上下文）作为基线，用于量化 RAG 注入文档后的增益，也是工单验收项之一。

## 5. 评估方案

| 层面 | 手段 | 工具 |
|---|---|---|
| 定量指标 | faithfulness / answer_relevancy / context_precision / context_recall / answer_correctness | RAGAS |
| 定性命中 | 人工核对答案中的关键数值/专有名词 | build_report.py 关键词检查 |
| 性能 | 端到端耗时 RAG vs 纯 LLM | evaluate.py 记录 elapsed |

**注意**：本地裁判 `deepseek-r1` 为推理型模型，输出非严格 JSON，RAGAS 常快速失败。故工程上以**确定性命中检查 + 耗时**为主评估；RAGAS 提供脚本 `ragas_score.py`，换 JSON 友好模型即可输出全套指标。

## 7. 演进方向

1. **换非推理型模型**提升响应速度（当前 deepseek-r1 是速度瓶颈）。
2. **按章节标题切片**优化召回（当前按固定长度切片）。
3. **精确数字重排**：对注册资本等关键数字走精确匹配后置重排。
4. **多文档支持**：当前为单文档，可扩展 collection 维度多文档隔离。
