# 架构设计

Role RAG 的架构说明：分层结构、两条核心数据流、存储表结构、检索与记忆策略、权限模型，以及支撑 8G 显存 / 0.6B 小模型的工程取舍。

## 1. 总体架构

```text
┌──────────────────────────────────────────────────────────────────────┐
│  表现层  web/index.html + style.css + app.js（零 CDN，原生 JS）        │
│          登录 / 角色选择 / SSE 流式对话 / 引用悬停 / 4 面板 tab        │
└───────────────────────────┬──────────────────────────────────────────┘
                            │ HTTP + SSE  (JSON / text/event-stream)
┌───────────────────────────▼──────────────────────────────────────────┐
│  接口层  src/role_rag/api/                                            │
│   app.py      路由 + SSE + 异常处理 + 限流 + 请求上下文                │
│   auth.py     PBKDF2 口令 + HMAC 无状态令牌（TokenCodec）              │
│   schemas.py  Pydantic 请求 / 响应模型                                │
└───────────────────────────┬──────────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────────┐
│  编排层                                                               │
│   rag/pipeline.py   问答编排：召回→记忆→组装→生成→引用校验→护栏        │
│   rag/prompts.py    人设 + 记忆 + 知识片段 + 引用协议                  │
│   retrieval/        三路召回 + 加权 RRF 融合 + 缓存                    │
│   memory/memory.py  分层记忆读写 + 规则式事实抽取                      │
│   ingest/pipeline.py 入库流水线（加载→分块→向量化→写库→刷新版本）      │
│   roles.py          角色注册表 + 风险词护栏                            │
│   jobs.py           后台任务进度登记                                   │
└───────────┬───────────────────────────────────┬──────────────────────┘
            │                                   │
┌───────────▼───────────────┐   ┌───────────────▼──────────────────────┐
│  模型层 models/            │   │  存储层 store/                        │
│   embedder.py BGE-M3       │   │   milvus_store.py  KB + 长期记忆      │
│    稠密 1024 + 稀疏权重    │   │   redis_store.py   聊天/记忆/缓存/用户 │
│   llm.py Qwen3-0.6B 流式   │   │                                       │
└───────────┬───────────────┘   └───────────────┬──────────────────────┘
            │                                   │
      D:\modelscope                     Milvus 3.0 (WSL) / Redis 8.0 (WSL)
```

分层原则：上层只依赖下层的抽象接口（`get_retriever` / `get_memory` / `get_pipeline` 等单例工厂），模型与存储都做成**懒加载单例**，便于测试时替换。

## 2. 技术选型与理由

| 环节 | 选型 | 理由 |
| --- | --- | --- |
| 向量化 | BGE-M3（本地） | 单模型同时产出稠密 + 稀疏，省一次前向与一份显存；中文效果强 |
| 生成 | Qwen3-0.6B（本地） | 0.6B 在 8G 显存下延迟可接受；支持 chat template 流式输出 |
| 向量库 | Milvus 3.0 standalone | 原生支持稠密 + 稀疏双字段与 `hybrid_search`；支持标量过滤做多租户隔离 |
| 缓存 / 记忆 | Redis 8.0 | 五类结构刚好覆盖「列表 / 摘要 / 画像 / 集合 / 排序」五种访问模式 |
| 关键词检索 | jieba + rank_bm25 | 无需 ES，内存索引对 78 块规模足够；中文分词质量好 |
| 融合 | 加权 RRF | 免训练、对分值尺度不敏感，可直接调权重做消融 |
| Web 框架 | FastAPI + uvicorn | 原生 async，`StreamingResponse` 直接做 SSE |
| 认证 | PBKDF2 + HMAC | 零额外依赖，无状态令牌便于横向扩展 |

## 3. 入库链路

```text
data/kb/<scope>/*.md|txt|pdf
   │
   ▼  loaders.load_documents()          读取文件，抽取正文与标题
Document(path, title, text, scope)
   │
   ▼  chunking.chunk_document()         结构感知切分
Chunk(text, doc_id, doc_title, section, chunk_index, char_len, ...)
   │      · 按 Markdown 标题分层
   │      · 目标 700 字符 / 重叠 120 / 硬上限 1400 / 最小 80
   ▼  embedder.encode_documents()       BGE-M3 批量前向（batch=16, fp16）
   │      · dense：CLS 归一化 → 1024 维
   │      · sparse：relu(W·h+b) → token-id max 池化 → 权重过滤
   ▼  milvus_store.upsert_chunks()      写入 role_kb_chunks（含 role/scope 过滤字段）
   │
   ▼  redis_store.bump_kb_version()     kb:version 自增 + 清检索缓存
```

分块要点：

- `role` = 知识域 id（`shared` / `financial_planner` / ...），`scope` 与之对应，用于检索时按角色过滤
- 公共库 `shared` 对所有角色可见（`ingest.include_shared=true`），无需每个角色重复入库
- 稀疏权重低于 `sparse_min_weight=0.02` 的 token 丢弃，每块最多保留 `sparse_top_terms=192` 个
- 重建（`--recreate`）会先 drop 再 create 集合，保证向量维度 / 索引配置干净

## 4. 问答链路

```text
POST /api/chat {role_id, question, session_id?}
   │
   ▼  current_user()          令牌校验 → AuthContext(user_id, roles, is_admin)
   ▼  _ensure_role_access()   角色白名单校验（非授权角色 → 403）
   ▼  _rate_limit()           每分钟 60 次限流（Redis 计数器）
   ▼  session 解析            无 session_id 则新建并写 sess:<sid>:meta
   │
   ▼  memory.load_bundle()    读最近 N 轮 + 摘要 + 长期事实向量（Milvus role_memory）
   │
   ▼  retriever.search()      三路召回 → 加权 RRF → 缓存（cache:retr:<hash>）
   │      dense(Milvus) + sparse(Milvus) + bm25(内存)
   │
   ▼  roles.check_guardrails() 问题命中风险词 → 生成 SAFETY_TEMPLATE 前置纠正指令
   │
   ▼  prompts.build_messages()  system 人设 + 已知信息 + 最近对话 + 知识片段 + 问题
   │
   ▼  llm.stream()            Qwen3-0.6B 流式生成
   │      ├─ SSE event: meta       会话 / 角色 / 召回统计
   │      ├─ SSE event: delta      增量文本
   │      ├─ SSE event: citations  引用片段（编号 / 标题 / 分值）
   │      └─ SSE event: done       结束 + 护栏标记
   │
   ▼  后处理
        · 引用校验：正则抽 [n] → 映射到片段 → 未标注时回填候选引用
        · 护栏：答案命中风险词 → 强制追加角色 disclaimer（⚠️ 标记）
        · 记忆回写：抽取事实写 Redis + Milvus；超 5 轮刷新摘要
        · 追加 sess:<sid>:msgs、更新 zSet/meta、统计 stats:<日期>
```
## 5. Milvus 表结构

共两个集合，均为「稠密 + 稀疏」双向量字段，`auto_id=True` 主键：

### 5.1 `role_kb_chunks`（知识块）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pk` | INT64 (PK, auto) | 主键 |
| `dense` | FLOAT_VECTOR(1024) | HNSW / COSINE |
| `sparse` | SPARSE_FLOAT_VECTOR | SPARSE_INVERTED_INDEX / IP |
| `text` | VARCHAR(8192) | 块正文 |
| `role` | VARCHAR(64) | 知识域 id，检索过滤用 |
| `scope` | VARCHAR(64) | 作用域（`shared` 或角色 id） |
| `doc_id` | VARCHAR(128) | 文档唯一 id |
| `doc_title` | VARCHAR(512) | 文档标题 |
| `section` | VARCHAR(512) | 章节标题 |
| `chunk_index` | INT64 | 块在文档内序号 |
| `source` | VARCHAR(512) | 源文件路径 |
| `tags` | VARCHAR(512) | 标签（逗号分隔） |
| `char_len` | INT64 | 字符长度 |
| `created_at` | INT64 | 入库时间戳 |

索引参数：稠密 `HNSW(M=16, efConstruction=200, metric=COSINE)`，搜索 `ef=128`；稀疏 `SPARSE_INVERTED_INDEX(metric=IP)`。

### 5.2 `role_memory`（长期记忆）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pk` | INT64 (PK, auto) | 主键 |
| `dense` | FLOAT_VECTOR(1024) | 同上，HNSW / COSINE |
| `sparse` | SPARSE_FLOAT_VECTOR | 同上 |
| `text` | VARCHAR(4096) | 事实文本（如「用户年龄 30 岁」） |
| `user_id` | VARCHAR(64) | 归属用户，检索过滤用 |
| `role_id` | VARCHAR(64) | 归属角色 |
| `kind` | VARCHAR(32) | 事实类型（name / age / goal / preference / explicit / ...） |
| `importance` | INT64 | 重要度 1–5 |
| `ts` | INT64 | 写入时间戳 |
| `session_id` | VARCHAR(64) | 来源会话 |

多租户隔离：知识检索用 `role in [<角色域>, 'shared']` 过滤；长期记忆检索用 `user_id == <当前用户>` 过滤。空集合时跳过原生 `hybrid_search`（否则报 `unsupported ID type`），改用 `_memory_has_rows()` 30s 缓存探针。

## 6. Redis 键设计

统一前缀 `rolerag:`（`redis.prefix` 可改），覆盖五类数据结构：

| 结构 | 键 | 内容 | TTL |
| --- | --- | --- | --- |
| String | `kb:version` | 知识库版本号（入库后自增，用于 BM25 / 缓存失效） | 永久 |
| String | `cache:retr:<hash>` | 检索结果缓存（hash 由 query + 角色 + top_k 生成） | `cache_ttl` 900s |
| String | `sess:<sid>:summary` | 会话摘要（短期记忆的压缩形式） | `summary_ttl` 7d |
| String | `rl:<uid>:<分钟>` | 每分钟提问计数器（限流） | 60s |
| Hash | `users` | 全量用户（username → JSON：口令散列 / 角色 / 是否管理员） | 永久 |
| Hash | `user:<uid>:profile` | 用户画像（昵称、偏好、累计提问数） | `history_ttl` 7d |
| Hash | `sess:<sid>:meta` | 会话元信息（owner / role / title / 轮数 / 时间） | `history_ttl` 7d |
| Hash | `stats:<日期>` | 当日运行指标（提问数、命中缓存数等） | 7d |
| List | `sess:<sid>:msgs` | 会话原始消息（按时间顺序 `RPUSH`，每条为 JSON） | `history_ttl` 7d |
| Set | `online` | 在线用户集合 | `online_ttl` 300s |
| Set | `sess:<sid>:cites` | 本会话引用过的文档 id（去重） | `history_ttl` 7d |
| zSet | `user:<uid>:sessions` | 用户的会话列表（score = 最近活跃时间） | 永久 |

设计要点：

- **聊天记录用 List 而非 Stream**：只需「追加 + 取尾部 N 条」，List 语义最贴合，`LRANGE -N -1` 一次取回
- **会话列表用 zSet**：按最近活跃时间倒序翻页天然有序，无需额外排序
- **引用去重用 Set**：`SADD` 幂等，避免同一文档反复出现在引用统计里
- **限流用 String + INCR + EXPIRE**：原子且无额外依赖
- 所有键共享前缀，便于 `SCAN rolerag:*` 做清理与统计
## 7. 检索与融合策略

### 7.1 三路召回

| 通路 | 实现 | 过滤条件 | 召回数 | 权重 |
| --- | --- | --- | --- | --- |
| 稠密 `dense` | Milvus HNSW / COSINE | `role in [域, shared]` | 20 | 0.55 |
| 稀疏 `sparse` | Milvus SPARSE_INVERTED_INDEX / IP | 同上 | 20 | 0.30 |
| 关键词 `bm25` | jieba + rank_bm25（内存） | 按 scope 分片 | 20 | 0.15 |

### 7.2 加权 RRF

```
score(d) = Σ_channel  w_channel / (rrf_k + rank_channel(d))
```

- `rrf_k = 60`，`w_dense = 0.55`，`w_sparse = 0.30`，`w_bm25 = 0.15`
- 只对「至少被一路召回」的文档计分；未召回的通道不计入
- 排序后取 `final_k = 6`，同一 `doc_id` 最多贡献 `per_doc_limit = 3` 块（避免单文档刷屏）
- 分值尺度差异由 RRF 的「排名倒数」天然抹平，调权重即可做消融

选择应用侧加权 RRF 而非 Milvus 原生 `RRFRanker` 的原因：三路里有一路（BM25）在内存中，原生 `hybrid_search` 只能融合 Milvus 内的两路；自研融合可统一三路并自由加权。项目同时保留 `fusion=milvus` 走原生混合检索，供对照。

### 7.3 缓存与失效

```text
cache_key = hash(query + role_id + final_k + mode + kb_version)
```

- 命中直接返回，`meta.cached = true`
- 失效依据 Redis `kb:version`：入库 / 重置后版本自增，旧缓存自然不可达（键中已含版本）
- BM25 内存索引同样以 `kb:version` 判断是否需要重建，另有 `bm25_refresh_seconds=60` 的兜底检查间隔

### 7.4 消融与评测

`tools/eval_retrieval.py` 提供小规模标注集上的 Recall@K / MRR / 命中率对比，支持 `--mode dense|sparse|bm25|hybrid`，用于验证「混合检索确实优于单路」。

## 8. 记忆机制

分三层，读写路径如下：

```text
               ┌──────────── 短期（本轮上下文） ────────────┐
提问 ──► 读最近 N 轮  ◄── Redis List  sess:<sid>:msgs
               │ 超过 5 轮 → 压缩刷新 Redis String sess:<sid>:summary
               │
               ├──────────── 结构化画像 ────────────────────
               │ Redis Hash  user:<uid>:profile（昵称/偏好/累计提问）
               │
               └──────────── 长期事实（跨会话） ───────────
                 写：规则抽取 → Redis + Milvus role_memory
                 读：对当前问题做向量检索，相似度 ≥ 0.35 取 4 条
```

**事实抽取是规则式的**（不额外调用模型，省延迟）：`FACT_PATTERNS` 覆盖通用模式，`ROLE_FACT_PATTERNS` 覆盖角色专属模式。

| 模式 | 触发示例 | kind | 重要度 | 产出 |
| --- | --- | --- | --- | --- |
| 显式记忆 | 请记住：我偏好稳健型 | explicit | 5 | 用户要求记住：… |
| 姓名 | 我叫小明 / 我的名字是… | name | 5 | 用户的名字是 小明 |
| 年龄 | 我今年 30 岁 | age | 4 | 用户年龄 30 岁 |
| 居住地 | 我住在杭州 | location | 3 | 用户常住地：杭州 |
| 目标 | 我的目标是… | goal | 4 | 用户的目标：… |
| 偏好 | 我偏好 / 我更看重… | preference | 4 | 用户偏好：… |

角色专属模式：

- `financial_planner`：风险承受能力、每月结余金额、N 年后目标
- `scientist`：研究方向、正在研究的内容、学历身份
- `lawyer`：遇到的纠纷、合同签订情况、诉讼状态

生命周期：`memory.write_back=true` 时事实落库；`long_term_top_k=4`、`long_term_min_score=0.35` 控制召回；`POST /api/memory/clear` 可按范围清理。

## 9. 角色护栏与安全

三层防护，逐层收紧：

1. **人设层**（`roles.yaml` → `persona`）：每个角色写明「只依据检索资料作答」「不推荐具体产品」「不编造文献」等行为准则，进入 system prompt
2. **问题侧纠正**（`roles.check_guardrails` → `SAFETY_TEMPLATE`）：用户问题命中风险词时，插入一条 system 指令，要求先用一句话指出预设不成立，再客观说明，不得顺着假设作答。**只作用于当前这轮**，写入历史时会被剔除，避免污染多轮对话
3. **答案侧免责**（`DISCLAIMER_MARK = ⚠️`）：生成文本命中风险词时，程序**强制追加**角色 `disclaimer`，不依赖模型自觉

风险词表（`RISK_KEYWORDS`，按角色分组）：

| 分组 | 风险词 |
| --- | --- |
| `*`（全局） | 包治百病、绝对安全、零风险、百分之百有效 |
| `financial_planner` | 稳赚、必赚、一定涨、保证收益、保本保息、无风险高收益、推荐买、满仓、全部投入、抄底、梭哈 |
| `stock_analyst` | 必涨、涨停、抄底、满仓、一定涨、目标价、买入评级 |
| `lawyer` | 包赢、保证胜诉、肯定能赢、百分之百胜诉、一定赢 |
| `doctor` | 可以确诊、不用去医院、自己吃药就行、按这个剂量吃 |
| `psychologist` | 你就是抑郁症、确诊为、停药、加药 |
| `scientist` | 绝对证明、已经彻底证实、100% 确定、百分百确定 |
| `english_tutor` | 绝对正确、唯一正确说法 |

## 10. 权限模型

```text
请求 ──► 令牌解析 ──► AuthContext(user_id, username, roles, is_admin)
                            │
                            ├─ 角色白名单：role_id ∈ roles 或 is_admin → 否则 403
                            ├─ 会话归属：session.owner == user_id → 否则 404/403
                            ├─ 管理接口：is_admin → 否则 403
                            └─ 限流：rl:<uid>:<分钟> ≤ 60
```

- **认证**：`PBKDF2-HMAC-SHA256`（12 万次迭代）散列口令；令牌为 `HMAC-SHA256` 签名的自包含载荷（含 user / exp），服务端无状态，默认 12 小时有效
- **授权**：用户可被授予任意角色子集，`is_admin` 拥有 `["*"]` 全集；`admin` 可创建新用户
- **隔离**：会话、记忆、画像均以 `user_id` 为键前缀或过滤条件，用户之间不可互访
- **限流**：每分钟 60 次，超限返回 429

## 11. 并发与性能设计

- **懒加载 + 双检锁**：`embedder` / `llm` 首次使用时加载，`_lock` 保护 `load()`，且发布前不赋值 `self.model`。曾因预热线程与请求线程并发加载触发 `mat1 and mat2 must have the same dtype` 与 `cannot import name 'AutoModel'`，双检锁后修复
- **启动预热**：`app.warmup=true` 时后台线程预热模型与 BM25，实测约 25.9s 完成，不阻塞接受请求
- **fp16 单份权重**：稠密与稀疏共用一次前向，8G 显存可同时容纳 BGE-M3 与 Qwen3-0.6B
- **分词过滤表缓存**：BGE-M3 的特殊 token 集合缓存到 `data_cache/embed_ignore_ids.json`，避免每次入库重复推断
- **BM25 内存索引**：78 块规模下检索耗时可忽略，按 scope 分片避免跨域噪声
- **SSE 流式**：首 token 即开始下发，交互体感显著优于整段返回
## 12. 模块职责

| 模块 | 职责 | 关键入口 |
| --- | --- | --- |
| `config.py` | 分层配置解析（默认 < yaml < env），`section()` 取子树 | `get_config()` |
| `roles.py` | 角色数据类、注册表、风险词护栏、免责声明 | `RoleRegistry` / `apply_guardrails` |
| `jobs.py` | 后台任务（入库 / 上传）的进度登记与查询 | `JobRegistry` |
| `logging_conf.py` | 统一日志（控制台 + `logs/app.log` + `logs/error.log`） | `setup_logging()` / `get_logger()` |

## 14. 扩展指引

**新增一个角色**（以「客服」为例）：

1. 在 `configs/roles.yaml` 里把 `customer_service` 的 `enabled` 改为 `true`，按需调整 `persona` / `guardrails` / `disclaimer` / `followups`
2. 新建知识目录 `data/kb/customer_service/`，放入 `.md` / `.txt` / `.pdf`
3. 重新入库：`python tools/ingest_cli.py --roles customer_service`（或 `--all --recreate`）
4. 在 `security.users_seed` 给对应用户的 `roles` 加上 `customer_service`

**替换模型**：改 `configs/config.yaml` 的 `models.embedder.path` / `models.llm.path`，或设置 `ROLE_RAG_EMBED_MODEL` / `ROLE_RAG_LLM_MODEL`。换 embedding 模型需同步改 `dense_dim` 并重建知识库。

**调整检索效果**：先跑 `tools/eval_retrieval.py` 建立基线，再改 `retrieval.weights` / `top_k_*` / `final_k` / `ingest.chunk_size`，用同一标注集对比。

**新增数据源**：在 `ingest/loaders.py` 注册新后缀的解析函数即可，其余链路无需改动。
