# 表格定位分析（工单备注第 1 条）

> 工单编号：**人工智能NLP-RAG-PDF文档的表格解析及检索优化**
> 工单备注原文：*分析待检索的问题答案在 pdf 中的定位，使用表格解析技术实现*

本文对 4 个表格类问题逐条给出：答案在 PDF 中的**页码定位**、**表格定位**、
**行列结构**，以及**为什么纯文本解析取不到**。
所有页码与表格规格均来自对《招股说明书2.pdf》的实际解析结果
（物理页码；招股书页脚印刷页码 = 物理页码 − 1）。

---

## 定位总览

| id | 问题 | 物理页 | 表格 | 规范化后规格 | 是否跨页 |
| --- | --- | --- | --- | --- | --- |
| 1 | 本次发行股数 + 占发行后总股本比例 | 22、24 | 「四、本次发行情况」/「本次发行概况」 | 5×2 / 15×2 | 否 |
| 2 | 本次募集资金拟投资项目 | 22 | 「五、募集资金用途」 | 6×3 | 否 |
| 3 | 存在控制关系的关联方 + 持股比例 + 关系 | 157 | 「1、存在控制关系的关联方」 | 2×3 | 否 |
| 4 | 不存在控制关系的关联方企业 | 157（+158 相邻小节） | 「2、不存在控制关系的关联方」 | 8×2 | 否（相邻有易混小节） |

4 张表全部是**有完整边框的原生表格**（非扫描件、非图片），
`pdfplumber` 的 `lines` 策略可以直接检出。

## id 1｜本次发行股数，以及占发行后总股本的比例

### 答案

> **1,670 万股，占发行后总股本（6,670 万股）的比例为 25.04%**

### 定位

答案在文档中出现两次，措辞略有差异，互为冗余：

| 位置 | 页 | 表结构 | 对应行 |
| --- | --- | --- | --- |
| 摘要「四、本次发行情况」 | 22 | 5 行 × 2 列（键值对表） | 第 3 行：`发行股数` → `1,670万股，占发行后总股本的比例为25.04%` |
| 第四节「本次发行概况」 | 24 | 15 行 × 2 列（键值对表） | 第 3 行：`发行股数及占发行后总股本比例` → 同上 |

p24 表的完整规格（规范化后）：

```markdown
| 项目 | 内容 |
| --- | --- |
| 股票种类 | 人民币普通股(A股) |
| 每股面值 | 人民币1.00元 |
| 发行股数及占发行后总股本比例 | 1,670万股，占发行后总股本的比例为25.04% |
| 每股发行价格 | 通过向询价对象询价或中国证监会认可的其他定价方式确定 |
| 发行前每股净资产 | 2.18元(按截至2010年6月30日经审计净资产除以发行前总股本计算) |
...
| 募集资金总额 | [ ◆ ]万元 |
| 募集资金净额 | [ ◆ ]万元 |
```

发行后总股本 6,670 万股可以在 **p2 的「本次发行概况」表**中交叉验证
（`发行股数 1,670万股` + `发行后总股本 6,670万股`，1,670 ÷ 6,670 = 25.04%）。

### 为什么纯文本解析取不到

1. **值本身很长且自带句号结构**。单元格内容是
   「1,670万股，占发行后总股本的比例为25.04%」——
   它包含两个答案（股数 + 比例），纯文本层会把它整行输出，
   但**「发行股数」这个标签在这行文本的上一行**，
   二者分处两个 chunk 的概率很高（p22 正文 483 字符 > CHUNK_SIZE 400）。
2. **15 行 × 2 列的键值表**里，标签列与内容列在文本层是两个连续的段落块；
   一旦检索只召回了包含内容、没召回标签的那一半，
   模型看到的就是一串孤立的「1,670万股，占发行后总股本的比例为25.04%」，
   无法确认这到底是「发行股数」还是「发行后总股本」。
3. 该表在 p22 与 p24 各有一份，键名不同（`发行股数` vs
   `发行股数及占发行后总股本比例`），**只有表格结构能保证键值配对**。

### 表格解析如何解决

表格块整表入库（`chunk_structure` 保证不切碎），入库文本形如：

```
【表格】四、本次发行情况
| 项目 | 内容 |
| --- | --- |
| 股票种类 | 人民币普通股(A股) |
| 发行股数 | 1,670万股，占发行后总股本的比例为25.04% |
...
```

标签与值处在同一行、同一个 chunk 内，行列对应关系显式可见。

## id 2｜本次募集资金拟投资项目

### 答案

> 仓储及物流中心、研发中心、电子商务平台、扩充产品种类和数量、
> 其他与主营业务相关的营运资金（共 5 个项目）

### 定位

- **物理页 22**，位于「五、募集资金用途」小节，正文引导句为
  「本次募集资金拟投资以下项目：」；
- 表格上方标题（由 `extract_caption()` 自动抽取）= **`本次募集资金拟投资以下项目：`**；
- 原始检出规格 6 行 × 9 列（合并单元格导致竖线误检），
  规范化后 = **6 行 × 3 列**：

```markdown
| 序号 | 项目名称 | 计划总投资(万元) |
| --- | --- | --- |
| 1 | 仓储及物流中心 | 3,393.40 |
| 2 | 研发中心 | 1,526.38 |
| 3 | 电子商务平台 | 2,492.78 |
| 4 | 扩充产品种类和数量 | 9,000.00 |
| 5 | 其他与主营业务相关的营运资金 | [ ◆ ] |
```

### 为什么纯文本解析取不到

这是 4 个问题中**最容易失败**的一个，原因有三层：

1. **答案是一个清单，不是一个值**。5 个项目分散在 5 行，
   纯文本分块会让它们跨越 chunk 边界。
   实测 p22 清洗后正文长度为 **483 字符**，`CHUNK_SIZE = 400`，
   该页必被切成 2 块；而这张表位于页面末尾 —— 5 个项目正好压在切分点上。
   top_k = 5 的重排结果里通常只出现其中一半，答案就会「只答 3 个项目」。
2. **文本层丢掉了「序号 ↔ 项目名 ↔ 投资额」的横向对应**。
   文本层输出是：

   ```
   序号
   项目名称
   计划总投资(万元)
   1
   仓储及物流中心
   3,393.40
   ```

   单看「1 / 仓储及物流中心 / 3,393.40」还能靠顺序推断，
   但第 5 行「其他与主营业务相关的营运资金」的金额是 `[ ◆ ]`（招股书占位符），
   一旦顺序推断被打断，模型极易把项目名与金额错配。
3. **同类干扰多**。全书「募集资金」出现 20+ 次（p6、p9、p22、p24、p30、p31、
   p139、p142、p144、p189…），纯文本检索很容易召回「募集资金总额」
   「募集资金净额」「募集资金投资使用安排」等其它表，答非所问。

### 表格解析如何解决

- 整表 1 个 chunk，5 个项目全部在同一 chunk 内，不存在「半张表」；
- 标题「本次募集资金拟投资以下项目：」前置入库，
  与问题中的「募集资金拟投资哪些项目」形成强词面重合；
- 该问题含「哪些」，命中 `_NUMERIC_CUES`，表格块加权 **1.35**，
  在同名干扰表中优先胜出。

## id 3｜存在控制关系的关联方（名称 / 持股比例 / 关系）

### 答案

> **赵马克，持股比例 42.35%，与本公司关系：公司控股股东**

### 定位

- **物理页 157**，位于「二、关联方及关联交易 → (一)关联方及关联关系 → 1、存在控制关系的关联方」；
- 表格上方标题 = **`1、存在控制关系的关联方`**；
- 原始检出规格 2 行 × 9 列，规范化后 = **2 行 × 3 列**：

```markdown
| 关联方名称 | 持股比例 | 与本公司关系 |
| --- | --- | --- |
| 赵马克 | 42.35% | 公司控股股东 |
```

### 为什么纯文本解析取不到

这是**三列强关联**的典型：问题同时要「是谁」「多少比例」「什么关系」
三个字段，三者必须严格同行对应。纯文本层的输出是：

```
关联方名称
持股比例
与本公司关系
赵马克
42.35%
公司控股股东
```

表头与数据被拆成两大段。因为该表只有一行数据，模型尚可靠顺序推断；
但**紧接着的下一张表（id 4）表头完全不在这里** ——
正文层在这一页连续输出两张表的表头与数据，
「关联方名称/持股比例/与本公司关系」与「企业名称/与本公司关系」
在文本流中彼此交错，模型很容易把 id 4 的公司名错误地配上「42.35%」
或把「公司控股股东」安到别的公司头上。

### 表格解析如何解决

表格块边界由 `find_tables()` 的闭合单元格决定，两张表被切成两个独立 chunk：

```
chunk A: 【表格】1、存在控制关系的关联方
         | 关联方名称 | 持股比例 | 与本公司关系 |
         | 赵马克 | 42.35% | 公司控股股东 |

chunk B: 【表格】2、不存在控制关系的关联方
         | 企业名称 | 与本公司关系 |
         | 融冰投资 | 持有公司股份5%以上的股东 |
         ...
```

标题前置让两张表在检索阶段就能被区分开，行列结构则保证三个字段不错配。

## id 4｜不存在控制关系的关联方企业

### 答案

> **融冰投资、武汉博润、上海博润、听音投资、联众聚源、力源贸易、普芯达**（7 家）
>
> （相邻小节另有「报告期内曾为关联方、目前已不存在关联关系」的
> 佰力电子、盈硅电子 2 家 —— 属于另一个小节，是否计入取决于口径，
> 本工单将其列为**加分项**而非必答项。）

### 定位

- **物理页 157**，位于「2、不存在控制关系的关联方」；
- 表格上方标题 = **`2、不存在控制关系的关联方`**；
- 原始检出规格 8 行 × 6 列，规范化后 = **8 行 × 2 列**：

```markdown
| 企业名称 | 与本公司关系 |
| --- | --- |
| 融冰投资 | 持有公司股份5%以上的股东 |
| 武汉博润 | 持有公司股份5%以上的股东 |
| 上海博润 | 持有公司股份5%以上的股东 |
| 听音投资 | 持有公司股份5%以上的股东 |
| 联众聚源 | 持有公司股份5%以上的股东 |
| 力源贸易 | 同一实际控制人控制的企业 |
| 普芯达 | 实际控制人近亲属控制的公司 |
```

### ⚠️ 本页的「陷阱」：紧邻一张表头完全相同、语义完全不同的表

翻到 **物理页 158**，紧接其后是第 3 小节：

```markdown
| 企业名称 | 与本公司关系 |
| --- | --- |
| 佰力电子 | 原为同一实际控制人控制的企业，2008 年对外转让 |
| 盈硅电子 | 原为同一实际控制人控制的企业，2008 年对外转让 |
```

表头与 id 4 的表**一字不差**，位置又是「上一页底部 → 下一页顶部」，
任何只依据「表头相同 + 位置相邻」的跨页合并规则都会把它们错误合并，
从而让 id 4 的答案多出两家**已经不属于关联方**的公司。
本工单的合并规则因此增加了第 4 条判据（标题是否为新编号小节），
明确**拒绝**这次合并，并在 `table_inventory.json` 中留下拒绝记录。

### 为什么纯文本解析取不到

1. **7 家公司是清单**，跨 chunk 丢行的问题与 id 2 同源；
2. **与 p158 的第 3 小节极难区分**。文本层里，
   「2、不存在控制关系的关联方」与「3、报告期内曾为关联方但目前已不存在关联关系的公司」
   只差一个编号，两家「已转让」公司跟 7 家现有关联方在文本流上首尾相接，
   模型很容易把 9 家混成一家名单；
3. **公司简称在正文中另有出现**。「融冰投资、听音投资、联众聚源、武汉博润和上海博润」
   在 p157 上半页的《避免同业竞争与利益冲突承诺函》段落里也出现过一次
   —— 纯文本检索很可能召回那段正文（它看起来更「像」自然语言的答案），
   但那段只列了 5 家，漏掉力源贸易与普芯达。

### 表格解析如何解决

- 表结构把「2、不存在控制关系的关联方」的 7 行锁定在一个 chunk 内，
  与第 3 小节的 2 行分属不同 chunk，标题不同、不会互相污染；
- 相较之下，召回 p157 上半页的承诺函正文只会答出 5 家 ——
  消融实验中若 A 组（不含表格）在 id 4 上失分，通常就是这个原因。

## 小结：4 个问题的共性

| 共性 | 说明 | 对应技术点 |
| --- | --- | --- |
| 答案都是「结构化事实」 | 股数+比例、项目清单、关联方三元组、企业清单 | 整表作为 1 个 chunk 入库 |
| 值很长且被标签限定 | `发行股数` → `1,670万股，占…25.04%` | 表头行保留 + 标题前置 |
| 清单类答案跨 chunk 就丢行 | p22 正文 483 字符 > CHUNK_SIZE 400 | `_block_to_single_chunk` 不切碎 |
| 同页/邻页存在高相似干扰表 | 发行概况出现两次；关联方两表表头相同 | 标题区分 + 表格块加权 1.35 |
| 表格本身会被抽错列 | 5 列表被抽成 9 列 | 全空列删除 + 表头错位修复 |

这五点决定了本工单的技术路线：
**表格抽取 → 网格规范化 → 标题前置 → 整表不切碎 → 表格块加权 → 精确度可量化**。
