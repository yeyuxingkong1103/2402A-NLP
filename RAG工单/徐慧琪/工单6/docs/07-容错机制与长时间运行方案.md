# 容错机制清单与长时间运行方案（工单06）

**工单编号**：人工智能NLP-RAG-混合检索任务
**对应硬性要求7**：必须给出容错机制清单（用户输入错误、文档解析失败、图像解析失败、
模型加载失败、Qdrant 连接失败、嵌入模型加载失败、Reranker 模型加载失败、Reranker 推理超时），
并给出长时间运行方案（日志轮转、内存监控、异常重启）。

> 本文所有机制均为**代码中已实现**的行为，逐条给出位置与实测现象，不写空头承诺。

## 一、容错机制清单

| # | 故障场景 | 系统行为（降级而非崩溃） | 实现位置 | 用户可见 |
| --- | --- | --- | --- | --- |
| 1 | **用户输入错误**（空问题、只有标点/空格、超长输入） | 空/空白问题直接返回友好提示不检索；查询解析失败（全是操作符）返回空结果；超长问题由 bge-m3 8192 token 上限截断 | `rag.ask` 空串分支、`fulltext.parse_query` 返回 None、`embedder.EMBEDDING_MAX_LEN` | 界面显示「请输入问题」/「无命中」 |
| 2 | **文档解析失败**（MinerU 子进程失败/超时） | 解析器自动回退 PyMuPDF 增强引擎；两条路都失败才报错。**本工单默认复用已落盘的解析产物，不重跑解析** | `src/pdf_parser.py`（上游复用）；`build_index.py --rebuild` 才走解析 | 建库日志打印实际使用的解析器 |
| 3 | **图像解析失败**（VLM 描述缺失/图未命中） | 图像块保留原占位文本进索引（不丢块），建库时**如实统计"命中 N / 未命中 M"**；图表题的替代路径：检索仍可命中同页正文 | `src/image_blocks.enrich_image_chunks` 返回统计；`build_index.py` 打印 | 建库日志 |
| 4 | **模型加载失败**（嵌入/Reranker，含权重缺失、显存不足、文件损坏） | 嵌入失败 → 检索报明确错误（含路径与处置建议，不再继续瞎答）；Reranker 失败 → **冷却 120s + 降级为召回序截断**，并在答案与界面标注「已降级」 | `embedder.get_model` 抛 `FileNotFoundError`+指引；`rerankers.get_model` / `rerank_detailed` | 界面 `🎯 精排算法 … ⚠️ 降级：原因` |
| 5 | **Qdrant 连接失败**（本地锁被占用 / 服务端不可达） | 本地模式**重试 3 次（间隔 3s）**，仍失败抛出**中文处置指引**（结束占用进程 或 切 server 模式）；检索侧捕获异常返回「检索失败：…」而答案不编造 | `src/vector_store.get_client`（本次新增）；`rag.retrieve` 的 try/except | 界面错误消息含明确出路 |
| 6 | **嵌入模型加载失败** | 同 #4；额外：模型路径不存在时提示 `python scan_local_models.py` 查看本机可用模型 | `src/embedder._spec` / `get_model` | 同上 |
| 7 | **Reranker 模型加载失败** | 同上；且**多模型容灾**：`bge-reranker-v2-m3` 与 `-ms` 两份同构权重在不同路径，可在界面切换避开损坏副本 | `config.RERANKER_MODELS`（3 个模型） | 界面「Reranker 模型」下拉 |
| 8 | **Reranker 推理超时** | LLM 重排器有总预算（`RERANK_TIMEOUT_S=8s`）+ 单条超时（4 路并发，每条 ≥2s）；超时/异常**保持召回序**并打印降级日志，不阻塞问答 | `src/rerankers._rerank_llm` | 界面显示精排耗时与降级状态 |
| 9 | **LLM（Ollama）不可用** | 生成失败 → **抽取式降级**（从上下文取证据句直接作答，标 `mode=extractive`）；Ollama 未启动时给出含 `ollama serve` 指引的错误 | `src/rag.ask` except 分支、`src/llm.resolve_model` | 答案 + 模式标注 |
| 10 | **生成内容不可信**（数字幻觉/书名号改写/时点错乱） | 生成后**确定性三重校验**（数字、表格行、书名号）+ 时点校验 → 触发一次定向重试 → 仍不合格则抽取式校正（`complete_numeric_list` / `complete_row_list`） | `rag.check_numbers/check_table_rows/check_quotes/check_chronology` + `complete_*` | `timings.retry` / `numeric_patch` / `row_patch` |
| 11 | **指代无法解析**（多轮） | 不猜：返回 `unresolved` 并**明确反问**请用户补充公司名 | `src/coref.py`（上游复用） | 界面提示 |
| 12 | **文档路由误判** | 限定文档后候选过少 → 自动**放开过滤全库重检**一次 | `rag.retrieve` 的 `fallback_opened` | 界面「文档路由」说明 |
| 13 | **多进程争用 Qdrant 本地库** | 见 #5；文档与 README 明确「本地嵌入式模式单进程独占」，压测采用单进程多线程 | `vector_store.get_client` + README §五 | 错误消息 + 文档 |
| 14 | **精排分打平导致排序翻转** | `RERANKER_TIE_EPSILON=0.01` 分桶，桶内用 RRF 名次裁决（噪声级分数差不参与排序） | `rerankers._sort_with_tiebreak` | 报告 §4.3 |

### 容错设计的两条原则

1. **降级必须可见**：任何降级都写进 `info`/`timings` 并在界面与报告中如实展示
   （`degraded`、`degrade_reason`、`retry`、`numeric_patch`、`mode=extractive`）。
   宁可让人看到"这次没精排"，也不静默假装。
2. **不编造**：检索失败就说失败，证据不足就答「根据已有资料无法确定」，
   抽取式兜底只允许使用上下文里出现过的原文片段。

## 二、长时间运行方案

| 关注点 | 方案 | 落地 |
| --- | --- | --- |
| **日志轮转** | 评估/压测脚本的日志统一落在 `logs/`，按**运行批次**命名（`eval_*.log`、`benchmark*.log`）；应用侧异常统一打印到 stdout 由 Streamlit/终端接管。生产化建议：用 `logging.handlers.RotatingFileHandler(maxBytes=50MB, backupCount=5)` 包裹 `print` 出口 | `logs/`、`scripts/run_all_evals.sh` |
| **内存/显存监控** | `benchmark_load.py` 内置采样线程：进程 RSS、系统内存、`torch.cuda.max_memory_allocated`（不可用时如实标「未测得」，不编造）；`rag._ensure_gpu_headroom()` 在加载大模型前排空显存并检查余量 | `benchmark_load.ResourceSampler`、`src/rag.py` |
| **异常重启** | ① 交互层：Streamlit 单次请求异常被 `rag.ask` 捕获并转成错误文案，**进程不退出**；② CLI 层：入口统一 `bootstrap.run_with_large_stack(main)` 包裹，异常原样抛回主线程并以非 0 退出码结束（便于 `while` 守护脚本重启）；③ 长跑建议：`nohup streamlit run app.py &` + 进程守护（Windows 用任务计划/`nssm`，Linux 用 `systemd Restart=always`） | `src/bootstrap.run_with_large_stack`、各脚本 `__main__` |
| **模型常驻** | Ollama `keep_alive=30m` 避免每题冷启动；`rag.warmup()` 一次性预热 embedding/reranker/BM25/**倒排索引**/LLM（实测冷启动 35~61s，随机器负载浮动；热态单题 1.2~2.0s） | `config.OLLAMA_KEEP_ALIVE`、`rag.warmup` |
| **索引重建** | 倒排索引持久化 `data/index/fulltext.pkl`（23 MB），启动优先复用；语料变更后 `fulltext.refresh()` 或重跑 `build_index.py` | `src/fulltext.build(persist=True)` |
| **会话与缓存** | 多轮会话表 LRU 上限 `DIALOGUE_MAX_SESSIONS=64`；答案缓存 `ANSWER_CACHE_SIZE=128`；改写缓存 256 —— 长跑下内存不无界增长 | `src/dialogue.py`、`src/rag.py` |
| **磁盘** | Qdrant 229 MB + 倒排 23 MB + 分块 38 MB + 解析产物 72 MB + 图 35 MB ≈ 400 MB（见 README 环境表）；日志按批次清理 | — |
| **并发** | 单进程多线程（Qdrant local 限制）；压测见 `docs/08-高并发压测报告.md`。若要更高并发：`QDRANT_MODE=server` + 多 worker | `config.QDRANT_MODE` |

## 三、运维速查（故障 → 处置）

| 现象 | 处置 |
| --- | --- |
| `Storage folder … is already accessed by another instance` | 结束占用该目录的进程（`tasklist | findstr python` → `taskkill /PID <pid> /F`），或改用 `QDRANT_MODE="server"` |
| 精排一直显示「已降级：模型不可用」 | 检查 `D:\model\reranker` 是否存在；或换 `bge-reranker-base`（随工程落盘，位于 `data/models/`） |
| 首题很慢（30s+） | 未预热。界面点「预热模型」或程序调用 `rag.warmup()` |
| 答案含"根据已有资料无法确定" | 检索 0 命中或上下文不含证据：确认 `python build_index.py` 已跑完（8010 点） |
| 数字答错/漏行 | 查看 `timings` 里的 `retry/numeric_patch/row_patch` 是否触发；未触发说明校验规则未命中该形态，需扩充金标或规则 |
