## 一、背景与目标

### 1.1 V2 遗留的靶点

V2 完成后，[指标对比文档](../../指标对比文档.md)明确了三类仍未解决的问题：

| 遗留问题 | V2 实测证据 | V3 对策 |
| --- | --- | --- |
| **R09 三版全 0** | 答案块 `d1b17a6c548cd4dc_0010` **根本不在候选池内**（稠密/稀疏 top-20 均无） | **查询改写**（唯一杠杆，见 2.5） |
| 答案块排序靠后 | `_0008`（软件质量特性）稠密仅排第 **10** | **BGE-reranker 重排** |
| 同义改写检索 | 稀疏通道只能字面命中 | 查询改写（多查询融合） |

### 1.2 本轮必须先修的两个缺陷

设计前的技术探针暴露了两个**必须先修**的问题，否则 V3 的效果无法被正确度量：

| 缺陷 | 严重性 | 说明 |
| --- | --- | --- |
| **空答案 bug** | 高 | 推理模型下 `content` 为空被静默返回，已实证 2 例，其中一例（G02）污染了 V2 评测 |
| **评测口径缺陷** | 高 | 检索指标只按 `page_no` 匹配，跨页块的次页命中被漏判，R09 因此**永远不可能通过** |

详见第三章与第四章。

### 1.3 V3 目标

1. 修复上述两个缺陷（前置条件）
2. 接入 **BGE-reranker** 做候选池内重排，提升 `recall@1` / `MRR`
3. 实现**查询改写**模块，作为**对照实验分支**，验证其能否修复 R09
4. 完善 Trace 日志：记录查询改写与重排的**输入输出**
5. 增加异常捕获、超时控制、输入校验，优化会话记忆逻辑
6. 更新 V3 架构图，汇总 V1/V2/V3 指标对比

### 1.4 明确不做

| 不做 | 原因 |
| --- | --- |
| 重写 V1/V2 代码 | ADR-010/018：增量扩展，且 V1 冻结以保基线可归因 |
| 改动前端交互 | 任务书 V3 约束「用户前端依旧简洁」 |
| 改动 API 契约 | ADR-010：仅允许新增响应字段 |
| 暴露 Trace 查询接口 | N5 约束 |
| 把查询改写设为默认开启 | 其耗时（3.2~4.4s）会使端到端超出 N3（见第五章） |

## 二、已实测证实的技术前提

> 以下均为 2026-09-20 在本机实跑验证的结论，非文档推断。

### 2.1 重排模型可直接加载，不需要 FlagEmbedding

`D:/桌面/模型/bge-reranker-v2-m3` 含 `model.safetensors`（2.27 GB），`sentence-transformers` 的 `CrossEncoder` 可直接加载本地路径：

```
CrossEncoder("D:/桌面/模型/bge-reranker-v2-m3", device="cpu", max_length=N)
```

加载耗时约 0.7 秒（权重已缓存）。与 ADR-014 同理，**无需引入 FlagEmbedding**。

### 2.2 重排耗时随输入长度近似线性

实测在同一批真实候选（20 个，平均长度 1426 字符）上：

| `max_length` | 重排 20 个候选 | 单对耗时 |
| --- | --- | --- |
| 512 | 15.68 s | 0.784 s |
| 256 | 7.77 s | 0.389 s |
| 128 | 4.13 s | 0.207 s |

单独实测 **10 个候选 × max_length=256 = 4.21 s**（0.421 s/对）。

**这是本设计的核心约束**：重排耗时直接决定能否满足 N3（首次提问 ≤ 8 秒）。

### 2.3 重排确实有效

对 R09 的 20 个候选重排后，排序发生了有意义的变化——原本排靠后的「软件质量特性」相关块被提到第 1 位：

| 重排后 | 分数 | 页码 |
| --- | --- | --- |
| 1 | 0.7424 | 第 6 页（`_0008`，含 6 个质量特性） |
| 2 | 0.6434 | 第 20 页（表 C.1） |
| 3 | 0.5235 | 第 10 页（表 A.1） |

即：重排能在**候选池内部**重新排序，对「答案已召回但名次靠后」的情形有效。

### 2.4 查询改写可行，但耗时显著

`deepseek-v4-flash` 能把问题改写成利于字面检索的关键词序列，实测：

| 输入问题 | 改写结果 | 耗时 |
| --- | --- | --- |
| GB/T 32904 中，功能充分性属于哪个质量特性的子特性？ | `GB/T 32904 功能充分性 功能性 质量特性 子特性 属于` | 3.21 s（max_tokens=3072） |
| 同上 | `GB/T 32904 功能充分性 子特性 所属 质量特性 功能性 功能完备性` | 4.44 s（max_tokens=1024） |

### 2.5 ⭐ R09 的答案块根本不在候选池内（查询改写的唯一依据）

这是决定「为什么必须做查询改写」的关键实测。

对 R09 的问题，用 V2 的完整检索链路取候选池（稠密 top-20 + 稀疏 top-20 → RRF 融合 top-20），检查覆盖第 7 页的 4 个块是否在其中：

| chunk | 在候选池中？ |
| --- | --- |
| `d1b17a6c548cd4dc_0010`（**含答案**） | ❌ 不在 |
| `d1b17a6c548cd4dc_0011` | ❌ 不在 |
| `d1b17a6c548cd4dc_0012` | ❌ 不在 |
| `d1b17a6c548cd4dc_0013` | ❌ 不在 |

候选池 20 个块的页码分布为 `{1, 5, 6, 8, 10, 11, 14, 15, 16, 17, 18, 20, 21, 25, 27, 29, 30}` —— **第 7 页一个都没有**。

**由此可推出两个结论**：

1. **重排无法修复 R09** —— 重排只能在候选池**内部**排序，池子里没有答案块。
2. **修正评测口径也无法修复 R09** —— 口径修的是「匹配规则」，而问题出在「压根没召回」。

**唯一可能的杠杆是查询改写**（改变送进检索的文本，从而改变召回集合）。这是 V3 必须实现该模块的根本原因，也是它被列为对照实验分支的价值所在。

### 2.6 ⚠️ `deepseek-v4-flash` 是推理模型

**这是一个此前未被发现的集成缺陷的根源。**

该模型先输出 `reasoning_content`（推理过程），再输出 `content`（正式答复）。实测：

| `max_tokens` | `finish_reason` | `content` | 推理内容长度 |
| --- | --- | --- | --- |
| 120 | `length` | **空字符串** | 被截断 |
| 600 | `length` | **空字符串** | 被截断 |
| 1024 | `stop` | 正常 | 约 1268 字符 |
| 3072 | `stop` | 正常 | 约 979 字符 |

而 `ChatLLM.chat()`（`backend/llm_client.py:77`）**只读 `message.content`，且不检查 `finish_reason`**。当推理过程吃光 token 预算时，返回空字符串且**无任何报错**。

## 三、前置修复 A：空答案 bug

### 3.1 实证

数据库中已存在 2 条空答案：

| id | 链路 | 问题 | 时间 |
| --- | --- | --- | --- |
| 29 | v1 | 网络数据处理中对个人信息处理有什么基本要求？（G05） | 2026-09-18 |
| **111** | **v2** | 优秀级（四级）的数据中心应当具备什么条件？（**G02**） | 2026-09-20 |

日志统计：129 次生成中 **10 次**输出 token 触顶（1024）。

**关键影响**：id=111 正是 V2 评测中 RAGAS 判为 `nan` 而被剔除的 G02 样本。此前将其解释为「RAGAS 裁判不稳定」，实测证明**是答案本身为空**——即该样本的 `nan` 是系统缺陷的表现，而非评测工具的噪声。

### 3.2 修复设计

| 项 | 方案 |
| --- | --- |
| `content` 为空且 `finish_reason == "length"` | 抛 `LLMError`，由既有降级路径处理 |
| 用户可见结果 | 返回固定提示「抱歉，答案生成服务暂时不可用，请稍后重试。」——**不向用户返回 `reasoning_content`**（推理内容是模型思考过程，质量不等同于正式答复） |
| 后台日志 | **保留 `reasoning_content` 全文**（截断至合理长度），便于排查「为什么没生成出答案」 |
| 提高预算 | `LLM_MAX_TOKENS` 由 `1024` 提升至 **4096** |
| 记录 `finish_reason` | 在生成完成日志中增加该字段，便于事后统计截断比例 |

**边界情况**：`finish_reason == "stop"` 但 `content` 为空（模型确实没输出内容）——同样视为异常，记 WARNING 并返回同样的提示。

## 四、前置修复 B：评测口径缺陷

### 4.1 缺陷描述

`scripts/ragas_eval.py:138` 构造检索命中页时**只取 `page_no`**：

```python
retrieved_pages = [(h.get("file_name", ""), int(h.get("page_no", 0))) for h in hits]
```

而 `page_no` 的语义是「chunk 覆盖的**首个**内容块页码」（ADR-006），chunk 可以跨页。当答案正文位于跨页块的**后半部分**时：

- 检索命中该块 → 评测记为首页
- 金标准标的是内容**实际**所在页
- → **永远匹配不上**

### 4.2 R09 的完整证据链

R09「GB/T 32904 中，功能充分性属于哪个质量特性的子特性？」，金标准 `32904:7`。

全库中「功能充分性」**只出现在一个块**里。覆盖第 7 页的块共 4 个：

| chunk | `page_no` | `page_nums` | 含「功能充分性」 |
| --- | --- | --- | --- |
| `d1b17a6c548cd4dc_0010` | **6** | **[6, 7]** | ✅ **答案在此**（位于块内 65% 处） |
| `d1b17a6c548cd4dc_0011` | 7 | [7] | ❌ |
| `d1b17a6c548cd4dc_0012` | 7 | [7, 8] | ❌ |
| `d1b17a6c548cd4dc_0013` | 7 | [7, 8] | ❌ |

**答案物理上在第 7 页，但它所在的块被记为第 6 页；三个被标为第 7 页的块都不含答案。**

**⚠️ 归因更正（2026-09-20，重跑后实测）**

本节初稿据此推断「R09 的 0.00 **与检索能力无关**，是口径缺陷所致」。**该推断是错的**，重跑后已证伪：

- 口径缺陷**确实存在**，且它**确实会**掩盖「命中 `_0010`」的成功（旧口径下该块记为第 6 页，匹配不上金标准第 7 页）
- 但在**本评测集上它一条也没掩盖到**：实测把同一批检索输出用两种口径重放，12 条样本逐条变化 **0 条**。原因是新口径是旧口径的**严格超集**（127 块全部满足 `page_no == page_nums[0]`），只可能升不可能降，而本数据集的命中**全部依赖主页码**
- R09 的 0.00 因此是**真实的召回失败**：第 7 页对应的块（`_0010` 与 `_0011`/`_0012`/`_0013`）**一个都没进 top-10**

**正确的靶点归属**（与 2.5 节一致）：R09 是「答案块不在候选池」的问题，**唯一杠杆是查询改写**。重排救不了它，修正口径也救不了它。

**该口径修正仍然值得做**：它让指标**正确**（跨页块的次页命中不再被漏判），只是这个特定数据集恰好没触发。保留它，但**不得声称重跑带来了分数提升**。

**影响面**：全库 **29/127（23%）**为跨页块，检索指标被系统性低估。

### 4.3 修复设计

`retrieved_pages` 改为携带**完整页码列表**，匹配规则改为「chunk 覆盖的**任一页**命中金标准即算命中」。

**配套要求（关键）**：由于该修复会改变指标的绝对值，**必须重跑全部三个评测点**，保证 V1 / V2 / V3 在**同一口径**下可比：

| 评测点 | 处理 |
| --- | --- |
| 原始基线（M3） | **必须重跑检索**（不可从存档重算，见下方说明） |
| V1 新索引 | 重跑 |
| V2 | 重跑 |
| V3 | 新跑 |

**为什么基线不能从存档重算（设计修正，2026-09-20）**

本节初稿曾写「可直接对已保存的 `retrieved_pages` 重算」，**该说法是错的**，实测核对后更正：

1. 存档里的 `retrieved_pages` 是 `"文件名:页码"` 字符串，**只含主页码** —— 正是本次要修掉的有损格式，拿它算不出「chunk 还覆盖了哪些页」
2. 存档**未记录 `chunk_id`**，无法反查每条的 `page_nums`
3. 旧索引本身已不存在（V2 重建时被覆盖），`.chunks.json` 也被 `--force` 重写过

因此基线**只能靠重建「V1 原始索引」后真跑一遍检索**来重算。好在这是**精确可行**的：6 个图片块的新 `content` = 旧 `content` + `"\n[视觉解析] " + 描述`，剥离描述即可还原；其余 121 块内容未变，且 `page_nums` 在新旧索引间完全一致（`compose_block_content` 只改 content）。

**文档要求**：修正后的指标**直接取代旧数字**写回[指标对比文档](../../指标对比文档.md)，不并列保留两套（避免读者误用失效数字）。但**必须保留修正说明**——记录「旧口径的缺陷是什么、为什么修正、影响面多大（29/127 个跨页块）」，使数字的变化可追溯，而不是无声替换。

同理，[基线评测报告](../../基线评测报告.md)（M3 产出）中的指标需按新口径重算并更新，并注明本次重算的日期与原因。

## 五、架构与数据流

### 5.1 主链路（默认，守 N3 ≤ 8s）

```
提问
 │
 ├─ 会话历史（Redis）→ 查询缓存（命中则直接返回）
 │
 ▼
BGE-M3 一次 forward
 ├── 稠密向量 ──→ Milvus search_dense  ──→ 候选 20 ─┐
 └── 稀疏权重 ──→ Milvus search_sparse ──→ 候选 20 ─┤
                                                    ▼
                              RRF 融合（k=settings.rrf_k）→ 候选 10
                                                    ▼
                          BGE-reranker 重排（10 对 × max_length=256）
                                                    ▼
                                                top-5
                                                    ▼
                        MySQL 回填页码 → deepseek 生成 → 答案 + 来源
```

**耗时预算（全部为实测值）**：

| 环节 | 实测 |
| --- | --- |
| 检索（稠密 + 稀疏 + 融合） | ~0.4 s |
| 重排（10 × 256） | **4.21 s** |
| 答案生成 | ~2.5 s |
| **合计** | **≈ 7.1 s ≤ 8 s** ✅ |

### 5.2 增强分支（对照实验，默认关闭）

```
提问 → 查询改写（LLM，~3.5s）→ 原问题 + 改写查询 多路检索 → RRF 融合
                                                              ↓
                                                        重排 → top-5 → 生成
```

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `QUERY_REWRITE_ENABLED` | **`false`** | 开启后启用上述分支 |

**开启后耗时约 10.5 秒，超出 N3**。该分支**仅用于对照实验**，其耗时与评测结果单独成节写入文档，**不计入主口径**。

**设计理由**：R09 的答案块不在候选池内（见 2.5 的实测），重排无法补救；查询改写是唯一的杠杆。但它太贵，故作为可选分支保留，让「能力」与「性能目标」各自成立。

## 六、模块设计

### 6.1 新增文件

#### `backend/reranker.py`

**职责**：BGE-reranker 封装，线程安全懒加载单例（与 `embedder.py` 同构）。

**接口**：

```python
class BGEReranker:
    def rerank(self, query: str, candidates: Sequence[Dict[str, Any]],
               *, top_k: Optional[int] = None) -> List[Dict[str, Any]]
```

- 输入候选为 V2 `retrieve()` 的输出结构（至少含 `content`）
- 返回按重排分数降序的候选列表，**保留原有全部字段**，并新增 `rerank_score`
- `max_length` 与 `batch_size` 可配置

**降级**：模型加载失败或推理异常时，抛 `RerankerNotAvailableError`；**调用方须捕获并退回 RRF 原顺序**，不得让重排故障中断问答。

#### `backend/rag_pipeline/query_rewrite.py`

**职责**：把用户问题改写为利于字面检索的关键词序列。

**接口**：

```python
class QueryRewriter:
    def rewrite(self, question: str) -> List[str]
```

- 返回改写查询列表（失败或关闭时返回空列表）
- **超时控制**：超过 `QUERY_REWRITE_TIMEOUT` 即放弃改写
- **降级**：任何异常都返回空列表，调用方只用原问题检索

#### `backend/rag_pipeline/v3_pipeline.py`

**职责**：V3 链路。**继承 `V2Pipeline`**，仅覆盖 `retrieve()`：

```
V3Pipeline(V2Pipeline):
    PIPELINE_NAME = "v3"
    def retrieve(...)
        # 1) 可选：查询改写（QUERY_REWRITE_ENABLED）
        # 2) 复用 V2 的稠密+稀疏+RRF 逻辑（多查询时对多路结果统一融合）
        # 3) 可选：重排（RERANK_ENABLED）
```

**关键设计**：V2 的检索逻辑（一次 forward、双路检索、RRF、MySQL 回填）要被复用而非复制。实现时把 V2 的「候选生成」部分保持原样，V3 在其前后插入改写与重排两步。

> **约束**：`v1_pipeline.py`、`v2_pipeline.py` 均**不修改**（ADR-018 的冻结策略扩展至 V2）。

### 6.2 修改文件

| 文件 | 改动 |
| --- | --- |
| `backend/llm_client.py` | `chat()` 增加 `finish_reason` 检查与空内容处理；日志记录 `reasoning_content` |
| `scripts/ragas_eval.py` | 检索匹配改用完整页码列表 |
| `backend/config.py` / `.env` / `.env.example` | 新增重排与改写配置项；`LLM_MAX_TOKENS` 提高到 4096；`PIPELINE_VERSION` 默认改 `v3` |

| `backend/rag_pipeline/__init__.py` | 无改动（v3 入口已预留） |

## 七、关键实现细节

### 7.1 重排的输入构造

- 每对为 `(query, candidate["content"])`
- 传入改写后的查询（若启用改写）还是原问题？——**使用原问题**。理由：改写查询是为**检索**（字面匹配）优化的关键词串，不是自然语言问题；重排模型是在自然语言问答数据上训练的，用原问题更契合其训练分布。

### 7.2 重排与 RRF 的关系

重排**替代** RRF 作为最终排序，而非叠加：

```
RRF 负责「把两路候选合并成一个候选池」（召回）
重排负责「在这个池子里排出最终顺序」（排序）
```

RRF 的融合分数仅用于**选出送入重排的候选**，不参与最终排序。原因：RRF 分数与重排分数尺度完全不同，混合无依据。

### 7.3 多查询检索的融合

启用改写时，候选来源从 2 路（稠密+稀疏）变为 2N 路（每个查询 × 2 通道）。统一用 `rrf.fuse()` 融合：

- 天然支持任意通道数
- 基于名次，免疫不同查询的分数尺度差异
- **Trace 需逐通道记录**，便于分析「是改写查询还是原问题召回了目标块」

### 7.4 Trace 日志要求

| stage | 记录内容 |
| --- | --- |
| `v3_query_rewrite` | **原问题 + 改写结果（全部）+ 耗时**；失败时记录失败原因 |
| `v3_dense_retrieve` / `v3_sparse_retrieve` | 同 V2（逐查询、逐通道） |
| `v3_rrf_fuse` | 融合结果 + 各通道名次 |
| `v3_rerank` | **重排前后顺序对比 + 每条候选的 rerank_score**；降级时记录降级原因 |

**重排前后对比**是本版最有价值的 Trace：它直接回答「重排把哪个块提上来了」，是归因分析的依据。

### 7.5 稳定性防护清单

| 项 | 设计 |
| --- | --- |
| **重排异常** | 捕获 `RerankerNotAvailableError` 及所有异常 → 退回 RRF 顺序，记 WARNING，**问答继续** |
| **改写异常/超时** | 同上 → 只用原问题检索 |
| **重排超时** | `RERANK_TIMEOUT`（默认 30s）；超时退回 RRF 顺序 |
| **输入校验** | 问题去除首尾空白后不得为空；长度 1–500（已有）；拒绝纯空白、纯符号输入 |
| **LLM 空响应** | 见第三章（抛 `LLMError` → 降级提示） |
| **会话记忆** | 复查 `SESSION_MAX_TURNS=5` 的 `ltrim` 逻辑；补充多轮场景测试，确认超出轮数时旧轮次被正确淘汰 |

**统一原则**：**任何增强环节失败都必须降级到 V2 的行为，绝不允许中断问答**。这是「加分项不得变成减分项」的底线。

## 十一、风险与回退

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 重排使端到端超 N3 | 违反性能要求 | 已实测 7.1s；`RERANK_CANDIDATE_K` / `RERANK_MAX_LENGTH` 可调；`RERANK_ENABLED=false` 即刻回退 |
| 重排反而降低指标 | 迭代失败 | 如实记录，不调参凑数；`RERANK_ENABLED=false` 回退 |
| 评测口径修正后基线数字上升 | 被质疑「换尺子」 | 文档中**两套口径并列**，说明修正依据与影响面 |
| 改写分支超时拖垮服务 | 稳定性 | 严格超时 + 异常降级；默认关闭 |
| 提高 `LLM_MAX_TOKENS` 增加成本 | 费用上升 | 仅在推理需要时才用满；实际输出长度受答案长度约束 |
| 重排模型内存占用（2.3 GB） | CPU 环境内存压力 | 懒加载；与 BGE-M3（2.3 GB）合计约 4.6 GB |
