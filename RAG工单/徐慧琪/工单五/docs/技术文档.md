## 1. 背景与目标

### 1.1 上游

| 工单 | 内容 | 本工单如何使用 |
| --- | --- | --- |
| 01 | 基于 PDF 的问答系统（单文档基线） | 作为「无表格优化」对比基线（子进程只读调用） |
| 02 | 问答系统优化（父子块 / 混合检索 / 重排 / 查询改写） | 链路基座 |
| 03 | 表格解析及检索优化（多文档 + 表格结构化） | **本工单的直接基线**：代码树与索引自工单3 复制，`工单3/` 目录保持**只读**，作为「优化前」对比臂 |
| 04 | 图像内容解析（CLIP） | **不采用**（CLIP 中文文图对齐实测失效 136/162，且违反禁止下载约束） |
| **05（本工单）** | **Query 理解优化：多轮对话** | 新增指代消解与省略补全，让追问可用 |

> 注意：工单5 的基线是**工单3**（不是工单4）。工单4 的图像链路经评估不可用，见 `docs/07` 第二节。

### 1.2 本工单的核心变化

**给单轮问答系统加上多轮对话能力**：用户用「他」「这个公司」「那 XX 公司呢」连续追问时，
系统结合对话历史把**省略/指代后的短问题补全成完整独立问题**，再走原有的检索与生成链路。

顺带解决两件事：

1. 删除工单3 遗留的**硬编码消歧**（把「该公司/其/公司」一律替换成第一家公司）——
   多文档下它会**答成另一家公司**，见 `docs/03` §3.1 的逐轮实证；
2. 服务验收 Q5 的**组织结构图解析**（矢量几何路线，零模型、确定性）。

### 1.3 验收指标

| 指标 | 目标 | 实测 |
| --- | --- | --- |
| 5 轮连续对话 | 逐轮答对 | **5/5**（全部通过），最大 1998ms |
| 20 轮扩展评测事实命中率 | ≥ 90% | **0.9062**（单轮基线 0.8125） |
| 响应时间 | ≤ 3 秒 | 验收最大 1998ms；20 轮 p90 2407.1ms，≤3s 占比 **1.0** |
| 多语言 | 中英双语，含指代 | 英文问句**按英文作答**（3/3 轮）；指代实体准确率 **1.0**；代价是中文专名被音译（§10 第 10 条） |
| 容错 | 指代无法解析不猜 | `unresolved` + 明确反问，反问率 1.0 |
| 高并发 | 稳定 | 并发下**不崩、0 失败**，但 3 路起**超 3 秒**（§10 第 1 条） |

## 2. 技术选型

### 2.1 为什么是这套组合

| 环节 | 选型 | 理由 |
| --- | --- | --- |
| PDF 解析 | **MinerU 3.4.5（pipeline）** | 唯一能同时给出**版面结构 + 表格 HTML** 的本地方案；模型与本机快照匹配，无需下载 |
| 表格兜底 / 图形复核 | **PaddleOCR-VL**（独立 venv 子进程） | 主环境未装 paddle，子进程零污染（本项目**实测它无法转录组织结构图**，见 `docs/07` §5） |
| 向量库 | **Qdrant**（local 模式） | 工单指定；本机无 Docker，嵌入式模式 API 一致，起服务后改一行配置切换 |
| Embedding | **bge-m3**（1024 维，CUDA） | 中英双语、长文本友好、本机已有 |
| 重排 | **bge-reranker-v2-m3** | cross-encoder，对"数字/专名"这类精确匹配的排序提升明显 |
| **改写判定** | **Ollama qwen2.5:0.5b** | 受约束子任务（候选二选一）实测可靠且快（0.05–0.25s） |
| **改写生成** | **Ollama qwen2.5:3b** | 省略补全只有 3b 能做（0.5b 会复述指令，实测） |
| 界面 | **Streamlit** | 开发快、原生支持 `st.chat_message` / `st.chat_input` |

### 2.2 本机环境实测（决定选型的依据）

| 项 | 实测 |
| --- | --- |
| Docker | **未安装** → Qdrant 用 local 模式 |
| MinerU | 独立 venv `D:\model\mineru-venv` 可用；模型本地快照 |
| PaddleOCR-VL | venv `D:\model\Paddle-OCR\venv` 可用；但对组织结构图**整页判为图像块、无文字输出** |
| 显存 | RTX 4060 Laptop 8GB；bge-m3 + reranker + qwen2.5:3b 需**分阶段加载**（见 §7.3） |
| 视觉大模型 | **本机无 CLIP 类可用模型**（`docs/01` 扫描结论） |
| Windows 栈 | 主线程栈约 1MB，加载 bge-m3 会触发导入期栈溢出（exit 139）→ 所有入口走 `bootstrap.run_with_large_stack` |

### 2.3 硬约束：禁止下载任何模型

- `src/bootstrap.py` 在**任何模型库导入之前**设置 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1`
  等离线开关——**漏写 `local_files_only=True` 的调用路径会直接失败，而不是偷偷联网**；
- 所有 `from_pretrained` 显式传 `local_files_only=True` 与本地绝对路径；
- MinerU 子进程注入 `MINERU_MODEL_SOURCE=local`；PaddleOCR 子进程注入 `PADDLE_PDX_MODEL_SOURCE=local`；
- 不出现 `snapshot_download` / `hf_hub_download` / `modelscope.download` / `ollama pull`。

## 3. 系统架构

### 3.1 在线问答（★ = 本工单新增/改造）

```
用户追问（中文/英文）
 │
 ├─ ★ dialogue   对话状态：focus_company（焦点公司）+ last_aspect（上一信息点）
 │               历史：turns 全量留痕 / 送 LLM 的滑动窗口 3 轮 / 超窗压成结构化摘要
 │
 └─ ★ coref      四层消解（L0 直通 → L1 检测 → L2 判定 → L3 生成 → L4 兜底）
       └─ 6 条校验不过 → L4 规则兜底；无候选实体 → unresolved（明确反问，不猜）
 │
 ▼ 改写后的独立问题（缓存 key = 改写后问题 + 焦点公司）
【工单3 既有链路】
 doc_router（公司名 → 限定 source）
   └─ query_rewrite.analyze（意图/分解/扩展；**已删除**硬编码消歧）
       └─ retriever.search_multi（向量 top-30 + BM25 top-30 → RRF k=60）
           └─ reranker.rerank（top-20 → FINAL_TOP_K）
               └─ ★ context.expand_parents
                    表格命中 → 按 table_id 还原整表
                    ★ 组织结构图命中 → 注入子树 + 聚合结论
                    正文命中 → 子块展开父块 + 以命中句为中心裁剪
                 └─ llm.chat（qwen2.5:3b, temperature=0）
                     └─ 三重校验（数字 / 表格行 / 书名号）→ 定向重试 → 抽取式降级
                         → 答案 + [n] 引用（PDF/页/表格行/**组织图节点路径**）+ 分阶段耗时
```

### 3.2 离线建库

```
两份 PDF
  └─ pdf_parser.parse_pdf（MinerU pipeline；失败回退 PyMuPDF 增强引擎）
       ├─ chunker        标题层级 → 父子块（子块 300–450 字检索 / 父块 ≤1800 字上下文）
       │    └─ 表格 → table_parser（HTML→矩阵/表头/kv 判定/质量分）→ table_chunker（表头块+行级块）
       └─ ★ build_orgchart / build_index 自动补回
            组织图矢量解析 → 建树 → 校验 29/28/单根 → 30 个块（1 整树 + 29 节点）
  └─ embedder（bge-m3）→ vector_store.upsert（Qdrant local，collection `zhaogu_v5_mt`）
```

> **为什么工单5 用自己的 collection**：工单3 的 `zhaogu_v3_table` 必须保持只读、
> 原样参与对比，两个库若同名会互相覆盖。

## 4. 多轮 Query 理解（本工单核心设计）

### 4.1 为什么不做端到端自由改写

这是本工单**最重要的选型依据**，来自实测（设计文档 §2.2）：

| 任务形式 | 0.5b | 3b |
| --- | --- | --- |
| 直接改写整句（history + question → 独立问题） | ✗ 原样吐回 | ✗ 「他」→「这个公司」 |
| 只判定「指哪家公司」（开放） | ✓ | ✓ |
| 二选一约束（给定候选公司） | ✓ | ✓ |
| 填空替换代词 | ✓ | ✓ |
| 省略补全「那 XX 公司呢？」 | ✗ 复述指令 | ✓（0.49s） |
| 英文指代 | ✗ 原样吐回 | ✓ |

**结论**：瓶颈是**任务粒度**，不是模型能力。故拆成
「规则定位 + LLM 受约束改写 + 规则兜底」的分层结构，而不是端到端改写。
分工由实测决定：判定用 0.5b、生成用 3b，**唯一候选时连判定都省掉**。

### 4.2 对话状态只保留两个量

| 字段 | 作用 | 更新的时机 |
| --- | --- | --- |
| `focus_company` | 指代消解的目标（Q2/Q3） | **只在用户点名公司时**更新，其余轮继承 |
| `last_aspect` | 省略补全的模板（Q4） | 抽到信息点时更新；代词轮保持上一轮的值 |

保存历史长度的手段（工单硬性要求 1）：`turns` 全量留痕（评测需要）+
送 LLM 的滑动窗口（3 轮）+ 超窗轮次压成「哪家公司：问了什么」的结构化摘要（规则拼接，零延迟）。

### 4.3 改写校验器（6 条，逐条对应实测失败模式）

| # | 规则 | 针对 |
| --- | --- | --- |
| 1 | 非空、长度 ≤ 120 | — |
| 2 | 不等于原文（`passthrough` 除外） | 未改写 |
| 3 | 指代消解必须含某个候选实体 | 改了个寂寞 |
| 4 | 不得残留同类代词 | **失败模式 1**：3b 把「他」换成「这个公司」 |
| 5 | 与指令模板 4-gram 重合率 ≤ 0.5 | **失败模式 2**：0.5b 复述指令 |
| 6 | **最小编辑**：原文去掉代词后必须是改写结果的子序列 | **失败模式 3**：3b 塞入不存在的公司名并吃掉原文 |

失败模式 3 是**跑三方评测才发现的**：英文题 `d2_person_pronoun_en` 被 3b 改写成
`…did Microsoft participate in that won t武汉兴图新科…Award?`——
既塞进一个不存在的公司（Microsoft），又吃掉原文的 "the"，而旧校验器**全票放行**，
导致检索 0 命中。该轮是 20 轮里**唯一输给单轮基线**的一轮。
修复后走 L4 规则替换（确定性且正确），回归测试固化在 `tests/test_coref_resolve.py`。

### 4.4 接入 RAG 的三处关键改动

| 改动 | 原因 |
| --- | --- |
| `rag.ask(state=...)` / 新增 `ask_turn()` | 多轮入口；`ask_turn` 负责把改写留痕回填进 `Turn` |
| 缓存 key 改为「改写后问题 + 焦点公司」 | 同一句「他参与的哪个工程获奖了？」在不同会话指不同公司，旧 key 会**串味** |
| `total_ms` 计入改写耗时 | 否则时延系统性少算约 200ms/代词轮，3 秒验收失真 |

### 4.5 UI（`app.py`）

新增「🧠 多轮对话」页（第 2 个页签）：`st.chat_message` 气泡 + `st.chat_input`，
每轮可展开「Query 理解（改写过程）」看**原问题 → 独立问题 + 改写方式 + 指代实体**，
支持 👍/👎、重新生成、清空会话。

两处实现细节（踩坑得来，见 §5）：

- **会话 id 用 uuid**：`DialogueState` 存在**进程级**会话表里，
  若所有浏览器会话共用一个固定 id，两个标签页会共用一段对话历史；
- **重新生成要重建状态**：只回退答案不回退焦点，被丢弃那轮的焦点会残留，
  使省略补全用错模板。

## 5. 工程问题记录（实测踩坑）

### 5.1 工单5 新增

| # | 问题 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- | --- |
| 1 | **自由改写完全不可用** | 3b 代词换代词、0.5b 复述指令 | 任务粒度过粗、约束不足 | 改四层结构 + 受约束子任务（§4.1） |
| 2 | **改写塞入不存在实体** | 英文轮检索 0 命中，唯一输给基线的一轮 | 校验器只查"含候选实体"，未查"其余文字是否保留" | 新增第 6 条「最小编辑」（子序列判定） |
| 3 | **指代判定被"最长优先"坑** | 「该公司」被更短的「其」抢先命中 | 词表按顺序尝试 | 命中按「起点升序 + 同起点取更长」排序 |
| 4 | **单字「其」大面积误伤** | 「其中/其他/尤其/如实」被当代词 | 单字代词歧义大 | 构词排除：`(?<![尤其中何如])其(?![中他实它次余])` |
| 5 | **省略句式正则过宽** | 「注册资本是多少？」被当成「X 呢」 | 正则只管形状不管内容 | 加实体护栏：实体槽必须基本就是公司名（允许多余 ≤4 字） |
| 6 | **基线硬编码消歧答错公司** | 问力源的控股股东，基线答成兴图新科的程家明 | 工单3 把「该公司/其」硬编码替换成第一家公司 | 删除该替换，改由对话焦点消解 |
| 7 | **缓存串味** | 同一句代词问题在不同会话得到同一答案 | 缓存 key 只有原问题 | key 加「改写后问题 + 焦点公司」 |
| 8 | **UI 两会话共用历史** | 两个标签页互相看见对方的对话 | `DialogueState` 是进程级表，固定 id 会撞 | 每浏览器会话一个 uuid |
| 9 | **重新生成后焦点残留** | 重生成后省略补全用了错的信息点 | 只回退了答案没回退状态 | 从剩余轮次重建 `focus_company` / `last_aspect` |
| 10 | **`build_index --rebuild` 冲掉组织图块** | 重建后 Q5 检索不到 | recreate 重建整个 collection | `build_index` 建完后自动调 `ingest_orgchart()` 补回 |
| 11 | **PaddleOCR-VL 无法转录组织图** | 交叉验证 `ok: false`：整页被判为一个图像块 | 该模型对本页不产出文字层 | **如实记录并落盘**（`docs/07` §5）；层级改由正文两处证据独立佐证 |
| 12 | **英文提问回了中文答案** | 3 个英文轮里 2 轮整句中文（如 `法定代表人：赵马克。[1]`） | 答案语言取自 `analysis["lang"]`，而它是 `query_rewrite.detect_language` 的**纯 ASCII 占比**口径：问句里嵌了中文公司全称时占比被稀释（`Who is the legal representative of 武汉力源信息技术股份有限公司?` → 0.58 ≤ 0.6）判成 zh，于是走中文 system prompt；语言守卫 `wrong_lang` 要求 `lang == "en"` 才触发，**根本不启动**。`coref.detect_language` 有「剥离实体后复判」的补丁，但只用于改写模板语言，没接到答案语言上 | 新增 `rag.answer_lang()`：答案语言一律按**用户原始提问**判定（含实体剥离），`ask` / `ask_stream` 两处同步；守卫改为按它判定。回归：`tests/test_answer_language.py`（含真模型端到端一条）。**代价**：英文轮事实命中率由 1.0 记为 0.0（模型音译中文专名），见 §10 第 10 条 |
| 13 | **把冲突表格喂进生成上下文 → Q1 答错** | 为满足「Q1 溯源到收入表格」把 p342 表提升进上下文后，Q1 答成 `4,627.15 万元、18,780.67 万元、6,464.51 万元`（漏 `14,414.16`、顺序也乱），验收序列直接不通过；5/5 次复现 | **源文档自身冲突**：该表「军用领域/小计/2019年1-6月」印的是 **4,627.15**（= 4,508.18 + 118.97 的舍入），正文第 129 页与验收标准答案是 **4,627.14**。表进了上下文，模型就改用表里的数字；且「数字列表校正」要求答案数字被**某句原文全覆盖**，而 4,627.15 不在任何正文句里 → 校正条件永不满足、**护栏反而失效** | 该表**只做引用定位、不进生成上下文**：`rag._nearby_table_notes` 找出「同表多行但没进上下文」的表，`_attach_nearby_tables` 把「表名 / 页码 / 命中行」挂到同章节的引用上。回归：`tests/test_table_citation.py`（含「该表不得进上下文」的闸门） |

### 5.2 继承自工单3（表格链路，仍然有效）

## 7. 错误处理与容错

### 7.1 多轮侧（本工单）

| 场景 | 行为 |
| --- | --- |
| 指代无法解析（无历史/无候选） | `mode=unresolved` + **明确反问**，不检索、不猜 |
| 改写 LLM 超时 / 坏输出 | 校验器 6 条拦截 → L4 规则兜底（确定性） |
| 对话历史过长 | 滑动窗口 + 摘要；单会话 50 轮硬上限；会话表 LRU 64 |
| 英文改写通过率低 | 降级到 L4 规则路径，**措辞不最优但实体不错**（20 轮中 3 轮） |
| 用户空输入 | 直接返回提示，不进链路 |

### 7.2 解析侧

| 场景 | 行为 |
| --- | --- |
| MinerU 失败/超时 | 回退 PyMuPDF 增强引擎；已有产物直接复用 |
| 表格 HTML 解析失败 | 降级为整表文本块（`degrade_reason=parse_failed`） |
| 表格质量分低 | PaddleOCR-VL 页级兜底；仍失败则降级并标记 |
| **组织结构图校验不过** | **抛错拒绝写入**（宁可失败，也不产出错误的树） |
| PaddleOCR-VL 不可用/无文字输出 | 记 `ok: false` 与原因，不静默；主链路不受影响 |

### 7.3 资源侧

| 场景 | 行为 |
| --- | --- |
| 显存不足（8G 卡跑三个模型） | `rag.warmup` 分阶段：embedding → 查显存 → reranker → 预热 Ollama |
| LLM 超时/异常 | 抽取式降级：给出最相关片段原文与页码 |
| LLM 数字幻觉 | 数字校验 → 定向重试一次 → 仍可疑则抽取式校正 |
| 跑基线子进程 | 先 `llm.unload()` + 清 CUDA 缓存，否则子进程加载模型会 OOM |

## 9. 评测口径

### 9.1 20 轮三方对比（`evaluate_multiturn.py`）

| 组 | 输入 |
| --- | --- |
| **工单5 多轮** | 每轮原始问题 **+ 对话状态** |
| **工单3 单轮**（优化前） | 每轮**原始问题**，逐轮独立、无历史（只读子进程调用工单3，用其 collection） |
| 纯 LLM | 原始问题，无检索、无历史 |

指标：事实命中率、改写准确率（严格）、指代实体准确率、无候选反问率、
首轮不误改写率、降级率、p50/p90/≤3s 占比、引用溯源率。

**口径要点**：基线也补一条**结果整条丢弃**的预热题（实测 28,294ms 冷启动），
与工单5 的 `rag.warmup()` 对等；否则就是拿"冷启动"比"热启动"。

### 9.2 5 轮验收序列（`run_acceptance.py`）

逐轮记录：原问题 / 独立问题 / 改写方式 / 指代 span / 命中事实 / 答案全文 /
引用 / 分阶段耗时 / **喂给 LLM 的逐字上下文**（供 RAGAS 复用，避免评测时重跑检索）。
报告由 `to_markdown()` 从落盘产物生成（`--report-only` 可离线重生成），不是人工复述。

### 9.3 RAGAS（`evaluate_ragas.py`）

两套题：**14 道必测题**（口径与工单3 完全一致，可直接对比）+ **5 轮验收序列**
（复用验收产物的 contexts）。`faithfulness / answer_relevancy / context_recall / context_precision`，
裁判用本机 qwen2.5:3b、embedding 用本机 bge-m3，全程离线。

> 报告里加了一列「**答案逐字来自上下文**」：用来把**裁判误判**与**真幻觉**分开。
> 本次实测 Q2 的 `faithfulness=0.0`，但该轮答案在 5 个检索片段中逐字可查，
> 脚本自动核对后判定为**裁判误判**——不把裁判噪声记成系统的缺陷。

## 10. 已知限制（如实记录）

| # | 限制 | 现状与原因 |
| --- | --- | --- |
| 1 | **并发下响应时间超 3 秒** | 已做并发实测（`_scratch/task12_verify_gaps.py 3`）：并发下**不崩、0 失败**，但 3 路 2/3 超 3 秒、5 路 3/5 超 3 秒。根因是本机单机单进程部署（Streamlit + Qdrant local + Ollama 串行推理），多路请求排队等同一张卡，属**部署形态**限制而非代码缺陷。未做吞吐量基准与长时高压。见 `docs/09` 要求 7 |
| 2 | **事实命中率 0.9062（29/32），非 1.0** | 失分三处：`d9` 首轮答案完整度（未提共同牵头单位"军事科学院"，发生在**直通轮**、与多轮无关）+ 两个英文轮的音译（见第 10 条）；未通过删改测试集来消除 |
| 3 | **英文轮改写降级率高于中文** | 20 轮中 3 轮走 L4 规则兜底（全在英文轮）。3b 在英文约束改写上通过校验器的概率更低；实体绑定不出错（`entity_accuracy=1.0`），但措辞不最优 |
| 4 | **PaddleOCR-VL 无法转录组织结构图** | 实测该模型把整页判为一个图像块、不产出文字层，交叉验证 `ok: false`。层级正确性改由正文两处独立证据佐证（`docs/07` §6） |
| 5 | **RAGAS 裁判是小模型** | qwen2.5:3b 作裁判存在噪声，且**不稳定性是实测的**：同一份 Q2 答案在两次裁判运行间得 **0.0** 与 **0.333**，而它两次都逐字来自检索片段。故报告标出「答案逐字来自上下文」一列做交叉核对，并同时给出事实命中率与逐轮实证，不以单一指标为准 |
| 6 | **首轮直通轮不做改写** | 完整问题（点名公司）走 `passthrough`，这是**有意的快路径**（验收 Q1/Q5 都是 0ms 改写开销），但对"问句本身有歧义"的完整问题无能为力 |
| 7 | **多文档路由仍是规则版** | 别名表覆盖当前两份文档；新增文档需同步维护 `DOC_ALIASES` |
| 8 | **对话状态不持久化** | 会话状态保存在**进程内存**（`dialogue._SESSIONS`，LRU 上限 64），服务重启即全部丢失；也未做多进程/多副本共享（本机单进程部署，未引入 Redis 等外部存储）。长时间运行的会话能力因此**不是**可恢复的 |
| 9 | **收入表与正文数字冲突（源文档自身）** | 招股1 第 343 页「4、主营业务收入按行业列示」的**军用领域小计** 2019 年 1-6 月印 **4,627.15**（= 4,508.18 + 118.97 的舍入），正文第 129 页印 **4,627.14**；验收标准答案取**正文口径**。系统按正文作答，并把这处表格作为**引用定位**给出（表名/页码/命中行），该表不进生成上下文——理由见 §5.1 第 13 条 |

| 10 | **英文作答时中文专名被音译** | 修掉「英文提问回中文答案」（§5.1 第 12 条）后，英文轮是英文整句了，但 3B 把 `赵马克`→"Zhao Mark"、`程家明`→"Cheng Jiaming"、`武汉力源信息技术股份有限公司`→"Wuhan P&S Information Technology Co., Ltd."。事实匹配按**中文原名**判，20 轮里两轮因此记 0（指代实体准确率仍 1.0，**答案内容本身正确，只是写法**）。**两种压法都实测无效**：① 在 `_SYSTEM_EN` 里明确"专有名词保留中文原名"并给反例——照旧音译；② 把音译答案回灌 + 定向重试提示——模型**逐字返回原答案**。取舍：语言要求是硬性的、音译只是写法问题，故保留现行为并如实记录 |

> 以上均为**如实记录**，未在报告中做美化；相关脚本可复现全部数字。
