# 用户手册

> 工单编号：人工智能NLP-RAG-图像内容解析及检索优化
>
> 本手册面向**操作者**：从零把系统跑起来、上传文档、提问、看引用页码与图像，以及出问题时怎么查。
> 原理与选型见 `docs/技术文档.md`，图像专项细节见 `docs/图像解析与检索专项说明.md`。

## 一、环境准备

| 项目 | 要求 | 检查命令 |
| --- | --- | --- |
| 操作系统 | Windows 11（本机实测）/ Linux / macOS | — |
| Python | 3.12（本机 3.12.10） | `python -V` |
| 依赖 | `requirements.txt` 全部依赖 | `python -m pip install -r requirements.txt` |
| Ollama | 本地服务 + `bge-m3` 与 `qwen2.5:3b` 两个模型 | `ollama list` |
| 模型权重 | CLIP（605.2 MB）与 reranker（1112.3 MB） | `python scripts/download_models.py` |
| API key | 生成与视觉模型共用，三选一：`API` / `QWEN_API` / `OPENAI_API_KEY` | `echo $API` |
| 语料 | 项目根目录下 `招股说明书1.pdf`、`招股说明书2.pdf` | `ls *.pdf` |

准备命令（一次性）：

```bash
python -m pip install -r requirements.txt
ollama pull bge-m3
ollama pull qwen2.5:3b
python scripts/download_models.py        # 从 hf-mirror 下载 CLIP 与 reranker，可断点续传
export API=sk-xxxx                       # Windows PowerShell：$env:API="sk-xxxx"
```

## 二、启动步骤

按顺序做三步（第一次跑必须做第 1 步；索引已建好可直接跳到第 2 步）：

```bash
# 1) 建库（全量约 15 分钟，日志在 logs/rag04.build.full_04.log）
python scripts/build_index.py full_04

# 2) 启动界面（Streamlit，端口 8501，headless 不自动开浏览器）
python scripts/run_ui.py
#    浏览器打开 http://localhost:8501

# 3) 可选：启动接口服务（压测与集成用，端口 8000）
uvicorn rag04.api.server:_get_app --factory --port 8000 --app-dir src
```

服务启动时会**同步预热**存储、reranker、CLIP 与嵌入模型（日志 `warmup[store]/[rerank]/`
`[clip]/[embed]`），约十几秒内不接流；这是为了让第一条问答不必付模型加载时延。

## 三、上传 PDF（可选，界面上完成）

1. 打开界面，左侧栏找到 **「上传 PDF 文档」**。
2. 点击选择本地 `.pdf` 文件（只接受 PDF；文件名会被消毒，
   形如 `..\..\x.pdf` 的名字会被拒绝并提示）。
3. 点击 **「上传并建库」**，等待转圈结束显示
   「建库完成：文档已追加进索引，可与语料一起检索。」。

注意事项：

- **上传是「追加」不是「重建」**：新文档并入现有索引，原来的两份语料留在索引里、
  与上传件并列可检索（上传框下方即写明「新文档会**追加**进索引…不清空现有索引」）。
- **只有与语料同名**（即覆盖 `招股说明书1.pdf` / `招股说明书2.pdf` 源文件）才走另一条分支：
  需先勾选「我确认覆盖该文件（覆盖后无法恢复）」，确认后覆盖源文件，并**先清空三库、
  再按语料全量重建**（约 15 分钟，期间界面不可用），提示为
  「建库完成：已按语料全量重建索引（含本次覆盖的文件）。」。
- 与项目根目录下**已有的同名文件**（如上次的上传件）同名时同样要勾选覆盖确认，
  但仍走追加分支（不清库）。源 PDF 不在版本管理内，覆盖无法恢复。
- 建库期间 `data/qdrant` 被本进程独占，其他进程需等其释放；常规全量重建的生产用法
  仍是命令行 `python scripts/build_index.py full_04`。

## 四、提问

1. 主区输入框（占位提示「例如：组织结构图中销售部有几个部门构成？」）输入问题。
2. 点击 **「提问」**。
3. 空问题会提示「请输入问题。」，不会发起检索。

可以直接用这两道最能体现本工单能力的问题验证：

- 中文（图像题，id 5）：`武汉力源信息技术股份有限公司组织结构图中，销售部有几个部门构成，其中大客户销售部有几个销售处构成？`
- 中文（图像题，id 6）：`从2008年中国IC市场应用结构与增长图中可以看出，增长率最快的是哪个行业？负增长的是哪个行业？`
- 英文：`How many departments make up the Sales Department, and how many sales offices make up the Key Account Sales Department?`

## 五、查看结果

答案返回后界面自上而下给出：

1. **答案**（Markdown 渲染；系统按**提问语言**作答——中文问用中文答，英文问用英文答）。
2. 四个指标块：

| 指标块 | 含义 |
| --- | --- |
| 响应时间 | 流水线内实测耗时（ms，一位小数，不含 HTTP 与前端开销） |
| 答案语言 | 本次答案的语言（中/英） |
| 生成后端 | 实际生效的生成后端：`deepseek` 或降级后的 `ollama` |
| 引用条数 | 本次答案引用的检索片段条数（不是精确度指标） |

3. **时延预算结论**（caption）：在预算内会显示
   「响应时间 1730.3 ms，在 3000.0 ms 预算内」；超预算如实显示
   「响应时间 41672.9 ms，超出 3000.0 ms 预算（如实上报，未截断）」。
   本机实测**热态 p50 = 1730.3 ms、15/16 题 ≤ 3 s**（`ollama_url` 改 IPv4 字面量后重测）；
   **超预算出现在进程内首题冷启动与并发档，是当前已知缺口，不是故障**。
4. 若模型判定问题与文档无关，会显示「该问题与文档无关，已拒答。」并只展示提示，不给答案。

## 六、查看引用页码和图像

- **引用来源**区逐行给出引用片段，格式为
  `p{页码} | {块类型} | {来源ID} | score={相似度}`，
  例如：`p39 | text | figuretext#39#fig4 | score=6.638414`。
  - 页码为 1-based PDF 页（印刷页 = 页码 − 1）；
  - 块类型 `text` / `table` / `image`；
  - 来源ID 形如 `text#39#782`、`table#22#10`、`figuretext#39#fig4`，可用于在
    `docs/答案定位报告.md` 中反查该题的证据出处；
  - `score` 是重排后的相关性分数（不是概率，不能跨题比较）。
- **图像溯源**区：只要**某条引用项携带图像路径**（`image_path`）就会渲染出对应的图区 PNG，
  图注为 `p{页码} {来源ID}`，例如 `p39 figuretext#39#fig4`。
  **以图像题（id 5/id 6）为例**：命中的引用条目是图区的**结构化描述块**——
  它的块类型显示为 `text`、来源ID 形如 `figuretext#…`，但它带着 `image_path`，
  指向同一张原始图区文件，因此图像溯源区会展示该原图：

  | 题目 | 引用行（引用来源区） | 图像溯源区展示的文件 |
  | --- | --- | --- |
  | id 5 | `p39 \| text \| figuretext#39#fig4 \| score=6.638414` | `data/figures/招股说明书2_p39_7fb46462e43d.png` |
  | id 6 | `p310 \| text \| figuretext#310#fig88 \| score=8.51071` | `data/figures/招股说明书2_p310_126713956351.png` |
  | id 6（次条） | `p72 \| text \| figuretext#72#fig9 \| score=7.370289` | `data/figures/招股说明书2_p72_00eb1d43b4c6.png` |

  也就是说：**引用里看到的 `type` 是 `text` 不代表没有图**——判断依据是这条引用有没有
  图像路径；图区文件都落在 `data/figures/`（命名含内容哈希），可单独打开核对。
- 侧栏 **「系统状态」** 显示 `/health` 原始 JSON，可用于确认 `counts`
  （三库条数，本机实测 text 4436 / table 681 / image 162）与各组件状态。

## 七、中英文切换

- 侧栏顶部 **「Language / 语言」** 下拉框切换 `中文` / `English`，界面标签随之切换。
- 语言选择**只影响界面文案**；答案语言始终由提问语言决定（LLM 按提问语言作答），
  因此切到 English 后用英文提问，答案就是英文；用中文提问则答案仍是中文。
- 「答案语言」指标块会明确标注本次答案的语言，避免中英混杂时误读。

## 八、接口用法（脚本/集成）

```bash
curl http://127.0.0.1:8000/health
curl -X POST http://127.0.0.1:8000/api/ask -H "Content-Type: application/json" \
     -d "{\"question\":\"武汉兴图新科电子股份有限公司法定代表人是谁？\"}"
curl http://127.0.0.1:8000/api/stats
```

> 地址请写 `127.0.0.1` 而不是 `localhost`：本机 `localhost` 先解析到 IPv6 的 `::1`，
> 而服务与 Ollama 都只监听 IPv4，写 `localhost` 每次新建连接要多等约 2 秒（实测
> 2053 ms vs 15 ms）—— 这条同样适用于下面的 Ollama 自检地址。

`/api/ask` 的响应字段：`answer`、`lang`、`citations`、`latency_ms`、`llm_backend`、
`refused`、`latency_budget_ms`、`within_budget`、`mode`。
错误统一为顶层 `error` 字段（400 参数/未确认重建、409 索引被占用或重建中、503 重建中不可问答）。
`POST /api/ingest` 是同步分钟级**全量重建**（`build(reset=True)`：先清空 text/table/image
三个 collection 再重建），必须显式发送 `{"confirm": true}`，**常规重建请用命令行**。
它与界面上的上传按钮语义不同：上传新文档是**追加**（不清库），只有上传与语料同名的文件
才会触发同等的清库重建。

## 九、常见问题排查

| 现象 | 可能原因 | 处置 |
| --- | --- | --- |
| 侧栏状态 `ollama: down: ConnectionError`；提问报连接错误或检索质量骤降 | Ollama 未启动或未拉模型 | 启动 Ollama（`ollama serve` 或打开客户端）→ `ollama list` 确认 `bge-m3`、`qwen2.5:3b` → `curl http://127.0.0.1:11434/api/tags` 应返回 200 |
| 侧栏状态 `clip: missing`；图像类问题（id 5/id 6）答不好 | CLIP 权重未下载 | `python scripts/download_models.py`；确认 `data/models/clip-vit-base-patch32/pytorch_model.bin` 存在且约 605.2 MB。缺失时 CLIP 检索路被跳过，图像块仍可由描述文本召回 |
| 侧栏状态 `llm: no key`；答案由小模型生成 | 未设置 API key | 设置 `API`（或 `QWEN_API` / `OPENAI_API_KEY`）后重启界面/服务；必要时设 `OPENAI_BASE_URL` |
| 提问失败并提示「请先上传 PDF 或确认已建库。」 | 索引为空或未建库（`data/qdrant`、`data/bm25.pkl` 缺失） | 运行 `python scripts/build_index.py full_04`；确认日志末行「建库完成，总块数 5279」 |
| 建库报错含 `already accessed` / API 返回 409「索引已被占用」 | `data/qdrant` 被另一进程独占（服务、界面或另一次建库） | 停掉正在运行的服务/界面后再建库；或改用 API 的 409 提示路径。**同一时刻只允许一个进程持有索引** |
| 改了分块/检索口径后检索结果变差或旧块仍在 | 新块与旧块共存 | 用 `python scripts/build_index.py full_04 --reset`（会先清空三库），执行前建议备份 `data/qdrant` |
| 日志出现「语料缺失，跳过：…」 | 根目录缺 PDF | 把 `招股说明书1.pdf`、`招股说明书2.pdf` 放回项目根目录后重建 |
| 上传 PDF 后提示「请先上传 PDF…」 | 文件名非法（含路径/非 .pdf）或未选中文件 | 用单段 `.pdf` 文件名重新上传 |
| 答案显示「该问题与文档无关，已拒答。」但你确信文档里有 | 检索未召回足够证据（拒答判定锚定答案动词），或问题超出两份语料范围 | 换用与原文接近的措辞重试；若为本仓已知残留（id 1），见 `docs/图像解析与检索专项说明.md` §六 |
| 响应时间显示超预算 | 性能缺口（热态 p50 = 1730.3 ms 在预算内；首题冷启动 41.7 s、并发档超预算） | 属已知问题而非故障。本仓只对整条问答计时，**没有逐阶段耗时产物**，重排与生成「是大头」只是估计。界面启动时会**同步预热** reranker/CLIP/存储（侧栏「系统状态」下方显示预热状态），首答不再额外付约 8 秒的模型加载时延；若该处提示「预热失败」，首答偏慢即由此而来，重启界面重试 |
| 端口被占用（8501 / 8000） | 已有实例在跑 | 关掉旧进程，或改用其他端口 |
| 想查看详细原因 | — | 日志在 `logs/rag04.log`（10MB×10 轮转）、建库日志 `logs/rag04.build.full_04.log`、评估日志 `logs/rag04.eval.full_04.log` |

## 十、一次完整验收（建议顺序）

```bash
python scripts/build_index.py full_04            # 1) 建库，确认总块数 5279
python scripts/run_eval.py full_04               # 2) 16 题评估 → docs/reports/检索精确度报告_full_04.md
python scripts/gen_location_report.py            # 3) 答案定位报告 → docs/答案定位报告.md
python scripts/run_ui.py                         # 4) 界面：问 id 5 / id 6，查看引用与图像溯源，切 English 再问一次
python -m pytest -q                              # 5) 单元测试（默认排除 integration）
```

第 2 步会真实调用 LLM（约 3~15 秒/题）；第 4 步的英文提问同样会调用 LLM。
两者都需要 API key 与 Ollama 均可用。

第 4 步图像题应当看到什么（验收点）：

1. 提问 id 5 后，「引用来源」第一行是
   `p39 | text | figuretext#39#fig4 | score=6.638414`——**类型是 `text`，来源ID 是 `figuretext#…`**；
2. 「图像溯源」区随之出现一张组织结构图，图注为 `p39 figuretext#39#fig4`，
   图中**能看见最下方「珠海/深圳/北京/武汉/广州/成都 销售处」一行**；
3. 提问 id 6 同理：引用行含 `p310 | text | figuretext#310#fig88 | score=8.51071`，
   图像溯源区展示 IC 市场图（左侧饼图 + 右侧完整柱状图，含底部「消费 5.1%」柱）；
4. 「答案语言」指标块显示本次答案语言（中文问→中文，切 English 英文问→英文）。

若第 2/3 条的图没有出现，先确认该引用项确实带图像路径——界面上的引用行只显示
`页码 | 类型 | 来源ID | score`，**看不到** `image_path`，可改用接口确认
（`POST /api/ask` 返回的 `citations[]` 每项含 `image_path` 字段，
id 5 应为 `data/figures/招股说明书2_p39_7fb46462e43d.png`），
或对照 `docs/答案定位报告.md` 的 id 5 / id 6 小节；再按第九节排查 `clip: missing` 等状态。
