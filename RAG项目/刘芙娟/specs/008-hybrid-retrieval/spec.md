# Feature Specification: 混合检索（语义 + BM25 关键词）（S9）

**Feature Branch**: `008-hybrid-retrieval`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "使用 speckit 技能生成检索脚本，实现混合检索（语义检索和 BM25 关键词检索），脚本保存到 d:\zg6_Project\9\med_rag\backend；如果超过 300 行就分模块写；同时连接前端，用向量化的问题在向量库中进行检索。"

## 背景与定位

本特性实现 `docs/05_接口设计.md` §4.2 定义的 **I-05 `retrieval_service.search`** —— 检索链路的第三步：**把一个问题向量换成一组有出处的原文片段**。

用户给出的链路是「输入 → 向量化 → **语义检索** → 生成提示词 → 生成答案」。S8 已交付第二步（`backend/query/`：问题落盘 + BGE-M3 在线编码 + 指纹门禁）。本特性交付第三步，并把结果第一次送到前端。

### 上游已经为这件事留好了接口

三处已经写好、只等填内容的接缝：

1. **契约已定义。** `docs/05` §4.2 给出了 `search(question, top_k, threshold) -> RetrievalResult` 的完整签名、`RetrievedPassage` / `RetrievalResult` 的字段，以及四条关键约束（阈值判定在内、空集不抛异常、参数显式传入、`below_threshold` 与空集分开记录）。本特性 MUST 逐字段实现该契约，MUST NOT 自行改形。

2. **向量已算好。** `backend/query/service.py` 在每次 `POST /ask` 时已经算出了查询向量（S8 交付）。本特性 MUST 直接消费它，MUST NOT 重新编码 —— 重新编码是第二个编码入口，正是 S8 花整篇规格去防的东西。

3. **前端与事件格式已就位。** `backend/api/stream.py` 已经发出 `citations` 事件，`frontend/js/sse.js` 已经解析它，`frontend/js/transcript.js` 的 `renderCitations` 已经能渲染 `chunk_id / file_name / page_start / page_end / section / block_type / text / score`。**本特性接入时，前端渲染代码一行都不用改**（这是 S7 规格 SC-009 预先声明的验证点，本特性正是它的兑现时点）。

### 为什么要"混合"，而不是只用语义

单走向量检索在本项目上有两个具体的失效方式：

- **罕见词被稀释。** 医疗问句里大量出现的是**指南原文照抄**的术语 —— 药品通用名、剂量数值、指南编号、疾病分型。这类词在 BGE-M3 的 1024 维稠密空间里权重很低：它们足够罕见，罕见意味着模型见得少、表示质量差。用户输入「盐酸氨氯地平」时，向量检索很可能返回一段讲"钙通道阻滞剂"的泛论，而真正写着这五个字的那一段排在后面。
- **精确字面命中是医疗场景的硬需求。** 用户核对一条剂量时，要的是**写着这个数的那一段**，不是"语义相近的一段"。语义相近在这里是负价值 —— 它会把用户引向一个数值不同但话题相近的段落。

BM25 恰好补上这两点：它对罕见词给高分，对字面命中给高分，且**不需要训练、不需要 GPU、可逐条解释**。两路合并后，"照抄术语"与"口语提问"都能命中。

### 本特性最大的风险：两路结果不可比

**余弦相似度是 `[-1, 1]` 的有界量，BM25 分数是无上界正数，且随语料规模增长。** 把两者直接加权相加，等于把一个"归一化过的"数与一个"没归一化的"数相加 —— 结果由 BM25 的分数量纲单方面决定，权重参数失去意义。

这个失效方式是**静默的**：检索照常返回、排名看起来合理、没有任何异常，只是在某个语料规模下悄悄退化成"实际上只有 BM25 在起作用"。因此本特性 MUST 在规格层面**先把融合规则定死**（见 FR-006 与 Q2 裁决），MUST NOT 留到实现时"先加起来看看"。

第二处相关风险：`RetrievedPassage.score` 在 `docs/05` §4.2 的注释里被明确写成「**余弦相似度**分数，引用片段的排序依据」，而前端 `transcript.js` 把它 `toFixed(2)` 直接显示给用户。**融合后的排名分不是余弦相似度**。若把融合分塞进 `score`，前端会显示一个用户无法解释的数字，且 `docs/05` §4.2 的契约被悄悄改写。本特性 MUST 区分「排序依据」与「对外展示分」（见 FR-007）。

### 三项前置裁决（2026-09-28 已确认）

规格起草时发现三处**需要人工裁决**的分叉。按「不明确处给方案 + 推荐、由人裁决」的约定提交裁决，结论如下：

| 编号 | 议题 | 分叉点 | 裁决 |
|---|---|---|---|
| **Q1** | BM25 语料从哪来、关键词怎么切 | Milvus 全量拉取建内存索引 / 读本地 chunks 产物 / Milvus 原生稀疏向量 | **Milvus 回捞 + jieba 分词**：启动期从 `med_rag_v1` query 全量标量字段，内存建索引。语料与向量库逐条一致 |
| **Q2** | 两路排名怎么融合 | RRF / 加权归一化分数 / 只取并集不融合 | **RRF 倒数排名融合**（k=60）：只取名次不取原始分，免疫量纲问题；对外 `score` 仍是余弦 |
| **Q3** | 检索已命中但生成未就绪，正文区说什么 | 新增过渡文案 / 复用拒答兜底 / 直接拼接命中原文 | **新增「检索就绪、生成未就绪」过渡文案**：如实说明，不把能力缺失伪装成拒答 |

**D1（Q1 的具体口径）** —— 语料源 = Milvus `med_rag_v1` 的全量 chunk（`query` 拉 `SCALAR_FIELDS` 中的 `chunk_id` / `text` / `file_name` / `page_start` / `page_end` / `section` / `block_type`）。
为什么不读本地 `data/chunks/*.chunks.jsonl`：本地产物与库内容**可以不同步**（重新入库了但没重跑 S4，或反之），那时两路语料会静默漂开 —— 表现为"某段原文在语义路能命中、在关键词路永远搜不到"，且没有任何报错。让两路共用同一个语料源，这条失效路径就不存在。
关键词切分用 **jieba**（新增依赖，须登记 `requirements.txt`）。理由：医疗问句的核心是药品通用名与分型名，字符 2-gram 会把「盐酸氨氯地平」切碎成跨词片段，直接削弱 US1 的命中率 —— 而 US1 正是本特性的存在理由。

**D2（Q2 的具体口径）** —— `score = Σ 1/(k + rank_i)`，k=60，Σ 遍历该 chunk 在语义路与关键词路中的名次（名次从 1 起；某路未命中则不加该项）。
- **对外 `score` 字段保持余弦相似度**，MUST NOT 写入 RRF 分。两条理由：① `docs/05` §4.2 明确把 `score` 定义为余弦相似度，前端 `transcript.js` 会 `toFixed(2)` 显示给用户 —— 塞入 RRF 分会让用户看到一个无法解释（且与"像不像"无关）的数字；② 阈值判定按 `docs/05` §4.2 语义是**相似度阈值**，用 RRF 分比对阈值等于换了把尺子。
- **RRF 分仅用于排序与日志**，MUST NOT 占用 `score` 字段（FR-007）。
- 关键词路命中的 chunk 若语义路未命中，其对外 `score` 取 **0.0**（诚实反映"语义上没命中"），不伪造一个余弦值。

**D3（Q3 的具体口径）** —— 新增固定文案 `RETRIEVAL_READY_NOTICE`（具体措辞在 plan 阶段定稿并进 `backend/api/__init__.py` 的文案唯一处），语义为「已找到相关资料，答案生成能力正在接入中，请先阅读下方原文引用」。
与 `REFUSAL_FALLBACK` 的分野：后者表示"知识库里没有"，前者表示"有，但生成没做完"。docs/05 §3.1.4 规则 3 明令禁止把「本该能答但基础设施没就绪」伪装成拒答 —— 用户对二者的后续动作完全不同（换问法 vs 等能力上线）。
`is_refusal` 取 `True`（本期未产出知识性内容，与 `CAPABILITY_NOT_READY` 同处理）；引用区**正常展示命中片段**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 照抄指南术语也能检索到那一页 (Priority: P1)

用户手里有一份纸质指南，想确认其中一句话的原文。他把术语原样敲进输入框（例如一个药品通用名、一个指南编号、一个疾病分型名），提交后在引用区看到**写着这几个字的那一段**，以及它的来源文件名与页码，点「展开原文」能读到完整段落。

**Why this priority**: 这是"混合"相对于"纯语义"的**全部增量价值**，也是本特性存在的最直接理由。只有语义路的系统在这类输入上会给出话题相近但字面无关的段落 —— 对"核对原文"这个动作而言，等于答错。首选 P1 是因为它定义了本特性与上一版的差别。

**Independent Test**: 用知识库中确实存在的罕见术语作为问题提交，断言引用区第一条引用的 `text` 中包含该术语；同时断言该条引用的 `file_name` / `page_start` 与原文位置一致。仅实现本故事（语义路可暂缺或退化）即可交付价值。

**Acceptance Scenarios**:

1. **Given** 知识库已入库且服务已启动，**When** 用户提交一个在原文中出现过的罕见术语（药品名、编号、分型名），**Then** 引用区首条引用的原文包含该术语。
2. **Given** 同上，**When** 用户提交一个原文中**不存在**的术语，**Then** 系统不返回任何"看起来像但字面不含该词"的片段冒充命中，而是按 FR-016 处置。

---

### User Story 2 - 口语化提问也能检索到 (Priority: P1)

用户不知道该用什么术语，用日常说法描述症状或疑问（例如"血压高平时要注意些啥"），提交后仍能得到与知识库相关的原文片段。

**Why this priority**: 项目面向非专业群众（constitution 原则 V），口语化提问是**主流输入形态**而非边缘情况。与 US1 同为 P1：两者共同构成"混合"的两个必要半边，缺任何一个都让另一边的价值打折。

**Independent Test**: 用不含任何原文术语的口语化问题提交，断言引用区非空且首条引用的 `score` 不低于配置阈值。可在 US1 未实现时独立验证。

**Acceptance Scenarios**:

1. **Given** 知识库已入库，**When** 用户提交一个与库内某主题相关、但用词与原文完全不同的口语化问题，**Then** 引用区非空，且返回片段与该主题相关。
2. **Given** 同上，**When** 用户提交一个与库内所有主题都无关的问题（如闲聊），**Then** 系统不返回低相关度的片段充数，而是按 FR-016 处置。

---

### User Story 3 - 引用片段在界面上可见且可核对 (Priority: P1)

检索命中后，前端引用区按服务端给出的顺序列出每条片段：序号、来源文件名、页码、相似度分数、原文预览；长片段可点「展开原文」就地展开。

**Why this priority**: 这是 constitution 原则 II（无据不答与强制溯源引用）在界面上的落点 —— **可核对**是把"模型说了什么"降级为"原文写了什么"的唯一机制。检索结果不送到界面，等于这套机制不存在。与 US1/US2 并列为 P1。

**Independent Test**: 提交任意能命中的问题，断言引用区渲染出与服务端返回**同序、同数量**的卡片，且每张卡片上的文件名、页码、分数与服务端返回逐字段一致。

**Acceptance Scenarios**:

1. **Given** 检索命中 n 条，**When** 前端收到 `citations` 事件，**Then** 引用区渲染 n 张卡片，顺序与 `answer_text` 中 `【n】` 标记所依据的顺序一致。
2. **Given** 某条引用原文超过预览长度，**When** 用户点「展开原文」，**Then** 就地把该条展开为全文（不影响其他卡片）。
3. **Given** 检索为空，**When** 前端收到空的 `citations`，**Then** 引用区显示空态而非残留上一次的引用（不得出现"上一次问题的引用配这一次的答案"）。

---

### User Story 4 - 检索可脱离服务单独自检 (Priority: P2)

运维或验收人员用命令行对单条问题跑一次检索，直接看到两路各自的命中与最终融合排名，不需要启动 Web 服务、不需要打开浏览器。

**Why this priority**: 检索参数（阈值、top_k、两路权重）需要靠反复试跑来标定，而 constitution 的 TODO(SIMILARITY_THRESHOLD) 至今未回填 —— 标定工作必须以本故事为前提。不是 P1 的理由：它不产出面向用户的功能，没有它主链路仍可交付。

**Independent Test**: 用一条问题跑 CLI，断言输出中包含每条引用的 chunk_id、两路各自分数、融合后排名、是否低于阈值；再对同一条问题跑第二次，断言输出逐字节一致（可复现）。

**Acceptance Scenarios**:

1. **Given** 服务未启动、Milvus 可用，**When** 用户对一条问题执行检索 CLI，**Then** 输出两路命中列表与最终排名，且进程以 0 退出。
2. **Given** 相同的输入与索引，**When** 连续执行两次，**Then** 两次输出的片段与顺序完全一致。
3. **Given** Milvus 不可达，**When** 执行 CLI，**Then** 以区别于 0 的退出码失败，且错误信息指出是外部依赖问题而非数据问题。

---

### Edge Cases

- **Milvus 不可达或 collection 不存在** —— 检索 MUST 明确失败并给出可操作信息，MUST NOT 退化为"只跑 BM25"静默继续（静默降级会让"向量检索坏了"这件事永远不被发现）。
- **知识库为空（0 chunks）** —— 两路都无候选，按 FR-016 处置；MUST NOT 抛异常。
- **问题为空白 / 全为标点 / 全为停用词** —— 分词后 BM25 无可查词项，语义路仍应正常返回；本情况 MUST NOT 使请求失败。
- **两路结果完全不相交** —— 融合后 MUST 同时保留两路的候选，MUST NOT 因为"另一路没有它"而降权到丢失。这正是"混合"要保住的东西。
- **同一条 chunk 被两路同时命中** —— 结果中 MUST 只出现一次，且 MUST 因被两路共同命中而排在仅单路命中的候选之前。
- **同一文档被切成多段且都被命中** —— 允许同时出现（它们是不同的原文位置），MUST NOT 去重掉。
- **所有候选都低于阈值** —— `is_empty=True` 且 `below_threshold=True`，与"完全没命中"（`below_threshold=False`）在日志与报告中可区分。
- **问题超过输入上限** —— 由既有 `validate.py` 在更早的环节拦截，本特性不重复校验。
- **重新入库后未重启服务** —— 内存索引与本进程持有的向量可能过期。本特性 MUST 在文档中明确"入库后 MUST 重启服务"，并让该前提在启动日志中可见。

## Requirements *(mandatory)*

### Functional Requirements

**检索契约（MUST 逐字段实现 `docs/05` §4.2）**

- **FR-001**: 系统 MUST 提供 `search(question, top_k, threshold) -> RetrievalResult`，签名与字段与 `docs/05` §4.2 逐字段一致，MUST NOT 增删改字段名。
- **FR-002**: 系统 MUST 同时执行**语义检索**与 **BM25 关键词检索**两路，MUST NOT 只执行其中一路。
- **FR-003**: 语义检索 MUST 消费 S8 已算出的查询向量，MUST NOT 在检索路径上重新编码问题。查询向量 MUST 与索引处于同一向量空间（由 S8 的指纹门禁保证）。
- **FR-004**: 检索 MUST 返回原文片段，每条片段 MUST 携带 `chunk_id`、`file_name`、`page_start`、`page_end`、`section`、`block_type`、`text`、`score` 八项，供界面直接渲染与用户回原文核对。
- **FR-005**: 返回的片段 MUST 按融合后的相关性降序排列；同一 chunk MUST NOT 在结果中出现两次。

**融合规则**

- **FR-006**: 两路结果 MUST 采用 **RRF 倒数排名融合**（D2）：`score = Σ 1/(k + rank_i)`，k=60，名次从 1 起，某路未命中则不计该项。融合 MUST NOT 依赖两路分数各自的量纲，MUST NOT 采用"把两路原始分数直接加权相加"的做法。共同的 k 值 MUST 作为显式配置项，MUST NOT 硬编码在函数体内。

**第四项前置裁决（2026-09-28 补，FR-013a 的依据）**

实现完成后对真实语料跑「无关提问」用例时发现：只卡 `lexical_admit_rank` 时
「今天晚饭吃什么好」会被判为命中，违反 SC-004 与 constitution 原则 II。该问题
提出后由人裁决，结论见 FR-013a（加查询词覆盖率门槛）。三项被否掉的候选判据
（BM25 绝对分阈值、IDF 门槛、余弦下限）及其被否的实测数据记录在
`contracts/retrieval.md` §2，以免后人重复尝试。
- **FR-007**: 对外 `score` 字段 MUST 保持**余弦相似度**语义（`docs/05` §4.2），因为前端会把它显示给用户且用户会用它判断可信度。RRF 融合分 MUST 只用于内部排序与日志，MUST NOT 占用 `score` 字段。关键词路独有命中的 chunk，其 `score` MUST 取 `0.0`，MUST NOT 伪造一个余弦值。
- **FR-008**: 语义路的**候选条数**与最终**返回条数** MUST 可分别配置，MUST NOT 依赖任何库的默认值。

**关键词路**

- **FR-009**: 系统 MUST 维护一份可供 BM25 检索的语料，其来源 MUST 是**向量库中的 chunk 全量**（D1），MUST NOT 读本地分块产物文件。同一份 chunk MUST NOT 出现"在语义路可见、在关键词路不可见"。语料 MUST 覆盖足够渲染引用的标量字段（`chunk_id` / `text` / `file_name` / `page_start` / `page_end` / `section` / `block_type`）。
- **FR-010**: 关键词索引 MUST 在**服务启动期**构建完成，MUST NOT 在用户请求路径上构建（请求路径上构建会把首次提问的延迟放大到不可接受）。启动期 MUST 打印语料条数，使"语料为空"这件事在启动时可见而非在提问时才暴露。

**阈值与拒答**

- **FR-011**: 阈值判定 MUST 在检索内部完成，调用方只读 `is_empty`，MUST NOT 在调用方重复比较分数。
- **FR-012**: 检索为空或最高分低于阈值时，系统 MUST 返回 `is_empty=True` 的**正常返回值**，MUST NOT 抛异常。
- **FR-013**: `below_threshold` MUST 区分"有候选但全部不达标"与"两路都没有候选"，两者 MUST NOT 合并为同一个状态。实现上它 MUST **独立于 `is_empty`** —— 按 `(not is_empty) and (...)` 实现会让二者拿到同一个值（实现期实测到的缺陷，见 contracts/retrieval.md §2 的象限表）。
- **FR-013a**: 关键词准入 MUST NOT 仅凭 BM25 名次放行 —— BM25 对任何查询都必然返回前 N 名，仅凭名次会让与知识库无关的提问被判为命中（违反 constitution 原则 II）。准入 MUST 另加**查询词覆盖率**下限（默认 0.5，显式配置），即候选命中的查询词占全部查询词的比例。（2026-09-28 补充裁决）
- **FR-014**: 检索结果为空或低于阈值时，答案 MUST 走拒答路径并输出固定兜底话术，MUST NOT 由模型生成任何内容（constitution 原则 II）。

**接入前端**

- **FR-015**: 检索结果 MUST 通过既有 `citations` 事件送达前端，字段与 `docs/05` §3.1.3 的 `citation` 对象一致。
- **FR-016**: 检索**命中**（非空且不低于阈值）时，答案正文 MUST 输出固定的「检索就绪、生成未就绪」过渡文案（D3），MUST NOT 复用拒答兜底话术、MUST NOT 直接拼接命中原文冒充答案。该文案 MUST 定义在用户可见文案的唯一处（`backend/api/__init__.py`），MUST 带有明确的移除时机（生成模块接入时删除）。
- **FR-017**: 引用片段的**顺序 MUST 由服务端决定**，前端 MUST NOT 重排；排序依据 MUST 在服务端日志中可查。
- **FR-018**: 接入检索后，**前端渲染代码 MUST NOT 需要修改**（`sse.js` / `transcript.js` 零改动）。若发现需要改动，说明服务端产出形状偏离契约，MUST 改服务端而非改前端。

**可观测性**

- **FR-019**: 每次检索 MUST 留下结构化日志，至少含：问题标识、两路各自命中数、融合后条数、首条分数、`is_empty` 与 `below_threshold` 判定、检索耗时。
- **FR-020**: 两路各自**失败**时 MUST 明确区分"本路无命中"与"本路执行失败"，MUST NOT 把执行失败静默记成无命中。

**工程约束**

- **FR-021**: 检索实现 MUST 放在 `d:\zg6_Project\9\med_rag\backend` 下，MUST 采用模块化组织（按「什么时机可能出错」切分，沿用既有 `backend/query/`、`backend/index/` 的划分风格）。
- **FR-022**: 任一单文件 MUST NOT 超过 300 行；超出 MUST 拆分为独立模块，且 MUST 保留唯一入口。
- **FR-023**: 检索逻辑 MUST 同时可被**运行时服务**与**命令行脚本**调用，两者 MUST 共用同一份实现，MUST NOT 各写一份（否则两条路径必然漂移）。
- **FR-024**: 检索所需的配置项 MUST 从启动期配置读取，MUST NOT 在请求路径上读环境变量；配置缺失时 MUST 明确失败。
- **FR-025**: 本特性新增的依赖 MUST 只安装进项目运行时，MUST 同步登记到仓库根 `requirements.txt`；若可以不引入新依赖，MUST 优先不引入。

### Key Entities

- **RetrievedPassage**: 一条可展示、可溯源的原文片段。八个字段（`chunk_id` / `file_name` / `page_start` / `page_end` / `section` / `block_type` / `text` / `score`）与 `docs/05` §4.2 一致。它是检索的**输出单元**，也是前端渲染单元的来源。
- **RetrievalResult**: 一次检索的完整结论 —— `passages`（降序）、`top_score`（空集为 `None`）、`is_empty`、`below_threshold`。它是检索与下游（生成、装配）之间的**唯一交接面**。
- **关键词索引语料**: BM25 可检索的全部 chunk 集合。它与向量库中的 chunk 集合必须一致（FR-009），是"两路能合并"的前提。
- **双路候选**: 语义路与关键词路各自产出的候选及其原始分数。**必须保留两路的原始分数直到融合** —— 融合规则的有效性只能靠回看两路分数来验证。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户提交一个知识库中确实存在的术语，**引用区首条片段的原文包含该术语**（人工核验 10 个术语，全部命中）。
- **SC-002**: 用户提交一个不含任何库内术语的口语化问题，**引用区非空**且首条片段与该主题相关（人工核验 10 个问题，至少 8 个相关）。
- **SC-003**: 用户从提交问题到在界面上看到引用片段，**感知等待不超过 2 秒**（不含答案生成本身）。
- **SC-004**: 知识库中不存在答案的问题，**100% 走拒答**，不出现"看起来相关但没有依据"的回答。
- **SC-005**: 同一次检索的结果中**不出现重复片段**（`chunk_id` 唯一）。
- **SC-006**: 相同问题在相同索引上连续检索两次，**结果片段集合与顺序完全一致**。
- **SC-007**: 检索模块的单文件行数**全部不超过 300 行**。
- **SC-008**: 检索接入后，**前端 `sse.js` 与 `transcript.js` 零改动**即可正确展示引用片段。
- **SC-009**: 检索链路的问题（索引未建、库不可达、参数错误）**全部在启动期或 CLI 中暴露**，MUST NOT 在用户提问时才首次出现。

## Assumptions

- **知识库非空且已入库。** 本特性假设 `data/index_manifest.json` 存在且向量库中已有 chunk（当前实测 1 篇文档 / 65 chunks）。空库路径按 FR-012 处理，但不作为主要验收场景。
- **查询向量由上游提供。** 本特性不负责编码；S8 的指纹门禁已经在启动期保证了向量空间一致，本特性不重复校验。
- **生成模块不在本期范围。** I-06（生成）与 I-04（紧急判定）仍未实现，因此本特性交付的是"检索 + 引用"，而非完整答案。正文区的处置见 FR-016 的裁决。
- **`top_k` 与 `threshold` 的具体数值尚未标定。** `docs/05` §8 已裁决 `top_k = 3`，但 constitution 的 TODO(SIMILARITY_THRESHOLD) 仍未回填。本特性交付 CLI 正是为标定提供手段；标定完成后 MUST 回填 `.env.example` 与宪法。
- **语料规模处于早期。** 当前 65 chunks，内存索引与全量扫描在数量级上完全可行。本特性可为更大规模预留位置，但 MUST NOT 为此提前引入分布式或持久化索引 —— 那是为不存在的需求付复杂度。
- **中文分词质量以"能给出可用排名"为标准。** 不追求与人工标注一致的分词边界；验收以 SC-001/SC-002 的端到端结果为准。D1 裁决引入 **jieba** 作为新增依赖（须登记 `requirements.txt` 并安装进项目运行时）；BM25 打分本身零依赖自实现，不引入 `rank_bm25` 之类的包 —— 几十行的公式引入一个包，代价大于收益。
- **服务为单进程。** 与 S8 相同前提（`backend/serve.py` 单进程单事件循环），本特性不引入跨进程共享状态。
