# 基于 PDF 文档的问答系统（RAG）

**工单编号：人工智能NLP-RAG-基于PDF文档的问答系统**

针对《招股说明书1.pdf》（548 页）的检索增强问答系统：自然语言提问 → 混合检索 → 精排 → 本机大模型生成**带页码引用**的回答。

> **硬约束**：全流程只使用本机已下载的模型，任何环节都不触发模型下载。

---

## 快速开始

```bash
# 1) 确认 Ollama 在跑，且本地已有 qwen2.5:3b
ollama list

# 2) 建库（首次或需要重建时；548 页约 3 分钟）
python build_index.py

# 3) 启动界面
streamlit run app.py
```

浏览器打开 `http://localhost:8501` 即可提问（**支持中文/英文文字提问，以及中文语音提问**）。

## 系统架构

```
【离线建库】
 招股说明书1.pdf
   └─ pdf_parser  PyMuPDF 抽文本+标题识别，pdfplumber 兜底表格 ──> 10,246 个结构化块
       └─ chunker  按标题层级分组 / 表格独立成块 / 版式噪声剔除 ──> 1,615 个 chunk
           └─ embedder  bge-m3（1024 维，CUDA，local_files_only）──> 1,615 条向量
               └─ vector_store  批量写入 ──> Qdrant collection

【在线问答】
 提问（文字 / 语音）
   └─ ⓪ 语音输入  Windows 自带离线识别器 → 领域词纠错 → 回显确认（可选）
  └─ ① Query 理解   意图识别 / 指代消歧 / 多跳分解
  │                  主体已明确时走**规则快路径**（省约 1.4s），含指代或英文问句才调 LLM
      └─ ② 混合召回  向量(top-20) + BM25(top-20) → RRF 融合
          └─ ③ 精排  bge-reranker-v2-m3 → top-6
              └─ ④ 生成  qwen2.5:3b 流式输出，强制标注 [n] 引用
              │          英文提问：问句先译成中文再检索，回答仍用英文
                  └─ ⑤ 引用核验  数字/词块比对，标出引用错位
                     └─ 答案 + 页码出处 + 耗时面板
```

## 技术选型

| 环节 | 选型 | 本地路径 |
| --- | --- | --- |
| PDF 解析 | PyMuPDF + pdfplumber | — |
| 分块 | 自研（标题层级 + 表格独立 + 去噪） | `src/chunker.py` |
| Embedding | BAAI/bge-m3（1024 维） | `D:\model\bge-m3` |
| 向量库 | Qdrant（本地嵌入式模式） | `data/qdrant` |
| 精排 | BAAI/bge-reranker-v2-m3 | `D:\model\reranker` |
| LLM | Ollama qwen2.5:3b | `D:\Ollama\OLLAMA_MODELS` |
| RAG 框架 | LangChain（ChatOllama） | — |
| 界面 | Streamlit | `app.py` |
| 语音输入 | Windows System.Speech（SAPI 5.4，**系统自带、零下载**） | `src/asr.py` |
| 评估 | RAGAS | `evaluate.py` |

**与工单原建议的差异及原因**（均为本机实测，详见[技术文档](docs/技术文档.md)第 3.2 节）：

- MinerU 软件包未安装（安装需联网）→ 改用 PyMuPDF + pdfplumber（本文件 548 页全有文本层，无需 OCR）。
  注：MinerU 的**权重已在 ModelScope 缓存中**（2.2 G + 1.6 G），装上 `mineru` 包即可零下载切换；
- 本机无 Docker → Qdrant 改用本地嵌入式模式（同一套 API）；
- 本机 Ollama 无 7b/14b → 用 qwen2.5:3b（质量与速度的最优平衡）。

## 性能

| 指标 | 实测 |
| --- | --- |
| 建库全流程（548 页） | 约 3 分钟 |
| 检索（向量+BM25+RRF） | 0.03 ~ 0.09 秒 |
| 精排（20 条） | 0.27 ~ 0.31 秒 |
| Query 理解（快路径） | ≈ 0 秒；走 LLM 时 1.4 ~ 1.75 秒 |
| 端到端问答 | 平均 **2.0 秒** / 中位 **1.8 秒**（**90% ≤ 3 秒**） |
| 界面首字延迟 | 约 0.9 ~ 1.5 秒（流式输出） |
| 语音识别（中文） | 约 1 秒 |

## 评估结果（工单给定的 10 道必测题）

| 指标 | RAG 检索问答 | 纯 LLM（无检索） |
| --- | --- | --- |
| 关键事实命中率 | **0.867** | 0.083 |
| LLM 裁判准确性（0~1） | **0.85** | 0.05 |
| 裁判满分题数 | **7/10** | 0/10 |
| 平均响应时间（秒） | 2.33 | 0.42 |
| ≤3 秒占比 | 0.90 | 1.00 |

RAGAS（仅 RAG 侧）：忠实度 **0.43** ｜ 答案相关性 **0.78** ｜ 上下文精确率 **0.93** ｜ 上下文召回率 **0.94**

> **关于命中率**：早先版本报过 0.917，那是一次偏乐观的单次采样。
> 重复 3 轮实测（两种 Query 理解模式各 30 次生成）得到的**稳定值是 0.867**，
> 且两种模式逐题结果**完全一致** —— 即"自动"快路径没有牺牲质量。详见技术文档 5.2 / 7.1。

> **不要拿单次运行的数字下结论。** 实测同一套代码连跑三轮，命中率在
> 0.867 ~ 0.917 之间跳动（Q95、Q34 两道题会因生成措辞不同而在 0.5/1.0 之间翻面）。
> 判断"改动有没有伤质量"必须重复取样——本项目就是靠"两种模式各跑 3 轮、逐题对比"
> 才确认快路径无损的。RAGAS 四项同样会浮动（裁判与被评是同一个 3B 模型）。
> 详见[技术文档](docs/技术文档.md)第 5.2、7.1 节。

> 纯 LLM 会"一本正经地编造"：例如问"参与制定了哪个技术标准"，它给出
> "GB/T 34689.2-2017 无人直升机系统技术要求"——**文档中根本不存在**的标准号。
> 这类错误从答案本身看不出来，正是 RAG 要解决的问题。
> 完整对比见 [`data/eval/评估报告.md`](data/eval/评估报告.md)。

## 注意事项

- **本地 Qdrant 是单进程文件锁**：运行 `build_index.py` / `evaluate.py` 前请先关闭正在运行的问答界面。
- 界面"知识库管理"页支持上传自己的 PDF 重建知识库（会覆盖当前知识库）。
- 所有模型配置集中在 `src/config.py`，更换模型只需改这一处。
