# 优化报告 · 瓶颈原因、优化方案与性能提升对比

> 工单编号：**人工智能NLP-RAG 项目-RAG 性能瓶颈识别与优化**
> 目标：分析检索性能慢的原因并对应优化，给出优化前后检索时间对比
> 验收：检索结果返回 ≤ 3 s
> 数据来源：`bench_compare.py`、`tools/load_test.py`、`tools/bench_components.py`、`profile_rag.py`

---

## 一、瓶颈原因（先定位，再优化）

### 1.1 阶段计时 → 哪一段慢

优化前（基线）稳态场景分阶段耗时：

| 阶段 | avg (ms) | 占端到端 |
|---|---|---|
| 查询处理与增强 | 0.3 | 0.0% |
| 查询理解 | 1.6 | 0.1% |
| **检索·向量召回** | **2282.1** | **95.5%** |
| └ **查询向量编码** | **2275.2** | **95.2%** |
| 检索·全文召回 | 37.7 | 1.6% |
| 检索·多通道融合 | 0.5 | 0.0% |
| 上下文组装·重排 | 7.8 | 0.3% |
| 后处理·答案合成 | 60.5 | 2.5% |
| **端到端总计** | **2390.5** | 100% |

**结论**：瓶颈高度集中在「检索·向量召回」，其中 **99.7% 花在子阶段「查询向量编码」**。

### 1.2 cProfile → 哪个函数慢

累计耗时 Top 函数（优化前）：时间几乎全部落在 `requests.post` —— 即**对 Ollama 嵌入服务的 HTTP 调用**（详见《性能测试报告》第四节）。

### 1.3 根因拆解

每次嵌入调用约 2.2 s，由以下**可消除的固定开销**构成：

| # | 根因 | 说明 |
|---|---|---|
| R1 | **模型重载** | 未设置 `keep_alive`，Ollama 在请求间卸载模型，每次调用重新加载（约 1.5~2 s） |
| R2 | **连接握手** | 未复用 `requests.Session`，每次新建 TCP 连接 |
| R3 | **重复编码** | 同一/相似查询被反复编码，无缓存 |
| R4 | **全量扫描** | 文档路由每次 O(N) 扫描 8086 块 |

> **瓶颈本质**：不是检索算法慢（向量/全文/重排均 < 100 ms），而是**查询向量编码阶段对本地嵌入服务的调用存在大量可消除的固定开销**（模型重载 + 连接握手 + 重复计算）。

## 二、优化方案

| # | 优化项 | 实现 | 文件 | 对应根因 |
|---|---|---|---|---|
| ① | **连接复用 + keep_alive** | 模块级 `requests.Session`；嵌入请求带 `keep_alive=30m` | `src/embedding.py` | R1、R2 |
| ② | **服务预热** | `qa.warmup()` 启动即加载模型与索引，移出请求路径 | `src/qa_engine.py` | R1 |
| ③ | **查询向量持久化缓存** | 内存 LRU + `output/query_embed_cache.json` 跨进程命中 | `src/embedding.py` | R3 |
| ④ | **文档路由预计算** | 预建「公司别名 → 块索引」路由表，O(N)→O(1) | `src/hybrid_retriever.py::_build_doc_route` | R4 |
| ⑤ | **分词与短语缓存** | 同一查询的 jieba 分词与 n-gram 短语缓存 | `src/rerankers.py` | R3 |
| ⑥ | **批量嵌入** | 多查询合并为单次 HTTP 调用，摊薄固定开销 | `src/embedding.py::encode` | R2 |
| ⑦ | **可观测性闭环** | 分阶段计时 + 结构化日志 + 指标聚合 + 阈值告警 | `src/perf.py` | — |

所有优化由环境变量 `PERF_OPT` 统一开关，保证「**同一套代码、同一份数据、同一台机器**」的公平对比。

## 五、下一瓶颈与改进建议

负载测试显示：并发 ≥ 4 后吞吐趋于平台（**~10 QPS**），延迟随并发近似线性上升。原因是**嵌入服务串行处理**成为新的吞吐瓶颈。建议：

1. **横向扩展**：嵌入服务多实例 + 负载均衡，突破单实例吞吐上限；
2. **请求批处理**：将高并发下的查询聚合为批次编码（当前已支持批量接口）；
3. **模型降维/轻量化**：可选 `bge-large`(44 ms) 或 `nomic-embed`(45 ms) 换取更低时延；
4. **异步 I/O**：将同步 `requests` 替换为异步客户端（`httpx`/`aiohttp`），提升并发效率；
5. **GPU 加速**：为嵌入/重排提供 GPU 推理，进一步压低单次编码时延。

## 六、结论

- **瓶颈**：查询向量编码（Ollama 嵌入调用）占基线端到端 **95.2%**，根因为模型重载 + 连接握手 + 重复编码 + 全量扫描。
- **优化**：连接复用 + keep_alive + 预热 + 查询缓存 + 路由预计算 + 分词缓存（`PERF_OPT` 统一开关）。
- **成效**：稳态端到端 **2375 ms → 230 ms（10.31×）**，冷启动 **2454 ms → 510 ms（4.81×）**，
  三场景均满足「≤ 3 s」验收标准，告警由 2 条降为 0 条。
- **下一瓶颈**：负载下嵌入服务吞吐封顶（~10 QPS），建议横向扩展 / 批处理 / 异步 I/O。
