### 1.4 术语表

| 术语 | 全称 / 英文 | 含义 |
|---|---|---|
| RAG | Retrieval-Augmented Generation | 检索增强生成。先从知识库检索相关资料，再把资料作为上下文交给大模型生成回答，从而抑制模型幻觉 |
| 切片 | Chunk | 知识入库时的最小检索单元。一条数据集记录可对应一个或多个切片 |
| Milvus | — | 开源向量数据库，本系统用于存放知识切片向量与长期记忆摘要向量，部署为 standalone 模式 |
| MinerU | — | 开源 PDF 解析工具，一次解析即产出 Markdown（版面、OCR、公式、表格一体）。本系统装在项目内的独立 venv，以子进程方式调用，默认 basic 档 |
| BGE-M3 | BAAI General Embedding M3 | 智源开源的多语言嵌入模型。一次前向可同时产出**稠密向量**与 **BM25 风格稀疏权重**，是混合检索的基础 |
| 稠密检索 | Dense Retrieval | 基于语义向量的相似度检索，擅长同义改写与语义泛化 |
| 稀疏检索 | Sparse Retrieval | 基于词项权重的检索（BM25 风格），擅长专有名词、法条序号、数字等精确匹配 |
| 混合检索 | Hybrid Retrieval | 稠密与稀疏两路并行召回，再融合排序 |
| RRF | Reciprocal Rank Fusion | 倒数排名融合算法。按 `1/(k+rank)` 累加各路排名得分，无需归一化不同量纲的分数，本系统取 k=60 |
| 重排序 | Rerank | 用交叉编码器（BGE-reranker-v2-m3）对粗排候选逐对打分精排，精度高于向量相似度但开销更大，故只对少量候选执行 |
| 短期记忆 | Short-term Memory | Redis List 中保存的最近 N 轮对话**原文**，保证「刚说过的话」一字不差 |
| 长期记忆 | Long-term Memory | 滑出短期窗口的旧对话经大模型压缩为摘要后，连同向量写入 Milvus，按问题语义按需召回 |
| 角色扮演 | Role-play | 大模型以固定人设（身份、语气、立场）与用户多轮对话。本系统要求角色扮演不牺牲专业性 |
| 兜底话术 | Fallback | 知识库未命中时角色应说的内容，逐个角色配置，禁止改用编造回答 |
| 免责声明 | Disclaimer | 每个角色固定的结语，由系统自动追加到回答末尾，存 `roles.disclaimer` 字段 |
| 追问改写 | Query Rewriting | 多轮对话中把「那他呢」这类含指代的追问，结合历史改写为可独立检索的完整问题 |
| SSE | Server-Sent Events | 服务端推送事件流，本系统用于 `/api/chat/stream` 的逐字输出 |

## 2. 项目背景与目标

### 2.1 项目背景

通用大模型的角色扮演产品（如 character.ai）长于「人设沉浸感」，但用于法律、心理、
金融等专业场景时存在两个突出问题：

1. **事实不可靠**——模型会生成看似专业但无法追溯、甚至凭空捏造的法条、诊断或数据；
2. **边界不可控**——缺乏领域约束的角色容易越界给出诊断、荐股等高风险建议。

本项目建设一个以 RAG 为底座的替代方案：把专业资料放进可检索的知识库，
让角色**严格依据检索资料作答**，资料不足时如实说明，从机制上而非仅靠提示词抑制幻觉。

### 2.2 项目目标

| 编号 | 目标 | 达成方式 |
|---|---|---|
| G1 | 角色回答有据可依、可追溯 | 混合检索 + 重排，回答返回 `sources` 命中来源，前端可展示 |
| G2 | 具备多轮对话的连贯性 | 双层记忆（Redis 短期原文 + Milvus 长期摘要） |
| G3 | 含指代的追问仍能准确检索 | 大模型追问改写（指代消解）后检索 |
| G4 | 角色可动态扩展、无需改代码 | 人设/规则/兜底/免责声明全部存 `roles` 表，启动时写入种子数据 |
| G5 | 知识可持续维护 | 数据集批量入库、文档上传入库（PDF 经 MinerU 解析并自动去水印）、按哈希比对增量更新与删除 |
| G6 | 专业边界可控 | 每个角色独立配置 `rules` 与 `fallback`，免责声明强制追加 |

### 2.3 与 character.ai 的定位差异

| 维度 | character.ai 类产品 | 本系统 |
|---|---|---|
| 首要目标 | 人设沉浸感、娱乐性 | 专业可靠性 + 人设一致性 |
| 知识来源 | 模型参数内知识 | 外部知识库（Milvus 检索结果） |
| 无答案时 | 自由发挥 | 走角色兜底话术，明确告知资料不足 |
| 风险控制 | 通用内容安全策略 | 角色级规则（禁诊断、禁荐股、法条须标注名称与序号） |
| 可追溯性 | 无 | 回答附带命中的知识来源与重排得分 |

## 4. 功能范围

### 4.1 本期实现范围

| 模块 | 主要接口 | 说明 |
|---|---|---|
| 对话模块 | `POST /api/chat/ask`、`POST /api/chat/stream` | RAG 完整链路、多轮会话、非流式与 SSE 流式两种返回 |
| 角色模块 | `GET /api/roles`、`GET /api/roles/hot`、`GET /api/roles/{role_key}` | 列表、热度排行、详情（含人设提示词） |
| 会话模块 | `GET /api/sessions`、`GET /api/sessions/{sid}/messages`、`GET /api/sessions/{sid}/memory`、`DELETE /api/sessions/{sid}` | 会话列表、历史消息、记忆查看、删除 |
| 用户模块 | `POST /api/users/register`、`POST /api/users/login`、`GET /api/users/{user_id}` | 注册、登录、查询 |
| 知识入库 | `POST /api/ingest/dataset`、`POST /api/ingest/upload` | 数据集批量入库、上传文档入库（PDF 走 MinerU 解析 + 去水印） |
| 知识更新 | `POST /api/update/document`、`POST /api/update/dataset/{role_key}`、`DELETE /api/update/document` | 哈希比对增量更新、批量更新、删除 |
| 系统模块 | `GET /api/health`、`GET /api/stats`、`GET /` | 依赖健康检查、业务统计、服务概览 |

内置角色固定为 3 个：`lawyer`（李律师）、`psychologist`（林医生）、
`financial_advisor`（陈理财师）。**角色数量固定但结构可扩展**——新增角色只需向
`roles` 表插入一行并准备 `data/{role_key}/` 目录，无需修改代码。

### 4.2 明确不在本期范围（Out of Scope）

| 编号 | 不做的事 | 原因 |
|---|---|---|
| O1 | 前端界面（Web / 移动端） | 本期交付后端服务，交互通过 `/docs` 或 HTTP 客户端完成 |
| O2 | JWT / Token 鉴权与接口权限体系 | 用户表与注册登录仅作数据准备；接口通过 `user_id` 参数标识用户，未接入鉴权中间件 |
| O3 | 角色数量的动态运营（超过 3 个） | 本期固定 3 个角色，仅保留扩展能力 |
| O4 | 多模态输入（图片、语音） | 仅支持文本问答 |
| O5 | 知识图谱、多跳推理 | 单跳向量检索 + 重排 |
| O6 | 用户反馈、点赞点踩与在线学习 | 无反馈回流链路 |
| O7 | 分布式部署与水平扩容 | 单机 Docker 部署，模型与向量库均为单实例 |

## 5. 非功能需求

### 5.1 性能需求

| 编号 | 指标 | 目标值 | 说明 |
|---|---|---|---|
| NFR-P1 | 非流式问答端到端时延 | P95 ≤ 60s，硬上限 120s | 上限由 `LLM_TIMEOUT=120` 兜底；`deepseek-flash` 为推理模型，先产出推理内容再产出正文，耗时高于普通对话模型 |
| NFR-P2 | 流式问答首包时延 | `meta` 事件 ≤ 5s；首字 ≤ 15s | `meta` 在检索完成后立即推送，用户可先看到来源 |
| NFR-P3 | 检索 + 重排耗时（不含大模型） | ≤ 2s | 两路各召回 `RETRIEVE_LIMIT=20`，RRF 融合后对 ≤ 40 条候选重排 |
| NFR-P4 | 模型冷启动 | 首次请求加载，其后常驻 | BGE-M3 与 Reranker 懒加载，避免阻塞服务启动；首次问答会额外耗时数十秒 |
| NFR-P5 | 纯数据库接口（角色/会话/用户） | ≤ 500ms | 角色走进程内缓存 |
| NFR-P6 | 知识库全量重建（约 13364 切片） | 实测约 2.5 分钟 | 向量化批大小 200，写入批大小 500 |

### 5.2 可用性与容错需求

系统对依赖故障采取**降级而非整体不可用**的策略：

| 编号 | 故障场景 | 系统行为 |
|---|---|---|
| NFR-A1 | MySQL 不可用 | 服务仍可启动（启动初始化异常被捕获并记录日志），角色/会话相关接口不可用 |
| NFR-A2 | Redis 不可用 | 短期记忆读写与热度统计降级：读返回空历史、写失败仅记录告警，不影响问答主流程 |
| NFR-A3 | Milvus 混合检索失败 | 自动降级为纯稠密向量检索 |
| NFR-A4 | 稠密检索亦失败 | 返回空资料，走角色兜底话术，不编造回答 |
| NFR-A5 | 重排序模型失败 | 退化为粗排顺序，取前 `RERANK_TOP_K` 条 |
| NFR-A6 | 大模型返回空正文（推理耗尽 token） | 自动将 `max_tokens` 放大至 3 倍（上限 8192）重试一次 |
| NFR-A7 | 未捕获异常 | 全局异常处理器统一返回 500 与错误信息，并记录完整堆栈 |
| NFR-A8 | Milvus 集合未加载 | 识别 "not loaded" 错误，自动重新 load 后重试一次 |

### 5.3 可扩展性需求

| 编号 | 需求 |
|---|---|
| NFR-E1 | 新增角色零代码：向 `roles` 表插入记录 + 准备 `data/{role_key}/*.jsonl` + 调用一次入库接口即可 |
| NFR-E2 | 角色人设、回答规则、兜底话术、免责声明均为数据（数据库字段），非硬编码提示词 |
| NFR-E3 | 知识来源可插拔：JSONL 数据集、PDF、TXT/MD 三类入口，统一清洗为 `embed_text` / `display_text` 结构 |
| NFR-E4 | 检索参数（召回数、重排保留数、切块大小、记忆轮数）全部通过 `.env` 可调，无需改代码 |
| NFR-E5 | 存储与模型解耦：向量库、关系库、缓存与本地模型均通过配置指向，可替换部署地址 |
| NFR-E6 | PDF 解析器可替换：MinerU 以子进程调用（`MINERU_BIN` / `MINERU_TIER` 可配），不可用时自动降级为**自研三件套**（PyMuPDF 文本层 + PaddleOCR 图表文字 + pdfplumber 表格），不影响入库接口可用性 |

### 5.4 数据安全需求

| 编号 | 需求 |
|---|---|
| NFR-S1 | 用户密码不得明文存储：使用 PBKDF2-HMAC-SHA256，20 万次迭代 + 16 字节随机盐，比对时使用 `hmac.compare_digest` 恒时比较 |
| NFR-S2 | 会话归属校验：复用已有 `session_id` 提问时若不属于当前用户，返回 403 并拒绝服务 |
| NFR-S3 | 长期记忆按 `user_id + role_id` 双维度过滤，用户之间记忆互不可见 |
| NFR-S4 | 回答不泄露系统实现细节：提示词要求角色不得提及「参考资料」「知识库」「检索」等字样 |
| NFR-S5 | 密钥与数据库口令通过 `.env` 或环境变量注入，环境变量优先（`override=False`）；`.env` 中为明文，公开或分享前须轮换 |

### 5.5 可维护性与可观测性需求

| 编号 | 需求 |
|---|---|
| NFR-M1 | 全链路日志：使用 **Python 标准库 logging** 记录角色装载、追问改写前后对比、检索召回条数、记忆归档字数等关键节点；控制台 + 滚动文件 + 错误日志三路输出 |
| NFR-M2 | `/api/health` 一次性返回 MySQL / Redis / Milvus / LLM 四项依赖状态 |
| NFR-M3 | `/api/stats` 返回集合行数、分角色知识量、用户/角色/会话/消息计数 |
| NFR-M4 | 提供 `scripts/knowledge_base.py` 支持全量重建、单角色重建、追加、清理、统计五种运维操作 |
| NFR-M5 | 接口自带 OpenAPI 文档（`/docs`），出入参由 Pydantic 模型约束 |

## 6. 约束与假设

### 6.1 技术约束

| 编号 | 约束 | 影响 |
|---|---|---|
| C1 | 大模型依赖 DeepSeek 在线 API（`deepseek-flash`） | 必须联网并配置有效 `DEEPSEEK_API_KEY`，无网络时问答不可用 |
| C2 | 向量化与重排依赖本地 GPU 运行 BGE-M3、BGE-reranker-v2-m3 | 需预先下载模型至 `/root/models/`；无 GPU 时自动退化为 fp16=False 的 CPU 推理，速度显著下降 |
| C3 | Milvus、Redis、MySQL 均为 Docker 部署 | 容器未启动时对应功能不可用；WSL 休眠会带走容器，建议设置 `restart unless-stopped` |
| C4 | 服务单实例部署（Uvicorn，默认 `0.0.0.0:8000`） | 角色缓存为进程内缓存，多实例部署时缓存不共享 |
| C5 | 向量维度固定为 1024 | 更换嵌入模型须同步调整 `EMBEDDING_DIM` 并重建集合与知识库 |
| C6 | PDF 解析主路径依赖 MinerU，装在项目内的独立 venv（`mineru/.venv`），模型约 2.0GB | 它与主环境的 `openai` 版本冲突（要求 `openai<3`），只能以子进程方式调用；未安装或解析失败时自动降级为自研三件套（PyMuPDF + PaddleOCR + pdfplumber），扫描件与图表仍能读出，但阅读顺序与公式弱于 MinerU，且 28 页文档耗时约 283 秒（MinerU 主路径约 38 秒） |

### 6.2 假设

| 编号 | 假设 |
|---|---|
| A1 | 用户提问为中文，知识库语料亦以中文为主 |
| A2 | 角色数量少、变更不频繁，允许使用进程内缓存（进程重启后自动重建） |
| A3 | 会话历史规模适中，`messages` 按 `session_id` 顺序查询即可满足需求 |
| A4 | 上传文档可为扫描件或含图表：PDF 解析走 MinerU（版面 + OCR + 表格），不再假设「必有文字层」；MinerU 不可用时退回三件套兜底（PyMuPDF 文本层 + PaddleOCR 图表文字 + pdfplumber 表格），扫描件与图表仍可读出，只是阅读顺序与公式弱于 MinerU |
| A5 | 上传文件大小与并发量处于单机可承载范围（无显式限流与配额） |

## 7. 验收标准

| 编号 | 验收项 | 验收方法 | 通过标准 |
|---|---|---|---|
| AC1 | 服务可启动 | 启动后执行 `docker start redis mysql8 milvus-standalone`，运行 `python run.py` | 日志显示模型就绪与角色种子数据写入成功，`/docs` 可访问 |
| AC2 | 依赖健康 | `GET /api/health` | `mysql` / `redis` / `milvus` 均为 `true`，`llm` 为 `true` |
