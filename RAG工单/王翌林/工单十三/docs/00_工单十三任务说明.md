# 工单十三：RAG 性能瓶颈识别与优化——任务说明

> 工单编号：人工智能NLP-RAG-RAG性能瓶颈识别与优化
> 创建时间：2025-08-26（工单）｜完成时间：2026-10-07
> 工时预估：1 人日

## 一、任务描述

RAG 系统搭建后，RAG 检索结果返回时间要优化到 **3S 以内**；针对检索结果返回
时间过长的问题，需要分析性能瓶颈的原因。

RAG 系统的延迟是其组成部分的延迟之和，再加上各阶段之间数据传输或排队产生的
任何开销；吞吐量通常由处理能力最低的阶段决定。本工单通过分析典型 RAG 流程
的运行时间，定位影响性能慢的原因：

1. 查询处理与增强
2. 检索阶段
3. 上下文组装与提示工程
4. LLM 生成
5. 后处理与响应格式化

## 二、识别缓慢之处的工具和技术

| 手段 | 本工单落地 |
| --- | --- |
| 1. 性能分析 | 应用级：Python cProfile（`scripts/benchmark_v13.py --phase profile`），产出 `docs/v13_profile_stats.txt` |
| 2. 日志记录 | 每阶段进入/退出结构化日志（`src/perf_v13.py` → `logs/perf_v13.jsonl`），含请求 ID、检索文档数、上下文长度、生成 token 数 |
| 3. 分布式追踪 | 单体部署，以请求 ID 贯穿线程池通道日志替代（OpenTelemetry 级别方案在文档中说明） |
| 4. 监控与告警 | 分阶段 p50/p95/max 聚合（`docs/v13_benchmark_*.json`），可对接 Prometheus/Grafana |
| 5. 负载测试 | 线程池并发压测（`--phase load_before/load_after --concurrency 5`），验证瓶颈在压力下显现 |
| 6. 基准测试 | 分阶段独立计时（嵌入/Milvus/全文/融合/重排/LLM），量化各组件原始性能 |

## 三、任务目标

1. 分析造成检索性能慢的原因在哪里，并对应优化
2. 给出优化前后的检索时间对比

## 四、产出物

1. 过程跟踪步骤、过程问题记录文档（`docs/14_工单十三性能瓶颈识别与优化.md`）
2. 出现瓶颈的原因、优化方案及性能提升对比（同上 + `docs/v13_benchmark_*.json` + 截图）

## 五、验收标准

**每个会话，用户输入 query 后，返回的检索结果要在 3S 以内。**

## 六、实现方案

- 基线：工单六 v6 可配置混合检索引擎（bge-m3 向量 + 倒排全文 + RRF 融合
  + bge-reranker-v2-m3 交叉编码重排 + 表格/图像通道 + DeepSeek LLM）
- 插桩：`src/perf_v13.py` 分阶段计时模块，五阶段 + 检索子阶段全部打点
- 基准：`scripts/benchmark_v13.py`（before/after/profile/load 四种模式）
- 优化：召回候选 24+24→12+12、重排输入截断 1500→512、查询嵌入 LRU 缓存、
  启动预热（消除冷启动）
