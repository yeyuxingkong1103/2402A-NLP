# 工单十七 · 性能瓶颈与内存泄漏排查分析报告

## 1. 故障现象（试运行阶段，≥10 并发）

| 现象 | 表现 |
|------|------|
| 响应延迟飙升 | 问答接口平均响应从 ~2s 增至 10s+ |
| 内存泄漏与崩溃 | 容器 RSS 随时间持续上涨，数小时后 OOM Killer 杀死进程 |
| GPU 利用不当 | 纯文本问答时 GPU 显存仍被大量占用且不释放 |

## 2. 定位方法

1. **压测复现**：用 Python 线程压测 + Locust 复现 20 并发问答（场景A）与混合负载（场景B）。
2. **应用剖析**：`py-spy top` 采样 API 进程，定位 CPU 热点；`memory-profiler`/`objgraph` 跟踪请求周期内对象留存。
3. **资源监控**：`docker stats`、`nvidia-smi` 观察容器内存与 GPU；`redis-cli INFO stats` 观察任务队列堆积。
4. **静态代码审查**：聚焦请求入口、模型加载单例、DeepDoc 调用上下文。

## 3. 根因定位（基线版 `src/api_baseline.py` 复现）

| 编号 | 泄漏/瓶颈点 | 代码位置 | 根因 |
|------|------------|----------|------|
| 泄漏1 | 全局缓存无限增长 | `LEAKY_CACHE` 字典 | 键带 uuid 永不命中去重，且无容量/TTL 上限，RSS 持续上涨（实测 +917%） |
| 泄漏2 | 向量连接不归还 | `LEAKED_CONNECTIONS.append(conn)` | 每次检索新建连接且永不释放，连接池泄漏 |
| 泄漏3 | 中间对象不释放 | `heavy_init()` 返回大对象被持有 | 每请求分配 2MB 且不 del、不 gc |
| 瓶颈1 | 每请求初始化重组件 | 每次调用 `heavy_init()` | 重复初始化解析器/模型，0.3s/次，并发时争用 |
| 瓶颈2 | 无队列/无限流 | LLM 直接阻塞 | 高并发线程堆积，延迟随并发线性上升 |

## 4. 优化措施（优化版 `src/api.py` + `src/rag_engine.py`）

| 问题 | 修复 | 实现 |
|------|------|------|
| 重复初始化 | 单例 + 进程内缓存 | `RAGEngine.__new__` 单例，组件启动时初始化一次 |
| 连接泄漏 | 连接池 borrow/return | `ConnectionPool`，try/finally 必归还 |
| 缓存泄漏 | 有界 LRU + TTL | `LRUCache(capacity=512, ttl=300)`，超容自动淘汰 |
| 请求堆积 | LLM 并发信号量 + 异步 | `Semaphore(40)` 限推理并发，`run_in_executor` 异步不阻塞事件循环 |
| 文档解析阻塞 | Redis/内存队列异步消费 | `_doc_consumer`，API 立即返回 task_id |
| GPU/内存不释放 | 显式 del + gc + empty_cache | 推理后 `del tmp; gc.collect()`（GPU 场景加 `torch.cuda.empty_cache()`） |
| 可观测性 | Prometheus 指标 | `/metrics` 暴露请求量/延迟分位/在途/缓存/RSS |

## 5. 验证结论

优化后在 20 并发、45s 压测下：
- 内存增长：+917% → **<10%**（无持续上涨，泄漏修复）。
- 延迟与吞吐：因去除每请求初始化开销，稳定优于基线（详见 `01_性能测试报告.md` 与截图）。
- 服务无崩溃、无请求失败。
