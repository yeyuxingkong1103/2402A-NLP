# 表格解析优化说明

**工单编号**：人工智能NLP-RAG-PDF 文档的表格解析及检索优化
**优化对象**：工单1/2 交付的问答系统
**数据来源**：`测试/eval_accuracy.py`，标准答案见 `测试/ground_truth.py`

---

## 一、为什么本工单的重点是表格解析

工单备注明确要求：「分析待检索的问题答案在 pdf 中的定位，**使用表格解析技术实现**」。

新增《招股说明书2.pdf》（武汉力源信息，350 页 / 241 个表格）后的 4 道新题，
答案**全部来自表格**：

| 题 | 答案 | 所在位置 |
|---|---|---|
| Q1 | 发行股数 1,670 万股，占发行后总股本 25.04% | p22/p24 发行基本情况表 |
| Q2 | 仓储及物流中心、研发中心、电子商务平台、扩充产品种类和数量、其他营运资金 | p22 募集资金用途表 |
| Q3 | 赵马克，持股 42.35%，公司控股股东 | p157 关联方表 |
| Q4 | 融冰投资、武汉博润、上海博润、听音投资、联众聚源、力源贸易、普芯达 | p157 关联方表 |

**纯文字提取会把这些表格打散**。以 p157 为例，PyMuPDF 抽出来是这样：

```
关联方名称          ← 表头
持股比例
与本公司关系
赵马克              ← 数据行 1
42.35%
公司控股股东
```

单元格之间只有换行、没有行结构，按 800 字切块时「赵马克」和「42.35%」
很可能被切到不同的块里。必须靠 pdfplumber 还原成
`| 赵马克 | 42.35% | 公司控股股东 |` 才能真正拿到答案。

## 二、三项表格解析优化

### 优化 1：清理空行空列

pdfplumber 会因为版面里的空白间隙切出大量空列。p157 的关联方表被切成 **9 列，其中 6 列全空**：

```
优化前：|  | 关联方名称 |  |  | 持股比例 |  |  | 与本公司关系 |  |
        | 赵马克 |  |  | 42.35% |  |  | 公司控股股东 |  |

优化后：| 关联方名称 | 持股比例 | 与本公司关系 |
        | 赵马克 | 42.35% | 公司控股股东 |
```

**效果**：表格块 Markdown 体积平均**减少 16%**，检索时不再被 `|  |  |` 这类
填充符稀释。

### 优化 2：给表格块补上标题（本工单最关键的一项）

表格单元格里只有 `赵马克 | 42.35% | 公司控股股东`，而**「关联方」这个关键词
在表格上方的标题行里**。不带标题的话，这张表会被文档里另外十几张「持股比例」
表格淹没。

实现：用 pdfplumber 的表格边框定位，裁出表格上方最近的 2 行文字作为标题，
拼在表格 Markdown 前面：

```
【(一)关联方及关联关系 1、存在控制关系的关联方】
| 关联方名称 | 持股比例 | 与本公司关系 |
| 赵马克 | 42.35% | 公司控股股东 |
```

**两个必须处理的细节**（都是实测踩出来的）：

1. **一页多表时要设下界**。p157 同页有「存在控制关系」「不存在控制关系」两张表，
   不设下界的话，第一张表的数据行会被当成第二张表的标题：
   `【关联方名称 持股比例 与本公司关系 赵马克 42.35% 公司控股股东 2、不存在控制关系的关联方】`。
   修正方式是把裁剪区的上界设为上一张表的底边。
2. **要滤掉页眉**。标题是从版面文字裁的，会裁到页眉
   （`【武汉力源信息技术股份有限公司 招股意向书 3、报告期内曾为关联方…】`）。
   复用文字层的页眉检测结果过滤即可，但**必须先做空白归一化** ——
   PyMuPDF 保留版面空白、pdfplumber 压成单空格，精确匹配会漏掉。

### 优化 3：多文档支持与按公司名路由

工单3 要求在同一套系统里同时解析两份招股书。实现方式：

- 每份 PDF 单独建索引，公司名从 PDF 开头三页自动提取
  （出现次数最多的「XX股份有限公司」即为发行人，实测两份都取对）
- 提问时看问题里出现的是哪家公司名，路由到对应知识库
- 都没匹配上则全库检索后合并

## 三、优化效果实测

### 3.1 表格块的检索名次（核心证据）

对 Q3/Q4 两道关联方题，测 p157 表格块在召回列表中的名次：

| 题目 | 优化前（无表格标题） | 优化后（有表格标题） |
|---|---|---|
| Q3 存在控制关系的关联方 | 名次 3 | **名次 1** |
| Q4 不存在控制关系的关联方 | 名次 10 | **名次 2** |

Q4 从第 10 名提到第 2 名 —— 优化前它刚好卡在 Top-8 边缘，换个问法就会掉出去。

### 3.2 14 题端到端结果

| 指标 | 优化前（工单2 代码） | 优化后（本工单） | 工单要求 |
|---|---|---|---|
| 回答准确率 | 100%（14/14） | **100%（14/14）** | ≥ 90% ✅ |
| 检索命中率 | 100%（14/14） | **100%（14/14）** | — |
| 检索精确率 | 23% | **24%** | — |
| 响应时间（平均） | 2.13 s | 2.30 s | ≤ 3 s |
| 超 3 秒题数 | 1 / 14 | 3 / 14 | — |

> 本轮优化前的代码也能拿到 100%，原因是**文字层的块恰好也带着标题文字**，
> 兜底命中了答案页。表格标题的价值在于**不依赖这个巧合**：文字层没有表格内容
> 或标题被切散时（真实 PDF 里很常见），只有带标题的表格块能召回。
> 从 3.1 的名次数据可以看到，表格块的排序鲁棒性确实提升了。

### 3.3 响应时间说明

两次测量中位水平都在 2.1 ~ 2.3 秒，超 3 秒的题目数在 1~3 之间波动。
**波动来自大模型（deepseek-flash 是推理模型）自身的推理步数差异，与检索无关** ——
同一道题在不同轮次可以跑出 1.4 秒和 4.2 秒。检索层本身的耗时是确定的：
BGE-M3 召回 20 个候选约 0.08 秒。

## 四、遗留问题

| 问题 | 现象 | 原因 |
|---|---|---|
| 检索精确率偏低（24%） | 送入 8 个块，平均约 2 个来自答案页 | 财务表格块的文字是「数字＋标签」，与散文式提问在向量空间对不上 |
| 偶发超过 3 秒 | 14 题中 1~3 题，最慢 4.16 s | 推理模型自身耗时抖动 |
| 跨页表格 | 跨页的表格会被 pdfplumber 拆成两张，标题只挂在第一张上 | 未做跨页表格合并；本工单 4 道新题的表格都不跨页，暂未影响结果 |
