
**离线建库链路**（`scripts/build_index.py`，一次性）：

```
PDF ─▶ pdf_parser(逐页提文本 + 去页眉页脚 + 行内标题断行 + 表格转 Markdown)
    ─▶ chunker(标题感知分块 + 滑动窗口 + 长度兜底)
    ─▶ embedder(bge-small-zh-v1.5, 512维, L2 归一化)
    ─▶ index_store(落盘 chunks.jsonl / embeddings.npy / index_meta.json)
```

**在线问答链路**（每次提问）：

```
问题 ─▶ normalize_query(切输出指令 / 去句末标点 / 口语转书面)
     ─▶ Query 理解(意图 + 改写检索式 + 子问题 + 关键词)
     ─▶ 剔除语料级无区分度词
     ─▶ 稠密召回(余弦 top20) ∪ 稀疏召回(BM25 top20)
     ─▶ 加权融合：依据分 = 余弦 + 0.30×BM25归一；融合分 = 依据分 + 0.25×文档共识
     ─▶ 阈值闸门(依据分 ≥ 0.80) ─▶ 取 top8
     ─▶ 组装上下文(带页码) ─▶ LLM 生成(带 [第X页] 引用，流式)
```

## 二、技术选型

| 层次 | 选择 | 理由 | 被否决的方案及原因 |
|---|---|---|---|
| PDF 解析 | **pypdf**（主）+ **pdfplumber**（表格） | pypdf 快（548 页 22s）；pdfplumber 表格结构还原好但慢，故只对**疑似表格页**启用 | 全量 pdfplumber：548 页要 6~9 分钟；PaddleOCR：本机未装，且该 PDF 是文字版不是扫描件 |
| 向量模型 | **bge-small-zh-v1.5**（512 维，CPU） | 本机已有，184MB，单条编码约 15ms，断网可用 | 在线 embedding API：多一次网络往返，无法保证 3 秒响应；bge-m3：1.2GB，本机内存吃紧 |
| 向量检索 | **NumPy 暴力余弦** | 1261 块 × 512 维，一次矩阵乘法 <5ms；零外部服务 | Milvus：本机 19530/19531 已被其它项目占用，多一个常驻进程就多一处故障点；FAISS：收益极小却多一个二进制依赖 |
| 关键词检索 | **jieba + rank-bm25** | 中文必须分词，否则 BM25 对长句恒为空（见第四节坑 3） | Milvus 内置 BM25：需要建表时指定 chinese analyzer，且要额外起服务 |
| 融合策略 | **加权融合**（余弦为基础 + BM25 加成 + 文档共识先验） | 见第四节坑 4：RRF 只看排名、会奖励纯关键词噪音 | RRF：会把「仅被 BM25 命中的噪音」按名次提上来，且归一化后 top1 恒为 1.0，阈值闸门失效 |
| 大模型 | **qwen-flash**（DashScope 兼容模式） | 实测 0.64s / 次，流式首字 0.44s，非推理模型 | qwen3.7-flash / qwen3.5-flash / qwen3.8-flash **都是推理模型**，先吐思维链，单次 2.9~88 秒（见第四节坑 6） |
| 评审模型 | **qwen-plus** | 0.95s/次，非推理，判断比 flash 严谨 | 与生成用同一模型：评审会偏向自己产出的答案 |
| 服务框架 | **FastAPI + 原生 HTML/CSS/JS** | 零构建、零 npm，改完刷新即生效 | Vue/React：本工单不需要组件复用，构建链反而增加交付复杂度 |
| 进程内存储 | 单例内存态 + 磁盘文件 | 无 MySQL / Redis 依赖，部署即拷目录 | 数据库：单文档场景没有多租户、并发写的需求 |

## 四、关键设计决策与踩坑记录

这一节记录**实际调通过程中踩到的坑**。每一条都是先观察到现象、再用数据定位、最后改代码验证过的。

### 坑 1：表格块撑爆长度上限，导致入库整批失败

**现象**：干跑报 `存在超上限的块 1768 > 1200`。

**原因**：表格 Markdown 直接成块，没走长度兜底。而表格**不能硬切**——从中间断开会让行列对不上。

**修法**：按行拆表，每块**重复表头**（Markdown 的 header + 分隔行），保证每一块单独看都是自洽的表格。见 `chunker._split_markdown_table`。

**回归**：`build_index.py` 里断言 `max(len(chunk)) <= CHUNK_MAX_LENGTH`，不满足直接退出码 3。

### 坑 2：标题识别失效 → 正确答案被挤出上下文

**现象**：问「注册资本是多少」，召回里根本没有第 22 页那张写着 `注册资本 5,520.00 万元` 的表。

**根因**（两步定位）：

1. 该 PDF 由 Word 转出，**标题常与上一段被压进同一行**：
   `……数字传输网络。第二节 概览 本概览仅对招股意向书全文做扼要提示。`
   行首匹配的标题正则全部失效 → 「释义」和「概览」两个大节混进同一块。
2. 混块的向量被两个主题拉扯，既不像释义也不像概览，余弦排名掉到第 81 位，落选。

**修法**（两层）：

- `pdf_parser.split_inline_headings`：在**紧跟在句末标点之后**的层级标题前强制断行；
- `chunker`：**一级标题（第X节/第X章）无条件断块**，跨节拼接从此不可能发生。

**验证**：修复后第 22 页与第 52 页的块都进入 top8，答案里的 `5,520.00 万元` 有了出处。

### 坑 3：中文 BM25 静默失效

BM25 必须用 jieba 分词。若按空格切词，整句中文会被当成**一个 token**，BM25 对任何中文长句都召不回东西——而且**它不报错**，混合检索会无声退化成纯向量检索。

本项目的 `KnowledgeBase.tokenize` 强制走 jieba，并在探针里打印 `BM25 命中 N 条`——只要这个数是 0，就是分词出了问题。

### 坑 4：不用 RRF

教科书做法 RRF（`Σ 1/(k+rank+1)`）在本场景会办坏事：

1. **给纯关键词噪音排名奖励**。RRF 只看排名、无视分数，任何一路的噪音都能按名次获得奖励。
2. **归一化后阈值失效**。归一化 RRF 的 top1 恒为 `1.0`，阈值闸门等于不存在。

改用加权融合：`依据分 = 余弦 + β·BM25归一`，`融合分 = 依据分 + δ·文档共识`。**阈值闸门只认依据分**——若让闸门看融合分，离题问题会因为主题先验加分而拦不住。

### 坑 5：子问题过度拆分污染召回

**现象**：问「报告期内……来自军用领域的收入分别是多少」，答「资料中没有相关内容」。

**根因**：Query 理解把问题拆成了「报告期**第一年**/**第二年**/**第三年**来自军用领域的收入」——文档里根本没有"第一年"这种说法。三路噪音召回的分数（0.9985）压过了主查询正确答案（0.9729），把正确答案挤出了上下文。

**修法**（双保险）：

- 检索侧：**主查询结果整体占位**，子查询只用于补位，且分数不得低于主查询最低分，最多补 `top_k/2` 条（`rag.retrieve_for`）；
- 理解侧：prompt 里明确「默认只返回原问题；禁止造词，子问题必须是文档里原样搜得到的表述」。

### 坑 6：推理模型让 3 秒要求直接落空

**现象**：端到端 39 秒。

**根因**：`.env` 里沿用了别的项目留下的 `qwen3.7-flash`——**它是推理模型**，会先输出思维链。实测单次请求：

| 模型 | 耗时 | 是否推理 |
|---|---|---|
| qwen3.5-flash | **88.08s** | 是 |
| qwen3.7-flash | **20.84s** | 是 |
| qwen3.8-flash | 2.97s | 是 |
| **qwen-flash** | **0.64s** | 否 |
| qwen-turbo | 0.63s | 否 |
| qwen-plus | 0.95s | 否 |

**修法**：生成与理解用 `qwen-flash`，评审用 `qwen-plus`。

**顺带**：`src/llm.py` 的流式接口同时消费 `content` 与 `reasoning_content`，换模型时上层代码不用改。

### 坑 7：冷启动吃掉第一个请求的 39 秒

**根因**：索引加载 + jieba 建 BM25 表（1.8s）+ 向量模型加载（约 3s）+ LLM 连接握手（约 10s），全部堆在第一次提问上。

**修法**：`main.py` 的 `warm_up()` 在启动时把这些跑一遍。预热失败只告警不阻止启动——索引问题应该体现在 `/ready` 里，而不是让服务起不来。

### 坑 8：主体名称是"高权重噪音"

**现象**：问「**武汉兴图新科电子股份有限公司**报告期内来自军用领域的收入分别是多少」召回错误；把公司名去掉（「报告期内来自军用领域的收入分别是多少」）立刻召回正确。

**根因**：单文档语料里，主体名称几乎无处不在，**没有区分力**，却是 BM25 的高频命中源；第 532 页的贷款合同表格里反复出现公司全称，于是被顶到第一。

**修法**：`KnowledgeBase.ubiquitous_terms` 按**文档频率**自动识别这类词（等价于让语料自己生成停用词表），检索前从查询里剔除；过滤后若不足 4 字则退回原串，避免把有效信息也滤空。

**阈值是扫出来的**（同一份 10 题 + 3 个离题问题）：

| DF 阈值 | 10 题命中 | 离题最高依据分 |
|---|---|---|
| 不滤 | 9/10 | 0.7410 |
| 0.30 | 9/10 | 0.7410 |
| **0.20** | **10/10** | 0.7410 |
| 0.15 | 9/10（把有效词也滤掉了） | 0.7410 |

### 坑 9：`needs_retrieval` 不能交给模型裁量

模型把「如何用 Python 实现快速排序？」判成闲聊，于是跳过检索、返回寒暄语。而正确处理应该是「照常检索 → 被闸门拦空 → 如实回答无依据」。

**修法**：判据改成确定性的——**只有命中纯闲聊正则才跳过检索**。

## 五、参数校准（都是实测，不是拍脑袋）

### 阈值闸门 `RETRIEVAL_MIN_EVIDENCE = 0.80`

命令：`python scripts/probe_retrieval_rank.py --calibrate`

| 问题类型 | 依据分区间 |
|---|---|
| 工单 10 个真相关问题 | top1 **0.9388 ~ 1.0542**，top6 最低 **0.8732** |
| 3 个明确离题问题 | 最高 **0.7487** |

两段区间不重叠，取中间值 0.80。

> **为什么不用 0.55？** 单文档语料上余弦分天生扁平——离题问题也能拿到 0.56~0.75（文档通篇都讲同一家公司）。只有加上 BM25 那一项，真相关问题才被推到 0.87 以上，离题问题（关键词一个都命中不了）留在 0.75 以下。
> **搬到多文档语料必须重新校准。**

### 融合权重

- `RETRIEVAL_BM25_BETA = 0.30`：BM25 先按组内最大值归一到 0~1 再相加。BM25 无上界（本语料实测 0~23），直接相加会淹没余弦。
- `RETRIEVAL_DOC_CONSENSUS_DELTA = 0.25`：**加法**而非乘法。乘法对「余弦高但没命中关键词」的块是灾难（0.72×0.5=0.36，反而输给余弦 0.68 有关键词加成的块）。单文档语料下该项退化为常数，不影响排序。

### 分块

`CHUNK_SIZE=600 / OVERLAP=80 / MIN=40 / MAX=1200`

打包策略是**跨小节累积**而非「遇标题就断」：招股书里大量小节只有一两句话，逐标题断开会产生大量 100 字以下的碎块。实测平均块长从 259 字提升到 **508 字**，块数 1767 → 1261。

## 六、性能实测

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 建索引（一次性） | 约 **2.5~6 分钟** | 解析 48s + 向量化 109~285s（纯 CPU，随内存压力波动） |
| 启动预热 | 约 **33 秒** | 索引 + BM25 + 向量模型 + LLM 握手，只跑一次 |
| Query 理解 | 0.6 ~ 2.8s | qwen-flash |
| 检索（热） | **18 ~ 60 ms** | 余弦 + BM25 + 融合 |
| 生成 | 0.9 ~ 3s | qwen-flash，上下文约 4800 字 |
| **端到端（热）** | **平均 2.30s，9/10 ≤3s** | 见评估报告 |
| 流式首字延迟 | **1.0~2.0s**（实测样例 1.96s，总额 2.56s） | 用户感知的"开始回答"时间 |

> 超过 3 秒的唯一一例是 id=260（3.91s），它要**列出 4 个年度的数据**，输出更长。
>
> **一处口径提醒**：评估脚本 `run_eval.py` 与 `main.py` 都必须在业务开始前预热。
> 不预热时第一次 `retrieve` 要额外承担「索引加载 + jieba 建 BM25 表 + 向量模型加载」，
> 实测会把这一题的耗时从 20ms 拉到 **14.4 秒**，直接把 `avg_total_ms` 从 2.2s 抬到 3.7s。
> 这不是检索慢，是冷启动——**报数之前先确认口径里没有冷启动**。

## 七、评估体系

`src/evaluator.py` 用 **LLM-as-judge** 实现 RAGAS 四项核心指标：

| 指标 | 定义 | 判据 |
|---|---|---|
| faithfulness 忠实度 | 答案是否由检索上下文支撑 | 拆分断言逐条判定，score = 有依据条数 / 总条数 |
| answer_relevancy 答案相关性 | 答案是否切题 | 五档打分，注意区分"确实超范围"与"材料里有却拒答" |
| context_precision 上下文精确率 | 召回片段中相关片段占比 | 逐条判定，score = 相关数 / 总数 |
| context_recall 上下文召回率 | 参考答案要点被覆盖比例 | 需要参考答案（工单 10 题已人工核对补入） |
| answer_correctness 答案正确性 | 与参考答案的事实一致程度 | 数字/名称/年份逐项比对 |
| llm_only_* | 纯 LLM 对照组的同名指标 | 用于工单要求的对比分析 |

**为什么自带实现而不用 ragas 包**：

1. ragas 会拉进 langchain-community 整套依赖（百 MB 级），本机内存常态只剩几百 MB，装完还要和 torch 抢内存；
2. 上述四项定义本身清晰可自查，同 prompt 逻辑实现的结果可复现、可人工复核；
3. 不引入新依赖 = 少一处版本冲突。

**串行执行**：本机 LLM 侧有账号级限流，并发只会把请求全打成 429，而重试退避会让评估"跑几十分钟、一条分数都没有"。

### 评估集

`data/eval/ticket_questions.json`：工单指定的 10 个问题 + **人工从原文核对出的参考答案**。

参考答案不是模型生成的，是逐条从招股意向书原文里找出来的（例如注册资本 5,520.00 万元
出自第 22 页「第二节 概览」的发行人基本情况表，法定代表人程家明同页）。

### 一个值得记录的发现：原文自身不一致

评估过程中 id=260 反复被判「与参考答案矛盾」。追查后确认**不是抽取错误，也不是模型错误**：

| 位置 | 2019 年 1-6 月军用领域收入 |
|---|---|

## 八、接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | JSON 根路由（保留，不被前端覆盖） |

| GET | `/docs` | FastAPI 自动文档 |

| GET | `/api/kb/status` | 知识库统计 |
| GET | `/api/questions` | 工单 10 题 |
| POST | `/api/ask` | 非流式问答 |
| POST | `/api/ask/stream` | SSE 流式问答 |
| POST | `/api/compare` | RAG vs 纯 LLM |
| POST | `/api/upload` | 上传 PDF 并重建索引 |

业务接口统一信封 `{code, message, data, trace_id}`；系统探针返回**裸对象**（不套信封），
前端解析时判据是 `payload.code === 'OK'`，而不是「有没有 code 字段」。

### SSE 帧序（顺序本身承载语义，不要"顺手优化"）

```
stage(understand,running) → stage(understand,done)
→ stage(retrieve,running) → stage(retrieve,done,含融合明细)
→ meta（不含引用）
→ stage(generate,running) → delta* （+ thinking* 若模型是推理型）
→ stage(generate,done,含首字延迟) → citations → done
```

- **引用必须排在正文之后**：用户要的是"先读到答案，再看依据"。
- **帧体统一用 JSON**：裸文本帧里的换行会破坏 SSE 帧边界，长回答会被截断成第一段。

## 九、已知限制

1. **单文档假设**。文档共识先验、无区分度词过滤都建立在"只有一个来源文档"的前提上。接入多文档知识库时需重新校准阈值，并让共识先验真正发挥作用。
2. **无 OCR**。本机未装 PaddleOCR，扫描件 PDF 解析不出文本。该招股意向书是文字版，不受影响。
3. **表格还原有限**。pdfplumber 只对**疑似表格页**启用（本语料 236 页），无边框的版式表格可能漏抽。
4. **未接重排模型**。本机 GPU 显存 4GB、可用提交内存仅 1.0~1.4GB，bge-reranker-v2-m3 加载会直接原生 abort。当前排序靠加权融合，实测 10/10 命中。
5. **评估仍依赖 LLM 判断**。judge 模型自身有偏差，报告里的分数应横向比较（RAG vs 纯 LLM）、不宜当作绝对精度。
6. **演示视频**需在真实浏览器中录制（工单产出物之一），无法由脚本生成。

## 十、复现步骤

```bash
# 1. 安装依赖（或复用本机已有虚拟环境 D:\roleplay-rag\.venv）
python -m venv .venv && .venv\Scripts\pip install -r requirements.txt

# 2. 填 .env 里的 LLM_API_KEY（其余可保持默认）

# 3. 干跑：先确认解析与分块正常（不向量化，约 30 秒）
python scripts/build_index.py --no-tables --dry-run

# 4. 正式建索引（约 2.5~6 分钟）
python scripts/build_index.py

# 5. 校准探针（确认阈值仍适用）
python scripts/probe_retrieval_rank.py --calibrate

# 6. 跑评估，产出报告
python scripts/run_eval.py

# 7. 启动服务
python main.py     # → http://127.0.0.1:8010/ui

# 8. 录制演示视频时，用这个台本逐屏展示内部过程
python scripts/demo_walkthrough.py
```
