# 需求规格说明书

## 1. 项目背景与目标

### 1.1 背景

电力检修人员日常需要查大量国家标准（GB/T）。痛点不是「查不到资料」，
而是**知道要查什么、却翻不到那一条**：一份标准几十页，条款分散在不同章节，
纸质或 PDF 目录检索只能靠关键词匹配，同义表达（「乙炔注意值」vs「C₂H₂ 含量注意值」）就搜不到。

### 1.2 目标

做一个**基于 RAG 的电力维修问答系统**，把标准文档切块入库，
提问时先检索出最相关的条款片段，再让大模型**只依据这些片段**作答，
并给出引用来源，做到**有出处、可追溯、不编造**。

### 1.3 交付形态

| 交付物 | 形态 |
|---|---|
| 后端服务 | FastAPI 应用，16 个 HTTP 接口，含流式 SSE |
| 前端页面 | Vue3 + Vite + Element Plus，9 个功能页面 |
| 知识库 | Milvus 集合 `power_repair_docs`，724 条子块向量 |
| 部署脚本 | `install.sh` / `run.sh` / `shutdown.sh` |
| 文档 | 需求、设计、接口、流程、业务规则、思维导图、测试成果 |
| 评测 | RAGAS 四指标评测集与结果 |

## 4. 业务流程

### 4.1 离线：资料入库

```
PDF 资料目录
  → 逐页解析（有文本层用 PyMuPDF / 表格用 pdfplumber / 扫描页用 PaddleOCR）
  → 规则清洗（去水印、去页眉页脚）
  → 语义切分（段落 → 超长按句 → 合并过短，单块 ≤ 500 字）
  → 离线增强（LLM 摘要 → 低质过滤 → 语义去重 → 父子块）
  → BGE-m3 向量化（稠密 1024 维 + 稀疏）
  → 写入 Milvus 集合 power_repair_docs
```

详细流程图见 `docs/流程图.md` 第 1 节。

### 4.2 在线：问答

```
用户提问
  → 取短期记忆（Redis）
  → 有历史则查询改写（把「那具体呢」补全）
  → 查答案缓存（非流式）→ 命中则跳过检索与生成，但仍写回记忆
  → 混合检索（稠密 + 稀疏）→ RRF 融合 → 20 条候选
  → 多路召回（Milvus 20 + MySQL 历史 10，MySQL 路权重 0.5）
  → 交叉编码器精排 → 过滤 < 0.3 → 取前 5
  → 附加父块全文 → 长期记忆单独召回 → 组装提示词
  → DeepSeek 流式生成 → 后处理 → 校验
  → 写回 MySQL / Redis / Milvus → SSE 推给前端
```

详细流程图见 `docs/流程图.md` 第 2 节。

### 4.3 用户操作主流程

```
打开前端 → 未登录跳登录页 → 注册/登录 → 选择角色 → 提问
  → 查看流式回答与引用来源 → 追问（多轮）→ 在历史页回看
  → 在知识库页查看条数 / 上传新资料 / 清缓存 → 在评测页看指标
```

## 5. 业务规则（摘要）

完整规则见 `docs/业务规则.md`，核心 8 条：

| # | 规则 | 要求 |
|---|---|---|
| 1 | 领域边界 | 只答电力维修、设备检测、电力标准；无关问题不展开 |
| 2 | 安全优先 | 涉及人身安全必须提醒「先断电、验电、挂接地线」，且放显著位置 |
| 3 | 不编造 | 无依据时必须说「标准文档中没有找到相关条款」，绝不编标准编号、条款号、数据 |
| 4 | 不偏方 | 不提供未经标准验证的偏方、土办法 |
| 5 | 结论先行 | 先结论 → 再依据（标准编号）→ 必要时分步 → 末尾列引用 |
| 6 | 条款高于记忆 | 历史记忆与标准条款冲突时，以标准条款为准 |
| 7 | 输出清洗 | 清掉代码块标记、多余空行、行尾与标点后空格；超 8000 字截断 |
| 8 | 合规校验 | 答案非空、不超长、不含「绝对安全 / 保证不出问题」 |

## 6. 技术选型（16 条）

| # | 选型项 | 选择 | 理由 |
|---|---|---|---|
| 1 | 大模型 | DeepSeek `deepseek-v4-flash` | 中文工程语境表现稳；OpenAI 兼容接口改动成本低；支持流式 |
| 2 | 向量模型 | BGE-m3 | 一个模型同时出稠密与稀疏，省一次推理；中文与专有名词表现好 |
| 3 | 重排模型 | BGE-reranker-v2-m3 | 交叉编码器精度显著高于向量相似度，用来把候选排准 |
| 4 | PDF 解析工具 | PyMuPDF + pdfplumber + MinerU + PaddleOCR | 正文 / 表格 / 复杂版面 / 扫描件各用所长，见设计文档 11.1 |
| 5 | 分块方式 | 语义切分（段落 → 句子 → 合并） | 保语义完整；固定长度会把一句话切断 |
| 6 | 检索方式 | 混合检索（稠密 + 稀疏） | 稠密管语义、稀疏管标准编号这类精确词 |
| 7 | 融合算法 | RRF（倒数排名融合） | 只看名次不看分数，免去两路分数量纲不一致的问题 |
| 8 | 提示词策略 | 角色化系统提示词 + 上下文严格约束 | 用提示词把「只依据条款作答」钉死 |
| 9 | 记忆方案 | Redis 短期（最近 N 条）+ Milvus 长期（语义召回） | 短期管「刚才说了什么」，长期管「以前聊过什么」 |
| 10 | 缓存方案 | Redis 按「用户 + 角色 + 归一化问题」建键 | 同问题不同标点命中同一条；按用户隔离可精确清理 |
| 11 | **存储** | **MySQL + Redis + Milvus** | MySQL 落结构化数据；Redis 做缓存与短期记忆；Milvus 存向量。三者职责不重叠 |
| 12 | **多路召回** | **Milvus + MySQL** | Milvus 找知识条款，MySQL 找同用户历史问答；两路融合后统一精排 |
| 13 | **测试** | **Postman + PyUnit(pytest)** | Postman 做接口联调与回归集合；pytest 做单元与集成断言 |
| 14 | **部署环境** | **WSL + Ubuntu** | 贴近生产 Linux；Milvus 官方推荐 Docker，WSL2 下可用 |
| 15 | **前端** | **Vue3 + Vite** | 组合式 API 写起来直接；Vite 冷启动与热更新快，适合演示迭代 |
| 16 | 效果评测 | RAGAS | RAG 领域事实标准，四个指标能区分检索环与生成环的问题 |

> 第 11–15 项按技术选型执行：存储三项、多路召回两项、测试两项、
> 部署环境两项、前端两项，均已落地（见 `docs/测试成果.md` 交付物清单）。

## 7. 非功能需求

| 类别 | 要求 | 实现情况 |
|---|---|---|
| 响应时间 | 非流式问答 10–20 秒内返回；流式首帧 3 秒内 | 实测流式逐帧返回，检索约 0.5–2.5 秒，生成 5–15 秒 |
| 并发 | 教学演示规模，支持多用户会话隔离 | 记忆与缓存按 `user_id` 隔离；会话/消息按用户过滤 |
| 安全 | 不泄露堆栈与密钥；删除操作做归属校验 | 异常统一转 500 只回简短说明；密钥只在 `.env`；删除双条件校验 |
| 数据一致性 | 删除会话必须级联删除消息 | 同事务先删子表再删父表，越权则一条不删 |
| 可维护性 | 单文件 ≤ 300 行；每行关键代码带中文注释 | 根目录 .py 均在 300 行内，见 `docs/测试成果.md` |
| 可观测性 | 关键链路有日志 | `logs/app.log` 记录检索、生成、写入、缓存命中；前后端另有独立日志 |
| 可部署性 | 一键装环境、一键起停 | `install.sh`（支持 `--dry-run`）/ `run.sh` / `shutdown.sh` |
