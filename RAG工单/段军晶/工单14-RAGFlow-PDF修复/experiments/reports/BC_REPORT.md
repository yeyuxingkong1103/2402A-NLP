## 0. 关键发现：运行时提示词 ≠ 源码树提示词

| 来源 | 字节 | md5 |

| **容器 `/ragflow/rag/prompts/...`（真正生效）** | **1552** | `c767374cbcf081bf74e8dc652166324b` |

两份**内容完全不同**。容器里是旧版「visual data analyst / bar chart / pie chart / Trends-Insights」提示词。
→ 印证需求分析 3.3.2 陷阱一：**容器跑的是镜像内代码，本地源码树不生效**。
→ 也回答了需求分析附录 B 待确认项 #8：**镜像内代码与本地源码树并非逐文件一致**。

**根因**：旧提示词只问「趋势/模式」，**从不询问部件方位或流动顺序** —— Q3/Q5 因此必然为空。

## 1. 修改内容

改动文件：容器内 `vision_llm_figure_describe_prompt.md`（本地备份 `C_orig_prompt_container.md`，新提示词 `C_prompt.md`）。
改动手段：`docker cp` 覆盖 + `docker restart`（重新加载模块级 prompt 缓存）。
**除该提示词外，其余配置与 B 完全一致。**

新提示词强制 5 段输出，其中两段为「MANDATORY」：
- **SECTION 3 部件方位三元组**：`(部件A, 方位关系, 部件B)`，方位取「位于左侧/右侧/上方/下方/内部/外部/重合/不确定」；
- **SECTION 4 气流流向**：先给箭头方向，再按经过顺序列出部件；
- SECTION 2 保留字形保真要求（`6′`/`6″`、下标 `x₁`/`h₁` 不得规范化）。

## 4. Q3 / Q5 验证

### Q3（正解 A：部件4 位于部件5 左侧）→ **首次命中** ✅（但有干扰）

- A：无任何 4-5 相对位置陈述
- B：只有「10 连接 4」「5 在交界处」的邻接描述，无左右
- **C 新增**：
  - `(4, 位于左侧, 5)` ← **正是正解 A**
  - `(5, 位于右侧, 4)` ← 与上条一致，正确
  - ⚠️ **但同时还输出** `(4, 位于下方, 5)` / `(5, 位于上方, 4)` ← **与上面矛盾，指向干扰项 D**

→ C 把一个二元关系**同时按水平和垂直两个方向都声称了一遍**，属于为凑够三元组数量而「两边都答」。
→ 净效果：**Q3 的答案文本首次进入索引**，可检索性从 0 到 1；但同一 chunk 内正解与干扰解并存，检索到后仍需消歧。

### Q5（正解 C：先经 6″，再经 6′）→ **仍未解决，且 C 给出了错误次序** ⚠️

- C 的流向段：`1 → 10 → 4 → 5 → 2` —— **三块配气带孔盘 6/6′/6″ 完全没被列入气流路径**
- C 的盘序三元组：`(6, 位于左侧, 6′)`、`(6′, 位于左侧, 6″)` → 蕴含左→右为 **6, 6′, 6″**
- 依据 `pdf_groundtruth.md`（Q5 正解：**先经 6″ 再经 6′**）与需求分析附录 A（**最左、盘径最大者为 6″**）：
  → 正确左→右应为 **6″, 6′, 6**。**C 的次序正好相反。**

→ **C 没有答出 Q5，反而写入了一条自信但错误的顺序** —— 对朴素检索器而言，比 B 的「沉默」更危险。

## 5. 噪声上升的原因（C 的副作用）

1. **三元组互相矛盾/重复**：同一对部件按左右、上下各写一遍，天然制造重复；
2. **提示词元话语泄漏进 chunk**：chunk 18 里出现了模型对指令的自我推理原文，例如
   - `→ After deduplication and enforcing coverage requirement *only for components actually present*...`
   - `(Additional required pairs: (4,6″), (6,6′), ... — all involve missing labels, so all are 不确定.)`
   - `(10, 位于下方, 2) — already listed, skip`

   这些是**指令排程的中间过程**，本不该进索引，现已成为噪音源。根因是提示词里那份**强制的配对清单**（要求覆盖 (4,5)(6,6′)(6′,6″)… 等固定组合）压力过大，模型为满足配额而自我解释。

3. chunk 18 对不存在的部件输出了 6 条 `不确定` 三元组（该页确无 4/5/6），属无效内容。
   （正面看：模型**没有幻觉编造**，明确写了「Components 4, 5, 6, 6′, 6″ are not visible」——可控。）

## 6. 检索风险复查

| 题面检索词 | A | B | **C** |
|---|---|---|---|
| `X1` / `X2` / `X3` | 是 | 是 | **是** |
| `6'` / `6"`（ASCII） | 是 | 是 | **是** |
| `部件4` / `部件5` | **否** | **否** | **是** ✅ |
| `气流方向` | 是 | 是 | 是 |

- **最大收益**：`部件4`/`部件5` 这两个字面串在 A、B 中**根本不存在**（旧提示词从不写「部件N」），C 首次写入 → Q3 检索引擎终于有词可匹配。
- **ASCII 失配风险低于预期**：C 保留了 ASCII `6'`×4、`6"`×2，且题面本身混用 `X1`（大写无下标），故精确/关键词匹配仍可命中，不需要额外归一化层。Unicode 形态是**增量**而非**替代**。

## 8. 结论

| 维度 | B → C 判定 |
|---|---|
| Q3 可检索性 | ✅ **首次命中**（`(4, 位于左侧, 5)`），但同 chunk 内含矛盾干扰解 |
| Q5 正确性 | ❌ **未解决，且新增错误盘序**（左→右写成 6,6′,6″） |
| 符号保真 | ✅ **显著提升**（′/″ 5→21，下标 11→17，`h1`→`h₁`） |
| 噪声 | ⚠️ **变差** 13.6% → 17.6% |
| 检索词面 | ✅ `部件4`/`部件5` 从无到有 |

**C 证明了「改提示词」这条路走得通**：空间关系确实能被 VLM 显式输出，Q3 从不可达变为可达。
**但当前提示词设计有缺陷**：强制的配对清单导致「两边都答」的矛盾与元话语泄漏，且流向段遗漏了配气带孔盘，Q5 仍错。

### 下一轮（D）建议的提示词收紧项

1. **删除固定配对清单**，改为「每对部件**只**输出一条最显著的关系，禁止同一对同时给水平与垂直关系」；
2. **禁止元话语**：明确「只输出三元组行本身，不得输出任何推理、去重说明、跳过说明」；
3. **流向段强制含全部轴上部件**：明确要求「凡位于气流轴线上的部件都必须按顺序列出，包括配气带孔盘 6/6′/6″」；
4. **不可见部件直接省略**，不要输出 `不确定` 三元组；
5. 保留 SECTION 2 字形保真要求（本轮有效）。
