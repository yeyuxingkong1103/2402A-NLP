# 文档质量评估

入库前的体检。回答一个问题：**这批文档现在这个样子，能不能直接进知识库？**

不能的话：哪些要 OCR、哪些是重复的、哪些有敏感信息、哪些根本打不开。

## 什么时候用

- 「帮我看看这个文件夹里的文档质量怎么样」
- 「这批 PDF 有多少要 OCR」（→ 直接看 `pdf.by_primary` 里的 `ocr`）
- 「查一下有没有重复文件」「有没有同一份文档的不同版本」
- 「入库前扫一遍有没有手机号身份证」
- 入库流水线里作为质检关卡，按路由结果分流到不同解析器

## 怎么跑

```bash
python scripts/assess.py <目录> -o <输出目录>            # 完整跑
python scripts/assess.py <目录> --limit 50 -o /tmp/x     # 先拿 50 份试跑
python scripts/assess.py <目录> --refresh -o <输出目录>   # 丢掉缓存重解析
```

输出两份东西：

| 文件 | 给谁 | 里面有什么 |
|---|---|---|
| `quality_report.json` | 程序 | 全部数据，含所有明细列表 |
| `quality_report.html` | 人 | 可读简报，重点列「待确认」「待审核」清单 |

## 五项检查

| # | 检查 | 产出 | 怎么用 |
|---|---|---|---|
| 1 | 格式分布 | 各扩展名的数量与占比 | 看知识库构成 |
| 2 | PDF 文字型/扫描型分流 | 每份 PDF 判 `text`/`scanned`/`mixed`，另出**待确认**列表 | 决定走不走 OCR |
| 3 | 长度分布 | P25/P50/P75/P90/P99 + 区间分布 | 定切块策略 |
| 4 | 重复检测 | MD5 精确重复组 + SimHash **待确认版本冲突**列表 | 去重 |
| 5 | 敏感信息 | 手机号/邮箱/身份证的**待审核**列表，每条带上下文 | 合规排查 |

外加**文档分类标签**：每份文档打标签并给出**主路由**（`ocr`/`text`/`hybrid`/`table`/`review`/`chunk_aggressive`），工作流按主路由选解析器。

## 读报告的顺序

1. **先看 `pdf.by_primary`** —— 有多少份要去 OCR。这决定后面要花多少时间。
2. **再看三张「待办」清单**：
   - `pdf.uncertain` —— 判定存疑的，人工定夺
   - `dup.sim_pairs` —— 版本冲突，**每条都要人工确认**（SimHash 是近似匹配）
   - `sensitive.hits` —— 敏感信息，**每条都要人工确认**（带上下文，方便判误报）
3. **最后看 `errors`** —— 打不开的文件没进统计口径，别当它们不存在。

## 三条容易踩的坑（都是实测踩出来的）

**判定阈值别照搬。** `simhash_distance: 7` 是在 IMDR 上扫出来的（阈值 7 → 18 对 / 94% 准确率；阈值 11 开始断崖式跌到 76%）。**阈值取决于语料的模板化程度**，换个语料要重扫：`python 测试/分析.py sweep <报告.json>`。已知反例：年报集合这种「一套模板换数据」的语料，不同公司之间距离也能到 4~7，用默认值会刷误报。

**扫描件比不了 SimHash。** 没有文字层就抽不出正文，正文太短的文档被 `simhash_min_chars` 挡在比较之外（报告里会写明跳过了多少份）。这批文档的版本冲突要**先 OCR 再比**。MD5 那层不受影响，照常有效。

**带水印的副本可能漏。** 同一份文档的水印版/无水印版，如果水印文字密集地插在正文里，n 字滑窗会被打断（实测招股说明书水印版 vs 无水印版距离 17，超出阈值）。这种要**先清洗文本再去重**，别指望 SimHash 认出来。

**「过短」不等于「坏」。** 扫描件字符数是 0 但完全正常，标签规则里用 `pdf_kind_not: scanned` 把它和「真坏文件」区分开。

## 调参

所有阈值都在 `assessment_config.yaml`，代码里不写死。改动分两类：

- **判定类**（`pdf_type` 的阈值、`length` 的区间、`dedup.simhash_distance`、`tags.rules`）——
  改完直接重跑，**几秒出结果**。因为解析结果缓存在 `workdir/parsed.jsonl`，存的是
  「字符数/每页字符数/SimHash/敏感信息命中」这些**事实**，判定是每次出报告现算的。
- **抽取类**（`sensitive` 的正则、`dedup.simhash_sample_chars`）——
  这些在解析阶段就固化了，要加 `--refresh` 重新解析。

## 中断恢复

解析缓存按「路径 + 大小 + 修改时间」做键，追加落盘，每 `checkpoint_every` 份刷一次。
Ctrl+C 会先落盘再退出。重跑自动接着来，不重复解析。**跑 1700 份这种量级时，
先 Ctrl+C 调参数再续跑，比从头再来省得多。**

## 接进工作流

报告 JSON 里工作流要读的就一个字段：

```jsonc
{"details": {"tags": {"docs": [["<文件路径>", "标签1、标签2", "主路由"], ...]}}}
                                         // ↑ 第三个字段，如 "ocr" / "text" / "review"
```

主路由是**每份文档第一条标签的去向**（规则按最确定→最兜底排序），一份文档只有一个。
`by_route` 是把所有标签都算一遍的统计值，**不要拿它定路由**。

RAGFlow 侧的对接见 `研发/patches/` 与 `设计/接口文档.md`。
