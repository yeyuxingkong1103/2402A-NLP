## 一、方法：先量化问题，再谈优化

本工单是**优化任务**，因此第一步不是写代码，而是把 08 的图谱与检索链路
**逐环节实测一遍**，找出真实瓶颈。下面每一条「问题」都附实测数字与复现路径，
不做「大概可能或许」式的猜测。

复用方式：09 通过 `w9/compat.py` 把 `../工单8` 挂到 `sys.path`，以**只读**方式
调用 08 的代码；Qdrant 索引复制一份到 09（同一份向量）。因此**08 目录物理零改动**
（由 `scripts/wo8_guard.py` 逐字节取证），前后差异只能归因于优化本身。

## 二、问题分析（08 实测）

### 2.1 【层面1】Prompt 构建实体、关系

| 编号 | 问题 | 实测证据 |
| --- | --- | --- |
| **P1** | **第2层 LLM 抽取产物从未合并入图谱** | `llm_extract_results.jsonl` 已有 349 块 / 2110 实体 / 127 关系（含 Person 441、SERVES_AS 83、SHAREHOLDER_OF 37），但 `kg.pkl` **只有第1层**：560 节点/873 边，仅 4 种关系，**零个 Person 节点**。08 自己在 `docs/12` 承认：「涉及『谁控股谁』『董监高任职』的问题图谱通道无贡献」 |
| **P2** | **chunk_id 跨文档重复** | `chunks.json` 7757 条块只有 **1185 个不同 chunk_id** —— 每份年报的编号都从 `c000001` 重新开始。任何以 chunk_id 为全局主键的下游逻辑（引用回溯、块级去重、证据核验）都会**跨文档串味** |
| **P3** | **小模型抽取严重退化** | 实测 qwen2.5:3b 在 40 个高价值块上：原始实体 361 条 → **去重后仅 150 条（58% 是重复输出）**；退化块占 **40%**；40 块只抽出 6 条关系（0.15 条/块）。且 v1/v2 两版 Prompt 表现同样退化 → 这是**模型能力上限**，不是 Prompt 写法问题 |
| **P4** | **实体未归一** | 1276 个 Company 实体里混有「本公司」「该公司」等指代表述；「深圳发展银行」（平安银行 2012 年前旧名）与「平安银行」被抽成两个割裂节点；「中国平安保险(集团)股份有限公司」（半角括号）与词典中的全角写法对不上，凭空多出一个重复节点并连出自指假边 |
| **P5** | **噪声类型混入** | 「高级管理人员」被当成 Person；「招商银行股份有限公司高级管理人员薪酬管理办法」被当成 Business |

### 2.2 【层面2】检索层

| 编号 | 问题 | 实测证据 |
| --- | --- | --- |
| **R1** | **文档路由未被使用** | 08 实现了 `doc_router`，但 `graph_qa._retrieve_text` 调 `strategies.retrieve()` 时**没传 `sources`**，等于弃用。实测问「平安银行…董事长致辞」，8 个召回块里 **7 个来自中国平安年报**（集团 vs 银行未区分），答案自然跑偏 |
| **R2** | **图谱事实无差别灌入上下文** | k-hop 模式把邻域**每条边**都转成事实，上限 60 条。实测单题吐回 **59 条**图谱事实，大量是「某指标某年为某值」，与「董事长致辞」无关 → 上下文被稀释，且在 RAGAS 口径下**每条无关事实都算一次「检索到但无用」** |
| **R3** | **低质量表格骨架块占据高位** | 报表附注页的块形如 `\| 平安银行股份有限公司 \| \| \| \| --- \| --- \| --- \| \| 财务报表附注 \|`，**含公司名**因此在向量与 cross-encoder 打分里都排前列，但通篇没有一个完整句子。实测 8 个上下文块里 **5 个是这类残片** |
| **R4** | **全局型问题单轮 top-k 覆盖不足** | `FINAL_TOP_K=6` 的单查询检索，无法覆盖跨 9 份年报的归纳题（sample_questions 第 4 题参考答案含 15+ 个论断、横跨 6 个侧面） |
| **R5** | 融合权重固定、融合后无二次精排 | `KG_FUSION_WEIGHTS` 为常量；Reranker 只在 `strategies` 内部对文本两路生效，图谱事实从不参与排序 |

## 三、三层优化设计

### 3.1 层面1：Prompt 构建实体、关系

**① 新 Prompt v2**（`w9/prompts/kg_extract_v2.yaml`）—— 每一条改动都对应实测缺陷：

| 改动 | 对应问题 |
| --- | --- |
| 关系方向硬约束（正反例对照） | 修正 `邮储银行 --SHAREHOLDER_OF--> 邮政集团` 这类**方向颠倒**（原文是「本行的控股股东邮政集团」，邮政集团才是股东） |
| evidence 必须「切题」（点到关系对象、且为同一句） | 修正 `储一昀 --SERVES_AS--> 平安银行`，证据却是其在**另外四家公司**任独董 |
| 指代消解规则（本公司/本行 → 正式名） | P4 |
| 多文档实体对齐与消歧（含历史名称合并） | P4 |
| 噪声黑名单（职务名、文件名、泛称） | P5 |
| 金融领域术语表（拨备覆盖率、六四占比、绿色金融…） | P5 |

> 如实说明：实测显示 **3B 模型对 Prompt 质量的响应有限**（P3）。Prompt v2 的价值
> 主要体现在**规则约束**（方向、切题、消歧），而非提升模型本身的抽全率。

**② 新增图谱合并环节**（`w9/kg_merge.py`）—— 补齐 08 缺失的一环，并加压**六道闸门**：

| 闸门 | 内容 |
| --- | --- |
| 1 | 关系类型必须在本体内 |
| 2 | 头尾类型组合合法 |
| 3 | evidence 必须真实出现在原文中（08 原口径） |
| **4** | **evidence 必须「在陈述」该关系**（金融术语标志词约束）**新增** |
| **5** | **evidence 必须提到关系对象**（防「文不对题」）**新增** |
| **6** | **方向敏感关系的方向必须与证据一致** **新增** |

闸门 4~6 是针对 08 三道闸门**拦不住的语义错误**：08 的闸门 3 只验证「这段文字确实出自原文」，不验证「这段文字跟这条关系有没有关系」，于是「实体共现」被误判成「关系成立」。

**合并策略：先判关系、后定节点。** 08 的 1276 个 Company 实体里绝大多数是孤立噪声，
若无条件入图会把图谱撑到 2500+ 节点并污染实体链接。09 只把**在已接受关系中真正
充当端点的实体**写入图谱 —— 一个实体进图，是因为它在某条被证实的关系里扮演了角色。

### 3.2 层面2：检索层

| 编号 | 优化 | 对应问题 |
| --- | --- | --- |
| O1 | 实体识别去噪：低分兜底实体不作种子，排除 Industry/Time | R1 |
| O2 | **文档路由**：复用 08 自己实现却没用上的 `doc_router`，问题只点名一家公司时限定该文档 | R1 |
| O3 | **图谱事实按相关性筛选排序**（2-gram 覆盖率打分），只把相关事实放进上下文 | R2 |
| O4 | **低质量块过滤**：按**表格分隔符占比**剔除表格骨架残片 | R3 |
| O5 | **查询分解 + 逐侧面 round-robin 选取**：全局型问题拆成侧面子查询，各取候选后轮流入选 | R4 |
| O6 | **统一精排**：图谱事实与文本块同池过 Reranker | R5 |
| O7 | 自适应融合权重（事实型偏文本、对比/组织型偏图谱） | R5 |

**O4 的阈值依据（实测）**：表格骨架块的分隔符占比 **0.33~0.39**，正常正文块 **0.00**
—— 两组完全不相交，阈值取 0.15 可无歧义区分。反观「有效字符占比」指标，
骨架块能到 0.50~0.60（它确实写了不少中文），区分度差得多。

**O5 为什么必须 round-robin 而不是全池排序**：最初实现复用 08 的 `retrieve_multi`
（合并后统一排序），实测第 4 题的 8 个上下文块**全部来自「绿色金融」一个侧面**
（该侧面措辞密集、相似度天然更高），而参考答案覆盖 6 个侧面 → 覆盖率结构性缺失。
改为逐侧面各取 N 条后，侧面覆盖得到结构性保证。

### 3.3 层面3：生成层

| 编号 | 优化 | 对应问题 |
| --- | --- | --- |
| G-1 | 结构化要点输出，强制覆盖每个子问；全局型题追加「覆盖每个方面」强化指令 | G2 |
| G-2 | **引用机制改为「模型只写证据编号 `[n]`，页码/block_type/ID 由代码生成」** | G1 |
| G-3 | 多跳推理引导（显式写出推理链） | — |
| G-4 | 兜底话术具体化（说明「已查到什么、还缺什么」） | G4 |
| G-5 | 上下文四分区：图谱事实 / 文本证据 / 表格证据 / 图像描述 | G3 |

**G-2 是本层面最关键的架构调整。** 原设计让模型「照抄来源里的页码」，实测它会把
真实页码 4/259/260 编造成 23/26/25/49。改为：**模型只负责指出「这句话依据哪条证据」，
来源元数据由检索结果直接取** —— 因此引用**在机制上不可能被编造**，
仍然完整满足工单「页码 + block_type + ID」的要求。
