## 1. 混合检索 + RRF 融合

### 1.1 为什么要"混合"

招股说明书问题高度依赖**精确实体与数值**：
- "注册资本是多少？" → 答案 `5,520万`
- "法定代表人是谁？" → 答案 `程家明`
- "参与制定了哪个技术标准？" → 答案 `某视频技术规范1.0`

两种检索方式各自有短板：

| 方式 | 擅长 | 短板 |
|---|---|---|
| 向量检索(FAISS,bge-m3) | 语义相似、同义改写 | 精确数字/专有名词弱 |
| 词法检索(BM25,jieba) | 精确匹配、专有名词 | 同义改写不敏感 |

两者**互补**，故采用混合检索。

### 1.2 RRF（Reciprocal Rank Fusion）原理

RRF 不用向量/BM25 的原始分数（量纲不同无法直接加权相加），而是**只按排名**融合：

```
score(d) = Σ_{进    路r}  w_r / (k + rank_r(d))
```

- `rank_r(d)`：文档 d 在第 r 路结果里的名次（从1计）；
- `k`：平滑常数（本系统 `RANK_FUSION_K=60`），防止 rank=0 时除零；
- `w_r`：该路权重（默认各1）。

**优点**：天然无需量纲归一化；对"某路排得很靠前"的文档给予强加权；两路都靠前的文档分数最高，最能代表"语义相关且词面匹配"。

### 1.3 流程图

```mermaid
flowchart TD
    Q[问题] --> V[FAISS语义检索 Top6]
    Q --> B[BM25词法检索 Top6]
    V --> R[RRF: 每条文档\nscore=Σ w/(k+rank)]
    B --> R
    R --> S[按分数降序取 TopN]
    S --> C[按内容去重]
    C --> F[contexts: 第x页...片段]
```

### 1.4 关键代码

```python
def _rrf(self, ranked):
    scores = {}
    for lst, weight in ranked:
        for rank, doc in enumerate(lst):
            key = doc.metadata["page"]
            scores[key] = scores.get(key, 0.0) + weight / (RANK_FUSION_K + rank + 1)
    return sorted(scores.items(), key=lambda x: -x[1])
```

## 2. 查询理解（Query Understanding）

### 2.1 目的

原始问题常有指代、歧义、多要点，直接检索命中率低。

| 原始问题 | 理解后的检索查询 |
|---|---|
| "该公司来自军用领域收入是多少" | 消歧后：武汉兴图新科电子股份有限公司 军用领域收入 |
| "收入和占比分别是多少" | 子问题1：军用领域收入；子问题2：占主营业务收入比重 |

### 2.2 输出结构（LLM 结构化 JSON）

```json
{
  "intent": "finance",
  "entities": ["武汉兴图新科", "军用领域"],
  "disambiguated_query": "武汉兴图新科电子股份有限公司 来自军用领域的收入",
  "sub_questions": ["军用领域收入分别是多少"]
}
```

### 2.3 健壮解析（_parse_json）

推理模型(deepseek-r1)输出常带思维链、多余文字。解析策略：
1. 剥掉 ```json ... ``` 代码块包裹；
2. 截取第一个 `{` 到最后一个 `}`；
3. 找不到则降级：`disambiguated_query=原问题`。

```mermaid
flowchart TD
    A[LLM 原始输出] --> B{含```json?}
    B --是--> C[剥掉代码块包裹]
    B --否--> D[直接解析]
    C --> E{含 {...}?}
    D --> E
    E --是--> F[json.loads 成功]
    E --否--> G[降级=原问题]
    F --失败--> G
    G --> H[生成 retrieval_queries]
```

### 2.4 检索查询组合

```python
@property
def retrieval_queries(self):
    primary = self.disambiguated_query or self.question  # 主问题优先
    subs = [s for s in self.sub_questions if s and s != primary]
    return [primary, *subs]
```

设计要点：**始终以消歧后的主问题为第一检索词**，子问题作为补充，保证主线语义不被拆分问题稀释。

## 3. 分批嵌入（Batched Embedding）

### 3.1 问题

本地 Ollama `bge-m3` 对大请求处理不稳，会触发 tokenizer 连接被拒：
```
Connection refused 127.0.0.1:1510  (ollama tokenizer)
```

### 3.2 解决

```python
class _BatchedEmbeddings(OllamaEmbeddings):
    def embed_documents(self, texts):
        out = []
        for i in range(0, len(texts), 50):      # 每批50
            out.extend(super().embed_documents(texts[i:i+50]))
        return out
```

### 3.3 效果

| 指标 | 值 |
|---|---|
| 切片总数 | 2670 |
| 批次 | 54 批（每批50） |
| 结果 | 全部稳定嵌入成功 |

## 4. 防幻觉提示词设计（qa_engine）

三条铁律从根本降低幻觉：
1. **仅依据参考文档回答**，禁止引入外部知识；
2. **数值/名称原样输出**，防止"四舍五入"或改写导致错误；
3. **无法回答时明示**，而不是编造。

配套"页码溯源"机制：每段检索上下文带 `page`，回答后能在界面展示"关键数据来源页码"。

## 附：算法复杂度简述

- 建库：O(total_chunks × dim)，bge-m3 分批并行。
- 检索：向量 ANN 检索 O(log n)+ 打分；BM25 预建倒排 O(BM25_TOP_K)；RRF 融合 O(N*log N)。
- 生成：受 deepseek-r1 逐 Token 推理限制，是响应时间的**主要瓶颈**（详见"优化"目录）。
