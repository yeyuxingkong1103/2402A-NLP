## 三、耗时构成与优化

| 阶段 | 优化前 | 优化后 | 手段 |
|---|---|---|---|
| Query 改写 | < 5 ms | < 5 ms | 确定性规则，无模型调用 |
| 查询编码 | ~6 s（4 次 HTTP） | ~2.0 s（1 次 HTTP） | **批量编码**：原始问句 + 同义词扩展 + 话题实体合并为一次请求 |
| 向量检索 | < 20 ms | < 20 ms | numpy 矩阵乘法（2357×1024） |
| BM25 检索 | < 10 ms | < 10 ms | 内存倒排 |
| 重排 | < 5 ms | < 5 ms | 加权线性融合 |
| 答案合成 | < 5 ms | < 5 ms | 抽取式，正则 + 覆盖度打分 |
| **合计** | **~8–10 s** | **~2.2 s** | 批量编码 + 预热 |

**关键优化**：
1. **批量查询编码**（`retriever._encode_queries`）：把一轮中的多条查询合并为一次 Ollama 调用，
   并缓存查询向量，重复问句零开销。
2. **启动预热**（`MultiTurnQA.warmup`）：提前加载 BM25 / jieba / 编码器，消除首问冷启动
   （冷启动实测 5.31 s → 预热后首问 2.15 s）。

## 六、高并发与长时间运行

- 检索与答案合成为**无状态纯计算**，可安全并发；向量矩阵乘法为只读。
- 单进程内存占用稳定，连续 50 轮问答无内存持续增长。
- Ollama 服务不可用时，检索可降级为纯 BM25，保证系统仍可应答。
