## 1. 这个项目是什么

### 1.1 一句话

一个**带知识库的多角色对话系统**：用户选一个角色（法律顾问 / 心理专家 / 虚拟朋友），发一句话，系统先去它自己的知识库里查资料，再让大模型（DeepSeek）**带着这些资料**回答。

### 1.2 它解决的痛点

普通大模型有两个问题：

| 问题 | 表现 | 本项目的解法 |
|---|---|---|
| 不知道你的私有资料 | 问"我们公司的年假规定"，它只能瞎编 | 把资料切碎存进向量库，回答前先检索出来塞给模型（这就是 RAG） |
| 不会演特定角色 | 问什么都是同一个"AI 助手"腔调 | 每个角色一套系统提示词 + 一个独立知识库 + 独立温度 |

### 1.3 三个角色

| 角色 | 干什么 | 知识库里装什么 | 特性 |
|---|---|---|---|
| **法律顾问** | 依据法条回答法律问题，可标注条款出处 | 民法典、刑法、劳动合同法、民事诉讼法、治安管理处罚法（PDF） | 严谨，温度 0.3，必须引用法条 |
| **心理专家** | 情绪支持 + 认知行为建议 | 6.6 万条中文心理咨询对话（JSONL） | 温和，温度 0.7 |
| **虚拟朋友** | 陪聊解闷，扮演"鞠婧祎（小鞠）"人设 | 179 条人设记忆 + 高情商回应（JSONL） | 轻松，温度 0.6，说话像微信聊天 |

### 1.4 界面长什么样

打开 `http://localhost:8000` 会自动跳到前端页面：顶部选角色，中间聊天区，底部输入框；左边有"用户ID / 引用条数 / 清空记忆"三个小控件。回答是**逐字蹦出来**的（流式输出），法律顾问和心理专家还会在回答下面显示"引用资料"卡片。

## 2. 先认识 5 个"外援"

这个项目自己只写了 20 来个 Python 文件，重活都交给 5 个独立服务。**理解它们的分工，是理解整个项目的第一步。**

| 外援 | 端口 | 生活化类比 | 在本项目里的具体职责 |
|---|---|---|---|
| **MySQL** | 3306 | 花名册 + 台账 | 存角色（名字、提示词、温度）、用户、每条对话记录 |
| **Redis** | 6379 | 短期记忆便签 | 存"最近 20 条对话"，让模型记得上文；2 小时没人说话就自动撕掉 |

## 3. 两条主流程

整个项目只有两条链路，看懂这两条，项目就懂了一半：

- **离线链路**：把资料搬进知识库（平时不用跑，只在导入新资料时跑一次）
- **在线链路**：用户发消息 → 检索 → 生成回答（每次聊天都会跑）

> **注意"两个知识库"的区别**：这里说的"知识库"，一是指离线入库的资料（法条、人设），二是指在线的向量库。前者是文件，后者是数据库。

### 3.1 离线链路：资料怎么变成知识库

入口是 `batch_ingest_pdfs.py`（一键入库脚本），它按角色决定目标集合，然后分两条子路径：

#### 路径 A：PDF 文档（法律顾问）

```text
G:\知识库pdf文件\法律\*.pdf
   │
   │ ① process_single_pdf()  读文件字节
   ▼
doc_parser.extract_text()      ← 按后缀选解析器（PDF→PyMuPDF；扫描件→PaddleOCR）
   │  得到纯文本 raw_text
   ▼
text_splitter.split_text()     ← strategy="paragraph"，500 字/块，重叠 80 字
   │  得到 N 个 Document（每块带 source / chunk_index / section）
   ▼
db_milvus.ingest_documents()   ← 幂等去重 → Ollama 向量化 → 每 10 条一批写入 Milvus
   │
   ▼
retriever.refresh_bm25()       ← 全量拉回文本，重建这一路的关键词索引
```

#### 路径 B：已处理好的 JSONL（心理专家 / 虚拟朋友）

```text
G:\知识库pdf文件\心理\processed_psych.jsonl          （6.6 万条心理咨询对话）
G:\知识库pdf文件\虚拟朋友\cecily_persona.jsonl        （179 条人设记忆）

   │ ② ingest_jsonl_file() → db_milvus.ingest_jsonl()
   ▼  逐行读 JSON，取 text + metadata（缺字段自动补：source="jsonl"、chunk_index=序号）
   ▼
db_milvus.ingest_documents()   ← 与路径 A 完全共用同一个入库函数
   ▼
retriever.refresh_bm25()
```

#### 入库函数内部到底做了什么（`ingest_documents`）

这是全项目最值得看懂的函数，5 步：

1. **收集已有键**：用 Milvus 的 `query_iterator` 游标，把集合里所有 `(source, chunk_index)` 拉出来（`_collect_existing_keys`）。拉失败就**直接抛错中止**，绝不放行。
2. **过滤重复**：新文档的 `(source, chunk_index)` 已在集合里 → 跳过。所以**同一个脚本重复跑不会让数据翻倍**。
3. **向量化 + 分批写入**：每 10 条一批，每条主键是 `uuid4()`（`auto_id=False`，主键由我们自己给），带 `tqdm` 进度条。
4. **统计条数**：从 Milvus 拿集合当前总条数并打日志。
5. **返回总数**，给调用方刷新 BM25。

#### 两种"重做"的方式（别搞混）

| 场景 | 用哪个 | 行为 |
|---|---|---|
| 只是加了新内容 | 直接再跑一次入库 | 旧的自带键被跳过，只写新增部分（增量） |
| 想改已有那段文字的内容 | 必须先删再入 | 因为幂等键是 `(source, chunk_index)`，**只改文字的"修正"不会被识别，会被当成重复跳过** |
| 换了向量模型 / 维度 | `POST /kb/rebuild`（或删集合重入） | 删集合 → 重建 schema → 全量写入 |

### 3.2 在线链路：一句话进来的完整旅程

以用户点"发送"为例，前端走的是**流式接口** `/chat/stream`：

```text
① 前端 app.js.onSend()
   └─ POST /chat/stream  {user_id, role_id, query, top_k, role_key}

② main.py : chat_stream()
   ├─ get_role(role_id)              → 从 MySQL 拿角色提示词 + 温度
   ├─ get_history_for_llm()          → 从 Redis 拿最近 20 条对话（旧→新排序）
   └─ 确定 role_key                   → 前端传了就用；没传就按角色名反查 ROLE_TEMPLATES

③ retriever.multi_route_recall()     ← 检索（最耗时的一步）
   ├─ 路 1：hybrid_search(collection)
   │    ├─ Milvus 向量检索 top 10          （按意思找）
   │    ├─ BM25 关键词检索 top 10          （按字面找，jieba 分词）
   │    ├─ EnsembleRetriever 用 RRF 融合   （两路排名加权合并，权重 0.5/0.5）
   │    ├─ CrossEncoder 重排取 top_k       （精算相关性，默认 5 条）
   │    └─ 分数 < 0.3 的丢掉               （不相关的别喂给模型）
   ├─ 路 2：search_long_term_memory()  → Milvus 里该用户的历史记忆（top 3）
   └─ 去重（按正文前 100 字）→ 最多返回 top_k × 2 条

④ prompt_templates.build_context(docs, query, role_key)
   ├─ 虚拟朋友 → MEMORY_CONTEXT_TEMPLATE：「下面是你自己的记忆片段……」
   └─ 其他角色 → CONTEXT_TEMPLATE：「请依据以下参考资料回答……[资料1]（来源：xxx）」

⑤ llm_client.stream_chat()
   └─ SystemMessage(角色提示词) + 历史消息 + HumanMessage(资料+问题) → DeepSeek 逐 token 返回

⑥ main.py 先把来源行推给前端：
   ###SOURCES###[{"index":1,"content":"...","source":"..."}]\n
   之后才是正文 token（前端看到这个前缀就先渲染引用卡片，再逐字显示正文）

⑦ 正文流完后收尾（三件事，一个都不能少）
   ├─ Redis：add_message(user) + add_message(assistant)   → 写进短期记忆
   ├─ MySQL：save_conversation(...)                       → 落对话日志
   └─ Redis：set_user_active(user_id)                     → 记在线用户
```

非流式接口 `/chat` 是同样的 ①~⑤，区别是：不走 SSE、把回答一次性返回，并且**多一步后处理** `post_process()`（正则清洗 + 引用校验）。

> **为什么 `/chat/stream` 不调 `post_process`？**
> 因为流式是一边生成一边推给前端，等生成完再"事后清洗"已经来不及了——前端早就把原文显示出来了。这是一个有意为之的取舍。


角色 key → 集合名的映射。传了非法 key 会**静默退回默认集合**（`rag_legal`），这点要注意（生产级副本已改成抛错）。

#### `logger.py` — 日志

`get_logger(name)`：按模块名创建 logger，**同时输出到控制台和文件**，格式 `时间 [级别] [模块名] 消息`。
文件用 `RotatingFileHandler`：单文件 10MB，保留 3 个备份，UTF-8（中文不乱码）。
重复调用同一个模块名会返回已有 logger（靠 `if logger.handlers` 判断），不会重复挂 handler。

### 4.3 数据层

#### `db_milvus.py` — 向量库数据层（最重要）

进程内三个单例：向量模型 `_embedding`、按集合缓存的向量存储 `_vectorstores`、原生客户端 `_milvus_client`。

| 函数 | 作用 | 关键细节 |
|---|---|---|
| `get_embedding()` | 初始化 Ollama bge-m3 | 单例，首次调用才连接 |
| `get_vectorstore(coll)` | 拿 LangChain 的 Milvus 封装 | `auto_id=False`（主键自己给）、索引参数是**字典**格式（langchain-milvus 0.4 要求） |
| `get_milvus_client()` | 拿原生 `MilvusClient` | 用于全量查询、建集合、删数据 |
| `_collect_existing_keys(coll)` | 拉全量 `(source, chunk_index)` | 用 `query_iterator` 游标，**规避单次 query 的 offset+limit ≤ 16384 限制** |
| `ingest_documents(docs, ...)` | 幂等入库主函数 | 去重 → 分批 10 条 → `uuid4` 主键 → tqdm 进度条 |
| `ingest_jsonl(path, ...)` | 读 JSONL 入库 | 兼容 `text`/`page_content` 两种字段；坏行跳过；缺 metadata 自动补 |
| `fetch_all_text(coll)` | 全量拉文本 | 供 BM25 重建；**必须带上 source/section/chunk_index**，否则 BM25 召回的引用卡片来源为空 |
| `save_long_term_memory(...)` | 存长期记忆 | 集合不存在就按 schema 自动创建（pk/text/vector/user_id/role_id/summary/created_at） |
| `search_long_term_memory(...)` | 按 `user_id` 过滤检索 | 返回 top_k 条记忆 |

#### `db_mysql.py` — 业务数据层

用 SQLAlchemy ORM，三张表：

| 表 | 字段要点 |
|---|---|
| `users` | username（唯一索引）、password_hash、nickname、is_active |
| `roles` | name（唯一索引）、description、**system_prompt（Text）**、temperature、knowledge_collection |
| `conversation_logs` | user_id（索引）、role_id（索引）、role_name（冗余，少一次 join）、query、answer、sources（JSON 字符串） |

- `init_db()`：启动时 `CREATE TABLE IF NOT EXISTS`。
- 引擎：`pool_size=5` + `pool_pre_ping=True`（连接池自动检活）。
- 每个 CRUD 函数自己开 session、`finally` 里关（归还连接池）。
- 函数：`create_user` / `get_user_by_name` / `get_role` / `list_roles` / `save_conversation`。

#### `db_redis.py` — 短期记忆层

- Key = `chat:{user_id}:{role_id}`（**每个用户每个角色一份独立历史**），Value = Redis List。
- 写法：`LPUSH`（新的插头部）+ `LTRIM 0..19`（只留 20 条）+ `EXPIRE 7200`（2 小时）。LTRIM 是 O(1)，滑动窗口很便宜。
- `get_history()` 拿到的是**新→旧**，`get_history_for_llm()` 会 `reverse()` 成**旧→新**（LLM 要求时间顺序）。
- 另有 Set `online_users`：`set_user_active()` / `get_online_users()`。

### 4.4 检索与生成

#### `retriever.py` — 检索层（第二重要）

`hybrid_search()` 五步管线：

```text
query
 ├─ ① Milvus 向量检索 k=10        （Dense：懂语义，"邻居吵到我"能命中"相邻关系"）
 ├─ ② BM25 关键词检索 k=10        （Sparse：懂字面，法条号、专有名词命中率更高）
 ├─ ③ RRF 融合（权重 0.5/0.5，c=60）（按排名合并，不依赖两路分数量纲一致）
 ├─ ④ CrossEncoder 重排取 top_n   （逐对精算 query-doc 相关性，最慢但最准）
 └─ ⑤ 分数过滤 score ≥ 0.3        （低分丢弃，宁少勿滥）
```

- BM25 索引存在内存字典 `_bm25_cache[集合名]`，**进程级**。`refresh_bm25()` 从 Milvus 全量拉文本重建；`refresh_all_bm25()` 在启动时对三个集合各建一次。
- 中文分词用 `jieba`（`_chinese_tokenize`），统一转小写去空白。
- `get_reranker()` 加载本地 CrossEncoder，**路径不存在直接抛错**；首次加载要十几秒。
- 集合不存在 / BM25 未初始化 → 抛 `RuntimeError`，由上层决定是报错还是忽略。
- `multi_route_recall()`：知识库 + 长期记忆两路合并，按正文前 100 字去重，最多返回 `top_k × 2`。

#### `prompt_templates.py` — 角色与上下文

- `ROLE_TEMPLATES`：三个角色的完整定义（name / description / collection / system_prompt / temperature / suggestions）。
- 两套上下文框架：

| 框架 | 用给谁 | 长什么样 |
|---|---|---|
| `CONTEXT_TEMPLATE` | 法律顾问、心理专家 | "请依据以下参考资料回答…【参考资料】[资料1]（来源：xxx）…【用户问题】…" |
| `MEMORY_CONTEXT_TEMPLATE` | 虚拟朋友（`MEMORY_ROLES`） | "下面是你自己的记忆片段…用第一人称自然地讲出来，不要提及'资料''来源''文档'" |

- `build_context(docs, query, role_key)`：人设类角色**不编号、不标来源**，其他角色带编号和来源（便于引用卡片）。

> 这里踩过一个真实的坑：虚拟朋友最初用「参考资料」框架，模型把检索到的人设读成"关于某个人的外部文档"，于是回答"我不是鞠婧祎"。换成第一人称"记忆片段"框架后，模型才自然认领身份。

#### `llm_client.py` — 大模型客户端

- `get_llm(temperature, use_local)`：按 `(模式, 模型名, 温度)` 缓存实例，切模型不会复用旧实例。
- 在线：`ChatOpenAI(base_url=DeepSeek)`；本地：`LOCAL_LLM_BASE_URL` 非空或 `use_local=True` 时走本地（api_key 用占位符）。
- 没配 API Key → 抛 `RuntimeError("未配置 LLM_API_KEY（环境变量 deepseek_api_key1）")`。
- `chat()`：`[SystemMessage] + 历史 + [当前问题]` → `invoke()` 一次性返回。
- `stream_chat()`：同样拼装，但用 `llm.stream()` 逐 chunk `yield`。

#### `post_processor.py` — 回答后处理（只用于非流式 `/chat`）

- `REPLACEMENT_RULES`：6 条正则，去掉"根据参考资料，"开头、"作为一个AI"等身份自述、全角空格、3 连换行、行尾空格。
- `normalize_markdown()`：拆掉整段 ``` 包裹、规整列表缩进。
- `validate_citations()`：正则找 `《X法》第N条` 和案号 `（2021）京0105民初12345号`，返回 `{valid, fabricated, case_count}`。
- `post_process()`：串起来返回 `{answer, citations}`。

> 说明：`validate_citations` 里的 `fabricated` 列表**从未被填充**，所以 `valid` 恒为真，实际只统计了案号数量。详见第 9 章。

### 4.5 文档处理与运维

#### `doc_parser.py` — 文档解析

`extract_text(file_bytes, filename)` 按后缀分发，返回 `(纯文本, 是否Markdown)`：

| 后缀 | 方法 | 依赖 |
|---|---|---|
| `.txt` | 直接 decode | 无 |
| `.md` | 直接 decode，并返回 `True`（后续强制标题切分） | 无 |
| `.docx` | `python-docx` 逐段落，空段落保留为换行 | python-docx |
| `.pdf` | `PyMuPDF(fitz)` 逐页提取，页间空行 | PyMuPDF |
| `.pdf`（提取为空时自动降级） | `extract_from_scanned_pdf()`：渲染 300 DPI 图 → PaddleOCR 中文识别 | paddleocr |
| `.wps` / `.doc` | `win32com` 调本机 WPS（`kwps.Application`），失败退 `Word.Application`，另存 txt 再读 | pywin32 |

另有 `extract_tables_from_pdf()`（pdfplumber → Markdown 表格）。
**文件下半部分是"未启用的扩展解析器"**（图片提取、VLM 图片描述、PDF 表格一体化、Excel、PPT），全部注释掉，按需放开即可。

#### `text_splitter.py` — 文本切分

五种策略，统一入口 `split_text(raw_text, source, strategy, is_markdown)`：

| strategy | 函数 | 分隔符优先级 | 适用 |
|---|---|---|---|
| `fixed` | `split_by_fixed_length` | 只有 `""`（纯按长度硬切） | 无结构纯文本 |
| `sentence` | `split_by_sentence` | `。！？；\n` | 尽量不切断句子 |
| `paragraph`（默认） | `split_by_paragraph` | 空行 → 换行 → 句号 → … | 通用 |
| `markdown` | `split_by_markdown_header` | 先按 `#/##/###` 切，再把**标题路径写进正文** | .md 文件 |
| `semantic` | `split_by_semantic` | 向量算语义断点 | 长文档；缺 embedding 或没装 `langchain_experimental` 时自动退回 paragraph |

- `is_markdown=True` 强制走 markdown 策略。
- 每块 metadata 固定三个键：`source` / `chunk_index` / `section`（markdown 时 section 是"h1 / h2 / h3"拼接）。

#### `kb_update.py` — 知识库运维（服务运行时的增删改查）

| 函数 | 对应接口 | 行为 |
|---|---|---|
| `delete_by_source(source, coll)` | `DELETE /kb/sources/{source}` | 按 source 查出所有 pk → 批量删除。**单次 limit=10000** |
| `update_by_source(source, new_text, ...)` | `PUT /kb/update` | 先删旧 → 重新切分 → 重新写入（"改内容"必须走这里） |
| `list_sources(coll)` | `GET /kb/sources` | 按 source 聚合条数，倒序返回。用 **offset 分页（每页 500）** |
| `get_source_detail(source, coll)` | `GET /kb/sources/{source}` | 该 source 的前 100 条 chunk 预览（截 200 字） |
| `rebuild_collection(docs, coll)` | `POST /kb/rebuild` | drop 集合 → 按新 schema 重建 → 全量写入（换模型/维度时用） |

#### `batch_ingest_pdfs.py` — 一键入库脚本（离线链路入口）

- 顶部两张配置表：
  - `ROLE_PDF_FILES`：`lawyer` 配了 5 个法条 PDF；另两个角色为空（心理/朋友走 JSONL）。
  - `ROLE_JSONL_FILES`：`psychologist` → `G:\知识库pdf文件\心理\processed_psych.jsonl`；`virtual_friend` → `G:\知识库pdf文件\虚拟朋友\cecily_persona.jsonl`。
- 本文件内还写死了 `CHUNK_SIZE = 500` / `CHUNK_OVERLAP = 80`（注意：与 `config.py` 里的同名参数是两份，改参数时别只改一处）。
- 命令行：`--role`（只跑某角色）/ `--jsonl 路径`（临时追加一个文件）/ `--no-jsonl`（只入 PDF）。
- 不带参数 = 全量跑一遍所有配置了资料的角色。
- 每个角色跑完都会 `refresh_bm25(集合)`。

#### `check_milvus.py` — 条数小工具

连 `localhost:19530`，打印所有集合名 + 每个集合条数，并对有数据的集合查 3 条样例（`rag_roleplay` 集合额外显示 source）。排查"入库到底成功没有"时最顺手。

### 4.6 主入口

#### `main.py` — FastAPI 应用

**启动时（lifespan，一次性做完 6 件事）**：

```text
1. init_db()                    → MySQL 建表
2. get_embedding()              → 连接 Ollama，加载 bge-m3
3. get_vectorstore(coll) × 3    → 连接 Milvus 的三个集合
4. get_reranker()               → 加载本地重排模型（十几秒）
5. refresh_all_bm25()           → 为三个集合重建内存 BM25 索引
6. _ensure_default_roles()      → 把 ROLE_TEMPLATES 里的角色同步进 MySQL
```

第 6 步是 **upsert（存在就更新）**，不是"只在缺失时插入"。原因很实在：对话接口读的是 **MySQL 里的** `role.system_prompt`，如果只插入不更新，改了 `prompt_templates.py` 的提示词**永远不会生效**。

**接口全清单**：

| 方法 | 路径 | 作用 | 备注 |
|---|---|---|---|
| GET | `/` | 跳转到前端 | 返回一个 meta refresh 的 HTMLResponse |
| GET | `/health` | 健康检查 | 返回 `{status, online_users}` |
| GET | `/roles` | 角色列表 | 从 MySQL 读，再回 `ROLE_TEMPLATES` 补 `role_key` 和 `suggestions` |
| POST | `/chat` | 对话（一次性） | 全链路 + 后处理 |
| POST | `/chat/stream` | 对话（流式 SSE） | 首行 `###SOURCES###[...]`，之后是正文 token |
| POST | `/ingest/text` | 粘贴文本入库 | 按 `role_key` 路由集合，入完刷新 BM25 |
| POST | `/ingest/files` | 上传文件入库 | 支持 txt/md/docx/wps/doc/pdf，多文件 |
| POST | `/cases` | 查原文/判例 | **不调 LLM**，只返回检索重排后的片段 |
| POST | `/memory/save` | 存长期记忆 | 写 `rag_long_term_memory` |
| POST | `/memory/clear` | 清短期记忆 | 删 Redis 的 `chat:{uid}:{rid}` |
| GET | `/kb/sources` | 列来源及条数 | 按 role_key 路由集合 |
| GET | `/kb/sources/{source}` | 看某来源的 chunk | 前 100 条预览 |
| DELETE | `/kb/sources/{source}` | 按来源删除 | 删完刷新 BM25 |
| PUT | `/kb/update` | 按来源更新 | 删旧 → 重切 → 重入 |
| POST | `/kb/rebuild` | 全量重建 | **必须传 `confirm=true`** 防误操作 |

**两个容错设计**：

- 检索失败**不阻塞对话**：`multi_route_recall` 抛 `RuntimeError` 时，`docs = []` 并记 warning，直接把问题丢给模型（总比整个接口 500 好）。
- 前端静态文件挂载在 `/app`（`StaticFiles`），所以前端可以直接用后端同源访问，CORS 也开了 `allow_origins=["*"]`。

#### `test_ragas.py` — RAGAS 自动评测

- 四个指标：`faithfulness`（忠实度，有没有编造）、`answer_relevancy`（切不切题）、`context_precision`（检索到的有多少有用）、`context_recall`（该检索到的有没有漏）。
- 原理：**用 LLM 当裁判**，不需要人工标注（`reference` 用于 recall 类指标）。裁判用 DeepSeek，温度设 0 保证打分稳定；embedding 复用 bge-m3，保持语义空间一致。
- 两种模式：
  - `--mode static`（默认）：用文件里预置的 3 条用例，其中第 3 条**故意让回答编造**（问知识产权，资料只给了相邻关系），用来检验忠实度能不能扣分。
  - `--mode dynamic`：真的往临时集合 `_test_ragas` 入库 → 调 `/chat` 拿真实回答和 sources → 再打分 → 清理集合。
- 结果打印到控制台，同时写 `ragas_result.json`。

## 5. 三个角色是怎么"分家"的

### 5.1 四张表对上一个角色

| 概念 | 存在哪 | 作用 |
|---|---|---|
| `role_key` | 前端下拉的 `dataset` / 请求体 | 程序的内部标识：`lawyer` / `psychologist` / `virtual_friend` |
| 角色名 | MySQL `roles.name` | 界面上显示：法律顾问 / 心理专家 / 虚拟朋友 |
| 系统提示词 + 温度 | MySQL `roles`（源头在 `prompt_templates.ROLE_TEMPLATES`） | 决定"它怎么说话" |
| Milvus 集合 | `config.MILVUS_COLLECTIONS` | 决定"它去哪查资料" |

### 5.2 路由是怎么走通的

```text
前端选中角色 → /roles 返回的 role_key 存在 option.dataset
   → 发消息时带上 role_key
   → main.py 若拿不到 role_key，用 role.name 反查 ROLE_TEMPLATES
   → get_collection_for_role(role_key) → 具体集合
   → hybrid_search(..., collection_name=该集合)
```

三个角色互不干扰：法律顾问的检索**永远进不去** `rag_companion`。

### 5.3 三个角色的性格差异（提示词要点）

| 角色 | 温度 | 提示词核心约束 |
|---|---|---|
| 法律顾问 | 0.3 | 只依据参考资料；引用要写清法律名+条款号；资料不足就说"资料不足"，**禁止编造法条案号**；提示咨询执业律师 |
| 心理专家 | 0.7 | 先倾听→再共情→最后建议；区分一般困扰与需要就医的疾病；**出现自伤/自杀倾向必须给危机热线**；像朋友聊天不像教科书 |
| 虚拟朋友 | 0.6 | 第一人称扮演"鞠婧祎（小鞠）"；被问身份就自然接住，**不许解释设定、不许说"我不是她"、不许提 AI**；**绝不说"根据资料/参考资料/文档"**；不确定的事自然带过（"我不太记得了"），不编造；关心情绪但不过度热情 |

> 第 3 条里"绝不说根据资料"这条，配合 `MEMORY_CONTEXT_TEMPLATE`（把资料包装成"你自己的记忆片段"）一起用，才把"资料→人格"的割裂感消掉。

## 6. 关键设计决策：为什么代码要这么写

这一章解释"为什么不是能跑就行"，也是这个项目最值得看的经验部分。

| # | 决策 | 不这么做会怎样 |
|---|---|---|
| 1 | 幂等键用 `(source, chunk_index)` 而不是主键 | 同一脚本重复跑，会有两套 uuid，数据翻倍 |
| 2 | 用 `query_iterator` 而不是 `offset` 分页 | Milvus 单次 query 有 `offset+limit ≤ 16384` 限制，大集合（6.6 万条）翻页必报 code=1100 |
| 3 | 去重键拉取失败时**抛错中止**而不是 warning 后继续 | 一旦静默失效，重复数据就真的写进去了（这是修过的真 bug） |
| 4 | 入库写入用 `uuid4` 主键 + `auto_id=False` | 让"数据内容"和"主键"解耦，重复入库不冲突 |
| 5 | `fetch_all_text` 必须带 `source/section/chunk_index` | 少了 source，BM25 召回的片段在引用卡片里来源显示为空 |
| 6 | 人设类角色单独一套上下文模板 | 用「参考资料」框架，模型会把资料读成"外部文档"从而否认自己是鞠婧祎 |
| 7 | 角色同步用 upsert 而不是 insert-if-absent | 改了提示词永远不生效（对话接口读的是 MySQL） |
| 8 | `/chat/stream` 一个请求里先推 `###SOURCES###` 行再推正文 | 旧版前端要额外再调一次 `/chat` 取来源，导致 LLM 被调两次、记忆存两遍、当前问题在历史里重复 |
| 9 | 流式接口不收尾会漏日志 | 改成单请求后必须在 `generate()` 里补 `save_conversation` + `set_user_active`，否则前端只调流式接口时 MySQL 里就没记录了 |
| 10 | 检索失败 `docs=[]` 继续对话 | 知识库暂时没数据/BM25 没初始化时，接口不至于直接 500 |
| 11 | 前端 `NO_SOURCE_ROLES` 只控制"显示"不控制"检索" | 陪聊角色不甩引用卡片（出戏），但人设语料照样参与检索 |
| 12 | `json.dumps` 序列化来源行 | 内容里的真实换行会被转义成 `\n` 两个字符，前端按 `\n` 切分不会截断 JSON |
| 13 | BM25 用进程内内存缓存 | 快、简单，代价是**新入库的数据不重启服务就只对向量检索可见** |
| 14 | `config.py` 支持"在线 API / 本地部署"二选一 | 没网或想省钱时可切 vLLM/SGLang，代码零改动（设 `LOCAL_LLM_BASE_URL` 即切） |

### 8.7 加了新资料之后的正确姿势

## 9. 已知问题与风险

这一章是给后来接手的人看的（也是这份文档最该被更新的部分）。

### 9.1 会影响数据正确性的

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| 1 | `list_sources` 用 `offset` 分页（每页 500） | `kb_update.py` | 集合超过 **16384** 条时翻页会报 code=1100，`GET /kb/sources` 结果不完整（心理库 6.6 万条已超线）。同文件里其他函数都用了 `query_iterator`，只有这里没改 |
| 2 | `delete_by_source` 单次 `limit=10000` | `kb_update.py` | 某来源 chunk 超过 1 万条时删不干净，需要多次调用 |
| 3 | 专注"修正文字"的更新会被幂等去重掉 | `db_milvus.py` | 只改 JSONL 里已有条目的内容，重跑入库无效，必须走 `/kb/update` 或先删再入 |
| 4 | `validate_citations` 的 `fabricated` 从未填充 | `post_processor.py` | 引用校验实际是空转，`valid` 恒为 `True`；只会统计案号数量 |
| 5 | 非法 `role_key` 静默退回 `rag_legal` | `config.py` | 前端传错 key 时，虚拟朋友会去检索法条库，而且**没有任何报错** |

### 9.2 会影响可用性/性能的

| # | 问题 | 说明 |
|---|---|---|
| 6 | **BM25 索引只在进程内存里** | 每次启动都要全量重建（心理库 6.6 万条要十几秒）；入库后必须重启才生效 |
| 7 | 新数据入库后 BM25 与向量库不同步 | 同上；重启前"关键词检索"找不到新内容 |
| 8 | 重排模型首次加载十几秒 | 启动慢的主因之一；CPU 推理也是检索慢（12.9s/次）的主因 |
| 9 | Redis 历史无 token 截断 | 固定留 20 条，遇到长回答可能超出上下文窗口 |
| 10 | 前端 `top_k` 上限 20 | 但 `ChatRequest` 的 `ge=1, le=20` 是硬限制，传超会 422 |
| 11 | 无并发/超时控制 | LLM 调用没有重试与超时；压测数据显示对话 19–23 秒 |

### 9.3 安全性

| # | 问题 | 说明 |
|---|---|---|
| 12 | **没有鉴权** | 所有接口开放，`user_id` 是前端一个数字输入框，谁都能填别人的 ID 读/清记忆 |
| 13 | CORS `allow_origins=["*"]` | 任意网页都能调本服务 |
| 14 | `/ingest/*` 与 `/kb/*` 是写接口 | 无权限校验，能删库（`/kb/rebuild` 有 `confirm=true` 挡一下，但只是防误操作） |
| 15 | 数据库密码默认值 `123456` | 只在 `config.py` 里作为环境变量兜底 |
| 16 | `sys.path.insert` + 相对路径日志 | 日志用的是相对路径，从不同目录启动服务会写到不同的 `rag_roleplay.log` |

### 9.4 文档层面

| # | 问题 |
|---|---|
| 17 | `README.md` 部分内容过时：虚拟朋友温度写 0.8（实际 0.6）、`post_processor` 被描述为"去重、压缩"（实际是正则清洗 + 引用校验）、`--dir` 参数在 `batch_ingest_pdfs.py` 里并不存在 |
| 18 | `batch_ingest_pdfs.py` 里的 `CHUNK_SIZE/CHUNK_OVERLAP` 与 `config.py` 同名参数重复，改参数容易只改一处 |

## 10. 名词速查表

| 名词 | 一句话解释 |
|---|---|
| **RAG** | Retrieval-Augmented Generation，检索增强生成：先查资料再让模型回答 |
| **Embedding / 向量** | 把一段文字变成一串数字（本项目 1024 个），意思相近的文字，数字也相近 |
| **chunk（切块）** | 把长文档切成一段段适合检索的小块；本项目默认 500 字/块、重叠 80 字 |
| **collection（集合）** | Milvus 里的一"张表"，本项目一个角色一个集合，互不干扰 |
| **Dense 检索** | 向量检索，按"意思"找，适合口语化提问 |
| **Sparse / BM25 检索** | 关键词检索，按"字面"找，适合法条号、专有名词 |
| **RRF** | Reciprocal Rank Fusion，把多路检索结果按**排名**融合，不用管两路分数是不是一个量纲 |
| **Rerank（重排）** | 用一个更准但更慢的模型（CrossEncoder）把候选重新打分排序，只留最好的几条 |
| **score_threshold** | 相似度下限，低于 0.3 的资料不喂给模型（宁少勿滥） |
| **幂等** | 同一个操作做多次，结果和做一次一样（本项目的 `(source, chunk_index)` 去重） |
| **SSE** | Server-Sent Events，服务端持续推数据给浏览器，流式输出的实现方式 |
| **短期记忆** | Redis 里最近 20 条对话，滑动窗口 + 2 小时过期 |
| **长期记忆** | Milvus 里按用户存的要点，用向量检索找回（`/memory/save`） |
| **温度（temperature）** | 模型随机性：低=严谨稳定（法律 0.3），高=活泼发散（心理 0.7） |
| **系统提示词** | 发给模型的"人设说明书"，决定它是什么角色、守什么规则 |
| **CrossEncoder** | 把"问题+候选文档"成对打分，精度高于双塔向量，代价是慢 |
| **query_iterator** | Milvus 的游标式遍历，用来绕开单次查询 16384 条上限 |
| **lifespan** | FastAPI 的启动/关闭钩子，本项目在这里把所有模型加载一遍 |

### 附：一分钟速览

```text
一句话进来 → 查角色提示词(MySQL) → 拿历史(Redis) → 三路找资料(Milvus向量 + BM25关键词 + 长期记忆)
          → RRF融合 → 重排精排 → 低于0.3丢掉 → 拼成"记忆/资料"上下文
          → DeepSeek生成 → 流式推给前端 → 顺手把本轮写回 Redis + MySQL
```

- 想改性格：改 `prompt_templates.py` → 重启（启动时自动 upsert 到 MySQL）。
- 想换模型：改 `config.py` 或环境变量（换 embedding 必须同步改 `EMBED_DIM` 并重建集合）。
- 想排查问题：先看 `rag_roleplay.log`，再用 `check_milvus.py` 对一下条数，最后用 `/cases` 验证检索是否正确。
