# 工单12 技术文档：LightRAG 知识图谱优化

## 一、目标与方案

用 LightRAG（HKU 开源的图结构 RAG 框架）对《招股说明书1/2.pdf》构建知识图谱，
实现"检索时可选 RAG（向量库）或 LightRAG（知识图谱）知识库"，并对 14 个验收问题
对比两套系统的检索-回答效果。

- 运行入口：`run_lightrag.py build`（构建图谱）/ `run_lightrag.py compare`（对比评测）
- 产出报告：《RAG与LightRAG对比-工单12.md》

## 二、技术栈与环境适配

| 组件 | 选型 | 说明 |
|---|---|---|
| 图 RAG 框架 | lightrag-hku 1.5.7 | pip 安装；1.5.x API 与旧版差异大 |
| LLM | qwen2.5:7b-instruct（Ollama） | 抽取与回答统一 7B，两侧对比公平 |
| Embedding | dengcao/bge-m3:567m（Ollama） | dim=1024，与项目向量库一致 |
| 图存储 | NetworkX + JSON（LightRAG 默认） | 产物 graphml + vdb_entities/relationships |

### 1.5.7 API 适配要点（踩坑实录）

1. **模块路径变更**：旧教程的 `from lightrag.embeddings import ollama_embed` 不存在，
   正确路径是 `lightrag.llm.ollama`（`ollama_embed` / `ollama_model_complete`）；
   `ollama_embed` 是裸异步函数，需用 `lightrag.utils.EmbeddingFunc(embedding_dim=1024, func=...)` 包装。
2. **异步生命周期**：1.5.7 强制要求 `await rag.initialize_storages()` /
   `finalize_storages()`，直接调 `rag.insert()` 会抛 `PipelineNotInitializedError`。
   因此脚本全程在单事件循环内完成：构建用 `ainsert`，查询用 `aquery`。
3. **实体类型定制**：1.5.7 通过 `addon_params={"entity_types_guidance": ...}` 注入
   领域抽取指引（无独立的关系类型接口，实体/关系类型一并写入指引文本）。

## 三、领域 Prompt 优化（工单要求）

针对金融招股书领域定制了实体/关系抽取指引：

- **实体类型**：公司、人物、机构/股东、产品/业务、技术标准、工程项目、财务指标、行业、合同/协议、资质/专利
- **关系类型**：持股/控股、任职（法定代表人/高管）、供应商关系、客户关系、参与制定、募集资金投向、子公司/关联方、行业上下游、同业竞争

## 四、本机性能攻关（本次最大的坑）

本机 GPU 为 RTX 4060 Laptop（8GB 显存），全过程实测数据：

| 阶段 | 现象 | 根因 | 对策 |
|---|---|---|---|
| 第1次构建 | 全部 chunk 抽取 480s 超时，图谱为空 | `max_async=2` + embedding 并发争抢 8GB 显存，7B 被挤到 CPU（同请求从 1.7s 恶化到 448s，约 250 倍） | `max_async=1` 单并发 + `keep_alive=60m` 保模型常驻 |
| 第2次构建（1.5B） | 每块数分钟，4.5 分钟仅完成 1 块 | 1.5B 生成无上限（num_predict 未设），复读模板占位符刷爆 token | 生成上限 `num_predict=1024` |
| 第3次尝试 | 1.5B 抽取质量差，输出 `<entity_name>` 占位符 | 1.5B 无法理解复杂抽取指令 | 弃用 1.5B，改回 7B + 控制并发 |
| 第4次构建 | 39 分钟完成，图谱 72 实体/135 关系 | — | 精选输入 + 上述参数 |

**关键实测数据**（同一约 1700 token 请求）：

- 7B 独占 GPU：**1.7s**（prompt eval 1020 tok/s）
- 7B 与构建进程并发：**448s**（prompt eval 约 4 tok/s）
- 1.5B 独测：**7.3s**（prompt eval 235 tok/s）

结论：8GB 显存跑 7B + bge-m3 必须严格单并发（`llm_model_max_async=1`），
且必须用 `keep_alive` 避免 Ollama 反复换载模型。

## 五、输入精选策略

全量插入两份招股书（约 2090 块、60 万字符）在本机不可行（估算 40+ 小时）。
采用**关键词密度精选 + 真值强制入选**：

1. 按 24 个金融领域关键词（股东/控股/关联方/募集/客户/技术标准/专利等）
   对每块打分，取密度 Top60/文档；
2. 强制补入含验收题真值的块（注册资本 5,520 万、持股 42.35%、发行占比 25.04% 等）；
3. 按页码还原阅读顺序后拼接插入。

最终：招1 精选 84 块 + 招2 精选 93 块（约 8 万字符），LightRAG 内部合并为 52 个
抽取块，39 分钟构建完成。**7 个关键事实 100% 覆盖**。

## 六、防呆设计

- 构建完成标记 `build_done.txt` 只在确认 `vdb_entities.json` 生成后才写入，
  避免实体抽取全部失败时"假完成"（第 1 次构建即出现过空图谱假完成）；
- LLM 响应缓存开启（`kv_store_llm_response_cache.json`），重复实验不重跑抽取。

## 七、遗留说明

- num_predict=1024 会截断个别实体超多的块（日志有 truncated warning），
  LightRAG 按部分内容继续处理，实测影响可忽略；
- 少量记录因 7B 输出实体类型不在限定清单内被 LightRAG 跳过（invalid entity type），
  属正常丢弃；
- rerank 未配置模型，LightRAG 查询侧用默认向量选择（告警可忽略）。
