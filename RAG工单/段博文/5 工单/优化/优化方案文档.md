# 工单编号：人工智能NLP-RAG-Query理解优化任务

# 优化方案文档

## 一、优化目标

在已有 RAG 系统（工单四：图像语义解析 + 表格解析）基础上，新增**多轮对话能力**，让用户能够用自然语言进行连续追问，系统自动完成**指代消解、主语继承、主语切换**等 Query 理解优化任务，把"他/这个公司/那XX呢"等口语化追问改写成独立完整问题，再去检索与回答。

## 二、核心优化点

### 1. 会话管理（SessionManager）
- **存储**：内存 `OrderedDict` + LRU 淘汰，最大 1024 个会话
- **窗口**：每个会话保留最近 10 轮（20 条消息），避免上下文过长
- **过期**：1 小时未活跃自动清理
- **线程安全**：`threading.Lock` 保护并发访问
- **实体追踪**：会话级 `last_entity` 字段，记录最近一个明确公司/机构名

### 2. Query 改写（QueryRewriter）

#### 2.1 问题分类（detect_query_type）
| 类型 | 触发条件 | 处理策略 |
|------|---------|---------|
| `standalone` | 已含完整公司实体 | 不改写，直接检索 |
| `coreference` | 含"他/这个/该/其"等指代词 | LLM 改写：替换为最近实体 |
| `switch` | 匹配"那XX呢？" | 规则快速路径：复用上轮谓语 + 替换主语 |
| `followup` | 短句缺主语 | LLM 改写：补全主语 |

#### 2.2 改写策略
- **规则前置**：对"那XX呢？"模式直接复用上一轮谓语 + 替换主语，**响应 < 5ms**，避免 LLM 调用
- **LLM 改写**：调用 DeepSeek，温度 0.0，max_tokens 128，使用专用系统提示词
- **缓存**：MD5(query + history_key) → LRU 缓存，命中后 < 1ms
- **回退**：LLM 失败时退化为启发式（实体拼接）

#### 2.3 改写示例
```
Q1: 武汉兴图新科...军用收入？     → 不改写
Q2: 他参与的哪个工程...？         → 武汉兴图新科电子股份有限公司参与的哪个工程...
Q3: 这个公司的法定代表人是谁？    → 武汉兴图新科电子股份有限公司的法定代表人是谁？
Q4: 那武汉力源信息技术股份有限公司呢？ → 武汉力源信息技术股份有限公司的法定代表人是谁？
```

### 3. 检索与生成复用
- 改写后的问题走原有"向量+BM25+RRF+bge-reranker"链路
- LLM 答案写回会话历史，供下一轮改写参考
- 会话历史长度与查询改写缓存独立，互不影响

### 4. 前端展示
- **会话徽章**：顶栏显示当前 session_id 前 8 位
- **新会话按钮**：清空历史 + 删除 localStorage
- **改写提示条**：assistant 气泡顶部显示"理解后的问题" + 类型标签（指代消解/主语切换/主语继承/独立问题）
- **session_id 持久化**：localStorage 保存，刷新页面后继续会话

## 三、性能与验收

| 指标 | 目标 | 实测 |
|------|------|------|
| 多轮对话链准确率 | ≥90% | **100%**（5/5） |
| 改写正确率 | - | **100%**（3/3 需要改写的全对） |
| 关键词命中率 | - | **100%**（9/9） |
| 响应时间 | ≤3s | 平均 7.5s（CPU 推理，冷启动慢；GPU 部署可达标） |
| 中英文支持 | 支持 | 通过（英文问题答案正确） |

## 四、容错机制

1. **改写失败**：自动 fallback 到启发式拼接，保证可回答
2. **LLM 超时**：20s 超时，超时后走启发式
3. **会话过期**：1 小时无活动自动清理，避免内存泄漏
4. **会话超载**：LRU 淘汰最旧会话，最多保留 1024 个
