## 3. 结论（如实陈述）

### 3.1 稳定性：达标 ✅

**三档并发 0 错误、0 失败、无崩溃**。对比上游工单04 的记录
（100 并发档「服务进程 GPU 显存耗尽而崩溃」），本工单在同等硬件上通过了 100 并发，
原因有两层：

1. Reranker 的**显存闸门**：加载前检查剩余显存，不足则自动改用 CPU（`src/rerankers._pick_device`）；
2. 服务侧**不做并发模型加载**：模型单例懒加载 + 锁，请求之间共享，不会出现多份权重争显存。

### 3.2 响应时间：**未达标** ❌

三档的 p50 分别为 **8.8s / 17.0s / 17.0s**，全部远超 3 秒；`≤3s 占比 = 0.0%`。
这与单请求热态实测（**1.2~2.0s**，见 `docs/04` 逐题 `total_ms`）形成鲜明对比 ——
**瓶颈不在单条链路，而在并发排队**。

### 3.3 根因分析

| 环节 | 为什么并发下会排队 |
| --- | --- |
| LLM（主因） | Ollama 单实例按请求**串行生成**（默认 `OLLAMA_NUM_PARALLEL=1`）。每题生成 0.7~1.4s，10 路并发 → 队尾等 7~14s。观察：QPS 三档都稳定在 **0.86~0.93**，即**吞吐被生成能力锁死**，与并发度无关 |
| 嵌入/精排 | 单卡 8GB，embedding 与 reranker 已按 fp16 常驻；并发查询需排队过同一张卡（单题合计约 0.2~0.3s，占比较小） |
| 系统内存 | 压测期间系统内存占用 **87.4%→97.4%（峰值 99.9%）**（16GB 机器），已顶到上限；桌面应用常驻占用是前提条件 |

> 换句话说：并发 10 与并发 100 的 p50 几乎一样（8.8s vs 17.0s），
> 说明系统在**串行化地消耗请求队列**，而不是"并发 100 就崩"。

### 3.4 改进方向（按性价比排序）

1. **提高生成吞吐**：`OLLAMA_NUM_PARALLEL=4`（显存允许时 3B 可并行多路）+ 多 Ollama 实例；
2. **CPU 精排**：并发下把 reranker 固定到 CPU（约 +1s/题，但把 GPU 全留给生成）；
3. **回答缓存**：压测刻意 `use_cache=False`，生产开启后重复问题命中缓存（0ms）；
4. **横向扩展**：`QDRANT_MODE=server` + 多 worker 进程 + 前置负载均衡；
5. **批量嵌入**：把并发请求的 query 合并成 batch 编码（当前逐条编码）。

### 3.5 与工单指标的差距说明

工单的「响应时间不超过 3 秒」在**单请求热态**下达成（16 题逐题实测，见 `docs/04`），
**高并发下未达成**。本报告不粉饰：**3 秒指标是单用户口径，不是 100 并发的口径**；
两者在本机（单卡 8GB + 16GB 内存 + 单实例 Ollama）不可能同时满足。

### 3.6 环境备注（影响可比性，必须说明）

* 本轮复测时机器后台负载较高（微信/QQ/会议软件/杀毒等桌面应用常驻，
  外加 Ollama 常驻 2.0GB）→ 预热耗时 61.3s（上轮 34.7s）、
  系统内存三档均顶到 99.4~99.9%（上轮峰值 90.9%）。
* 因此本轮**绝对时延略高于上一轮**；两轮的"0 错误 + QPS 锁定 + 时延区间"
  结论完全一致，代码未变化。
* 后续如需更干净的对照数据，建议在**关闭桌面应用、系统内存占用 <70%** 时重跑同一条命令。
