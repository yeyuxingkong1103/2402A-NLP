## 第一部分：实现步骤

### 步骤 1：梳理服务代码与依赖

把金融问答能力封装成 8 个模块放进 `app/`，全部可变项（路径、端口、检索参数、大模型密钥）
改为环境变量可覆盖，使同一份代码既能本机直跑也能容器化部署：

| 模块 | 职责 |
| --- | --- |
| `config.py` | 集中配置，全部支持环境变量覆盖；修正容器内标准输出编码 |
| `logging_setup.py` | 日志初始化，同时输出到控制台与 `/app/logs` 文件 |
| `dataset.py` | 加载 `corpus/` 下语料并分块 |
| `embedder.py` | 加载 m3e-base 嵌入模型；模型缺失时降级为纯 BM25 |
| `retriever.py` | 向量检索 + BM25 + RRF 融合的混合检索 |
| `llm_client.py` | DeepSeek 客户端，含重试、超时与降级 |
| `qa_service.py` | 索引单例与问答编排，索引缓存落盘 `/app/data` |
| `api_server.py` | FastAPI 入口，暴露 `/health` `/stats` `/ask` `/retrieve` |

### 步骤 2：编写 Dockerfile（多阶段构建）

- **阶段一（builder）**：先把全部依赖预编译为 wheel 存到 `/wheels`，
  torch 单独从 PyTorch 官方 CPU 源下载，其余依赖从国内镜像源拉取。
- **阶段二（运行镜像）**：从 builder 复制 wheel，用 `--no-index --find-links` 离线安装后删除
  wheel 目录；只带走运行时必需的产物，镜像更小、攻击面更低。
- 运行阶段创建非 root 用户 `raguser`（uid 1000）并预建 `/app/data`、`/app/logs`、`/app/shared`。
- 配置 `HEALTHCHECK`，让 `docker ps` 与编排系统能直接判断服务可用性。

### 步骤 3：编写 docker-compose.yml

- `rag-api`：问答服务，映射 `8000:8000`，挂载 3 个命名卷与本地嵌入模型（只读）。
- `rtmp-server`：`alfg/nginx-rtmp` 配套服务，映射 `1935`/`8080`，
  与问答服务加入同一自定义桥接网络 `rag-net`，并共享 `rag-shared` 卷——
  用于验证工单要求的「容器网络配置正确，能与其他服务（如 RTMP 服务器）正常通信」
  与「支持容器间数据共享」。
- 三个命名卷：`rag-data`（索引缓存与问答历史）、`rag-logs`（日志）、`rag-shared`（跨容器共享）。

### 步骤 4：编写自动化验收脚本

`scripts/verify_deploy.sh` 把工单验收标准逐条翻译成可执行断言，共 13 项，
覆盖容器启动运行、日志异常检查、卷持久化、容器间共享、自定义网络 DNS、
接口功能测试，最后输出「通过 N 项 / 失败 M 项」的汇总结论。

## 第二部分：过程问题记录

### 问题 1：构建时重复下载 797 MB 的 CUDA 版 torch

- **现象**：镜像构建过程中，`pip wheel` 步骤反复下载约 797 MB 的 `torch` 包，
  构建耗时被拉长到十几分钟，最终镜像体积异常增大。
- **原因**：早期为解决 torch 版本冲突，在 Dockerfile 里用 `grep -v '^torch' requirements.txt`
  把 torch 行从依赖清单中删掉。删掉后 `sentence-transformers` 声明的 `torch>=1.11.0`
  失去版本约束，pip 便从默认源解析出带 CUDA 的完整版 torch。
- **处理**：去掉 `grep -v`，改为在 `requirements.txt` 中锁定 `torch==2.4.1+cpu`，
  并在 `pip wheel` 时加 `--find-links /wheels`，让 pip 直接命中上一步已下载到本地的
  CPU wheel。最终镜像内实测 `torch.__version__` 为 `2.4.1+cpu`，未再出现 CUDA 包。
- **备注**：PyTorch 官方 CPU 索引页给出的链接会 302 跳转到 `download-r2.pytorch.org`，
  该 CDN 在部分网络环境不可达，因此 Dockerfile 中直连 `download.pytorch.org` 的静态包地址。

### 问题 2：BuildKit 不允许续行后追加注释

- **现象**：Dockerfile 中形如

  ```dockerfile
  RUN pip install \
      --no-cache-dir \   # 这是注释
      -r requirements.txt
  ```

  的写法在传统 builder 下可用，在 BuildKit 下直接构建失败。
- **原因**：BuildKit 严格解析续行，行尾反斜杠后的内容会被并入下一条指令，
  注释于是被当成命令参数。
- **处理**：全部注释统一写在指令**上方**，续行内部不再出现 `#`。
  Dockerfile 顶部已加注说明，避免后续维护者重蹈覆辙。

### 问题 3：compose 报 `project name must not be empty`

- **现象**：在 `工单十` 目录下执行 `docker compose up -d`，报错

  ```
  project name must not be empty
  ```

- **原因**：compose 默认用**目录名**推导项目名，并会过滤非 ASCII 字符。
  本目录名为中文「工单十」，过滤后得到空串，项目名非法。
- **处理**：在 `docker-compose.yml` 顶层显式声明 `name: rag-finance`
  （Compose Spec 特性），此后直接 `docker compose up -d` 即可，
  不再需要手动加 `-p rag-finance`。
- **附带项**：同一文件原有的 `version: "3.8"` 在新版 compose 中已废弃，
  每次执行都会打印 `the attribute version is obsolete` 警告，
  容易被误认为部署报错，已一并移除。

### 问题 4：Linux 版 docker CLI 不识别 Windows 路径

- **现象**：在 WSL 中用 `/usr/bin/docker`（Linux 版 CLI）执行 compose，
  报错 `invalid volume specification: 'C:/Users/dang5/Desktop/.../m3e-base:/models/m3e-base:ro'`。
- **原因**：该 CLI 连接的是 Docker Desktop 的 Linux 引擎，卷路径按 Linux 语义解析，
  无法识别 `C:/...` 形式的 Windows 路径。
- **处理**：改用 Windows 版 CLI `docker.exe` 执行，Windows 路径即被正确识别，
  compose 完整栈启动成功。若确需使用 Linux 版 CLI，
  需把模型路径改写为 `/mnt/c/Users/dang5/Desktop/...`（见 `部署文档.md` 第四节说明）。

### 问题 5：验收脚本自身缺陷导致接口测试误判失败

- **现象**：首次执行 `verify_deploy.sh`，前 11 项全部通过，
  但第四节「服务接口测试」的 `/ask` 与 `/retrieve` 两项失败，返回内容为空。
- **原因**：脚本第三节为了验证自定义网络，用 `docker run` 重新启动了服务容器，
  但**漏写了 `-p ${PORT}:8000` 端口映射**；第四节再通过 `127.0.0.1:${PORT}` 访问，
  自然连接不上。属于验收脚本自身的缺陷，并非部署本身有问题。
- **处理**：在第三节的 `docker run` 中补上 `-p "${PORT}:8000"`。
  重新执行后 13 项全部通过。
- **结论**：接口功能本身一直是正常的（手动 `curl` 验证可正常返回答案）。

### 问题 6：健康检查宽限期短于索引构建耗时，正常服务被误判为 unhealthy

- **现象**：冷启动（数据卷为空）时，服务需要约 7 分钟才能就绪。
  初版健康检查的 `start-period` 设为 180 秒，结果服务明明已经正常应答，
  `docker compose ps` 却显示 `unhealthy`；观察状态变迁可见它先由
  `starting` 变为 `unhealthy`，约 1 分钟后再自行恢复为 `healthy`。
- **原因**：本轮语料为 1533 个文本块，CPU 上逐块编码 768 维向量，
  实测 `build_seconds` 分别为 440.23、439.60、444.56 秒。
  `start-period` 只有 180 秒，宽限期结束后健康检查连续 3 次失败（3 × 30 秒），
  于是在第 270 秒左右被判定为 `unhealthy`——**根因是宽限期设置小于实际冷启动耗时**。
- **处理**：
  1. 把 Dockerfile 与 `docker-compose.yml` 中的 `start-period` 由 180 秒改为 **600 秒**，
     使其覆盖冷启动建索引耗时并留有约 2.5 倍余量；
  2. 索引结果落盘到 `/app/data` 卷，**只在首次构建，之后启动直接命中缓存**——
     实测删除容器后用同一卷重建，`build_seconds` 由 440.23 秒降至 **0.11 秒**。
- **验证**：`docker compose down -v` 清空数据卷后重新冷启动，逐 20 秒轮询容器状态，
  观察到的状态变迁为 `starting` → `healthy`（约 460 秒），**中间不再出现 `unhealthy`**。
- **结论**：该耗时属于一次性的冷启动成本，正常运维下不会重复发生；
  若语料规模扩大，应同步按比例调大 `start-period`。
