# 工单03 · PDF 文档的表格解析及检索优化

> 工单编号：**人工智能NLP-RAG-PDF 文档的表格解析及检索优化**
> 在工单01/02 的问答系统上，加入第二份 PDF《招股说明书2.pdf》（武汉力源信息技术股份有限公司），
> 用**表格解析**把答案定位到表，并让两份文档的题互不串味。

---

## 一、工单要求与本次难点

工单原文的要求是：在 01/02 建成的系统上增加《招股说明书2.pdf》的解析，使下列 14 道题
（4 道力源 + 10 道兴图）的**回答准确率 ≥ 90%**、**响应 ≤ 3 秒**，并在备注里点名：

> 1、分析待检索的问题答案在 pdf 中的定位，使用表格解析技术实现；
> 2、代码注释需包括工单编号。

难点不在"再灌一份 PDF"，而在三处**两份文档互相干扰**的地方，每一处都能静默出错：

| 难点 | 具体表现 | 实测依据 |
|---|---|---|
| **分词与页码格式都写死了书1** | 页脚：书1 印 `1-1-N`，书2 印**裸数字 `N`**；页眉模板、旋转页也不同 | 书2 350 页里 8 页是旋转 90° 的横向表，页眉页脚不在常规分带内 |
| **两份书章节结构雷同，检索分不清谁是谁** | 「发行股数」「占发行后总股本」「募集资金」**两边都有** | 同一个问题两家答案完全不同：书1「发行股数 1,840 万股 / 不低于25.00%」vs 书2「1,670 万股 / 25.04%」，而"发行股数"一词两边各出现 3 页 |
| **提示词里写死了文档名** | system prompt 写「基于《武汉兴图新科电子股份有限公司招股意向书》…」 | 见第三章：模型对力源的题**系统性拒答** |

一个 `grep` 就能看出前两处的来源 —— 这些规则原先散在 `pdf_parser` / `config` / `evaluator` /
`generator` 里，全部硬编码成书1，共 **六处**：

```
$ grep -rn "兴图\|1-1-XX" --include="*.py" app/ | wc -l
```

所以本次改法的总纲是：**把这六处收进一份「文档配置」**（`app/core/doc_profiles.py`，
一份 PDF 一条），其余代码只认配置，不再认具体文档。

## 二、答案在 PDF 里到底在哪 —— 表格解析的必要性

工单备注要求"先分析答案的定位"。逐题核实的结论是：**力源的 4 道题，答案全在表格里**。

| 题号 | 答案 | 定位（印刷页码） | 结构 |
|---|---|---|---|
| 1 | 发行股数 1,670 万股，占发行后总股本 **25.04%** | 21；23 亦载明 | 「四、本次发行情况」两列键值表 |
| 2 | 仓储及物流中心 3,393.40 / 研发中心 1,526.38 / 电子商务平台 2,492.78 / 扩充产品种类和数量 9,000.00 / 其他与主营业务相关的营运资金 | 21（项目名）；305（全部金额） | 5 行 3 列项目表 |
| 3 | 赵马克，持股 **42.35%**，公司控股股东 | 156；20 亦载明 | 「存在控制关系的关联方」表 |
| 4 | 融冰投资、武汉博润、上海博润、听音投资、联众聚源、力源贸易、普芯达（共 7 家） | 156 | 「不存在控制关系的关联方」表 |

这直接决定了实现方式**必须**是表格解析，而不是 `get_text()` 抽文字：

```
get_text() 抽一页"两列键值对"表，得到的是 项目/值 交替的孤立行：
    发行股数
    1,670 万股，占发行后总股本的比例为25.04%
    ← 哪一行是标签、哪一行是值，全靠猜

find_tables() 按 bbox 重建后行列分明：
    | 发行股数 | 1,670 万股，占发行后总股本的比例为25.04% |
    ← 单元格自带标签，语义密度完全不同
```

因此表格一律走 `find_tables()`（`app/core/pdf_parser.py`），并配套两条防污染规则：

1. **表格区域内的文本块要丢弃**（`n_table_text_dropped`）。同一份内容若同时以"散文"和
   "表格"两种形态进库，检索会召回两条重复结果、互相挤占 top-k 名额。
2. **表格要补标题**：取表上方最近的一段短文本当标题（如「（二）本次发行上市的重要日期」），
   让表格 chunk 自带语义锚点。

实测（`preflight.py` 7b 节）：第 21 页能抽出 3 张表，其中「四、本次发行情况」与
「五、募集资金用途」两张正是题 1、题 2 的答案所在。

## 三、六处文档绑定的收拢，与三次实测踩坑

### 3.1 解析层：页眉/页脚/页码格式按文档走

`DocProfile` 里一条配置长这样：

```python
"liyuan": DocProfile(
    key="liyuan", doc_name="招股说明书2.pdf",
    header_re=re.compile(r"^\s*武汉力源信息技术股份有限公司\s+招股意向书\s*$"),
    footer_re=re.compile(r"^\s*\d{1,3}\s*$"),     # ← 裸数字，与书1 的 1-1-N 完全不同
    label_fmt="{n}",                              # ← 页码格式也按文档走
    entity_names=["武汉力源信息技术股份有限公司", "武汉力源信息技术", "武汉力源", "力源信息"],
    evidence_re=re.compile(r"(?<!\d)\d{1,3}(?!\d)"),
    title="武汉力源信息技术股份有限公司招股意向书",
    citation_hint="XX",
    notes="7. 【占位符原样】原文中印作「[ ◆ ]」的位置是**空缺占位**…",
),
```

`profile_for_path()` 遇到**没配过的文档直接报错**，不静默套用别的文档的规则 ——
静默套用的后果是"页眉一条都清不掉、页码格式显示错"，不报错、只是结果悄悄变差
（加书2 时实测各清 0 条）。

**页码格式必须按文档走**，不能统一成 `1-1-N`，两个理由：
- 引用与读者在 PDF 里看到的页码对不上，验收时无法核对；
- 两份文档都会产生 `1-1-21` 这种页码，页级精确率/召回率**跨文档歧义**。

### 3.2 检索层：实体路由（硬过滤，不赌排序）

两份书章节结构雷同，靠相关性排序**无法可靠区分**（分数会随上下文措辞上下浮动），
但问题里点名了公司 —— 匹配是确定的。所以按 `doc_name` 硬过滤：

```python
r = route(query)                                   # 认问题里的公司专名
expr = r.expr if len(route_multi(query)) <= 1 else ""   # 一句话点两家 → 不过滤
pools = await asyncio.gather(*(... store.search(vec, n_pool, expr=expr) ...))
if expr and not any(pools):                        # 过滤后零召回 → 回退全库
    route_fallback = True
    pools = await asyncio.gather(*(... store.search(vec, n_pool) ...))
```

三个设计点，都是"不做就会错"的：

- **用 `doc_name` 而不是 `doc_id` 过滤**：`doc_id` 是入库时按「文件名:大小:mtime」算的 sha256
  —— 文件被重新保存一次（mtime 变）就对不上了。`doc_name` 稳定且可读。（邻块查询仍用 `doc_id`，
  那是从命中行里带出来的，天然正确。）
- **必须回退**：问题里点了名的公司，和答案所在的公司**不总是同一家**
  （如"和兴图比，力源的发行股数是多少"）。宁可多召回也不能空手，空上下文会让模型只能凭空编。
  回退这件事记进 `route_fallback`，否则事后分不清"路由生效了"和"路由白过滤了一次"。
- **命中的专名要记全称**：`武汉力源信息技术股份有限公司` 必须先于 `武汉力源` 命中，
  否则排查时看不出到底匹配到了什么。

实测：14 道题全部正确路由（书1 10 道 / 书2 4 道），**零回退**。

### 3.3 生成层：提示词口径按文档走 ← 本次最隐蔽的一个坑

`SYSTEM_PROMPT` 原本写死两处：

```
你是一个严谨的文档问答助手，基于用户提供的《武汉兴图新科电子股份有限公司招股意向书》片段回答问题。
4. 【标注页码】回答末尾用「（见 1-1-XX 页）」的形式标注依据的页码。
```

后果是**系统性拒答**。实测 id=1（力源发行股数）：

```
上下文里明明有：  [片段1] 页码 21｜… | 发行股数 | 1,670万股，占发行后总股本的比例为25.04% |
                 CKC（关键词覆盖率）= 100%
模型却答：        资料中未提及相关信息（见 1-1-21 页）
                            ↑ 还按书1 的格式编了个页码（书2 根本没有 1-1-N）
```

机制很清楚：模型被告知"你拿到的是兴图新科的文件"，于是判定"问题与文档不符"→ 拒答。
修法是 `generator.system_prompt_for(doc)`：文档名与页码格式都从 `DocProfile` 取。
不点名文档时（跨文档提问 / 问题里没点公司名）退化成**通用版**，不硬套任何一份
—— 点名任何一家都是错的，甚至会把上面那种拒答引到另一份文档上。

> 修掉之后 id=1 的答案变成："本次发行股数为1,670万股，占发行后总股本的比例为25.04%（见 21 页）。"

### 3.4 表格邻块：引子句和表格被切开时的救回

id=2（力源募集资金拟投哪些项目）第一轮实测仍然失败，原因是**分块切在了引子和表格之间**：

```
chunk 42（正文）「五、募集资金用途本次募集资金拟投资以下项目：…」
chunk 41（表格）「| 1 | 仓储及物流中心 | 3,393.40 | … | 5 | 其他与主营业务相关的营运资金 |」
```

引子句与问法高度相似 → 稠密检索把它排到第 1；而整张表全是项目名和金额，
**与"哪些项目"的问法不相似**，连候选池（每路 30）都进不去。

已有的"邻块扩展"机制本该救回这种"答案被切在相邻块里"的情况，但它的**互补性过滤**
把表格挡掉了：该过滤要求邻块带来"原块没有的**查询词**"，而 chunk 41 里全是项目名和金额，
一个查询词都没有（"募集资金/投资项目"这些词它和引子句共有）—— 可答案是它。
**查询词集合这套判据天然测不出"邻块里有答案"。**

所以工单03 给表格开一个例外：**表格邻块一律收**（表格是稠密事实载体、且是"整表不可切分"
的原子块）。同时表格不走 `best_window` 截窗口 —— 按查询词密度切窗口会把表切在行中间，
破坏原子性；预算由 `neighbor_total_chars` 兜底，放不下就跳过这张表、不打断后面的小邻块。

> 修掉之后 id=2 的答案："…包括仓储及物流中心、研发中心、电子商务平台、扩充产品种类和数量，
> 以及其他与主营业务相关的营运资金。（见 21 页）" —— 5/5 关键词全中。

### 3.5 评估层：页级指标的证据页格式按文档走

`evaluator` 里也有一处同样的硬编码：`_PAGE_RE = re.compile(r"1-1-\d+")`，
而 `DocProfile.evidence_re` 已备好却没人用（死字段）。后果是**静默失效**：
书2 的 `evidence_page` 是裸数字 `"21"`，拿 `1-1-\d+` 去抽是**空集** → gold 为空 →
`page_recall` 变成 `None`，页级指标整列没了，且不报错。

修法是 `page_re_for(hits, routed_doc)`：问题路由到哪份文档就按哪份的格式抽；
没路由时退回命中块所属的文档；都不确定才用书1 的格式（保持工单01/02 的既有行为）。

> ⚠️ 正因为书2 的抽取正则是**裸数字**，`questions.json` 里书2 的 `evidence_page`
> 字段**只能写页码**（`"21 23"`）。混进年份、金额之类的数字会被误抽成页码
> —— 这个约束写在 `doc_profiles.py` 的注释里，位置就在那条正则旁边。

## 五、口径声明（看数字前必须知道的三件事）

### 5.1 响应时间口径 = TTFT，且**不能用 P95 单独判达标**

与工单02 一致：判据取"**TTFT ≤ 3s 的题数**"。n=14 时 P95 是最邻近样本，
本身就不稳；14/14 这个计数比 P95 更硬。

### 5.2 CKC（上下文关键词覆盖率）是**检索侧**口径，不含邻块

CKC 问的是"**top-k 命中块**里覆盖了多少 `rule_keywords`"。邻块扩展补进来的上下文
**不计入**它 —— 这和页级精确率排除邻块是同一个理由：邻块本就不指望落在证据页上。

于是会出现 id=2 这种看起来矛盾的现象：**CKC=60% 而模型 5/5 全中**。
不是 bug —— 第 5 个关键词是靠**表格邻块**补进上下文的（第 3.4 节），而 CKC 按口径不算邻块。
排查时要把 CKC 和 `n_added_neighbors` 一起看。

### 5.3 页级指标偏低是正常现象，不是检索失败

两份招股书的同一事实会在十几页重复披露（书1 尤其严重），而 `evidence_page` 只登记了
1–2 页权威出处。所以"召回了 A 页、证据页写的是 B 页"很常见，页精确率天然上不去。
判断检索质量要看**规则命中**与 **CKC**，页级指标只用来看趋势。

## 六、顺带修掉的缺陷

| 缺陷 | 后果 | 修法 |
|---|---|---|
| `expand_with_neighbors` 只取 `hits[0].doc_id` 查邻块 | 两份文档进库后，top-k 一旦跨文档，邻块会用第一份文档的 `doc_id` 去查，**把另一份文档的块静默拉进上下文**（串库） | 按 `doc_id` 分组，各组用自己的 id 查 |
| `DocProfile.evidence_re` 是死字段 | 见 3.5 节：书2 的页级指标整列静默失效 | `page_re_for()` 接线 |
| `config.query_entity_names` 只列书1 三个专名 | 查询抽象不会去掉"武汉力源信息技术股份有限公司"，力源的题会原样重演工单01 的召回退化 | `_entity_names()` 改以 `doc_profiles.all_entity_names()` 为准（按长度降序，最长匹配优先），config 那份降级为补充 |
| 邻块重构时遗留一行 `qt = _tokens(abstract_query(query))` | `NameError: name 'query' is not defined`，两个邻块用例直接挂 | 删除（`qt` 已改为参数传入） |

## 七、已知限度与推迟项

1. **第 4 题（不存在控制关系的关联方）的 golden 是 7 家全列**，用的是 `all` 口径。
   模型若漏 1 家就算不中 —— 这是有意从严：工单原文把 1–4 题列入"检索结果准确无误"的验收项。
2. **表格邻块一律收**会小幅增加 prompt（实测 14 题共补入 26 个邻块，平均上下文 1996 字）。
   TTFT 仍有 545ms 余量（最大 2454ms / 3000ms 线），但没有再做更细的筛选。
   若后续加文档，建议加一条"表格邻块也要与查询有最小词面重叠"的门槛。
3. **没有为书2 做旋转页的专项处理**：书2 有 8 页旋转 90° 的横向表，
   `find_tables()` 在旋转页上的表现未单独验证。目前 4 道力源题不涉及这些页。
4. **演示视频**需人工录制（见 `docs/工单03-演示截图清单.md`）。
5. **跨文档提问（"兴图新科和力源信息的注册资本各是多少？"）拿不到完整答案** ——
   这是**已识别、未修**的限度，写在实现处（`retriever.retrieve` 第 0 步的注释）。
   事实经过：这类问句 `route_multi` 会认出两份文档，于是**不过滤**（限定任何一份都会漏）。
   但"不过滤"只是不主动漏，**并不保证两家的答案都进 top-k**。实测该问句 7 条命中块
   全来自书1，力源的「注册资本：人民币5,000万元」根本没进上下文，模型只能答"未提及"。
   追查过根因，不在路由而在**检索本身**：力源那条在第 21 页的**编号列表**里
   （"1、公司名称…3、注册资本：人民币5,000万元"），字段被稀释，在力源自己的候选池里
   也排不进前 30；而书1 的同类信息是**表格块**（1-1-21）所以排第 3。
   试过两个修法（分池 + 按文档保底名额）都不能真正解决，故**撤掉不留半成品**。
   这项工作不在工单要求的 14 题内；真要修，方向是按字段切分"基本情况"列表，
   与工单04（图像内容解析）更契合。
