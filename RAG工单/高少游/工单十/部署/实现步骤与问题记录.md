## 三、过程问题记录

> 下表按「现象 → 原因 → 解决 → 验证」记录真实踩坑与处置。

### 问题 1：Docker 守护进程未运行

- **现象**：`docker ps` 报 `error during connect: ... The system cannot find the file specified`。
- **原因**：Docker Desktop 未启动。
- **解决**：启动 Docker Desktop，等待引擎就绪后再执行命令。
- **验证**：`docker info` 正常返回。

### 问题 2：项目骨架拷贝命令不可用

- **现象**：`robocopy` 在 PowerShell 会话中不可用 / 报错。
- **原因**：环境差异，`robocopy` 需完整路径且返回码语义特殊。
- **解决**：改用 `Copy-Item -Recurse -Force`。
- **验证**：`src/`、`data/`、`vector_db/` 目录完整。

### 问题 3：第三方 RTMP 镜像不在镜像站白名单

- **现象**：`docker pull alfg/nginx-rtmp`、`jasonrivers/nginx-rtmp` 均失败（白名单/网络受限）。
- **原因**：构建环境无法访问 Docker Hub，公共镜像不可获取。
- **解决**：用 **Python 标准库**自建最小 RTMP 服务器（`deploy/rtmp_server/`），实现符合 RTMP 1.0 规范的
  `C0/C1 → S0/S1/S2 → C2` 握手流程，并用 `python:3.10-slim` 打包为 `finqa-rtmp:1.0`。
- **验证**：`deploy/rtmp_client.py` 与对端握手成功，对端日志记录 `握手完成: C0=0x03 S0=0x03 C2=ok`。

### 问题 4：基础镜像从 Docker Hub 拉取失败

- **现象**：`docker pull python:3.10-slim` 反复超时 / 403（不同镜像站）。
- **原因**：Docker Hub 与多数公共镜像站在构建环境不可达。
- **解决**：确认本地已存在 `python:3.10-slim`（186 MB），**直接复用本地镜像构建**，不再拉取。
- **验证**：构建日志 `[1/12] FROM docker.io/library/python:3.10-slim DONE 0.0s`（秒级，命中本地缓存）。

### 问题 5：BuildKit 前端镜像拉取失败

- **现象**：`docker build` 卡在 `resolve image config for docker-image://docker.io/docker/dockerfile:1`。
- **原因**：Dockerfile 首行 `# syntax=docker/dockerfile:1` 需联网拉取前端镜像。
- **解决**：**移除 `syntax` 指令**，使用默认内置构建器。
- **验证**：`#1 [internal] load build definition from Dockerfile DONE 0.1s`。

### 问题 6：构建期 apt 源不可达（关键问题）

- **现象**：`RUN apt-get update` 长时间 `Ign:` 重试后失败（`deb.debian.org` / `mirrors.tuna...` 均不可达）。
- **原因**：构建环境可访问 PyPI 镜像，但**无法访问 Debian apt 源**。
- **解决**（三处协同改造，彻底去 apt）：
  1. **移除 Dockerfile 的 apt 层**，不再安装 `curl / libgl1 / libglib2.0 / libgomp1 / tzdata`；
  2. **精简容器依赖** `requirements.docker.txt`：去掉 `opencv-python`、`matplotlib`
     （经核查，`app.py` 与 `src/` 运行期**未 import cv2 / matplotlib**，二者仅用于宿主侧离线出图工具），
     从而不再需要 `libGL` 等系统库；时区数据改由 pip 安装 `tzdata`；
  3. **健康检查去 curl**：`HEALTHCHECK` 改用 `python -c "import urllib.request..."`。
- **验证**：镜像构建一次通过；容器 `healthy`；`/_stcore/health` 返回 `ok`。

### 问题 7：pip 下载缓慢

- **现象**：默认 PyPI 源下载速率低，构建耗时长。
- **解决**：Dockerfile 内置 `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple` 与 `PIP_TRUSTED_HOST`。
- **验证**：依赖下载速率提升，构建顺利完成。

### 问题 8：PowerShell 验收脚本中文乱码 / 解析报错

- **现象**：运行 `verify.ps1` 报 `The string is missing the terminator`，且中文显示为乱码。
- **原因**：脚本被改写后**丢失 UTF-8 BOM**，Windows PowerShell 5 按 ANSI/GBK 读取 `.ps1`，导致中文与引号解析错乱。
- **解决**：以 **UTF-8（含 BOM）** 重新保存脚本：
  ```powershell
  $c = Get-Content verify.ps1 -Raw -Encoding UTF8
  Set-Content verify.ps1 $c -Encoding UTF8 -NoNewline   # PS5 的 UTF8 带 BOM
  ```
- **验证**：`BOM: EF BB BF`，脚本正常解析并全部 PASS。

### 问题 9：容器间数据共享验收失败

- **现象**：容器 B 读共享卷后，脚本匹配不到 `finqa-share-a`，判定「读取失败」。
- **原因**：`socket.gethostname()` 默认返回**容器 ID**（而非 `--name` 指定的名字），
  写入凭据里记录的是容器 ID，脚本按名称匹配自然失败。
- **解决**：演示容器显式指定 `--hostname finqa-share-a`（读写双方一致）。
- **验证**：容器 B 输出 `发现写入凭据: finqa-share-a`，验收 PASS。

### 问题 10：PowerShell 字符串插值误解析

- **现象**：验收输出显示 `问答容器与对端 RTMP 服务():1935`，`$PEER` 为空。
- **原因**：`"$PEER:1935"` 被 PowerShell 解析为**作用域变量** `$PEER:`，而非 `$PEER` + 字面量 `:1935`。
- **解决**：改用 `${PEER}:1935` 显式界定变量边界。
- **验证**：输出正确显示 `(finqa-peer:1935)`。

### 问题 11：`cmd /c` 被安全策略拦截

- **现象**：尝试用 `cmd /c "docker logs ..."` 获取纯净日志时被拦截。
- **解决**：改用 PowerShell 原生管道 `2>&1 | ForEach-Object { "$_" }` 采集日志文本。
- **验证**：日志文件内容干净、无包装噪声。

### 问题 12：冒烟测试单题未通过（Q01）

- **现象**：10 题中 Q01（「平安银行董事长致辞中提到的盈利增长关键因素有哪些？」）关键信息命中 0/3。
- **原因**：该题为**分析/归纳型**，答案散落在长篇「董事长致辞」叙事文本中，抽取式答案未能覆盖关键要点。
- **影响评估**：整体 **9/10 = 90%**，达到系统目标准确率 `TARGET_ACCURACY = 0.90`；
  其余数值型 / 比例型 / 列举型题目全部命中。
- **处置**：如实记录为已知局限，列入《优化报告》后续改进项（叙事型问题的答案合成增强）。

## 四、经验总结

1. **先探网络，再定构建策略**：构建环境网络受限时，`apt` 与镜像拉取都可能成为阻塞点；把「能用什么」探清楚再写 Dockerfile，可少走弯路。
2. **依赖最小化即是可移植性**：去掉运行期不需要的 opencv/matplotlib，不仅缩小镜像，更直接**移除了对系统库的依赖**，使「无 apt 构建」成为可能。
3. **健康检查不依赖外部工具**：用 Python 标准库 `urllib` 替代 `curl`，容器无需任何额外二进制。
4. **命名卷播种**：把知识库预置进镜像，首次创建卷时自动播种，兼顾「开箱即用」与「数据持久」。
5. **脚本编码要显式**：Windows PowerShell 5 读取 `.ps1` 依赖 BOM，含中文的脚本务必以 UTF-8 BOM 保存。
6. **验收脚本要覆盖真实细节**：容器名 vs 主机名、字符串插值等细节，往往就是「看起来对、实际失败」的根因。
