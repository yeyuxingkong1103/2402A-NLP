## 1. document.py — 文档处理

### `load_pdf(pdf_path) -> (list, list)`

解析 PDF，返回文字页列表与表格块列表。

| 参数 | 类型 | 说明 |
|---|---|---|
| `pdf_path` | str \| Path | PDF 文件路径 |

**返回**：`(text_pages, table_blocks)`

```python
text_pages   = [{"page": 22, "text": "中文名称 武汉兴图新科电子股份有限公司 ..."}]
table_blocks = [{"page": 221, "table": "| 项目 | 2018年度 |\n| --- | --- |\n..."}]
```

### `parse_pdf_tables(pdf_path) -> list[dict]`

只解析表格，转成 Markdown 字符串。

### `split_text(text, chunk_size=500, overlap=80) -> list[str]`

固定长度滑窗切分，优先在换行处断开（避免把金额数字切成两半）。

> 若 `overlap >= chunk_size` 会自动收敛为 `chunk_size - 1`，防止步长非正造成死循环。

### `build_chunks(text_pages, table_blocks) -> list[dict]`

合并为带页码与类型的块。

```python
[{"text": "...", "page": 22, "type": "text"},
 {"text": "| 项目 | ...", "page": 221, "type": "table"}]
```

---

### `parse_pdf_tables(pdf_path, junk_lines=()) -> list[dict]`

抽取表格并转成 Markdown，**同时带上表格上方的标题**。

```python
[{"page": 157,
  "caption": "(一)关联方及关联关系 1、存在控制关系的关联方",
  "table": "| 关联方名称 | 持股比例 | 与本公司关系 |"}]
```

> 工单3 的核心：表格单元格里没有「关联方」这个词，它在标题里。不带标题的表格块
> 会被文档里其它同类表格淹没。`junk_lines` 是页眉页脚行集合，由 `load_pdf` 传入。

### `company_name(pdf_path, head_pages=3) -> str`

从 PDF 开头几页提取发行人公司名（出现次数最多的「XX股份有限公司」），用于多文档路由。

## 1.5 image_parser.py — 图像内容解析（工单4 新增）

### `chart_pages(pdf_path, min_side=250) -> list[int]`

挑出含图表的页：有较大位图的页、出现「结构图/示意图/如下图」字样的页，
**以及这些页的下一页**（图常被放在引言之后）。返回页码升序列表。

### `describe_page(pdf_path, page_no, retry=2) -> str`

把该页渲染成 PNG，交给多模态模型转写成文字（组织结构图写层级、统计图写数值与极值）。

### `parse_pdf_images(pdf_path, limit=40, progress=None, cache_dir=None) -> list[dict]`

带缓存的入口。返回可直接入库的块：

```python
[{"page": 39, "type": "image", "text": "【第39页 图表】销售部下属：电话及网络销售部……"}]
```

> 缓存按**页**增量维护（`kb_cache/<文档名>_images.json`）。选择规则变宽或某页
> 因网络抖动失败时，重跑只补解析缺的页 —— 实测约 18 秒/页，全量重跑代价高。

## 1.6 dialogue.py — 多轮对话（工单5 新增）

### `Conversation(companies=None)`

一次会话的上下文。`companies` 是已加载文档对应的公司名 —— 主体识别只认这些，
避免把「国信证券股份有限公司」这类中介机构当成提问主体。

| 方法 | 说明 |
|---|---|
| `.resolve(question)` | 把带指代/省略的问句改写成自足问题，返回 `{"resolved", "strategy", "company"}` |
| `.add_turn(question, resolved, answer)` | 记录一轮对话 |
| `.reset()` | 清空上下文（界面「清空对话」按钮调用） |
| `.size` | 已记录轮数 |
| `.current_company` | 当前话题主体 |

改写策略按优先级：

| 优先级 | 策略 | 例子 |
|---|---|---|
| ① | 省略补全 | 「那武汉力源…呢？」→「武汉力源…**的法定代表人是谁**？」 |
| ② | 原样 | 问题已点明公司名 |
| ③ | 指代消解 | 「**他**参与的哪个工程…」→「**武汉兴图新科…**参与的哪个工程…」 |
| ④ | 话题延续 | 既无公司名也无代词时补上当前主体 |

## 2. query_understanding.py — Query 理解

### `understand(question) -> dict`

规则实现，耗时接近于 0（不调用大模型）。

| 返回字段 | 类型 | 说明 |
|---|---|---|
| `lang` | str | `zh` / `en`，用于选择提示词语种 |
| `intent` | str | 数据查询 / 事实查询 / 关系查询 / 比较查询 |
| `ambiguous` | list[str] | 命中的歧义词，如 `["报告期", "注册资本"]` |
| `clarifications` | list[str] | 歧义词的澄清说明 |
| `rewrite` | str | 补全澄清说明后的检索用查询（仅用于检索） |
| `sub_questions` | list[str] | 拆出的子问题，拆不开则为 `[]` |
| `entities` | list[str] | 提取到的实体 |
| `numbers` | list[str] | 提取到的数字 |

### `detect_lang(text) -> str`

含中日韩字符返回 `zh`，否则返回 `en`。

## 3. vector_store.py — 向量检索

### `BGEM3VectorStore(model_path=None, use_fp16=True)`

构造时加载本地 BGE-M3（自动使用 GPU，若无则回退 CPU）。

### `.build(chunks, batch_size=16) -> None`

对全部块编码，建立索引。

### `.search(query, top_k=5) -> list[tuple[dict, float]]`

混合检索。返回 `[(chunk, score), ...]`，按相关性降序。

> 融合方式为 RRF（Reciprocal Rank Fusion）：分别把稠密分与稀疏分转成名次，
> 按 `权重 / (60 + 名次)` 相加。不直接相加分数，避免两种分数量纲不同导致
> 稀疏分靠一次偶然的词汇重叠顶掉语义分。

### `.save(out_dir) -> None` / `.load(in_dir) -> bool`

知识库持久化与加载。落盘文件：`dense.npy`、`chunks.json`、`sparse.json`。

## 4. rag_engine.py — 答案生成

### `chat(prompt, system=..., temperature=0.0, max_tokens=1024, timeout=30) -> str`

大模型调用封装。

> 失败时**抛出 `LLMError`**，不返回错误文案——否则错误信息会被当成答案一路传到界面和评估模块。

### `RAGEngine(vector_store, top_k=5)`

### `.answer(question, use_query_understanding=True) -> dict`

完整 RAG 链路。

| 返回字段 | 说明 |
|---|---|
| `answer` | 答案文本 |
| `contexts` | `[(chunk, score), ...]`，检索到的上下文 |
| `elapsed` | 端到端耗时（秒） |
| 其余字段 | 透传 `understand()` 的结果 |

### `.answer_without_rag(question) -> dict`

纯 LLM 回答，不检索。用于工单要求的对比分析。

---

### `rerank(query, candidates, top_k=8, max_chars=400) -> list`

交叉编码器重排序（`vector_store.py`）。对候选逐对打分后取前 `top_k`。

| 参数 | 说明 |
|---|---|
| `candidates` | `[(chunk, score), ...]`，来自 `search()` 的召回结果 |
| `max_chars` | 送检正文长度上限。模型只看 512 token，截断可显著提速（1.0s → 0.5s） |

> 由 `config.RERANK_ENABLED` 控制是否启用，**默认关闭**。实测在本任务的
> 财务表格上为负收益，详见 `优化/优化方案与对比.md`。

## 5. evaluator.py — RAG 评估

### `evaluate(engine, questions=None) -> list[dict]`

对每个问题分别跑 RAG 与纯 LLM，并用 LLM 裁判打分。

| 字段 | 说明 |
|---|---|
| `rag_score` / `plain_score` | `{"grounded": 0/1, "relevant": 0/1, "reason": str}` |
| `rag_cited` / `plain_cited` | 是否引用了页码 |
| `rag_elapsed` / `plain_elapsed` | 耗时（秒） |
| `pages` | 检索命中的页码 |

### `report(rows) -> str`

把明细汇总成可直接写入文档的评估报告。

### `main(pdf_path)`

命令行入口：`python evaluator.py [PDF路径]`，结果写入 `eval_result.json`。

## 6. rag_engine.py 中的多文档引擎

### `MultiDocEngine()` — 工单3 新增

同一套系统里挂载多份文档的知识库，按问题里的公司名路由。

| 方法 | 说明 |
|---|---|
| `.add(company, engine)` | 挂载一份文档的知识库 |
| `.route(question)` | 按公司名匹配；全称没命中时退化为前 4 字简称；都没命中返回全部 |
| `.answer(question)` | 单库命中直接作答；多库命中则合并各库上下文后统一生成 |
