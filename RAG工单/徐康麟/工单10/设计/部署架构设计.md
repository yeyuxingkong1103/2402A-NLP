## 2. 容器清单与职责

| 服务 | 镜像 | 启动命令 | 端口 | 职责 | 关键依赖 |
| --- | --- | --- | --- | --- | --- |
| `rag-api` | `rag-finqa:1.0.0` | `uvicorn service.api:app --host 0.0.0.0 --port 8200` | **8200** | **正式对外 API**：`POST /api/v1/ask`、`/health`、`/metrics` | Redis（健康后启动）、Ollama、索引卷 |
| `rag-ui` | 同一镜像 | `python /app/app/main.py --serve --host 0.0.0.0 --port 8201` | **8201** | 工单7 中文 Web 界面（人机对话入口） | 同上（同一份索引、同一份会话卷） |
| `redis` | `redis:7-alpine` | `redis-server --appendonly yes --requirepass …` | 6379 | 会话/缓存**跨容器共享**的第二通路 | 卷 `rag-redis` |
| `prometheus` | `prom/prometheus:v2.55.1` | 默认 | 9090 | 指标采集（profile `monitoring`，默认不起） | `rag-api:8200/metrics` |

> **一个镜像两个服务**：`rag-ui` 不重新构建镜像，只是换 `command`。这样保证 UI 与 API
> 跑的是**同一份业务代码、同一份索引、同一份会话卷**，从根上避免"两边行为不一致"。

## 3. 分层设计（为什么这样切）

```
┌─────────────────────────────────────────────────────────────────┐
│  接入层    rag-api(FastAPI)  │  rag-ui(标准库 HTTP 界面)          │  ← 只做协议/会话/限流，不含 RAG 逻辑
├─────────────────────────────────────────────────────────────────┤
│  部署层    service/config.py（DEPLOY_* 环境变量）                │  ← 端口/卷/会话后端/阈值，全部可配
│           service/session_store.py（Redis + 文件卷双写）          │
├─────────────────────────────────────────────────────────────────┤
│  业务层    app/core/qa_engine.py 等（**工单7 原样复用**）         │  ← 解析/分块/嵌入/FAISS/BM25/RRF/重排/护栏
├─────────────────────────────────────────────────────────────────┤
│  依赖层    Ollama（宿主）│ Redis（编排内）│ 卷（索引/日志/会话）  │  ← 外部能力一律"可降级"
└─────────────────────────────────────────────────────────────────┘
```

**核心纪律：业务逻辑零复制。** `研发/app` 是从工单7 原样 `robocopy` 过来的同一批文件，
`研发/service` 只做三件事：**暴露 HTTP 协议、管会话落盘、报健康**。
这样工单7 的任何修复都能通过重新拷贝 `app/` 直接继承。

## 4. 关键设计决策与理由

| # | 决策 | 备选方案 | 为什么选它 |
| --- | --- | --- | --- |
| D1 | 嵌入/生成走**宿主机 Ollama** | 容器内装 torch + 模型权重 | 镜像从 ~3GB 降到 ~300MB 级；本机 GPU/内存资源不重复占用；换模型不动镜像（真实数字见 `优化/部署优化说明.md`） |
| D2 | **一个镜像两个服务** | api/ui 两个 Dockerfile | 单一构建产物，版本天然一致；减少构建时间与镜像存储 |
| D3 | 索引**只读挂载** | 读写挂载 | 索引是构建产物，运行期不需要写；只读挂载同时防止运行期写坏索引 |
| D4 | 运行期 sqlite 独立到 `rag-runtime` 卷 | 写进索引目录 | 索引目录只读（见上），写进去在容器里必然 `EROFS` 失败 |
| D5 | 会话**双写**（Redis + 文件卷） | 只用 Redis 或只用文件 | Redis 提供实时跨容器共享；文件卷保证"拔掉 Redis 数据也不丢"（验收要求"数据不丢失"） |
| D6 | `HEALTHCHECK` 探 `/healthz` | 探 `/health` 或 `/readyz` | `/healthz` 不碰索引，避免索引加载慢导致容器被编排系统误杀；就绪判断交给 `/readyz` |
| D7 | `--start-period 90~150s` | 用默认 0s | 基座实测冷启动 **27.3 秒**（全文索引 20.1s + 实体标注 2.1s + 索引载入），默认值会让容器被判不健康 |
| D8 | 不写顶层 `version:` | 写 `version: "3.8"` | Compose V2 已废弃该字段并打印 obsolete **警告** —— 而验收要求"运行过程无异常日志输出" |
| D9 | `--no-access-log`（uvicorn 访问日志关掉） | 保留 | 业务侧已有 JSON 结构化 `http.request` 日志，重复记录只会淹没日志；且 uvicorn 访问日志噪声大 |
| D10 | 网络用自定义 bridge + 固定子网 | 默认 bridge | 默认 bridge 无服务名 DNS；固定子网避免与公司网段/其它编排冲突 |

## 5. 启动时序（含健康门控）

```
docker compose up -d
   │
   ├─▶ redis 启动 ──► HEALTHCHECK redis-cli ping ──► healthy
   │                                                   │
   ├─▶ rag-api 启动 ◀──── depends_on: service_healthy ─┘
   │      │
   │      ├─ entrypoint.sh：目录体检（logs/sessions/uploads 写探针）→ 写容器启动快照
   │      ├─ uvicorn → lifespan → Runtime.setup()
   │      │     ├─ get_config()（RAG_* 环境变量 → AppConfig）
   │      │     ├─ SharedSessionStore（Redis 探测；失败→文件卷降级）
   │      │     ├─ SqliteManager(runtime 卷/qa_runtime.sqlite3)
   │      │     └─ QAEngine.warmup(with_generate=False)   ← 实测 ≈27.3 s
   │      └─ HEALTHCHECK → /healthz (start-period 120s 内允许不健康)
   │
   └─▶ rag-ui 启动（同样 depends_on redis healthy）
          └─ main.py --serve → QAEngine（同一份索引）→ /health
```

## 6. 故障域与降级矩阵

| 故障 | 影响 | 自动行为 | 观测点 |
| --- | --- | --- | --- |
| Redis 挂 | 无（会话仍可用） | 连续失败 3 次 → 熔断 30s → 全程走文件卷；`backend=file` | `/health` → `checks.session_store.backend` |
| Ollama 挂 | 生成退化 | 走确定性抽取合成器（`generation_method=rule_composer`），答案事实一致仅少润色 | 答案里的 `backend` 字段 |
| 索引卷未挂 | 服务不能答 | 服务照常启动；`/health` 报 `engine.ok=false`；`/readyz` 返回 503 | `/health` → `checks.volume_index` |
| 运行期卷不可写 | 历史不落盘 | 问答**继续可用**，仅不记历史（显式 WARNING 日志） | `/health` → `checks.volume_runtime` |
| 日志卷不可写 | 无 | entrypoint 直接退出（exit 78）—— 日志是验收证据，不能悄悄丢 | 容器退出码 78 |
| 单请求异常 | 单请求失败 | 异常兜底 handler → 500 JSON + ERROR 日志（不裸崩） | `部署/日志/` 里 `http.unhandled` |

## 7. 与"服务器部署"的对应关系

原文说"部署**在服务器中**"。本机的 Docker Desktop 即等价于一台 Linux 服务器：
compose 文件里的路径、卷、网络、资源限制都是**平台无关**的。迁到真实 Linux 服务器只需：

1. 把 `工单10/` 整个目录拷到服务器（或只拷 `部署/` + `研发/`）；
2. 把索引放到服务器某路径，改 `HOST_INDEX_DIR`；
3. `RAG_LLM__OLLAMA_BASE_URL` 改成服务器能访问到的 Ollama 地址（同机 `172.17.0.1:11434` 或内网 IP）；
4. `docker compose --env-file 部署/配置/.env up -d --build`。

> Linux 上 `host.docker.internal` 需靠 `extra_hosts: host-gateway`（compose 里已声明），
> 这也是本设计**不依赖 Docker Desktop 特性**的原因。
