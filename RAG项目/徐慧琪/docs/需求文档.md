## 一、项目背景

### 1.1 业务背景

律师在办案过程中需要频繁检索法律依据。传统方式依赖人工翻阅法典、检索商业数据库或凭记忆引用法条，存在五类问题：

| 编号 | 问题 | 表现 | 造成的后果 |
|---|---|---|---|
| B-1 | 效率低 | 逐条翻找法条耗时，翻目录、翻数据库 | 打断办案思路，检索时间挤占分析时间 |
| B-2 | 易出错 | 法条修订频繁，人工难以保证引用的是现行有效版本 | 可能出现新旧法混用、引用已废止或未生效条文 |
| B-3 | 经验难复用 | 已办案件的经验散落在个人手中 | 无法沉淀为团队可检索的资产，人员变动即断层 |
| B-4 | 数据敏感 | 案卷涉及当事人隐私与商业秘密 | 不能使用公网 AI 工具处理，效率与合规两难 |
| B-5 | 普通人求助难 | 普通人在租房、网购、劳动、借贷、婚姻家庭等纠纷中，不清楚适用哪条法律；网上搜到的说法真假难辨、彼此矛盾 | 要么花高价咨询，要么凭错误认知行事，可能错过时效或做错选择 |

### 1.2 项目目标

构建一套私有化部署的法律 RAG 检索系统，实现三件事：

| 编号 | 目标 | 说明 | 对应验收 |
|---|---|---|---|
| G-1 | 可核对、可溯源的法条检索 | 律师用自然语言提问，系统精准返回现行有效的法条原文，可核对、可溯源 | AC-1~AC-8、AC-12、AC-13 |
| G-2 | 经验资产化 | 将已办案件/卷宗脱敏入库，作为可检索的经验资产辅助办案 | AC-9 |
| G-3 | 全本地运行、数据不出内网 | 全流程本地运行，不调外部 API，满足律所保密与合规要求 | AC-15、AC-16 |
| G-4 | 普通人也问得明白 | 普通用户（公网匿名访问，不采集个人信息）用大白话描述问题，系统给出相关法条原文 + 通俗解释 + 初步处理建议 + 推荐律师与律师费用区间参考，并明示这只是法律信息、不是正式法律意见 | AC-17~AC-21 |

### 1.3 建设范围

**一期（核心，律师侧）**：法条库（民法典 + 常用司法解释）结构化入库 + 混合检索 + 可验证引用生成。

**一期（公众侧，v1.1 新增）**：面向普通用户的**公网**问答入口（匿名、不采集个人信息）——普通用户用自然语言描述问题，系统基于公开法条库给出法条依据 + 通俗解释 + 初步处理建议 + 推荐律师与律师费用区间参考，并强制附风险提示与免责声明（FR-8、FR-9）。公众侧只读公开法条库，不涉及任何案卷/类案数据。

**二期（辅助）**：类案/卷宗脱敏入库 + 法条—类案关联检索。

**本期不包含**：跨法域（刑法、行政法）覆盖、多租户 SaaS、移动端、个案代理意见与胜诉预测、线上委托成交与线上收费。

> 范围解读：一期的成败标准是"每一条引用都能被律师一键核对到原文"；二期才引入"经验资产"这条价值链。二期功能（FR-5）中标注为 P0 的条目（FR-5.1 脱敏入库、FR-5.4 脱敏后仍可检索）是二期上线门槛，但**脱敏规则与数据字段需在一期预留**，否则二期要改造已入库数据。

## 二、用户角色

### 2.1 角色总览

> 角色数量：**四类**（普通用户、主办律师、助理、合伙人（管理员））。合伙人角色同时承担系统管理职责（部署、法规更新、用户与权限管理、审计）；普通用户为公众咨询者，只面向公开法条库提问，不接触任何案件数据。

| 角色 | 描述 | 核心诉求 | 使用频率 |
|---|---|---|---|
| 主办律师 | 主要使用者，办案中查询法条、参考类案 | 快速、准确、可核对地拿到有效法条 | 高频 |
| 助理 | 辅助检索、整理法条与案例 | 降低检索门槛，快速上手 | 高频 |
| 合伙人（管理员） | 关注知识沉淀与合规，并负责部署、更新法规、权限管理 | 经验资产化、数据安全、审计可查、易部署易维护 | 低频（业务）／中频（管理） |
| 普通用户 | 遇到纠纷的普通人（租房、网购、劳动、借贷、婚姻家庭等场景），以公众身份提问 | 用大白话问清"我这事法律上怎么说""我该怎么做"，并拿到可核对的法条依据 | 中低频（按需） |

### 2.2 角色画像

**主办律师（主要用户）**

- 使用场景：开庭前或写文书时，需要确认某个争议点的法条依据、条款号与现行有效版本。
- 关键诉求：①一句话提问就能拿到条款号和原文；②每条引用能一键跳到原文核对；③不要"看起来对但查无此条"的答案。
- 关键约束：办案时间碎片化，不接受需要学习的检索语法；引用格式要能直接写进文书（FR-7.4）。
- 对开发的含义：答案区必须把"法条原文"与"AI 解读"视觉分开（FR-4.4），因为律师要引用的是原文。

**助理**

- 使用场景：按律师指令批量检索法条、整理类案、汇总依据。
- 关键诉求：①口语提问也能命中；②结果可复制、可整理；③"第584条"这类精确条款号能直达（FR-3.2）。
- 关键约束：经验不足，最容易被编造的条文误导 —— 所以生成层必须有引用回查校验（FR-4.3、AC-6）。
- 对开发的含义：拒答话术必须说清"为什么没查到"，否则用户会反复追问并尝试绕过。

**合伙人（管理员）**

- 使用场景（业务侧）：关注知识沉淀与合规，查看审计台账与检索质量；不定期确认系统输出是否可用于所内办案。
- 使用场景（管理侧）：部署系统、更新法规版本、维护用户与权限、处理故障、执行备份。
- 关键诉求：①案卷与检索记录不出内网；②老案子能被检索复用；③谁查了什么有记录；④单机一键部署、法规增量更新不需重建全库、Embedding/LLM/Rerank 可插拔替换、命中率与拦截率与延迟可观测。
- 关键约束：非算法专家（一般也不写代码），运维动作必须能在文档支持下独立完成。
- 对开发的含义：①审计日志的完整性（AC-11）与合规验收（AC-15/AC-16）是给这一类角色看的证据；②管理动作须全部可在网页完成，运维须有可独立运行的脚本。

**普通用户（公众咨询者，v1.1 新增）**

- 使用场景：遇到具体纠纷或困惑（如租房押金不退、网购到假货、被拖欠工资、借款不还、婚姻家庭纠纷）时，想知道法律上怎么规定、自己有哪些权利、下一步该做什么；需要找律师时，希望能看到推荐律师与费用区间参考。访问方式：公网直接打开，不注册、不填个人信息。
- 关键诉求：①不懂法律术语也能提问（用大白话）；②答案里要看得见法条原文并能核对，不接受"AI 说"；③要看得懂——给通俗解释，并说清这只是法律信息、不是正式法律意见；④公网直接用，不用注册登录（FR-9.1）；⑤要找律师时，能看到推荐律师与对应费用区间参考（FR-9.3、FR-9.4）。
- 关键约束：法律知识不足，最容易被"看起来很权威"的答案误导，也容易把系统输出当成正式意见——因此：不得访问任何案卷数据；输出必须带法条出处（FR-4.2）、必须带风险提示（FR-8.4）、不得出具个案代理意见或胜诉预测（FR-8.3）；另外，系统对普通用户只开放**查询（只读）**能力——可提问、检索、查看法条原文与回答，不可上传、编辑、删除、导出任何数据（FR-8.7）；公众侧匿名访问，不采集、不留存任何个人信息（FR-9.1）。
- 对开发的含义：①公众侧与律师侧数据严格隔离（FR-6.1、AC-19），越权可见案卷按泄密处理；②通俗解释与法条原文必须视觉分开（FR-4.4），否则用户会把解释当法条往外转述；③问询信息不足时先反问补齐（FR-8.5），不能靠猜测给结论；④公网入口必须防滥用（限流、防爬、防注入），否则单机资源会被刷爆并拖垮律师侧可用性（FR-9.2、AC-20）；⑤推荐律师与费用区间只是信息指引，不能演变为付费插位或变相报价（FR-9.5、AC-21）。

### 2.3 权限与数据可见性（依据 FR-6.1、FR-6.2 定稿）

| 能力 | 主办律师 | 助理 | 合伙人（管理员） | 普通用户 |
|---|---|---|---|---|
| 自然语言检索法条 | ✅ | ✅ | ✅ | ✅（**仅《民法典》公开法条**，不可查历史案件） |
| 查看引用原文并跳转 | ✅ | ✅ | ✅ | ✅ |
| 操作性质 | 查询为主（写操作受所内授权控制） | 查询为主 | 查询 + 管理（写） | **仅查询（只读），无任何写操作** |
| 注册与信息留存 | 所内账号 | 所内账号 | 所内账号（管理员） | ❌ 匿名访问，无需注册；不采集、不留存任何个人信息 |

| 检索类案/卷宗（二期） | ✅（本人参与案件） | ✅（受授权范围） | ✅ | ❌ |
| 跨团队案件可见性 | 团队内（FR-6.2：团队级隔离） | 团队内 | 团队内（管理范围内） | ❌（不可见任何案件数据） |
| 查看审计日志 | ❌ | ❌ | ✅ | ❌ |

| 系统部署与故障处理 | ❌ | ❌ | ✅ | ❌ |

> 本表为按 FR-6.1、FR-6.2、FR-6.3、FR-6.4 推导并已定稿的权限口径。普通用户列只覆盖公众侧对公开法条库的只读问答，不得延伸到 FR-5 的类案/卷宗数据；该隔离由 AC-19 验证。公众侧入口已定为**公网匿名入口**（见 7.1、FR-9.1），故普通用户不注册、不留存任何个人信息。

## 三、用户痛点

### 3.1 痛点清单

| 编号 | 痛点 | 现状 | 期望 | 对应需求 |
|---|---|---|---|---|
| P1 | 法条引用不可信 | 通用 AI 会编造不存在的法条 | 每条引用可一键核对原文 | FR-4.2、FR-4.3、FR-7.2 |
| P2 | 新旧法混用 | 检索到已废止/未生效条文 | 默认只返回现行有效版本 | FR-1.5、FR-3.3、FR-3.7 |
| P3 | 条款号检索难 | 语义检索召不回"第584条" | 精确条款号直达 | FR-3.2 |
| P4 | 条文脱离上下文 | 只给一款，理解有歧义 | 命中款的同时给出整条 | FR-2.1、FR-3.5 |
| P5 | 案卷不能上公网 | 无法用在线 AI 处理 | 全本地私有化部署 | FR-6.1、NFR 5.2 |
| P6 | 经验无法复用 | 老案子躺在硬盘里 | 脱敏后可检索、可关联法条 | FR-5.1、FR-5.3、FR-5.4 |
| P7 | 检索打扰办案 | 翻目录、翻数据库耗时 | 自然语言提问，秒级返回 | FR-3.1、FR-7.1、5.1 |
| P8 | 合规审计缺失 | 谁查了什么无记录 | 操作日志可追溯 | FR-6.3、FR-6.4 |
| P9 | 普通人不知道"这事归哪条法律管" | 只能靠搜索引擎或短视频里的零散说法，真假难辨、彼此矛盾，且常引用未生效或已废止条文；即便知道该找律师，也不清楚该找谁、大概要花多少钱 | 用大白话提问，就能拿到带条款号与原文出处的法律依据，并附通俗解释与初步处理建议；需要时还能看到推荐律师与费用区间参考 | FR-8.1~FR-8.7、FR-9.1~FR-9.5 |

### 3.2 痛点优先级

- **底线类（不满足即不可上线）**：P1（法条引用不可信）、P2（新旧法混用）、P5（案卷不能上公网）。
- **主要痛点（本期核心价值）**：P3、P4、P7、P8。
- **二期痛点**：P6。
- **公众侧痛点（v1.1 新增）**：P9——其中"引用可核对、不得编造、不得出具个案代理意见"按底线类标准执行（与 P1 同一红线），口语化理解与追问引导按 P1 执行。

> 说明：P1 是本项目的**立项理由**——如果答案里的法条可能被编造，律师就必须逐条手工复核，系统省下的时间等于零。因此 FR-4.3（生成后回查校验）与 AC-6（幻觉拦截率 100%）优先于任何体验优化。

## 四、功能性需求

> 优先级定义：**P0 = 本期必做（不达标不上线）**；**P1 = 本期应做（可在迭代内补齐）**。
> 每组需求后附"落地要点"说明实现口径与易踩的坑；"验收要点"列说明"怎么算做到"。

### 4.1 法条库建设（FR-1）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-1.1 | 支持将民法典及司法解释按编—章—节—条—款—项结构化入库 | P0 | 抽检任意条款，层级路径与条款号与原文本一致 |
| FR-1.2 | 每条法条记录包含：法律名称、版本、条款号、编章节路径、原文、生效日期、效力状态、被替代关系 | P0 | 任一字段可查且非空；被替代关系可双向查看 |
| FR-1.3 | 支持法条版本管理，保留历史版本及修订记录 | P0 | 可查询某条的历次版本与修订时间 |
| FR-1.4 | 支持法条增量更新，更新时同步父子块与元数据 | P0 | 更新单条后，该条父块/子块与元数据同步变化，全库不重建 |
| FR-1.5 | 支持标记效力状态：现行有效 / 已废止 / 待生效 | P0 | 三种状态可标注，并可作为检索过滤条件 |

**落地要点**：

- FR-1.2 的"被替代关系"是解决 P2（新旧法混用）的基础——没有这条关系，系统只能知道"某条废止了"，无法告诉律师"现在应看哪一条"。
- FR-1.4 的"同步父子块"与 4.2 的父子切分强耦合：更新一条法条时，子块的向量必须一并重建，否则会出现"元数据是新的、向量是旧的"这类静默错误。

### 4.2 切分与向量化（FR-2）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-2.1 | 法条采用层级对齐父子切分：条为父块，款/项为子块 | P0 | 结果中可见父块（整条）与子块（款/项）的对应关系 |
| FR-2.2 | 子块（款/项）生成 embedding，父块（整条）用于上下文 | P0 | 命中在子块粒度，交给生成层的是父块整条 |
| FR-2.3 | 超长条文（单条 > 800 字或单款 > 500 字）按句/分号切叶块，叶块回指同款 | P1 | 超长条文被切分且叶块能回溯到所属款 |
| FR-2.4 | 法律文本切分 overlap 设为 0，避免重复引用 | P0 | 分块结果无重叠内容 |
| FR-2.5 | 子块携带精确路径元数据：article_no、paragraph_no、item_no | P0 | 元数据字段齐全，可用于精确引用与过滤 |
| FR-2.6 | 类案按争议焦点/逻辑段落切分，携带案由、适用法条元数据 | P1 | 类案片段带案由与适用法条，可反向关联 |

**落地要点**：

- **层级对齐切分是本项目与通用 RAG 最大的差异**：通用 RAG 切出的是"文本块"，法条切出来必须是"第X条第Y款"，因为律师需要的是**可引用的单元**。这也是 7.2 技术边界中"法条禁用纯语义切分"的原因。
- overlap=0（FR-2.4）与常规 RAG 经验相反，但法律文本条款边界天然清晰，重叠只会造成同一款被重复引用。

### 4.3 检索能力（FR-3）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-3.1 | 支持混合检索：BM25 关键词 + 向量语义 | P0 | 两路召回均生效；口语与术语问法都能命中 |
| FR-3.2 | 支持精确条款号命中（如"584""第584条"直接定位） | P0 | 输入"第584条"准确返回该条，准确率 100%（AC-2） |
| FR-3.3 | 支持元数据过滤：按法律名称、效力状态、生效日期过滤 | P0 | 三类过滤条件可组合生效 |
| FR-3.4 | 支持法律术语同义词/别名映射（如"违约金"↔"损害赔偿"） | P1 | 同义词表可维护；同义词提问能命中对应法条 |
| FR-3.5 | 检索命中子块后，按 parent_id 聚合去重，取回父块整条 | P0 | 同一父块多个子块命中时只返回一次父块 |
| FR-3.6 | 支持 Rerank 精排：召回 top 20–50，精排后取 top 3–5 | P0 | 精排前后顺序可对比；top3 含正确答案 ≥ 85%（AC-4） |
| FR-3.7 | 支持按案件发生时间匹配当时适用的法律版本（法不溯及既往） | P1 | 给定案件时间，返回当时有效版本 |
| FR-3.8 | 默认只检索法条；用户显式切换或系统判断需要时才检索类案 | P1 | 默认结果集不含类案；切换后可含类案 |

**落地要点**：

- FR-3.2 不能只靠向量相似度实现，必须**条款号抽取 + 元数据精确匹配**作为独立通路，否则"第584条"会被语义检索稀释。
- FR-3.5 与 FR-2.1/FR-2.2 是一套机制的两端：子块负责"被找到"，父块负责"被理解"。缺了父子回填，P4（条文脱离上下文）无法解决。
- FR-3.7（法不溯及既往）隐性要求 FR-1.2 的"生效日期 + 版本"与 FR-1.3 的"历史版本"先建好，属依赖前置的 P1。

### 4.4 生成与引用（FR-4）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-4.1 | 基于检索结果生成回答，仅允许基于召回内容作答 | P0 | 答案内容可在召回片段中找到对应依据 |
| FR-4.2 | 每条结论强制附带条款号与原文出处，精确到款/项 | P0 | 每条结论均带条款号；款/项级定位可核对 |
| FR-4.3 | 生成后回查校验：引用条款须真实存在且现行有效，否则拦截重生成 | P0 | 构造不存在的条款号，系统拦截且不输出（AC-6） |
| FR-4.4 | 明确区分"法条原文"与"AI 解读"，视觉上分开呈现 | P0 | 界面上原文与解读有清晰视觉区分 |
| FR-4.5 | 生成参数低温度（0–0.2），不发挥、不文学化 | P0 | 生成参数可查；输出风格稳定无修辞性发挥 |
| FR-4.6 | 未检索到依据时，明确回答"未找到相关依据"，不编造 | P0 | 库外问题不出现任何法条引用 |

**落地要点**：

- **FR-4.3 是本系统的安全阀**：它把"信任模型"变成"校验模型"——不指望模型不犯错，而是让每一次引用都必须通过**独立校验通路**（直接查库核对条款号存在性与效力状态，而不是再问一次模型）。
- **FR-4.4 是执业风险的隔离带**：律师写进文书的是法条原文，AI 解读只是参考。两者若在视觉上混同，一旦解读偏差，责任边界即模糊。
- 低温度（FR-4.5）配合 FR-4.1，目标是"抄得准"而不是"答得漂亮"。

### 4.5 类案/经验库（FR-5，二期主体，一期预留）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-5.1 | 支持案卷/判决书脱敏后入库（姓名、身份证、账号、联系方式等） | P0 | 脱敏后入库文本无上述敏感信息残留（AC-9） |
| FR-5.2 | 结构化提取：案由、争议焦点、裁判要旨、适用法条、代理思路 | P1 | 五类字段可提取且可查询 |
| FR-5.3 | 支持法条—类案双向关联：查法条可见相关案例，查案例可反查法条 | P1 | 两个方向的关联均可查询 |
| FR-5.4 | 脱敏后保留法律特征，保证可检索性 | P0 | 脱敏前后检索命中率无显著下降（AC-9） |

**落地要点**：

- FR-5.1 与 FR-5.4 是一对张力：**脱敏要够彻底，但过度脱敏会丢掉可检索的法律特征**（如把主体统一替成"XX公司"后，主体类型信息消失）。建议**分类替换**（人名→当事人A、公司→某公司、金额保留区间）而非统一打码，并在评估集中专门覆盖脱敏后的检索效果。
- 建议一期即确定脱敏规则表与字段结构，避免二期改造一期已入库数据。

### 4.6 权限与审计（FR-6）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-6.1 | 支持用户/团队细粒度权限，仅可检索有权访问的案件 | P0 | 越权访问被拒绝，隔离测试 100% 通过（AC-10） |
| FR-6.2 | 支持所内团队级数据隔离（不同团队数据互不可见，非 SaaS 多租户） | P1 | 跨团队数据不可见 |
| FR-6.3 | 记录操作日志：谁、何时、查了什么、召回路径 | P0 | 日志含四要素；可回溯一次问答的召回路径（AC-11） |
| FR-6.4 | 日志支持审计导出 | P1 | 可按时间范围导出 |

**落地要点**：

- FR-6.3 的"召回路径"是排障与质量改进依据：出问题时需能看出"这条答案由哪几个片段拼出"。
- FR-6.2 的口径已统一为"**所内团队级数据隔离**"（非 SaaS 多租户），与 7.1"单律所/单团队内网使用"一致：隔离的对象是**所内不同团队的案件数据**，不对外提供多租户 SaaS 形态。

### 4.7 前端交互（FR-7）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-7.1 | 自然语言提问框，秒级返回 | P0 | 提问后 P95 < 2s 出检索结果（见 5.1） |
| FR-7.2 | 回答中引用可一键跳转法条原文 | P0 | 跳转准确率 100%（AC-5） |
| FR-7.3 | 支持按编章节导航浏览法条 | P1 | 编—章—节—条可逐级浏览并定位 |
| FR-7.4 | 生成内容支持一键复制（带条款号，便于写入文书） | P1 | 复制内容自带规范条款号引用格式 |

**落地要点**：

- FR-7.4 是"好不好用"的分水岭：律师的最终动作是把依据写进文书，复制出来的文本若还要手工补条款号，工具价值即打折。
- FR-7.2 与 FR-4.2 是一体两面：能跳转的前提是引用精确到款/项且库内定位准确。

### 4.8 面向普通用户的法律问答（FR-8，v1.1 新增）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-8.1 | 提供普通用户提问入口：用自然语言（口语、大白话）描述纠纷或困惑即可提问，无需法律术语 | P0 | 口语化问题可直接发问并获得回答，无需指定法条或条款号 |
| FR-8.2 | 回答须给出与该问题相关的法条原文（条款号 + 出处）且可一键核对，在此基础上再给通俗解释 | P0 | 公众侧引用准确率 ≥ 95%，编造/失效法条拦截率 100%（AC-17） |
| FR-8.3 | 输出限定为一般性法律信息：不出具个案代理意见、不预测胜诉输赢、不替用户下结论 | P0 | 构造"你帮我打官司能赢吗"类提问，系统不给出结论性判断（AC-18） |
| FR-8.4 | 每条回答强制附风险提示与免责声明，并区分"法条原文"与"AI 解读" | P0 | 输出 100% 带免责声明（AC-18） |
| FR-8.5 | 信息不足时先反问补齐关键事实（时间、地点、身份、证据等），不凭猜测作结论 | P1 | 含糊提问会先追问关键要素再作答 |
| FR-8.6 | 非法律问题、情绪化或紧急情形（如人身安全受威胁）不硬答，给出引导话术与线下求助渠道建议 | P1 | 非法律/紧急提问不输出法条结论 |
| FR-8.7 | 普通用户仅有**查询（只读）**权限：只能提问、检索、查看法条原文与回答，不提供上传、编辑、删除、导出等任何写操作入口 | P0 | 公众侧界面上不存在写操作入口；构造写操作请求（上传/编辑/删除/导出）100% 被拒绝（AC-19） |

**落地要点**：

- 公众侧与律师侧**共用同一套法条库、检索与引用校验通路**（FR-3、FR-4），差别只在入口、可见数据范围、可做的操作（普通用户仅查询，只读，FR-8.7）与表达语气；**公众侧不得触达任何案卷/类案数据**（FR-5），这是 AC-10、AC-19 的硬边界。
- FR-8.3 与 FR-4.3 是两条不同的红线：FR-4.3 管"答得准不准"（不编法条），FR-8.3 管"能不能答"（不给个案结论）。两条都靠**规则约束 + 输出校验**落地，不依赖模型自觉。
- 公众侧是一条**只读查询通道**（FR-8.7）：不提供上传、编辑、删除、导出入口，避免公众问答变成数据写入或信息外带的新通道；权限校验须在**服务端按角色收口**，不能只靠前端隐藏按钮。
- 通俗解释必须与法条原文在视觉上分开（沿用 FR-4.4），否则普通用户会把"解释"当成法条原文转述出去。
- 公众侧**不采集、不留存任何个人信息**（FR-9.1）：不做注册与身份识别，问答中的身份信息不入库、不用于训练、不对外提供；为满足审计与质量观测，仅保留不含身份信息的运行指标（问答量、拦截率、延迟）。这也是公众侧"匿名可用"的产品前提，不能以"改善服务"为由反悔。
- 相对地，问询信息不足时只能靠**会话内临时上下文**反问补齐（FR-8.5），不做跨会话的用户画像——这是匿名设计的必然代价，需在交互话术上让用户自己补全关键事实。

### 4.9 公众侧公网入口与推荐律师（FR-9，v1.1 新增）

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-9.1 | 公众侧以**公网 Web 入口**提供服务，匿名访问：无需注册登录，不采集、不留存任何可识别公众身份的信息（姓名、手机号、身份证号、账号等） | P0 | 公网可直接访问；不注册即可提问；落库与日志检查无身份信息（AC-19） |
| FR-9.2 | 公网侧安全与防滥用：限流、防爬、防提示注入与越权探测、异常请求拦截与封禁 | P0 | 构造高频请求、扫描爬取、提示注入与越权探测请求，100% 被拦截或限流（AC-20） |
| FR-9.3 | 回答中给出**推荐律师**（基于律师执业信息名录，按问题类型/专业领域/地域匹配展示） | P1 | 推荐字段完整（姓名、执业机构、专业领域、联系方式获取方式）；推荐依据可说明 |
| FR-9.4 | 给出与该问题类型相对应的**律师费用区间**（含计费方式说明），并明示为参考区间、不构成报价或委托承诺 | P1 | 展示费用区间时 100% 带"参考区间，不构成报价或委托"提示（AC-21） |
| FR-9.5 | 推荐中立性：排序与展示规则可说明，不因推广付费改变排序或展示位置 | P1 | 排序规则有文档说明；无付费插位（AC-21） |

**落地要点**：

- 公网入口改变了 AC-15 / AC-16 的口径：系统对外"**入站可达**"但"**出站禁止**"——公众侧能被公网访问不等于允许调用外部 API，推理、检索、存储仍全部在本机完成（见 5.2、6.4）。
- "不采集公众信息"落到工程上就是：公众侧不做账号体系与身份识别，不保存问答中的身份信息；相应地**也无法按用户做长期追踪**，多轮上下文只能用临时会话态，且仅在本次会话存续期间保留（超时或关闭即清除），服务端不作持久化留存。
- 推荐律师与费用区间属"**信息指引**"，与 FR-8.3"不出具个案代理意见"不冲突：前者告诉用户"可以找谁、大概多少钱"，后者禁止替用户判断"你这官司能不能赢"。两者都必须带免责提示（AC-18、AC-21）。
- 公网 + 律师执业推广/收费信息展示是**合规敏感区**：上线前须由律所合规负责人确认口径（含 ICP 备案主体与要求），见 7.3、7.5。
- 费用区间必须挂在可维护的数据源上（谁维护、多久更新一次），否则会变成过期误导信息（见 7.5）。

## 五、非功能性需求

### 5.1 性能

| 指标 | 要求 |
|---|---|
| 检索响应 | 单次查询 P95 < 2 秒 |
| 端到端生成 | 单次问答 P95 < 8 秒（本地 LLM） |
| 并发 | 律师侧支持 10–20 人同时使用；公众侧为公网入口，**必须独立限流与排队**，不得挤占律师侧资源（公众侧并发上限与 AC-14 对齐取 20，超出即排队或拒绝；律师侧优先级始终高于公众侧） |
| 数据规模 | 支持 5 万 chunk 级别（一本法典 + 类案）无性能衰减 |

### 5.2 安全与合规

| 指标 | 要求 |
|---|---|
| 部署方式 | 律师侧全本地私有化、不出站；公众侧开放公网**入站**入口，生成可调用**外部大模型 API**（密钥由服务端从本机环境变量读取，不写进代码），出站仅限白名单域名 |
| 数据出境 | 案卷、检索记录不出内网；公众侧仅外发提问文本与公开法条片段，**不外发案卷/类案内容与任何身份信息**，且不采集、不留存身份信息 |
| 脱敏 | 入库前完成敏感信息脱敏 |
| 权限 | 细粒度访问控制 + 所内团队级数据隔离 |
| 审计 | 全操作日志留存，可追溯 |
| 公众侧数据隔离 | 普通用户对公开法条库**只读查询**，不可访问任何案卷/类案数据、不可执行任何写操作（上传/编辑/删除/导出），越权即拒绝（AC-19） |
| 公众侧个人信息 | 公众侧匿名访问：不采集、不留存任何可识别个人身份的信息；仅保留不含身份信息的运行指标（问答量、拦截率、延迟），见 FR-9.1 |
| 公众侧公网防护 | 公网入口须限流、防爬、防提示注入、防越权探测，异常请求可拦截与封禁（FR-9.2、AC-20） |

| 指标 | 要求 |

| 指标 | 要求 |

| 风险提示 | 回答中显著位置给出"不构成正式法律意见"提示（FR-8.4） |
| 公众侧访问方式 | 公网直接访问，无需注册登录（FR-9.1） |
| 推荐信息呈现 | 推荐律师与费用区间以参考信息呈现，显著标注"不构成报价或委托承诺"（FR-9.4、AC-21） |

## 六、验收标准

### 6.1 功能验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-1 | 法条结构化入库 | 民法典及指定司法解释 100% 入库，层级、条款号、效力状态正确 |
| AC-2 | 精确条款号检索 | 输入"第584条"能准确返回该条，准确率 100% |
| AC-3 | 混合检索 | 标准评估集上法条召回率 ≥ 90% |
| AC-4 | Rerank 精排 | 精排后 top3 包含正确答案比例 ≥ 85% |
| AC-5 | 引用可核对 | 每条引用可一键跳转原文，跳转准确率 100% |
| AC-6 | 幻觉拦截 | 编造/失效法条拦截率 100%，输出中无未校验引用 |
| AC-7 | 时效过滤 | 默认检索不返回已废止条文，准确率 100% |
| AC-8 | 父子切分 | 命中款/项时能返回完整父条，引用精确到款 |
| AC-9 | 类案脱敏 | 脱敏后无敏感信息残留，且仍可检索 |
| AC-10 | 权限隔离 | 越权访问被拒绝，隔离测试 100% 通过 |
| AC-11 | 审计日志 | 操作可追溯，日志完整率 100% |
| AC-17 | 公众问答可核对 | 普通人口语化评估集上，回答引用准确率 ≥ 95%，编造/失效法条拦截率 100% |
| AC-18 | 免责与输出边界 | 输出 100% 带免责声明；要求出具个案代理意见或预测胜诉的提问，100% 不给出结论性判断 |
| AC-19 | 公众侧数据隔离与只读 | 普通用户越权访问案卷/类案数据 100% 被拒绝；公众侧无写操作入口，上传/编辑/删除/导出请求 100% 被拒绝；公众侧不采集身份信息（落库与日志检查无身份信息） |
| AC-20 | 公网侧防护 | 公网入口可访问；高频请求被限流；构造的爬取、提示注入、越权探测请求 100% 被拦截 |
| AC-21 | 推荐律师与费用区间 | 推荐律师与费用区间可展示且字段完整；展示费用区间时 100% 带"参考区间，不构成报价或委托"提示；无付费插位 |

### 6.2 性能验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-12 | 检索延迟 | P95 < 2 秒 |
| AC-13 | 端到端延迟 | P95 < 8 秒 |
| AC-14 | 并发 | 20 并发下性能不显著下降 |

### 6.3 评估集验收

- 建立 **50–100 个律师真实问题**评估集，标注标准法条。
- 关键指标：**法条召回率、引用准确率、时效正确率、幻觉率**。
- 由**执业律师人工抽检**，边缘案例重点覆盖。
- 上线门槛：**引用准确率 ≥ 95%，幻觉率 = 0（拦截后）**。
- 增设 **30–50 个普通人真实问题**（口语化描述，覆盖租房、消费、劳动、借贷、婚姻家庭等常见场景）作为公众侧评估子集，与律师侧评估集分开统计；公众侧沿用同一门槛（引用准确率 ≥ 95%、幻觉率 = 0）。
- 公众侧另设两类**非质量类检查项**（不参与准确率统计，但作为 AC-20、AC-21 的验收证据）：①公网滥用与防护（限流、爬取、提示注入、越权探测的构造请求）；②推荐合规（免责提示齐全、费用区间口径统一、无付费插位）。

> 说明：评估集是本项目唯一可信的"好不好用"判据。建议一期开工前先冻结评估集（问题 + 标准条款号 + 时效要求），中途不得为了好看而修改标注；否则指标将失去对比意义。

### 6.4 合规验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-15 | 出站管控 | 律师侧全流程无外部网络调用；公众侧出站**仅限白名单内的外部大模型 API 域名**，抓包验证无其他外联 |
| AC-16 | 数据不出内网 | 案卷与检索记录不出内网；公众侧出站内容不含案卷/类案内容与身份信息（抓包 + 出站内容过滤记录为证据） |

### 6.5 验收的一票否决项

下列指标不达标时，项目整体判定为不通过，不允许用其他指标的加分交换：

| 编号 | 一票否决项 | 理由 |
|---|---|---|
| AC-6 | 幻觉拦截 100% | 编造法条是执业事故级风险 |
| AC-7 | 默认不返回已废止条文 | 引用失效条文同样构成错误依据 |
| AC-10 | 权限隔离 100% | 越权可见案卷等于泄密 |
| AC-15 / AC-16 | 出站管控与数据不出内网 | 案卷不出内网是立项前提；公众侧出站须白名单收口、内容可审计 |
| AC-18 / AC-21 | 免责声明与输出边界（含推荐与费用口径）100% | 缺免责声明的法律建议会被当成正式意见；费用区间被当成报价属合规风险 |
| AC-20 | 公网侧防护生效 | 公网入口无限流、无防注入，等于把单机资源与法条库交给自动化滥用 |
| AC-10 / AC-19 | 权限隔离（含公众侧只读）100% | 越权可见案卷等于泄密，越权写入等于数据污染 |
| 6.3 门槛 | 幻觉率 = 0（拦截后） | 同上，属质量红线 |
| 5.4 代码规范 | 单文件代码行（非空行）≤ 300 行、无未注释代码行 | 项目方硬约束（建议以静态校验脚本零告警作为验收证据） |

## 七、约束边界

### 7.1 范围边界

| 约束 | 说明 |
|---|---|
| 法域范围 | 一期仅覆盖民事法典 + 指定司法解释，不含刑法、行政法 |
| 数据规模 | 面向一本法典 + 少量类案（≤ 5 万 chunk），不做大规模分布式 |
| 用户规模 | 律师侧：单律所/单团队内网使用；普通用户侧：**公网**（互联网可访问的公开法条库咨询入口，匿名、无需注册）；两侧均非多租户 SaaS |
| 终端 | 律师侧一期仅 Web 端，不含移动端；普通用户侧沿用同一 Web 入口（FR-8.1） |
| 公众侧入口与合规 | 公众侧为公网 Web 入口，上线前须完成 ICP 备案等合规手续，并具备限流、防爬、防注入与滥用处置能力（FR-9.1、FR-9.2）；备案主体为律所（项目方），合规口径由律所合规负责人书面确认并存档 |
| 公众侧操作范围 | 仅查询（只读）：提问、检索、查看法条原文与回答；不提供上传、编辑、删除、导出等写操作（FR-8.7） |

### 7.2 技术边界

| 约束 | 说明 |
|---|---|
| 部署 | 单机私有化，不依赖公有云；律师侧不出站；公众侧开放公网入站，并允许到白名单内的外部大模型 API 出站（见 5.2、6.4） |
| 架构 | 不采用分布式向量库/K8s，避免过度设计 |
| 模型 | 本地 LLM + 本地 Embedding + 本地 Rerank |
| 切分 | 法条禁用纯语义切分，必须对齐法律层级 |
| 生成 | 低温度，禁止自由发挥 |

### 7.3 合规边界

| 约束 | 说明 |
|---|---|
| 数据安全 | 案卷不得出境、不得调外部 API |
| 隐私 | 入库前必须脱敏 |
| 审计 | 操作日志必须留存 |
| 责任 | 系统输出仅供参考，最终引用由律师核对确认 |
| 责任（公众侧） | 对普通用户的输出为一般性法律信息，不构成正式法律意见，不得替代律师；必须明示免责声明（FR-8.4）；推荐律师与费用区间仅为参考信息，不构成委托关系或报价承诺（FR-9.4） |
| 个人信息（公众侧） | 公众侧匿名访问：不得采集或留存任何可识别个人身份的信息（见 5.2、FR-9.1） |
| 公网合规 | 公众侧公网入口须完成备案，并满足互联网信息服务的合规要求；律师执业推广与收费信息展示须符合现行互联网信息与律师执业推广相关要求，口径由律所合规负责人书面确认后留档 |
| 推荐中立性 | 推荐律师排序不得因推广付费改变；排序与展示规则须可说明（FR-9.5） |

### 7.4 明确不做（Out of Scope）

- ❌ 分布式向量库 / K8s 集群
- ❌ 公网 LLM API 调用
- ❌ 纯语义切分法条
- ❌ 无引用校验的自由生成
- ❌ 跨法域全量法规覆盖
- ❌ 移动端 App
- ❌ 个案代理意见、胜诉/输赢预测
- ❌ 线上委托成交与线上收费（仅提供推荐律师与费用区间**信息**，见 FR-9.3、FR-9.4）
- ❌ 线上出具法律意见书
- ❌ 面向普通用户的任何写操作（上传、编辑、删除、导出）

### 7.5 假设与依赖

| 项 | 说明 |
|---|---|
| 数据源 | 需获得结构化民法典文本及司法解释数据源 |
| 硬件 | 单卡 4090 级工作站（14B 模型可跑） |
| 法规更新 | 依赖法规数据源的持续更新能力 |
| 人工评估 | 需执业律师参与评估集标注与抽检（公众侧子集同样需人工抽检） |
| 公众侧合规 | 公众侧为公网入口，须在上线前完成 ICP 备案，并确认律师执业推广与收费信息展示的合规口径（含备案主体） |
| 律师名录与费用数据源 | 推荐律师与费用区间需有可维护的律师执业信息与收费标准数据源（由律所指定责任人维护；费用区间以现行律师服务收费政府指导价与律所公示的收费标准为口径，收费依据变更后同步更新） |

> 风险提示：7.5 的"数据源"与"人工评估"是**外部依赖**，不在项目团队控制范围内。一期启动时须同步确认：①结构化法条文本的获取渠道与授权；②可参与评估集标注的执业律师及其可投入工时；③公众侧公网备案与推广/收费信息展示的合规口径（未完成不得开放公网入口，对应 AC-20）；④推荐律师名录与费用区间的数据源与维护责任人（未落实则 AC-21 无法验收）。任一项延迟，都会直接卡住 AC-1、AC-21 与 6.3 的评估集验收。
