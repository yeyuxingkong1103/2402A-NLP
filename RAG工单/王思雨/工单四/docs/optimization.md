## 0. 口径声明（先说清楚，避免数字被误读）

| 项 | 口径 |
|---|---|
| 准确率 | 16 题里判分正确的题数占比。判分 = 关键词命中率 + `expect_not` 负样本不得出现 + 枚举题个数核对，判分器本身用已知错答自检过（`--selfcheck`） |
| 响应时间 | 从 `/api/ask` 收到问题到返回答案，含检索、重排、DeepSeek 生成。**绕开缓存**（`--no-cache`），否则测得的是缓存读取代不了端到端 |
| 检索精确度 | 在线代理口径：返回的 N 条上下文中重排分 ≥ 0.5 的占比。**这是无标注代理指标，不等于准确率**，两者全程分开陈述 |
| 性能指标 | 工单只写"响应时间 ≤ 3 秒"，未指明分位数。本项目取 **P50 ≤ 3 秒**为达标线，并**同时如实给出 P95 与最大值**（见 §5） |
| 测量干扰 | 本地模型跑 GPU。测量时**必须确保只有一个进程占用显存**——曾出现 uvicorn 与测试脚本同时驻留，P50 从 2428ms 虚高到 3112ms |

## 2. 瓶颈定位（先测再调，不凭经验猜）

### 2.1 端到端：生成占 73%

16 题逐题拆分（`retrieval_ms` / `generate_ms`）：

| 阶段 | 平均 | 最大 | 占比 |
|---|---|---|---|
| 检索 + 重排 | 733 ms | 1134 ms | 27% |
| DeepSeek 生成 | 2007 ms | 4806 ms | **73%** |
| 端到端 | 2740 ms | — | 100% |

**结论：本地检索不是大头，外部大模型生成才是。** 把检索优化到 0 也只能把 2.7 秒压到 2.0 秒。

### 2.2 检索内部：重排占 92%

对 16 题分别计时（`embed` / Milvus `search` / `bm25` / `rrf` / `rerank`）：

| 子阶段 | 平均耗时 | 占检索 |
|---|---|---|
| bge-m3 编码 | 15.7 ms | 3% |
| Milvus 向量检索 | 18.7 ms | 3% |
| BM25 关键词检索 | 15.3 ms | 3% |
| RRF 融合 | 1.2 ms | 0% |
| **bge-reranker 重排** | **554.1 ms** | **92%** |
| 合计 | 604.9 ms | 100% |

**结论：检索侧唯一值得动的是重排。**

### 2.3 提示词大小：不是瓶颈

16 题提示词平均 4342 字符（最大 5857），上下文 8~22 条（表格行补全后）。但生成耗时与提示词大小无相关（最大提示词的 id=33 生成 2028ms，提示词中等的 id=5 生成 4806ms）。
**生成耗时主要由输出长度与 API 延迟决定，不是 prefill。** 故不做提示词瘦身——砍上下文只会伤准确率。

## 3. 逐项优化与实测

### 3.1 重排批大小 16 → 4（**本次采纳**）

`RERANK_BATCH`。60 条候选、16 题，正反两种顺序各测一遍取中位（排除测量顺序干扰）：

| batch | 正序中位 | 反序中位 |
|---|---|---|
| 2 | 445.2 ms | 432.3 ms |
| **4** | **409.5 ms** | **413.0 ms** |
| 8 | 440.2 ms | 435.3 ms |
| 16（原值） | 533.9 ms | 536.7 ms |
| 32 | 804.2 ms | 804.6 ms |

**batch=4 最优，比原来的 16 快 125 ms/题（23%）。**

> 顺带修正一处误导性注释：原注释写"显式设 16 实测提速 4.6 倍"。这句本身没错——16 相对**库默认值**确实快得多——但会让人以为 16 就是最优，从而错过更优的 4。**只跟默认值比就收工，是调参里最容易犯的错。**

### 3.2 水印残渣清洗（**本次采纳**）

招股说明书的斜向水印不在文本层，MinerU 读图时必然把水印读进单元格。实测 id=3 的答案被写成 **"赵马克gzh"**——真名是"赵马克"（全库干净出现 66 次，带 gzh 仅 2 次）。**关键词判分照样给过**，属于判分器抓不到的那类错。

`backend/rag.py` 新增 `clean()`：删掉**紧贴中文的全小写拉丁串**（水印"人工智能刘敏"拼音被 OCR 打碎后的残渣，如 `gzh`/`reng`/`umin`/`engonz`）。

- 全库命中 **1336 处、涉及 970 个块**
- 判据用"全小写"是因为正规术语（`IC`/`ERP`/`GDP`/`BOM`）全是大写，实测一个都没被误删
- 已知误伤仅 `logo` 与 `min` 两词，在中文招股书里不承载信息，取舍划算

### 3.3 融合池保持 60（**试过，不改**）

| FUSION_TOP_K | 准确率 | 说明 |
|---|---|---|
| 60（现值） | **16/16** | — |
| 40 | 16/16 | 重排省 ~110ms，但检索精确度 0.930 → 0.898 |
| **30** | **15/16 ✗** | id=260 复现为"资料中未找到报告期内各期军用领域收入的具体金额" |

id=260 的答案块在 BM25 通道排第 21、向量通道未进前 50，池子太小就挤不进重排。**这正是 `config.py` 里那条注释记录的坑，被本次实验独立复现。** 准确率是工单第一验收项，为省 110ms 去踩它不值得，故保持 60。

### 3.4 rerank top_k 保持 8（**试过，不改**）

`RERANK_TOP_N` 8 → 6：准确率仍 16/16，检索耗时 733ms → 726ms（**在噪声内**）。既然拿不到确定性收益，就不动它。

### 3.5 缓存策略（已生效，未改）

Redis 缓存同一问题答案，TTL 由 `CACHE_TTL` 配置（默认 86400 秒）。重复提问端到端降至 **毫秒级**（实测 0~30ms）。缓存键含**源码结构指纹**——改了检索逻辑而指纹未变时会静默吞掉新字段（`degraded` 被吞等于降级无提示），故键由源码哈希自动生成，不手升版本号。

## 5. 残留问题（如实列出，不粉饰）

### 5.1 响应时间的长尾压不下去

优化后仍有 1 题 > 3 秒：**id=5 用时 4629 ms**，其中生成 4000+ ms。原因是它的答案要枚举"销售部下辖 4 个部门 + 大客户销售部下辖 6 个销售处"，输出长、生成慢。

**这是外部 API 的固有成本，不是本项目可优化项。** 若要硬压，只能截短答案，但那会牺牲完整性（并可能直接判错，见 id=4 曾因少列 3 家企业判错）。

## 7. 上下文精确度（RAGAS `context_precision`）专项

动机：RAGAS 四项里 `llm_context_precision_with_reference` 最低（0.788），是明确短板。目标：抬到 0.85+。

### 7.1 先量裁判的噪声底（**这一步决定了后面所有结论的可信度**）

RAGAS 的 LLM 裁判本身是测量工具，**用它比较"改前改后"之前，必须先知道它自己抖多少**。
同一份代码、同一批问题连跑两次：

| 指标 | 第 1 次 | 第 2 次（同代码） | 波动 |
|---|---|---|---|
| context_precision | 0.7359 | 0.7793 | **±0.043** |
| faithfulness | 0.9875 | 0.9250 | **±0.063** |
| answer_relevancy | 0.9244 | 0.9572 | ±0.033 |

单题波动更夸张：id=2 在 **0.167 ↔ 0.667** 之间跳，id=1 在 0.347 ↔ 0.506 之间跳；
判分器还会把上下文明显相关的题判成 **0.0**（id=4 的上下文就是"不存在控制关系的关联方：融冰投资、武汉博润…"，判 0）。

**结论：context_precision 的分辨力约为 ±0.05。任何小于这个幅度的"提升"都无法与噪声区分。**
这一步没做的话，我会把"裁尾后 0.788→0.736"错读成**性能回退**——实际只是噪声。

### 7.2 针对诊断出的两个缺陷动手（依据是**直接检视**，不是指标）

| 缺陷 | 证据 | 处置 |
|---|---|---|
| **表格补全误伤** | id=793 问"下游行业"，却被塞进 5 行 P22「发行人基本情况表」（注册资本/注册地址/控股股东）——完全无关 | 只有排进重排**前 3 名**的表格行才允许触发补全（`TABLE_EXPAND_TRIGGER_RANK`） |
| **低分尾巴** | id=34 的 8 条上下文里有 4 条重排分仅 0.40~0.47（「审计机构声明」「验资复核机构声明」「承诺函」套话页） | 重排分低于相关性阈值(0.5)的块不进上下文（`MIN_CONTEXT` 保底） |
| **行碎片喂模型** | id=4 返回 12 条上下文，同一张表的多行各自成条、互不连贯 | **行级检索、表级呈现**：喂模型前把同表行拼回整张表（`merge_table_rows`） |

**为什么触发判据用名次而不是分数**：有害触发是 0.719 分，而合法触发里有 0.743 —— 差 0.024，
按分数切必然误伤。改成看名次后，所有需要补全的题都至少有一个触发行在前 3（id=1@2、3@1、4@1、260@2、33@2、543@1、531@2、207@3），
而 id=793 最好的触发行只到第 4 —— **干净分开**。

**极差 0.052，全部落在 §7.1 量出的噪声带内**。

### 7.4 结论

**先纠正一个我差点犯的错**：最初我据"0.788 < 0.85，差 0.062"宣布"目标未达成"。
但同一份代码的复测标准差是 **0.043**——**这个"未达成"的结论本身就落在噪声边缘**，单次测量没有资格下这个判断。
0.85 完全可能落在置信区间内。故此处不写"未达成"，改为下面三条：

1. **单次测量不足以判定是否达标**。要看多轮均值与置信区间（`--repeat` 已实现，见 §7.6）。
2. **确定性证据是正向的**：上下文总条数 −42%、id=793 最低分 0.270→0.719、id=34 最低分 0.401→0.650，
   准确率保持 16/16。这部分不依赖裁判，可独立复核。
3. **表格题子集 +0.105**（0.605→0.710）是同口径对比，但存在反向项（id=260 1.0→0.833），
   **只能称"正向信号"**。

### 7.5 已知的稳定弱项：id=207

**id=207 在三次独立运行里均为 0.325**（精确到三位小数完全一致：ctxfix、ctxfix_rep2、mergerows2），
**不是噪声，是可复现的弱项**。该题在其余指标上正常，仅上下文精确度稳定偏低。
问题问"募集资金多少用于补充流动资金"，属**表内定位**问题：向量检索对"同一张表里是哪一行"没有分辨力，
因为同一张表的各行上下文高度相似，混入的兄弟行稳定拉低精确度。

**注意**：在切分/合并这一层继续抠，边际收益已接近噪声（见 §8 中"按分数切触发"被否决的记录）。
若后续要动，方向应转向**查询侧**（表结构感知检索 / 查询重写），
但**前提是先完成 §7.6 的复测**——否则无法验证新方案是否真的有效。

### 7.6 复测：把"是否达标"从单次测量变成区间与概率

`scripts/eval_ragas.py --repeat N --target 0.85`：跑 N 轮完整评估，输出**均值、样本标准差、95% 置信区间、
单次测量 ≥ 目标值的概率**，并统计作废轮数（nan 比例 > 10% 的轮次不进入统计，见 §9.1）。

这一条**优先于任何调参**：它首先回答的是"0.85 是不是这个裁判能可靠测出来的目标"，
其次才是"当前离目标多远"。在 ±0.05 的噪声下跳过这一步去调参，等于在噪声里打转。

判读口径：
- 若多轮均值仍稳定在 ~0.78 且区间不含 0.85 → 才是真正的未达成，此时瓶颈在检索侧。
- 若区间含 0.85 → "未达成"的结论应收回，改为"口径需修正、需更多轮次才能判定"。

**执行结果（2026-10-08 14:00 起）**：协议已实现并**验证可用**（第 1 轮顺利跑完：`context_precision=0.8014`，
nan 比例 0.0，标记为有效），但**未能跑满 3 轮**——第 2 轮起 API 严重拥塞，
单轮 20+ 个超时、25 分钟才推进 18/64，按该速率每轮需 ~1 小时且大概率因 nan 超阈值作废，只能中断。
（中断时还发现脚本只在全部跑完才落盘，**第 1 轮的逐题数据就此丢失**；已改为每轮增量落盘，
`complete` 字段标明是否跑满。）

**用现有干净样本做的初步估计——按代码版本分组，不跨版本求均值**：

| 代码版本 | 各轮值 | n | 均值 | 标准差 |
|---|---|---|---|---|
| 原始（未修上下文） | 0.7880 | 1 | 0.7880 | — |
| 裁尾 + 补全触发修复（无合并） | 0.7359 / 0.7793 | 2 | 0.7576 | 0.0307 |
| **表级合并（当前代码）** | **0.7813 / 0.8014** | **2** | **0.7913** | **0.0142** |

> **一处已修正的错误**：先前我把"合并前 2 轮 + 合并后 2 轮"合并成 `n=4、均值 0.7745` 与当前代码并列，
> 并据此说"两条区间都不含 0.85"。**那个 0.7745 是没有物理意义的混合数**——
> 它既不是合并前的均值，也不是合并后的均值，把它和 n=2 并列会诱导出"样本更大所以更可信"的错觉。
> 跨代码版本的轮次只能分组看，不能求均值。

**可读的对比**：当前代码均值 0.7913 比"裁尾后"均值 0.7576 高 0.034，比原始单点 0.7880 高 0.003。
**两个差距都远低于 ±0.05 的噪声底 → 表级合并的效果依然未被验证**（与 §7.3 的结论一致：
确定性证据为正、指标证据不足）。

**就"0.85 是否达成"而言**：当前代码 n=2，95% 区间 (0.772, 0.811)，**不含 0.85**，
初步证据**倾向于未达成**；但 n=2 的标准差不可信，**这仍不是定论**。
脚本已就绪，API 健康窗口一次跑满即可定案：
`python scripts/eval_ragas.py --repeat 3 --target 0.85`。

**为何不趁现在重试（决策留痕）**：拥塞时段重跑的**期望收益为负**——
作废轮不计入统计，最可能的结果是"n=1 干净 + 2 轮作废"，比现有 n=2 更差，
且第 1 轮的 0.8014 也失去配对比较的意义。**等健康窗口，别为确认一个数字消耗三小时。**

**健康窗口开启时的建议顺序（一个窗口干两件事，摊薄等待成本）**：

1. `--repeat 3 --target 0.85` 定案本节的口径问题；
2. 同窗口对 §7.5 的 id=207 候选方案各跑 1 轮对照。

**在此之前，id=207 的候选方案先在本地离线比较**（不调大模型、不耗 API）：
表名定位 / 查询重写（"补充流动资金"→"补充流动资金 项目名称 募集资金投资"）/ 表内行级 BM25，
先在 id=207 及其对照题的检索上下文上比召回，**筛出有效候选再上 RAGAS**。
`id=207` 的稳定弱项已确认（三次 0.325），新方案有基线可比，不必等 3 轮定案才动手。

**这一轮真正的收获不是数字，而是把"是否达标"从单次测量变成了可复算的区间与概率**，
并且暴露出"长任务必须先落盘"这个工程问题。

## 8. 被否决的优化及原因（与"做了什么"同等重要）

| 候选 | 实测结果 | 决定 |
|---|---|---|
| `FUSION_TOP_K` 60 → 40 | 准确率仍 16/16，但检索精确度 0.930 → 0.898，重排仅省 ~110 ms（在噪声内） | **否决** |
| `FUSION_TOP_K` 60 → 30 | **id=260 直接错答**（"资料中未找到…军用领域收入的具体金额"），复现了 config 注释记录的坑 | **否决** |
| `RERANK_TOP_N` 8 → 6 | 准确率 16/16，检索耗时 733 → 726 ms，收益在噪声内 | **否决** |
| `max_tokens` 800 → 400 | 准确率 16/16，生成耗时无确定性收益 | **否决** |
| 表格补全触发**按分数**切（如 ≥0.75） | 有害触发 0.719 与合法触发 0.743 仅差 0.024，切不干净 | **改用名次判据** |
| 直接缩短上下文来压 P95 | 生成占端到端 73%，属外部 API 成本；截短答案会牺牲完整性（id=4 曾因少列 3 家判错） | **否决** |
| 调整语义分块参数 | 无任何失败案例指向分块粒度 | **否决（无靶射击）** |

**这七条"不做"和前面几条"做"是同一套标准下的结果**：有确定性证据才动，拿不到证据就不动。

> **其中"按分数切表格补全触发"一条最有复用价值**：它用数据说明，在 ±0.05 的噪声下，
> **0.024 的差距不足以支撑一个方向性决策**（有害 0.719 vs 合法 0.743）。
> 这类"差距小于度量分辨力"的判断，比具体修了哪个参数更值得留给下次。

## 9. 评估可信度：三种会把结论带反的假信号

这一节不是工单要求的交付物，但每一条都真实误导过一次，成本低、回报高。

### 9.1 假信号一：RAGAS 整轮作废，但 exit code 仍是 0

**现象**：某轮 16 题里 **10 题**的 `llm_context_precision_with_reference` 变成 `nan`，
聚合值算出 **0.6682**，比"改动前"的 0.788 低。若不检查，会得出**"我的改动让指标变差"**的反向结论。
**真相**：日志里是 **42 个 `Error code: 402`**（DeepSeek 余额瞬时不足，重试即恢复），与改动无关；
`nan` 的题被 RAGAS 排除在均值之外，剩下 6 题凑出了那个假数字。**脚本退出码为 0，不会报错。**

**守则（已落进代码）**：

| 规则 | 实现 |
|---|---|
| 聚合值异常或出现 `nan` 时，**必须查日志**里的 402 / Timeout 计数 | 见本文 §7.5 |
| **exit code 不可信**，不能作为"评估跑成功"的依据 | — |
| **nan 比例 > 10% 则整轮作废**，不进入统计 | `scripts/eval_ragas.py` 的 `NAN_GUARD`，作废轮标记 `valid=False` 并计入 `dropped` |
| 只看聚合均值不够，必须看逐题 | 结果 JSON 的 `per_question` 字段 |

### 9.2 假信号二：`--no-cache` 是假的，测出 3 ms 的"端到端耗时"

**现象**：`python scripts/test_questions.py --no-cache` 走 HTTP 时，16 题**全部命中缓存**、
平均耗时 **7.7 ms**——数字漂亮得不像话。
**真相**：该开关只是在**测试进程**内给 `K.get/K.set` 打了补丁，而 HTTP 模式下**缓存在服务端**，
补丁根本够不着。README 却把它写成"绕开缓存测真实端到端耗时"。
更糟的是它**不报错**，只是安静地给出失真数据。

**处置**：`/api/ask` 增加 `no_cache` 入参并透传到 `use_cache`，测试脚本在 HTTP 模式下把它放进请求体。
那个 3 ms 的结果文件已删除。

**通用教训（写给以后）**：**任何"绕过服务端状态"的测试参数，都必须在服务端有对应的开关。**
在客户端打补丁只对同进程（`--direct`）有效；跨进程时它不会失败，只会静默失效。

### 9.3 假信号三：把噪声当成改进或回退

见 §7.1 与 §8 的方法论：`context_precision` 同代码复测波动 ±0.043、`faithfulness` ±0.063，
单题最大跨度 0.167↔0.667。**度量分辨力约 ±0.05，小于此幅度的差异一律不做方向性结论。**
这也是为什么 §7.4 把"未达成"收回为"落在噪声边缘、需复测判定"。
