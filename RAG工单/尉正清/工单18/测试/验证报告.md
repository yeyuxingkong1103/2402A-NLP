## 三、结果分析（工单点名要做的三件事）

### 3.1 统计结果是否符合数据集整体特征 ✅

工单预期「**扫描型 PDF 占比较高**」。实测 **36.6%**（622/1700），符合预期。

而且是**完美的两极分化**：1700 份的扫描页占比只有两个取值 —— **0.0 或 1.0**，
中间地带**一份都没有**。

```
扫描页占比 0.0 : 1078 份
扫描页占比 1.0 :  622 份
（0.05 ~ 0.95 之间：0 份）
```

物理上说得通：一份专利 PDF 要么是数字排版的原生文档，要么是整份扫描件，
不存在「一半页扫描一半页原生」的。**这也意味着 `mixed`（混合型）这个分类
在本数据集上不会被触发**，但阈值和代码路径都保留着，换语料用得上。

> ⚠️ 因此本数据集上的「待确认的 PDF 类型判定」列表**是空的**——不是功能没做，
> 是这批数据确实没有拿不准的。混合型分支的正确性由单元测试
> `test_混合型进待确认列表` 覆盖。

### 3.2 人工抽查两张「待办」列表

#### （a）待确认的版本冲突列表 —— 准确率 94%

**抽查方法**（可复现，工具在 `测试/分析.py`）：

```
python 测试/分析.py verify 测试/results/imdr/quality_report.json   # 逐对打开取著录项
python 测试/分析.py sweep  测试/results/imdr/quality_report.json 12 original_problems
```

判据：**同申请人 + 同申请日**即为真阳性。

IMDR 语料里捞出来的近似对，**全部是同一种情况**：同一个申请人把同一项技术在
**同一天**既报发明专利又报实用新型（中国特有的「双申请」做法），两件的著录项、
摘要、说明书几乎逐字相同，只有文献种类码差个 `A`/`U`。这种对知识库来说确实该
人工确认（内容重复，要不要两份都留），所以算真阳性。

**阈值扫描结果**：

| 阈值 | 条数 | 真阳性 | 误报 | 准确率 |
|---|---|---|---|---|
| 3 | 6 | 6 | 0 | 100% |
| 6 | 12 | 12 | 0 | 100% |
| **7** | **18** | **17** | **1** | **94%** ← 采用 |
| 10 | 24 | 23 | 1 | 96% |
| 11 | 34 | 26 | 8 | **76%** ← 断崖 |
| 12 | 49 | 27 | 22 | 55% |

阈值 7 是「高准确率平台（2~10）」的中段，离断崖隔 4 档。
**每个样本都带文件路径、相似度、汉明距离**，满足验收标准里「列表可操作性」。

样例（真阳性，同申请人同申请日）：

```
CN110775870A  一种螺杆升降机   苏州千律工业设备有限公司  2019.11.08
CN211226175U  一种螺杆升降机   苏州千律工业设备有限公司  2019.11.08
```

**一个重要的反例**：`CN111873149A`（一种瓷砖壁板加工模具、瓷砖壁板**及其加工方法**）
vs `CN212602486U`（一种瓷砖壁板加工模具以及瓷砖壁板）—— 标题不一样，但**是同一项技术的两件**：
发明专利能写方法权利要求，实用新型不能。所以判定**不能拿标题比**，得看申请人+申请日。

#### （b）待审核的敏感信息列表 —— IMDR 0 条，附件集 57 条且**消除 2 条误报**

IMDR 那 1700 份专利**一条敏感信息都没有**——合理：专利是公开文献，
著录项里只有申请人（公司）、发明人姓名和代理机构，没有手机号/邮箱/身份证。

所以这一项改用 `附件/` 的年报语料验证（年报里联系方式密集，是最好的靶子）：

| | 修复前 | 修复后 |
|---|---|---|
| 命中总数 | 59 | **57** |
| 手机号 | 2（**全是误报**） | **0** |
| 邮箱 | 57 | 57 |

**两条手机号误报长这样**（平安年报，工具：`python 测试/分析.py hits <报告.json>`）：

```
本年提取数18921754811,6892,734      ← 其实是 1,892,175,481.1 被截出 11 位
应收账款21,19362019822,011          ← 同类
```

*怎么回事*：财务金额用逗号千分位书写，`(?<!\d)` 数字边界挡不住逗号 ——
前面是「数」不是数字，后面是逗号也不是数字，于是 11 位数字被当成手机号。

*怎么修的*：加一条判据 —— 命中的数字串**前后紧邻逗号/小数点/百分号**，
就说明它是一个更大数字的片段，不是独立号码（`scripts/sensitive.py:_numeric_context_ok`）。

*代价*（写在配置注释里了）：「手机号后紧跟半角逗号」这种写法会漏
（`电话13812345678,邮箱…`）。权衡下来值得：知识库语料里连续 11 位数字绝大多数是
财务数字，而中文文档里手机号后面跟的通常是全角逗号或空格，不受影响。

**57 条邮箱全部是真实邮箱**（投资者关系信箱，如 `ir@psbc.com`），
且**每条都带前后 40 字上下文**，操作员一眼能判断「这是公开披露的联系方式，
不是个人隐私」——这正是验收标准要的「列表可操作性」。

> 顺带一个结论：**在公开披露类语料上，「敏感信息」命中绝大多数是合法的公开联系方式**，
> 不是 PII。这张表的用途是「让合规人员快速确认」，不是「自动拦截」。

### 3.3 分类标签合理性审查 ✅

**独立验证方法**：标签是按「每页可提取字符数」判的。如果核对时还去数字符数，
那是自己证明自己。所以改用**物理上独立**的信号 —— **图片面积占页面比例**
（字符数读的是文字层，图片覆盖率读的是页面资源，两条路互不相干）。

实测（每类随机抽 12 份，seed=18）：

| 标签 | 图片覆盖率（中位数） | 分布 |
|---|---|---|
| `Scan_PDF` | **1.00** | 0.96 ~ 1.00（整页位图铺满） |
| `Text_PDF` | **0.10** | 0.04 ~ 0.13（只有小插图） |

**区分度极干净**，标签与物理特征完全对应。

**再加上肉眼抽查**（截图在 `测试/截图/`）：

| 文件 | 判定 | 肉眼看到 |
|---|---|---|
| `CN2926129Y.pdf` | 扫描型 | 拍下来的专利说明书首页，无文字层 ✅ |
| `CN100408987C.pdf` | 扫描型 | 高清扫描件（4376×6665 位图），**看起来很像电子版但一个字都抽不出来** ✅ |
| `CN106926565B.pdf` | 文字型 | 清晰的数字排版 + 一张带标注的附图 ✅ |
| `CN111318330A.pdf` | 文字型 | 同上，16 个文本块 / 707 字符 ✅ |

> `CN100408987C` 这条值得记一笔：**「扫描型」的含义是「没有文字层、必须 OCR」，
> 不是「画质差」**。高清扫描件看起来比电子版还干净，但直接抽文字只能得到空白。

**标签分布无杂项**：1700 份只打出 `Text_PDF` 和 `Scan_PDF` 两种标签，
没有 `Unclassified`、没有误报的 `Empty_or_Broken`（详见第四节的三处修复）。

## 四、调优记录：验证过程中改掉的 5 个问题

验证不是「跑一遍看着还行」，下面每一条都是**实测数据推翻了原本的写法**才改的。

### 4.1 附图页冒充扫描页（影响 298 份，最大的一处）

**现象**：按工单原话「字符数低于阈值就算扫描页」实现后，**298 份被判成「混合型」**。

**查证**：逐份打开看低字符页是什么，答案是**专利附图页**：

```
CN106926565B.pdf
  第 1~5 页   字符 925~1477   图片覆盖 0.01      ← 正文
  第 7~10 页  字符 32         图片覆盖 0.32~0.44 ← 附图页（整页只有「图1」「图2」）
```

附图页字符数当然少，但它是**数字排版的原生页**，不需要 OCR。

**修复**：每页多加一个判据 —— **图片覆盖率**（图片面积 ÷ 页面面积）。
「扫描页」= 字符数低 **且** 图片铺满（≥0.8）。

**效果**：

| | 扫描型 | 文字型 | 混合型 |
|---|---|---|---|
| 修复前 | 622 | 780 | **298（误判）** |
| 修复后 | **622** | **1078** | **0** |

扫描型数量**一个没丢**，只把误判的 298 份归位。

**过程中还踩了一个坑**：第一版用 `get_text("dict")` 取图片块面积，
结果有 4 份真扫描件（`CN2926129Y.pdf` 等）**取到的 blocks 是空的，面积算出来 0.00**，
被判成文字型 —— 送去抽文字只会得到一篇空白。渲染出来肉眼看才发现的。
换成 `get_image_info()` 就正常了（那几个文件的内容流用 Form XObject 画图）：

```
文件                    dict块   get_image_info
CN2926129Y（扫描件）     0.00    1.00   ← dict 漏了
CN100408987C（扫描件）   0.93    0.93
CN111318330A（文字型）   0.09    0.10
```

### 4.2 SimHash 按单字切，准确率只有 38% → 改 3 字滑窗后 94%

**现象**：最初按单字切中文算 SimHash（理由写在代码注释里：「不引分词器，
按字切对这个用途足够了，少一个依赖少一份风险」）。实测被数据打脸：

阈值 5 捞出 **19 对**，逐对打开核对，**标题对得上的只有三分之一**。

**根因**：单个汉字的熵太低。「的、一、是、在」这类字每份中文文档里都是常客，
两份**毫不相干**的专利也能有 92% 的二进制位相同。

**修复**：改用 **3 字滑窗**（shingle）。比的是「短语」而不是「用字偏好」——
「带有预前处理的水泥磨」和「螺旋内刮式自清洗过滤器」在单字层面很像，
在三字滑窗层面几乎不重叠。**依然不用引分词器**，滑窗就够。

**效果**：距离分布从「平滑衰减、无空档」变成「有明确空档」，
阈值 7 的准确率从 38% 提到 **94%**。

### 4.3 空 when 的兜底规则变成「永远命中」

**现象**：30 份文档打出了 **90 个标签** —— 其中 30 个是 `Unclassified`。

**根因**：配置里 `Unclassified` 规则的 `when: {}` 是「兜底」的意思，
但代码把空 `when` 当成「条件永远满足」，于是**每份文档都被挂上它**，
标签分布直接失去意义。

**修复**：把空 `when` 的规则摘出来，只在**其他规则一条都没命中**时才用。
修复后 1700 份只打出 2 种标签，无杂项。

### 4.4 扫描件全被判成「坏文件」

**现象**：`Empty_or_Broken`（字符数 < 50）的本意是抓「解析失败或占位文件」，
但扫描件本来就没有文字层，字符数当然是 0 ——
**IMDR 那 1700 份扫描专利每一份都会被判成坏文件**，
而且路由变成「`ocr`、`review`」两个，工作流不知道该送哪个解析器。

**修复**：规则加 `pdf_kind_not: scanned` —— 已经被判为扫描型的，字符数少是
预期内的，不叫坏。真正要抓的是「有文字层却几乎没抽出字」的文件。

### 4.5 金额被截成手机号（见 3.2(b)）

修复见上，命中数 59 → 57，两条误报消除且不影响真实号码。

## 五、已知局限（诚实记录）

### 5.1 阈值是语料相关的，换语料必须重扫 ⚠️

`simhash_distance: 7` 是在 **IMDR（专利）** 上扫出来的。在 `附件/`（年报）语料上，
**这个默认值会产生误报**：6 对全部是不同公司的年报（同一套模板换数据，
彼此也能到距离 4~7）。

这不是 bug 是特性 —— 阈值取决于语料的「模板化程度」。配置里写明了这一点，
并给了重扫命令：`python 测试/分析.py sweep <报告.json>`。

### 5.2 带水印的副本可能漏检

同一份文档的「水印版 / 无水印版」，如果水印文字密集插在正文里，
3 字滑窗会被打断。实测 `招股说明书1.pdf` vs `招股说明书1-无水印.pdf`
（52 万字符 vs 30 万字符，水印注入了 22 万字符）**距离 17，超出阈值，漏检**。

这种要**先清洗文本再去重**，别指望 SimHash 认出来。

### 5.3 扫描件的版本冲突要到 OCR 之后才能比

622 份扫描件没有文字层，抽不出正文，被 `simhash_min_chars: 200` 挡在
SimHash 比较之外（报告里会写明跳过了多少份，**不会假装查过**）。
这批文档的版本冲突要**先 OCR 再比**。MD5 那层不受影响，照常有效。

### 5.4 混合型分类在本数据集上未被触发

IMDR 是完美两极分化（见 3.1），`mixed` 分类和「待确认的 PDF 判定」列表
在这批数据上都是空的。功能正确性由单元测试覆盖。

## 六、容器内实测（集成侧验证）

集成能不能成，卡点在「RAGFlow 容器里的 Python 能不能跑这个 Skill」。
技能在宿主机上跑得好好的，不代表容器里也行 —— 解释器、依赖、路径都可能不一样。
所以把 Skill 拷进容器真跑了一遍。

```bash
# 把 Skill 和 6 份样本 PDF 拷进容器
docker cp 研发/document_quality_assessment docker-ragflow-cpu-1:/ragflow/
docker cp <样本>.pdf docker-ragflow-cpu-1:/ragflow/qc_sample/

# 用容器自带的解释器跑（不是宿主机的 rag_gd）
docker exec -w /ragflow/document_quality_assessment docker-ragflow-cpu-1 \
    /ragflow/.venv/bin/python scripts/assess.py /ragflow/qc_sample -o /ragflow/qc_out
```

**结果：跑通，且与宿主机结果一致**

```
文件总数 6 份，3MB，解析失败 0 份
PDF 分流  scanned 2   text 4   （扫描型占 33%）
待确认版本冲突  1 对（另有 2 份正文过短未参与比较）
主路由    text ← 4 份   ocr ← 2 份
```

- 2 份扫描型正是肉眼核验过的那两份（`CN100408987C`、`CN2926129Y`）
- 1 对版本冲突正是核对过的双申请对（`CN110775870A` ↔ `CN211226175U`）
- 2 份「正文过短未参与比较」正是那两份扫描件 —— 跳过计数也正确

这证明 API 端点里 `subprocess` 调 `assess.py` 那条路径是通的（端点做的就是这件事）。

### 顺带查出一个部署坑：容器 venv 里没有 pip

原部署文档写的是 `docker exec ... /ragflow/.venv/bin/pip install pymupdf`。
实测**这条命令必然失败**：

```
$ docker exec docker-ragflow-cpu-1 /ragflow/.venv/bin/pip -V
sh: 1: /ragflow/.venv/bin/pip: not found
$ docker exec docker-ragflow-cpu-1 /ragflow/.venv/bin/python -m pip -V
No module named pip
```

镜像是用 **uv** 建的 venv，`/ragflow/.venv/bin/` 下没有 pip 可执行文件，
也没有 pip 模块。正确命令是：

```bash
docker exec docker-ragflow-cpu-1 /usr/local/bin/uv pip install \
    --python /ragflow/.venv/bin/python pymupdf
```

已修正 `部署/install.sh`（主路径改为 uv，pip 降级为兜底）和 `部署/DEPLOYMENT.md`。

**另一个反直觉的发现**：运行中的容器**其实已经装了 pymupdf**（1.24.14），
所以那一步看着「不用做」。但拉一个纯净镜像来验：

```bash
$ docker run --rm --entrypoint /ragflow/.venv/bin/python  \
      infiniflow/ragflow:v0.23.1 -c "import pymupdf"
ModuleNotFoundError: No module named 'pymupdf'
```

**镜像本身不带** —— 运行中那份是后来装进可写层的。
也就是说**容器一旦重建就会丢**，那一步不是可选项。部署文档里已经写明。

> 这一条值得记：只看「当前容器能不能 import」会得出错误结论，
