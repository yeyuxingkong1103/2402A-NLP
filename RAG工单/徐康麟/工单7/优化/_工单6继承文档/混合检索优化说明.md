## 2. 优化 ①：多字段倒排索引预热

**问题**：全文检索通道依赖 `fulltext_query.FulltextIndex` —— 需要为 4 个字段
（正文 / 标题 / 关键词 / 摘要）各建一份倒排表。2676 块实测构建耗时约 **4 秒**。
若惰性构建，**用户第一次点「全文检索」就会吃掉 4 秒**，直接违反「响应 ≤3 秒」。

**做法**：在 `QAEngine.warmup()` 里显式调用 `retrieval_strategy.warmup_strategy()` 完成构建并缓存；
失败**不阻断启动**（写 WARNING、如实降级），保证「预热挂了服务照常起」。

**实测**（2676 块）：

| 指标 | 值 |
| --- | --- |
| 倒排索引构建耗时 | **3877 ~ 4469 ms**（多次实测区间） |
| 预热总耗时（含索引加载 + 分词器 + 嵌入 + 生成模型） | **8360 ~ 10017 ms** |
| 预热后**单次全文检索**耗时（P50 / P95） | **7.03 / 13.74 ms** |
| 预热后混合检索耗时（P50 / P95） | **46.64 / 65.67 ms** |

→ 预热把「4 秒的一次性成本」从**用户可感知路径**移到了**服务启动路径**，首问即达标。

## 3. 优化 ②：检索结果缓存跳过「显式策略」路径

**问题**（实测踩坑）：工单4 的检索结果缓存只存**命中行**，不存**策略诊断**
（模式 / 权重 / 融合 / 重排 / 各阶段耗时）。一旦命中缓存：

* `retrieve` 耗时降到 **0.5 ms**；
* `diagnostics.strategy` 变成 `None`；
* 界面「三模式对比」出现**整行为空**的假象，报告缺耗时字段。

同一个会话里，未命中缓存的 `vector` / `fulltext` 有完整诊断、命中缓存的 `hybrid` 没有 —— **数据自相矛盾**。

**做法**：`retrieve()` 里 `read_cache = use_cache and strategy is None`。
显式传策略时**不读**检索缓存（仍可写），并在日志里记 `retrieval.cache_skipped` 说明原因。

**代价与取舍**：策略路径每次真实检索。检索层耗时 **8 ~ 120 ms**，而生成约 **1000 ms** ——
用不到 12% 的可控开销，换取「诊断始终完整、对比始终可信」，值得。

## 4. 优化 ③：`use_cache=False` 真正生效（工单4 遗留修正）

**问题**：工单4 的**内层**缓存（`cache.retrieval` / `cache.generation`）不受调用方
`use_cache` 开关管辖 —— `QAEngine.answer(..., use_cache=False)` 只跳过了**答案级**缓存，
内部的检索与生成缓存照常命中。

**症状**：用 `use_cache=False` 跑「响应时间测试」，量到的却是缓存命中的约 **1 ms**，而不是真实 LLM 耗时。
实测在修正前的 `t6-full` 轮次里，30 行中有多行「生成耗时 < 50 ms」，端到端低至 **56.88 ms** —— 明显失真。

**做法**：给 `retrieve()` 与 `generate()` 加 `use_cache` 形参并逐层透传；
`QAEngine.answer(..., use_cache=False)` 现在会让**三级缓存全部只写不读**。

**修正后实测**（`t6-full` 重跑）：

| 指标 | 修正前（含缓存命中） | **修正后** |
| --- | --- | --- |
| 生成耗时 < 50 ms 的行数 | 多行 | **0 行** |
| 生成耗时 P50 | 混杂失真 | **940.63 ms**（真实 LLM） |
| 端到端 P50 / P95 / max | 含 56.88 ms 的失真行 | **908.72 / 2392.43 / 2418.87 ms** |
| 端到端超 3000 ms 轮次 | 0 | **0** |

> 这条修正的意义不是「更快」，而是「**数字可信**」——
> 优化报告里最危险的不是慢，而是把缓存命中当成了真实性能。
