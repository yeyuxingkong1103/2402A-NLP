# RAG 功能测试及评估 · 测试报告

> 工单编号：人工智能NLP-RAG-功能测试及评估
> 测试对象：工单01~06 实现的 RAG 系统
> 语料：`附件/ccf_competition/` 的 9 份金融年报
> 问题来源：`附件/sample_questions.pdf` 示例问题 + 基于年报扩充

---

## 一、测试范围与目标

### 1.1 测试目标

工单要求：「基于 01-06 任务工单实现的 RAG，实现《ccf_competition.zip》中的 pdf 文件的
RAG 测试及检索评估任务」「使用《sample_questions.pdf》中的示例问题进行问题的整理及测试，
并通过评估框架进行检索结果的评估」。

落到可执行的三个目标：

| 目标 | 判定方式 |
|---|---|
| G1 系统能在金融年报语料上正常工作 | 语料解析成功、索引建立成功、10 个问题全部返回答案 |
| G2 检索结果与年报内容相关 | 每题标注应命中的源文档，统计 Hit Rate |
| G3 答案质量可量化 | RAGAS 四大指标 + 答案正确性 + 关键词命中式准确率 |

### 1.2 与工单06 的差异

工单06 的语料是**招股说明书**（2 份，548 页 / 约 200 页），本工单是**上市公司年报**
（9 份，每份数百页）。年报与招股书的差异恰恰是本工单要暴露的问题：

| 维度 | 招股说明书 | 上市公司年报 |
|---|---|---|
| 文档数量 | 2 份 | 9 份 |
| 单份篇幅 | 200~550 页 | 300~400 页 |
| 章节结构 | 高度规范（固定 10 节） | 基本规范但各公司编排不同 |
| 表格密度 | 中 | **极高**（财务附注占比过半） |
| 跨文档干扰 | 低（两家公司行业不同） | **高**（9 份年报都有「风险管理」「公司治理」等同名章节） |
| 文件名 | 规范 | **GBK 乱码** |

## 三、测试用例设计

### 3.1 问题来源

`sample_questions.pdf` 提供了 4 组示例问答：

| # | 问题主题 | 涉及文档 |
|---|---|---|
| S1 | xx银行 2019 年董事长致辞中提到的盈利增长关键因素 | 银行年报 |
| S2 | xx银行 2019 年年报提到的创新商业模式 | 银行年报 |
| S3 | 平安银行风险管理体系如何体现应对宏观经济周期波动的能力 | 平安银行年报 |
| S4 | 这些银行和保险公司面对经济周期波动的共同策略与差异化策略 | 多份年报（归纳型） |

### 3.2 扩充为 10 题

仅 4 题不足以覆盖不同的检索失败模式，因此按「题型 × 文档类型」两个维度扩充到 10 题：

| 题型 | 说明 | 考察的检索能力 |
|---|---|---|
| 数值型 | 问具体金额/比率/年份 | 表格与数字定位、数值精确性 |
| 事实型 | 问名称/人物/事项 | 单点事实定位 |
| 分析型 | 问「如何体现」「为什么」 | 跨段落信息聚合 |
| 归纳型 | 问「共同点/差异」 | **跨文档检索 + 多路召回** |

设计原则：**每题必须标注「应命中的源文档」**，否则无法计算 Hit Rate；
且要覆盖不同公司（银行 / 保险 / 证券各至少 2 题），避免只在单类文档上评估。

> 具体 10 题及参考答案见 `results/test_cases.json` / `test_cases.md`
> （由 `build_questions.py` 生成，会自动从年报原文中定位参考答案所在段落）。

## 四、测试执行

### 4.1 执行流程

```bash
cd 工单07-功能测试及评估/src
python prepare_corpus.py     # 1. 语料准备（含 GBK 文件名还原）→ results/corpus_stats.json
python build_questions.py    # 2. 构建测试集              → results/test_cases.json/.md
python run_rag_test.py       # 3. 执行 RAG 测试          → results/rag_test_results.json/.md
python run_evaluation.py     # 4. RAG 评估               → results/evaluation.json/.md
python analyze_problems.py   # 5. 问题分析               → results/problem_analysis.md
```

### 4.2 逐题结果

结果记录在 `results/rag_test_results.md`，每题包含：

| 字段 | 说明 |
|---|---|
| `question` | 问题原文 |
| `retrieved` | 检索到的片段列表：文档名 / 页码 / 分数 / 片段摘要 |
| `answer` | LLM 基于检索结果生成的答案 |
| `latency` | 端到端耗时（秒） |
| `hit` | 是否命中标注的源文档 |
| `keywords_hit` | 答案命中的关键信息点 |

### 4.3 评估指标汇总

由 `run_evaluation.py` 产出，记录在 `results/evaluation.md`：

| 指标 | 含义 | 判读标准 |
|---|---|---|
| `faithfulness` | 答案论断被上下文支撑的比例 | ≥0.85 表示基本无幻觉 |
| `answer_relevancy` | 答案切题程度 | ≥0.80 |
| `context_precision` | 检索片段中相关内容的排序质量 | ≥0.70 |
| `context_recall` | 标准答案信息被检索覆盖的比例 | ≥0.85 |
| `answer_correctness` | 答案与参考答案的一致度 | ≥0.70 |
| `hit_rate` | 命中正确文档的题目比例 | ≥0.90 |
| `mrr` | 正确文档首次出现的位次倒数均值 | 越高越好 |
| `latency_p95` | P95 响应时间 | ≤3.0 秒 |

> 指标定义与计算方法见 `评估方法说明.md`。

### 4.4 响应时间

工单性能验收要求「响应时间不超过 3 秒」。需说明的是：
**3 秒约束针对的是检索结果返回**，而 LLM 生成的网络往返通常就占 1.5~2.5 秒。
因此测试中同时记录两个口径：

- `retrieval_latency` —— 检索阶段耗时（不含 LLM 生成）
- `total_latency` —— 端到端耗时（含生成）

工单13 会针对后者做专项优化。

## 五、测试结论

### 5.1 达成情况

| 验收项 | 判定依据 | 结论 |
|---|---|---|
| 10 个问题体现 ccf 年报内容相关性 | 每题标注源文档并统计 Hit Rate | 见 `results/evaluation.md` |
| 使用 01-06 工单实现的 RAG 系统 | 直接复用 `rag_core.Pipeline` 的 `wo06_hybrid` 预设 | 满足 |
| 10 题的检索结果与评估结果 | `rag_test_results.md` + `evaluation.md` | 满足 |
| 检索结果存在的问题分析 | `problem_analysis.md` | 满足 |

### 5.2 已知局限

1. **4 组示例问题中的「xx银行」「yy银行」是脱敏占位符**，无法直接对应到具体年报。
   `build_questions.py` 通过「在年报全文中定位最匹配的段落」来还原真实主体，
   该还原过程本身可能引入偏差，已在 `问题分析与改进建议.md` 中列为问题类别之一。
2. **`sample_questions.pdf` 的参考答案较长且偏分析性**（如 S4 的答案近千字），
   与检索到的片段做 `context_recall` 比对时，因答案包含大量跨文档归纳内容，
   单次检索难以完全覆盖——这正是工单08 引入 Graph RAG 的动机。
3. **本报告中的指标数值需实际运行脚本产生**。仓库中 `results/` 仅含说明文件，
   未预置跑批结果，避免出现「未经运行就写死的指标」。

## 六、复现说明

```bash
# 前置：配置 DEEPSEEK_API_KEY
export DEEPSEEK_API_KEY="sk-xxxx"          # Windows: $env:DEEPSEEK_API_KEY="sk-xxxx"

# 前置：安装依赖
pip install -r requirements.txt

cd 工单07-功能测试及评估/src
python prepare_corpus.py && python build_questions.py \
  && python run_rag_test.py && python run_evaluation.py && python analyze_problems.py
```

预计耗时：语料解析与建索引约 15~25 分钟（9 份年报，表格解析较慢），
测试与评估约 10~15 分钟（10 题 × 多次 LLM 调用）。

> 提示：`rag_core.llm` 带磁盘缓存，重复运行不会重复计费。
