# 优化方案

## 1. 已落地优化

| 方向 | 已实现内容 | 价值 |
|---|---|---|
| 数据质量 | JSONL 规范化、异常隔离、同问去重、近似重复报告、业务分类 | 减少脏数据和重复向量 |
| 文档解析 | 解析器适配器与统一模型、多种分块策略 | 降低格式耦合，提升上下文完整性 |
| 索引一致性 | 文档 SHA256 去重、强制重建、元数据存储、删除向量 | 降低重复索引和数据漂移风险 |
| 检索 | Dense + BM25 混合召回、可配置 Top-K | 兼顾语义问题和关键词问题 |
| 重排序 | Lexical / 本地 / HTTP / Mock 多提供商 | 可按资源和精度选择方案 |
| 问答编排 | 标准与流式接口复用 `ChatService` | 避免两套逻辑产生差异 |
| 低相关兜底 | 相关性阈值和拒答话术 | 减少无依据生成 |
| 记忆 | Redis 短期记忆、Milvus 长期记忆、会话归档 | 支持多轮和跨会话信息 |
| 安全 | API Key、多租户服务端范围、限流、请求大小限制 | 降低未授权访问和资源滥用 |
| 可观察性 | `/health`、`/ready`、Prometheus 请求量/错误/延迟 | 支持运行状态诊断 |

## 2. 近期优先优化

### P0：部署与配置一致性

- 固化 Python、Milvus、Redis、MySQL 和关键 Python 包版本；
- 把 Conda CPU/GPU 依赖拆成可复现的环境文件；
- 将 Docker 依赖编排为固定 `compose.yaml`，避免运行时下载；
- 校对旧部署脚本中的默认密码、开放监听、日志配置和可选依赖；
- 生产环境统一由 Nginx/网关执行 TLS 和全局限流。

**验收指标**：新 Ubuntu 主机按文档一次安装成功；重启后服务自动恢复；不在仓库写入明文密钥。

### P0：索引与元数据一致性

- 将“元数据写入 + 向量写入”设计成可恢复操作；
- 增加失败补偿、删除重试和孤儿向量巡检；
- 为知识库删除、文档重建、并发重复上传增加幂等保证；
- 记录索引任务状态和失败原因。

**验收指标**：故障注入后不出现不可追踪的半成功文档；重复上传不会重复增加向量。

### P1：检索质量

- 基于真实客服数据建立离线评测集；
- 调优 Dense/BM25 融合权重、召回数量和阈值；
- 对订单号、产品型号、政策名称增加精确匹配通道；
- 比较 Lexical 与 BGE Reranker 的 NDCG、Recall@K 和延迟；
- 按知识库类别配置不同检索策略。

**验收指标**：用固定评测集报告 Recall@5、MRR、Faithfulness 和 Answer Relevancy，禁止只写主观“效果更好”。

### P1：性能与容量

- Embedding 批处理和连接池复用；
- 对相同规范化问题增加有版本失效机制的结果缓存；
- 调优 Milvus HNSW/IVF 参数，并记录数据规模对应配置；
- 为流式接口增加断连取消和超时处理；
- 对上传、问答和会话接口分别设置资源预算。

**验收指标**：给出 P50/P95/P99、吞吐量、错误率和资源占用，不使用未经实测的目标数字冒充结果。

### P1：可观察性

- 增加检索耗时、LLM 耗时、召回来源数、拒答率和缓存命中率；
- 为外部依赖增加超时、失败次数和熔断状态指标；
- 建立请求 ID，并贯穿 API、检索和 LLM 日志；
- 为敏感字段配置日志脱敏。

**验收指标**：一次请求可通过请求 ID 定位各阶段耗时；依赖异常有明确告警。

## 3. 中长期优化

- 将后台建库改为异步任务，避免大文档占用 API Worker；
- 引入版本化知识库和灰度切换，支持无停机重建索引；
- 加入人工反馈闭环，把低分问题进入评测集；
- 按租户隔离限额、索引和成本统计；
- 对 Prompt、模型、Embedding 和 Reranker 做可追溯版本管理；
- 支持结构化数据工具调用，但必须保持权限校验和审计。

## 4. 优化实施顺序

```mermaid
flowchart LR
    A[配置与部署可复现] --> B[索引一致性]
    B --> C[离线评测基线]
    C --> D[检索与重排调优]
    D --> E[性能容量优化]
    E --> F[监控告警与反馈闭环]
```

先建立可复现环境和客观基线，再做模型或参数调优；否则无法判断改动是否真正有效。
