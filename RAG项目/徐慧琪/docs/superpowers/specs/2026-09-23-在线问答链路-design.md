## 一、背景与本子项目的定位

子项目①把三册语料变成了 `law_articles.jsonl`（1260 条）与 `law_chunks.jsonl`（3388 块）；子项目②把块变成 MySQL 主数据 + Milvus 双向量索引，并跑通了 `hybrid_search()` 的 RRF 混合检索。

但②期交付的是**能检索**——调用方拿到的是一堆子块。本子项目交付的是**能回答**：一个问题进去，一条带引用的、过了独立校验的答案出来；并且这套东西第一次有了可重复的尺子（评估集 v0）。

选它作为第三个子项目的理由：需求文档 6.5 的一票否决项里，AC-2（条款号 100%）、AC-4（精排 top3 ≥ 85%）、AC-6（幻觉率 0）全落在这一层——它们不是"服务化了才需要满足"的指标，而是这层算法本身的性质。HTTP 只是壳，单列④不会被③的复杂度拖累。

**本子项目要一次撞掉的技术方案不确定项**：精排模型在本机的实际速度（②期遗留第 5 条的 8GB 显存问题）、qwen2.5:3b 的 JSON 合规率、以及"引用回查校验"在 `paragraph_no` 于 MySQL 恒 NULL 的现实下该怎么落（见 4.3）。

## 四、数据流与核心规则

```
问句 ──┬─► [query_parse] 抽"第X条" ──► [article_lookup] MySQL 精确查 ──┐
       │                                                              ├─► 合并置顶
       └─► bge-m3 双向量 ──► [hybrid_search] RRF 粗排 top50
                                     │
                            [backfill] 子→父、按 parent_id 去重
                                     │
                            [rerank] 父块精排，输入 top30、输出 top5
                                     │
                            prompt(profile) ◄───┘
                                     │
                            [llm_router] Ollama / DeepSeek
                                     │
                            [parser] → Answer{status, answer, citations, disclaimer}
                                     │
                            [cite_verify] 四关（存在性 / 效力 / 款号真实 / 原文子串）
                                     失败 → 重生成一次 → 仍失败 → 降级"未找到相关依据"
```

### 4.1 条款号精确通路（FR-3.2 / AC-2）

问句里用正则抽 `第([一二三四五六七八九十百零两0-9]+)条`，复用 `app/ingest/cn_num.py` 的 `cn2int()` 归一化（支持到千位，民法典最大 1260，够用），查 MySQL `article_no`。命中即作为"精确块"**置顶**，与向量召回结果合并去重。

两条边界：

- **条号超出 1~1260 不置顶**——问"第9999条"就该答没找到，不能编
- **一句里多个条号按出现顺序全部置顶**——"第584条和第577条"两条都要给

精确块的内容取 MySQL `article.text`（条级全文），与向量路的父块同构，下游无需分支。

### 4.2 检索三段式

| 步 | 做什么 | 参数 |
|---|---|---|
| 粗排 | `hybrid_search()`，dense+sparse 各 top50 → RRF(k=60) | 沿用②期的常量，本期不调参 |
| 回填 | 子块按 `parent_id` 取父块；同一父块的多个子块命中时，取**最高子块分**作为该父块的粗排分 | 一次批量查询，不逐条回表 |
| 精排 | 对**父块全文**打分，按粗排顺序取前 30 个父块，输出 top5 | `RERANK_INPUT_TOPK=30` / `RERANK_OUTPUT_TOPK=5` |
| 合并 | 精确块**不参与精排打分**，按问句出现顺序直接置顶，再拼上精排 top5，按 `article_no` 去重 | 见 4.1 |

**精排对象是父块而非子块**：技术方案 6.1 的提示词给的正是"父块整条，按精排顺序"，子块只承担召回职责。父块文本实测最长 400 字，`max_length=512` 装得下。

### 4.3 引用回查校验（本系统的安全阀）

技术方案 6.2 ① 写的是"查 MySQL 该 `(law_id, article_no, paragraph_no)` 是否存在"。**照字面实现是错的**：②期定的分工是 `paragraph_no` 在 MySQL 恒为 NULL（条级行），款/项编号留在 Milvus 的块级 payload 里——任何带款号的引用都会被误判失败。故落成四关：

| 关 | 判据 | 数据来源 |
|---|---|---|
| ① 存在性 | `law_id + article_no` 在 `article` 表存在 | MySQL |
| ② 效力 | 该 `law_version` 的 `status = 现行有效` | MySQL `law_version` |
| ③ **款/项号真实存在** | 款号 ≤ 该条实际款数；项号 ∈ 该条实际项号集合 | **查 Milvus 该条的全部子块**（非召回结果） |
| ④ 原文子串 | `quote` 归一化后是**该条原文**归一化后的子串，且长度 ≥ 10 字 | MySQL `article.text` |

第③关的比对口径要与②期的存储口径对齐：Milvus 里 `item_no` 存的是**光杆中文数字**（存「一」不存「（一）」），故引用的项号须先剥掉「（一）」括号再比对；条级引用（无款无项）视为合法。第④关的"归一化"口径是**剔除全部空白字符**（含全角空格 `　`、换行、制表符），标点保持敏感——太宽会把编造放过，把标点也抹平则会把"逗号写成句号"的改写放过。

**第③关查全量而非召回集，是为降级率着想**：若只比对"这一轮召回回来的子块"，那么模型正确引用了"第二款"、而第二款的子块恰好没进 top5 时，一条**正确的**引用会被判失败并把整段答案送进降级——假拒绝比漏放更伤，因为它直接推高 4.4 的降级率。**单款条的特例**：某条在 Milvus 里没有 paragraph 子块时，"第一款"视为合法（实务上整条即一款），"第二款"及以后仍判失败。

三处刻意的口径选择：

1. **第③关是新增的**（技术方案只有存在性/效力/子串三关）。款号是典型幻觉位——模型写"第584条第三款"而该条只有两款时，纯子串匹配抓不住；而款/项的真实编号恰好就在 Milvus payload 里，不用是浪费。
2. **第④关的基准取 MySQL `article.text`，不取"召回父块"**。技术方案写的是召回父块，但召回块就是喂给模型的输入，让它自证有循环之嫌；MySQL 的条级原文与生成通路完全独立，且不依赖"召回里恰好取回了父块"。同一份文本，取更独立的那份来源。
3. **`quote ≥ 10 字`** 是防止模型拿"的""可以"这类两字片段骗过子串匹配。

第②关**必须真查库**，不能因为"本期只有一个版本、状态是现行有效"就硬编码成常量——硬编码会让法规更新后安全阀静默失效。召回侧虽然已按 `status == "现行有效"` 过滤，但校验侧独立查 MySQL 正是 FR-4.3"独立校验通路"的意义所在。

### 4.4 输出边界与降级

| 处理 | 落法 |
|---|---|
| 拒答（FR-8.3：能不能赢 / 帮我写诉状 / 替我代理） | **纯规则匹配**，且在**检索之前**判定——命中即返回 `status="out_of_scope"` 与引导话术，一次检索与一次生成都省下。不交给模型判断：合规项不能靠模型心情 |
| 追问补齐、非法律、紧急（FR-8.5、FR-8.6） | 交给提示词，输出 schema 带 `status: ok \| need_more_info \| out_of_scope`，编排层只做路由 |
| 公众侧免责声明（FR-8.4、AC-18） | **由代码强制注入**，模型输出的 `disclaimer` 字段被覆盖 |
| 法条原文与 AI 解读分区（FR-4.4） | 输出结构里原文来自召回块、解读来自 `answer` 字段，前端按字段渲染（③a 只保证字段分离） |

**降级链**：JSON 解析失败 **或** 引用校验失败 → 丢弃整段答案 → 带"上次未通过"提示**重生成一次** → 仍失败 → 输出"未找到相关依据"并记录。

**粗排零结果时不调模型**，直接返回"未找到相关依据"——省一次调用，也断了模型自由发挥的念想。

### 4.5 路由与两侧差异

| | 律师侧 | 公众侧 |
|---|---|---|
| 模型 | `ChatOllama(model="qwen2.5:3b", temperature=0.1)` | `ChatOpenAI(base_url="https://api.deepseek.com/v1", model="deepseek-chat", temperature=0.1)` |
| 密钥 | —— | `os.environ["api"]`，**缺失即抛错，不静默降级到本地模型** |
| 提示词差异 | 可给可直接写入文书的引用格式（FR-7.4） | 禁个案结论、不预测胜诉、必带风险提示（FR-8.3、FR-8.4） |
| 结构化输出 | Ollama `format="json"` + `PydanticOutputParser` 双保险 | DeepSeek `response_format={"type":"json_object"}` |

**为什么缺密钥要抛错而不是降级到 Ollama**：静默换模型会让"公众侧走外部 API"这条已定稿口径（技术方案 9.6）名存实亡，且排查时看不出来。

**输出 schema**（Pydantic）：

```
Answer{  status: "ok" | "need_more_info" | "out_of_scope"
         answer: str
         citations: [Citation{ law, article, paragraph?, item?, quote }]
         disclaimer: str }
```

`status` 的三值是**模型可选**的；另有 `status="error"`（LLM 不可用）与 `status="abstain"`（校验失败降级）由编排层**单方面赋给调用方**，模型无权输出——否则模型可以自称"未找到依据"来绕过校验关。用户原始问题用定界符包裹后放进 human 消息（防提示注入，技术方案 9.4）。

### 4.6 评估集 v0（需求 6.3、技术方案 12.1）

`data/eval/qa_eval_v0.jsonl`，100 条：**60 律师题 + 40 公众题**。

| 字段 | 说明 |
|---|---|
| `id` / `side` / `query` | 题号、侧别、题面 |
| `gold_articles` | 标准条款号（整数列表） |
| `category` | 语义改写 / 条款号直问 / 易混条对 / 公众口语化（覆盖租房、消费、劳动、借贷、婚姻家庭五类） |
| `source` | 恒为 `ai_draft` |

**逐条标注未经律师核。** 评测报告里必须写明：本集由 AI 照法条内容起草，属"看着答案出题"，**只能作回归基线，不得作为召回率依据**——技术方案 12.1 要求的"执业律师抽检后冻结"仍是待办（见第九节）。

文件冻结后算 MD5，评测报告记录该 MD5；中途改标注必须重算并在报告里体现差异。

## 五、模块划分

| 文件 | 职责 | 明确不做 |
|---|---|---|
| `app/retrieval/query_parse.py` | 从问句抽条款号并归一化 | 不查库 |
| `app/retrieval/article_lookup.py` | MySQL 精确取条（含效力状态） | 不算分、不排序 |
| `app/retrieval/backfill.py` | 子块 → 父块，按 `parent_id` 去重 | 不重排 |
| `app/retrieval/rerank.py` | CrossEncoder 封装，父块打分取 topK | 不调 Milvus |
| `app/retrieval/pipeline.py` | 串起上述四步 + 精确块置顶 | 不碰 LLM |
| `app/generation/profiles.py` | 两侧 system prompt 与差异 | 不管调用 |
| `app/generation/llm_router.py` | 按侧返回 ChatOllama / ChatOpenAI | 不写 prompt |
| `app/generation/schema.py` | `Answer` / `Citation` 的 Pydantic 定义 | 无逻辑 |
| `app/generation/cite_verify.py` | 四关校验（纯函数 + 注入的查询器） | 不调模型 |
| `app/generation/boundaries.py` | 拒答规则、免责注入、status 路由 | 不调模型 |
| `app/generation/chain.py` | LCEL：`prompt \| llm \| parser`（+ 校验 lambda） | 不写业务规则 |
| `app/generation/answer.py` | 编排：检索 → 生成 → 校验 → 重生成 → 降级 | 无 HTTP 概念 |
| `tools/ask.py` | CLI 冒烟 | —— |
| `tools/eval_qa.py` | 评估集打分与报告 | —— |

**分层依据**（技术方案 2.2）：LangChain 只做编排与连接，业务规则自研并保持可单测。故 `cite_verify` 的输入是"答案对象 + 召回块 + 一个注入的 MySQL 查询函数"——测试时塞假查询器即可，不必起库；`rerank` 的模型是构造参数，单测不必加载 2.2GB。

**编排层选 LCEL 的边界**（本期定的 A1 混合）：生成段落成 `prompt | llm | parser`，校验写成自研 `RunnableLambda` 串在链尾；但**重生成与降级这两个分支留在 Python 编排里**，不硬塞进 LCEL——`with_fallbacks` 表达"带原因重试一次再降级"会把可读性吃掉。

**300 行约束**：每个文件各自远低于上限；`chain.py` 是唯一有触线风险的（技术方案 2.2 摩擦点 4 已预警，提示词正文放 `profiles.py`）。

## 六、错误处理

| 场景 | 处理 | 理由 |
|---|---|---|
| 粗排零结果 | 不调模型，直接"未找到相关依据" | 见 4.4 |
| MySQL / Milvus 连不上 | 抛错，不降级 | 降级成"凭记忆回答"是绝对红线 |
| 精排模型加载失败 | 抛错，不静默跳过精排 | 静默降级会让 AC-4 的达标与否无法解释 |
| LLM 超时 / 连不上 | `status=error`，**与"未找到相关依据"区分** | 模型不可用 ≠ 没有依据；④期 HTTP 层要映射成 5xx 而不是 200 的假答案 |
| JSON 解析失败 | 重生成一次 → 降级 | 3b 模型一次不合规就废掉整条答案太脆 |
| 引用校验失败 | 重生成一次 → 降级 | 技术方案 6.2 |
| 条款号超范围 | 不置顶，正常走向量路 | 见 4.1 |
| 缺 DeepSeek 密钥 | 抛错 | 见 4.5 |
| 降级（重生成仍失败） | `status="abstain"` + 输出"未找到相关依据" + 结构化日志 | 与 `status="error"` 分开；审计表在④ |

## 七、与《技术方案》的偏离

## 八、测试策略

延续「真实语料做夹具，不造数据」的项目约定。

| 层次 | 内容 | 依赖 |
|---|---|---|
| 纯函数单测 | 条款号抽取与归一化、四关校验、拒答规则、免责注入、输出 schema 解析、评估指标计算 | 无 |
| 集成测 | `article_lookup` 真查 MySQL；`backfill` 真查 Milvus；`pipeline` 端到端检索；`rerank` 真模型打分 | MySQL + Milvus（+ 模型） |
| 冒烟 | `tools/ask.py` 人工看答案与引用；`tools/eval_qa.py` 出报告 | 全套 |

**测试必须能失败**（项目已有八次「不可能失败的测试」的前车之鉴）：校验类是这类问题最高发的形态——喂进去的假数据恰好能过，测试永远绿。因此每道校验关**至少配一条"应当被拒绝"的用例**：编造条号、编造款号、改写原文、已废止条文各一。且写完要用**忠实变异**验一次：把校验实现改坏，测试必须变红；改不红说明那条测试是摆设。

模型替身的使用边界：单测里 LLM 一律用假对象（不连云、不连 Ollama）；但**四关校验与降级编排的用例必须包含真实形态的输入**（真实的条原文、真实存在的款号与不存在的款号），否则假数据会掩盖"款号集合取错了表"这类真问题。

## 九、遗留事项

1. **评估集 v0 未经律师核**——需求 6.3 要求"执业律师抽检后冻结"，本集是 AI 起草。所有召回率类结论只作回归基线（见 4.6）
2. **AC-6 的幻觉率 0 是"拦截后"口径**——达标靠四道校验关，不靠模型。因此**降级率**才是③a 最该盯的健康指标：qwen2.5:3b 若把大半答案都送上降级路径，指标虽好看而系统不可用。冒烟报告须把它当一等公民打印
3. **AC-12/13 延迟**——依赖 4G 显存上的两家模型共存实测；若 Ollama 与精排抢显存导致互斥，需回到"精排候选数压缩 + CPU"的退路
4. **多轮上下文缺席**——③a 的单轮质量与④期接上 Redis 后可能不同，评估集应在④期重跑一次
5. **技术方案 9.6 的出站过滤器缺席**——③a 外发内容仅"问题 + 民法典公开片段"，本就落在 9.6 允许集合内；但③b 接案卷语料前必须补上，否则 AC-16 无证据
6. **`requirements.txt` 钉了一个不存在的 PyMySQL 版本**——2026-09-23 实测 `pip index versions PyMySQL`：可用版本最高 **1.2.3**，**没有 2.x**。文件里的 `PyMySQL==2.2.8` 是②期写错的，实装的 1.2.3 才对。修法很轻（改一行常量），随本期 Task 1 一并订正，不单开任务
