## 一、准确率优化

### 1.1 加权 RRF 的隐蔽缺陷（影响 Q1、Q5）

**现象**：Q1「军用领域收入」与 Q5「组织结构图销售处」都答"未找到相关内容"，但 BM25 通道明明排第 1。

**定位**：分阶段打印两路召回与融合结果，得到：

```
Q5  BM25 通道 命中目标? True   score=42.65（第 1 名）
Q5  向量通道 命中目标? False
Q5   融合后 命中目标? False          ← 目标在融合阶段消失
```

**根因**：两路各取 20 条时，RRF 的取值范围是 `[1/(60+20), 1/(60+1)] ≈ [0.0125, 0.0164]`。

- 乘 `VEC_WEIGHT=0.7` → `[0.0088, 0.0115]`
- 乘 `BM25_WEIGHT=0.3` → `[0.0038, 0.0049]`

**两段区间完全不相交**。结果是"BM25 排第 1 的块"永远打不过"向量排第 20 的块"——关键词通道被彻底架空，
而 Q1 的金额、Q5 的部门名恰恰只有 BM25 能精确命中。

**修复**：先把每个通道的 RRF 在**通道内**线性归一化到 `0~1`（第 1 名 = 1，最后一名 = 0），再乘权重相加。
这样权重才真正表达"通道重要度"，不会因名次偏移互相压制。

**实测效果**：

| 问题 | 修复前融合名次 | 修复后融合名次 | 修复后重排名次 |
| --- | --- | --- | --- |
| Q1 军用收入 | 不在前 20 | 第 12 / 30 | **第 1**（0.9952） |
| Q5 组织结构图 | 不在前 20 | 第 11 / 30 | 前 8 |

> 修复过程中还发现归一化公式写反（`(hi - rrf)` 应为 `(rrf - lo)`），导致排序完全颠倒。
> 教训：**排序类改动必须打印前后名次核对**，只看"有没有结果"是发现不了的。

### 1.2 标题启发式误杀关键行（影响 Q4）

**现象**：Q4「那武汉力源信息技术股份有限公司呢？」回答"法定代表人是**胡戎**"（关联公司融冰投资的法定代表人），正确答案是**赵马克**。

**定位**：直接在索引里检索"法定代表人 + 赵马克"：

```
索引中 法定代表人+赵马克 的块: 0    ← 正确答案根本不在索引里
含 法定代表人胡戎 的块:      7      ← 却存在
```

回查 MinerU 原始产物，发现正文中确实存在：

```
idx 130  page 14  text  '4、法定代表人：赵马克'
idx 229  page 22  text  '4、法定代表人：赵马克'
idx 255  page 24  text  '1、法定代表人：赵马克'
```

**根因**：分块器把"章节/条号开头的短行"一律当作标题丢弃（只留作语境）。
`4、法定代表人：赵马克` 形态上完全符合标题正则，于是**把最关键的事实从索引里删掉了**。
系统检索不到正确依据，只能召回**其他公司**的同名条目，于是答错。

**修复**：标题判定增加"不含冒号"条件——含冒号的是键值内容，必须保留为可检索块。

**实测效果**：索引中出现 3 个含"法定代表人+赵马克"的块，Q4 正确回答赵马克（引用 P23/P25/P15）。

### 1.3 短行碎片化（影响 Q4）

**现象**：即使把 `4、法定代表人：赵马克` 保留下来，它也只有 **12 个字符**——向量被稀释、BM25 只有一两个词命中，
重排得分很低，仍进不了前 8，而且**行内不含公司全称**，无法与"某公司的法定代表人是谁"对齐。

**修复**：新增 `merge_short_blocks()`，把**连续的同页短文本块**合并成一段（上限 512 字符）。
合并后得到完整段落：

```
【招股说明书2·(四)主要财务指标】第三节 本次发行概况
一、发行人的基本情况
1、公司名称：武汉力源信息技术股份有限公司
2、英文名称：Wuhan P&S Information Technology Co.,Ltd.
3、注册资本：人民币 5,000 万元
4、法定代表人：赵马克
5、公司成立日期：2001年8月9日
...
```

**实测效果**：分块总数 5790 → **3583**；Q4 的三条依据块重排得分 **0.9992 / 0.9990 / 0.9980**，稳居前 3。

### 1.4 章节语境失效（影响 Q5）

**现象**：修完 1.1 后 Q5 一度又答不出来。打印重排明细发现组织结构图块挂在错误的章节名下：

```
0.6183  招股说明书2-02283  p 39  image
'【招股说明书2·(五)机构独立】【图片内容：组织结构/流程图】\n股东大会 下辖：监事会、董事会\n...'
            ↑ 错误：这一节在第 251 页，与本页（第 39 页）无关
```

**根因**：1.3 的合并逻辑把**标题行也吞进去了**，于是 `chunk_blocks` 里的"章节语境"再也更新不到，
图片块就一直挂着几页之前的陈旧章节名。用错误的章节名去重排，得分自然低。

**修复**：抽出 `is_heading()` 统一判定，标题行**不参与合并**（既保留章节语境，又不进检索）。

**实测效果**：组织结构图前缀恢复为 `【招股说明书2·1、公司组织结构图】`，随后稳定进入重排前 8，Q5 正确作答。

### 1.5 缓存会复用错误答案（正确性隐患）

**现象**：修好 1.2/1.3 并重新入库后，Q4 **仍然**返回旧的错误答案"胡戎"，且 `cached=true`。

**根因**：缓存键只包含 `问题 + 历史摘要 + 代码指纹`，**不含知识库版本**。
知识库换了，但键没变，于是旧缓存把新结果挡住了。

**修复**：新增 `index_fingerprint()`——对 `data/index.json` 与 `data/bm25.pkl` 做内容哈希并加入缓存键。
重新入库即自动换键，不需要人工清缓存，也不会忘记清。

> 这与设计文档 §7 描述的"结构指纹"是同一类问题的两个面：库变了要换键，代码变了也要换键。
> 两者都必须是**自动**的——任何依赖人工记得升版本的机制，迟早会被忘记。

## 二、响应时间优化

**目标**：≤3 秒。**验收口径**：从用户提问到返回答案。

### 2.1 分阶段计时定位首问耗时

对"首问"与"第二问"分别打点：

```
第1问: 改写 3127ms  检索 542ms  重排 912ms  生成 635ms  合计 5216ms
第2问: 改写  311ms  检索  35ms  重排 671ms  生成 978ms  合计 1995ms
```

首问的额外开销**全部在 Query 改写上**（3127ms vs 311ms）。拆开是两个原因：

| 原因 | 说明 | 修复 |
| --- | --- | --- |
| 大模型首次建连 | DNS + TLS 握手 + 连接池初始化，实测约 3.1 秒 | `deepseek_llm.warmup()`：启动时发一次 `max_tokens=1` 的调用 |
| 首轮白跑一次改写 | 见 2.2 | 修短路条件 |

### 2.2 首轮改写短路失效（设计缺陷）

设计里有一条短路规则：**首轮 + 问句自带实体 + 无指代词 → 不改写，直接检索**。
但实现时把"本轮问题"在改写**之前**就写进了会话历史，导致 `history` 永不为空，**短路条件永远不成立**——
每一轮的首问都白跑一次大模型改写。

**修复**：改写只看"之前几轮"的历史（本轮问题是通过参数单独传入的），改写完成后再把本轮问句写入历史。
缓存命中分支则照旧推进历史，保证多轮连续。

### 2.3 预热形状不对（第一次没修好）

第一版预热只做了"加载模型 + 用一个 4 字样本跑一次"，结果首问仍是 **5775ms**。
原因是**预热样本的形状与真实请求差太远**：真实请求要处理"30 条 × 约 500 字"的候选，
CUDA 仍要为这个新形状重新编译/选核。

**修复**：按真实规模预热——向量侧 32 条、重排侧 30 对 × 约 512 字。

### 2.4 优化后的实测结果

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 最大响应时间 | 6915 ms | **2755 ms** |
| 平均响应时间 | — | **2132 ms** |
| 3 秒内完成比例 | 0.6 ~ 0.9 | **1.0（10/10）** |
| 缓存命中响应时间 | — | **0 ~ 1 ms** |

分阶段耗时（稳态）：改写 0.3s + 检索 0.04s + 重排 0.7s + 生成 1.0s。

## 三、缓存优化

| 项 | 做法 | 实测 |
| --- | --- | --- |
| 答案缓存 | 键 = 代码结构指纹 + **知识库指纹** + `问题 + 历史摘要 + 召回参数` | 命中 0~1ms |
| 会话历史 | `chat:{sid}:history`，`LTRIM` 只留最近 6 轮 | 保证多轮连续且不无限膨胀 |
| 会话实体 | `chat:{sid}:entity` | 支撑"他/这个公司"与实体切换 |
| 长任务中间结果 | 图像 OCR 结果缓存 `data/image_texts.json`；分块缓存 `data/index.json` | 图像阶段 150s 在重建时**全部复用** |
| 评测结果 | **先落盘再算指标** | ragas 出错也不会丢掉已跑出的问答结果 |
| 熔断 | 重排加载失败后不再重试加载 | 避免每次请求都卡在加载上 |

### 缓存键的两个指纹（都是自动生成，不靠人工升版本）

1. **代码结构指纹**：对 `config.py / schemas.py / deepseek_llm.py / hybrid_retriever.py / reranker.py / query_rewriter.py` 的源码做哈希。
   起因：曾出现 `degraded` 字段被旧缓存**静默吞掉**，导致发生了降级却没有任何提示。
2. **知识库指纹**：对 `index.json` 与 `bm25.pkl` 做内容哈希（见 1.5）。

## 四、重排优化

| 项 | 做法 | 原因 |
| --- | --- | --- |
| 打分输入截断 | `RERANK_MAX_CHARS=512` | 整表块可达数千字，不截断会把"成对打分"的 padding 开销放大数倍；**只截打分输入，不改交给大模型的原文** |
| 候选量 | `FUSION_TOP_K=30`、`RERANK_TOP_N=8` | 目标块常在融合第 11~16 名（实测 Q1 第 12、Q5 第 11），候选太窄会直接漏掉 |
| 降级 | 模型不可用 / 打分异常 → **回退混合检索原始排序**，并上报 `degraded=["rerank"]` | 重排是增强项，不该成为单点故障 |
| 耗时 | 约 0.7s（30 对候选） | |

## 五、Query 改写优化

| 项 | 做法 | 实测效果 |
| --- | --- | --- |
| 短路 | 首轮 + 自带实体 + 无指代词 → 不改写 | 省掉一次大模型调用（首问省约 3 秒） |
| 实体表 | 入库时从正文统计公司全称，长名优先匹配 | `武汉力源信息技术股份有限公司` 不会被短名抢先命中 |
| 实体追踪 | 识别到与上轮不同的实体即判定为**切换**并立即更新 | Q4 正确从兴图新科切到力源信息 |
| 主题继承 | "那X呢" → 新公司 + 上一轮的问题主题 | Q4 改写为"武汉力源信息技术股份有限公司的法定代表人是谁？" |
| 提示词 | 明确"只输出改写后的问句本身"，`temperature=0`、`max_tokens=120`、超时 12s | 输出稳定、耗时可控 |
| 规则兜底 | 大模型不可用 → 上轮问句模板 + 实体替换，上报 `degraded=["rewrite"]` | 改写故障不阻断问答 |

**多轮改写实测**（工单 5 问）：

| 轮次 | 原始问句 | 改写后 |
| --- | --- | --- |
| Q1 | 报告期内，武汉兴图新科…军用领域的收入分别是多少？ | 原句（短路，不改写） |
| Q2 | 他参与的哪个工程荣获了国家科技进步一等奖？ | 武汉兴图新科电子股份有限公司参与的哪个工程荣获了国家科技进步一等奖？ |
| Q3 | 这个公司的法定代表人是谁？ | 武汉兴图新科电子股份有限公司的法定代表人是谁？ |
| Q4 | 那武汉力源信息技术股份有限公司呢？ | 武汉力源信息技术股份有限公司的法定代表人是谁？ |
| Q5 | 武汉力源…组织结构图中… | 原句（自带实体） |

## 六、入库性能优化

| 问题 | 实测 | 修复 |
| --- | --- | --- |
| 并发抢显存 | 两个进程同时跑时，入库 **86s → 13 分钟以上**，GPU 显示 100% 看不出异常 | 重任务串行；并给入库加**每批进度输出**，让"慢"与"卡死"可区分 |
| 超长表格块 | 单块最大 **5550 字符** | `split_atomic()` 按行拆分到 ≤900 字符，并为每段补首行表头，保证每段能自证属于哪张表 |
| 无进度输出 | 缓冲导致日志长时间为空，无法判断状态 | 全部改为 `flush=True` 的进度输出 |

## 七、评估流程优化（保证数字可信）

| 问题 | 症状 | 修复 |
| --- | --- | --- |
| 判官参数传错层 | `bypass_n` 被透传给 `Completions.create()`，10 条样本全失败，四项指标**静默变成 `null`** | 移除该参数（本版本 ragas 走 instructor，不再需要 `n>1`）；`AnswerRelevancy(strictness=1)` 减少调用 |
| 结果文件选错 | `glob("eval_*.json")` 把 `eval_warm_*.json`（缓存命中组，仅 5 条）当成最新结果，`n_samples` 静默变成 5 | 排除 `eval_warm_*` 前缀 |
| 缓存污染耗时 | 重复评测全部命中缓存，响应时间被"优化"到 32ms 这种假数据 | 评测默认 `use_cache=False`；另跑一组开缓存，单独报告命中耗时 |
| 上下文被截断 | ragas 只拿到前端展示用的 260 字 snippet，`context_recall` 被截断副作用压低到 **0.3333** | 评测改用**完整片段**；修复后 **0.80** |
| 判分器未被验证 | 关键词判分抓不到"多答无关内容" | 加入负样本 `expect_not`，并提供 `--selftest` 用已知错误答案回验判分器（5/5 通过后才采信准确率） |
| 指标噪声 | 指标本身有噪声底 | 本报告不做"±0.0x 即改进"的结论；所有结论都对应可复现的**定性**变化（答对/答错、名次、毫秒） |
