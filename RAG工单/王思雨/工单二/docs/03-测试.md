## 2. 判分口径（先定口径，再跑数据）

| 指标 | 定义 |
|---|---|
| **回答准确率** | 答案**同时包含该题全部关键字段**（`data/eval/questions.json` 的 `expect`）的题数 ÷ 10。比对前去掉空白与中英文逗号并转小写，避免 `5,520` 与 `5520` 这类格式差异被误判为答错 |
| **检索上下文命中率** | 检索返回的上下文文本中**已包含该题关键字段**的题数 ÷ 10。衡量「检索有没有把答案捞上来」，与生成质量解耦 |
| **出处页命中率** | 检索上下文的页码区间**覆盖标准答案出处页**的题数 ÷ 10 |
| **响应时间** | 从进入问答主流程到返回答案的端到端耗时（含检索、重排、生成），**每题关闭缓存**，测真实耗时 |
| **RAGAS 四项** | `faithfulness`、`answer_relevancy`、`context_precision`(`LLMContextPrecisionWithReference`)、`context_recall`(`LLMContextRecall`)；判官为 DeepSeek，嵌入为本地 bge-m3 |

**测试前先预热一次问答链路**：首次调用含模型加载（bge-m3 约 10 秒、重排模型约 5 秒），
预热后的数据才代表稳态响应时间。这一点已固化在 `evaluate.main()` 里。

## 3. 优化前后总体对比（工单产出物一）

| 指标 | 优化前（baseline） | 优化后（optimized） | 变化 |
|---|---|---|---|
| **回答准确率** | 0.60（6/10） | **1.00（10/10）** | **+40 个百分点** ✅ 目标 ≥90% |
| **检索上下文命中率** | 0.70 | **1.00** | +30 个百分点 |
| **出处页命中率** | 0.30 | **1.00** | +70 个百分点 |
| 平均响应时间 | 1.769 s | 2.455 s | +0.69 s（检索更深、多了重排） |
| 最大响应时间 | 2.210 s | 3.043 s | 见 §6 说明 |
| 3 秒内完成比例 | 1.00 | **0.90（9/10）** | 见 §6 说明 |
| faithfulness | 0.6667 | **1.0000** | +0.33 |
| answer_relevancy | 0.6167 | **0.8585** | +0.24 |
| context_recall | 0.7000 | **1.0000** | +0.30 |
| context_precision | 0.8667 | **0.9867** | +0.12 |

**结论**：
1. **回答准确率 100% ≥ 90%** —— 达标；
2. **检索精确度显著提升**：上下文命中率 0.70 → 1.00，出处页命中率 0.30 → 1.00，RAGAS 四项全部提升（其中两项满分）；
3. **响应时间**：10 题中 9 题 ≤3 s，平均 2.455 s；唯一的 3.043 s 超出 0.04 s，原因见 §6。

> 优化后耗时高于优化前属预期——优化前只做一次向量检索（约 20 ms）就交给大模型，
> 省下的时间换来的正是准确率从 60% 到 100%。

### 4.3 优化后仍值得注意的地方

- **id 531**：优化后只回「程家明」三个字，信息正确但不如优化前完整。
  生成侧要求「简洁」，短答案容易被压到极简；不影响正确性判定，但演示时观感一般。

## 6. 响应时间明细（工单性能验收第 1 条）

**优化后逐题耗时（秒）**：

| id | 260 | 95 | 33 | 34 | 957 | 793 | 795 | 543 | 531 | 207 |
|---|---|---|---|---|---|---|---|---|---|---|
| 端到端 | 2.45 | 2.12 | 2.04 | 2.53 | **3.04** | 2.40 | 2.25 | 2.67 | 2.65 | 2.40 |
| 检索+重排(ms) | 1069 | 768 | 759 | 764 | 773 | 983 | 760 | 766 | 942 | 776 |
| 生成(ms) | 1378 | 1351 | 1286 | 1763 | **2270** | 1418 | 1489 | 1905 | 1709 | 1619 |

- 平均 **2.455 s**，10 题中 **9 题 ≤ 3 s**；
- **检索+重排稳定在 0.76～1.07 s**，方差很小，这是系统自己可控的部分；
- **生成 1.29～2.27 s**，全部 10 题里最长的一次（id957 的 2270 ms）正是唯一超过 3 秒的那题。

### 6.1 关于那一次 3.043 s（如实说明）

超出 0.04 s 的这题不是检索慢（检索 773 ms，属正常范围），而是**大模型 API 当次响应偏慢**。
为验证这一判断，评测结束后做了对照测量：

| 测量时间 | 检索+重排 | 生成 | 端到端 |
|---|---|---|---|
| 正式评测（11:20 前后，10 题） | 0.76～1.07 s | 1.29～2.27 s | 2.04～3.04 s |
| 同一环境 30 分钟后（3 题 × 2 轮） | 0.96～1.08 s | **2.79～3.21 s** | 3.87～4.26 s |

**检索耗时两次测量几乎不变（约 1.0 s），生成的耗时翻了一倍以上**。
结论很清楚：端到端时间的长尾由 DeepSeek API 的在线响应波动决定，不由本项目代码决定。
本项目可控部分是检索+重排（≤1.1 s）与缓存。

**可用的对策**（已实现的部分见 `05-部署.md`）：

1. **Redis 缓存**：同一问题第二次提问实测 **0.00 s**（未缓存 2.44 s）——高频问题场景下 3 秒目标有充足余量；
2. `LLM_TIMEOUT=20` 秒 + `max_retries=1`：API 异常时快速失败并返回友好提示，不拖死请求；
3. 上下文只送 6 条、`max_tokens=512`：已是本方案对生成耗时的可控优化；
4. 若必须在任何 API 状态下都压到 3 秒内，可换用本地部署模型或与供应商确认 SLA——这超出本工单范围。

## 7. 并发与稳定性测试（工单性能验收第 2 条）

**未缓存（最坏情况）**，4 个不同问题并发请求 `/api/ask`：

| 并发数 | 成功 | 墙钟 | 单请求平均 | 单请求最大 | 全部 ≤3 s |
|---|---|---|---|---|---|
| 1 | 1/1 | 3.97 s | 3.96 s | 3.96 s | 否 |
| 4 | 4/4 | 5.78 s | 4.32 s | 5.78 s | 否 |
| 8 | 8/8 | 9.41 s | 7.82 s | 9.40 s | 否 |

**已缓存（生产高频路径）**：

| 并发数 | 成功 | 墙钟 | 单请求平均 | 缓存命中 |
|---|---|---|---|---|
| 4 | 4/4 | 0.05 s | 0.027 s | 4/4 |
| 8 | 8/8 | 0.05 s | 0.024 s | 8/8 |

**结论（如实说明）**：

1. **稳定性达标**：并发 1/4/8 下**零失败、零异常**，进程不崩溃，符合「高并发下稳定运行」；
   并发 8 时单请求平均 7.82 s，但请求全部成功返回正确答案。
2. **并发下时延上升有两个原因**：
   - bge-m3 编码与重排在同一块 8 GB GPU 上串行执行，并发请求互相排队；
   - 上表测量时段的 API 生成耗时本身已达 2.8～3.2 s（见 §6.1），并非并发导致的额外增长。
3. **缓解手段**：高频问题走 Redis 缓存（并发 8 实测单请求 0.024 s）；
   生产环境在上游网关按容量限流；必要时下调 `FUSION_TOP_K` / `RERANK_TOP_N` 线性降低单请求算力占用。

| **DeepSeek 不可用** | `LLM_BASE_URL=http://localhost:19999` | 系统繁忙或依赖服务暂时不可用，请稍后重试。（error=InternalServerError） | ✅ |
| **缺 API Key** | `DEEPSEEK_API_KEY=`（空） | 未配置 DEEPSEEK_API_KEY，请参考 .env.example 配置后重试 | ✅ 明确指引 |
| MinerU 解析失败 | 解析器内部异常 | 自动降级 PyMuPDF/pdfplumber 并打印 `[解析降级] MinerU 失败：…` | ✅ 链路继续可用 |

> 「Milvus/Redis/DeepSeek 不可用」用**环境变量指向错误地址**模拟，未停掉正在运行的容器，
> 因此这些场景的耗时包含子进程冷启动加载模型的时间（10～23 s），**耗时不作时延结论**，
> 结论只针对「返回友好提示、不失稳、不崩栈」。

**测试中发现并修复的一个缺陷**：缺 API Key 时，模块自己抛出的中文提示
「未配置 DEEPSEEK_API_KEY…」被通用兜底分支吞掉，统一变成了「系统繁忙」。
已修复：`RuntimeError`（本模块自己抛的可读提示）直接透出，其他异常才用通用文案
（见 `src/rag_pipeline.py` 的 `answer()` 异常分支）。

**另一次测试中发现的假象（记录备查）**：在 Git Bash 里用
`curl -d '{"question":"中文问题"}'` 提问时，中文参数被按本地代码页编码传输，
服务端收到乱码问题，于是正常地返回「资料中未找到相关信息」。这不是程序缺陷——
用 UTF-8 明确编码的客户端（Python `urllib`、浏览器界面、`curl --data-binary @file.json`）均正常。
演示时若用 curl，请把 JSON 写入文件再 `--data-binary @q.json`。

**遗留与已知限制**

1. 端到端耗时的长尾由在线 DeepSeek API 决定（实测同一环境 30 分钟内生成耗时从 1.4 s 涨到 3.2 s），
   本项目可控部分（检索+重排）稳定在 1.1 s 以内；
2. 并发 4 以上单请求时延显著上升（GPU 串行 + API 排队），须靠缓存与上游限流缓解；
3. RAGAS 判官为在线 DeepSeek，20 个样本评测耗时 12～15 分钟，受网络与余额影响
   （本次评测期间曾遇到一次 API 余额不足导致判官调用失败，已重跑）；
4. 短答案（如 id531 只答「程家明」）信息正确但偏简，演示观感一般。
