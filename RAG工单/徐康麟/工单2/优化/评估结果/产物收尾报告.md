## 1. 硬编码修补（`优化/脚本/compare_optimization.py`）

原则：**报告里不再出现任何无条件「达标/满足」，也不出现写死的题号与历史结论**——判定一律引用真实计算值（`acc_ok` / `ft_ok` / `cite_ok`）或由逐题记录推导。

| # | 原写死内容（失效点） | 现实现 |
| --- | --- | --- |
| 1 | `✅ 答案准确率 …，达到工单 ≥90% 的要求`（无条件 ✅） | `{acc_ok}` + `before→after` 数值（`acc_ok` 由 `accuracy ≥ 0.9` 判定） |
| 2 | `✅ 首字响应 … 满足 ≤3 s`（无条件 ✅） | `{ft_ok}` + 均值/P95/最大值（`ft_ok` 由 `first_token_max_ms ≤ 3000` 判定） |
| 3 | `- ✅ 引用正确率 …`（无条件 ✅） | `{cite_ok}`（`citation_accuracy ≥ 1.0` 才算「保持」） |
| 4 | `未通过的 1 题为 **Q95** … 证据稳定在第 2 位` | 未通过题号由 `per_question[*].after.is_correct` **推导**；根因指向逐题记录，不再写死 |
| 5 | `1. **Q95 未过**（准确率 9/10）` | 同上，动态 `failed_ids` |

## 2. 防覆盖双保险（根因修复）

**根因**：脚本每次运行都会**无条件重写**四件正式交付物，`--limit 1` 冒烟运行因此把 10 题口径覆盖成单题口径（`after.count=1`，报告出现「10 题」与「1/1」并存）。

**双保险（两条同时生效）**：

1. **部分运行只写临时目录**：`0 < --limit < 全库题数` 时输出目录强制切到 `.tmp_review/compare_partial/limitN`
   （工作区**交付目录之外**）；若 `--out` 显式指向正式交付目录则**直接拒绝执行**（退出码 3）。
   显式 `--allow-partial` 可豁免第 1 条（第 2 条仍然生效）。
2. **写正式路径前断言题数**：`after.count != 全库题数` 时打印错误并 `sys.exit(4)`——**宁可不产出，也不产出错的**。

**为什么不用 `优化/评估结果/_smoke/`（captain 原建议）**：`测试/离线/test_deliverable_integrity.py`
判据 4 明令 `优化/评估结果/` 与 `优化/脚本/` **不得出现下划线前缀文件或目录**（正是为了钉住临时件命名习惯），
写 `_smoke/` 会把该守卫判红。故临时输出改到 `.tmp_review/compare_partial/`（守卫范围之外、且已被 captain 裁定保留的取证目录）。

**实测证据（冒烟 `--limit 2 --paths extractive`）**：

```
冒烟前：accuracy_report.json 7588B 16:55:34 / optimization_compare.md 12067B / .csv 2220B / ragas_report.md 7198B
输出 ：[防覆盖保护] 部分运行（--limit 2 < 全库 10 题）→ 输出改到 …\.tmp_review\compare_partial\limit2；正式交付目录 …未被写入
        CSV/JSON/MD/RAGAS 全部落在 .tmp_review\compare_partial\limit2\ 下（4 个文件）
冒烟后：四件正式产物 **mtime 仍为 16:55:34、字节数不变**；accuracy_report.json 的 SHA256 **完全相同** ✅
临时报告口径自洽：`答案准确率（2 题）`、`分母…本次运行的 2 道题（全库 10 道）`、`样本量 2 条（全库 10 条）`、`❌ 未达标（1/2）`
```

另外修掉一处**同源缺陷**：RAGAS 声明的写入目标原先写死模块常量 `RAGAS_DOC`（正式路径），
部分运行会连 `ragas_report.md` 一起覆盖；现已改为**只写本次输出目录**（部分运行在临时目录保留一份副本再追加，正式文件不触碰）。

## 4. `cold_start` 字段名歧义修正

**原歧义**：只有 `cold_start_first_token_ms` 一个字段，但它的取值是「**首题**首字」——
**只有 `--skip-warmup` 运行时才是冷启动**；预热后它只是首题稳态值。
曾有产物出现 `cold_start_first_token_ms == first_token_max_ms`（1 题运行）被误读成「冷启动=最大耗时」（verifier finding O4）。

**修正后（字段语义显式化，向后兼容）**：

| 字段 | 语义 | 本次全量运行实测值 |
| --- | --- | --- |
| `first_question_first_token_ms` | 首题首字耗时（**与是否冷启动无关**） | 178.73 |
| `cold_start_eligible` | 本次是否为 `--skip-warmup`（冷启动口径）运行 | `false` |
| `cold_start_first_token_ms` | **仅** `--skip-warmup` 时才有值，否则 `null` | `null` |
| `cold_start_口径` | 人类可读的口径说明 | 「本次已预热，故 `cold_start_first_token_ms=None`；`first_question_first_token_ms` 只是首题稳态值，**不是冷启动**」 |

报告 §6 行 5 同步改写（不再说「冷启动首题值单独列出」这种含糊表述）。
注：verifier 的 `verify_judge_and_citation.py` 只**打印**该字段、其判定不依赖它（已读源码确认），故本次改动不影响其结论。

## 6. ⑤ trace 体积削减：实测结论（**未按原方案实施**）

captain 原方向：把 `retrieved[*].chunk.content` 改为「长度 + 前 N 字符摘要」（保留 `chunk_id`/`page`/`score`/`type`）。
**实测数据不支持该方案**（对 `部署/日志/rag_trace.jsonl` 32.04 MB / 32,302 行逐字段归因）：

| 项 | 字节 | 占 trace 总量 |
| --- | --- | --- |
| `chunk.content`（**原方案要削减的字段**） | **122.5 KB** | **0.37%** |
| `boosts`（每条检索/重排记录的 33 个规则权重） | 10,299.7 KB | **31.39%** |
| 其中 `boosts` 零值项（丢弃零值可省） | 47.6 KB | 0.15% |

按事件类型：`Reranker.rerank/exit` 9.4 MB（2418 条，均 3976 B）、`Retriever.retrieve/exit` 7.1 MB、
`Retriever.retrieve_multi/exit` 2.0 MB —— 这些记录的 `content` 合计仅 70 KB，**体积来自 `boosts` + 每条 item 的元数据 + 事件外壳**。

**结论**：按原方案改会得到 **0.37%** 的收益，却要改动一个可能被人工审计阅读的字段名（`content`→`content_summary`），
**性价比不成立**，故本次**不做**（不做「为改而改」的变更）。若要真正压体积，可选（**需 captain 决策，属语义变更**）：

1. 削减 `boosts`：433,789 个键值对中 430,571 为非零（即确有信息），可只保留白名单键（如 `total_boost` + 命中类规则）或四舍五入到 3 位小数；
2. 或降级整类事件：`Reranker.rerank/exit`（9.4 MB）只记 `top_ids + scores`，不记逐 item `boosts`。

另：轮转本身已不再影响取证——tester 已把日志断言改为**轮转感知**（分卷家族 + 头指纹锚点），
本窗口 `rag_trace.jsonl` 从 2.4 MB 涨到 27.4 MB 未触发轮转，三连跑均报「非法 JSON 0 行」。
