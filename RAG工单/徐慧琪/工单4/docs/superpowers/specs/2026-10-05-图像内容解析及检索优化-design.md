## 1. 背景与目标

在工单 01/02/03（基于 PDF 的问答系统 → 系统优化 → 表格解析及检索优化）的基础上，本工单新增两个关键变化：

1. **多文档**：新增《招股说明书2.pdf》（武汉力源信息技术股份有限公司），与《招股说明书1.pdf》（武汉兴图新科电子股份有限公司）并存，系统从单文档升级为多文档问答。
2. **图像语义解析与图像检索**：16 道题中的 id 5、id 6 两道题，答案**既不在文本里、也不在表格里**，只存在于 PDF 的插图/组织结构图/图表中。

目标：构建一套三模态（文本 / 表格 / 图像）RAG 系统，使 16 道题的答案准确率 ≥ 90%，单次问答响应时间 ≤ 3 秒，并输出可量化、可溯源的检索精确度。

### 2.2 硬性要求 1 强制上报：本机无 CLIP

工单 PDF P8 备注要求「PDF 中的图像语义解析使用多模态模型（CLIP 或多模态大模型）实现」。**本机经检查确认：无 CLIP，无任何本地多模态模型**（`~/.cache/huggingface/hub` 下仅有空的 `PDF-Extract-Kit` 引用和英文 `all-MiniLM-L6-v2`）。

**采用方案：CLIP + 多模态大模型双通道（用户已确认）**

- **通道一（CLIP）**：从 `hf-mirror.com` 下载 `openai/clip-vit-base-patch32`，用于图像向量化，实现真正的跨模态「以文搜图」。
- **通道二（多模态大模型）**：调用已配置的 `deepseek-v4-flash-vision-exp`，对图表做语义解析，生成结构化文字描述，供 LLM 生成答案。

两条通道各司其职：**CLIP 负责"找到图"，多模态大模型负责"读懂图"**。

### 2.3 已实测验证的关键结论

**（1）视觉大模型读图能力——已验证通过**

对 id 5 组织结构图（第 39 页）实测，模型完整正确输出：

```
1) 销售部下设 4 个部门：电话及网络销售部、渠道销售部、大客户销售部、国际贸易部
2) 大客户销售部下设 6 个销售处：珠海销售处、深圳销售处、北京销售处、武汉销售处、广州销售处、成都销售处
```

与工单 P7 展示的标准答案完全一致（集合相同）。**这是本项目最关键的一条验证结论**——
提示词中「逐条完整列出、保留层级、不得省略」的强制要求是 6 个销售处全部列出的直接原因。

> ⚠️ id 6 的早期探索性验证**不成立，已作废**：当时裁切框取 y=230~430，
> 而 IC 市场图实际位于 y=367~539，裁掉了下半部分——恰恰包含答案所在的
> 「汽车 14.0%」那根柱子。模型当时的输出被截断，从未给出 汽车 14.0%。
> 这正是设计文档反复强调的「裁切过短导致静默丢答案」，**在探索阶段就已经真实发生过一次**。
> id 6 的有效性需在 Task 6 用完整图区重新验证（见该任务的验收步骤）。

**（2）两个必须遵守的实测约束**

- **约束 A：必须禁用思考链，且 `max_tokens` ≥ 2000**。该视觉模型默认先输出 `reasoning_content`（思维链）。
  实测演进：400 tokens 时答案被截断为空 → 提到 2500 仍不够，模型实际产生 4200~8600 个推理 token，
  `content` 始终为空（`finish_reason=length`），首轮实测直接掉到 OCR 兜底。
  **真正的解法是发送 `thinking: {"type": "disabled"}`**：推理 token 归零、输出 438 token 即完整作答，
  **单图耗时从 55 秒降到 3 秒**。后者尤其关键——工单要求端到端响应 ≤ 3 秒，
  若不禁用思考链，仅图像解析一项就已超时。
  仍保留 `max_tokens ≥ 2000` 下限与 `finish_reason=="length"` 重试，以兼容不支持该参数的第三方后端。
- **约束 B：图区裁切必须完整**。实测裁切框过短会**静默丢失**底部内容——首次测试裁掉最后一行后，模型不报错，而是自信地回答"图中未标出销售处层级"。这是本项目最大的风险点，直接决定 id 5 能否满分。

**（3）两张目标图表的来源不同，必须分别处理（已实测校正）**

| 目标 | 页（1-based PDF 页） | 图表来源 | 抽取方式 |

| id 5 组织结构图 | **39** | **矢量绘制**（31 个 drawing）+ 1px 宽渐变条 | 矢量聚类，`get_images()` 无效 |
| id 6 IC 市场图 | **72**（复现于 310） | **两张嵌入位图**（638×479 与 525×473） | 位图抽取 + 矢量聚类双路 |

> ⚠️ 此处曾有一处早期误判：最初认为"两张图都是矢量、`get_images()` 都拿不到"。
> 实测证明 **id 6 的 IC 市场图是真实嵌入位图**，`page.get_images()` 能正常返回。
> 若图区检测只做矢量聚类，会**漏掉 id 6**。因此 `figures.py` 必须同时走

水印干扰：两页都平铺了 15 个 143×127 的"八维教育" logo（约 1.8 万像素）。

### 3.3 三个关键设计决策

**决策 1：三个 Qdrant collection 而非一个**

| Collection | 向量 | 用途 |
|---|---|---|
| `text_chunks` | dense `bge-m3` 1024维 + sparse BM25 | 正文段落检索 |
| `table_chunks` | dense `bge-m3` 1024维 | 表格检索 |
| `image_chunks` | CLIP 512维 + VLM描述文本向量 | 图像跨模态检索 |

分离原因：图像块需用 CLIP 做真正的跨模态检索，其向量维度与语义空间同文本向量完全不同，混入同一 collection 会互相污染、且无法对两类向量分别设置相似度阈值与融合权重。

采用 Qdrant **本地嵌入式模式**（`QdrantClient(path=...)`）免装服务，同时在 `store.py` 中封装连接池接口，可一键切换到 server 模式，以满足硬性要求 4 中「Qdrant 连接池」的描述。

**决策 2：图像块双重表征**

- **CLIP 向量**：用于「以文搜图」，回答"哪张图与问题相关"。
- **VLM 结构化描述**：用于 LLM 生成答案，回答"图里写了什么"。

描述 prompt 强制要求：保留层级父子关系、完整枚举所有叶子节点。此约束经实测验证——正是它让 6 个销售处全部列出、不遗漏。

**决策 3：同库双模式对比**

`pipeline_mode` 配置开关，两种模式共用同一套代码与同一批 16 题：

| 维度 | `baseline_03`（代表 01/02/03） | `full_04`（本工单） |
|---|---|---|
| 模态 | 仅文本 | 文本 + 表格 + 图像 |
| 分块 | 固定 512 字 | 按 block_type 语义分块 |
| 检索 | 纯 dense | dense + sparse + CLIP，RRF 融合 |
| 重排 | 无 | 有 |
| 图像 | 无 | VLM 描述 + CLIP 向量 |

产出的对比表变量可控，一条命令即可重新生成。

## 4. 核心组件设计

### 4.1 图区检测 `figures.py`（★最高风险组件）

**设计约束：绝不静默丢答案。** 宁可多给模型一些像素，也不能少裁一行内容。

三层自适应检测：

1. **矢量图形聚类**：`page.get_drawings()` 收集所有绘图对象的 bbox → 按间距聚类（并查集合并相邻矩形）→ 得到候选图区。矢量图表的特征即大量绘图对象密集聚集。
2. **题注锚定校正**：正则匹配图题注与提示语（`图\s*\d+[-－]?\d*[:：]`、`如下图`、`组织结构图`、`应用结构`、`产业链` 等）→ 取题注 bbox → 向上方关联最近图形簇，精确锁定图区上下边界。
3. **整页兜底**：前两层置信度不足时，整页渲染交模型做页级理解，保证不漏。

**强制项**：最终裁切框向外扩展 **15%**，且必须包含题注区域。渲染 DPI 固定 **200–220**（实测该分辨率下竖排小字可被正确识别）。

输出：`FigureBlock{page, bbox, image_path, caption, detect_method, confidence}`

### 4.2 多模态语义解析 `vlparser.py`（★）

对每个 `FigureBlock`：

1. **VLM 语义解析**：将渲染图 + 结构化提问模板送 `deepseek-v4-flash-vision-exp`。
   - **`max_tokens ≥ 2000`**（实测硬约束，防止思维链挤占答案被截断）
   - 提示词要求：完整枚举所有层级、不遗漏任何叶节点、保留父子关系、输出中文
   - 失败重试 3 次（指数退避）→ 仍失败则降级为 `rapidocr_onnxruntime` OCR 文本 + 规则模板兜底，并记录 `warning` 标记
2. **CLIP 图像向量**：同一张渲染图经 CLIP 图像编码器得到 512 维向量，写入 `image_chunks`。

两者共同构成图像块的双重表征。缓存策略：以 `(doc_id, page, bbox)` 为键缓存解析结果，重复运行不重复调用 API。

### 4.3 分块策略 `chunker.py`

| 类型 | 策略 |
|---|---|
| 文本 | 按标题/段落语义边界切分，目标 500–800 字，重叠 15% |
| 表格 | 整表为一个块（不切分），附列头说明；超长表按行分组并保留表头 |
| 图像 | 整图为一个块，正文 = VLM 描述 + 题注 + 所在章节标题路径 |

所有块统一携带元数据：`doc_id`、`page`、`block_type`、`source_id`、`section_path`、`lang`。

### 4.4 检索层

- `embed.py`：bge-m3 走 Ollama `/api/embed`，**批量 16 条/请求**，失败自动降批次重试。
- `bm25.py`：jieba 分词（带领域词典）+ rank_bm25，索引持久化。
- `hybrid.py`：RRF 融合，`score = Σ 1/(k + rank_i)`，`k=60`，各通道权重可配。
- `image_index.py`：问题文本经 CLIP 文本编码器 → 与 `image_chunks` 的 CLIP 向量做余弦相似度检索。
- `rerank.py`：对融合后 top-30 重排，输出最终 top-5。重排模型采用 **`BAAI/bge-reranker-base`**（多语言 CrossEncoder，约 1.1 GB，经 `hf-mirror.com` 下载，与 bge-m3 同源、中英兼顾）。**降级链**：模型下载失败或加载失败 → 退化为「RRF 分数 + 章节邻近度 + block_type 优先级」的启发式重排，功能不中断。

**id 5/6 的保障机制**：问题中出现「组织结构图」「图」等图像指向词时，**强制提升图像通道权重**并保证至少 1 个图像块进入上下文。

### 4.5 生成层 `generate/llm.py`

- 主：DeepSeek API；失败/超时/限流 → 自动降级本地 Ollama `qwen2.5:3b`。
- **多语言**：检测提问语言（中/英），prompt 显式要求「用与提问相同的语言作答」。中文问→中文答，英文问→英文答。
- **引用溯源**：要求模型在答案中标注来源，系统侧同时回传结构化引用（页码 + block_type + 图像ID/表格ID/段落ID）。
- 并发控制：`asyncio.Semaphore` 限流 + 超时控制。

## 5. 评估体系

### 5.1 16 道题的标准答案与出处

`eval/questions.py` 内置 16 题、标准答案、出处标注。已完成核实的关键项：

- **id 5**（图像题）：销售部下设 4 个部门（渠道销售部、电话及网络销售部、大客户销售部、国际贸易部）；大客户销售部下设 6 个销售处（北京销售处、深圳销售处、广州销售处、成都销售处、珠海销售处、武汉销售处）。出处：《招股说明书2.pdf》p38 组织结构图。**已实测模型可完整答对**。
- **id 6**（图像题）：增长率最快的是**汽车（14.0%）**，负增长的是 **IC卡（-2.0%）**。出处：《招股说明书2.pdf》p71《2008年中国IC市场应用结构与增长图》。

其余 14 题（id 1、2、3、4、260、95、33、34、957、793、795、543、531、207）主要落在文本/表格块，出处已初步定位，实现 `questions.py` 时逐题复核并固化。

### 5.2 指标定义

**检索层**（对每题标注的相关文档集合计算）：

报告主口径 **k = 5**（同时输出 k = 3 与 k = 10 作为参考列）：

- `Precision@k` = 命中相关块数 / k
- `Recall@k` = 命中相关块数 / 总相关块数
- `Hit Rate` = 至少命中 1 个相关块的题目占比
- `MRR` = 第一个相关块排名倒数的均值
- `NDCG@k` = 归一化折损累计增益

**答案层**：

- `Answer Accuracy` = 标准答案要点覆盖率 **≥ 80%** 的题目占比。对 id 5 这类列表型答案采用**严格口径**：4 个部门 + 6 个销售处共 10 个要点全部命中方计为正确，缺一不可。

**性能层**：端到端响应时间 P50 / P95 / P99。

### 5.3 输出产物

每题一行，包含：答案 + 各量化指标 + 引用来源（页码 + block_type + 图像ID/表格ID/段落ID）。

### 5.4 RAGAS

`ragas_eval.py` 计算 faithfulness、answer_relevancy、context_precision、context_recall，产出 RAGAS 评估报告。

## 6. 容错与稳定性（硬性要求 7）

### 6.1 容错清单

| 异常场景 | 处理策略 |
|---|---|
| 用户输入错误（空/超长/无关问题） | 输入校验 + 意图相关性阈值判断，无关则明确拒答并提示 |
| 非 PDF 上传 | 类型与魔数校验，友好报错 |
| 文档解析失败（加密/损坏页） | 逐页 try/except，跳过坏页并记录，不中断整体解析 |
| 无文本层 PDF | 标记为扫描件，走 OCR 通道 |
| 图像解析失败（VLM 超时/报错） | 重试 3 次（指数退避）→ CLIP + OCR 规则模板兜底 → 记录 warning |
| 图区检测置信度低 | 降级整页渲染，保证不丢内容 |
| CLIP 模型加载失败 | 降级为「VLM 描述文本」单通道检索，功能可用性不中断 |
| bge-m3 / Ollama 不可用 | 明确报错 + 修复指引（含 `ollama serve` 提示），不静默失败 |
| Qdrant 连接失败 | 自动重连 + 重试；本地模式异常时回退只读缓存 |
| LLM API 失败/限流 | 降级本地 Ollama；再失败则返回检索原文与引用，不空手而归 |

### 6.2 长时间运行方案

- 日志：`RotatingFileHandler` 轮转（单文件 10 MB × 保留 10 份）
- 内存监控：定期采样 RSS/显存，超阈值告警
- 健康检查：`/health` 端点（含向量库连通性、模型可用性、向量条数）
- 异常重启：服务级自动重启脚本

### 6.3 显存/内存优化（硬性要求 4）

- CLIP 仅在图像入库阶段批处理推理，推理完释放显存，不常驻
- 模型共享：bge-m3 由 Ollama 统一托管，避免多进程重复加载
- 缓存：VLM 解析结果、embedding 结果双重缓存，避免重复计算
- 批处理：embedding 批量 16 条/请求，图像渲染按需流式处理不驻留

## 7. 高并发方案（硬性要求 4）

- **Qdrant**：连接池封装，最大连接数可配
- **LLM**：`asyncio.Semaphore` 并发上限控制 + 超时 + 重试
- **Embedding**：批处理 + 请求合并，避免高频小请求打爆 Ollama
- **压测方案**：`benchmarks/loadtest.py` 在 10 / 50 / 100 并发下压测，产出响应时间（P50/P95/P99）、错误率、QPS、资源占用（CPU/内存/显存），形成《高并发压测报告》
