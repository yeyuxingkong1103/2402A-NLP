# 技术文档：PDF 文档的表格解析及检索优化

> 工单编号：**人工智能NLP-RAG-PDF文档的表格解析及检索优化**
> 对应需求：解析《招股说明书2.pdf》（武汉力源信息技术股份有限公司），
> 使 4 个「答案只存在于表格中」的问题可被准确检索并作答。

本文档说明本工单采用的技术栈、原理、关键取舍，以及在本项目真实 PDF 上
实测到的现象与对策。文中的页码均为 **物理页码**（= PDF 阅读器页码；
招股书页脚印刷页码 = 物理页码 − 1）。

---

## 一、为什么表格必须单独处理

### 1.1 纯文本层丢失的不是「字」，而是「字与字的对应关系」

4 个目标问题的答案全部落在表格里：

| id | 问题 | 答案所在 | 物理页 |
| --- | --- | --- | --- |
| 1 | 本次发行股数、占发行后总股本比例 | 「四、本次发行情况」表 | 22、24 |
| 2 | 本次募集资金拟投资项目 | 「五、募集资金用途」表 | 22 |
| 3 | 存在控制关系的关联方及持股比例 | 「1、存在控制关系的关联方」表 | 157 |
| 4 | 不存在控制关系的关联方企业 | 「2、不存在控制关系的关联方」表 | 157 |

用 PyMuPDF 取纯文本层时，能拿到全部字符，但拿不到「哪个数字属于哪一行」。
以 p22「五、募集资金用途」表为例，文本层的输出是：

```
序号
项目名称
计划总投资(万元)
1
仓储及物流中心
3,393.40
2
研发中心
1,526.38
...
```

文本层面里的项目名和金额是**各自成行**的。要回答「哪些项目」尚可，
但一旦问题变成「研发中心计划投资多少万元」，模型就必须自己推断
「1,526.38 紧跟在研发中心后面」——这种推断在多列表格、跨行合并单元格、
跨页续表时会直接失效。

### 1.2 真正的杀手是分块

工单01/02 使用的 `structure` 分块，`CHUNK_SIZE = 400` 字符。
实测《招股说明书2.pdf》每页清洗后的正文长度：p22 = 483 字符、
p24 = 669 字符、p157 = 596 字符、p158 = 510 字符，全书平均 759.8 字符。

也就是说**典型的一页正文会被切成 2 个 chunk**。
p22 上的「募集资金用途」表位于该页末尾，5 个项目正好压在切分点附近，
极可能一半在前一个 chunk、一半在后一个 chunk；而 top_k = 5 的重排结果里
通常只会出现其中一个 —— 生成的答案就会「只答出 3 个项目」。
这是纯文本方案在**清单类问题**上失分的核心机制，也是本工单做消融实验
（`compare_with_without_tables.py`）要量化的对象。

### 1.3 表格方案的两条收益

1. **结构收益**：表格块整表入库，行列对应关系在 chunk 内完整保留，
   模型不需要「猜」哪个数字配哪一行；
2. **边界收益**：表格块走 `chunk_structure()` 的 `_block_to_single_chunk()`，
   **整表不参与字符切分**，从根本上消除「半张表」问题。

## 二、pdfplumber 的表格抽取原理

### 2.1 `extract_tables()` 的四步流水线

```
① 收集边(edges)       page.lines / page.rects / page.curves
                        ↓ 过滤出水平边与垂直边
② 求交点(intersections) 水平边 × 垂直边 → 交点集合
                        ↓
③ 划分单元格(cells)     TableFinder 沿交点网格行走，找出闭合区域
                        ↓
④ 装字(extract)         每个 word 的中心点落在哪个 cell，就归给哪个 cell
```

第 ④ 步是关键，也是最容易被误解的地方：**它按 word 的几何中心归属，
而不是按阅读顺序**。因此：

- 单元格内多行文本会被拼成一个字符串（默认用空格/换行连接）；
- 合并单元格里的长文本，其中心点可能落在相邻子列，导致内容「串列」；
- 一个词只要中心点越界一点点，就会被分到隔壁列。

这就解释了为什么同一张 5 列的表会被抽成 9 列甚至 15 列 —— 见下一节实测。

### 2.2 策略与参数

`page.find_tables(table_settings)` 的 `vertical_strategy` / `horizontal_strategy`
取值：

| 取值 | 含义 | 适用 |
| --- | --- | --- |
| `lines`（默认） | 用页面上的线段/矩形边作为网格线 | 有完整边框的表（招股书绝大多数的表） |
| `lines_strict` | 只用 `page.lines`，忽略 `rects` 的边 | 排除装饰性矩形干扰 |
| `text` | 用词的 x/y 坐标聚类出行列（`text_x_tolerance` 等控制粒度） | 无边框表、三线表 |
| `explicit` | 调用方显式给出网格线坐标 | 已知版式的批量处理 |

本项目 `table_extractor.py` 的策略：

1. 默认走 `lines`（`LINE_SETTINGS`）；
2. **仅当**该页一条有效表都没抽到、且页面上有 ≥ 8 条 lines/rects 时，
   才依次回退到 `lines + text`、`text + text`（`FALLBACK_SETTINGS`）。

这样做的理由是速度与准确度的折中 —— 实测在本 PDF 上：

| 策略 | p22 结果 | p157 结果 | 结论 |
| --- | --- | --- | --- |
| `lines` | 3 张表，6×15 / 5×2 / 6×9 | 2 张表，2×9 / 8×6 | **数据最全，采用** |
| `lines + text` | 3 张表，11×13 / 9×2 / 11×9 | 2 张表，3×7 / 2×4 | 引入大量空行，结构更差 |
| `text + text` | 1 张表，43×1 | 1 张表，59×1 | 退化成单列，不可用 |

`lines + text` 的横线用线段、竖线靠文本聚类，反而把一行拆成了两行；
`text + text` 完全依赖坐标聚类，在本 PDF 上把所有内容并成了一列。
因此本次**不采用**多策略融合，而是用「兜底」的方式只在必要时启用。

## 三、表格网格规范化：三步把「脏网格」还原成可用表格

### 3.1 问题现象（实测）

p22 的「五、募集资金用途」表，`lines` 策略抽出 **6 行 × 9 列**：

```
header : ['', '序号', '', '', '项目名称', '', '', '计划总投资(万元)', '']
row1   : ['1',  '',    '', '', '仓储及物流中心', '', '', '3,393.40', '']
```

表头 `序号` 在第 2 列，数据 `1` 在第 1 列 —— 整张表**错开一列**。
直接转 Markdown 会得到一份「表头配错数据」的废表，检索精确度归零。

同样的现象出现在 p157 的关联方表：`关联方名称/持股比例/与本公司关系`
分别落在第 2/5/8 列，而 `赵马克/42.35%/公司控股股东` 落在第 1/4/7 列。

### 3.2 三步规范化（`normalize_grid()`）

```
① 单元格清洗 + 去空行
       None → ''，换行/连续空白 → 单空格；删除整行皆空的空行
② 删全空列 → 表头列错位修复 → 再删全空列
       合并单元格造成的竖线误检，表现为「所有行都是空的列」
③ 去空行
```

第 ② 步中的**表头列错位修复**（`_repair_header_alignment()`）是本模块的核心技巧：

```python
# 统计数据行「首个非空列」的众数位置
# 表头首个非空列位置 - 该众数 = 稳定偏移 delta
# |delta| <= 2 时，把表头整体平移回 delta 列
```

判定必须用「众数」，否则单行缩进（如「其中：」这类子项）会污染判断。
平移后要求非空单元格数量不变，否则放弃修复（保守策略）。

### 3.3 实测效果

| 表 | 修复前 | 修复后 | 结果 |
| --- | --- | --- | --- |
| p22 募集资金用途表 | 6×9，表头右移 1 列 | **6×3** | `序号 / 项目名称 / 计划总投资(万元)` 三列严格对齐 |
| p22 主要财务指标表 | 6×15 | **6×5** | `项目 / 2010年1-6月 / 2009年度 / 2008年度 / 2007年度` |
| p157 存在控制关系关联方表 | 2×9 | **2×3** | `关联方名称 / 持股比例 / 与本公司关系` |
| p157 不存在控制关系关联方表 | 8×6 | **8×2** | `企业名称 / 与本公司关系`，7 家企业全部到位 |

修复后的 Markdown：

```markdown
| 序号 | 项目名称 | 计划总投资(万元) |
| --- | --- | --- |
| 1 | 仓储及物流中心 | 3,393.40 |
| 2 | 研发中心 | 1,526.38 |
| 3 | 电子商务平台 | 2,492.78 |
| 4 | 扩充产品种类和数量 | 9,000.00 |
| 5 | 其他与主营业务相关的营运资金 | [ ◆ ] |
```

## 四、为什么把表格转成 Markdown

| 方案 | 优点 | 缺点 | 是否采用 |
| --- | --- | --- | --- |
| 保留二维数组（JSON） | 结构无损 | LLM 读起来冗长；检索时无词面信号；与现有 chunk 文本流不兼容 | ✗ |
| CSV | 紧凑 | 表头只出现一次，模型容易错行；无视觉分隔 | ✗ |
| **Markdown** | 表头与分隔行让行列关系显式可见；`\|` 天然分词；与工单01/02 的 chunk 文本流兼容；人可读，演示视频里能直接投屏 | 长表字符数偏多 | **✓** |
| 自然语言描述（"该表共 5 行……"） | 检索词面友好 | 生成成本高、易引入描述错误、不可逆 | ✗ |

采用 Markdown 的另一个工程理由：`rag_core.pdf_parse._table_to_markdown()`
已经是工单01/02 的既定口径，本模块**直接复用该函数**（`table_extractor.table_to_markdown()`
在共享库可用时调用它，缺失时才使用本地等价实现），保证三个工单的表格
表示完全一致，不需要重新调参。

> 注：`_table_to_markdown` 以**首行作为表头**并自动补齐列宽，
> 因此本模块的 `normalize_grid()` 必须先保证「第 0 行确实是表头且行列已对齐」。

### 4.1 入库文本还要拼上标题

`chunk_structure()` 对表格块走 `_block_to_single_chunk()`，**不会**注入章节路径
（只有正文块会被注入 `【章节路径】`）。如果表格块的正文只有一堆数字，
向量检索时它和任何一张财务表都很像。因此 `_build_content()` 把表格标题
拼到正文最前面：

```
【表格】2、不存在控制关系的关联方
| 企业名称 | 与本公司关系 |
| --- | --- |
| 融冰投资 | 持有公司股份5%以上的股东 |
...
```

标题由 `extract_caption()` 抽取：取表格 bbox **上方最近的一条非噪声文本行**，
过滤页眉、页码、「(单位：元)」等说明行。实测抽到的标题：
`四、本次发行情况`、`五、募集资金用途`、`1、存在控制关系的关联方`、
`2、不存在控制关系的关联方`、`合并资产负债表(续)`。

这相当于给表格块补回了正文块才有的「章节路径」，且成本为零。

## 五、跨页续表合并策略

### 5.1 难题：合并不足与合并过度都是错

- **漏合并**：财务报表（资产负债表、利润表）跨页续排，下一个 chunk 只有半张表，
  答案行若落在后半张就检索不到 —— 这是召回问题；
- **错合并**：招股书里相邻两张表**表头完全相同**但属于不同小节，
  合并会把不同口径的数据混进同一个 chunk —— 这是正确性问题，比漏合并更严重。

### 5.2 实测的两种真实情形

**应当合并**（p204 → p205）：

```
p204  caption='合并资产负债表'      header=[项目, 2010-6-30, 2009-12-31, 2008-12-31, 2007-12-31]
      bbox 纵向占比 0.14 - 0.60，26 行
p205  caption='合并资产负债表(续)'  header=[项目, 2010-6-30, 2009-12-31, 2008-12-31, 2007-12-31]
      bbox 纵向占比 0.14 - 0.69，31 行
```

**绝不能合并**（p157 → p158）：

```
p157  caption='2、不存在控制关系的关联方'
      header=[企业名称, 与本公司关系]     7 家企业，表格纵向占比 0.77 - 0.90
p158  caption='3、报告期内曾为关联方但目前已不存在关联关系的公司'
      header=[企业名称, 与本公司关系]     佰力电子 / 盈硅电子，表格纵向占比 0.12 - 0.17
```

两者表头一字不差、位置也「上页底部 → 下页顶部」，
**任何只看表头和位置的合并规则都会把它们错误合并**。
而语义上，第 3 小节的公司已经**不再是关联方**，合并进「不存在控制关系的关联方」
名单会导致 id=4 的答案多出 2 家错误企业。

### 5.3 判定规则（`merge_cross_page_tables()`）

四条同时满足才合并：

| 条件 | 判据 | 作用 |
| --- | --- | --- |
| ① 跨页相邻 | `nxt.page == cur.page + 1` | 只处理相邻页 |
| ② 表头兼容 | 表头去空、去「(续)」后集合重合度 ≥ 0.6 | 确认是同一张表的延续 |
| ③ 位置连续 | `nxt.y0_ratio ≤ 0.30` 且 `cur.y1_ratio ≥ 0.50` | 排除「同页两张表」 |
| ④ **语义连续** | 下一张表标题含「续」，**或**与上一张表同属一个小节（标题归一化后相等）；若标题形如 `3、xxx` 等编号小标题 → **拒绝合并** | 防错合并 |

第 ④ 条是让 p157→p158 被正确拒绝的关键。规则严格偏向「宁可漏合并，
不可错合并」：漏合并只损失召回，错合并会污染事实。

被拒绝的合并会写入 `table_inventory.json` 的 `merge_events`，注明理由：

```json
{"action": "rejected", "pages": [157, 158],
 "reason": "表头相同但属于新小节「3、报告期内曾为关联方但目前已不存在关联关系」，合并会造成语义串类"}
```

### 5.4 无表头续页（保守分支）

有些表跨页时下一页不重复表头（实测 p181 的「对外投资情况表」19 行到页底，
p182 顶部还剩 3 行）。这类合并且**更严格**：
上一张表 `y1_ratio ≥ 0.80` + 下一张表 `y0_ratio ≤ 0.15` + **列数完全相等** + 非新小节。

实测 p181 表为 7 列、p182 的续行为 5 列（pdfplumber 在换页处的线条识别
发生了变化），列数不等 → 判定不合并。这是正确的保守行为：
列都对齐不了的续行，合进来只会污染数据。该情形会在表中打上
`header_lost` / 保留独立记录，供人工复核。

## 六、表格检索的难点与对策

### 难点 1：表格块与问题的字面重合度天然低

问题说「发行股数是多少，占发行后总股本的比例是多少」，
表格里写的是「1,670万股，占发行后总股本的比例为25.04%」。
`发行股数` 这个词恰好不在值里，而在相邻单元格里。

**对策**：
1. 表格标题前置入库（见 4.1），补回 `本次发行情况`、`募集资金用途` 这类关键词；
2. 表格块优先级提升 `boost_table_docs()`：
   数值/清单类问题（问题含「多少/比例/占比/哪些/分别/金额」等）系数 **1.35**，
   其它问题 **1.15**，对 `final_score` 加权后重新排序；
3. BM25 侧天然受益 —— 表格里的数字与项目名是独立的 token，
   问题中的数字（如「42.35%」）能直接命中。

> 为什么系数不大：加得太猛会让表格块无差别压过正文。1.15/1.35 是在
> 「表格类问题必须赢」与「正文类问题不能输」之间取的保守值，
> 并且用 10 个文本类问题做反向验证（消融实验第二组）。

### 难点 2：长表的向量截断

合并后的资产负债表有 56 行、约 4000 字符，而 BGE 的
`EMBED_MAX_LENGTH = 512` token —— 嵌入时尾部会被截断。

**对策**：标题与表头必须放在最前面（Markdown 天然满足），
保证被截断后的向量仍然携带「这是哪张表」的主题信息；
表体中后段的精确匹配交给 BM25 通道兜底（工单06 的混合检索会进一步强化这一点）。

### 难点 3：同一张表在文档中出现多次

「本次发行情况」在 p22（摘要）和 p24（正文「第三节 本次发行概况」）
各出现一次，内容高度重复。检索时可能同时命中两份。

**判定**：这属于**召回冗余**而非错误 —— 两份内容一致，任一份都能支撑正确答案。
`table_qa.json` 会同时记录 `retrieved_pages`，便于人工确认命中的是哪一份。

### 难点 4：表格与正文的竞争

表格块数量增加会挤占 top_k 名额。

**对策**：索引构建时两类块一一对应入库，不做数量放大；
消融实验专门用 10 个文本类问题验证「加表格没有把正文挤下去」。

### 难点 5：表格质量问题会放大到答案

错列、错行、半张表在检索阶段看不出来（召回正常），
却会让 LLM 生成一个「看起来很像样」的错误答案。

**对策**：本工单把质量校验前置到抽取阶段（第三章、第五章），
并在 `table_inventory.json` 中为每张表记录 `flags` 与 `merge_events`，
使质量问题可审计、可回溯。

## 七、模块与数据流

```
《招股说明书2.pdf》
   │
   ├─ rag_core.pdf_parse.parse_pdf(with_tables=False) ──→ PageBlock(text)
   │
   └─ table_extractor.extract_all()
         pdfplumber.find_tables(lines)      ← 线条检测
         normalize_grid()                   ← 删全空列 + 表头错位修复 + 再删全空列
         table_to_markdown()                ← 复用 rag_core 口径
         is_valid_table()                   ← 质量校验（空表/单行单列/列数异常/字符过少）
         merge_cross_page_tables()          ← 跨页续表合并（四条件判定）
         extract_caption()                  ← 标题抽取，拼进入库文本
              │
              ├─→ results/tables/*.md           每表一个 Markdown 文件
              ├─→ results/table_inventory.json  表清单 + 合并事件
              └─→ PageBlock(table, Markdown)
                     │
                     ▼
   rag_core.chunk.chunk_blocks(strategy="structure")
         （表格块整表保留，不切碎）
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
   VectorStore(collection)   BM25Retriever
```

## 九、已知局限与后续可做

1. **合并规则依赖标题质量**：若某页表格上方没有可识别的标题，
   跨页合并会退化为「不合并」。这是刻意的保守取舍。
2. **无表头续页识别率有限**：p181→p182 这类跨页处列数发生变化的表仍会漏合并，
   已在 `table_inventory.json` 标记供人工介入。
3. **长表未做行级切分**：56 行的大表整体入库，依赖标题前置 + BM25 兜底。
   若后续 top_k 更大的场景，可考虑「表头 + 行窗口」的滑窗切分（工单06 可扩展）。
4. **表格类型未做语义分类**：目前所有表一视同仁，
   后续可识别「财务三表 / 关联方表 / 募集资金表」并给不同加权。
