### 3.3 局域网访问

部署主机局域网 IPv4 地址：**10.223.15.227**（以太网适配器）。

| 目标 | 实际结果 |
| --- | --- |
| `http://10.223.15.227:8000/api/health` | `HTTP 200` |

**验证过程分两步**：

| 步骤 | 执行方 | 结果 |
| --- | --- | --- |
| ① 部署主机经自身局域网 IP 访问 | 部署实施者 | `HTTP 200` |
| ② **另一台终端访问同一地址** | **用户**（同一局域网内的另一台设备） | ✅ **可正常打开问答页面** |

**关于步骤 ① 的说明**：该请求由部署主机自身发起，访问的是自身的局域网 IP。它证明了服务确实绑定在非回环地址上、且局域网 IP 路径可达，但**不等价于另一台终端能访问成功** —— 后者还受 Windows 防火墙入站规则影响。因此才有必要做步骤 ②。

**步骤 ② 由用户在另一台设备上实际复核完成，跨主机访问确认可用。** 这意味着防火墙入站规则未构成阻碍，局域网访问链路（`前端页面 → 主机网卡 → FastAPI :8000`）完整打通。

> 若后续更换部署主机或调整网络环境（如切换到不同网段、更换防火墙策略），本项需重新验证。无法访问时的排查顺序见《部署运行手册》5 节「局域网访问验证」。

### 5.2 并发能力（N4）

**测试方法**：使用 Python 临时脚本（未入库）对 `POST /api/chat/query` 发起 **20 并发**请求，每条使用**不同问题**以避免命中查询缓存而走捷径；先预热一次以排除 BGE-M3 模型冷加载耗时。

**测试结果**：

| 指标 | 实测值 |
| --- | --- |
| 并发数 | 20 |
| 成功（HTTP 200） | **20** |
| 失败 | **0** |
| **成功率** | **100%** |
| 整体墙钟耗时 | 9 秒 |
| 最小耗时 | 0.10 s（该条命中缓存） |
| **P50** | **5.59 s** |
| **P95** | **8.17 s** |
| 最大耗时 | 8.67 s |
| 平均耗时 | 5.70 s |

**结论**：20 并发下**无任何请求失败**，满足 N4「不少于 20 个并发问答请求不出现错误」。✅

**如实说明两点**：

1. **缓存命中说明**：20 条中有 1 条命中查询缓存（该问题在本次验证更早时提问过），耗时 0.10 s。其余 19 条均走完整检索 + 生成链路。缓存设计本身是 F8 要求的正常行为，不影响并发结论。
2. **并发下的时延高于单用户**：单用户串行时延为 1.50 ~ 3.60 s，20 并发下 P50 升至 5.59 s、P95 达 8.17 s、最大 8.67 s。即 **N3 的「≤ 8 秒」是单请求目标，在 20 并发压力下 P95 与最大值略高于该目标**。根因是本机为 CPU 推理（无 GPU），向量化与检索均为 CPU 计算，20 路并发争抢 CPU 导致排队。这是硬件条件限制，不属功能缺陷 —— 20 并发全部成功返回，未出现错误或超时。若后续对并发时延有要求，可考虑 GPU 加速或增大 `EMBED_BATCH_SIZE` 之外的线程控制策略。

### 5.3 异常隔离能力（N4）

N4 另要求「单个请求异常不得导致整个服务不可用」。本次部署过程中**真实发生了**一次可验证该能力的场景：

**场景**：部署过程中 MySQL80 服务中途停止，此时后端已在运行。

**实际表现**：

| 观察项 | 结果 |
| --- | --- |
| 后端进程 | ✅ 未崩溃，持续运行 |
| `/api/health` | ✅ 正常响应，`"mysql": false` 如实反映依赖故障 |
| 问答请求 | ✅ 正常返回（返回 500 与中文提示，进程未退出） |
| 日志 | ✅ 完整记录错误堆栈：`MySQL 健康检查失败：(2003, "Can't connect to MySQL server on '127.0.0.1' ...")` |
| MySQL 恢复后 | ✅ **无需重启后端**，页码溯源立即恢复（每次请求新建连接） |

**结论**：单个依赖故障不会导致整个服务不可用，且故障被如实上报与记录。✅

## 六、部署过程中实际遇到的问题与处理

> 本节记录本次部署中**真实踩到的坑**，已整理进《部署运行手册》第八章。

| # | 现象 | 根因 | 处理 |
| --- | --- | --- | --- |
| 1 | Milvus（19530）与 Redis（6379）均未监听 | Docker Desktop 未启动 | 启动 Docker Desktop，等待其就绪 |
| 2 | MySQL 连接被拒（`WinError 10061`） | MySQL80 服务中途停止（会话开始时仍在运行） | 用管理员窗口 `net start MySQL80` |
| 3 | `net start MySQL80` 报「系统错误 5，拒绝访问」 | 当前 shell 无管理员权限 | 改用管理员 PowerShell / `services.msc` |
| 4 | 后端启动后 43 秒内无响应，端口未监听 | 等待 Milvus 服务端就绪（端口先就绪，但服务端尚不可用） | 等待即可，无需干预 |

**关于第 4 项的取证**：为确认这 43 秒的成因，在 Milvus 预热后做了对照测试：

| Milvus 状态 | `MilvusClient()` 构造 + `list_collections()` 耗时 |
| --- | --- |
| 刚启动（首次建连，后端启动时） | 约 **43 秒** |
| 已预热（本次对照测试） | **0.92 秒** |

两次差值说明该阻塞来自 Milvus 服务端就绪等待，而非客户端固定开销 —— 「端口 19530 已 LISTENING」并不代表服务端可用。

**经验总结**：本系统的三个存储组件**部署形态不统一**（两个容器 + 一个 Windows 服务），因此不存在「一条命令拉起全部依赖」的方式，必须按 Docker → MySQL → 后端 的顺序分步启动与验证。这是本手册把「启动顺序」单独成节的原因。
