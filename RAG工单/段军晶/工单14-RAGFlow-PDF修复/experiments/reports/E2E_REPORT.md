## 四、两处失败的原因分析（都不是解析问题）

### Q5：解析正确、检索正确，**选项绑定错** ❌→ 属问答层

模型引用的证据**完全正确**：`依次经过部件1、部件10、部件6″、部件6′、部件6、部件4、部件5、部件2`。
但它推出的结论是「气流首先经过部件10，紧接着经过部件6″」→ 选了 B。

**根因**：题面「气流方向(7)首先经过哪个部件？」存在字面歧义。
按真实路径，气流确实**先经 1、再经 10、再经 6″**，所以选项 B「先经过部件10，再经过部件6″」**在字面上也成立**；
标准答案 C 的读法是「（在三块配气盘这一组里）先经 6″、再经 6′」。

→ **这是题目与选项的歧义，不是流水线缺陷**。解析产物里流向顺序是对的、也被检索到了。

### Q2：证据检索正确，**但 A 选项在文档中同样为真** ❌→ 属问答层 + 题目质量

模型**已经检索到并引用了 C 的全部依据**：「管状入口具有一个单个的圆锥形部分，该圆锥形部分达到外壳直径的80至95%，……台阶 [ID:3]」。
但它最终选了 A。

**根因**：选项 A「具有平行于外壳主轴线的垂直方向的片状沉积电极」**在本专利说明书中确实是真实描述**（chunk 10：「并等间距排列的垂直方向的片状沉积电极……这些沉积电极平行于外壳主轴线等间距排列」）。
模型还主动排除了 B（判为现有技术）与 D（判为不符），但**没有在 A 与 C 之间做出「哪个才是本发明的区别技术特征」的取舍**。

→ 题面问「以下哪个描述符合该静电除尘器的特征」，而 A、C **都符合**；判分口径取 C（摘要 [57] 强调的 80–95% + 台阶 这一区别特征）。

## 五、重要：首轮 3/6 是**测试脚本自身的缺陷**，不是流水线问题

首轮 e2e 得 3/6，Q1 也失败。经排查，根因在**我的测试脚本**：我把答题格式指令
（「请严格依据检索到的资料作答……以「答案：X」的格式给出」）**直接拼进了 `question` 字段**，
而 RAGFlow 用 `question` 原文做检索 —— 指令文本淹没了真正的查询意图。

实测证据（同一问题、逐级加料）：

| 查询构造 | 召回 chunk 数 | 发明人所在排名 |
|----------|--------------|---------------|
| 裸问题 | 15 | **#1** |
| 问题 + 选项 | 8 | #1 |
| 问题 + 选项 + **格式后缀**（首轮用法） | **1** | **消失** |

**修正**：把格式指令移入 `prompt_config.system`（保留 `{knowledge}` 占位符），
`question` 只留「题干 + 选项」干净文本。Q1 随即恢复为正确。

> 这条经验对交付有直接价值：**检索查询文本必须保持干净，答题约束应放在 system prompt**。

| 维度 | 结论 |
|------|------|
| 解析层（F 组改造） | ✅ 目标达成：Q3 无歧义关系、Q5 流向正确且被检索、Q4/Q6 字形保真生效 |

| 剩余 2 题的性质 | **均在问答/选项绑定层，不在解析层** |
| Q5 | 题目字面歧义，选项 B 按字面亦为真 |
| Q2 | 选项 A 在文档中亦为真，模型未做「区别技术特征」取舍 |

**距离 6/6 的差距已不在解析流水线内。** 若要继续推进，方向是问答层：

1. **system prompt 增加取舍规则**：「当多个选项都看似符合时，选择与本发明区别技术特征（权利要求特征部分 / 摘要强调的特征）最直接对应的那一项」——可定向修正 Q2；
2. **system prompt 明确「先经过」的判读口径**：「若题问『首先经过』且选项涉及同一组同类部件，以该组部件内部的先后为准」——可定向修正 Q5；
3. 或：与出题方确认 Q2/Q5 的题面口径（两题均可论证为**题目本身存在歧义**）。

> ⚠️ 需说明：上述 1、2 是针对本题集的定向调整，存在**过拟合测试集**的风险。
> 是否采用，建议由工单方决定 —— 这也正是 D2「原因分析」需要如实呈现的内容。

## 七、容器补丁固化（已完成并验证）

**问题**：补丁原先通过 `docker cp` 注入容器，`compose down/up` 重建容器即丢失；且本仓库的
`docker-compose.yml` 卷列表**不含** `deepdoc/`、`rag/prompts/`（印证需求分析 3.3.2 陷阱一）。

**方案**（路线 A：官方镜像 + 按需挂载）：

1. 新增目录 `ragflow-main/docker/patches/`，存放两个补丁文件：
   - `figure_parser.py`（含 `dedup_component_triples`）
   - `vision_llm_figure_describe_prompt.md`（三元组提示词 v3 = E 版）
2. 在 `docker-compose.yml` 的 `ragflow-cpu` 与 `ragflow-gpu` **两个服务**各追加两条 bind mount：
   ```yaml
   - ./patches/figure_parser.py:/ragflow/deepdoc/parser/figure_parser.py
   - ./patches/vision_llm_figure_describe_prompt.md:/ragflow/rag/prompts/vision_llm_figure_describe_prompt.md
   ```
3. `docker compose -p ragflow14 config --quiet` 校验通过 → `up -d ragflow-cpu` 重建容器。

**验证（关键：重建后容器内的 `docker cp` 残留全部消失，文件只可能来自挂载）**

| 检查项 | 结果 |
|--------|------|

| 容器内提示词 md5 | `2b0e5965…` ✅ 与补丁一致 |
| `docker inspect` 挂载点 | 两条 patches 挂载均生效 ✅ |
| 重建后重新解析 | 日志出现 `[TriplePostProcess]`，丢弃 `(4, 位于下方, 5)` 等 ✅ |
| 重建后切片（F2） | 18 chunk / 9557 字 / **违反 0** / Q3 仅 `(4, 位于左侧, 5)` ✅ |

→ **补丁已固化，容器重建后自动生效，结果可复现。**
