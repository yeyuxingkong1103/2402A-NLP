| --- | --- | ---: | --- |

> 最大 2444.79 ms。若把「105 样本里的冷启动（3 个）剔除」，则预热后的 **102 个真实首问样本

**在与其它任务并发竞争时 94.12% 达标**，超线的 3 个样本全部落在 Q13（英文题）与 Q10（长数值题）
—— 这两题评测官自己量到的也是全场最慢的 2501.16 / 2384.62 ms，本就贴着红线。

## 二、优化开关逐条实测

### 开关 1：`QAEngine.warmup(with_generate=True)` —— **预热**（唯一不可省略的一项）

| 项 | 实测 |
| --- | --- |
| 不预热的端到端 | **7940.95 / 7467.83 / 7339.18 ms**（三轮），达标率 **0/3** |
| 预热后的端到端 | 均值 **1530.33 ms**（51 样本），达标率 **48/51** |
| 增益 | 均值 **−79.8%（提速 4.96×）**，中位 **提速 6.29×** |
| 预热本身的代价 | **≈20～26 秒**（全新进程；见下方专节解释 19.6 s 与 26.5 s 的差异） |
| 代价构成 | 多字段倒排索引 **18.70～19.33 s**；索引加载 4.62 s；实体标注器 2.04 s；嵌入 0.27 s；生成后端探测 0.03 s；生成模型 `keep_alive` 0.30 s（除倒排索引外均为**构件分项实测**） |

**冷启动 7.5 秒的成分（`响应时间基准_冷启动分项.json`，独立干净进程逐项实测）**：
`import app` 0.52 s + `load_bundle` 4.62 s + `warmup_entity_tagger` 2.04 s + 嵌入 0.27 s +
后端探测 0.03 s + 生成预热 0.30 s ≈ **7.8 s**；与实际冷启动 `total` 7582.65 ms 吻合
（冷启动记录里的 `unaccounted_ms` = 6562.63～6947.67 ms，正是其中的 `load_bundle` + 实体标注器）。

#### ⚠️ 两个「预热代价」数字为什么不一样（19.6 s vs 26.5 s）—— 必须解释清楚

| 测量 | 数值 | 原因 |
| --- | ---: | --- |
| 主基准（`--mode full`）里 `warmup()` 自报 | **19.13 / 19.80 / 19.93 s** | 该进程**先跑了冷启动场景**，索引（`load_bundle`）与实体标注器**已经被那次冷问加载过**，warmup 走到这两项时命中模块级缓存 ≈0。证据：warmup 明细里 `entity_tagger.elapsed_ms` 只有 **1.41～1.49 ms**（冷的是 2035.08 ms） |
| 干净进程的分项实测（`--mode probe-cold`）构件合计 | **26.46 s** | 每一项都是**本进程首次**调用，没有任何前置预热 |

**推论（这才是生产启动的真实代价）**：一个**全新启动**的服务进程调用
`warmup(with_generate=True)`，要付的是 **≈20～26 秒**（19.6 s 只在「已经先答过一问」的前提下成立）；
其中 **18.7～19.3 s 是多字段倒排索引**。这解释了为什么预热**必须放在服务启动期**
而不是第一个用户请求上 —— 放在请求上就是本文测到的 7.5 秒违约。


**建议：必开，且必须在服务启动期完成，不要在第一个用户请求上懒加载。**
生产入口已经这么做（已核验）：
`部署/_工单6继承部署资产/脚本/serve_api.py`（第 107、141 行）、
`部署/_工单6继承部署资产/界面/web_app.py`（第 164 行）、
`部署/_工单6继承部署资产/界面/gradio_app.py`（第 143 行）都调用 `engine.warmup(with_generate=True)`。
⇒ **生产路径的用户首问不吃这 7.5 秒。**

> ⚠️ **重要边界**：上述「多字段倒排索引 18.7 s」只服务**全文检索策略模式**
> （`retrieval_strategy.MODE_FULLTEXT / MODE_HYBRID`）。默认的 `strategy=None` 混合链路
> （向量 + BM25 + RRF）**不使用**这个倒排索引。所以这 18.7 秒是为了「全文检索首问不违约」
> 而付的启动成本，不是默认链路的必需项。

### 开关 5：`RAG_RETRIEVAL__PROMPT_TOP_K` **3 → 2**（任务书举例的那一项）

配对交错设计（同题背靠背、两臂前都清空检索/生成缓存），8 题：

| 指标 | =3 | =2 | 变化 |
| --- | ---: | ---: | ---: |
| 总耗时 均值 ms | 1177.84 | 863.24 | −26.7% |
| 生成段 均值 ms | 852.90 | 738.30 | −13.4% |
| **生成段 配对中位变化** | — | — | **−17.16 ms（4 快 / 3 慢 / 1 平）** |
| **答案字符数 均值** | 242.6 | **168.2** | **−30.7%** |
| 关键词覆盖率（官方判分口径） | 0.0500 | 0.0708 | +0.0208（两者都接近 0，分辨不出差异） |

**结论：不采用（未实施）。**
① 生成侧配对中位数只有 −17 ms 且 4 快 3 慢 ⇒ **收益不稳健**，被 CPU 竞争（单题波动可达 ±1000 ms）淹没；
② 答案字符数 **−30.7%** 是明确的质量代价；
③ 本语料严格准确率仅 **11.76%**（评测官 `评估汇总.json`），**没有余量用准确率换 100 毫秒**。

### 开关 6：`RAG_EMBEDDING__BATCH_SIZE`（批处理嵌入）

* **在线路径：零影响（确定性结论，不是推测）** —— 在线只嵌 1 条查询文本，任何批大小都退化为 1 次往返。
* **离线/建索引路径**（32 条真实语料块，600 字符截断）：

| batch_size | 1 | 2 | 4 | 8 | 16 | 32 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 总耗时 ms | 2772.85 | 3366.08 | 4525.09 | 2845.62 | 2035.52 | 2801.78 |
| 往返次数 | 32 | 16 | 8 | 4 | 2 | 1 |

耗时**非单调**、极差 2.2× ⇒ 在纯 CPU 推理下嵌入是**算力瓶颈而非往返瓶颈**，
减少往返不减少总计算量。**建议保持默认 16**；要验证批量的真实收益需要独占 CPU 复测（本工单做不到）。

## 四、为什么不进一步优化（取舍说明）

### 4.1 生成段是绝对大头，而它已经在合理水平

预热后 51 个样本的分段占比：检索 **141.11 ms（9.2%）**、生成 **1331.48 ms（87.0%）**。
**瓶颈就是 CPU 上的 `qwen2.5:3b` 解码**，而不是检索、不是缓存、不是代码。
检索侧已经做到 P90 173.39 ms，即使把它优化到 0 也只能省 9%。
所以「继续优化检索」的边际收益极低 —— **这是不继续投入的方向性理由**。

### 4.2 能压生成的只有三条路，每一条的代价都超出「低风险」

| 思路 | 预期收益 | 为什么不做 |
| --- | --- | --- |
| 减注入证据（`prompt_top_k` 3→2） | 生成 −13.4%（不稳健） | 答案 **−30.7%**；准确率无余量（严格 11.76%） |
| 换更小模型（`qwen2.5:1.5b` / `0.5b`） | 未运行 | 会改变答案内容 ⇒ 必须评测官重新判分，属**质量变更**非性能优化 |
| 关闭 LLM 走确定性 extractive | 未运行 | 改变答案形态与生成方式口径（`generation_method`），会破坏评测口径 |

### 4.3 冷启动的 7.5 秒不优化，因为它在生产路径上不存在

`load_bundle`(4.62 s) + 实体标注器(2.04 s) 都是**一次性惰性初始化**，生产入口在启动期就付掉了。
进一步压缩它们只会缩短**服务启动时间**（当前 ≈20～26 s），**不影响用户响应时间**，
却要动 `研发/` 的核心加载路径 —— 收益/风险比不成立。

### 4.4 不做的事（明确记录，避免被当成遗漏）

* **不做 CPU 独占 / 多 Ollama 实例 / 线程数调优**：`127.0.0.1:11434` 是**共享单实例**，
  这是本工单既定的运行环境约束，不属于本工单可变更范围；本文所有数字都带这条声明。
* **不改任何 `研发/` 代码**（含「把检索耗时降到 0」这类收益很小的改动）。
* **不引入新的第三方依赖**（本机 pip 通道受限，见 `run_py.ps1` 记录的环境事实）。

## 六、边界、风险与不确定（如实登记）

| 项 | 说明 |
| --- | --- |
| **共享 CPU 竞争** | Ollama 是 CPU 单实例，与「评测官 17 题评估」「测试官回归」并发。三轮同协议复跑的均值 1420.28 / 1658.24 / 1512.48 ms、最大 2303.24 / 6247.48 / 4950.13 ms —— **最大值相差 2.7 倍**，差异来自竞争而非代码。 |
| **冷启动未含模型冷加载** | 三轮测量的全过程 `/api/ps` 都显示 `qwen2.5:3b`、`bge-m3:latest` 已驻留（其它任务 keep-alive）。若模型需从磁盘冷加载（任务书背景事实里的「首字 3.4 s」即该情形），冷启动会更差。**本文的冷启动 = 进程冷 + 索引冷 + 缓存冷 + 模型已驻留。** |
| **run1 期间 `generator.py` 被改** | 文件 mtime 21:26:09 落在 run1（21:24:00–21:26:16）尾段。**但 Python 模块只 import 一次，run1 进程内跑的始终是启动时导入的那一版**（`修订_start` = `1be2c097ff899eee`），故 run1 内部自洽、可归因到该修订。run2（主产物）与 run3 期间**无任何模块被修改**。 |
| **超线样本集中在 Q10 / Q13** | Q13 是英文题（多一次翻译 LLM 调用），Q10 是长数值题。两题评测官独立实测也是全场最慢（2501.16 / 2384.62 ms），**基线就贴着红线**。 |
| **`prompt_top_k` 子集是 Q01–Q08** | 这 8 题恰好是本套题里最难的一段（关键词覆盖率 0.05～0.07，评测官在这 8 题上仅 Q06 部分正确）。因此**质量维度的分辨力不足**，不能据此断言 prompt_top_k=2 不伤准确率 —— 只能说「有 −30.7% 的答案长度代价，且性能收益不稳健」。 |
| **`sqlite_fill` 不是「全冷」** | 该场景下检索层与生成层缓存已热，只有答案级内存缓存是空的，所以 21～27 ms 不代表一次完整的首次问答（完整首问见 `warm_no_cache` 的 1530.33 ms）。 |
| **批量嵌入扫描受竞争污染** | 各档耗时非单调、极差 2.2×，**不足以支撑任何结论性调参**，只足以支撑「在线路径零影响」这一结构性结论。 |
| **未运行项** | ① 生成模型磁盘冷加载后的首字延迟；② `RAG_CACHE__TTL_S` 到期场景；③ 独占 CPU（无并发）条件下的复测；④ 多进程/多实例压测；⑤ 换更小生成模型的性能与质量。 |
