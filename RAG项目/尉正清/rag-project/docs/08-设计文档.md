# 设计文档

> 本文说明技术架构与功能设计，重点在**为什么这么设计**。
> 组件与字段的具体规格见 `05-系统设计.md`，接口出入参见 `07-接口文档.md`。

## 1. 设计目标与取舍

| 目标 | 取舍 |
|---|---|
| 专业领域回答有据可依 | 宁可如实说"资料不足"，也不让模型凭记忆作答——法律、医疗、金融三个领域编造代价太高 |
| 角色可扩展 | 人设与规则存 MySQL，新增角色是插一行数据，不改代码 |
| 检索既准又全 | 单一向量检索对**编号类精确信息**不敏感，必须补一路结构化召回 |
| 多轮对话不丢上下文 | 短期记忆保"记得清"，长期记忆保"想得起"，两者职责分开 |
| 单机可跑 | 全部组件用 Docker 单机部署，未引入 K8s 等重型依赖 |

**明确不做**：不做前端界面；不做 Token 鉴权（仅用户标识）；不做模型微调；
不引入 MongoDB / ClickHouse 等本项目用不上的存储。

## 2. 总体架构

```
                       ┌──────────────────────────┐
   客户端 / Postman ──▶ │  app/api/   接口层        │  参数校验、响应包装
                       └────────────┬─────────────┘
                                    │
                       ┌────────────▼─────────────┐
                       │  app/core/  业务层        │  11 个服务，各司其职
                       └────────────┬─────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
      │ app/db/      │     │ 本地模型      │     │ 外部服务      │
      │ MySQL        │     │ BGE-M3       │     │ DeepSeek API │
      │ Milvus       │     │ BGE-reranker │     │              │
      │ Redis        │     └──────────────┘     └──────────────┘
      └──────────────┘
```

**依赖方向单向向下**：接口层不碰存储，业务层不碰 HTTP，数据层不含业务判断。
好处是每一层都能单独替换——例如把 DeepSeek 换成本地 vLLM，只改 `llm_service`。

### 业务层服务划分

| 服务 | 职责 | 不做什么 |
|---|---|---|
| `rag_service` | 编排一次问答的完整链路 | 不实现具体检索/记忆逻辑 |
| `query_service` | 追问改写、查询扩写 | 不访问存储 |
| `retrieve_service` | 多路召回、RRF 融合、精排 | 不生成回答 |
| `metadata_service` | 法条号精确召回 | 不做语义检索 |
| `memory_service` | 双层记忆读写 | 不关心回答内容 |
| `ingest_service` | 切块、向量化、写入 | 不做检索 |
| `update_service` | 哈希比对、先删后增 | 不重复实现切块 |
| `pdf_service` / `watermark` | PDF 解析编排、水印擦除 | 不碰向量库 |
| `mineru_service` | 调 MinerU 子进程把 PDF 解析成 Markdown（独立 venv） | 不管水印，不判定降级 |
| `ocr_service` / `table_service` | 兜底路径：PaddleOCR 补图表文字、pdfplumber 还原表格 | 只在 MinerU 不可用时被调用，主路径下不参与 |
| `role_service` / `session_service` | 角色与会话的 MySQL 读写 | 不含提示词拼装 |

## 3. 检索链路设计

这是系统的核心。一次检索经过三段：

```
查询理解        多路召回                      融合        精排
─────────      ──────────────────────      ──────      ──────
追问改写    ┌─▶ ① 稠密向量（BGE-M3）  ─┐
   ↓        │                           │
查询扩写 ───┼─▶ ② 稀疏权重（BM25 风格）─┼─▶ RRF ─▶ BGE-reranker ─▶ top-5
（1→3 个）  │                           │  加权      交叉编码器
            └─▶ ③ 元数据路（法条号）  ─┘
```

### 3.1 为什么要三路

| 路 | 擅长 | 短板 |
|---|---|---|
| 稠密向量 | 语义相近，换个说法也能找到 | 对编号、专名不敏感 |
| 稀疏权重 | 关键词、条文号、专有名词 | 不理解同义改写 |
| 元数据路 | 条文号等**精确信息** | 只在能识别出编号时才有结果 |

实测：用户问「刑法第一百三十三条怎么规定的」，纯向量检索会把语义相近的
第一百三十条、第一百三十一条一起召回，真正那一条未必排第一。加元数据路后
可以精确命中。

### 3.2 为什么用 RRF 而不是分数加权

向量相似度（0~1 的余弦）与 BM25 分数（无上界）**量纲不可比**，
归一化又会引入额外假设。RRF 只用「排第几」不用「多少分」：

```
score(d) = Σ w_i / (k + rank_i(d))        k = 60
```

权重 `w_i` 用来表达各路的可信度差异：元数据路是精确匹配，给 2.5 倍权重，
否则单路召回的精确命中会被「多路都提到」的宽泛结果挤下去。

### 3.3 为什么扩写后再检索

单一表述只能覆盖知识库中的一种说法。把一个问题扩成多个查询分别检索、
结果融合，相当于用不同角度各撒一次网。实测：

```
「酒驾撞人要判多久？」
  ├─ 酒后驾驶机动车撞人需要承担多少年刑罚
  └─ 交通肇事罪 酒驾撞人 量刑标准
```

扩写用大模型完成，失败时回退为原查询，不阻断主流程。

## 4. 双层记忆设计

```
第 N 轮对话 ──▶ Redis List（最近 10 轮原文）
                    │ 窗口滑出的旧行
                    ▼
              mem:pending 缓冲（攒够 6 行）
                    │ 大模型压缩
                    ▼
              Milvus long_term_memory（摘要 + 向量）
                    │ 每轮按当前问题语义召回 top-3
                    ▼
                 注入提示词
```

**为什么分两层**：Redis 保证"刚说过的话"一字不差且读写 O(1)；
Milvus 保证"很久以前说过的关键信息"在想得起来时还能被想起。
只保留窗口会丢信息，只保留摘要会丢细节。

**为什么不设相似度阈值**：实测在 BGE-M3 的向量空间里，相关问句（0.440）
与无关问句（0.434）的余弦相似度几乎重叠，任何固定阈值都会静默丢掉真正
相关的记忆。召回的是用户自己的历史，多带一条的代价远小于漏掉一条，
因此按 top-k 取用即可（该结论记录在 `memory_service.recall` 的注释中）。

## 5. 查询理解设计

| 手段 | 解决的问题 | 触发条件 |
|---|---|---|
| 追问改写 | 「那它呢」脱离上下文无法检索 | 存在历史对话时 |
| 查询扩写 | 单一表述覆盖不全知识库说法 | 始终（可用 `QUERY_EXPAND_N=1` 关闭） |
| 法条号抽取 | 编号是精确信息，不该靠语义猜 | 问题中出现「第X条」时 |

三者都是**尽力而为**：任一步失败都回退到原问题，不影响主流程。

## 6. 提示词模板设计

分四段组装，各段来源不同：

| 段落 | 来源 | 作用 |
|---|---|---|
| 角色人设 + 回答规则 | MySQL `roles` 表 | 决定身份、语气、边界 |
| 用户长期记忆 | Milvus | 保持跨会话连贯 |
| 参考资料 | 检索结果 | 回答的事实依据 |
| 最近对话 | Redis | 保持多轮连贯 |

基础规则由 `prompt.py` 的 `BASE_RULES` 提供（不得编造、资料不足走兜底、
不暴露"检索"等实现细节），角色自身的 `rules` 追加其后。
**免责声明不在提示词里，而是生成后由代码追加**——避免模型改写或遗漏。

## 7. 知识入库设计

### 7.1 切块策略

| 记录长度 | 策略 |
|---|---|
| ≤ 1500 字 | 整条入库，用 `embed_text`（清洗过的问题/标题）做向量 |
| > 1500 字 | 走语义分块（按话题转折切分），每块各自向量化 |

**为什么用 `embed_text` 而不是正文做向量**：问答类数据里，
问题才是用户会问的话，用问题做检索目标命中率明显更高；
正文存下来喂给大模型。数据集在 `scripts/prepare_dataset.py` 阶段
就把两者分开了。

### 7.2 更新幂等

入库时把文件 SHA256 写进每条切片的 `content_hash`。更新时先比对哈希，
一致就跳过，避免无谓的重新向量化；变更则「先删后增」——
按 `source` 删除旧切片再重建，保证不会新旧混杂。

删除后**立即 flush**：Milvus 的删除是最终一致的，不 flush 会出现「接口已经返回
200 删除成功、紧接着查询仍能查到旧数据」。项目其他地方确立了「200 即已生效」的
口径，这里对齐（`MilvusStore.delete_by_expr`）。

## 8. 可靠性与降级

| 环节 | 失败时的行为 |
|---|---|
| MinerU 未安装 / 解析失败 / 超时 | 降级为**三件套**（`path=pymupdf`）：PyMuPDF 逐页取文本层、PaddleOCR 补图表文字、pdfplumber 还原表格。图表与扫描件仍能读到，弱在阅读顺序与公式；接口不报错 |
| PaddleOCR 不可用（如 `enable_mkldnn` 未关导致加载失败） | 静默退回纯文本层，记一条「OCR 不可用，仅提取文本层」 |
| pdfplumber 不可用 | 跳过表格提取，记一条「pdfplumber 不可用，跳过表格提取」，表格退化为纯文本 |
| 混合检索 | 降级为纯向量检索 |
| 重排序 | 退化为融合顺序 |
| 查询改写 / 扩写 | 回退为原问题 |
| Redis 不可用 | 读返回空、写记录告警，不阻断问答 |
| Milvus 集合未载入 | 自动重新 load 并重试一次 |
| 大模型返回空正文 | 放大 `max_tokens` 重试；仍为空则用角色兜底话术 |
| MySQL 不可用 | 服务仍启动，角色/会话类接口不可用 |

**重模型懒加载**：BGE-M3 与 Reranker 在首次请求时才加载，
避免 `import app.main` 就占显存，脚本与测试可以轻量运行。

## 9. 可扩展点

| 想做什么 | 改哪里 |
|---|---|
| 新增角色 | 往 `roles` 表插一行（人设、规则、兜底、免责声明） |
| 换大模型 | 改 `.env` 的 `DEEPSEEK_*`；接口是 OpenAI 兼容协议 |
| 换向量模型 | 改 `EMBEDDING_MODEL_PATH` 与 `EMBEDDING_DIM`，重建知识库 |
| 扩法条覆盖 | 在 `scripts/fetch_statutes.py` 的 `PRIORITY` 追加法规名，调大 `TARGET` |
| 接入新数据源 | 实现一个 `search()` 返回 `[{text, title, source}]`，加进 `retrieve_service` 的 `route_lists` |
| 换 PDF 解析器 / 关掉 MinerU | 改 `.env` 的 `MINERU_BIN` / `MINERU_TIER`；移除 `mineru/.venv` 即自动降级为三件套兜底，无需改代码 |
| 关掉兜底路径的 OCR / 表格 | 上传接口传 `use_ocr=false` / `use_tables=false`（只对兜底路径生效） |
| 关闭某项优化 | `.env` 里 `QUERY_EXPAND_N=1` 或 `ENABLE_METADATA_ROUTE=false` |
