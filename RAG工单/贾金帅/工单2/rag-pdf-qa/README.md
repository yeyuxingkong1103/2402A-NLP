# 招股说明书 RAG 问答系统 · 用户手册

> **工单编号：人工智能NLP-RAG-基于PDF文档的问答系统**（工单1 · 功能实现）
> **工单编号：人工智能NLP-RAG-基于PDF文档的问答系统优化**（工单2 · 优化任务）
> 项目：RAG · 基于 PDF 文档的问答系统 · 创建人：王洪荣

本系统针对《武汉兴图新科电子股份有限公司首次公开发行股票并在科创板上市招股意向书》
（548 页）提供检索增强问答。所有答案**只依据文档内容**生成，并标注来源页码，便于核对。

> **工单2 做了什么**：在优化前（朴素 RAG：定长切分 + 纯向量检索）基础上，
> 关键事实命中率 **0.60 → 1.00**、正确答案命中率 **0.60 → 1.00**、MRR **0.298 → 0.707**，
> 平均响应时间 **1379ms → 1314ms**。
> 完整方案与对比见 **`docs/工单2-优化方案.md`**。

## 一、5 分钟跑起来

### 1. 环境

| 项 | 说明 |
|---|---|
| Python | 3.10+（本项目在 3.12 / 3.13 上验证） |
| 依赖 | 见 `requirements.txt`（pypdf / pdfplumber / sentence-transformers / jieba / rank-bm25 / openai / fastapi / uvicorn） |
| 向量模型 | 本机已存在 `D:\bge-small-zh-v1.5`（512 维，约 184MB） |
| 大模型 | 任一 OpenAI 兼容服务（DashScope / Moonshot / 硅基流动） |

> 本机已有一套现成的虚拟环境，包含上述全部依赖，可直接用它作为解释器：
> `D:\roleplay-rag\.venv\Scripts\python.exe`
> 若要在干净环境重建：`python -m venv .venv && .venv\Scripts\pip install -r requirements.txt`

### 2. 配置

编辑根目录 `.env`，只需确认两项：

```ini
LLM_API_KEY=sk-...            # 大模型 Key（必填）
EMBEDDING_MODEL_PATH=D:\bge-small-zh-v1.5   # 本地向量模型目录
```

### 3. 建索引（首次必须做）

```bash
python scripts/build_index.py
```

首次约 6 分钟（解析 48s + 向量化 285s，纯 CPU）。完成后 `data/index/` 下会生成三件套。

> 想先看看解析和分块效果、不花时间向量化：
> `python scripts/build_index.py --no-tables --dry-run`

### 4. 启动服务

```bash
python main.py
```

浏览器打开 **http://127.0.0.1:8010/ui**

## 二、怎么用

### 提问

在底部输入框打字，回车发送。支持三种输入方式：

1. **文字输入** —— 直接打字，Shift+回车换行。
2. **语音输入** —— 点「🎤 语音」，对着麦克风说话，识别结果会填进输入框，确认后发送。
   *需要 Chrome / Edge 浏览器并允许麦克风权限；其他浏览器该按钮会自动禁用。*
3. **点现成问题** —— 右侧「工单验收问题」面板里有 10 道题，点一下直接问。

### 看答案

答案里每个关键事实后面会有红色页码标记，形如 `[第22页]`，表示这句话的依据出自该页。

答案下方是**依据片段**列表：

- 每条显示页码、依据分、融合分、块编号；
- **点一下标题行**可以展开该片段在原文里的**完整文字**——这是原始文本，不是模型复述的，
  可以直接拿去和 PDF 对照。

### 看检索链路

右侧「检索链路」面板显示这一次提问的内部过程：

| 区块 | 含义 |
|---|---|
| ① QUERY 理解 | 系统把问题判成什么意图、改写成什么检索式、拆出了哪些子问题 |
| ② 检索 | 稠密（余弦）与稀疏（BM25）两路各自耗时、候选池大小、融合权重、依据分区间、阈值与保留条数 |
| ③ 实际检索用的 QUERY | **真正送进检索器的那句话**。如果觉得答案不对，先看这里——多半是改写偏了 |

面板底部会明确提示闸门是通过还是拦空：

- 绿色「闸门通过」→ 有足够依据，答案基于这些片段生成；
- 黄色「检索被阈值闸门拦空」→ 资料里没有相关片段，模型会如实说"资料中没有相关内容"，
  **不会编**。

### 对比纯 LLM / 优化前后

左下角「对比模式」是个下拉框，四种选择：

| 选项 | 效果 |
|---|---|
| 关闭（仅本系统） | 只跑本系统，流式输出答案 |
| **优化前 vs 优化后** | 并排给出「朴素 RAG」与「本系统」两栏，并标出**关键事实命中情况** |
| 本系统 vs 纯 LLM | 并排给出「RAG（基于文档）」与「纯 LLM（无检索）」，即工单1 要求的那组对比 |
| 三方对比 | 优化前 / 优化后 / 纯 LLM 三栏并排 |

「优化前 vs 优化后」这栏下方会显示一行**关键事实命中条**：

```
优化前   5,520       1/1
优化后   5,520       1/1
```

被划掉标红的词，表示这条事实**根本没被检索到**——模型不可能答对。问到工单验收的
10 道题时，这一行就是最直观的优化效果展示。

> 右侧还提供 **「一键对比 10 题」** 按钮：依次跑完 10 道验收题，
> 输出一张「优化前/优化后关键事实命中数 + 耗时」的对照总表。
> 整轮约需 1~2 分钟（要调 20 次大模型）。

### 换文档

```bash
python scripts/build_index.py --pdf "D:\path\to\你的.pdf"
```

或调用上传接口（会同步重建索引，前端有耗时计时器）：

```bash
curl -F "file=@你的.pdf" http://127.0.0.1:8010/api/upload
```

## 三、工单 10 题的实际表现

完整评估报告见 `data/eval/` 下的 `report_*.md`（工单1）与 `工单2_*.md`（工单2）。

### 3.1 优化前 vs 优化后 vs 纯 LLM（工单2）

同一套 10 题，三条链路各跑一遍。命令：`python scripts/compare_optimization.py`

| 指标 | 优化前（朴素 RAG） | **优化后（本系统）** | 纯 LLM（参照） |
|---|---|---|---|
| **关键事实命中率**（检索层·客观规则） | 0.600 | **1.000** | — |
| **全部关键事实命中的题目数** | 6/10 | **10/10** | — |
| 忠实度 faithfulness | 0.700 | **0.975** | — |
| 答案相关性 answer_relevancy | 0.630 | **1.000** | 0.500 |
| 上下文精确率 context_precision | 0.350 | **0.600** | — |
| 上下文召回率 context_recall | 0.600 | **1.000** | — |
| **答案正确性 answer_correctness** | 0.590 | **0.930** | **0.060** |
| 平均响应时间 | 1379 ms | **1314 ms** | 877 ms |
| 最大响应时间 | 4947 ms | **3368 ms** | 2294 ms |
| ≤3 秒达标率 | 0.9 | 0.9 | 1.0 |

> 响应时间几乎全部花在大模型生成上（检索只占 ~15ms、Query 理解 ~20ms）。
> 优化后的**尾延迟明显更稳**（最大 3.37s vs 优化前 4.95s），
> 剩余的超 3 秒来自模型服务侧的单次抖动，不是系统侧开销。

### 3.2 检索精确度逐层变化（消融实验）

命令：`python scripts/ablation_retrieval.py`（不调 LLM，纯客观规则指标）

| 配置 | 关键事实命中率 | 全部命中 | 正确页命中率 | MRR |
|---|---|---|---|---|
| A0 朴素 RAG（优化前） | 0.650 | 6/10 | 0.600 | 0.298 |
| A1 + 解析层（行内标题断行） | 0.650 | 6/10 | 0.600 | 0.298 |
| A2 + 分块层（标题感知，检索仍纯向量） | 0.450 | 4/10 | 0.400 | 0.325 |
| A2b 受控：定长分块 + BM25（无 DF 过滤） | 1.000 | 10/10 | 1.000 | 0.489 |
| A2c 受控：定长分块 + 完整检索（BM25+DF） | 0.950 | 9/10 | 1.000 | 0.700 |
| A3 + 检索层（BM25 混合） | 1.000 | 10/10 | 1.000 | 0.422 |
| **A4 + 检索层（DF 过滤·词级+短语级）** | 1.000 | 10/10 | 1.000 | **0.707** |
| **A5 完整优化系统（+ 阈值闸门）** | **1.000** | **10/10** | **1.000** | **0.707** |

**收益归因**（受控对照，每行只变一个变量）：

| 层面 | 优化项 | 关键事实命中率 | MRR |
|---|---|---|---|
| 检索层 | BM25 混合 | **+0.550** | +0.097 |
| 检索层 | DF 过滤（词级 + 短语级） | +0.000 | **+0.285** |
| 分块层 | 标题感知分块（纯向量下） | −0.200 | +0.027 |
| 分块层 | 标题感知分块（完整检索下的严格受控对照 A2c→A4） | +0.050 | +0.007 |
| 解析层 | 行内标题断行 | +0.000 | +0.000 |

> 结论反直觉但可复现：**把命中率从 65% 拉到 100% 的是检索层，不是「把 PDF 切得更好」。**
> 最严格的一格是 `A2c`（定长分块 + 与最终版完全相同的检索层）：它拿到
> **0.950 命中率 / 0.700 MRR**，几乎与 `A4` 持平，说明**分块层的收益上限只有 +0.050**——
> 而且这 0.050 全部来自一道题（id=95：定长滑窗把一句话里的两个关键事实切进了相邻两块）。
> 详细分析见 `docs/工单2-优化方案.md` 第四节。

### 3.4 稳定性、容错与多语言（工单2 验收项）

脚本：`python scripts/load_test.py --concurrency 8 --rounds 2 --soak 400`（需服务已启动）

**并发**——把「系统层」和「端到端」分开测，否则数字没法解读：

| 链路 | 并发 | 成功率 | 吞吐 | P50 | P99 |
|---|---|---|---|---|---|
| **系统层** `/api/search`（只检索不生成） | 8 | 100% | **56.2 rps** | 135.6 ms | **146.0 ms** |
| **端到端** `/api/ask`（含模型生成） | 8 | 100% | 0.68 rps | 10 635.6 ms | 13 468.0 ms |

端到端在 8 并发下变慢，**根因在上游不在本系统**：单路平均 1 268.7 ms，
16 请求 ÷ 8 并发理想墙钟应为 2.5 s，实测 23.4 s —— **串行化系数 9.22 ≈ 并发数**，
即大模型侧把请求排成了一队，实际并发度是 1。压测期间**无 429、零失败**。

**长时间运行**：连续 400 次检索，**400/400 成功**，P50 27.3 ms / P99 53.1 ms，
前 25% 均值 31.08 ms → 后 25% 均值 27.98 ms，**漂移系数 0.90**（后段没变慢）；
进程 RSS 703 MB → 705 MB（**+1.7 MB**），无泄漏迹象。

**容错**：9 类异常输入（空 / 空白 / 非字符串 / 缺字段 / 3000 字超长 / 离题 / 闲聊 / 两个对比接口空问题）
**全部返回结构化错误，未兜住 0 个**。超长输入选择「截断后照常作答」而非报错。

**多语言**：中英文各问一遍，英文回答语种一致性 0.90 / 0.99。
已知缺陷：英文里 `5,520万元` 曾被译成 `5,520.00 million RMB`（**放大 100 倍**），单位换算不可靠。

## 四、阈值是怎么定的（不是拍脑袋）

`RETRIEVAL_MIN_EVIDENCE` 控制"什么算有依据"。取值用实测校准，命令：

```bash
python scripts/probe_retrieval_rank.py --calibrate
```

本语料的实测结果（依据分 = 余弦 + 0.30 × BM25归一）：

| 问题类型 | 依据分区间 |
|---|---|
| 工单 10 个真相关问题 | top1 **0.9388 ~ 1.0542**，top6 最低 **0.8732** |
| 3 个明确离题问题（Python 快排 / 北京天气 / 红烧肉） | 最高 **0.7487** |

两段区间**不重叠**，0.80 落在中间，因此取 **0.80**。

> 为什么不用更低的 0.55？因为在**单文档语料**上余弦分天生扁平——离题问题也能拿到
> 0.56~0.75 的余弦（文档通篇都在讲同一家公司）。只有加上 BM25 那一项，
> 真相关问题才会被推到 0.87 以上，而离题问题（关键词一个都命中不了）留在 0.75 以下。
> **如果把这套参数搬到多文档语料，必须重新跑一遍校准。**

## 五、常见问题

**Q：状态栏「大模型」显示红色？**
`.env` 里的 `LLM_API_KEY` 没填、填错，或额度用尽。探针是真发一次请求，不是只看 Key 存不存在。
点一下浏览器刷新可重新检测；后端每 30 秒也会自动刷新。

**Q：状态栏「索引」显示不可用？**
还没建索引。跑 `python scripts/build_index.py`。

**Q：每次都回答"资料中没有相关内容"？**
先看右侧链路面板的「③ 实际检索用的 QUERY」，确认改写没跑偏；再看「依据分区间」——
如果最高分低于 0.80，说明确实没召回到相关片段。可以调大 `.env` 里的
`RETRIEVAL_FINAL_TOP_K`（召回条数）或降 `RETRIEVAL_MIN_EVIDENCE`，改完重启服务。

**Q：响应时间超过 3 秒？**
看链路面板的耗时拆分。若卡在「生成」这一步，是模型侧排队/限流；
若卡在「理解」，可以在 `.env` 里设 `QUERY_UNDERSTANDING_ENABLED=false`，
Query 理解会退回纯规则实现（几乎不耗时，代价是改写与子问题拆解变简单）。

**Q：多人同时用会不会把服务压垮？**
不会。瓶颈不在本服务 —— 本地检索能跑到 56 rps / P99 146 ms，
慢的是上游大模型（它会把自己的并发请求排成队）。
想看某个问题实际召回了哪些块、耗时多少，直接打 `/api/search`：

```bash
curl -X POST http://127.0.0.1:8010/api/search \
  -H "Content-Type: application/json" \
  -d '{"question":"注册资本是多少？"}'
```

**Q：语音按钮点不动？**
浏览器不支持 Web Speech API（Firefox 不支持）。换 Chrome / Edge。
