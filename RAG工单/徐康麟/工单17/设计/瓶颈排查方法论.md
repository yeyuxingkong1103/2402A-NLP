## 0. 总原则：假设 → 验证 → 修改（工单原文备注1）

每个疑似点都走同一条链，**任一步拿不出数字就不写进结论**：

```
现象（可观测数值）
  → 证据（数字 / 火焰 / 对象统计 / 曲线）
  → 代码位置（文件:行，必须真实存在）
  → 根因（一句话能讲清机制）
  → 修复（可开关、阈值配置化）
  → 复测（同脚本同参数的前后对比）
```

**反例（本工单明确拒绝的写法）**：
- ❌ 「推测是 DeepDoc 重复初始化」——本仓库没有 DeepDoc，必须先核实再写。
- ❌ 「内存泄漏可能是缓存」——必须给出 tracemalloc 的 Top 对象与类型统计。
- ❌ 只给优化后数字、不给优化前数字——无对比即无结论。

## 2. 四条排查主线

### 2.1 主线一：CPU / 时间去哪了

1. **分段计时**：`qa_engine.answer()` 已经内建 `latency_ms = {retrieve, generate, first_token, total}`，
   直接可从每请求响应体与 JSONL 日志聚合出「检索 vs 生成」占比 —— **先看这条，成本最低**。
2. **cProfile 全量**：对一个串行请求跑 `cProfile.runctx`，`pstats.sort_stats('cumulative')` 取前 30。
   注意：cProfile 会让耗时膨胀 2~5 倍，**只用于定位相对占比，不用于绝对性能结论**。
3. **线程栈快照**：并发压测中对服务进程做 3 次 `threading.enumerate()` + `sys._current_frames()`，
   按栈顶函数聚类 —— 若大量线程停在 `urlopen`/`socket.recv`，即「I/O 阻塞」实证；
   若停在 `sqlite3` 的 `commit`，即「落盘串行化」实证。
4. **`_http_json` 调用计数**：对 `urllib.request.urlopen` 打计数器，
   除以请求数 = **每请求外部 HTTP 往返次数**。这是「连接未复用 / 重复探测」的直接证据。

### 2.2 主线二：内存涨在哪

1. **RSS 曲线**：压测期间每 5 s 采样，判「是否有持续上涨趋势」
   —— 用首 20% 窗口均值 vs 末 20% 窗口均值，再做一元线性回归给斜率（MB/min）。
2. **tracemalloc 快照 diff**：`t0`（压测前）→ 压测中 → 压测后 `gc.collect()` → `t1`，
   `snapshot1.compare_to(snapshot0, 'lineno')` 取 Top 20 行号。
   **只有 diff 的 `size_diff` 为正且持续增长的调用点才是泄漏点**，一次性分配不是。
3. **对象计数分类**：`gc.get_objects()` 按 `type(obj).__name__` 统计，对比前后 `count` 与估算 `bytes`。
   重点看 `dict` / `list` / `Answer` / `Turn` / `str`。
4. **容量上界审查（静态）**：逐个打开所有 `dict` / `OrderedDict` / `list` 形式的全局或实例级集合，
   确认「有没有 max size / TTL / 淘汰」。**没有上界的一律判为泄漏点**。
   本工单需审：`qa_engine._memory_cache`、`cache.py::TTLCache`、`dialogue_cache.DialogueCache`、
   `session_store.FileSessionStore`、`conversation.ConversationStore`、`sqlite_manager.answer_cache` 表、
   `retriever._BUNDLE_CACHE` / `_CORPUS_ID_CACHE`。

### 2.3 主线三：并发为什么崩

1. **在途请求数曲线**：压测器每 2 s 记录「已发射 - 已完成」= 在途数。
   在途数随并发线性上升且不收敛 ⇒ 服务端吞吐已达上限、请求在堆积。
2. **队列深度 / 线程池占用**：任何 `ThreadPoolExecutor` 的 `_work_queue.qsize()`；
   anyio 默认线程池 40 —— 若 20 并发下 40 个线程全被占满，说明**同步路由把重活放在线程池里跑**。
3. **无界 vs 有界**：检查「有没有 429 / 排队上限」。
   `service/config.py` 定义了 `max_concurrency=4` 却**零引用** ⇒ 无任何限流（实证用 `grep` 计数）。
4. **GIL 争用**：numpy `vectors @ q` 与 FAISS `search` 会释放 GIL；纯 Python 重排（`reranker.py`）
   不释放。若线程栈大量停在 reranker/composer 的 Python 帧 ⇒ GIL 是瓶颈。

### 2.4 主线四：连接与外部依赖

1. **每请求 TCP 建连计数**：统计 `socket.create_connection` / `urlopen` 调用次数，
   对比请求数。≈ N 倍即**无连接复用**。
2. **sqlite 事务次数**：统计 `commit()` 调用次数 / 请求数。>1 即**每请求多次 fsync**。
3. **Ollama 驻留**：`GET /api/ps` 看 `expires_at` 与 `size_vram`。
   `keep_alive="30m"` ⇒ 模型在最后一次请求后仍驻留 30 分钟，期间显存/内存不释放
   —— 这正是原文「GPU 内存被大量占用且释放不及时」的机制。
