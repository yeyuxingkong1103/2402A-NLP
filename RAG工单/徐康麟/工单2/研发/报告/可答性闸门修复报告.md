## 1. 缺陷与根因

### 缺陷 A：含公司名/文档名的无关问题被误答（验收 4）
旧口径 `Retriever.is_answerable` 只统计"问题实义词是否出现在片段里"（`min_overlap_terms=1`）。
含公司名的无关问题（如「武汉兴图新科电子股份有限公司的**食堂**今天中午吃什么？」）因为
`武汉兴图新科电子股份有限公司` 被切出的 `兴图/新科/电子/股份/有限公司` 全部命中片段，
覆盖度天然很高 → 放行 → 抽取式只好"硬取一段"。
**同机复算（关闭新闸门后的旧口径）**：官方 12 条里有 **4 条**被放行（高铁题、食堂题、新能源汽车题、奖学金题）。

### 缺陷 B：闸门 v1 把合法追问判死（验收 5 回归，t1 修复）
`answerability.check` 取"IDF 最高"的词当 rarest 并要求它出现在证据里。
`_idf_lookup` 对**语料未登录词**返回"语料最大 IDF + 1"——即未登录词**必然**是最罕见词；
于是只要疑问代词漏进主题词表（`QUESTION_FILLERS` 缺「哪里」），
它就成为 rarest 且**永远不可能出现在证据里** → **合法问题被一票否决**。
实测：`它的注册地址在哪里？` → `rare_term_missing:哪里` → 误答「不清楚」，
在线用例 `test_multiturn_v2.py::test_three_turn_conversation_with_coreference` 由绿转红。

### 缺陷 C：意图↔取值类型一致性在中文路径上静默失效
中文意图名来自 `query_understanding.INTENT_PATTERNS`（标准类＝**"标准"**），
英文桥接来自 `language.detect_english_intent`（标准类＝**"技术标准"**）；
`INTENT_VALUE_KINDS` 只登记了后者 → 中文标准类问题的"取值类型一致性"这一半**从未生效**。

### 缺陷 D：非文档型任务请求绕过闸门（captain 独立复核发现）
「帮我写一首关于**股票**的诗」的唯一主题词是「股票」，而招股书里「股票」遍地都是
（股票代码/发行股票…）→ 主题覆盖必然通过，又没有字段取值类型可校验 → 闸门放行，
实测答成「华汇创投与杜成城签订了《关于武汉兴图新科电子股份… [页码: 57]」。

### 缺陷 E：日志跨进程并发写产生半行 JSON（②加固）
原实现用**文本句柄 + flush**写行，文本层 8KB 缓冲 → 单条大记录被拆成多次 `write()`；
而同一批 JSONL 会被**多个进程**同时追加（在线套件自己会起服务子进程、还会起"stderr 不可写"测试子进程），
两次写入的片段互相穿插 → 非法 JSON 半行（`test_logs_are_json_lines_and_non_empty` 红）。

## 3. 修复设计（为什么这样改）

闸门在**生成之前**独立判三件事（`answerability.check`）：

1. **非文档型任务闸门**（新增）：创作/预测/主观评价类请求 → 直接判不可答（`non_document_task:*`）。
   判据要点：创作动词后紧跟「了/过/的是/明白/清楚」的属于"文档记载"（**排除**），
   只有「写一段/写一首/生成…」这类**请求生成**句式才判不可答——
   因此「招股说明书写了公司的简介吗？」不会被误判（见 §5 负例）。
2. **主题覆盖（rarest-first）**：取问题**内容实义词**里语料中最低频者，要求它出现在证据里。
   **前提**：提问性虚词必须先剔除（闭集表 + 「哪/谁/什/怎/几/多少/何/是否/有没有」前缀兜底）。
3. **意图 ↔ 取值类型一致性**：注册资本/收入→金额；占比→百分比；法定代表人→人名；
   标准→标准名；荣誉→奖项；上下游/客户/供应商→企业名。

**为什么"语料未登录词"不能一刀切跳过（关键，勿改）**：未登录词分两类——
提问性虚词（剔除）与内容性未登录词（食堂/高铁/奖学金…，**必须保留否决权**）。
实测反例：若把未登录词一律跳过，问「北京到上海的高铁要几个小时？」时，
剩下的语料内实义词只有「北京/上海」——它们**都出现在检索片段里**（招股书含北京、上海），
闸门就会放行，**验收 4 的 12/12 立刻失守**。故按"类别"处理而不是"一刀切 fail-open"。

## 7. 日志跨进程加固（②）的定性与实测

**定性**：产品缺陷（不是"并发写者伪影"）——写入路径**不具备跨进程原子性**。
用 `研发/scripts/selftest_log_concurrency.py` 在同一台机器上做机制 A/B
（6 个并发子进程 × 200 行 ~40KB，期望 1200 行）：

| 机制 | 落盘行数 | 非法 JSON |
| --- | --- | --- |
| 文本句柄 + flush（**修复前**） | 629/1200（缺 571） | 27 |
| `open(..., "ab", buffering=0)` + write（中间方案） | 586/1200（缺 614） | 44 |
| `os.open(O_APPEND)` + `os.write` | 1128~1157/1200（**仍丢行**） | 0~11 |
| **`CreateFileW(FILE_APPEND_DATA)` + 单次 `WriteFile`（修复后）** | **1200/1200** | **0** |
| 跨进程锁 + 追加写（备选，未采用） | 1200/1200 | 0 |

→ Windows 上 `_O_APPEND` / `open(...,"ab")` **并不保证**单次写原子（实测丢行与撕裂），
故最终实现选 **FILE_APPEND_DATA**（POSIX 走 `os.open(O_APPEND)` + 单次 `os.write`，POSIX 保证原子追加）。
加固后残留观察：**`rag_trace.jsonl` 的 32MB 轮转**会让 tester 的"新增字节"取证窗口失效
（本轮全量在线跑因此在该用例上判"不可判定"，非撕裂复发）。轮转策略属基线口径，未擅改；
若需要，可考虑"压小 trace 单条体积"或"轮转后自动重开窗口"（需 captain 决策）。

## 9. 残留风险与边界（如实报告）

1. **残余误答类（未做逐题特判）**：问题主题词**全部在语料内**、但文档未记载其答案的
   "断言型/审议型"提问（例：「公司为什么在 2019 年更换了会计师事务所？」——`为什么/更换/会计师/事务所`
   都在语料里），三信号闸门无法判定，仍可能抽取式硬取一段。
   **未加逐题特判**；如需覆盖，应上"答案跨度 ↔ 问句目标"的模型级校验（成本更高，需 captain 决策）。
2. **未登录内容词保留否决权**是不可让渡的：失败反例如 §3 所述（高铁题会立刻回退成误答）。
3. **闸门在生成之前**：LLM 可用时，被放行的题仍由 LLM 组织语言；本闸门只管"该不该答"，不影响答案质量口径。
4. **多轮依赖改写质量**：追问改写若把主题词丢掉，闸门仍会拒答（本轮 3/3 未触发）。
5. **日志**：跨进程原子追加已由 FILE_APPEND_DATA 保证；但
   （a）轮转在**进程启动时**执行，长驻进程持有句柄期间被别的进程轮转，会继续写旧文件（既有边界，未改）；
   （b）32MB 轮转会打断"新增字节"取证窗口（见 §7）。
6. **本报告未覆盖（out of scope）**：`优化/` 侧交付物（`compare_optimization.py` 硬编码/防覆盖/全量重跑/临时件清理）
   与 t5 的 4 个脚本编号——按 t1 契约 `优化/` 属 outOfScope，待 t5/后续任务处理。
