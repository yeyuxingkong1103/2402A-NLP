### 2.1 分阶段打点设计（对应工单五流程）

`src/perf_v13.py` 提供 `new_request()` / `stage()`（contextmanager 计时器）/ `record()` / `with_request_id()` 四个原语，在引擎链路插桩：

| 工单五流程 | 插桩阶段名 | 插桩位置 |

| ② 检索阶段 | `retrieval_text/table/image`（通道墙钟）+ 子阶段 `vector_embed`、`vector_milvus`、`fulltext_recall_wall`、`vector_recall_wall`、`fusion`、`rerank` | `hybrid_retriever_v6.retrieve()` 及向量召回内部 |

| 证据 | 结论 |
| --- | --- |
| `chat()`（openai API 调用）cumtime 3.466s，占 4.9s 的 **70.7%** | 端到端大头是 LLM 外部 API 网络等待 |

| 本地检索函数（rerank/embed/milvus）未进入 Top15 前列 | 优化后本地检索已不是 e2e 主导因素 |

### 3.3 负载测试暴露的并发问题（4 并发 × 36 请求，优化前）

| 指标 | 数值 |
| --- | --- |
| 吞吐量 | 0.40 rps |
| 检索 p50 / p95 / max | 2 211.0 / **62 924.7** / 63 981.1 ms |
| rerank p50 / p95 / max | 1 458.1 / **40 313.8** / 41 372.6 ms |
| e2e p95 | 65 358.2 ms |

单用户 0.8s 的检索在 4 并发下恶化到 63s，**放大 78 倍**——这是基准测试发现不了、只有负载测试才能暴露的瓶颈（详见 4.4）。

### 3.4 瓶颈定位结论（按影响排序）

| # | 瓶颈 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | **交叉编码重排 CPU 密集**：24 候选 × 1500 字符送入 bge-reranker-v2-m3 | 热态 p50 721ms，占检索墙钟 89% | 单用户主要延迟；并发下串行化排队 |
| 2 | **OMP 线程超订**：32 核机器默认每重排开 32 线程，4 并发 = 128 线程争抢 | 负载下单次重排飙至 41.4s | 检索 p95 恶化 78 倍 |
| 3 | **冷启动模型懒加载**：bge-m3 + reranker + CLIP + 倒排索引全部懒加载 | 冷启动 24.6~25.6s，嵌入首编 17.8s | 服务重启后首个请求超时 |
| 4 | **查询嵌入重复编码**：同一 query 在文本通道/表格通道/重试中重复编码 | 热态 embed p50 70ms | 浪费 10% 检索时间 |
| 5 | LLM 生成 ~1.1-1.2s | cProfile：70.7% 为 SSL socket 等待 | 外部 API 网络 IO，非本地可优化项 |

## 4. 瓶颈根因分析

### 4.1 交叉编码重排（rerank）

bge-reranker-v2-m3 是 cross-encoder，需对每个 (query, 候选) 对做一次前向推理。优化前链路：向量召回 24 条 + 全文召回 24 条 → RRF 融合去重后约 24 条候选 → 每条截断 1500 字符 → batch 推理。序列长度 1500 字符 ≈ 750+ token，注意力计算量 O(n²)，单次重排 700ms+。

### 4.2 OMP 线程超订（负载下最致命）

FlagEmbedding/PyTorch 默认使用全部物理核（本机 32 核）作为 OMP 线程数。4 个并发请求同时触发重排时：4 × 32 = 128 个 OMP 线程在 32 核上争抢，上下文切换开销远超计算收益，单次重排从 0.7s 飙至 41s。

### 4.3 冷启动懒加载

引擎各组件（bge-m3、reranker、CLIP、倒排索引）均为首次使用时加载。基准实测进程冷启动到首个请求完成 24.6s（其中 bge-m3 首次编码 17.8s）。生产场景下服务重启后的第一个用户必然超时。

### 4.4 查询嵌入重复编码

文本通道（hybrid 模式向量召回）与表格通道各自调用 `Embedder.encode([query])`；`ask()` 内 LLM 失败重试等路径也会再次检索。同一查询文本被重复送入 bge-m3 编码（每次 ~65ms）。

### 4.5 LLM 生成（外部依赖，定位为不可优化项）

cProfile 显示 e2e 的 70.7% 是 `chat()` 中 SSL socket read 等待——纯网络 IO。本地已无计算瓶颈，该项只能通过流式输出/缓存等业务手段缓解，不属于检索性能优化范围（工单验收口径为检索结果返回时间，此项不阻塞验收）。

## 5. 优化方案与实施

| # | 优化项 | 实施 | 代码位置 |
| --- | --- | --- | --- |
| 1 | **缩减召回候选** 24+24 → 12+12 | `RetrievalConfig(vector_recall_k=12, fulltext_recall_k=12)`，候选数减半直接减半重排推理量 | `scripts/benchmark_v13.py` |
| 2 | **重排输入截断** 1500 → 512 字符 | 新增环境变量 `RAG_V13_RERANK_MAX_CHARS`（默认 1500 保持原行为），传给 reranker `max_chars`；序列压到 512 token 内，注意力计算量约降 4 倍 | `src/retrieval/rerankers.py` |
| 3 | **查询嵌入 LRU 缓存** | `RAG_V13_EMBED_CACHE=1` 开启；单条查询编码走 `OrderedDict` LRU（容量 512，加锁），文本/表格通道同查询只编码一次 | `src/embedding.py` |
| 4 | **启动预热** | `engine.warmup()`：预加载 bge-m3/reranker/CLIP/倒排索引 + 一条真实查询打通全链路，负载测试前调用消除冷启动 | `src/rag_engine_v6.warmup()`（工单六已有，本工单纳入基准流程） |
| 5 | **限制 OMP/MKL 线程** | `OMP_NUM_THREADS=8`、`MKL_NUM_THREADS=8`（必须在 import 前设置），4 并发 × 8 线程 = 32，恰好占满 32 核无超订 | `scripts/benchmark_v13.py` |

所有优化项均通过环境变量/配置开关控制，默认关闭（保持原系统行为），便于 A/B 对比与回滚。

优化前基准配置：`EMBED_CACHE=0, RERANK_MAX_CHARS=1500, 召回24+24, 无预热`；
优化后基准配置：`EMBED_CACHE=1, RERANK_MAX_CHARS=512, 召回12+12, 预热+OMP=8`。

关键代码见截图 06（`docs/screenshots/06_optimize_code.png`）。

## 8. 过程问题记录

| # | 问题 | 根因 | 解决 |
| --- | --- | --- | --- |
| 1 | benchmark 脚本 LLM 调用瞬间失败（~0ms，答案为兜底话术） | 脚本未加载 `.env`，`DEEPSEEK_API_KEY` 读不到 | `import src` 前 `load_dotenv(ROOT / ".env")` |
| 2 | 环境变量开关不生效（缓存/截断仍走旧行为） | `embedding.py`/`rerankers.py` 在 **import 时**读取 env | 脚本内先 parse args → `os.environ[...]` → 再 `import src` |
| 3 | `with_request_id` 最初实现为 `@contextmanager`，线程池调用处按包装函数使用报错 | 语义设计错误（装饰器 vs 闭包） | 改为返回闭包包装函数：`pool.submit(with_request_id(rid, fn), *args)` |
| 4 | `stage()` 上下文内取不到耗时（`_s.ms` AttributeError） | contextmanager yield None | 新增 `_StageTimer` 类，`finally` 中回写 `.ms` |
| 5 | 插桩后向量召回返回空结果 | 编辑时误删 hits→标准 dict 的格式化循环 | 恢复格式化逻辑，插桩只包计时不改数据流 |
| 6 | 复用的 `eval_test.json` 只有 1 题，统计无意义 | 历史遗留文件 | 新建 12 题基准集 `benchmark_questions_v13.json`，含 doc_id 过滤 |
| 7 | 负载测试期间 WSL 整体崩溃（错误 0x8007274c） | WSL VM 不稳定（内存 7.6GB + 高负载） | `wsl --shutdown` 重启，Docker 容器（Milvus）自动恢复后重跑 |
| 8 | `setsid`/`nohup` 启动的长测试进程被静默回收（日志 0 字节） | WSL 对脱离终端的后台进程回收 | 改用 PowerShell 后台作业保持 `wsl.exe` 前台管道 |
| 9 | **优化后负载测试反而更慢（p95 达 150s）** | ① 未预热，首个请求冷加载 reranker 133s；② 4 并发 × 默认 32 OMP 线程严重超订 | `load_after` 增加 `engine.warmup()` 预热 + `OMP_NUM_THREADS=8` |
| 10 | PowerShell 内联多行 python 命令引号冲突 | PowerShell 引号转义规则 | 一律写临时 `.py` 脚本文件执行 |
