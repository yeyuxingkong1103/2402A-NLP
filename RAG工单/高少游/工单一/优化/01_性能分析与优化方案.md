# 性能分析与优化方案

> 工单编号：人工智能 NLP-RAG-基于 PDF 文档的问答系统
> 分析响应时间瓶颈，提出可落地的优化方案，服务于"响应 ≤3s"需求。

---

## 1. 性能现状（架构性瓶颈）

系统的响应链路：

```
提问 → 查询理解(LLM) → 检索(向量+BM25) → 生成(LLM)
        ▲                    ▲                ▲
      调用①                 几乎常数         调用②(最重)
```

- **检索阶段**：向量 ANN + BM25 + RRF，耗时可忽略（毫秒级）；
- **瓶颈在生成阶段**：本地 `deepseek-r1:1.5b` 属**推理型(reasoning)模型**，回答前会先生成一大段"思维链"，逐 Token 推理，导致单次回答显著超时；
- 查询理解调用①也走同一模型，进一步叠加耗时。

## 2. 耗时优化方向（按收益排序）

### 2.1 换用非推理型对话模型（收益最大）
- 将 `LLM_MODEL` 改为 **Qwen2.5-1.5B/3B-Instruct** 或 Llama3.2-3B 这类直接输出结论的模型，可省掉思维链带来的大量 Token。
- 操作：改 `src/config.py` 的 `LLM_MODEL` 或 `.env`，`ollama pull` 后重启界面。
- 预期：单次回答耗时可下降 50%+，接近 ≤3s。

### 2.2 收敛生成长度
- 降低 `LLM_MAX_TOKENS`（默认 768）→ 限制回答篇幅，减少生成 Token。
- 在提示词中要求"简洁回答，控制在 N 句内"。

### 2.3 精简上下文
- 降低 `TOP_K`（6→4）与 `BM25_TOP_K`，减少注入提示词的片段数，缩短输入长度、加速推理。
- 权衡：Top-K 过低会伤召回，需结合评估命中率定。

### 2.4 推理相关
- 提示词显式要求"直接给出结论，不要输出思考过程"（对可配置的模型生效）；
- 若 Ollama 支持，关闭思维链参数。

### 2.5 服务层优化
- 向量库预热：启动时把 FAISS 索引常驻内存，避免首次加载延迟；
- 结果缓存：对相同问题缓存回答（LRU），重复提问秒回。

## 3. 检索质量优化（对应"准确回答"）

| 方案 | 说明 | 预期 |
|---|---|---|
| 按章节标题切片 | 用 PDF 目录定位章节，按标题切块 | 召回更聚焦，误召回减少 |
| 增大 Top-K | 6→8 召回更多 | 命中率↑（本次评估用8） |
| 关键数字精确重排 | 注册资本等数字走精确匹配二次重排 | 数值类问题更稳 |
| 关键短语改写 | 查询理解阶段对问题做同义改写再检索 | 召回↑ |

## 4. 模型层面优化

- **Embedding**：bge-m3(1024维) 质量高但偏大，可对比 `bge-large`/`nomic-embed` 在召回上的收益/代价；
- **量化**：生成模型用 Q4 已较小，若仍慢可考虑更小 size；
- **RAGAS 裁判**：换 JSON 友好对话模型，才能拿到全套指标。

## 5. 度量方法

- 记录每题 `elapsed`（evaluate.py 已内建）；
- 对比 RAG vs 纯 LLM 平均耗时；
- 优化前后各跑一遍 `evaluate.py --skip-ragas`，对照耗时与命中。

## 6. 优先级建议

```
P0 (立竿见影): 换非推理型模型 + 提示词禁思维链
P1 (性价比高): 收敛 LLM_MAX_TOKENS / TOP_K
P2 (提升质量): 按章节切片 / 精确数字重排
P3 (锦上添花): 结果缓存 / 预热 / 多模型对比
```

> 说明：本项目已通过 `TOP_K=8`、提示词加强数据提取等方法做了基础优化；"响应≤3s"若要稳定达成，**换非推理模型**是首选杠杆。
