## 二、瓶颈定位过程（关键推理链）

### 2.1 第一步：阶段计时给出「哪一段慢」

基线（优化前）稳态场景分阶段耗时：

| 阶段 | avg (ms) | 占端到端 |
|---|---|---|
| 查询处理与增强 | 0.3 | 0.0% |
| 查询理解 | 1.6 | 0.1% |
| **检索·向量召回** | **2282.1** | **95.5%** |
| └ **查询向量编码** | **2275.2** | **95.2%** |
| 检索·全文召回 | 37.7 | 1.6% |
| 检索·多通道融合 | 0.5 | 0.0% |
| 上下文组装·重排 | 7.8 | 0.3% |
| 后处理·答案合成 | 60.5 | 2.5% |
| **端到端总计** | **2390.5** | 100% |

**结论**：瓶颈高度集中在「检索·向量召回」，且其中 99.7% 花在子阶段「查询向量编码」。

### 2.2 第二步：cProfile 给出「哪个函数慢」

`cProfile` 累计耗时 Top 函数（优化前，5 次请求，共 11.638 s）：

```
ncalls  cumtime  filename:lineno(function)
     5   11.639  src/qa_engine.py:96(ask)
     5   11.258  src/hybrid_retriever.py:231(search)
     5   11.207  src/hybrid_retriever.py:145(recall)
     5   10.843  src/vector_retriever.py:35(encode_queries)
     5   10.843  src/embedding.py:218(encode_many_cached)
     5   10.842  src/embedding.py:185(encode)
     5   10.840  src/embedding.py:151(_embed_batch)
     5   10.834  requests/api.py:103(post)          ← 对 Ollama 的 HTTP 调用
     5   10.825  requests/sessions.py:503(request)
```

**结论**：几乎全部时间花在 `requests.post` —— 即**对 Ollama 嵌入服务的 HTTP 调用**。

### 2.3 第三步：定位根因

进一步排查发现，每次嵌入调用的 ~2.2 s 由以下固定开销构成：

1. **模型重载**：未设置 `keep_alive`，Ollama 在请求间卸载模型，每次调用重新加载（约 1.5~2 s）；
2. **连接握手**：未复用 `requests.Session`，每次新建 TCP 连接；
3. **重复编码**：同一/相似查询被反复编码，无缓存；
4. **全量扫描**：文档路由每次 O(N) 扫描 8086 块。

> **瓶颈原因（对应工单「出现瓶颈的原因」）**：不是检索算法慢，而是**查询向量编码阶段
> 对本地嵌入服务的调用存在大量可消除的固定开销**（模型重载 + 连接握手 + 重复计算）。

## 三、优化实施记录

| 优化项 | 实现 | 文件 |
|---|---|---|
| ① 连接复用 + keep_alive | 模块级 `requests.Session`；嵌入请求带 `keep_alive=30m` | `src/embedding.py` |
| ② 服务预热 | `qa.warmup()` 启动即加载模型与索引，移出请求路径 | `src/qa_engine.py` |
| ③ 查询向量持久化缓存 | 内存 LRU + `output/query_embed_cache.json` 跨进程命中 | `src/embedding.py` |
| ④ 文档路由预计算 | 预建 `公司别名 → 块索引` 路由表，O(N)→O(1) | `src/hybrid_retriever.py::_build_doc_route` |
| ⑤ 分词与短语缓存 | 同一查询的 jieba 分词与 n-gram 短语缓存 | `src/rerankers.py` |
| ⑥ 批量嵌入 | 多查询合并为单次 HTTP 调用，摊薄固定开销 | `src/embedding.py::encode` |
| ⑦ 分阶段计时 + 结构化日志 + 指标告警 | 可观测性闭环 | `src/perf.py` |

所有优化由 `PERF_OPT` 统一开关，保证「同一套代码、同一份数据、同一台机器」的公平对比。

## 四、过程问题记录（真实遇到并解决）

| # | 问题 | 现象 | 根因 | 解决 |
|---|---|---|---|---|
| P1 | JSON 解析失败 | `Unexpected UTF-8 BOM (decode using utf-8-sig)` | 数据文件带 UTF-8 BOM | 统一以 `utf-8-sig` 读取 |
| P2 | 数据路径错误 | `Could not find a part of the path ...\data\eval_questions.json` | 沿用前序工单相对路径 | 改为 `config.DATA_DIR` 绝对定位 |
| P3 | 源文件被写入 BOM | 批量替换脚本引入 BOM，Python 解析异常 | 脚本以 `utf-8` 写入含 BOM 内容 | 用 `_fixbom.py` 清理 `.py/.json/.md` |
| P4 | 交互吞吐显示为 0 | 性能面板「吞吐 (QPS)」恒为 0.0 | 吞吐按墙钟计算，交互场景含大量空闲间隔 | 改为按**请求处理耗时（busy time）**计，不受空闲影响 |
| P5 | 性能面板滞后一轮 | 提问后指标仍为上一次 | 面板在提问处理前渲染 | 答完 `st.rerun()` 刷新面板 |
| P6 | 负载下延迟线性上升 | 并发 1→16，QPS 恒约 10，P95 128→2290 ms | 嵌入服务串行处理，吞吐被封顶 | 记录为「下一瓶颈」，给出横向扩展建议 |
| P7 | 冷启动 P95 仍偏高 | 冷启动 P95 约 2.9 s | 冷启动首个请求仍需加载模型 | 由预热消除；服务化部署下预热为常驻 |

## 六、结论

- **瓶颈**：查询向量编码（Ollama 嵌入调用）占基线端到端 95.2%。
- **优化**：连接复用 + keep_alive + 预热 + 查询缓存 + 路由预计算 + 分词缓存。
- **成效**：稳态端到端 2375 ms → **230 ms（10.31×）**，冷启动 2454 ms → 510 ms（4.81×），
  三场景均满足「≤ 3 s」验收标准。
- **下一瓶颈**：负载下嵌入服务吞吐封顶（~10 QPS），建议后续以多实例 / 批处理 / 更小模型横向扩展。
