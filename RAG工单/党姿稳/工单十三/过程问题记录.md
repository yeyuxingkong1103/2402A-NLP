# 工单十三 · 过程问题记录

> 记录 RAG 检索性能分析与优化过程中实际遇到的问题、定位方式与处理结论。

---

## 问题一：检索链路上到底哪里慢——先定位，再动手

**现象**：工单十二交付的扁平 RAG 与 LightRAG 两条链路，单次「检索结果返回」耗时在百毫秒到十几秒之间大幅波动，光看总耗时无法判断优化点。

**定位过程**：

1. 先按工单要求把一次 RAG 请求拆成五个阶段：查询处理与增强 / 检索 / 上下文组装与提示工程 / LLM 生成 / 后处理与响应格式化。
2. 写 `logger.py` 的 `StageTracer`，用 `time.perf_counter()` 在每阶段首尾打点，并给每个请求分配 `request_id`，把明细以 JSON Lines 追加到 `data/stage_trace.jsonl`；同一条 `request_id` 的五条阶段记录天然串成一次请求的耗时瀑布。
3. 再写 `profile_cprofile.py` 做函数级剖析，按 `cumulative` 排序找热点函数。

**结论**：查询处理与增强（阶段一）内部的一次 **在线 LLM 关键词抽取调用** 是绝对大头，单独就占 1 秒上下；检索阶段（阶段二）在**首次调用**时因 BLAS 冷启动会飙到 4 秒以上，稳态后回落到几十毫秒。

**函数级确认**：`profile_cprofile.py` 对两条流水线各跑 2 条查询做 cProfile 剖析，只看本工单模块（`project_only=True`，避免 socket/ssl 等库调用把表格占满）：

优化前（`run` 累计 10.83 秒 / 2 条查询）：

| 函数 | 文件:行 | 累计(s) |
|---|---|---|
| `run` | `baseline_pipeline.py:49` | 10.8273 |
| `run_tail` / `call_llm` | `pipeline.py:150` / `:111` | 4.4965 / 4.4918 |
| **`extract_keywords_llm`** | **`baseline_pipeline.py:21`** | **1.9893** |
| `vector_search_naive` | `pipeline.py:16` | 0.0383 |
| `mmr_dedup` | `pipeline.py:59` | 0.0374 |
| `bm25_search` | `pipeline.py:35` | 0.0288 |

优化后（`run` 累计 8.22 秒 / 2 条查询）：

| 函数 | 文件:行 | 累计(s) |
|---|---|---|
| `run` | `optimized_pipeline.py:63` | 8.2190 |
| `run_tail` / `call_llm` | `pipeline.py:150` / `:111` | 4.4440 / 4.4412 |
| `_understand` | `optimized_pipeline.py:55` | 3.6509 |
| `bm25_search` | `pipeline.py:35` | 0.0569 |
| `mmr_dedup` | `pipeline.py:59` | 0.0563 |
| `extract_keywords_local` | `optimized_pipeline.py:27` | 0.0099 |
| `vector_search_fast` | `pipeline.py:26` | 0.0098 |

**对照结论**：

- 同样是「抽关键词」这件事，`extract_keywords_llm` 1.9893 秒 vs `extract_keywords_local` 0.0099 秒，**差约 200 倍**。两者都是纯 Python 函数，cProfile 对它们的计入方式一致，这个对比是可信的。
- 同样是向量检索，`vector_search_naive` 0.0383 秒 vs `vector_search_fast` 0.0098 秒，约 4 倍。
- **一个必须说明的读数陷阱**：`_understand`（3.6509 秒）看着比 `extract_keywords_llm` 还慢，但这**不是真实开销**。`_understand` 内部是 `torch` 的前向推理，cProfile 会为每一个算子（`linear` / `layer_norm` / `gelu` / `scaled_dot_product_attention` …）单独插桩记账，几十毫秒的推理在剖析下被放大成秒级。**torch 路径的 cProfile 读数只能横向比结构、不能当绝对耗时用**；绝对耗时以 `benchmark.py` 的实测为准（阶段一优化后均值 0.0634 秒）。
- 两条链路的 `call_llm`（阶段四，LLM 生成答案）基本没变（4.49 vs 4.44 秒），符合预期——**本工单优化的是「检索结果返回」，不动生成阶段。**

另外，全量热点表（含库调用）里排名靠前的是 `_ssl._SSLSocket.read` / `socket.readinto` / `http.client` 等网络阻塞调用——这从另一个角度印证了：**优化前的检索链路上挂着一次真实的网络往返，它就是耗时本身。**

**处理**：阶段一改为完全离线的本地查询理解（详见问题二），阶段二改为预归一化矩阵 + argpartition（问题三）。

## 问题二：查询理解为什么要调 LLM——这是本次优化的核心

**现象**：原链路沿用 LightRAG 的双层关键词抽取思路——把用户 query 丢给 DeepSeek，让模型返回「实体 + 概念词」，再拿这些词去检索。

**为什么这是瓶颈**：

- 该调用发生在**检索链路上**，是串行的、阻塞的：用户必须等 LLM 返回关键词，检索才能开始。
- 每次用户 query 都是新的，**无法跨请求缓存**，这笔开销在每个真实会话里都要付一次。
- 单次往返实测 1.9~2.4 秒，且在网络抖动时会触发 `timeout=60` 的上限，尾延迟不可控。

**处理**：新增 `optimized_pipeline.extract_keywords_local()`，把关键词抽取完全离线化：

- **图谱实体识别**：直接拿工单十二构建的 3355 条图谱实体名做最长匹配。查询里出现了「武汉力源信息技术股份有限公司」就命中该实体，无需模型推断。实体名按长度降序排列，保证长名优先于其子串，并用 `any(name in h for h in hits)` 去重，避免同时收下「武汉兴图新科电子股份有限公司」与其中的短名。
- **通用关键词**：用 `jieba` 对 query 分词，过滤单字与「什么/哪些/多少」这类低信息量疑问词。

两者都只依赖内存中的词典，单次耗时降到毫秒级。**这一步把阶段一从约 2 秒压到 0.14 秒。**

## 问题三：向量检索每次都在重算全量范数

**现象**：`vector_search_naive()` 每次查询都执行 `np.linalg.norm(vecs, axis=1)`，对全部 1950 行 × 768 维重算一遍行范数，再生成一份归一化副本 `vecs / norms`，最后才做点积。

**为什么这是瓶颈**：语料矩阵是不变的，行范数也是不变的。每个 query 都重算 1950 次开方、再分配一份 1950×768 的浮点副本，纯属重复劳动——既费 CPU 又多一次内存分配与拷贝。

**处理**：`vector_search_fast()` 改为两处优化：

- **预归一化**：在流水线构造函数里一次性把语料矩阵归一化，存为 `self.unit_vecs`（连续 float32），查询时只需归一化那一条 query 向量，然后单次 `unit_vecs.dot(qn)` 矩阵乘法出全部相似度。
- **`np.argpartition` 代替全排序**：取 top-30 不需要把 1950 个分数全排序。`argpartition` 是 O(n) 的选择算法，只对切出来的候选做一次小规模 `argsort`。

**实测**：同一 query 各重复 200 次。

| 实现 | 中位耗时 | 均值 | 最大 |
|---|---|---|---|
| `vector_search_naive` | 0.00337s | 0.00395s | 0.01596s |
| `vector_search_fast` | **0.00048s** | **0.00062s** | **0.00262s** |

加速约 **7 倍**，且返回的 30 个候选块行号**完全一致**（脚本里直接做了集合比对，`相等: True`）。

**但要如实说明一点**：这个 7 倍在端到端阶段二的数字上**看不出来**——基准报告里「检索」阶段优化前 0.0237 秒、优化后 0.0261 秒，基本持平。原因是阶段二里还有 BM25 分词计分与 MMR 去冗余，两者合计约 20 毫秒，把省下的这 2.9 毫秒盖住了。也就是说：**这一项优化本身是真的，但在本工单的语料规模（1950 块）下对总耗时不构成影响。** 真要在阶段二看到收益，得先把 BM25 与 MMR 也换掉，而那属于另一个量级的工作。

**注意**：这里用的仍是**精确点积检索**，不是近似索引。优化的是「同样的结果怎么算得更快」，而非「用近似换速度」，所以检索结果与优化前逐块一致，不影响工单十二的 RAGAS 指标。

## 问题四：查询向量被重复编码

**现象**：`model.encode([query])` 每次请求都真跑一遍 m3e-base 前向。单条 query 大约 30~80 毫秒，单看不致命，但基准测试同一批问题重复多轮、演示时反复点同一个问题时，这份开销完全白付。

**处理**：`OptimizedPipeline._understand()` 里加 `_kw_cache` / `_vec_cache` 两个字典，以 query 原文为键缓存「关键词抽取结果 + 查询向量」。同 query 二次进入直接命中，阶段一降到 0.1427 秒里的大头实际只剩首次编码。

**边界说明**：缓存键是 query 原文，无状态，不跨语料版本复用，不会因语料更新而返回过期结果。

## 问题五：把 LLM 调用拿掉之后，真实的剩余瓶颈是查询编码

**现象**：离线化改造完成后重跑基准，优化后的「查询处理与增强」仍出现 0.22 秒到 **14.4 秒**的剧烈抖动，远超同一批查询里检索阶段（毫秒级）的耗时。这说明阶段一里还有东西在拖后腿。

**逐子步骤打点定位**：把阶段一与阶段二拆成 `encode / vector / bm25 / rrf / mmr` 五段逐条计时，结果非常干净——`vector` 1~90 毫秒、`bm25` 8~290 毫秒、`rrf` 约 0.1 毫秒、`mmr` 10~340 毫秒，**只有 `encode`（m3e-base 单条查询前向推理）在 0.22~14.4 秒之间乱跳**。检索侧完全没问题，锅在嵌入模型的 CPU 推理。

**进一步定位到线程数**：本机 16 核，而 `resources.load_model()` 里写的是 `torch.set_num_threads(8)`。固定一条 query 重复 15 次，逐一测试线程数：

| 线程数 | 中位耗时 | 均值 | 最大 |
|---|---|---|---|
| 1 | 0.634s | 0.666s | 0.936s |
| 2 | 0.433s | 0.900s | **5.304s** |
| 4 | 0.309s | 0.302s | 0.327s |
| 8 | 0.077s | 0.095s | 0.260s |
| **16** | **0.063s** | **0.063s** | **0.073s** |

- 线程给少了（1~2 个），单条推理慢 5~10 倍，且 2 线程时出现 5.3 秒的尖峰——线程被抢占后剩下的那个要独力跑完，抖动放大。
- 线程给到满核（16）时，中位耗时最低且最大/最小几乎贴在一起，尾延迟最可控。

**根因还有一层**：本机 16GB 内存只剩约 3GB 可用，WSL 的 OpenMP 默认策略是**自旋等待**，工作线程被抢占后会持续空转烧 CPU。因此在 `config.py` 顶部（**必须在 torch 被导入之前**）加了：

```python
os.environ.setdefault("OMP_WAIT_POLICY", "PASSIVE")      # OpenMP 线程空闲时休眠而非自旋
os.environ.setdefault("TOKENIZERS_PARALLELISM", "false") # 分词不再另起进程与 torch 抢核
EMBED_THREADS = 16                                       # 取满核
```

**注意存放位置**：`torch` 是在 `resources.load_model()` 里**延迟导入**的，而 `config` 又先于 `resources` 被导入，所以环境变量写在 `config.py` 顶层才能生效。若写成模块级 `import torch` 之后再设，OpenMP 早已按默认值初始化完毕，设了也白设。

**结果**：编码中位耗时从 0.077 秒降到 0.063 秒、尾延迟从 0.26 秒收到 0.073 秒，阶段一的抖动基本消除。

## 问题六：并行召回——实测没有收益，因此没有引入

**初始假设**：向量检索与 BM25 检索是两个完全独立的召回通道，输入都是 query、输出互不影响，原实现里却一前一后顺序执行，看起来是典型的可并行化点。于是先写了 `_parallel(fn_a, fn_b)`，用两个 `threading.Thread` 并行跑。

**实测否定**：在同一份向量矩阵与 BM25 索引上，对同一条 query 各重复 60 次：

| 实现 | 中位耗时 | 均值 | 最大 |
|---|---|---|---|
| 串行两路 | 0.0031s | 0.0033s | 0.0065s |
| 双线程并行 | 0.0033s | 0.0040s | 0.0163s |

**并行反而更慢**。原因很清楚：预归一化之后，向量召回退化成一次 1950×768 的矩阵向量乘（约 1.5 MFLOP），BM25 也就是一千多篇文档的计分，两路本身合计才 3 毫秒。而创建两个线程、做两次上下文切换、再 `join()` 的固定开销与这个量级同阶，重叠省下的时间还不够付线程开销。并行化的收益本来就只在「单路耗时远大于线程创建开销」时才存在。

**处理**：**删掉 `_parallel` 与 `import threading`**，改回串行两路。

**这条负面结论比一条"看起来合理"的优化更有价值**：它说明在把阶段一那笔 2 秒的 LLM 调用拿掉之后，检索阶段本身已经小到不值得再做并行改造——真正该优化的地方不在这里。工单要求"不要编写不必要或冗余的代码"，一条实测无收益的并行分支正属于此列。

## 问题七：冷启动被误判成「瓶颈」

**现象**：基线流水线第一次跑检索时耗时 4.13 秒，第二次就掉到几十毫秒。如果只测一次并把 4.13 秒写进报告，就是拿冷启动当稳态，结论会严重失真。

**定位**：用 `StageTracer` 逐轮打印后发现，第 0 轮检索阶段异常、第 1 轮及以后立刻正常；且 cProfile 显示耗时集中在底层 BLAS 的首次线程池初始化与矩阵分块策略选择上。

**处理**：

- `benchmark.summarize()` 里显式把 `round == 0` 的第一轮标记为 `cold`，`round > 0` 标记为 `steady`，**两类分开统计并在报告中同时列出**，不做掩盖。
- `optimized_pipeline` 构造时调 `resources.warm_up(model, entity_names)`：先跑一次小批量编码、对 jieba 词典做一次分词，把 BLAS 线程池与 jieba 的词典加载在服务启动阶段付掉，而不是留在用户的第一次查询上。

这正是工单要求「每个会话，用户输入 query 后返回检索结果要在 3S 以内」的题眼——**首个 query 也必须达标，所以冷启动必须显式处理，不能靠"跑一次就好了"糊弄过去。**

**真正的进程冷启动实测**（全新 `python.exe`，只跑一条查询，即用户开新会话后问第一句话的场景）：

```bash
python.exe -u optimized_pipeline.py    # 检索结果返回 0.363305 秒  within_budget=true
python.exe -u baseline_pipeline.py     # 检索结果返回 3.840869 秒  within_budget=false
```

拆开看基线的这 3.84 秒：查询处理与增强 1.585 秒（LLM 抽关键词）+ 检索 2.255 秒（BLAS 首次初始化）+ 上下文组装 0.000177 秒。两条链路里，**只有优化后的那条在构造阶段做了预热，把 BLAS 线程池与 jieba 词典的加载开销移出了首次查询**，所以它首次查询就是 0.363 秒。

这正是「每个会话」四个字的落地：验收看的是用户新开会话后的第一句话，不是跑热之后的稳态。

## 问题八：3 秒口径的界定——LLM 生成该不该算

**现象**：如果按端到端总耗时算，优化后也要 4.1 秒左右，看起来不达标；但工单的验收原话是「返回的**检索结果**要在 3S 以内」，不是「返回答案」。

**处理**：在 `config.py` 里显式定义口径：

```python
RETRIEVAL_STAGES = [STAGE_QUERY, STAGE_RETRIEVE, STAGE_CONTEXT]   # 属于「检索结果返回」的阶段
RETRIEVAL_BUDGET = 3.0                                            # 工单验收：检索结果返回时间 ≤3 秒
```

即「检索结果返回」= 查询处理与增强 + 检索 + 上下文组装与提示工程，**不含阶段四 LLM 生成**。`StageTracer.retrieval_seconds()` 按这份清单求和，`within_budget` 也据此判定。

同时报告里仍保留端到端总耗时一栏，避免读者误以为整体只要 0.17 秒。**口径写明、两种数字都给，比只给一个好看的数字更诚实。**

## 问题九：优化前后必须可比，不能顺手把检索质量也改了

**现象**：做性能优化时很容易顺手调参（加召回数、改融合权重、放宽 MMR），速度好看了，但和工单十二的检索质量就不可比了。

**处理**：`config.py` 里把 `VECTOR_TOP_K=30`、`BM25_TOP_K=30`、`FINAL_TOP_K=6`、`RRF_K=60`、`MMR_LAMBDA=0.90`、`CONTEXT_MAX_CHARS=12000` 全部固定，**与工单十二完全一致**；两条流水线共用 `pipeline.py` 里的 `rrf_fuse` / `mmr_dedup` / `assemble_context` / `build_prompt` / `call_llm` / `format_response`，五个阶段的第 3~5 阶段实现逐行相同（共用 `run_tail`）。

差异只在四处，也正是被优化的四处：

| 维度 | 优化前 `baseline_pipeline.py` | 优化后 `optimized_pipeline.py` |
|---|---|---|
| 查询理解 | `extract_keywords_llm()` 在线调 LLM | `extract_keywords_local()` 图谱词典 + jieba |
| 向量检索 | `vector_search_naive()` 每次重算范数 | `vector_search_fast()` 预归一化 + argpartition |
| 查询缓存 | 无，每次重新编码 | `_kw_cache` / `_vec_cache` |
| 冷启动 | 无预热 | 构造时 `warm_up()` |

BM25 检索文本的构造也统一走 `pipeline.expand_query()`：两条流水线用同一套规则（原文中已出现过的关键词不重复拼接），差别只在关键词从哪来——一个走网络，一个走本地词典（详见问题十三）。

**关于「检索出来的块是否相同」**：本工单考核的是耗时而非检索质量，两条流水线在**超参数与第 3~5 阶段实现上完全一致**，但阶段一得到的关键词集合不同（LLM 抽的概念词 vs 本地图谱实体 + jieba 分词），因此 BM25 通道的召回结果可能略有差异。检索质量本身已在工单十二用 RAGAS 做过完整评估，本工单不再重复评估、也不拿它当优化的卖点。

## 问题十：Windows 控制台 GBK 编码导致日志中断

**现象**：在 Windows 的 `python.exe` 下打印含中文阶段名的日志、或含「%」的性能报告时，控制台按 GBK 解码报 `UnicodeEncodeError`，程序中断。

**处理**：在 `config.py` 顶部统一把 `sys.stdout` / `sys.stderr` 用 `reconfigure(encoding="utf-8", errors="replace")` 切到 UTF-8，并包 `try/except` 兜住「流被重定向、不支持 reconfigure」的场景。所有模块 `import config` 时即生效，无需各自处理。

## 问题十一：cProfile 自身的开销会污染结论

**现象**：用 cProfile 剖析时，如果连「加载模型」「导入 matplotlib」这类一次性初始化也一起计时，热点列表里会混进大量噪声函数，真正要看的检索热点被挤到看不见。

**处理**：

- `profile_pipeline()` 只把 `enable()` / `disable()` 包在**查询执行循环**外面，模型加载与流水线构建放在剖析区间之外。
- 剖析时只取 2 条查询（`config.QUERIES[13]` 与 `[15]`），控制单次剖析时长——cProfile 本身会给每个函数调用记账，比正常执行慢数倍。
- 输出同时保留累计耗时 Top-20 的**表格**与原始 `.prof` 文件（`data/before.prof` / `data/after.prof`），后者可用 `python -m snakeviz` 打开交互式查看调用树。

## 问题十二：优化前的基线必须"真的慢"，否则对比没有意义

**现象**：如果基线也复用图谱词典做关键词抽取，两条流水线跑得一样快，报告会变成空话。

**处理**：`baseline_pipeline.py` 刻意保留**生产环境真实会付的那份开销**——每次查询实打实调一次 DeepSeek 做关键词抽取（`temperature=0.0`、`max_tokens=200` 控制成本），不做任何缓存。这正是「未做性能优化时的检索链路长什么样」。

**代价与取舍**：基准测试要跑 16 问题 × 3 轮 = 48 次基线查询，每次都真调一次 API，整轮跑下来要几分钟、并消耗对应 token。这是为了拿到可信的对比数据必须付的成本，比用假数据编一份好看的报告划算。

## 问题十三：抽出来的关键词根本没进召回——真正的「白干」

**现象**：核对代码时发现，基线的 `extract_keywords_llm()` 把关键词抽出来了、也记进追踪记录了，但阶段二的 BM25 用的还是**原始 query**：

```python
keywords = extract_keywords_llm(query)          # 花约 1 秒调 LLM 抽出关键词
...
bm_hits = pipeline.bm25_search(self.bm25, query, config.BM25_TOP_K)   # 用的却是 query，不是 keywords
```

抽出关键词却不用，等于每个用户查询都白付一次网络往返。

**为什么这是本工单最有价值的一处发现**：它把「慢」和「该不该慢」区分开了。前面几个问题解决的是「怎么把这一步变快」，这一处揭示的是**这一步对召回结果根本没有贡献**——不是优化它，而是应该重新审视它该不该在关键路径上。

**处理**：新增 `pipeline.expand_query(query, keywords)`，把阶段一的关键词用于扩写 BM25 的检索文本，**两条流水线都接上**：

- 基线：用 LLM 抽出的概念词扩写 → `expand_query(query, keywords)`
- 优化后：用本地图谱实体 + jieba 分词结果扩写 → `expand_query(query, kw["all_keywords"])`

统一规则：**已经在原文中出现过的关键词不重复拼接**（`w not in query`），避免只是把同样的词再说一遍、白白抬高词频。这是公平对比的前提——两条流水线做的是同一件事，差别只在关键词从哪来：一个走网络，一个走本地词典。

**顺带修正的一处不对称**：改造前优化版的检索文本是 `query + entities[:3]`，而实体名必然是 query 的子串（`match_entities` 就是这么匹配的），拼接等于重复；基线那边则压根没拼。两边都不一致。统一用 `expand_query` 之后，规则一致、去重一致，对比才站得住。

## 问题十四：同一份代码，两次基准测试的结论可以完全不同

**现象**：基准测试前后跑了三轮，第一轮和后面两轮的结论差异极大：

| 指标（优化前基线） | 第一轮（主机负载高） | 第二轮（主机空闲） |
|---|---|---|
| 阶段一均值 | 2.4434s | 0.9718s |
| 检索结果返回均值 | 2.5143s | 0.9957s |
| 检索结果返回 P95 | 4.8153s | 1.3728s |
| 检索结果返回最大值 | 5.2582s | 2.0016s |
| 3 秒内达标率 | 37/48 | 48/48 |

**代码没变**，变的只是跑的时候主机上还开着 PyCharm、Docker、微信、浏览器等一堆进程。

**根因有两层**：

1. **阶段一是网络往返**：基线要调 DeepSeek 抽关键词，返回延迟本来就随网络与服务端负载浮动，1~5 秒都出现过。这是**不可控的外部方差**。
2. **嵌入模型编码受主机 CPU 争抢**：优化后的版本虽然阶段一不联网了，但在主机空闲前实测单条编码仍在 0.2~14 秒之间乱跳，直到调整了线程数与 OpenMP 等待策略（问题五）才收敛。

**处理与结论**：

- **两次数据都保留**，不挑好看的那份。第一轮数据恰恰是有价值的证据：它说明**优化前那条链路把一次不设上限的网络往返放在了关键路径上，一旦网络或主机稍有波动就会突破 3 秒**。第二轮主机空闲时它碰巧达标（P95 1.37 秒、48/48），但把达标与否交给网络抖动的运气，本身就是这个设计的问题。
- **优化后的版本把阶段一从网络往返换成了本地 CPU 计算**，耗时从「0.97~2.44 秒、方差不可控」压到「0.06 秒、最大 0.30 秒」，而且这个上界只由本机 CPU 决定，不由外部服务决定。这才是满足「每个会话 ≤3 秒」的正确形态。
- **报告口径**：`evaluation/性能对比.md` 采用的是主机空闲、线程配置修正后的那一轮数据。当前机器同时开着 IDE、Docker 与多个聊天软件，跑性能基准前应尽量腾出 CPU——这也是本次实验最实在的一条教训。
