## 问题一：分块策略与解析任务如何触发并放入 Redis Stream

### 1.1 先澄清一个命名问题

工单说的「paper_id」在代码里不同层叫法不同，**指的是同一个东西**：

| 层 | 名称 | 位置 |
|---|---|---|
| 数据库字段 | `parser_id` | `api/db/db_models.py`（`Document.parser_id`） |
| 对外 API / 前端 | `chunk_method` | `api/utils/api_utils.py:635` 做了 `"parser_id" ↔ "chunk_method"` 的别名映射 |
| 枚举类 | `ParserType` | `common/constants.py:93-108` |

### 1.2 四种分块策略（含 naive 对照）

| 维度 | `naive` | `paper` | `table` | `one` | `knowledge_graph` |
|---|---|---|---|---|---|
| chunker 实现 | `rag/app/naive.py` | `rag/app/paper.py` | `rag/app/table.py` | `rag/app/one.py` | **复用 `naive.py`** |
| FACTORY 行号 | `task_executor.py:85` | `:86` | `:92` | `:95` | `:98` |
| 切分依据 | `chunk_token_num` + `delimiter` | 章节标题层级 + `sec_id` 合并 | **每行 1 块** | **不切，整篇 1 块** | 同 naive |
| 默认 `chunk_token_num` | 512 | 512（未覆盖） | — | — | **8192** |
| 一个 PDF 拆几个 task | 12 页/个 | **22 页/个** | PDF 走页拆分 | **整篇 1 个** | **整篇 1 个** |
| 摘要特殊处理 | 无 | **摘要独占整块**（`paper.py:216-225`） | 无 | 无 | 无 |

**`paper` 的分块细节**（`paper.py:144-255`）：先算 `column_width` 中位数判断双栏排版
（`paper.py:62`），用正则识别正文起点（`:75-78`），抽 title/authors/abstract
（`:89-122`）；分块时**摘要整块不切**（`:216-225`），其余按章节标题层级合并
（`:230-249`）。注意它**不按 `chunk_token_num` 强制切**，切分边界由章节标题决定。

**`knowledge_graph` 有两个容易误解的地方**（这两条是源码里的反直觉点）：

1. `rag/app/` 目录下**没有** `knowledge_graph.py` —— 分块阶段完全复用 `naive`
   （`task_executor.py:98`）。差异化只体现在默认配置 `chunk_token_num=8192`
   （`api_utils.py:407-413`）。
2. `parser_id == "knowledge_graph"` **不会自动触发图谱抽取**。GraphRAG 是一个**独立的、
   知识库级的、需手动触发**的任务（`POST /kb/run_graphrag`，`api/apps/kb_app.py:593`），
   它从**已入库的 chunk** 里抽实体关系（`graphrag/general/index.py:189`），
   走 `task_type="graphrag"` 分支（`task_executor.py:1053-1100`）。

> **另注**：前端不给 PDF 提供 `table` 选项（`web/src/components/chunk-method-dialog/hooks.ts:4-40`），
> 而 `table.py:430-431` 对非 excel/txt/csv 抛 `NotImplementedError` ——
> **PDF + `table` 组合会失败**（此结论由代码路径推导，非实测）。

### 1.4 并发与限流

| 信号量 | 环境变量 | 默认 | 保护对象 | 行号 |
|---|---|---|---|---|
| `MAX_CONCURRENT_TASKS` | 同名 | **5** | 单进程同时"在飞"的任务数 | `task_executor.py:122` |
| `MAX_CONCURRENT_CHUNK_BUILDERS` | 同名 | **1** | 同时执行的 chunker 调用数 | `:123` |

> 分块本身是串行的（CPU 密集，OCR/版面分析的保护措施）。
> 这条对工单 17 的并发排查很关键。

## 问题二：`do_handle_task` 的主要逻辑与技术实现

`do_handle_task`（`rag/svr/task_executor.py:948`）是一个**按 `task_type` 分派的多分支异步函数**。

### 2.1 执行流程（标准解析路径）

| 步骤 | 做什么 | 涉及组件 | 行号 |
|---|---|---|---|
| 0 | 入口短路：`memory` / 画布调试任务另走分支 | — | `:950-958` |
| 1 | 解包任务上下文（`embd_id`/`parser_config`/`from_page`/`to_page`） | MySQL（4 表 join） | `:960-974` |
| 2 | 构造进度回调 `progress_callback` → `set_progress` | MySQL `task` 表 | `:977` |
| 3 | 取消检查（读 Redis 键 `{task_id}-cancel`） | Redis | `:979-982` |
| 4 | **探测向量维度**：真跑一次 `embedding_model.encode(["ok"])` | Embedding 服务 | `:984-993` |
| 5 | 建索引/建表 | ES / Infinity | `:995` |
| 6 | 按 `task_type` 分支 → 标准解析走 `build_chunks` | — | `:1105-1127` |
| 7 | 写索引 `insert_chunks`（分批，批大小 `DOC_BULK_SIZE`=4） | ES / Infinity + MySQL | `:1129-1146` |
| 8 | 统计落库 `increment_chunk_num` | MySQL | `:1148` |
| 9 | （可选）TOC 落库 | ES + MySQL | `:1152-1157` |
| 10 | 收尾 / 取消时反向清理 chunk | ES + MinIO | `:1159-1188` |

### 2.2 上游调用链

```
main()  :1330
  └─ task_limiter.acquire()          :1374   # 信号量准入（先 acquire 再建协程）
  └─ asyncio.create_task(task_manager())  :1375
       └─ task_manager()             :1323
            ├─ await handle_task()          :1325
            └─ finally: task_limiter.release()  :1327
                 └─ handle_task()   :1191
                      ├─ await collect()            :1193
                      ├─ await do_handle_task(task) :1205
                      ├─ except → set_progress(-1)  :1209-1221
                      └─ redis_msg.ack()            :1231   ← 唯一的 ACK 点
```

**三者关系**：`collect()` 只取任务+补元数据；`handle_task()` 做异常兜底+统计+ACK；
`do_handle_task()` 才是业务逻辑。**`do_handle_task` 自身不碰队列。**

### 2.3 关键技术实现

**解析**：`build_chunks`（`:242-287`）从 MinIO 取原文 → `FACTORY[parser_id]` 查 chunker
（`:248`）→ `async with chunk_limiter` 包住 `chunker.chunk()`（`:268-280`）。
前置保护：文档超 `DOC_MAXIMUM_SIZE`（默认 128MB）直接失败（`:243-246`）。

**向量化**（`:569-620`）：
- 批量大小 `EMBEDDING_BATCH_SIZE` 默认 **16**；并发闸门 `embed_limiter` 默认 **1**
- 逐条 `truncate(c, mdl.max_length - 10)` 截断
- **标题加权融合**：`v = w*title_vec + (1-w)*content_vec`，`w = filename_embd_weight`（默认 0.1）（`:605-612`）
- 写回字段名 **`q_{dim}_vec`**，如 1024 维 → `q_1024_vec`（`:619`）

**索引**：

| 项 | Elasticsearch | Infinity |
|---|---|---|
| 命名 | 一租户一索引 `ragflow_{tenant_id}` | 一数据集一表 `{index_name}_{dataset_id}` |
| 向量字段 | `q_{dim}_vec`，靠 `conf/mapping.json` 的 `dynamic_templates` 按后缀匹配 `*_1024_vec` → `dense_vector` | 动态加列 + HNSW 索引 |
| ⚠️ 隐含约束 | **维度必须命中 512/768/1024/1536 之一**，否则匹配不到 dense_vector 模板 | — |
| 全文检索字段 | `content_with_weight` 后缀 `_with_weight` 命中 `index:false` ——**只存不索引** | — |

**检索权重**（`rag/nlp/query.py:32-38`）——这条直接关系到工单任务二的优化：

```
title_tks^10, important_tks^20, question_tks^20, content_ltks^2, content_sm_ltks
```

**任务状态流转**：
- 进度写 MySQL `task` 表，`progress_msg` 追加式截断到 3000 行，**进度单调不回退**（`task_service.py:298-345`）
- 失败：`handle_task` 捕获所有业务异常并 `set_progress(-1)`，**不向上抛**（`:1209-1221`）
- **重试**：只有 Redis Stream 未 ACK 的消息会在重启后重投（`get_unacked_iterator`）。
  `retry_count >= 3` 时放弃（`task_service.py:127-140`）。**业务异常被捕获并 ACK 后没有任何自动重试**，需人工重解析。

### 2.4 影响解析质量的参数

| 参数 | 默认 | 作用 |
|---|---|---|
| **`layout_recognize`** | `"DeepDOC"` | **PDF 解析器总开关**（详见问题三）。还影响任务切页：非 DeepDOC 时整篇 1 个任务 |
| `chunk_token_num` | naive 512 / 内部兜底 128 | 每块最大 token，直接决定粒度 |
| `delimiter` | `"\n"` | 句级切分符 |
| `auto_keywords` | 0 | LLM 为每块抽关键词 → `important_kwd`，**检索权重 ^20** |
| `auto_questions` | 0 | LLM 生成候选问题 → `question_kwd`，**检索权重 ^20** |
| `filename_embd_weight` | 0.1 | 标题向量权重 |
| `raptor` / `graphrag` | 均 `use_*=False` | 层级摘要 / 知识图谱；⚠️ 权威定义在**知识库级**，文档级改它们**不会触发重新分块**（`task_service.py:430-434` 算 digest 时剔除） |

### 3.2 PDF 解析主流程

**在实际生产路径上**（`rag/app/naive.py:547-579` 的 `Pdf(PdfParser)` 子类）：

| 步 | 方法 | 行号 | 做什么 |

| 1 | `__images__` | `pdf_parser.py:1047-1185` | pdfplumber 按 `resolution=72*zoomin` 渲染每页（默认 zoomin=3 → **216 DPI**）；抽原生字符层；**逐页跑 OCR** |
| 2 | `_layouts_rec` | `:350-356` | 版面识别，给每个框打 `layout_type` 与 `layoutno` |
| 3 | `_table_transformer_job` | `:199-283` | 裁表格区域 → 表格结构识别 → 打 `R/H/C/SP` 标记 |
| 4 | `_text_merge` | `:444-480` | `_assign_column`（KMeans+轮廓系数定栏数）→ 同页同栏同行做水平合并 |

### 3.3 用到的模型

| 模型 | 文件 | 类与位置 | 输出 | 后端 |
|---|---|---|---|---|
| OCR 检测 | `det.onnx` | `TextDetector`（`vision/ocr.py:414`） | 文本框四点坐标（DBNet 系） | onnxruntime |
| OCR 识别 | `rec.onnx` + `ocr.res` | `TextRecognizer`（`ocr.py:133`） | 字符串（CTC 系） | onnxruntime |
| 版面识别 | `layout.onnx` | `LayoutRecognizer4YOLOv10`（`layout_recognizer.py:164`） | **11 类**版面框 | onnxruntime |
| 表格结构 | `tsr.onnx` | `TableStructureRecognizer`（`table_structure_recognizer.py:30`） | **6 类**单元格框 | onnxruntime |
| 文本行拼接 | `updown_concat_xgb.model` | `self.updown_cnt_mdl`（`pdf_parser.py:91-104`） | 是否拼接 | XGBoost |

**统一是 ONNX，不是 PyTorch**。PyTorch 在本模块里**只用来探测有没有显卡**
（`torch.cuda.is_available()` 决定是否切 `CUDAExecutionProvider`），**没有加载任何 .pt/.pth 权重**。

**模型文件位置**：固定目录 `<项目根>/rag/res/deepdoc`。仓库里该目录**只有** `ner.json`/`synonym.json`，
`.onnx` 在 Docker 构建期从 `InfiniFlow/deepdoc` 下载并解压进去（`Dockerfile:11-16`）。

### 3.4 两个重要的「实现现状」（源码反直觉点）

这两条在排查问题时容易踩，如实记录：

1. **`_concat_downward` 已是空壳**：`pdf_parser.py:587` 排序后，**第 588 行是一个无条件 `return`**，
   其后约 100 行（含 XGBoost 预测）**全是死代码**。因此 `updown_concat_xgb.model` 虽被加载，
   **运行期从不参与拼接**。实际生效的纵向合并是规则版本。

2. **`layout_recognize` 的专用版面模型在 ONNX 路径下失效**：`deepdoc/vision/__init__.py:25`
   把 `LayoutRecognizer4YOLOv10` 别名成 `LayoutRecognizer`，而它 `__init__` 第 179 行
   **硬编码 `domain = "layout"`**。所以 `paper.py:33` 等设置的 `model_speciess` 不起作用 ——
   只有昇腾（Ascend）路径才真正按 domain 取模型。

### 3.5 低质量 / 图片型 PDF 怎么处理（**与工单任务二直接相关**）

**首要事实：源码中没有任何「检测到扫描件 → 切换解析路径」的分支。**
以 `scanned` / `扫描` / `image_based` 等关键词全仓检索，只命中一条注释。

实际生效的是**隐式机制**：

| 机制 | 位置 | 说明 |
|---|---|---|
| **OCR 无条件执行** | `pdf_parser.py:287`、`1107-1172` | 不管有没有文字层，每页渲染图都过一遍 OCR。**扫描件天然走 OCR** |
| 原生字符层按语言取舍 | `:1130` | `chars = self.page_chars[i] if not self.is_english else []` —— **英文 PDF 直接丢弃文字层**，全量依赖 OCR |
| **零结果放大重试** | `:1184-1185` | `if len(self.boxes) == 0 and zoomin < 9: 用 zoomin*3 重跑` —— 216 DPI → **648 DPI**。这是**唯一**的「质量不足自动重试」逻辑 |
| 不可见字符过滤 | `:192-197` | 丢弃 `DeviceGray` 且描边填充均为白色的字符（水印/隐形字） |
| OCR 置信度门槛 | `ocr.py:581` | `drop_score = 0.5`，低于阈值置空 |
| 检测输入分辨率 | `ocr.py:416-420` | `limit_side_len=960, limit_type="max"` —— **小图会被放大到 960 再检测**，利于低分辨率扫描件 |
| 任务分片 | `task_service.py:395-403` | 仅当 `layout_recognize == "DeepDOC"` 时按页切片；**改成其它解析器则整篇一次处理** |

### 3.6 `PlainParser` vs `RAGFlowPdfParser`

| 维度 | `PlainParser` | `RAGFlowPdfParser` |
|---|---|---|
| 原理 | pypdf 直抽文字层 | 渲染成图 → OCR → 版面 → TSR → 多轮合并 |
| 引入模型 | **无** | OCR + Layout + TSR 三个 ONNX |
| 结构还原 | 无（表格变散落文本行） | 有（表格 HTML / 描述文本） |
| 位置戳 | 无 | 有（`@@页码 x0 x1 top bottom##`），支持溯源高亮 |
