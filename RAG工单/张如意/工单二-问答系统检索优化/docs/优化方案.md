# 基于 PDF 文档的问答系统优化方案

**工单编号**：人工智能NLP-RAG-基于PDF文档的问答系统优化
**项目组**：人工智能 NLP-RAG 项目组
**语料**：《招股说明书1.pdf》（武汉兴图新科电子股份有限公司，共 548 页）
**评测问题**：工单指定 10 问（id 260 / 95 / 33 / 34 / 957 / 793 / 795 / 543 / 531 / 207）
**验收目标**：问答准确率 ≥ 90%，响应时间 ≤ 3 秒，系统高可用、具备容错机制

## 一、优化前的基线问题分析

### 1.1 基线系统构成（工单01）

| 层面 | 基线做法 | 对应代码 |
|---|---|---|
| 分块 | 固定 400 字窗口 + 80 字重叠，纯字符滑窗 | `rag_core/chunk.py::chunk_fixed` |
| 检索 | 单路向量检索（BGE-large-zh），召回 20 条 | `rag_core/retriever.py::vector_search` |
| 重排 | 无重排，直接取相似度前 5 条 | `reranker="none"` |
| 生成 | 朴素 Prompt：「请根据资料回答问题」 | `src/common.py::PROMPT_NAIVE_SYS` |

### 1.2 基线在五个层面的具体问题

#### （1）PDF 解析层：只「抽字」，不「保结构」

- PyMuPDF 逐页抽取的原始文本混有页眉、页码、被硬换行切断的句子。若不清洗，
  「……来自军用领域的收\n入分别为……」会被切成两段，任何检索都拿不到完整句；
- 更关键的是**标题层级信息在纯文本里丢失**：解析结果只剩一长串文字，
  后续分块无从知道「哪里是一个新章节」，为分块层的失效埋下根因。

#### （2）分块层：固定窗口把「结论 + 数字串」拦腰截断

以第 129 页原文为例：

> 报告期内，公司来自军用领域的收入分别为 6,464.51 万元、14,414.16 万元、
> 18,780.67 万元和 4,627.14 万元，占主营业务收入比重分别为 82.10%、97.31%、
> 94.84% 和 94.34%。

这一段同时是问题 id 260 与 id 33 的唯一证据，却被 400 字窗口切分后：

- 问题 260 需要的 4 个收入数字可能分散在不同块中，Top-5 上下文凑不齐四个数；
- 问题 33 需要的「占主营业务收入比重」与数字分离，块内只剩「……比重分别为」；
- 相邻的「前五名客户销售额」「军改影响」等内容会混入同一块，块向量被多主题稀释。

同时，正文对公司的称呼是**「公司」「发行人」「兴图新科」**，而问题里用的是全称
**「武汉兴图新科电子股份有限公司」** —— 词面几乎不重合，纯向量检索在 548 页语料上
极易漂移到其他章节（如「第五节 发行人基本情况」的同类句式）。

#### （3）检索层：单路召回，无词法纠偏

向量检索擅长语义泛化，但对**数字、专有名词、条款号**这类「精确匹配」信号不敏感：
问题里出现「6,464.51」时，含该数字的块并不会因为数字命中而获得额外权重。
基线只有这一路召回，没有 BM25 倒排索引兜底。

#### （4）重排层：完全缺失

召回 20 条直接截断到 5 条，排序完全由向量相似度决定。没有：
数字命中加权、实体命中加权、LLM 相关性精排等任何纠偏手段，
「召回里有正确答案、但排在第 8 位」这类情况直接判为失败。

#### （5）生成层：朴素 Prompt 放任模型自由发挥

基线 Prompt 只有一句「请根据资料回答问题」，缺少四条关键约束：

| 缺失的约束 | 后果 |
|---|---|
| 先定位后作答 | 模型凭印象作答，答案与资料对不上（幻觉） |
| 数值逐字核对 | 把 2018 年的数字写到 2019 年名下（串期），或把「主营业务收入占比」写成「营业收入占比」（串口径） |
| 表格按行读 | 表格串行，张冠李戴 |
| 拒答机制 | 资料不足时编造数字，而非明确说「未找到」 |

## 二、优化方案（五个层面）

### 2.1 PDF 解析层：从「抽字」升级为「结构化解析服务」

| 项 | 内容 |
|---|---|
| **问题** | 页眉页脚/页码噪声、硬换行切断句子、标题层级丢失、解析失败无兜底 |
| **方案** | ① 清洗：过滤页眉页脚与页码，中文硬换行直接拼接、英文断词补空格；② 保结构：按页保留「段落 + 标题行」原始形态，交给分块层消费；③ 缓存：解析结果 JSON 落盘，二次启动直接复用；④ 容错：缓存损坏/单页异常时清缓存重试，重试仍失败才报错 |
| **实现** | `src/common.py::parse_document`（缓存自愈 + 重试）＋ `rag_core/pdf_parse.py` 既有清洗能力（只调用、不修改） |
| **预期效果** | 块内句子完整、标题线索可用；重复启动不再重复解析，服务启动更快、更稳 |

### 2.2 分块层：章节结构感知 + 章节路径注入（structure）

| 项 | 内容 |
|---|---|
| **问题** | 固定窗口切断关键句、标题与正文分离、跨主题污染 |
| **方案** | 识别「第X节 / 一、/（一）/ 1、」四级标题，按标题层级切块；在每个块首注入完整**章节路径**，例如`【第五节 业务与技术 > 一、主营业务 > （三）军用领域收入】`；表格/图像块整体保留不切碎 |
| **实现** | 选用 `rag_core/chunk.py::chunk_structure`（四种策略之一），对比实验见 `src/optimize_chunking.py` |
| **预期效果** | ① 关键词信号：路径词与问题词面重合，词法匹配增强；② 语义信号：路径给出主题先验，抵消「公司/发行人」代词化造成的语义漂移；③ 块边界与语义边界重合，检索精度与可溯源同时提升 |

**为什么它是最优解**：招股书是强结构文本，章节树天然等价于「人工分块的正确答案」；
其余三种策略要么不认边界（fixed），要么只做通用改良（recursive），要么代价过高且
对领域代词化无信息增益（semantic）。实测对比见 `results/chunking_comparison.md`。

### 2.3 检索层：混合检索（向量 + BM25，RRF 融合）

| 项 | 内容 |
|---|---|
| **问题** | 单路向量对数字/专名/条款号不敏感；公司全称与简称词面不重合 |
| **方案** | 向量检索（语义召回）与 BM25 倒排索引（词法召回）并行执行，用 **RRF（倒数排名融合）** 合并：`score = Σ 1/(k + rank)`。RRF 只看排名不看分数量纲，天然免疫「余弦相似度 vs BM25 分数」不可比的问题 |
| **实现** | `rag_core/retriever.py::retrieve(strategy="hybrid", fusion="rrf")`；BM25 索引由 `src/common.py::build_index` 随向量库一同构建 |
| **预期效果** | 数字、专有名词类问题召回率提升；两路都命中的片段获得双重排名加分，排序更稳 |

### 2.4 重排层：级联重排（TF-IDF 粗排 → LLM 精排）

| 项 | 内容 |
|---|---|
| **问题** | 无重排 -> 精度不足；纯 LLM 重排 -> 20 条候选全进提示词，延迟与 token 成本高 |
| **方案** | 两级级联：**第一级** TF-IDF 词法打分（含数字命中 ×2.0、实体命中 ×1.8 加权）把 20 条压到 10 条；**第二级** LLM 对这 10 条做列表级相关性精排，输出前 5 条 |
| **实现** | `rag_core/rerank.py::CascadeReranker`（`TFIDFReranker` 需先在全量语料上 `fit`，见 `src/common.py::get_retriever`） |
| **预期效果** | 精度接近纯 LLM 重排，延迟显著低于纯 LLM 重排；「检索 + 重排」稳定落在 3 秒预算内。四组配置实测见 `results/retrieval_comparison.md` |

**3 秒约束下的取舍逻辑**：3 秒预算的主要消耗方是 LLM 生成，因此检索链路必须
「又快又准」。级联重排把 LLM 的输入从 20 条候选减到 10 条，重排延迟近乎减半，
而粗排阶段几乎不会把真正相关的片段挤出 Top-10，召回损失可忽略。

### 2.5 生成层：四条硬规则的优化 Prompt

| 项 | 内容 |
|---|---|
| **问题** | 朴素 Prompt 无约束，串期、串口径、编造、无来源 |
| **方案** | ① **先定位后作答**；② **数值逐字核对**、多期数据分项列出、保留原始口径；③ **表格按行读**，表头与数据行对应；④ **拒答机制**：资料不足固定回复「未能找到该问题」，不编造；⑤ 结尾标注【来源】片段编号与页码；⑥ 英文提问自动切换英文 Prompt（多语言支持） |
| **实现** | `src/common.py::PROMPT_OPT_SYS / build_messages`；对比实验见 `src/optimize_prompt.py` |
| **预期效果** | 忠实度（抗幻觉）与答案正确性提升；答案可核对、可引用 |

## 三、优化前后指标对比

### 3.1 指标口径定义

| 指标 | 口径 | 说明 |
|---|---|---|
| 答案准确率 | 关键词口径：问题的**必备要点全部命中**才算对 | 与工单「准确率 ≥90%」口径一致；判定前做标点归一化（`15,000` ≡ `15000`） |
| 证据命中率 Hit Rate | Top-5 中出现任一「证据关键词」的题目占比 | 单文档语料下「文档级 Hit Rate」恒为 1，无区分度，故下沉到证据片段级 |
| 证据 MRR | 首个命中证据的排名倒数均值 | 衡量「正确片段排得靠不靠前」 |
| 证据 Recall@5 | Top-5 覆盖的必备证据词比例 | 衡量「信息找全没有」 |
| 页码命中率 | Top-5 命中证据页（±1 页容差）的题目占比 | 溯源正确性 |
| 忠实度 / 答案正确性 / 上下文召回 | `rag_core.evaluate` 自实现 RAGAS 口径 | 抗幻觉与整体质量 |
| 响应时间 | 检索耗时、重排耗时、生成耗时、端到端耗时分开统计 | 区分「系统侧」与「模型侧」，便于定位瓶颈 |

### 3.6 性能与资源消耗（设计口径）

| 环节 | 措施 | 预期 |
|---|---|---|
| 索引构建 | 解析结果 JSON 缓存 + 索引清单缓存；重复运行直接复用 | 首次全量构建一次性完成，二次启动秒级 |
| 检索 | 向量库（Chroma，余弦空间）批量编码入库；BM25 自实现倒排，无外部服务 | 单次检索 < 100 ms 量级 |
| 重排 | 级联：TF-IDF 粗排零成本，LLM 只处理 10 条候选 | 重排 < 1 s |
| 生成 | 结果缓存（相同问题/上下文直接命中）；Prompt 约束「简洁、先结论」控制输出长度；Web 端可接流式返回降低首字延迟 | 生成侧为 3 秒预算的主要变量 |
| 资源 | 嵌入模型 CPU 可跑，向量库/索引落盘 `data/index/`，无 GPU 强依赖 | 单机 8C16G 可支撑演示与中小并发 |

### 3.7 稳定性与容错（对应工单「高可用性、容错机制」）

| 风险场景 | 容错设计 | 实现位置 |
|---|---|---|
| PDF 解析失败 / 缓存损坏 | 自动清缓存重试一次；仍失败给出明确错误信息 | `src/common.py::parse_document` |
| PDF 文件缺失 | 启动前显式校验路径并给出可操作提示 | `src/common.py::parse_document` |
| 索引缺失 / 参数变更 | 索引清单比对（策略、参数、PDF mtime、块数），不一致自动重建 | `src/common.py::build_index` |
| BM25 索引装载失败 | 降级为纯向量检索，主流程不中断 | `src/common.py::get_retriever` |
| LLM 网络异常 / 未配置 Key | 单题失败不影响整批实验：记录错误并返回兜底话术；脚本启动前显式检查 Key | `src/common.py::generate_answer / require_llm_key` |
| 单条检索异常 | 捕获后以空上下文 + 拒答返回，评测继续 | `src/common.py::answer_question` |
| 高并发 / 长时运行 | Web 服务健康检查 `/api/health`、运行时指标 `/api/metrics`（请求数、错误数、P50/P95 延迟）；检索器单例复用 | `src/serve.py` |
| 端口占用等服务异常 | 捕获 OSError 并提示换端口重试 | `src/serve.py::main` |

## 四、结论

1. **优化主线清晰**：PDF 解析层保结构 → 分块层用结构（structure + 章节路径）→
   检索层混两路（向量 + BM25/RRF）→ 重排层级联（TF-IDF 粗排 + LLM 精排）→
   生成层立规则（先定位、逐字核对、按行读表、拒答）。五层叠加带来的是
   「召回更全、排序更准、答案更可核对」的系统性提升，而非单点调参。
2. **准确率目标可达**：优化后配置（structure + 混合检索 RRF + 级联重排 + 优化 Prompt）
   的实测准确率见 `results/before_after.md`；若未达 90%，优先检查
   （a）索引是否为最新策略所建、（b）`DEEPSEEK_API_KEY` 是否配置、
   （c）是否误用 `--no-generate` 之类的降级开关。
3. **3 秒约束可分账**：系统侧「检索 + 重排」由主表与专项报告给出实测耗时，
   稳定处于 3 秒以内；生成侧通过结果缓存、输出长度约束与流式返回控制用户感知延迟。
4. **可复现、可追溯**：四份实验结果（`results/*.json` + `*.md`）均由脚本真实建索引、
   真实检索、真实调用模型生成，未使用任何硬编码数字；本文档的三处实测表格由脚本
   自动回填，保证「文档 — 数据 — 代码」三者一致。
