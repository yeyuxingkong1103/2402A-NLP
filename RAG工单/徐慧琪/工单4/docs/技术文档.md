## 一、系统架构

### 1.1 数据流

```
                 ┌──────────────── 解析层 ────────────────┐
PDF ──────────►  │ 文本块 │ 表格块 │ 图像块(图区检测→渲染)   │
                 └────────────────────────────────────────┘
                                    │
                 ┌──────────────── 分块层 ────────────────┐
                 │ 按 block_type 差异化语义分块            │
                 │  图像块 = VLM结构化描述 + CLIP向量       │
                 └────────────────────────────────────────┘
                                    │
                 ┌──────────────── 索引层 ────────────────┐
                 │ Qdrant: text_chunks / table_chunks /    │
                 │         image_chunks                    │
                 └────────────────────────────────────────┘
                                    │
   用户提问 ──► 语言检测 ──► ┌── 检索层 ──┐
                          │ dense(bge-m3)  ∥  sparse(BM25) │
                          │        ∥  CLIP 文→图            │
                          │        ↓  RRF 融合 → 重排        │
                          └────────────────────────────────┘
                                    │
                 ┌──────────────── 生成层 ────────────────┐
                 │ DeepSeek API（主）/ Ollama（兜底）       │
                 │ 按提问语言作答 + 引用溯源                │
                 └────────────────────────────────────────┘
                                    │
                 答案 + 检索精确度 + 引用来源(页码/类型/ID)
```

（架构图沿用 `docs/superpowers/specs/2026-10-05-图像内容解析及检索优化-design.md` §3.1，
实现与图一致：解析/分块/索引/检索/生成五层，界面与服务是两个并列的入口。）

### 1.2 分层职责

| 层 | 关键模块 | 职责 |
| --- | --- | --- |
| 解析 | `ingest/loader.py`、`figures.py`、`tables.py`、`vlparser.py` | 文本块（含旋转标记、坏页容错）、图区检测与高 DPI 渲染、表格抽取、VLM 结构化描述 + CLIP 向量 |
| 分块 | `ingest/chunker.py` | 文本语义分块、表格整表成块、图像双重表征（描述文本 + CLIP 向量，`dedup_key` 关联） |
| 索引 | `ingest/store.py` | Qdrant 三 collection、连接封装、采样与计数 |
| 检索 | `retrieve/embed.py`、`bm25.py`、`image_index.py`、`hybrid.py`、`rerank.py`、`boilerplate.py` | 三路召回 → RRF 融合（含图像指向词加权）→ 重排；样板过滤 |
| 生成 | `generate/prompt.py`、`llm.py` | 中英双语 prompt、按提问语言作答、DeepSeek 主 + Ollama 兜底、超时与降级（**无请求限流**，见 §二 生成行）、拒答判定 |
| 编排 | `pipeline.py` | `ingest_document` / `build_all` / `ask` / `RAGPipeline`（惰性加载 + 预热 + 重建让路） |
| 评估 | `eval/questions.py`、`metrics.py`、`runner.py`、`compare.py`、`ragas_eval.py` | 16 题标准答案、指标、执行器、双模式对比、RAGAS |
| 服务/界面 | `api/server.py`、`ui/app.py` | FastAPI（压测与集成入口）、Streamlit 中英双语界面 |
| 可观测 | `obs/logging.py` | 轮转日志 10MB×10、计时上下文、内存快照 |

## 二、技术选型

选型以「本机可离线运行 + 每个决定有实测依据」为准；备选一栏给出被放弃的方案与原因。

| 层次 | 选型（版本） | 备选 | 选型理由 |
| --- | --- | --- | --- |
| PDF 文本/矢量 | PyMuPDF 1.25.5 | pypdf、pdfminer | 唯一同时提供文本块 bbox、旋转标记（`dir`/`wmode`）、矢量绘制（`get_drawings`）、嵌入位图（`get_image_info`）与高 DPI 渲染（`get_pixmap`）的库；图区检测两条来源都依赖它 |
| 表格 | pdfplumber 0.11.10 | PyMuPDF `find_tables` | 表格网格识别更稳；RC4 起额外调用 `find_tables()` 取 bbox 供行标签对照，表格阶段耗时约翻倍（招股说明书1 的 447 张表约 30s），属一次性建库成本 |
| 向量库 | Qdrant（embedded，client 1.18.0） | FAISS、Chroma、pgvector | 多 collection + payload 过滤 + 本地无服务模式，Windows 友好。**并发口径**：`store.py` 的 `pool_size` 只在**服务端 URL 模式**（`QdrantClient(url=...)`）下生效，本机默认的嵌入式模式（本地路径）**没有 httpx 连接池**，靠「一次打开、进程内复用同一客户端」避免重复开销。**代价**：本地客户端对 `data/qdrant` 持独占文件锁，跨进程/同进程再开会抛「already accessed」——故有启动预热抢锁、重建先释放句柄、撞锁映射 409/503 三处防护 |
| 稠密向量 | bge-m3（Ollama，1024 维，批量 16） | OpenAI text-embedding-3、m3e | 中文长文档表现好、可离线；Ollama 一条命令拉起，无 key 依赖 |
| 稀疏检索 | jieba 0.42.1 + rank-bm25 0.2.2 | Elasticsearch / BM25 | 零服务依赖；带招股书领域词典，避免关键实体被切碎 |
| 跨模态 | CLIP ViT-B/32（512 维） | Chinese-CLIP、OpenCLIP | 权重可取得（hf-mirror `pytorch_model.bin` 605.2 MB），CPU 可推理；「以文搜图」只需粗定位，精读交给 VLM |
| 重排 | bge-reranker-base（CrossEncoder，1112.3 MB） | Cohere Rerank（需联网付费）、不重排 | 本地可跑、中文对句打分有效；加载约 8s（进程内一次性，`warmup()` 预热），是 CPU 时延主要来源之一，故融合 top-30 → 输出 top-5 |
| 图像语义 | 多模态大模型 `deepseek-v4-flash-vision-exp` | 纯 OCR、仅 CLIP | 组织结构图需理解层级与枚举，OCR 只能得到零散单字；须 `thinking: disabled` + `max_tokens ≥ 2000`（见专项说明 §三） |
| 生成 | DeepSeek API（`deepseek-v4-flash`）主 + Ollama `qwen2.5:3b` 兜底 | 纯本地小模型、纯云 | 中文问答质量与成本平衡；无 key 时自动降级并如实上报 `llm_backend`。**并发口径（如实说明）**：`Settings.llm_max_concurrency=8` 目前只是**预留配置项**——`generate/llm.py` 及全仓没有任何信号量/线程池/锁读取它，**没有实现请求限流**；当前真正约束并发的只有：`/api/ask` 是同步端点（由 anyio 线程池承载）与 LLM 客户端自带超时（`llm_timeout_s=30`，无自动重试）。10/50/100 并发下的真实时延与错误率由压测报告给出（数值见 §八） |
| 服务 | FastAPI 0.115.14 + uvicorn 0.34.3 | Flask、gRPC | 类型校验（Pydantic）、自动文档；工厂模式 `_get_app` 避免导入即加载模型/锁索引 |
| 界面 | Streamlit 1.61.1 | Gradio、Vue 前端 | 单文件可交付、中英双语与文件上传开箱即用；`import streamlit` 只在 `main()` 内，纯函数可单测 |
| 评估 | 自研 `eval/metrics.py` + ragas 0.2.15 | 只用 RAGAS | 自研口径可复现（Precision/Recall/NDCG@k、HitRate、MRR、AnswerAcc、严格口径 id5）；RAGAS 作补充，依赖 LLM 时如实标注「未执行/部分执行」 |
| 测试 | pytest 9.1.1（`integration` 标记）+ ruff | unittest | 默认 `-m "not integration"` 全绿；需要外部 API/模型的用例单独标记 |

运行环境（本机实测）：Windows 11 + Python 3.12.10 + torch 2.13.0+cu126（CPU 推理为主）+ transformers 5.15.0。

## 三、开发流程

1. **计划先行**：`docs/superpowers/plans/2026-10-05-图像内容解析及检索优化-实施计划.md`
   把交付拆成 Task 1–23，每个任务给出 Files / Interfaces / TDD 步骤 / 验收命令 / 提交信息。
2. **TDD 逐任务交付**：先写失败测试（RED）→ 最小实现 → 通过（GREEN）→ 提交。
   每个任务留有 `.superpowers/sdd/task-N-brief.md` 与 `task-N-report.md`（证据、偏离、遗留）。
3. **复核轮**：任务完成后由复核角色出结论（Critical/Important/Minor 分级），
   修正单独提交并在报告里逐条登记处置（如 Task 19 的 4 Important + 6 Minor）。
4. **RC 修复阶段**：检索质量不达标时不重建索引、不动数据，先做「免重建修复」
   （RC-1 样板过滤与拒答判定、RC-2 dedup/行块合并、RC-3 CLIP 条数上限），
   每步都以真实 16 题评估复测为准。
5. **提交规范**：每条提交信息含工单编号；每个 `.py` 文件首行注释含工单编号
   （校验方式见 `docs/superpowers/plans/2026-10-05-图像内容解析及检索优化-实施计划.md`
   Task 23 Step 3：那是一段**人工执行**的遍历检查命令，尚未脚本化，也不是 CI 步骤）。
   入库范围：`src/`、`scripts/`、`tests/`、`benchmarks/`、`docs/`；
   **`_scratch/`、`data/`、`docs/reports/*.json` 不入库**；
   `.superpowers/sdd/` 由该目录下的 `.gitignore`（内容为 `*`）整体忽略——
   其中 `progress.md` 是**已被历史提交跟踪**的文件，忽略规则不影响它，
   但按约定它不随交付提交（本任务只提交交付文件本身）。
6. **质量门**：默认套件 `python -m pytest -q` 全绿且不新增 warning；
   integration 用例单独运行（需 Ollama、模型权重与 API key）。

## 五、运行方法

### 5.1 环境准备

```bash
python -m pip install -r requirements.txt      # 依赖（含 torch/transformers/qdrant/streamlit/ragas）
ollama pull bge-m3                             # 稠密向量模型（Ollama）
ollama pull qwen2.5:3b                         # 生成兜底模型
python scripts/download_models.py              # CLIP(605.2MB) + bge-reranker-base(1112.3MB)，走 hf-mirror
export API=sk-xxx                              # 生成/VLM 的 API key（依次尝试 API → QWEN_API → OPENAI_API_KEY）
# 可选：export OPENAI_BASE_URL=https://api.deepseek.com（默认值）
```

`python scripts/download_models.py` 失败不阻断：reranker 缺失自动降级为启发式重排，
CLIP 缺失则该路检索被跳过（`/health` 会如实显示 `clip: missing`）。

### 5.2 建库

```bash
python scripts/build_index.py full_04            # 一键建库（全量约 15 分钟）
python scripts/build_index.py full_04 --reset    # 先清空三库再建（分块/口径变更后必须用）
python scripts/build_index.py baseline_03        # 对照模式建库
```

日志写入 `logs/rag04.build.full_04.log`，末行给出每份语料的
「文本（入库侧剔除样板）/ 表格 / 图区 / 分块 / 用时 / 告警」与总块数。
本机全量建库实测的索引构成（三库之和 = 总块数）：

| collection | 条数 |
| --- | --- |
| `text_chunks` | 4436 |
| `table_chunks` | 681 |
| `image_chunks` | 162 |
| **合计** | **5279**（4436 + 681 + 162） |
容量提示：`data/qdrant` 由 Qdrant 本地客户端独占，**同一时刻只能有一个进程持有**；
重建前请停掉 API/界面进程（或直接用 `/api/ingest` 带 `confirm` 的路径）。

### 5.3 评估与报告

```bash
python scripts/run_eval.py full_04               # 中文 16 题 → 检索精确度报告_full_04.md + eval_full_04.json
python scripts/run_eval.py full_04 en            # 英文模式（answer_accuracy 置 null，见下）
python scripts/gen_location_report.py            # 答案定位报告（数据源默认 docs/reports/eval_full_04.json）
python scripts/gen_location_report.py --src docs/reports/eval_full_04.json \
                                     --out docs/答案定位报告.md   # 显式指定输入输出
```

英文模式的诚实口径：问题为英文而标准要点（`answer_key`）为中文，逐字覆盖率无意义，
故不判定答案正确性（`answer_accuracy` 为 `null`），检索指标与耗时照常统计。

### 5.4 接口与压测

```bash
# 终端 A：起服务（工厂模式，避免导入即加载模型；启动时同步预热存储/reranker/CLIP/embed）
uvicorn rag04.api.server:_get_app --factory --port 8000 --app-dir src

# 终端 B：接口自检 + 压测（地址一律写 127.0.0.1，理由见下方「本机地址口径」）
curl http://127.0.0.1:8000/health
curl -X POST http://127.0.0.1:8000/api/ask -H "Content-Type: application/json" \
     -d "{\"question\":\"组织结构图中销售部有几个部门构成？\"}"
python benchmarks/loadtest.py http://127.0.0.1:8000 10,50,100     # 三档并发，每档缺省 3×100 = 300 请求
```

**每档请求数的真实口径**（`benchmarks/loadtest.py: resolve_per_level`，有单测守护）：
不传第三个参数时每档请求数 = **3 × 最大并发**（10/50/100 即每档 300，共 900 请求）；
显式传的数值若**小于最大并发**（例如写 `… 10,50,100 60`），会被**上调到最大并发 100**
并打印告警——否则该档的在飞请求数不足、标称并发根本施加不出去，报告会夸大压测强度。
故 `… 10,50,100 60` 实际跑的是**每档 100 请求**，不是 60。

压测报告写入 `docs/reports/高并发压测报告.md`，含客户端墙钟（主口径）与服务端上报两组时延
及逐级 3 秒预算判定。**注意**：`/health` 会同步探测 Ollama（最多 3 秒），压测时只打 `/api/ask`。

**本机地址口径（必须写 IPv4 字面量）**：本机 `localhost` 的 `getaddrinfo` 先返回 IPv6 的
`::1`，而 Ollama 只监听 `127.0.0.1:11434`、本项目服务绑 `0.0.0.0`（同为仅 IPv4）。因此在
本机写 `localhost` 时，每个**新建**连接都要先等 IPv6 连接失败再回退到 IPv4。实测：

| 目标 | `localhost` | `127.0.0.1` |
| --- | --- | --- |
| Ollama `/api/embed`（每次新建连接，`requests.post`） | 2205 / 2269 ms | 229 / 229 / 211 ms |
| 本项目 `/health`（每次新建连接，`urllib`） | 2065 / 2047 / 2053 ms | 46 / 46 / 15 ms |

故 `Settings.ollama_url` 默认值、压测脚本默认 URL 与文档命令一律用 `127.0.0.1`：
嵌入路径每次问答都要新建连接，若写 `localhost` 等于**每问白付约 2 秒**（3 秒预算的 2/3）。
调用方若改用长连接（`requests.Session`/httpx 连接池），该代价只在建连时付一次，
但默认配置不依赖这一点。`tests/test_config.py::test_ollama_url_is_ipv4_literal_not_localhost`
钉住该默认值，防止回退。

## 六、双模式说明

`Settings.pipeline_mode` 有 `baseline_03`（代表工单01/02/03 的能力）与 `full_04`（本工单）
两个取值，由 `config.__post_init__` 覆写开关，**两条链路共用同一套代码、同一批 16 题、同一份语料**，
变量可控。选择方式：命令行参数（`scripts/*.py` 第一个参数）或环境变量 `RAG04_MODE`。

| 维度 | baseline_03 | full_04 |
| --- | --- | --- |
| 图区解析 `use_figures` | 关 | 开（三层检测 + VLM + CLIP） |
| 表格 `use_tables` | 关 | 开（pdfplumber → Markdown） |
| 混合检索 `use_hybrid` | 关（纯稠密） | 开（dense + BM25 + CLIP → RRF） |
| 重排 `use_rerank` | 关 | 开（bge-reranker-base，top-30 → top-5） |
| CLIP 跨模态 `use_clip_retrieval` | 关 | 开（512 维，`clip_max_k=10`） |
| 分块 | 固定 512 字（`fixed_chunk_size`） | 语义分块 500~800 字 + 表格/图像差异化 |
| 入库侧样板剔除 | 不做（对照组保持原样） | 做（与检索侧同一判据） |

对照报告的生成方式：分别以两个模式跑 `run_eval`，再用
`rag04.eval.compare.write_comparison(baseline, full, path)` 产出
`docs/reports/优化前后对比分析.md`（含逐指标变化与 id 5/id 6 图像题专项）。

> **基线口径备注（如实标注）**：baseline_03 **已测**数据产出时 `use_hybrid` 尚未接线
> （当时是死开关，实际跑的是稠密 + 稀疏 RRF）——上表「纯稠密」是该模式的**设计语义**，
> 不是那批数字的实际路径；开关现已在 `retrieve/hybrid.py` 接线，此后重跑的 baseline_03
> 才是纯稠密。该差异只会**低估**优化幅度，不会夸大；如需纯稠密基线需重建其索引
> （实测约 2.6 小时），已登记为后续项。

**两模式对比数值与 RAGAS 指标：** 见 `docs/reports/优化前后对比分析.md`

## 七、接口契约

| 方法与路径 | 说明 | 关键字段 |
| --- | --- | --- |
| `GET /health` | 各组件可用性 | `mode`、`qdrant`（`ok` / `down: <异常类>`）、`counts`、`bm25`、`ollama`、`llm`、`clip`、`rerank`、`figures`、`tables`、`latency_budget_ms`、`warmup`、`rebuilding` |
| `POST /api/ask` | 单题问答 | 请求 `{question, mode?}`；响应 `answer`、`lang`、`citations`、`latency_ms`、`llm_backend`、`refused`、`latency_budget_ms`、`within_budget`、`mode`（实际生效模式回显） |
| `GET /api/stats` | 索引统计 | `store`（`ok` / `not_loaded` / `error`）、`counts`、`mode` |
| `POST /api/ingest` | **全量重建**（`build(reset=True)`：先清空三个 collection 再重建） | 必须 `{"confirm": true}`；同步阻塞约 15 分钟，标准路径仍是 CLI |

界面上的上传按钮**不是**这个语义：新文档走 `build(names=corpus + [新文件], reset=False)`
**追加**进索引（两份语料仍可答），只有上传与语料同名的文件（覆盖源文件、`chunk_id` 随之变化）
才在前端勾选覆盖确认后走 `reset=True` 全量重建。两者都不调用 `/api/ingest`。

约定与防护：

- **时延口径**：`latency_ms` 一律取流水线内自测值（不含 HTTP 与前端开销），
  按 `Settings.latency_budget_ms`（3000 ms）如实回 `within_budget`；超预算不截断、不缓存、不重试。
  达标判定只有 **`rag04.config.latency_verdict(ms, budget_ms)`** 一份实现（先把实测值四舍五入到
  1 位小数再比较，边界含等号），API 的 `within_budget`、界面文案与压测报告的逐级判定三处共用，
  因此同一份测量在三个界面上不会给出互相矛盾的结论。
- **错误形状**：业务错误统一为顶层 `error` 字段——400（请求不合法/未确认重建）、
  409（索引被占用或重建进行中）、503（重建中不可问答）；FastAPI 的 422 校验错误保持默认 `detail` 形状。
- **重建防护**：重建期间该 worker 不接问答（503），同一时刻只允许一个重建（并发第二个 → 409），
  重建前先释放本进程的存储句柄再让 `build_all` 独占索引。
- **跨进程撞锁**：任何进程持有 `data/qdrant` 时，`/api/ask` 与 `/api/ingest` 都返回可执行的 409/503 文案
  （附原始错误），不抛裸栈。
