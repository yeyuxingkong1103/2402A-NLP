## 1.1 首期部署范围

首期只要求在 Ubuntu 服务器完成成功部署和验收。算力云、腾讯云、阿里云和 Windows 环境暂不作为首期发布阻断条件。

部署分两部分，由 `scripts/deploy/` 下的脚本负责：

- **数据服务**：MySQL、Redis、Milvus —— 由 `install.sh` 第 d 步处理（先探测端口，本机已有外部实例则跳过，否则 docker run 起官方镜像）；
- **应用服务**：FastAPI 后端（uvicorn）、Next.js 前端（`next start`，构建用 `output: 'standalone'`）；
- **Nginx**：反向代理，`/` 走前端、`/api/` 直连后端；SSE 流式接口必须关闭响应缓冲（`proxy_buffering off`）。

项目**不使用 Docker Compose 编排应用**，也不需要 Celery/Worker（首期没有异步任务队列）。



```text
用户
  -> Nginx / HTTP Proxy
  -> FastAPI API 服务（含检索与护栏）
  -> MySQL / Redis / Milvus
  -> 在线模型 API（LLM / Embedding / Reranker）
```

## 3. 服务器要求

### 3.1 最小测试配置

- CPU：4 核；
- 内存：16 GB；
- 磁盘：100 GB SSD；
- GPU：非必须，可使用在线模型 API；
- 操作系统：Ubuntu 22.04 LTS 或更高（`install.sh` 仅支持 Ubuntu 22.04+，不兼容 CentOS）；
- Python：3.11 或更高版本；
- Docker：建议安装。

### 3.2 推荐生产配置

- API 节点与前端节点可分离部署；
- Milvus、MySQL 和 Redis 使用高可用或托管服务；
- 本地模型节点配置 GPU；
- Nginx 配置 HTTPS 和负载均衡；
- 定期备份数据库、Milvus 和原始文件。

## 4. 目录结构

```text
rag/
  backend/                    后端（FastAPI）
    app/
    tests/
    requirements.txt
    pyproject.toml
    .env.example
  frontend/                   前端（Next.js）

    run.sh                    启动服务（依赖检查→后端→前端→双健康检查→打印地址与日志路径）
    shutdown.sh               停止服务（默认只停前后端，数据服务需显式 --stop-data）
    nginx.conf                反向代理（/ 走前端，/api/ 直连后端，SSE 关缓冲）

    health-check.sh           健康检查
    backup.sh                 备份 MySQL / Milvus / 原始文件

  data/                       运行期数据，不入 Git

    backups/
  logs/
  README.md
```

> 说明：原目录结构里的 `configs/` 已取消——应用配置走 `.env` 与 `app/core/config.py`，外部服务配置（nginx.conf）放根目录；只有外部服务配置文件达到 3 个以上时才新建 `configs/`。脚本放在 `scripts/deploy/`：`install.sh`（安装初始化）、`run.sh`（启动）、`shutdown.sh`（停止）、`nginx.conf`（反代）。

## 7. 配置环境变量

复制配置文件：

```bash

# 按 ENVIRONMENT 选择加载；真实凭据写在本机私有的 .env（后读并覆盖，不入交付物）
```

示例（键名以 `backend/.env.example` 为唯一权威清单；**生产以 `.env.production` 为准**——`.env.example` 里的召回窗口、拒答阈值、会话 TTL 是默认值，与生产调优后的取值不同）：

```dotenv
# 键的完整清单以 backend/.env.example 为唯一权威（它与代码实际读取点逐一对齐，已清理无效键）。
# 下面是生产部署**必须显式配置**的部分，键名务必照抄（历史上踩过键名错位的坑）：

# 运行环境：production 会强制校验"模型 API + 邮件"共 9 个必填键，缺失则启动失败
ENVIRONMENT=production
APP_NAME=legal-rag
LOG_LEVEL=INFO

# 数据库（MySQL）：保存文档、版本、分块、会话与记忆
MYSQL_HOST=mysql
MYSQL_PORT=3306
MYSQL_DATABASE=legal_rag
MYSQL_USER=rag_user
MYSQL_PASSWORD=<数据库口令>
# SQLAlchemy 连接串：CLI 与迁移脚本优先读它，未配置时由上面 5 项拼装
DATABASE_URL=mysql+pymysql://rag_user:<数据库口令>@mysql:3306/legal_rag

# Redis：会话令牌 + 短期记忆（应用用 0 号库，测试用 9 号库）
REDIS_URL=redis://:<Redis 口令>@redis:6379/0
# 会话令牌有效期（秒）；production 下不允许沿用默认值
SESSION_TTL_SECONDS=86400

# Milvus：知识库集合与长期记忆集合**必须分开**（存储层杜绝跨用户泄漏）
MILVUS_HOST=milvus
MILVUS_PORT=19530
MILVUS_COLLECTION_NAME=legal_documents
MILVUS_LONG_TERM_COLLECTION_NAME=legal_long_term_memory

# 模型 API（必须与索引时使用的模型一致，否则检索结果错位）
EMBEDDING_API_BASE_URL=<Embedding 服务地址>
EMBEDDING_API_KEY=<Embedding 密钥>
EMBEDDING_MODEL=BAAI/bge-m3
EMBEDDING_DIMENSION=1024
RERANKER_API_BASE_URL=<重排服务地址>
RERANKER_API_KEY=<重排密钥>
RERANKER_MODEL=BAAI/bge-reranker-v2-m3
LLM_API_BASE_URL=<大模型服务地址>
LLM_API_KEY=<大模型密钥>
LLM_MODEL=<大模型名称>
# 推理型模型必须给足，否则思考过程会吃光 token 导致空回答
LLM_MAX_TOKENS=4096

# 邮件（production 必填，用于注册与改密的验证码）
SMTP_HOST=smtp.qq.com
SMTP_PORT=465
SMTP_USERNAME=<发信邮箱>
SMTP_PASSWORD=<邮箱授权码>
SMTP_FROM_EMAIL=<发信邮箱>
SMTP_USE_SSL=true
```

> 已废弃、**不要再用**的旧键名（历史上造成过"改了不生效也不报错"）：
> `APP_ENV`（代码读 `ENVIRONMENT`）、`REDIS_SESSION_TTL_SECONDS`（读 `SESSION_TTL_SECONDS`）、
> `MYSQL_DSN`（读 `DATABASE_URL`）、`SMTP_AUTH_CODE`（读 `SMTP_PASSWORD`）、

## 启动前自检（每次开机都要做）

```text
【运行环境】本项目正式环境是 conda 环境 rag：conda activate rag
            不要用 anaconda3 base 环境（版本不同，验收结论无效）

本机开发环境依赖三个外部服务，机器重启后它们**不会自动启动**，必须手动拉起：

1. Docker Desktop（Milvus 与 Redis 都跑在容器里）
   · 没启动时的症状：Milvus 连接失败 / 检索报错 / 测试里 real_api 用例失败
   · 启动方式：打开 Docker Desktop（本机安装在 D:\Docker），等托盘图标变为 Running

2. 容器本身的启动顺序（Docker 起来后）
   docker start my-redis milvus-standalone attu

3. 自检三连（任一失败先解决再启动应用）
   docker ps                      # my-redis 与 milvus-standalone 应为 Up
   redis-cli -u redis://127.0.0.1:6379 ping     # 期望 PONG
   curl -s http://127.0.0.1:9091/healthz        # Milvus 健康端点，期望 OK
```

> Milvus 若以 `Exited (134)` 反复退出，多半是嵌入式 etcd 元数据损坏
> （日志出现 `voters=()`），修复步骤见《开发路线图》已知限制第 5 条。

## 首次初始化（部署后必须做，不可跳过）

> 认证体系已改为数据库存储（用户主体落 MySQL），因此**新库部署后没有任何账号**，
> 需要按下面两步建立第一个管理员，否则审核发布接口无人可调用。

```bash
# 第 1 步：注册一个账号（页面注册，或调用注册接口）
#   页面：http://<host>:3000/register
#   接口：POST /api/v1/auth/register  { "email": "...", "password": "...", "code": "..." }
#   注意：**所有环境都用真实 SMTP 发信**（需先配好 SMTP_*，生产缺配置会在启动期直接失败）；
#   development 环境只有 /api/v1/auth/password-reset/code 会在响应里回显 debug_code 便于本地联调，
#   注册接口在任何环境都不回显验证码。

# 第 2 步：把该邮箱升级为管理员（CLI 幂等，未注册邮箱会明确报错）
cd backend
python -m app.cli.create_admin --email someone@example.com

# 第 3 步：验证管理员可用
#   用该账号登录后调用：GET /api/v1/admin/documents?status=pending_review → 期望 200
```

```text
本地演示环境可以保留两个演示账号（一个管理员、一个普通用户）便于演示：
  · 管理员账号用于演示审核发布流程（/admin/documents）
  · 普通账号用于演示权限拦截（访问管理端应显示无权限）
  · 账号由项目负责人保管，密码不写入任何文档
  ⚠️ 上线前必须删除演示账号或改强密码（生产环境不得存在已知口令的账号）

注意：
· create_admin 不会静默创建账号，只把"已注册"的账号升级为管理员
· 未登录访问管理员接口返回 401；已登录但非管理员返回 403（接口存在，不是隐藏）
```

## 12. Nginx 配置示例

```nginx
upstream rag_api {
    server 127.0.0.1:8000;
    # server 127.0.0.1:8001;
}

server {
    listen 80;
    server_name rag.example.com;

    client_max_body_size 50m;

    location / {
        proxy_pass http://rag_api;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Request-ID $request_id;
        proxy_buffering off;
        proxy_read_timeout 300s;
    }
}
```

## 17. 部署前必读：端口占用、前端代理、数据一致性与交付包

### 17.1 端口占用检查（本机踩过的坑，务必先看）

```text
现象：前端所有 /api 请求返回 401，提示"登录状态已失效，请重新登录"，且**无法登录**。
根因：本机 8000 端口被 **attu**（Milvus 的 Web 管理界面，映射 0.0.0.0:8000->3000）占用，
     访问它返回 {"error":"Authentication required"}；
     而 frontend/.env 的 BACKEND_ORIGIN 指向 http://127.0.0.1:8000
     → 前端把 /api 全部代理到了 attu，请求根本没到后端。
处理：① 后端固定起在 8001；② frontend/.env 的 BACKEND_ORIGIN 指向真实后端；
     ③ `scripts/deploy/run.sh` 已内置端口占用检查，被占用时明确报错而不是静默启动。
部署到服务器时：attu 不要映射 8000（或另选端口），避免同类冲突。
```

### 17.2 前端 BACKEND_ORIGIN 的正确口径

| 场景 | 取值 |
| --- | --- |
| 本机开发 | `http://127.0.0.1:8001`（后端实际监听端口） |
