## 1. 文档目的

本文档描述在《工单十七》要求下，对既有 RAG 问答服务进行 **并发瓶颈定位与资源泄漏治理** 的
系统设计。核心目标：在**不改变检索质量**的前提下，使服务满足工单第 7 页的验收标准：

| 验收项 | 指标 |
|--------|------|
| 场景 A（20 并发问答，持续 10 分钟） | P95 ≤ 3000ms，无请求失败，内存增长 ≤10% 且无持续上涨 |
| 场景 B（10 并发混合负载，持续 10 分钟） | 服务不崩溃，解析任务正常入队并被消费，问答 P95 ≤ 5000ms |
| 资源泄漏 | 连续稳定运行 12 小时后 RSS 增长 ≤ 20% |

## 2. 系统背景与故障现象

系统在工单二完成 6 个测试问题 100% 准确率后进入试运行，当模拟 10+ 用户并发时出现：

1. **响应延迟飙升**：问答接口平均响应时间从约 2s 陡增至 10s 以上；
2. **内存泄漏与崩溃**：容器内存随运行时间持续增长，数小时后触发 OOM Killer，服务崩溃重启；
3. **GPU/资源利用不当**：仅文本问答（未重解析文档）时资源也被大量占用且释放不及时。

## 3. 总体架构设计

### 3.1 生产拓扑（RAGFlow 等价实现）

工单要求以 `docker-compose` 部署「API Server + Task Executor + 向量数据库 + Redis」完整拓扑。
本工程采用等价拓扑（详见 `部署/docker-compose.yml`）：

```
        并发用户 / 压测端（JMeter / tools/loadtest.py）
                       │
              ┌────────▼─────────┐
              │   API Server     │  FastAPI · async def · uvicorn workers=1
              │  (无状态，可扩展) │  单例引擎 / 连接池 / 有界缓存 / 并发信号量
              └───┬──────────┬───┘
     上传（异步入队）│          │ 检索+生成（限流）
              ┌───▼───┐   ┌──▼───────────────┐
              │ Redis │   │  向量库 vector_db │  emb_*.npy + inverted_index.pkl
              │ 队列  │   │  Ollama 本地模型  │  bge-m3 嵌入 · deepseek-r1 LLM
              └───┬───┘   └──────────────────┘
              ┌───▼─────────────┐
              │  Task Executor  │ 解析 worker 池（2 worker + parse_sem=2）
              └─────────────────┘
                       │
              Prometheus /metrics ──► Grafana（性能与资源监控面板）
```

> 沙箱环境无 Docker/Redis 时，队列自动回退到进程内内存队列（接口完全一致），
> 保证「离线可复现跑通」；生产环境配置 `REDIS_URL` 即切换为 Redis 队列。

### 3.2 分层职责

| 层 | 组件 | 职责 |
|----|------|------|
| 接入层 | `api/app_optimized.py` | 异步端点、请求限流、指标埋点 |
| 治理层 | `service/resources.py` | 单例容器、连接池、有界会话缓存、信号量 |
| 执行层 | `service/executor.py` | 解析 worker 池、异步消费、知识入库 |
| 队列层 | `service/queue.py` | Redis/内存统一任务队列 |
| 检索层 | `src/*` | 向量+BM25 混合召回、重排、答案合成 |
| 观测层 | `service/metrics.py` + `tools/monitor_resources.py` | Prometheus 指标 + 进程外采样 |

## 4. 缺陷根因设计（基线版）

基线版 `api/app_baseline.py` **刻意保留** 工单描述的 4 类缺陷，用于基准压测与根因定位：

| 编号 | 根因 | 代码位置 | 复现方式 |
|------|------|----------|----------|
| 瓶颈一 | 文档解析与模型加载重复初始化 | `_reload_index_per_request()` | 每请求重读向量/切片并重建 `QAEngine`（≈2.5s 固定开销） |
| 瓶颈二 | 请求处理无队列 / 限流 | `chat_completions` / `upload_document`（同步 `def`） | PDF 解析在请求线程内同步执行（数十秒），高并发请求堆积 |
| 泄漏点一 | 全局缓存 / 会话未释放 | `_SESSIONS` / `_LEAKED_TENSORS` / `_PARSE_ARTIFACTS` | 无界会话字典 + 每请求留存召回向量快照 + 解析产物累积 |
| 泄漏点二 | 连接池泄漏 | 每请求 `requests.Session()` 从不 `close()` | `_LEAKED_SESSIONS` 持有引用 → 套接字/句柄泄漏 |

> **容器内存约束模拟**：工单备注 2 建议用 `docker run --memory` 暴露问题。本机无 Docker，
> 基线以进程内看门狗等效模拟 OOM Killer：RSS 超限（默认 3072MB）即 `os._exit(137)`，
> 复现「持续泄漏下被内存限制杀死、服务崩溃重启」的真实现象。

## 5. 优化设计（优化版）

针对 4 类缺陷逐一治理（详见 `优化/优化报告.md`）：

### 5.1 资源池化与单例（治理瓶颈一）

- `ResourceManager.instance()`：进程内唯一资源容器；
- `engine()`：`QAEngine` 单例 + 启动预热一次（分词/检索器/向量），请求零重复初始化；
- 查询编码走 **有界 LRU 缓存**（`EMBED_CACHE_MAX=2048`），热门问题零 Ollama 开销。

### 5.2 请求链路异步化与限流（治理瓶颈二）

- 端点改为 `async def`，阻塞检索经 `run_in_threadpool` 卸载，事件循环不被阻塞；
- `Semaphore(QUERY_CONCURRENCY=8)` 限制在飞检索并发，避免资源争用；
- 上传请求**立即入队**返回 `task_id`，由 `TaskExecutor` 后台消费，API 不阻塞。

### 5.3 有界缓存与清理（治理泄漏点一）

- `BoundedSessionStore`：LRU + TTL（容量 512 / 1800s），后台线程定时 `purge_expired()`；
- 解析中间产物用后即弃，不再进入全局容器。

### 5.4 连接池复用（治理泄漏点二）

- 共享 `requests.Session` + `HTTPAdapter`（`pool_connections=32` / `pool_maxsize=64`），
  经 `set_session()` 注入 `src.embedding`，Ollama 调用全部复用连接并归还。

### 5.5 可观测性（产出物要求）

`/metrics` 暴露：请求计数、延迟直方图（P50/P95/P99）、在飞请求、RSS、**私有提交内存 commit**、
队列深度、任务计数。配套 `tools/monitor_resources.py` 进程外采样 USS/CPU/线程/句柄，
`部署/grafana/rag_dashboard.json` 提供对比面板。

> **为何引入 commit 口径**：Windows 下 RSS（工作集）受系统回收影响，泄漏曲线会失真；
> 私有提交内存（commit）不受回收影响，作为泄漏判定核心依据更稳健。

## 6. 关键设计权衡

| 决策 | 取舍 | 理由 |
|------|------|------|
| 单进程内嵌 Executor（而非独立容器） | 简化部署 vs 隔离性 | 沙箱无 Docker；`service.executor` 支持独立进程模式，生产可拆分 |
| 内存队列回退 | 无跨进程解耦 vs 离线可跑 | 接口一致，配置 `REDIS_URL` 即启用 Redis |
| 信号量限流而非无限并发 | 峰值吞吐受限 vs 稳定性 | 保护下游 Ollama/向量库，换取 P95 稳定达标 |
| commit 作为泄漏口径 | 与 RSS 略有差异 vs 抗干扰 | 规避工作集回收导致的误判 |
