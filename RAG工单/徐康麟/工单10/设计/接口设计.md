## 1. 端点总览

| 路径 | 方法 | 用途 | 成功码 | 失败码 |
| --- | --- | --- | --- | --- |
| `/api/v1/ask` | POST | **金融问答（核心）** | 200 | 422 参数错 / 502 生成后端不可用 / 503 未就绪或索引缺失 / 500 处理失败 |
| `/health` | GET | 健康检查（容器层 + 业务层全量） | 200（诚实报告子项） | — |
| `/healthz` | GET | 存活探针（不碰索引，容器 HEALTHCHECK 用） | 200 | — |
| `/readyz` | GET | 就绪探针（索引必须可用） | 200 | 503 |
| `/metrics` | GET | Prometheus 文本指标 | 200 | 404（`DEPLOY_METRICS_ENABLED=0`） |
| `/api/v1/index` | GET | 索引元信息（块数/维度/模态分布） | 200 | 503 |
| `/api/v1/retrieve` | POST | 只检索不生成（诊断用） | 200 | 503 / 500 |
| `/api/v1/sessions` | GET | 会话列表（容器间共享的可观测证据） | 200 | 503 |
| `/api/v1/sessions/{session_id}` | GET | 指定会话多轮历史 | 200 | 404 / 503 |
| `/` | GET | 服务信息（版本/端口/后端/会话统计） | 200 | — |
| `/docs`、`/openapi.json` | GET | FastAPI 自带文档与契约 | 200 | — |

**共 10 条业务路径**（含 `/docs`、`/openapi.json` 则为 12 个 URL），实测 `openapi.json` 里 `paths` 键数 = **10**。

## 2. `POST /api/v1/ask`（核心接口）

### 请求体

```json
{
  "question": "平安银行2019年年度报告中，报告期末的资产总额是多少？",
  "session_id": "user-42",          // 可选；相同 id 即构成多轮对话
  "lang": "auto",                    // auto | zh | en
  "top_k": 5,                        // 可选，1~20；默认取 RAG_RETRIEVAL__TOP_K
  "with_evidence": false             // 可选；true 时返回证据块（响应体更大，诊断用）
}
```

校验规则（`pydantic` 模型，实测 422 场景）：
`question` 非空且 ≤2000 字符、`lang ∈ {auto,zh,en}`、`top_k ∈ [1,20]`。

### 响应体（字段与工单7 的 `Answer` 对齐）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `question` | str | 回显问题（便于日志对齐） |
| `answer` | str | **答案正文**；拒答时为配置的 `unknown_text`（默认「不清楚」） |
| `refused` | bool | 是否拒答。**拒答是正确行为，HTTP 仍是 200** |
| `refusal_reason` / `refusal_detail` | str? | 拒答原因（向量余弦不足 / 关键词覆盖不足 / 主体闸门…） |
| `citations[]` | list | 引用块：`corpus` / `page` / `modality` / `chunk_id` |
| `cited_pages[]` | list[int] | 引用页码（与 `citations` 的 page 集合自洽，测试有断言） |
| `latency_ms` | dict | 分段耗时：`retrieve` / `generate` / `first_token` / `total` |
| `backend` / `model` | str | 实际后端与模型（如 `ollama:qwen2.5:3b` / `extractive:rule-based`） |
| `generation_method` | str | `llm` 或 `rule_composer`（降级路径会体现出来） |
| `language` | str | 实际走的语言链路 |
| `trace_id` | str | 链路追踪 id（与 `部署/日志/app.log`、`rag_trace.jsonl` 对得上） |
| `session_id` | str? | 实际落库的会话 id |
| `cache` | dict | `{"hit": bool}` |
| `chunks[]` / `evidence[]` | list | 检索命中块（`evidence` 仅在 `with_evidence=true` 时填充） |
| `session_turns` | int | **本轮之后的会话总轮数**（多轮计数，测试断言 1→2→3） |
| `session_backend` | str | 会话后端：`redis+file` / `file`（容器间共享状态的可观测点） |

### 真实响应样例（节选，完整见 `测试/测试数据/问答接口-真实问题-A1.json`）

```json
{
  "question": "平安银行2019年年度报告中，报告期末的资产总额是多少？",
  "answer": "……资产总额 3,939,070 ……",
  "refused": false,
  "cited_pages": [ … ],
  "latency_ms": {"retrieve": …, "generate": …, "total": …},
  "generation_method": "llm",
  "trace_id": "…",
  "session_turns": 1,
  "session_backend": "file"
}
```

> 注：具体数值以 `测试/测试数据/` 下的真实 JSON 为准（本文档不复制易过期数字）。

## 3. 三档探针的语义（**这是编排能不能正确摘流量的关键**）

| 探针 | 语义 | 是否碰索引 | 返回 |
| --- | --- | --- | --- |
| `/healthz` | **进程存活** | ❌ 不碰 | 恒 200 + `{status:"alive", pid, uptime_s}` |
| `/health` | **健康全量** | ✅ 碰（但失败也 200） | 恒 200；`status: ok\|degraded`，`ready: bool`，逐子项 `ok` + 原因 |
| `/readyz` | **就绪（可接流量）** | ✅ 碰 | 就绪 200；索引不可用 **503** |

**为什么要分三档**：基座实测冷启动 **27.3 秒**（全文索引构建 20.1 s）。
若容器 HEALTHCHECK 直接探 `/health`（要读索引），启动期必然连续失败 → 编排误判不健康 → 重启循环。
因此容器 HEALTHCHECK 探 `/healthz`，而"能不能接流量"交给 `/readyz`。

### `/health` 的子项结构

```json
{
  "status": "ok",
  "ready": true,
  "work_order": "人工智能NLP-RAG 项目-金融问答系统部署",
  "api_version": "1.0.0",
  "build_ref": "local-1.0.0",
  "port": 8200,
  "uptime_s": 128.4,
  "init_ms": 26488.05,
  "runtime_db": "…/runtime/qa_runtime.sqlite3",
  "checks": {
    "volume_logs":     {"ok": true, "path": "…", "detail": "可读写"},
    "volume_sessions": {"ok": true, "path": "…"},
    "volume_index":    {"ok": true, "path": "…", "entries": 7, "sample": [...]},
    "volume_uploads":  {"ok": true, "path": "…"},
    "volume_runtime":  {"ok": true, "path": "…"},
    "session_store":   {"ok": true, "backend": "file", "file": {...}, "redis": {...}, "degraded_reason": "…"},
    "engine":          {"ok": true, "status": "ok", "checks": {"index": {...}, "llm": {...}, "index_meta": {...}}}
  },
  "warmup": { "index_chunks": 8847, "elapsed_ms": 27286.43, ... }
}
```

**设计原则：健康检查不撒谎。** 任何未就绪项都带 `ok:false` + **原因字符串**，
绝不出现"报告健康但其实用不了"的情况。Redis 不可用时 `session_store.backend=file`
且 `degraded_reason` 写明原因（实测：`未安装 redis 客户端（ModuleNotFoundError: redis）`）。

## 4. `/metrics` 指标口径

Prometheus 文本格式（`text/plain; version=0.0.4`），供 compose 里的 prometheus 抓取：

| 指标 | 类型 | 含义 |
| --- | --- | --- |
| `rag_api_requests_total` | counter | HTTP 请求总数（中间件累加） |
| `rag_api_errors_total` | counter | 4xx/5xx 总数 |
| `rag_api_ask_total` | counter | 问答请求总数 |
| `rag_api_refused_total` | counter | 拒答数（护栏触发次数） |
| `rag_api_ask_latency_ms_sum` / `_count` / `_max` / `_avg` | summary | 问答耗时分布 |
| `rag_api_uptime_seconds` | gauge | 进程存活秒数 |
| `rag_engine_asked_total` / `rag_engine_cache_hit_total` | counter | 引擎内部统计 |

> 这套指标口径同时给 **工单17（并发瓶颈与泄漏）** 复用，避免两套口径对不上。

## 5. 中间件与横切关注点

| 关注点 | 实现 |
| --- | --- |
| 请求追踪 | 读 `x-request-id` 或生成 16 位 hex；回写响应头 |
| 耗时观测 | 响应头 `x-process-time-ms`；同时写 JSON 日志 |
| 结构化日志 | `/healthz`、`/metrics` 不记（避免探针刷日志）；其余每请求一行 `http.request` |
| 异常兜底 | 全局 `exception_handler(Exception)` → 500 JSON（**不裸崩、不吐栈给调用方**）+ ERROR 日志 |
| 生命周期 | `lifespan` 里初始化引擎（同步阻塞，一次性）；退出时关 sqlite 连接 |

## 6. 与工单7 原 Web 界面的关系

| 入口 | 端口 | 协议 | 用途 |
| --- | --- | --- | --- |
| **本工单 FastAPI** | 8200 | `POST /api/v1/ask`（JSON） | **对外正式 API**：给程序调用、可被网关/压测工具直接打 |
| 工单7 Web 界面 | 8201 | `http://…/` 表单 + `POST /api/ask` | 人机对话 UI（浏览器直接用） |

两者**共享同一份 `QAEngine` 与同一份索引卷、会话卷**，不复制业务逻辑
（`rag-ui` 就是同一镜像换 `command` 起 `main.py --serve`）。
