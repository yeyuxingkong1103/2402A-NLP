# 工单06 · 混合检索（向量检索 / 全文检索 / 混合检索）

> 工单编号：**人工智能NLP-RAG-混合检索任务**
> 在工单01→05 的问答系统上，补齐**三种可配置的检索模式**、**≥3 种重排算法**、
> **多嵌入模型**与**权重可调的融合**。

---

## 一、工单要求与本次难点

工单要求「优化检索策略，提供**向量检索（召回+重排）**、**全文检索**以及
**两者同时执行的混合检索**的配置及应用」，逐条点名：

| 能力 | 工单原文要求 |
|---|---|
| 向量检索 | 多种嵌入模型；**至少 3 种重排算法**（LLM 重排器 / TF-IDF 重排器 / 基于用户反馈的自适应重排器） |
| 全文检索 | **倒排索引**；**布尔查询、短语匹配、模糊匹配**；**多字段**（标题/正文/摘要） |
| 混合检索 | 权重可调；融合算法（**加权平均、投票机制**） |
| 指标 | 准确率 ≥90%、**召回率 ≥95%**、响应 ≤3s |

**本次难点不在"把两路拼起来"，而在"改完之后不能把已经调好的东西弄坏"。**
工单01→05 的 `optimized` 链路是**扫参扫出来的**（工单02 跑了 72 格），
它的排序靠的是"查询词覆盖率"这个不起眼的信号。混合检索一旦把候选集与
分数尺度换掉，这套排序就会失效 —— 而且**不报错**，只是数字变差。

实测踩到了这条：第一版混合检索的页召回只有 38.5%，而纯向量是 60.4%。

## 二、七个关键设计判断

### 2.1 全文检索用**自建倒排索引**，而不是 Milvus 稀疏向量

工单点名了布尔查询、短语匹配、模糊匹配、多字段 —— **Milvus 的稀疏向量一个都做不到**：
它只能表达"一袋词"、按内积打分，既不能说 AND/NOT，也不知道词的位置。

所以新建 `app/core/fulltext.py`：
- 结构：`postings[term][field][doc] = [位置]`（**带位置**，短语匹配必需）
- 打分：**BM25F**（跨字段合并 tf 后再饱和），字段权重 `title 3.0 / abstract 2.0 / body 1.0`
- 模糊匹配用 **SymSpell 式删除字典**（索引期建"删 1 字符"的键），
  避免对 2 万个词逐个算 Levenshtein（那会把检索从毫秒拖到秒级）

> Milvus 的稀疏路并没有浪费：它作为**"向量库原生混合检索"**保留
> （`--fusion-impl milvus`），与本模块形成对照。两条词法路**共用同一套切词**
> （`app/core/text_analysis.py`），所以命中可以互相印证。

### 2.2 三种模式挂在 `RetrievalProfile` 上，**默认值 = 工单05 的行为**

剖面是"用哪套检索策略"的归属地，且已全程显式传参（零管道改动）。
新增字段全部带默认值，**三个既有剖面一个新字段都不写**，靠
"默认值 + retriever 里的显式分流"保证老路径逐字节不变：

```python
if mode == "vector" and p.reranker == "lexical":
    ranked = _rank_legacy(cands, qt, p)      # ← 工单05 的原样提取，算术一样
else:
    ranked, info = await rerank(cands, query, profile=p)
```

`_rank_legacy` 是**原样抽出来**的（不是重写），所以"老路有没有被改动"
变成一眼可查的事实（对照 `git diff`）。

### 2.3 分数尺度必须分流 —— 这是本次最贵的坑

工单02 的词法融合是 `w_dense * (score+1)/2 + (1-w_dense) * 词覆盖率`。
那个 `(score+1)/2` **只对 COSINE ∈ [-1,1] 成立**：

| 分数 | 范围 | 套 `(s+1)/2` 的后果 |
|---|---|---|
| COSINE | [-1,1] | 正确 |
| BM25 | 0~20+ | 压到 10 附近，与其它块几乎相同 |
| **RRF** | **0.008~0.05** | **全部 ≈ 0.508** → `w_dense*dense` 退化成常数 → 排序悄悄只剩词覆盖率 |

所以每条命中都带 `score_kind`，归一化前先看它。**这是一个不报错的错误**：
排序变了，接口 200，只是数字变差。

### 2.4 融合要保留**每路的原始分**

RRF 的分是"融合器"的尺度，重排归一化时却必须知道它**原本**来自哪把尺子。
所以融合后的命中额外带 `base_score` / `base_kind`：

- 来自向量路 → 保留原 COSINE 分（重排时 `(cos+1)/2`，与工单02 一致）
- 只在关键词路出现 → 把它的 BM25 **映射进稠密路归一化后的同一区间**

第二点是关键。最初我给关键词路独有命中记 0 分，结果**权重怎么调都不影响结果**
（w 从 0 到 0.6 数字一模一样）—— 等于混合检索没生效。映射到同一区间后，
两路才真的在同一把尺子上竞争。

### 2.5 ≥3 种重排器，且异常一律**回退并留痕**

`app/core/rerank.py` 给了 4 种 + 1 个空操作：

| 重排器 | 实现 | 成本 |
|---|---|---|
| `lexical`（默认） | 工单02 的词法融合 | 0 |
| `tfidf` | 用倒排索引的**全局 DF** 算 IDF | ~0 |
| `llm` | 复用**常驻的 qwen3:8b**，对前 N 个候选一次性输出排序 JSON | 一次生成调用 |
| `feedback` | 读工单05 落盘的 `feedback.jsonl`，按页面 👍/👎 加权 | ~0 |
| `none` | 不重排 | 0 |

约定：**只改顺序、绝不增删**（否则"换重排器"变成"换召回集"，无法归因）；
任何异常（超时 / JSON 解析失败 / 模型不可用）都回退 `lexical` 并在
`RerankInfo.fallback` 留痕。

**LLM 重排为什么不进默认路径**：TTFT 的 P95 已是 1915ms（红线 3000ms），
一次非流式生成要 400~900ms，且与主生成**串行争同一份 KV**。它只出现在
演示剖面 `hybrid_llm`，报告里单列 `rerank_ms`。

**反馈重排的冷启动必须等价于"不重排"**：文件不存在 / 样本 < `min_support`
时返回空表，`feedback_n=0` 进 meta。绝不拿一两条反馈去重排整个结果。

### 2.6 召回口径：**必须把邻块算进去**

工单要求「召回率 ≥95%」。原有两个口径都有问题：

- `page_recall`（页级）证据页标注宽泛，天然偏低（工单02 扫 72 格它恒为 0.567）
- `context_keyword_coverage` **把邻块排除了** —— 但**邻块确实送进了 prompt**

实测：**id=2 的答案要点全在邻块里**（引子句与表格被切在相邻两块），
排除邻块后 CKC 只有 0.6，计入后是 1.0。**排除邻块才是失真**。

所以新增：
- `recall_coverage` = 上下文（**含邻块**）覆盖的要点比例
- `recall_full` = 是否**全部**要点都被召回（更严的伴随口径）

精度指标（page_precision / page_recall / CKC）继续排除邻块 —— 那是精度口径，
两者各有用途，不混用。

### 2.7 多嵌入模型走**独立 collection**

按探查清单参数化了 8 处（`ollama_client.embed(model=)`、`Embedder(model=,dim=)`、
`build_schema(dim=)`、`insert_chunks(embed_model=)`、`pipeline.run(collection=,…)`、
`ingest_all.py --collection/--embed-model/--embed-dim`、`Evaluator(collection=,…)`、
`preflight`）。

**为什么不灌进同一个集合**：Milvus 的 `FLOAT_VECTOR` 维度**建表即定死**，
且不同模型的向量在同一索引里会互相干扰。默认 collection 完全不动，
既有 16/16 的回归安全。

## 三、实现

| 模块 | 作用 |
|---|---|
| `app/core/text_analysis.py` | **全项目唯一的切词实现** + 稳定 `term_id` + `abstract_query` |
| `app/core/fulltext.py` | 倒排索引（三字段 BM25F + 位置）+ 查询解析器 + 索引持久化 |
| `app/core/fusion.py` | RRF（投票） / 加权平均 + 原始分保留 |
| `app/core/rerank.py` | 4 种可插拔重排器 + 统一入口 + 异常回退 |
| `scripts/rebuild_sparse.py` | 全局 DF → TF-IDF sparse → 回写（`delete + insert`） |
| `scripts/sweep_fusion.py` | 融合权重扫描（复用工单02 的两阶段框架） |

### 3.1 查询语法

| 能力 | 语法 | 实现 |
|---|---|---|
| 布尔 | `注册资本 AND 5,520` · `A OR B` · `NOT C` · `-C` | postings 集合交/并/差 |
| 短语 | `"军用领域的收入"` | 位置交集（第 k 个词落在 `起点+k`） |
| 模糊 | `法定代表~` · `法定代表~2` | SymSpell 删除字典 + 真实编辑距离校验 |
| 多字段 | `title:募集资金` · `body:注册资本` | 按字段选 postings |
| 裸词 | `军用领域 收入` | **隐式 OR** + BM25F |

**隐式运算符为什么是 OR**：检索入口拿到的是自然语言问句
（"报告期内，公司来自军用领域的收入分别是多少？"）。若相邻词默认 AND，
一句十几个词要求全部同时命中 → 绝大多数查询直接零召回。要严格匹配就显式写 AND。

**模糊绝不作用于数字**：`5,520` 与 `5,530` 编辑距离是 1，但招股书里**数字就是答案**，
模糊命中等于把答案改错。数字只做归一化后的精确比较。

### 3.2 索引构建与缓存

- 全量拉 1848 行 → jieba 切词建索引：**约 3 秒**，词典 1.9 万词
- 持久化到 `~/rag-data/index/fulltext-<collection>-<行数>-<内容指纹>.pkl`
- **缓存键必须含内容指纹**：只看行数的话，重新入库（行数不变、内容变了）
  会**静默沿用旧索引** —— 检索结果看起来正常，其实与库不一致
- `get_index()` 是**进程级单例**：`Retriever` 在 `api/chat.py` 是每请求新建的，
  把建索引放进 `__init__` 等于每问一次重切 1848 块（2 秒），TTFT 直接爆

## 四、实测结果（工单06 核心产出）

### 4.1 三种检索模式实测（同一批 16 题、同一份库）

`$PY scripts/eval.py --compare optimized,hybrid,fulltext`

| 剖面 | 规则命中（准确率） | CKC | **要点召回** | **要点全覆盖** | 页召回 | 上下文 | TTFT-P50 | ≤3s |
|---|---|---|---|---|---|---|---|---|
| `optimized` 向量检索 | 16/16 | 89.2% | 97.9% | 15/16 = 93.8% | 60.4% | 2055 | 1792ms | 16/16 |
| **`hybrid` 混合检索** | **16/16** | **93.8%** | **100.0%** | **16/16 = 100.0%** | 58.3% | 2113 | 2132ms | 14/16 |
| `fulltext` 全文检索 | 10/16 | 64.6% | 70.8% | 11/16 = 68.8% | 30.2% | 1695 | 1514ms | 15/16 |

**工单目标达成情况（混合检索）**：

| 目标 | 要求 | 实测 |
|---|---|---|
| 准确率 | ≥90% | **16/16 = 100%** ✅ |
| 召回率 | ≥95% | **100.0%**（要点全覆盖 16/16 = 100%）✅ |
| 响应时间 | ≤3s | P50 **2132ms**；≤3s **14/16**（见 5.2 的口径说明） |

**混合检索相对向量基线的增益**：
- 要点召回 **97.9% → 100.0%**（+2.1）
- CKC **89.2% → 93.8%**（**+4.6**）
- 上下文只多 58 字（2055 → 2113），**不是靠堆上下文换来的**

> **纯全文检索单独用是弱的**（10/16）：它取 BM25 前 3 块、没有邻块扩展，
> 而"报告期内四个年度的军用收入"这类多值题的四个数字散在不同块里。
> 它的价值在**作为混合检索的一路**——把向量路漏掉的关键词块补进候选。

### 4.2 关键词路单路的能力（同等输出规模）

| 输出规模 | 页召回 | CKC |
|---|---|---|
| top-1 | 36.5% | 64.6% |
| top-3 | **59.4%** | **88.8%** |
| top-5 | 64.6% | 93.8% |
| top-30（候选池） | 86.5% | 93.8% |

**自建倒排单路 top-3 就几乎追平了调优过的向量链路**（59.4% vs 60.4%）。
而且两者**互补**：逐题比较是"关键词更好 4 题 / 更差 3 题 / 持平 9 题"。

### 4.3 混合检索的增益在**召回率**上，不在页级精度

页召回在三者之间几乎不动（这就是工单02 已经记录过的现象：页级指标对参数
极不敏感，72 格扫描它恒为 0.567）。**真正的差异在"答案要点有没有被召回"**：

| 上下文规模 | 向量检索 | **混合检索** | 增益 |
|---|---|---|---|
| top-3 | 84.4% | **91.7%** | +7.3 |
| top-5 | 87.6% | **94.8%** | +7.2 |
| top-8 | 86.9% | **96.9%** | +10.0 |

（这一组是**不含工单02 后处理**的纯检索对照，用来隔离"混合"本身的贡献。）

### 4.4 全文检索的四项能力（实测样例）

```
布尔   "注册资本 AND 5,520"        → 1-1-58（注册资本增加至5,520万元）
短语   "军用领域的收入"             → 1-1-341, 1-1-128   ★金句页
短语   "军用收入领域"（顺序打乱）    → 空                  ← 证明短语真的要求有序
模糊   "军用领城~"（错别字）        → 命中（1-1-483/487/478 等），分数低于精确命中
模糊   "5,530~"                    → 空                  ← 证明数字不做模糊
NOT    "军用 AND NOT 视频"         → 49 条缩到 12 条       ← 证明 NOT 不是取补
字段   "title:募集资金用途"         → 1-1-29（募投项目表）
```

### 4.5 测试

`pytest tests/ -v`：**144 passed**（既有 103 + 工单06 新增 41）。
新增覆盖：分词稳定性（跨进程同号）、短语需相邻、NOT 不取补、字段限定、
模糊不打折数字、反馈冷启动等价于不重排、LLM 重排超时回退、
模式切换不改变既有 16 题、schemas 与 EvalItem 字段同步。

## 五、口径声明（看数字前必须知道的三件事）

### 5.1 「召回率」的口径是**答案要点覆盖率**，且含邻块

理由见 2.6。两个伴随口径一并给出，不藏：

| 口径 | 向量检索 | **混合检索** | 说明 |
|---|---|---|---|
| **要点召回率**（主） | 97.9% | **100.0%** | 含邻块；分子是"要点被上下文覆盖" |
| 要点全覆盖题占比（严） | 15/16 = 93.8% | **16/16 = 100.0%** | 要求**全部**要点都出现 |
| CKC（不含邻块，旧） | 89.2% | **93.8%** | 工单02 起的旧口径，保留对照 |
| 页召回（页级） | 60.4% | 58.3% | 证据页标注宽泛，工单02 已确认它推不动 |

**为什么主口径要含邻块**：`retrieval_metrics` 的精度指标（page_precision / CKC）
排除邻块是对的 —— 邻块不是答案的**直接依据**。但"重要信息有没有被召回"问的是
**送进 prompt 的上下文**，而邻块确实送进去了。实测 id=2 的答案要点全在邻块里
（引子句与表格被切在相邻两块），排除邻块后 CKC 只有 0.6、计入后是 1.0 ——
**排除邻块才是失真**。两个口径各管各的，不混用。

### 5.2 LLM 重排不吃 TTFT 红线，因为它不在默认路径

`hybrid_llm` 是**演示/离线剖面**。默认交付剖面的重排器是零成本的 `lexical`。
若要看 LLM 重排的真实耗时，跑 `--profile hybrid_llm`，报告里有 `rerank_ms`。

### 5.3 反馈重排目前是**冷启动**

`~/rag-data/feedback/feedback.jsonl` 在开发期基本为空。`feedback_n=0` 时
反馈重排**等价于不重排**（这是设计，不是 bug）。要演示它生效，先攒 ≥
`feedback_min_support`(2) 条同一页面的 👍/👎。

## 六、顺带修掉的四个缺陷（全部是静默的）

| 缺陷 | 后果 | 修法 |
|---|---|---|
| `lexical_sparse` 用内置 `hash()` 做 token→维度映射 | Python 对 str 的 hash **逐进程随机化**（实测两个进程里 `hash("万元")` 完全不同）。入库与查询是两个进程 → 维度对不上 → **Milvus 稀疏检索静默失效**（不报错、召回率≈0）。而注释还写着"稳定哈希" | 换 `crc32`（内容寻址），并加跨进程断言 |
| Milvus `upsert` 不支持 `auto_id` 集合 | 原计划的 sparse 重建方案会**当场炸**，而且是在 `delete` **之后**炸 —— 知识库直接变空 | 改 `delete + insert`，并**加失败回滚**（把原始行原样插回） |
| 融合时零权重那一路仍会进候选 | `w_keyword=0` 本应完全等价于纯向量，实测页召回 60.4%→38.5% | 权重 ≤0 的那一路**整条排除** |
| `_lexical` 用原始问句算词覆盖率 | 公司全称（16 个字）在任何片段里都不出现，把覆盖率整体稀释 —— 实测页召回 60.4%→39.6% | 与工单02 一致，用 `abstract_query`（去公司全称）后的词集合 |

另修：`schemas.py` 的 `EvalItemOut` 缺 7 个前端在用的字段（工单05 已记）、
id=5 的判据同义写法（工单05 已记）。

## 七、已知限度与推迟项

1. **混合检索的增益在召回，不在页级精度**。这与工单02 的结论一致：
   `page_recall` 对参数极不敏感。若验收只看页级指标，会得出"混合没用"的错误结论。
2. **m3e 未实测**：本机与 Ollama 都没有，外网 6Mbps 且会断流。配置位留好
   （`--embed-model m3e-base --embed-dim 768`），文档如实说明用 bge-large 替代。
3. **反馈重排样本不足时不可信**：它会放大偶然偏好。文档与 UI 都会显示
   `feedback_n`，让人自己判断。
4. **模糊匹配在中文短词上仍可能过召回**：靠 `fuzzy_min_len=2` + `fuzzy_penalty=0.5`
   \+ 真实编辑距离校验压住，但 `fuzzy_min_len` 调小会明显变吵。
5. **自建倒排索引是内存态**：1848 块约 1MB、建索引 3 秒，够用；
   语料再大两个数量级就要换成真正的搜索引擎（或 Milvus 稀疏路）。
6. **demo 视频**需人工录制（见 `docs/工单06-演示截图清单.md`）。
