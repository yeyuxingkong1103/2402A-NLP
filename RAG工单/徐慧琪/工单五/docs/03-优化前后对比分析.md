## 一、三方对比口径（先说清「优化前」到底是什么）

| 对比臂 | 是什么 | 输入 |
| --- | --- | --- |
| **工单5 多轮系统** | 本工单交付的系统 | 每轮原始问题 **+ 会话对话状态**（焦点公司 / 上一信息点 / 历史窗口） |
| **工单3 单轮系统**（优化前） | 只读子进程调用 `D:\xinzg6\zy-gq\工单3` 的 `rag.ask`，用其自己的 collection `zhaogu_v3_table` | 每轮**原始问题**，逐轮独立，**不带任何对话状态**（它的 API 也没有多轮入口） |
| 纯 LLM（下界对照） | 本机 `qwen2.5:3b`，无检索、无历史 | 每轮原始问题 |

三点口径说明（不说清，数字没有意义）：

1. **喂给工单3 的是原始跟进句**（「他…」「这个公司…」「那 XX 呢？」），
   **不是**先替它改写再喂。这是它作为「优化前」的真实能力边界，**不是把它做残**。
2. **时延口径对等**：工单5 有 `rag.warmup()`，基线也补了一条**结果整条丢弃**的预热题
   （实测该题耗时 **28,294ms**，即工单3 的进程冷启动）。两边都是热启动后再计时。
3. `timings["total_ms"]` **已含**多轮改写延迟，直接读，**不**叠加 `rewrite["latency_ms"]`。

> ᵃ 这两轮的事实分**不是被指代拖垮的**：指代实体准确率仍是 **1.0**（`this company` →

> 模型弱点，实测提示词与定向重试都压不住（`docs/技术文档.md` §10 第 10 条）。

### 3.1 为什么有些「指代类」单轮也不输？——因为工单3 硬编码了一家公司

工单3 的 `query_rewrite.disambiguate()` 把 `该公司|本公司|公司|其|发行人|兴图新科`
**一律替换成「武汉兴图新科电子股份有限公司」**（当时只有一家公司的语料）。后果是：

- 指代**恰好指回兴图新科**时（d1 / d6 / d9），单轮系统被这处硬编码"蒙对"，
  `person_pronoun` / `zero` / `topic_back_reference` 因此都是 1.0；
- 一旦指代对象换成**第二家公司**或换成英文，它没有任何机制可用 ——
  `demonstrative_en` / `demonstrative_gai` / `ellipsis_*` 四类**全线 0.0**。

**最值得看的一条逐轮证据**（d4 第 2 轮：问「该公司」，而焦点是**力源**）：

| 系统 | 答案 |
| --- | --- |
| 工单5 多轮 | 控股股东是**赵马克**。[2]　✅ 正确 |
| 工单3 单轮 | 该公司的控股股东是**程家明**。[2]　❌ **答成了另一家公司** |

单轮系统不是"答不出"，而是**理直气壮地答错**——这正是硬编码消歧在多文档下的真实危害。
工单5 删除了这处硬编码（见 `src/query_rewrite.py`），改由**对话焦点**决定指代，
并把「改写后问题 + 焦点公司」写进缓存 key，堵住"同一句话在不同会话里答案串味"。

### 3.2 英语轮为什么有 3 轮走规则兜底（降级率 0.15）

严格口径下唯一未达标的改写是 `ellipsis_what_about_en`（`ellipsis_rule`）：
规则补全给出「武汉兴图新科电子股份有限公司的法定代表人是谁？」，实体与语义都对，
但与期望句的**措辞**不同，故严格改写准确率记 0。
同时 `指代实体准确率 = 1.0` —— **绑定的公司无一错**。
3 轮降级全部发生在英文轮：本机 3b 模型在英文约束改写上通过校验器的概率低于中文，
L4 兜底本就是为此设计的确定性路径，代价是措辞不最优，**不是答错**。

## 四、如实记录未达标项与说明

按工单要求，不挑好看的报：

1. **事实命中率未到 1.0（0.9062 = 29/32）**。3 处失分：
   - `d9 第 1 轮`（首轮完整问题「参与制定了哪个技术标准？」，1/2）：答案给出了标准
     名称（《某视频指挥系统技术规范（1.0版）》），但未提该标准由**军事科学院**牵头。
     属**答案完整度**问题，发生在**首轮直通**（`passthrough`，与多轮改写无关）；
     同一轮工单3 为 0/2（连标准名都不对）。
   - `demonstrative_en` / `ellipsis_what_about_en` 两轮（各 0/1）：见第 5 条。
   **未通过删改测试集来消除失分** —— 标准答案由需求文档定义（标准名 + 牵头单位），
   如实保留。
2. **p90 耗时 2407.1ms，比基线高 1009ms**：全部来自改写，是本工单引入的确定性成本，
   远低于 3 秒上限；但应当知道**多轮不是免费的**。
3. **引用溯源率 0.95 而非 1.0**：唯一无引用的是**对抗轮**（无历史的代词问题），
   系统按设计**明确反问**而不检索，因此没有引用——这是**正确行为**，不是缺陷。
4. **`none` 组双方都未达 1.0**（0.9524 / 0.9048）：首轮完整问题的准确率主要受检索与
   生成影响，**与多轮能力无关**；本工单未针对该组做优化，也不应把它的提升记在多轮头上。
5. **英文作答时中文专名被音译**（本轮新增的失分点，来自"修语言"）。修掉
   「英文提问回中文答案」之后，英文轮由整句中文变为英文整句，但 3B 模型把
   人名/公司名音译：`赵马克` → "Zhao Mark"、`武汉力源信息技术股份有限公司` →
   "Wuhan P&S Information Technology Co., Ltd."。事实匹配按语料中文原名判，故这两轮
   事实记 0（**指代实体准确率仍是 1.0，答案内容本身也对**）。
   **已实测两种压法都不奏效**：改 system prompt 明确要求"专有名词保留中文原名"
   （含反例）无效；把音译答案回灌 + 定向重试提示，模型逐字返回原答案。
   **取舍**：语言的优先级更高——「LLM 按提问语言回答」是需求文档的硬性要求，
   而音译是**写法**问题、不是事实错误。故保留修好的行为，把音译如实记为已知限制
   （`docs/技术文档.md` §10 第 10 条）。

## 六、结论

1. 多轮能力的净增益集中在**「指代对象是第二家公司」与「英文指代」**四类上，
   每类都是 0.0 → 1.0；在指代恰好指向第一家公司的轮次上增益为 0
   （单轮系统靠硬编码蒙对）——这反向说明**基线并没有多轮能力，只是碰巧**。
2. 多轮改写的成本是 p90 +645ms，仍在 3 秒内；准确率与可溯源性的收益大于该成本。
3. 本报告只覆盖这 20 轮；RAGAS 指标见 `docs/04-RAGAS评估报告.md`，
   5 轮验收序列的逐轮证据（含引用与组织结构图节点路径）见
   `docs/06-验收序列逐轮报告.md`。
