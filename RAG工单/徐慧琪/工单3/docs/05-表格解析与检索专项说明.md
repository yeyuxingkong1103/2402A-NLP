# 表格解析与检索专项说明（工单 03）

**工单编号：人工智能NLP-RAG-PDF文档的表格解析及检索优化**

工单要求「表格作为一等公民，不能把表格当成普通文本」。本文档说明表格在本系统中的
**识别 → 结构化 → 入库 → 检索 → 生成**全链路，以及与 01/02「整表一个块」的差异。

---

## 1. 问题：工单 01/02 的表格处理错在哪

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 表格超过 3000 字被截断（首尾保留、中间丢弃） | 长表尾部信息永久丢失 |
| 2 | 没有表头独立块 | 无法"按列名检索" |
| 3 | 没有行级 chunk | 无法定位到"哪一行"，长表内部信息检索不到 |
| 4 | HTML 未入 payload | 生成时无法还原表格结构 |
| 5 | 没有 `table_id` / `row_index` | 答案无法追溯到具体表格与行 |

工单3 的目标就是逐条消除这 5 个问题。

## 2. 表格识别

### 2.1 数据来源

MinerU 3.4.5（pipeline 后端）在 `content_list.json` 中把表格标为 `type="table"`，
字段包含 `table_body`（HTML）、`table_caption`、`table_footnote`、`page_idx`、`bbox`。

`pdf_parser.normalize_item` 做了一处关键改动：**保留原始 `table_html`**
（01/02 是把它转成 Markdown 后就丢弃 HTML）。

### 2.2 实测规模

| 文档 | 页数 | MinerU 表格块 | 可结构化 | 低质量（有 HTML 但解析不出） | 无 `table_body` |
| --- | --- | --- | --- | --- | --- |
| 招股说明书1.pdf | 548 | 502 | **389** | 9 | 113 |
| 招股说明书2.pdf | 350 | 224 | **201** | 2 | 23 |
| 合计 | 898 | 726 | **590** | 11 | 136 |

> 「无 `table_body`」的 136 个块是 PP-DocLayoutV2 把**双栏正文误判为表格**（工单2 已记录该现象）。
> 它们的页面文本由 `pdf_parser.merge_pymupdf_gap` 用 PyMuPDF 补齐，**不触发 OCR**
> ——否则会白跑上百页 OCR 且毫无增益。只有"**有 HTML 却解析不出结构**"的 11 张表
> 才是真正的表格识别失败，走 PaddleOCR-VL 兜底。

### 2.3 质量判定

`table_parser.score_table` 给出 [0,1] 质量分，四个因子加权：

| 因子 | 权重 | 含义 |
| --- | --- | --- |
| 解析成功 | 0.25 | 能解析出非空矩阵 |
| 单元格规模 | 0.20 | `min(1, 单元格数 / 6)` |
| 填充率 | 0.25 | 非空格子占比（版面误判的"表"大面积空） |
| 有效字符率 | 0.30 | 单元格平均字符数 / 阈值 |

低于 `TABLE_QUALITY_PASS = 0.55`、或单元格数 < 3、或无表头/无数据行 → 低质量。

### 2.4 PaddleOCR-VL 兜底

低质量表所在页**按页去重**后批量送 PaddleOCR-VL（独立 venv 子进程，
`PADDLE_PDX_MODEL_SOURCE=local` 强制离线）。约束：单次最多 40 页、超时 600 秒、
**任何失败都返回空且不影响主链路**。

实测（本机 RTX 4060 Laptop）：

| 文档 | 页数 | 用时 | 结果 |
| --- | --- | --- | --- |
| 招股1 | 9 | 246.1s | 9 页返回文本 → 写入 6 个兜底 chunk |
| 招股2 | 2 | 41.2s | 2 页返回文本 → 写入 1 个兜底 chunk |

> **OCR 兜底是 best-effort**：其中一次重跑时招股1 的这批返回 0 页（子进程批处理失败），
> 系统如实降级为 MinerU 的文本块，不报错、不中断建库。
> 结果会缓存到 `data/tables/<文档>_ocr_pages.json`，避免每次重建白等 4 分钟。

## 3. 表格结构化

### 3.1 HTML → 单元格矩阵

`table_parser.html_to_grid` 用正则解析 `<tr>/<td>`（MinerU 的 HTML 结构规整，
无需引入 bs4），并把 **`rowspan`/`colspan` 展开为完整矩阵**——
合并单元格的值填充到其覆盖的每一个格子。

为什么必须展开：招股书的表格大量使用合并单元格（首列跨行的分类列、两级表头）。
不展开就按 `<tr>` 取 `<td>`，**每行列数不一致**，"列名：值"全部错位。

### 3.2 表头识别与**形态判定**（本专项最重要的设计）

招股书里有两类语义完全不同的表格：

**① header 型（列式表）**

```
| 项目     | 2019年7-9月 | 2018年7-9月 | 同比变动 |
| 营业收入 | 1,918.21    | 625.12      | 206.85%  |
```

**② kv 型（字段-值表）**——招股书里极其常见，容易踩坑

```
| 发行股票类型 | 人民币普通股（A股） |
| 发行股数     | 1,670万股           |
| 发行后总股本 | 6,670万股           |
```

以及释义表：

```
| 发行人、兴图新科 | 指 | 武汉兴图新科电子股份有限公司 |
```

**如果不区分**：kv 表会被当成"首行是列名"，于是列名变成
"发行股票类型 / 人民币普通股(A股)"，**后续每一行的描述全部错位**——
「发行股数」这一行会变成"发行股票类型：发行股数 | 人民币普通股(A股)：1,670万股"，
既检索不准，喂给 LLM 也是错的。

`table_parser.detect_mode` 的判定规则：

| 优先级 | 条件 | 判定 |
| --- | --- | --- |
| 1 | 存在"连接词列"（某列 ≥60% 取值是 `指/为/：/－` 之一）且列数 ≥3 | **kv**（释义表） |
| 2 | 仅 2 列 | **kv** |
| 3 | 其余 | **header** |

规则 2 的依据：招股书的 2 列表几乎都是"字段→值"。即便真是"年度|金额"这种带表头的
2 列表，按 kv 解析得到 `年度：2018年度`、`金额：1.2亿元` 依然可读可检索，
**比把首行误当列名的风险小得多**。

实测判定结果（招股1 前 40 页样本）：

```
模式分布 (mode, ≥3列): {('kv', False): 35, ('header', True): 348, ('kv', True): 6}
```

### 3.3 表头识别的另一个坑：日期表头

财务表的表头常常是日期：`| 项目 | 2010-6-30 | 2009-12-31 | 2008-12-31 |`。

原判定逻辑用宽松正则 `[\d,\.%\-—]+` 判断"是不是数值"，而 `2010-6-30` 恰好匹配
（全是数字、点、横线）→ 表头行被判为数据行 → **列名退化成"列1/列2/列3"**。

修正：数值判定收紧为 `^-?[\d,]+(?:\.\d+)?%?$`（支持千分位、小数、百分号、负号，
但不含内部短横），日期不再被误判。

### 3.4 无标题表格：用章节标题补表名

招股2 的绝大多数表格 `table_caption` 为空，行级描述会长成
「**表：（无标题）** | 关联方名称：赵马克…」——"（无标题）"既占字数又稀释语义。

修正：`table_chunker.resolve_caption` 在 caption 为空时**回退到所属章节标题**
（`chunker.item_headings` 计算）。效果：

```
修正后：表：1、存在控制关系的关联方 | 关联方名称：赵马克 | 持股比例：42.35% | …
修正前：表：（无标题） | 关联方名称：赵马克 | 持股比例：42.35% | …
```

这一改动直接让 id 3 / id 4 的表格块被检索到，是本专项里性价比最高的一处优化。

## 4. 表格 chunk 表示

### 4.1 三类 chunk

对每张可结构化的表生成：

**① 表头块**（`table_header`，支持"按列名检索"）

```
header 型：表：关联方及关联交易 | 表头：关联方名称｜持股比例｜与本公司关系 | 页码：157
kv   型：表：本次发行概况 | 包含字段：发行股票类型、发行股数、每股面值、… | 页码：2
```

> kv 表没有列名，但把**全部字段名列出来**，等价于一张"字段清单"——
> 问"发行股数"时 BM25/向量都能命中这张表。

**② 行级块**（`table_row`，检索主单元）

```
header 型：表：四、本次发行情况 | 项目：发行股数 | 2010年1-6月：1,670万股 | 页码：22
kv   型：表：本次发行概况 | 发行股数：1,670万股 | 页码：2
```

**③ 整表**（作为前两者的 `parent_text`，并保留 `table_html` 进 payload）

### 4.2 父子结构复用既有机制

```python
parent_id   = table_id          # "招股说明书2.pdf#p1#t0"
child.text  = 行级描述           # 向量化 / BM25 的单元
parent_text = 整表 Markdown      # 送 LLM 的上下文
```

于是 `context.expand_parents` **无需特判**即可把"命中某一行"自动还原为"整张表"。
这是本工单代码量可控的关键设计。

### 4.3 元数据（工单硬要求 8 项，每个表格 chunk 都携带）

| 字段 | 说明 |
| --- | --- |
| `block_type` | `table_header` / `table_row`（降级时为 `table`） |
| `page_idx` | 页码（0 基，展示 +1） |
| `source` | `招股说明书1.pdf` / `招股说明书2.pdf` |
| `table_id` | `{source}#p{page_idx}#t{页内序号}`，文档内唯一 |
| `table_html` | 原始 HTML |
| `table_header` | 表头（`｜` 连接；kv 表为空，用 `table_caption`+字段表达） |
| `row_index` | 行号（表头块为 -1） |
| `heading_path` | 所属章节标题路径 |

另附 `table_caption`、`table_quality`、`table_n_rows`、`from_ocr`。

**内存权衡**：`table_html` 每个行级块都带一份（工单要求），全量 scroll 会把几十 MB
HTML 拉进内存，而 BM25 只用 `text`。故 `vector_store.scroll_all` 用
`PayloadSelectorExclude` 排除该字段——**落库保留、读取排除**。

## 5. 表格检索

### 5.1 链路

```
问题
 └─ 向量检索（bge-m3，行级描述 + 表头块）
     + BM25（行级块文本 + 表头 + heading_path，精确数字/专名靠它）
      → RRF 融合（k=60）
      → bge-reranker-v2-m3 精排（top-20 → 6）
      → 上下文组装：命中行 → 按 table_id 还原整表
```

### 5.2 上下文组装的两个特殊处理

| 处理 | 正文块 | 表格块 | 原因 |
| --- | --- | --- | --- |
| 同页去重 | 是 | **否** | 同一页常有多张语义不同的表（如"本次发行概况"与"募集资金运用"同页），去重会丢掉恰好命中的那张 |
| 以命中句为中心裁剪 | 是 | **否** | 表格题常需要**同一张表的多个单元格**（如"发行股数"与"发行后总股本"算比例），只给命中那一行答不了 |

表格按 `TABLE_CTX_MAX_CHARS = 2600` 整体装入。

### 5.3 精排候选数：从 4 提到 6

实测（id 3）重排分数：

| 排名 | 分数 | 块 | 内容 |
| --- | --- | --- | --- |
| 1 | 0.985 | text p11 | 释义表内容（含"关联方"等词） |
| 2 | 0.980 | text p158 | "4、公司的关联方关系图示" |
| 3 | 0.960 | text p157 | "1、存在控制关系的关联方"（**小标题，只有问题措辞、没有答案**） |
| 4 | 0.955 | text p58 | 股东委托持股说明 |
| **5** | **0.939** | **table_row p157** | **关联方名称：赵马克｜持股比例：42.35%｜与公司控股股东** ← 正确答案 |

招股书里有大量"**只含问题措辞、不含答案**"的标题块，cross-encoder 会给它们
0.95+ 的高分。`FINAL_TOP_K = 4` 时正确答案恰好被切掉；提到 **6** 后进入上下文
（`CONTEXT_MAX_CHARS` 同时从 3200 提到 3600 兜住总长）。

> 这是"表格能检索到"与"表格能进到 LLM 面前"之间的最后一公里问题——
> 不是召回问题，也不是排序正确性问题，而是**截断点**问题。

### 5.4 答案定位（可追溯到行）

`context.citation_map` 输出每个片段：

```json
{"source": "招股说明书2.pdf", "page_display": 157, "is_table": true,
 "table_id": "招股说明书2.pdf#p156#t1",
 "table_caption": "2、不存在控制关系的关联方",
 "row_indices": [3, 7]}
```

界面显示为：`招股说明书2 第157页｜表格：2、不存在控制关系的关联方（第 4、8 行）`

## 6. 生成阶段

表格片段在上下文里被显式标注并说明用法（`context.build_context` + 系统提示词）：

```
【片段2】来源：招股说明书2.pdf 第157页（第七节 同业竞争与关联交易 / 二、关联方及关联交易）【表格数据｜2、不存在控制关系的关联方】
| 项目 | 内容 |
|---|---|
| 融冰投资 | 持有公司股份5%以上的股东 |
| 力源贸易 | 同一实际控制人控制的企业 |
...
```

系统提示词对表格给出专门规则：

1. 先按表头找到问题问的那一列/那一行，再读值；
2. 表格题往往需要**同一张表的多个单元格**，都要找出来；
3. 若问题问的是未直接给出的比例/占比，**允许用表中数字做一步除法/减法**并说明依据；
4. 除该计算外不得引入表外数字。

配套地，`rag.check_numbers` 新增 `_is_derivable`：某个数字若可由上下文中的
**两个数经一步四则运算**得到（容差 0.5%），不算幻觉。这解决了 id 1
（"占发行后总股本的比例"需要 1,670 ÷ 6,670）被误判为编造的问题；
但仍只放行**一步运算**，不给编造数字开口子。

### 6.1 生成后校验 → 定向重试（一次性）

小模型（qwen2.5:3b）在表格题上有三个稳定可复现的失误模式，靠提示词约束不住，
因此都补了**确定性校验 + 一次定向重试**（只重试一次，控住 ≤3 秒预算）：

| # | 失误模式 | 校验 | 实测案例 |
| --- | --- | --- | --- |
| ① | 漏列表格行（因同属一类就合并概括） | `check_table_rows`：列举型问题下，表格首列的"行名"必须在答案里出现 | id 4：7 家企业只答了 5 家 |
| ② | 改写字号内专有名称 | `check_quotes`：答案里《…》的名称必须与片段逐字一致 | id 95：把标准全称写成简称 |
| ③ | 数字错抄（写出的数字不在片段中） | `check_numbers`：见上方"可推导"白名单 | id 260 曾把 4,627.14 写成 4,627.15 |

### 6.2 重试护栏：不得偏离问题

重试本身可能让答案**变差**——实测 id 1：首次答案把 25.04% 写成了相近的错误值，
重试后模型答到了完全无关的段落（注册资本、股权演变），而该答案"没有可疑数字"，
于是被判为"不更差"而采纳，正确答案反被顶掉。

因此重试采用需同时满足：`问题层面不更差` **且** `question_relevance ≥ 原答案 × 0.7`。
`question_relevance` 用问题的 4-gram 被答案覆盖的比例衡量，
且**先剔除公司名/别名**——公司名只是路由上下文，却占了问题的大半词面，
不剔除的话任何提到"武汉力源"的句子都能拿到虚高的相似度。

### 6.3 枚举句抽取式校正

实测 id 33：文档里存在两句**结构几乎一样**的话——

```
报告期内，公司来自军用领域的收入…占主营业务收入比重分别为 82.10%、97.31%、94.84%和 94.34%。   ← 问的是这句
报告期内，公司视频指挥控制类产品的销售收入…占主营业务收入比例分别为 78.39%、95.86%、94.37%和 91.92%。
```

模型把两句的数字混着抄（94.37%、95.86%、78.39%、94.34%）。
`complete_numeric_list` 因此增加一条：按**问题词重叠度**挑出最贴合的枚举句，
若其数字集合与答案不一致则用原文替换（原文永远比转述可靠）。

该规则需要两道闸门才安全：阈值 `≥0.45`，且最佳句须比次佳句高 40% 以上。
——阈值定成 0.25 时曾误伤 id 1（选中一段讲注册资本的枚举句，把正确回答整个替换掉）。

## 8. 降级路径（容错）

| 场景 | 行为 | 标记 |
| --- | --- | --- |
| 无 `table_html` | 整表文本块（沿用工单2 行为） | `degrade_reason="no_html"` |
| 有 HTML 但解析不出结构 | 整表文本块 | `degrade_reason="parse_failed"` |
| 解析失败 + OCR 有结果 | OCR 文本作为表格内容 | `from_ocr=true` |
| 表格结构化总开关关闭 | 全部走整表文本块 | `degrade_reason="disabled"` |

任何一条降级路径都**不会中断建库**，也不会让该表从索引中消失。
