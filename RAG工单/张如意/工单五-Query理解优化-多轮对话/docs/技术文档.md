# 工单05 技术文档：Query 理解优化

> 工单编号：**人工智能NLP-RAG-Query理解优化任务**
> 实现位置：`工单05-Query理解优化-多轮对话/src/`（调用共享库 `rag_core/query_understand.py`，未修改共享库任何代码）
> 目标：在「招股说明书 PDF 检索问答」基础上实现多轮对话，重点解决 **指代消解、省略句补全、话题继承、跨文档检索** 四类多轮理解难题，

## 二、四项 Query 理解能力

### 2.1 意图识别：规则表 + 兜底

**实现**：`INTENT_PATTERNS`（正则规则表）+ `classify_intent()`。

规则表按顺序匹配 **8 类意图**，先命中先返回：

| 顺序 | 意图 | 触发词（节选） | 检索策略含义 |
|------|------|----------------|--------------|
| 1 | 数值查询 | 多少、比例、占比、分别是、增长率 | 需要表格块 / 数字加权重排 |
| 2 | 实体属性 | 是谁、法定代表人、注册资本、成立时间 | 命中即锁定实体 + 属性 |
| 3 | 关系查询 | 关联方、控制关系、持股、子公司 | 适合 Graph RAG（工单08/09） |
| 4 | 列表查询 | 有哪些、包括哪些、列出 | 答案需穷举，召回要全 |
| 5 | 比较查询 | 对比、相比、最高、最低、负增长 | 多片段比较后生成 |
| 6 | 图表查询 | 图中、如图、图表 | 需要图像语义块参与检索（工单04） |
| 7 | 操作指令 | `^上传`、`^解析`、`^重新` | **不检索**，走操作分支 |
| 8 | 闲聊 | `^你好`、`^谢谢`、`^你是谁` | **不检索**，礼貌回复 |

**兜底**：全部未命中时返回 `事实查询`——宁可多检索一次，也不漏答。
`understand()` 中若意图为「闲聊 / 操作指令」，置 `needs_retrieval=False`，直接短路，省掉整条检索 + 生成链路（响应时间与成本双降）。

**规则优先的理由**：招股书问答的问法高度集中（「是多少 / 是谁 / 有哪些」），规则零成本、零延迟、可解释、可回归测试；只有长尾问法才需要模型兜底。

**已知边界**：规则按序匹配，`实体属性` 优先于 `关系查询`，因此「…关联方**是谁**？」会被判为实体属性（`是谁` 先命中）。测试用例中如实标注了这一点，工程上更稳的做法是把「关联方 / 控制关系」等强特征词提到最前，或改为打分制而非顺序匹配。

### 2.2 消歧：多实体检测

**实现**：`understand()` 第 6 步 + `extract_entities()`。

- 用招股书场景的实体正则 `_ENTITY_PAT` 抽取 `…有限公司 / …股份有限公司 / …集团 / …银行…` 形态的公司全称；
- 若一句话出现 **≥ 2 个公司实体** 且没有「分别 / 对比 / 区别」等限定词，写入 `ambiguity` 提示：
  `问题中出现多个实体（A、B），已按全部实体并行检索`；
- 单一实体不产生提示（避免误报打断用户）。

**消歧与指代消解的分工**：消歧回答「**问的是谁**」（多个候选），指代消解回答「**省略/替代的是谁**」（上文找回）。二者互补，共同保证检索式有明确主语。

**已知边界**：当前只做「提示 + 并行检索」，没有反问用户「您问的是哪一家？」。若接入前端，可把 `ambiguity` 渲染成澄清按钮（见「改进方向」）。

### 2.3 分解与抽象：LLM 分解 + 规则兜底

**实现**：`decompose(question, use_llm=True)`。

两级策略，先做**代价判断**再决定是否动用模型：

```
        问题长度 < 25 且 不含（并/并且/以及/同时/分别/还包括）
                        │
              ┌─────────┴──────────┐
             是                     否
              │                      │
        直接返回 [原问题]      use_llm ?
     （不调 LLM、不拆）       ┌───────┴────────┐
                             是                否
                              │                 │
                     LLM 分解（_DECOMPOSE_SYS）  规则分解 _rule_decompose
                     最多 4 个子问题             按 ？/；/并且/以及 切分
                              │                 │
                              └────────┬────────┘
                                  子问题列表
```

- **LLM 分解**：系统提示要求「每个子问题只问一件事、保留公司名与时间限定、本身简单就别硬拆、最多 4 条」，输出严格 JSON；
- **规则兜底**：LLM 不可用（无 Key / 网络异常 / JSON 解析失败）时按并列连词与问号切分，**保证降级可用**，不阻塞主流程；
- **多路检索**：`Pipeline.ask()` 检测到 `len(sub_questions) > 1` 时，逐个子问题检索，按 `chunk_id` 去重合并，避免「A 和 B 分别…」只答一半。

### 2.4 指代消解：规则快速通道 + LLM 慢通道（工单05 核心）

**实现**：`resolve_coreference(question, history)`。

```
                    ┌──────────────────────────────┐
                    │ 历史为空 或 不含指代/省略？   │
                    └──────────────┬───────────────┘
                          是 │            │ 否
                             ▼            ▼
                    原样返回（零开销）  ┌──────────────────────────┐
                                        │ ① 规则快速通道 _rule_rewrite │
                                        │   命中「那 X 呢？」句式：    │
                                        │   取上一轮问题做模板，       │
                                        │   旧实体 → {ENTITY} 占位，   │
                                        │   替换为新实体               │
                                        └──────────┬───────────────┘
                                          命中 │        │ 未命中
                                               ▼        ▼
                                     直接返回改写结果  ┌────────────────────┐
                                     （不调 LLM，<1ms） │ ② LLM 慢通道        │
                                                       │   历史(近4轮) + 问题 │
                                                       │   → 自包含问题       │
                                                       │   规则：替换指代词、  │
                                                       │   补全省略谓语、      │
                                                       │   保留全部限定条件、  │
                                                       │   只改写不回答        │
                                                       └─────────┬──────────┘
                                                         异常 │        │ 成功
                                                              ▼        ▼
                                                       回退原问题   返回改写结果
```

**两级设计的收益（为什么必须两级）**：

| 维度 | 规则快速通道 | LLM 慢通道 |
|------|--------------|-----------|
| 覆盖场景 | 「那 X 呢？」等高频省略句式 | 「他 / 这个公司 / 它」等自由指代 |
| 延迟量级 | 微秒级（纯字符串模板替换） | 一次网络往返 + 生成（秒级） |
| 成本 | 0 | 每次调用计费 |
| 失败影响 | 无 | 异常时**回退原问题**，不阻断问答 |

1. **省 LLM 调用**：工单 5 轮脚本中第 4 轮（最难的省略句补全）由规则通道零成本完成；实测断言（`query_understanding.py::规则通道零 LLM 调用`）验证改写前后 LLM 调用计数增量为 0。
2. **降延迟，满足 3 秒约束**：一次 LLM 往返通常在 1~3 秒量级，若每轮问答都叠加一次改写调用，3 秒预算会被直接吃满；规则通道把「需要消解」的轮次压缩到只在必要时付这个成本（5 轮里第 2、3 轮需 LLM，第 4 轮走规则，第 1、5 轮本身自包含、无开销）。
3. **可解释、可回归**：规则通道输出确定，能写成断言（「那武汉力源信息技术股份有限公司呢？」+ 给定历史 → 「武汉力源信息技术股份有限公司的法定代表人是谁？」），便于单元测试与答辩演示。
4. **容错**：慢通道 `try/except` 包裹，LLM 不可用时返回原问题——**降级而不是报错**，符合「高可用 / 容错机制」验收项。

**规则模板替换示例**（第 4 轮）：

```
上一轮问题（模板）：这个公司的法定代表人是谁？
提取实体        ：这个公司          → 模板化为 {ENTITY}的法定代表人是谁？
本轮新实体      ：武汉力源信息技术股份有限公司
替换结果        ：武汉力源信息技术股份有限公司的法定代表人是谁？
```

## 三、性能设计：3 秒响应时间预算

`Pipeline.ask()` 各阶段耗时均被记录在 `trace["timings"]` 中，脚本会逐轮打印并在结果 JSON 中留档。预算拆解（量级参考）：

| 阶段 | 典型量级 | 说明 |
|------|----------|------|
| Query 理解（规则通道） | < 10 ms | 第 4 轮；纯模板替换 |
| Query 理解（LLM 通道） | 0.5 ~ 2 s | 第 2、3 轮；受网络与模型影响 |
| 向量召回 + BM25 召回 + RRF 融合 | 数十 ms ~ 数百 ms | 本地嵌入模型 + 本地索引 |
| 重排 | tfidf：< 100 ms；cascade：+ 一次 LLM 调用 | `--fast` 用 tfidf 可严格压 3 秒 |
| 生成 | 1 ~ 3 s | 与答案长度、模型负载相关 |

**结论与调优手段**：

1. `--fast`（`reranker=tfidf`）可去掉重排环节的 LLM 调用，把预算留给生成；
2. `rag_core.llm` 内置磁盘缓存，评测/演示重复跑同一问题时直接命中，延迟近似为 0；
3. 规则通道命中时，第 4 轮只需「检索 + 生成」两段耗时；
4. `latency_summary()` 输出平均/最大耗时与 **3 秒达标率**，作为性能验收证据；若某轮超标，`timings` 明细可定位到具体阶段。

## 四、稳定性与容错设计

| 风险点 | 处理方式 | 代码位置 |
|--------|----------|----------|
| LLM 指代消解失败（超时/限流/无 Key） | 捕获异常 → 返回原问题，问答继续 | `rag_core.query_understand.resolve_coreference` |
| LLM 问题分解失败 | 回退规则分解 | `decompose` → `_rule_decompose` |
| LLM 重排失败 | 回退原顺序 | `rag_core.rerank.LLMReranker.rerank` |
| 单轮问答抛异常 | 记录 `error` 字段后继续下一轮，历史不丢 | `wo05_common.run_script` |
| 评估指标不可用（无嵌入模型/无 Key） | 单项指标标记不可用，其余指标照常汇总 | `run_evaluation.safe_metrics` |
| 索引未建立 | 启动前检查并给出中文提示（退出码 2） | `wo05_common.index_ready` |
| 数据文件缺失 | 明确报出缺失路径后退出 | `wo05_common.check_data_files` |

服务侧高可用由 `rag_core.api` 提供：`/api/health` 健康检查、`/api/metrics` 运行指标（请求数、P95 延迟、LLM 用量），可接容器编排探针（工单10）。

## 五、可观测性与评估口径

| 观测对象 | 输出字段 | 落盘文件 |
|----------|----------|----------|
| Query 理解结果 | 原始问题、改写后、意图、实体、子问题、歧义提示、识别方式 | `results/understanding_demo.*` |
| 每轮检索式与片段 | 改写后检索式、Top-3 片段（文档/页码/类型/分数） | `results/multi_turn_conversation.*` |
| 消融对比 | 开/关 Query 理解的检索命中率、答案准确率、失败轮次 | `results/multiturn_ablation.*` |
| RAG 指标 | Faithfulness / Answer Relevancy / Context Precision / Context Recall / Answer Correctness | `results/evaluation*.json` |
| 性能 | 每轮耗时、阶段耗时、3 秒达标率 | 各结果文件与 `results/evaluation.md` |

**判定口径**（`wo05_common.TURN_SPECS`，可被 `results/ground_truth.json` 覆盖）：

- **检索命中**：Top-K 中出现期望文档的片段，且该片段覆盖本轮考察点关键词（如「法定代表人」「销售处」）；
- **答案正确**：非拒答 + 关键信息点齐全 + 年份数量达标（数值题要求多期数据）；
- 说明：这是「最小必要证据」口径，保证 **离线可复现**；若要更严格的全文参考答案，把 `reference_answer` 写入 `results/ground_truth.json` 即可，`Context Recall` 与 `Answer Correctness` 会自动改用参考答案计算。

## 六、已知边界与改进方向

1. **「其中」误触发消解**：指代词表包含「其」，`其中 / 其他 / 其余` 会被误判为指代（多走一次 LLM 改写，结果通常与原句一致，不影响正确性但增加延迟）。改进：改为词边界匹配并维护否定词表。
2. **规则表按序匹配的优先级问题**：「关联方是谁？」因 `是谁` 先命中被判为实体属性。改进：改顺序匹配为「强特征词加权打分」。
3. **多实体仅提示不澄清**：可把 `ambiguity` 渲染为前端澄清选项，让用户点选目标公司。
4. **指代窗口为近 4 轮**：历史很长时更早的实体可能被遗忘；改进：维护「对话实体栈」，优先消解到最近一次提到的主体（第 3 轮「这个公司」正属此类）。
5. **跨文档串味**：多轮中切换主体后，若检索到旧主体文档的片段，会稀释上下文。当前通过检索式显式带上公司全称缓解；进一步可加文档级过滤（`where={"doc": 目标文档}`）。
