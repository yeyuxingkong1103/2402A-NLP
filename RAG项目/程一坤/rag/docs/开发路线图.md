### 任务 0.5 认证改为 Redis 会话令牌（取消 JWT）

> **决策记录（2026-09-16）**
> 原实现使用手写 JWT：只有签发、没有校验，且默认密钥为 `development-secret`。
> 核对文档后确认：**需求文档与技术栈文档从未要求 JWT，它是实现阶段自行引入的**。
> 首期为单机 Docker Compose、内部用户、且本就部署 Redis —— JWT 的"无状态多实例扩展"优势用不上，
> 反而带来三项负担：密钥管理（默认密钥等于无防护）、无法即时吊销、需要 refresh token 才能补上吊销能力。
> **决定：改用 Redis 会话令牌。** HTTP 契约保持 `Authorization: Bearer <token>` 不变，接口文档无需改动。

| 项 | 内容 |
|---|---|
| 问题 1 | `app/auth/router.py` 把验证码回显给调用方 → 不收邮件即可完成注册与改密 |
| 问题 2 | 手写 JWT 只有签发、无校验；默认密钥 `development-secret` |
| 方案 | 登录成功后生成随机会话令牌存 Redis（key `session:<token>`，value 含 user_id 与角色，TTL 2 小时）；每次请求查 Redis 校验；注销 / 改密 / 禁用直接删 key，**即时生效** |
| 涉及文件 | 新建 `app/auth/session_store.py`、`app/auth/current_user.py`（FastAPI 依赖）；修改 `app/auth/service.py`（删除手写 JWT）、`app/auth/router.py`、`app/core/config.py`（Redis 地址、会话 TTL）；删除 `app/db/sql_models.py` 中未被使用的 `UserSession` 表 |
| 安全要求 | 令牌用 `secrets` 生成（不少于 32 字节熵）；Redis 未连接时必须拒绝受保护请求，不得放行；响应与日志不得输出令牌与验证码 |
| 验收 | ① 接口响应不含验证码；② 未带令牌返回 `40100`；③ 注销后原令牌立即失效；④ 伪造令牌被拒绝；⑤ Redis 不可用时返回明确错误而非放行 |
| 状态 | ✅ 已完成（2026-09-18）：认证改为 Redis 会话令牌 |
| 当前实现 | `app/auth/tokens.py`（153 行）实现了 JWT 签发与校验，`app/core/config.py` 在生产强制 `JWT_SECRET`，`tests/test_jwt_tokens.py` 8 个测试通过——**这是任务 0.5 的旧方案，本任务决定改用 Redis 会话令牌后需返工** |
| 返工范围 | JWT 改为 Redis 会话令牌（已完成，见 app/auth/session_store.py） |
| 待补接口 | `POST /api/v1/auth/logout`（注销会话，删 Redis key 即时生效）——已补入《接口文档》3.6 |

## 阶段 1：法律元数据与时效数据模型

> **为什么这是关键**：法律 RAG 与普通 RAG 的分水岭是"某一时间点、某一法域下有效的是哪一版法条"。
> 当前 MySQL 与 Milvus **完全没有**生效日期、失效日期、法域、法规名称、效力等级字段。
> 不补这一层，需求文档 FR-LAW-004/007/008（法条检索、引用生成、时效提示）无法实现。

## 已知限制（2026-09-20 记录，均有实测依据）

```text
1. 列举式长条文的精排排序偏后
   现象：问句与条文用语差异大、或条文为列举式（如劳动合同法第四十条三项）时，
        重排分偏低，golden 会排在 5~10 名（confuse-046 第 7、confuse-049 未进 top10）
   已排除：不是窗口问题（20→40 反而下降）、不是长度截断（6550 字块仍得 0.48 分）
   结论：要解决需换方案（分项索引 / 句级重排），当前收益递减，暂不立项

2. 长期记忆写入 Milvus 后到可检索有秒级延迟
   影响：跨会话语义下可接受；同会话内立刻追问可能读不到刚写入的记忆

3. 外部模型 API 存在瞬态超时（SiliconFlow Embedding）
   现象：评测中出现过 55 条连续失败（服务瞬断），读失败时长期记忆走"不注入"兜底
   计划：给 embedding 客户端加通用重试（指数退避，只重试超时与 5xx）

4. 术语同义词扩写（SYNONYM_EXPANSION_ENABLED）净增益 <0.5 个百分点
   现状：默认关；对口语化提问有效（10 条口语题 MRR 0.745 → 0.795），
        但对通用集有挤占风险（confuse-085 已通过收窄扩写词修复）
   结论：作为可选能力保留，配置开关 + 权重旋钮（SYNONYM_EXPANSION_WEIGHT，默认 1.0）

5. 本机 Milvus 单机部署的嵌入式 etcd 已损坏两次（2026-09-18、2026-09-21）
   现象：容器 Exited(134)，日志 `voters=()` / `member-initialized: false`，无法选出主节点
   修复：把 `D:\milvus\volumes\milvus\etcd` 移开（改名保留，不删）→ 重启容器 →
        集合元数据随之丢失，需重建 collection 并重新嵌入全部向量（1627 条，约 2~3 分钟）
   建议：生产环境改用独立 etcd 部署；本机开发时把 etcd 目录纳入定期备份

6. 部分法规元数据仍待人工核对（2026-09-21 更新）
   现状：效力状态 11 部中 4 部已填"现行有效"（有页面原文支撑：修订沿革）、1 部填"不适用"
        （案例材料）、6 部留空；公布日期缺 1 部、生效日期缺 1 部
   原则：抽不到就留空，**禁止规则推定**（例如"有生效日、无失效日 ⇒ 现行有效"这种推断一律不做）
   去向：《待人工确认清单》交人工逐部核对后回填

7. as_of_date（适用时间点）的语义边界
   现状：首期每部法规只有 1 个版本，因此 as_of_date 的作用是
        "**排除在该时间点尚未施行的法规**"，**不是**"还原当时的历史文本"
   已知后果：问 2008~2013 年之间的《劳动合同法》，返回的是 2012 修正后的现行文本
   为什么不做成"还原历史文本"：需要同一法规多版本并存（law_versions 多行）+ 按版本切分块与向量，
        属独立能力（多版本支持），登记为后续扩展
   已确认不做的事：不把该版本生效日改成"修正案施行日"——那样会让 as_of=2010 时整部法规消失，比现在更糟
```
