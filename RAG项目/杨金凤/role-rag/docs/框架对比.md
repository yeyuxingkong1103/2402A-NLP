# 框架对比说明

本项目是一个自研的 RAG 角色扮演问答系统，面向高血压健康咨询场景：依据《国家基层高血压防治管理指南》回答患者问题，支持多角色人设、多轮记忆与答案溯源。技术栈为 Milvus（向量库）+ Redis（会话记忆）+ MySQL（元数据）+ BGE-M3（Embedding）+ BGE-reranker（精排）+ DeepSeek（生成）。

本文说明为什么核心链路选择自研，而不是直接采用 LangChain、LlamaIndex、Dify、RAGFlow、LightRAG、LinearRAG 等现成框架。结论先行——核心链路自研，仅在思想层面借鉴各框架的成熟做法。选型时主要看三个维度：是否匹配场景、定制成本、引入成本。

需要说明的是，这里说的「自研」指自研编排层——向量库、Embedding、reranker、大模型都是成熟组件，自研的是把这些组件按业务需求串起来的胶水代码。自研不等于重复造轮子。

## 一、框架对比

| 框架 | 定位 | 是否采用 | 理由 |
| --- | --- | --- | --- |
| LangChain | 通用 LLM 应用编排框架（链 / Agent / 工具 / 记忆） | 否 | 面向通用 Agent 场景，RAG 只是其中一个模块；重依赖（几十个包）；抽象层厚，做角色隔离与记忆分层要绕很多层 |
| LlamaIndex | 专注 RAG 的数据框架（文档加载 / 索引 / 查询引擎 / Node 抽象） | 否 | 数据管线与索引抽象强，但查询侧角色与记忆仍需自行拼装，引入成本大于收益；仅借鉴其 Node 元数据思想 |
| Dify | 低代码 LLM 应用平台 | 否 | 可视化编排开箱即用，但核心链路是黑盒，难以定制多角色 + 记忆分层，不利于答辩讲清原理 |
| RAGFlow | 深度文档理解的开源 RAG 引擎（DeepDoc 解析：版面 / 表格 / OCR） | 否 | 文档解析能力很强但整套过重、部署运维成本高；只需借鉴其解析思想 |
| LightRAG | 图结构 RAG（实体关系图谱 + 图/向量双级检索） | 否 | 图检索对指南类扁平文本增益有限，图构建成本高；借鉴其「混合检索 + 重排序」思路 |
| LinearRAG | 线性化图 RAG（把图谱压成序列喂给 LLM） | 否 | 较新，图检索对当前语料收益不明显 |

## 二、为什么自研

**1. 链路简单清晰，代码可控。** 本系统链路分两段。离线入库：`parser.py` 负责 PDF 正文 / 表格 / 图片 OCR 解析，`ingest.py` 负责分块、清洗与向量化入库；在线检索：`query_rewrite.py` 做多轮指代消解，`retrieval.py` 做双路召回与重排，`memory.py` 召回长期记忆，最后由 `rag.py` 拼装 prompt 并调用 DeepSeek 生成。十几个文件、每个文件单一职责，任何环节出了问题都能直接定位修改。每个环节都带降级兜底——Redis 挂了降级为无记忆、reranker 挂了降级为混合召回、改写失败降级为原始 query，链路既不崩也不静默出错。相比之下，现成框架把链路封装成链 / 索引 / 引擎，出了问题要么翻源码、要么改不动。

**2. 按需定制，不做减法做加法。** 本项目有四个强定制点，现成框架都难以直接满足：角色隔离（`roles.py` 从 MySQL 读角色、每个角色绑定独立 collection）、记忆分层（`rag.py` 用 Redis 存短期 N 轮对话，`memory.py` 用 Milvus `user_memory` 存长期客观事实）、混合检索（`retrieval.py` 里向量 + BM25 双路召回、RRF 融合、BGE-rerank 精排）、Query 改写（`query_rewrite.py` 指代消解 + Redis 缓存）。这些是系统核心卖点，自研比在框架里绕层更直接。现成框架的抽象是为通用场景设计的，落到「多角色 + 分层记忆」这种具体需求上，要么改源码、要么被迫妥协，定制成本反而高于自研。

**3. 依赖轻。** 系统直接依赖 `openai`、`redis`、`pymilvus`、`sentence-transformers`、`sqlalchemy` 等十几个基础包，不引入 LangChain 动辄几十个的传递依赖。依赖越少，环境越稳定、部署越省心，也更容易向导师讲清楚每一层用了什么、为什么用它。

**4. 学习价值。** 亲手实现分块、清洗、向量化、双路召回、重排、记忆抽取，能真正理解 RAG 的每一个环节。比如 `retrieval.py` 里 `_tokenize` 用 jieba 分词喂 BM25、`_rrf_fuse` 做双路融合、`_sigmoid` 把 reranker logits 压到 0-1；`memory.py` 里 `_fact_id` 用 MD5 去重、`_maybe_extract_memory` 每 5 轮触发一次抽取。这些细节只有自己写才会踩到并记住。

**5. 论文 / 答辩友好。** 每个技术选型都能讲清为什么这么选、为什么不那么选——比如 `similarity` 字段在 rerank 成功时是 sigmoid(logits)、降级时是 1-cosine，这种双语义只有自己实现才会意识到。没有藏在黑盒里「调包即所得」的环节，答辩时经得起追问。

## 三、借鉴了哪些框架思想

自研不等于闭门造车，四个框架的做法被吸收进了代码：

- **RAGFlow → 表格结构化解析**：`parser.extract_tables` 用 pdfplumber 抽表并渲染成 Markdown，每个表格作为独立 chunk，与 RAGFlow DeepDoc「结构化表格 + 上下文保留」的思路一致。
- **LightRAG → 混合检索 + 重排序**：`retrieval.retrieve` 的向量 + BM25 双路召回、`_rrf_fuse` 融合、BGE-rerank 精排，是对 LightRAG 混合检索思路的工程化落地。
- **LangChain → prompt 模板管理**：把人设、改写、抽取三类 prompt 抽成常量——`rag.py` 的 `DOCTOR_PERSONA`、`query_rewrite.py` 的 `REWRITE_PROMPT`、`memory.py` 的 `EXTRACT_PROMPT`，相当于轻量版 PromptTemplate。
- **LlamaIndex → chunk 元数据设计**：`milvus_store.py` 为每个 chunk 建了 page / source / domain / summary / created_at / updated_at 等元数据字段，便于按来源覆盖式入库与溯源，对应 LlamaIndex 的 Node metadata。

这些借鉴只取「思想」、不取「代码」，落地仍是十几行可读的自研实现，保持了链路的透明度。

## 四、如果重来会怎么做

- **保持自研核心链路。** 角色隔离、记忆分层、混合检索、Query 改写这四件事，框架帮不上大忙，自研的价值依然成立。
- **借鉴 RAGFlow 的文档解析模块。** 手写解析在复杂版面、跨页表格等边界场景仍不够稳，会用 DeepDoc 替换掉 `parser.py` 里的手写部分。
- **评测用现成方案。** 评测不是核心业务，不必自研——沿用项目已有的 `eval/run_ragas.py`（RAGAS），或引入 LangChain 的 evaluation 部分即可。
