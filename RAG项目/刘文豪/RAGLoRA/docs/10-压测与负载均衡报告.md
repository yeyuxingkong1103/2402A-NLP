# 压测与负载均衡报告

> 日期：2026-09-20
> 工具：`backend/scripts/loadtest.py`（自研，asyncio + httpx）
> 环境：本机 Windows，15.7GB，Milvus 2.6.6（Docker），Dify 常驻

---

## 一、为什么自研压测器

本机**没有装任何压测工具**（`jmeter` / `ab` / `wrk` / `locust` / `hey` 全部不存在）。
按项目的「本地优先、下载需授权」原则，不为一次压测引入新依赖 ——
`asyncio` + `httpx` 已足够，且能直接复用项目的鉴权流程。

---

## 二、⚠️ 压测过程中发现的真 bug（本次最大收获）

### 并发下精排设备切换竞态

```
Expected all tensors to be on the same device,
but found at least two devices, cpu and cuda:0!
```

**现象**：并发 8 压测，**81 个请求里 22 个失败（27%）**，其中 12 个 HTTP 500。

**根因**：`rerank._model` 是进程内共享单例，而 `nn.Module.cuda()/.cpu()`
是**原地修改**。精排为了给 Ollama 让显存，每次请求都要
「搬上 GPU → 推理 → 搬回 CPU」，但这段**没有锁**：

```
线程 A: model.cuda()  →  正在 GPU 上推理
线程 B: 取 _model、输入放到 cuda  →  此时 A 已 model.cpu()
→ 设备不一致
```

**修复**：用 `_gpu_lock` 把**整段设备切换 + 推理**串行化。
只锁推理那一段不够 —— 设备切换本身才是竞态所在。
（`release()` 也要拿同一把锁，否则会把正在推理的模型引用置空。）

**验证**：

| | 修复前 | 修复后 |
|---|---:|---:|
| 检索场景并发 8 失败率 | **22/81 = 27%** | **0/26 = 0%** |
| 重启后精排失败日志 | 61+ 次 | **0 次** |

> ⚠️ **这个 bug 的失效是静默的**：`except` 会把异常吞掉并「降级为粗排顺序」，
> 接口照样返回 200，只是**结果质量悄悄退化成未精排**。
> 单线程永远触发不了，只有并发压测才能暴露 —— 这正是压测的价值。

回归测试：`backend/tests/test_rerank_concurrency.py`（3 个用例）。

## 三、单 worker 基线（Web 层）

```bash
python backend/scripts/loadtest.py --url http://127.0.0.1:8001 --scenario light --concurrency 20
```

| 并发 | QPS | p50 | p95 | p99 |
|---:|---:|---:|---:|---:|
| 20 | **1063** | 18 ms | 24 ms | 29 ms |
| 50 | **1106** | 41 ms | 56 ms | 74 ms |
| 150 | **965** | 133 ms | 174 ms | 778 ms |

**单 worker 在并发 50 时达到峰值约 1100 QPS**，之后延迟上升而 QPS 不再增长。

> 📌 **`--scenario light` 用的是 `/openapi.json`**，它不碰任何外部依赖，
> 测的是 Web 层。**不要拿 `/api/health` 当轻量端点** —— 它逐个探活
> MySQL/Redis/Milvus/Ollama，实测**每次约 2 秒**（Ollama 那次调用占大头），
> QPS 只有 **9.2**。用错端点会得出「后端只能扛 9 QPS」的荒谬结论。

## 四、负载均衡实测（结论与预期相反）

nginx 配置见 `docker/nginx.conf`（round-robin，SSE 专用 location 关缓冲）。

### 4.1 负载**确实分出去了**

```
5332  upstream=192.168.65.254:8001
5323  upstream=192.168.65.254:8010
```

近乎精确的 50/50 轮询 —— 负载均衡机制本身**工作正常**。

### 4.2 但 QPS 全面下降

| 并发 | 单 worker | nginx（2 worker） | 变化 |
|---:|---:|---:|---:|
| 20 | 1063 | 947 | **−11%** |
| 50 | 1106 | 971 | **−12%** |
| 150 | 965 | 832 | **−14%** |

**加了 nginx + 第二个 worker，吞吐反而下降。**

### 4.3 为什么

**瓶颈不在后端 worker。** 证据：

- 单 worker 并发从 50 提到 150（3 倍），QPS **不升反降**（1106 → 965），
  只是延迟从 41ms 涨到 133ms —— 典型的「客户端/链路到顶」特征，
  而不是「服务端 CPU 跑满」。
- 两个 worker 加起来没有带来任何提升，说明请求根本没有堆在 worker 上。

最可能的原因是**压测客户端本身**：单个 Python 进程（asyncio）同时充当
流量生成器和响应收集器，在 ~1000 QPS 量级先于后端饱和。
其次是 Windows 的 loopback/TCP 栈在容器→宿主这一跳上的开销。

**因此：本机环境下无法测出后端的真实吞吐上限，也无法证明负载均衡的收益。**
要得到有意义的结论，需要压测工具与被测服务分离部署（不同机器），
或用更高效的压测器（wrk/hey，但会引入下载）。

## 五、诚实的结论

| 项 | 结论 |
|---|---|
| **负载均衡机制** | ✅ **工作正常**，50/50 轮询精确 |
| **负载均衡的吞吐收益** | ❌ **本机测不出来**（瓶颈在压测客户端，不在后端） |
| **单 worker 吞吐** | 约 **1100 QPS**（Web 层，并发 50） |
| **多 worker 的前提** | ✅ 已具备 —— **Milvus 解除了 Qdrant 的单 worker 限制** |
| **并发安全性** | ✅ **修掉了一个 27% 失败率的真 bug** |

**答辩时的正确说法**：

> 「Milvus 接入解除了 Qdrant 嵌入式独占文件锁的限制，使多 worker 成为可能；
> nginx 负载均衡已验证能精确分发（50/50）。但**本机压测环境测不出吞吐收益** ——
> 瓶颈在压测客户端而非后端，这一点我们如实记录，没有把它包装成优化成果。
>
> 压测真正的收获是**发现并修复了精排模块的并发竞态** ——
> 并发 8 时 27% 的请求静默退化为未精排。这个 bug 单线程永远测不出来。」

## 六、运维

```bash
# 起 nginx
docker compose -f docker/docker-compose.nginx.yml up -d

# 多 worker（要求 VECTOR_STORE=milvus，脚本会校验）
bash backend/run_multi.sh 2

# 压测（指向 nginx 的 8080）
python backend/scripts/loadtest.py --url http://127.0.0.1:8080 --scenario light

# 确认负载分出去了
docker logs raglora-nginx 2>&1 | grep -oE "upstream=[0-9.:]+" | sort | uniq -c
```

### ⚠️ 内存是真瓶颈

**每个 worker 各加载一份 bge-m3 + 精排（约 3.4GB）** —— 进程内模型不跨进程共享。

| worker 数 | 常驻内存 |
|---:|---:|
| 1 | 3.4 GB |
| 2 | 6.8 GB |
| 3 | 10.2 GB |

再叠加 Milvus（2.5G）+ Dify 会直接爆。`run_multi.sh` 因此**默认 `RAGLORA_WARMUP=0`**
（模型按需加载），并会把这段内存账打印出来。
