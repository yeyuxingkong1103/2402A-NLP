## 二、过程问题记录

### 问题 1：CUDA 基础镜像从加速器拉不动（影响最大）

**现象**：`docker pull nvidia/cuda:12.6.3-cudnn-runtime-ubuntu22.04` 反复失败，
`pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime` 拉了 10 分钟**零进度**、输出文件 0 字节。
重试时看到真实报错：

```
failed to copy: httpReadSeeker: failed open: ... 
net/http: TLS handshake timeout
```

本机配了三个 registry 加速器（daocloud / rainbond / lmirror），小镜像
（alpine 12MB）没问题，但 2GB 以上的大镜像层频繁 TLS 握手超时。

**排查过程**：先确认不是网络完全不通（`docker pull alpine:3.20` 成功）；
再确认不是镜像名写错（`docker manifest inspect` 对两个镜像都失败，
但这是加速器不代理 manifest API 导致的，不能作为判据）；
最后用「拉取时观察 `docker_data.vhdx` 是否增长」确认是真的卡住而非静默重试。

**解决**：换思路 —— 不用 CUDA 基础镜像。

关键事实：**Linux 上 PyPI 的 torch 轮子自带 CUDA 12 运行时**。
容器用 GPU 需要「宿主机驱动 + 容器内 CUDA 用户态库」两样：
前者由 NVIDIA Container Toolkit 在 `--gpus all` 时注入，
后者 pip 装的 `nvidia-cuda-runtime-cu12`、`nvidia-cudnn-cu12` 已经提供。
于是基础镜像降级成 `python:3.11-slim`（50MB），大头全部走 pip 源下载。

**效果对比**：

| 项 | 原方案 | 现方案 |
|---|---|---|
| 基础镜像 | 2~4GB，加速器拉不动 | 50MB，秒下 |
| 主要下载 | Docker registry（慢） | pip 清华源（实测约 11MB/s） |
| Python 版本 | 3.10（Ubuntu 22.04 默认），与开发环境不符 | **3.11，与开发环境一致** |

**顺带解决问题 2**：nvidia/cuda 的 ubuntu22.04 标签带的是 Python 3.10，
而开发环境是 3.11.16。换基础镜像后版本自动对齐，不用再折腾 deadsnakes PPA 或 conda。

### 问题 2：模型目录里有一半是没用的

**现象**：`bge-m3` 目录 4.3GB，往数据卷里灌要很久。

**排查**：逐个目录看构成：

| 内容 | 体积 | 用不用得上 |
|---|---|---|
| `pytorch_model.bin` | 2.2GB | ✅ FlagEmbedding 走这个 |
| `onnx/` | 2.2GB | ❌ 给 onnxruntime 用的，本项目不加载 ONNX |
| `imgs/`、`long.jpg` | 1.2MB | ❌ README 配图 |
| `.cache/` | 64KB | ❌ |

**解决**：`model-init` 服务复制时排除 `onnx/`、`imgs/`、`.cache/`、`long.jpg`，
模型体积 **4.3GB → 2.3GB**，少灌一半。

### 问题 3：两个 Docker 引擎互不可见

**现象**：本机同时存在两套 Docker —— Docker Desktop，以及 WSL `Ubuntu2404`
里独立装的 Docker 29.8.0。在 WSL 里 `docker ps` 看不到 Docker Desktop 的容器，反之亦然。

**排查**：`docker context ls` 显示 Windows 侧默认 context 是 `desktop-linux`
（走 `npipe:////./pipe/dockerDesktopLinuxEngine`）；WSL 里的 docker 走本机 socket，
是另一个引擎，镜像、容器、卷完全隔离。

**决策**：**统一用 Docker Desktop**。理由：

| | Docker Desktop | WSL 里的 Docker |
|---|---|---|
| GPU 透传 | 开箱即用 | 需另装 `nvidia-container-toolkit`（实测 `which nvidia-ctk` 为空） |
| 镜像盘 | 已在 D 盘 | 也在 D 盘 |
| 休眠后恢复 | 托盘图标可重启 | dockerd 停了要手动起 |

**遗留风险**：如果有人在 WSL 里执行过 `docker compose up`，
那些容器在 Docker Desktop 里是看不到的。已在《部署文档》常见问题里写明。

### 问题 4：transformers 的告警看着像异常

**现象**：容器日志里会出现

```
You're using a XLMRobertaTokenizerFast tokenizer. Please note that with a fast tokenizer,
using the `__call__` method is faster than using a method to encode the text followed by
a call to the `pad` method to get a padded encoding.
```

验收标准要求「容器运行过程中**无异常日志输出**」。这条本身无害（只是性能提示），
但混在日志里会让人以为出了问题。

**解决**：Dockerfile 里设 `TRANSFORMERS_VERBOSITY=error` 与 `TOKENIZERS_PARALLELISM=false`，
把 transformers 的 warning 级别压掉。验收测试脚本另外用
`grep -iE "traceback|exception|error|critical"` 扫一遍日志，把这件事变成可复现的检查。

### 问题 5：知识库怎么进容器

**背景**：验收要求知识库必须放 Docker 卷持久化（不能固化在镜像层），
但又要求 `docker run` 一条命令就能起服务。

两条要求看着矛盾：卷是空的，服务就没有知识库可用。

**方案对比**：

| 方案 | `docker run` 能否直接跑 | 是否满足卷持久化 |
|---|---|---|
| 知识库只放卷，靠外部挂载初始化 | ❌ 要带一长串 `-v` 参数 | ✅ |
| 知识库打进镜像，运行时不落卷 | ✅ | ❌ 数据在镜像层，删镜像即丢 |
| **种子随镜像分发 + 入口脚本按需初始化进卷** | ✅ | ✅ |

**解决**：知识库只有 58MB，打进镜像完全可行；入口脚本发现数据卷里没有知识库时，
自动把 `/app/seed_kb` 复制到卷里。两条要求同时满足。

判据用 `chunks.json` 是否存在，而不是只看目录 ——
上次初始化中断会留下一个空目录，只看目录会误判成"已初始化"。

### 问题 6：Git Bash 会改写容器内路径

**现象**：本地测试 `KB_CACHE_DIR=/kb python -c ...` 时，程序看到的是
`C:\Program Files\Git\kb` —— MSYS 把以 `/` 开头的参数当成 Unix 路径转成了 Windows 路径。

**影响**：**只影响 Git Bash 里直接跑 Python 的调试场景，不影响容器**。
容器里没有 MSYS 层，`/kb` 就是 `/kb`。

**规避**：调试时用 `MSYS_NO_PATHCONV=1` 前缀，或者干脆在容器内验证。
记在这里是免得下次又当成代码 bug 去查。

### 问题 7：Docker Desktop 会被 WSL 休眠带走

**现象**：这是本机的已知问题 —— WSL 发行版休眠时，Docker Desktop 的引擎
（跑在 `docker-desktop` 这个 WSL 发行版里）会一起停掉，
表现为容器"莫名其妙"连不上、报 Connection refused。

**应对**：
- 数据都在命名卷里，引擎重启后 `docker compose up -d` 即可恢复，不丢数据；
- 验收测试每次都新建临时容器，不依赖上一次的容器还活着；
- 已在《部署文档》常见问题里写明排查方向。

### 问题 8：RTMP 现成镜像一律拉不到

**现象**：验收标准点名「与其他服务（如 RTMP 服务器）正常通信」，
需要一个真实的 RTMP 服务做对端。试了四个常见镜像：

```
alfg/nginx-rtmp:latest        403 Forbidden
tiangolo/nginx-rtmp           不可用
jasonrivers/nginx-rtmp        不可用
mekesim/nginx-rtmp            不可用
datarhei/restreamer           不可用
```

加速器返回的是 `unexpected status from HEAD request ... 403 Forbidden` ——
不是网络不通，是加速器不代理这些镜像。

**解决**：自己构建。Alpine 官方源里有现成的 `nginx-mod-rtmp` 包，
`apk add nginx nginx-mod-rtmp` 即可，镜像只有 **4.2MB**。

```dockerfile
FROM alpine:3.20
RUN sed -i 's|dl-cdn.alpinelinux.org|mirrors.tuna.tsinghua.edu.cn|g' /etc/apk/repositories \
    && apk add --no-cache nginx nginx-mod-rtmp
```

**这比拉第三方镜像更好**：部署到目标服务器时不依赖任何第三方镜像仓库，
来源可控，而且体积小两个数量级。配置见 `部署/rtmp/nginx.conf`。

### 问题 9：构建全部成功，却卡在导出镜像

**现象**：`docker build` 十个步骤全部 DONE，最后一步报错退出：

```
#15 naming to docker.io/library/rag-finance:1.0 done
#15 ERROR: image "docker.io/library/rag-finance:1.0": already exists
ERROR: failed to build: failed to solve: image ...: already exists
```

**排查**：层全部构建成功，问题出在 BuildKit 生成 **attestation 清单**
（ provenance/SBOM 元数据）时与已存在的同名镜像冲突。

**解决**：`docker rmi -f rag-finance:1.0` 后加 `--provenance=false` 重建。
层都在缓存里，重建只花了 38 秒。

构建命令定型为：

```bash
docker build --provenance=false -f 部署/Dockerfile -t rag-finance:1.0 .
```

### 问题 10：验收脚本自己制造了 4 个"失败"

**现象**：第一轮验收 **11 通过 / 4 失败**，看上去像部署有问题。

**排查**：逐个看，**4 项全部是脚本自身的问题**：

| 现象 | 真实原因 |
|---|---|
| 读不到卷里的知识库 | Git Bash 把 `docker exec ... ls /kb/...` 的参数 `/kb/...` 转成了 `C:/Program Files/Git/kb/...`（同问题 6） |
| 重建容器后"数据丢失" | 同上，`cat /kb/...` 读到的是不存在的路径，返回空 |
| 探不到 rtmp-server（两项） | **探测对象选错**：`rag-verify` 是裸 `docker run` 起的，没接入 compose 的 `rag-net`，本来就解析不到 `rtmp-server` |

**解决**：
1. 带容器内绝对路径的命令包进 `sh -c '...'`，参数不以 `/` 开头就不会被转换；
2. 网络探测改为从**真正部署的 `rag-app`** 探测 —— 验收标准问的是
   「部署后的服务能否与其他服务通信」，拿一个没接入网络的临时容器去探是探错了对象。

**修正后复跑：15 项全部通过。**

第三条这个坑值得单独记：如果没意识到是"探错了对象"，
很容易得出「容器网络配置有问题」的错误结论，然后去改本来正确的网络配置。
