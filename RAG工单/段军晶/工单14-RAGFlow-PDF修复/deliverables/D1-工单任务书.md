## 一、工单背景

### 1.1 业务诉求

公司需快速搭建一套 RAG 系统，用于**中文工业技术文档的多模态推理问答**。数据集为 IMDR / ITMQ
（工业制造领域多模态理解与推理数据集，共 **10,096 个问题**），问题分三类：

| 类型 | 说明 |
|------|------|
| 纯文本问题 | 答案位于文档文字层 |
| 纯图像问题 | 答案位于工程图纸，需视觉理解 |
| 文本-图像混合问题 | 需同时理解文字与图纸，并做机械原理推理 |

### 1.2 领域特征（难点来源）

该数据集有两个关键特征，直接造成本工单的技术难点：

1. **文档以「不可编辑的图片型 PDF」形式提供** —— 无文本层、分辨率低、格式不一、版面复杂；
2. **问题大量为图文交错类型** —— 需跨越「文字描述」与「工程图纸」两侧信息并做推理。

### 1.3 现状问题

RAGFlow 的默认解析流水线在这类图片型 PDF 上会**丢失图文信息、错配图文关联**，导致问答不准。
需要定位缺陷并修复，使工单规定的 6 个测试问题达到验收精度。

## 二、原始问题

### 2.1 待解决的技术问题（文档验收明确要求的三个分析题）

| # | 技术问题 | 要求 |
|---|---------|------|
| 1 | **分块策略与任务触发链路** | 阐明解析 PDF 时，`paper_id` 为 `paper` / `table` / `one` / `knowledge_graph` 时**分别采用的分块策略**；解析任务**如何触发**、**如何放入 Redis Stream 消息队列**、**如何被任务执行器消费处理** |
| 2 | **`do_handle_task` 主逻辑** | 阐明文档解析、分块、向量化和索引的**完整流程**，主要逻辑有哪些，用到了哪些技术实现方案 |
| 3 | **DeepDoc 深度解析模块** | 梳理内置了**哪些文件解析器**、能解析什么类型的文件，**重点梳理 PDF 文件的解析技术** |

> ⚠️ **工单内置陷阱（须在交付文档中点明，否则视为未读代码）**：
> 第 1 问的措辞暗示 `knowledge_graph` 有独立分块器，**实际并非如此** ——
> `rag/svr/task_executor.py:83-100` 的 `FACTORY` 中 `"knowledge_graph": naive`，
> 即 **KG 复用 naive 分块器**；`rag/app/` 下**不存在** `knowledge_graph.py`。
> 图谱构建在独立的 `graphrag/` 模块，是与分块并列的**独立阶段**，不是分块策略。

### 2.2 待修复的功能缺陷

**核心缺陷**：图片型 PDF 的图文信息在解析链路中丢失，导致 Q3~Q6（依赖第 7 页工程图）不可达。

经源码核实，**「信息丢失」并不发生在「未配置 VLM」上**（未配 VLM 时图纸仍会入库），
真正的流失发生在**更上游**：

| # | 流失环节 | 位置 | 说明 |
|---|---------|------|------|
| 1 | OCR 置信度过滤 | `deepdoc/vision/ocr.py:738-744` | 得分 < `drop_score = 0.5` 的文本行**整条丢弃**，图纸细线小字极易低分 |
| 2 | 图区图文高度差过滤 | `deepdoc/parser/pdf_parser.py:310-314` | 字高与框高差比 ≥0.7 的字符被踢进 `lefted_chars`，而该列表**全仓无读取处**（写了不用），等于永久丢失 |
| 3 | 图组文本为空即丢弃 | `deepdoc/parser/pdf_parser.py:901-903` | 图内无文字且无图注 → 不产出 chunk |
| 4 | 跨页合并逻辑不可达 | `deepdoc/parser/pdf_parser.py:586-588` | `_concat_downward` 首行即 `return`，其后 590-688 行的 XGBoost 跨页拼接**是死代码** |
| 5 | 列感知阅读顺序未启用 | `rag/app/naive.py:576` | `_final_reading_order_merge` 在 naive 路径被**注释掉** |

**VLM 的真实定位**：其作用是**补 OCR 拿不到的信息** —— 尤其是空间关系（如「部件 4 在部件 5 左侧」）。
**VLM 是 Q3 的必要条件，是 Q4~Q6 的增强项**，而非「信息丢失」的根因。

## 三、验收标准

### 3.1 功能验收

| 项 | 验收线 |
|----|--------|
| 部署并运行 RAGFlow（`github.com/infiniflow/ragflow`） | 可访问、可解析 |
| 构建知识库并上传 `CN100342976C.pdf` | 解析 → 切片 → 向量化 → 索引**全链路成功** |
| **6 个测试问题精度** | **100%（6/6）** |

**允许的技术手段**：调整解析方法、分块策略、向量相似度权重、Rerank 模型等（配置或代码实现均可）。

### 3.2 判分口径（重要）

`questions.jsonl` 中这 6 题为**单选题**，各带 4 个选项与选项字母答案，并有 `group` 字段：

> **group 1 = Q1/Q2（纯文本）｜group 2 = Q3/Q4（纯图像）｜group 3 = Q5/Q6（图文混合）**
> —— 正好对应工单所述三类问题。

因此**判分口径应为「选项字母命中」，而非文本相似度比对**。答案分别为
Q1=A、Q2=C、Q3=A、Q4=A、Q5=C、Q6=B。

### 3.3 性能验收 ⚠️

| 项 | 验收线 | 冲突提示 |
|----|--------|----------|
| 响应时间 | 从提问到返回答案 **≤ 3 秒** | Rerank 会显著增加查询延迟，需权衡 |
| 资源消耗 | 合理利用计算资源，**高并发下稳定运行** | ES 内存占用高，是硬约束 |

> 缓解因素：VLM 调用发生在**解析/索引阶段**，**不占用查询时的 3 秒预算**。

### 3.4 文档验收

需体现三个技术问题（见 §2.1）的**清晰准确的实现方案总结**。

### 6.4 ⚠️ 部署注意（两个陷阱，已实测确认）

**陷阱一：Docker 不挂载源码，改代码不生效**

`docker/docker-compose.yml` 的 ragflow 服务 volumes **仅**挂载 logs / nginx / entrypoint /
`service_conf.yaml.template`，**未挂载 `rag/`、`deepdoc/`、`api/`、`common/`**。
这些 Python 源码由 `Dockerfile` 在构建阶段 `COPY` 进镜像。

> **实测证据**：容器内 `rag/prompts/vision_llm_figure_describe_prompt.md` 为 **1552 字节**
> （md5 `c767374c…`），而本地源码树同名文件为 **2749 字节**，**内容完全不同**；
> `deepdoc/parser/figure_parser.py` 容器内 **178 行** vs 源码树 **255 行**。
> 即**镜像内代码与本地源码树并非逐文件一致**。

**后果**：在本地源码树修改 `rag/app/naive.py` 等文件后，容器内运行的仍是镜像内原始代码，**改动完全无效**。

**陷阱二：用这份源码重新构建镜像会失败**

`Dockerfile:168` 有 `COPY .git /ragflow/.git`，`Dockerfile:170` 执行 `git describe`；
但该源码树**不含 `.git` 目录**（由 zip 解压而来）→ 构建失败。
此外完整构建还需安装 Node 并执行前端 `npm run build`，耗时较长。

### 6.5 部署路线（选定）

| 路线 | 做法 | 评价 |
|------|------|------|
| **A. 官方镜像 + 按需挂载** | 运行官方镜像；改动以 bind mount 覆盖镜像内同名文件 | ✅ **本工单采用**：部署快、改动真正生效、D3 可交付 |

| C. 改 Dockerfile 后重新构建 | 先移除 `.git` 相关两行再 build | 构建慢、需 Node 工具链，2 人日工期下不划算 |

| **不覆盖 1700 个文件的全量数据集** | 验收只针对工单指定的 `CN100342976C.pdf` 及其 6 题 |
| **不修改 RAGFlow 核心架构** | 仅在解析/检索层做可挂载的增量改动，不动队列、存储、调度等基础设施 |
| **不做模型微调/训练** | 仅使用现成模型（Embedding / Chat / VLM） |
| **不重新构建镜像** | 见 §6.4 陷阱二；采用路线 A |
| **不解决题目本身的口径争议** | 若测试题存在题面歧义（如 Q5「首先经过」），如实记录并上报，由工单方裁定 |
| **不引入 Rerank** | 因与 3 秒响应约束冲突，需权衡后决策 |

### 7.3 交付判定原则

1. **单变量原则**：每轮只改一个变量并记录得分，否则无法归因；
2. **可复现原则**：所有结论须可由脚本/命令复现，不只给结论；
3. **诚实原则**：未达标项、失败实验、方法学错误**如实记录**，不掩盖；
4. **源码同源原则**：运行时改动必须同步到源码树，避免「改了运行时、源码没改」的评审风险。
