## 1. 引言

### 1.1 编写目的

定义 RAGLoRA 的功能需求、业务规则、数据要求与非功能指标，作为开发、测试与验收的依据。
阅读对象：开发者、测试者、验收方。

### 1.2 项目背景

构建一个**基于 RAG（检索增强生成）的角色扮演对话系统**：用户选择专家角色（如心血管内科医生、
执业律师）对话，角色的回答被约束在其绑定知识库的范围内，逐句标注来源编号，检索不到就明确
拒答——以此解决通用大模型「编造事实、无法溯源」的两个核心问题。

### 1.3 术语定义

| 术语 | 定义 |
|---|---|
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| dense / sparse | 稠密向量（语义）与学习型稀疏向量（关键词）两种表示 |
| RRF | Reciprocal Rank Fusion，多路召回结果的排名融合算法 |
| 精排 | cross-encoder 对「query-候选」逐对打分并重排 |
| 短期记忆 | 当前会话最近 N 轮对话（Redis） |
| 长期记忆 | 跨会话的用户相关历史（Milvus 向量召回） |
| 知识片段 | 检索命中并注入提示词的文本块（chunk） |
| fail-open | 依赖故障时选择「放行/降级」而非「阻断」的失效策略 |

## 2. 总体描述

### 2.1 产品定位

面向个人用户的知识型角色对话 Web 应用。两类典型场景：

1. **领域咨询**：向「医生」「律师」等绑定权威语料的专家角色提问，获得**可溯源**（[n] 引用）
   、**有边界**（超范围拒答）的回答；
2. **个性化陪伴**：系统记住跨会话的用户相关历史（长期记忆），回答结合用户个人情况。

### 2.2 用户角色

| 角色 | 说明 |
|---|---|
| 普通用户 | 注册登录、管理自己的会话、与角色对话、查看回答来源 |
| 高级用户 | 可新建自定义角色（人格三层 + 知识库绑定），使用检索调试台 |

### 2.3 运行环境

| 项 | 要求 |
|---|---|
| 客户端 | 现代浏览器（React 19 前端，Vite 构建） |
| 服务端 | Windows 已验证；Linux 迁移指引见部署文档 §2（待验证） |
| GPU | NVIDIA 8G 显存（RTX 4060 实测）；无 GPU 时编码/精排自动落 CPU |
| 内存 | ≥ 16 GB（推荐 24 GB），内存构成见 README §3.1 |
| 依赖服务 | MySQL 8.0 · Redis 5 · Milvus（Docker，默认）/ Qdrant（嵌入式，备选）· Neo4j（Docker）· Ollama（qwen2.5:7b） |

### 2.4 设计与实现约束

- **C1 本地优先**：模型、依赖全部复用本机已有环境，绝不联网下载；确需下载必须显式授权
  （`RAGLORA_OCR_ALLOW_DOWNLOAD=1`）。
- **C2 单 worker**：Qdrant 嵌入式模式持有独占文件锁，后端禁止多 worker。
- **C3 降级优先**：Redis / Neo4j / 精排 / 长期记忆任一不可用，主问答链路必须仍然可用（见 BR-08）。
- **C4 双链路并存**：LangChain（LCEL）为默认链路，手写链路保留为可切换退路
  （`RAGLORA_CHAIN=manual`），两者的 trace 口径一致。

## 3. 功能需求

> 优先级：★ 必须实现 / ☆ 应实现。每条 FR 标注实现位置；「验证」列为实测证据的出处。

### FR-01 用户注册与登录 ★

- **描述**：用户名 + 密码注册；登录签发 JWT（HS256，72h 有效）。
- **规则**：密码 PBKDF2-SHA256 200,000 轮加盐哈希；用户名 3-32 字符，密码 ≥6 位。
- **实现**：`routers/auth.py` · `core/security.py`
- **验证**：接口文档 §鉴权；压测报告中登录接口 QPS 实测。

### FR-02 角色管理 ★

- **描述**：角色 = **人格三层**（身份 `identity_block` / 风格 `style_json` / 约束
  `domain_constraints`）+ 提示词骨架 `prompt_template` + 知识库绑定 `kb_collection` +
  检索参数（recall_top_k=20 / rerank_top_k=5 / temperature=0.3）。
- **接口**：列表（支持 `?category=` 分类过滤）、详情（Hash 缓存 read-through）、
  新建/修改/删除（自定义角色）；内置角色不可删除（BR-05）。
- **附加**：`GET /characters/rank/hot` 返回 Redis zSet 热度榜（FR-12）。
- **实现**：`routers/characters.py` · `services/persona.py` · `services/redis_extra.py`
- **验证**：`tests/test_redis_extra.py`（12 用例）；种子角色见 `seed.py`。

### FR-03 会话管理 ★

- **描述**：按角色创建会话；消息历史查询（游标分页）；重命名；软删除（连带清短期记忆）。
- **规则**：所有接口校验 `conversation.user_id == 当前用户`，不满足返回 404 而非 403，
  不暴露「会话存在」这一信息（BR-03）。
- **实现**：`routers/conversations.py`

### FR-04 对话问答（核心链路）★

- **描述**：`POST /chat/stream`（SSE 流式，事件序 `trace → sources → delta* → done`）与
  `POST /chat/completions`（非流式）。回答必须逐句携带 `[n]` 引用，并随响应下发全部来源。
- **处理步骤**（对应业务流程图 12-§图2）：

  | # | 步骤 | 关键参数 / 规则 |
  |---|---|---|
  | 1 | 限流检查 | String 计数器，30 次/分/用户（`RAGLORA_RATE_LIMIT`），超限 429（BR-06） |
  | 2 | 上下文装载 | 校验归属；取短期记忆（FR-08） |
  | 3 | 查询改写 | 仅多轮且触发启发式（≤12 字 / 命中代词 / 承接连词开头）才调 LLM；改写结果异常放弃用原句 |
  | 4 | 多路召回 | 三路：向量库混合检索 + MySQL 文档级 + Neo4j 法条图谱（FR-06） |
  | 5 | RRF 融合 | `weight/(60+rank)`，权重 vector=1.0 / graph=1.2；指名文档命中 ×1.5 加分 |
  | 6 | 精排 | bge-reranker-v2-m3，top 20 → 5；GPU 分时复用约 413ms（BR-12） |
  | 7 | 长期记忆召回 | 跨会话 top3 注入 system 头部，按用户隔离（FR-08） |
  | 8 | 提示词组装 | 人格三层 + 编号知识片段（800 字/条）+ 对话历史 + 用户问题 |
  | 9 | 生成 | Ollama qwen2.5:7b，temperature 0.3，max_tokens 800，流式 |
  | 10 | 后处理 | 压缩多余换行、去首部装饰符、规范连续 `[n]` 编号 |
  | 11 | 落库与记忆 | 消息 ×2、会话计数、短期记忆、长期记忆、热度 +1（FR-08/12） |

- **实现**：`routers/chat.py` → `services/chain.py`（分发）→ `lc_chain.py`（默认）/
  `rag_chain.py`（备选），两链路共用 `persona.render_system`、精排与后处理。
- **验证**：评测报告（43 题：来源命中率 100% / 引用标注率 100% / 答案覆盖率 95%）。

### FR-05 查询改写（指代消解）☆

- **描述**：多轮对话中把「那第二种呢」改写为自含完整语义的独立问句。
- **规则**：启发式前置判断（见 FR-04 #3），无需改写时**跳过 LLM 调用**以省延迟；
  改写结果为空或超长（> 原文×4+40 字）时放弃改写。
- **实现**：`services/llm.py`（`needs_rewrite` / `rewrite_query`），开关 `REWRITE_ENABLED`。

### FR-06 混合检索与多路召回 ★

- **描述**：单库内 dense（1024 维 COSINE）+ sparse（IP）两路各召回后 RRF 融合（库内混合检索）；
  其上再做多路召回：

  | 路 | 数据源 | 逻辑 | 权重 |
  |---|---|---|---|
  | 向量 | Milvus（默认）/ Qdrant / both | 库内混合检索（RRF_K=60） | 1.0 |
  | 文档级 | MySQL | query 指名文档与库内 178 份文档名包含匹配；命中则做**限定检索**（不重复计票），未收录记入 trace | — |
  | 图谱 | Neo4j | 《法名》第 X 条精确命中（带 CITES/ADJACENT 邻居）；刻意不做「只给法名返回前几条」 | 1.2 |

- **规则**：图谱命中需回向量库补正文，无正文的丢弃（BR-09 相关：RRF 分不用于相关性阈值）。
- **实现**：`services/retrieval.py` · `milvus_store.py` · `qdrant_store.py` · `graph_store.py` ·
  `doc_store.py`；开关 `RAGLORA_MULTI_RECALL`。
- **验证**：`docs/08-多路召回说明.md`；`tests/test_multirecall.py`、`test_retrieval_filter.py`。

### FR-07 精排（重排序）★

- **描述**：bge-reranker-v2-m3（cross-encoder）对召回池 20 条重排，取 top 5 进提示词。
- **规则**：权重常驻 CPU 内存、推理时搬 GPU 用完即还（BR-12）；候选正文截 2048 字、
  tokenizer 512 token；任何异常降级为原序并置 `rerank_score=None`，**不允许静默丢请求**
  （2026-09-20 已修并发竞态）。
- **实现**：`services/rerank.py`；验证：`tests/test_rerank_concurrency.py`、压测报告。

### FR-08 记忆体系 ★

- **短期**：Redis LIST `conv:{user}:{conv}` 存最近 6 轮（12 条），LTRIM 封顶 + TTL 3600s
  每写续期；未命中从 MySQL 懒加载重建。
- **长期**：Milvus 集合 `kb_memory` 存整轮问答（≤1200 字），**仅 `VECTOR_STORE=milvus` 时启用**；
  召回时过滤 `user_id == X AND conversation_id != 当前`（过滤表达式下推到每个检索请求，
  2026-09-20 修复过被 kwargs 吞掉的隔离失效 bug）；删除后强制 flush 保证即时不可见。
- **实现**：`services/memory.py` · `services/long_memory.py`；验证：`tests/test_long_memory.py`。

### FR-09 知识库管理（离线链路）★

- **描述**：上传（pdf/txt/md）→ 解析 → 清洗 → 分块 → 嵌入 → 双写向量库 + MySQL 登记；
  支持删除（连带删向量）与集合统计；服务内入库走后台任务 + 进度轮询。
- **规则**：(collection, file_hash) 唯一实现**入库幂等**（BR-04）；Qdrant 为主写
  （内容哈希主键，幂等覆盖），Milvus 次写，失败不回滚主写并给出补同步脚本指引。
- **实现**：`services/ingest.py`；验证：`docs/07-Milvus接入说明.md`。

### FR-10 OCR 分流解析 ☆

- **描述**：抽前 5 页算页均字符数：≥50 → 文本层 PDF 走 PyMuPDF；<50 → 扫描件走
  MinerU（独立 conda 环境，vlm-engine，900s 超时），MinerU 失败且已授权时降级 PaddleOCR。
- **附加**：pdfplumber 表格抽取（≥2 行判定为表）为独立可选能力。
- **实现**：`services/ocr.py`；验证：`docs/09-OCR分流说明.md`、`tests/test_ocr.py`
  （实测扫描件 3392 字 / 95s）。

### FR-11 检索调试台 ☆

- **描述**：纯检索不生成，可指定集合、top_k、开关精排、传过滤条件；结果与耗时计入
  `search_history` 表供回看对比。
- **实现**：`routers/search.py`。

### FR-12 Redis 五类数据类型支撑 ★（2026-09-27 新增）

- **描述**：在 LIST 短期记忆之外，把其余四类接入真实业务（键设计见 §5.3）：

  | 类型 | 业务 | 失效策略 |
  |---|---|---|
  | String | 每用户每分钟问答限流计数（INCR+EXPIRE 60s，TTL<0 自愈补期） | fail-open（BR-06） |
  | Hash | 角色详情 read-through 缓存（15 字段扁平化，bool/int/float/dict 类型还原） | 写路径主动失效 + TTL 300s 兜底 |
  | Set | 角色分类二级索引 `char_cat:{category}`；启动时全量幂等重建自愈漏更 | 增删角色同步维护 |
  | zSet | 角色热度榜：每完成一轮问答 ZINCRBY 1 | 无 TTL（榜单长期有效） |

- **规则**：全部降级安全——限流 fail-open；缓存/索引/榜单不可用时回源 MySQL 或返回空，
  绝不阻塞问答主链路（BR-08）。
- **实现**：`services/redis_extra.py`；**验证：`tests/test_redis_extra.py` 12 用例全过**。

### FR-13 健康检查 ☆

- **描述**：`GET /api/health` 逐项探活 MySQL / Redis / Qdrant / Milvus / Neo4j / Ollama，
  `?deep=1` 附带本地模型文件与 GPU 显存；响应携带当前生效配置
  （`active.chain / vector_store / llm_model / multi_recall`）。
- **规则**：未启用的可选组件（如 `VECTOR_STORE=milvus` 时的 Qdrant）报 `skipped` 而非失败，
  且**不得占用其独占锁**。
- **实现**：`routers/health.py`。

## 4. 业务规则

| 编号 | 规则 | 动机 |
|---|---|---|
| BR-01 | **拒答边界**：只依据提示词中的【知识片段】回答；片段中没有的明确说「我无法确定」，绝不编造；与角色专业无关的问题礼貌拒答并引导回专业领域 | 反幻觉，守住专业边界 |
| BR-02 | **引用标注**：每句结论后必须带 `[1]`、`[2][3]` 编号；即便提到法名/条号也要保留编号；后处理统一规范连续编号格式 | 可溯源是本系统的核心卖点 |
| BR-03 | **多用户隔离**：会话/消息/检索历史按 user_id 过滤；越权一律 404；长期记忆过滤表达式下推到向量检索请求内（不能在应用层二次过滤——曾因被 kwargs 吞掉而失效） | 隐私安全 |
| BR-04 | **入库幂等**：MySQL (collection, file_hash) 唯一；向量库 point id 由内容哈希派生，重复导入覆盖而非追加 | 重复导入不产生脏数据 |
| BR-05 | **角色保护**：内置角色不可删除；名下仍有会话的角色不可删除 | 防误删破坏种子数据 |
| BR-06 | **限流 fail-open**：Redis 不可用时放行并告警。限流是保护措施，不能反过来变成全站不可用 | 可用性优先 |
| BR-07 | **缓存一致性**：MySQL 为权威源；写路径（改/删角色）主动失效 Hash 缓存，TTL 300s 兜底；读路径 read-through 回填 | 简单可靠的一致性模型 |
| BR-08 | **降级矩阵**：Redis 挂→短期记忆回源 MySQL、限流放行、榜单为空；Neo4j 挂→图谱路跳过；精排挂→原序返回；长期记忆挂→不注入；向量库是唯一**不可降级**依赖 | 单一组件故障不放大为全站故障 |
| BR-09 | **阈值口径**：RRF 融合分是量化值（大量并列），**不得**用作相关性阈值；相关性过滤只能用精排分 | 实测无关查询也常得 0.5 分 |
| BR-10 | **单 worker**：`VECTOR_STORE=qdrant`（嵌入式）时后端必须单进程 | Qdrant 独占文件锁 |
| BR-11 | **本地优先**：不联网下载模型/依赖；OCR 模型下载需显式授权 | 环境可复现、成本可控 |
| BR-12 | **精排 GPU 分时复用**：精排权重常驻 CPU，推理时搬 GPU、用完即还——生成与精排本不重叠，用 413ms 精排延迟换 47.8 tok/s 的生成吞吐（常驻 GPU 会把它打到 5.2 tok/s） | 8G 显存下的关键取舍 |
| BR-13 | **短期记忆封顶**：只保留最近 6 轮 12 条（LTRIM）+ TTL 3600s 每写续期；进程崩溃导致的「无过期键」在每次写入时自愈 | 控制上下文长度与成本 |
| BR-14 | **评测独立会话**：每道评测题使用独立会话——共享会话会让上下文带偏回答风格，把引用标注率从 100% 误判为 30%（实测踩过） | 评测脚本缺陷会伪装成系统缺陷 |

## 5. 数据要求

### 5.1 MySQL（业务权威源，6 张表）

| 表 | 关键字段 | 说明 |
|---|---|---|
| users | username（唯一）、password_hash、salt | PBKDF2 200k 轮 |
| characters | slug（唯一）、identity_block / style_json / domain_constraints / prompt_template、kb_collection、recall_top_k、rerank_top_k、temperature、is_builtin | 人格三层 + 知识库绑定 |
| conversations | user_id→users、character_id→characters、message_count、is_deleted | user_id 是隔离核心 |
| messages | conversation_id→conversations、role、content、rewritten_query、sources_json、trace_json、latency_ms | 长期记忆与链路追溯的回源依据 |
| search_history | user_id、query、result_json、elapsed_ms | 检索调试台历史 |
| kb_documents | (collection, file_hash) 唯一、chunk_strategy、chunk_count、status | 入库幂等与进度 |

### 5.2 Milvus 集合（`VECTOR_STORE=milvus` 默认）

| 集合 | 用途 | schema 要点 |
|---|---|---|
| kb_medical / kb_legal | 知识库向量 | id INT64 主键（内容哈希，非自增——以内容寻址保证幂等）；dense FLOAT_VECTOR 1024（HNSW/COSINE，M=16, efConstruction=200）；sparse SPARSE_FLOAT_VECTOR（SPARSE_INVERTED_INDEX/IP）；text/source/law_name/article_no/summary/created_at/updated_at |
| kb_memory | 长期记忆 | 同双路索引；**user_id INT64 过滤字段**（隔离）+ conversation_id |

### 5.3 Redis 键设计（五类全覆盖）

| 键 | 类型 | 生命周期 | 业务 | 所属 FR |
|---|---|---|---|---|
| `conv:{user_id}:{conversation_id}` | LIST | TTL 3600s，每写续期 | 短期记忆（最近 12 条 JSON） | FR-08 |
| `rl:chat:{user_id}` | **String** | TTL 60s（TTL<0 自愈补期） | 每分钟问答限流计数 | FR-12 |
| `char:{character_id}` | **Hash** | TTL 300s | 角色详情 read-through 缓存 | FR-12 |
| `char_cat:{category}` | **Set** | 永久，启动全量重建 | 分类二级索引（member=角色 id） | FR-12 |
| `rank:char_hot` | **zSet** | 永久 | 角色热度榜（member=角色 id，score=问答轮数） | FR-12 |

### 5.4 Neo4j 图模型（法条关系）

- 节点 `(:Article {uid, law_name, article_no, num, collection})`，`uid="{law_name}|{article_no}"`；
- 关系 `(:Article)-[:CITES]->(:LawRef {name})`（跨法引用，规则抽取）与
  `(:Article)-[:ADJACENT]->(:Article)`（同法相邻条文）；重建前 DETACH DELETE 幂等；
- kb_medical 无条号结构，图谱不适用（显式返回 note）。
