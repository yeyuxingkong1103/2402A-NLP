## 2. 响应时间优化（三项，都有 A/B 实测）

### 2.1 DeepSeek 客户端必须复用 —— 最大的一笔

**问题**：`llm_chat` 原本每次请求都 `OpenAI(...)` 新建客户端，于是每次都要重付 DNS + TLS + 连接池构建。

**A/B 实测**（同一台机器、同一天）：

| 写法 | 单次生成耗时 |
|---|---|
| 每请求新建客户端 | **4327 ms**（输出仅 46 字，与长度无关，纯握手开销） |
| 复用同一客户端 | **663 ~ 923 ms** |

**做法**：`llm_client()` 进程内单例。这一项就把端到端从约 2.5s 拉到约 1.3s。

### 2.2 启动预热必须做到"端到端跑一次检索"

**问题**：只预热编码模型是不够的——重排模型"加载了"但没"打过分"，首次成对打分仍要付 CUDA 内核编译的代价。

**实测**：评估脚本（无预热）首问 **22222 ms**，后续各题 1261~2382 ms。
**做法**：`lifespan` 里依次预热 索引 → 编码 → **端到端 `retrieve()` 一次** → 大模型连接。
**效果**：服务化后热态首问 2116 ms。

### 2.3 两级 Redis 缓存

| 场景 | 耗时 |
|---|---|
| 未命中（完整检索 + 生成） | 1520 ms |
| 命中缓存 | **24 ms** |

缓存键含**代码指纹 + 知识库指纹 + 内容哈希**三部分：改代码、重建索引、或调整 topK/权重/融合/重排器顺序，键都会变，不会复用旧结果。缓存条目里**不含 `latency_ms`**，命中时回填本次真实耗时并打上 `cached=true`。

### 2.4 响应总预算（把"通常达标"变成"有上界"）

**做法**：新增 `LLM_DEADLINE_S=3.0`。每次问答从进入 `answer()` 开始计时，扣除检索已用时后，把剩余预算作为大模型的超时上限；预算耗尽则直接返回检索原文并标记 `degraded=["llm_deadline"]`。超时**不再重试**（重试只会把耗时翻倍）。

**停机实测（强制触发）**：

| 预算 | 结果 |
|---|---|
| 3.0 s（模型未预热） | 17714 ms，`degraded=['llm_deadline']` —— 预算被冷启动吃掉，正确降级 |
| 0.05 s（强制） | **631 ms**，`degraded=['llm_deadline']`，返回检索原文 |
| 3.0 s（已预热） | 1205 / 1315 / 1931 ms，`degraded=[]`，答案正常 |

> 注意第 1 行的现象：**预算计时包含冷启动加载模型的时间**。线上服务在启动时就完成了预热，所以不会出现这种情况；但这也说明"预热失败仍继续启动"这一设计会让首问容易被预算误杀。这一点保留在此，作为已知边界。

## 3. 检索精度优化

### 3.1 融合池与用户 topK 解耦

**问题**：`retrieve()` 原本把用户的 `top_k` 同时当成"融合池大小"。用户要 8 条 → 融合后只留 8 条 → 正确片段（融合后名次第 10）**还没进重排就被砍掉**。表现为"问同一个问题，`top_k=30` 答得出、`top_k=8` 答"无法回答""。

**做法**：融合池固定 `FUSION_TOP_K=30`，`top_k` 只控制最终返回条数。
**验证**：修复后 `top_k=8` 时正确片段稳定排在第 1（bge 重排分 0.997）。

### 3.2 入库去噪

**问题**：向量召回的第一名长期是一个 **14 字**的块——内容就是「武汉兴图新科电子股份有限公司」。这是被 MinerU 标成 `text` 的页眉，跨页成批重复，与任何问题都"高相似"（0.743），纯属噪声。同类还有表格的「单位：万元」标注（出现 50 次）。

**做法**：丢弃「长度 <40 字 且 全文归一化后出现 ≥3 次」的块。
**实测代价**：丢 108 块 / 3025 块 = **3.6%**，抽样确认丢掉的全是这两类结构噪声。

### 3.3 重排器顺序与默认值（一次被自己实测推翻的配置）

**原默认**：`rerankers=["tfidf","bge"]`（便宜的 TF-IDF 先截断到 12 条，再由 bge 精排）——直觉上省 GPU 时间。

**实测推翻**：

| 问题 | 金标块 TF-IDF 名次 | 金标块 bge 名次 |
|---|---|---|
| 力源信息的法定代表人 | 15 / 20 | 4 / 1 |
| 兴图新科的注册资本 | 21 / 20 | 2 / 1 |

`CASCADE_MID=12` 意味着这两个金标**在 bge 看到它们之前就已被淘汰**，直接导致答"无法回答"。

**做法**：① 默认重排器改为单级 `["bge"]`；② `CASCADE_MID` 提到 24（只削尾不腰斩）。级联能力保留且可选，但默认不用。

**补做的调参实验（候选池 30/50/80 × 截断阈值）**：扩大候选池对召回**毫无帮助**（三档命中率完全相同：截断时 0.6087、不截断时 0.7391），
却让单次检索中位耗时从 694 ms 涨到 **1082 ms（池 50，+56%）**、1182 ms（池 80）。
即：**坏的是排序，不是池子大小**——金标本就在池内（融合名次第 10），池子变大只是把更多弱候补塞进 TF-IDF 的打分表，不改变其相对名次。
完整数据、机制分析与"真要预筛该怎么做"见专题文档 [`pitfall-tfidf-prescreen.md`](pitfall-tfidf-prescreen.md)。

### 3.4 检索层精度对比（最终结果）

| 配置 | k=4 recall | k=8 recall |
|---|---|---|
| 纯向量 + bge | 0.9565 | 0.9565 |
| 纯 BM25 + bge | 0.9565 | 0.9565 |
| **混合 + weighted + bge（默认）** | **1.0000** | **1.0000** |
| 混合 + rrf + bge | 0.9565 | 0.9565 |
| 混合 + vote + bge | 0.9565 | 0.9565 |
| 混合 + weighted，**关闭重排** | 0.6957 | 0.8696 |

**结论**：默认配置（混合 + 加权平均 + bge 重排）在 k=4 与 k=8 上都达到 **召回 100%**；关掉重排会掉到 0.8696——重排是刚需而非装饰。

## 4. 评估可信度优化：RAGAS 从 6/23 有效修到 23/23

第一轮评估四项指标**只有 6/23 条样本有效**，其余被静默打成 `nan`。定位过程：

1. 单独跑 `AnswerRelevancy` 一个指标 → **23/23 全部有效**；
2. 四个指标混在一次 `evaluate()` 里跑 → 只剩 6 条有效。

**结论**：四指标同跑会让并发请求数翻四倍，超限的样本被 `raise_exceptions=False` 静默吞掉，**均值其实只覆盖了少数样本**，而报告上完全看不出来。

**做法**：改为**逐指标串行评估**，并输出 `metric_valid`（每个指标各自的有效样本数）。修复后四次测量全部 23/23 有效。

## 5. 准确率 / 召回率 / 响应时间：优化前后对比

### 5.1 两轮完整运行的实测

| 指标 | 优化前（无预算兜底） | 优化后（含预算兜底） |
|---|---|---|
| 问答准确率（关键词判分） | **1.0000** (23/23) | **1.0000** (23/23) |
| faithfulness | 0.9855 | 0.9638 |
| answer_relevancy | 0.9544 | 0.9544 |
| context_precision | 0.8390 | 0.8780 |
| context_recall（=召回率口径） | **0.9565** | **0.9130** |
| 响应时间 p50 / p95 / max | 1557 / 8882 / 9054 ms | **1530 / 2036 / 2116 ms** |
| 超 3 秒题数 | 4 / 23 | **0 / 23** |
| 触发降级的题数 | 0 | 0 |

准确率、响应时间看起来都变好了。**但这里必须踩一脚刹车——见下一节。**

### 5.2 指标噪声底实测：上表里的 RAGAS 差值不是真实变化

我把两轮运行的**逐题检索上下文做了逐字比对**：

```
检索上下文完全相同的题: 23/23      ← 送给 RAGAS 的输入一模一样
答案完全相同的题:       18/23      ← 5 题答案有措辞差异（同为正确）
优化前 recall: 0.9565   优化后 recall: 0.9130    Δ = 0.0435
优化前 precision: 0.8390  优化后: 0.8780         Δ = 0.0390
```

**输入逐字相同，输出却差了 0.04。** 这只能来自判官模型自身的非确定性。也就是说：

- **本机 RAGAS 指标在这套 23 题上的噪声底约为 ±0.044**；
- 上表里 context_recall 0.9565 → 0.9130 **不是**预算兜底造成的退化（那一轮预算一次都没触发），而是噪声；
- 同理 precision 0.839 → 0.878 也不能当作提升。

**这条结论直接约束了验收口径**：工单要求召回率 ≥95%。本项目两轮实测为 **0.9565 与 0.9130**，噪声底 ±0.044，即 **在 23 题规模下，这个指标无法把 0.913 与 0.95 区分开**——一轮达标、一轮不达标。要给出可信结论，需要把题集扩到 100 题以上以压缩标准误。**本项目不宣称召回率"稳定达标"，只如实给出这两个测量值及其噪声底。**

> 作为对照，`tests/compare_modes.py` 给出的**确定性召回指标**（关键词判分，不经过大模型）在同一套题上是 **1.0000**，可复现、无噪声。两个指标口径不同（前者要判官逐句判断"支撑声明所需的全部信息是否都在上下文里"，后者只查关键字段是否出现），不矛盾，但**必须分别标注口径，不能混为一个数**。

### 5.3 响应时间

- **热态 p50 = 1530 ms，p95 = 2036 ms，max = 2116 ms，23 题 0 题超 3 秒** —— 满足工单 ≤3 秒要求。
- 优化前那一轮的 4 题超时（7.6~9.1s）**未能在第二轮复现**；把这 4 题单独拉出来热态重复测 3 次，均为 **1371~1602 ms**。因此判断为**外部 DeepSeek API 的瞬时抖动**，而非本系统问题（本系统自身的检索+重排稳定在 ~0.7 s）。
- 抖动无法根除，但**已被预算兜底封顶**：`LLM_DEADLINE_S=3.0` 保证最坏情况退化为"返回检索原文"而不是无限等待。降级路径已用极小预算强制实测（631 ms 完成）。

## 6. 调参项与其依据

| 参数 | 取值 | 依据 |
|---|---|---|
| `VEC_TOP_K` / `BM25_TOP_K` | 30 / 30 | 两路各召回 30 条再融合，融合池 30 条足够覆盖金标（实测金标最差名次第 21） |
| `FUSION_TOP_K` | 30 | 融合池必须显著大于用户 topK，否则金标会被截断在重排之前 |
| `RERANK_TOP_N` | 8 | 默认返回/送入上下文的条数 |
| `VEC_WEIGHT` / `BM25_WEIGHT` | 0.7 / 0.3 | 向量为主、关键词为辅；两者**先通道内归一化再加权**，否则量级不同会架空 BM25 |
| `CASCADE_MID` | 24 | 实测 12 会误杀金标（金标 TF-IDF 名次 15~21） |
| `FIELD_WEIGHTS` | title 2.0 / body 1.0 / abstract 0.6 | 章节标题是最强相关性信号；摘要为正文前缀，权重最低 |
| `RERANK_MAX_CHARS` | 512 | 打分输入截断，避免按最长序列 padding |
| `FUZZY_CUTOFF` | 65 | 3 字人名错 1 字的 `partial_ratio` 只有 66.7，设 80 会全部漏掉 |
| `EVAL_MAX_WORKERS` | 2 | ragas 默认 16 并发会打满限流；本项目还需逐指标串行 |
| `LLM_DEADLINE_S` | 3.0 | 与工单 ≤3 秒对齐，给最坏情况封顶 |

## 7. 没有做的优化（以及为什么）

- **没有做查询改写/同义扩展**：那是工单五（Query 理解优化）的范围，本工单不越界。
- **没有做向量索引调优（HNSW 等）**：当前 2917 个片段、IVF_FLAT + nlist=1024，实测向量召回 22 ms（热态），不是瓶颈。
- **没有把摘要字段改成生成式**：为 2917 个块各调一次大模型既慢又贵，且本工单未要求生成式摘要。摘要字段的边际贡献已如实标为"与正文高度相关、权重最低"。
- **没有做横向扩容压测**：工单要求"高并发下稳定"，本项目以"模型单例 + 线程池路由 + Redis 缓存 + 预算封顶"作为设计层面的回应，**未做真实压测，因此不宣称任何并发指标**。
