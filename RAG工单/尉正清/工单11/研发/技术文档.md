# 技术文档

**工单编号**：人工智能NLP-RAG项目-Embedding 模型微调任务

---

## 一、任务与技术路线

工单要求微调一个自己领域的 Embedding 模型，让检索效果比微调前更好，
并且**要有数据指标支撑**。

本工单的形态与前十个不同：它不是一个常驻服务，而是一条**一次性训练流水线** ——
产出的东西是「一个微调好的模型 + 一份可复现的评估证据」。

技术路线：

| 环节 | 选型 | 理由 |
|---|---|---|
| 基座模型 | `BAAI/bge-base-en-v1.5`（110M） | 工单点名 |
| 微调语料 | FiQA-2018（英文金融问答检索） | 自带 qrels 标注，能算标准检索指标 |
| 损失函数 | MultipleNegativesRankingLoss（MNR） | batch 内互相作负例，一次前向对比 2×batch 个候选 |
| 训练方式 | 全参数微调，自写训练循环 | 6GB 显存够用，不必引入 LoRA 的额外复杂度 |
| 评估口径 | nDCG@10 / Recall@10 / MRR@10 | BEIR 标准口径，可对外对照 |

> **关于语言**：语音料原本是中文金融年报，但 `bge-base-en-v1.5` 是纯英文模型
> （词表 30522，无中文词片），实测中文句子 48%~70% 被切成 `[UNK]`，检索接近随机，
> 微调前后都测不出有意义的结果。经确认后改用英文金融语料。
> 详见 `设计/设计说明.md` 第二节。

## 二、技术选型与版本约束

| 组件 | 版本 | 说明 |
|---|---|---|
| Python | 3.11 | conda 环境 `rag_gd` |
| PyTorch | 2.14.0+cu126 | 驱动 566.36 最高支持 CUDA 12.7 |
| transformers | **4.44.2** | 被 FlagEmbedding 1.3.3 硬锁，**不能动** |
| datasets | **2.19.0** | 同上 |
| sentence-transformers | 5.7.0 | 只用它的模型加载与编码，不用其训练器 |

### 为什么不用 `SentenceTransformerTrainer`

`sentence-transformers` 5.7.0 的 `SentenceTransformerTrainer` 内部调用
`transformers.Trainer(processing_class=...)`，而 `processing_class` 参数
**4.46 才引入**；本环境被 FlagEmbedding 锁在 4.44.2，两者对不上，一跑就报：

```
TypeError: Trainer.__init__() got an unexpected keyword argument 'processing_class'
```

**不能靠升级 transformers 解决**：这套环境同时跑着工单 01-10 的 RAG 系统，
`transformers==4.44.2` + `datasets==2.19.0` 是 FlagEmbedding 的硬性要求，
为一份训练循环把它升掉，会把已交付的系统全搞坏。

所以 `finetune.py` **自己写训练循环**。MNR 损失本质上就是一个交叉熵：

```python
candidates = positive                       # B × d（批次内负例）
scores = anchor @ candidates.t() / 0.02     # B × B
loss = F.cross_entropy(scores, torch.arange(B))
```

好处是训练循环完全透明，损失、学习率、显存都能直接打日志，交付出去别人不用啃黑盒。

## 三、文件职责与数据流

```
build_dataset.py   ① 数据集生成
      ├─ data.load_fiqa()          下载/读缓存 FiQA（corpus 57638 / queries 6648 / qrels 1706）
      ├─ data.split_queries()      按 query 切分：训练 453 / 评估 195
      ├─ mine_hard_negatives()     用基座模型检索，挖 top-50 中的难负例
      └─ 落盘 cache/fiqa/{corpus,train_triples}.jsonl + eval_set.json

gen_qa.py          ② 问答对生成（大模型）
      ├─ 排除评估集标准答案文档（防污染）
      └─ cache/fiqa/gen_pairs.jsonl     4648 条 (问题, 文档)

evaluate.py        ③ 评估器入口
      ├─ retrieval.encode()        编码语料（分块缓存）与查询
      ├─ retrieval.search()        矩阵乘 + top-k
      └─ retrieval.evaluate()      nDCG / Recall / MRR

finetune.py        ④ 微调（命令行 + 训练循环）
      ├─ freeze_bottom()           冻结底部 N 层
      ├─ 优化器 / 学习率 / 早停 / 回滚
      └─ output/bge-base-en-v1.5-fiqa

train_data.py      ④' 训练侧的两块（被 finetune.py 依赖）
      ├─ build_loaders()           去重 → 切 dev → DataLoader
      ├─ embed() / batch_loss()
      └─ mnr_loss()                MultipleNegativesRankingLoss
                                    （工单要求的「定义损失函数」在这里）

compare.py         ⑤ 对比出报告（测试/compare.py）
      └─ 读 results/{base,finetuned}.json → 测试/评估报告.md
```

依赖关系：

```
config.py ── 所有脚本共用（路径、超参、指令前缀）
data.py   ── 纯 CPU 字符串处理，不碰模型
retrieval.py ── 编码 + 检索 + 指标，被 build_dataset / evaluate 共用
finetune.py  ── 依赖 data + retrieval + config + train_data（只放流程控制）
train_data.py ── 依赖 data + config（数据管道与损失，不碰流程控制）
```

**为什么 `retrieval.py` 被训练和评估共用**：微调前后必须是同一套代码、
同一份语料、同一个指令前缀，唯一变量是模型权重 —— 否则指标差异归因不到微调本身。

## 四、核心实现要点

### 1. 按 query 切分，不按标注行切分

qrels 有 1,706 条标注，但只覆盖 648 个 query。若按**标注行**随机切 70/30，
同一个 query 的正例会同时落进训练集和评估集 —— 模型训练时见过这个问题，
评估自然答得好，指标虚高。所以按 **query** 切。

### 2. 指令前缀前后严格一致

BGE 官方用法：短查询检索长文档（s2p）时**查询侧**加
`Represent this sentence for searching relevant passages: `，文档侧不加。
FiQA 正是 s2p 场景。

训练时 anchor 也带这个前缀（`data.with_instruction()`），评估时查询侧同样带。
**一边加一边不加等于人为抬高微调收益**，对比就失去意义。

### 3. 训练样本必须去重（本工单最关键的坑）

`build_dataset.py` 按「正例 × 难负例」做笛卡尔积，一个 `(anchor, positive)`
会对应 4 行负例各异的记录（`HARD_NEG_PER_QUERY=4`）。
而训练时若不用难负例（`USE_HARD_NEGATIVES=False`），negative 列被丢掉，
**这 4 行就成了内容完全相同的样本**：

```
train_triples.jsonl   4,720 行
唯一 (anchor, positive) 1,180 组      ← 每组精确重复 4 次
```

名义上跑 4 个 epoch，实际每条唯一样本被看了 **16 遍**。
`finetune._dedupe()` 负责按 `(query_id, positive_id)` 去重。
详见 `优化/过程问题记录.md` 问题 8。

### 4. 冻住底部 6 层再微调

训练样本只有约 5.6k 条，模型有 1.09 亿参数。全参数微调会把预训练学到的通用语义
一起改掉，指标**低于**基线（0.4321 vs 0.4350）；冻住 embedding + 底部 6 层、
只训顶部 6 层（43.1M / 109.5M）之后变成 0.4412。

这是本工单从亏转盈的那一步，`--freeze-layers N` 控制。
详见 `优化/过程问题记录.md` 问题 9。

### 5. 向量缓存要带上模型身份

语料有 57,638 篇，编码一次十几分钟，必须缓存。但缓存键**不能只按语料算** ——
重训一次模型后语料没变、缓存键不变，会把**上一个模型的向量**当成新模型的用，
表现为「换了模型但指标纹丝不动」，极难排查。

`retrieval.model_salt()` 把模型路径 + 权重文件修改时间并进指纹，
重训后自动失效。

### 6. 编码分块落盘

编码中途可能被系统内存压力杀掉（本机 15.7GB，WSL 里还跑着别的服务）。
`retrieval.encode()` 每 4,000 条落一块，中断后重跑只补没算完的块。

### 7. 大模型调用要给足 `max_tokens`

`deepseek-flash` 是推理模型，reasoning token 先于正文消耗额度，
额度被吃光时**正文返回空串**（不报错，只是空）。`gen_qa._chat()`
检测到空正文就翻倍重试，最多三次。

### 8. 生成问答对必须防污染

`gen_qa.py` 生成用的文档**排除掉评估集里任何 query 的标准答案文档**，
否则等于把考题答案提前喂给模型。

## 五、使用方法

```bash
conda activate rag_gd
cd 研发

python build_dataset.py                                   # ① 数据集生成
python evaluate.py --model base                           # ② 微调前基线
python gen_qa.py --n 5000                                 # ③ 生成问答对
python finetune.py --use-gen --batch 24 --epochs 2 \
       --freeze-layers 6 --keep-last --patience 1000      # ④ 微调
python evaluate.py --model finetuned                      # ⑤ 微调后评估
cd ../测试 && python compare.py                           # ⑥ 生成报告
```

或一键跑完整条流水线：`bash 部署/start.sh`（日志在 `部署/logs/pipeline.log`）。

`finetune.py` 主要参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--freeze-layers` | 6 | **最关键的一个**：冻结 embedding + 底部 N 层，只训顶部。见核心要点 4 |
| `--epochs` | 2 | 冻结之后 2~3 轮持平，取保守值 |
| `--batch` | 24 | 不用难负例（两次前向）时的值；开 `--use-hard` 要降到 16 |
| `--lr` | 2e-5 | |
| `--use-gen` | 关 | 并入 `gen_pairs.jsonl` 扩充训练集 |
| `--use-hard` | 关 | 用难负例训练。**在 FiQA 上会掉 0.09**，见问题 7 |
| `--keep-last` | 关 | 不按 dev loss 回滚，用最后一版权重。**正式训练必开**，见问题 10 |
| `--patience` | 5 | dev loss 连续多少次没改善就停；正式训练用 1000 关掉 |
| `--temperature` | 0.02 | MNR 缩放系数的倒数；调大反而更差（0.05→0.4253，0.10→0.3898） |
| `--max-len` | 256 | 训练截断长度；评估用 512，口径差异见问题 11 |

## 七、已知限制

| 限制 | 说明 |
|---|---|
| 语料是英文 | 基座模型不支持中文，中文语料需换 `bge-m3` 一类多语言模型，属另一条路线 |
| dev loss 不能当早停信号 | 只用 batch 内负例时它随训练单调上涨，与检索质量脱钩，见问题 10 |
| FiQA 标注稀疏 | 1,706 条标注 / 57,638 篇文档 = 覆盖率 0.003%，难负例里混有假负例，见问题 7 |
| 训练截断 256 token | 语料中 19.4% 超过 256 token，训练时被截断而评估用 512，口径有偏差，见问题 11 |
| 评估集只有 195 个 query | 按 query 切分后评估集偏小，指标的统计噪声较大；`--freeze-layers` 的取值是在这个评估集上选的，口径局限已如实记录 |
| 未做超参搜索 | 2 人日工单，只沿「可训练参数量」一个维度试了 5 个点 |
