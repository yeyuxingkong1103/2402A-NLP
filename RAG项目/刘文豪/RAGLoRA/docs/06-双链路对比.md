# 手写链路 vs LangChain 链路 对比

> 日期：2026-09-16
> 切换方式：环境变量 `RAGLORA_CHAIN=langchain|manual`，重启后端生效
> **当前默认：`langchain`**（2026-09-16 用户指定）
> 样本：`--limit 5`，medical 5 题 + legal 5 题 + 拒答 3 题，共 13 题

---

## 一、为什么要做两条链路

现有手写链路（`rag_chain.py`）已跑出 **100% 来源命中率 / 100% 引用标注率**的实测成绩，
是**已验证基线**。直接换成 LangChain 会把一个已知可用的系统变成未知状态，
且一旦改造引入回归，将同时损失功能与已有指标。

因此两条链路**并存**，用配置切换。这样能现场对比，并讲清「框架省了什么、又藏了什么」——
比单纯声称「使用了 LangChain」更有说服力。

---

## 二、两条链路的分工

| 环节 | manual | langchain |
|---|---|---|
| Prompt 渲染 | `persona.render_system` | `persona.render_system`（**共用**） |
| 混合检索 | `retrieval.hybrid_search` | `HybridRetriever` → `retrieval.hybrid_search`（**共用**） |
| 精排 | `rerank.rerank` | `rerank.rerank`（**共用**，框架无该集成） |
| **编排** | 手写函数调用 | **LCEL：`prompt \| ChatOllama \| StrOutputParser`** |
| **大模型** | `llm.chat`（OpenAI SDK） | `langchain_ollama.ChatOllama` |
| 后处理 | `rag_chain.postprocess` | `rag_chain.postprocess`（**共用**） |
| 流式 | 手写 SSE 事件生成器 | LCEL `chain.stream()` + 同一套事件协议 |

**关键点**：两条链路刻意复用同一批底层能力，**差异只在编排层**。
否则对比实验没有意义 —— 那会把「编排方式的影响」和「检索质量的影响」混在一起。

---

## 三、框架覆盖了什么、没覆盖什么

### 覆盖（确实省了事）

- **编排表达**：LCEL 管道 `a | b | c` 比手写函数调用更直观，改动链路结构更容易
- **LLM 客户端抽象**：`ChatOllama` 统一了流式/非流式的接口形状
- **Prompt 模板化**：`ChatPromptTemplate.from_messages`
- **运行时能力**：LCEL 自带 `invoke` / `stream` / 批量 / 异步等调用形态

### 未覆盖（必须自研或适配）

1. **bge-m3 的 learned sparse 分支**
   LangChain 的 `Embeddings` 接口只认 dense。强行套用会**丢掉混合检索能力**，
   而混合检索正是本项目检索质量的主要来源。因此 dense 走框架、sparse 走手写、RRF 融合走手写。

2. **bge-reranker cross-encoder 精排**
   框架未提供该集成，`_rerank_step` 用 `RunnableLambda` 手工插进管道。

3. **模型单例管理**（最容易被忽略的一处）
   `langchain_huggingface.HuggingFaceEmbeddings` 会**新建一份模型实例**。
   bge-m3 fp32 约 2.3GB，本机 15.7GB 内存下两份就是 4.6GB —— 不可接受。
   因此写了 `BgeM3DenseEmbeddings` 适配器**委托给现有 `embed` 单例**，而不是直接用框架封装。
   这条已有**常驻测试**守护（`backend/tests/test_lc_retrievers.py`）：
   函数对象同一性、`langchain_huggingface` 未进入 `sys.modules`、干净子进程内
   `XLMRobertaModel` 实例恰为 1 个且就是 `embed._model`。

## 四、实测对比

### 4.1 指标（13 题）

| 角色 | 题数 | 来源命中 | 答案覆盖 | 引用标注 | 平均延迟 |
|---|---:|---:|---:|---:|---:|
| medical (manual) | 5 | **100%** | 100% | **100%** | 7.2s |
| medical (langchain) | 5 | **100%** | 100% | **100%** | 7.2s |
| legal (manual) | 5 | **100%** | 100% | **100%** | 6.1s |
| legal (langchain) | 5 | **100%** | 100% | **100%** | 8.4s |
| 拒答 (manual) | 3 | — | 100% | 66.7% | 6.0s |
| 拒答 (langchain) | 3 | — | 100% | 33.3% | 6.9s |

**结论：两条链路的检索与引用指标完全一致**，符合预期 ——
同 Prompt、同检索、同精排，差异只在编排层。

> 拒答的「引用标注」两档都低（66.7% / 33.3%），这是**样本只有 3 题**的统计噪声，
> 且拒答类回答本身就不该引用来源。**不足以得出任何链路优劣的结论**，
> 要判断需扩样本量。

### 4.2 链路耗时分解

| 环节 | manual | langchain |
|---|---:|---:|
| 查询改写 | 0 ms | 0 ms |
| 混合检索 | 329 ms | 347 ms |
| 精排 | 737 ms | 708 ms |
| 生成 | 5438 ms | 6515 ms |

检索与精排耗时基本一致（差异在噪声范围）。生成耗时 langchain 略高（+1077ms，约 +20%），
**但这不足以断定框架更慢**：生成耗时受 Ollama 输出长度与当时负载影响极大，
单次 13 题样本不足以支撑该结论。若要定论需固定问题集重复多次取中位数。

### 4.3 内存占用（后端进程，模型预热完成后）

| 链路 | 工作集 | 提交量 |
|---|---:|---:|
| manual | 4.85 GB | 6.63 GB |
| langchain | 5.33 GB | 7.36 GB |
| **差值** | **+0.48 GB** | **+0.73 GB** |

两组都**只加载了一份 bge-m3 与一份精排**（适配器生效）。
langchain 模式多出的约 0.5GB 来自 LangChain 运行时本身的依赖
（pydantic 模型、Runnable 编排机制、`langchain_ollama` 客户端栈）。

> 局限：这是**单次采样**，未做多次测量。趋势可信（框架有固有开销），具体数值仅供参考。

## 五、验证方法（如何确认后端真的切了链路）

不能只看环境变量 —— 要确认请求真的走了目标链路。本次用的判据是**日志时间戳**：

```bash
grep -c "LCEL 检索完成" backend/logs/app.log    # 评测前 23 条 → 评测后 36 条
```

langchain 模式下评测 13 题，日志新增 **13 条** `LCEL 检索完成`
（时间戳 20:13–20:14，与评测时间吻合）；manual 模式下该日志**不增长**
（手写链路打的是「检索完成」，不写 "LCEL"）。

另外 `lc_chain` 会在 `trace` 里写入 `"chain": "langchain"`，
前端「链路可视」面板可直接看到，也便于将来从接口层面断言。

## 六、取舍与结论

**这个项目的结论是：两条链路都不吃亏，各有所长。**

| 维度 | 更优的一方 | 说明 |
|---|---|---|
| 编排可读性 | LangChain | LCEL 管道更直观，改链路结构成本低 |
| 能力覆盖 | **手写** | bge-m3 sparse、cross-encoder 精排、模型单例管理，框架都不覆盖，仍需自研 |
| 资源开销 | **手写** | langchain 模式多约 0.5GB 内存 |
| 依赖可控性 | **手写** | 不引入框架版本链约束（本项目已因 ragas 的框架依赖踩过坑） |

**最值得讲的一点**：本项目的核心检索能力（混合检索 + 精排）**框架都没覆盖**，
LangChain 真正省下的是编排与 LLM 客户端抽象。这也是为什么最终选择「并存 + 可切换」，
而不是「迁移到 LangChain」—— 迁移的收益不足以抵消引入的依赖与内存开销。

## 附：复现步骤

```bash
# 1. 停后端
bash backend/shutdown.sh

# 2. 以指定链路启动（改 CHAIN 即可切换；不设则走默认 langchain）
bash backend/run.sh --bg                             # LangChain 链路（默认）
RAGLORA_CHAIN=manual bash backend/run.sh --bg         # 手写链路（备选/退路）

# 3. 跑同一套评测
cd backend && D:/anaconda3/envs/rag_env/python.exe eval/run_eval.py --limit 5

# 4. 确认链路生效（langchain 模式应有新增的 "LCEL 检索完成" 日志）
grep -c "LCEL 检索完成" backend/logs/app.log
```

> **端口提示**：本机 8000 端口可能被其它应用（实测酷狗音乐 `KuGou.exe`）抢占。
> 此时用 `RAGLORA_PORT=8001 bash backend/run.sh --bg` 换端口启动，
> 并让评测脚本指向该端口：`RAGLORA_API_BASE=http://127.0.0.1:8001/api`。
> 评测脚本已支持该环境变量覆盖。
