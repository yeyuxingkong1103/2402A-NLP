# 流程图

本文用 Mermaid 画两条主链路的流程图：**离线入库**与**在线问答**。
图中节点名与代码模块一一对应，方便对照阅读。

---

## 1. 离线：资料入库流程

从「一堆 PDF」到「Milvus 里可以检索的向量」。对应模块：
`ingest.py`（解析与分块）→ `enrich.py`（离线增强）→ `vector_store.py`（向量化与入库）。

```mermaid
flowchart TD
    A["PDF 资料目录<br/>PDF_DIR（.env 配置）"] --> B["遍历每个 PDF<br/>ingest.parse_all_pdfs()"]

    B --> C{"逐页判断<br/>有没有文本层？"}
    C -- "有文本层" --> D["PyMuPDF 提取正文<br/>parse_text_with_pymupdf()"]
    C -- "无文本层（扫描页）" --> E["PaddleOCR 识别<br/>ocr_with_paddleocr()"]
    C -- "复杂版面 / 多栏 / 公式" --> F["（可选）MinerU 解析<br/>parse_with_mineru()<br/>第 12 步实测后不接入主链路"]

    D --> G["pdfplumber 单独抽表格<br/>parse_tables_with_pdfplumber()"]
    E --> G
    F --> G

    G --> H["规则清洗<br/>clean_pages()<br/>去水印、去页眉页脚"]
    H --> I["语义切分<br/>ingest_chunk<br/>段落切 → 超长按句切 → 合并过短<br/>单块 ≤ 500 字"]
    I --> J[("data/parsed_chunks.json<br/>5 个 PDF，894 块")]

    J --> K["离线增强 enrich.enrich_all()"]
    K --> K1["LLM 生成摘要<br/>generate_summary()"]
    K1 --> K2["低质过滤<br/>remove_low_quality()<br/>80 ≤ 长度 ≤ 2000"]
    K2 --> K3["语义去重<br/>dedup_chunks()<br/>余弦相似度 ≥ 0.95 视为重复"]
    K3 --> K4["构建父子块<br/>build_parent_child()<br/>每 3 个子块挂 1 个父块"]
    K4 --> L[("data/enriched_chunks.json")]

    L --> M["BGE-m3 向量化<br/>vector_store.embed_texts()"]
    M --> M1["稠密向量<br/>1024 维"]
    M --> M2["稀疏向量<br/>词典权重"]

    M1 --> N["写入 Milvus<br/>vector_store.main() --rebuild"]
    M2 --> N
    N --> O[("Milvus 集合<br/>power_repair_docs<br/>724 条子块")]
    N --> P["同时建索引<br/>HNSW + 稀疏倒排"]

    style A fill:#e8f4ff,stroke:#409eff
    style O fill:#e6ffe6,stroke:#67c23a
    style J fill:#fff4e6,stroke:#e6a23c
    style L fill:#fff4e6,stroke:#e6a23c
```

**几个关键取舍**（详见设计文档 11、12 节）：

| 环节 | 做法 | 为什么 |
|---|---|---|
| 解析分工 | 文本层用 PyMuPDF、表格用 pdfplumber、扫描页用 OCR；MinerU 主线**不用**（第 12 步实测它会丢数字，见设计文档 11.5） | 各取所长：速度、表格结构、图片文字；版面还原能力换不来丢数字的代价 |
| 切分方式 | 只用语义切分（段落 → 句子 → 合并） | 保语义完整，避免固定长度把一句话切断 |
| 增强顺序 | 先摘要 → 再去噪 → 再去重 → 最后建父子块 | 去重放在摘要之后，用摘要比对更准；父块必须最后建，否则去重会打乱编号 |
| 向量 | 同时存稠密与稀疏 | 稠密管语义、稀疏管专有名词（如标准编号）精确命中 |

## 2. 在线：问答流程

从「用户提问」到「流式返回带出处的答案」。对应模块：
`rag.py`（主流程）→ `optimize.py` / `retrieval.py` / `prompt.py` / `postprocess.py` / `memory.py`。

```mermaid
flowchart TD
    A["用户提问<br/>POST /chat"] --> B["取短期记忆<br/>memory.get_short_memory(user_id)<br/>Redis 最近 10 条"]
    B --> C{"有历史吗？"}
    C -- "有" --> D["查询改写<br/>optimize.rewrite_query()<br/>把「那具体呢」补全成完整问题"]
    C -- "没有" --> E["直接用原问题"]
    D --> F["生成缓存键<br/>optimize.cache_key()<br/>cache:rag:answer:{用户}:{角色}:{归一化问题}"]
    E --> F
    F --> G{"非流式？<br/>且缓存命中？"}
    G -- "命中" --> G1["跳过检索与生成<br/>但仍写回记忆<br/>save_turn()"]
    G1 --> Z["返回结果<br/>cache_hit = true"]
    G -- "未命中" --> H["混合检索<br/>retrieval.hybrid_search_milvus()"]

    H --> H1["稠密检索 dense<br/>取 40 条"]
    H --> H2["稀疏检索 sparse<br/>取 40 条"]
    H1 --> H3["RRF 融合 rrf_fuse()<br/>按名次倒数加权"]
    H2 --> H3
    H3 --> I["Milvus 路候选 20 条"]

    I --> J["多路召回 fuse_multi_route()"]
    K["MySQL 历史对话路<br/>search_mysql() 10 条<br/>权重 0.5 降权"] --> J
    J --> L["去重后候选集"]

    L --> M["交叉编码器精排<br/>retrieval.rerank()<br/>BGE-reranker-v2-m3"]
    M --> N{"相关度 ≥ 0.3？"}
    N -- "低于阈值" --> N1["丢弃"]
    N -- "达标" --> O["保留，取前 5 条 top_k=5"]
    O --> P["附加父块全文<br/>attach_parent_text()<br/>子块命中 → 补上所在父块"]

    P --> Q["长期记忆单独召回<br/>rag.collect_long_memory()<br/>不进精排，避免自我强化"]
    B --> R["组装提示词<br/>prompt.get_system_prompt(角色)<br/>+ 历史 + 上下文 + 长期记忆"]
    Q --> R
    P --> R

    R --> S["调用 DeepSeek<br/>call_deepseek_stream()<br/>SSE 逐段返回"]
    S --> T["后处理<br/>postprocess<br/>去多余空行、规范标点、清理行尾"]
    T --> U["校验<br/>validate_answer()<br/>是否有依据、是否说了「无依据」"]
    U --> V["写回三处<br/>save_turn()"]
    V --> V1[("MySQL<br/>messages 两张行<br/>user + assistant")]
    V --> V2[("Redis<br/>短期记忆 mem:short:<br/>user_id")]
    V --> V3[("Milvus<br/>长期记忆 power_repair_memory")]
    V --> W["SSE 推给前端<br/>正文帧 + 结束信息帧<br/>含 sources/usage/long_memory_used"]
    W --> X["前端逐段渲染<br/>气泡 + 引用来源折叠面板"]

    style A fill:#e8f4ff,stroke:#409eff
    style X fill:#e6ffe6,stroke:#67c23a
    style G1 fill:#fff4e6,stroke:#e6a23c
    style Q fill:#f0e6ff,stroke:#a06ee0
```

**几个关键设计**（详见设计文档 12–15、16.9 节）：

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 缓存键用「原问题」 | `cache_key` 用归一化后的**原始问题**，不用改写后的问题 | 改写结果依赖历史，同问题在不同轮次会改写不同 → 键不稳定，缓存永远不命中（第 8.5 步修复） |
| 长期记忆不进精排 | 走独立召回路径，不参与 reranker | 长期记忆存的是「问题+答案」，与提问高度相似，会把真实条款挤出前几名（第 8.5 步修复） |
| 缓存命中仍写回 | 命中只跳过检索与生成，`save_turn` 照常执行 | 否则这一轮不进记忆，下一轮 history 缺一段，多轮对话断片（第 9.7 步修复） |
| MySQL 路降权 | 融合权重 0.5 | 历史提问与当前问题词面接近，不降权会压过知识条款 |
| 父子块 | 子块用于检索（向量准），父块用于喂模型（上下文全） | 兼顾检索精度与上下文完整性 |

## 3. 流式输出（SSE）帧结构

`POST /chat` 传 `{"stream": true}` 时，服务端逐帧推送。前端不用 `EventSource`
（它只支持 GET），而用 `fetch` + `ReadableStream` 手写解析，详见接口文档第 11 节。

```mermaid
sequenceDiagram
    participant U as 前端 Chat.vue
    participant B as 后端 app.py
    participant R as rag.py
    participant L as DeepSeek

    U->>B: POST /chat {stream:true}
    B->>R: _stream_chat() 生成器
    R->>L: 流式调用
    loop 每积满一行
        L-->>R: 文本片段
        R-->>B: 后处理后的片段
        B-->>U: data: 正文片段\n\n
    end
    R->>R: save_turn() 写回三处记忆
    R-->>B: 结束信息 JSON（sources/usage/long_memory_used）
    B-->>U: data: {...}\n\n
    B-->>U: data: [DONE]\n\n
    U->>U: 渲染气泡与引用来源，解除输入禁用
```

> 说明：结束标记 `[DONE]` **一定**会出现——正常结束时推；出错时先推错误帧、
> 再推 `[DONE]`，保证前端读取循环能退出。详见接口文档 11.2。
