## 二、任务一：RAGFlow 解析流程分析

### 2.1 不同 parser_id 的分块策略与 Redis Stream 触发流程

RAGFlow 支持多种 chunking method，对应不同的 `parser_id`：

| parser_id | 分块策略 | 适用场景 |
|---|---|---|
| `paper` | 按论文结构（摘要、章节、段落）切分 | 学术论文、专利 |
| `table` | 表格优先，保留行列结构 | 表格密集型文档 |
| `one` | 整篇文档作为 1 个 chunk | 短文 |
| `knowledge_graph` | 基于实体-关系图结构切分 | 知识图谱场景 |
| `manual` | 按说明书章节切分 | 技术说明书 |
| `general` | 通用递归切分 | 通用文本 |
| `laws` | 按法条切分 | 法律文本 |

**触发流程：**

1. **前端上传文件** → 调用 `v1/document/run` 接口
2. **API Server 的 `document_app.py` 的 `run` 函数**：校验权限 → 生成任务列表
3. **`task_service.py` 的 `queue_tasks` 函数**：按文档类型和页数切分任务 → 通过 `REDIS_CONN.queue_product` 放入 **Redis Stream 消息队列**
4. **Task Executor 从 Redis Stream 消费**：调用 `do_handle_task` 处理

**关键代码路径：**
- `api/apps/document_app.py` — `run` 接口
- `api/db/services/task_service.py` — `queue_tasks`
- `rag/svr/task_executor.py` — `do_handle_task`

### 2.2 `do_handle_task` 的主要逻辑

`do_handle_task` 是 RAGFlow 的任务处理函数，负责文档解析、分块、向量化和索引的完整流程。

**主要逻辑：**

```python
async def do_handle_task(task):
    # 1. 进度回调：偏函数固定 task_id 等参数
    progress_callback = partial(set_progress, task_id, task_from_page, task_to_page)
    
    # 2. 检查任务是否取消
    # 3. 绑定嵌入模型
    embedding_model = LLMBundle(task_tenant_id, LLMType.EMBEDDING, ...)
    
    # 4. 初始化知识库索引（按向量维度）
    init_kb(task, vector_size)
    
    # 5. 按任务类型分流
    if task_type == "raptor":
        chunks = run_raptor(...)       # RAPTOR 递归抽象
    elif task_type == "graphrag":
        chunks = run_graphrag(...)     # GraphRAG 图构建
    else:
        chunks = build_chunks(...)     # 标准分块
    
    # 6. 向量化：embedding(chunks, embedding_model, ...)
    # 7. 批量插入 docStore（Elasticsearch / Infinity）
    # 8. 更新文档统计（token 数、chunk 数）
```

**用到的技术：**

| 技术 | 作用 |
|---|---|
| `functools.partial` | 固定回调参数 |
| `trio.to_thread.run_sync` | 异步执行同步 I/O |
| `DOC_BULK_SIZE` | 批量插入 |
| 混合检索权重 | `tkweight=0.7, vtweight=0.3` |
| RAPTOR | 递归抽象摘要 |
| GraphRAG | 实体-关系图构建 |

### 2.3 DeepDoc 内置解析器及 PDF 解析技术

**DeepDoc 的两大组成：**
1. **视觉处理**（Vision）
2. **解析器**（Parser）

**内置解析器：**

| 解析器 | 支持格式 | 说明 |
|---|---|---|
| PDF | `.pdf` | **最复杂**，含 OCR、布局分析、表格识别 |
| DOCX | `.docx` | 纯文本，无需 OCR |
| EXCEL | `.xlsx` | 表格结构保留 |
| PPT | `.pptx` | 逐页提取 |
| Image | `.jpg/.png` | OCR + VLM 描述 |
| Audio | `.mp3/.wav` | 语音转文本（需配 ASR） |

**PDF 解析的 6 个步骤：**

1. **转图像**：`zoomin=3` 放大，提升 OCR 精度
2. **OCR**：文字识别
3. **布局分析**（`_layouts_rec`）：识别标题、正文、表格、图片
4. **表格提取**（`_extract_table_figure`）：输出 HTML 格式表格
5. **文本合并**（`_concat_downward`）：合并多段落
6. **输出**：带页码和矩形位置的文本块

**DeepDoc 用的模型：**
- OCR（光学字符识别）
- TSR（表格结构识别）
- DLR（文档布局识别）
- 都是 **ONNX** 格式，在 `rag/res/deepdoc/` 目录

**PDF 解析关键代码路径：**
- `deepdoc/parser/pdf_parser.py` — PDF 解析主流程
- `deepdoc/vision/ocr.py` — OCR
- `deepdoc/vision/layout_recognizer.py` — 布局识别
- `deepdoc/vision/table_structure_recognizer.py` — 表格结构识别

## 四、过程问题记录

### 问题 1：RAGFlow 端口冲突

- **现象：** 启动时 MySQL 端口 3306 被占用
- **原因：** 已有的 `mysql-user` 容器内部用了 3306
- **解决：** 改 `.env` 的 `EXPOSE_MYSQL_PORT=13307`，对外暴露改 13307

### 问题 2：pip/Docker 镜像拉取超时

- **现象：** `nvidia_cudnn`、`elasticsearch` 等大镜像拉取超时
- **解决：** 配 Docker 镜像加速器，逐个拉镜像

### 问题 3：DeepSeek VLM 解析失败

- **现象：** `stream error: stream ID 9; INTERNAL_ERROR`
- **原因：** DeepSeek VLM 接口不稳定
- **解决：** 换智谱 GLM-4V

### 问题 4：智谱 VLM 限流 429

- **现象：** `该模型当前访问量过大`
- **原因：** `glm-4.6v-flash` 免费版限流严重
- **解决：** 关闭 RAGFlow 内置 VLM，改用独立 GLM-4V 生成图像描述，作为 txt 上传

### 问题 5：txt 文件不能解析

- **现象：** `当前解析配置不支持该文件类型`
- **原因：** 用了 PDF 的 Paper 模板
- **解决：** 重新选解析方法 `General` + 模型 `deepseek-v4-flash`

### 问题 6：ES 启动慢导致 RAGFlow 崩溃

- **现象：** RAGFlow 反复 `Restarting`，报 `Failed to ping Elasticsearch`
- **原因：** ES 启动慢，RAGFlow 启动时连不上
- **解决：** 等 1~2 分钟，ES healthy 后 RAGFlow 自动恢复

### 问题 7：GLM-4V 图像描述不准确

- **现象：** 描述中 X3、h1、h2 含义错误
- **原因：** VLM 对机械图纸理解有偏差
- **解决：** 人工修正 3 处描述
