# 工单17 设计说明

**工单编号**：人工智能NLP-RAG-解决API服务并发瓶颈与资源泄漏
**目标**：定位并修复 RAGFlow API 服务在 10+ 并发下的响应劣化与资源问题

---

## 一、总体思路

工单给了四条「初步根因推测」（模型重复加载、无队列限流、缓存未释放、连接池泄漏）。
**这些推测方向都有道理，但先验地去查会白费功夫** —— 本工单实际的做法是：

```
先测量（哪些资源真的紧张、延迟到底花在哪）
   ↓
再定位（火焰图 + 代码调用链）
   ↓
后修改（只改被证实有问题的地方）
   ↓
复测（同场景、同脚本、可对比）
```

工单备注里也是这个意思：「建议使用**假设-验证-修改**的方法，务必在每次修改前后
进行可对比的基准测试」。

## 二、诊断设计

### 2.1 三个层次同时采，互相印证

| 层次 | 手段 | 回答什么问题 |
|---|---|---|
| **系统层** | `docker stats` + `nvidia-smi` + `redis-cli XLEN` | 资源真的不够吗？有没有泄漏？ |
| **进程层** | `py-spy` 采样（60s / 50Hz） | CPU 时间花在哪些函数上？ |
| **代码层** | 静态分析调用链 | 为什么是这些函数？ |

**关键设计**：三个层次要**同时**看。只看火焰图会以为「分词器慢」，
只看资源监控会以为「一切正常」；合起来才看明白是**在等而不是在算**。

### 2.2 火焰图必须看 self time

火焰图的父帧是累计值，直接看会得出错误结论。
本设计里把 py-spy 的 `--format raw` 导出来自己统计叶子帧，
才得到「12.7% 的样本停在 `concurrent.futures` 的 `_worker`」这个决定性线索
—— 线程池里的线程在**等**。

### 2.3 压测设计

| | 场景A | 场景B |
|---|---|---|
| 并发 | 20 | 10（5 问答 + 5 上传解析） |
| 目的 | 高频问答下的延迟与稳定性 | 混合负载下解析任务是否正常入队、不拖累问答 |
| 关注 | P50/P95/P99、失败率、内存曲线 | 服务不崩、队列被消费 |

**为什么问答问题要轮换**：JMeter 用 CSV 轮换 6 道题，
避免全部请求命中同一个缓存路径，测出来偏乐观。

## 三、修复设计

### 3.1 主修：把阻塞调用挪出事件循环

**问题**：`retrieval()` 是同步函数，内部三次阻塞 HTTP（嵌入 / ES / 重排），
却被 async 的 `async_chat()` 直接调用 → 冻住整个事件循环。

**方案选择**：

| 方案 | 取舍 |
|---|---|
| 把 `retrieval()` 改成 async，内部逐处 `await` | 改动面大，且会波及所有调用方 |
| **在调用方用 `asyncio.to_thread()` 整体包住**（采用） | **改动最小、语义最清晰**：这一整段本来就是阻塞的，整体扔进线程池即可 |
| 换成 httpx 异步客户端 | 要动 LLM/ES 的底层封装，风险大、收益不明显 |

选第二条。两个调用点（`async_chat` / `async_ask`）都改了。

### 3.2 次修：nginx 上游地址

`localhost` → `127.0.0.1`。见 `优化/过程问题记录.md` 第 6 条。

### 3.3 缓解：重排候选数上限

**这是硬件约束的妥协，不是 bug 修复。** 本机 GPU 的重排吞吐实测约
**60 个 (query, doc) 对/秒**，20 并发 × 16 候选 = 320 对 ≈ 5.3 秒纯 GPU 时间，
单独就超过 3 秒的整个预算。

做成外部可配（`.env` 里的 `RERANK_MAX_CANDIDATES`），设 4 时预算降到 1.3 秒。
**代价是召回率**：重排只在前 4 条里选。这个取舍要按业务场景定，所以做成配置项
而不是写死。

### 3.4 配套：嵌入模型挪到 GPU

原来 bge-m3 在 CPU 上。20 并发下 CPU 嵌入成为并行瓶颈（实测吞吐 8.5 req/s，
单请求从 0.14s 劣化到 2.27s）。挪到 GPU 后与重排共用一张卡，
两者共 3.4GB 显存，装得下。

### 3.5 可观测性：集成 Prometheus

**设计要点**：指标走**独立端口**（9390），不经过 nginx、不占业务端口。
理由：压测把业务端口打满时，监控端点必须仍然可达，否则最关键的时刻反而看不到数据。

暴露六类指标：请求量（按路由/状态码）、延迟直方图、在途请求数、进程 RSS、
CPU、解析队列深度。分桶按实测分布设计（2/3/5/10/20/30/60 秒），
让 P95 落在有区分度的桶里。

## 四、已知局限

1. **P95 未达标**（19.3s vs 要求 3s）。链路两端（纯检索 P95 1.9s、
   LLM P95 2.8s）都不慢，但合起来 15 秒的额外开销还没定位完。
   下一步见 `测试/性能测试报告.md` 第五节。
2. **重排吞吐是硬件下限**。即使链路优化到极致，20 并发 × 16 候选仍要 5.3 秒。
   要达标必须配合减少候选数或换显卡。
3. **12 小时长稳测试没跑满**。10 分钟实测内存 +8% 后走平，趋势是好的，
   但验收要求的是 12 小时，需要单独排期跑。
