# 医小助 · 答辩演示稿

## 一、开场（30 秒）

大家好，我演示的项目是**医小助**——一个基于检索增强生成（RAG）的 AI 健康顾问。
它解决一个问题：通用大模型回答健康问题时会"一本正经地胡说八道"，
我的方案是让回答**只基于权威临床指南**，并且带页码引用、可溯源。

系统支持多角色（全科/西医/心理）、图片识图问答、急症识别、个人病情追问，
全链路本地部署，共 22 个 Python 模块，每个不超过 150 行，由测试自动守护。

## 二、架构总览（1 分钟，配合 docs/03 架构图）

```
用户输入 ──► 安全层（急症关键词/免责） ──► 意图分流（7 类）
   │                                        │
   ▼                                        ▼
图片 OCR（PaddleOCR）            检索：BM25 + Milvus 向量双路召回
   │                              → RRF 融合 → bge-reranker 重排
   ▼                                        │
LLM（DeepSeek）◄── prompt 组装（角色人设+指南片段+历史+记忆）
   │
   ▼
回答 + 页码引用 + 免责声明
```

- **存储**：Milvus（知识库 4272 条 + 长期记忆）、Redis（短期会话）
- **模型**：BGE-m3 嵌入、bge-reranker-v2-m3 重排、DeepSeek-chat 生成，全部本地/国内可达

## 三、核心技术点（每个按"问题→方案→效果"讲）

### 3.1 混合检索 + 重排
- **问题**：纯向量检索对药名、专业术语召回差；纯关键词不理解语义。
- **方案**：BM25（jieba 分词）与 Milvus 向量各召回 top-k，RRF 融合（向量路权重 ×2），
  再用 bge-reranker-v2-m3 精排，相关度低于 0.3 不作答。
- **效果**：清单型问题（"不能吃什么"）能召回盐/脂/酒/糖多条，而不是一两条。

### 3.2 文档解析分层策略（老师点名 MinerU/PaddleOCR，重点讲）
按数据形态选解析器，三者各司其职、不重复造轮子：

| 数据形态 | 工具 | 说明 |
|---|---|---|
| 有文本层的电子版 PDF | **PyMuPDF** | 主链路：页眉页脚剥离+水印过滤+表格提取，入库 2477 条 |
| 纯图片的扫描版 PDF | **MinerU 4.0** | 离线批量：版面分析+OCR 引擎，两份扫描版指南入库 1795 条 |
| 用户运行时上传的图片 | **PaddleOCR** | 在线识别：化验单/药盒拼入 RAG 问答 |

- 扫描版 PDF 没有文本层可抽，PyMuPDF 无能为力——MinerU 是兜底；
- 会话中的图片需要秒级响应，走轻量 PaddleOCR，而非重量级 MinerU。

### 3.3 图片识图链路（B 场景）
- 图片先压缩（长边 1200px）再识别，实测耗时从 47.6s 降到约 15s，识别行数不变；
- 按"文件名:大小"指纹缓存，Streamlit 重跑不重复 OCR；
- 启动时后台线程预热模型，首次上传从 29s 降到约 7s；
- 15 张真实图片（4 化验单 + 11 药品）实测全部识别成功，平均置信度约 0.95。

### 3.4 意图分流（7 类）
急症 / 系统能力 / 情绪 / 身体症状 / 个人病情 / 化验单解读 / 知识问答，
每类有专属处理路径和提示词，避免"一上来就检索"的粗暴流程：
- 系统能力（"你能做什么"）→ 不走检索，直接返回预设文案；
- 化验单图片 → 提取异常项拼成检索词，绝不反问；
- 情绪表达（"心里堵得慌"）→ 先接住情绪，再给方法，最后引导就医；
- 身体症状（"心悸/头晕"）→ 先追问关键信息（起病/持续时间/伴随症状）再建议。

### 3.5 三层急症处理（安全设计亮点）
1. **关键词识别**：胸痛、晕厥、呼吸困难等命中即绕过模型，固定文案提示拨打 120；
2. **容错**：常见错别字（胸通/胸疼/心口痛）直接命中——**宁误报、不漏报**，
   因为急症场景下"先跟用户确认"本身就可能延误救治；
3. **动态判断**：追问中发现急症信号（伴随胸痛/意识不清），随时可升级到急症路径。

### 3.6 角色差异化
同一问题不同角色回答视角不同：角色检索增强（心理医生偏向情绪/压力词汇）、
专属人设提示词、禁用术语过滤（如心理角色不推荐具体药物）。

### 3.7 记忆
- 短期：Redis 存最近对话，超出窗口自动截断；
- 长期：Milvus 向量化存储用户既往病史/用药，检索时召回相关记忆拼入 prompt。

### 3.8 工程守护
pytest 17 个用例，其中守护测试自动检查：src 不超过 24 个文件、每个文件 ≤150 行——
用测试锁住工程约束，而不是靠自觉。

## 四、数据指标（主动报数）

| 指标 | 数值 |
|---|---|
| 知识库总量 | 4272 条（电子版 2477 + 扫描件 1795） |
| 覆盖文档 | 高血压防治指南 2025（电子版 71 页 + 扫描版 15 页节选）、成人高血压食养指南 2023 扫描版 56 页 |
| OCR 实测 | 15/15 识别成功，平均置信度约 0.95，压缩后单图约 15s |
| 检索阈值 | 重排相关度 < 0.3 不作答（防瞎编） |
| RAGAS 评测 | 4 题四指标：召回 0/1/0.5/1，精度均值 0.55，忠实度均值 0.68，相关性均值 0.94 |
| 测试 | 17 passed |

### 4.1 评测结果分析（老师看到分数大概率追问，主动讲）

> 指标覆盖两个维度：上下文召回率/精度评**检索**，忠实度/答案相关性评**生成**。
> 急症场景不进 RAGAS，用规则断言（"胸痛"必出 120 提示）单独测试。

| 追问 | 回答 |
|---|---|
| 为什么不用 FactualCorrectness？ | 它依赖参考答案，而我们的参考答案摘自知识库原文、与检索内容同源，再评事实正确性是逻辑循环；且该指标在 RAGAS 0.2 + DeepSeek 下有兼容问题。四指标已覆盖检索和生成。 |
| 吃盐题召回率 0.0 怎么回事？ | 参考答案写的是"盐勺、隐性盐"，命中的原文 chunk 写"5 g 以下"，表述颗粒度不一致被 Judge 误判；人工核对该数字确实召回了，模型回答也明确写出"不超过 5 克"，是评测口径问题不是系统缺陷。 |
| 精度低说明什么？ | 相关内容能检索到，但排序还不够靠前，这是 rerank 重排序的后续优化空间——评测本身帮我们定位了改进方向。 |
| 忠实度为什么不到 0.9？ | 扣分来自回答末尾的"补充提示"通用知识段落；该段在界面上已显式标注"非指南原文"，是设计内的诚实补充，不是模型瞎编。 |

## 五、现场演示流程（约 8 分钟）

1. **能力自述**：问"你可以做什么" → 不走检索直接回答
2. **知识问答**：问"高血压患者每天吃盐不能超过多少克" → 引用**扫描版**食养指南页码（展示 MinerU 成果）
3. **清单检索**：问"高血压不能吃什么" → 分条列举
4. **角色切换**：切心理医生问"睡眠不好想的很多" → 心理视角
5. **个人病情**：说"我最近血压偏高" → 先结论后追问；补充"在吃氨氯地平" → 追问不重复
6. **症状追问**：说"头晕两天了" → 先关注、追问关键信息
7. **急症识别**：输"胸痛" → 红色急症提示；再输错别字"胸通" → 同样触发（安全容错）
8. **图片识图**：传药盒图问"这是什么药" → OCR 解读；传化验单 → 化验单解读模式
9. **收尾**：指着界面强调常驻免责声明 + "不提供诊断处方"

## 六、预设 Q&A

**Q：怎么防止大模型胡编？**
> 三道防线：重排相关度 <0.3 拒答；提示词强制"仅基于参考资料回答"；引用页码可溯源。

**Q：为什么不用 LangChain 全家桶？**
> 只用 langchain-openai 对接 LLM 和消息封装，RAG 主链自研编排——检索、融合、重排、
> 意图分流都是按业务定制的，框架通用组件反而绑手绑脚。

**Q：扫描件为什么要用 MinerU 而不是 OCR 直接识别？**
> MinerU 先做版面分析（区分标题/表格/正文）再 OCR，保持文档结构；
> 裸 OCR 逐行识别会丢失阅读顺序，表格会碎掉。

**Q：急症为什么直接绕过大模型？**
> 固定文案零延迟、零幻觉风险，急救提示不需要生成，只需要准确和快。

**Q：多轮追问怎么避免机械重复？**
> prompt 约束"结合前序对话递进追问，不得重复已回答信息"，例如用户提到多个症状时改问"同时出现还是分别出现"。

**Q：项目局限？**
> 知识库仅两份高血压相关指南，覆盖面窄；OCR 依赖图片清晰度；未做在线知识更新。
> 后续可扩展更多指南、接入检验知识库解读化验单异常项。
