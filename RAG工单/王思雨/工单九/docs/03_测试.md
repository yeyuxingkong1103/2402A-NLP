### 0.2 偏差二：附件把汉字输出成**康熙部首**，会让检索整体失配（已修）

pdfplumber 抽出的是 `银⾏`/`⻛险`/`⾦融`/`⾼`/`⼒` 这类**康熙部首与 CJK 兼容字形**（U+2E80–U+2FDF），
不是标准汉字。若不归一化，`银行` 与 `银⾏` 永不相等 → **BM25 分词与图谱实体链接会整体落空，且不报错**。

实测处理：
- `unicodedata.normalize("NFKC", …)` 能修 **23 种**（`⾏→行`、`⾦→金`、`⾼→高`、`⼈→人`…）；
- **NFKC 修不了 CJK 部首补充区**——本附件残留 **2 种**：`⻛`(U+2EDB→风)、`⻓`(U+2ED3→长)，须手工补映射；
- 归一化函数 `C.fix()` 落在 `app/config.py`，并接入 `graph_rag._norm` 与题集加载，**题面与参考答案两侧都过**。

**解析器自检（已内置，反例必拦）**：
- 文件不存在 → 抛 `RuntimeError` 并给出"放到 data/ 下或用 --sample-pdf"的具体动作；
- 三级解析器（MinerU → pdfplumber → pymupdf）全失败 → 抛 `RuntimeError` 并列出三级各自失败原因；
- 切不出题（版式与解析器口径不符）→ **直接中止并报错，不给任何结论**，同时把解析结果写进 JSON 供人工校对；
- 解析出的题数会打印出来并提示人工核对。**首版解析器正是被这条自检拦下的**：原正则要求
  `问题\s*(\d+)`（带编号），而本附件的标记是「`问题：`」**无编号**，导致切出 **0 题**；
  并且它同时暴露了上面的康熙部首问题（见 `docs/02_研发.md` §4 的 D6/D7）。

### 5.7 为什么 recall 达不到 0.90（**结构性原因，附实测证据**）

这不是调参不够，而是**该类参考答案的性质决定的**：

1. **Q03/Q04 的参考答案是"综述/推断性长文"**，不是原文摘录。例如 Q03 的参考答案写的是
   "拨备覆盖率的持续优化确保了银行在经济低迷时期能够吸收潜在不良资产的冲击"——
   这是**写题人的推论**，任何单一原文片段都不会逐字支持它。RAGAS 的 `context_recall`
   按"参考答案的每一条 claim 是否能在 contexts 里找到支撑"计分，**推断性 claim 天然找不到支撑**。
2. **实测证据（排除"检索没找到"这个可能）**：对 Q03 检索到的 8 个片段做词命中统计——
   `风险管理` 出现在 **5/8** 个片段、`不良贷款` **3/8**、`拨备覆盖率` **1/8**、`逾期` **1/8**。
   **金标主题确实被检索到了**；recall 仍为 0，说明缺口在"参考答案的表述无法逐句归属"，而非检索失败。
3. **加宽候选池无效**：把 `RERANK_N` 从 6 提到 12，recall **纹丝不动仍是 0.3375** ⇒ 瓶颈不在截断，在 claim 归属。
4. **问题拆解只对事实题有效**：把问题按标点拆成子查询后，Q02 的 recall 升到 **1.0**、Q01 到 **0.6**，
   但 **Q03/Q04 仍是 0.0**——再次印证：事实题能救，综述题救不了。
5. **★社区摘要消融给出决定性对照**：`USE_COMM` 开/关实测——
   **关**：Q01 0.60 / Q02 0.75 / Q03 0.00 / Q04 0.00；**开**：**Q01 1.00 / Q02 1.00** / Q03 0.00 / Q04 0.00。
   同一个开关能把事实题拉到满分，**对综述题却毫无作用**。若是"检索不够好"，社区摘要应当也能帮上综述题——
   它没有。这在机制上排除了"检索能力不足"这一解释。

**诚实结论**：`context_recall ≥ 0.90` 在这 4 道**含综述型参考答案**的题上**未达成**，
且**不是靠调 `HOPS`/`RERANK_N`/权重能达成的**。若要达成，需要的是"参考答案本身改写为可归属的事实清单"，
那是**改题**（工单禁止），不是改系统。

### 5.8 判官噪声实测：**这是本单评估层最重要的一个发现**

第一轮跑完后发现一个**说不通的现象**：`before`（08 原链路，输入 contexts 逐字不变）
在不同轮次给出 **0.80 / 0.55 / 0.7024** 三种 precision、**0.4904 / 0.1875 / 0.2067** 三种 recall。
**同输入不同分**，说明结论不可用。于是做了隔离实验——**拿同一批已存的 contexts，只重跑判官，不重跑检索与生成**：

| 判官设置 | `context_precision` 三次 | 极差 | `context_recall` 三次 | 极差 |
|---|---|---|---|---|
| 08 默认（未设温度） | 0.7107 / 0.7107 / 0.7107 | 0.0000 | 0.1875 / 0.2067 / **0.3750** | **0.1875** |
| **本单改设 `temperature=0`** | 0.7107 / 0.7024 / 0.7024 | 0.0083 | 0.2260 / 0.1875 / 0.1875 | **0.0385** |

**结论与处置**：
- 根因是**判官跑在 DeepSeek 的默认温度下**，`recall` 这种需要逐条 claim 判定的指标抖动尤甚
  （极差 **0.1875**，是原先假设噪声底 ±0.05 的 **3.75 倍**）；
- **未设温度时，任何单次 recall 结果都不能用来比较配置**——本单前两轮的对比数据因此全部作废；
- 处置：在 `app/eval_ragas.py` 用**本单自建**的 `_judge0()`（`temperature=0.0`）替代 08 的判官
  （**不改 08 一行代码**），噪声降到 0.0385，落回 ±0.05 内；
- **验证**：改后 C1 与 C2 两次独立运行的 `context_precision`/`context_recall` **完全一致（0.80 / 0.3375）**，
  证明测量链已确定性。

> 这条与既有记忆 `ragas-with-deepseek-gotchas` 里"噪声底 ±0.05、比较前必须先量"一脉相承，
> 但把口径推进了一步：**±0.05 只在判官温度为 0 时成立；默认温度下的实际噪声可达 0.19**。

### 5.6 本轮暴露的评估器缺陷（已修，D7）

**before/after 的时延曾不可比**：`main()` 里 `for which in ("before","after")` 让 **before 先跑并独自承担冷启动**，
实测把 before 的 Q01 记成 **18276 ms**（纯属模型加载），而 after 因模型已热只记 2788 ms —— 会得出
"after 比 before 快 6 倍"的**完全错误**结论。修法：在两条链路开跑前先预热检索栈（`retrieve_after("预热")`）。
**这类偏差不报错、只体现在数字上**，与 D2（`codes` 静默失效）属同一类。

### 5.3 评估口径（为保证结论可信而预先声明）

1. **before 必须重跑**，不引用 08 归档的旧数字——08 归档用的是它自己的 10 题，
   题不同则指标不可比。本单的 before = **同一 3 题跑 `工单八.app.rag_core.answer(mode="graph")`**。
2. **逐指标串行**：工单九只跑工单点名的两项，且一项跑完再跑下一项
   （既有记忆 `ragas-with-deepseek-gotchas`：四指标混跑会把并发翻倍触发限流，样本被打成 nan）。
3. **nan 记 None、不入均值**，并上报每个指标的**有效样本数**（`valid_llm_context_precision_with_reference`）；
   绝不把 nan 当数字。
4. **402 会让整轮静默作废**：整体失败时如实打印失败原因，`ragas` 字段留空而不是填 0。
5. **比较前先量噪声底**：本单沿用 08 的 `scripts/measure_noise.py` 口径（噪声底 ±0.05）。
   若 after 相对 before 的提升小于噪声底，**不得声称有提升**。
6. **指标卡在目标线附近时不得声称达标**（如 0.79 vs 0.80 不算达标）。
7. 复用的是 08 已实测的判官与嵌入**单例**（`工单八.app.evaluate._judge/_emb`）——
   每个指标各建一次会把 bge-m3 反复搬上 GPU，8 G 显存在第 6 次加载就 CUDA OOM。

### 6.1 关于端到端 max = 3246 ms 的**声明口径**（避免被误读为"优化回退"）

附件 **4 题口径**下、同一环境、模型预热后、全部 `use_cache=false` 的端到端时延（真值见 `eval/before.json` / `eval/after.json`）：

| 链路 | p50 | max | 越过 3 秒的题 |
|---|---|---|---|
| before（08 原链路） | 2999 ms | **4189 ms** | Q01 |
| **after（工单九优化）** | **2678 ms ≤ 3000 ✅** | **3246 ms** | Q04（超 **246 ms**） |

**本单声明的口径**：
> **「稳态 p50 = 2678 ms ≤ 3 秒，且检索侧有 3 秒预算的降级兜底」**。
> **不声明"任何一次都 ≤ 3000 ms"**——后者与实测不符（after 的 Q04 = 3246 ms）。

**两条必须连同一起读的事实**：

1. after 的 max 落在 **Q04（跨机构综述题：题面最长 + 无图约束 ⇒ 上下文来源最杂）**，**不是首个请求**，
   故**不是冷启动**（评估脚本已在两条链路开跑前预热检索栈，见 §5.6 / 缺陷 D7）；
2. **before 的 max 为 4189 ms**，比 after **更早、更大幅度**地越过 3 秒线 ⇒
   "偶发越线"是**两条链路共同面对的边界**，**不是本次优化引入的回退**。

**因此明确不做的三件事**（不为凑 max ≤ 3000 ms 引入无谓风险）：
不把 `LLM_MAX_TOKENS` 压到实测拐点以下（300 是"时延—精度"拐点：800 超 3 秒，250 使 precision 掉到 0.7167）、
不改写题目来缩短生成、不为边缘抖动加工程手段——**根因是单次生成固有的长尾，工程手段解决不了它**。
