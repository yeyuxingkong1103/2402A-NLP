## 2. 三类通信路径（这是本设计的核心分类）

| 类型 | 对端 | 容器内写法 | 为什么不能混用 |
| --- | --- | --- | --- |
| **A. 编排内服务** | redis、rag-api、prometheus | **服务名**：`redis:6379` | compose 自动为同一 network 的服务注册 DNS；写 `localhost` 会指到容器自己 |
| **B. 宿主机上的服务** | Ollama(11434)、RTMPServer(1935) | **`host.docker.internal`** | 容器有独立 network namespace，`127.0.0.1` = 容器自身，**不是**宿主机 |
| **C. 外部互联网/内网服务** | 后续接入的第三方 API | 直接域名/IP + 走宿主机 NAT | 自定义 bridge 默认 SNAT 出网，无需额外配置 |

**B 类是本工单最容易踩的坑**：Win/Mac 的 Docker Desktop 自带 `host.docker.internal`
解析，但 **Linux 上不存在该域名**，必须在 compose 里显式声明：

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"      # 由 Docker 注入一个指向宿主网关的条目
```

本设计的 compose 对 `rag-api` 与 `rag-ui` 都声明了它 —— 这样同一份 compose
**在 Windows/macOS 与 Linux 上行为一致**，迁服务器不用改配置。

## 3. 自定义 bridge 网络（为什么不用默认 bridge）

```yaml
networks:
  rag-net:
    name: rag-net
    driver: bridge
    ipam:
      config:
        - subnet: 172.28.0.0/16
```

| 决策 | 理由 |
| --- | --- |
| **自定义 bridge** 而非默认 `bridge` | Docker 的**默认 bridge 不提供服务名 DNS**，容器只能靠 `--link`（已废弃）或 IP 互访；自定义 bridge 内置 DNS 解析 |
| **固定子网 `172.28.0.0/16`** | ① 保证服务 IP 稳定、排障可预期；② 避免与宿主局域网/公司网段（常见 `192.168.*`、`10.*`、`172.17.*`）撞车；③ 多套编排并行时可换 `NETWORK_SUBNET` 隔离 |
| **显式 `hostname`** | 日志与 `/metrics` 里能直接看出是哪个服务；部分场景按 hostname 做路由 |
| **`name:` 固定网络名** | 默认会加项目前缀（`rag-finqa_rag-net`）；固定后，**外部服务（如 RTMP 容器）可以用 `docker network connect rag-net <容器>` 直接接入** |

## 4. 与 RTMPServer 的通信（工单点名的场景）

RTMP 服务器（1935）通常**不在本 compose 里**，两种接入方式：

### 方式一：RTMP 跑在宿主机（本机当前形态）

```
容器 rag-api ──TCP──▶ host.docker.internal:1935 ──▶ 宿主 RTMPServer
```

容器内验证命令（`部署/脚本/health.ps1` 的【⑥ 网络连通性】会自动执行）：

```powershell
docker exec rag-api python -c "import socket;s=socket.create_connection(('host.docker.internal',1935),5);print('tcp-ok')"
```

### 方式二：RTMP 也是一个容器（推荐）

```powershell
# 把既有的 RTMP 容器接进本编排的网络（名字固定为 rag-net，就是为了这一步）
docker network connect rag-net rtmp-server
# 然后容器内直接用服务名互访
docker exec rag-api python -c "import socket;s=socket.create_connection(('rtmp-server',1935),5)"
```

> 本机实测：**1935 端口当前无服务监听**（RTMP 未运行），因此测试只做"探测并留证据"，
> 不断言必须在线。证据：`测试/测试数据/网络连通性-rtmp.json` 与截图 `容器网络连通性验证.png`。

## 5. 端口规划

| 宿主端口 | 容器端口 | 服务 | 是否必须对外 |
| --- | --- | --- | --- |
| **8200** | 8200 | rag-api（正式 API） | ✅ **工单指定端口** |
| **8201** | 8201 | rag-ui（中文 Web 界面） | ✅ **工单指定端口** |
| 6379 | 6379 | redis | ⚠️ 仅调试需要；生产建议**注释掉**（编排内用服务名互访，不需要暴露到宿主） |
| 9090 | 9090 | prometheus | ⚠️ 建议只在内网暴露（`127.0.0.1:9090:9090`） |

**安全提醒**：Redis 已设 `--requirepass`（`.env` 里的 `REDIS_PASSWORD`），
但把 6379 直接发布到宿主仍是风险面；`部署/配置/.env.example` 里已注明生产应注释该映射。

## 6. 网络相关环境变量

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `NETWORK_NAME` | `rag-net` | 网络名（多环境隔离用） |
| `NETWORK_SUBNET` | `172.28.0.0/16` | 子网（避让现有网段） |
| `RAG_LLM__OLLAMA_BASE_URL` | `http://host.docker.internal:11434` | Ollama 地址（容器视角） |
| `DEPLOY_REDIS_URL` | `redis://:ragfinqa@redis:6379/0` | Redis 地址（服务名 + 密码 + DB） |
| `DEPLOY_REDIS_TIMEOUT_S` | `0.5` | Redis 连接/读写硬超时（**防止网络问题拖垮问答**） |
| `RAG_TEST_RTMP_PORT` | `1935` | 测试里探测的 RTMP 端口（阈值配置化） |

## 8. 故障排查速查

| 症状 | 最可能原因 | 排查命令 |
| --- | --- | --- |
| 容器内连不上 Ollama | 用了 `127.0.0.1` 而不是 `host.docker.internal` | `docker exec rag-api python -c "import socket;socket.create_connection(('host.docker.internal',11434),3)"` |
| Linux 上 `host.docker.internal` 解析失败 | 缺 `extra_hosts: host-gateway` | `docker exec rag-api cat /etc/hosts` |
| 容器间互访失败 | 不在同一 network | `docker network inspect rag-net --format '{{range .Containers}}{{.Name}} {{end}}'` |
| 宿主连不上 8200 | 端口未发布或服务只听 `127.0.0.1` | `docker port rag-api`；确认 `DEPLOY_API_HOST=0.0.0.0` |
| Redis 连接慢拖垮问答 | 未设超时 | 已由 `DEPLOY_REDIS_TIMEOUT_S=0.5` + 熔断兜底；查 `/health` → `degraded_reason` |
| 子网与公司网段冲突 | `172.28/16` 撞车 | 改 `NETWORK_SUBNET` 后 `docker compose down && up -d` |
