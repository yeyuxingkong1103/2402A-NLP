# RAG 知识问答系统 Constitution

> **地位声明**：本宪法是「RAG 知识问答系统」项目的最高指导原则，凌驾于所有其他实践、惯例与临时决策之上。所有 spec / plan / tasks / 实现代码 / 测试 / 文档必须与本宪法保持一致。与宪法冲突的任何改动一律不得合入。
>
> **Version**: v2.6.0 | **Ratified**: 2026-08-29 | **Last Amended**: 2026-08-30

---

## Core Principles（核心原则，NON-NEGOTIABLE）

### I. 单一需求文档 + 版本化（Single Source of Truth）

- 全项目**只有一份需求文档**：`docs/需求说明.md`。规格链产物围绕它展开，禁止另立多份需求文档。
- 需求文档首个版本为 **v1**，之后**每次迭代 / 优化必须升级版本号**（v1 → v2 → v3 …），并记录版本迭代表（版本号 / 日期 / 本次改动 / 涉及文件）。
- **每次迭代 / 优化完成，必须向用户明确汇报「本次改了什么」**（改动清单：涉及条目、文件、影响范围），禁止静默修改。
- **每个版本必须配套一份架构图**：以架构分层图绘制当版本系统架构，必须按 **呈现层 → 接口层 → 服务层 → 管线层 → 数据层 → 外部** 六层展开，明确展示数据流、模块边界与技术组件，存放于 `docs/架构/架构图-vN.md`，文件名含版本号，与需求文档版本一一对应。
- 口头需求、临时想法不直接进入实现，必须先回写需求文档 / 规格链。

### II. 规格链驱动（Spec-Driven）

- 一切功能从规格链出发，规格链产物（spec → plan → tasks → checklist）是唯一被认可的需求来源与事实源。
- **该原则对第一个需求与后续所有迭代 / 优化一视同仁**：后续任何改动（哪怕只改一行代码、一个参数）都必须先走完整规格链，取得对应规格条目后方可实施。
- 任何实现、测试、验收都追溯到规格文档中的一条明确条目；规格未覆盖的改动视为违规。
- 若实现中发现规格缺陷，先回写规格并获得批准，再改代码；禁止先改代码后补文档。

### III. 设计先于编码，测试先于实现（TDD）

- 创造性工作（新增功能、修改行为）必须先从 `superpowers:brainstorming` 出发探索意图、约束与设计。
- 实现阶段强制 TDD：先写失败测试 → 再写实现使其通过 → 重构（Red-Green-Refactor）。
- **禁止「先写代码再补测试」**；无测试覆盖的代码不得合入。

### IV. 数据真实性（Data Authenticity）

- 知识库、评测、示例中的任何内容必须来自**真实数据源**（真实 PDF / 真实文档 / 真实查询），**严禁编造、虚构或臆造数据**。
- 无法确证的内容必须标注「未知」或「待核实」，**禁止用占位假数据填充**。
- 向量库、索引、检索结果必须可回溯到 `data/` 中的原始文档。
- **回答必须可溯源到页码**：chunk 元数据必须包含页码（page）等溯源字段，回答引用须能定位到原始文档的具体页码；禁止无溯源依据的回答。
- 评测指标必须来自真实运行结果（`eval/` 中真实语料与真实查询跑出的结果），**禁止编造、预估或伪造指标**。
- 回答生成：无检索依据时必须诚实兜底（如「知识库中未找到相关依据」），禁止编造引用或结论。

### V. 目录边界（Directory Boundaries）

- 目录结构定死（见 Technical Constraints），**禁止跨越**：代码只落在 `backend/` 与 `scripts/`，文档只落在 `docs/`，原始数据只落在 `data/`，评测产物只落在 `eval/`，前端只落在 `frontend/`。
- 新增任何文件前先判断归属目录；不确定时必须询问，禁止擅自落地。

- **嵌入模型禁止走 Ollama**：bge-m3 必须由本地代码直接离线加载 `D:\八维学习\bge-m3`，**禁止调用 Ollama 中的 bge-m3 / bge-large 模型**（本地 Ollama 虽装有 `bge-m3:latest`、`bge-large-zh-v1.5:latest`，一律不得使用）。

- 依赖版本必须在 `requirements.txt` 中**精确锁定**（固定版本号），禁止浮动版本（`>=`、`~=` 等）。
- 新增第三方依赖必须在 plan 阶段说明理由，未经规格链审批不得引入。
- 技术栈任何变更 = 宪法修订，须走 Governance 流程。

## Development Workflow（研发流程，强制）

### 1. 需求入口（唯一，适用于一切需求）

- **一切需求都必须经过本流程——包括第一个需求，以及后续所有迭代 / 优化 / 功能变更 / 问题修复**：入口一律是 **`superpowers:brainstorming`**，先探索意图、约束与设计，再进入规格链。
- **禁止例外条款**：不得以「小改动」「微调」「临时修复」「顺手优化」「跟上次一样的改动」等理由跳过 brainstorming 或规格链中的任何一步；**后续每一次迭代 / 优化都视为一次完整的新需求**，必须完整走一遍规格链（specify → clarify → plan → tasks → checklist）。
- 禁止跳过 brainstorming 直接进入实现；口头需求、临时想法不直接进代码，必须先走规格链。

### 2. 规格链（顺序固定，不得跳步、不得逆序）

```
speckit-specify → speckit-clarify → speckit-plan → speckit-tasks → speckit-checklist
```

- 规格链产物是唯一事实源；plan / tasks / checklist 必须逐条回溯到 spec，任何偏离需回写 spec 重新批准。
- 实现阶段使用 speckit implement 交互模式，逐任务推进，保持与 tasks 清单一致。

### 3. 快速通道（用户专属豁免，仅限小改动）

> **目的**：避免「只改一点点」也被完整规格链拖累。**判定权只属于用户本人**——只有用户亲口明确指示「只改这一个点」时才能走快速通道；Claude Code 一律不得自行认定某改动为小改动而跳过流程。

**允许走快速通道的改动（必须同时满足）**：

1. 用户明确指示，且改动能用一句话说清（改一个参数值 / 文案 / 格式 / 阈值 / 单点 bug 修复）。
2. 不触碰红线（见下方禁止清单）。

**快速通道流程**：

- 直接实施改动 → 运行相关测试确认通过 → **向用户汇报：改了什么、影响什么** → 在 `docs/需求说明.md` 追加一行记录并升级版本号（vN → vN+1）→ 更新 `docs/版本迭代.md`。
- 不强制走 brainstorming 与规格链，但**版本号、汇报、测试三项要求不变**。
- **架构图规则**：
  - 架构图必须使用分层表达，且每版图中都要显式包含 **呈现层、接口层、服务层、管线层、数据层、外部** 六层；层级顺序不得打乱，层名不得省略。
  - 改动**不涉及模块关系 / 数据流**（纯参数值、文案、格式、阈值、单点 bug 修复）→ **不强制重画架构图**，但在 `docs/需求说明.md` 本次记录中注明「架构图沿用 vN，未变化」。
  - 改动**涉及模块间关系、数据流、调用链**（即使一句话能说清）→ **必须同步更新架构图**为 `docs/架构/架构图-vN+1.md`，保持架构图与代码实际一致；禁止出现「架构图与代码脱节」的状态。

**禁止走快速通道（必须走完整流程）**：

- 触碰**技术栈**（Python 版本 / LangChain / FastAPI / Qdrant / 嵌入模型 / LLM 接入方式）
- 触碰**目录结构**（新增或移动顶层目录、跨目录迁移文件）
- 触碰**对外契约**（API 路由、请求 / 响应格式、SSE 事件、配置项名称）
- 触碰**数据源与数据真实性**（入库数据、评测集、检索逻辑、编造数据的任何风险）
- 改动**跨多个模块 / 影响架构**（即使一句话说清，只要动到链路结构就须走完整流程）
- 用户语气模糊或未明确授权时，一律走完整流程。

**红线提示**：Claude Code 若以「这是小改动」为由跳过流程，且实际触碰上述任何一条，视为违反宪法，改动不得合入。

### 4. 需求文档版本化 + 指标比对（强制）

- 全项目只有一份 `docs/需求说明.md`，首版 **v1**。
- 每次迭代 / 优化：升级需求文档版本（v1 → v2 → v3 …）→ 更新版本迭代表 → 更新对应架构图 `docs/架构/架构图-vN.md` → **向用户汇报改动清单**。
- 版本迭代记录统一维护在 `docs/版本迭代.md`。

#### 指标比对（强制，仅完整规格链迭代必出）

- **指标对比文档只维护一份**：全项目仅一份人读的指标对比文档 `docs/指标对比/优化指标对比.md`，每轮完整规格链迭代后向其**追加**该版本成绩，最终形成「各版本对比表（版本 / 检索指标 / 生成指标 / 变化）+ 提升归因」；**禁止每版另立新文档**。快速通道改动不追加。
- 每轮评测的**原始机器结果**落盘 `eval/results/vN_metrics.json` 留档（不计入文档份数，用于追溯与复盘）。
- **基线定义：v1 版本（MVP 基线版）跑评测集得出的成绩即基线**，后续所有版本（v2、v3 …）均以 v1 基线为准绳对比。v1 的评测结果落盘 `eval/baseline/`。
- 比对基准为**两列**：**v1 基线**（看累计进步）+ **上一版 vN-1**（看本次增量）。
- **评测集规模下限（对齐任务书，不可低于）**：检索集 **≥10 条**、生成集 **≥5 条**、安全集 **≥10 条**。
- 评测集存放于 `eval/sets/`；评测集允许随 RAG 项目演进而修改，但每次修改必须在指标对比文档中注明改动内容，保证指标可比性可追溯。
- 指标必须来自**真实运行结果**，禁止编造、预估或伪造（见 Core Principles IV）；无真实评测数据时，指标对比文档必须如实标注「未评测」，禁止用假设数字充数。
- 具体指标口径（如 Hit@k / MRR@k / 要点覆盖率等）在项目首个迭代时与用户确认后确定，本宪法不预先限定。

### 5. 实现阶段（强制 TDD）

- 写代码阶段**必须使用 TDD**（`superpowers:test-driven-development`）：先写失败测试 → 实现 → 重构。
- 测试使用 pytest，命名 `test_` 前缀，放在与代码同模块的 `tests/` 目录。
- 测试必须使用真实数据或明确标注的 fixture，禁止用假数据充数。
- 每次改动后必须运行全部相关测试，全部通过才算完成。

### 6. 质量段

- 调试：`superpowers:systematic-debugging` — 遇 bug / 测试失败先定位根因再修复。
- 审查：`superpowers:requesting-code-review` — 完成 / 合并前请求审查验证。

## Coding Standards（编码规范，统一，全项目强制）

### 命名

- 变量、函数、方法一律 `snake_case`；类名 `PascalCase`；常量 `UPPER_SNAKE_CASE`。
- 禁止拼音命名；保留通用英文缩写（`embedding`、`retriever`、`chunk`）。

### 类型注解（强制）

- 所有公开函数、方法必须包含完整的参数类型注解与返回类型注解。
- 容器类型必须精确（`list[str]`、`dict[str, Any]`），禁止裸 `list` / `dict`。
- 关键业务结构使用 Pydantic 模型或 `dataclass` 定义。

### 风格

- 遵循 PEP 8；使用 `ruff` 或 `black` 统一格式化（全项目同一工具，禁止混用）。
- 每个模块、每个公开函数必须有简短中文 docstring 说明用途。
- 魔法数字必须提取为命名常量。
- 禁止硬编码路径 / 密钥 / 模型名 / 端口；一律走配置（`.env` / 配置对象）。

### 测试规范

- 每个功能模块必须有对应测试；测试断言要具体，禁止只测不报错。
- 测试不依赖真实网络 / 外部服务时不得联网；依赖 Ollama / 模型时用 fixture 显式标记。

## Security & Data Requirements（安全与数据要求，NON-NEGOTIABLE）

1. **禁止编造数据** — 见 Core Principles IV。
2. **禁止越界读写** — 所有文件读写严格限定在本项目目录内；`D:\八维学习\bge-m3` 是获准只读访问的外部模型数据源，除该路径外不得读取、写入、删除项目目录之外的任何路径。
3. **密钥走环境变量** — API Key、token、凭据禁止硬编码进源码或提交版本库；统一 `.env` 注入，提供 `.env.example` 占位（不含真实值）；日志与异常信息禁止输出密钥与敏感数据。
4. **禁止擅自更改技术栈与目录结构** — 变更须走宪法修订流程。

## Governance（治理）

- 本宪法是项目最高规范，任何 PR / review / 实现都必须校验合规性。
- 宪法修订流程：文档化修改动机 → 说明影响范围 → 获得批准 → 更新版本号与 `Last Amended` 日期 → 记录修订日志。
- 违反「禁止事项」与「技术栈 / 目录结构定死」条款的改动，一律不得合入。
- 每次迭代的改动与版本号必须向用户汇报（见 Development Workflow §3）。
