## 一、系统定位

本工单在 01 工单（基础 RAG 问答）之上，针对**检索准确率**做端到端优化，目标：

- 问答准确率 **≥ 90%**；
- 从提问到返回答案 **≤ 3 s**。

优化主线一句话概括：**让正确的片段排到前面（排序优化），让答案直接从原文抽出来（合成优化）**。

---

## 二、优化前后的链路对比

| 阶段 | 优化前（01 工单基线） | 优化后（本工单） |
|---|---|---|
| PDF 解析 | `page.get_text()` 直接取全文 | 版式清洗 + 表格结构化 + 行合并 + 标题识别 |
| 分块 | 固定 500/80 字符递归切片 | 结构感知分块 + 表格原子块 + 父子块 |
| 查询 | 原始问题整句检索 | 确定性 Query 理解 → 多路查询 |
| 召回 | 向量 Top-6 + BM25 Top-6 → RRF | 向量 Top-15 + BM25 Top-15 → RRF |
| 重排 | 无（仅 RRF 排名） | 加权线性重排（5 维信号） |
| 答案 | 本地 `deepseek-r1:1.5b` 生成 | 抽取式答案合成（带页码引用） |

## 四、四条可对比链路（消融设计）

为把"检索优化"和"答案合成优化"的贡献分离开，引擎提供四条链路：

| 链路 | 检索 | 答案合成 | 用途 |
|---|---|---|---|
| `baseline` | 基线检索（固定切片 + RRF） | 本地 LLM 生成 | **复刻 01 工单，优化前基准** |
| `baseline_extractive` | 基线检索 | 抽取式合成 | 消融：仅换答案合成 |
| `optimized` | 优化检索（结构分块 + 多路召回 + 重排） | 抽取式合成 | **本工单最终方案** |
| `optimized_llm` | 优化检索 | 本地 LLM 生成 | 消融：仅换检索 |

对比结论：基线瓶颈在"**排序不准 + 生成幻觉**"——Top-K 召回率两者均为 100%，但基线 Top-1 命中率仅 60%、答案命中率 60%；优化后答案命中率提升到 100%。

## 五、核心数据流（在线问答）

以「武汉兴图新科电子股份有限公司注册资本是多少？」为例：

```
用户提问
   │
   ▼
[1] Query 理解（query_understanding.py，~1ms）
     · 噪声剥离：剔除"武汉兴图新科电子股份有限公司""是多少"
     · 关键词：["注册资本"]            ← 真正关键的实词
     · 答案类型：amount（命中"注册资本/资本"）
     · 多路查询：["注册资本", "注册资本", "注册资本 万元 %"]
   │
   ▼
[2] 多路混合召回（retriever.py）
     · 向量召回：bge-m3 + FAISS，每路 Top-15
     · 词法召回：BM25Okapi（jieba 搜索引擎分词），每路 Top-15
     · RRF(k=60) 融合两路排名 → 候选集合
   │
   ▼
[3] 加权线性重排（reranker.py）
     score = 0.30·向量 + 0.20·BM25 + 0.25·关键词覆盖率
           + 0.15·数值匹配 + 0.10·实体匹配 (+0.03 表格加成)
     → 取 Top-N（ANSWER_POOL=25 供答案合成）
   │
   ▼
[4] 抽取式答案合成（answer_builder.py）
     · 候选句收集：块正文 + 父块 → 句子 / 表格行（剔除标题行）
     · 逐句打分（关键词覆盖 / 类型信号 / 实体 / 定义式 / 章节先验
                 / 对比词惩罚 / 套话惩罚）
     · 取 Top-3，单页限流 2 句，按分数排序拼装
   │
   ▼
输出："根据招股说明书第22页、第52页：注册资本，5,520.00 万元，法定代表人，程家明；……"
     （附页码引用，可溯源、零幻觉）
```

## 六、为什么这样设计

### 6.1 为什么做版式清洗与表格结构化

招股说明书每页页眉重复出现"武汉兴图新科电子股份有限公司 招股意向书"，页码行也高频重复。这些行在向量化时形成高频噪声，稀释真正语义；财务数据又以表格形式密集出现，固定长度切片会把表头与数据切断。因此解析阶段必须"去噪 + 保结构"。

### 6.2 为什么用结构感知分块 + 父子块

固定长度切片会跨小节切断语义（"串味"）。结构感知分块先按标题切出语义小节，再在小节内切片；同时保留"小节全文"作为父块，子块用于**精确检索**，父块用于**补全上下文供答案抽取**，兼顾精度与完整性。

### 6.3 为什么做多路查询与重排

基线把整句问题丢给检索，公司全称等高频词占据语义权重，导致"答非所问"。剥离噪声后得到核心问句，再配合关键词组合、实体增强三路查询并行召回；重排阶段引入**关键词覆盖率、数值线索、实体匹配**等内容级信号，把真正含答案的片段顶上来。

### 6.4 为什么用抽取式而非 LLM 生成

需求同时要求"准确率 ≥ 90%"与"响应 ≤ 3 s"。本地 `deepseek-r1:1.5b` 属推理型模型，回答前输出长思维链（基线平均 3.53 s、个别 >10 s），既慢又不稳定，还存在数值张冠李戴的幻觉。金融招股说明书问答的答案多是"原文事实句 / 表格行"，抽取式合成可做到**零幻觉、可溯源、毫秒级**。

## 七、稳定性与容错设计

| 场景 | 处理机制 | 代码位置 |
|---|---|---|
| 空问题输入 | 返回空分析结果，答案合成输出兜底话术 | `query_understanding.analyze` / `build_answer` |
| 向量检索异常 | 捕获异常并降级为 BM25 单路结果 | `HybridRetriever._vector_retrieve` |
| LLM 调用异常 | 捕获并返回可读提示，不抛出 | `QAEngine._invoke` |
| PDF 单页解析异常 | 单页文字 / 表格解析失败时降级跳过 | `pdf_parser.parse_pdf` |
| FAISS 中文路径写入失败 | 临时 ASCII 目录桥接后再拷贝回目标目录 | `knowledge_base.save_local/load_local` |
| 长时运行 | 向量库与 BM25 索引进程内构建一次并复用；界面用 `st.cache_resource` 缓存引擎 | `retriever.BM25Index` / `app.get_engine` |
