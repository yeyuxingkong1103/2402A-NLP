# 部署文档

> 已在 Ubuntu 22.04 / 24.04 上完成部署验证，脚本同样适用于 CentOS 系与主流云服务器。
> 部署相关文件统一放在 `deploy/` 下：`install.sh`（安装）、`run.sh`（启动）、
> `shutdown.sh`（停止）、`docker-compose.yml`（依赖服务编排）。

## 1. 环境要求

| 项 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| CPU | 2 核 | 8 核 | 向量化与重排耗 CPU |
| 内存 | 8 GB | 16 GB | 低于 8GB 时 BGE 模型与 Milvus 同时运行易 OOM |
| 磁盘 | 20 GB | 50 GB | 模型约 6.5GB（BGE 系列 4.5GB + MinerU 约 2.0GB）+ 向量数据 + 镜像 |
| GPU | 不需要 | NVIDIA 6GB+ | 有 GPU 时向量化快 5–10 倍 |
| 系统 | Ubuntu 20.04+ / CentOS 7+ | Ubuntu 22.04+ | |
| Docker | 20.10+ | 24+ | 需含 compose 插件 |

> **内存是最容易踩的坑**：本机实测 7.6GB 内存下，同时跑「评测判分 + 数据采集」
> 会把 swap 打满并触发 OOM。部署后如需跑评测，建议错开执行。

## 2. 部署架构

```
┌─────────────────────────── 单台服务器 ───────────────────────────┐
│                                                                  │
│   FastAPI 服务 (:8000)  ←── deploy/run.sh 启动，日志落 logs/     │
│        │                                                         │
│        ├── MySQL   :3306   ←┐                                    │
│        ├── Redis   :6379    ├── docker compose 拉起              │
│        └── Milvus  :19530  ←┘   (含 etcd + MinIO)                │
│                                                                  │
│   /root/models/bge-m3            本地模型，约 2.3GB              │
│   /root/models/bge-reranker-v2-m3 本地模型，约 2.2GB             │
│   /root/.mineru/models           MinerU 模型，约 2.0GB           │
│   mineru/.venv                   MinerU 独立环境（子进程调用）    │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    DeepSeek API（公网 HTTPS）
```

## 3. 部署步骤

### 3.1 获取代码与模型

```bash
git clone <项目地址> /root/rag-project
cd /root/rag-project

# 模型需单独下载放到上级目录（合计约 4.5GB）
pip install -U "huggingface_hub[cli]"
export HF_ENDPOINT=https://hf-mirror.com          # 国内网络建议走镜像
huggingface-cli download BAAI/bge-m3 \
  --local-dir /root/models/bge-m3
huggingface-cli download BAAI/bge-reranker-v2-m3 \
  --local-dir /root/models/bge-reranker-v2-m3
```

> 若模型放在别处，改 `.env` 里的 `EMBEDDING_MODEL_PATH` / `RERANKER_MODEL_PATH` 即可。
> 下载超过 5GB 的模型前请先确认磁盘余量。

**MinerU（PDF 解析主路径）是可选组件**：它要求 `openai<3`，与主环境的 `openai` 3.x 冲突，
因此装在项目内的独立 venv（沿用 `evals/.venv` 的做法），由 `pdf_service` 以子进程调用。
不装也能用——PDF 会走兜底三件套，这条路径的依赖（`pymupdf` / `pdfplumber` /
`paddlepaddle` / `paddleocr`）已写进 `requirements.txt`，随主环境一起装好。

`deploy/install.sh` **默认不装**（依赖 6.4GB + 模型 0.8GB，不该让每次部署都付这笔开销）。
需要完整解析能力时加参数：

```bash
./deploy/install.sh --with-mineru
```

手动安装等价于：

```bash
python3 -m venv mineru/.venv
mineru/.venv/bin/pip install mineru==4.0.5
MINERU_MODEL_SOURCE=modelscope mineru/.venv/bin/mineru-models-download \
    --tier basic --small-backend torch -s modelscope
```

> **CUDA 版本必须对齐**：`pip install mineru` 默认拉到的 torch 是 cu130 构建，
> 而本机驱动 566.36 只支持到 CUDA 12.7，会导致 `torch.cuda.is_available()` 为
> `False`、MinerU 静默退回 CPU。需按 README「PDF 解析（MinerU）」一节换成
> cu126 的 torch，并用 `mineru-kit models show` 确认后端是 `torch` 而非 `onnx`。

> 模型约 2.0GB，落在 `/root/.mineru/models/`；模型源默认 `modelscope`
> （`MINERU_MODEL_SOURCE`，本机 huggingface.co 直连不通）。
> 不装也能启动服务：上传 PDF 时自动降级为**三件套兜底**——PyMuPDF 取文本层、
> PaddleOCR 补图表文字、pdfplumber 还原表格，扫描件与图表照样能读出内容，
> 代价是慢（28 页文档约 283 秒，MinerU 主路径约 38 秒）。相关开关：`MINERU_BIN` /
> `MINERU_TIER` / `MINERU_TIMEOUT`。

### 3.2 安装 Docker（如未安装）

```bash
# Ubuntu / Debian
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker

# CentOS / RHEL
sudo yum install -y yum-utils
sudo yum-config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo yum install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo systemctl enable --now docker
```

### 3.3 配置

```bash
cp .env.example .env
vim .env       # 至少填写 DEEPSEEK_API_KEY
```

| 变量 | 必填 | 说明 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 是 | 大模型密钥 |
| `MYSQL_PASSWORD` | 是 | 需与 compose 中一致 |
| `REDIS_PASSWORD` | 是 | 同上 |
| `EMBEDDING_MODEL_PATH` | 是 | BGE-M3 本地路径 |
| `RERANKER_MODEL_PATH` | 是 | Reranker 本地路径 |

### 3.4 一键安装

```bash
chmod +x deploy/*.sh
./deploy/install.sh
```

脚本按四步执行：**环境检查 → Python 环境 → 依赖服务 → 初始化数据库 → 构建知识库**。
首次运行会拉取镜像并构建知识库（约 2.5 分钟，视 CPU/GPU 而定），依次执行：

```
scripts.knowledge_base      全量重建，产出 13432 条
scripts.dedup_kb --apply    去重，产出 13364 条
scripts.build_law_index     构建 MySQL 法条索引（4068 条）
```

> 去重这步不能省。源数据里有 68 条记录只差标点写法、归一化后文本完全相同，
> 全量重建会把它们变成重复切片。**13364 是去重后的数字**，
> 本文档与 README 中引用的切片数均以此为准。

可选参数：

```bash
./deploy/install.sh --skip-docker   # 依赖服务已在别处运行
./deploy/install.sh --skip-kb       # 跳过知识库构建，稍后手动执行
```

### 3.5 启动与验证

```bash
./deploy/run.sh -d                                  # 后台启动
curl http://127.0.0.1:8000/api/health        # 四个依赖应全为 true
curl http://127.0.0.1:8000/api/stats | head  # 知识库应为 13364 条
```

接口文档：`http://<服务器IP>:8000/docs`，演示账号 `demo / demo123`。

### 3.6 停止

```bash
./deploy/shutdown.sh          # 只停 API
./deploy/shutdown.sh --all    # 连 Redis / MySQL / Milvus 一起停
```

## 4. 云服务器适配

### 4.1 通用注意事项

| 事项 | 说明 |
|---|---|
| 安全组 | 需放行 **8000**（API）、可选 22（SSH）。**3306 / 6379 / 19530 不要对公网开放** |
| 数据盘 | 模型与 Milvus 数据建议挂载到数据盘，避免占满系统盘 |
| 内存 | 2C4G 的入门机型跑不动，至少 2C8G |
| GPU 机型 | 阿里云 gn 系列、腾讯云 GN 系列、算力云的 GPU 实例均可 |

### 4.2 阿里云

```bash
# 镜像：Ubuntu 22.04 64位；实例规格建议 ecs.g7.xlarge(4C16G) 及以上
# 安装 Docker
curl -fsSL https://get.docker.com | sh
# 镜像加速（可选）
sudo mkdir -p /etc/docker && sudo tee /etc/docker/daemon.json <<'EOF'
{ "registry-mirrors": ["https://<你的加速器地址>.mirror.aliyuncs.com"] }
EOF
sudo systemctl restart docker
```

### 4.3 腾讯云

```bash
# 镜像：Ubuntu 22.04；安全组放行 8000
# 腾讯云内网访问 DeepSeek API 无需额外配置，直接公网出网即可
sudo systemctl enable --now docker
```

### 4.4 算力云（GPU 实例）

```bash
# 确认驱动与 CUDA
nvidia-smi
# 有 GPU 时无需额外配置，torch 会自动使用；可在日志中确认
#   "加载 BGE-M3: /root/models/bge-m3 (fp16=True)"
```


## 6. 常见问题

| 现象 | 原因与处理 |
|---|---|
| `/api/health` 中 milvus 为 false | 容器未起或仍在初始化，`docker logs milvus-standalone` 查看；Milvus 冷启动约需 30–60 秒 |
| 检索报 `collection not loaded` | Milvus 重启后集合不在内存。代码已做自动重新 load 重试；仍失败则重启容器 |
| `Connection refused` 到 Redis | 容器被停。WSL 环境下发行版空闲休眠会带走容器，`docker start redis` 并设置 `--restart unless-stopped` |
| 回答为空但无报错 | `deepseek-flash` 是推理模型，`max_tokens` 被推理过程吃光。调大 `.env` 的 `LLM_MAX_TOKENS` |
| 首次提问特别慢 | BGE-M3 与 Reranker 懒加载，首次请求需数十秒；之后常驻 |
| 上传 PDF 后 `watermark.path` 为 `pymupdf` | MinerU 未安装或解析失败，接口已自动降级为三件套兜底。查 `logs/app.log` 里的 `MinerU 解析失败` 告警；确认 `mineru/.venv/bin/mineru-kit` 存在、模型已下载。若 `watermark.notes` 里另有「OCR 不可用」或「pdfplumber 不可用」，说明兜底也不完整，按本表后文「兜底路径」两条排查 |
| 上传 PDF 很慢 —— 走 MinerU（约 38 秒） | 这已是正常速度：28 页 basic 档实测约 38 秒（GPU）、峰值显存约 0.9GB；解析完子进程退出、内存归还。若把 `MINERU_TIER` 改成 `standard`，VLM 引擎只有 CPU 版 llama.cpp，单次加载就要 6 分钟，实测同一份文档 431 秒，不实用 |
| 上传 PDF 很慢 —— 走兜底（约 283 秒） | 三件套逐页跑，本身就是分钟级：28 页实测约 283 秒，其中 PaddleOCR 是大头（CPU 上 10~40 秒/页，代码已用 `_needs_ocr()` 只挑扫描页与图表页跑）。想让上传变快就把 MinerU 装上——两条路径的差距是 38 秒 vs 283 秒 |
| 兜底路径报 `NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support ...`（`onednn_instruction.cc`） | paddlepaddle 3.3.1 的 oneDNN 指令在 PP-OCRv5/v6 上跑不通。`ocr_service` 已固定传 `enable_mkldnn=False` 走通用 CPU 路径，**这不是性能选项而是必须项**；若自行改回 `True` 会复现该错误 |
| 兜底路径读不到图表文字（`ocr_scanned` 为 0） | 一是 `use_ocr=false` 传了（该参数只作用于兜底路径）；二是 PaddleOCR 3.x 的返回结构变了——文本在同级的 `rec_texts` 里（`[{'rec_texts': [...], 'rec_scores': [...]}]`），2.x 的 `[文本, 置信度]` 嵌套结构已不存在，`ocr_service.recognize_image` 按 3.x 解析 |
| 换 torch 后首次解析特别慢 | 后端从 onnx 切到 torch 时要现下 torch 版模型（约 227MB），那次耗时不代表常态 |
| `mineru-kit models show` 显示后端是 `onnx` | torch 用不了 GPU（CUDA 版本不匹配），MinerU 自动退回 CPU。按 README 换成 cu126 的 torch |
| 内存告警 / 进程被杀 | 同机并行跑评测与采集会 OOM，错开执行 |
| 端口 3306 连不上正确的库 | 本机若另有 MySQL 占用 3306，`localhost` 会连到它；用 `docker ps` 确认容器端口映射 |

## 7. 运维要点

| 事项 | 做法 |
|---|---|
| 日志 | `logs/app.log`（全量，滚动 10MB×5）、`logs/error.log`（WARNING 以上） |
| 日志级别 | 环境变量 `LOG_LEVEL=DEBUG` 打开调试 |
| 知识库重建 | `.venv/bin/python -m scripts.knowledge_base` |
| 法条更新 | 重新拉取后 `scripts/fetch_statutes.py` + `scripts/knowledge_base.py lawyer` + `scripts/build_law_index.py` |
| 单文档更新 | `POST /api/update/document`，按哈希判断是否需要重建 |
| 备份 | MySQL 用 `mysqldump`；Milvus 数据在 `milvus_data` 卷；知识库可由 `data/` 随时重建 |
