### 表格抽取修复（本工单必需的适配）

上游 `_extract_tables` 用 PyMuPDF 默认策略 `find_tables()`（= `strategy="lines"`），
在招股书上正常，但在**银行/保险/券商年报**上会把整张表压成 2~3 列——
行标签全挤进第 1 格、数值全挤进第 2 格，行与值的对应关系完全丢失。实测（中国人寿
2020 年报 p8「主要会计数据」）：默认策略 36 行 × 3 列且内容错位。

修复（`scripts/patch_table_extract.py`，已内联到 `src/pymupdf_parser.py`）：
1. 抽取策略改为**先 `text` 后 `lines`**（text 按文字位置聚类，能还原合并单元格网格）；
2. `_clean_grid` 清洗：去空行空列、折叠换行、合并被切散的单字格（"营|业收入"→"营业收入"）；
3. 抽出表内「单位：人民币百万元」这类**计量单位**并前置到 Markdown 首行。

修复后同一张表：**40 行 × 7 列**，`营业收入 2020年=824,961 / 2019年=745,165 /
同比=10.7% / 2018年=643,101`，单位 = 人民币百万元，与 PDF 原文一致。

> 该修复不改检索逻辑，只修**解析器在本语料上的失效**，属于让"复用系统能被正确测试"的
> 必要前提。其残留问题（表格块未走工单03 的结构化行切分）已在
> `docs/06-检索结果问题分析报告.md` 中作为缺陷记录。

### 表格抽取修复 · 第二轮（实测回归后补修，2026-10-13）

第一轮改用 `strategy="text"` 后，**实测端到端问答**又暴露两个副作用，已一并修复：

| 问题 | 实测现象 | 修复 |
| --- | --- | --- |
| **大额数字被切散** | 千分位金额被切成两格：`"1"` \| `",494.07亿元"`（应为 `1,494.07亿元`）。语料中 **42/2101** 个表块命中此模式，直接影响取数（中国平安 id4 即受影响） | `_clean_grid` 新增数字合并：**仅当左格是 1~3 位纯数字且右格以「,三位数字」开头**时合并。判据刻意收窄，避免把 `2020 \| 2019` 这类相邻年份列误并 |
| **双栏正文被误判为表格** | `text` 策略会把**双栏排版页**聚成"网格"——左右两栏句子被交替切进同一行，形成假表格（实测中国平安 p9/p20）。危害：①`block_type` 标成 table，**引用来源失真**；②金额被切碎；③假表块参与排序挤占真实表块 | `_is_prose_grid` 判定，**两个条件同时成立**才判伪：①**无任何列的数值占比 ≥ 0.10**（真实财务表必有数字列）②**长句碎片占比 ≥ 0.30**（>20 字且含中文句读的单元格）。命中则不作为表格返回 |

**关键设计：命中伪表格后是"重新归类"而非"丢弃"**——`_extract_tables` 不返回该网格，
其 bbox 就不进 `table_bboxes`，而该 bbox 只用于**排除**正文（`_in_any_bbox`），
于是这些文字**自动回流为普通 text 块**。**内容零丢失**，只是不再冒充表格。

**实测效果**（重建索引后）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 分块总数 | 7225 | **7757** |
| text 块 | 5124 | **5833** |
| table 块 | 2101 | **1924**（-177 个假表转正文） |
| 中国平安（单文档）table 块 | 193 | **138** |
| 含「数字被切散」的表块 | 42 | **0** |

**但必须如实说明**：该修复对**端到端指标是混合影响**，不是净提升——
重建索引改变了分块边界与检索竞争关系，部分题的证据名次发生位移
（如 id8 答案准确率 0.67→**1.00** 改善，id6 正确证据名次 4→**5**、id4 0.50→**0.25** 变差）。
因此该修复的价值应记在**语料正确性**（数字完整、`block_type` 真实）上，
而非记在指标提升上。逐题影响见 `docs/06`。

## 二、检索策略与 Reranker 配置

测试**覆盖三种策略**（工单推荐），逐题对比：

| 策略 | 实现 | 说明 |
| --- | --- | --- |
| `vector` | `strategies.py::_dense_recall` + `rerankers.py` | bge-m3 稠密向量余弦召回 → Reranker 精排 |
| `fulltext` | `fulltext.py`（**自研倒排索引**） | 位置倒排 + BM25；支持布尔/短语/模糊/多字段 |
| `hybrid`（默认，推荐） | `strategies.py` + `fusion.py` | 双路召回 → **RRF 融合** → **必须经 Reranker 精排** |

**Reranker 精排：全程启用**（`RERANK_ALGORITHM_DEFAULT = "model"`，真实模型推理，非降级）。

| 配置项 | 取值 |
| --- | --- |
| 嵌入模型 | `bge-m3`（`D:\model\bge-m3`，1024 维，本机绝对路径 + `local_files_only=True`） |
| Reranker 模型 | `bge-reranker-v2-m3`（`D:\model\reranker`，fp16，CUDA） |
| 精排算法 | `model`（生产默认）。另有 `llm` / `tfidf` / `adaptive` 作对比基线，本工单未启用 |
| 融合算法 | `rrf`（倒数排名融合，k=60） |
| 融合权重 | 向量 0.5 / 全文 0.5（等权，与 01~06 基线可比） |
| top_k_recall | 20（宽召回 VECTOR_TOP_K=30） |
| top_k_rerank | 5 |
| FINAL_TOP_K | 6 → 送 LLM |

**每一步都走 `rag.retrieve`（含 Query 理解 + 文档路由）**，与 `rag.ask` 生成答案时
是同一条链路，保证"检索留痕"与"答案实际看到的片段"一致。

## 三、解析路径选型

| 方案 | 本语料表现 | 结论 |
| --- | --- | --- |
| MinerU 3.4.5（上游主解析器） | 2812 页，按上游实测速度需**数小时** | 弃用 |
| **PyMuPDF（`--fallback-only`）** | **288.6 s 完成 9 份 PDF 全量解析**，文字覆盖 98.1%—100% | **采用** |

选型依据：本语料 9 份年报**全部带完整文本层**（逐页实测：中位 761—1237 字/页，
有文字页占比 98.1%—100%），非扫描件，PyMuPDF 文本抽取质量足够；
且 MinerU 的增量价值（版面/公式）在本语料上收益有限，而时间成本高 2 个数量级。

**解析质量实测**（逐文档）：有文本页占比、表格检出量、块数见 `docs/02`。
