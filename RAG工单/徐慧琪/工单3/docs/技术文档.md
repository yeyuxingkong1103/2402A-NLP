## 2. 技术选型

### 2.1 为什么是这套组合

| 环节 | 选型 | 理由 |
| --- | --- | --- |
| PDF 解析 | **MinerU 3.4.5（pipeline）** | 唯一能同时给出**版面结构 + 表格 HTML** 的本地方案；模型清单与本机 `PDF-Extract-Kit-1.0` 快照完全匹配，无需下载 |
| 表格兜底 | **PaddleOCR-VL**（独立 venv 子进程） | 主环境未装 paddle，子进程调用零污染；对 MinerU 解析失败的表格做页级重识别 |
| 向量库 | **Qdrant**（local 模式） | 工单指定；本机无 Docker，`qdrant-client` 的嵌入式模式 API 完全一致，payload 结构不变，起服务后改一行配置即可切换 |
| Embedding | **bge-m3**（1024 维，CUDA） | 中英双语、长文本友好、本机已有 |
| 重排 | **bge-reranker-v2-m3** | cross-encoder，对"数字/专名"这类精确匹配的排序提升明显 |
| LLM | **Ollama qwen2.5:3b** | 本机已 pull；`keep_alive` 常驻显存，满足 ≤3 秒 |
| 界面 | **Streamlit** | 开发快、原生支持流式与表格展示 |
| 评估 | **RAGAS 0.2.15** + 自研四路对比 | 裁判与 embedding 全部换成本机模型，离线可复现 |

### 2.2 本机环境实测（决定选型的依据）

| 项 | 实测 |
| --- | --- |
| Docker | **未安装**（无 Docker Desktop、无 `docker` 命令）→ Qdrant 用 local 模式 |
| MinerU | 独立 venv `D:\model\mineru-venv` 可用；模型在 modelscope 本地快照 |
| 显存 | RTX 4060 Laptop 8GB；bge-m3 + reranker + qwen2.5:3b 需**分阶段加载**（见 §7.3） |
| 模型路径 | `D:\model\bge-m3`、`D:\model\reranker`、Ollama `qwen2.5:3b` |

### 2.3 硬约束：禁止下载任何模型

实现方式：

- `src/bootstrap.py` 在**任何模型库导入之前**设置 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1`；
- 所有 `from_pretrained` 显式传 `local_files_only=True` 与本地绝对路径；
- MinerU 子进程环境注入 `MINERU_MODEL_SOURCE=local`；PaddleOCR 子进程注入 `PADDLE_PDX_MODEL_SOURCE=local`；
- 不出现 `snapshot_download` / `hf_hub_download` / `modelscope.download` / `ollama pull`。

## 3. 系统架构

### 3.1 离线建库

```
两份 PDF
  └─ pdf_parser.parse_pdf（MinerU pipeline；失败回退 PyMuPDF 增强引擎）
       └─ content_list.json 归一化（保留 table_html）
            ├─ chunker._iter_sections   标题层级切节
            │    ├─ 正文 → 父子块（子块 300–450 字检索 / 父块 ≤1800 字上下文）
            │    └─ 表格 → table_chunker
            │         ├─ table_parser.parse_table_html  HTML → 矩阵（rowspan/colspan 展开）
            │         │    ├─ 表头识别（含多级表头）
            │         │    ├─ 形态判定：header（列式表）/ kv（字段-值表、释义表）
            │         │    └─ 质量分 → 低质量表 → PaddleOCR-VL 页级兜底
            │         └─ 表头块 + 行级块（parent = 整表 Markdown）
            └─ embedder.embed_texts（bge-m3）
                 └─ vector_store.upsert_chunks（Qdrant local）
```

### 3.2 在线问答

```
问题
 └─ doc_router.route            公司名 → 限定的 source（多文档路由）
     └─ query_rewrite.analyze   意图 / 消歧 / 子问题分解 / 领域扩展
         └─ retriever.search_multi   向量 top-30 + BM25 top-30 → RRF(k=60)
             │                         （带 source 过滤；候选不足时自动放开重检）
             └─ reranker.rerank      bge-reranker-v2-m3：top-20 → 4
                 └─ context.expand_parents
                 │      表格命中 → 按 table_id 还原整表（不做行级裁剪）
                 │      正文命中 → 子块展开父块 + 以命中句为中心裁剪
                 │      同页去重（表格块豁免）+ 总预算 3200 字
                 └─ llm.chat（qwen2.5:3b, temperature=0）
                     └─ 数字校验（含"表格两数一步运算"白名单）→ 重试 → 抽取式降级
                         → 答案 + [n] 引用 + 表格定位
```

## 4. 关键设计决策

### 4.1 表格复用「子块 / 父块」而不另建机制

父块机制原本是给正文用的：小块检索保证精度，展开父块保证上下文完整。
表格天然契合这个结构——**行是检索单元，整表是上下文单元**。于是：

```python
parent_id   = table_id                              # "招股说明书2.pdf#p1#t0"
child.text  = "表：本次发行概况 | 发行股数：1,670万股 | 页码：2"
parent_text = 整表 Markdown（表头 + 全部行）
```

好处：`context.expand_parents`、引用映射、payload 结构、评测口径**全部不用改**，
命中任一行就自动带出整张表。这是本工单代码量可控的关键。

代价：`expand_parents` 里要豁免表格的"同页去重"和"行级裁剪"（见 4.3）。

### 4.2 表格形态判定：header vs kv（本工单最重要的鲁棒性设计）

招股书里有两类表格，混为一谈会让行级描述**整体错位**：

| 类型 | 例子 | 错误处理的后果 |
| --- | --- | --- |
| **header**（列式） | `项目 \| 2019年7-9月 \| 2018年7-9月 \| 同比变动` | — |
| **kv**（字段-值） | `发行股数 \| 1,670万股`、释义表 `术语 \| 指 \| 释义` | 列名变成"发行股票类型/人民币普通股(A股)"，**每一行的"列名：值"全部对不上** |

判定规则（`table_parser.detect_mode`）：

1. 存在"连接词列"（某列 ≥60% 的取值是 `指/为/：` 之类）且列数 ≥3 → **kv**（释义表）；
2. 仅 2 列 → **kv**。理由：招股书的 2 列表几乎都是"字段→值"；
   即便真是"年度\|金额"这种带表头的 2 列表，按 kv 解析得到的
   `年度：2018年度`、`金额：1.2亿元` 依然可读可检索，比把首行误当列名安全得多；
3. 其余 → **header**。

### 4.3 表格上下文的两个特殊处理

- **不做同页去重**：同一页常有多张语义不同的表（"本次发行概况"与"募集资金运用"可能同页），
  按页去重会丢掉恰好命中的那张；
- **不做行级裁剪**：正文父块会以命中句为中心裁剪到 1200 字，但表格题常常需要**同一张表的多个
  单元格**（如"发行股数"与"发行后总股本"算比例）——只给命中那一行就答不了。
  因此表格按 `TABLE_CTX_MAX_CHARS`（2600 字）整体装入。

### 4.4 数字校验放行"表格算出来的比例"

`rag.check_numbers` 原本把"上下文中不存在的数字"一律判为幻觉。
但工单的表格题（id 1）要求回答"占发行后总股本的比例"，而表里只有分子分母。
于是新增 `_is_derivable`：某个数字若可由上下文中的**两个数经一步四则运算**得到
（容差 0.5%），不算幻觉。仍只支持一步运算，避免给编造数字开口子。

### 4.5 多文档路由

规则版（别名表，<1ms）：`武汉力源/力源信息/力源/赵马克` → 招股2；
`武汉兴图新科/兴图新科` → 招股1。命中唯一文档时用 Qdrant payload filter 限定；
未命中或同时命中两家则全库检索。

**兜底**：限定文档后候选不足 `RERANK_INPUT_TOP_K` 时，自动放开过滤重检一次，
避免路由误判导致空召回。

## 5. 工程问题记录（实测踩坑）

| # | 问题 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- | --- |
| 1 | **多文档点 ID 冲突** | 7968 个点入库后集合里只剩 5024 个 | 两文档的 `chunk_id` 各自从 `c000001` 开始，`_stable_id` 只取数字部分 → 招股2 覆盖招股1 | 点 ID 改用全局唯一键 `source#chunk_id`（blake2b 稳定哈希） |
| 2 | **父块 ID 跨文档冲突** | 招股1 的某节与招股2 的某节被当成同一父块合并 | `parent_id = s000001` 未带 source | `parent_id = f"{source}#s{idx}"` |
| 3 | **RRF 融合键跨文档冲突** | 两文档中序号相同的块被当作同一条融合 | `rrf_fuse` 只用 `chunk_id` 做键 | 融合键改为 `source#chunk_id` |
| 4 | **kv 表被误判为列式表** | 「本次发行概况」行级描述里列名是"发行股票类型/人民币普通股(A股)" | 首行被当成表头 | 新增 kv 形态识别（§4.2） |
| 5 | **日期表头被误判为数据行** | 财务表列名退化成"列1/列2/列3" | 数值判定正则 `[\d,.\-%—]+` 把 `2010-6-30` 当成数值 | 收紧为 `^-?[\d,]+(?:\.\d+)?%?$` |
| 6 | **BM25 语料被 HTML 撑爆** | 全量 scroll 拉入几十 MB `table_html` | 工单要求每个表格 chunk 都带 `table_html` | `scroll_all` 用 `PayloadSelectorExclude` 排除重字段（落库保留、读取排除） |
| 7 | **OCR 兜底重复耗时** | 每次重建都要重跑 236 秒 OCR | 结果未落盘 | 缓存到 `data/tables/<doc>_ocr_pages.json`，只补缺失页 |
| 8 | **表格块挤占正文上下文预算** | 正文父块被长表截断 | 表格原样并入节父块（1800 字上限） | 表格不再并入节父块，各自独立成 parent |
| 9 | **113 个空表格块的误处理** | 若全部触发 OCR 会白跑上百页 | MinerU 把双栏正文误判为表格，`table_body` 为空 | 仅对"**有 HTML 但解析不出结构**"的表触发 OCR；无 HTML 的走 PyMuPDF 页文本补齐 |
| 10 | **无标题表格语义稀薄** | 行级描述长成"表：（无标题）\| 关联方名称：赵马克…" | 招股2 多数表 `table_caption` 为空 | 用所属章节标题补表名（`resolve_caption` + `item_headings`），id 3/4 因此被检索到 |
| 11 | **正确表格行被截断点切掉** | id 3 的正确行排重排第 5，而 `FINAL_TOP_K=4` | 招股书有大量"只含问题措辞、不含答案"的小标题块，cross-encoder 给它们 0.95+ | `FINAL_TOP_K` 4 → 6，`CONTEXT_MAX_CHARS` 3200 → 3600 |
| 12 | **防幻觉校验被"可推导"规则架空** | 编造数字全被判为"可由两个数算出" | 用上下文全部 129 个数字两两运算 ≈ 5.6 万个候选值 | 两轮收敛：先要求"算子出现在答案里"（误伤 id 1 的自然句式）→ 最终改为"两个数须同处一个片段且分母更大"（§4.4） |
| 13 | **两句结构相同的枚举句被抄混** | id 33 把"军用领域收入占比"与"视频指挥控制类产品收入占比"两句的数字混着抄 | 招股书里两句措辞几乎一致、数值相近 | `complete_numeric_list` 增加"按问题词重叠选枚举句"的抽取式校正 |
| 14 | **列举型答案漏列表格行** | id 4 表格 7 家企业只答了 5 家（因同属一类被合并） | 小模型倾向归类概括 | 生成后核对表格行覆盖，漏行则定向重试（`check_table_rows`） |
| 15 | **基线子进程因显存崩溃** | `evaluate_compare` 报"baseline 无结果输出" | Ollama 常驻 qwen2.5:3b 时，另一个进程再加载模型会 OOM/崩溃 | 跑基线前先 `llm.unload()` 让出显存（8G 卡实测必需） |

## 7. 错误处理与容错

### 7.1 输入侧

| 场景 | 行为 |
| --- | --- |
| 空问题 | 返回"请输入问题。" |
| 与两份文档均无关 | 回答"根据已有资料无法确定。"，**不编造** |
| 路由误判 | 候选不足时自动放开 source 过滤重检 |

### 7.2 解析侧

| 场景 | 行为 |
| --- | --- |
| MinerU 失败/超时 | 回退 PyMuPDF 增强引擎；已有产物时直接复用缓存 |
| MinerU 表格 HTML 解析失败 | 降级为整表文本块（`degrade_reason=parse_failed`） |
| 表格质量分低 | PaddleOCR-VL 页级兜底；仍失败则降级（标记 `from_ocr` / `degrade_reason`） |
| MinerU 空表格块（版面误判） | 不触发 OCR，由 PyMuPDF 页文本补齐（`merge_pymupdf_gap`） |
| PaddleOCR-VL 不可用/超时 | 打印提示并跳过，主链路不受影响 |

### 7.3 资源侧

| 场景 | 行为 |
| --- | --- |
| 显存不足（8G 卡跑三个模型） | `rag.warmup` 分阶段：加载 embedding → 检查显存 → 加载 reranker → 最后预热 Ollama；显存不足时先让 Ollama 释放 |
| LLM 超时/异常 | 抽取式降级：直接给出最相关片段原文与页码 |
| LLM 数字幻觉 | 数字校验 → 定向重试一次（不更差才采用）→ 仍可疑则抽取式校正 |

## 9. 评测口径

### 9.1 四路对比（`evaluate_compare.py`）

| 组 | 说明 |
| --- | --- |
| **03（表格优化）** | 本系统：多文档 + 表格结构化 + 混合检索 + 重排 |
| **03 消融（无表格优化）** | **同一索引**，检索时排除 `table_row`/`table_header`。排除分词、模型等干扰，量化表格结构化的**净增益** |
| **01/02 基线** | 上游系统（子进程只读调用）：单文档、表格整块处理 |
| **纯 LLM** | 不检索直接问模型，验证 RAG 增益 |

指标：关键事实命中率、LLM 裁判准确率（0/0.5/1）、端到端响应时间、
Hit Rate@5 / MRR@5 / NDCG@5（相关页 = 含任一 key_fact 的 chunk 所在页）。

### 9.2 RAGAS（`evaluate_ragas.py`）

`faithfulness / answer_relevancy / context_recall / context_precision`，
裁判用本机 qwen2.5:3b、embedding 用本机 bge-m3，全程离线。

### 9.3 答案定位报告（`src/answer_location.py`）

14 题逐题跑完整检索，核对 ground truth 的 `key_facts` 是否出现在送进 LLM 的上下文里，
输出该事实所在的 PDF / 页码 / 表格或段落 / 表格行号。

## 10. 已知限制（如实记录）

| # | 限制 | 现状与原因 |
| --- | --- | --- |
| 1 | **id 95 的回答不是最完整表述** | 问题是"参与制定了哪个技术标准"。文档里**同时存在两种写法**：概览页写《某视频技术规范 1.0》，后文写《某视频指挥系统技术规范（1.0版）》并由军事科学院牵头。模型检索到概览页并**逐字引用**了前者——答案本身是文档原文、并非编造，但不如后文完整。提示词已要求"以信息最完整的那条为准"，3B 模型未能稳定执行 |
| 2 | **LLM 裁判准确率 0.75，低于事实命中率 0.93** | 裁判是 qwen2.5:3b（离线要求所限）。实测它对若干**事实完全正确**的回答（如"法定代表人：程家明"）只给 0.5，存在明显裁判噪声。故报告中同时给出"关键事实命中率"与"全对题数"，不以单一裁判分为准 |
| 3 | **长列表题的响应时间会超 3 秒** | 14 题中 3 题 ~3.1s；生成耗时占比 ~75%（qwen2.5:3b 输出 100+ token 的枚举答案）。平均 2.4s、中位 2.1s 在预算内，尾部超标 |
| 4 | **表格 OCR 兜底是 best-effort** | PaddleOCR-VL 子进程在其中一次重跑时对招股1 的 9 页返回 0 页（批处理失败），系统按设计降级为 MinerU 文本块、不中断建库。结果已落盘缓存 |
