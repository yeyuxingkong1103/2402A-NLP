### 1.5 重导流程与**两个已知陷阱**

流程（4 篇）：修好的清洗规则重跑 解析→切块→数据包 → `import_mysql --replace-existing`
→ 回填审核/效力状态（`scripts/migrations/restore_reingest_status.py`）→ **先删旧向量**
→ 索引 → 重生成摘要 → 校验。原始文件未删，只动清洗规则。

**陷阱 1：`chunk_key` 是位置型的 → 重导后 key 不变，索引服务会跳过**
索引按 `chunk_key` 判重，重导后 key 与旧 key 完全相同 → CLI 报 `indexed_chunks: 0`，
向量还是旧内容。**必须先删该文档旧向量再索引**（本次删 508 条 = 81+183+167+77）。

**陷阱 2：摘要同样会"串位"**
`chunk_summaries` 也以 `chunk_key` 为键，位置型 key 与旧 key **100% 重叠**（实测 54/54、
20/20 全交集）→ 旧摘要直接挂到新文本上，其中**末条 parent 的旧摘要来自带页脚的旧文本**。
处理：删掉这 4 篇的 149 条摘要后重生成（`summarized: 149, failed: 0`）。
最终 **486/486 = parent 486**。

**状态回填**：replace 会把 `version_status` 重置为 `pending_review`、重建 `law_versions` 行
（`status` 变 NULL）。按裁决 1 的同类口径，用 `restore_reingest_status.py`（快照写死在脚本里、
逐字段可审计）回填：4 篇恢复 `approved`（沿用原留痕 `chunker-v3-重建批准` 与原
