# Phase 0 Research: 混合检索（S9 步骤）

**Feature**: `008-hybrid-retrieval` | **Date**: 2026-09-28

本文件记录 plan 之前必须定死的技术选择。每条给出「决定 / 理由 / 被否决的替代方案」。

---

## R0 — 混合检索的整体形状

**决定**：语义路与关键词路**独立检索、RRF 融合**，融合后取 `top_k`，阈值判定作用在**语义路**（R7）。

```
查询向量 (S8 已算) ──▶ 语义路: Milvus FLAT/COSINE, limit=C ──┐
                                                            ├─▶ RRF 融合 ─▶ 过滤 ─▶ top_k ─▶ RetrievalResult
问题原文 ────────────▶ 关键词路: 内存 BM25, top=C ───────────┘
```

**理由**：两路各自使用最擅长的方式取候选，融合只在**名次**层面发生。这正是 D2 要的"免疫量纲"。

**被否决**：
- *先 BM25 召回、再用向量重排* —— 召回阶段就已经丢掉了只有语义路能命中的片段（口语化提问里 BM25 常常一个词都不命中），与 US2 直接冲突。
- *把 BM25 分数插进 Milvus 做单次混合查询* —— Milvus 2.6 的稀疏 BM25 需要 collection 带稀疏向量字段，必须重建集合并重跑 S6；影响面远超本特性（spec Q1 选项 D 已否决）。

## R1 — BM25 自实现，不引入 `rank_bm25`

**决定**：在 `backend/retrieve/lexical.py` 内实现标准 Okapi BM25（约 40 行），参数 `k1=1.5`、`b=0.75` 作为显式常量。

```
score(q, d) = Σ_{t ∈ q} IDF(t) · tf(t,d)·(k1+1) / (tf(t,d) + k1·(1 − b + b·|d|/avgdl))
IDF(t)      = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
```

**理由**：
1. `rank_bm25` 是纯 Python 实现，与自写在性能上无差别，却多一个依赖、多一层版本耦合 —— 违背 constitution 原则 I 的取向（"装一个用不上的包"）。本项目已有先例：specs/003 的 D2 用环境里已有的 `transformers` 而非引入 `FlagEmbedding`。
2. IDF 公式各版本有差异（有些用 `log((N−df+0.5)/(df+0.5))` 且允许负值）。**自写才能锁定公式**，而锁定的公式正是"同问题两次检索结果一致"（SC-006）的前提。
3. 语料只有几十到几千条，公式就是全部成本。

**被否决**：`rank_bm25`（多依赖、公式不可控）；`bm25s`（同上，且为大规模场景优化，此处用不上）。

## R2 — 分词：jieba，索引侧与查询侧共用同一个分词函数

**决定**：`jieba.lcut(text, cut_all=False)`，随后过滤空白与纯标点 token。索引期与查询期**必须调用同一个函数**。

**理由**：
- 索引期把「盐酸氨氯地平」切成 A，查询期切成 B，则 BM25 永远返回空 —— 而且**不报错、不告警**，表现为"关键词检索时灵时不灵"。这是分词类系统最经典的静默失效，靠"共用一个函数"从结构上消除。
- jieba 0.42.1 **实测已安装在项目运行时**（本机核对），因此 D1 的裁决不产生实际安装动作，只需登记进 `requirements.txt`（constitution 原则 I 要求登记表与实际一致）。
- 医疗术语识别 jieba 无专用词典，但本特性不要求分词边界与人工标注一致（spec Assumptions 已声明）；验收以端到端命中率为准（SC-001/SC-002）。

**被否决**：字符 2-gram（把术语切成跨词片段，削弱 US1，正是本特性的存在理由）；`pkuseg`/`LAC`（新依赖、新模型权重，收益不明确）。

**已知代价**：jieba 首次调用会加载词典（约 0.5–1 s）。MUST 在**启动期**预热一次，MUST NOT 让首次提问承担它（与 S8 的"启动期加载权重"同一取向）。

## R3 — 语料从 Milvus 全量拉取（落地 D1）

**决定**：启动期用 `MilvusClient.query(filter="", output_fields=[...], limit=N)` 拉全量 chunk 的展示字段，构建内存语料。

**理由**：语料与向量库逐条一致，从结构上消除"语义路可见、关键词路不可见"的 chunk（FR-009）。

**两个必须显式处理的点**：

1. **`limit` 必须显式给足，MUST NOT 依赖默认值。** Milvus 的 `query` 有默认返回上限（既有 `backend/index/store.py` 因同一原因显式写了 `QUERY_LIMIT = 16384`）。依赖默认值会让**语料被静默截断** —— 关键词路悄悄少了一部分文档，而语义路不受影响，两路从此不一致，且没有任何报错。本特性的 limit 同样显式声明，并在拉回条数等于 limit 时**告警**（说明可能被截断）。
2. **拉回的条数 MUST 与 manifestation 中的 `total_chunks` 比对。** `data/index_manifest.json` 记录了入库时的总条数；不一致说明库被改过而 manifest 未更新，MUST 告警。

**被否决**：读本地 `data/chunks/*.chunks.jsonl`（与库内容可以静默不同步，见 spec D1 说明）；把语料落盘成中间文件（多一份会过期的产物，违反"不做不存在的需求"）。

## R4 — 索引常驻内存，不做持久化

**决定**：启动期一次性构建，进程生命周期内常驻，与 S8 的 Encoder 单例同一模式（`backend/query/service.py` 的 `get_encoder()`）。

**理由**：当前 65 chunks，倒排索引是几 KB 量级，构建耗时在毫秒级。持久化索引会引入"索引文件与库内容是否一致"这个新的一致性维度 —— 为一个不存在的性能问题引入一个真实的一致性风险，是净负收益。

**何时需要重新考虑**：语料达到**十万条量级**、启动构建时间超过 5 秒时。届时的正解是把 BM25 迁到 Milvus 原生稀疏向量（R0 的选项 D），而不是给内存索引加持久化。

## R5 — 融合：RRF，k=60（落地 D2）

**决定**：`rrf(d) = Σ_{列表 ∈ {语义, 关键词}} 1/(k + rank_list(d))`，`k=60`，`rank` 从 1 起；某列表未命中该 d 则不计该项。

**理由**：
- 只使用**名次**，与两路分数的量纲、取值范围、分布全部无关 —— 这就是 spec"最大风险"那一节要的免疫性。
- 无需标定权重即可用。加权归一化方案在语料规模变化时会漂（min-max 依赖本次候选的极值），而 RRF 不会。
- k=60 是原论文（Cormack et al., 2009）的经验值，也是 Elasticsearch / Vespa 等系统的默认取值。**它是一个平滑常数，不是调参旋钮** —— 因此写进配置只为可追溯，不为日常调整。

**k 的作用**（为什么不是 1）：k 越大，头部名次的差距被压得越平。k=60 时第 1 名与第 2 名的 RRF 贡献是 `1/61` vs `1/62`，差距很小 —— 这看起来反直觉，但它正是 RRF 稳健的来源：**它不信任任何一路的名次精度**。两路都靠前的片段会因"两项相加"而胜出，这才是我们要的信号。

**被否决**：加权归一化分数（需标定权重，且 min-max 随语料漂）；只取并集（仍是跨量纲比大小，"混合"退化为"拼接"，spec Q2 选项 C 已否决）。

## R6 — `score` 字段保余弦（落地 D2 续）

**决定**：`RetrievedPassage.score` 恒为**语义路余弦相似度**；仅被关键词路命中的 chunk 取 `0.0`。RRF 分只用于排序与日志（字段名 `rrf_score`，不出现在响应模型里）。

**理由**（两条都是硬的）：
1. `docs/05` §4.2 把 `score` 定义为余弦相似度，而前端 `frontend/js/transcript.js` 会 `score.toFixed(2)` 直接显示给用户。塞入 RRF 分，用户看到的是一个**与"像不像"无关的数字** —— 0.03 分和 0.02 分在他看来毫无区别，而它们其实对应完全不同的排名。
2. 阈值判定用的是相似度（R7）。若 `score` 与阈值不是同一把尺子，`below_threshold` 这个字段就失去了可解释性。

**`0.0` 而不是 `None` 的理由**：契约里 `score: float` 非可选；`0.0` 诚实表达"语义上完全没命中"，且前端能正常渲染。用 `None` 会让 `toFixed` 抛异常。

## R7 — 阈值只管语义路（2026-09-28 用户裁决）

**决定**：候选是否纳入最终结果，判定条件为

```
纳入 ⟺ (余弦 ≥ similarity_threshold) 或 (BM25 名次 ≤ lexical_admit_rank)
```

`lexical_admit_rank` 默认 3，显式配置。相应地：

| 字段 | 混合检索下的定义 |
|---|---|
| `top_score` | 最终结果中**最大的余弦**；结果全为关键词命中时为 `0.0`；结果为空时为 `None` |
| `is_empty` | 最终结果**为空** |
| `below_threshold` | 结果非空，**且所有结果的余弦都低于阈值** —— 即"全部靠关键词救回来的" |

**理由**：`docs/05` §4.2 的原文只设想了单路检索。混合检索下若阈值只卡余弦（选项 C），用户照抄罕见术语时 BM25 的精确命中会被判为"不相关"并走拒答 —— 而 US1 恰恰是本特性的存在理由。方案 C 等于把本特性的价值整体抵消。

**`below_threshold` 的新定义反而更有用**：它现在标记的是"知识库里有这个词，但语义模型不理解它"。这个信号若随时间上升，说明 BM25 侧在承担主要工作，是模型/语料不匹配的早期征兆 —— 比原来的"命中但不够像"更具操作性。

**契约影响（MUST 回写）**：`docs/05_接口设计.md` §4.2 需要增加一段，说明混合检索下阈值的适用对象与三字段的上述定义。本特性 MUST NOT 悄悄改契约。

**被否决**：两路各自设阈值（BM25 绝对阈值随语料规模漂移，不可移植）；只卡余弦（见上）。

## R8 — 查询向量的来源：由 `capture.py` 回传，不重新编码

**决定**：`backend/api/capture.py` 的 `capture_question()` 由返回 `None` 改为返回 `list[float] | None`（编码成功时为查询向量，失败时为 `None`）；`routes.py` 把它透传给 `stream_answer()`。

**理由**：
- FR-003 明令禁止在检索路径上重新编码。而查询向量**已经存在** —— `routes.py` 在 `capture_question()` 里刚算过（S8），只是当前被丢掉只写了盘。
- 重新编码一次的成本是**每次提问多 100–300 ms 的 CPU 推理**，外加一个第二编码入口（S8 整篇规格防的就是这个）。
- `capture_question` 的既有契约"**MUST NOT 向调用方抛异常**"**不变** —— 只改返回值。

**失败路径**：向量为 `None`（编码失败，记录已按 `status=failed` 落盘并可被 CLI 重跑）时，语义路不可用。此时 MUST NOT 静默退化为只跑关键词路（FR-020），MUST 记为检索降级：写 ERROR 日志 + 走拒答路径（见 R9）。

## R9 — 基础设施失败 vs 检索为空的处置

**决定**：

| 情形 | `search()` 的行为 | 请求链路上的表现 |
|---|---|---|
| 命中为空 / 全部不达标 | 返回 `is_empty=True` 的**正常值** | 拒答兜底话术（FR-014） |
| 查询向量缺失 | 抛 `RetrievalError` | ERROR 日志 + **拒答兜底话术** |
| Milvus 查询失败 | 抛 `RetrievalError` | ERROR 日志 + **拒答兜底话术** |

**为什么异常不冒泡成 500**：检索发生在 SSE 流**已经开始之后**（`status` 帧已发出、响应头已定），此时无法再改 HTTP 状态码。若让它冒泡，客户端拿到的是流中断 —— 与"网络断了"不可区分，而这两件事该做的处置完全不同。

**为什么这不违反 constitution 的"禁止 try/except 吞掉失败条件"**：判定标准是"事后能不能查出来"。这里 MUST 留下 ERROR 级日志（含 `answer_id` 与异常类型），因此失败**是可查的**。同一条推理已在 `backend/api/capture.py` 的模块文档字符串中确立，本特性沿用。

**为什么在启动期就挡掉 Milvus 不可达**：语料构建（FR-010）发生在启动期。若那时 Milvus 不可达，服务**直接启动失败**，而不是"能启动但每次检索都降级"。这把一类运行期才暴露的问题提前到了启动期（SC-009）。

**行为变更提示**：这是对 S8 的**行为改变** —— 当前 `backend/serve.py` 在 Milvus 未运行时也能正常启动（门禁只读 `index_manifest.json`）。接入本特性后，**Milvus 成为启动的硬前提**。这个变更是 R3 + FR-010 的必然结果，MUST 在启动输出的提示语中写清楚。

## R10 — 模块划分（落地 FR-021 / FR-022）

**决定**：新增 `backend/retrieve/` 包，按「什么时机可能出错」切分，沿用 `backend/query/`、`backend/index/` 的既有风格。

| 模块 | 职责 | 何时会出错 | 预估行数 |
|---|---|---|---|
| `__init__.py` | 常量、错误类型、配置契约 | — | ~130 |
| `models.py` | `RetrievedPassage` / `RetrievalResult` / `Candidate`（Pydantic） | 契约字段写错 | ~90 |
| `store.py` | **唯一碰 Milvus 的模块**：连接、全量语料、向量检索 | 库不可达、collection 不存在 | ~170 |
| `lexical.py` | jieba 分词 + BM25 建索引 + 关键词检索 | 分词不一致、语料为空 | ~180 |
| `fuse.py` | RRF 融合 + 去重 + 确定性排序 | 纯计算，出错的只有排序不稳定 | ~100 |
| `service.py` | `search()` 编排 + 阈值判定 + 索引单例 | 编排顺序、阈值判错 | ~160 |
| `report.py` | CLI 报告渲染 | 纯输出 | ~110 |
| `backend/retrieve_search.py` | CLI 唯一入口 | 参数解析 | ~150 |

**唯一入口**：包内唯一对外的检索入口是 `backend/retrieve/service.py` 的 `search()`；唯一对外的 CLI 入口是 `backend/retrieve_search.py`。

**为什么 `store.py` 独占 Milvus 访问**：与 `backend/index/` 的"只有 store 持有 Milvus 连接"同一取向 —— 让"检索不写库"成为**结构上的事实**而不是一句约定。本特性的 `store.py` MUST 只读，MUST NOT 出现任何写操作。

**单文件 ≤ 300 行**（FR-022）：上表最大预估 180 行，留有余量。`backend/query/store.py` 实测 300 行是既有上限先例。

## R12 — 阻塞调用与事件循环

**决定**：`search()` 为**同步函数**，在 SSE 异步生成器中直接调用（与 `routes.py` 中既有的同步 `capture_question()` 同一方式）。

**理由**：当前规模下（65 chunks、FLAT 索引、单用户本机）检索耗时在几十毫秒量级，阻塞事件循环的代价可忽略。改成 `asyncio.to_thread` 会把 Milvus 客户端与 BM25 索引的使用跨到工作线程 —— 这两者是否线程安全是**未经验证的前提**，为一个不存在的性能问题引入一个真实的正确性风险。

**何时必须改**：并发用户数 > 1、或语料规模增长到检索耗时超过 100 ms 时。届时正解是 `asyncio.to_thread` + 验证 Milvus 客户端线程安全，而不是先猜。

**已知代价（明确记录）**：本服务当前**在请求路径上是同步阻塞的**（`capture_question` 的编码阻塞更久）。这是 S8 就有的性质，本特性不加剧它、也不在本特性范围内修复它。
