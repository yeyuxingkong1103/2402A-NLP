# 容错机制与长时间运行方案（硬性要求7）

> 工单编号：人工智能NLP-RAG-基于GraphRAG实现金融问答
> 实现位置：`src/runtime_ext.py`（本文件描述的通用设施）+ 各模块内建的降级分支。

本工程有两类「长时间/易失败」的运行形态：
**离线构建**（解压语料 → PDF 解析 → 建库 → 图谱抽取，动辄数小时）与
**在线问答**（单次 1~7 秒，但需要模型、向量库、图谱、LLM 四方同时可用）。
下文分别给出故障清单、长时运行保障与降级标注。

## 一、故障清单与处理（8 类）

| # | 故障 | 触发条件 | 系统行为（实现位置） | 用户可见表现 | 恢复方式 |
| --- | --- | --- | --- | --- | --- |
| 1 | **zip 解压失败** | 语料包损坏/磁盘满/权限不足 | **运行时不适用**：语料已解压落盘（`data/corpus/`），问答与构建链路均不读 zip。`ccf_competition.zip` 仅作为原始留档 | 无 | 如需重新解压，用 `guarded("unzip", fallback=[])` 包裹后**校验文件数**（解压成功但缺文件同样视为失败） |
| 2 | **PDF 解析失败** | 扫描件无文本层 / MinerU 超时 / 单页损坏 | `src/pdf_parser.parse_pdf`：MinerU 失败自动回退 PyMuPDF（`force_fallback=True` 可强制）；OCR 兜底见 `src/ocr_fallback.py`；坏页跳过不中断整册 | 该文档命中率低或页面缺失；问答时该题命中不足会如实显示低覆盖 | 重跑 `python scripts/... / build_index.py --reparse`；或把该 PDF 加入跳过清单 |
| 3 | **实体识别失败** | 词典/正则处理异常块（畸形表格、超长块） | `src/kg_build.build_layer1` 逐块 `try/except ValueError`（`src/kg_build.py:62`）跳过该块继续；`src/kg_dict.py` 最长匹配对异常输入返回空集 | 图谱少该块贡献的实体（`data/kg/kg_stats.json` 的实体数可见） | 修掉问题块后重跑 `python build_kg.py --layer1`（秒级，全量重建） |
| 4 | **关系抽取失败** | Ollama 未启动 / 模型未拉取 / 输出非法 JSON / 超时 | `src/kg_extract_llm.extract_one`：**任何异常都不外抛**，重试 `config.KG_LLM_RETRY` 次后把 `error` 写进结果（`src/kg_extract_llm.py:183-199`）；`build_layer2` 逐块兜底（`src/kg_build.py:100`） | 该块 `error` 非空、贡献 0 条关系；汇总行打印失败块数 | **断点续抽**：`python build_kg.py --all --resume`（已完成块走 JSONL 检查点，不重复消耗） |
| 5 | **图数据库读写失败** | 写盘中断 / 进程被杀 / 磁盘满 | `KnowledgeGraph.save` **原子写**：先写 `*.tmp` 再 `os.replace` 覆盖（`src/kg_store.py:383-392`）；GraphML 写入失败时清理临时文件、保留 pickle 产物 | 旧图谱完好，不会出现半截文件；下次启动仍可用 | 重跑 `python build_kg.py --layer1` 重建并保存 |
| 6 | **图谱查询失败** | 子图检索异常 / 图谱文件损坏 / 加载失败 | `src/graph_qa.ask` 两处降级：图谱不可用→`degraded=True, reason="图谱不可用：…"`；子图检索抛错→降级为纯文本通道（`src/graph_qa.py:176-206`） | 答案仍返回（纯 RAG 口径），界面/结果 JSON 中 `degraded=true` 并附原因，**不静默** | 检查 `data/kg/kg.pkl` 是否存在；`python -c "from src.runtime_ext import health_check; print(health_check())"` 看 `graph.graph_error` |
| 7 | **模型加载失败** | 本机缺少权重 / 路径写错 / 显存不足 | `src/embedder.get_model` 懒加载并缓存；缺权重时抛 `FileNotFoundError` 并附带**处置指引**（`src/embedder.py:92-96`）；重排序模型同理（`src/rerankers.py`），不可用时 `warmup()` 如实报告 `False` | 启动预热打印 `{'embedding': False, …}`；不静默假装成功 | 跑 `python scan_local_models.py` 核对本机模型；或改 `src/config.py` 的模型路径 |
| 8 | **LLM 调用失败** | Ollama 未启动 / 端口占用 / 超时 / 显存不足 | `src/llm.chat` 统一抛 `LLMUnavailable`（`src/llm.py:40,160-162`）；`graph_qa.ask` 捕获后走**抽取式答案**（子图事实直接成文）并标 `degraded` | 答不出「自然语言总结」但**关键数字仍在**；状态区提示 LLM 不可用 | 启动 Ollama：`ollama serve`；`llm.health()` 返回 `ok=true` 即恢复 |

> 说明：第 1 项如实标注为「运行时不适用」——语料已解压落盘，本工程没有在问答/构建链路里动态解压 zip，
> 因此不存在该故障点；不虚构一个并未接入的容错分支。

### 通用兜底设施

`src/runtime_ext.guarded` 提供统一写法，便于把上表之外的易失败操作按同一口径接入：

```python
from src.runtime_ext import guarded

@guarded("pdf_parse", fallback={"blocks": []})
def parse_one(path): ...
```

失败时写入 `logs/fault.log`（含操作名与异常类型），并返回 `fallback`；
`reraise=True` 则记录后继续向上抛（供调用方自行处理）。

## 二、长时间运行方案

### 2.1 日志轮转（磁盘不会写满）

`setup_logging(name)` 为每个模块建**幂等**的 logger：`RotatingFileHandler`，
单文件上限 **8 MB**、保留 **5 份**历史（`LOG_MAX_BYTES` / `LOG_BACKUP_COUNT`），
UTF-8 编码，同时输出到控制台。

- 位置：`logs/<模块名>.log`（`config.LOG_DIR`）；
- 长跑批处理时，日志总量上限 = 8 MB × (5+1) × 模块数，**不会随运行时长线性膨胀**；
- 重复调用不叠加 handler（`_wo08_configured` 标记），避免日志重复写。

### 2.2 内存监控（超阈值告警）

`MemoryMonitor(threshold_mb=6000, interval_s=30)`：后台守护线程周期采样
进程 RSS，超阈值即 `WARNING` 写入 `logs/memory.log`；`stop()` 返回
`{current_mb, peak_mb, threshold_mb, over_threshold}`。

阈值 6000 MB 的依据：本机实测峰值约为「embedding(bge-m3) + reranker(bge-reranker-v2-m3 fp16)
+ BM25/倒排索引（7757 篇）+ 图谱（493 节点/810 边）」之和，留出余量。

### 2.3 断点续抽（长时构建的核心保障）

LLM 关系抽取是唯一的小时级步骤（本机约 500 块/小时）。`src/kg_extract_llm.py`：

- 每块结果**即时追加**写入 JSONL 检查点 `data/kg/llm_extract_ckpt.jsonl`；
- `--resume` 时加载检查点，**已完成的块直接跳过**；
- 中断（Ctrl-C / 断电 / Ollama 崩溃）后重新执行
  `python build_kg.py --all --resume` 即从断点继续；
- ⚠️ 注意：**不带 `--resume` 的 `--all` 会全量重抽**（约每小时 500 块），务必带 `--resume`。

### 2.4 异常重启

- 图谱构建：`build_layer1` 秒级可整体重建（无需续跑）；`build_layer2` 由 2.3 的
  JSONL 检查点兜底，重启即续抽；
- 批量评测：`graph_qa_cli.py` 单题失败不中断整批（`run_question` 捕获异常并把
  `error` 写入该题记录），最终结果一次性落盘 `data/eval/graph_qa_results.json`；
  该命令全量 14 题约 1 分钟，重启成本可忽略，**不需要**状态文件；
- 保存环节：`KnowledgeGraph.save` 原子写保证任何时刻磁盘上的图谱都是完整版本（见故障 5）。

### 2.5 健康检查

`health_check()` 汇总三块状态，供界面「系统状态」页与命令行使用：

```bash
python -c "from src.runtime_ext import health_check; import json; print(json.dumps(health_check(), ensure_ascii=False, indent=2))"
```

```json
{
  "ok": true,
  "graph":     {"graph_loaded": true, "graph_nodes": 493, "graph_edges": 810, ...},
  "llm":       {"ok": true, "model": "qwen2.5:3b", "models": [...]},
  "retriever": {"stats": {...}, "strategies": {...}}
}
```

任一子系统不可用 → 顶层 `ok=false`，且对应子块给出 `error`。
典型场景：**同一目录的 Qdrant 嵌入式存储被另一个进程占用**（例如评测脚本
还在跑时又启动界面），此时 `retriever.error` 会明确提示「已被另一实例占用」
并给出两条处置建议（结束占用进程 / 改用服务端模式），而不是给出一个
看似正常却检不到任何内容的检索器。

## 三、降级方案标注表（硬性要求0 Step 4）

按工单要求：凡因**用户拒绝下载模型**而产生的替代实现，必须显式标注。

| 能力 | 工单要求的形态 | 本工程实现 | 是否满足字面要求 | 说明 |
| --- | --- | --- | --- | --- |
| 语音输入 | 界面支持语音提问 | 浏览器原生 **Web Speech API**（`src/speech.py`） | ⚠️ **不完全满足** | 本机无 Whisper 等本地 ASR 权重，用户确认「零下载」。Chrome/Edge 需联网；离线或 Firefox 下不可用，界面明确提示并降级为文字输入。若需完全离线识别，需额外下载 ASR 模型 |
| 关系抽取 | 抽取实体间关系 | 第 1 层词典+正则（离线、确定性）+ 第 2 层本地 LLM（Ollama `qwen2.5:3b`） | ✅ 满足 | 模型为本机已有权重，未触发下载 |
| 文本嵌入 / 重排 | 语义检索与精排 | 本机 `bge-m3` / `bge-reranker-v2-m3` | ✅ 满足 | 零下载（见 `docs/01-本机模型扫描报告.md`） |
| 图谱查询降级 | —— | 图谱不可用时退化为纯 RAG 并标 `degraded` | ✅ 满足 | 属主动容错，非模型缺失；降级**如实标注**，不伪装成正常结果 |
