## 0. 背景与约束

### 0.1 项目目标

构建一个**多用户、多角色**的 RAG 角色扮演系统：用户注册登录后，可选择不同角色（医生、律师……）进行对话；每个角色有独立的人格提示词模板和独立的知识库；对话具备多轮记忆能力。

### 0.2 硬约束（必须遵守）

| 约束 | 说明 |
|---|---|
| **绝不重复安装** | 所有依赖必须使用本机已有环境。仅允许补齐 `rag_env` 中确实缺失的轻量包（`qdrant-client`、`FlagEmbedding`），且这两个包的 wheel 在本机 base 环境已缓存 |
| **模型使用本地** | 嵌入模型、精排模型一律使用 `D:\桌面\模型\` 下的本地文件，禁止在线下载 |
| **生成走 Ollama** | 生成模型使用 Ollama 上已就绪的 `qwen2.5:7b` |
| **显存红线 8G** | 见 §0.4 |

### 0.3 环境矩阵（实测结果）

| 后端需要的库 | base | rag_env | mineru |
|---|---|---|---|
| fastapi / uvicorn / pydantic | ✅ | ✅ | ✅ |
| torch CUDA（精排上 GPU） | ❌ CPU 版 | ✅ | ✅ |
| transformers | ✅ | ✅ | ✅ |
| qdrant-client | ✅ | ✅ **M0 已补** | ✅ |
| pymysql + sqlalchemy | ✅ | ✅ | ❌ |
| redis 客户端 | ❌ | ✅ | ❌ |
| rank-bm25 | ✅ | ✅ | — |

**结论：`rag_env` 作为唯一后端运行时**，M0 已补齐 `qdrant-client`（**唯一新增依赖，dry-run 确认无任何既有包被升降级**）后，即可覆盖全部后端需求（GPU 精排 + MySQL + Redis 三者齐备的唯一环境）。

> 📌 **FlagEmbedding 已确认不需要**（M0 修正）：实测其要求 `transformers>=4.44.2`，而 rag_env 是
> `4.39.3`，安装会触发 transformers 连锁升级并拖入 `datasets/peft/ir-datasets` 等新依赖。
> 改用 rag_env 现有的原生 `transformers` + `torch` 手写 dense+sparse，数学完全等价、零新增依赖。
> 详见 [02-M0环境验证报告.md](02-M0环境验证报告.md) §2.1。

### 0.4 显存预算

| 组件 | 显存（M0 实测） | 策略 |
|---|---|---|
| Ollama qwen2.5:7b | **4.42 GB** + KV cache | 生成时常驻 |
| bge-reranker-v2-m3 (fp16) | **1.06 GB** | **GPU 分时复用**：用时搬入、用完搬回 CPU |
| bge-m3 嵌入 | **0（走 CPU）** | 单条 query 编码 CPU 仅几十毫秒，不抢显存 |
| **生成时峰值** | **≈ 6 GB** | 精排已释放，无争抢 |

> ⚠️ **M0 推翻的关键假设**：原设计让精排**常驻** GPU（预估 2.3GB）。实测若两者同时常驻，
> 显存达 7218/8188 MiB，Ollama 的 KV cache 无处安放，**生成吞吐从 47.8 暴跌到 5.2 tok/s**。
>
> **修正方案**：精排模型权重常驻 **CPU 内存**，每次精排时 `.cuda()` 搬入 → 前向 → `.cpu()` 释放。
> 搬运开销实测仅 148ms（搬入）+ 115ms（搬出），加 150ms 计算 **共约 413ms**，
> 而生成吞吐保持 **47.8 tok/s**。因为**精排发生在生成之前，两者本就不重叠**。

## 2. 数据流与角色人格注入

### 2.1 离线入库流程

```
数据源                解析                    清洗                 分块                   编码                 入库
──────────────────────────────────────────────────────────────────────────────────────────────────────────────
medical/*.pdf   →  PyMuPDF 抽取文本   →  去页眉页脚/水印  →  章节标题+段落    →  bge-m3 dense(1024)  →  Qdrant
                  （文本型，直抽）       去连续空行          512 字符           + learned sparse        kb_medical
                                                           overlap 10%                                   payload: source/page
legal/*.pdf     →  PyMuPDF 抽取文本   →  去页码/多余空白  →  按「第X条」切分    同上                    kb_legal
legal/*.txt     →  直接读取           →  去 BOM           （一条 = 一 chunk）                      payload: law_name/
(176 部法条)                                                 超长条文按句再切                            article_no/source
```

**分块策略按语料类型分流**（法律 RAG 的关键）：

| 语料 | 分块单元 | 参数 | 理由 |
|---|---|---|---|
| 高血压指南 PDF | 章节标题 + 段落 | `chunk_size=512`, `overlap=50` | 叙述性文本，按语义段落切 |
| 民法典 PDF | 「第X条」正则切分 | 单条为单元 | 条文是天然最小语义单元 |
| 176 部法条 txt | 「第X条」切分 | 超长条文按句再切 | 同上 |

**编码器**：用 rag_env 现有的 `transformers` + `torch` **直接加载**本地 bge-m3（不装 FlagEmbedding），
一次前向同时产出 dense 与 sparse：

```python
dense  = mean_pooling(last_hidden_state, attention_mask) → L2 normalize
sparse = relu(sparse_linear(last_hidden_state)) * attention_mask
         → 按 token_id 取 max 聚合（必须过滤 tokenizer.all_special_ids）
```

其中 `sparse_linear.pt` 实测为 `OrderedDict{'weight':[1,1024],'bias':[1]}`，
用 `nn.Linear(1024,1).load_state_dict()` 直接重建即可。两路向量写入 Qdrant 的 named vectors，
检索时并行、RRF 融合——这是"混合检索 + 多路召回"的载体。

> ⚠️ M0 实测：`<s>` 特殊符会带 0.16 权重，**生产代码必须过滤 `tokenizer.all_special_ids`**。

**幂等性**：每条 chunk 用 `sha1(collection + source + article_no + text)` 作 Qdrant point id。重复入库为覆盖而非追加，重跑管线不产生重复数据。

### 2.2 在线问答流程

```
①  用户提问  { user_id, character_id, conversation_id, question }
②  鉴权 → 校验 conversation 归属该 user（越权 403）
③  取角色配置  ←  MySQL: characters.system_prompt, kb_collection, temperature, top_k
④  取短期记忆  ←  Redis: conv:{uid}:{cid} 最近 6 轮（TTL 1h），miss 则回源 MySQL
⑤  Query 改写  ←  LLM 指代消解 + 补全
                 "他吃这个药行吗" → "高血压患者服用XX药是否可行"
⑥  混合检索    ←  Qdrant collection = 角色绑定的 kb_collection
                 dense(bge-m3) ∥ sparse(bge-m3) → RRF 融合 → top 20
                 可选过滤：法律按 law_name 缩小范围
⑦  精排        ←  bge-reranker-v2-m3：权重留 CPU 内存 → 搬入 GPU → 打分 → 搬回并释放显存
                  (约 413ms) → top 5
                  ⚠️ 必须用精排分做阈值过滤；RRF 分是 1/(k+rank) 量化值，会大量并列
⑧  组织上下文  ←  chunk 拼接 + 来源标注（[1] 民法典 第577条 / [2] 指南 P32）
⑨  组装 Prompt  ←  [角色人格 system] + [知识片段] + [短期记忆] + [当前问题]
⑩  流式生成    ←  Ollama qwen2.5:7b（SSE 流式返回）
⑪  后处理      ←  正则清理 markdown 残留、引用编号规范化、追加免责声明
⑫  写回记忆    ←  Redis LPUSH + MySQL 持久化消息表
⑬  返回        { answer, sources[], rewritten_query, trace{召回/精排明细} }
```

第 ⑬ 步的 `trace` 是前端"检索链路可视化"的数据来源，移植时保留。

### 2.3 角色人格注入：三层模板结构

角色扮演的本质不是"换一个 system prompt"，而是**身份 / 风格 / 约束**三层解耦，以实现"加角色零代码改动"：

| 层 | 内容 | 存储位置 | 可编辑 |
|---|---|---|---|
| **身份层** | 角色名、职业、专业背景、擅长领域 | `characters.identity_block` | 前端表单 |
| **风格层** | 语气、称呼、回答长度、是否口语化 | `characters.style_json` | 前端表单 |
| **约束层** | 必须基于知识库、引用来源、边界拒答、免责声明 | `characters.domain_constraints` + `prompt_template` | 前端表单 |

**统一 Prompt 骨架**（所有角色共用，变量占位）：

```
{identity_block}                       ← 身份层渲染

## 你的知识范围
{knowledge_scope}                      ← 由 kb_collection 反推，如"中国现行法律法规"

## 回答要求
{style_block}                          ← 风格层渲染

## 硬性约束
1. 仅依据下方【知识片段】回答，片段中没有的内容明确说"我无法确定"
2. 引用时标注来源编号，格式 [1][2]
3. {domain_constraints}                ← 领域专属
4. 与角色无关的问题，礼貌拒答并引导回专业领域

## 【知识片段】
{context}

## 【对话历史】
{memory}

## 【用户问题】
{question}
```

**两个角色的实例化差异**：

| 变量 | 医生（心血管/营养） | 律师 |
|---|---|---|
| `identity_block` | 从业 20 年的心血管内科医生，擅长高血压诊疗与生活方式干预 | 执业 15 年的中国执业律师，精通民商事法律 |
| `knowledge_scope` | 中国高血压防治指南（2024修订版）等 | 中国现行法律法规（民法典、消保法……） |
| `style_block` | 亲切、先结论后解释、避免堆术语、必要时用比喻 | 严谨、条文优先、先结论后依据、区分"法律规定"与"实务建议" |
| `domain_constraints` | 不给具体处方剂量、建议线下就诊、紧急情况拨 120 | 声明"以下为一般法律信息，不构成正式法律意见" |
| `kb_collection` | `kb_medical` | `kb_legal` |

### 2.4 多用户隔离的三个切面

| 切面 | 隔离手段 | 越权后果 |
|---|---|---|
| 会话归属 | `conversations.user_id` 外键，每次访问校验 | 403 |
| 短期记忆 | Redis key 带 `{user_id}` 前缀 | 读不到 |
| 检索范围 | 由 `character_id` 决定 collection | 天然隔离（知识库是角色级公共资源，非用户私有） |

**关键认知**：知识库不是用户私有的，是**角色绑定的公共资源**。用户 A 和用户 B 都能问律师角色、共享同一 `kb_legal`；但两人的会话历史与记忆互不可见。

## 3. 数据模型与接口清单

### 3.1 MySQL 表结构（6 张表，utf8mb4）

```sql
-- ① 用户
CREATE TABLE users (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  username      VARCHAR(64)  NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,          -- pbkdf2_hmac(sha256, 20万轮)
  salt          VARCHAR(32)  NOT NULL,
  display_name  VARCHAR(64),
  is_active     TINYINT(1)   DEFAULT 1,
  created_at    DATETIME     DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ② 角色（人格模板 + 知识库绑定）
CREATE TABLE characters (
  id                 BIGINT PRIMARY KEY AUTO_INCREMENT,
  slug               VARCHAR(64)  NOT NULL UNIQUE,   -- doctor / lawyer
  name               VARCHAR(64)  NOT NULL,
  category           VARCHAR(32),                    -- 医疗 / 法律 / 社交
  avatar             VARCHAR(255),
  description        VARCHAR(512),
  identity_block     TEXT,                           -- 人格·身份层
  style_json         JSON,                           -- 人格·风格层 {tone, length, address...}
  domain_constraints TEXT,                           -- 人格·约束层（免责声明等）
  prompt_template    TEXT,                           -- 完整模板骨架（含 {context}{question} 占位）
  kb_collection      VARCHAR(64)  NOT NULL,          -- 绑定的 Qdrant collection
  rerank_top_k       INT DEFAULT 5,
  recall_top_k       INT DEFAULT 20,
  temperature        FLOAT DEFAULT 0.3,
  is_builtin         TINYINT(1) DEFAULT 1,           -- 内置角色不可删
  created_at         DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at         DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ③ 会话（多用户隔离的核心外键）
CREATE TABLE conversations (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id         BIGINT NOT NULL,
  character_id    BIGINT NOT NULL,
  title           VARCHAR(128),
  message_count   INT DEFAULT 0,
  last_message_at DATETIME,
  is_deleted      TINYINT(1) DEFAULT 0,
  created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_user_char (user_id, character_id, is_deleted, last_message_at),
  CONSTRAINT fk_conv_user FOREIGN KEY (user_id)      REFERENCES users(id),
  CONSTRAINT fk_conv_char FOREIGN KEY (character_id) REFERENCES characters(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ④ 消息（长期记忆 + 链路追溯）
CREATE TABLE messages (
  id               BIGINT PRIMARY KEY AUTO_INCREMENT,
  conversation_id  BIGINT NOT NULL,
  role             ENUM('user','assistant','system') NOT NULL,
  content          MEDIUMTEXT NOT NULL,
  rewritten_query  TEXT,            -- 改写后的 query（仅 user 消息）
  sources_json     JSON,            -- [{idx, text, source, score, law_name, article_no}]
  trace_json       JSON,            -- 召回/精排明细，供前端可视化
  latency_ms       INT,
  created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_conv_time (conversation_id, id),
  CONSTRAINT fk_msg_conv FOREIGN KEY (conversation_id) REFERENCES conversations(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ⑤ 检索历史（保留参考项目能力，新增归属）
CREATE TABLE search_history (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id     BIGINT NOT NULL,
  query       VARCHAR(512) NOT NULL,
  collection  VARCHAR(64),
  top_k       INT,
  use_rerank  TINYINT(1),
  result_json JSON,                 -- 命中列表快照
  elapsed_ms  INT,
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_user_time (user_id, created_at),
  CONSTRAINT fk_search_user FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ⑥ 知识库文档（支撑"知识库动态更新"）
CREATE TABLE kb_documents (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  collection     VARCHAR(64) NOT NULL,
  source_path    VARCHAR(512) NOT NULL,
  file_hash      CHAR(40)  NOT NULL,   -- sha1，判重 / 判断是否变更
  doc_type       ENUM('pdf','txt','md') NOT NULL,
  chunk_strategy ENUM('auto','article','paragraph') DEFAULT 'auto',
  chunk_count    INT DEFAULT 0,
  status         ENUM('pending','parsing','indexing','ready','failed') DEFAULT 'pending',
  error_msg      TEXT,
  created_at     DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at     DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_coll_hash (collection, file_hash),
  KEY idx_coll_status (collection, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**设计要点**

- 表 ⑥ 的 `UNIQUE(collection, file_hash)` 让入库天然幂等：同文件重复上传只更新状态；`file_hash` 变了才重新解析（动态更新的判定依据）。
- `trace_json` / `sources_json` 用 JSON 列而非拆表——展示型数据，无需 JOIN。
- 索引围绕实际查询路径：会话列表走 `(user_id, character_id, is_deleted, last_message_at)`；消息按 `(conversation_id, id)` 顺序翻页。

### 3.2 Redis 记忆结构

```
Key:   conv:{user_id}:{conversation_id}
Type:  LIST（最新在右侧）
TTL:   3600s（每次写入续期）
Value: JSON 串 {"role":"user","content":"...","ts":1736...}

LPUSH + LTRIM -12 -1  → 恒定保留最近 6 轮（12 条）
Miss → 回源 MySQL messages 取最近 6 轮，重建缓存（懒加载）
```

选 LIST 而非 String 的理由：`LRANGE` 天然按时间序取最近 N 条，`LTRIM` 天然做容量封顶，避免 String 存整个 JSON 数组每次都要重新序列化。

**M0 已就位**：免安装版 Redis 5.0.14.1 在 `tools/redis/`，`bash tools/redis/start_redis.sh` 启动。

> ⚠️ **连接必须加 `encoding_errors="replace"`**：Windows 版 Redis 的 `INFO` 响应含 GBK 编码的
> 中文路径字节，redis-py 7.2.1 默认严格 UTF-8 解码会抛 `UnicodeDecodeError: byte 0xd7`。
> ```python
> redis.Redis(host="127.0.0.1", port=6379, decode_responses=True, encoding_errors="replace")
> ```
