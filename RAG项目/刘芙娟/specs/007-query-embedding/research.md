# Phase 0 Research: 提问落盘与问题向量化（S8）

**Feature**: `007-query-embedding` | **Date**: 2026-09-27 | **Spec**: [spec.md](./spec.md)

本阶段要消解的是"复用哪份实现、模型什么时候加载、门禁卡在哪一步、并发怎么写"这四件事。全部结论**基于实测**，估算值一律标注为估算。

---

## 实测基线（本机，2026-09-27）

跑模型之前先测清楚代价，否则"常驻内存"只是一个听起来无害的词。

| 项 | 实测值 | 怎么测的 |
|---|---|---|
| 权重文件 `pytorch_model.bin` | **2.27 GB** | 文件大小 |
| 加载耗时 | **7.4 s / 11.1 s**（两次） | `Encoder()` 前后计时 |
| 加载后进程**私有内存** | **3,259 MB** | 外部读 `PrivateMemorySize64` |
| 首次编码 | **0.712 s**（含预热） | 单条中文问句 |
| 预热后单次编码 | **0.066 – 0.104 s** | 多次测量 |
| 空闲 45 s 后再编码 | **0.082 s** | 未观察到换页退化 |
| 向量 | `(1024,)` float32，L2 范数 `0.99999994` | 直接读属性 |
| 两次编码逐位相同 | **是** | `(v == v2).all()` |
| 单条向量 JSON 文本 | **21,175 字节** | 1024 个 float32 序列化 |
| float32 → JSON → float32 | **逐位无损**（4096 样本） | 随机向量往返比对 |
| 本机**可用物理内存** | **1.41 GB** | `\Memory\Available MBytes` |

### 由这组数字直接得出的两条结论

**1. 模型能加载，但本机内存很紧。**

可用内存 1.41 GB < 权重的 2.27 GB，加载之所以成功，是靠页面文件兜住了。当时占用最高的是 PyCharm（1.86 GB）与 vmmemWSL（700 MB）。加载后实测进程私有内存 3.26 GB —— 比权重本身多出约 1 GB，是 torch/transformers 运行时的开销。

这不构成本特性的阻断项（实测加载与编码都正常，空闲 45 s 后也没退化），但**必须如实写进验收**：这台机器上同时开 IDE 与服务，换页压力是真实存在的。

> ⚠️ 一处测量不可靠，如实记录：`GetProcessMemoryInfo` 读到的 `WorkingSet` 返回过 0，明显失真。因此**只采信 `PrivateMemorySize64`（3.26 GB）**，不采信 WorkingSet。空闲退化那条结论是基于"实测编码耗时没变"，而不是基于 WorkingSet 的读数。

**2. 单行 JSONL 是 21 KB，不是 10 KB。**

规格里我在裁决 D2 的代价栏写的是"每行约 10 KB"。**实测是 21,175 字节**，翻了一倍 —— 因为一个 float32 用最短往返表示也要 ~19 个字符，1024 个就是 ~20 KB。

按每天 100 问算：**2.1 MB/天，约 64 MB/月**。仍是 MB 级，不影响 D2 的成立（追加写 + 可 grep 的收益仍在），但规格里的那个数字要改。

**3. float32 → JSON → float32 无损**，这是 SC-010（读回逐位相同）能够成立的前提。JSON 用最短往返表示，而原值本身就是 float32 的精确表示，所以转回 float32 必然回到同一个位模式。已验证 4096 个随机样本全部逐位相同。

## R1. 复用既有实现，不新建编码层

**Decision**：直接 `from backend.embed.model import Encoder, fingerprint`。本特性**不新增任何编码逻辑**，连"薄封装"都不做。

**Rationale**：

`backend/embed/model.py` 的模块文档字符串在 specs/004 里就写好了这件事：

> BGE-M3 编码器 —— **全项目唯一的编码口径定义**（D3）。批处理脚本（S5）与**将来的后端查询（读路径）共用本模块**，口径只有一处，"抄错口径"的风险因此为零。

它已经提供了 `encode_query(text)`，`MODEL_DIR` 的默认值也已经是 `E:\资料\BAAI--bge-m3`。**本特性只需要用它。**

我原本打算加一个 `backend/query/encoder.py` 做"常驻单例的薄封装"。**放弃了**，理由：

- 薄封装会变成第二个"编码入口"。今天它转发给 `Encoder`，明天有人为了加个缓存/日志/重试就在里面写逻辑 —— 而"口径只有一处"这个保证**恰恰是靠没有第二个入口来维持的**。
- 常驻单例这件事不需要新模块：`backend/query/service.py` 里一个模块级变量即可。

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| 新建 `query/encoder.py` 薄封装 | 制造第二个编码入口，口径单一性靠自觉维持 |
| 复制一份编码代码到查询侧 | 直接违反 FR-009/FR-032；且这正是 `docs/04` §8 列为头号风险的"向量空间漂移"的标准成因 |

## R2. 加载时机与失败行为 → 启动期加载，失败即启动失败

**Decision**：`backend/serve.py` 启动流程中加载模型。**加载失败 → 打印可读错误 → 非 0 退出**，MUST NOT 以"能提问但算不出向量"的状态继续运行。

**Rationale**：

1. **既有文档已经把它归为关键项**。`docs/05` §3.3 的 `/health` 把 `embedding_model` 与 `config`、`index`、`milvus` 并列为**关键项**，任一失败 → `status: "down"` → 503。既然它在健康检查里是"服务不可用"的判据，那在启动时拒绝启动与之一致。
2. **降级状态的失效方式很隐蔽**。若允许启动，用户提问照常拿到 200 与"能力未接入"文案，运维看服务活着、日志没报错 —— 只有翻开留存记录才会发现所有条目都是"向量化失败"。这正是 constitution 原则 III 要防的"静默降级"。
3. **失败是确定的、不是波动的**。模型加载失败（目录不对、权重残缺、内存不足）不会在几分钟后自愈，重启也不解决 —— 没有"先起来再说"的价值。

**代价（必须写进验收）**：服务启动从 < 1 s 变成 **7–11 s**。任何"启动后立刻探测端口"的脚本都要相应放宽等待时间，否则会得到假的"服务未就绪"。

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| 懒加载（首次提问时加载） | 第一次提问卡 7–11 s；`docs/05` §2.4 的端到端 10 s 预算被一次加载全吃掉；且这个卡顿会被误认为"服务卡死" |
| 加载失败仍启动，标记 degraded | 静默降级，见上 |
| 后台线程异步加载，加载完前拒绝请求 | 复杂度增加，且"请求到达时模型还没好"仍需要一个失败路径 —— 等价于懒加载的坏处 |

## R3. 指纹门禁的时机 → 启动期一次

**Decision**：在启动期读 `data/index_manifest.json`，把它的 `pipeline_config.embed` 块与本进程算出的指纹逐字段比对。不一致 → 启动失败。

**比对基准**（实测该块有 10 个字段，与 `fingerprint()` 的返回一一对应）：

| 字段 | 索引侧实测值 |
|---|---|
| `model_dir` | `E:\资料\BAAI--bge-m3` |
| `config_sha256` | `26159e7a…49fa` |
| `weight_file` | `pytorch_model.bin` |
| `weight_bytes` | `2271145830` |
| `max_length` | `4096` |
| `pooling` | `cls` |
| `normalization` | `l2` |
| `dtype` | `float32` |
| `dim` | `1024` |
| `rule_version` | `embed-v1+bge-m3` |

**Rationale**：

- 编码参数在进程生命周期内**不会变**（`max_length` 等是启动参数，模型权重不会在运行时被替换）。每个请求比对一次，等于反复读一个 12 KB 的 JSON 文件去回答一个恒定不变的问题。
- FR-017 只要求"校验先于任何写入" —— 启动期一次即满足（启动早于一切写入）。
- 出错早、信息全：启动时就告诉运维"哪一项对不上"，比等第一次提问才发现好。

**已知局限（如实记录，本期不解决）**：

服务运行期间若**重新入库**（specs/005 的 S6 被重跑，索引指纹变了），运行中的服务指纹就陈旧了 —— 它仍在用旧口径编码，而库里已经是新口径。本期的处置是**不做处置**，但要把补救点写在案：

- `docs/05` §3.3 的 `/health` 里已设计 `matches_index` 检查，那是正解 —— 服务重新校验一次并暴露不一致。`/health` 不在本特性范围内。
- 运维规程上：**重新入库后必须重启服务**。这条要写进 quickstart。

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| 每次请求比对 | 每请求一次无谓的文件 IO；且比对结果恒定 |
| 每次请求比对 + 缓存 mtime | 复杂度换来的只是"不用重启"，而重启本来就是 11 s 的事 |

## R4. 落盘形态与并发写

**Decision**：

- 路径：`data/questions/{yyyymmdd}.jsonl`，一行一条记录，文件名按**本地日期**切分。
- 写入：`open(path, "a", encoding="utf-8", newline="\n")`，**一次 `write()` 写入整行**（含末尾 `\n`），随即 `flush()`。
- 编码：`json.dumps(..., ensure_ascii=False, separators=(",", ":"))` —— 与 `backend/api/events.py` 同一套约定。
- 时间戳：ISO 8601 带时区偏移（与 `index_manifest.json` 的 `built_at` 格式一致），如 `2026-09-27T20:31:38+08:00`。

**Rationale**：

**为什么按日期切分**：单个文件无限增长会让"找出某天的问题"变成全文扫描；按天切分后，清理（FR-028）就是删文件，而不是重写整个文件。删文件天然比重写安全。

**为什么整行一次写入**：即使退一步假设存在并发，单次 `write()` 配合 `O_APPEND` 的偏移原子性，也不会出现两行字节交错 —— 而"分多次写"（先写前半、再写向量）则必然有交错窗口。

**并发假设（必须写明，因为它是个假设）**：

当前 `backend/serve.py` 以 `uvicorn.run(app, ...)` 单进程启动，asyncio 单事件循环。请求处理器之间**不存在真并发**，一个 `write()` 中间不会插入另一个请求的写 —— 因为写操作里没有 `await`。

⚠️ **若将来启用 `--workers N` 或多进程部署，这个保证立刻失效**，需要改用文件锁（Windows 上 `msvcrt.locking`）。本期不实现，但要在 `store.py` 的注释里点明这个前提，否则后来者会以为它是并发安全的。

**为什么不做成异步写/线程池**：21 KB 的本地追加写在磁盘上是亚毫秒级。引入线程池会带来"写序不确定"的新问题，收益却接近零。**用复杂度换一个测不出来的收益，是净亏。**

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| 一问题一 `.npy` | 文件数爆炸（每天 100 问 → 三个月 9000 个小文件）；且问题与向量分处两地，一侧写失败就产生孤儿文件 |
| 共享矩阵 + 行对齐（specs/005 模式） | `.npy` 不支持追加，每来一问要重写整个矩阵；且"追加写"这条语义得重新表述，与 FR-004 冲突 |
| 写入 SQLite | 引入数据库依赖与 schema 迁移负担，而 MVP 体量用不上查询能力 |

## R5. 模块拆分

**Decision**：

```text
backend/
├── serve.py                  # 唯一进程入口（改：启动期加载模型 + 门禁）
├── embed_chunks.py           # S5 离线管线入口（不动）
├── embed/                    # S5 实现包（不动；本特性只 import）
├── api/                      # 运行时服务（specs/006）
│   └── capture.py            # ★ 新增：提问采集的接缝
└── query/                    # ★ 本特性新增
    ├── __init__.py           # 常量、错误类型、退出码、JSONL 字段名
    ├── gate.py               # 指纹门禁（读清单 + 比对）
    ├── store.py              # JSONL 追加写 / 读取 / 按日期清理
    ├── service.py            # 常驻 Encoder + capture_and_embed（服务端与 CLI 共用）
    └── query_embed.py        # ← 不在这里，见下
└── query_embed.py            # ★ CLI 唯一入口（批量 / 清理 / 自检）
```

**切分理由**（按"什么时机可能出错"）：

| 模块 | 只做 | 为什么单独切出来 |
|---|---|---|
| `__init__.py` | 常量与契约：字段名、路径模板、退出码、错误类型 | 让 JSONL 的字段名只有一处定义 —— 写入方与读取方引用同一份常量，改名不会只改一半 |
| `gate.py` | 读清单、比对、报错 | 这是唯一"读别人的产物来判断自己能不能干活"的地方；独立后可以单独测（README 用例 2 就是只测它） |
| `store.py` | 文件读写与清理 | 唯一碰文件系统的地方；并发前提写在这里的注释里 |
| `service.py` | 常驻 Encoder + 组装一条记录 | 服务端与 CLI 的**共用实现**（FR-012/FR-032）；单条与批量走同一函数，两条路径不可能漂移 |
| `api/capture.py` | 把提问交给 service，处理失败 | 让 `routes.py` 保持"只做协议转换"（specs/006 FR-015 的约束）；失败不拖垮应答的决策集中在这一处 |

**为什么 CLI 入口放在 `backend/` 根而不是 `backend/query/` 内**：与既有约定一致 —— `backend/chunk_clean.py`（入口）配 `backend/chunk/`（实现）、`backend/index_milvus.py` 配 `backend/index/`、`backend/embed_chunks.py` 配 `backend/embed/`。本特性沿用这个形状。

**Alternatives considered**：全部塞进 `backend/query_embed.py` 单文件（会超 300 行，违反 FR-023）；放进 `backend/embed/`（那是 S5 离线管线的包，混入运行时代码会让"离线管线不被后端进程调用"这条边界消失，`docs/05` §5 明确划了这条线）。

## R6. 失败不拖垮请求（FR-011）的落法

**Decision**：`backend/api/capture.py` 捕获落盘/向量化过程中的异常，**记一条 `capture_failed` 日志**（含 `answer_id` 与异常类型），然后**正常返回**，让应答流程继续。

**与 constitution 的张力，以及怎么解**：

constitution 的代码规范写着"代码 MUST NOT 以 try/except 吞掉证据不足、密钥缺失等失败条件——这些 MUST 显式暴露"。这里有张力，但**不是冲突**：

> 被禁止的是**吞掉**（静默、不可观测），不是**捕获**。本设计的失败是显式暴露的：日志里有 `capture_failed`、有 `answer_id`、有异常类型。

区分标准是"**事后能不能查出来这次提问没有被留存**"。能，就不是吞掉。

**为什么不让提问失败**：留存活在应答链路的旁支上（`docs/05` §4.4 的装配是纯函数，本特性不改它）。用户来是为了问答，不是为了帮系统写日志。为了一次落盘失败把一个能正常回答的请求打成 500，是把系统的内部维护成本转嫁给用户。

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| 落盘失败 → 请求失败 | 用户承担系统内部故障；且违反 FR-011 |
| 完全静默（连日志都不记） | 真·吞掉，违反 constitution |

## R7. 服务的启动输出与启动时间

**Decision**：`serve.py` 在加载模型前后各打印一行，让"慢在哪"可见：

```text
正在加载 BGE-M3 权重（约 2.3 GB，首次约 10 秒）…      ← 加载前
权重已加载（7.4 s），编码指纹 26159e7a…              ← 加载后
指纹与索引一致（med_rag_v1 / 65 chunks）              ← 门禁通过
医知源服务已启动  http://127.0.0.1:8000/              ← 开始监听
```

**Rationale**：启动从 < 1 s 变成 ~10 s，是一处**用户可感知的变化**。若只打印最后一行，使用者会经历 10 秒的"按了没反应"，然后怀疑是不是自己命令打错了 —— 而这 10 秒是设计内的、有明确原因的。把原因打出来，这 10 秒就从"故障"变成"预期"。

同理，门禁失败时的错误信息 MUST 点出**参数名与两个取值**（FR-016），而不是只说"指纹不一致"。

## 汇总：研究消解的未知

| 规格/任务书中的未知 | 结论 |
|---|---|
| 如何复用既有编码实现 | 直接 import `Encoder`/`fingerprint`，不建第二层（R1） |
| 模型加载时机与失败行为 | 启动期加载，失败即非 0 退出（R2） |
| 指纹门禁的时机 | 启动期一次；已知局限与补救点已记录（R3） |
| JSONL schema 与并发写 | 按天切分、整行一次写、单进程前提显式写明（R4） |
| `backend/` 下如何拆分 | `query/` 四模块 + `query_embed.py` 入口 + `api/capture.py` 接缝（R5） |
| 失败不拖垮请求怎么落 | `capture.py` 捕获 + 显式失败日志（R6） |

**无残留待确认项。**
