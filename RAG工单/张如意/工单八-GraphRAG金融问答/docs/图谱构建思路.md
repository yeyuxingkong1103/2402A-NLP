# 图谱构建思路 —— 实体、关系是怎么创建出来的

> **工单编号：人工智能NLP-RAG-基于Graph RAG 实现金融问答**
>
> 本文档专门回答演示视频的第二个要求：**「展示对 Graph RAG 构建的知识图谱的可视化展示，
> 以及如何进行实体、关系的创建思路的讲解」**。
>
> 讲解主线：**Prompt 设计 → 类型体系选择 → 抽取 → 归一化 → 社区检测与摘要**，
> 每一步都给出「为什么这么做」以及「不这么做会怎样」。

## 〇、一句话总览

> 实体和关系**不是预先定义的字典，而是 LLM 逐块从年报原文里读出来的**；
> 我们提供的是一套**类型体系（Schema）**，用来约束抽取结果的形状，
> 使不同文本块、不同文档抽出来的实体能够落到同一套类型上，从而可以被合并、检索、统计和可视化。

```
年报原文  ──①分块──▶  文本块  ──②LLM抽取──▶  实体+关系 JSON  ──③归一化合并──▶  知识图谱
                        │                      │                        │
                   章节路径注入          类型体系约束            别名消解/同向边加权
```

对应的代码位置：

| 步骤 | 代码 |
| --- | --- |
| ① 分块 | `rag_core/chunk.py::chunk_structure`（由 `src/prepare_corpus.py` 调用） |
| ② 抽取 | `rag_core/graph_rag.py::GraphExtractor.extract`（prompt 见 `_SYS_OPTIMIZED`） |
| ③ 归一化 | `rag_core/graph_rag.py::KnowledgeGraph.add_extraction` / `_resolve_alias` / `_rebuild_graph` |
| ④ 社区 | `rag_core/graph_rag.py::KnowledgeGraph.detect_communities` / `summarize_communities` |
| 全流程 | `rag_core/graph_rag.py::build_knowledge_graph`（由 `src/build_graph.py` 调用） |

## 一、抽取 Prompt 的设计

`optimized` 档位的系统提示词（`_SYS_OPTIMIZED`）包含六个设计点，每一点都对应一个真实坑：

### 1. 封闭类型枚举（封住输出空间）

prompt 里把 `FIN_ENTITY_TYPES`（11 类）与 `FIN_RELATION_TYPES`（15 类）逐条列出，
并明确要求 **`type` 必须从这个列表中选择**。

> **不这么做会怎样**：模型的自由发挥会产生「银行机构」「金融机构」「企业」等近义类型，
> 同一类实体被贴上几十种不同标签，类型统计失去意义，可视化也无法按类型着色。

### 2. 指代还原（解决跨块实体对齐）

prompt 原文：

> 实体名称必须是完整规范的全称，不要用「公司」「本公司」「该行」等指代，
> 遇到指代要还原成文本中出现的具体名称（如「平安银行股份有限公司」）。

> **不这么做会怎样**：9 份年报里每一份都会自称「本行」「本公司」「本集团」。
> 若不还原，这些指代会全部合并成一个名为「本公司」的节点，
> 把 9 家不同机构的业务、指标、风险混成一锅——这是金融多文档图谱最致命的错误。

### 3. 指标带报告期（解决数值串台）

prompt 原文：

> 财务指标实体要带期间，例如「营业收入（2019年）」，并把它在文本中的具体数值写进 description。

> **不这么做会怎样**：年报里「2019年营业收入」「2018年营业收入」「2017年营业收入」
> 会塌缩成同一个「营业收入」节点，三行数值被累加进同一段 description，
> 于是「招商银行2019年营业收入是多少」会答出三个数字，且无法判断哪个是 2019 年。

### 4. 只抽明确陈述的关系（抗幻觉的第一道闸）

prompt 原文：

> 关系必须是文本中**明确陈述**的，不要推断。每条关系的 description 要引用原文的关键短语作为依据。

> **不这么做会怎样**：模型会基于常识补出「平安银行 —投资→ 某某公司」这类原文没有的关系，
> 这类幻觉在图上看起来完全正常，但在答数值题时会给出错误论据。
> 有了 description 的原文依据，人工核对（以及本工单的 `extraction_examples.md`）才有落脚点。

### 5. 突出「指标数值 / 同比变化」（对齐评测问题）

prompt 原文：

> 注意抽取「指标数值」「同比变化」这两类关系——它们是回答数值型问题的关键。
> 遗漏比冗余更严重：宁可多抽有原文依据的关系，也不要漏掉关键数值关系。

> **为什么**：`questions/eval_question.md` 中 Q05~Q09 全是数值型问题，
> 且 `sample_questions.pdf` 的参考答案里大量出现「同比增长 15.28%」这类表述。
> 这两类关系就是数值型问答的「检索高速公路」。

### 6. Few-shot 示例（固化输出格式与粒度）

prompt 中内嵌一个完整的输入输出示例：

```
输入：「2019年，本行实现营业收入1,379.58亿元，同比增长18.2%。」

输出：
{"entities": [
  {"name": "营业收入（2019年）", "type": "财务指标", "description": "1,379.58亿元"},
  {"name": "报告期（2019年）",   "type": "时间",     "description": "2019年"}],
 "relations": [
  {"source": "营业收入（2019年）", "target": "报告期（2019年）", "type": "指标数值",
   "description": "2019年营业收入为1,379.58亿元"},
  {"source": "营业收入（2019年）", "target": "报告期（2019年）", "type": "同比变化",
   "description": "同比增长18.2%"}]}
```

> **为什么有效**：示例同时告诉模型三件事——实体怎么命名（带期间）、
> 数值放在哪里（description）、一段话至少要抽出两条关系（数值 + 变化）。
> 没有示例时，模型经常只抽实体不抽关系，或者把数值丢掉。

### 7. 二次补漏（gleaning）

`optimized` 档位在首轮抽取后追加一轮 `_SYS_GLEAN`，专门检查四类遗漏：

1. 只出现过一次的数字（金额、比例、年份）
2. 中文括号、顿号分隔的并列实体（如「A、B、C 三家公司」中的 B 和 C）
3. 表格中的行列对应关系
4. 否定表述中的实体（如「不存在控制关系的关联方」）

> **为什么需要**：LLM 的首轮抽取会优先抓「显眼」的主干关系，
> 长尾数值和并列实体很容易被吞掉。补漏轮把「已抽取的实体」一起给它，
> 让它专注于「还缺什么」，实测能显著提高数值关系的召回。
> 代价是每块多一次调用，因此可在 `PromptProfile` 中用 `gleaning_rounds=0` 关掉。

### 8. 上限保护

单块最多 30 个实体 / 45 条关系（`max_entities` / `max_relations`）。
年报的财务附注表格块动辄上千行，不设上限会导致输出被截断，反而丢掉结构化结果。

## 二、金融领域类型体系的选择理由

完整的类型表见《技术文档》第四节，这里只讲**选择逻辑**。

### 2.1 实体类型：按「问答需要什么」倒推

评测问题可以归成四类信息需求，实体类型体系正好与之一一对应：

| 信息需求 | 对应实体类型 | 对应评测题 |
| --- | --- | --- |
| 谁（主体） | 公司、机构、人物 | Q01~Q10 全部 |
| 做什么（业务） | 金融产品、业务板块、行业、地区 | Q02、Q04、Q10 |
| 多少（度量） | 财务指标、时间 | Q05~Q09 |
| 受什么约束（风险/监管） | 风险类型、监管政策 | Q03、Q04、Q10 |

**为什么不把「财务指标」再拆细？**
因为年报里同一个指标会出现多种表述（「不良贷款率」「不良率」「不良贷款比率」），
拆分越细，模型的选择越不一致，反而降低合并率。**Schema 的第一价值是稳定可合并，
第二价值才是语义精细度。**

### 2.2 关系类型：按「答案路径」设计

关系类型的多少取决于「答案需要经过几跳」：

- 「招商银行2019年营业收入是多少？」
  → 需要 `披露指标`（文档→指标）+ `指标数值`（指标→数值）
- 「招商银行营业收入同比增速？」
  → 需要 `同比变化`
- 「平安银行面临哪些风险？」
  → 需要 `面临风险`
- 「中国平安与平安银行是什么关系？」
  → 需要 `控股股东` / `子公司`（这两个方向都要有，因为提问方向可能反过来）
- 「这些机构的共同策略是什么？」
  → 单条关系不够，需要**社区摘要**（第四节）

`提及` 是兜底关系：当模型识别出「文档提到了某实体」但没有更强语义关系时用它，
避免这条信息彻底丢失。

### 2.3 一个具体的取舍例子

**「指标数值」为什么不做成实体属性，而要做成关系？**

如果做成属性（`营业收入(2019年).value = 2697.03亿`），
属性无法参与「实体链接 → 沿关系扩展」的检索过程，图谱会退化成一张「实体表」，
既不能展示三元组网络（验收要求），也无法回答「哪些指标在 2019 年同比增长超过 15%」这类需要遍历关系的问题。

做成关系后：`营业收入(2019年) --[指标数值]--> 报告期(2019年)`，
description 里存 `2697.03亿元` —— 检索时子图会自然带上这条边及其依据，
LLM 也能在上下文中看到「数值 + 期间 + 原文短语」三件套。

## 三、实体归一化与别名消解

即使 prompt 要求用全称，实际抽取结果仍会存在多种写法。核心库用**三级流水线**处理：

```
原始实体名
   │  ① _norm_name()      去空白、去首尾标点、全角括号「（）」转半角「()」、
   │                      剔除纯指代（「本公司」「该行」「本行」「发行人」等）
   ▼
规范化名称
   │  ② _resolve_alias()   a. 查别名索引 _alias_index（之前登记过的别名直接命中）
   │                       b. 与已有规范名做包含匹配：双方长度 ≥6 且一方包含另一方 → 视为同一实体
   ▼
规范名称（canon）
   │  ③ add_extraction()   描述累加去重（截断 400 字）、记录来源 chunk_id、登记别名
   ▼
图谱节点
```

### 3.1 冲突处理规则

| 场景 | 处理 | 结果 |
| --- | --- | --- |
| 「平安银行」 vs 「平安银行股份有限公司」 | 长度 ≥6 且包含 → 合并 | 统一为「平安银行股份有限公司」，前者登记为别名 |
| 「本行」「本公司」（单独出现） | `_norm_name` 直接剔除 | 丢弃，避免污染 |
| 「招商银行」 vs 「招商证券」 | 长度 4 < 6，且互相不包含 | 不合并（避免误合并） |
| 「中国平安」 vs 「中国平安保险（集团）股份有限公司」 | 前者 4 字 < 6，不触发包含匹配 | 保持独立（保守策略，宁可少合不要错合） |

> **设计取舍**：包含匹配加了「长度 ≥ 6」的门槛，是**故意保守**。
> 金融语料里「招商银行 / 招商证券 / 招商局」这类前缀相同的不同法人主体极多，
> 激进合并会造成比不合并严重得多的错误（把两家的财务数据混在一起）。
> 短名建议依靠 prompt 的「全称要求」+ few-shot 示例在源头解决。

### 3.2 别名与实际检索

被合并的别名会写入 `Entity.aliases`，并在 `link_entities()` 中参与匹配：

```python
for name, e in self.entities.items():
    if name and name in query:            # 全称直接命中
        hits.append(name)
    elif any(a and a in query for a in e.aliases):   # 别名命中
        hits.append(name)
```

因此用户问「平安银行的拨备覆盖率」，即使图谱里存的是全称，
也能通过别名匹配到同一个节点。若仍无命中，`link_entities` 还会用正则
`[一-鿿]{4,}(?:股份有限公司|有限公司|集团|银行)` 从问题里抠出候选公司名做后缀匹配，
最后按节点度数排序返回 Top-5 种子实体。

### 3.3 关系的去重与加权

关系层面按 `(source, target)` 合并同向边：

- `weight` 累加出现次数 → 可视化时**边的粗细 = 该关系在年报中被强调的强度**
- `type` 不同则用 `|` 拼接（如 `指标数值|同比变化`）
- `description` 去重后累加（截断 400 字）→ 保留所有原文依据

## 四、社区检测与社区摘要的作用

### 4.1 为什么需要它

传统 RAG 的检索单元是 chunk，Top-K 之后拼成上下文。
对于「**这些银行和保险公司应对经济周期的共同策略是什么**」（Q04）这类问题，
答案分散在 9 份文档的几十个 chunk 里，Top-5 的 chunk 无论如何也覆盖不全。

Graph RAG 的解法是**先把图切成主题簇，再为每个簇生成摘要**：

```
Louvain 社区检测（按连接稠密度切分）
        │
        ├── 社区 0（86 个实体）：零售金融 / 财富管理 / App / 客户经营 …
        ├── 社区 1（74 个实体）：拨备覆盖率 / 不良贷款率 / 逾期贷款 / 减值损失 …
        ├── 社区 2（61 个实体）：资本充足率 / 核心一级资本 / 利润留存 …
        └── 社区 3（58 个实体）：科技投入 / 数字化 / 专利 / 绿色金融 …
                │
                ▼
        逐社区 LLM 摘要（150 字以内）
        "本社区聚焦银行资产质量与风险抵补能力，主要涉及平安银行、招商银行等机构的
         拨备覆盖率、不良贷款率、逾期贷款与信用减值损失……"
```

全局检索（`global_search`）就发生在这些摘要上：把问题与所有社区摘要做相关性排序，
取 Top-3 摘要作为上下文，于是「跨文档的共性」被浓缩进了有限长度的上下文里。

### 4.2 参数与产物

| 项 | 值 | 说明 |
| --- | --- | --- |
| 算法 | Louvain（`nx.community.louvain_communities`） | 内置在 networkx，无需额外依赖 |
| `resolution` | 1.0（可调） | 越大社区越细；`build_graph.py --resolution` 可调 |
| `seed` | 42 | 固定随机种子，结果可复现 |
| 摘要条数 | 默认前 20 个社区（`--communities-top`） | 摘要需要 LLM 调用，按社区规模优先 |
| 摘要长度 | ≤150 字 | 提示词内约束 |
| 提示词输入 | 社区实体（最多 40 个）+ 社区内部关系（最多 60 条，带 description） | 摘要基于结构而非原文，避免引入幻觉 |

### 4.3 社区摘要在本工单中的三处用途

1. **问答**：`GraphRAG(mode="hybrid")` 的全局检索通道（Q04、Q10 主要靠它）
2. **研报**：`research_report.py::rank_communities` 按主题相关性给社区排序，
   选中社区的摘要直接构成研报的「行业背景」与「战略布局」章节
3. **可视化**：`results/graph/knowledge_graph.html` 的右侧详情面板与
   `results/graph_stats.json` 的 `communities` 字段，展示每个社区的大小、成员与摘要

## 五、抽取示例（原文 → 抽取结果）

> 完整版由 `src/visualize_graph.py` 自动生成在 `results/extraction_examples.md`
> （逐类型给出真实抽取对照）。下面是几个具有代表性的形态：

### 示例 1：数值 + 同比变化

**原文**（平安银行 2019 年年度报告，第 51 页）：
> 不良贷款率 1.65%，较上年末下降 0.10 个百分点；拨备覆盖率 183.12%，较上年末增加 27.88 个百分点……

**抽取结果**：
```json
{"entities": [
  {"name": "不良贷款率(2019年)", "type": "财务指标", "description": "1.65%"},
  {"name": "拨备覆盖率(2019年)", "type": "财务指标", "description": "183.12%"}],
 "relations": [
  {"source": "不良贷款率(2019年)", "target": "平安银行股份有限公司", "type": "指标数值",
   "description": "2019年末不良贷款率1.65%"},
  {"source": "不良贷款率(2019年)", "target": "报告期(2018年)", "type": "同比变化",
   "description": "较上年末下降0.10个百分点"}]}
```
→ 这条链路让「平安银行2019年不良贷款率是多少」（Q03）能直接命中数值与变化方向。

### 示例 2：指代还原

**原文**（招商银行 2019 年年度报告，第 19 页）：
> 2019 年本集团实现归属于本行股东的净利润 928.67 亿元，同比增长 15.28%

**抽取结果**：
```json
{"entities": [
  {"name": "招商银行股份有限公司", "type": "公司", "description": "本集团/本行"},
  {"name": "归属于本行股东的净利润(2019年)", "type": "财务指标", "description": "928.67亿元"}],
 "relations": [
  {"source": "归属于本行股东的净利润(2019年)", "target": "招商银行股份有限公司",
   "type": "披露指标", "description": "2019年实现归属于本行股东的净利润928.67亿元"},
  {"source": "归属于本行股东的净利润(2019年)", "target": "报告期(2018年)",
   "type": "同比变化", "description": "同比增长15.28%"}]}
```
→ 注意「本集团/本行」被还原成了「招商银行股份有限公司」，而不是留下一个「本行」节点。

### 示例 3：并列实体（gleaning 补漏的典型战果）

**原文**：
> 跨界参与咖啡零售、出行预订和影票销售等场景

**首轮可能只抽到**：`咖啡零售`
**补漏轮补上**：`出行预订`、`影票销售`，并补齐
`平安银行股份有限公司 --[提供产品服务]--> 出行预订`

→ 对应 Q02「创新商业模式有哪些」，三个场景缺一不可。

### 示例 4：股权关系（关系方向）

**原文**（中国平安 2019 年年度报告）：
> 平安银行 …… 本集团持有其 49.56% 的股份，为其控股股东

**抽取结果**：
```json
{"relations": [
  {"source": "中国平安保险（集团）股份有限公司", "target": "平安银行股份有限公司",
   "type": "控股股东", "description": "本集团持有平安银行49.56%股份"}]}
```
→ 有了这条边，问「中国平安和平安银行是什么关系」时，
种子实体「平安银行股份有限公司」沿**入边**两跳内即可拿到答案。

## 六、可视化中如何「看见」这些设计

用浏览器打开 `results/graph/knowledge_graph.html`：

| 操作 | 观察到的设计 |
| --- | --- |
| 看节点颜色 | 11 类实体类型各自配色，一眼看出语料里哪种类型最多 |
| 点击「财务指标」图例关闭 | 剩余网络露出「公司—公司」的股权/子公司骨架 |
| 点击任意指标节点 | 右侧面板显示：类型、度数、别名、累积 description（多来源合并的证据） |

| 对比 `knowledge_graph.png` 与 `knowledge_graph_circular.png` | 环形布局下社区聚集更明显（同一社区的节点挤在一起） |

`results/graph_stats.json` 中的 `entity_type_distribution`、`relation_type_distribution`、
`top_entities`、`communities` 则是同一批设计决策的**量化体现**。
