## 一、测试方法

### 1.1 为什么是"检索评估"而不是"端到端打分"

RAG 的答案错误可能来自**检索没找到**，也可能来自**找到了但没答对**。二者改进方向完全相反
（一个改召回/精排，一个改提示词/生成）。因此本工单把二者**分开度量**：

- **检索事实覆盖**：top-k 片段并集里，本题的关键事实出现了几个 → 度量"证据是否到手"；
- **答案准确率**：最终答案里，关键事实出现了几个 → 度量"证据是否被正确用上"。

两值并列即可**直接定位失败环节**。示例（hybrid 策略）：

| 题 | 检索覆盖 | 答案覆盖 | 判读 |
| --- | --- | --- | --- |
| id1 | 0.83 | 0.00 | 证据到手，**生成端**丢失要点 |
| id6 | 1.00 | 0.00 | 证据到手，**生成端**取错数（精排把正确表压到第4位） |
| id2 | 0.00 | 0.00 | **检索端**失败 |
| id10 | 0.00 | 0.11 | **检索端**失败（证据在图像里） |

### 1.2 金标准的构造与自检（关键前置步骤）

金标准不能由 LLM 生成（会把模型幻觉固化成"正确答案"），必须**回原文逐字核对**：

1. 用 `scripts/grep_corpus.py` 在 9 份 TXT 里检索关键词，拿到**原文句子 + 页码**；
   TXT 是结构化 JSONL（`{"page":N,"type":"text|excel","inside":"..."}`），页码可直接采信；
2. 数值逐位抄录（含千分位与百分号），单位单独记录（本语料混用 百万元/元/亿元 5 种量纲）；
3. 写入 `data/eval/ground_truth.json`，**区分两个字段**：
   - `evidence_facts` —— 判**检索相关性**用的证据串（必须能在某个块里逐字找到）；
   - `key_facts` —— 判**答案**必须包含的内容（可以比 evidence 更严，如单位、专名）。
4. **跑 `scripts/validate_ground_truth.py` 自检**（评估前强制闸门）：
   逐条统计 `evidence_facts` 在全语料的命中块数，
   **0 命中 → 报错**（说明写成了转述，会把指标假性压低）；
   **> 200 命中 → 告警**（说明过泛，无区分度，会稀释 Recall）。

> 实测价值：首轮自检揪出 6 条 0 命中 + 2 条过泛。若跳过这步，
> id10 的 Recall 分母会被兜成 1、该题所有块判为不相关，报告会呈现
> "系统全面失败"的**错误**结论。

### 1.3 三策略对比的设计

同一批 10 题，固定嵌入模型 / Reranker / top-k，**只切换检索策略**（`vector` / `fulltext` /
`hybrid`），逐题记录同一套指标。这样任何差异都可归因到策略本身。

**关键实现约束**：留痕必须走 `rag.retrieve`（含 Query 理解 + 文档路由），
而非 `strategies.retrieve` 裸检索——否则"检索留痕"与"答案实际看到的片段"不一致。
实测差异显著：id6 在裸检索下被中信证券的同名表格挤占（覆盖 0.00），
走完整链路后为 1.00。本工单全部留痕均走 `rag.retrieve`。

### 1.4 失败归因方法

对判定为失败的题，逐层下钻到**可复核的原始数据**：

```
答案错 → 看 answer_fact_check.miss（缺哪个事实）
      → 看 hits[].rank 与 rerank_score（正确证据排第几、多少分）
      → 看 chunks.json 里该块的 block_type / heading_path / 长度（分块是否合理）
      → 看 doc_route.sources（路由是否限定到正确文档）
      → 结论落到具体环节（召回 / 精排 / 分块 / 路由 / 生成）
```

## 二、评估指标定义

全部指标取值 0—1，**实现复用上游 `evaluate_retrieval.py`**（`score_hits` / `corpus_stats` /
`answer_accuracy` / `ndcg_at_k`），保证与 01~06 报告可比。

设 top-k 结果的相关性标记为 `rel_i ∈ {0,1}`，`i = 1..k`；
`rel_i = 1` 当且仅当第 i 个片段的正文包含本题任一 `evidence_facts`。

| 指标 | 公式 | 解读 |
| --- | --- | --- |
| **Precision@k** | `Σrel_i / k` | top-k 中相关片段的占比。受"同事实重复块多"影响，天然偏低 |
| **Recall@k** | `Σrel_i / N_rel`，`N_rel` = 全语料相关块数 | 严格 IR 口径。年报中同一事实常以正文+多张表+附注重复，`N_rel` 可达几十，故该值天然低，**只适合横向比较策略** |
| **Hit Rate@k** | `1` if `Σrel_i > 0` else `0`（再按题平均） | "至少找到一个相关片段"的比率，最贴近可用性 |
| **MRR** | `1 / rank_first_rel`（无相关片段记 0） | 第一个相关片段的名次倒数，度量"多快找到" |
| **NDCG@k** | `DCG@k / IDCG@k`，`DCG = Σ rel_i / log2(i+1)` | 二值增益的排序质量 |
| **事实覆盖@k** | `\|{f ∈ evidence_facts : f ∈ ∪top-k 文本}\| / \|evidence_facts\|` | **信息召回率**，业务口径："本题要点被检索到几成" |
| **Answer Accuracy** | `\|{f ∈ key_facts : f ∈ answer}\| / \|key_facts\|` | 答案对关键事实的**逐字**覆盖率 |
| **Faithfulness** (RAGAS) | 答案中的每个陈述是否可由 contexts 推出 | 度量**幻觉**，见 `docs/07` |
| **Answer Relevancy** (RAGAS) | 由答案反向生成的多个问题与原问题的平均相似度 | 度量答案**是否答到点上** |

**为何同时给 Recall@k 和 事实覆盖@k**：前者是标准 IR 口径便于横向比较，
后者才是业务关心的"该找的信息找到了没有"。两者都给，避免"用宽松口径凑指标"。

## 三、使用方法

### 3.1 从零跑通

```bash
cd 工单7
python scan_local_models.py                                        # ① 模型扫描 → docs/01
python scripts/setup_project.py                                    # ② 解压 + 语料规范化 + 自检
python build_index.py --rebuild --fallback-only --no-ocr --no-embed --skip-orgchart  # ③ 解析分块(~5min)
python build_index.py --no-ocr --skip-orgchart                     # ④ 向量化 + 建索引(~3min)
python scripts/validate_ground_truth.py                            # ⑤ 金标准闸门（必跑）
python run_rag_questions.py --strategy hybrid                      # ⑥ 10题留痕 → docs/04
python run_rag_questions.py --strategy vector
python run_rag_questions.py --strategy fulltext
python evaluate_rag07.py                                           # ⑦ 指标汇总 → docs/05
python evaluate_ragas.py --strategy hybrid                         # ⑧ RAGAS → docs/07
```

### 3.3 复现但不想重跑解析

`build_index.py` 默认**复用 `data/chunks/chunks.json`**（只有加 `--rebuild` 才重新解析）。
调提示词/检索参数后重跑评估，无需再花 5 分钟解析：

```bash
python run_rag_questions.py --strategy hybrid     # 直接复用已有索引
```

RAGAS 同理支持 `--reuse-answers`（复用 `data/eval/ragas_answers.json`，只重跑评判）。

### 3.4 增量扩展

| 想加什么 | 怎么做 |
| --- | --- |
| 加测试题 | 往 `data/test_questions.json` 加 `{id, question}`，往 `data/eval/ground_truth.json` 加同 id 的金标（**必须先跑 `validate_ground_truth.py`**） |
| 换嵌入模型 | `python build_index.py --embedding-model bge-m3-ft-v1`（各模型独立 collection，互不覆盖） |
| 换 Reranker / 精排算法 | `evaluate_retrieval.py --reranker-model bge-reranker-base --rerank-algorithm tfidf` |
| 只跑某几题 | `python run_rag_questions.py --ids 3,6,10` |
| 调融合权重 | 改 `src/config.py` 的 `VECTOR_WEIGHT` / `FULLTEXT_WEIGHT`，或用 `strategies.with_overrides(..., vector_weight=..., fulltext_weight=...)` |
| 换语料 | 把新 PDF 放进 `data/corpus/pdf/`，同步 `config.SOURCE_PDFS`（自动 glob）、`DOC_ALIASES`、`COMPANY_BY_SOURCE`，再 `build_index.py --rebuild --fallback-only` |

### 3.5 两个已知的运维约束（实测）

1. **Qdrant local 模式单进程占用**：嵌入式存储同一目录只能被一个进程打开。
   并发跑多个评估脚本会互斥——**串行执行**，或把 `QDRANT_MODE` 切 `server`。
2. **进程退出时的 Qdrant 析构告警**：日志末尾可能出现
   `Exception ignored in: <function QdrantClient.__del__> … ImportError: sys.meta_path is None`。
   这是解释器关闭阶段的**无害告警**，退出码为 0、数据已落盘，可忽略。
