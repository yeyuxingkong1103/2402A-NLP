# 设计文档 —— 基于 RAG 的角色扮演系统

## 1. 技术架构

分层架构，核心思想：**所有外部服务通过抽象接口接入，MVP 用轻量本地实现，生产可无缝切换**。

```
┌──────────────────────────────────────────────────────────┐
│  接入层  FastAPI (main.py + api/*)                        │
│    /health  /chat  /chat/stream  /knowledge/*  /role/*    │
├──────────────────────────────────────────────────────────┤
│  编排层  core/pipeline.py（检索→重排→提示词→LLM→后处理）     │
├───────────────┬──────────────────┬───────────────────────┤
│ 在线链路       │ 离线链路          │ 存储                  │
│ retrieve/     │ document/        │ store/                │
│  hybrid_retriever│ parser/chunker │  milvus_store（向量）  │
│  reranker     │ cleaner          │  sql_store（关系）      │
│ embedding     │                  │  memory（短期记忆）     │
│ llm           │                  │                       │
│ prompt/       │                  │                       │
│ postprocess   │                  │                       │
├───────────────┴──────────────────┴───────────────────────┤
│  外部依赖（可配置切换）                                     │
│  LLM/Embedding: Ollama ←→ OpenAI 兼容 API                 │
│  向量库: Milvus Lite ←→ Milvus 服务器                      │
│  关系库: SQLite ←→ MySQL                                  │
│  短期记忆: 内存 ←→ Redis                                   │
└──────────────────────────────────────────────────────────┘
```

## 2. 功能设计（模块职责）

### 2.1 接入层

| 模块 | 路径 | 职责 |
|---|---|---|
| main | `app/main.py` | FastAPI 实例、lifespan 组装 pipeline、挂路由与静态页、`/` 内容协商 |
| api.chat | `app/api/chat.py` | `/chat`、`/chat/stream`；把内部异常翻译成 404/502/503 与 SSE `error` 事件 |
| api.health | `app/api/health.py` | `/health`：五组件分档状态 + 降级原因 |
| api.knowledge | `app/api/knowledge.py` | 上传入库、文档列表 |
| api.role | `app/api/role.py` | 角色查询与创建 |
| schemas | `app/schemas/__init__.py` | 请求/响应模型；`role_id` 白名单正则 |
| static | `app/static/index.html` | 单文件前端（无框架无构建），消费 SSE 流 |

> 接入层只做「校验 → 调 pipeline → 翻译错误码」，不放业务逻辑，这样脚本（`scripts/*.py`）
> 可以绕过 HTTP 直接复用 `core/`。

## 3. 数据设计

### 3.1 Milvus collection（role_knowledge）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | VARCHAR(64) 主键 | 自生成 UUID |
| role_id | VARCHAR(64) | 角色隔离召回 |
| text | VARCHAR(65535) | 原文 chunk |
| vector | FLOAT_VECTOR(1024) | BGE-m3 稠密向量，IP 度量（已归一化=余弦） |
| title | VARCHAR(512) | 文档标题 |
| source | VARCHAR(512) | 文档来源（路径/upload://） |
| chunk_index | INT64 | chunk 序号 |
| summary | VARCHAR(2048) | 摘要（LLM 生成，`SUMMARY_ENABLED` / `ingest --summary` 开启） |
| created_at / updated_at | INT64 | 时间戳 |

### 3.2 关系库（SQLite/MySQL，SQLAlchemy）

- **users**：id、username、created_at
- **roles**：id(role_id)、name、avatar、description、system_prompt、is_active、created_at、updated_at
- **documents**：id、role_id、source、title、chunk_count、created_at

> ⚠️ **`documents` 是一张登记表，不是正文库**：它只说明"某角色下有过 source 这么一份
> 文档、当时切了多少块"，供 `/knowledge/list` 展示。检索真正用的正文在 Milvus。
> 因此同一份文档重灌必须**两边一起处理**（先删向量 + 再删登记），只清一边就会出现
> "列表里显示已入库、检索却全空"或"列表里两条一模一样的记录"。
> 换 MySQL 时也**必须把 documents 表一起搬过去**（见 `scripts/migrate_sqlite_to_mysql.py`），
> 否则新库里列表是空的、向量却还在，看起来像数据丢了。

### 3.3 短期记忆

- 内存实现：`dict[session_id -> deque(maxlen=max_turns*2)]`，一条一问一答。
- Redis 实现：`List`（RPUSH + LTRIM + EXPIRE 24h），key = `memory:{session_id}`。

## 4. RAG 主链路时序

```
Client      pipeline        retriever        milvus        bm25        llm          memory
  │ POST /chat │                │               │            │           │             │
  │──────────>│ retrieve(q,role)│               │            │           │             │
  │           │───────────────>│ embed_query(q) │            │           │             │
  │           │                │ search(role,qv)│            │           │             │
  │           │                │────────────────────────────>│           │             │
  │           │                │ bm25.search(q) │            │           │             │
  │           │                │───────────────>│            │           │             │
  │           │<── RRF 融合结果 ──│               │            │           │             │
  │           │ rerank(chunks) │               │            │           │             │
  │           │ get_history(session) ──────────────────────────────────>│             │
  │           │ build_messages(persona,chunks,history,q)   │            │           │
  │           │─────────────────────────────────────────────────────────>│ chat()      │
  │           │<──────────────────────────────────────────────────────────│             │
  │           │ postprocess(answer) ──────────────────────────┐          │             │
  │           │ memory.add(user+assistant) ───────────────────┴──────────>│             │
  │<──────────│ {answer, sources}        │               │            │           │             │
```

## 5. 关键设计决策

1. **混合检索的 BM25 放 Python 侧**：MVP 用 `rank_bm25 + jieba` 对角色内 chunk 建索引，避免依赖
   Milvus 版本对稀疏向量/BM25 function 的支持差异；接口保持一致，生产可迁入 Milvus 稀疏向量。
2. **向量归一化 + IP 度量**：embedding 统一 L2 归一化，Milvus 用 IP（内积）等价余弦相似度，配合阈值过滤低分。
3. **RRF 融合**：对稠密/BM25 两路召回按排名融合，天然吸收不同量纲分数，无需调参。
4. **dummy 模式**：`LLM_PROVIDER/EMBED_PROVIDER=dummy` 走确定性离线实现，用于单元测试与无 Ollama 环境的冒烟联调。
5. **可替换抽象**：LLM/Embedding/Reranker/Memory/向量库/关系库均为接口，切换仅改 `.env`。
6. **OCR 惰性加载**：RapidOCR 模型随包打包、首次调用才初始化（约 0.6s），普通文档零开销；`OCR_ENABLED=false` 时完全退回旧行为。
7. **Query 改写/扩写**：用 LLM 把问题扩成多个检索查询、多查询各自召回后 RRF 融合；关闭时就是单查询，退化为原路径。默认关（每次多一次 LLM 往返）。
8. **数据增强与去重**：入库侧按 `source` + chunk 内容哈希去重、过滤过短 chunk，可选 LLM 摘要；`rrf_fusion` 天然支持 N 路召回，扩展数据源（Neo4J/Mongo/ClickHouse）只需新增 route。
9. **三环境**：`APP_ENV=dev/test/prod` 加载 `.env.{env}` 覆盖 `.env`，同一份代码跑开发（本地 Ollama）、测试（全离线 dummy）、生产（服务化组件）。
10. **同会话串行化**：前端只在单个标签页内禁并发，多标签页/脚本随时能同时打同一个
    `session_id`，两个请求交错写记忆会把历史配错对（出现 `[user QA][user QB, assistant AB, assistant AA]`）。
    故 `pipeline` 按「会话+角色」加锁，锁只覆盖「读历史 → 生成 → 写历史」，检索不进锁。
11. **精排池宽是精排输入的上界**：开精排时先按 `RERANK_POOL` 宽召回再截断。
    开了 Query 改写后上游会把多条 query 的召回去重合并，条数可达池宽的数倍，
    而 CrossEncoder 是逐对推理——80 对意味着十几秒到 60s 超时，超时即整体降级回
    score_fusion，精排等于白开。故融合分数排好序后先截断到 `RERANK_POOL`。
12. **空答案必须显式报错**：模型一个字都没答（推理吃光预算被截断、上游返回空 `choices`）
    时抛 `EmptyAnswerError`，由接口层转成 502 / SSE `error` 事件。绝不静默返回空串——
    那会让 `/chat` 返回 200、前端渲染空白，而且空答案还会被写进短期记忆污染下一轮。
13. **降级必须留痕**：BGE 重排不可用、Redis 降级为进程内内存、精排只回了部分分数……
    这些情况下链路都保证可用（可用性优先），但**一律打日志并在 `/health` 的 `details` 里报出原因**。
    历史教训是"静默降级"：调用方与前端拿到的仍是"已精排"的分数，却没有任何痕迹。
