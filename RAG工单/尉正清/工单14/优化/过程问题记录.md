# 工单14 过程问题记录

记录实施过程中踩到的坑。每条都写了**现象 → 真因 → 怎么绕过去**，避免下次重踩。
按主题分组，不按时间顺序。

---

## 一、环境与部署

### 1. 附件源码和镜像不是同一个版本，不能直接挂进容器

**现象**：把附件 `ragflow-main` 里改好的 `rag/llm/chat_model.py` 直接 bind mount
进容器，容器起不来：

```
ImportError: cannot import name 'thread_pool_exec' from 'common.misc_utils'
```

**真因**：附件源码比镜像 `infiniflow/ragflow:v0.23.1` 里的代码**新**，
镜像里的 `common/misc_utils.py` 没有 `thread_pool_exec` 这个符号。

**处置**：不要改附件源码、也不要挂附件源码。正确做法是
`docker cp <容器>:/ragflow/rag/llm/chat_model.py` 把**镜像自带的那份**导出来，
在它上面改，再把改好的文件挂回去。见 `研发/patches/rag/llm/chat_model.py`。

### 2. `.env` 里的 `MINIO_PORT` 是无效的

**现象**：`.env` 写 `MINIO_PORT=9010`，但宿主 9010 没在监听，一度以为存储挂了。

**真因**：`service_conf.yaml.template` 里端口是**写死**的：

```yaml
minio:
  host: '${MINIO_HOST:-minio}:9000'
```

`MINIO_PORT` 只用于 compose 的端口映射，不参与 `service_conf` 生成。

**另外**：这份部署用的 MinIO 其实是宿主上 Milvus 自带的那个（监听 127.0.0.1:9000），
RAGFlow 靠 Docker Desktop 的 `host.docker.internal` 代理到宿主的 localhost。
`.env` 里面的 9010/9011 是误导。

### 3. 容器重建后登录 token 失效，且 token 位置很反直觉

**现象**：`/v1/user/*`、`/v1/llm/*` 一律 401，但用 SDK API Key 访问
`/api/v1/datasets` 是好的。

**真因**（三个叠加）：

1. 这些接口只认**登录 token**，不认 API Key；
2. 登录 token 存在 Redis，容器一重启就没了；
3. **token 不在响应体里** —— 体里的 `access_token` 是登录**前**的旧值
   （`user_app.py:128` 先 `to_json()` 再 `get_uuid()`）；
   真正能用的是**响应头 `Authorization`**，值是一个 itsdangerous 签名串，
   必须**裸发**，加 `Bearer ` 前缀会被当成 API Key 去查表然后 401。

见 `测试/ragflow_client.py` 的 `login()` 和 `_h()`。

### 4. 服务重启后 `layout_recognize` 是错的

默认库里 `layout_recognize` 被设成了 `deepseek-flash` —— 那是**纯文本模型**，
当版面解析器毫无意义。已改回 `DeepDOC`。
（文档级 parser_config 一直是 `DeepDOC`，所以解析结果没受影响，属于潜伏配置错误。）

## 二、RAGFlow 接口的坑

### 5. `add_llm` 的字段名是 `api_base`，不是 `base_url`

**现象**：注册模型报 `ValueError('url cannot be None')`。

**真因**：`api/apps/llm_app.py:206` 读的是 `req.get("api_base", "")`。
传 `base_url` 会被静默忽略，落到空串，然后下游 `OpenAI(api_key, base_url="")` 报错。

### 6. 用 SDK 更新助手时**必须带 `dataset_ids`**，否则知识库被解绑

**现象**：第 5 轮突然 0/6，答非所问、且是凭空猜的。

**排查**：日志里 system prompt 长这样 —— `{knowledge}` **原样没被替换**；
查库发现 `dialog.kb_ids` 变成了 `[]`；代码走的是 `async_chat_solo`
（"没有知识库"的分支），它把原始 system 直接发给模型。

**真因**：`PUT /api/v1/chats/{id}` 不带 `dataset_ids` 时会把 `kb_ids` 清空
（`api/apps/sdk/chat.py:169-170`）。

### 7. 助手的 `rerank_id` 校验用的是**不带 @工厂**的全名

**现象**：`rerank_model bge-reranker-v2-m3___OpenAI-API@OpenAI-API-Compatible doesn't exist`

**真因**：校验是
`TenantLLMService.query(llm_name=req["rerank_id"], model_type="rerank")`
（`api/apps/sdk/chat.py:84`），拿的是 `tenant_llm.llm_name` 的原始值，
要写 `bge-reranker-v2-m3___OpenAI-API`，**不带 `@工厂` 后缀**。

### 8. 更新知识库 `parser_config` 时多带字段会导致**整条更新被拒**

**现象**：调 `PUT /datasets/{id}` 改解析配置，返回
`Extra inputs are not permitted: parser_config.image_context_size`，
并且 `chunk_token_num` 也没改成功。

**真因**：接口 schema 不认 `image_context_size` / `table_context_size`，
**整条请求被拒**，不是只忽略这两个字段。要只发 schema 认的字段。

### 9. 解析配置没变时，RAGFlow 会跳过重解析

**现象**：改了图纸描述提示词，重新触发解析，进度条一闪而过，chunk 还是旧的。

**真因**：`rag/svr/task_service.py:467-511` 有 digest 去重 ——
`from_page` 和 `parser_config` 的 digest 都命中就**直接复用旧 chunk、不入队**。

**处置**：先 `DELETE /api/v1/datasets/{ds}/documents/{doc}/chunks` 删掉已入库
chunk，再触发解析（`测试/reparse.py --force`）。

## 三、模型相关的坑

### 10. `deepseek-flash` 是推理模型，思维链会吃光 `max_tokens`

详见 `测试报告.md` 第 1 轮。另外：关闭它要用
`extra_body={"reasoning_effort": "none"}`，且**必须在
`_construct_completion_args` 这一层注入** —— 因为流式路径
`async_chat_streamly` 不会把调用方的 `kwargs` 透传下去，只在 `async_chat`
里改的话，网页端（走流式）不生效。

### 11. `deepseek-flash` 支持图片输入，但 RAGFlow 里没有对应的视觉类

**现象**：图纸描述那条路径整条被静默跳过，解析日志里连
`Visual model detected` 都没有。

**真因**（两层）：

1. `tenant_llm` 里 `deepseek-flash` 只注册成 `chat`，没有 `image2text`；
2. `rag/llm/cv_model.py` 里**没有 DeepSeek 这个视觉类**，
   `CvModel["DeepSeek"]` 直接 KeyError。

**处置**：借 `OpenAI-API-Compatible` 工厂（对应现成的 `OpenAI_APICV`）
再注册一遍成 `image2text`，再把租户默认 `img2txt_id` 指过去。
`deepseek-flash` 的 `/models` 返回 `input_modalities: ["text","image"]`，
API 兼容 OpenAI 的 `image_url` 格式，所以这条路走得通。

### 12. RAGFlow 自带的图纸描述提示词会**主动删掉**图上最要紧的信息

原提示词明写：

> Do NOT interpret intent, behavior, workflows, gameplay rules, **or processes**.
> Do NOT describe the figure as a chart, diagram, **process**, phase, **or sequence**

工业专利附图里「谁在左、谁在右、箭头朝哪边」恰恰就是顺序信息。
已定制该提示词强制要求描述空间次序与气流穿过顺序，见
`研发/patches/rag/prompts/vision_llm_figure_describe_prompt.md`。

### 13. 长上下文里，写在末尾的指令会被淹没

**现象**：第 5 题的作答约定写在 system prompt 末尾，模型 5 次全不执行。

**原因**：RAGFlow 拼出来的 system prompt 里知识库占一大段，规则在最末尾。

**处置**：同一段规则**在知识库前后各写一遍**，5 次全对。
这是长上下文指令跟随的常见问题，和模型能力无关。

## 四、硬件与性能

### 14. 重排必须放 GPU，否则响应时间直接崩

RAGFlow 一次检索会送 **66 条候选**（`rag/nlp/search.py:388` 的 `RERANK_LIMIT`）
给重排模型打分。实测 `bge-reranker-v2-m3`：

| 位置 | 66 条耗时 |
|---|---|
| 8 核 CPU | **80 s** |
| GPU(fp16, batch=16) | **1.0 s** |

批大小对 CPU 几乎没用（bs=1 38.5s、bs=8 48.6s、bs=32 57.3s）。

### 15. 两个模型都塞 GPU 会偶发卡死

**现象**：某一题响应 73s，其余题 ~2s。日志显示 70 秒全花在重排那一步。

**真因**：6GB 的笔记本 3060，bge-m3 + 重排都在 GPU 上，占用 5908/6144 MB，
**只剩 236MB**，显存一紧张就卡。

**处置**：嵌入挪到 CPU（单条查询 0.25s，可接受），重排独占 GPU。
占用降到 1276MB，重排稳定 1.0s。

### 16. GPU 上还有一个不相关的进程在占显存

`nvidia-smi` 显示 QQ.exe 也占着显存。排查显存问题时要把这类无关进程算进去。

## 五、其它

### 17. `GET /api/v1/datasets/{id}` 在这版上是 405

要取知识库详情得用列表接口带参数：`GET /api/v1/datasets?id=<id>`。

### 18. 数据集里 `chunk_count` 与实际 chunk 数对不上

界面/接口报的 `chunk_count`（曾显示 36、54）是**累计计数**，
而 ES 里实际只有 18 条。判断「解析产物到底有多少」要以
`GET /datasets/{ds}/documents/{doc}/chunks` 或直接查 ES 为准。
