# 功能需求说明书

> 配套文档：《01-需求规格说明书》。本文档按模块列出功能点，编号规则为 `FR-模块-序号`。
> 优先级：**P0** 核心必需 ｜ **P1** 重要 ｜ **P2** 辅助。
> 所有接口统一响应体：`{"code": 200, "msg": "ok", "data": ...}`。

| 模块 | 功能点数 | 对应代码 |
|---|---|---|
| 1. 对话模块 | 8 | `app/api/chat.py`、`app/core/rag_service.py` |
| 2. 角色模块 | 4 | `app/api/role.py`、`app/core/role_service.py` |
| 3. 会话模块 | 5 | `app/api/role.py`、`app/core/session_service.py` |
| 4. 用户模块 | 3 | `app/api/system.py` |
| 5. 知识入库 | 6 | `app/api/knowledge.py`、`app/core/ingest_service.py`、`app/core/pdf_service.py`、`app/core/mineru_service.py`、`app/core/ocr_service.py`、`app/core/table_service.py` |
| 6. 知识更新 | 3 | `app/api/knowledge.py`、`app/core/update_service.py` |
| 7. 系统模块 | 4 | `app/api/system.py`、`app/main.py` |

## 1. 对话模块

| 编号 | 功能名称 | 描述 | 输入 | 处理 | 输出 | 优先级 |
|---|---|---|---|---|---|---|
| FR-CHAT-01 | 角色扮演问答（非流式） | 执行完整 RAG 链路并一次性返回完整回答，接口 `POST /api/chat/ask` | `question`（必填非空）、`role_key`（必填）、`user_id`（默认 1）、`session_id`（可选） | 角色装载 → 会话装载/新建 → 双层记忆召回 → 追问改写 → 混合检索 → 重排 → 提示词组装 → 大模型生成 → 追加免责声明 → 记忆与消息落库 → 角色热度 +1 | `answer`、`session_id`、`role`、`search_query`、`sources[]`（含 `text`/`title`/`source`/`doc_type`/`score`）；异常：400 问题为空或角色不存在/停用，403 会话不属于当前用户，500 内部错误 | P0 |
| FR-CHAT-02 | 流式问答（SSE） | 以 Server-Sent Events 逐段推送回答，接口 `POST /api/chat/stream` | 同 FR-CHAT-01 | 检索完成后先推送 `meta`，再逐段推送大模型正文 `delta`；免责声明若未包含在正文中则补发一段 `delta`；最后落库并推送 `done` | `data:` 行序列：`{"type":"meta",session_id,role,search_query,sources}` → `{"type":"delta",content}` × N → `{"type":"done",session_id}`，异常时为 `{"type":"error",message}`；响应头含 `text/event-stream`、`no-cache`、`X-Accel-Buffering: no` | P0 |
| FR-CHAT-03 | 会话自动创建与延续 | 不传 `session_id` 时自动新建会话并返回；传入时延续该会话 | `session_id`（可选） | `get_or_create`：未传则新建 UUID 会话；传入且存在则校验归属后复用；传入但不存在则以该 ID 新建 | 生效的 `session_id` | P0 |
| FR-CHAT-04 | 追问改写（指代消解） | 多轮对话中把含指代或省略的追问改写为可独立检索的完整问题 | 当前问题 + 最近 6 行短期记忆 | 仅当存在历史时触发；调用大模型（temperature=0.1，max_tokens=1024）改写，失败时回退使用原问题 | `search_query`（随响应返回，便于排查检索偏差）；示例：「那要是逃逸了呢？」→「酒驾撞人后逃逸的，要判多久？」 | P1 |
| FR-CHAT-05 | 混合检索与重排序 | 从角色知识库中召回与问题最相关的资料 | `search_query`、`role_key` | BGE-M3 一次前向产出稠密向量与稀疏权重；Milvus 按 `role_id` 过滤，两路各召回 20 条（`RETRIEVE_LIMIT`），RRF（k=60）融合；BGE-reranker-v2-m3 逐对打分取 top-5（`RERANK_TOP_K`）。降级：混合检索失败转纯向量检索；重排失败取粗排前 5；全部失败返回空资料 | `sources[]`，每项含 `title`、`source`、`doc_type`、`score` | P0 |
| FR-CHAT-06 | 免责声明自动追加 | 回答末尾强制追加角色对应的免责声明 | 大模型原始正文、`roles.disclaimer` | 去首尾空白后比对，若声明尚未出现在正文中则以两个换行分隔追加，已存在则不重复追加。写入记忆用**不含**声明的正文，写入 `messages` 表的是**含**声明的完整回答 | 最终 `answer` | P0 |
| FR-CHAT-07 | 对话记忆写入 | 每轮问答结束后更新短期记忆并按需归档长期记忆 | `user_id`、`role_key`、`session_id`、问题、回答正文 | 追加到 Redis List 并裁剪至最近 10 轮（`SHORT_TERM_TURNS`）；被裁出的旧记录进入待归档缓冲区，累计 ≥ 6 行（`MEMORY_SUMMARY_TRIGGER`）时取出压缩为不超过 300 字的摘要写入 Milvus | 无（失败仅记录告警，不阻断问答） | P0 |
| FR-CHAT-08 | 角色热度累加 | 每次问答成功后为该角色热度 +1 | `role_key` | Redis zSet `role:hot` 执行 `ZINCRBY`，失败静默降级 | 供 FR-ROLE-03 排行使用 | P2 |

|---|---|---|---|---|---|---|
| FR-ROLE-01 | 角色列表 | 返回全部启用角色，接口 `GET /api/roles` | 无 | 按 `sort_order`、`id` 升序查询 `roles` 表 | 角色数组，每项含 `role_key`、`name`、`category`、`description`、`greeting`、`avatar`、`sort_order`、`status` | P0 |
| FR-ROLE-02 | 角色详情 | 返回角色完整信息，含人设提示词等调试字段，接口 `GET /api/roles/{role_key}` | `role_key`（路径参数） | 先查进程内缓存，未命中则查库并回填 | 在列表字段基础上追加 `persona`、`rules`、`fallback`、`disclaimer`、`collection`；角色不存在返回 404 | P1 |
| FR-ROLE-03 | 角色热度排行 | 返回被提问次数最多的前 k 个角色，接口 `GET /api/roles/hot?k=10` | `k`（默认 10） | 读取 Redis zSet `role:hot` 倒序取前 k | `[{"role_key": "...", "score": 12.0}]`；Redis 不可用时返回空数组 | P2 |

## 3. 会话模块

| 编号 | 功能名称 | 描述 | 输入 | 处理 | 输出 | 优先级 |
|---|---|---|---|---|---|---|
| FR-SESS-01 | 会话列表 | 查询某用户的会话，接口 `GET /api/sessions` | `user_id`（默认 1）、`role_key`（可选过滤）、`limit`（默认 50，上限 200） | 按 `updated_at` 倒序查询 `sessions` 表 | 会话数组，含 `session_id`、`role_key`、`title`、`turn_count`、`created_at`、`updated_at` | P1 |
| FR-SESS-02 | 会话历史消息 | 返回会话基本信息与全部消息，接口 `GET /api/sessions/{session_id}/messages` | `session_id`（路径）、`limit`（默认 100，上限 500） | 按消息自增 ID 升序读取 `messages` 表 | `{"session": {...}, "messages": [{"role","content","sources","created_at"}]}`，`sources` 为 JSON 字符串；会话不存在返回 404 | P1 |
| FR-SESS-03 | 记忆查看 | 调试接口，直观展示双层记忆内容，接口 `GET /api/sessions/{session_id}/memory` | `session_id`（路径）、`user_id`（默认 1）、`role_key`（必填） | 读取 Redis 最近 10 轮原文，并统计 Milvus 中长期记忆条数 | `{"short_term": ["用户：...", "助手：...", ...], "long_term": {"long_term_count": n}}` | P2 |
| FR-SESS-04 | 删除会话 | 删除会话及其全部消息，接口 `DELETE /api/sessions/{session_id}` | `session_id` | 先删除该会话下所有 `messages`，再删除 `sessions` 记录；不清理 Redis 短期记忆与 Milvus 长期记忆（记忆按 `user_id + role_key` 维度沉淀、跨会话复用） | `msg = "已删除"`；会话不存在返回 404 | P1 |
| FR-SESS-05 | 会话归属校验 | 防止用户通过猜测 `session_id` 读取或污染他人会话 | 请求 `user_id`、`session_id` | 问答链路复用已有会话时比较 `sessions.user_id` 与请求 `user_id`，不一致则抛出 `PermissionError` | HTTP **403**，`detail = "会话不属于当前用户"`；适用于 `/api/chat/ask` 与 `/api/chat/stream` | P0 |

## 4. 用户模块

| 编号 | 功能名称 | 描述 | 输入 | 处理 | 输出 | 优先级 |
|---|---|---|---|---|---|---|
| FR-USER-01 | 注册 | 接口 `POST /api/users/register` | `username`（2–64 字符）、`password`（6–64 字符）、`nickname`（可选，缺省取用户名） | 校验用户名唯一；密码用 PBKDF2-HMAC-SHA256（20 万次迭代、16 字节随机盐）哈希后存储 | 用户信息 `{id, username, nickname, status}`；用户名已存在返回 400 | P1 |
| FR-USER-02 | 登录 | 接口 `POST /api/users/login` | `username`、`password` | 按用户名查询，使用 `hmac.compare_digest` 恒时比对密码哈希，再校验账号状态 | 用户信息（本期不签发 Token）；用户名或密码错误返回 401，账号停用返回 403 | P1 |
| FR-USER-03 | 查询用户 | 接口 `GET /api/users/{user_id}` | `user_id` | 按主键查询 `users` 表 | 用户信息；不存在返回 404 | P2 |

## 5. 知识入库

| 编号 | 功能名称 | 描述 | 输入 | 处理 | 输出 | 优先级 |
|---|---|---|---|---|---|---|
| FR-ING-01 | 数据集批量入库 | 接口 `POST /api/ingest/dataset`，把角色目录下的 JSONL 灌入 Milvus | `role_key`（必填，须为已存在角色）、`force`（默认 false） | 定位 `data/{role_key}/`，按文件名排序逐份读取 `.jsonl` 并逐行解析（跳过空行与解析失败行），切块、向量化后批量写入 `rag_knowledge` | `{role_id, files, records, chunks, details[{source, records, chunks}]}`；400 角色不存在/目录不存在/无 jsonl 文件，500 入库失败 | P0 |
| FR-ING-02 | 强制重建 | `force=true` 时先删除该角色已有全部知识再导入，用于修正脏数据 | `force` | 按表达式 `role_id == "{role_key}"` 删除 Milvus 中该角色的切片后执行入库 | 同 FR-ING-01；日志额外记录「已清空角色 [x] 的旧知识」 | P1 |
| FR-ING-03 | 上传文档入库 | 接口 `POST /api/ingest/upload`（multipart/form-data） | `file`（扩展名限 `.pdf`/`.txt`/`.md`）、`role_key`、`remove_watermark`（默认 true）、`use_ocr` / `use_tables`（默认 true，**只作用于兜底路径**；走 MinerU 时被忽略并记一条 note） | 校验角色与扩展名 → 以 UUID 命名落盘 `uploads/` → 按类型分派：PDF 走解析与去水印，TXT/MD 直接读取 → 切块向量化写入 Milvus | PDF：`{pages, chunks, watermark{text_removed, image_removed, text_samples, path, mineru{tier, raw_chars, text_chars, images_dropped}, ocr_scanned, ocr_pages, ocr_lines, table_pages, table_count, notes}, filename}`；文本：`{chunks, filename}`；400 格式不支持/内容为空/角色不存在 | P1 |
| FR-ING-04 | PDF 去水印 | 解析 PDF 前识别并擦除水印，避免水印文本污染检索结果 | PDF 文件、`remove_watermark` | 识别对象：① 多页相近位置重复出现的短文本（含斜向旋转）；② 重复铺版的图片对象或大面积透明图层；③ 文档元数据与注释。判定：出现页数 ≥ max(3, 页数×50%)，文本长度 2–60 字，形态特征满足其一（≤12 字、旋转、字号 ≥20、浅灰低对比）。处理：PyMuPDF redaction 精确擦除命中区域而非丢弃整页，并清空文档元数据，随后另存一份干净 PDF 交给 MinerU（**MinerU 不做水印擦除**，故这一步必须前置） | 去水印报告：文字水印处数、图片水印处数、文本样本、备注；页数 <3 时跳过统计，正文页眉因不满足形态特征不会被误删 | P1 |
| FR-ING-05 | 切块与向量化策略 | 决定一条记录切成几个切片、用什么文本做检索目标 | 清洗后的 JSONL 记录 | `display_text` ≤1500 字：整条作为一个切片，以 `embed_text`（问题/标题）作向量目标、`display_text` 原样存库；>1500 字：走**语义分块**（`chunk_service.semantic_split`，按相邻句向量相似度低谷切分，单块上限 900 字，失败退化为按长度合并）并丢弃 <20 字碎块，每块以自身文本作向量目标。BGE-M3 批量编码（批大小 200）同时产出稠密与稀疏向量，按 500 条一批写入 Milvus，写后 flush 并 load | 切片数统计 | P0 |
| FR-ING-06 | PDF 解析（MinerU 主路径 + 三件套兜底） | 把 PDF 解析为可入库文本 | PDF 文件 | 主路径：调用独立 venv 中的 MinerU（`mineru/.venv/bin/mineru-kit`，`MINERU_TIER=basic`）解析为整篇 Markdown → 剥掉 base64 内嵌图（否则单份文档会带进数 MB 垃圾）→ 返回单元素列表 `[{page: 1, text: Markdown}]`，由语义分块切块；Markdown **不做** `_normalize()`（硬换行合并会毁掉标题与表格结构）。兜底路径：MinerU 未安装、超时或报错时，退回**自研三件套**——PyMuPDF 逐页取文本层并做归一化（合并硬换行、压缩空白），按 `_needs_ocr()` 判断该页是否为扫描页或图表页（图片占页面 15%~95%）后由 PaddleOCR 补图表文字、去重后并入正文，再由 pdfplumber 提取表格还原为 Markdown 追加到正文，逐页返回 | 解析结果与 `watermark.path`（`mineru` / `pymupdf`）；MinerU 统计写入 `watermark.mineru`；兜底路径的 OCR / 表格计数写入 `watermark.ocr_scanned` / `ocr_pages` / `ocr_lines` / `table_pages` / `table_count`（走 MinerU 时这五项恒为 0，OCR 与表格由 MinerU 内部完成，这一层统计不到） | P0 |

## 6. 知识更新

| 编号 | 功能名称 | 描述 | 输入 | 处理 | 输出 | 优先级 |
|---|---|---|---|---|---|---|
| FR-UPD-01 | 单文档增量更新 | 接口 `POST /api/update/document`，按内容哈希判断是否需要重建 | `file_path`（绝对路径）、`role_key`、`force`（默认 false） | 计算文件 SHA256 → 与库中同 `source + role_id` 的 `content_hash` 比对 → 一致则跳过；不一致或 `force=true` 时按表达式 `source == "x" and role_id == "y"` **先删旧切片**，再按扩展名（`.jsonl`/`.pdf`/`.txt`/`.md`）重新入库 | `{code, msg, source, changed, chunks}`；文件不存在或类型不支持返回 400 | P0 |
| FR-UPD-02 | 批量更新角色数据集 | 接口 `POST /api/update/dataset/{role_key}?force=false` | `role_key`（路径）、`force`（查询参数） | 遍历 `data/{role_key}/` 下全部 `.jsonl`/`.pdf`/`.txt`/`.md`，逐个执行 FR-UPD-01 | `{code, role_id, changed_files, total_files, details[]}` | P1 |
| FR-UPD-03 | 删除文档知识 | 接口 `DELETE /api/update/document` | `source`（文件名）、`role_key` | 按 `source + role_id` 表达式删除 Milvus 中该文档的全部切片（源文件保留在磁盘） | `{code, msg, source}` | P1 |

## 7. 系统模块

| 编号 | 功能名称 | 描述 | 输入 | 处理 | 输出 | 优先级 |
|---|---|---|---|---|---|---|
| FR-SYS-01 | 依赖健康检查 | 接口 `GET /api/health` | 无 | MySQL 执行 `SELECT 1`；Redis 执行 `PING`；Milvus 执行 `list_collections`；LLM 检查是否已配置 API Key | `{mysql, redis, milvus, llm, llm_model}`；布尔项全真时 `msg="ok"`，否则 `msg="存在不可用依赖"` | P0 |
| FR-SYS-02 | 业务统计 | 接口 `GET /api/stats` | 无 | 统计两个 Milvus 集合行数、分角色知识量，以及 users/roles/sessions/messages 四表计数；单项失败记 0 不影响其余字段 | `collections`、`knowledge_per_role`、`users`、`roles`、`sessions`、`messages` | P1 |
| FR-SYS-03 | 全局异常处理 | 捕获未处理异常，避免堆栈直接暴露 | 任意请求 | 记录「方法 + 路径 + 堆栈」，统一转换为 500 响应 | `{"code": 500, "msg": "服务内部错误: ..."}` | P1 |
| FR-SYS-04 | 服务概览 | 接口 `GET /` | 无 | 汇总系统元信息 | 系统名称、版本、当前大模型名、`/docs` 地址与主要接口清单 | P2 |
