# 工单17 过程问题记录

记录实施过程中踩到的坑。每条都写了**现象 → 真因 → 怎么绕过去**。
其它工单已记过的不重复（见工单14/15/16 的同类文档）。

## 一、压测本身

### 1. JMeter 的 `-l` 是**追加**写，同名文件跑两次会混在一起

**现象**：基线文件 `jmeter_a_baseline.jtl` 有 400 行，但只跑过两次 200 请求 ——
两次运行的数据叠在一个文件里，算出来的分位是错的。

**处置**：跑之前先 `rm -f` 结果文件；或者在 `jmeter_run.sh` 里带时间戳。
分析脚本里也加了 `split_runs()`，按时间断点自动拆开。

### 2. 后台跑的 JMeter 会**残留**，污染后续测量

**现象**：一次测量显示「20 并发纯检索要 4.82 秒」，和之前单发 1.5 秒差太多。
查进程发现上一个 `timeout 400 jmeter ...` 还在跑，在抢资源。

**处置**：每次测量前
`powershell -Command "Get-Process java -EA SilentlyContinue | Stop-Process -Force"`。
**这条很关键** —— 污染导致我一度以为检索接口很慢，方向跑偏。

### 3. JMeter 的 `ResponseAssertion` 位掩码和想的不一样

**现象**：断言「响应不应包含 NO_MATCH」，写成 `test_type=10` 却一直失败，
而且报错信息是 `text expected to contain /NO_MATCH/`（看着像断言写反了）。

**真因**：JMeter 5.x 里常量是 `MATCHES=1, CONTAINS=2, NOT=4, EQUALS=8, SUBSTRING=16`。
**`NOT` 是 4 不是 8**，所以「Not Contains」= 2+4 = **6**。
而且失败消息里**不会**拼 "not"，容易误判。

## 二、RAGFlow 代码

### 4. 镜像版和附件版的 `retrieval()` 一个 async 一个 sync

**现象**：按附件的写法在 `rag/nlp/search.py` 的 `retrieval()` 里加
`await asyncio.to_thread(...)`，容器起不来：

```
SyntaxError: 'await' outside async function
```

**真因**：**附件里 `retrieval()` 是 `async def`，镜像里是普通 `def`**。
两份代码版本不同，不能照抄。

**处置**：改在**调用方** `api/db/services/dialog_service.py` 里包 ——
那里的 `async_chat()` / `async_ask()` 确实是 async 的。
**这个教训通用：改 RAGFlow 前先 `docker cp` 出镜像那份确认真实签名。**

### 5. `asyncio.to_thread` 是**按位置**传参，容易踩错

**现象**：`rerank_by_model` 的签名是
`(rerank_mdl, sres, query, tkweight=0.3, vtweight=0.7, cfield="content_ltks", rank_feature=None)`，
把 `rank_feature` 当第 6 个位置参数传，会**静默传给 `cfield`**（字段名），不报错但行为不对。

**处置**：`rank_feature=rank_feature` 用关键字传。

### 6. nginx 里的 `localhost` 在本容器里解析成 IPv6

**现象**：压测中 71% 的请求返回 502，nginx 日志 `no live upstreams`。

**真因**：容器 `/etc/hosts` 里 `::1 localhost` 在前，
`getent hosts localhost` **只返回 `::1`**；而 RAGFlow 监听 `0.0.0.0`（纯 IPv4）。
nginx 配的 `proxy_pass http://localhost:9380` 就会打到死地址。
低负载时重试能兜住，高负载下整组被判死。

**处置**：改成 `proxy_pass http://127.0.0.1:9380`。

## 三、剖析工具

### 7. py-spy 报「找不到 Python 版本」其实是**采错进程了**

**现象**：`py-spy dump --pid 20` 报
`Failed to find python version from target process`，
但 `nm -D /usr/bin/python3.12 | grep Py_Version` 明明有符号。

**真因**：容器**重建过，PID 变了** —— 20 那会儿是 nginx，不是 API Server。
这个报错信息很有误导性，看着像 Python 构建的问题。

**处置**：每次采样前重新查 PID：
```bash
docker exec docker-ragflow-cpu-1 sh -c "ps -eo pid,args | grep api/ragflow_server | grep -v grep"
```
实测 PID 在 18~27 之间跳。

### 8. 容器默认没有 `SYS_PTRACE`，py-spy 进不去

**现象**：`Failed to copy Py_Version symbol: Permission denied`

**处置**：compose 的 `ragflow-cpu` 服务加 `cap_add: [SYS_PTRACE]`。

### 9. 容器重建后，装进去的剖析/监控包全没了

**现象**：装了 py-spy / objgraph / prometheus-client，`--force-recreate` 之后
再采就报 `not found`。

**真因**：它们在容器的**可写层**里，重建即丢。（镜像没动，这是有意的。）

**处置**：固化成 `部署/install_extras.sh`，**每次重建后跑一次**。
这是设计取舍，不是 bug。

### 10. 容器里**有 uv 没有 pip**

**现象**：`python -m pip install` 报 `No module named pip`

**真因**：RAGFlow 镜像的 venv 是 uv 建的，没装 pip。

**处置**：`uv pip install --python /ragflow/.venv/bin/python <包>`

### 11. 从 Git Bash 调 `docker exec 容器 /绝对路径` 会被改写

**现象**：`docker exec 容器 /ragflow/.venv/bin/python -c ...` 报
`stat C:/Program Files/Git/ragflow/.venv/bin/python: no such file or directory`

**真因**：Git Bash 的路径转换把容器内路径当成宿主路径改写了。

**处置**：包在 `sh -c` 里跑，或加 `MSYS_NO_PATHCONV=1`。

## 四、测量方法

### 12. 火焰图要看**叶子帧**，父帧是累计值

**现象**：`py-spy record` 出的火焰图，从 `<module>` 往下看每个函数都占 60%+，
看不出热点。

**真因**：火焰图的每一层都是**包含其子调用的累计样本数**，父帧天然接近 100%。

**处置**：用 `--format raw` 导出，按分号切分后统计**最后一个函数**（叶子），
才是真正的 self time。本工单就是这样发现 `_worker`（线程在等）占 12.7%。

### 13. 「延迟随并发线性增长 + CPU 空闲」是事件循环被阻塞的指纹

这条是本工单最有价值的方法论：

| 观察 | 说明什么 |
|---|---|
| 延迟随并发**线性**增长 | 串行排队，不是资源不够 |
| CPU 大量空闲 | **在等，不在算** |
| 容器内存/GPU 全程不动 | 不是内存/GPU 压力 |
| 单发很快、并发上不去 | 硬串行点 |

四条同时出现，基本可以断定是**同步阻塞调用卡住了异步事件循环**，
应当直接去 async 函数里找 `requests.get/post`、`time.sleep`、同步 DB 调用，
而不是去查模型加载、连接池这些方向。
