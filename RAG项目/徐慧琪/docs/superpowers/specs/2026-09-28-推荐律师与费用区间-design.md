## 一、范围

**做**：③b 的公众侧功能三块 —— **案由标签 → 推荐律师 → 费用区间**，以及它们到问答结果的接入。

**不做**（本设计不含）：

- **出站内容过滤器**（技术方案 9.6 第 2 条）—— ③b 的另一块，独立推进
- **多轮会话上下文**（Redis）、**HTTP 接口 / JWT / 限流 / 审计表 / 前端 / 部署** —— ④期
- **真实律师名录**接入 —— 技术方案 6.4 定稿为「随机生成（演示用）」，正式运营前替换（风险 11）

**前置依赖**：收费口径语料（律师服务收费管理办法 / 政府指导价文件 / 律所公示标准）由**用户提供**，放 `data/raw/`，走与民法典相同的解析入库链路。语料未到位期间，可完成除「检索接入 + 真跑」外的全部工作（见 §九）。

**语料落地补记（2026-09-29，用户已确认）**：语料最终由**爬取**取得（用户指示「爬取相关律师收费信息」），共 4 份政务公开件 —— 司发通〔2021〕87 号 + 三份北京律所公示标准，来源 URL 与取舍理由见 `data/raw/fee/_sources/README.md`，重建脚本 `tools/prepare_fee_corpus.py`。

其中**解析路径是本设计的例外，经用户 2026-09-29 裁决**：这 4 份都是电子件（两份 `.docx` 原生 XML、两份 PDF 有干净文本层），**直接提取，不走 MinerU + PaddleOCR-VL** —— 即技术方案 §3.2「不设『文本层直接抽取』旁路 —— 入口唯一」的例外。理由：①电子件的文本层是无损的，直取比 OCR 更保真；②本功能靠数字精确（费用回查逐字命中片段里的数字），而 OCR 对数字有误识风险，一旦识别错就会写进给用户的区间。该例外**仅限电子件**：扫描件仍必须走 MinerU + PaddleOCR-VL。

## 二、定稿口径（2026-09-28 确认）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 案由标签判定 | **纯规则映射**（内置关键词表）。与技术方案 6.4「内置映射表、纯规则、不用模型」同源 |
| 2 | 费用区间生成 | **模型生成 + 数值回查**：区间里每个数字必须能在命中片段里找到字面出处；查不到即降级为「暂无费用口径依据」 |
| 3 | 推荐律师 | **随机生成**（姓名 / 机构字表）+ 输出**显式标注「示例数据」**，代码留开关常量 |
| 4 | 模块归属 | **独立子包 `app/recommend/`** + 到 `Answerer` 的**接入钩子**（默认关闭）。③a 的既有代码几乎不动 |
| 5 | 语料来源 | 用户提供真实文件，走与民法典相同的切分 / 向量 / 检索链路 |

## 三、架构

新子包 `backend/app/recommend/`，五个模块 —— 每个都是「一个清晰职责 + 可独立测试」：

| 模块 | 职责 | 依赖 | 可否纯函数测试 |
|---|---|---|---|
| `cause.py` | 问句 → 案由标签；案由 → 专业领域 | 无 | 是 |
| `price_intent.py` | 问句 → 是否在问价（费用区块的第二路判据，见 §四） | 无 | 是 |
| `lawyers.py` | 按领域匹配生成示例律师卡片 | 无 | 是（注入随机源） |
| `fees.py` | fee_corpus 检索 → 模型生成区间 → **数值回查** → 指回片段 | 检索链路 + LLM（**均注入**） | 回查逻辑是纯函数 |
| `attach.py` | 把三块结果挂到问答结果上（接入钩子） | `cause` / `lawyers` / `fees` | 是（依赖注入） |

分层遵守 ③a 的铁律：`recommend/` **可以**导入 `retrieval/` 与 `db/`；`retrieval/` 与 `db/` 不得反向导入 `recommend/`。
`price_intent.py` 的消费方在 `generation/answer.py` 的接入判据里（不在 `attach` 内：要不要组装区块是编排层的判断，不是组装层的），
故这是一条 `generation/` → `recommend/` 的**单向**导入。它压得住这条方向：`price_intent.py` 是纯 regex、无任何 app 内外依赖，
**守则：它必须保持零依赖**（只 `import re`）—— 一旦它开始导入 `retrieval/`、`db/` 或任何模型，
「这条导入方向是安全的」这个论证就随代码漂移失效了，而失效那天没有任何红灯（终审复核点出）。
既不拖 LLM/连接，也不与 `recommend/` 的其余模块互引（③a 的调用方不传 `extras_fn` 时行为一字不变）。

## 四、数据流

```
用户问题 + ③a 的 QAResult
  │
  ├─ cause.tag(question) ─────────→ 案由（str | None）
  │  cause.field_of(案由) ────────→ 专业领域（str；案由认不出时返回常量 "通用"）
  │
  ├─ lawyers.recommend(领域) ─────→ [律师卡片]（1~3 张，标注示例数据）
  │
  ├─ fees.estimate(案由) ─────────→ fee_corpus 混合检索
  │                                   ├─ 命中 → 模型据片段产区间 → 数值回查
  │                                   │         ├─ 全数字有出处 → 采用 + 留痕
  │                                   │         └─ 有数字无出处 → 降级「暂无费用口径依据」+ 留痕
  │                                   └─ 未命中 → 「暂无费用口径依据」（设计行为，非降级）
  │
  └─ attach(...) ─────────────────→ QAResult（新增附加区块；律师侧恒为空）
```

**接入钩子**：`Answerer` 在**公众侧出口**调用一次 `attach`，由开关控制（默认关闭）→ ③a 既有测试与行为不受影响；律师侧永不经过这条路径。

> **接入口径（用户 2026-09-29 两次裁决：先解耦、再给问价开第二路）**：判据是
> 「**公众侧 +（回答状态 ≠ `out_of_scope` 或 问句命中问价意图）**」，
> 且收在 `Answerer._extras_for` 一处，**八条返回路径全部经过它**（侧别 / 状态 / 问价意图 /
> `extras_fn` 是否为 None / 异常吞掉都在那里判）。演进与理由（每次改动都留在此处，不覆盖历史）：
>
> 1. **只判 `status == "ok"`（初版）**：后果是用户直接问「律师费大概多少」时，法条本来就答不出
>    （→ `need_more_info` / `abstain`），费用区块**也不出现**，用户什么都没拿到 —— 而语料里
>    明明有收费口径。
> 2. **解耦为「状态 ≠ `out_of_scope`」**：追问 / 降级 / 故障恰恰是**用户问法条问不出、
>    但可能正在问价**的情形，理应照给；`out_of_scope` 则被当成「与法律无关」（拒答、以及
>    「今天天气怎么样」这类非法律提问，此时推律师与费用会被读成「系统在回应我这件事」）。
> 3. **再给问价开第二路（本版）**：第 2 步的前提被**真跑推翻** —— 模型把「律师费大概多少」
>    判成 `out_of_scope`（原话「这属于律师服务收费的**市场行情**问题，不是由上面这些法条来
>    规定的内容」），即这个状态在本链路上更像「**这些法条答不了**」，而用户问价时恰恰最容易
>    落进这一档（2/2 复现）。于是裁决举例的那条问句在判据 2 下**仍然什么都不给**。判决：
>    **问价的话不看状态，照给**。
>
> **为什么是词表而不是继续放宽状态**（本版要回答的那个「为什么」）：放宽状态只有两条路 ——
> ① 连模型自报的 `out_of_scope` 一起放行，则「今天天气怎么样」也会带出费用区块（用户明确
> 点名它**不该**出现，费用侧还会拿近零分命中白跑一次 DeepSeek）；② 只排除 `boundaries.is_refusal`
> 那条规则出口，则天气题**照样**带出区块（它是模型自报的，不是规则拒答），等于什么都没解决。
> 词表（`recommend/price_intent.py`，纯规则、与 `cause.py` 同风格）是唯一同时满足
> 「用户问价必给」与「天气题不给」两端的做法。它的代价是必须靠正反例穷举测试保住边界，
> 且只放行**问价**这一类，不回答「为什么问价问句能穿过 out_of_scope 的门」——
> 答案是：`out_of_scope` 在这条链路上已证明不代表「与法律无关」，
> 而问价词是能确定性识别的、与法条无关也无妨的一类。
>
> 判据的**唯一**放宽维度是状态；侧别红线一字未松（律师侧问了价也不给区块，逐出口有测试钉住）。
> 成本（已知并接受）：放行的问答多一次费用检索（Milvus 双路 + 本地精排，便宜）与一次费用生成
> 调用（DeepSeek，不便宜）；误命中的代价同此，且不会给出错数（费用数字仍要过 `fees` 的数值回查）。
> 实测数（改前 / 改后各 3 条，代表性问句）见 `.superpowers/sdd/b/final-review-fix-report-4.md`。
>
> ⚠️ **问价意图还须命中法律服务语境**（用户 2026-09-29 第三次裁决；语境词本身同日又收窄一次）：
> 问价词表只能保证「**不含**问价词的非法律题不给」，管不住「**含**问价词的非法律题」——
> 终审复核自造 10 条非法律问价题实测 **8 条命中**（「今天油价多少钱」「iPhone 15 多少钱」
> 「白菜多少钱一斤」…），它们会拿到律师卡片与费用区间：上一句刚说「这不属于法律问题」，
> 下一块就推律师与费用，**与答案自相矛盾**，还白花一次付费调用。
> 故判据收紧为「问价词 **且** 法律语境词」（`LEGAL_CONTEXT_RULES`）。
>
> **语境层只挡『无语境词』的那一半**：复核对收紧后的版本再自造 10 条**含语境词却仍非
> 法律服务**的问价题，**全部仍会命中**（`法律规定打车多少钱一公里` 靠裸「法律」、
> `代理记账多少钱一个月` 靠裸「代理」、`法院拍卖的房子多少钱` 靠「法院」）。同日再收两处：
> 裸「法律」→ 只认 `法律问题|法律服务|法律咨询`（它是万能前缀），
> 裸「代理」→ 只认 `代理费|代理案件|诉讼代理`（否则网住记账与淘宝）。**残存误伤**（不收紧，
> 已知并接受）：靠「法院」「赔偿」这类词仍会命中 —— 它们离法律更近、观感比天气/数码题轻，
> 标本钉在反例集里。
>
> **已知漏判**（用户裁决时知情并接受，测试里**逐条断言**而非只写注释）：省略语境的问法 ——
> `你们收费怎么算` / `先给我个报价` / `要花几万块钱吗` / `计费方式是怎样的`，
> 以及 `请律师一般怎么收`（不含「钱/费」字，刻意不补：补它会误伤「违约金怎么算」）。
> 方向是「不给」而不是「给错」—— 与词表其余部分同一取舍。语境的每条词族都有正例撑着
> （`LEGAL_CONTEXT_RULES` 按**词族**拆成多条 pattern，故 `test_every_context_rule_is_alive`
> 是真护栏 —— 但**只兜「新增孤儿词」这一个方向**：往表里塞一条没人用的词它会红，
> 而删掉一条 pattern 它看不见（删掉的不在循环里），那个方向靠**正例集**兜
> （复核逐条统计：13/13 条 pattern 都有独占正例）。写成一条大交替式时，两个方向都兜不住。）

## 五、数据结构

```python
# 律师卡片（演示数据）。**形状随模式变**：DEMO_MODE 开（演示期）是 6 键，多一个
# note；关掉后是 5 键（无 note）。读方必须用 .get("note")，硬下标会在「已接真实
# 名录」的那一天在渲染期抛 KeyError（那时答案已经算好）
{"name": str, "org": str, "field": str,
 "contact_hint": str,   # 演示期固定为「通过平台留言获取」——不产出任何真实联系方式
 "demo": True, "note": str | 缺}   # note 形如「示例数据」，仅 DEMO_MODE 下有

# 费用区间结果（estimate 的返回值）：**恒 9 键**，四种状态同形（渲染方不必先判
# 键在不在；少一个键就是渲染期的 KeyError，而故障那支最没人手工测到）
{"status": "ok" | "no_corpus" | "rejected",   # 有依据 / 未命中 / 回查未过
 "low": float | None, "high": float | None,
 "unit": str | None,           # 量级单位（元 / 万元 / %）：有值就必须在命中数字的
                               # 邻近窗口里有出处，缺省时若命中数字紧邻万/千/百/亿
                               # 也判拒（量级不得静默错档）
 "charge_basis": str | None,   # 计价基础（「小时」「件」…）：有值就必须在片段里
                               # 出现（宽松存在性），缺省不判拒。渲染附在费用行上
 "basis": str | None,          # 命中的收费口径片段原文
 "source_doc": str | None, "source_no": str | None,
 "reason": str | None}         # 给人看的原因（如「语料未收录该案由」）

# 故障（检索 / LLM 不可用）**不**表达成上面任何一种状态：
# estimate 直接抛异常，由 attach 捕获后在附加区块写成
# {"status": "unavailable", "reason": ..., ...}（**同一组 9 键**，见 attach._unavailable），
# 与「暂无依据」严格区分（§七红线）。

# 挂到问答结果上的附加区块
{"cause": str | None, "field": str, "lawyers": [...], "fee": {...},
 "disclaimer": "参考区间，不构成报价或委托"}   # AC-21 固定提示
```

> **`charge_basis` 与 `unit` 的分工（2026-09-29 补实现）**：`unit` 答「量级」（元 /
> 万元 / %），`charge_basis` 答「这笔钱按什么算」（小时 / 件…）。真跑实证 N10：
> 语料「四、计时收费标准：1000元—8000元/有效工作小时。」被渲染成「1000 ~ 8000元」，
> 用户会读成一次性收费 —— 丢掉的就是计价基础。两者的出处判定**有意不同源**：
> `unit` 承担量级，要求独立出现且贴着上报的那个数（子串匹配会让「元」混进「万元」，
> 静默错 4 个数量级）；`charge_basis` 不承担量级，「小时」出现在「有效工作小时」里
> 就是合法出处，故用宽松存在性。

## 六、存储

| 对象 | 形态 | 关键字段 | 用途 |
|---|---|---|---|
| `fee_corpus` | **Milvus 新集合** | `text, source_doc, source_no, region, effective_date, status` | 收费口径语料，走与法条相同的切分/向量/混合检索链路 |
| `fee_generation_log` | **MySQL 新表** | `ts, cause, snippet_id, range_low, range_high, model, request_id, status` | 每次费用生成留痕（**AC-21 的证据**，含被回查拒绝的区间） |

> **留痕表的列就是上表那七列**（2026-09-29 核实）：**不含 `unit`，也不含
> `source_doc`** —— 「模型报了什么单位 / 计价基础」在库里查不到。故抽查某个区间的
> 流程是：凭 `snippet_id` **复跑检索**取回片段原文，再逐字核对数字、单位与计价基础；
> `source_doc` 的唯一出口是渲染的「依据」行。要加列须先过裁决（AC-19 的列白名单
> 有测试钉住，多传的字段会被 `fee_log.record` 静默丢弃）。

> **`search_fn` 的 hit 字段契约**（编排层不假定检索方守约）：每个 hit **必须带
> `status`**，且只有等于「现行有效」才被采用；**缺失 / 空串 / 任何非现值一律判拒**
> （fail-closed —— 证明不了现行就不等于现行）。`text` 必给（生成与回查都用它），
> `source_doc` / `source_no` 可缺（只进「依据」）。

> **`region` 的处理口径（本期）**：用户问句通常不含地区，故**本期检索不按 `region` 过滤**（预计语料只覆盖一个地区）。字段照技术方案保留；将来接入多地区语料时再定「问题里显式地区 → 过滤，否则用配置默认值」的策略。

## 七、错误处理与降级

**红线（延续 ③a）：故障 ≠ 没有依据。** 「检索/模型不可用」与「语料里确实没有」必须给用户不同的结果。

| 情形 | 行为 | 性质 |
|---|---|---|
| 案由认不出 | 律师卡片退化为「通用」领域；费用照常走检索 | 正常路径 |
| fee_corpus 无命中 | 「暂无费用口径依据」+ 说明不猜数 | **设计行为** |
| 区间有数字在片段里找不到字面出处 | 降级为「暂无费用口径依据」+ 留痕记下被拒区间 | **降级** |
| fee_corpus 检索报错（Milvus 不可用） | **不得答成「暂无依据」**，如实报故障 | **故障** |
| 费用生成用的 LLM 不可用 | 同上 | **故障** |
| 命中片段的 `status` 非现行 / 已过期 | 不采用该片段，报告里说明 | 依据失效 |

> 上表最后一行（效力）的**实现口径**（2026-09-29 落实）：**检索侧**在每条
> `AnnSearchRequest` 上挂 `FEE_FILTER_EXPR`（`status == "现行有效"`，两路召回都挂）
> —— 主防线；**编排侧**在 `fees.estimate` 里再判一次 `snippet["status"] != "现行有效"`
> → 走 rejected 出口 + 留痕，**且判在生成之前**（不会被采用的片段不值得再问一次模型）
> —— 兜底，因为 `search_fn` 可注入、编排层不假定检索方一定过滤了。**渲染侧**按 reason
> 分句给用户一句明确的说明（「命中的收费口径效力非现行有效，未采用该口径」），
> 与回查判拒「无法指回收费口径」区分开。

**测试策略**（确定性为主）：

- **集成测**：fee_corpus 检索 + 留痕落库（真 Milvus / MySQL）
- **忠实变异**：本项目每任务惯例，逐条按原始字节还原并核对
- **不建新评估集**：③b 是确定性逻辑，单测足够。模型产区间的**质量**由真实语料到位后的 CLI 冒烟看，不写进单测

**验收判据**：

1. 推荐字段完整（姓名 / 执业机构 / 专业领域 / 联系方式获取方式），且**推荐依据可说明**（FR-9.3）

3. **无付费插位**：排序规则纯由领域匹配度决定（FR-9.5、AC-21），有测试钉住排序规则本身
4. 技术方案 6.4 两条硬规矩：区间**不得脱离命中片段编造**；命中不到**不猜数**
5. 项目惯例闸门：全量测试全绿 + `python tools/check_style.py backend tools` 零告警
6. 律师卡片在 `DEMO_MODE` 下**必须**带「示例数据」标注（有断言钉住）
