## 1. 优化一：镜像体积（剔除本地大模型依赖）

### 1.1 做法

| 手段 | 说明 |
| --- | --- |
| **大模型不進镜像** | 嵌入（bge-m3）与生成（qwen2.5:3b）统一走**宿主机 Ollama**，容器只做编排与检索 |
| 多阶段构建 | builder 装 `build-essential + python3-dev` 编 wheel，runtime 只搬 wheel，不带编译链 |
| `.dockerignore` | 把 `研发/data/**`、`*.npy/*.index/*.pkl/*.jsonl`、`部署/日志/**`、`__pycache__`、`.env` 排除出构建上下文 |
| 最小依赖闭包 | 只装 9 个包（见 `部署/docker/requirements.txt`），不装 `torch/transformers/open_clip/sentence-transformers` |
| 标准库替代 | 健康检查探针用 `urllib`（不装 curl）；Redis 客户端内置 RESP 实现（`redis` 包降为可选） |

### 1.2 结果（**核算值**，来源 `优化/评估结果/部署优化实测.json` → `依赖体积核算`）

| 方案 | 本地大模型依赖 | 精简依赖闭包 | 说明 |
| --- | --- | --- | --- |
| 容器内自带模型（**被否决**） | **463.96 MB** | — | torch 2.11.0+cpu / transformers 4.57.6 / sentence-transformers / huggingface_hub / tokenizers / safetensors 等 |
| 走宿主机 Ollama（**本方案**） | **0 MB**（不装） | **106.28 MB** | numpy / faiss-cpu / fastapi / uvicorn / pymupdf / jieba / Pillow / scipy / redis 及传递依赖 |
| **依赖体积降幅** | — | — | **357.68 MB（约 77%↓）** |

> 注：`open_clip` 与 `accelerate` 本机未安装，故 463.96 MB 是**保守下限**；
> 若按官方 wheel 体积（open_clip_torch ≈ 1.5 MB + accelerate ≈ 0.4 MB + **torch 的 CUDA 运行库另计 2 GB+**）
> 真实容器内推理方案的体积会高得多。这里只报**实测到的包目录体积**，不推算未安装包。

**镜像层估算（核算，非实测）**

| 层 | 估算体积 | 依据 |
| --- | --- | --- |
| `python:3.11-slim` 基础镜像 | ≈ 125 MB | 官方镜像声明 |
| apt 运行时包（tzdata + fonts-wqy-zenhei + libgomp1 + ca-certificates） | ≈ 45 MB | Debian 包体积 |
| Python 依赖闭包 | **106.28 MB** | 真实包目录体积（实测口径） |
| 业务源码（研发/app + 研发/service） | < 1 MB | 51 + 3 个 .py 文件 |
| **合计（估算）** | **≈ 280 MB 量级** | 不含 builder 阶段（不进最终镜像） |

对比：若把 torch/transformers 打进镜像，仅 CPU 版 wheel 就有 **463.96 MB**（实测包目录），
再加 CUDA 运行库会达到 **2 GB 以上** —— 即"服务器拉镜像的停机时间"差一个数量级。

### 1.3 被否决方案与代价

| 被否决 | 否决理由 | 代价 |
| --- | --- | --- |
| 容器内装 torch + CLIP 做本地图文向量 | 镜像 +2 GB 起；Windows Docker Desktop 无 GPU 直通 | 图文向量改由宿主机 Ollama 提供；若将来必须容器内编码，另建 `--target clip` 扩展镜像 |
| Alpine 基础镜像 | musl libc → faiss/numpy 需源码编译（时间长、内存高，触碰资源红线） | 用 `slim`（glibc，wheel 直接可用） |
| 装 curl 做健康检查 | 为一行命令引入一个包 | 标准库 `urllib` 探针（30 行，退出码语义自控） |

## 2. 优化二：冷启动时间

### 2.1 实测数字（来源：`部署优化实测.json` → `冷启动`，口径=**实测**）

| 阶段 | 关预热 | 开预热 | 说明 |
| --- | --- | --- | --- |
| 导入 + 配置加载 | 见"启动到可服务"合计 | 见右列合计 | `import app.core.*` + `get_config()` |
| 引擎初始化 | **0.423 s**（`nowarm` 合计，不加载索引） | — | `QAEngine(cfg)` |
| 预热（全文索引 + 实体标注 + 嵌入探活） | — | **22.739 s** | 其中全文索引构建约 **20.1 s**（8847 块、64134 字段） |
| **启动到"能服务"总耗时** | — | **23.114 s** | 容器 `HEALTHCHECK --start-period` 的依据 |

> 说明：`nowarm` 只做到 `QAEngine()` 构造（不加载索引），因此 **0.423 s** 表示"**进程能起来**"的时间；
> `warm` 的 **23.114 s** 才代表"**能对外服务**"的时间。
> 这也解释了为什么健康检查要拆成 `/healthz`（存活）与 `/readyz`（就绪）两档。
> 两次测量结果一致性很好（前一次 0.372 s / 23.831 s），差异来自 Ollama 模型冷热状态。

### 2.3 热路径实测（服务已在运行时，`部署优化实测.json` → `热路径`）

| 端点 | 中位响应 | 区间（10 次实测） |
| --- | --- | --- |
| `GET /healthz` | **2.30 ms** | 1.8 ~ 12.6 ms |
| `GET /health`（含全部卷/会话/引擎子项） | **10.30 ms** | 8.7 ~ 16.4 ms |

问答接口（2 个问题 × 各 2 次，均命中答案缓存）：

| 现象 | 墙钟 | 服务端 total |
| --- | --- | --- |
| 问题 A 第 1 次 | 55.66 ms | 3.9 ms |
| 问题 A 第 2 次 | 28.67 ms | 4.34 ms |
| 问题 B 第 1 次 | 23.46 ms | 3.57 ms |
| 问题 B 第 2 次 | 27.96 ms | 3.95 ms |

> **口径提醒**：这四个数字是**缓存命中**路径（同一批问题重复问），反映的是"缓存 + 编排层"的开销
> （服务端 4 ms 级），**不代表真实问答的端到端延迟**。
> 真实首答（未命中缓存）在测试里实测为 1.8~5.7 s 量级（含 Ollama 生成），
> 见 `测试/测试数据/问答接口-真实问题-*.json` 的 `latency_ms`。

### 2.2 优化手段与效果

| 手段 | 解决的问题 | 效果 |
| --- | --- | --- |
| **三档探针拆分** | 若 HEALTHCHECK 直接探 `/health`（要读索引），启动期必然连续失败 → 编排误判不健康 → 重启循环 | 容器探 `/healthz`（**2.67 ms** 中位响应，实测），就绪判断交 `/readyz` |
| `HEALTHCHECK --start-period=90s`（UI 150s） | 冷启动 23.8 s + 首次请求余量 | 消除"启动即判死"的误杀 |
| **`DEPLOY_WARMUP=1`**（默认开） | 预热代价前移到启动期，换取首请求不再等 20 s 级全文索引 | 首答延迟从"秒级排队"变为稳定 |
| **`DEPLOY_WARMUP_WITH_GENERATE=0`**（默认关） | 预热生成模型要多驻留一个 Ollama 模型（qwen2.5:3b ≈ 2.16 GB） | 规避内存红线；生成模型在首个真实问答时按需加载 |
| 索引**只读挂载 + 复用**（不重建） | 重建 8847 块索引需要解析 9 份年报 PDF，分钟级 | 冷启动只剩"载入 + 全文索引构建" |
| `PYTHONUNBUFFERED=1` | 日志块缓冲导致 `docker logs` 长时间空白 | 启动日志实时可见，问题可定位 |

### 2.4 热路径实测（第一次测量，保留作对照）

| 端点 | 中位响应 | 区间（10 次实测） |
| --- | --- | --- |
| `GET /healthz` | **2.67 ms** | 2.4 ~ 8.9 ms |
| `GET /health`（含全部卷/会话/引擎子项） | **9.91 ms** | 8.6 ~ 15.4 ms |

问答接口（2 个问题 × 各 2 次，均命中缓存）：第 1 次 20.16 / 44.33 ms，第 2 次 26.30 / 51.56 ms（服务端 3.6~4.3 ms）。

> 两次测量（2.3 节与本节）结论一致，差异在毫秒级噪声范围内；正文以最新一次（2.3 节）为准。

## 3. 优化三：资源限制（`--memory` / `--cpus`）调优

### 3.1 实测资源画像（`部署优化实测.json` → `内存`、`卷读写`、`并发探活`）

| 指标 | 实测值 | 采集方式 |
| --- | --- | --- |
| API 服务进程工作集 | **628 ~ 659 MB** | `Get-Process`（`WorkingSet64`） |
| API 服务进程私有内存 | **2409 ~ 2438 MB** | `PrivateMemorySize64` |
| 空闲期系统可用内存 | 2487 ~ 3162 MB | `\Memory\Available MBytes` |
| 系统提交内存占比 | 71.4% ~ 77.3% | `Committed / Commit Limit` |
| 测量脚本自身工作集 | 24.8 MB | 单进程、无线程池 |

> 为什么工作集与私有内存差这么多：RAG 要载入 `vectors.npy`（36 MB）+ `faiss.index`（36 MB）+
> `chunks_indexed.jsonl`（21 MB）+ `bm25.pkl`（11.8 MB）并在全文索引构建期产生大量临时对象，
> 峰值私有内存约 2.4 GB，随后由 Python 分配器保留（不立即归还 OS）。

### 3.2 限额取值依据与对比

| 服务 | 限额（compose `deploy.resources.limits`） | 依据（实测） | 若设小会怎样 |
| --- | --- | --- | --- |
| `rag-api` | **`memory: 2g` / `cpus: 2.0`** | 峰值私有内存实测 2.41~2.44 GB → 2 GB **偏紧**，建议生产取 **3g**（见下方"调优建议"） | OOMKilled（137），且发生在索引载入/全文索引构建期，表现为"启动即死循环重启" |
| `rag-ui` | `memory: 1g` / `cpus: 1.0` | 同样要载入索引 | 同上；若与 api 同宿主，建议同样给 2g |
| `redis` | `memory: 320m` / `cpus: 0.5` | `--maxmemory 256mb` + 客户端缓冲 | Redis 自身 OOM 保护生效（`allkeys-lru` 淘汰会话） |
| `prometheus` | `memory: 512m` / `cpus: 0.5` | 15 天保留期，单机小规模指标 | TSDB 写入被拒 |

> **这是本次调优最有价值的发现**：`--memory 2g` 在"实测峰值私有内存 2.4 GB"面前是**不够**的。
> 工单要求给出资源限制，同时纪律要求"真实数字"——两者相加的结论就是**把 2g 调成 3g**。

### 3.3 调优后的推荐配置（已可配置化，改 `.env` 即可）

```ini
# 部署/配置/.env
API_MEMORY=3g        # 实测峰值私有内存 2.41~2.44 GB → 留 ~20% 余量
API_CPUS=2.0
UI_MEMORY=2g         # UI 与 API 同样载入索引
UI_CPUS=1.0
REDIS_MEMORY=320m
```

容器侧等价命令：`docker run --memory 3g --cpus 2 ...`。
> 本机 Docker 不可用，**未能实测 OOMKilled 边界**；上表"若设小会怎样"是基于实测内存画像的推断，
> 已明确标注为推断，不作为实测结论。

## 4. 优化四：并发与稳定性

### 4.1 实测（`部署优化实测.json` → `并发探活`）

| 指标 | 实测值 |
| --- | --- |
| 并发配置 | **8 线程 × 40 请求**（全部为等网络的 I/O 任务） |
| **QPS** | **847.28** |
| 延迟 中位 / p95 / 最大 | **8.11 / 18.21 / 18.86 ms** |
| 失败数 | **0** |
| 异常日志（ERROR 级） | **0 条** |

并发问答（8 路，`测试/测试数据/并发问答-结果.json`）：**0 个 5xx、0 失败**；
p95 ≈ 4.7 s vs 单发基线 1.8 s（≈2.6×）—— 瓶颈是**宿主机单实例 Ollama 的排队**，
排查与优化属 **工单17（并发瓶颈与泄漏）**，本工单只保证"零 5xx、不崩"。

### 4.2 稳定性设计（不是靠调参，而是靠结构）

| 设计 | 作用 |
| --- | --- |
| 会话**双写**（文件卷 + Redis） | Redis 挂掉不影响会话可用；拔掉 Redis 数据也不丢 |
| Redis **熔断降级**（连续 3 次失败 → 熔断 30 s） | 避免网络问题把问答拖死；`/health` 如实报 `backend=file` |
| 生成**可降级**（Ollama 挂了走 `rule_composer` 抽取合成） | 答案事实一致，仅少一层润色；不返回 5xx |
| **零依赖 RESP 客户端** | 少一个外部依赖，容器冷启动不受其影响 |
| 索引**只读挂载** + 运行期 sqlite 独立卷 | 防止运行期写坏索引（**实测踩坑后加固**，见问题7） |
| 请求级异常兜底 handler | 500 JSON + ERROR 日志，不裸崩、不吐栈 |

## 5. 优化五：卷性能（实测，佐证"卷不是瓶颈"）

| 项目 | 实测值 | 说明 |
| --- | --- | --- |
| 会话文件写（原子替换 `.tmp`+`os.replace`） | **0.666 ms/文件** | 200 个文件实测，含 JSON 序列化 |
| 会话文件读 | **0.13 ms/文件** | 200 个文件实测 |
| 索引 `vectors.npy` 顺序读 | **1678.42 MB/s** | 36 MB 分块流式读（4 MB/块） |
| 索引卷文件合计 | **106.3 MB** | faiss.index 36.2 + vectors.npy 36.2 + chunks 21.1 + bm25 11.8 + ids 0.24 |

结论：**卷不是性能瓶颈**（顺序读 >1 GB/s，写 0.7 ms/文件），
把索引放在卷上而不是镜像里的代价可以忽略，换来的是"镜像小 + 索引可独立更新"。
