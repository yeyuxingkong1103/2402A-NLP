# 用户手册

**工单编号**：人工智能NLP-RAG项目-RAG性能瓶颈识别与优化

本手册面向要**跑这套性能对比**或**给 RAG 做性能排查**的人。

---

## 一、这套东西是什么

给已交付的 RAG 问答系统做了性能排查与优化，把端到端延迟从
**均值 3.82s / P95 11.76s** 降到 **均值 1.03s / P95 1.44s**。

测量手段三件套，缺一不可：

| 用途 | 工具 |
|---|---|
| 单请求「时间花在哪」 | `测试/bench.py` + `研发/perf.py` 埋点 |
| 「哪个函数是热点」 | cProfile + snakeviz、py-spy |
| 「并发上去了会怎样」 | JMeter |

## 三、怎么给别的系统做同样的排查

这套流程不绑定本系统，换个 RAG 也能用。**顺序很重要**：

1. **先让系统可被测量**
   - 有 HTTP 接口吗？没有就先加（JMeter 需要标准 REST，Gradio 压不了）
   - 加阶段埋点：每个阶段的出入口打时间戳 + 请求 ID
   - **自检埋点**：算一下「未归入任何阶段的时间」，占比高说明有盲区

2. **再定位**
   - 串行跑几次 → 看阶段占比，知道该往哪使劲
   - cProfile 找热点函数（**只看调用次数和累计占比，别看绝对耗时**）
   - py-spy 采样（开销低，适合在压测中同时采）

3. **然后压测**
   - JMeter 按并发梯度跑（1/4/8/16），画「吞吐-并发」和「延迟-并发」曲线
   - **吞吐不再涨而延迟继续涨的那个点**就是容量上限

4. **最后优化，并且验证没算错**
   - 每项优化都用**组件基准**量真实收益（别信 profiler 的绝对值）
   - 换了算法要**对拍**：新旧实现的结果必须逐位一致

## 四、常见坑（本工单都踩过）

### 「JMeter 两次运行的数据混在一起」

`-l` 参数**默认追加写**。加 `-f` 强制覆盖，或者每次跑前删掉 jtl 文件。

### 「吞吐算出来大得离谱」

JTL 里有两列容易混：
- `elapsed` = 该请求的耗时
- `timeStamp` = 请求发出的时刻

吞吐要用 **`timeStamp` 的跨度**算（`样本数 ÷ (max-min)`），
用 `elapsed` 的跨度算出来的是「样本耗时区间的倒数」，跟每秒请求数没关系。

### 「反复问同一个问题，延迟特别低」

命中了**大模型的提示缓存**。压测要用一组不同的问题轮换
（本项目用 `测试/jmeter/questions.csv`，10 道轮换）。

### 「cProfile 说某个函数特别慢，改了却没效果」

cProfile 给每次函数调用插桩，调用次数多的代码段会被放大好几倍
（本工单实测放大了 7 倍）。**它的绝对值不能用来做决策**，
要用组件基准测试单独量。

### 「优化前后数字几乎一样」

检查是不是拿**已经优化过的代码**跑的基线。本项目留了开关：

```bash
PERF_OPT=off LLM_REASONING_EFFORT= python 研发/api.py    # 优化前
python 研发/api.py                                        # 优化后
```

### 「高并发下延迟爆炸」

先分清是**本地**还是**外部服务**的问题：看阶段埋点里
「本地两段」与「LLM 段」各自随并发怎么变。
本项目的陡降点在并发 8，根因是外部大模型服务的限流 —— 本地改不了。
