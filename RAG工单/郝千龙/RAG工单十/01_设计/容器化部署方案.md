# 金融问答系统 Docker 容器化部署方案

- 工单编号：**人工智能NLP-RAG-金融问答系统部署**
- 版本：V1.0（2025-02）
- 对应工单产出物：① Docker 部署容器及部署文档；② 实现步骤、过程问题记录文档
- 关键词：Docker、卷持久化、自定义桥接网络、健康检查、非 root、纯 CPU 离线、TF-IDF + BM25

---

## 1. 需求与验收点映射

| 工单验收标准 | 本方案落地措施 |
|---|---|
| docker run 能成功启动容器并在指定端口提供服务 | 镜像 `finqa-service:1.0`，`docker run -p 8000:8000` 直接启动 Flask 服务监听 8000 |
| 容器运行无异常日志 | 屏蔽 pdfminer 常规告警；启动/问答关键节点结构化日志；异常完整堆栈；compose 日志滚动 |
| Docker 卷持久化关键数据，确保不丢失 | `/data`（PDF 语料）、`/app/index`（TF-IDF/BM25 索引）两个挂载点；原子写索引 |
| 支持容器间数据共享 | 两个挂载点声明为 `VOLUME`，可用命名卷被多个容器共享；compose 纳入自定义桥接网络 `finqa-net` |
| 网络配置正确，能与其他服务（如 RTMP 服务器）通信 | 端口映射 `8000:8000`；自定义 bridge 网络，容器间以容器名/服务名互访；对外仅暴露必要端口 |
| 部署后的金融问答服务测试通过 | `/health` 健康检查 + `/ask` 问答接口；本机与容器双重冒烟测试（见 03_测试） |

## 3. 镜像分层设计

| 层 | 内容 | 设计意图 |
|---|---|---|
| 基础层 | `python:3.11-slim` | 比完整 python 镜像小约 60%，纯 CPU 无需编译工具链；PyMuPDF/sklearn 均有 manylinux wheel |
| 系统层 | `tzdata`、`curl`、时区 `Asia/Shanghai`、`C.UTF-8` | 日志时间为北京时间；中文文件名/日志编解码正常；curl 供容器内人工排障 |
| 依赖层 | `requirements.txt` 单独 COPY 后 pip 安装 | 业务代码变更不会使依赖层缓存失效；`--no-cache-dir` 减小镜像 |
| 应用层 | `COPY app ./app` | 仅拷贝服务代码；data/index 由卷提供，不入镜像 |
| 运行层 | 非 root 用户 `appuser(uid=1000)`、`VOLUME`、`EXPOSE 8000`、`HEALTHCHECK`、`ENTRYPOINT` | 最小权限、声明式挂载与探活 |

- pip 源通过构建参数 `PIP_INDEX_URL` 配置，默认清华源，可切换阿里云等内网源；
- 不安装 `fonts-noto-cjk`（约 300MB）：本服务只抽取文本不渲染页面，`C.UTF-8` 已满足中文处理；后续若扩展页面截图/OCR 再追加（已在问题记录中说明）。

## 4. 卷（数据持久化）设计

| 容器路径 | 宿主机来源（compose） | 读写 | 内容 | 失效/重建策略 |
|---|---|---|---|---|
| `/data` | `./data` | 只读 `:ro` | 招股说明书等 PDF 语料 | 增删 PDF 后重启容器，按来源清单自动重建 |
| `/app/index` | `./index`（或命名卷 `finqa-index`） | 读写 | `vectors.npz`/`tfidf.pkl`/`bm25.pkl`/`chunks.pkl`/`meta.json` | 清单不变则新容器直接加载 |

**缓存命中判定（meta.json 校验）**：① 索引算法版本 `index_version`；② PDF 清单（文件名 + 大小 + mtime）；③ numpy/scikit-learn 运行时版本；④ 四个索引文件齐全。任一不满足即重建，避免跨版本 pickle 不兼容与半截索引。索引写入采用“临时文件 + `os.replace` 原子改名”，容器被 kill 也不会留下损坏索引。

**容器间数据共享**：`/data` 可同时以只读方式挂给多个问答实例（水平扩容）；`/app/index` 可挂给索引构建侧车容器做离线重建（蓝绿切换）。

## 5. 网络设计

- 端口：容器内固定监听 `0.0.0.0:8000`，宿主机映射 `8000:8000`，可按 `-p 18000:8000` 调整宿主端口；
- 网络驱动：compose 创建自定义 bridge `finqa-net`，同内容器可用服务名 `finqa` 端口 8000 互访（Docker 内置 DNS）；
- 与外部服务（工单举例 RTMP 服务器）协作：`docker network connect finqa-net <rtmp容器>` 后即可按容器名通信；跨主机时由宿主机防火墙/反向代理放行；
- 安全：语料卷只读挂载，镜像内非 root 运行，不对宿主机暴露其他端口。

## 6. 健康检查与可观测性

- Docker `HEALTHCHECK`：每 30s 请求 `GET /health`，超时 5s，**首次建库宽限 start-period=180s**，连续 3 次失败标记 unhealthy；
- `/health` 返回：`status / documents / chunks / index_built / index_load_seconds / started_at`，建库期间返回 503，就绪返回 200；
- 日志：标准输出 JSON 友好的结构化文本，`docker logs` 直接可见；compose 配置 json-file 单文件 20MB、保留 3 个滚动文件；
- 问答日志记录问题、命中页码与耗时，便于审计与回归。

## 7. 资源限制与纯 CPU 路线

| 项目 | 配置 | 依据 |
|---|---|---|
| 内存 | `mem_limit: 1024m`（预留 512m） | TF-IDF 采用 **CSR 稀疏矩阵**（稠密方案约 400MB → 稀疏约 30~60MB），全量索引常驻约 300~500MB |
| CPU | `cpus: 2.0` | 无 GPU；jieba 分词 + sklearn 稀疏点积，单次问答百毫秒级 |
| 磁盘 | 镜像约 500~700MB；卷：14MB PDF + 索引约 50~120MB | 不含中文字体与模型权重 |
| 模型 | 无外部模型、无外网调用 | TF-IDF（char 2~4gram，max_features=2 万）+ BM25，符合离线无外网约束 |

## 8. 接口设计摘要

| 方法 | 路径 | 入参 | 出参要点 |
|---|---|---|---|
| GET | `/` | 无 | 服务说明 HTML（人工探活） |
| GET | `/health` | 无 | status/documents/chunks/index_built/index_load_seconds |
| POST | `/ask` | JSON `{"question":"...","top_k":3}` | code/answer/evidences(rank,page_no,title,snippet,score,双路名次)/latency_ms/mode/timings |
