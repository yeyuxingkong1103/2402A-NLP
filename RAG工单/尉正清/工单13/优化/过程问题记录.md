## 二、过程问题记录

### 问题 1：现有 RAG 系统没有 JMeter 能压的接口

**现象**：工单要求「使用负载测试工具（k6、Locust、JMeter 等）模拟生产流量」，
但现有 RAG 系统只有 Gradio 界面。

**为什么不能直接压 Gradio**：它的 API 要先拿 session hash，请求体还是私有的
`data` 数组格式。压出来的数字反映的是 **Gradio 外壳**（它自己还有队列、
并发限制 `default_concurrency_limit=4`），而不是 RAG 本体。

**解决**：加一个最小的 FastAPI 端点（`研发/api.py`），`POST /query`。
**没有引入新依赖** —— fastapi/uvicorn 环境里本来就有（gradio 依赖它们）。

**关键设计**：知识库与模型**启动时加载一次常驻**。
「每次请求重新加载 BGE-M3」和「加载一次复用」差好几个数量级，
这是压测里最容易把结论带偏的地方。

---

### 问题 2：埋点分不清「时间花在哪」

**现象**：最初只有 `RAGEngine.answer()` 返回的 `retrieve_seconds` 和 `elapsed`
两个数，只能看出「检索 vs 总时长」，检索内部是什么情况完全不知道。

**解决**：按工单对「日志记录」的三条要求实现 `研发/perf.py`：

| 工单要求 | 实现 |
|---|---|
| 每个主要阶段和子阶段的进入/退出打时间戳 | `perf.stage()` 上下文管理器，支持嵌套（记 `depth`） |
| 包含请求 ID 追踪单个请求 | `Trace.id`，随响应返回、写进日志 |
| 记录召回文档数、上下文长度、生成 token 数 | `perf.metric()` |

**分五层埋点**，最后用「未归入任何阶段的时间」自检埋点有没有漏：

```
1-查询理解
2-检索召回 ├─ 2.1-单路检索 ├─ 2.1.1-查询编码
                           ├─ 2.1.2-稠密打分
                           ├─ 2.1.3-稀疏打分
                           └─ 2.1.4-RRF融合
3-上下文组装
4-LLM生成
```

实测 **未归入阶段的时间占 0.0%** —— 埋点没有漏掉任何耗时。

---

### 问题 3：cProfile 的绝对耗时会骗人（本工单最重要的一条）

**现象**：cProfile 显示 `socket.connect` 每次调用 **2.225 秒**，
3 次请求累计 6.676 秒；`ssl.do_handshake` 每次 1.656 秒。
照这个数推算，改成连接复用一个请求能省 2 秒多。

**实际去测**：单独写了个组件基准，同一个端点、同一个极短请求，
只改连接方式：

```
裸 requests.post（现状）      均值 0.811s
requests.Session（连接复用）   均值 0.503s     ← 真实收益 0.31s
```

**差了 7 倍。** 原因：cProfile 给**每一次函数调用**插桩，
而本流程里 `_sparse_score` 会被调用 **7,009 次**、
内部生成器表达式 **658,846 次**、`dict.get` **1,242,934 次** ——
这么多调用点的插桩开销，把相关代码段整体放大了。

**结论（写进了性能报告）**：

> cProfile 用来**定位热点函数**可靠，用来**量绝对耗时**不可靠。
> 报告里所有绝对值都出自 `perf.py` 的阶段埋点与 JMeter。

这条不是理论 —— 如果直接信了那 2.2 秒，会把优化重心放错地方。

### 问题 4：JMeter 的 `-l` 默认追加写，两轮数据混在一起

**现象**：重跑压测后分析吞吐，算出「并发 1 时 3.2 请求/秒」，
比串行基准的 0.5 请求/秒还高 —— 明显不对。

**排查**：读 JTL 发现 `jmeter_before_u1.jtl` 里有 13 个样本（本次只发了 5 个），
时间戳跨度 **377 秒** —— 文件里混了前后两次运行的数据。

**根因**：JMeter 的 `-l` 参数**默认追加**而不是覆盖。

**解决**：加 `-f`（force overwrite）。**同时修掉一个衍生 bug**：
我的吞吐计算用的是「耗时」列的跨度而不是「时间戳」列的跨度 ——
这两列含义完全不同，用错了算出来的是「样本耗时区间的倒数」，
跟每秒请求数没关系。改用 `max(timeStamp) - min(timeStamp)` 后数字才正确。

---

### 问题 5：改完代码没回退就重测，两组数字几乎一样

**现象**：第一次做「优化前后对比」时，优化后跑完直接重跑了一遍 JMeter 当基线 ——
结果两组数字几乎一模一样（1 用户 1207ms vs 1247ms）。

**根因**：**基线是用已经优化过的代码跑的**。我改完代码没有回退，
所谓「优化前」其实是「优化后」的第二遍。

**解决**：加 `PERF_OPT` 环境开关，让四项优化可以一键关掉：

```bash
# 优化前（回到原始状态）
PERF_OPT=off LLM_REASONING_EFFORT= python api.py

# 优化后（默认）
python api.py
```

**留着这个开关是有意的**：它让前后对比**可复现** ——
评审不用翻代码历史，改一个环境变量就能把两轮都跑一遍。

---

### 问题 6：优化最容易出错的地方是「悄悄算错」

**风险**：稀疏打分从「全表扫描」改成「倒排索引」，
如果分数有偏差，检索排序就会变，**答案质量下降但不会报错**，
跑一遍还「一切正常」。

**解决**：写 `测试/verify_optimization.py`，用原算法对新算法**逐题对拍**：

```
10 道题，倒排索引与原全表扫描的最大相对差 1.04e-07
（只有 float32 累加顺序的误差）→ 计算结果一致
```

**先对拍、再比性能** —— 顺序不能反。

## 三、优化措施与依据

| # | 措施 | 怎么发现的 | 效果 |
|---|---|---|---|
| A | 大模型**连接复用**（线程级 `requests.Session`） | cProfile 标出 `socket.connect` 可疑 → 组件基准测试定量 | 组件级 0.81s → 0.50s |
| B | **关掉推理模型的思维链**（`reasoning_effort=none`） | 阶段埋点显示 LLM 占 88% 且方差极大（1.3s~9.9s） | LLM 段 3.39s → 0.85s |
| C | 稀疏打分改**倒排索引** | cProfile 的**调用次数**视图：7,009 次调用 / 65 万次字典查找 | 单路 0.148s → 0.005s |
| D | **启动预热** | 首请求 9.68s vs 稳态 0.4s | 冷启动移到启动阶段（2.7s） |

> B 的关键：`deepseek-flash` 是**推理模型**，思维链与正文共用 `max_tokens`，
> 且思考长度随问题波动极大 —— 这正是「平均 3.8s、P95 却 11.8s」的来源。
> 关掉后不仅更快，**方差也塌下来了**（这是 P95 从 11.76s 降到 1.44s 的主因）。

## 四、最终结果

| 指标 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 端到端 均值 | 3.82s | **1.03s** | 3.7× |
| 端到端 **P95** | **11.76s** | **1.44s** | **8.2×** |
| 检索段 均值 | 0.41s | **0.17s** | 2.4× |
| 并发 8 吞吐 | 0.4/s | **3.3/s** | 8× |

**验收标准「每个会话，用户输入 query 后，返回的检索结果要在 3S 以内」达成**：
优化后均值 1.03s、P95 1.44s、最大 1.44s，全部低于 3s。
