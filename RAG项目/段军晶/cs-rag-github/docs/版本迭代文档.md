### 2.3 刻意不改动的文件

**`backend/rag_pipeline/v1_pipeline.py` 一行未改。**

理由：重灌知识库后**索引内容已变**（图片块追加了视觉描述）。只要 V1 代码保持原样，V1 在新索引上的指标变化就能**干净归因到索引改动**；若顺手重构了它，就再也分不清指标波动来自代码改动还是索引改动。

这是对 ADR-010「公共逻辑抽到共享模块」的**有意偏离**，取舍记录于 ADR-018。代价是 V1/V2 之间存在少量重复代码，换来的是基线可归因性——本轮[指标对比文档](指标对比文档.md)的三点归因能成立，正是靠这一点。

## 三、遇到的问题与解决方案

> 本节记录 V2 开发中**真实遇到并解决**的问题。其中三个属于「静默失效」——不报错、只是能力受损，是本项目最需要警惕的一类故障（ADR-013 记录过同类教训）。

### 3.1 稀疏向量是否需要引入 FlagEmbedding？——不需要

**问题**：BGE-M3 的稀疏权重（lexical weights）通常通过 `FlagEmbedding` 库获取。但本项目现用 `sentence-transformers 5.2.3`，引入 `FlagEmbedding` 有触发版本降级、破坏既有稠密编码的风险。

**排查**：检查模型权重目录，发现 `sparse_linear.pt`（仅 3.5 KB，即稀疏权重的线性层）**已在本地**。该文件可直接用 `torch.load` 加载，无需 FlagEmbedding。

**验证**：先写探针脚本比对，确认两点：

1. 手动 CLS 池化 + L2 归一化的结果与 `sentence-transformers.encode(normalize_embeddings=True)` **逐元素完全相同**（最大差 0.000e+00，余弦 1.000000）
2. 稀疏权重落在实词上，语义合理：「等级」0.3162、「充分」0.3090、「功能」0.2424

**结论**：不引入新依赖，且因稠密输出完全一致，可安全地把稠密与稀疏合并为**一次 forward**（省一半 CPU 推理）。记录于 ADR-014。

### 3.2 特殊 token 污染稀疏权重

**问题**：探针输出显示 `<s>`（id 0）、`</s>`（id 2）也获得了 0.1760~0.1956 的权重。

**分析**：这些 token 在**任何**文本中都出现，只贡献常量偏置、无区分度，是纯噪声。

**解决**：在 `_to_sparse_dict()` 中显式排除 `{0, 1, 2}`。实测非零维度数从 12 降到 10、11 降到 9——正好各少 2 个，与预期一致。记录于 ADR-015。

### 3.3 追加视觉描述后 content 可能超限 ⚠️

**问题**：`chunk_split.py` 原有一行 `content[:settings.chunk_max_chars]` 截断，但它发生在**追加视觉描述之前**。若先追加再硬切片，可能把描述拦腰截断，甚至在图注很长时把描述**整段切掉**——视觉解析白做，且**没有任何报错**。

**解决**：抽出纯函数 `compose_block_content()`，**图注优先完整保留，剩余预算分配给描述**，并在截断发生时记 WARNING。抽成纯函数的原因正是：截断是最容易出静默错误的地方，只有纯函数才能用大量边界用例覆盖（含一个 500 组随机输入的长度不变式测试）。

### 3.4 Milvus 的超长兜底对中文是失效的 ⚠️ 高危

**发现方式**：写回归测试时，向 `content` 写入 20000 个中文字符，Milvus 直接报错：

```
MilvusException(code=1100, length of varchar field content exceeds max length,
                row number: 0, length: 24576, max length: 8192)
```

**根因**：`VARCHAR(max_length=8192)` 以 **UTF-8 字节**计数，而 Python 的字符串切片按**字符**计数。一个中文字符占 3 字节，因此 `text[:8192]` 对中文内容实际产生 **24576 字节**，超限 3 倍。这是**整条插入被拒绝**，不是静默截断。

**影响面**：触发阈值是 **2730 个中文字符**（8192 ÷ 3）。当时 `CHUNK_MAX_CHARS = 2000`（=6000 字节）尚未触达，所以该缺陷此前一直**潜伏**——一旦有人调大配置，所有含长中文块的写入会整体失败。

**解决**：新增 `_truncate_utf8()`，按字节截断（`errors="ignore"` 避免在多字节字符中间切断时抛异常），并在截断时记 WARNING。记录于 ADR-021。

### 3.5 写入后不 flush，新数据静默不可检索 ⚠️ 高危

**发现方式**：Milvus 集成测试中，同一进程内先 `insert` 再 `search`，**命中数为 0**；加 `flush` 后立刻命中。

**根因**：Milvus 在默认一致性级别下，新写入的数据要等自动 flush 之后才进入可检索状态。**原代码库中没有任何 flush 调用。**

**为什么 V1 从未暴露**：V1 的知识库是提前一天灌入的，期间已被 Milvus 自动 flush。但 V2 的「重建后立刻评测」工作流**必然踩到**，且失败是**静默的**——不报错、只是少召回甚至完全查不到。

**解决**：新增 `flush_collection()`，并在 `insert_vectors()` 写入完成后调用。记录于 ADR-020。

### 3.6 加稀疏字段把 V1 检索整个打崩 ⚠️ 高危

**发现方式**：计划中「冒烟测试 V1 仍可用」这一步，实测直接抛异常：

```
MilvusException(code=65535, message=multiple anns_fields exist,
                please specify a anns_field in search_params)
```

**根因**：V1 时期集合只有一个向量字段，Milvus 能自动推断检索目标。加入 `sparse_embedding` 后集合内出现**两个向量字段**，`search_dense()` 若不明示 `anns_field` 就无法工作。

**严重性**：这意味着「加稀疏字段」这个 V2 的**前置动作本身**就会让 V1 完全不可用。若只验证 V2 能跑，会以为一切正常。

**解决**：`search_dense()` 显式声明 `anns_field="embedding"`。同时新增 `has_sparse_field()` 与写入前护栏：向没有稀疏字段的集合写稀疏向量时，抛出**可执行的中文提示**（告知需 `--rebuild`），而不是让 Milvus 抛晦涩错误。记录于 ADR-022。

### 3.7 集合 schema 建立后不可变更

**问题**：`create_collection(drop_existing=False)` 对已存在的集合**直接跳过**（日志：「集合已存在，跳过创建」）。因此从 V1 升级到 V2 时，即使代码里写了 `enable_sparse=True`，旧集合也不会有稀疏字段。

**解决**：`embedding_store.py` 在非 rebuild 路径下显式检查 `has_sparse_field()` 并告警；写入侧护栏（3.6）兜底。

### 3.8 分通道页码只能取自 Milvus

**问题**：Trace 要求记录两路各自的「命中页码」。但 MySQL 的元数据回填发生在 RRF **之后**，融合前拿不到 MySQL 的页码。

**解决**：融合前的页码取自 Milvus 中冗余保存的 `page_no`。这与 ADR-005 的分工一致（Milvus 的 `page_no`/`content` 本就用于「检索结果快速回显与日志记录」），**对外返回的溯源信息仍一律以 MySQL 为准**。

### 3.9 `pytest.ini` 不能写中文

**问题**：Windows 下 pytest 通过 `iniconfig` 以系统本地编码（GBK）读取 `.ini` 文件，写入中文会导致 `UnicodeDecodeError`，**测试完全无法收集**。

**解决**：`pytest.ini` 保持纯 ASCII（`markers = slow` + `addopts`），中文说明移到 `tests/conftest.py`（Python 文件按 UTF-8 读取）。

### 3.10 运维层面的两件事（非代码缺陷，但值得记录）

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 后端启动时报「端口 8000 被占用」而拒绝启动 | 早先启动的后端进程在父 shell 被杀后成为孤儿，且因输出管道断开而卡死（监听端口但不响应） | 结束该进程；并在启动脚本的体检环节增加「占用进程 PID + `taskkill` 命令」提示 |
| 启动脚本输出中文乱码 | Python 在 stdout 非真实控制台（重定向到管道/文件）时退回系统本地编码 GBK | 脚本中设置 `PYTHONIOENCODING=utf-8` |

## 四、评测结果要点

完整数据与归因见[指标对比文档](指标对比文档.md)，此处只列三条最值得记住的：

1. **V2 检索指标全面优于基线**：recall@1 +0.0834、recall@3 +0.0834、MRR +0.0528，满足 M5 门禁。
2. **视觉解析贡献明确**：recall@1 +0.1667、MRR +0.0875；R11 由 RR 0.50 升至 1.00。
3. **R09 未被解决，且基线报告的归因被实测推翻**：原以为「功能充分性」是字面匹配弱导致失败、稀疏通道可解；实测该术语在附录表格中同样密集出现，**字面匹配反而偏向附录大表**。该失败模式需要**判断相关性的重排**，已明确划入 V3 靶点。
