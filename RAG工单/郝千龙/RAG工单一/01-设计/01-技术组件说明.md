# 技术组件说明

> 工单编号：人工智能NLP-RAG-基于PDF文档的问答系统
> 数据来源：招股说明书1.pdf（武汉兴图新科电子股份有限公司 招股意向书，共548页）
> 文档版本：V1.0
> 编写日期：2026-09-28

## 一、组件总览

本系统基于 RAG（Retrieval-Augmented Generation，检索增强生成）架构，围绕"PDF 解析 → 向量化 → 混合检索 → 生成"主链路设计，共划分为 7 大技术组件：

| 编号 | 组件名称 | 主要职责 | 核心技术选型 |
| :--: | :--- | :--- | :--- |
| C1 | PDF 解析组件 | 提取招股说明书的文本、表格、版式 | PyMuPDF + PDFPlumber |
| C2 | 文本切分组件 | 切分长文档为语义块 | LangChain RecursiveCharacterTextSplitter |
| C3 | 向量化组件 | 文本块嵌入为向量（中英文） | bge-base-zh-v1.5 / sentence-transformers |
| C4 | 向量库与缓存组件 | 存储向量、相似度检索、答案缓存 | FAISS（默认）/ Chroma / Milvus；Local 文件 / Redis |
| C5 | LLM 生成组件 | 基于检索上下文生成回答（中英双语） | DeepSeek API（OpenAI 兼容协议） |
| C6 | 交互界面组件 | 问答 / 知识库 / 评估，含语音输入 | FastAPI 全异步后端 + Streamlit 前端 |
| C7 | 混合检索组件 | 稠密+稀疏召回、RRF 融合、重排 | BM25(jieba) + RRF + CrossEncoder |

## 二、组件详细设计

### C1 PDF 解析组件
- **输入**：`招股说明书1.pdf`
- **输出**：结构化文本（页码、段落、表格）
- **关键能力**：
  - 文字层提取（PyMuPDF `page.get_text()`）
  - 表格识别（PDFPlumber `extract_tables()`）
  - 页码保留，便于溯源引用
  - 解析结果落盘缓存为 `.jsonl`，避免重复解析
- **异常处理**：扫描页（无文字层）跳过并记录告警

### C2 文本切分组件
- **切分策略**：递归字符切分（中文优先按 `。！？\n` 切分）
- **块大小**：chunk_size=512，overlap=64
- **元数据**：保留 `page`、`chunk_id`、`source`

### C3 向量化组件
- **模型**：`BAAI/bge-base-zh-v1.5`（中英文语义检索优化，支持工单多语言验收）
- **维度**：768 维
- **批量编码**：batch_size=32，CPU/GPU 自适应（无 GPU 环境使用 CPU）
- **归一化**：L2 归一化后入库，使用 cosine 相似度

### C4 向量库与缓存组件（门面模式多后端）
- **向量库**：
  - 单机默认 **FAISS**（IndexFlatIP 精确内积，向量归一化后即余弦；单文件持久化，Windows 稳定，检索 <10ms）
  - 可选 **Chroma**（PersistentClient）与 **Milvus**（HNSW，M=16/ef=64，分布式生产）
  - id=`{doc_id}_{chunk_id}`
- **答案缓存**：
  - 单机默认 **LocalCache**（带 TTL 的 JSON 文件 + 线程锁）
  - 生产可切 **Redis**
  - 缓存键含语言标识，中英问题分别缓存
- **切换方式**：环境变量 `VECTOR_BACKEND=faiss|chroma|milvus`、`CACHE_BACKEND=local|redis`，业务代码零改动

### C5 LLM 生成组件
- **Prompt 模板**（中英双语，按 `lang` 选择）：
  ```
  你是招股说明书问答助手。仅依据检索上下文回答；
  上下文不含答案时回答"招股说明书中未提及该信息"。
  上下文：{context}
  问题：{question}
  ```
- **调用方式**：OpenAI 兼容协议，默认 **DeepSeek**（deepseek-chat）；可切 Ollama/vLLM
- **参数**：temperature=0.3，max_tokens=400（控制生成时延保障 3s SLA），timeout=8s
- **基线对比**：另设无上下文 Prompt，用于纯 LLM vs RAG 对比

### C6 交互界面组件
- **FastAPI 全异步后端**：
  - `/api/ask`、`/api/ask/baseline`：RAG 与基线问答
  - `/api/evaluate`、`/api/evaluate/workorder`：RAGAS 评估
  - `/api/feedback`（GET/POST）：答案反馈
  - `/api/upload`、`/api/documents`：知识库管理
  - CPU 密集任务通过 `asyncio.to_thread` 隔离，不阻塞事件循环
- **Streamlit 前端**：
  - 三个标签页：智能问答 / 知识库管理 / RAGAS 评估
  - 侧边栏中英文切换（I18N 字典）
  - 语音输入组件（浏览器 Web Speech API，zh-CN/en-US）
  - RAG vs 纯 LLM 同屏对比、引用页码展开、👍👎 反馈

### C7 混合检索组件
- **稠密召回**：bge-base 向量 Top-20
- **稀疏召回**：BM25（jieba 中文分词）Top-20
- **融合**：RRF（Reciprocal Rank Fusion，`score=Σ 1/(60+rank)`）
- **重排**：CrossEncoder（bge-reranker-large）对融合结果精排
  - GPU 环境默认开启；CPU 默认关闭以防破坏 3s SLA；内部 800ms 超时/异常自动降级
- **输出**：Top-5 上下文块送入 LLM

## 三、组件依赖关系

```
招股说明书1.pdf
        │
        ▼
   [C1 PDF 解析] ──► .jsonl/.pkl 缓存
        │
        ▼
   [C2 文本切分] ──► 1612 chunks
        │
        ▼
   [C3 bge-base 向量化]
        │
        ▼
   [C4 FAISS/Chroma/Milvus]   [BM25 索引(jieba)]
        ▲                           ▲
        └──────── 检索时 ───────────┘
                   │
                   ▼
   用户 Query ─► [C3 向量化] ─► 双路召回 ─► [C7 RRF 融合 + CrossEncoder 重排]
                                                        │
                                                        ▼
                                   [C5 DeepSeek 生成] ─► [C6 FastAPI/Streamlit]
                                                        │
                                              [C4 缓存 Local/Redis]
```

## 四、性能与稳定性

- **响应时间**：单次问答 ≤ 3s（混合检索 < 200ms，DeepSeek 生成约 2s；缓存命中 < 50ms）
- **容错**：PDF 解析失败跳过、BM25/重排异常自动降级为纯向量检索、LLM 超时 8s 熔断
- **高可用**：FastAPI 全异步 + asyncio.to_thread 隔离 CPU 任务；向量库/缓存门面可平滑扩展为 Milvus + Redis 集群

---

> 技术备注：
> - **RAG（Retrieval-Augmented Generation）**：检索增强生成，核心思想是"先检索相关文档片段，再将其作为上下文喂给 LLM 生成答案"，用以缓解 LLM 知识滞后与幻觉问题。
> - **Transformer**：LLM 与 Embedding 模型的基础架构，由 Self-Attention + FeedForward 组成，支持长序列建模。
> - **Fine-tuning**：在本工单中采用领域数据对 Embedding 模型做 ANCE/对比学习微调可进一步提升检索质量，但默认使用通用预训练模型即可满足验收。
