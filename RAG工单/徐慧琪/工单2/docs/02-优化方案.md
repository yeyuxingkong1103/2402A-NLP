# 工单 02 优化方案

- 工单编号：**人工智能NLP-RAG-基于PDF文档的问答系统优化**
- 优化对象：工单 01《基于 PDF 文档的问答系统》
- 目标文档：《招股说明书1.pdf》（548 页）
- 日期：2026-10-03

---

## 一、总体思路

工单 02 要求"从 **PDF 解析、分块、检索** 三个层面做优化，把回答准确率提升到 ≥90%，
响应时间保持 ≤3 秒"。三层的优化点与实测结果如下：

| 层面 | 工单 01（优化前） | 工单 02（优化后） | 状态 |
| --- | --- | --- | --- |
| 解析 | PyMuPDF 直抽 + 启发式标题 | PyMuPDF **增强引擎**（编号+字号双证据、目录页识别、折行标题合并、页眉页脚清洗）+ 表格提取 + OCR 兜底；MinerU 路径保留（见 2.1 实测） | ✅ |
| 分块 | 固定 900 字窗口 + 重叠 | **标题层级分块 + 父子块**（子块 300–450 字检索 / 父块 ≤1800 字上下文）+ 表格独立成块 + 全量元数据 | ✅ |
| 检索 | 向量 + BM25 + RRF + 精排 | 在上述基础上增加 **查询改写（意图/消歧/分解/扩展）+ 多路召回 + 父块上下文压缩 + 缓存与降级** | ✅ |

## 二、解析层优化

### 2.1 MinerU 主解析：版本选择与实测记录（重要工程记录）

工单指定"MinerU（主力）+ PaddleOCR-VL（兜底）"。本机对 MinerU 的**四个版本/后端组合**
逐一实测，最终打通 **3.4.5 + pipeline**：

| 版本 | 后端 | 结果 | 原因 |
| --- | --- | --- | --- |
| 2.7.6 | pipeline | ❌ | 硬编码需要 `models/Layout/YOLO/doclayout_yolo_...pt` 与 `models/MFD/YOLO/yolo_v8_ft.pt`，本机 PDF-Extract-Kit 快照**缺这两个文件**，且硬约束禁止下载 |
| 2.7.6 | vlm-auto-engine | ❌ | MinerU2.5-Pro-1.2B 在 RTX 4060 8G 上**单页推理 >1 小时**未收敛（模型加载仅 2.7s；已修正 `Qwen2VLConfig` 兼容补丁与 `max_new_tokens` 上限，无实质改善） |
| 4.0.10 | flash | ⚠️ | 可直跑，但输出丢失**表格结构**（财务表格数据缺失），质量低于 PyMuPDF |
| 4.0.10 | basic/standard | ❌ | 本地解析服务需要 `MinerU2.5-Pro-2605-1.2B-GGUF`（llama.cpp 量化模型），本机没有且禁下载 |
| **3.4.5** | **pipeline** | **✅ 采用** | **模型清单与本机快照完全匹配**（下表），版面分析 ~1.1 s/页，全量 548 页十几分钟跑完 |

**为什么 3.4.5 能行**——它的模型清单与本机 `PDF-Extract-Kit-1.0` 快照逐一对应：

| 3.4.5 需要的模型 | 本机路径 | 状态 |
| --- | --- | --- |
| `models/Layout/PP-DocLayoutV2` | 同左 | ✅ |
| `models/MFR/unimernet_hf_small_2503`、`pp_formulanet_plus_m` | 同左 | ✅ |
| `models/OCR/paddleocr_torch` | 同左 | ✅ |
| `models/TabRec/SlanetPlus/slanet-plus.onnx`、`UnetStructure/unet.onnx` | 同左 | ✅ |
| `models/TabCls/paddle_table_cls/PP-LCNet_x1_0_table_cls.onnx` | 同左 | ✅ |

即：本机快照是**新版**（含 PP-DocLayoutV2、无 YOLO/MFD），正好对应 3.x 的模型契约；
2.7.6 属旧版契约、4.0 属新版 GGUF 契约，因此两头都跑不通。

**依赖隔离**：MinerU 3.4.5 依赖 transformers 4.x 的旧 API
（如 `pytorch_utils.find_pruneable_heads_and_indices`），主环境为 transformers 5.15（已移除）。
为此建独立 venv `D:\model\mineru-venv`（`--system-site-packages` **复用主环境 CUDA torch**，
仅隔离 transformers==4.57.6 及其直接依赖），通过 `scripts/mineru_run.py` 子进程调用，
主环境（工单1/工单2 其余模块）完全不受影响。

**混合补齐（全项目测试后新增，2026-10-04）**：
MinerU 3.4.5 在**"伪表格页"**（双栏正文/释义页被 PP-DocLayoutV2 误判为表格、
TableRec 解析失败且未回退 OCR）上会丢弃内容——实测 502 个表格块中 113 个
`table_body` 为空（22.5%），`content_list_v2` 同样为空。
`src/pdf_parser.py::merge_pymupdf_gap` 对"MinerU 文本量 < 120 字"的稀疏页
用 PyMuPDF 补正文（实测补齐 94 页），**页覆盖从 489/548 提升到 543/548**；
剩余 5 页内容归属跨页表格（非丢失）。

**页码归属修复（同批）**：`src/chunker.py` 原先把所有子块的 `page_idx`
统一标为 section 起始页（导致引用页码偏移、页覆盖统计失真），已改为
**每个子块记录自身起点所在页**——修复后 260 题引用第 129 页（正文页），
543/531 题引用第 52 页（发行人基本情况），均与内容实际位置一致。

**容错**：MinerU 任何环节失败（依赖/显存/超时）时，
`src/pdf_parser.py::parse_pdf` 自动回退 PyMuPDF 增强引擎（见 2.2），建库链路不被单点阻塞。

### 2.2 PyMuPDF 增强解析引擎（回退路径，`src/pymupdf_parser.py`）

> 定位：MinerU 不可用时的自动回退（容错），日常主链路走 MinerU 3.4.5。
> 本模块移植自工单01，含五遍扫描，能力如下表。

| 遍 | 处理 | 关键规则 |
| --- | --- | --- |
| 1 | 统计正文字号 | 按字符数加权的众数字号（body_size） |
| 2 | 逐页抽行 + 表格 | `line.get_text("dict")` 取 span 字号/加粗；`find_tables()` 提表格并转 Markdown |
| 3 | 剔除页眉/页脚 | 跨页重复行模式识别（实测剔除 3 类，如 `#-#-#`） |
| 4 | 合并折行标题 | 长标题被排版折成 2–3 行时合并回一行 |
| 5 | 维护标题栈 | 编号正则（`第X节/一、/（一）/1.`）× 字号，双证据判层级；目录页整页不做标题识别（避免目录条目污染 heading_path） |

输出等价 MinerU 的 `content_list` 结构（`type/text/page_idx/heading_path/source`），
并额外标注 `is_heading` 供分块器还原层级。

### 2.3 PaddleOCR-VL 兜底（`src/ocr_fallback.py`）

- 触发：质量报告中"低文本页"（< 30 字符）且 PaddleOCR-VL venv 可用；
- 方式：PyMuPDF 渲染页面为 PNG → **独立 venv 子进程**调用（`D:\model\Paddle-OCR\venv`，
  paddleocr 3.7 + paddlepaddle-gpu 3.3.1），`PADDLE_PDX_MODEL_SOURCE=local` 强制离线；
- 容错：超时/失败自动跳过，主链路结果不受影响；
- 实测：本工单 548 页均有文本层，兜底**未触发**（26 页低文本页均为空白页/分隔页）。

## 三、分块层优化

### 3.1 为什么弃用固定窗口（工单明确要求"不要 RecursiveCharacterTextSplitter 一刀切"）

固定 900 字窗口的问题：切断标题与正文（检索命中的片段不知道自己属于哪一节）、
拆散表格（表头与数据行分离）、切开的片段缺少上下文（"6,464.51 万元"脱离
"2016 年度军用领域收入"就失去意义）。

### 3.2 标题层级分块 + 父子块（`src/chunker.py`）

```
条目流 ──按 text_level 切"节"（维护 heading_path 标题栈）──► section
                                                              │
        ┌─────────────────────────────────────────────────────┤
        │                                                     │
    正文段落按句子边界贪心打包                          表格/公式/图片
    （300–450 字/块，不切断句子）                        （独立成块，不拆分）
        │                                                     │
        ▼                                                     ▼
     子块（检索/向量化单位）                              独立块（block_type 标注）
        └──────────────┬──────────────────────────────────────┘
                       ▼
              父块 = 整节文本（≤1800 字，送 LLM 的上下文单位）
              子块 payload 携带 parent_id / parent_text / parent_page_idx
```

**为什么要父子块**：小块（300–450 字）语义集中，向量检索命中率高；
但小块缺上下文，直接送 LLM 会导致回答片面。检索命中子块后，按 `parent_id`
去重展开为父块（整节），既精确又完整。

**参数与理由**：

| 参数 | 值 | 理由 |
| --- | --- | --- |
| CHILD_MIN_CHARS / MAX | 300 / 450 | bge-m3 在 300–450 字片段上语义聚焦；再大则主题混杂，再小则上下文不足 |
| PARENT_MAX_CHARS | 1800 | 送 LLM 的上下文预算与 fetch 成本平衡（约 1200 token） |
| TABLE_MAX_CHARS | 3000 | 表格整块不拆；超长时保留头尾并标注省略 |
| SECTION_MIN_CHARS | 80 | 过短小节并入相邻，避免碎片化 |

**元数据（全部写入 Qdrant payload）**：
`text / page_idx / heading_path / source / block_type / parent_id / parent_text / parent_page_idx / chunk_id / seq`
—— 满足工单"每个 chunk 必须保留元数据"要求，并支撑过滤、引用与去重。

**实测（548 页，MinerU 3.4.5 解析产物）**：`content_list` 条目 5,998
（text 3,805 / table 502 / header 1,092 / page_number 534 / image 52 / chart 2 …，
其中 header 与 page_number 等版面噪声在归一化时丢弃）→
**chunks 1,812**（文本 1,369 + 表格 389 + 图片 54），父块 1,137，平均 257 字。
表格块由 MinerU 的 HTML 结构转为紧凑 Markdown（字符数约降 60%）。

### 3.3 与工单 01 的分块对比

| 维度 | 工单 01 | 工单 02 |
| --- | --- | --- |
| 切分依据 | 固定字符窗口 + 重叠 | 标题层级（#~###### 语义）+ 句子边界 |
| 表格 | 并入正文流（或独立但无父子） | 独立块，不拆分，带 caption |
| 上下文 | 无（命中片段即送入） | 子块检索 → 父块上下文（去重 + 裁剪） |
| 元数据 | text/page_idx/source/heading_path | 上述 + block_type/parent_id/parent_text/parent_page_idx/seq |

## 四、检索层优化

### 4.1 混合检索（`src/retriever.py`）

- **向量**：bge-m3 稠密向量，Qdrant `query_points` cosine，top-30；
- **稀疏**：BM25（jieba 分词 + 领域保护词：注册资本/法定代表人/军用领域…），top-30；
- **融合**：RRF（Reciprocal Rank Fusion，k=60），只依赖名次，无需量纲归一化。

### 4.2 多路召回（查询改写驱动）

查询改写（`src/query_rewrite.py`）产出多路查询：
- `resolved`（消歧后主查询）——指代词还原（"该公司"→公司全称）；
- `expansions`（同义/领域扩展）——如"军用领域"→"军用领域 收入 / 军工 收入"；
- `sub_questions`（子问题）——仅当出现多个独立疑问结构时分解。

各路检索结果统一 RRF 融合（`search_multi`），避免单一表述漏召回。

### 4.3 查询改写细节（规则优先，零额外延迟）

| 能力 | 实现 | 示例 |
| --- | --- | --- |
| 意图识别 | 关键词规则 → numeric / list / fact / compare | "…比重分别是多少" → numeric |
| 消歧 | 指代词替换 + 空白规整 | "该公司的注册资本" → "武汉兴图新科电子股份有限公司的注册资本" |
| 分解与抽象 | 多疑问结构检测（避免过度分解："分别"指多年份不拆） | "制定了哪个标准？由谁牵头？" → 2 个子问题 |
| 扩展 | 领域同义表（10+ 条目，可扩展） | "上游" → "上游 行业 企业 / 电子元器件 金属壳体" |
| **核心查询（去实体）** | 剥离公司全称/简称等**零信息量实体**，生成独立检索路 | "武汉兴图新科电子股份有限公司的主要产品包括哪些？" → "主要产品包括哪些？" |

> **核心查询的必要性（本机实测案例）**：问"…的主要产品包括哪些？"时，19 字的公司
> 全称淹没了真正的信息需求——向量与 BM25 都被"提及公司名"的块主导（封面标题、
> 释义表、声明页），系统答"根据已有资料无法确定"。加入去实体的核心查询后，
> 正确片段（含"主要产品包括视频指挥控制系统、视频预警控制系统…"）进入 top-k，
> 系统正确作答。知识库只收录单一公司文档时，公司名是纯噪声。

延迟考量：规则版分析耗时 <1 ms；LLM 改写默认关闭（配置项保留），
避免与 ≤3 秒的响应预算冲突。

### 4.4 精排（`src/reranker.py`）

- bge-reranker-v2-m3 cross-encoder（`D:\model\reranker`，本地，`local_files_only`）；
- 输入 RRF 融合后的 top-20 子块，输出 top-6；
- 容错：模型不可用时退化为按召回顺序截断（不中断问答）；
- 平局裁决：分数差 <0.01 时按融合名次裁决（避免精排噪声打乱稳定排序）。

### 4.5 上下文压缩（`src/context.py`）

1. **去重**：同一 `parent_id` 命中的多个子块只保留一份父块；
2. **裁剪**：父块以命中子块为锚点裁剪到 1200 字（句子边界优先）；
3. **预算**：全部片段总长 ≤3200 字，按最佳名次装填；
4. **结构化**：输出带【片段N】+ 页码 + 标题路径，供 LLM 生成 [n] 引用。

### 4.6 生成与引用（`src/rag.py`）

- 提示词（中英双语）：只依据片段作答；数字/名称**逐字一致**；末尾标注 [n]；
  资料不足时明确说"无法确定"；
- 引用抽取：答案中的 [n] → 映射为 {页码, 标题路径}，界面展示；
- 降级：LLM 不可用/超时 → 抽取式答案（直接给最相关片段与页码），不返回空白。

## 五、性能设计（响应 ≤3 秒）

| 手段 | 说明 |
| --- | --- |
| 预热 | 启动即加载 embedding / reranker / BM25 索引，Ollama `keep_alive=30m` 常驻显存 |
| 单次编码 | query 只编码一次（多路召回共享向量） |
| 规则改写 | 查询理解零额外 LLM 调用 |
| 缓存 | 答案 LRU（128）+ 查询分析 LRU（256），重复问题直接命中 |
| 并行 | 稠密/稀疏检索彼此独立，RRF 在名次层面融合 |
| 流式 | 界面支持流式输出；报告同时给出总耗时与首 token 耗时（TTFT） |
| 降级 | 任何环节失败都有确定性的兜底路径，不出现长时间阻塞 |

## 七、取舍与替代方案说明

| 决策 | 选择 | 被否方案及原因 |
| --- | --- | --- |
| 解析器 | PyMuPDF 增强（MinerU 路径保留） | MinerU pipeline（缺权重且禁下载）；MinerU VLM（单页 >1h，不可行）——两者均附实测证据 |
| 向量库 | qdrant-client 本地模式 | Docker 部署 qdrant/qdrant（本机无 Docker；本地模式同 API，`QDRANT_MODE=server` 一键切换） |
| 查询改写 | 规则优先，LLM 可选 | 全 LLM 改写（延迟不可控，破坏 ≤3s 预算） |
| 分块 | 标题层级 + 父子块 | 纯 token 窗口（工单明确禁用）；纯语义分块（Embedding 聚类成本高且不可解释） |
| 评估裁判 | 本地 qwen2.5:3b | 外部 API（离线约束 + 成本） |
