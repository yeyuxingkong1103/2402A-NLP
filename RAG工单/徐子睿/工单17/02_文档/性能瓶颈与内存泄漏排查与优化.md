# API 服务并发瓶颈与资源泄漏：排查与优化

> 工单：人工智能NLP-RAG-解决API服务并发瓶颈与资源泄漏（工单 17，V1.1-20260123）
> 依据源码：`D:\_RAG新工单素材\ragflow-main`
> 说明：本文给出**排查方法论 + 可疑点定位（附代码位点）+ 优化方案**；实测数值需在真实 RAGFlow 实例回填（见 `03_演示与结果/压测基准报告.md`）。

---

## 1. 症状与假设

| 症状 | 工单给出的根因假设 |
|---|---|
| 响应 2s → >10s | **瓶颈一**：每请求重复初始化重量级组件（DeepDoc 解析器 / VLM / 重排模型）→ 并发争用 + 初始化延迟 |
| 内存随时间增长 → OOM | **瓶颈二**：耗时操作无异步队列/限流 → 请求堆积线程阻塞；**泄漏点一**：全局缓存/会话中间对象未释放；**泄漏点二**：DB/向量库连接池未归还 |
| 纯文本问答也占大量显存 | 模型/张量未复用或未释放（keep_alive、随机初始化） |

## 2. 任务二的排查路径（可执行）

### 2.1 CPU 热点（`py-spy`）
```bash
bash 01_代码/py_spy_profile.sh <API_SERVER_PID> 30    # 出火焰图 profile.svg
```
- **重点看**：并发时是否出现 `PdfParser()` / `LLMBundle(...)` / `Rerank` 的 **`__init__` 大量自底向上耗时**（重复初始化）；
- 若热点集中在 `rag/nlp/search.py` 的网络/序列化，则瓶颈在检索链路。

### 2.2 内存对象留存（`memory_profiler` / `objgraph`）
```bash
python 01_代码/memory_probe.py --pid <PID> --minutes 30 --out mem.csv
# 结合 tracemalloc / objgraph.show_most_common_types() 看 Top 对象
```
- **重点看**：`RSS` 曲线是否**单调上升**（泄漏特征）；`objgraph` 里 `ndarray`/`dict`/`LLMBundle` 数量是否随请求数线性增长。

### 2.3 系统资源
```bash
docker stats                         # 容器内存/CPU
nvidia-smi dmon                      # GPU 显存随时间
redis-cli INFO stats | grep -E "pending|instantaneous"   # 队列堆积
redis-cli XINFO GROUPS rag_flow_svr_queue               # 消费组 lag（未 ACK 数）
```
- 若 `XINFO` 的 `pending`（未 ACK）持续增长 → **Task Executor 消费不及/卡住**，解析任务堆积。

### 2.4 代码静态审查（工单点名模块）
| 模块 | 位置 | 看什么 |
|---|---|---|
| 请求处理入口 | `api/apps/*`（`document_app.py` / `sdk`） | 是否在请求线程内**同步触发解析** |
| 模型单例管理 | `api/db/services/dialog_service.py :: get_models()` | `LLMBundle(...)` 是否**每请求新建**（embd/chat/**rerank**/tts） |
| 解析器调用上下文 | `rag/svr/task_executor.py :: build_chunks` | 解析是否只在 **Task Executor** 进程（而非 API 进程）发生 |
| 连接池 | `rag/utils/redis_conn.py`、DocStore 连接 | 是否进程级单例、有无请求内 new/close |

## 3. 任务三的优化方案

### 3.1 资源池化 + 单例（修复「瓶颈一」）
- 把 **解析器 / 重排模型 / embedding 模型** 改为**进程内单例**（`01_代码/singleton_patch.py`）：
  ```python
  rerank_mdl = get_rerank_model(LLMBundle, tenant_id, rerank_id)   # 命中缓存则复用
  ```
- 确保 **ES / Redis / MinIO 客户端为进程级单例**，请求结束**不 close**（RAGFlow 的 `settings.docStoreConn`、`REDIS_CONN` 本就是模块级单例——排查重点是**别在请求路径里重复 new client**）。

### 3.2 请求处理链路优化（修复「瓶颈二」）
- **解析异步化**：上传/解析接口只做「入库 + `queue_tasks` 投 Redis」**立即返回**，真正解析由 Task Executor 消费（RAGFlow 既有设计；确认没有反向同步调用）；
- **检索+生成限流**：对耗时的检索调用用 `asyncio.Semaphore` 限流（`RequestLimiter`），或用内存队列 + 工作线程池，避免线程堆积；
- **asyncio 化 I/O**：把同步阻塞的检索/网络调用放进 `asyncio.to_thread` / `run_in_executor`，释放事件循环。

### 3.3 泄漏修复（修复两处泄漏点）
- **全局缓存/会话**：对解析中间对象、图像 Base64、会话上下文显式 `del` + 定期 GC（`gc.collect()`）；给缓存加 **TTL / 容量上限（LRU）**；
- **连接池**：确认 DocStore/Redis 客户端复用且不泄漏；对请求级资源用 `try/finally` 归还。

### 3.4 可观测性（Prometheus + Grafana）
- 埋点：请求时延直方图、in-flight、队列 pending、RSS、GPU 显存（`01_代码/prometheus_metrics.py`）；
- Grafana 面板用于**演示优化前后资源曲线对比**。
