## 0. 工单范围（先说清楚做什么、不做什么）

**做**（工单九点名的五件事）：
1. 在 08 工单已建的 GraphRAG 服务与检索结果之上做**优化**，不重写 08；
2. 从 **prompt 构建实体关系 / 检索 / 生成 / 评估** 四层优化；
3. 用 **RAGAS** 评估 `context_precision ≥ 0.8`、`context_recall ≥ 0.9`；
4. **响应时间 ≤ 3 秒**、容错降级、长时运行稳定、中英文问答；
5. 交付优化方案 + 演示视频脚本 + 优化思路视频脚本（含优化前后指标对比）。

**不做**（工单九未要求，一律不实现）：
用户登录/权限/后台管理/可视化大屏/监控告警/模型训练微调/多租户/K8s/支付/工单管理/复杂运维平台；
不替换指定技术选型；不引入 Neo4j 等未指定图数据库（**图存储用 NetworkX + JSON**）。

**与 08 的边界（关键设计约束）**：工单九**不修改、不重写** 08 的任何一行代码，只以
`import 工单八.app.*` 的方式**复用**其服务与索引（`工单八/app/rag_core.py`、`ingest.py`、`evaluate.py`，
Milvus 集合 `gd8_chunks`）。这样 before/after 的差异**只可能来自优化本身**，不来自语料或分块器的漂移。

## 2. 目标与验收口径

| 验收项 | 目标 | 测量方式 | 口径说明 |
|---|---|---|---|
| `context_precision` | **≥ 0.8** | RAGAS `LLMContextPrecisionWithReference` | 每题单跑，上报有效样本数；nan 记 None 不入均值 |
| `context_recall` | **≥ 0.9** | RAGAS `LLMContextRecall` | 同上 |
| 响应时间 | **≤ 3 秒** | `answer()["latency_ms"]` 端到端 | p50/p95 同时报；超预算走降级而非超时 |
| 稳定性 | 长时运行不退化 | 连续 N 轮问答 + Redis 缓存命中率 | 缓存键带结构指纹，改动即失效 |
| 容错 | 4 类异常可处理 | 见 §6.4 异常矩阵 | 每类都有停机实测用例 |
| 中英文 | 双向可问答 | 同一问题的中英两问 | 生成层按问题语言自适应 |

**对照基准（before）**：**同一批 3 个问题**跑 **08 原链路**（`工单八.app.rag_core.answer(mode="graph")`）。
不引用 08 归档的旧数字——08 归档用的是它自己的 10 题，题不同则指标不可比。
**这是本单唯一诚实的 before 口径**：同语料、同问题、只有链路不同。

> ⚠ **阻塞项（已在报告中标红）**：题集真源 `data/sample_questions.pdf` 由工单附件提供，
> **当前尚未放入项目**。按工单九第三步明文要求「如果 sample_questions.pdf 不存在，先提示放置，**不要自己编造参考答案**」，

## 5. 四层优化技术方案

### 5.1 第一层：prompt 构建实体、关系层面（`graph_rag.py::EXTRACT_SYS`）

**08 的痛点**：08 的 LLM 抽取 prompt 未把"金融本体"约束死，实测把 `13.22%`、`2019年` 这类**数值/日期当实体**返回，
只能靠 `NONENTITY` 正则事后补救；也未强制要求 evidence，抽出的边无法回溯到原文。

**工单九的优化**（改动集中在抽取 prompt，不改 08 代码）：

| 项 | 08 | 工单九 |
|---|---|---|
| 类型词表 | 开放 | **闭合枚举**：实体 ∈ {公司,人物,指标,机构,产品}；关系 ∈ {任职,披露指标,持股,子公司,合作,监管} |
| 数值日期 | 事后正则过滤 | **prompt 前端禁止**："禁止把纯数值、百分比、日期当作实体" |
| 证据 | 无 | **强制 `evidence`**：每个关系必须给原文短句，便于人工抽查与引用溯源 |
| 输出格式 | 自由文本 | **强制 JSON 单对象**，便于 `json.loads` 直接入库，解析失败可重试 |

> 该 prompt 同时用于：① 新增文档的增量抽取；② `/graph` 演示接口的"贴文本建图"。

### 5.2 第二层：检索层面（`retrieval.py`）

按 P2（重排器吃掉融合权重）的实测教训，**调整顺序是：先重排候选数，再融合权重**。

| 旋钮 | 08 | 工单九 | 依据 |
|---|---|---|---|
| 融合候选 `FUSION_K` | 30 | **40** | 多留候选给重排裁，精排器有更大选择空间 |
| 重排后喂模型 `RERANK_N` | 8 | **6** | `context_precision` 的分母就是喂进模型（并被 RAGAS 计为 contexts）的片段数，**降 N 是提精度最直接的手段** |
| 融合权重 `VEC_W/BM25_W` | 0.7 / 0.3 | **0.6 / 0.4** | 数值型/表格型问题靠关键词命中更稳；且先归一化后加权，弱权通道不被架空 |
| 图扩展跳数 `HOPS` | 1 | **2** | 治 P4 多期聚合类召回短板的直接手段 |
| 扩展词注入数 `EXPAND_TERMS` | 6 | **8** | 同上 |
| **社区摘要通道** | 无 | **新增** | GraphRAG 的 global search：命中实体所属社区的结构化摘要作为补充上下文 |
| 图约束 | 唯一公司时 code 硬过滤 | **沿用**（08 已验证有效） | 记忆 [[group-report-subsidiary-name-collision]] 实测能提到 1.00 |

**融合公式**（与 08 同构，仅参数重标定）：

```
∀h ∈ 通道c:  n_h = (s_h - min_c) / (max_c - min_c)         # 通道内 min-max 归一化
score(h) = VEC_W · n_h(向量通道) + BM25_W · n_h(BM25通道)   # 两通道命中则两项相加
```

### 5.3 第三层：生成层面（`retrieval.py::generate_after`）

| 项 | 08 | 工单九 |
|---|---|---|
| 结构 | 一段话 + 句末来源 | **结论 → 证据 → 来源** 三段式，便于人工核验与演示 |
| 无答案 | "年报中未提及" | 沿用（这是防幻觉的关键约束，不改） |
| 语言 | 中文 | **按问题语言自适应**（中文问中文答 / 英文问英文答） |
| 时序 | 检索超预算降级 | 沿用 3 秒预算 + **生成异常同一降级形态** |
| 客户端 | 08 已做单例 + `max_retries=0` | 复用（每请求新建会多付约 1s TLS） |

### 5.4 第四层：评估层面（`eval_ragas.py`）

| 项 | 08 | 工单九 |
|---|---|---|
| 指标集合 | 四指标混跑 | **只跑工单点名的两项**（precision/recall），省时省钱，且避免混跑触发限流 |
| 跑法 | 逐指标串行（08 已修） | 沿用逐指标串行 |
| 有效样本 | 上报 | 沿用，且 **nan 记 None 不入均值** |
| 噪声底 | 有 `measure_noise.py` | **沿用口径**：比较任何指标前先量噪声底（±0.05） |
| 题集 | 08 的 10 题 | **工单附件 3 题（sample_questions.pdf）** |
| before 口径 | 08 自报 | **同一 3 题跑 08 原链路重算**（题不同则不可比） |
| 文本归一化 | 去空格去千分位 | 沿用（PDF 会在中文词间插空格，不去会得假阴性） |

## 6. 关键设计细节

### 6.1 实体关系抽取 prompt（全文，即 `graph_rag.py` 中的 `EXTRACT_SYS`）

```
你是金融知识图谱抽取器。从给定年报片段中抽取实体与关系，只输出 JSON，不要解释。
实体类型限定：公司/人物/指标/机构/产品；关系类型限定：任职/披露指标/持股/子公司/合作/监管。
禁止把纯数值、百分比、日期当作实体；每个关系必须给出 evidence（原文短句）。
输出格式：{"entities":[{"name":"","type":""}],"relations":[{"head":"","rel":"","tail":"","evidence":""}]}
```

**为什么这样写**（每条约束都对应一个实测踩过的坑）：
- 「只输出 JSON」→ 08 时期自由文本需要正则凑合解析，格式漂移就整批入库失败；
- 「类型限定」→ 08 抽出 `类型:实体` 这种兜底类目占 55/320，本体不闭合则社区摘要无法按类型组织；
- 「禁止数值/日期」→ 对应 08 的 `NONENTITY` 补丁，把过滤前移到 prompt；
- 「必须有 evidence」→ 让每条边可回溯到原文，是 `/graph` 演示与人工抽查的前提。

### 6.2 检索融合方案

已在 §5.2 给出公式。补充两条实现约束：
1. **两通道都必须下推图约束**。08 的注释已实测：只锁向量通道时，BM25 仍会把别家公司的片段放进来，"锁到目标公司"名存实亡。
2. **图约束只在"唯一语料公司"时启用**。多公司对比题（如"平安银行和中国平安的净利润分别是多少"）加 code 过滤会误杀另一家——
   这与 08 的既定结论一致，本单沿用该开关与前提。

### 6.3 生成层方案

见 §5.3。核心是**引用可核验**：每段上下文在 prompt 里带 `【片段i｜公司+年度年报 第X页】`，
要求生成答案句末标 `【来源：公司 第X页】`，人工可逐句对照原文。

### 6.4 容错矩阵（工单九"能处理常见异常"的落地口径）

| # | 异常 | 处理策略 | 验证方式 |
|---|---|---|---|
| E1 | 用户输入错误（空串 / 超长 / 注入型提示） | Pydantic `min_length=1, max_length=500` 直接 422；生成层 system 约束抗提示注入 | 传空串与 600 字超长串，断言 422 |
| E2 | 文档解析失败（PDF 损坏 / 无文本层） | MinerU → pdfplumber → pymupdf 三级降级，逐级打印失败原因；全失败抛明确异常并提示把文件放到 `data/` | 传一个非 PDF 文件，断言抛 `RuntimeError` 且信息可读 |
| E3 | 大模型超时 / 402 余额不足 | `try/except` 捕获 → 同一降级形态（返回检索原文），HTTP 仍 200 | 停机实测：把 Key 改错后仍能返回检索原文 |
| E4 | Redis 不可用 | 读写都 `try/except`：读失败当未命中，写失败只打印不抛 | 停 Redis 后问答仍成功 |

> 纪律（`../CLAUDE.md` 第二条）：**每条降级路径都要停机实测**，不能只在代码里"看起来有"。
> 记忆 [[fault-paths-must-be-tested-by-breaking]] 记录过"声称的降级路径实测是假的"——本单的 E3/E4 必须真停机跑一遍。

### 6.5 稳定性与 3 秒预算

- **超时右界**：`DEADLINE_S=3.0`。检索阶段已耗时超预算 → 直接降级，不再赌一次大模型调用（长尾封顶）。
- **缓存**：Redis `TTL=86400`，键含**源码结构指纹**（模块字节哈希 + 索引/图谱 mtime），改动即失效，
  避免旧缓存静默吞掉新字段（记忆 [[cache-key-needs-schema-version]]）。
- **单例**：DeepSeek 客户端、向量模型、重排模型进程内只建一次（08 已实现，本单复用）。
- **资源**：GPU 仅 8G，重任务（建图 / RAGAS）**串行**，不同时跑。
