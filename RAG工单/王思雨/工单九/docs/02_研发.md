## 2. 模块职责与复用边界（本单**不重写 08**）

| 本单模块 | 做什么 | 复用 08 的什么 |
|---|---|---|
| `config.py` | 读本单 .env；把工单要求的 `BGE_M3_PATH`/`BGE_RERANKER_PATH` 映射到实际路径 | `工单八.app.config`（Milvus 集合、Redis、LLM 凭据、全部阈值） |
| `graph_rag.py` | NetworkX 图、社区摘要、实体链接、邻域扩展、LLM 三元组抽取 | `工单八.data/graph.json`（08 的抽取结果，**不重复调大模型**）、`rag_core.llm` |
| `retrieval.py` | after 链路（图扩展 2 跳 + 社区摘要 + 重标定融合/重排）、before 链路转发 | `rag_core.vector_search / bm25_search / rerank / embed / llm / rds / _fp` |
| `eval_ragas.py` | 题集解析、逐指标 RAGAS、对比表 | `工单八.app.ingest.parse_mineru / parse_pymupdf`、`工单八.app.evaluate._judge / _emb` |
| `main.py` | HTTP 分发 | `rag_core.milvus / rds`（健康探测） |

**为什么不重写**：工单九的靶心是"在 08 的服务与检索结果上做优化"。
复用保证 before/after 的差异**只可能来自优化本身**，而不来自语料、分块器或模型加载方式的漂移——
否则指标变化无法归因。这是本次对比能站得住的前提。

## 4. 开发期自检抓出的缺陷（全部已修复，且都做了实测复验）

> 依据 `../CLAUDE.md` 第二条：自造的任何产物进评估前，先过"已知正例全过 + 已知反例全拦"的自检。
> 下面 7 个缺陷**没有一个是靠读代码看出来的**，都是跑起来才暴露的（D1~D5 在附件到位前，D6/D7 在附件到位后）。

| # | 缺陷 | 怎么被抓到 | 后果（若不修） | 修法与复验 |
|---|---|---|---|---|
| D1 | 挂载 `/` 要求 `frontend/` 目录必须存在 | 首次 `import app.main` 直接抛 `RuntimeError` | 服务起不来 | 补齐 `frontend/`（index.html + app.js + vue 运行时）；复验：模块导入 OK、`/` 返回页面 |
| D2 | **2 跳图扩展把同业公司拉进 `codes`** | 打印 `graph.codes` 发现恒为空 | 「唯一公司才硬约束」**永不触发**，图约束名存实亡（08 花大力气治的同名混淆会复发） | 改为**只从"命中实体"收集代码**；复验：单公司问题 `codes=['000001']`，多公司对比题 `codes=[]`（设计如此） |
| D3 | **冷启动模型加载吃掉 3 秒预算** | 首个 `/ask` 实测 45 秒且走降级 | 首次访问体验崩坏，且 3 秒指标无法解释 | 在 `/health` 预热 embed + rerank；复验：预热 18.3s 后 `models=warm`，业务请求 p50=1775ms |
| D4 | `data/` 不存在 → 上传保存抛 `FileNotFoundError` | 容错 E2 实测返回 500「保存上传文件失败」 | 上传功能直接不可用，且错误信息误导 | 保存前 `mkdir(parents=True, exist_ok=True)`；复验：非 PDF 上传返回 HTTP 400 +「三级解析器均失败…」 |
| D5 | （环境，非代码）**残留 python 进程占满显存** → `rerank` 耗时 42 秒 | 单测 `rerank(40 候选)` 用时 42.6s，与线上 0.7s 矛盾 | 会误判成"代码性能问题"并做错误优化 | 查出 3 个残留 PID 占 5551/8188 MiB；清理后 `rerank(40)=0.74s`。**记入纪律：重任务必须串行，测完必须杀进程** |
| **D6** | **附件把汉字输出成康熙部首**（`银⾏`/`⻛险`），且题目标记「`问题：`」**无编号** | 附件到位后首次解析：**切出 0 题**（原正则要求 `问题\s*(\d+)`） | 不修则题集永远解析不出来；**即使侥幸解析出来，`银行`≠`银⾏` 会让 BM25 与实体链接整体落空且不报错** | ①正则改为匹配无编号的「`问题：`…`参考答案：`」；②加 `C.fix()`：`NFKC` 修 23 种康熙部首，手工补 NFKC 管不到的 2 种（`⻛`→风、`⻓`→长）；复验：**4 题全部切出**，题面已正常显示为"银行/风险" |
| **D7** | **before/after 时延不可比**：`for which in ("before","after")` 让 before 先跑、独自承担冷启动 | 首次正式评估：before 的 Q01 被记成 **18276 ms**，after 只 2788 ms | 会得出"after 比 before 快 6 倍"的**完全错误**结论 | 在两条链路开跑前先 `retrieve_after("预热")`；复验：改为预热后重跑，两边量级一致 |

**D6 与 D7 是附件到位后才暴露的**，且都属于"不报错、只体现在结果里"的静默失效：
D6 是数据层（字形/版式），D7 是测量层（冷启动归因）。**两者都无法靠读代码发现。**

**D2 与 D3 是本次最重要的两个修复**：前者是"看起来有、实际不生效"的静默失效（正是 08 记忆里
`fault-paths-must-be-tested-by-breaking` 记录过的那类），后者是"指标无法解释"的体验缺陷。
两者都不是靠读代码能发现的。

## 6. 跨工单教训（沉淀给 RAG 系列后续工单）

> 下面 4 条是本单产出的、**不限于本单**的教训，已回写进系列记忆。它们的共同点：
> **不报错、只体现在数字里**，因此读代码看不见，只能靠"真跑 + 打印中间量"抓。

| # | 教训 | 为什么危险 | 复现/验证方式 |
|---|---|---|---|
| **L1** | **图约束的触发条件会被扩展深度静默破坏** | "命中唯一公司才硬过滤"若把扩展邻居也计入公司代码，跳数一加深，`len(codes)==1` 就**永不成立** → 约束静默失效，08 治过的同名实体混淆会复发 | 分别打印「命中实体」「`codes` 取值」「注入 BM25 的扩展词」三者；改跳数后必须重验约束是否仍触发 |
| **L2** | **PDF 会把汉字渲染成康熙部首**（`银⾏`/`⻛险`/`⾦融`，U+2E80–U+2FDF） | `银行 ≠ 银⾏` ⇒ BM25 分词、图谱实体链接、关键词核验**整体落空且不抛异常** | 拿到新 PDF 先扫字符区间：`{c for c in text if 0x2E80<=ord(c)<=0x2FDF}`。NFKC 修 23 种，**CJK 部首补充区的 `⻛`/`⻓` 须手工补**；归一化要同时施加在语料侧与查询侧 |
| **L3** | **基准对比里的冷启动归因错误** | `for x in ("before","after")` 这种顺序执行会让**先跑的一方独自承担模型冷加载**（实测 18276 ms vs 2788 ms），直接得出"快 6 倍"的错误结论 | 任何 A/B 时延对比，**开跑前先预热**；比较前先看数字量级是否荒诞 |
| **L4** | **GPU 性能数字先看显存** | 残留进程占着显存会让同一函数慢几十倍（rerank 0.74 s → 42.6 s），极易误判成代码性能问题 | 采信任何 GPU 数字前先 `nvidia-smi`；Git Bash 的 `pkill` 杀不掉 Windows 原生进程，要 `taskkill //F //PID` |
