> 工单编号：**人工智能NLP-RAG-PDF文档的表格解析及检索优化**（工单03）
> 工单编号：**人工智能NLP-RAG-图像内容解析及检索优化**（工单04）
> 工单编号：**人工智能NLP-RAG-Query 理解优化任务**（工单05）

> 项目：八维 NLP-RAG 项目（共 18 份工单，本仓库覆盖工单 01–07）

针对两份招股意向书 + **ccf_competition 的 9 份上市公司年报**（共 11 份 PDF / 3710 页）
的 RAG 问答系统：
PDF 文字+表格解析 → **图表/结构图多模态转写（入库期）** → 句子边界分块 → 去重 →
bge-m3 向量化 → Milvus 检索 → **实体路由** → 同事实聚合 + 邻块扩展 →
qwen3:8b 流式生成 → 三轨评估；**多轮对话（指代消解 / 省略补全）**；
**三种可配置检索模式（向量 / 全文 / 混合）+ 可插拔重排器**。

## 快速开始

```bash
# 0. 环境自检（第一道拦截，必须先跑；共 34 项，含工单05 的第 9 节 —— 该项全离线）
$PY scripts/preflight.py

# 0b. 多模态模型（工单04，一次性）
ollama pull qwen2.5vl:3b

# 1. 启动向量库（Milvus Standalone + Attu）
docker compose -f docker-compose.milvus.yml up -d
#    Attu 可视化： http://localhost:8000

# 2. 图像转写作业台（工单04，**不碰 Milvus**，可反复跑）
$PY scripts/transcribe_images.py --run    # 跑 VLM（缓存命中的会跳过）
$PY scripts/transcribe_images.py --list   # 一览：页/类型/题注/是否已人工核对

# 3. 入库（图像解析随流水线自动发生）
$PY scripts/ingest_all.py                 # ★ 工单03/04：把已配置的两份 PDF 都灌进去
$PY scripts/ingest_all.py --status        #    只看库里有哪些文档
#    旧的单文档入口仍在（只灌书1）：$PY scripts/ingest.py

# 4. 起服务（注意 8080 —— Attu 占着 8000）
$PY -m uvicorn app.main:app --host 0.0.0.0 --port 8080
#    问答界面： http://localhost:8080  ——「问答」页是单轮，「多轮对话」页是工单05
#    想演示会话 TTL 过期：SESSION_TTL_SECONDS=20 $PY -m uvicorn app.main:app --port 8080

# 5. 评估（题库 16 题：10 道书1 + 4 道书2 + 2 道图题）
$PY scripts/eval.py --profile optimized   # ★ 工单04：16 题口径
$PY scripts/eval.py --compare all         # 工单02：三剖面横向对比

# 5b. 多轮评测（工单05：5 轮剧本 + 4 组扩充用例）
$PY scripts/eval_multiturn.py             # ★ 工单05 核心产出
$PY scripts/eval_multiturn.py --scripts WO05-main    # 只跑工单原文 5 轮
$PY scripts/eval_multiturn.py --via-api http://localhost:8080  # 走 HTTP 冒烟

# 6. 工单02 专项实验
$PY scripts/chunker_ablation.py           # 分块层对照（离线，不需要向量库）
$PY scripts/sweep.py                      # 检索参数扫描（两阶段）

# 6b. 工单06 专项
$PY scripts/rebuild_sparse.py             # ★ TF → TF-IDF 稀疏向量回写（原生混合检索前置）
$PY scripts/eval.py --profile hybrid      # 混合检索（RRF 投票融合）
$PY scripts/eval.py --profile fulltext    # 纯全文检索
$PY scripts/sweep_fusion.py               # 融合权重扫描（阶段一不调 LLM）

# 6c. 工单07 专项（ccf_competition 的 9 份年报）
$PY scripts/verify_ccf_profiles.py        # ★ 9 份年报的页码/页眉配置复核（4 条判据，全量约 8 分钟）
IMAGE_ENABLE=false $PY scripts/ingest_all.py --ccf   # 只灌这 9 份（不碰两份招股书）
$PY scripts/lookup_ccf.py "逾越者联盟"      # ★ 出题取证：短语 → 文档 + 印刷页码 + 原文
$PY scripts/eval.py --questions eval/wo07_questions.json --compare optimized,hybrid
$PY scripts/diagnose_wo07.py --json eval报告/工单07-检索问题归因-optimized.json

# 7. 测试
$PY -m pytest tests/ -v                   # 148 passed（工单05/06 新增 86，工单07 新增 4）
```

（`$PY` = `~/rag-data/venv/bin/python`，数据与 venv 都在 WSL 原生盘，避开 `/mnt/c` 的 9p 慢速。）

## 三种检索模式实测（工单06 核心产出）

`$PY scripts/eval.py --compare optimized,hybrid,fulltext`，
报告 `~/rag-data/eval/eval-20261004-203814-*.json`（本目录 `eval报告/` 下附存档）：

| 剖面 | 规则命中（准确率） | CKC | **要点召回** | **要点全覆盖** | 上下文 | TTFT-P50 | ≤3s |
|---|---|---|---|---|---|---|---|
| `optimized` 向量检索 | 16/16 | 89.2% | 97.9% | 15/16 | 2055 | 1792ms | 16/16 |
| **`hybrid` 混合检索** | **16/16** | **93.8%** | **100.0%** | **16/16** | 2113 | 2132ms | 14/16 |
| `fulltext` 全文检索 | 10/16 | 64.6% | 70.8% | 11/16 | 1695 | 1514ms | 15/16 |

**工单目标**：准确率 ≥90% → **16/16 = 100%** ✅；召回率 ≥95% → **100.0%** ✅。

- 混合检索的增益在**召回**：要点召回 97.9% → **100%**、CKC 89.2% → **93.8%**，
  而上下文只多 58 字（**不是靠堆上下文换的**）。页级召回几乎不动 —— 与工单02
  「页级指标推不动」的结论一致。
- **纯全文检索单独用是弱的**（10/16）：它取 BM25 前 3 块、没有邻块扩展，
  多值题的几个数字散在不同块里。它的价值在于**作为混合检索的一路**。
- 全文本体支持：布尔（`A AND NOT B`）/ 短语（`"军用领域的收入"`，顺序打乱则为空）/
  模糊（`军用领城~` 可命中，但 **`5,530~` 命中不了 `5,520`** —— 数字不做模糊）/
  多字段（`title:募集资金用途`）。

## 工单07 实测（ccf_competition 的 9 份年报）

`$PY scripts/eval.py --questions eval/wo07_questions.json --compare optimized,hybrid`，
报告 `~/rag-data/eval/eval-20261006-211428-*.json`（本目录 `eval报告/` 下附存档）：

| 剖面 | 规则命中 | CKC | 要点召回 | 页精确 | 页召回 | 上下文 | TTFT-P50 | ≤3s |
|---|---|---|---|---|---|---|---|---|
| `optimized` 向量检索 | **5/10** | 69.0% | 69.3% | 13.3% | 43.8% | 2573 | 2281ms | 8/10 |
| `hybrid` 混合检索 | 3/10 | 46.5% | 59.6% | 16.7% | 43.8% | 2551 | 1698ms | 9/10 |

LLM judge：`optimized` 上下文相关性 1.00 / 忠实度 0.98 / 答案相关性 0.95 / 正确性 0.71。
**忠实度 0.98 ⇒ 系统不编造；正确性 0.71 ⇒ 短板在"取证据"，不是"胡说"。**

- **10 题覆盖 9 份年报**（每份至少一题）+ 1 道跨文档综合题；真值全部由
  `scripts/lookup_ccf.py` 回到 PDF 逐条取证，见 `eval/wo07_questions.json`。
- **页码改为「页脚实读优先」**：9 份年报的页脚有 6 种形态，招商银行 / 邮储银行 / 中国太保
  还在「财务报告」节**重新从 1 编号** —— 任何单一偏移都对不上，只能读页脚实际印的那个数。
- **评估器补了一处量纲缺陷**：`543.83亿元` ↔ `54,382,730,241.56元` 原先判成两个无关的数
  （答对判错）；而 `612,265 百万元` 被答成 `612,265 亿元`（差 100 倍）原先却判对。
  现按量纲归一到「元」比较，容差 0.1%，且**只给大数容差**（`1.65` 与 `1.66` 仍严格不等）。
- **问题分析（工单点名）**：把「答不出来」拆成 ①语料缺口 / ②检索侧漏召 / ③生成侧漏答，
  四个根因逐条落到证据（文档标题短语抢占检索位、跨页块页码标错、跨文档张冠李戴、
  top-k 顶不住综合题）。详见 **[`docs/工单07-功能测试及评估.md`](docs/工单07-功能测试及评估.md)** §6。
- **没有回归**：新语料灌进**同一个 `rag_chunks`**（1848 → 8458 行）后，
  招股书那 16 题复跑仍 **16/16**；单测 144 → **148 passed**。

## 关键设计取舍

| 决策 | 选择 | 理由（均为实测） |
|---|---|---|
| 向量库 | **Milvus Standalone** | Lite 不监听端口 → Attu 连不上；且单进程文件锁过不了高并发验收 |
| 分块 | **句子边界优先**（300–600 字） | 固定字数会切断 p128 那句同时装着两道题答案的 137 字金句（离线对照：句边界 10/10 vs 固定 500 字 8/10） |
| 表格 | **`find_tables()` + 表头下推** | 纯文本流抽出的是粘连的 `发行前每股净资产3.55元/股…` |
| 页眉清洗 | **锚定整行模板** | 按关键词删会误伤正文（公司全称在正文反复出现）→ 静默答错 |
| 去重 | **入库只压精确重复；冗余控制放检索时** | 实测"重复段落"chunk 间海明距离 14–34，放宽阈值会误删真实内容 |
| 语音 | **后端 faster-whisper** | Chrome Web Speech 走 Google 服务器，国区不可用且报错误导 |
| 评估 | **自实现三轨** | ragas 走 Ollama 有三个必炸点；规则化数值命中比 LLM 打分更可信 |
| 响应口径 | **TTFT**（并主动披露完整耗时） | 工单写"返回答案的时间"，流式下首 token 即开始返回；**n=10 时 P95 = 最大值，达标看 P50 与「≤3s 的题数」** |
| 同事实聚合 | **句子级 6-gram + 并查集** | 整块 Jaccard 只有 0.055，抓不到"同一句话的三种矛盾说法"；传递闭包必需（316~355=0.48 但都能连到 358） |
| 邻块扩展 | **`chunk_index±1` + 互补性过滤** | 不填 `parent_id`：`section_path` 已编码章节，真填要全量重入库而嵌入无重试 |
| 嵌入放 CPU | **`embed_query_on_cpu=True`** | bge-m3 上 GPU 会挤掉 qwen3，TTFT 从 35ms 劣化到 6117ms |
| 响应缓存 | **放 `api/` 不放 `core/`** | 评测器直接调 core，因此评测天然不吃缓存、TTFT 数字是真的 |
| 多文档分流【工单03】 | **按公司专名硬过滤 `doc_name`** | 两份招股书章节结构雷同（"发行股数"两边都有），排序无法可靠区分；过滤后零召回才回退全库 |
| 文档差异【工单03】 | **收进 `doc_profiles.py`，一份 PDF 一条** | 页眉/页脚/页码格式/专名/证据正则/提示词口径原先散在 6 个文件里写死书1；不配的文档**当场报错**，不静默套用 |
| 提示词口径【工单03】 | **system prompt 按文档拼** | 写死"基于《兴图新科招股意向书》"会让模型对力源的题**系统性拒答**（实测 CKC=100% 却答"未提及"） |
| 表格邻块【工单03】 | **表格邻块不受互补性过滤** | 引子句"拟投资以下项目："与表格被切在相邻两块时，表格不含新查询词会被过滤掉 —— 可答案是它 |
| 图像解析【工单04】 | **多模态模型只在入库期用** | 3B VLM 读一张图 ≈ 2s，放查询期会直接击穿"≤3s"；入库期转写成文字后，问答链路一行没改 |
| 图像解析【工单04】 | **不用 CLIP，用多模态大模型** | CLIP 只给图文相似度、**没有计数能力**（答不了"销售部有几个部门"），且要加一路 CLIP 向量就得重建 schema |
| Query 理解【工单05】 | **规则优先 + LLM 兜底** | 本场景的指代/省略可枚举；规则层 0 ms、可单测、可解释。实测 15 轮**全部规则可解、0 次模型调用** |
| 问点继承【工单05】 | **槽位模板**（`⟦公司⟧法定代表人是谁？`） | `abstract_query` 的残句法会把英文削成 `What is the registered capital of?`（介词悬空）、把「根据…」整个丢掉；槽位模板顺带让英文多轮规则可解 |
| 改写顺序【工单05】 | **先判省略式追问，再判「点名即消解」** | Q4「那力源呢？」**确实点名了公司**；顺序颠倒就会短路成"不改写"，丢掉核心考点 |
| 代词替换【工单05】 | **连后面的「的」一起吃** | 否则与题面差一个字 → 查询串不同 → 排序可能漂移。吃掉后 Q3 改写结果与 id=531 题面**逐字相同** |
| 会话存储【工单05】 | **服务端内存 + TTL + LRU** | 指代消解要的是**结构化状态**（焦点实体 / 问点模板），不是对话文本；不引入 Redis，限度写进文档 |
| history 预算【工单05】 | **与 context 共享 `num_ctx`，超了整轮丢** | 实测 context 最大 2470 字、余量仅约 1000 token；不设闸门时 Ollama **静默截断**（切掉 system/context，接口照常 200） |
| 多轮缓存【工单05】 | **带 `session_id` 完全绕过** | 同一句话在不同上下文下答案不同；且会话答案写进公共缓存会**反向污染**单轮路径的 TTFT |
| 语言指令【工单05】 | **按用户原话判，不按改写后的** | 否则英文提问被改写成中文全称后指令变「请用中文回答」，多语言验收当场挂 |
| VLM 结果可覆写【工单04】 | **`reviewed_text` 优先于 `vlm_text`** | 实测模型把柱状图 `-2.0%` 的归属记错（记成"计算机"，实际是 IC卡），而那道题问的恰恰是它 |
| 转写缓存【工单04】 | **内容寻址**（PNG 字节 + 模型 + 提示词版本） | 全量重建时书2 的 33 张图 **33 次缓存命中 / 0 次 VLM 调用 / 0.6 秒** |

## 环境要求

- WSL2（`/etc/wsl.conf` 需 `systemd=true`）、Python 3.11、Docker
- Windows 侧 Ollama，模型：`qwen3:8b`、`bge-m3`、**`qwen2.5vl:3b`（工单04）**
- `.wslconfig` 建议 `memory=8GB`、`swap=8GB`
- **不需要**设 `OLLAMA_MAX_LOADED_MODELS=2`：嵌入跑在 CPU、不占显存，两个模型本来就并存
  （实测 `基准 39ms → 交替1 40ms → 交替2 46ms`）。只有把 `embed_query_on_cpu` 改成
  `False` 时才需要。
