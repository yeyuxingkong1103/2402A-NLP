# 工单13 RAG性能瓶颈识别与优化｜设计文档
## 1.项目概述
RAG完整链路分为：查询处理与增强、检索阶段、上下文组装与提示工程、LLM生成、后处理响应格式化。
本工单目标：对现有RAG链路做性能埋点、性能分析，定位链路中的性能瓶颈，给出对应的优化方案，采集优化前后耗时做对比。

### RAG全链路阶段
1. 查询处理与增强：query改写、query扩展、query向量化
2. 检索阶段：向量库检索、重排序rerank
3. 上下文组装与提示工程：拼接检索上下文、构建prompt
4. LLM生成：大模型推理生成回答
5. 后处理与响应格式化：结果清洗、输出格式化

## 2.瓶颈识别手段（工单文档要求）
1. **应用级性能分析**：Python cProfile + snakeviz，定位慢函数、慢代码路径
2. **结构化日志埋点**：全链路增加时间戳、request_id，记录每个阶段耗时、检索文档数量、token数量
3. **系统级分析**：Linux perf观察CPU、IO、系统调用
4. **监控指标**：延迟（均值、中位数、P95/P99）、吞吐量、错误率、CPU/内存/GPU/网络磁盘IO
5. **负载测试**：Locust/k6模拟并发请求，压力下暴露瓶颈
6. **组件基准测试**：单独对embedding、向量库、LLM做基准测速

## 3.预期常见RAG性能瓶颈
| 模块 | 可能瓶颈原因 |
|---|---|
| Query向量化 | embedding模型推理速度慢、模型过大 |
| 向量检索 | 向量库索引未优化、top‑k取值过大、向量数量庞大 |
| Rerank重排 | rerank模型推理耗时高 |
| Prompt组装 | 上下文文档过多，prompt token过长 |
| LLM生成 | LLM推理速度慢、网络IO、token输出量大 |
| IO | 磁盘读取、数据库读写、网络请求延迟 |

## 4.优化方向设计
1. Embedding侧：使用更小更快的embedding模型、embedding预计算缓存
2. 向量检索侧：向量库索引调优，合理设置top‑k，开启索引
3. Rerank：可关闭/降级rerank，或者使用轻量rerank模型
4. Prompt：控制上下文长度，做上下文压缩，减少prompt token
5. LLM：调小max_new_tokens，开启流式输出，使用更快推理后端
6. 缓存：对重复query做结果缓存，避免重复检索+推理
