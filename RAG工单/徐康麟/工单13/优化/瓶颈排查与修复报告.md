# 工单13 瓶颈排查与修复报告

**工单编号**：人工智能NLP-RAG 项目-RAG 性能瓶颈识别与优化
**验收标准**：每个会话，用户输入 query 后，返回的检索结果要在 **3S 以内**
**数据来源**：`优化/评估结果/*.jsonl`、`*_汇总.json`、`对比.csv`（**每个数字都可追溯到产物文件**）

---

## 1 结论速览

| 项 | 结论 |
| --- | --- |
| 瓶颈所在 | **阶段④ LLM 生成**：优化前占端到端 **92.7%**（2100 ms / 2265 ms），优化后仍占 **94.7%**（1315 ms / 1388 ms） |
| 次瓶颈 | 阶段② 检索：优化前 154 ms（其中**查询嵌入占约 87%**），优化后降到 **64 ms（−58.6%）**；其余三阶段合计 < 16 ms |
| 3S 验收 | **优化后达标**：P95 **2338.8 ms**，16/17 题 ≤ 3 s（94.1%）；优化前同口径 88.2% |

> 说人话：这个 RAG 系统的耗时几乎全在**让 LLM 吐字**上。检索链路本身只有百毫秒级，
> 所以"检索侧优化"最多省下百来毫秒（实测省了 90 ms，−58.6%），
> 想再降一个数量级必须动生成侧（模型/硬件/输出长度）—— 这一点已在 §5 如实列为受限项。

### 2.1 优化前实测（2026-10-12 20:08，机器空闲）

| 阶段 | 均值 ms | 占比 |
| --- | ---: | ---: |
| ① 查询处理与增强 | 3.9 | 0.4% |
| ② 检索 | 125.3 | 13.1% |
| ③ 上下文组装与提示工程 | 0.3 | 0.0% |
| ④ **LLM 生成** | **822.1** | **86.2%** |
| ⑤ 后处理与响应格式化 | 6.8 | 0.7% |
| **合计（total_ms 均值）** | **954.6** | 100% |

子阶段佐证：`embed_query` 109.3 ms（检索的 87%）、`generate_total` 822.1 ms、`llm_guard` 0.3 ms、`fusion_rerank` 3.6 ms。

### 2.2 根因

1. **生成侧是硬约束**：本机无 GPU 推理环境（RTX 2060 6 GB 未接入 vLLM/TGI），
   `qwen2.5:3b` 走 CPU，单次回答 800 ms 级；输出越长越慢（长答案题可到 1.6 s）。
2. **查询嵌入每次都打 HTTP**：基线口径下每条 query 都要向 Ollama 探测/调用一次 `/api/tags` 与嵌入接口，
   109 ms 里相当一部分是**探测与建连**，而非计算。
3. **重排候选偏多**：RRF 融合后送特征重排的候选上限 60 条，实测 40 条与 60 条的 Top-5 结果一致（见等价性验证）。
4. **日志同步写盘**：主链路内直接写 `rag_trace.jsonl`，在长答案场景下累积可观。

## 3 优化方案（全部可配置、可一键回退）

配置：`部署/配置/优化开关.json`；回退：`--perf-profile baseline`（全部开关置 false）。

| 开关 | 值 | 针对的根因 | 依据 |
| --- | --- | --- | --- |
| `embed_backend_cache` + `embed_probe_ttl_s=300` | true | 根因 2：探测结论缓存 300 s | 基线每次调用都探测 |
| `rerank_prune` + `rerank_budget=40` | true | 根因 3：候选 60→40 | 等价性验证：Top-5 一致 |
| `adaptive_top_k` | true | 检索广度按 `answer_shape` 收敛（multi=5 / single=3） | 不牺牲枚举/对比题召回 |
| `cache_enabled` | true | 重复 query 直接命中 | 生产有效；**对比实验只写不读** |
| `context_io_cache` | true | 上下文读盘缓存 | — |
| `async_log` + `async_log_queue=4096` | true | 根因 4：日志异步化 | — |
| `parallel_channels` + `parallel_workers=2` | true | 检索两路并行（上限 2，遵守资源纪律） | 并发压测 |
| `warmup_enabled` | true | 消除首题抖动（索引/分词/嵌入/生成预热） | 预热实测 9.4 s |
| `generate_budget` | true / 512 | 生成上限 | **不无证据压缩**，保持 512 以免护栏失败 |

### 4.1 验收判定

- **优化后达标**：端到端 **P95 = 2338.8 ms ≤ 3000 ms**，**16/17 题（94.1%）** 端到端 ≤ 3 s。
- 唯一未达标题：**Q10（3,136.6 ms，超线 4.6%）** —— 长答案生成题（营业收入/净利润/总资产多点枚举），
  CPU 推理下受输出长度直接制约；**未通过缩短答案来"制造"达标**。
- 参照：优化前在**完全空闲**机器上（2026-10-12）曾达成 17/17 全达标、P95 1664 ms。
  本轮两次测量同机同负载，故**优化前后的差值是可信的**；绝对水平受当前机器状态影响。

### 4.2 测量纪律（重要，避免误判）

**对比实验必须在机器空闲时跑。** 本报告编写过程中出现过一次污染测量：
优化后那一跑与另一工单的重活（LLM 抽取）并发，生成阶段被抢到 4739 ms（+476%），
SLA 达标率从 100% 掉到 35% —— 该数据**不可用于结论**，已作废并重测。
判据：优化前后两次测量的机器负载必须可比，否则结论无效。

## 5 未达标/受限项（如实记录）

| 项 | 状态 | 说明 |
| --- | --- | --- |
| GPU 推理 | **未启用** | 本机 RTX 2060 6 GB 空闲但未接 vLLM/TGI，生成仍走 CPU；若接入，生成阶段预计可下降一个数量级 |
| 生成阶段占比 | 86% → 仍是大头 | 检索侧优化最多再省 100 ms 级，无法改变数量级 |
| 外部监控组件 | **未使用** | Grafana/Prometheus/OpenTelemetry/k6 在本机不可用（无 Docker 提权、无依赖），一律以标准库自实现等价手段替代，口径已在 `设计/瓶颈定位方法论与优化方案.md` 说明 |
| 并发压测深度 | 受限 | 单机 CPU 推理，高并发下生成排队会显著劣化；未做长时间 soak |
