**Feature Branch**: `006-medical-qa-input`

**Created**: 2026-09-27

**Status**: Draft

**Input**: User description: "医知源：医疗 RAG 在线问答系统。需要后端「输入问题脚本」（FastAPI，保存到 `d:\zg6_Project\9\med_rag\backend`）与蓝白色调前端界面（左右布局：左侧导航栏含「医疗问答」功能项且可扩展；右侧问答详情页，用户输入医疗问题，回车或点击发送图标提交）。检索流程：输入 → 向量化 → 语义检索（余弦相似度）→ 生成提示词 → 大模型生成答案。答案输出：先展示引用片段（按余弦相似度分数排序），再流式输出正文答案。本期前端仅负责获取用户输入问题，向量化/检索/提示词/大模型生成等模块后续实现。"

## 背景与定位

本特性是 `docs/05_接口设计.md` 中 **I-01 `POST /ask`** 的**第一阶段落地**，也是"医知源"这个名字第一次出现在用户可感知的界面上。

它只做一件事：**把用户在界面里敲下的一句话，安全、可追溯地送进服务端**。后面那四步（向量化 → 语义检索 → 生成提示词 → 大模型生成）本次**一律不实现**，只把接口形状、页面结构与渲染容器留好，让后续步骤可以"插进去"而不是"推倒重来"。

因此本规格的边界可以一句话概括：

> **本期交付的是"提问的通道"，不是"回答的能力"。**

这带来一个必须写在前面的约束——**通道建成后，界面会看起来像是能回答问题**。所以需求里显式要求：在答案链路接入之前，任何路径都**不得**输出任何看似医学结论的内容（FR-025）。宁可界面上写着"回答能力正在接入"，也不能给出一句未经知识库支撑的"参考信息"。

上游依赖：`specs/004-bge-embedding`（向量化）、`specs/005-milvus-ingest`（索引入库）是后续回答链路的必要前置，本特性**不消费**它们的产物。

### 三项前置裁决（2026-09-27 已确认）

规格起草时发现三处**既有文档与本次诉求冲突**，按"严禁私自做决策"的约定提交人工裁决，结论如下：

| 编号 | 议题 | 既有文档立场 | 裁决 |
|---|---|---|---|
| **D1** | 前端实现方式 | `docs/02` §373/§379、`docs/03` §6 选定 **Streamlit** | **改为原生 HTML/CSS/JS，由问答服务在 8000 端口同源托管**（无独立前端进程、无构建步骤） |
| **D2** | 本期接收反馈形态 | `docs/05` §3.1.3 定义的是**完整回答体** | **按 `docs/05` §3.1.3 的字段契约返回**，答案相关字段以显式的"能力未就绪"状态表达 |
| **D3** | 流式 vs 非流式 | `docs/05` §3.1.1 明确 **V1 不流式**（N7 可断言性理由） | **改为流式**。N7 断言从"字符串以话术开头"下移到"**首个数据块等于话术**"，顺序控制权仍在服务端 |

**D3 的代价必须写清**：`docs/05` §3.1.1 给出的理由不是保守，而是一条真实的风险——流式下前端可能在收到完整回答前就开始渲染。裁决之所以成立，是因为把话术固定为**首个数据块**后，"第一句是什么"仍由服务端单方面决定，前端只做按序追加、不做重排。**这条约束若在实现中被破坏（例如前端先渲染占位再回填），N7 就真的失守了**——因此它被写成 FR-030 并须有断言覆盖。

D1 与 D3 都需要**同步修订既有文档**，清单见文末《需同步修订的既有文档》。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 提交一个医疗问题 (Priority: P1)

用户在本机浏览器打开 `http://127.0.0.1:8000/`，看到"医知源"界面：左边是导航栏，第一项是「医疗问答」；右边是问答详情区，中间有一个输入框。用户键入"我最近血压有点高，多少算高血压？"，按回车（或点右侧的发送图标），问题被服务端接收，界面给出明确的"已收到"反馈与进行中状态。

**Why this priority**: 这是整个产品唯一的入口动作。没有它，后面的检索、生成、引用全都没有输入源。它单独交付即构成一个可演示、可验证的 MVP——能证明"从界面到服务端的通道是通的"。

**Independent Test**: 启动服务后打开网址，输入任意合法中文问题并提交；检查界面出现明确的接收反馈，且服务端日志中出现一条带请求标识与问题内容的记录。全程不依赖 Milvus、向量模型或大模型。

**Acceptance Scenarios**:

1. **Given** 服务已启动且界面已打开，**When** 用户在输入框键入"体检说甲状腺结节3类是什么意思"并按回车，**Then** 界面显示该问题已被提交、处于进行中状态，且服务端收到该问题。
2. **Given** 服务已启动且界面已打开，**When** 用户键入同样的问题并点击发送图标，**Then** 产生与按回车**完全相同**的结果。
3. **Given** 一次提问已提交，**When** 答案链路尚未接入，**Then** 界面在结束进行中状态后给出明确的能力未就绪说明，且**不显示任何**医学结论、引用片段或建议（FR-025）。

### User Story 2 - 非法输入被当场拦住并说清原因 (Priority: P2)

用户尝试提交空白输入、或粘贴了一大段超出长度上限的文字。界面**不发请求**就当场提示"请输入你的问题"或"问题过长"，用户不需要等待、也不需要猜测哪里出了问题。若界面拦截失效（如直接调用接口），服务端同样拒绝，并返回与界面一致的可读提示。

**Why this priority**: 空问题会污染后续的检索与成本统计，超长输入会放大提示词注入与调用成本（`docs/05` §3.1.2）。在通道阶段就把边界钉死，比等链路建好后回补便宜得多。P2 而非 P1，是因为 US1 不通时校验本身没有意义。

**Independent Test**: 分别提交空串、纯空白、纯换行、201 字符的中文问题；四者的预期结果逐一核对，且确认前三者**未产生**服务端请求。

**Acceptance Scenarios**:

1. **Given** 输入框为空或只有空格/换行，**When** 用户按回车或点击发送图标，**Then** 界面提示"请输入你的问题"，且**不发出**任何服务端请求。
2. **Given** 用户输入了超过 200 个字符的问题，**When** 用户提交，**Then** 界面提示问题过长，并说明当前字数与上限，且**不发出**服务端请求。
3. **Given** 绕过界面直接向问答入口提交空问题，**When** 服务端收到，**Then** 返回 422 与 `INVALID_QUESTION` 错误体，且错误体**不含**堆栈、异常类名、文件路径或密钥。
4. **Given** 输入框内容为 200 个字符，**When** 用户提交，**Then** 该问题被正常接收（边界值取闭区间）。

### User Story 3 - 导航栏能长出第二个功能界面 (Priority: P3)

产品经理提出下一个功能是"用药助手"。开发者在导航栏增加一项、指向一个新的内容区，**问答页的代码一行都不用改**，两者的提问状态互不干扰。

**Why this priority**: 用户明确要求"导航栏这里后续可以持续增加其他功能界面"。这是防技术债的结构性要求，不是装饰。它排 P3，因为它不影响本期任何可演示的功能——但**必须在骨架期就做对**，事后重构导航的代价远高于现在留一个口子。

**Independent Test**: 在导航配置中追加一个占位功能项，确认它出现在左侧导航中、可切换、切换到空白内容区后切回「医疗问答」时，此前输入的草稿与提交状态仍然正确。

**Acceptance Scenarios**:

1. **Given** 界面已打开，**When** 用户查看左侧导航，**Then** 可见「医疗问答」项，且它处于选中状态。
2. **Given** 导航中新增了一个功能项，**When** 用户点击该项，**Then** 右侧切换到对应内容区；再点回「医疗问答」，输入框可用且行为与之前一致。
3. **Given** 新增导航项，**When** 检查问答功能的实现，**Then** 无需修改问答相关的任何逻辑代码。

---

### User Story 4 - 答案与引用的展示容器已经就位 (Priority: P3)

本期问答区在提交后只能显示"能力未就绪"。但版面上**已经画好了**将来要放的东西的位置：答案正文区在上，引用片段区在下；引用片段一旦有内容，就按余弦相似度分数从高到低排列，每条显示来源文件名与页码；正文以逐块出现的方式流式呈现。

**Why this priority**: 用户要求"答案输出：先展示引用片段（按余弦相似度分数排序），再流式输出正文答案"。本期虽然无内容，但**排序规则与渲染顺序必须在骨架期定下来**——它们是契约，不是样式细节。排 P3 是因为它在本期没有可观测的正确行为，只能验证"结构存在且顺序正确"。

**Independent Test**: 用一组固定的假数据（含不同相似度分数的引用片段）注入渲染层，确认引用按分数降序排列、正文区在引用区之上、且正文支持逐块追加渲染。

**Acceptance Scenarios**:

1. **Given** 问答区已渲染，**When** 用户提交一个合法问题，**Then** 版面中出现答案正文区与引用片段区两个可辨识区域，且引用区位于答案区**下方**。
2. **Given** 一组相似度分数不同的引用片段，**When** 它们被渲染，**Then** 显示顺序为分数**降序**，且每条都带有来源文件名与页码。
3. **Given** 答案正文分多次到达，**When** 界面接收，**Then** 已到达的内容立即可见并可继续追加，无需等待全部完成。
4. **Given** 本期答案链路未接入，**When** 提问提交完成，**Then** 答案区与引用区均显示明确的能力未就绪空态，**不显示**任何示例性或臆造的医学内容。

### Edge Cases

- **纯空白与纯换行**：空格、全角空格、制表符、换行组成的输入，去除首尾空白后长度必须为 0 → 拒绝（US2）。
- **边界长度**：200 字符接受、201 字符拒绝；按**去除首尾空白后**的字符数计。
- **中文输入法回车**：用户在使用拼音输入法时按回车是为了选词，**不得**被当作提交。输入法组合状态下的回车必须忽略。
- **重复提交**：进行中状态下再次回车或点击发送 → 忽略新提交或提示等待，**不得**产生并发的重复请求。
- **服务未启动 / 请求失败**：界面必须给出明确失败提示（N14），不得停留在无限加载。
- **超时**：等待超过约定时限仍无结果 → 结束加载态并提示可重试。
- **页面刷新**：刷新后输入框清空、状态重置，不回显上次问题（系统不做历史记录，M1 §7.2）。
- **特殊字符与提示词注入文本**：输入含 `【1】`、换行、HTML 标签等内容时，界面必须**原样转义**显示，不得作为标记或标签被解释。
- **超长粘贴**：粘贴超过上限的内容时，界面应即时提示，而不是等提交时才报错。
- **界面资源加载失败**：样式或脚本未加载时，页面 MUST NOT 呈现为空白页；至少应可见品牌名与一句可读的失败说明。

## Requirements *(mandatory)*

### Functional Requirements

#### 界面与布局

- **FR-001**: 系统 MUST 支持通过本地网址 `http://127.0.0.1:8000/` 直接打开"医知源"问答界面，无需额外启动第二个服务或构建步骤。
- **FR-002**: 界面 MUST 采用左右两栏布局：左侧为导航栏，右侧为当前功能的详情区。
- **FR-003**: 界面整体 MUST 采用蓝白色调（导航/强调色为蓝色系，背景与内容底为白色系），且正文与背景的对比度 MUST 满足正常阅读的可读性要求。
- **FR-004**: 左侧导航 MUST 包含「医疗问答」功能项，且默认处于选中状态。
- **FR-005**: 导航项 MUST 由一份集中配置定义，新增功能项 MUST NOT 需要修改问答功能的逻辑代码。
- **FR-006**: 右侧问答详情区 MUST 包含一个可输入医疗问题的输入区，以及一个提交控件。
- **FR-007**: 界面资源（页面、样式、脚本）MUST 由问答服务在同一端口直接提供，MUST NOT 需要独立的前端进程、打包器或构建步骤（裁决 D1）。
- **FR-008**: 界面 MUST 与接口同源，MUST NOT 依赖跨域配置或代理才能正常工作。

#### 提问交互

- **FR-009**: 用户按回车键 MUST 提交当前问题。
- **FR-010**: 用户点击发送图标 MUST 提交当前问题，且产生与按回车**完全相同**的结果。
- **FR-011**: 在输入法组合状态下按回车 MUST NOT 触发提交（不得打断选词）。
- **FR-012**: 提交后 MUST 立即给出可见的接收反馈与进行中状态。
- **FR-013**: 进行中状态下重复提交 MUST NOT 产生并发的重复请求。
- **FR-014**: 请求失败或超时 MUST 结束进行中状态并给出明确可读的提示，MUST NOT 停留在无限加载（N14）。
- **FR-015**: 界面 MUST NOT 自行执行紧急判定、拒答决策、风险分级，也 MUST NOT 拼接或改写任何固定话术（`docs/02` §2.1：业务判定收敛在服务层）。

#### 输入校验

- **FR-016**: 输入去除首尾空白后为空时，界面 MUST 拒绝提交、提示"请输入你的问题"，并 MUST NOT 发出服务端请求。
- **FR-017**: 输入去除首尾空白后超过 200 个字符时，界面 MUST 拒绝提交并提示问题过长（含当前字数与上限），MUST NOT 发出服务端请求。
- **FR-018**: 服务端 MUST 独立校验问题非空且长度在 1–200 字符（闭区间），非法时返回 422 与 `INVALID_QUESTION` 错误体。
- **FR-019**: 错误响应 MUST NOT 包含堆栈、异常类名、内部文件路径、密钥或模型供应商原始错误体（constitution 原则 III）。
- **FR-020**: 用户输入 MUST 在界面中被原样转义显示，MUST NOT 被解释为标记、标签或可执行内容。

#### 服务端输入入口

- **FR-021**: 服务端 MUST 提供接收用户问题的入口，接收内容至少包含问题原文，并为每次请求生成一个可关联日志的请求标识。
- **FR-022**: 服务端 MUST 在启动期一次性读取配置，MUST NOT 在请求路径上读取环境变量；必需项缺失时 MUST 启动失败并以非 0 状态退出（`docs/05` §4.5）。
- **FR-023**: 服务端返回体 MUST 使用 `docs/05` §3.1.3 定义的字段契约（`answer_id` / `is_refusal` / `emergency` / `risk_level` / `answer_text` / `citations` / `disclaimer`），字段名 MUST 与之一致，以免后续模块接入时二次改动契约（裁决 D2）。
- **FR-024**: 本期答案相关字段 MUST 以**显式的"能力未就绪"状态**表达，MUST NOT 通过填充臆造内容或假数据来占位；响应 MUST NOT 表达为系统故障（合法提问 MUST 返回 200）。
- **FR-025**: 服务端 MUST NOT 在任何响应或界面中输出未经知识库支撑的医学结论、建议、诊断或剂量（constitution 原则 II、V）。
- **FR-026**: 服务端 MUST 记录每次提问的请求标识与问题原文，日志 MUST NOT 包含密钥（constitution 原则 III）。

#### 答案与引用展示

- **FR-027**: 问答详情区 MUST 包含答案正文区与其**下方**的引用片段区两个可辨识区域。
- **FR-028**: 引用片段一经渲染，MUST 按余弦相似度分数**降序**排列，每条 MUST 展示来源文件名与页码。
- **FR-029**: 答案正文 MUST 以流式方式呈现——内容分多次到达时逐块追加渲染，MUST NOT 要求等待完整答案到达后才开始显示（裁决 D3）。
- **FR-030**: 若紧急前置话术出现，服务端 MUST 将其作为流式输出的**第一个**数据块，且 MUST NOT 在流中插入任何先于它的内容；界面 MUST 按到达顺序渲染，MUST NOT 对内容块重排（裁决 D3 —— 这是 N7 在流式下的替代断言点）。
- **FR-031**: 本期答案链路未接入时，两个区域 MUST 显示明确的能力未就绪空态，MUST NOT 展示任何示例性、占位性或臆造的医学内容。

#### 工程约束

- **FR-032**: 服务端 MUST 以 `D:/zg6_Project/9/med_rag/rag/python.exe`（Python 3.12.14）运行，MUST NOT 使用裸 `python`/`python3`/`py`（constitution 原则 I）。
- **FR-033**: 新增依赖 MUST 只安装进 `rag/`，并 MUST 同步登记到仓库根 `requirements.txt`（constitution 原则 I）。
- **FR-034**: 所有密钥与凭据 MUST 仅通过环境变量读取，MUST NOT 硬编码进源码、配置、测试、文档或日志（constitution 原则 III）。
- **FR-035**: 本特性新增的服务端脚本与模块 MUST 保存在 `d:\zg6_Project\9\med_rag\backend` 目录下。
- **FR-036**: 单个源码文件 MUST NOT 超过 300 行；超出时 MUST 拆分为模块，但对外入口 MUST 保持唯一。
- **FR-037**: 标识符 MUST 使用 snake_case；函数签名 MUST 带类型注解，公开函数 MUST 带返回类型注解（constitution 代码规范）。

### Key Entities

- **用户提问（Question）**：用户在界面中输入的一句话。关键属性：问题原文（去除首尾空白后 1–200 字符）、请求标识、提交时间。
- **接收反馈（AskResponse）**：服务端对一次提问的应答，字段与 `docs/05` §3.1.3 对齐。关键属性：`answer_id`、`is_refusal`、`emergency`、`risk_level`、`answer_text`、`citations`、`disclaimer`。本期其中与答案相关的字段承载"能力未就绪"状态，而非医学内容。
- **引用片段（Citation）**：未来答案的溯源依据，本期只定义展示契约。关键属性：序号、来源文件名、起始页码、结束页码、章节、原文片段、**余弦相似度分数**（排序依据）。
- **导航功能项（NavItem）**：左侧导航的一个条目。关键属性：显示名称、标识、对应内容区、是否默认选中。
- **错误响应（ErrorBody）**：非法请求的统一应答，结构见 `docs/05` §2.3。关键属性：错误码、用户可见文案、请求标识。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在浏览器中打开本地网址后，**3 秒内**能看到可输入的问答界面。
- **SC-002**: 用户提交一个合法问题后，**2 秒内**看到明确的接收反馈（本期不含检索与生成，该时限不包含后续链路的时间）。
- **SC-003**: 空输入与超长输入在被拦截时，**100%** 不产生服务端请求，且给出可读的原因说明。
- **SC-004**: **100%** 的被接收提问都能在服务端日志中通过 `answer_id` 定位到，且日志中检索不到任何密钥内容。
- **SC-005**: 新增一个导航功能项所需的改动**不超过 1 处配置**，问答功能代码改动量为 0 行。
- **SC-006**: 在答案链路未接入的全部路径下，界面上出现的医学结论性内容条数为 **0**。
- **SC-007**: 用固定假数据渲染引用片段时，其显示顺序与相似度分数的降序顺序**完全一致**（100% 匹配）。
- **SC-008**: 提问失败或超时的情况下，界面在约定时限内退出加载状态的比例为 **100%**，不出现无限加载。
- **SC-009**: 后续四个模块（向量化、检索、提示词、生成）接入时，**不需要修改**界面侧的响应字段解析代码——以"响应契约字段名与 `docs/05` §3.1.3 完全一致"验证。

## Assumptions

- **运行时与端口**：服务绑定 `127.0.0.1:8000`，仅本机访问，V1 无鉴权（`docs/05` §2.2）。UI 与接口同源（FR-008），前端不需要跨域处理。
- **依赖现状**：`rag/python.exe` 中 `fastapi 0.141.1` 与 `uvicorn 0.53.0` 已实测安装，本期无需新增依赖即可启动 HTTP 服务并可托管静态资源；若实现中确需新依赖，按 FR-033 登记。
- **前端资源目录**：沿用仓库既有约定 `frontend/`（`docs/02` §379 已预留该目录），存放静态页面、样式与脚本，由 `backend/` 的问答服务挂载提供。**此处为起草时的合理默认，若你希望并入 `backend/` 或另起目录，请在 plan 前指出。**
- **范围边界**：本期**不实现**向量化、语义检索、提示词生成、大模型调用，也不消费 `specs/004`/`specs/005` 的产物。检索为空、低于阈值、拒答、紧急话术、免责声明等行为**本期不产生、不测试**，待答案链路接入时按 constitution 补齐断言——**唯一例外是 FR-030**：它约束的是流式顺序本身，必须在本期就写对，否则后续无从补救。
- **会话模型**：单轮问答，无历史回显、无会话存储（M1 §7.2）；`POST /feedback` 不在本期范围。
- **内容安全兜底**：由于答案链路缺失，本期的"安全"体现为**不输出任何医学内容**，而不是"输出正确的话术"。固定话术在答案链路接入前不出现，避免出现"有话术、无正文"的半成品观感；但流式通道与首块顺序（FR-029/FR-030）先行落地。
- **输入长度上限**：沿用 `docs/05` §3.1.2 的 1–200 字符，理由是 M1 定义的是单轮、非专业的口语化提问。
