# 跨模态检索问答系统 · 性能测试报告

> **工单编号**：人工智能NLP-RAG-优化技术图纸与文本的跨模态检索流程工单（简称「工单十五」）
> **项目**：人工智能 NLP-RAG 项目
> **测试时间**：2026-10-09
> **测试脚本**：`perf_bench.py`（性能基准）
> **结果文件**：`output/perf_results.json`

---

## 1. 测试目标

量化系统的端到端与分阶段性能，验证工单「端到端响应 ≤ 3~5 s」的验收标准，并定位性能瓶颈。

具体测量：

| 编号 | 测量项 | 说明 |
| --- | --- | --- |
| P1 | 冷启动 / 预热 / 缓存命中延迟 | 评估首问开销与缓存收益 |
| P2 | 分阶段耗时拆解 | 查询理解 / 向量编码 / 向量召回 / 全文检索 / 融合 / 跨模态重排 / 答案抽取 |
| P3 | 三种检索策略端到端耗时 | vector / fulltext / hybrid |
| P4 | 稳定性 | 20 次冷查询的均值 / P50 / P95 / 最大 / 标准差 |

> **测量口径说明**：系统对**同一查询文本**缓存其向量（重复问同一问题几乎零延迟）。
> 但性能报告关注的是**用户提新问题**的真实延迟，故基准脚本在每次计时前**清空查询向量缓存**，
> 保证每次均为「真实冷查询」。同时单独记录缓存命中延迟以体现优化收益。

## 3. 测试结果

### 3.1 冷启动 / 预热 / 缓存（P1）

| 场景 | 延迟 |
| --- | --- |
| 冷启动（首次问答，含索引/模型懒加载） | **2657.5 ms** |
| 预热后新问题（引擎已加载，冷编码） | **2221.6 ms** |
| 缓存命中（重复问同一问题） | **2.3 ms** |
| 预热收益（降低首问延迟） | 435.9 ms |

**结论**：`engine.warmup()` 预热可显著降低首问延迟（约 436 ms）；查询向量缓存使
**重复提问的延迟降至 2.3 ms**（约 950× 加速）。

### 3.2 分阶段耗时拆解（P2）

| 阶段 | 耗时 | 占比 | 说明 |
| --- | --- | --- | --- |
| 多轮改写 | 0.02 ms | <0.1% | 规则式指代消解，纯 CPU |
| 查询理解 | 0.21 ms | <0.1% | 正则识别视觉引用 / 部件编号 + 同义词扩展 |
| **向量编码** | **2151.86 ms** | **≈98%** | **Ollama 嵌入 HTTP 调用（固定开销）—— 唯一瓶颈** |
| 向量召回 | 0.20 ms | <0.1% | 20×1024 内积 + 排序（numpy） |
| 全文检索 | 1.18 ms | ≈0.1% | 倒排索引 BM25 |
| 融合召回（整体） | 2238.83 ms | — | 含一次独立冷编码（本项为整体测量，非增量） |
| 跨模态重排 | 0.55 ms | <0.1% | 图文块联合打分 |
| 答案抽取 | 0.14 ms | <0.1% | 按题型分流抽取 |
| **端到端** | **2167.10 ms** | 100% | 走完整引擎链路 |

**关键发现**：端到端延迟**几乎完全由向量编码（Ollama 嵌入调用）决定**（≈98%），
其余所有阶段（查询理解 + 召回 + 融合 + 跨模态重排 + 答案抽取）**合计 < 2.5 ms**。
这说明本工单引入的跨模态优化（多路召回 + 跨模态重排）**几乎没有增加计算开销**。

### 3.3 三种检索策略对比（P3）

| 策略 | 重排 | 平均端到端耗时 |
| --- | --- | --- |
| vector（纯向量） | none | 2173.77 ms |
| fulltext（纯全文） | none | **1.34 ms** |
| hybrid（向量 + 全文） | crossmodal | 2176.06 ms |

**结论**：

- **全文检索**不含向量编码，单次仅 **1.34 ms**，极快；
- **向量 / 混合检索**因需调用 Ollama 嵌入，均为 **≈2.17 s**；
- **混合检索 + 跨模态重排（优化后默认）相对纯向量检索仅增加 ≈2.3 ms**（2173.77 → 2176.06），
  说明跨模态优化**代价可忽略**，却带来准确率 33.3%→100% 的巨大提升（见《测试报告》）。

### 3.4 稳定性（P4）

对基准问题做 **20 次冷查询**（每次清空向量缓存）：

| 统计量 | 值 |
| --- | --- |
| 均值 | **2187.14 ms** |
| P50 | 2171.44 ms |
| P95 | 2305.15 ms |
| 最大 | 2305.15 ms |
| 最小 | ≈2170 ms（见 `perf_results.json`） |
| 标准差 | **54.23 ms** |

**结论**：延迟**高度稳定**，标准差仅 54 ms（≈2.5%），P95 与均值差异 < 120 ms，
无长尾抖动。波动主要来自 Ollama 嵌入服务的响应抖动。

## 5. 性能瓶颈与优化建议

### 5.1 瓶颈定位

端到端延迟的 **≈98% 来自 Ollama 向量嵌入 HTTP 调用（≈2.15 s/次）**。
这是 Ollama 单次调用的**固定开销**（含模型加载/推理调度），与文本长度关系不大。

### 5.2 已实施的优化

| 优化项 | 效果 |
| --- | --- |
| **批量编码**：一次 ask 的多路查询合并为**单次 HTTP 调用** | 避免多路查询多次调用（否则 ≈2.15 s × N） |
| **查询向量缓存**：同一查询文本缓存向量 | 重复提问 2.3 ms（≈950× 加速） |
| **预热**（`warmup()`）：启动时预跑一次 | 降低首问延迟 ≈436 ms |

### 5.3 后续可优化方向（不影响本工单验收）

1. **本地嵌入模型替代 HTTP 调用**：改用 `sentence-transformers` / ONNX 直接加载 bge-m3，
   消除 HTTP 与调度开销，预计可降至 **50~200 ms** 量级；
2. **嵌入服务常驻**：保持 Ollama 模型常驻内存（`keep_alive`），减少冷加载；
3. **向量索引规模化**：当前 20 块全量内积仅 0.2 ms；若知识库扩展到十万级，
   可引入 HNSW / IVF 近似索引；
4. **异步并行**：多路召回的向量编码与全文检索并行执行（当前全文已 <2 ms，收益有限）。
