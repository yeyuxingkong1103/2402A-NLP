### 1.2 为什么要给 9 份年报各写一条 `DocProfile`

工单03 就已经把「页眉模板 / 页脚模板 / 页码格式 / 实体专名 / 证据页正则」收进了
`app/core/doc_profiles.py`，一份 PDF 一条，**配不到就当场报错**。这 9 份年报正是这条
机制的延伸：它们与两份招股书的排版差异极大，靠"一套通用规则"必然做错。

页码偏移实测各不相同（+1 / −1 / −3 / +20），且**同一份文档内部还会变**：

```
中国太保2021年报（264 页）实测有 4 段各自编号的页码：
  idx  1~16   前导节，页脚印 `2021 年 年度报告前导 ｜N` / `N ｜ 公司名`  → 印 1~16
  idx 17~20   经营业绩节，页脚印 `N 2021 年度报告`                     → 印 1~4
  idx 21~127  公司治理/重要事项节                                      → 印 1~107
  idx 144~    财务报告节，页脚印 `公司名N`                              → 印 1~…
```

招商银行（idx60 印 `61`、idx140 印 `- 15 -`）与邮储银行（idx50 印 `50`、idx220 印 `- 12 -`）
同样是多段编号。**任何单一偏移都不可能同时对上这几段**，所以本工单把页码来源改成：

> **页码优先从该页页脚实际印着的那串数字读**，读不到才回退 `index − 偏移`。

实现在 `DocProfile.footer_label()` / `printed_label()`（`app/core/doc_profiles.py`）。
好处不只是"更准"——**引用页码从此与读者在 PDF 里看到的完全一致**，验收时能逐条核对。

### 1.3 页码/页眉模板的复核（可判定的判据）

配错模板的后果是**不报错的错**：页码错了 → 引用全错；页眉模板写松了 → 正文被当页眉删掉。
所以新增 `scripts/verify_ccf_profiles.py`，对 9 份年报**逐页**复核 4 条判据：

| 判据 | 内容 | 结果 |
|---|---|---|
| 1 | 页脚实读覆盖率 ≥ 60% | 94.3%（招商银行）～100%（中信/招商证券/国君）×9 全过 |
| 2 | 页眉命中**零**带外（带外 = 疑似误删正文） | 全过（国泰君安封面 1 处例外，属封面标题） |
| 3 | 无「带外文本块 == 本页页码」的碰撞 | 全过 |
| 4 | 实读页码分段单调（只允许"节重启"式回跳） | 全过（节重启 8 处，均已在 1.2 说明） |

```
$ ~/rag-data/venv/bin/python scripts/verify_ccf_profiles.py
  ...
  总判据：✅ 全部通过
```

**判据 2 当场抓到一个真问题**（不是脚本自娱自乐）：

> 中国平安2019年报的页眉是孤零零一行「2019年度」。它太短，实测有 **20 处**命中落在
> y=0.17~0.23（正文带）而不是页眉带 —— 无法区分"被大图挤下来的页眉"与"正文里的年度小标题"。
> 按本项目一贯的「**宁可留噪声，也不静默删正文**」，最终选择**不做页眉删除**：
> 留一行 `2019年度` 只是噪声，删错就是答案消失。

**判据 3 也当场抓到一个真 bug**（已修）：

> 解析器里有一条**不带页脚带**的兜底规则：「整行恰好等于本页页码 → 当页脚删掉」，
> 原本是为招股书2 那 8 页**旋转 90° 的横向表**准备的（它们的页脚落在 y≈0.69，进不了常规分带）。
> 实测国泰君安2019年报 idx=10 的资质表里，有一格正文**就是「11」**，而该页页码也是 11
> → 整格被静默删掉。修法：把这条规则**收紧到非标准版面**（`page.rotation` 或横版）才生效 ——
> 那正是它当初存在的唯一理由。招股书2 那 8 页照旧能清掉
> （`tests/test_pipeline.py::test_pdf2_header_footer_fully_removed` 断言 `n_footer_removed == 350` 仍在守）。

跑的就是工单01–06 的同一套评估器（`app/core/evaluator.py`，自实现三轨，不用 ragas），
只是换了题库：

```bash

```

为此给 `Evaluator` 加了 `questions=` 参数、给 `eval.py` 加了 `--questions`（**默认值不变**，
不带这个参数就是工单01–06 的 16 题）。

### 3.1 本工单对评估器做的一处修正：数值判据要**校验量纲**

实测发现的**两个方向**的问题，逼出了这次修正：

- **答对了却判错**：中信证券 id=707，模型答「54,382,730,241.56元」（= 543.83 亿元，
  **完全正确**），但原文在「管理层讨论与分析」写的是 `543.83亿元` —— 字面不同，被判未命中。
- **答错了却判对**（更糟）：中国人寿 id=706，模型把原文的 `612,265 百万元` 答成
  `612,265 亿元`，**差 100 倍**；而"612,265 这串数字出现过"就算命中。

修法（`app/core/evaluator.py`）：新增量纲归一到「元」的比较，并且**带量纲的关键词不再走裸数字路径**。

| 用例 | 结果 |
|---|---|
| `543.83亿元` vs `54,382,730,241.56元` | ✅ 命中（容差 0.1%，吸收年报的四舍五入） |
| `612,265百万元` vs `612,265亿元` | ❌ 未命中（差 100 倍，必须判错） |
| `1.65` vs `1.66` | ❌ 未命中（**小数值不给容差**，否则两个不良率会被判成同一个数） |
| `5,520.00`（不带单位）vs `5,520.00万元` | ✅ 命中（工单01–06 的既有口径，一字未改） |

4 条用例已进 `tests/test_pipeline.py`。

> **附带代价，如实记下**：带量纲的关键词不再接受"只答数字不写单位"的答案。
> 这 9 份年报里同一笔钱按元 / 百万元 / 亿元三种口径都出现过（见 §6.4），
> 不写单位确实有歧义，所以本工单选择"金额类判据一律带量纲"。
> id=706 最终仍是 ❌，但那正是**应该**判错的一次。

## 6. 检索结果存在的问题分析（本工单重点）

### 6.1 先把"答不出来"拆成三类

"哪几题没答对"是现象，不是分析。要给出可归因的结论，必须把每题拆成三段：

```
库里有没有？ ──▶ 检索有没有召回到？ ──▶ 生成有没有用上？
     │                    │                     │
     │                    │                     └─ ③ 生成侧漏答
     │                    └─ ② 检索侧漏召
     └─ ① 语料缺口
```

三类问题的修法完全不同（改出题 / 改检索 / 改生成），必须先分开。
`scripts/diagnose_wo07.py` 就是干这件事的，判据与评估器**共用同一套关键词匹配**，
避免出现"评估说召回了、归因说没召回"的两套口径打架。

> **归因脚本自己踩过的坑（写下来免得再犯）**：第一版拿 `recall_keywords`（要点词，
> 是"不良贷款率"这类**概念词**）去判"生成侧漏答"，于是把 id=703–706 四道**答对的题**
> 全归成了"生成侧漏答"。正确口径是：**判"答没答对"只用 `rule_keywords`（答案判据）**，
> `recall_keywords` 只用来衡量"要点召回得全不全"。

| id | 结论 | 具体表现 |
|---|---|---|
| 701 | ② 检索侧漏召 | 致辞所在页（p.4）**根本没进 top-3**，见 6.3-A |
| 702 | 剖面敏感 | optimized ✅ / hybrid ❌：混合检索把 p.12/82/85 顶上来了，正确页 p.5 被挤掉 |
| 703 | ✅ | 三指标全中，页精确 1.0 |
| 704 | ✅ optimized / ❌ hybrid | hybrid 下模型把净利润答成 1,643.65 亿元（正确 1,494.07 亿） |
| 705 | ✅ | — |
| 706 | ③ 生成侧（量纲） | 检索**是对的**（p.06 就是那张主要财务指标表），模型把 `612,265 百万元` 写成 `612,265 亿元` |
| 707 | ✅（修正判据后） | 模型答 `54,382,730,241.56元`，量纲换算后判为正确 |
| 708 | ②+③ | 检索抓到了**财务报表细分表**而不是管理层讨论；模型把"产险+寿险"相加当成集团保险业务收入 |

`optimized` 剖面下的自动归因汇总（`eval报告/工单07-检索问题归因-optimized.json`）：

```
汇总：
  ② 检索侧漏召：4 题 [701, 706, 708, 710]

```

> （实测 709 这次落在"生成侧漏答"、评测那次落在"跨文档错配"，两次的**失败集合完全一致**，
> 只是模型每次生成措辞不同）。因此：**"哪几题没通过"看评测报告，"为什么没通过"看本文的根因分析**，
> 自动分类只当线索用。

### 6.3 四个具体问题（都能落到根因）

#### A. 「文档首页」把「正文那一页」挤掉了（id=701）

题面问的是**董事长致辞**。实测（`optimized`）：

```
召回页 = ['1', '24']            ← 期望的 p.4 一次都没进
p.1 的块：'平安银行股份有限公司2019年年度报告重要提示1、本行董事会…'    dense 0.742
p.24 的块：'创新应用方面，依托平安集团核心技术和资源…'                 dense 0.683
```

根因很明确：**p.1 的块字面上就写着「平安银行股份有限公司2019年年度报告」**，
查询串里"2019年年度报告"这几个字与它高度重合，稠密相似度天然最高。而**答案所在的 p.4**

```
p.4 的块（chunk_index=4，确实在库里）：
  '业务结构不断优化，且更趋均衡。零售进一步巩固收入贡献的支柱地位…盈利增长形成趋势，且风险可控…'
```

**通篇不含"年度报告""经营成果""归纳"这几个查询词** —— 它讲的是"是什么"，问的是"怎么归纳"。
三种检索模式（`optimized` / `hybrid` / `fulltext`）实测**都召不回 p.4**：

```
[optimized ] pages=['1', '1', '24', '3']   ← p.4 在否: False
[hybrid    ] pages=['120', '1', '1', '3']  ← p.4 在否: False
[fulltext  ] pages=['1', '1', '120']       ← p.4 在否: False
```

这与 §6.5 的 hybrid 退步是**同一个病根**：**查询里的"文档标题短语"是个强噪声源**。
可行的修法（本工单未实施，留作工单08 的输入）：把文档标题行/首页标题从向量里剥掉，
或给"标题短语命中"降权。

#### B. 跨页块把页码标成了起始页（引用页码会偏）

实测某块的 `page_label = 1`，但它的内容是
「p.1 重要提示第 7 条 + p.3 释义标题 + **p.4 董事长致辞**正文」：

```
chunk_index=3  page_label=1  page_no=1
content: '7、本行经本次董事会审议通过的普通股利润分配预案为：…释义 董事长致辞 金融向善，履责前行…'
```

`chunk_pages()` 本来就**允许跨页**（注释写着"章节连续时更自然"），也记录了覆盖的全部页码
（`Chunk.pages`），但入库时**只带走了起始页**（Milvus 的 schema 早期就定死了，没有 pages 字段）。
后果：引用页码指向 1，真实内容在 4，**差了 3 页**。

这不是个别现象。9 份年报逐块实测（**跨度一律用 PDF 页序 = "在 PDF 里翻到第几页"**，
与印刷页码区分开 —— 后者在这几份文档里还有节内重编号）：

| 文档 | text 块 | 跨页块 | 占比 | 最长跨度（PDF 第 N 页） |
|---|---|---|---|---|
| 平安银行2019年报 | 430 | 233 | 54.2% | 第 107~111 页 |
| 中国平安2019年报 | 749 | 337 | 45.0% | 第 109~112 页 |
| 招商银行2019年报 | 681 | 337 | 49.5% | 第 248~251 页 |
| 邮储银行2019年报 | 583 | 355 | 60.9% | 第 194~205 页 |
| 中信证券2020年报 | 762 | 338 | 44.4% | 第 47~51 页 |
| 中国人寿2020年报 | 462 | 227 | 49.1% | 第 91~94 页 |
| 中国太保2021年报 | 419 | 209 | 49.9% | 第 134~143 页 |

**近一半的正文块跨了页**，最长的一例内容横跨 10 页（PDF 第 134~143 页），
而它在库里只带着**起始页**的印刷页码 —— 引用给读者看的就是那一个起始页码。

> 这是"页精确率只有 13.3%"的一个重要结构性原因（另一部分是证据页标注本身宽泛，
> 与工单02「页级指标推不动」的结论一致）。
> 修法方向：入库时把 `page_label` 写成页码范围（如 `4~4` / `1~4`），或把 `pages` 落到
> `section_path` 这类已有字段里。**改动会波及全部 11 份文档的引用口径，本工单不擅自改。**
> 需要说明的是：这里统计的"跨页"包含了**1 句重叠**带过来的相邻页，所以占比偏高；
> 上表给出的"最长跨度"才是无争议的证据。

#### C. 跨文档问题会「张冠李戴」（id=709）

题面点名两家：「招商证券与国泰君安2021年…营业收入分别是多少？」。
路由按设计**不做过滤**（`route_multi` 命中两家 → 全库检索），模型答：

```
招商证券2021年营业收入为42,817,138,705元        ← 428.17 亿，这是**国泰君安**的数
国泰君安2021年营业收入为13,707,280,412.80元      ← 137.07 亿，两边都不是
```

**答反了一家，还编了一家。** 这种错误对"数值命中"类判据只暴露一半
（缺了 294.29 所以判 ❌，但 428.17 是被判命的），
**判据本身检测不出"数值对、归属反了"** —— 这是这套评分的已知盲区，如实记下。

另外 `hybrid` 剖面对同一题直接拒答（"资料中未提及相关信息"），
说明混合检索在**跨文档**场景下更容易被单文档的强信号带跑。

#### D. 跨文档综合题顶不住（id=710）

题面要求综合"这些年报"谈共同策略与差异化策略。实测召回只有 **3 页**（`top_k=3`），
覆盖不到 5 份以上文档。要点召回 25%、命中 0/5。

**这是 top-k 的结构性限制，不是模型能力问题** —— 忠实度 0.98 说明模型只用了给它的资料。
可行的修法：跨文档题走「按文档分路召回 + 每路取 1~2 块」而不是"全局 top-3"。

### 6.4 判据口径本身的问题（同样是"测试与评估"的一部分）

| 问题 | 现象 | 处理 |
|---|---|---|
| 同一数值多量纲 | `543.83亿元` / `54,382,730,241.56元` / `440,643百万元` 是同一事实 | **已修**：量纲归一 + 0.1% 容差（§3.1） |
| 单位写错却被判对 | `612,265 百万元` 答成 `612,265 亿元`（差 100 倍） | **已修**：带量纲的关键词不再走裸数字路径 |
| 数值对、归属反 | id=709 张冠李戴 | **未修**（已知盲区）：需要"值-实体"绑定判据，不是关键词匹配能覆盖的 |
| 页码跨节重号 | 招商银行/邮储银行/中国太保在财务报告节从 1 重编 | **已核实并记录**：页码取自页脚实读，与 PDF 一致；跨节统计时须意识到重号 |

### 6.5 为什么 hybrid 在这套语料上**更差**（3/10 vs 5/10）

工单06 的结论是"混合检索增益在召回"（要点召回 97.9% → 100%）。换到 9 份年报上，
hybrid 的要点召回反而从 69.3% 掉到 59.6%。差异来自语料性质：

- **招股书的查询词与正文用词高度一致**（"募集资金""军用领域收入"），BM25 那一路几乎不引入噪声；
- **年报的查询词大量是"文档级"措辞**（"2019年年度报告""2021年年度报告"），
  而 BM25 恰恰最擅长匹配这种**字面高频词** —— 于是它把"封面/首页/目录"这类块顶了上来，
  把真正含答案的正文块挤下去。id=702 就是典型：hybrid 召回 p.12/82/85，而正确页是 p.5。

> 一句话：**混合检索的收益取决于"关键词路带来的是信号还是噪声"**。
> 在这套语料上，头部那几份年报的"文档标题短语"是噪声源。
> 这条结论是**用两套语料、同一条流水线对比出来的**，不是推测。

## 8. 结论

1. **功能测试**：10 道题全部跑通，端到端准确率 **5/10**（`optimized`），
   忠实度 0.98、答案相关性 0.95 ⇒ 系统**不编造**，主要短板在**取证据**。
2. **评估**：三轨指标 + LLM judge 齐全，报告存档在 `eval报告/`；
   过程中修掉了评估器自身的一处量纲缺陷（§3.1）。
3. **检索问题**：四个具体问题都落到了根因（§6.3），其中两个（文档标题短语抢占、
   跨页块页码错标）是**新语料才暴露出来**的，招股书那 16 题碰不到。
4. **没有回归**：新语料入同一 collection 后，招股书 16 题复跑仍 **16/16**；
   单测 144 → **148 passed**（新增 4 条量纲换算用例）。
5. **已知未修**：跨页块页码（改动波及全部文档的引用口径）、
   跨文档"值-实体绑定"判据（超出关键词匹配能力）、文档标题短语降权 —— 都已写清根因与修法，
   留作后续工单的输入。
