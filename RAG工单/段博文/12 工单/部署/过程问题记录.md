# 过程问题记录 — LightRAG 优化任务

> 工单编号：人工智能NLP-RAG项目-LightRAG优化

## 问题 1：LightRAG 1.5.7 直接 ainsert 报 PipelineNotInitializedError

- **现象**：创建 `LightRAG` 实例后直接调用 `await rag.ainsert(...)`，抛出
  `PipelineNotInitializedError: Pipeline namespace 'pipeline_status' not found`。
- **原因**：新版（1.5.x）不再在 `ainsert` 内部隐式初始化存储，要求显式初始化/终结存储。
- **解决**：
  ```python
  rag = build_rag()
  await rag.initialize_storages()
  try:
      await rag.ainsert(text)
      ...
  finally:
      await rag.finalize_storages()
  ```

## 问题 2：默认抽取实体类型过于通用，招股书特征丢失

- **现象**：小试图谱中出现大量 Concept/Organization 等通用类型节点，
  无法体现招股书领域特征（募投项目、技术标准、工程奖项等）。
- **原因**：LightRAG 默认 `entity_types_guidance` 是通用类型定义。
- **解决**：通过 `addon_params={"entity_types_guidance": ENTITY_TYPES_GUIDANCE}`
  注入招股书定制的 13 类实体 + 13 类关系，并附加抽取要求（全称一致、
  金额/比例/报告期必须入描述等）。小试验证后类型分布变为：
  财务指标/公司/事件/机构/技术标准/产品/人员/行业/募投项目等招股书领域类型。
- **补充修正**：小试中发现少量英文类型（financialmetric、project），
  在 guidance 中追加约束"entity_type 必须按'中文名(English)'格式书写"。

## 问题 3：`entity_type_prompt_file` 不支持绝对路径

- **现象**：尝试用 `addon_params={"entity_type_prompt_file": "D:/.../profile.yaml"}`
  完全替换抽取示例时报错（文件名沙箱拒绝绝对路径与目录分隔符）。
- **原因**：该参数只接受放置于 PROMPT_DIR 下的裸文件名。
- **决策**：不使用该机制，改用 `entity_types_guidance`（字符串注入），
  同样可完整定制实体/关系类型体系，且无需迁移文件。

## 问题 4：DeepSeek 偶发限流/超时

- **现象**：并发抽取过程中偶发 429 / 超时异常。
- **解决**：`deepseek_llm_func` 内置 3 次指数退避重试（2s/4s/8s，上限 20s）；
  同时利用 LightRAG 的 LLM response cache，失败重跑时命中缓存不重复计费。

## 问题 5：公平对比的基线选择

- **问题**：传统 RAG 基线用什么切块？若自行切块，chunk 粒度不一致会导致对比失真。
- **解决**：直接读取 LightRAG 的 `kv_store_text_chunks.json`（LightRAG 切块结果），
  传统 RAG 与 LightRAG 面对完全相同的文本块，仅检索机制不同，
  保证"扁平向量检索 vs 图谱双层检索"对比的公平性。

## 问题 6：答案中千分位逗号导致关键词误判

- **现象**：参考答案关键词含 "6,464.51"，而 LLM 答案可能输出 "6464.51"（或反之）。
- **解决**：评分函数 `_hit_count` 统一去除中英文逗号与空格后再匹配。

## 问题 7：CPU 批量编码触发 embedding 30s 超时，文档 failed

- **现象**：首次全量构建时两份文档状态均为 `failed`，日志出现
  `TimeoutError`，定位到 LightRAG 的 `DEFAULT_EMBEDDING_TIMEOUT=30s`。
- **原因**：本机为纯 CPU 环境，bge-m3 批量编码 547 个文本块，首批编码
  含模型加载，单次批量远超 30s。
- **解决**：config 中新增 `EMBEDDING_TIMEOUT=600`，并在 `build_rag()` 中
  传入 `default_embedding_timeout=EMBEDDING_TIMEOUT`；再用 `--rebuild` 重建。
  由于 LLM 抽取结果已缓存，重建只重算向量、不重复调用 LLM、不重复计费。

## 问题 8：重跑构建被 "No new unique documents" 跳过

- **现象**：修复超时后直接重跑，日志提示没有新文档、不做任何处理。
- **原因**：LightRAG 按文件名判重，旧（failed）记录仍在存储中。
- **解决**：`lightrag_build.py` 提供 `--rebuild`，先对每个文档调用
  `await rag.adelete_by_doc_id(doc_id)` 删除旧记录再重新插入。

## 问题 9：后台 python 孤儿进程空转抢占 CPU

- **现象**：一次后台构建任务结束后，构建进程未退出，持续占满 CPU 约 40 分钟，
  导致后续所有操作异常缓慢。
- **解决**：`Stop-Process -Id <PID> -Force` 手动结束。
- **教训**：后台任务完成后必须检查并清理残留 python 进程。

## 问题 10：graphml 持久化后 entity_type 全部丢失为 UNKNOWN

- **现象**：图谱构建成功、3677 节点，但读取 graphml 时所有节点
  `entity_type=UNKNOWN`，无法按类型着色/统计。
- **原因**：LightRAG 1.5.7 写 graphml 时未持久化实体类型，类型只存在于
  LLM 抽取的原始输出中（`kv_store_llm_response_cache.json`）。
- **解决**：编写 `fix_entity_types.py`，从 LLM 缓存按分隔符 `<|#|>`
  （兼容偶发变体 `<|>`）解析"名称→类型"，对同名实体众数投票、
  对其余做名称模糊包含匹配后回填 graphml。
  最终 **3631/3677 节点（98.7%）获得准确类型**，仅 46 个保持 UNKNOWN。

## 问题 11：离线环境 CDN 不可用，vis-network 无法加载

- **现象**：pyvis 先按默认（本地 lib 相对路径）生成 HTML，lib 目录被生成到
  脚本运行目录而非 HTML 旁，页面引用不到；改用 CDN 后浏览器 `load` 事件
  超过 120s 仍不触发（沙箱无法访问 unpkg/jsdelivr）。
- **解决**：pyvis 设 `cdn_resources="in_line"`，把 vis-network 库直接内联进
  HTML，生成单个完全自包含文件（1.5MB），不依赖任何外部文件或网络。

## 问题 12：图谱加载进度条 loadingBar 不消失

- **现象**：截图时画面中央停留在一个 80%~95% 的进度条，遮挡画布。
- **原因**：展示的 300 节点超过 vis-network `improvedLayout` 的阈值（200），
  且默认 stabilization 迭代次数多，`stabilizationIterationsDone` 事件未及时
  触发，pyvis 模板绑定的隐藏 loadingBar 逻辑没有执行（画布其实已在渲染）。
- **解决**：导出时 `set_options` 关闭 `improvedLayout` 并将 stabilization
  迭代降为 200；截图前再用 JS 将 `#loadingBar` 置为 `display:none` 兜底。

## 问题 13：RAGAS 检索精度口径修正

- **现象**：初版把 LightRAG 返回的 8 段结构化上下文（实体标题、实体/关系
  JSON 块、参考文档标题等）整体当作检索证据单元，导致 context_precision
  被系统性低估（0.2855），与传统 RAG 的"纯文本块"口径不一致。
- **解决**：编写 `reeval_ragas.py`，两链路统一只基于 **Sources 源文本块**
  评分（LightRAG 从 reference_id/content 块提取 Top-8，剔除实体/关系/标题）；
  faithfulness 仍基于完整上下文；图实体/图关系命中作为 `graph_evidence`
  单独展示。修正后 LightRAG context_precision 由 0.2855 提升至 0.3521。

> 上更完整、性价比更高；LightRAG 答案忠实度更高、在跨期数据汇总（Q260）上
> 答案更完整，并额外产出 3677 节点 / 5862 边的可交互领域知识图谱，优势集中在
