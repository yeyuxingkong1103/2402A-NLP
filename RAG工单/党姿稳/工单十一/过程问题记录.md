## 问题 1：Windows 控制台中文日志抛 UnicodeEncodeError

**现象**：脚本一启动就抛 `UnicodeEncodeError: 'gbk' codec can't encode character`，日志无法打印。

**原因**：Windows 控制台默认使用 GBK 编码，而日志中含 `：`、`（` 等字符与部分年报用字不在 GBK 覆盖范围内；脚本通过重定向写文件时编码也不会自动变成 UTF-8。

**处理**：在 `config.py` 顶部对 `sys.stdout` 与 `sys.stderr` 统一执行 `reconfigure(encoding="utf-8", errors="replace")`，并用 `hasattr` 兼容不支持该方法的流对象。此后所有模块 `import config` 即自动生效。

## 问题 2：大模型返回的 JSON 解析失败（Extra data）

**现象**：生成问答对时反复报 `json.JSONDecodeError: Extra data: line 1 column 78`，大量问答对被判为无效丢弃。

**原因**：原解析逻辑在去除 ```` ```json ```` 围栏后，**先找 `{` 再找 `}`**。而模型这次返回的是 `[{...}, {...}]` 数组，于是被切成 `{...},{...}`，多出一个 `,{...}` 即为 "Extra data"。

**处理**：改写 `llm_client.chat_json`，改为三段式容错解析：

1. 先对整段文本做一次 `json.loads`（覆盖绝大多数正常返回）；
2. 失败则枚举 `("[", "]")` 与 `("{", "}")` 两组括号对，按起始位置排序后逐个截取候选片段重试；
3. 全部失败才返回 `None`，并打印前 120 字原文便于排查。

修复后问答对生成不再出现无谓丢弃。

## 问题 3：`model.fit()` 报 `NameError: name 'Dataset' is not defined`（**本次微调最核心的阻塞**）

**现象**：损失函数、数据加载器、训练参数全部构造成功，进入 `model.fit()` 后立即报错：

```
File "sentence_transformers/fit_mixin.py", line 264, in ...
    NameError: name 'Dataset' is not defined
```

**原因**：本机 sentence-transformers 3.2.1 的 `fit()` 内部依赖 HuggingFace `datasets` 包的 `Dataset` 类，而该包未安装（工单要求复用已装环境）。

**为什么没有直接安装 `datasets`**：试探性 dry-run `pip install datasets==2.18.0` 会连带把 `fsspec` 从 2025.3.0 **降级**到 2024.2.0。已验收的工单九、工单十都跑在这套环境上，为一个训练入口去改动它们的依赖风险不对等。

**处理**：不使用 `model.fit()`，改为在 `train_model.py` 中自实现等价的 **PyTorch 训练循环**：

- `torch.optim.AdamW(model.parameters(), lr=2e-5)` 对应原 `optimizer_params`；
- `transformers.get_linear_schedule_with_warmup` 对应原 `scheduler="warmuplinear"`，预热步数按 `总步数 × warmup_ratio` 换算；
- 每批先用 `model.tokenize()` 把三元组的三列文本分别分词，组成 `[锚点特征, 正例特征, 负例特征]` 交给损失函数；
- 保留原有的 `measure_triplet_loss`（训练前后各测一次 768 维三元组损失）、逐轮损失记录与 `data/train_log.json` 落盘。

训练日志中新增 `"trainer": "manual_torch_loop"` 字段，明确记录本次训练不是通过 `fit()` 完成的。

## 问题 4：`TripletLoss.forward()` 缺少位置参数 `labels`

**现象**：自实现循环中调用 `loss(feats)` 抛 `TypeError: forward() missing 1 required positional argument: 'labels'`。

**原因**：sentence-transformers 3.2.1 中 `TripletLoss.forward(self, sentence_features, labels)` 把 `labels` 声明为**必填位置参数**，尽管三元组损失本身不使用标签。

**处理**：调用时显式传入 `criterion(feats, labels=None)`。已先写探针脚本验证：前向得到损失值、`backward()` 成功、参数梯度非零（`grad_sum ≈ 19283`），确认整条反向链路可用后才改主流程。

---

## 问题 5：DataLoader 默认 collate 无法处理 `InputExample`

**现象**：训练循环第一行 `for step, batch in enumerate(loader)` 就报：

```
TypeError: default_collate: batch must contain tensors, numpy arrays, numbers,
dicts or lists; found <class 'sentence_transformers.readers.InputExample.InputExample'>
```

**原因**：`InputExample` 是自定义对象，PyTorch 的 `default_collate` 不认识它（原 `model.fit()` 内部用的是自己的 collate 实现，所以此前没暴露）。

**处理**：给 `DataLoader` 传入直通 collate 函数 `keep_batch(batch)`，原样返回样本列表，由训练循环自行按 `texts[0] / texts[1] / texts[2]` 拆成三列。

## 问题 6：`run_eval.py` 直接运行是"静默空转"

**现象**：`python run_eval.py` 退出码 0，但没有任何输出，`data/eval_result.json` 也没有生成。

**原因**：该文件只定义了 `run()` 函数，被 `run_all.py` 以 `import run_eval; run_eval.run()` 方式调用，**文件末尾缺少 `if __name__ == "__main__":` 入口**。因此直接执行时只是完成了一次模块定义，函数从未被调用。

**处理**：补上 `__main__` 入口。同时排查了其余模块：`gen_dataset.py`、`build_dataset.py`、`train_model.py` 均有入口；`corpus.py`、`embedder.py`、`llm_client.py`、`evaluator.py` 是被其他模块复用的工具模块，直接执行不产生副作用也不报错。

## 问题 7：`evaluators` 模块导入失败

**现象**：按官方文档写 `from sentence_transformers import evaluators` 抛 `ImportError`。

**原因**：sentence-transformers 3.2.1 中该模块位置为 `sentence_transformers.evaluation`，旧路径不再导出。

**处理**：改用 `from sentence_transformers.evaluation import ...`。本次检索评估为自实现的 `RetrievalEvaluator`（指标口径需与工单要求对齐），该导入仅用于确认环境接口。

## 问题 8：`model.tokenize()` 的返回结构不是"每个文本一个 dict"

**现象**：最初按 `[model.tokenize(a), model.tokenize(b), model.tokenize(c)]` 逐条分词，得到的结构与损失函数期望的输入对不上。

**原因**：`tokenize()` 接收的是**文本列表**，返回**一个**批量字典（内部各张量带 batch 维度），而不是逐条结果组成的列表。

**处理**：正确形式是按"列"分词 —— `feats = [model.tokenize(锚点列表), model.tokenize(正例列表), model.tokenize(负例列表)]`，得到一个长度 3 的列表。探针验证：2 条样本的一批得到张量形状 `[(2,5), (2,7), (2,7)]`，与 `TripletLoss` 期望的 `sentence_features` 结构一致。

## 问题 9：训练损失（1.48）大于评测损失（0.52），一度怀疑训练出错

**现象**：微调前手工测得的三元组损失是 `0.521756`，但训练第 1 轮的平均损失却是 `1.481549`，几乎翻了三倍，看起来像损失在"变差"。

**原因**：两者口径不同，不是同一件事：

- 训练用的是 **MatryoshkaLoss**，即 `TripletLoss` 在 `768 / 384 / 192` 三档截断维度上的**均值**。192 维截断表示的区分能力天然弱于 768 维，其三元组损失显著偏高，把均值整体拉大；
- `measure_triplet_loss` 只在 **768 维**上按 `max(0, d(a,p) − d(a,n) + margin)` 计算，且只在未打乱的前 64 条样本上、以 eval 模式（关闭 dropout）测量。

**处理**：不改代码，改为在报告中显式区分两个口径，并同时给出同口径的前后对比：`0.521756 → 0.342153`，**下降 0.179603**。同口径下损失确实下降，训练是有效的。

## 问题 10：平均排名（mean_rank）指标恶化

**现象**：微调后 Recall@1/5/10、MRR、nDCG@10 共 5 项指标全部改善，唯独平均排名从 `22.92` 恶化到 `150.58`。

**原因**：平均排名是重尾指标。逐题核对发现，全部恶化量由 **3 条招商证券"利润分配"问题**贡献（排名 `0/5/6` 分别掉到 `1444/1343/1419`）。这 3 条问题的答案落在年报中版面结构高度雷同的"利润分配"段落上，微调在整体拉高同名指标区分度的同时，把这少数样本推得更深，从而主导了均值。

**处理**：不修改指标定义、不做样本剔除（那会掩盖真实结果）。改为补充两个更稳健的分布指标一并报告：

| 观察项 | 微调前 | 微调后 |
| --- | --- | --- |
| 排名中位数 | 4.0 | 4.0 |
| 排名 < 10 的问题数 | 23 / 36 | 26 / 36 |

中位数持平、进入前 10 的问题数增加，说明微调是净改善的，均值恶化由 3 条异常样本造成。该分析已写入 `微调报告.md` 第六节。
