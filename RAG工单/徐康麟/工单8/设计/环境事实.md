## 3. 内存约束（★ 本工单最关键的实测事实）

### 3.1 事故背景

本轮施工期间，机器曾因**并行任务过多**出现提交内存 45.89/47.77 GB ≈ 96% 的 OOM 事故
（PowerShell 启动失败、浏览器标签被顶崩、子代理以 `0xC0000409` FailFast 退出）。
`_共享约定.md` 因此新增 §5.5 资源纪律，本工单全程遵守。

### 3.2 内存受限下的 `MemoryError` 与修复（实测记录）

**症状**：加载 工单7 索引时抛

```
numpy.core._exceptions._ArrayMemoryError: Unable to allocate 34.6 MiB
for an array with shape (8847, 1024) and data type float32
  File "研发/app/core/vector_store.py", line 102, in try_build_faiss
    matrix = l2_normalize(vectors)
```

**根因（两层）**：

1. `faiss.read_index` 在本机**非 ASCII 路径**（`E:\gao6gongdan\工单8\...`）上必然失败
   （faiss 1.7.4 C++ 侧窄字符 `fopen`，报 `could not open ... No such file or directory`），
   于是走回落路径 `np.frombuffer(path.read_bytes())` —— 这一步会把 **36 MB 文件整读成 Python bytes**；
2. 回落路径失败后还会调用 `try_build_faiss` 现场重建索引，等于**再复制一份 l2 归一化矩阵 + IndexFlatIP**。
   在可用内存仅约 300 MB 的当时，chunks 表（8847 条）+ bm25.pkl + vectors.npy 已占约 120 MB，
   任何一次 36 MB 的额外分配都会失败。

**修复（已落地在 `研发/app/core/vector_store.py`，并注明工单8 增补）**：

| 修复 | 做法 | 效果（实测） |
| --- | --- | --- |
| ① 零拷贝反序列化 | `np.memmap(path, dtype=np.uint8, mode="r")` 替代 `path.read_bytes()` | 省掉 36 MB Python 副本；在 150 MB 内存压力下仍能成功加载 FAISS |
| ② 构建前内存探测 | `_memory_headroom_mb()` 试分配 64 MB，余量 < `FAISS_BUILD_MIN_HEADROOM_MB`(120 MB) 时**跳过重建** | 退回 numpy 精确检索（与 IndexFlatIP 内积等价），不再抛 MemoryError |
| ③ 日志留痕 | `vector.faiss_build_skipped` 记录实测余量与退回动作 | 可审计，不静默降级 |

**结果**：内存恢复后实测 `load_bundle()` 成功，`faiss=True`，耗时 **4.3 s**（8847 块）。

### 3.4 越界写入 工单7 的实测事故与修复（**必须记录**）

**现象**：施工中发现 `E:\gao6gongdan\工单7\` 下有被本工单进程写入的文件：

| 文件 | 写入时间 | 原因 |
| --- | --- | --- |
| `工单7\研发\data\index\qa_runtime.sqlite3` | 2026-10-12 19:54~20:08 | `研发/app/main.py`（从 工单7 复制的 CLI）用 `Path(cfg.paths.index_dir)/"qa_runtime.sqlite3"` 建运行期数据库，而本工单的 `RAG_DATA__INDEX_DIR` 指向**只读的 工单7 索引目录** ⇒ 库文件落到了 工单7 |
| `工单7\部署\日志\app.log` / `rag_trace.jsonl` | 2026-10-12 19:57:49（**经核实由 工单7 自己的进程写入**，此后未再变化） | 无 —— 但风险真实存在：`app/core` 副本默认会按 工单7 路径写日志 |

**根因**：`app/core/config.py` 的 `REPO_ROOT` 是按**文件位置**算的（`parents[3]`），
而 `研发/app/core/**`、`研发/app/storage/**` 是从 工单7 复制来的副本 ——
不显式覆盖 `RAG_LOG__DIR` 与运行期数据目录，它们就会按 工单7 的路径去写。

**修复（已落地）**：

1. `研发/app/main.py`：运行期 SQLite 改写到 `研发/data/runtime/qa_runtime.sqlite3`（本工单内）；
2. `研发/app/graphrag/engine.py`：`DEFAULT_ENV` 增加 `RAG_LOG__DIR` → 本工单 `部署/日志`，
   检索/生成层的结构化日志不再落到 工单7；
3. `研发/评估/run_eval.py`：`setup_logging()` 之前强制设置 `RAG_LOG__DIR` 与 `RAG_DATA__INDEX_DIR`。

**验证**：修复后重跑评估烟测，比对 `工单7\部署\日志\app.log` 的 `LastWriteTime` ——
运行前后均为 `2026-10-12 19:57:49`（**未再写入**），同时本工单 `部署\日志\app.log` 正常增长。

**残留说明**：`工单7\研发\data\index\qa_runtime.sqlite3` 由事故期写入，**未删除** ——
按「工单7 只读」纪律，本工单不对其做任何修改（删除同样属于修改）；该文件是 工单7 的运行期缓存，
其索引数据（`chunks_indexed.jsonl` / `vectors.npy` / `faiss.index`）与冻结评估结果
（`工单7\测试\测试数据\*`）**均未被触碰**。
